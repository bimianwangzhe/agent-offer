# 工具清单减肥与分层路由

## 场景提问

你给 Agent 接的工具越来越多：查订单、改地址、申请退款、查库存、锁库存、改手机号、查积分、查运单、拦截包裹、建工单……不知不觉攒到二十几个。图省事，你每轮都把这一整份工具清单原封不动地放进请求里。很快怪事来了：用户明明只是问「我的快递到哪了」，模型却挑了个「申请退款」去调；参数也开始张冠李戴，把订单号填进了运单号的位置。账单还一天比一天高，明明没多干活。你把提示词改了又改，反复强调「看清楚再选工具」，时好时坏。到底是模型变笨了，还是哪里没做对？

## 破误解

**不是模型退化，是把「可选工具的清单」当成了「可以无限堆的免费摆设」，一次性把几十份互相干扰的工具定义全塞进了同一轮请求。**

先把一件事说透：函数调用（Function Calling，让模型不直接给自然语言答案，而是输出「要调哪个工具、传什么参数」这样一份结构化请求的能力）在发起时，需要把每个可用工具的名字、用途描述、参数结构描述（schema，结构描述，用来声明一个工具收哪些字段、各是什么类型）一并交给模型。这份清单不是免费的：它按 token（词元，模型读写文本的最小单位，也是计费口径）计费，每轮都要重新付一遍；更要紧的是，它不是「摆着不看」——模型得在这几十份描述里逐一比对，才能决定此刻该用哪一个。清单越长，彼此长得越像，注意力被摊得越薄，挑错的概率就上升。于是出现了开头那种「问快递却点了退款」的错选：不是模型不认识字，是你给它的候选项里，塞了太多此刻根本不该出现的干扰项。真正的解法不是继续加提示词求它「仔细点」，而是给清单减肥——让每一轮只出现与当前意图相关的那几个工具。这篇讲的就是最常用的一招：分层路由（routing，先按大类分流，再只展开被选中的那一类），把「一次性全给」改成「先选领域、再挂载该领域的工具」。

## 生活类比

把它想成去一家大型医院看病。医院有几百个科室、上千名医生，如果导诊台把「全院所有科室和每位医生的详细说明」厚厚一摞全塞给你，让你自己从中挑该找谁，你多半会挑花眼，甚至走错楼层。真实的分诊不是这么干的：门口先有一张极简的分诊牌，只列几个大类——内科、外科、五官、急诊，你先说自己哪儿不舒服，护士据此判断该去哪个大类；到了对应楼层，墙上才贴着这一层那几位医生的具体介绍，你再从这几个人里选。

对应关系很具体：那张只列大类的分诊牌，就是第一层的「领域目录」——它只写「订单」「库存」「账户」「物流」「售后」这类粗粒度名字加一句用途，短到可以忽略成本；护士按症状判断大类，就是「按用户这句话的意图路由到一两个领域」；那一层楼里贴的几位医生介绍，就是第二层「只在命中领域后才展开的具体工具定义」；你最终从这几位里挑一个，就是模型在当前这一小份工具集里选出真正要调的那个。这个比喻还点出两处容易被忽略的细节：其一，分诊牌必须常驻、且永远极短，否则「减肥」就白费了；其二，最怕的不是分错一次，而是有人嫌麻烦干脆撤掉分诊、让病人抱着全院名录自己翻——那正是「每轮把全部工具塞进请求」的做法。还有一层：万一护士一时判断不出该去哪个大类，稳妥的做法不是把所有医生全叫过来，而是先请病人把症状说得更具体一点、或由人补一句方向，再重新分诊——这就是「未知意图时只给目录、请上层补选领域」的兜底。

## 自绘示意图

:::figure 分层路由的一轮顺序
@flow
问题进来|先看领域目录|命中一两个领域|只挂载该域工具|模型从中选一个
:::

这五格的关键在「先」与「只」。「先看领域目录」意味着模型第一步面对的是极短的大类清单，而不是几十份工具描述；「只挂载该域工具」意味着这一轮真正进请求的，只有命中领域那几份。两处一掐，可选集就从几十骤降到个位数，错选与开销同时被压下去。

:::figure 分层路由要备好的两层和三道约束
@stack
第一层 领域目录::只列大类与一句用途，常驻且极短
第二层 领域工具::命中领域后才展开的具体工具定义
命中上限::一次最多展开两个领域，防止并集膨胀
未知兜底::没命中就停在目录，请上层补选领域
成本代理::用本轮挂载的工具数估算这一轮开销
:::

五格里最容易漏的是「命中上限」和「未知兜底」。前者管住「一句话跨好几个领域」时不至于把清单又撑回全量；后者管住「一时判断不出」时不会慌慌张张把所有工具都摊开。至于「成本代理」，是提醒你别凭感觉说「好像省了」，而是拿本轮真实挂载的工具数去度量，让减肥效果可验证。

:::figure 两种做法的差别
@compare
全量平铺::每轮都带全部工具|可选集太大易挑错|描述文本线性烧钱
分层路由::先选领域再挂载|本轮可选集很小|无关工具不进请求
:::

左边是「攒了一堆工具就整份塞进去」的朴素做法，工具少时最省事；右边是把可用工具当成随意图变化的动态集合。二者的差距，不在某一轮谁更聪明，而在「工具数量往上长」时，哪一边不会跟着一起劣化。

## 层层追问

:::ask 那如果用户一句话跨了两个领域，比如「快递太慢想投诉，顺便把订单地址也改了」呢？
:::

这正是分层路由必须提前想清楚的情形，处理不好就会退化回全量。合理的做法是允许一次命中多个领域，把它们的工具取并集作为这一轮的工具集，但要给「最多几个领域」设一道硬上限，比如两个。为什么设上限？因为每多命中一个领域，就多挂一整组工具，跨三四个领域时并集几乎等于全量，减肥就名存实亡了；遇到真要跨很多领域的复杂请求，更稳的是让 Agent 拆成几步、每步各自路由，而不是一轮里全铺开——这与 [Agent 的唯一判据](./k021-agent-criterion.md) 里「能不能自己决定下一步做什么」是同一条思路。还有个细节：多领域并集里，同名或近义的工具容易撞车（「查单」「查询」「详情」分属不同领域），这时候靠 [工具描述写法](./k033-tool-description.md) 把每个工具的适用边界写死就格外重要，否则挂载得再少，模型照样在两个相似名字之间选错。所以「跨域」不是难题，难题是「跨域之后还能不能守住小集合」：靠领域上限、靠描述去歧义、靠必要时拆步，三样一起才成立。

:::ask 那如果路由本身判错了领域，把该给的工具藏起来了，模型不就巧妇难为无米之炊吗？
:::

这是比跨域更隐蔽、也更贵的一问，因为它把「减肥」变成了「误删」。要分清两种「判错」：一种是完全没命中关键词，这时别硬塞全部工具，正确做法是停在第一层，只把领域目录交给上层（让模型或规则补一句方向），再重路由一次，演示代码里的 `need_domain_choice` 与补选领域就是这个用途；另一种是命中了、但命中的领域不对，这时光靠更精确的词表往往补不回来，得留一条「可观测、可修正」的路子——把「本轮路由到了哪些领域、最终用了哪个工具、任务有没有做成」记进轨迹，事后统计路由命中率，发现某类问法老被分错，就回去修词表或修领域边界，这条闭环在 [Trace 该记什么](./k094-trace-fields.md) 与 [结果评测与轨迹评测](./k089-trajectory-eval.md) 里都绕不开。还有一个容易混淆的点：给工具分层，和 [多模型路由与网关](./k082-model-router.md) 里「把请求分给不同模型」不是一回事，前者分的是「本轮让模型看见哪些工具」，后者分的是「这次交给哪个模型算」，别把两套路由搅成一套。最后一句兜底：领域目录本身要常驻且稳定，别让它也随每轮变化，否则今天能选对的领域明天突然不在目录里，排查起来比工具错选还难，这点和 [前缀缓存与即时注入](./k050-prefix-cache.md) 里「把不变的部分固定在前面」是同一种克制。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一份模拟的工具注册表，完整演示「全量平铺」与「先选领域、再挂载」的差别，以及跨域、上限、未知兜底、补选重路由几种情形，结尾用一组断言逐条验证。路由用可复现的关键词打分，结果能手工推算；复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json


TOOL_CATALOG = {
    "订单": ["查订单", "改地址", "申请退款", "催发货", "开发票"],
    "库存": ["查库存", "锁库存", "补货预警", "查仓库"],
    "账户": ["查资料", "改手机号", "查积分", "冻结账户"],
    "物流": ["查运单", "改派送时间", "查网点", "拦截包裹"],
    "售后": ["建工单", "查工单", "升级投诉", "回访登记"],
}

DOMAIN_CATALOG = [
    {"domain": "订单", "desc": "下单后的订单查询与改动"},
    {"domain": "库存", "desc": "商品库存与仓库情况"},
    {"domain": "账户", "desc": "用户资料与账户状态"},
    {"domain": "物流", "desc": "配送进度与运单"},
    {"domain": "售后", "desc": "工单、投诉与回访"},
]

ROUTE_WORDS = {
    "订单": ["订单", "下单", "退款", "发票"],
    "库存": ["库存", "缺货", "仓库", "补货"],
    "账户": ["手机号", "积分", "资料", "账户"],
    "物流": ["快递", "运单", "派送", "包裹", "物流"],
    "售后": ["投诉", "工单", "回访", "售后"],
}


def route(query, max_domains=2):
    """按关键词给每个领域打分，返回得分最高的若干个领域，结果确定性。"""
    scores = {d: 0 for d in TOOL_CATALOG}
    for domain, words in ROUTE_WORDS.items():
        for w in words:
            if w in query:
                scores[domain] += 1
    hit = [d for d, s in scores.items() if s > 0]
    hit.sort(key=lambda d: (-scores[d], d))
    return hit[:max_domains]


def select_tools(domains):
    """只把命中领域的工具取出来，作为本轮真正交给模型挑选的工具集。"""
    return [{"domain": d, "name": t} for d in domains for t in TOOL_CATALOG[d]]


def build_request(query, extra_domains=None, max_domains=2):
    """组装一轮请求：第一层永远是领域目录，第二层只在命中领域后给出。"""
    domains = route(query, max_domains)
    if extra_domains:
        for d in extra_domains:
            if d in TOOL_CATALOG and d not in domains:
                domains.append(d)
        domains = domains[:max_domains]
    return {
        "level1": DOMAIN_CATALOG,
        "routed_domains": domains,
        "level2": select_tools(domains),
        "need_domain_choice": len(domains) == 0,
    }


def describe_size(obj):
    """用序列化后的字符数当成本代理，衡量这一轮塞给模型的文本量。"""
    return len(json.dumps(obj, ensure_ascii=False, sort_keys=True))


def main():
    full_tools = [{"domain": d, "name": t}
                  for d, ts in TOOL_CATALOG.items() for t in ts]
    full_count = len(full_tools)
    checks = []
    all_in_one = {"level2": full_tools}

    r1 = build_request("我的订单想申请退款")
    checks.append(("单一意图只命中一个领域", r1["routed_domains"] == ["订单"]))
    checks.append(("第一层只是领域目录", len(r1["level1"]) == len(TOOL_CATALOG)))
    checks.append(("目录项不暴露具体工具名",
                   all("name" not in item for item in r1["level1"])))
    checks.append(("本轮工具数远小于全量", 0 < len(r1["level2"]) < full_count))
    checks.append(("本轮工具都属于命中领域",
                   all(t["domain"] == "订单" for t in r1["level2"])))
    checks.append(("分层后文本量明显更小",
                   describe_size(r1["level2"]) < describe_size(all_in_one["level2"])))

    r2 = build_request("物流太慢了想投诉")
    checks.append(("跨域意图命中多个领域", len(r2["routed_domains"]) == 2))
    checks.append(("跨域工具恰是各领域并集",
                   {t["domain"] for t in r2["level2"]} == set(r2["routed_domains"])))

    crowded = build_request("订单 库存 账户 物流 售后")
    checks.append(("领域数受上限约束", len(crowded["routed_domains"]) <= 2))

    r3 = build_request("随便问一句")
    checks.append(("未知意图不硬塞具体工具", r3["level2"] == []))
    checks.append(("未知意图标记需先选领域", r3["need_domain_choice"] is True))
    r3b = build_request("随便问一句", extra_domains=["订单"])
    checks.append(("补选领域后能拿到该域工具",
                   len(r3b["level2"]) == len(TOOL_CATALOG["订单"])))
    checks.append(("补选后不再要求选领域", r3b["need_domain_choice"] is False))

    checks.append(("同一问题路由结果稳定",
                   route("订单退款") == route("订单退款")))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `TOOL_CATALOG` 是模拟的完整工具注册表，五个领域共二十一个工具；`DOMAIN_CATALOG` 是那张极短的分诊牌，每个领域只有名字和一句用途，刻意不含任何具体工具名；`ROUTE_WORDS` 是路由用的关键词表。三份数据把「全量」「目录」「怎么分」分开摆，便于后面逐项对比。
2. `route` 给每个领域打分：某领域的关键词在问题里出现一次就加一分，只留得分大于零的领域，按「分数从高到低、同分按领域名」排序后截取前 `max_domains` 个。排序里带上领域名这个固定次序，是为了让同分时结果仍然确定、可复现，不会这次和下次不一样。
3. `select_tools` 是「减肥」真正发生的地方：它只把命中领域的工具展开成 `{领域, 名字}` 列表。命中一个领域，本轮就只有那几个工具；一个都没命中，返回的就是空列表。
4. `build_request` 组装一轮请求，`level1` 永远给领域目录、`level2` 只放命中领域的工具。`extra_domains` 表示「路由没把握时由上层补选的领域」，用来模拟补一句方向后重新分诊；`need_domain_choice` 在没有任何命中时为真，等于告诉调用方「先选个领域，别急着要具体工具」。
5. `describe_size` 用序列化成 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）后的字符数当成本代理。`main` 里把「整份二十一个工具」与「本轮只挂五个工具」各序列化一次比长度，让「减肥」这件事有个可断言的度量，而不是停留在感觉。
6. `main` 逐组断言：单一意图只命中一个领域、本轮工具都来自该领域且远少于全量、文本量更小；跨域时能命中两个领域且工具恰是并集；一句话点满五个领域时领域数被上限压住；未知意图不塞任何具体工具并标记「需先选领域」，补选后能拿到该域工具；最后验证同一问题两次路由结果一致。
7. 结尾把每条性质的通过与否打成一行，汇总成 `通过 N/N 项` 并 `assert` 全部成立，任何一条被破坏都会以非零状态退出。这里用关键词打分代替了真实系统里的向量检索或小模型分类、用字典代替了工具注册中心，全是为了让整条链路不联网、不依赖账号就能独立跑通并手算验证；它演示的是分层挂载与几道约束的顺序，不是任何具体平台的实现。

## 踩坑与边界

- **整份清单每轮全带**：现象是工具越接越多，错选越来越频繁、账单跟着涨 → 原因是把工具清单当成一次性写死的静态配置、每轮原样重发 → 改成随意图动态挂载，第一层只给领域目录，命中后再展开具体工具。
- **领域边界互相重叠**：现象是「查单」「查询」「详情」这类近义工具分在不同领域，挂载得再少模型仍选错 → 原因是只按名字分层、没写清各自适用边界 → 先把领域划成互斥的几类，再用 [工具描述写法](./k033-tool-description.md) 把每个工具的「什么时候用、什么时候别用」写死。
- **跨域请求把清单撑回全量**：现象是一句话牵扯四五个领域，一轮下来挂载量几乎等于全量 → 原因是没给「最多命中几个领域」设硬上限 → 设上限，超出的复杂请求拆成几步各自路由，别指望一轮全铺开。
- **未知意图慌忙回退全量**：现象是路由没命中时，代码图省事直接把所有工具塞回去，等于减肥白做 → 原因是没设计「停在目录」这一档 → 没命中就只给领域目录并标记需补选，由上层补一句方向后重路由，参考 [三类能力原语与渐进披露](./k079-primitives-skills.md) 里「用到才展开」的思路。
- **路由结果不留痕**：现象是某些问法老被分错领域，却始终说不清错在哪、改了有没有变好 → 原因是路由命中与否、最终用了哪个工具都没记进轨迹 → 把「路由到哪些领域、用了哪个工具、任务是否做成」写进可回放的记录，按 [Trace 该记什么](./k094-trace-fields.md) 的思路统计命中率再回修词表。

还要分清两件事：分层路由减的是「本轮让模型看见多少工具定义」，它和 [上下文预算表](./k041-context-budget.md) 里管「整段输入占多少 token」是两笔账，前者瘦身后照样可能有很长的对话历史，别以为工具减肥了整体就一定不超 [上下文窗口](./k003-context-window.md)；它和 [一次请求拆成五块](./k008-request-anatomy.md) 里「工具定义只是请求的一部分」也对得上——减肥动的正是这一块，其它几块该占多少还是多少。另外，把不随意图变化的那张领域目录固定在请求最前面、每轮复用，除了省事，也顺带对 [前缀缓存与即时注入](./k050-prefix-cache.md) 友好；而工具描述本身写得含糊、参数结构描述定义得别扭，属于 [工具 Schema 设计](./k032-tool-schema.md) 要管的事，分层路由救不了描述质量。若想从整体上看这套教程怎么组织，可以回到 [从这里开始](./00-start-here.md)。

:::check 学完自检
- [ ] 能说清为什么「每轮把全部工具塞进请求」会同时抬高成本、摊薄注意力、诱发错选
- [ ] 能徒手画出「领域目录 → 命中一两个领域 → 只挂载该域工具 → 模型从中选」的顺序
- [ ] 能解释跨域请求为什么要设「最多几个领域」的上限，超了该怎么拆
- [ ] 能判断「路由没命中」时正确兜底是停在目录、补选重路由，而不是退回全量
- [ ] 能区分工具分层路由与多模型路由，也说得清它和上下文预算各管哪笔账
:::

## 三句话小结

工具清单减肥与分层路由，是把「每轮把几十份工具定义整份交给模型」改成「先按意图挑出一两个领域、只把这几个领域的工具挂进本轮请求」的动态做法。

关键做法是常驻一张极短的领域目录、命中后才展开具体工具、给跨域设领域上限、未知意图只给目录并补选重路由，再把路由命中率记进轨迹持续回修。

当系统只有寥寥几个互不相似的工具、或任务压根不靠模型挑工具而是固定编排好的时候，不必硬加这一层；但只要工具数量会往上长、且由模型自主决定调哪个，清单就该随意图瘦下来。

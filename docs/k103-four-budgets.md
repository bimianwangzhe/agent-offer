# 四重预算

## 一、场景提问

一个任务卡住了：它明明已经收集到足够的信息，却在一轮又一轮里反复调用同一个工具，跑了几十轮才被你手动掐掉。账单出来吓一跳，上下文越堆越厚，中间还重复发了两封本不该发的通知。你翻代码，发现「最多跑 N 轮」其实是设了的——只不过设的是轮次，这一趟每轮塞进去的内容翻了倍、单步等了很久、还顺手做了好几个动作，轮次没超，别的三样全失控了。更无奈的是，等你从监控上看到异常，任务早就跑完了，钱也花掉了。到底该设几道闸，才能在「刚要越线」的那一刻就停住，而不是事后对着账单复盘？

## 二、破误解

**不是设一个「最多几轮」就万事大吉，也不是等跑完再统计有没有超；要给四种彼此独立的资源各设上限，并在每一步开始前预检「加上这一步会不会越线」，任一重将超就当场停。**

先把「四重」说清，它们防的是四种不同的失控。步数预算（也叫轮次预算，一次任务最多走几步、循环最多转几圈）防的是停不下来的死循环，判定什么时候该收手可对照 [停止条件](./k028-stop-conditions.md) 与 [循环状态](./k027-loop-state.md)。词元预算（Token，模型处理文本按词元计量，是上下文占用和计费的基本单位；这里指一次任务累计的输入加输出词元上限）防的是上下文越堆越厚、账单悄悄膨胀，见 [上下文预算](./k041-context-budget.md) 与 [用量与计费](./k010-usage-billing.md)。时间预算（一次任务最多占用多长的墙钟时间）防的是某一步卡在等待上、迟迟不返回，超时怎么处理见 [超时兜底](./k109-timeout-fallback.md)。动作预算（一次任务里工具调用尤其高风险动作最多发生几次）防的是副作用扩散——反复重试、重复发通知、连续改动数据，见 [幂等键](./k038-idempotency-key.md) 与 [人在回路与高风险确认](./k102-human-in-loop.md)。

关键在于「独立」二字：这四样不能互相挪用，钱没花完不代表可以无限等，轮次没到顶不代表能塞进任意长的内容。所以任何一重将越线都要停，而不是等四重都用满。第二个关键是「预检」：判据是「当前用量 + 这一步的预估 > 上限」，在动作发生之前算，而不是等动作做完了再记账——事后统计只能告诉你「刚才超了」，拦不住已经产生的花费和已经发出去的通知。第三个关键是「越线不等于崩掉」：停下来的同时要保住已经完成的部分结果，写清楚是因为哪一重停的，让任务能体面收尾、能被接着往下做，见 [优雅恢复](./k110-graceful-resume.md)。这三条合起来，才把「预算」从一个被动的统计数字变成一道主动的护栏；真正的拦截动作必须落在代码里，不能只写在提示词里，见 [代码内护栏](./k106-guardrail-in-code.md)。

## 三、生活类比

把它想成一家四口自驾出游，出发前在便签上写死四件事：钱包里带多少现金、天黑前必须到家、最多安排几个落脚点、一路上最多做几件「订了就不能退」的事。路上每想加一个景点，先掏便签核一遍：加油和过路费是不是要超钱包、加上这一站会不会赶不回家、落脚点是不是已经满了、这站又要订一间不可退的房。哪一样先见底，就照着它收尾返程，而不是硬撑到天黑或把钱花光。

对应关系很具体。「钱包里的现金」是词元与成本预算，每次加油、每段过路都从同一个钱包扣，不能因为「这一站便宜」就忘了前面花过多少；「天黑前到家」是时间预算，钱没花完也不能拿它换时间；「最多几个落脚点」是步数预算，绕得再顺也不会无限加站；「最多做几件不可退的事」是动作预算，专管那些做了收不回来的决定。而「每加一站先核便签」正是每步前置预检，「哪样先见底就收尾」正是四重独立、任一越线即停。

这个类比还点出两处容易被忽略的细节。第一，便签是出发前写好、全车人都能看见的，不是开到半路才有人嘀咕「好像钱不太够」——预算要写进可查的配置、越线要留痕，事后能回答「当时上限是多少、因为哪一样停的」，见 [Trace 该记什么](./k094-trace-fields.md)。第二，返程不等于这趟白跑了：已经去过的几个景点、拍过的照片照样带回家——越线要保住部分结果，而不是把整趟推翻。还有一层：同行的人各自记各自的账最容易乱，得由一个人统一记，这正对应「预算要在同一个账本上累计」，后面会展开。

## 四、自绘示意图

:::figure 每一步开始前的四重预检
@flow
准备下一步|四项逐一预检|任一将超则停|带部分结果收尾|写留痕可查
:::

五格里「四项逐一预检」必须发生在「准备下一步」之后、真正执行之前，而且四项是并列的检查、不是层层递进的四个阶段——任何一项不过就直达「任一将超则停」。「带部分结果收尾」和「写留痕可查」是两件事：前者保住已有产物，后者记下停在哪个上限上，缺了前者任务白跑，缺了后者事后查不出为什么停。

:::figure 四重预算各自管什么
@stack
步数预算::最多走几步、循环几圈，防停不下来的死循环
词元预算::累计输入加输出词元上限，防上下文膨胀与账单
时间预算::墙钟耗时上限，防某一步卡在等待上不返回
动作预算::工具调用与高风险动作次数，防副作用扩散
前置预检::用当前用量加本步预估去比，不做事后统计
越线收尾::保住已完成结果，写明因哪一重停，留痕可查
:::

六行里前四行是四道独立的上限，后两行是让它们真正生效的两条纪律。把「前置预检」和「越线收尾」也列进图里，是因为只写上四个数字、不写怎么用，最容易退化成一段没人调用的常量。四重数值该定多少、按哪类任务分档，可以对照 [成本清单](./k116-cost-checklist.md) 与 [健康检查与 SLO](./k114-health-slo.md) 里给目标定可守护的线那套思路。

:::figure 两种设闸方式的差别
@compare
只设轮次上限::其余三重失控|绕远路照样贵|超时仍卡死
四重同时预检::各维独立封顶|越线体面收尾|重试也计入
:::

左边不是「设得不够严」——轮次卡到再紧，也管不到单步塞了多少内容、等了多久、顺手做了几个动作。右边把四种资源分别封顶，才让「绕远路」「卡住」「反复重试」这三类各有各的刹车。

## 五、层层追问

:::ask 那如果四重都设了，某个任务确实需要多走几步才能做完，是不是被卡死了？
:::

预算是上限，不是目标，也没规定所有任务用同一档。合理的做法是按任务类型分档：只做一次查询的任务给得紧一些，需要多轮检索与核对的任务给得宽一些，档位和上限都写进配置，别散落在代码各处各写一份。更要紧的是把「体面收尾」做扎实：越线时保留已经完成的步骤与中间产物、写明停在哪一重，让人或后续任务能接着往下走，而不是整趟推倒重来，恢复与断点见 [优雅恢复](./k110-graceful-resume.md)。再追一层：那能不能超了之后自动加一点额度、接着把任务跑完？不能由模型自己续。预算之所以是护栏，就因为它是外部定死的线；若允许「快到了就自己抬一抬」，等于把闸门的钥匙交给了被约束的那一方，任何一次「就差一步」都能把上限顶穿，这类绕过与 [持久化后门](./k147-persistent-backdoor.md) 是同一类问题。真要加，得走显式的路径：留痕说明为什么不够、由人确认后另起一个任务并给新账本，见 [人在回路与高风险确认](./k102-human-in-loop.md)；反复触线则说明档位本身定得不合实际，该改的是配置，而不是让单次任务破例。熔断与重试的关系见 [熔断器](./k104-circuit-breaker.md) 与 [重试与退避](./k108-retry-backoff.md)。

:::ask 那如果重试、并发分支、子任务各自算各自的，总量会不会失控？
:::

会，而且这是比「忘设某一重」更隐蔽的漏法。每个分支各自从零计数，看起来都没超，合起来却可能翻倍：主任务走四步、两个并发分支各走四步、再加重试几轮，总消耗远不是单个账本上的那个数。所以预算要在同一个账本上累计，所有步骤、重试、子任务都往同一处加减，不能各数各的；并发下谁先扣、怎么避免扣重，见 [并发](./k115-concurrency.md) 与 [会话隔离](./k105-session-isolation.md)。再追一层：多个分支同时来扣同一个账本，扣重了或者扣漏了怎么办？扣减动作本身要幂等——同一笔消耗凭稳定标识只记一次，见 [幂等落盘](./k107-idempotent-persist.md) 与 [超时对账](./k039-timeout-reconcile.md)；预算的读改要作为一个不可拆分的操作完成，避免两个分支同时读到「还剩一格」然后都放过去。还有一处常漏：重试不是免费的，它同样吃步数、词元、时间和动作四重额度，必须当作普通步骤记进同一个账本，否则「失败就重试」会变成绕过预算的捷径。把这些都摊到一次任务的总量上看，才和 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 里「全部消耗摊到成功任务上」的口径对得上；权限范围另由 [最小权限](./k100-least-privilege.md) 管，预算管的是「最多做多少」，不是「允许做什么」。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，实现一套最小的四重预算闸门：四个上限各自独立，每步前用「当前用量 + 本步预估」逐项预检，任一重将越线就停下、保住已完成的部分结果并写出可序列化的留痕。另做一组「只盯轮次」的对照，用来验证单重设闸确实挡不住词元超支。数据全是构造的整数，复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
from dataclasses import dataclass, asdict


@dataclass
class Budget:
    max_steps: int = 6
    max_tokens: int = 900
    max_ms: int = 1200
    max_actions: int = 4
    label: str = "b1"


@dataclass
class Step:
    name: str
    tokens: int
    ms: int
    actions: int = 1


@dataclass
class Usage:
    steps: int = 0
    tokens: int = 0
    ms: int = 0
    actions: int = 0


def exceeded(usage, step, budget):
    """前置预检：假设加上这一步，哪一重会越线就返回它的名字。"""
    if usage.steps + 1 > budget.max_steps:
        return "steps"
    if usage.tokens + step.tokens > budget.max_tokens:
        return "tokens"
    if usage.ms + step.ms > budget.max_ms:
        return "ms"
    if usage.actions + step.actions > budget.max_actions:
        return "actions"
    return ""


def run(plan, budget):
    """逐步前置预检；任一重将越线就停，带部分结果收尾并留痕。"""
    usage = Usage()
    done = []
    stop_reason = "completed"
    for step in plan:
        hit = exceeded(usage, step, budget)
        if hit:
            stop_reason = hit
            break
        usage.steps += 1
        usage.tokens += step.tokens
        usage.ms += step.ms
        usage.actions += step.actions
        done.append(step.name)
    trail = {
        "budget": asdict(budget),
        "usage": asdict(usage),
        "done": done,
        "stop_reason": stop_reason,
    }
    return done, stop_reason, trail


def only_steps(plan, budget):
    """对照组：只盯轮次，其余三重完全不管。"""
    done = []
    tokens = 0
    for step in plan:
        if len(done) + 1 > budget.max_steps:
            break
        tokens += step.tokens
        done.append(step.name)
    return done, tokens


def main():
    checks = []
    b = Budget(max_steps=6, max_tokens=900, max_ms=1200, max_actions=4)

    ok_plan = [Step("s%d" % i, 100, 100, 1) for i in range(4)]
    done, reason, trail = run(ok_plan, b)
    checks.append(("四重都够用时全部走完", reason == "completed" and len(done) == 4))
    checks.append(("累计用量被逐项记下",
                   trail["usage"]["tokens"] == 400 and trail["usage"]["ms"] == 400))

    edge = Budget(max_steps=2, max_tokens=200, max_ms=200, max_actions=2)
    edge_plan = [Step("a", 100, 100, 1), Step("b", 100, 100, 1)]
    done, reason, _ = run(edge_plan, edge)
    checks.append(("恰好用满上限不算越线", reason == "completed" and len(done) == 2))

    cases = [
        ("steps", [Step("s%d" % i, 1, 1, 0) for i in range(7)]),
        ("tokens", [Step("big", 901, 1, 0)]),
        ("ms", [Step("slow", 1, 1201, 0)]),
        ("actions", [Step("many", 1, 1, 5)]),
    ]
    for name, plan in cases:
        _, reason, _ = run(plan, b)
        checks.append(("预算「%s」可独立触发" % name, reason == name))

    over = [Step("a", 100, 100, 1), Step("huge", 5000, 1, 0)]
    done, reason, trail = run(over, b)
    checks.append(("越线那一步根本没被计入",
                   done == ["a"] and trail["usage"]["tokens"] == 100))
    checks.append(("越线原因写明是词元", reason == "tokens"))
    checks.append(("越线仍保留已完成的部分结果", len(done) > 0 and done == ["a"]))

    runaway = [Step("s%d" % i, 400, 10, 0) for i in range(4)]
    only_done, total_tokens = only_steps(runaway, b)
    checks.append(("只盯轮次时步数没超", len(only_done) == 4))
    checks.append(("但词元已远超上限",
                   total_tokens == 1600 and total_tokens > b.max_tokens))
    _, full_reason, _ = run(runaway, b)
    checks.append(("四重预检会在这里拦住", full_reason == "tokens"))

    retries = [Step("call", 100, 100, 1)]
    retries += [Step("retry%d" % i, 100, 100, 1) for i in range(5)]
    _, reason, trail = run(retries, b)
    checks.append(("重试同样消耗预算",
                   reason == "actions" and len(trail["done"]) == 4))

    both = [Step("x", 5000, 5000, 9)]
    _, reason, _ = run(both, b)
    checks.append(("多重同时越线时给出确定的一重", reason == "tokens"))
    checks.append(("留痕含预算用量与停止原因",
                   set(trail) >= {"budget", "usage", "done", "stop_reason"}))
    checks.append(("留痕可序列化往返", json.loads(json.dumps(trail)) == trail))
    checks.append(("预算配置本身可序列化",
                   json.loads(json.dumps(asdict(b)))["max_actions"] == 4))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Budget` 用 `dataclasses` 把四个上限写成一个可序列化的配置对象：`max_steps` 步数、`max_tokens` 词元、`max_ms` 时间（毫秒）、`max_actions` 动作次数，外加一个 `label` 便于区分档位。四个数字并列存在，从结构上就拒绝了「只设一个轮次」那种写法，也方便整份配置写进文件供人查。
2. `Step` 描述一步的预估消耗，`Usage` 记录当前累计用量。二者字段一一对应，预检才能写成「累计 + 预估」这种统一的比较，而不是每重各写一套算式。
3. `exceeded` 是前置预检的全部逻辑：按顺序判断加上这一步后，步数、词元、时间、动作哪一重会超过上限，返回第一个越线的名字；都不超则返回空串。注意比较用的是严格大于，恰好用满不算越线；返回固定顺序，意味着多重同时越线时结果也是确定的、可复现的。
4. `run` 是主循环：每一步先调 `exceeded`，越线就把原因记下并 `break`，这一步**不**计入用量、也不进 `done`；只有检查通过才累加四项计数。循环结束把「配置、用量、已完成步骤、停止原因」打包成 `trail` 返回——这就是「带部分结果收尾」和「越线留痕」两个动作的落点。
5. `only_steps` 是刻意保留的对照组，只检查轮次、完全不管另外三重。它存在的意义不是给出另一套实现，而是让后面能用断言证明「单重设闸确实会漏」，把破误解里那句话验成一条可核对的性质。
6. `main` 前段验证基本性质：四重都够用时四步全走完、累计用量逐项记下；另造一份恰好用满的边界配置，确认「等于上限」不被误判为越线。
7. `cases` 四组计划各自只让一重越线（多走一步、单步塞 901 词元、单步等 1201 毫秒、单步做 5 个动作），逐组断言停止原因正好是那一重。这四条合起来就是「四重彼此独立、任一将超即停」的直接证据。
8. `main` 后段验证边界与配套：越线那一步没被计入、已完成的 `a` 被保住；对照组的四步没超轮次却累计了 1600 词元、而四重预检会在第三步就拦住；连续重试把一个动作次数上限吃满，说明重试不免费；多重同时越线给出确定的一重；最后三条确认留痕齐备、可经 JSON 往返、配置本身也能序列化。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用整数增量代替真实的词元与耗时、用构造的步骤列表代替真实工具调用、用内存对象代替集中式账本，全是为了让「四重独立预检、越线保住部分结果」这条链路不需要联网、账号或第三方包就能独立跑通并手工核对。它演示的是预算的定义、检查时机与收尾顺序，不是任何具体运行平台的实现，也不是对真实系统表现的测量结论。

## 七、踩坑与边界

- **只设一个轮次上限**：现象是轮次没超，词元翻倍、单步卡死、通知重复发 → 原因是四种资源会各自被不同方式耗尽，一道闸管不到另外三样 → 四重分别设上限，任一将越线就停，档位对照 [成本清单](./k116-cost-checklist.md)。
- **事后统计才发现超了**：现象是监控报警时钱已花掉、动作已发出去 → 原因是把预算当成了跑完再算的报表 → 改成每步前的「累计 + 预估」预检，检查不过就不执行那一步，见 [代码内护栏](./k106-guardrail-in-code.md)。
- **重试不计入预算**：现象是「失败就重试」把四重额度悄悄打穿，账本上却看不出来 → 原因是把重试当成免费的额外尝试 → 重试按普通步骤记进同一个账本，见 [重试与退避](./k108-retry-backoff.md) 与 [幂等落盘](./k107-idempotent-persist.md)。
- **越线就抛异常丢弃结果**：现象是任务一超限整趟白跑、前面做过的全没了 → 原因是把越线当成了崩溃 → 停下时保住已完成步骤与中间产物、写明因哪重停，让后续能接着做，见 [优雅降级](./k020-graceful-fallback.md) 与 [优雅恢复](./k110-graceful-resume.md)。
- **各分支各算各的账**：现象是每个并发分支都没超，合起来总量翻倍 → 原因是预算被拆成多份独立计数 → 全任务共用一个账本累计，扣减要幂等，见 [并发](./k115-concurrency.md) 与 [会话隔离](./k105-session-isolation.md)。

还要划清三条边界。第一，预算管「最多做多少」，不管「允许做什么」：动作能不能做由 [权限矩阵](./k037-permission-matrix.md) 与 [最小权限](./k100-least-privilege.md) 决定，高风险动作要不要人点头由 [人在回路与高风险确认](./k102-human-in-loop.md) 决定，沙箱能不能先试由 [沙箱](./k101-sandbox.md) 决定，三者与预算是叠加的几层。第二，预算是自动刹车，不是评测：它不判断结果好不好，只负责在资源将耗尽时收住；「这趟值不值」要用 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 那套口径事后算，而算得出来的前提是 [Trace 该记什么](./k094-trace-fields.md) 里的用量字段当初一条没少记。第三，越线频繁触发说明档位或流程本身有问题，该改的是配置与重试策略，而不是给单次任务破例抬上限——反复触线又不改，跟 [熔断器](./k104-circuit-breaker.md) 反复跳闸却不查根因是同一种毛病。

- [ ] 能解释「前置预检」的判据为什么是「累计 + 本步预估」，而不是事后统计

## 九、三句话小结

四重预算，是给一次任务的步数、词元、时间、动作四种资源各设一道独立上限，任何一重将越线就当场收住，不靠跑完之后的统计补救。

关键做法是把上限写成可查的配置、在每步开始前用「累计 + 预估」逐项预检、越线时保住已完成的部分结果并写明因哪一重停，同时让重试与并发分支都记进同一个账本。

当任务只做一次性的本地计算、既无循环也无外发副作用、资源消耗天然有界时，不必硬套四道闸；但只要一次任务会自主循环、调用工具或反复重试，只盯轮次就一定会被另外三种失控钻空子。

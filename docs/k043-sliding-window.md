# 滑动窗口裁剪：最省事，也最容易弄丢早期约束

## 聊到后面，它把开头的话忘了

你给助手加了个「只保留最近六轮」的设置，长会话果然不再顶满窗口，速度也稳了。可用户聊到第二十轮时问「按我们最开始说好的来」，助手却给出一套完全不同的口径：它把开头声明的「只回答中文、报价一律含税」忘得干干净净，甚至反过来问用户要不要英文。你查了记录，那两句话确实还在数据库里，只是早就没被送进这一轮的输入。

## 先破一个误解

**不是窗口开得太小，是你把「最近」当成了「重要」。**

滑动窗口裁剪的做法很直白：每来一轮新的对话，就把它追加到队尾；一旦总轮数超过设定的条数，就把队首最旧的一轮丢掉。于是窗口里永远是最近那几轮原文，长度恒定、成本可控、实现只要一行切片。这里的「一轮」（turn，指一次用户发言加紧接着的一次回复）是裁剪的最小单位。

问题恰恰出在「恒定」上。它假设了「越新的越要紧、越旧的越可以扔」，可会话开头那几句往往不是闲聊，而是全程生效的规则：语种、口径、身份边界、谈好的价格。这些内容在时间上最旧，在重要性上却最高。滑动窗口分不清这两件事，它只认位置，于是把最该留的先丢了。这就是很多长会话「越聊越不受控」的根子，跟模型记性没关系。

先补一个后面会用到的词：id（identifier，标识），指给每一轮编的号，凭它可以把某一轮单独认出来，而不必靠「第几句」这种会随裁剪变化的位置。

## 用行车记录仪的循环录像来理解

把上下文窗口想成行车记录仪里那张存储卡。容量是固定的，录满了就自动从最旧的一段开始覆盖，新画面不断进来，旧画面不断消失。这套机制便宜、省心、不用你手动整理，正是滑动窗口的好处。

对应关系是这样的：存储卡容量对应上下文窗口；「录满就覆盖最旧」对应超出轮数就丢队首；最近几小时的画面，对应窗口里保留的近期轨迹；而三天前那次轻微剐蹭，对应会话开头谈好的约束——事发当时不觉得要紧，等真要回看时才发现它早被覆盖了。

老师傅会怎么做？给关键片段加个锁，标记为「不参与循环覆盖」。存储卡照旧滚动，但加锁的那几段永远留着。滑动窗口要补的正是这个动作：把少数几条规定单独标记成不参与滚动，其余内容照旧按最近若干轮裁。改动只有几行，效果却是从「必定丢约束」变成「约束不丢、成本仍然很低」。

:::quote
滑动窗口本身没有错，错的是**让它独自承担全部裁剪**。它擅长处理会过期的内容，不擅长处理不过期的内容。
:::

## 把裁剪链路画出来

先看朴素做法每一步在做什么，再对比补了保底之后的差别。

:::figure 朴素滑动窗口的一轮处理
@flow
新轮到达|追加到队尾|超出设定轮数|丢弃最旧一轮|组装本轮输入
:::

五个环节里，第四步是唯一动刀的地方，而它判断「谁该走」的依据只有位置，没有任何关于内容重要性的信息。这就是开头那个故障的成因。

:::figure 两种窗口做法的差别
@compare
只留最近若干轮::成本恒定|实现只需一行|早期约束会丢
最近若干轮加保底::成本仍很低|多几行标记|约束不丢且顺序不乱
:::

:::figure 窗口里该被单独保底的内容
@stack
语种与格式::只回答中文、输出固定结构等全程生效的规则
口径与边界::报价含不含税、能承诺到什么程度
谈定的数值::价格、地址、日期、单号这类会被反复引用的事实
未结事项::上一轮答应过但还没做的事
:::

这四类有个共同点：**都不随时间过期**。它们和「最近三轮说了什么」是两种性质完全不同的信息，本就不该用同一条规则裁。至于这四类之外、又确实需要长期携带的内容，更适合写成紧凑字段，见[结构化状态摘要](./k046-structured-state.md)；而窗口该占多少额度，由[上下文预算表](./k041-context-budget.md)统一划定。

## 再往深问两层

:::ask 那这个「若干轮」到底该取多少？取大了怕超支，取小了怕丢上下文。
:::

没有通用数字，但有个可靠的定法：先按额度倒推，再按内容校验。额度倒推的意思是，从预算表里分给近期轨迹的那一份出发，用它除以单轮平均长度，得到一个大致轮数；内容校验的意思是，拿几段真实长会话手动跑一遍，看在该轮数下有没有把「未结事项」挤出去。两者取更保守的那个。千万别凭「感觉六轮差不多」拍板，因为一旦某轮夹了个很长的工具返回，同样六轮的长度能翻好几倍。

:::ask 再深一层：按轮数切和按字数切，哪个更稳？
:::

按字数切更稳，但要多做一件事。按轮数切的前提是「每轮差不多长」，而现实里一条工具原始返回能顶十几轮闲聊，这个前提很脆；按字数切则是从最新一轮往回累加长度，加到逼近额度就停，不关心一共几轮，天然抗住长短不均。代价是你得给每轮量一次长度，并且仍然要给常驻规则留一条不参与累加的固定份额。两种切法不冲突：先用字数把量卡住，再用轮数当上限兜底，防止出现「一条超长轮把整个窗口独吞」的情况。窗口之外那些被挤出去的内容，若后面还要用，就该压成摘要或外置，分别见[摘要式压缩](./k044-summary-compression.md)与[四层上下文结构](./k042-context-layers.md)。

## 一份能跑的窗口实现

下面这份实现只用标准库和内置函数，把「朴素窗口」「带保底的窗口」「按额度从后往前滚」三种做法放在一起对比，复制成文件直接运行即可。

```python
# sliding.py —— 只用标准库，python sliding.py

def naive_window(turns, keep):
    # 只留最近 keep 轮，最朴素的做法
    return turns[-keep:]


def pinned_window(turns, keep, pinned):
    # 常驻条目单独保底，其余条目按最近 keep 轮滚动，最后按编号复原顺序
    head = [t for t in turns if t["id"] in pinned]
    tail = [t for t in turns if t["id"] not in pinned][-keep:]
    return sorted(head + tail, key=lambda t: t["id"])


def window_by_budget(turns, budget):
    # 从最近一轮往前累加长度，超预算即停；返回仍按原序排列的条目与用量
    picked, used = [], 0
    for t in reversed(turns):
        cost = len(t["text"])
        if used + cost > budget:
            break
        picked.append(t)
        used += cost
    return list(reversed(picked)), used


if __name__ == '__main__':
    turns = [
        {"id": 0, "text": "只回答中文，别改这条", "pinned": True},
        {"id": 1, "text": "好的"},
        {"id": 2, "text": "运费多少"},
        {"id": 3, "text": "包邮"},
        {"id": 4, "text": "几天到"},
        {"id": 5, "text": "三天"},
        {"id": 6, "text": "能改地址吗"},
    ]
    pinned = {t["id"] for t in turns if t.get("pinned")}
    naive = naive_window(turns, keep=4)
    safe = pinned_window(turns, keep=4, pinned=pinned)
    assert len(naive) == 4
    assert 0 not in [t["id"] for t in naive]                  # 朴素做法丢了早期约束
    assert 0 in [t["id"] for t in safe]                       # 保底做法留住约束
    assert max(t["id"] for t in safe) == 6                    # 最近一轮仍在
    assert [t["id"] for t in safe] == sorted(t["id"] for t in safe)
    assert len(safe) == 5                                     # 四轮近期加一条常驻
    win, used = window_by_budget(turns, budget=12)
    assert used <= 12                                         # 用量不超预算
    assert win[-1]["id"] == 6                                 # 末尾仍是最新一轮
    assert win[0]["id"] == 3                                  # 更早的被挡在窗口外
    print("通过 9/9 项：朴素窗口会丢约束，保底窗口与按额度滚动均正确")
```

1. `naive_window` 就是那一行切片，`turns[-keep:]` 取尾部若干轮。它代表最省事的做法，也是本文要指出问题的对象。
2. `pinned_window` 先把编号落在 `pinned` 集合里的条目挑出来单独放着，其余条目才参与滚动，最后用 `sorted` 按编号把两拨内容复原成原本的先后顺序。为什么要复原顺序？因为对话的先后会影响理解，把开头那句规则挪到末尾会变成另一种含义。
3. `window_by_budget` 用 `reversed` 从最新一轮往回走，逐条累加 `len(text)`，一旦再加就超预算立刻停，最后再把结果反转回正序。注意它返回用量 `used`，方便外面核对到底吃了多少额度。
4. 主函数里构造了七轮对话，编号零那条带 `pinned` 标记，模拟「开头声明的规则」。前六条断言在对比两种窗口：朴素做法确实只剩四轮且把编号零弄丢了，带保底的做法则同时留住规则与最新一轮，长度是四加一，顺序也没乱。
5. 后三条断言验证按额度滚动：把预算设成十二个单位，从队尾往回恰好装下编号三到六，用量不超限，更新的仍在末尾，更早的被挡在外面。九条断言全过之后打印通过项数。

想自己试边界，可以把 `budget` 调到很小，会看到窗口只剩最后一轮；也可以把 `pinned` 清空，`safe` 就退化成 `naive`。这些都是能复现的构造场景，不需要接任何外部服务。

## 踩过的坑

- **把常驻规则混进滚动队列**：现象是聊久了忘了语种或报价口径 → 原因是所有轮次一视同仁地按位置淘汰 → 怎么改：给全程生效的条目打保底标记，单独留存且不参与滚动。
- **只按轮数不按字数**：现象是某轮突然超支 → 原因是一条长工具返回顶了十几轮的长度 → 怎么改：改用按字数从后往前累加，再用轮数当上限兜底。
- **保底内容越加越多**：现象是窗口又慢慢被撑满 → 原因是把「可能有用」的历史不断标成保底 → 怎么改：只标真正不过期的规则，会增长的改写紧凑字段。
- **裁剪后没复原顺序**：现象是规则被挪到末尾，含义变了 → 原因是简单拼接两拨内容 → 怎么改：合并后按编号排回原序。
- **以为裁掉就永远没了**：现象是后面要引用早期事实却找不到 → 原因是只做丢弃、没有落盘 → 怎么改：被挤出去的原文外置留存，需要时按编号取回。

## 三句话

滑动窗口裁剪是只保留最近若干轮原文、把更旧的队首逐条丢掉的最省事做法。
关键做法是把不过期的规则单独保底、并改用按字数从后往前累加来决定留多少。
当会话开头没有长期约束、且每轮长度都很均匀时，朴素的一行切片就够，不必加保底。

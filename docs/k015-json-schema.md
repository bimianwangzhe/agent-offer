# JSON Schema 约束

## 一、五个人写出五套「订单该长什么样」

一个小功能要读模型给出的「一条订单结果」，几个同事各写了一段解析。有人认定 `amount` 是整数，有人按字符串处理；`priority` 有人收到 `high`，有人收到 `urgent`，还有人收到 `P1`；碰上带地址的单子，嵌套的 `address` 有时整块消失。代码里于是散落着一堆 `if` 和兜底，改一个字段得翻五六个文件，谁也说不清「到底哪种才算合格」。你试着在提示词里补了一大段中文说明：「订单编号要两个大写字母加四位数字，优先级只能是低、中、高，数量必须是大于零的整数，缺一不可……」写得够细了，可解析代码里那套判断跟这段话是不是一回事，没人敢打包票。你隐约觉得，缺的不是一个更会写说明的人。

## 二、不是说明不够细，是缺一份机器也能查的描述

**不是缺一段更详细的中文说明，而是缺一份「机器也能逐项检查」的结构描述。**

先把词说清。JSON（JavaScript Object Notation，用花括号和键值对表示数据的文本格式）是下游爱读的文本。JSON Schema 是用 JSON 本身写成的一份结构描述，专门讲清楚一份数据该有哪些字段、每个字段是什么类型、能取哪些值、哪些必须有；这里的 Schema 就是「结构描述」的意思。校验（validation）指按这份描述逐项核对一份具体数据合不合格，被核对的那份数据叫实例（instance）。几个常见条目也顺手认一下：`type` 声明类型、`required` 列出必填字段、`enum`（枚举，把取值限定在事先列好的几个选项里）圈死有限取值、`minimum` 给数值下界、`pattern`（正则表达式，regular expression，用一串规则描述字符串该长什么样）管字符串形状、`properties` 描述嵌套对象里还有哪些子字段。

中文说明是写给人看的，机器读不了；结果往往是你手上同时攒出两份东西——提示词里说一套，解析代码里查另一套，改一处忘了另一处，行为就悄悄漂移了。结构描述的价值在于「同一份，两头用」：写进提示里，模型有了明确目标，知道 `priority` 只能是那三个词、编号得是那个形状；喂给校验器，代码有了明确依据，逐项照着查。想改字段，只改这一张描述，提示和校验一起跟着变，还能拿改动前后的差异去定位是哪一处引起的行为变化。

不过有件事必须点破：结构描述仍然是「描述」，不是「自动强制」。模型看到了也可能不照做——这跟[「请只输出 JSON」为什么不是保证](./k014-json-request.md)讲的是同一个道理。要让它真正生效，要么拿到结果后校验、不合格打回，要么在生成时直接屏蔽不合法候选。还有一层常被混在一起：「语法合法」「字段齐、类型对」「值合法、不自相矛盾」是三层不同的事，结构描述主要管中间那层，最外层的解析要看[语法层校验](./k016-syntax-check.md)，最里层的含义要看[语义层校验](./k018-semantic-check.md)。把三层叠着用，才谈得上兜住。

## 三、口头说「装好一点」，还是一张验收清单

把这件事想成请人装厨房。你只交代一句「弄规范些、装好一点」，验收那天就各说各话了：台面多高算合适、插座要不要地线、柜门缝多大算能接受，工长有工长的标准，你有你的标准，谁也说服不了谁。

换一种做法：开工前打印一张验收清单，逐行写死——台面高度 80 厘米、允许偏差 2 厘米；插座必须带接地、逐个试电；柜门缝隙小于 3 毫米；每一行后面留一个「合格／不合格」的勾选框。工长照这张单子施工，你照同一张单子验收，勾不满就不签字。

对应关系一条条摆出来：那句「装好一点」，就是提示词里的模糊中文说明；验收清单，就是那份结构描述；清单上每一行指标，就是 `type` 一个字段、`required` 一个字段、`enum` 一个字段、`minimum` 一个字段；行尾的勾选框，就是校验结果；工长是模型，你是校验代码；「勾不满不签字」，就是校验不通过、结果不准进下游。最要紧的一点在「同一张纸两头用」：工长和你不会各拿一份略有出入的版本，改一个指标也只需改这一张。想明白这层，就该看出把说明写得再长并没解决根子上的问题——问题从来不是说明不够细，而是它没有一份能被逐行核对的固定形式。

:::tip
一句话记住：**把「该长什么样」写成一张能勾的清单，而不是一段要读的话。** 判断描述够不够格，只问一句：能不能让一段代码照着它，对每个字段给出「合格／不合格」？
:::

## 四、一份结构描述里都装了什么

把「写一份描述」这件事拆开看，它并不是一口气写完的一大坨，而是几类约束拼起来的。

:::figure 结构描述从写出到生效的顺序
@flow
定字段清单|写类型与必填|加取值约束|给模型当目标|给校验当依据
:::

先圈出有哪些字段，再定每个的类型和哪些必须出现，接着给有限取值、数值范围、字符串形状加约束，然后同一份描述一方面进提示词当目标，另一方面进校验器当依据。第四步和第五步用的是同一个东西，这正是它比中文说明值钱的地方。

:::figure 一份结构描述里常见的六类约束
@stack
type 类型::这个字段是整数、字符串、布尔还是数组
required 必填::哪些字段必须出现，缺一个就不合格
enum 枚举::字段只能取事先列好的几个值
minimum 下界::数值或数组长度不得小于某个值
pattern 格式::字符串要匹配某种形状，比如编号格式
properties 子字段::嵌套对象里还要有哪些字段
:::

六类不必每份都用满，够描述清楚就停手。经验上有两条：取值有限的字段一律用枚举锁死，别只在说明文字里写「传 A 或 B」；必填字段只放真能从输入推断出来的，别贪多。

:::figure 中文说明与结构描述的差别
@compare
中文说明::机器读不了|提示与校验各说各话|改一处漏多处
结构描述::代码可逐项查|同一份两头用|改动集中可比对
:::

把描述写成机器可读之后，逐项去查的那段代码就是[结构层校验](./k017-structure-check.md)；把这张清单和别的提示片段分开存放、便于比对改动，是[结构化提示词模板六模块](./k132-prompt-template.md)要讲的组织方式；至于从生成时就不让不合法取值出现，则属于[约束解码原理](./k134-constrained-decoding.md)那条路。这几件是配合关系：描述定标准，校验来执法，生成时强制是另一道更早的闸门。

## 五、那如果必填列很多、或者想拿描述替掉校验呢

:::ask 把必填字段列得越多是不是越严谨
:::

恰恰相反。模型看到一长串必填、又从当前输入里推不出那些值，往往不会老实说「不知道」，而是自己编一个凑齐：你没提过时区，它补一个；你没给编号，它造一个。于是必填是齐了，值却全是编的，反而更难发现。做法是把「必须有」压到少而硬，只放真的能从上下文推断出来的字段。顺着再追一层：那是不是干脆把其余字段全设成可选？也不对，可选太多，校验就形同虚设，什么都能过。更稳的分法是两层：少数「必须有」的字段硬卡，其余字段「一旦出现就必须合法」——有则查、无则放，既不给编造留动机，也不让漏网之鱼蒙混。

:::ask 有了结构描述，是不是就能删掉服务端校验
:::

绝对不能，这是最危险的一种裸奔。描述只是约定，模型完全可能不照做；而且描述管的是形状，管不了权限，也管不了「这个编号是不是真的存在」「这个金额算得对不对」。一个形状完全合规的结果，照样可能操作别人的单子。再追一层：那把嵌套写深一点、把后端数据模型原样搬进来，是不是表达力更强？也不是，层数一多，字段容易在中间丢，提取的可靠性会明显往下掉。追到最后你会发现，描述该薄而准：只写下游真正要查的那些约束，越贴近实际要用的字段越好，别把整张数据库表照抄成一份描述。

## 六、一段能直接跑的迷你校验器

下面这段只靠 Python 标准库，不装任何第三方的结构描述库。它用普通字典写一份描述，再手写一台小校验器逐项核对，最后拿一批本地构造的候选输出把各类违规都撞一遍。样本全是构造场景，不是对任何真实模型的统计。

```python
# JSON Schema 约束：手写一台迷你校验器，演示「结构描述」如何让校验有依据。
# 只用标准库，不安装任何第三方包，不联网、不调用真实模型。

import json
import re

# 一份用普通 dict 写成的结构描述：既是给模型的目标，也是校验器的依据。
SCHEMA = {
    "type": "object",
    "required": ["order_id", "priority", "count"],
    "properties": {
        "order_id": {"type": "string", "pattern": r"^[A-Z]{2}\d{4}$"},
        "priority": {"type": "string", "enum": ["low", "medium", "high"]},
        "count":    {"type": "integer", "minimum": 1},
    },
}


def type_ok(value, expected):
    """按期望类型判断；特意把 bool 从 integer 里摘出去。"""
    if expected == "integer":
        return isinstance(value, int) and not isinstance(value, bool)
    if expected == "string":
        return isinstance(value, str)
    if expected == "object":
        return isinstance(value, dict)
    return True


def validate(instance, schema):
    """返回 (是否合格, 错误列表)：按描述逐项核对，攒齐所有错处。"""
    errors = []
    if schema.get("type") == "object" and not isinstance(instance, dict):
        return False, ["整体应是一个对象"]
    for field in schema.get("required", []):
        if field not in instance:
            errors.append(f"缺少必填字段 {field}")
    for field, rule in schema.get("properties", {}).items():
        if field not in instance:
            continue
        value = instance[field]
        if not type_ok(value, rule.get("type")):
            errors.append(f"字段 {field} 类型应为 {rule.get('type')}")
            continue
        if "enum" in rule and value not in rule["enum"]:
            errors.append(f"字段 {field} 取值不在允许枚举内")
        if "minimum" in rule and value < rule["minimum"]:
            errors.append(f"字段 {field} 小于下界 {rule['minimum']}")
        if "pattern" in rule and not re.search(rule["pattern"], value):
            errors.append(f"字段 {field} 不符合格式")
    return (len(errors) == 0), errors


# 一批本地构造的候选输出：每一条都已是合法 JSON 文本。
CANDIDATES = [
    '{"order_id":"AB1234","priority":"high","count":3}',
    '{"order_id":"AB1234","priority":"urgent","count":3}',
    '{"order_id":"ab1234","priority":"low","count":3}',
    '{"order_id":"AB1234","priority":"low","count":0}',
    '{"order_id":"AB1234","priority":"low"}',
    '{"order_id":"AB1234","priority":"low","count":true}',
]

if __name__ == '__main__':
    results = [validate(json.loads(c), SCHEMA) for c in CANDIDATES]
    checks = []
    checks.append(("合法样本通过", results[0][0] is True))
    checks.append(("枚举越界被拦", results[1][0] is False
                   and any("枚举" in e for e in results[1][1])))
    checks.append(("格式不符被拦", results[2][0] is False
                   and any("格式" in e for e in results[2][1])))
    checks.append(("小于下界被拦", results[3][0] is False
                   and any("下界" in e for e in results[3][1])))
    checks.append(("缺必填被拦", results[4][0] is False
                   and any("必填" in e for e in results[4][1])))
    # bool 是 int 的子类，若不特判就会被当成合法整数
    checks.append(("布尔不冒充整数", results[5][0] is False
                   and any("类型" in e for e in results[5][1])))
    # 同一份描述可直接当模型目标，也可直接喂给校验器
    checks.append(("描述可复用", "required" in SCHEMA and "properties" in SCHEMA))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `SCHEMA` 是那份「同一张纸」：`required` 列必填，三个字段各带自己的 `type`、`enum`、`minimum`、`pattern`，普通字典就能表达，不需要额外工具。
2. `type_ok` 里那句 `not isinstance(value, bool)` 是特意加的：在 Python 里布尔值是整数的子类，不摘出去，`count: true` 就会被当成合法整数蒙混过关。
3. `validate` 不遇到第一个错就返回，而是把 `required`、`type`、`enum`、`minimum`、`pattern` 逐项查完、攒齐所有错处再一并返回；这种「列全哪里不对」的输出，正好能喂给[自动纠正与重试上限](./k019-auto-repair.md)那种带错回传的流程。
4. `CANDIDATES` 六条全是能被解析的合法 JSON 文本，各自只坏一处：合法、枚举越界、编号格式不符、低于下界、缺必填、布尔冒充整数，用来演示「语法合法」离「结构合格」还差一整层。
5. 主函数把六条逐一代入校验器，七项断言分别确认该过的过、该拦的都带着对应错处被拦下，最后打印「通过 7/7 项」，任一项不成立就报错退出。

顺带一提，这里 `pattern` 用的是标准库 `re` 的正则表达式，靠一串规则描述「两个大写字母接四位数字」这种形状；它只管长相，管不到「这个编号在台账里是否存在」，那属于后面语义那关。

## 七、踩坑与边界

- **把枚举写进说明却没声明**：现象是描述里写了「传 A 或 B」，模型照样自造 `urgent`、`P1` → 原因是自由字符串没有任何硬约束 → 怎么改：有限取值一律声明 `enum`，别只写在文字里。
- **必填列得太多**：现象是字段倒是齐了，值却明显是编的 → 原因是模型推不出又不想缺，就自己凑 → 怎么改：必填只放真能从输入推断的，其余改成「出现即校验」。
- **把后端模型原样搬成描述**：现象是嵌套一深，中间字段常常丢 → 原因是层数越多越难稳定提取 → 怎么改：描述贴近下游实际要用的字段，够用就好。
- **布尔混进整数**：现象是 `count: true` 一路通过 → 原因是某些语言里布尔属于整数的子类 → 怎么改：类型判断时显式把布尔排除。
- **有了描述就删服务端校验**：现象是形状全对却出了越权或坏账 → 原因是描述只是约定、且只管形状 → 怎么改：描述与校验并存，语义和权限另设一关。

还要说清一个边界：结构描述擅长表达「形状、类型、有限取值、简单范围」这类能机械判定的规则，表达不了「两字段之和必须等于第三个」「这个编号必须属于当前用户」这种跨字段、跨系统的业务含义；后者得写进语义校验或服务端逻辑里。别为了把这些都塞进一份描述而把它撑成一张谁也维护不动的大网，描述越薄越准，反而越好用。

## 九、三句话小结

JSON Schema 约束是用一份机器可读的结构描述，把输出该有哪些字段、各是什么类型与取值写清楚，让模型有目标、校验有依据。
关键做法是同一份描述既进提示词又喂校验器，有限取值用枚举锁死、必填少而硬，并把语法、结构、语义三层分开查。
当规则是跨字段的业务含义、权限判定或「这个编号是否真实存在」时，就别硬塞进描述，该交给语义校验与服务端逻辑。

# 高并发与并发上限

## 场景提问

你写的 Agent 在本地一次只跑一个任务，几秒钟出结果，稳稳当当。放到对外服务里，同一秒涌进来几十个请求，情况立刻变了：模型接口开始大面积超时，工具调用排队排到看不见尾，账单一天涨了好几倍，客服还转来一条最吓人的反馈——「我怎么看到了别人的对话内容」。你翻代码，逻辑一个字没改，只是同时来的人变多了。为什么单跑没问题、一起跑就全线崩，而且崩的方式还五花八门，超时、变贵、串数据三件事一起冒出来？

## 破误解

**不是机器不够快，是把「同一时刻最多能有几个任务正在跑」这件事交给了运气，从来没有一道写死的、显式的上限。**

先把两个常被混用的词分开。并发（concurrency，同一时刻已经开工、但还没结束的任务数量）和并行（parallelism，真正被中央处理器在某一个瞬间同时执行的任务数量）不是一回事：一台单核机器上也可以有几百个并发，因为绝大多数任务此刻都卡在等待网络返回，并没有占用计算资源。每秒请求数（QPS，Queries Per Second，一秒内到达的请求数量）也不是并发数。它们之间有个朴素但极要命的关系：稳定状态下，同时在跑的任务数约等于「每秒到达数 × 每个任务平均耗时」。Agent 任务恰好把这个乘积撑得很大——一次请求内部要跑好几轮模型调用和工具调用，动辄几十秒；假设每秒来 10 个、每个耗时 30 秒，那么平稳时就有大约 300 个任务同时挂在系统里，哪怕你的机器一瞬间只能真正算几个。很多人只按每秒请求数配机器，压根没算这个乘法，于是下游连接池被占满、请求开始排队、超时触发重试、重试又把「每秒到达数」抬得更高，乘积被两头一起推上去，越堵越慢、越慢越堵。要补的不是「换台更大的机器」，而是三样朴素的东西：一道明确的并发上限、超限时是排队还是拒绝的既定策略、以及按用户或按租户（tenant，共用一套服务但彼此数据必须隔开的独立使用方）分配的公平配额。少了这三样，系统的行为就由流量随手决定。

## 生活类比

把它想成一家只开有限几个窗口的银行网点，门口摆着一台取号机。来办业务的人是一个个请求，正在柜台前办理的业务数就是并发数，窗口数量就是并发上限，取号后排的那条队就是等待队列，柜员办完一单喊「下一位」就是归还槽位、让队列里的下一个补进来。这套对应关系里，最贴切的一点是 Agent 业务的「办理时长」特别长：柜员办一笔普通存取款几分钟，而你的每笔业务都要求他当场打三个电话到不同部门核实，一单下来半小时。于是哪怕每分钟只叫两个号，窗口前也会迅速堆起一批「正在打电话、还没办完」的业务。

这个比喻能一口气解释场景里的三桩怪事。第一桩，窗口不设上限会怎样？经理把所有叫到号的人都请到柜台前，每个柜员同时接十个电话，结果谁都听不清、谁都办不完，后面的人连门都挤不进来——这就是打爆下游：连接池和速率限制（RPM / TPM，每分钟请求数与每分钟 token 数）是有硬边界的，超过之后不是变慢一点，而是集体卡死。第二桩，账单为什么会翻几倍？网点每开一个窗口都要付一份人工，窗口全开且长时间占着，成本就是「同时在办的业务数 × 每单单价」在持续计时，光看叫号速度根本估不出来。第三桩，为什么会串数据？柜员图省事，把上一位客户的单据一直摊在桌面上没清走，下一位来了直接接着写——这就是共享的可变状态在并发下被交叉读写，比数量超限更隐蔽。还有一层：取号机如果只管发号、不管「队伍最长排到哪」，队伍会无限长，客户等一整天也轮不上，大厅（内存）先被挤爆；所以除了窗口数，还得有一条「排队超过多久就明确劝退」的线。最后，一个人一次领十张号把窗口占满也不行，得按人限号，这就是单租户配额。整件事的关键从来不是「多雇几个柜员」，而是把窗口数、队伍长度、每人限号数都写成明面上的规矩。

## 自绘示意图

:::figure 一次请求穿过并发闸门的顺序
@flow
请求到达|取并发槽位|槽内执行多轮|归还槽位|队列下个补进
:::

这张图里最容易被写错的是「归还槽位」这一格。它必须和「取并发槽位」严格成对，而且无论中间那一格是正常跑完、抛了异常、还是被超时打断，都得走到它。真实代码里只要有一条分支漏了归还，槽位就会被永久占住，上限会像漏水的桶一样慢慢降到零——系统看起来还活着，却再也接不进新任务。所以归还动作要放在「无论如何都会执行」的那一段里，而不是写在正常路径的最后一行。

:::figure 并发上限要同时掐住的四处
@stack
进程内槽位数::同一实例最多几个任务同时占用执行位
下游连接池::对模型与工具接口的总并发连接上限
单租户配额::一个用户最多占几个槽位，防止吃满
排队与超时::排队多久没轮到就明确拒绝
:::

四格里最常被漏掉的是最后一格。只设「最多同时跑几个」而不设「队伍最长等多久」，队列就会无限膨胀：请求数不丢、错误率也不涨，但每个请求的等待时间越来越长，内存里堆着的全是还没开工的任务，用户体感是「服务假死了」。另一处容易漏的是第二格——本机放行 200 个并发，可模型接口的连接池只接得住 50 个，剩下 150 个并不是在真正执行，而是在下游排队，本机还以为它们都跑得好好的。

:::figure 不设上限与设上限的差别
@compare
不限并发::下游被占满|重试叠加放大|长任务互相拖慢
设并发上限::峰值可被预算|超限明确拒绝|支出速率可预期
:::

左边顺风顺水时最省事，因为它不需要任何额外的判断；右边多了一道闸门，却换来了三件在低流量时看不出价值、一旦出事就救命的性质：峰值能被提前算进预算、超限有明确的拒绝而不是无声地拖、每单位时间烧钱的速度有个封顶。二者真正的差距不在平时，而在流量突然翻倍的那一刻能不能收得住。

## 层层追问

:::ask 那如果我把上限设得很大，比如几百，是不是就绕开这个烦恼了？
:::

绕不开，而且这恰恰是把问题从本机挪到了下游。上限不是按本机内存拍脑袋定的，得按整条链路上「最窄的那一处」倒推：模型接口有每分钟请求数与每分钟 token 数的限制，工具接口有连接池上限，数据库有最大连接数，这些值通常远小于你能同时开出的任务数。本机放行 500 个并发、下游只接得住 50 个，多出来的 450 个不会凭空消失，它们挤在排队与超时里；一旦超时，调用方往往立刻重试，于是「每秒到达数」被重试抬高，而「平均耗时」因为排队也被拉长，那个乘积被两头一起放大，形成越堵越重试、越重试越堵的正反馈。这就是雪崩的形状，也是为什么光调大上限只会让崩得更晚、更彻底。正确的顺序是：先量出下游能承受的并发数，把上限设在它之下；再让重试带上退避与抖动，具体做法见 [重试退避与抖动](./k108-retry-backoff.md)；当下游已经明显不健康时，由 [熔断与 kill switch](./k104-circuit-breaker.md) 直接切断，别再把请求往里送。还有更深的第二层：硬上限管的是「同时跑几个」，管不了「一共能花多少钱」。并发跑满时，支出速度是「并发数 × 单任务成本」在持续计时，如果任务被卡住又不断重试，光限并发、不设总支出封顶，长时间满载照样能把预算烧穿。这一步要靠 [生产失败模式清单与支出硬上限](./k150-failure-modes.md) 里那道按任务、按租户、按时间窗计算的硬线；把这几类约束合起来看，就是 [四重预算](./k103-four-budgets.md) 的思路。换句话说，并发上限是必要的一道，但不是最后一道。

:::ask 那如果并发的任务之间会互相影响，光限制数量够不够？
:::

不够，这是另一条独立的线索。数量上限解决「占多少资源」，解决不了「串味」：共享的可变状态在并发下会被交叉读写。一个全局复用的对话缓存、一个工具客户端里残留的上一次身份、一个静态变量里存着的上一轮上下文，都可能让甲的任务读到乙的数据，或者更糟——乙借着甲的权限调用了本不该调用的工具。所以每个槽位里的任务要有各自独立的会话上下文，身份由服务端按本次请求注入，而不是从一个大家共用的对象里翻出来，这部分在 [会话隔离与租户边界](./k105-session-isolation.md) 和 [用户身份服务端注入](./k137-identity-injection.md) 里各自展开。再往下还有一处很隐蔽的坑：任务超时被本地判定为「失败」时，下游其实可能已经执行完了，如果这时槽位一释放就立刻塞进新任务去做补偿，很容易产生重复的副作用。这和 [超时不等于没执行](./k039-timeout-reconcile.md) 讲的是同一件事；稳妥的做法是把「释放本地槽位」和「核对动作是否真的落地」分成两件事——槽位按本地生命周期照常归还，动作有没有生效则靠 [幂等键与副作用防重](./k038-idempotency-key.md) 那种稳定标识去对账，不靠「超时了就重来一遍」。把这两层合起来才完整：一道闸管住数量，一套隔离管住边界，谁也替代不了谁。至于这道闸该由谁探知、目标定成多少才叫守得住，可以对照 [健康检查与 SLO](./k114-health-slo.md)。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，不着网络、不建线程，而是用离散时钟把「到达—排队—取槽位—执行—归还」推进许多轮，把并发上限、租户配额、排队超时拒绝、异常也归还槽位这几件事都做成可手工推算的确定性模拟。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
from collections import deque, defaultdict


class SlotPool:
    """固定容量槽位池：拿到槽位才算开工，归还后才能给下一个任务。"""

    def __init__(self, capacity):
        self.capacity = capacity
        self.in_use = 0
        self.peak = 0

    def try_acquire(self):
        if self.in_use >= self.capacity:
            return False
        self.in_use += 1
        if self.in_use > self.peak:
            self.peak = self.in_use
        return True

    def release(self):
        assert self.in_use > 0, "归还了并未占用的槽位"
        self.in_use -= 1


def build_requests(count, arrival_rate, duration, tenant_count):
    """构造确定性到达序列：第 i 个请求在第 i // arrival_rate 拍到达。"""
    reqs = []
    for i in range(count):
        reqs.append({
            "id": "req-%03d" % i,
            "arrive": i // arrival_rate,
            "duration": duration,
            "tenant": "t%d" % (i % tenant_count),
        })
    return reqs


def simulate(reqs, capacity, per_tenant_cap, queue_timeout, ticks):
    """按离散时钟推进，返回峰值并发、最终占用、已开工与被拒清单。"""
    pool = SlotPool(capacity)
    waiting = deque()
    running = []
    tenant_used = defaultdict(int)
    admitted = []
    rejected = []

    by_arrival = defaultdict(list)
    for r in reqs:
        by_arrival[r["arrive"]].append(r)

    for now in range(ticks):
        # 1) 先归还到点任务，归还放最前面，同一拍的槽位就能被复用
        still = []
        for finish, rid, tenant in running:
            if finish <= now:
                pool.release()
                tenant_used[tenant] -= 1
            else:
                still.append((finish, rid, tenant))
        running = still

        # 2) 本拍新到达的进队
        for r in by_arrival[now]:
            waiting.append((r, now))

        # 3) 排队超时且还没开工的直接拒绝，避免队列无限长
        fresh = deque()
        for r, entered in waiting:
            if now - entered >= queue_timeout:
                rejected.append(r["id"])
            else:
                fresh.append((r, entered))
        waiting = fresh

        # 4) 配额检查放最前，未占槽就短路；有空槽才真正开工
        pending = deque()
        for r, entered in waiting:
            if tenant_used[r["tenant"]] < per_tenant_cap and pool.try_acquire():
                tenant_used[r["tenant"]] += 1
                running.append((now + r["duration"], r["id"], r["tenant"]))
                admitted.append(r["id"])
            else:
                pending.append((r, entered))
        waiting = pending

    return {
        "peak": pool.peak,
        "in_use": pool.in_use,
        "admitted": admitted,
        "rejected": rejected,
    }


def run_one(pool, tenant, tenant_used, work):
    """单个任务的模板：用 finally 保证抛异常也归还槽位与配额。"""
    assert pool.try_acquire(), "拿不到槽位就不该开工"
    tenant_used[tenant] += 1
    try:
        return work()
    finally:
        pool.release()
        tenant_used[tenant] -= 1


def demo_finally():
    """验证一次执行中途抛异常后，槽位与配额都没有被残留占用。"""
    pool = SlotPool(2)
    used = defaultdict(int)

    def boom():
        raise RuntimeError("模拟执行中抛异常")

    try:
        run_one(pool, "t0", used, boom)
    except RuntimeError:
        pass
    return pool.in_use == 0 and used["t0"] == 0


def main():
    rate, duration = 6, 8
    reqs = build_requests(60, rate, duration, tenant_count=3)
    cost_per_slot = 3
    checks = []

    # 不设实际约束：峰值应等于 到达率 × 单任务耗时
    open_run = simulate(reqs, 1000, 1000, 1000, 60)
    checks.append(("不限并发时峰值等于到达率乘耗时",
                   open_run["peak"] == rate * duration))
    checks.append(("不限并发时全部请求都开工",
                   len(open_run["admitted"]) == 60))
    checks.append(("不限并发时没有拒绝",
                   len(open_run["rejected"]) == 0))

    # 设上限但允许长队：峰值被掐住，任务一个不丢
    limited = simulate(reqs, 12, 12, 1000, 200)
    checks.append(("设上限后峰值不超过容量", limited["peak"] <= 12))
    checks.append(("设上限后峰值确实被压低", limited["peak"] < open_run["peak"]))
    checks.append(("允许排队时不丢任务", len(limited["admitted"]) == 60))
    checks.append(("排队结束时槽位全部归还", limited["in_use"] == 0))
    checks.append(("峰值支出速率随上限被压低",
                   limited["peak"] * cost_per_slot
                   < open_run["peak"] * cost_per_slot))

    # 排队有超时：超时的明确拒绝，绝不无限堆着
    shed = simulate(reqs, 12, 12, 5, 200)
    checks.append(("排队超时会产生明确拒绝", len(shed["rejected"]) > 0))
    checks.append(("被拒的请求没有偷偷开工",
                   set(shed["admitted"]).isdisjoint(set(shed["rejected"]))))
    checks.append(("每个请求都有明确去向",
                   len(shed["admitted"]) + len(shed["rejected"]) == 60))
    checks.append(("拒绝后槽位仍全部归还", shed["in_use"] == 0))

    # 单租户独占：即使容量很大，也只按配额占用
    single = build_requests(30, 10, duration, tenant_count=1)
    tenant_run = simulate(single, 100, 4, 1000, 200)
    checks.append(("单租户配额精确生效", tenant_run["peak"] == 4))
    checks.append(("配额场景槽位全部归还", tenant_run["in_use"] == 0))

    checks.append(("异常路径也归还槽位与配额", demo_finally() is True))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `SlotPool` 用两个数字表达整件事：`in_use` 是当前已经开工、还没归还的任务数，`peak` 是历史最高值。`try_acquire` 在 `in_use` 达到 `capacity` 时直接返回 `False`，这就是「并发上限」最原本的样子——不是限流算法有多精巧，而是「拿不到槽位就不许开工」。`release` 里那句断言防止出现「归还了一个根本没占用的槽位」这类把计数减成负数的隐性错误。
2. `build_requests` 构造可手工推算的到达序列：第 `i` 个请求在第 `i // arrival_rate` 拍到达，租户编号按 `i % tenant_count` 轮转。全程没有随机数，所以同一组参数每次跑出的峰值、开工清单、拒绝清单完全一致，哪一条断言不成立都能直接顺着编号查回去。
3. `simulate` 是整套模拟的主体，每一拍严格按四步走，顺序不能换。第一步先归还到点任务，放在最前面意味着「这一拍刚空出来的槽位，同一拍就能给新任务用」，贴近真实服务里连接被释放即可复用的行为；第二步把新到达的进队；第三步清扫排队超时且尚未开工的请求，把它们记进 `rejected`，这一步就是「队伍最长等多久」的落地；第四步才尝试取槽开工。
4. 第四步那个 `and` 的顺序是刻意安排的：`tenant_used[r["tenant"]] < per_tenant_cap` 放在 `pool.try_acquire()` 前面，配额不满足时短路、根本不会去占槽位。若把两者反过来，配额已满的请求会先占一个槽再被判不合格，就得额外补一次归还，极易漏写——用短路把「不该占的槽」从源头掐掉，比事后清理稳得多。
5. `run_one` 是单个任务的执行模板，`finally` 里同时归还槽位和租户配额。它对应前文那句「归还必须覆盖所有分支」：正常返回会走它，抛异常也会走它。`demo_finally` 故意让 `boom` 抛出一个运行时错误，再检查 `in_use` 和配额都归零，把「异常不漏归还」变成一条可验证的性质，而不是一句口号。
6. `main` 里第一组是不设实际约束的对照：容量、租户配额、排队超时都给到极大，于是六十个请求全部开工，峰值恰好等于 `rate * duration`，也就是 6 乘 8 等于 48。这正是破误解里那个乘法的可复现版本——它说明并发数由「到达速度 × 任务时长」决定，而不是由机器快慢决定。
7. 第二组把容量压到 12、但允许长队，断言峰值不超过 12 且明显低于 48、六十个请求一个不丢、结束时 `in_use` 归零。这组把「设上限」和「丢任务」区分开：上限只掐同时在跑的数量，请求排队等着就行。峰值支出速率用「峰值 × 每槽单价」算，断言它随上限一起被压低，对应「成本按同时在跑的数量计时」。
8. 第三组把排队超时设成 5 拍，于是会有一部分请求被明确拒绝；断言拒绝非空、被拒的请求与已开工的请求没有交集、两者数量合起来正好是六十、槽位最终全部归还。「每个请求都有明确去向」这条尤其重要：既不静默丢弃、也不无限堆着，是排队策略的最低要求。
9. 第四组用全部属于同一租户的三十个请求、把容量放大到 100，单租户配额设成 4，断言峰值恰好等于 4。这说明配额是独立于总容量的另一道约束——没有它，一个使用方就能把 100 个槽全占满。最后把 `demo_finally` 也并进检查，统一统计通过项数并在任何一条不成立时以非零状态退出。

如实说明一句：这里用离散时钟代替真实时钟、用字典和队列代替线程池与连接池、用取模代替真实哈希，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算核对。它演示的是上限、排队、拒绝、配额与归还之间的顺序关系，不是任何具体并发库的实现；复制运行即可逐条看到上述性质是否成立。

## 踩坑与边界

- **只按每秒请求数配机器**：现象是压测时请求量明明不高，下游却大面积超时、内存持续上涨 → 原因是没算「到达率 × 单任务耗时」这个乘积，长任务让并发悄悄堆到几百 → 先量出下游能承受的并发数，把上限设在它之下，再按这个上限反推该配多少资源，别拿每秒请求数当并发数用。
- **槽位漏在异常路径归还**：现象是服务跑一阵子后能接的任务越来越少，最后彻底不进新请求，但进程还活着、错误率也不高 → 原因是某条抛异常或超时的分支没走到归还，`in_use` 只增不减 → 把归还统一放进「无论如何都执行」的那一段，并像 `demo_finally` 那样用一条断言验证异常后计数归零。
- **设了上限却让队列无限长**：现象是错误率没涨、请求也没被拒，可用户普遍反映「等好久没反应」，内存里堆满未开工任务 → 原因是只限了同时执行数，没限等待时长 → 给队列定一个明确的超时，超时就返回一个可预期的拒绝，让调用方知道该重试还是该放弃，而不是无声地拖着。
- **一超限就立刻重试**：现象是流量翻倍的瞬间错误数暴涨，退回一点又立刻再冲上去，反复振荡 → 原因是被拒请求原地重试，把到达率进一步抬高，与排队变长一起放大了那个乘积 → 重试必须带退避与抖动，并在下游不健康时直接熔断，见 [重试退避与抖动](./k108-retry-backoff.md) 与 [熔断与 kill switch](./k104-circuit-breaker.md)。
- **共享状态在并发下串味**：现象是偶发出现「看到了别人的数据」，或者某个用户借着别人的身份调用了越权工具，且极难复现 → 原因是复用了全局对话缓存、共享工具客户端或静态变量 → 每个任务用独立会话上下文、身份由服务端按请求注入，参考 [会话隔离与租户边界](./k105-session-isolation.md)；超时后的补偿也别靠重做，按 [幂等键与副作用防重](./k038-idempotency-key.md) 去对账。

还要分清两件容易混的事：「并发上限」掐的是同一时刻开工的数量，「支出硬上限」掐的是一段时间内总共能花多少，前者是速率、后者是总量，长时间满载时只有前者不够，见 [生产失败模式清单与支出硬上限](./k150-failure-modes.md)。而「超限拒绝」和「熔断」也不是一回事：前者是容量满了、明确告诉调用方这次不接，后者是下游已经不健康、主动停止向它送流量，触发条件和处理对象都不同。把这些约束连同监控目标一起写进可查的配置，是 [成本优化与上线检查清单](./k116-cost-checklist.md) 里发布前要逐条过一遍的内容；量出「下游到底接得住多少」这件事，则离不开 [健康检查与 SLO](./k114-health-slo.md) 提供的可观测依据。

## 三句话小结

高并发与并发上限，是承认 Agent 任务又长又占资源之后，给「同一时刻最多几个任务正在跑」写一道明面上的硬线，超出的排队或明确拒绝，而不是让流量替你决定。

关键做法是按下游最窄的一处倒推上限、取槽与归还严格成对且覆盖异常、给队列设超时、按租户分配额，并让退款重试带退避、必要时熔断。

当系统只在本地一次跑一个离线任务、根本没有同时到达的请求时，不必硬套这道闸门；但只要它会同时接多个真实请求，这道上限就不该缺席。

# 成本优化与上线检查清单

## 场景提问

月底看账单，你愣了一下：明明把模型换成了更便宜的那档，调用报价一路往下，可这个月的总支出反而比上个月高。你翻优化记录，该做的都做了——提示词缩短了、历史只留最近几轮、还加了缓存。再往下查才发现两件事：一是失败的任务比上个月多不少，那些没做成的请求照样把输入、输出、重试、工具调用的钱全烧了一遍；二是某个改动上线后，一个原本两轮就结束的任务开始反复兜圈子，一轮一轮地调同一个工具。单价降了，钱却没少花，问题到底出在哪？更让你犯愁的是，下次再改一版，怎么才能保证不又把某个口子漏开。

## 破误解

**不是单价没压到位，是把「一次调用」当成了记账单位，而真正该记账的是「一个做成的事」。**

先把账重新算一遍。一次任务的花费并不等于一次模型调用的报价，它至少由五处叠起来：送进去的输入、吐出来的输出、失败之后的重试、每次工具调用、以及被反复带进上下文的历史；如果同时跑着很多任务，还要再乘上「同时在跑的数量 × 时长」。这里有个容易被忽略的事实：钱花在这五处的每一处，但「价值」只在任务做成的那一刻才产生。于是一个更实在的指标是「每成功任务成本」——把一段时间里所有请求的花费加起来做分子，只把真正做成的任务数做分母。它是 effective cost（有效成本，为拿到一个可用结果平均付出的代价）的白话说法，展开在 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 里。为什么这个分母重要？因为一次失败的任务不是「没花钱」，而是「花了钱、没产出」；把单价压低却让成功率下滑，分子缩一点、分母缩更多，比值反而升高。很多人优化时只盯调用报价和总支出，恰恰漏掉了分母。

还有一层常被混为一谈：成本优化是持续在做的动作，而「上线检查清单」是发布前一次性逐条确认的门禁，两者不是一回事。前者的典型手段是输入裁剪、前缀复用、模型分流、循环封顶、并发与预算约束；后者是把「这些手段有没有真的接上、口径有没有变差、可观测与护栏有没有缺」变成一条条能回答「通过还是不通过」的检查项。优化做得再好，只要发布时漏配一处，前面全白搭。所以这篇要讲清的是两件事：怎么把账记对，以及怎么把「别漏」变成可以逐条打勾的确定性动作，而不是一段写在文档里、靠人临场回忆的注意事项。

## 生活类比

把它想成开一家小餐馆算账。菜单上每盘菜的标价，是一次模型调用的单价；而一桌客人从进门到结账所消耗的食材、燃气、服务员来回跑的工夫，才是一次任务的完整花费。菜做砸了被退回来重做一盘，是重试——它没有多卖出一份钱，却把食材和燃气又烧了一遍。客人最后没付账就走了，是失败任务：成本一分不少，收入是零。老板真正该盯的数字不是「今天菜价降没降」，而是「今天实际结账的每一桌，平均替我赚回多少、又垫进去多少」，这就是把分子记全、只拿成功的桌数做分母。

对应关系可以逐条对上。只顾着换更便宜的食材（压单价），客人觉得不对味、退菜变多，看起来每盘成本降了，可「每桌实收」反而缩水——这正是压单价却抬高每成功任务成本。做砸重做那一盘，对应重试：它不产生新价值，却重复消耗前面几格，所以记账时绝不能只统计成功请求的花费、把失败的花费藏起来。厨房里那位师傅一着急就反复尝同一锅汤、来回跑十几趟，对应循环没有封顶，一轮轮重复调用同一个工具。而「开张前逐条检查」就是那份发布前清单：燃气阀关没关、冰箱温度对不对、秤准不准、收银系统记不记得住每一桌、备用灶能不能点着——每一条都得能当场回答「合格 / 不合格」，不能写成「注意用火安全」这种谁都说得过去、却谁也没法判定的话。最要命的一处细节是：这张检查单不能只在开业那天用一次，换了新菜单（新版本）还得拿它跟上一版的「每桌实收」比一比，否则单看每一项都合格，整体却悄悄变贵了，老板还蒙在鼓里。

## 自绘示意图

:::figure 一次任务把钱花在哪、价值在哪产生
@flow
构造输入|模型推理|工具调用|失败重试|按成功任务记账
:::

这张图最值得盯的是前四格与第五格的错位：钱从第一格就开始流，一直流到第四格，可「做成了一件事」这个分母只在第五格才出现。第四格「失败重试」尤其容易被漏掉，因为它既不产生新结果、也不改变要解决的问题，只是把前三格的花销再复刻一遍。记账时如果把这一格当成「没发生过」，算出来的成本天然偏乐观，优化方向也就跟着跑偏了。

:::figure 成本优化能下手的五处
@stack
输入裁剪::去掉无关历史与冗余片段，少算输入单位
前缀复用::稳定前缀命中缓存，重复部分不重复计费
模型分流::简单步骤走轻量模型，难题才用大模型
循环封顶::限制最大轮数与重复调用，防兜圈子烧钱
并发与预算::限制同时在跑数量并设支出硬上限
:::

五处里最容易只做前两处、漏掉后三处。前两处是「把每次变便宜」，见效快、也好看；后三处是「别让次数和时长失控」，平时看不出功劳，一旦某个改动让任务开始兜圈子，或者流量突然翻倍，它们才是真正兜底的那几道。特别是「并发与预算」这一格，它管的不是单次贵不贵，而是「同一时间有多少个任务在同时烧钱」，和 [高并发与并发上限](./k115-concurrency.md) 是同一条线。

:::figure 两种记账口径的差别
@compare
只压单价::成功率可能下滑|有效成本反升|失败照样计费
按成功任务核算::盯每单真实开销|重试无所遁形|优化不牺牲成败
:::

左边把「便宜」当成目标，顺风时数字漂亮，可它默认了成功率不变——而换便宜模型、狠裁上下文恰恰最容易动到成功率。右边把「拿到一个可用结果平均花多少」当成目标，于是任何以牺牲成败换取低单价的做法都会立刻在比值上露出来。两种口径的差距，全在「失败的请求算不算数」这一念之间。

## 层层追问

:::ask 那如果我把上下文裁得很狠、模型也换成最便宜的，成本总该降了吧？
:::

不一定，而且这是最典型的一次「降了账单、抬了实价」。用一组完全构造出来、可以手算的算例说清楚：假设有一百个任务，旧版每个任务花 45 个计费单位、做成 80 个，那么每成功任务成本是 4500 除以 80，约 56；新版把单价压到每个 33 个单位、总花费降到 3300，但成功率掉到只做成 30 个，每成功任务成本就变成 3300 除以 30，整整 110。单价降了、总支出也降了，可每拿到一个可用结果反而贵了将近一倍。这不是任何真实系统的运行数据，只是一个把「分子缩一点、分母缩更多」摆到明面上的算术例子，任何人都可以在纸上复核；它说明只盯报价和总支出会得到与事实相反的结论。

再往下一层：为什么狠裁上下文会动到成功率？因为上下文里有些东西是不能压的——系统规则、本轮要办的事、刚拿回来的工具结果，压掉任何一样，模型就会在信息不全的情况下做决定，返工和失败跟着上来。裁剪该砍的是无关历史、重复片段和过期的检索内容，而不是这些不可压缩项，哪些必须留、哪些可以压，在 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 和 [上下文预算表](./k041-context-budget.md) 里分得很细；压缩完还得验证信息确实没丢，这是 [压缩后信息丢失怎么验证](./k048-compression-verify.md) 要管的。同理，换便宜模型也不该一刀切，简单步骤走轻量档、真遇到难题再升档，是 [模型路由](./k082-model-router.md) 的做法；而任务反复兜圈子，得靠 [四个终止条件](./k028-stop-conditions.md) 把最大轮数写死。一句话：优化的是「浪费」，不是「能力」，凡是动到能力的省法，都要拿成功率先过一遍账。

:::ask 那如果优化手段都接上了，怎么保证发布时没把某个口子漏开？
:::

靠的不是记性，而是一份「每一项都能判定通过与否」的发布前清单。这里的关键不是列得多全，而是每一条都要写成能算出真假的布尔条件：不是「并发控制要注意」，而是「并发上限已配置且大于零」；不是「日志要规范」，而是「结构化日志必填字段里包含 trace_id（轨迹标识）、花费、版本号」；不是「审批别放过」，而是「高风险动作审批超时默认拒绝」。写成这样，清单才能被程序自动跑一遍，任何一条不成立就挡住发布，而不是指望有人临场想起来。结构化日志该记哪些字段、怎么支撑事后回放，见 [结构化日志与轨迹回放](./k095-structured-log.md)；发布前那套固定用例与基线卡住「这版能不能进下一步」，是 [回归门禁与基线](./k091-regression-gate.md)；对外能探知状态、给目标定一条守得住的线，则是 [健康检查与 SLO](./k114-health-slo.md)（SLO，Service Level Objective，服务等级目标）。

再追一层：清单「全项通过」还不够，得跟上一版比。单独看每一项，并发上限设了、循环封顶了、硬上限配了、日志字段齐了，条条合格；可如果这一版恰好让每成功任务成本比基线高出一大截，逐项检查是发现不了的——因为它衡量的是「有没有配」，不是「有没有变差」。所以清单里必须有一条硬项：当前版本的每成功任务成本不得明显劣于基线。这条把「逐项检查」和「版本对比」接了起来，也让这张清单从一张静态表格变成一道会随版本更新的门禁。几类约束合起来看，就是 [四重预算](./k103-four-budgets.md) 的思路；而「一旦超线就切断、不是只报警」的那道硬线，属于 [生产失败模式清单与支出硬上限](./k150-failure-modes.md)，必要时由 [熔断与 kill switch](./k104-circuit-breaker.md) 落地。清单本身也要跟着配置一起版本化，否则「这次到底按哪张单子检查的」又说不清了，这一点和 [提示与策略版本化](./k113-prompt-versioning.md) 是同一个道理。

## 可运行代码与逐行解释

下面这段只用 Python 内置功能，把「按成功任务核算」和「发布前清单自动判定」两件事做成一个可手工推算的确定性例子：先构造两版任务记录，证明压低单价反而抬高每成功任务成本；再把清单写成一组可判定的布尔表达式，验证合格版本全通过、被破坏的配置能挡住、变贵的版本也能挡住。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
PRICE_IN = 2      # 每输入单位的构造单价
PRICE_OUT = 5     # 每输出单位的构造单价
RETRY_COST = 3    # 每次重试的构造固定成本
TOOL_COST = 1     # 每次工具调用的构造成本


def cost_of(rec):
    """把一次任务的花费算全：输入、输出、重试、工具调用一处不漏。"""
    return (rec["in"] * PRICE_IN
            + rec["out"] * PRICE_OUT
            + rec["retries"] * RETRY_COST
            + rec["tools"] * TOOL_COST)


def make_records(version):
    """构造一百条任务：v1 做成多，v2 返工多做成少，none 全失败测边界。"""
    rows = []
    for i in range(100):
        if version == "v1":
            rec = {"in": 10, "out": 4, "retries": 1, "tools": 2}
            ok = i < 80
        else:
            rec = {"in": 4, "out": 2, "retries": 4, "tools": 3}
            ok = i < 30
        if version == "none":
            ok = False
        rows.append((ok, rec))
    return rows


def summarize(version):
    """汇总总花费、成功数、单条花费与每成功任务成本。"""
    rows = make_records(version)
    total = sum(cost_of(rec) for _, rec in rows)
    success = sum(1 for ok, _ in rows if ok)
    unit = cost_of(rows[0][1])
    effective = total / success if success else None
    return {"total": total, "success": success,
            "unit": unit, "effective": effective}


def build_checklist(config, baseline, current):
    """每项都返回 (名称, 是否通过)，把「别漏」变成能自动判定的条件。"""
    return [
        ("并发上限已配置且大于零", config["concurrency_cap"] > 0),
        ("单任务最大轮数已封顶", config["max_rounds"] <= 12),
        ("支出硬上限已配置", config["spend_hard_cap"] > 0),
        ("按成功任务核算已接入", current["effective"] is not None),
        ("每成功任务成本未明显劣于基线",
         current["effective"] is not None
         and current["effective"] <= baseline["effective"] * 1.1),
        ("结构化日志必填字段齐全",
         set(config["log_fields"]) >= {"trace_id", "cost", "version"}),
        ("回归基线已记录", baseline["success"] > 0),
        ("高风险动作审批超时默认拒绝",
         config["approval_default"] == "deny"),
    ]


def all_pass(items):
    return all(good for _, good in items)


def main():
    v1 = summarize("v1")
    v2 = summarize("v2")
    baseline = v1
    config = {
        "concurrency_cap": 12,
        "max_rounds": 10,
        "spend_hard_cap": 10000,
        "log_fields": ["trace_id", "cost", "version", "tenant"],
        "approval_default": "deny",
    }
    checks = []

    # 压单价确实让单条与总花费都下降
    checks.append(("v2 单条花费低于 v1", v2["unit"] < v1["unit"]))
    checks.append(("v2 总花费低于 v1", v2["total"] < v1["total"]))
    # 但成功率掉得更多，每成功任务成本反而升高
    checks.append(("v2 成功数明显少于 v1", v2["success"] < v1["success"]))
    checks.append(("压单价后每成功任务成本反升",
                   v2["effective"] > v1["effective"]))
    checks.append(("成功数为零时比值有明确边界",
                   summarize("none")["effective"] is None))

    # 合格配置全部通过
    good_items = build_checklist(config, baseline, v1)
    checks.append(("合格配置逐项全通过", all_pass(good_items)))
    checks.append(("清单一共八项", len(good_items) == 8))

    # 任意一处被破坏，清单就挡住发布
    broken = dict(config)
    broken["concurrency_cap"] = 0
    checks.append(("并发上限漏配会被挡住",
                   not all_pass(build_checklist(broken, baseline, v1))))

    missing = dict(config)
    missing["log_fields"] = ["trace_id", "version"]
    checks.append(("日志字段缺失会被挡住",
                   not all_pass(build_checklist(missing, baseline, v1))))

    # 逐项都合格但整体变贵的版本，也要被硬项挡住
    checks.append(("变贵版本被基线对比挡住",
                   not all_pass(build_checklist(config, baseline, v2))))
    checks.append(("极端许可不会被默认放行",
                   config["approval_default"] != "allow"))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. 开头四个常数是构造出来的计价参数，把输入、输出、重试、工具调用分别定价。它们不是任何真实报价，只是让「一次任务的花费由五处叠加」这件事能被算出来；把 `token` 折算成「计费单位」是为了省掉单位换算的噪声，专注在口径上。
2. `cost_of` 把四项一次性加总，对应前文那句「钱花在前四格」。它刻意把 `retries` 和 `tools` 也算进去——很多账算得偏乐观，就是因为只统计了输入和输出，把失败后的重来与工具调用当作不存在。
3. `make_records` 构造两版各一百条记录，全无随机数：v1 每条约 45 个单位、做成 80 条；v2 每条约 33 个单位、却因返工更多只做成 30 条；另有一个 `none` 版把每条都标成失败，专门用来测分母为零的边界。用 `i < 80`、`i < 30` 这种直接可数的写法，谁都能手算核对，不依赖任何碰运气的结果。
4. `summarize` 是记账口径的关键一步：分子 `total` 把一百条的花费**全部**加起来（包括失败的那二十条或七十条），分母 `success` 只数做成的条数，`effective` 就是每成功任务成本。这里专门处理了 `success` 为零时返回 `None` 的边界——分母为零不能硬除，得有个明确约定，否则清单里那条比较会直接抛异常。
5. `build_checklist` 把发布前清单写成八条布尔表达式，每条都对应一个能当场判定的事实：上限大于零、轮数不超过十二、硬上限已配、比值已算出、比值未明显劣于基线、日志必填字段是超集、基线有成功记录、审批默认拒绝。注意「日志字段齐全」用集合的包含关系判断，`>=` 在这里是「左边集合包含右边集合」，比逐个比对字符串稳。
6. 基线对比那条写了 `current["effective"] is not None and ...`，两个条件用 `and` 串起来：先确认比值存在，再比大小。若当前版本一个任务都没做成，这一项就该判不通过，而不是让 `None` 混进数值比较里。这正是「清单要能自动跑」所要求的严谨——每一条都得在任何输入下给出真假，而不是偶尔抛异常。
7. `main` 第一组断言先把那个反直觉的结论钉死：v2 的单条花费、总花费都低于 v1，成功数也更少，但 `effective` 反而更高。还单独验证了「成功数为零时比值为 `None`」这条边界。这组断言不针对任何真实系统，只用来证明记账口径本身会改变结论。
8. 第二组验证清单：合格配置下八项全通过；把 `concurrency_cap` 改成 0、把 `log_fields` 删掉一个字段，两种破坏分别都能让 `all_pass` 变假，说明清单确实在「挡」而不是摆设。第三组把 v2 当作当前版本喂进去，尽管逐项配置都合格，基线对比那条硬项仍会把它挡住——这就是「单看每项都合格、整体却变贵」的防漏机制。
9. 结尾统一统计通过项数并逐条打印，任何一条不成立都会以非零状态退出。整段只用内置功能，把「按成功任务核算」和「可判定的发布前清单」这两件抽象的事，变成了能复制、能手算、能逐条核对的确定性例子。

如实说明一句：这里的计价参数、任务记录和检查项都是为讲清口径而构造的教学例子，不是任何真实报价；全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算核对。它演示的是分子该记全、分母只数成功、以及清单必须可判定且带基线对比，复制运行即可逐条看到这些性质是否成立。

## 踩坑与边界

- **只盯单次调用报价**：现象是账单降了、优化记录很漂亮，业务方却抱怨「更难用了」 → 原因是没按每成功任务核算，成功率下滑被单价下降掩盖了 → 把一段时间全部请求的花费做分子、只把做成的任务数做分母，把 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 的口径接进监控。
- **失败与重试的花费没进账**：现象是算出来「优化后成本大降」，实际支出却没怎么动 → 原因是统计时只累加成功请求，把失败任务与重试的花费藏了起来 → 所有请求一律计入分子，重试次数单独作为一个可观测字段，必要时配合 [重试退避与抖动](./k108-retry-backoff.md) 把次数本身压下去。
- **裁剪把不可压缩项一起裁掉**：现象是上下文变短了，任务却开始频繁返工、答非所问 → 原因是把系统规则、当前目标、刚拿回的工具结果也压进了摘要 → 只砍无关历史与冗余片段，保留不可压缩项并验证信息未丢，见 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 与 [压缩后信息丢失怎么验证](./k048-compression-verify.md)。
- **清单写成「注意事项」**：现象是每次发布都有人漏配一处，事后复盘谁都说「以为别人检查了」 → 原因是检查项没有可判定的通过条件，无法自动执行 → 每条改写成能算出真假的表达式，缺一项就挡住发布，日志字段这类要求对照 [结构化日志与轨迹回放](./k095-structured-log.md) 定成字段集合。
- **清单只过一次、不跟基线比**：现象是逐项都合格，整体每成功任务成本却比上一版高出一大截 → 原因是清单只衡量「有没有配」，没衡量「有没有变差」 → 把「当前比值不得明显劣于基线」列为硬项，并让清单随配置一起版本化，见 [回归门禁与基线](./k091-regression-gate.md) 与 [提示与策略版本化](./k113-prompt-versioning.md)。

还要分清两道约束：「成本优化」是持续把浪费挤掉的动作，「发布前检查清单」是一次性确认有没有漏配的门禁；前者追求更省，后者追求别把前面省下的又漏回去。而「支出硬上限」与「成本优化」也不是一回事——优化是让正常情况更便宜，硬上限是异常情况下「超线就切断、不只是报警」的最后一道，见 [生产失败模式清单与支出硬上限](./k150-failure-modes.md)。缓存能省下的那部分也别重复指望：只有稳定前缀命中时才生效，见 [前缀缓存与即时注入](./k050-prefix-cache.md)；把「同时在跑多少」也算进支出速度，则回到 [高并发与并发上限](./k115-concurrency.md)。清单能被自动判定，前提是每项都有可观测依据，这部分离不开 [健康检查与 SLO](./k114-health-slo.md)。

## 三句话小结

成本优化与上线检查清单，是把记账单位从「一次调用」换成「一个做成的事」，再把优化手段和发布前逐条可判定的检查项都定成不会靠记性的规矩。

关键做法是分子记全输入、输出、重试与工具调用、分母只数成功，优化只砍浪费不动能力，清单每条都能自动判定且带一条不劣于基线的硬项。

当系统只在本地跑离线任务、既没有按次计费也没有对外发布时，不必硬套这套核算与清单；但只要一次改动会改变对外行为和支出，这本账和这张单子就不能省。

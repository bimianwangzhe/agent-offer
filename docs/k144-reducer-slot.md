# Reducer 合并语义与分槽写入

## 一、场景提问

你搭了一个会分头干活的小程序：一个节点负责检索，一个节点负责核对，最后把结果汇总成一份状态。跑起来却发现，检索节点刚写进去的两条消息，被核对节点一写就没了；或者明明两个节点各写各的字段，最终状态里却只剩最后一个节点交上来的那一小截。你想加重试，结果同一条消息被追加了两遍；你想把中断前的状态存下来接着跑，读回来却又和当时的顺序对不上。你翻代码，每处写的都是「把这份字典塞进状态」这么一句，看起来人畜无害。为什么几处各写各的，最后会互相盖掉？

## 二、破误解

**不是「谁最后写谁生效」的先后问题，而是你从没定义过「同一份状态被写很多次时，到底按什么规则合成一份」。**

先把两个词说清。归约器（reducer，一段接收「旧值 + 一次新写入」、返回合并后新值的函数，白话讲像一条写死的填表规矩）负责回答「多次写入怎么合」：是后到的盖掉旧的、是把数值加起来、是把消息一条条接在后面、还是按某个标识去重。槽（slot，状态里一个有名有姓的栏位，各自绑定一条归约规则，白话讲像表格里分好的列）负责回答「写到哪儿」：目标是一个槽、轮数是一个槽、消息列表是一个槽、发现项是一个槽，写某槽时只经过这一槽的规则，碰不到别的槽。这两件事合起来，才让「多个节点往同一份状态里写」变成可预期的过程：每次写入先认槽，再走该槽的规则，产出新值，其余槽原样不动，见[结构化状态](./k046-structured-state.md)。

很多人的默认做法是把整份状态当成一个大字典，哪个节点算完就把自己那份字典整个塞回去。这相当于把「合并」这件事偷偷交给了「后写覆盖先写」这一条没写下来的规则：只要两个节点交回的字典字段不全，没被提到的那几个字段就被冲成空值；只要两个节点写同一个字段，先写的成果必定丢失。这类问题特别难查，因为它不报错、不抛异常，只是安静地少了一块，而且换个到达顺序，少的还不是同一块。更麻烦的是，一旦状态要落盘回放，这种「就地改一个大字典」的写法会让「当时到底是第几次写入、谁写的」无从追溯，见[检查点与重放](./k030-checkpoint-replay.md)。

所以要补的不是加锁、也不是约定「大家别同时写」，而是先把规则显式化：状态切成几个槽，逐槽写清楚它的合并语义，所有写入统一走「认槽 → 取旧值 → 过规则 → 存新值 → 留一条痕」这条路径。归约规则要写成不就地修改旧值的纯函数——读旧值、算出新值、返回新对象，而不是在原来的列表上直接追加。这一点看着是风格小事，实则是回放与追踪能不能对得上的前提：就地改会让历史快照跟着一起变，等你想复盘「第三步结束时状态是什么」，读到的却是最后一步的形状。至于哪些槽该用哪条规则，取决于字段本身的含义：单值的结论适合覆盖，轮数与计数适合累加，轨迹与消息适合追加，带稳定标识的记录适合按键去重。

## 三、生活类比

把它想成几个人合填一张旅行记账表。表不是一张空白纸，而是事先划好了几栏：当日花销、累计天数、行程备注、报销单据。每栏旁边还贴着一行小字，写明这栏怎么填：花销栏「每笔加上去」，天数额「记最新的那一天」，备注栏「一行行往下写，别涂掉前面的」，单据栏「按单号登记，同一个单号只记一次」。这样四个人同时填，各填各的栏，谁也不会把别人那栏擦掉。

对应关系要一条条对上。划好的栏，就是槽；栏旁边那行小字，就是每槽一条的归约规则；只往自己那栏写，就是分槽写入；几个人交回的不是「各自重抄的一整张表」，而是「我这一栏新增了什么」，这正是「写入只带增量、合并交给规则」的意思，也和[状态共享、冲突处理与失败恢复](./k120-shared-state.md)里「字段有唯一属主」的思路相接。反过来，如果规定每个人交表时都重抄一整张、以最后交的为准，那么先交的人没抄到的栏就凭空空了——这就是把整份状态整体覆盖的样子。

这个类比还能把「顺序」讲清楚。备注栏是一行行往下写的，甲先写、乙后写，与乙先写、甲后写，纸上两行的先后不同，读起来意思就有细微差别，这类规则对写入顺序敏感。单据栏按单号登记，同一个单号只记一次，谁先谁后、甚至同一张单据被递两遍，最终表上都只有一条，这类规则对顺序不敏感，也顺带把「重试导致重复写入」挡住了。真要在一个会被多个节点同时推进、还可能中断重放的系统里少踩坑，就该尽量让关键槽用后一类规则：带稳定标识再合并，而不是靠「谁先谁后」碰运气。表格里的「累计天数」还有个容易忽略的点：它只认最新值，若两份填写互相矛盾，就得先说清凭什么判谁新，这属于[冲突解决](./k071-conflict-resolution.md)要管的边界。

## 四、自绘示意图

:::figure 一次写入经过的路径
@flow
认槽|取该槽旧值|过归约规则|存回新值|留一条写入痕
:::

五格的关键在「取该槽旧值」和「过归约规则」必须成对：只取旧值却直接覆盖，等于没定规则；定了规则却不留写入痕，事后就说不清某一步的结果是怎么合出来的。最后一格也别省，它是回放与排障的共同依据。

:::figure 四种槽各自的合并语义
@stack
结论槽::单值，后到的写入覆盖旧值，只留最新
计数槽::数值，多次写入累加，重试前要带标识
消息槽::列表，逐条追加，返回新列表不就地改
发现槽::按键去重合并，同键以最后一次为准
:::

四行其实是四句自问自答：这个字段是单值还是集合？重复写一次该变还是不该变？写入顺序变了结论会不会跟着变？把这三问答完，规则基本就定下来了。第三行特意强调「返回新列表」，是因为就地追加会让旧快照一起被改动，回放时对不上。

:::figure 整份覆盖与分槽归约的差别
@compare
整份塞回大字典::没提到的字段被冲空|同槽先写必丢|顺序影响丢失哪块
逐槽走归约规则::未涉及的槽原样不动|同槽按规则汇聚|带标识可乱序重放
:::

左边三点是连着的：整体替换 → 字段不全就冲掉别人 → 谁最后谁说了算 → 换个顺序丢的不是同一块，于是问题难以复现。右边三点也是连着的：认槽 → 别的槽不受影响 → 同槽按写死的规则合 → 规则与顺序无关时，重放也能得到同一份结论。

## 五、层层追问

:::ask 那同一个槽被两个节点各写一次，到底该用哪条规则，会不会还是乱？
:::

不会乱，前提是「规则先于写入定好」，而不是等冲突发生了再判断。举四种最常见的选择：结论、目标这类单值字段，用覆盖，语义就是「以最新判断为准」；轮数、已处理条数这类数值，用累加，但要注意重试会让同一笔被加两次，所以累加的输入最好带稳定标识；消息、轨迹这类天然有序的记录，用追加，接受它对顺序敏感；带编号的发现项、单据、实体，用按键去重合并，同键覆盖、新键登记，见[实体摘要与去重](./k069-entity-summary.md)。真正会乱的情形是「这个槽没登记规则」或者「一次往好几个槽写还顺手改了别的字段」——前者容易静默退化成最后写入生效，后者把分槽的意义抹掉了。所以在代码里把「未登记的槽」直接判成错误，比默认收下更安全。再往下追一层：那如果两个节点对同一个单值槽给了互相矛盾的结论，覆盖规则只认「后到的」，万一「后到」只是网络慢了一点呢？这就说明覆盖规则本身把「谁更新」交给了到达顺序，而到达顺序在分布式或并发里并不代表业务上的新旧。要稳，就得让写入带上版本号或序列，由规则比较之后再决定取谁，而不是让网络延迟替你做判断，这与[幂等键](./k038-idempotency-key.md)用稳定标识识别同一次动作是同一套思路。

:::ask 那如果归约规则对顺序敏感，中断之后按另一种顺序重放，会不会得出不同结论？
:::

会，而且这正是分槽设计里最值得提前想清的一处。纯追加就是这样：甲先乙后，与乙先甲后，列表内容次序不同，读起来含义也随之变。如果这类槽还要参与「中断续跑」和「回放」，就得给它补一样东西：让每条写入自带稳定标识，合并时按标识排序或去重，使结果只取决于「写入了哪些条」，不取决于「它们按什么顺序到」。按键去重合并天然具备这个性质，所以带编号的记录适合它；纯追加若也想乱序重放一致，就得额外存一个可排序的序号，见[时间旅行与回放](./k145-time-travel.md)。再往下追一层：那是不是所有槽都该改成与顺序无关的规则？也不必。有些槽的意义本来就是「发生的先后」，比如对话轨迹，硬要排序反而丢了信息；对这类槽，正确做法不是改规则，而是把到达顺序本身记录成一条可复现的依据——写入痕里带上轮次或序列，重放时按这个序列喂给规则，让「顺序」变成被保存下来的输入，而不是碰运气的环境变量。顺带一提，消息槽无上限地追加会把状态撑大，这时该考虑的是截断与压缩的边界，见[上下文膨胀](./k049-context-bloat.md)；而把「哪几件交给谁管」的判断落到编排上，可对照[框架选型与自研编排的取舍](./k083-build-vs-framework.md)。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把「槽 + 归约规则」写成一份可运行的小状态容器：不同槽各按自己的规则合并，写某槽不碰别的槽，并演示整份覆盖为什么会冲掉字段、纯追加为什么对顺序敏感、按键去重与带标识合并为什么能乱序重放一致。复制成文件直接运行即可，不需要联网、账号或任何第三方包，也不依赖文章前面定义过的变量。

```python
# -*- coding: utf-8 -*-
"""Reducer 合并语义与分槽写入：每槽一条规则，写入只改自己那一槽。"""
import copy
from collections import OrderedDict


def overwrite(old, new):
    """覆盖规则：后到的值替换旧值，适合单值的目标、结论。"""
    return new


def add_int(old, new):
    """累加规则：适合轮数、计数这类数值槽。"""
    return old + new


def append_msg(old, new):
    """追加规则：返回新列表，保留先后，不在原对象上就地改。"""
    return list(old) + [new]


def merge_by_key(old, new):
    """按键去重合并：新值带 (键, 值)，同键覆盖，返回新字典。"""
    key, value = new
    result = OrderedDict(old)
    result[key] = value
    return result


def merge_once(old, new):
    """带标识合并：标识已存在就不写第二遍，用来挡住重试重放。"""
    rid, value = new
    result = OrderedDict(old)
    if rid in result:
        return result
    result[rid] = value
    return result


class Reducers:
    """把槽名映射到它自己的合并规则与初始值。"""

    def __init__(self):
        self.rules = {}
        self.initial = {}

    def slot(self, name, rule, initial):
        self.rules[name] = rule
        self.initial[name] = initial
        return self


class SlottedState:
    """一份分成若干槽的状态；每次写入只经该槽的规则。"""

    def __init__(self, reducers):
        self.rules = dict(reducers.rules)
        self.data = {k: copy.deepcopy(reducers.initial[k])
                     for k in reducers.rules}
        self.trace = []

    def write(self, slot, value, writer="anon"):
        if slot not in self.rules:
            raise KeyError("未登记的槽: " + slot)
        before = self.data[slot]
        after = self.rules[slot](before, value)
        self.data[slot] = after
        self.trace.append((writer, slot, value))
        return after

    def read(self, slot):
        return self.data[slot]

    def snapshot(self):
        out = {}
        for k, v in self.data.items():
            out[k] = dict(v) if isinstance(v, OrderedDict) else v
        return out


def naive_apply(state, patch):
    """反例：整份替换，旧字典里没被提到的字段全部丢失。"""
    return dict(patch)


def main():
    checks = []

    def ok(cond, name):
        checks.append((name, bool(cond)))

    reg = (Reducers()
           .slot("goal", overwrite, "")
           .slot("steps", add_int, 0)
           .slot("messages", append_msg, [])
           .slot("findings", merge_by_key, OrderedDict()))

    s = SlottedState(reg)
    s.write("goal", "整理报销单", "planner")
    s.write("steps", 1, "node_a")
    s.write("steps", 2, "node_b")
    ok(s.read("steps") == 3, "累加槽把两次写入合成 3")
    ok(s.read("goal") == "整理报销单", "覆盖槽保留最后一次目标")

    s.write("messages", "检索到两条规定", "node_a")
    s.write("messages", "需要人工复核", "node_b")
    ok(s.read("messages") == ["检索到两条规定", "需要人工复核"], "追加槽保留全部消息")
    ok(s.read("goal") == "整理报销单", "写消息槽没有碰到目标槽")

    s.write("findings", ("金额", "上限 600"), "node_a")
    s.write("findings", ("发票", "需原件"), "node_b")
    s.write("findings", ("金额", "上限 600 含税"), "node_c")
    ok(len(s.read("findings")) == 2, "按键合并让同键收敛成 2 项")
    ok(s.read("findings")["金额"] == "上限 600 含税", "同键以最后一次为准")
    ok(list(s.read("findings")) == ["金额", "发票"], "键的顺序按首次出现固定")

    whole = {"goal": "整理报销单", "steps": 3}
    clobbered = naive_apply(whole, {"steps": 4})
    ok("goal" not in clobbered, "整份覆盖把没提到的字段冲掉了")
    ok(s.snapshot()["goal"] == "整理报销单", "分槽写入下未涉及的槽原样保留")

    a = SlottedState(reg)
    b = SlottedState(reg)
    a.write("messages", "甲", "x")
    a.write("messages", "乙", "y")
    b.write("messages", "乙", "y")
    b.write("messages", "甲", "x")
    ok(a.read("messages") != b.read("messages"), "纯追加对写入顺序敏感")

    ka = SlottedState(reg)
    kb = SlottedState(reg)
    ka.write("findings", ("金额", "甲"), "x")
    ka.write("findings", ("发票", "乙"), "y")
    kb.write("findings", ("发票", "乙"), "y")
    kb.write("findings", ("金额", "甲"), "x")
    ok(dict(ka.read("findings")) == dict(kb.read("findings")), "按键合并对乱序不敏感")

    idem = (Reducers()
            .slot("receipts", merge_once, OrderedDict())
            .slot("steps", add_int, 0))
    r = SlottedState(idem)
    r.write("receipts", ("r-001", "已记"), "w")
    r.write("receipts", ("r-001", "已记"), "w")
    ok(len(r.read("receipts")) == 1, "带标识重放不产生重复记录")

    blocked = False
    try:
        s.write("unknown", 1, "z")
    except KeyError:
        blocked = True
    ok(blocked, "写未登记的槽被拒绝")

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. 开头五个函数是五条归约规则：`overwrite` 覆盖、`add_int` 累加、`append_msg` 追加、`merge_by_key` 按键去重合并、`merge_once` 带标识去重。共同点是都「读旧值、返回新对象」，`append_msg` 用 `list(old) + [new]`、`merge_by_key` 用 `OrderedDict(old)` 造副本，都不在传入的旧对象上就地修改，这样旧快照不会被后来的写入悄悄改掉。
2. `OrderedDict` 是标准库 `collections` 里的有序字典（能记住键第一次插入的先后），这里用它让「按键合并」既去重又保序，于是「键的顺序按首次出现固定」这条性质可以被断言直接验出来。
3. `Reducers.slot` 把「槽名 → 规则 + 初始值」登记下来并返回自身，所以能链式连写四行；`SlottedState.__init__` 按登记表造出各槽的初始数据，这里用 `copy.deepcopy` 逐份复制初始值，是为了让后面几个实例（对照用的 `a`、`b`、`ka`、`kb`）各自拿到独立的空列表与空字典，不共用同一个可变初值——若共用，某个实例的写入可能把别的实例的初值也带着改了。`self.trace` 用来留写入痕。`write` 是整段的关键：先查槽有没有登记，没登记直接抛 `KeyError`；再取旧值、过该槽规则、把新值存回这一槽、追加一条 `(写入者, 槽名, 值)`，其余槽一行都没碰。
4. 第一段断言验证「同槽按规则合、异槽不干扰」：`steps` 写 1 又写 2，累加得 3；`goal` 覆盖后仍是目标文字；`messages` 追加两条都在；写消息之后 `goal` 原样保留。这四条把「分槽」的意义从口号变成可核对的结果。
5. 第二段验证按键合并：`金额` 写两次、`发票` 写一次，最终收敛成 2 项，`金额` 取最后一次的值，且键顺序仍是首次出现的 `["金额", "发票"]`——因为 `OrderedDict` 对已存在的键只更新值、不挪动位置。
6. `naive_apply` 是刻意写下的反例：整份替换成 `{"steps": 4}`，`goal` 就没了；而同一份分槽状态 `s.snapshot()` 里的 `goal` 仍在。两条断言并排放，正是开头那个「字段凭空少一块」的最小复现。
7. 第三段验证顺序性质：两份状态把 `甲`、`乙` 反过来追加到消息槽，结果不相等，说明纯追加对到达顺序敏感；换成按 `金额`、`发票` 两个键乱序写入发现槽，转成普通字典比对却相等，说明按键合并与顺序无关。这对应前面追问里「要不要给顺序敏感槽补标识」的判断。
8. `merge_once` 演示幂等（idempotency，白话讲：同一个动作做一次和做几次，结果都一样）：同一条 `r-001` 写两遍，第二次发现标识已存在就直接返回，列表里只有一条。最后用 `try/except` 确认写未登记的槽会被拒绝；`ok` 收集全部性质，结尾逐条打印并输出「通过 N/N 项」，`assert` 保证任一条不成立都会以非零状态退出。

有一处要如实说明：这里用几个纯函数和一份内存字典代替真实框架里的状态容器，用固定字符串代替真实节点的产出，纯粹是为了让「认槽 → 过规则 → 存新值」这条链不需要联网、账号或第三方包就能独立跑通，且每一步结果都能手工推算。它演示的是合并规则怎么定、分槽为什么不串味、顺序敏感与不敏感的差别，不是任何具体框架的状态实现，也不是对某套配置优劣的结论。

## 七、踩坑与边界

- **整份状态整体塞回**：现象是两个节点各写各的字段，最终却只剩最后一小截，没被提到的字段悄悄变空 → 原因是把「合并」交给未写明的「后写覆盖」，节点交回的字典字段不全 → 怎么改：切成槽，每次写入只带本槽增量，统一走归约路径。
- **归约规则就地改旧值**：现象是落盘前的旧快照，读回来却已经是最后一步的形状，回放对不上 → 原因是追加或合并时直接在原列表、原字典上修改 → 怎么改：规则一律返回新对象，旧值只读，见[检查点与重放](./k030-checkpoint-replay.md)。
- **没登记规则还默认收下**：现象是某个新字段写进去后行为怪异，查不出它按什么规矩合的 → 原因是未登记槽被静默当成覆盖处理 → 怎么改：写入时先查登记表，未登记的槽直接判错，不让隐性规则混进来。
- **靠到达顺序判新旧**：现象是同一条结论，网络慢半拍的那次反而盖掉了更新的判断 → 原因是覆盖规则把「谁更新」交给了到达先后，而到达先后不代表业务新旧 → 怎么改：写入带版本或稳定标识，由规则比较后决定取谁，见[幂等键](./k038-idempotency-key.md)。
- **消息槽无上限追加**：现象是跑得越久状态越大，重放越慢，还把无关旧消息带进当前判断 → 原因是把轨迹当成只增不减的列表 → 怎么改：给这类槽设截断与压缩边界，见[上下文膨胀](./k049-context-bloat.md)。

还要说清边界。这套「逐槽定规则」针对「多个节点或多个轮次共同推进同一份状态」的系统；只有一个执行者、单轮跑完即弃的小脚本，把状态切成四五个槽、每个都写一条归约函数反而是负担，一个普通字典顺序写下来就够了。另一个常见误会是「加了归约规则就不会有冲突」——规则只保证「怎么合」是确定的，不保证「合出来的结论对」；两个节点给出互相矛盾的单值结论，覆盖规则照样会取一个，只是取得可预期而已，矛盾的判定仍要靠版本或属主约定，见[冲突解决](./k071-conflict-resolution.md)与[状态共享、冲突处理与失败恢复](./k120-shared-state.md)。还有一层：槽切得太粗，不同含义的字段挤在一槽里仍会互相盖；切得太细，规则多到没人维护得住，合适的粒度通常按「这个字段被谁写、重复写一次该不该变」来定。至于状态该怎么用节点和边表达、归约发生在图的哪一步，是[状态机与图编排](./k076-state-machine.md)接下去讲的事。

## 九、三句话小结

Reducer 合并语义与分槽写入，是把状态切成各有名分的槽、给每槽写死一条合并规则，让多次写入按可预期的方式汇聚，而不是互相盖掉。

关键做法是写入只带本槽增量、统一走「认槽 → 取旧值 → 过规则 → 存新值 → 留痕」，规则返回新对象不就地改，顺序敏感的槽补稳定标识，未登记的槽直接判错。

当只有一个执行者、单轮跑完即弃、也无需回放时，不必铺这套机制；但只要多个节点或多轮共同推进同一份状态，合并规则就得先于第一次写入定清楚。

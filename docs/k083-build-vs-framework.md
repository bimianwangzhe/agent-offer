# 框架选型与自研编排的取舍

## 一、场景提问

你照着一段示例，用某个现成框架三行就搭出一个能自己调工具的小程序，跑通了，心里挺踏实。可没过多久要加一条规矩：某类临时故障最多重试两次，而且每次重试之前必须先确认上一步没有真的写进去。你翻遍配置项，发现那个重试次数被写在框架内部，改不动。组里有人说「那就别用框架了，自己手写一圈循环，什么都可控」，于是你们真的推倒重来，结果花在状态存取、逐轮留痕、中断续跑上的工夫，比原本那三行多出许多，还冒出一堆「同一条数据被写两遍」的新毛病。到底该用现成的，还是自己写？换一个框架，能不能躲开这个问题？

## 二、破误解

**不是「框架好用」或「框架是黑盒」这种二选一，而是你没先点名框架究竟替你接管了哪几件事，就把「选工具」当成了「定架构」。**

先把词说清。框架（framework，把一批通用能力打包好、只留业务细节给你填的可复用代码，白话讲像一台预装好流水线的机器）省下的工夫是真的；编排（orchestration，决定下一轮做不做、把动作分给哪个工具、把结果写回状态、什么时候停的那一层调度逻辑，白话讲像流水线上那个喊口令的调度员）也是真的。这两样都没有凭空消失，只是被收进了框架内部，逐件摆开可以看[框架六大件](./k075-framework-six.md)。很多人以为选型要回答的是「哪家示例更短、支持的工具更多」，于是比较一直停留在上手那几行；可真正决定日后痛不痛的，是那几件被接管的规矩——状态怎么存、循环怎么转、失败怎么兜、轨迹怎么留——能不能单独拿回来改。

所以取舍的判断线不该画在「用不用框架」上，该画在「哪一件我必须自己握着」上，分四步走。第一步，逐件点名：把状态、循环、工具分发、追踪、重试、持久化这六件写进自己的设计说明，标出每件现在由谁管、默认值是多少。第二步，逐件问一句「这一件的默认规矩，和我的场景冲突吗」，比如涉及写操作时，超时后的重试必须先对账而不能直接重做，这一条就常常和框架的默认重试对不上。第三步，看框架允不允许把冲突的那一件单独替换；允许，就替换它，其余照用；不允许但规矩又非改不可，才把这一件拿回来自己写。第四步，把业务计划——也就是「下一步该做哪个动作、什么算做完」这部分判断——写在不依赖框架具体形状的地方，让编排只是一层薄薄的壳。这四步走完，你会发现多数情况下既不用全盘照用，也不用全盘重写，而是「大部分交给框架，只有一两件自己握着」。

两个极端各有各的代价，值得摆明。全盘照用最省事，代价是规矩被藏在默认值里，一旦场景从「只读、单轮、跑完即弃」变成「有写操作、跨进程、长任务」，你会发现想改的那一处正好动不了，而此时业务代码已经长在框架的形状上，动一处牵全身。全盘自研最自由，代价是六件的正确性都落到你头上：状态要能按字段续跑，重试要配稳定标识以免重复写，轨迹要能回答「当时到底选了哪个工具、传了什么参数」，持久化要能在进程重启后读回来。这些都不是三行代码能兜住的，写漏一件，排障时就少一条线索。更重要的是，「自己写」并不会让版本影响消失，只是把「框架升级带来的漂移」换成了「你自己维护的那层代码的兼容性」，见[版本漂移与升级策略](./k084-version-drift.md)。看懂六件，是为了能比较、能替换，不是为了非得亲手实现一遍。

## 三、生活类比

把这件事想成装修一套房子。你可以整包给装修公司：水电、泥瓦、木工、验收排成一套固定工序，你只要签合同、挑家具，按期收房，这是「全盘照用」。你也可以自己买材料、分别找水电工和木工、自己排先后、自己盯每一道验收，这是「全盘自研」。而第三条路是：大部分工序仍交给公司，但在合同里指定「厨房的插座位置与防水做法由业主另给图纸」，也就是「逐件替换」。

对应关系要一条条对上。装修公司那套固定工序，就是框架接管的六件默认规矩；你坚持要自己画图的那一处，就是与场景冲突、必须自己握着的那一件；合同里「允许业主指定某处做法」这一条，就是框架允不允许逐件替换——有的公司允许，有的合同写着「工序不可拆」，这正好对应不同框架在这件事上的差别，也是[解耦适配层](./k077-adapter-layer.md)要补的缺口。你的家具清单和每个房间打算怎么用，是业务计划：它只描述「要什么」，不依赖谁来施工，所以换一家公司照样能用。施工日志与验收单，是追踪与状态：哪天做了哪一步、用了什么料，出问题时全靠它回答「当时到底怎么弄的」。整包最省心，但你想把插座挪半米时会被一句「工序定死了」挡回来；全自己找工人最自由，可你得自己排工序、自己盯验收，漏掉一遍防水闭水试验，住进去才发现问题。这个比喻还点出一个常被忽略的细节：真正贵的不是「改那一处」本身，而是收房之后才发现改不动——所以「能不能逐件替换」要在签合同之前问，而不是等墙砌好了再问。

## 四、自绘示意图

:::figure 一次取舍要走完的判断顺序
@flow
点名接管的件|问哪件必须握着|看能否逐件替换|能换就接着用|不能换才自己写
:::

这五格的关键在顺序，而不在某个结论。第二格「问哪件必须握着」容易被跳过：很多人直接从「点名」跳到「选哪家用」，中间少了对场景冲突的判断，于是选型又变回比示例长短。第三格是分水岭，它把一个问题拆成两个可回答的小问题——「冲突在哪」「能不能单独换」，比笼统地问「这框架好不好」有用得多。

:::figure 逐件要问清的四件事
@stack
状态谁存::字段归谁写，中断后能不能按字段续跑
循环谁转::下一轮做不做、什么时候停由谁定
失败谁兜::临时故障重试几次，超时要不要先对账
轨迹谁留::每轮输入与选择是否记成可查的结构化行
:::

四行里最容易被漏的是「失败谁兜」。它平时不出声，一旦有写操作就变成最贵的那一件：请求超时不等于动作没发生，重试前不对账，同一动作会被执行两次。这类规矩往往和框架默认实现冲突，也正是最需要自己握着的候选，相关思路可对照[循环状态与轮次](./k027-loop-state.md)和[结构化状态](./k046-structured-state.md)。

:::figure 全盘照用与逐件权衡的差别
@compare
全盘照用::上手最快|默认规矩被藏起|要改时动不了
逐件点名::能比较差异|业务计划可迁移|只换冲突那一件
:::

左边三点是连着的：上手快 → 规矩不必去看 → 等要改时才发现没处下手。右边三点也是连着的：逐件点名 → 能说清差异在哪 → 于是只替换冲突的那一件，其余照用。两行的差别不在勤奋程度，而在「出问题时能不能定位到具体是哪一件的规矩不合适」。

## 五、层层追问

:::ask 那一开始就全自己写，是不是最可控、以后也不用受框架版本影响？
:::

「可控」要拆开看才不会误导人。全自己写，确实把每一行的可见性都拿到了手里，但同时也把六件的正确性都接了过来：状态字段怎么约定、循环靠哪两个条件收手、临时故障重试几次、每轮留痕留哪些字段、快照写到哪里、重启后怎么读回来，每一件写漏一点，排查时就少一条线索。更实际的一层是，「不受版本影响」这个说法并不成立：你不再跟着框架升级走，却要维护自己那层代码的兼容性，工具协议一变、模型返回结构一变，改动照样落到你头上，只是没有别人替你先趟一遍，见[工具协议](./k078-tool-protocol.md)。再往下追一层：那如果只想把其中一件拿回来、其余仍交给框架呢？这恰恰是更常见的答案，前提只有一个——框架允许把那一件单独替换。能替换，说明六件之间走的是明确接口，边界清楚；不能替换，说明它们缠在一起，动重试次数连循环终止条件都跟着变。所以看一个框架，与其数它有多少现成能力，不如问「这六件我能不能各自拿回来」，答案会直接决定要不要补一层隔离，把业务代码与框架的具体形状隔开。

:::ask 那框架默认规矩正好合用时，是不是就什么都不用管了？
:::

合用也要留两样东西：可观测和可替换。可观测，指默认值再合适，你也要能看见它实际做了几次重试、状态被写成了什么、每轮选了哪个工具；否则场景一变，你连「变的是哪一步」都说不清，只能靠猜。可替换，指业务计划别长在框架的形状上，把编排写成一层薄壳、把「下一步做什么」写成独立的判断，这样哪天默认规矩不再合用，换掉壳即可，业务计划一行不用改，这也是[决策循环](./k023-decision-loop.md)里把「决定」和「执行」分开的同一套想法。再往下追一层：那怎么提前知道以后会不会变？没人能提前知道，但可以做一件不亏的事——把状态、重试、轨迹、停止判定做成可注入的部件，用的时候传默认值，需要时传自己写的版本。这样「合用」是当下的结论，不是把自己锁死。顺带一提，逐轮留痕不只是为了排障，它还是中断续跑和回放的前提，见[检查点与重放](./k030-checkpoint-replay.md)与[时间旅行与回放](./k145-time-travel.md)；而「哪几件交给谁」的最终判断，通常要落到可验证的约束上，可对照[约束、权衡与可验证结果](./k123-tradeoffs.md)。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把「编排」写成几个可注入的部件，演示同一份业务计划分别跑在框架式打包与自研式循环下结果一致，以及「只换重试件」「只换停止判定」这两次逐件替换。工具是本地确定性桩函数（桩函数，指用一段固定行为替代真实外部服务的替身），前几次故意抛临时故障，让替换的差异在断言里看得见。复制成文件直接运行即可，不需要联网、账号或任何第三方包，也不依赖文章前面定义过的变量。

```python
# -*- coding: utf-8 -*-
"""框架选型取舍：把编排拆成可逐件替换的部件，业务计划不动。"""
import json


class TransientError(Exception):
    """代表一次临时故障：重试有机会成功。"""


def make_add_tool(fail_times=0):
    """确定性工具桩：前几次抛临时故障，之后每调用一次把计数加一。"""
    counter = {"n": 0}

    def add(state):
        counter["n"] += 1
        if counter["n"] <= fail_times:
            raise TransientError("临时故障")
        state["value"] += 1
        return state["value"]

    return add


def business_plan(state):
    """业务决策：只回答下一步用哪个工具，属于必须自己握着的那一件。"""
    return "add"


class RetryNever:
    """重试件的一种实现：从不重试，故障直接向外抛。"""

    def call(self, fn, state):
        return fn(state)


class RetryTwice:
    """重试件的另一种实现：临时故障最多再试两次。"""

    def call(self, fn, state):
        last = None
        for _ in range(3):
            try:
                return fn(state)
            except TransientError as exc:
                last = exc
        raise last


def default_stop(state, goal, max_steps):
    """默认停止判定：达到目标值或走到步数上限就收手。"""
    return state["value"] >= goal or state["steps"] >= max_steps


def run_with_parts(plan, tools, retry, stop, goal, max_steps=10):
    """把编排写成可注入部件的循环：换掉某一件，plan 一行都不用改。"""
    state = {"value": 0, "steps": 0}
    trace = []
    while not stop(state, goal, max_steps):
        tool_name = plan(state)
        retry.call(tools[tool_name], state)
        state["steps"] += 1
        trace.append((state["steps"], tool_name, state["value"]))
    return state, trace


def framework_orchestrator(plan, tools, goal):
    """框架式：把默认部件打包，调用方只传业务决策与工具。"""
    return run_with_parts(plan, tools, RetryNever(), default_stop, goal)


def self_built_orchestrator(plan, tools, goal, retry, stop, trace_out):
    """自研式：手写同样的循环，但把重试与停止换成传进来的实现。"""
    state = {"value": 0, "steps": 0}
    while not stop(state, goal, 10):
        tool_name = plan(state)
        retry.call(tools[tool_name], state)
        state["steps"] += 1
        trace_out.append((state["steps"], tool_name, state["value"]))
    return state


def main():
    checks = []

    def ok(cond, name):
        checks.append((name, bool(cond)))

    goal = 3
    state_fw, trace_fw = framework_orchestrator(
        business_plan, {"add": make_add_tool(0)}, goal)
    ok(state_fw["value"] == goal, "框架式编排达到目标值")
    ok(len(trace_fw) == goal, "框架式追踪逐轮留痕")

    custom_trace = []
    state_sb = self_built_orchestrator(
        business_plan, {"add": make_add_tool(2)}, goal,
        RetryTwice(), default_stop, custom_trace)
    ok(state_sb["value"] == goal, "自研式编排也达到目标值")
    ok(state_sb == state_fw, "换编排不改业务计划，两份状态一致")
    ok(len(custom_trace) == goal, "自研式追踪同样逐轮留痕")

    flaky = {"add": make_add_tool(1)}
    blocked = False
    try:
        run_with_parts(business_plan, flaky, RetryNever(), default_stop, goal)
    except TransientError:
        blocked = True
    ok(blocked, "默认不重试件遇到临时故障会中断")
    state_ok, _ = run_with_parts(
        business_plan, {"add": make_add_tool(1)},
        RetryTwice(), default_stop, goal)
    ok(state_ok["value"] == goal, "只换重试件就能继续跑完")

    def stop_at_two(state, g, m):
        return state["steps"] >= 2

    state_two, trace_two = run_with_parts(
        business_plan, {"add": make_add_tool(0)},
        RetryNever(), stop_at_two, goal)
    ok(state_two["steps"] == 2, "自定义停止判定在两轮后收手")
    ok(len(trace_two) == 2, "追踪步数与停止判定一致")

    blob = json.dumps(state_fw, sort_keys=True)
    ok(json.loads(blob) == state_fw, "状态可序列化并原样还原")

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `make_add_tool` 用闭包里的 `counter` 记住被调用过几次：前 `fail_times` 次抛 `TransientError`，之后每次把 `state["value"]` 加一。它是本地确定性桩函数，把「外部服务偶尔抖动」这件事做成可复现的固定行为，全程不联网、不调外部地址。
2. `business_plan` 是被刻意独立出来的那一件：它只回答「下一步用哪个工具」，不碰状态字段、不碰循环、不碰重试。这就是「业务计划不依赖框架形状」的落点——后面换几次编排，这个函数一行没改。
3. `RetryNever` 与 `RetryTwice` 是同一件能力的两种实现，接口都是 `call(fn, state)`。能被互换靠的是这个一致的小接口，而不是靠谁继承了谁；`RetryTwice` 里 `for _ in range(3)` 表示最多三次尝试，三次都失败就把最后一次异常抛出去。
4. `default_stop` 把「什么算做完」和「最多走几轮」合成一个判定，两个条件一起看，避免目标达不到时循环跑飞；`run_with_parts` 则是那层薄壳：`while` 里读计划、调工具、写状态、留一条痕，四件事都通过传进来的部件完成。
5. `framework_orchestrator` 与 `self_built_orchestrator` 分别代表两种姿势：前者把默认部件打包、调用方只传业务决策和工具；后者手写同样的循环，但把重试和停止改成外部传入。两者跑出的 `state` 用断言比对相等，说明换掉编排的壳，业务结论不变。
6. `main` 里第一段让框架式跑到目标值，并确认追踪条数等于轮数；第二段让自研式在一个「前两次调用都失败」的工具上，靠 `RetryTwice` 照样跑到目标值，且状态与框架式完全一致，追踪条数也一致。
7. 接着做两次逐件替换：同一个会抖一次的工具，配 `RetryNever` 会被故障挡下（用 `try/except` 接住并记为 `blocked`），换成 `RetryTwice` 就能跑完；再传一个自定义 `stop_at_two`，循环两轮就收手，追踪里也正好两条。这两处演示的正是「只换冲突的那一件」。
8. 最后把状态用 `json` 序列化再读回，验证它能原样还原——`json` 指 JavaScript Object Notation，一种纯文本的数据表示格式，这里用它代表「状态可落盘、能交给别的编排器接续」。`ok` 收集每条性质，结尾逐条打印并输出「通过 N/N 项」，`assert` 保证任何一条不成立都会以非零状态退出。

有一处要如实说明：这里用一小段确定性函数代替真实模型与外部工具，用两个小类代替框架里成套的重试配置，纯粹是为了让整条链不需要联网、账号或第三方包就能独立跑通，并且每一件被替换后发生什么都能手工推算。它演示的是「业务计划与编排壳可以分开、部件能逐件替换」这条判断线，不是任何具体框架的实现，也不是对某套配置好坏的结论。

## 七、踩坑与边界

- **拿示例长短当选型标准**：现象是挑了个三行能跑通的方案，接上写操作后想改重试次数却找不到入口 → 原因是比较只停在上手成本，没点名被接管的六件规矩 → 怎么改：先把状态、循环、分发、追踪、重试、持久化逐件写进设计说明，再拿这份清单去核对。
- **一冲突就全盘重写**：现象是只因为一处重试规矩不合用，就把状态、轨迹、持久化全自己写，结果重复写、中断接不上等新毛病接连冒出 → 原因是把「某一件冲突」误当成「整套都不能用」 → 怎么改：先确认框架允不允许单独替换那一件，允许就只换它，必要时补一层隔离。
- **业务计划长在框架形状上**：现象是想换一种编排方式，发现连「下一步做什么」的判断都得跟着重写 → 原因是业务代码直接读写框架内部字段、依赖它的私有结构 → 怎么改：让业务计划只通过明确接口拿状态、只返回动作名，编排作为薄壳注入，见[工作流与智能体的分界](./k022-workflow-vs-agent.md)。
- **默认规矩合用就不留观测**：现象是场景一变，说不清究竟是重试次数变了还是状态被写岔了 → 原因是默认实现被当成空气，没有逐轮留痕、也没有可查的当前状态 → 怎么改：每轮把输入、选中的动作、结果记成结构化行，把状态写成可序列化的字段，见[结构化状态](./k046-structured-state.md)。
- **把自研当成躲开升级**：现象是以为不用框架就没有兼容问题，结果工具返回结构一变，自己那层代码照样要改，还没人先趟过 → 原因是版本影响只是换了承担者 → 怎么改：承认漂移总在，用适配层把变化挡在业务代码之外，见[版本漂移与升级策略](./k084-version-drift.md)。

还要说清边界。这套逐件权衡针对「要长期改动、会接真实写操作、可能跨进程或长任务」的系统；一个只读、单轮、跑完即弃的小脚本，把六件逐件点名一遍反而是负担，照现成示例用就好。另一个常见误会是「框架会替我决定何时该停」——什么算做完属于业务判断，框架最多给个步数上限，标准还得你给，这与[决策循环](./k023-decision-loop.md)里「终止条件要自己写死」是同一回事。还有一层：逐件替换能不能做到，取决于六件之间有没有明确接口；若发现动一件牵全身，先别急着重写，补隔离往往更省，见[解耦适配层](./k077-adapter-layer.md)。而状态该按什么语义合并、多个来源同时写怎么办，是[Reducer 合并语义与分槽写入](./k144-reducer-slot.md)要接下去讲的事。

## 九、三句话小结

框架选型与自研编排的取舍，是先把框架接管的几件事逐件点名，再判断哪一件与场景冲突、能不能单独替换，而不是在「全盘照用」和「全盘重写」之间站队。

关键做法是让业务计划独立于编排壳、把状态与重试与轨迹做成可注入的部件、冲突时只换那一件，并用断言验证换壳前后结论一致。

当系统只读、单轮、跑完即弃，也无需长期改动时，不必铺这套权衡，照现成示例用更省事；但只要一次改动会牵动真实写操作，那条「哪件必须自己握着」的线就得先画清楚。

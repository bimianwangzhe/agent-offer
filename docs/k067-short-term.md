# 短期记忆与滑动窗口：最近几轮原文为什么留不住早期的约束

## 场景：规矩明明说过，聊到后面就不管用了

你给助手定了个很省事的办法：每轮把原文追加进一个列表，但只保留最近四轮，超了就把最老的一条丢掉。第一轮用户说「回答一律不超过三句、只用中文」，跑起来一切正常。聊到第十轮，用户问了个稍微复杂的问题，助手回了一整屏英文，还分了四五段。你把窗口里的内容打印出来一看，那句「不超过三句」早就不在了，剩下的是最近几轮的问答和一次工具回显。你没改过任何提示，也没换过模型，规矩却像从没存在过。

## 先破一个最常见的误解

**不是模型不守规矩，是那条规矩被窗口按「先来后到」挤出去了。** 短期记忆指的是把最近若干轮对话原文原样保留下来，它的取舍标准只有位置：谁最旧谁先走。它完全不看内容价值，一句硬约束和一句「好的收到」在它眼里没有区别，只要排到了最左边，都会被同样地丢掉。这跟「记忆」这个词给人的直觉正好相反——我们以为记着的东西会一直管用，实际上这种存法只保证「最近发生过什么还在」，不保证「一直该生效的东西还在」。想明白这一点，很多玄乎的排查就能收拢成一句：早期约束有没有被当成普通一轮、跟着窗口一起滑走。滑动窗口本身没错，错的是把本该长期生效的东西托付给了一个只按位置决定去留的容器。

## 用生活里的事打个比方：只放得下四张便签的桌面

把短期记忆想成收银台上那块只贴得下四张便签的小板子。每来一位顾客（相当于新的一轮），店员就在最右边贴一张新便签，板子满了，最左边那张就被挤掉进废纸篓。第一张便签上写的是「找零一律四舍五入到角」，这是店里的硬规矩；可它最旧，所以第一批被挤掉。对应关系逐条对一遍：板子容量就是窗口大小，四张就是「保留最近四轮」；一张便签就是一轮原文；挤出规则只看贴上去的先后，不看上面写的是规矩还是闲聊；掉进废纸篓的内容不会再被读第二遍。为什么不能靠「多看两眼」解决？板子物理上就那么大，你没法既贴第五张又留住第一张。想守住那条硬规矩，只有两条路：要么把板子加大，但总有再次被挤掉的一天；要么把规矩从便签体系里拿出来，抄进一本不会被每天清台的册子里。后者才是治本的办法，也正好说明了短期窗口该管什么、不该管什么。

## 画出来看

先看一轮新内容进来时发生了什么，留意「挤出」这一步是自动的、无差别的。

:::figure 一轮原文推入时窗口怎么变
@flow
新的一轮|从右推入|挤出最左|窗口定长|早期约束消失
:::

「窗口定长」是这套做法最大的优点：无论聊多久，占用的篇幅都是一个常数，不会随着轮数越滚越大。「早期约束消失」则是它必然的代价，两者来自同一个机制，没法只要好处。再看它和长期事实的差别。

:::figure 两种内容的去留方式
@compare
滑动窗口::按位置去留|实现最省|早期约束会丢
稳定事实::按价值去留|跨会话保留|不随轮数丢
:::

两行摆在一起，是想把「最近发生过什么」和「一直该生效什么」彻底分开。前者按位置滚动，后者按价值沉淀，用同一个容器同时装这两类，就一定会顾此失彼。被滑动窗口挤掉的那条硬约束，正确的归宿正是右边那一行的处理方式。

## 再往下追两层

:::ask 追问一
那把窗口从四轮调到四十轮，是不是就不会丢了？
:::

只是把丢失往后推。规矩在第一轮，只要对话足够长，它照样会被挤出去；而且窗口越大，每轮要带进输入的原文就越多，可用的位置被这些旧问答占满，本轮真正要处理的材料反而被挤到边上。更要紧的是，长长一段材料里，夹在中间的那些句子本来就不容易被留意到，把硬约束埋在几十轮原文的中段，并不比放在开头更保险。所以调大窗口是个缓解手段，不是解法。真正的分界线在于：这条内容是不是只在「最近几轮」有意义。是，就让它随窗口滚动；不是，就别交给窗口。

:::ask 追问二
那早期约束到底该怎么保住？
:::

别指望窗口，改在写入时就把会长期生效的内容单独提炼出来。用户第一轮那句「不超过三句、只用中文」，在进窗口的同时，还应该被判定成一条稳定事实，放进不随会话清空、按主题更新的那一层——这正是[工作 / 情景 / 语义三层记忆](./k066-memory-types.md)里语义层的位置，判定手续见[写入判定：什么时候该记](./k070-write-decision.md)。提炼出来的条目每轮按需带一小份，而不是靠整段原文去碰运气；带多少、按什么顺序带，是[召回排序与相关性](./k072-memory-recall.md)要处理的事。窗口本身继续只干它擅长的活：说清最近这几轮发生过什么。至于「全存下来为什么也不等于记住」，可以回到[记忆不是日志](./k065-memory-vs-log.md)再对一遍。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，用一个定长容器演示五轮原文推入后早期约束被挤出的过程，结尾用断言把三条性质钉住。复制成 `.py` 直接运行会打印窗口内容。

```python
from collections import deque


class ShortTermMemory:
    def __init__(self, size: int):
        self.window = deque(maxlen=size)

    def push(self, turn: str):
        self.window.append(turn)

    def context(self) -> list:
        return list(self.window)


if __name__ == '__main__':
    stm = ShortTermMemory(size=4)
    turns = [
        "约束：回答一律不超过三句",   # 早期约束
        "用户问天气",
        "模型答晴",
        "用户问汇率",
        "模型答 7.2",
    ]
    for t in turns:
        stm.push(t)
    ctx = stm.context()
    # 断言 1：窗口始终不超过 N
    assert len(ctx) == 4
    # 断言 2：最早的约束已被滑出窗口
    assert "约束：回答一律不超过三句" not in ctx
    # 断言 3：最近一轮还在
    assert ctx[-1] == "模型答 7.2"
    print("窗口内容：", ctx)
    print("通过 3/3 项")
```

1. `from collections import deque`：双端队列是标准库里自带定长能力的容器，`maxlen` 一设，超出时从另一端自动弹出，不用自己写「删掉第 0 条」的逻辑。
2. `deque(maxlen=size)`：这个 `size` 就是那块便签板的容量。它把「窗口定长」变成了容器自带的性质，而不是靠每次推入后手动检查，少一处出错的机会。
3. `push` 与 `context`：一个负责把一轮原文从右端推进去，一个把当前内容转成普通列表交出去。接口刻意做得很窄，调用方拿不到「删哪条」的选择权，因为按位置去留本来就不该有选择。
4. `turns = [...]`：五条手工构造的数据，第一条故意是那句硬约束，后面四条是普通问答。推完五条、容量为四，第一条必然出局——这是可复现的构造场景，不是从哪份真实记录里摘的。
5. 三条 `assert`：分别钉住「长度恒为容量」「最早那条已不在」「最近一轮还在」。断言写的是窗口的性质，换一批数据照样成立，适合当回归用。
6. 末尾 `print`：把窗口内容打出来，肉眼就能确认那句约束确实不在了，而不是只看到一句「通过」。

## 踩过的坑与边界

- **把硬约束当普通一轮塞进窗口**：现象是聊到十几轮后规矩失效 → 原因是窗口按位置去留，不看内容价值 → 把会长期生效的内容在写入时单独提炼成稳定事实，窗口只留最近原文。
- **窗口大小凭感觉定**：现象是调大之后成本明显上去、早期约束照样丢 → 原因是没意识到调大只是推迟丢失、还占掉本轮额度 → 先按「最近几轮才有用」来定容量，长期内容另走一层。
- **工具返回大段原文也整段推进去**：现象是刚推一轮就把前面几轮全挤没了 → 原因是按轮数而不是按内容量计，一轮里塞了太多字 → 工具结果先提炼成简短可判定的一行再进窗口，原文留在日志里。
- **以为窗口就是记忆的全部**：现象是用户换个会话再来，之前说过的话一句都不记得 → 原因是窗口只活在本次会话内 → 需要跨会话保留的内容走长期存储，见[长期记忆与向量化存储](./k068-long-term.md)。
- **窗口滑动后没重新注入约束**：现象是同一句规矩有时管用有时不管用 → 原因是它只在第一轮出现过一次 → 让稳定事实每轮按需带一小份，而不是指望最早的原文还在。

边界也要说清：滑动窗口适合「只关心最近发生了什么」的场景，比如接着上一句把指代接上、记住刚问过的那个型号。它便宜、定长、好实现；但任何「一直该生效」的东西都不该托付给它。

## 三句话小结

短期记忆是把最近若干轮原文原样留着，靠定长窗口按位置去留，便宜但会滑掉早期约束。
做法是让窗口只管「最近发生过什么」，把一直该生效的内容在写入时提炼成稳定事实另行保存。
需要跨会话保留、或内容本身长期有效时，别指望窗口，改用长期存储。

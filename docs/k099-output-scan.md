# 输出扫描与内容过滤

## 场景提问

你让助手整理一段客服回复，它输出得挺像样，前端直接把这段文本当成富文本渲染到了页面上。没过几天，有人发现页面里能弹出莫名其妙的提示框——追下去才发现，某次模型生成的回复里混进了一段脚本标签，前端照单全收地插进了文档。另一次更隐蔽：助手在解释订单时顺手把一串内部凭据写了出来，用户截图发到了别处。你翻遍提示词，明明写了「不要输出敏感信息」，可它还是输出了。

## 先破一个误解

**不是模型「忘了规矩」，而是你把「对外发送前的清洗」这件事交给了模型自觉；生成和审查用同一个概率性的脑子，盲区是共享的。**

这里讲的是输出侧护栏：内容真正发出去之前，由确定的代码规则再扫一遍、按目标场景做编码与脱敏。要先接受一个前提：模型的输出，无论看起来多规矩，都该当成一段不可信文本。它可能携带超文本标记语言标签（HyperText Markup Language，简称 HTML，用来描述网页结构的标记）、链接地址、结构化查询语言片段（Structured Query Language，简称 SQL，操作数据库的语言）、命令行片段，甚至从检索材料里带出来的敏感串。这些不是「模型学坏了」，而是它被输入里的内容、被上下文里的示例、被一次采样带偏了而已。

为什么不能靠提示词里那句「不要输出敏感信息」？因为它是请求，不是约束。请求可能被忽略、被后文覆盖、被注入内容反过来改写，见 [直接提示注入](./k097-direct-injection.md)。更关键的一层：让同一个模型既生成、又审查自己的输出，两件事共享同一套理解方式和同一批盲区——它当初为什么会写出那段脚本，审查时大概率也判断不出那段脚本有问题。真正可靠的判决必须来自一段不依赖模型判断的确定性代码：协议白名单、标签清洗、正则脱敏、按目标上下文转义。这套东西和传统网页安全里防跨站脚本（Cross-Site Scripting，简称 XSS，指把恶意脚本注入到别人会看到的页面里执行）的做法是同一套，不是新发明。

## 用出港前的安检来类比

把「模型生成内容」想成一件要装上货机、发往外部的包裹。模型是打包的人，手脚快、脑子活，但你没法保证它每次都记得把不该放的东西挑出来——它忙起来会把仓库里顺手拿到的单据也塞进箱子。

提示词里那句「别放敏感东西」，相当于贴在打包台墙上的一张提醒纸条。多数时候有用，但它只是提醒，不是检查。真正管事的是出港前那道安检机：传送带把每个箱子过一遍，机器按固定规则识别金属、液体、超规物品，识别出来要么开箱取出、要么整箱扣下。安检机不会「理解」这件货是干什么用的，它只认规则，正因为不靠理解，才不会被一句漂亮话糊弄过去。

对应关系拆开：打包的人 = 模型；墙上的提醒 = 系统提示词里的约束；仓库里顺手拿到的单据 = 从上下文、检索片段、工具结果里混进来的敏感串；安检机的识别规则 = 协议白名单、标签清洗、脱敏正则；「开箱取出」= 把危险片段替换成占位；「整箱扣下」= 命中高危特征时直接拦截、不予发出；传送带尽头的放行章 = 一段可以核对的「干净」状态。

这里最要紧的一点是：安检机在打包的人**之外**。它不读打包人的心思，只看箱子里实际有什么。翻回程序语言，就是「扫描函数读的是输出字符串本身，而不是模型对这段输出的自我评价」。而且安检要按「箱子最终去哪儿」来定规则：发到网页上要防脚本和危险协议、发到纯文本短信里要防换行注入、发到数据库要落到固定模板与参数化查询、发到命令行要换成参数明确的领域工具。同一段文本，目的地不同，编码方式也不同，这叫「按目标上下文做输出编码」，一刀切地全局替换往往既漏又误伤。

## 把这条链画出来

先看一段内容从生成到对外，中间该卡在哪。

:::figure 一段内容从生成到对外该过的关卡
@flow
模型产出内容|进入发送前检查|命中危险特征|清洗或直接拦截|才允许对外
:::

图的重点是第二格和第五格：扫描必须发生在「对外」这个动作**之前**，且是强制经过的一站，不是可跳过的一步。很多人把过滤放在「模型生成之后、心里觉得没问题就发」，那等于没有独立关卡。程序结构里应当让「发送」这个动作只有一个入口，而入口内部第一件事就是调用扫描函数，这样任何路径都绕不过去。

再看两种做法的差别。

:::figure 只审输入 与 发出前确定性扫描
@compare
只审输入不审输出::输出直接渲染到页面|脚本与危险协议漏过|泄露已发生才发现
发出前确定性扫描::按目标上下文编码|敏感串按规则脱敏|判决落在内容状态
:::

左边那行是常见的侥幸：把力气全花在「别让坏东西进来」，却默认「出去的都干净」。可输入侧再严，也挡不住模型从检索片段、工具返回、历史上下文里带出来的东西。右边那行的关键是最后一格——「判决落在内容状态」：能不能发，取决于扫描后那段字符串里还有没有危险特征，而不是取决于模型说「我这次很小心」。

一次扫描通常要覆盖几类不同的检查，分开写才不会互相干扰。

:::figure 出港安检的四类规则
@stack
协议检查::只放行约定的链接写法，其余协议一律清掉
标签清洗::按富文本白名单剥掉脚本类标签，再统一转义
敏感脱敏::疑似编号与凭据串按规则替换成占位
状态兜底::仍含高危特征的，直接拦截不予发出
:::

## 层层追问

:::ask 那我让另一个模型专门当「审查员」，把输出再读一遍判断安不安全，行不行？
:::

比「同一个模型自审」强一点，但性质没变：审查员输出的仍是概率判断，它漏掉的那一条就是事故，误杀的那一条就是投诉。而且两个模型很可能在同一批语料上训练、对同一类伪装缺乏分辨力，盲区依旧相关。更实际的问题是成本和延迟：每发一段就多一次调用。所以审查模型可以当「辅助线索」，用来给可疑内容打个分、触发人工复核，但绝不能当放行的最终开关。最终开关得是一段确定性代码：协议在不在白名单里、标签是不是白名单允许的、正则有没有命中敏感串、转义有没有做。这些判断每次输入相同就得到相同结果，能写进测试、能复现、能审计——这正是安全判决要的东西。

:::ask 那我把所有尖括号、冒号、数字全删掉，最省事不是最安全吗？
:::

这是另一个极端，叫「过度清洗」，同样会出事。现象上看起来干净了，实际把有语义的内容一并毁掉：订单编号、金额、单位、表格结构、代码缩进全没了，用户拿到一段没法用的残文；更糟的是，如果你的扫描规则是「命中就整段丢弃」，攻击者反而可以用一段无害但会命中规则的文本，让系统频繁拒答，变相制造骚扰。正确的做法是按「目标上下文」分别处理，而不是全量抹平：发到网页就做标签白名单与 HTML 转义，发到数据库就只用参数化查询、让模型生成的 SQL 落到固定模板里，发到纯文本渠道只处理换行与分隔符。清洗的目标不是「把文本变得最短」，而是「让这段文本在它要去的地方不具备执行能力，同时保留该有的信息」。顺着这条线往下，不同用户、不同会话之间还不能被清洗后的缓存串味，那是 [会话隔离与租户边界](./k105-session-isolation.md) 要守的另一半。

## 一段能跑的代码

下面这段程序只用 Python 标准库，把「扫描 → 清洗 → 脱敏 → 编码 → 状态判决」跑成可核对的判定。恶意输出全部本地构造，不联网、不读环境变量、不装任何第三方包，复制成 `.py` 直接运行即可。

```python
import re
import html

# 本地构造的一组待发送内容：前两条正常，后三条各带一类风险
OUTPUTS = [
    "订单 A-1002 已发货，预计后天到达。",
    "共 3 件商品，合计 380.00 元。",
    "点这里领奖：javascript:runSomething()",
    "联系我 13800000000，或看这段 <script>gather()</script>",
    "内部凭据：sk-FAKE-0000-0000 请勿外传",
]

DANGEROUS_SCHEME = re.compile(r"javascript\s*:|data\s*:|vbscript\s*:", re.I)
SCRIPT_TAG = re.compile(
    r"<\s*/?\s*script[^>]*>.*?<\s*/\s*script\s*>|<\s*/?\s*script[^>]*>",
    re.I | re.S)
PHONE = re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)")
SECRET = re.compile(r"sk-[A-Za-z0-9-]{6,}")

def scan_and_clean(text):
    """对外发出前的确定性扫描：只认规则，不认模型的自我评价。"""
    hits = []
    cleaned = text
    if DANGEROUS_SCHEME.search(cleaned):
        hits.append("危险协议")
        cleaned = DANGEROUS_SCHEME.sub("[协议已移除]", cleaned)
    if SCRIPT_TAG.search(cleaned):
        hits.append("脚本标签")
        cleaned = SCRIPT_TAG.sub("", cleaned)
    if PHONE.search(cleaned):
        hits.append("疑似编号")
        cleaned = PHONE.sub("[编号已脱敏]", cleaned)
    if SECRET.search(cleaned):
        hits.append("疑似凭据")
        cleaned = SECRET.sub("[凭据已脱敏]", cleaned)
    # 按「发到网页」这个目标上下文做转义，残留尖括号不再具备标签能力
    cleaned = html.escape(cleaned, quote=True)
    return cleaned, hits

def still_dangerous(cleaned):
    """状态判决：扫描后若仍有危险协议或脚本标签，就不放行。"""
    return bool(DANGEROUS_SCHEME.search(cleaned) or SCRIPT_TAG.search(cleaned))

if __name__ == '__main__':
    results = [scan_and_clean(t) for t in OUTPUTS]
    checks = []
    checks.append(("正常文本不被误伤、原样保留",
                   results[0][0] == OUTPUTS[0] and results[1][0] == OUTPUTS[1]))
    checks.append(("危险协议被移除并留下命中记录",
                   "javascript" not in results[2][0].lower()
                   and "危险协议" in results[2][1]))
    checks.append(("脚本标签被剥离且不留残片",
                   "script" not in results[3][0].lower()
                   and "脚本标签" in results[3][1]))
    checks.append(("疑似编号被脱敏",
                   "13800000000" not in results[3][0]
                   and "疑似编号" in results[3][1]))
    checks.append(("疑似凭据被脱敏",
                   "sk-FAKE" not in results[4][0] and "疑似凭据" in results[4][1]))
    checks.append(("扫描后全部内容都不再含危险特征",
                   all(not still_dangerous(c) for c, _ in results)))
    checks.append(("残留尖括号被转义而非直接插入页面",
                   "&lt;b&gt;" in html.escape("<b>加粗</b>", quote=True)
                   and "<b>" not in html.escape("<b>加粗</b>", quote=True)))
    passed = sum(1 for _, ok in checks if ok)
    for label, ok in checks:
        print(("通过" if ok else "未通过") + "：" + label)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks)
```

逐段看它在做什么：

1. `OUTPUTS` 是五条手工构造的待发内容，前两条是正常业务文本，后三条分别携带危险协议、脚本标签加编号、疑似凭据。全部写死在文件里，保证演示可复现，也不涉及任何真实数据。
2. 四个正则各管一类：`DANGEROUS_SCHEME` 盯危险链接协议，`SCRIPT_TAG` 盯成对或单个脚本标签，`PHONE` 盯十一位编号形态，`SECRET` 盯凭据串形态。它们都是确定性规则——同样的输入永远得到同样的命中结果，这正是能写进回归测试的前提。
3. `scan_and_clean` 是安检机本体：逐类命中就替换成占位，并把命中项记进 `hits`。注意它**先清危险结构、再统一转义**，顺序不能反——若先转义，标签变成普通字符，正则就认不出来了。
4. `html.escape(cleaned, quote=True)` 演示「按目标上下文编码」：内容最终要放进网页，就把残留的尖括号与引号转成实体，让它们彻底失去「被当成标签执行」的能力。若目标是数据库或命令行，这一步要换成参数化查询或参数明确的领域工具，而不是同一种转义。
5. `still_dangerous` 把放行判决写成对**内容状态**的检查：扫描后若还残留危险协议或脚本标签，就返回真，调用方据此拦截。这里没有任何「模型觉得安全」的成分。
6. 末尾七条断言分别验证不误伤、协议清除、标签剥离、编号脱敏、凭据脱敏、全局无残留、尖括号被转义，最后打印「通过 7/7 项」。整组断言都能复现、能进持续集成，是安全测试该有的样子。

## 踩坑与边界

- **把提示词约束当输出保证**：现象是写了「不要输出敏感信息」就以为万事大吉，实际照漏不误 → 原因是请求不是约束，且生成与自审共享盲区 → 怎么改：把扫描与编码放进发送动作的唯一入口，由确定性代码强制执行，见 [护栏放在代码里](./k106-guardrail-in-code.md)。
- **只审输入不审输出**：现象是入口过滤做得很细，前端却把模型回复直接插进页面，脚本或危险链接照常生效 → 原因是默认「出去的都干净」，漏了检索片段、工具返回、历史上下文这些带出来的内容 → 怎么改：按目标上下文做输出编码、富文本白名单清洗，必要时配内容安全策略（Content Security Policy，简称 CSP，限制页面能加载和执行哪些资源的策略）。
- **用同一个模型审查自己的输出**：现象是加了一道「模型自审」，遇到同类伪装依旧双双漏过 → 原因是两次判断共享同一套理解方式与训练盲区 → 怎么改：模型只给可疑分、触发人工复核，放行开关交给正则与白名单构成的确定性代码。
- **扫描规则一刀切**：现象是把尖括号、冒号、数字全删，订单号、金额、表格、代码全被毁掉，用户拿到残文 → 原因是把「变最短」当成了「变安全」 → 怎么改：按目的地分别处理，目标是「让文本在该场景里不具备执行能力、同时保留该有的信息」。
- **先记后脱敏**：现象是日志里先把完整回复落盘、再想着脱敏，结果观测系统本身成了敏感数据池 → 原因是把脱敏放在了采集之后 → 怎么改：采集侧就只记元数据（版本、哈希、用量、判决结果），完整原文按需加密留存并配访问控制与保留期限。

## 三句话小结

输出扫描与内容过滤，是内容真正对外之前，由确定性代码再做一遍协议检查、标签清洗、敏感脱敏与按场景编码。

关键做法是让发送动作只有一个入口、入口内强制过安检，并把「能不能发」写成对扫描后内容状态的检查，而不是模型的自我评价。

当内容只在进程内部流转、既不渲染到页面、也不落进数据库或命令行、更不会发给外部时，这套对外清洗可以简化；但只要有一个出口，就必须按那个出口的场景单独设规则。

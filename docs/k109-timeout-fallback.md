# 超时与确定性降级：下游出事时返回一个说得清的结果

## 场景提问

你的助手要查一份实时库存再回答用户，库存服务偶尔会卡住十几秒甚至不返回。没做处理的版本里，用户看到的是一片空白、一个转不完的圈，或者一句谁也看不懂的错误堆栈；运气更差时，整个会话直接断掉，前面聊过的上下文全白费。你去翻日志，发现有的请求是超时、有的抛了异常、有的返回了半截内容，三种坏法长得完全不一样，上游每一种都得单独应付。你开始怀疑：下游出事是躲不掉的，那能不能至少让「出事之后发生什么」变得可控？

## 破误解

**不是要把下游修到永不失败，而是把「失败」也当成一种要好好设计、结构固定的正常返回。**

很多人把超时和异常当成「意外」，于是代码里到处是临时补丁：这里 `try` 一下、那里给个默认值、实在不行就把错误往上抛。结果同一类故障有七八种表现，上游根本没法统一处理，用户体验全看命。真正该转的弯是：既然下游的抖动、超时、报错无法被消灭，那就明确规定「一旦它不可用，我们返回一个什么样的东西」。这个东西必须满足两个条件——它是确定的（同样的坏情况永远得到同样的结果，不随时间、次数、随机波动），它是结构完整的（字段、类型、能不能继续往下走都写得明明白白）。把它做成一等返回，而不是散落各处的例外，这就叫确定性降级（graceful degradation，在系统部分失效时主动退回一个能力较弱但依旧可用的结果，而不是整体崩掉）。它和 [幂等落盘](./k107-idempotent-persist.md) 关注「重复」不同，这里关注的是「坏了以后给什么」。

## 生活类比

把它想成一家餐厅的备用菜单。厨房的设备偶尔会坏，某道招牌菜做不了。糟糕的服务员会跑到桌边说「师傅说做不了，我也不知道怎么办」，把难题原样丢给客人，客人只能干坐着；或者干脆装作没听见，让客人一直等。训练有素的服务员则有一张事先写好的备用菜单：设备坏了就明确告知「这道今天没有，但同价可以换这三道里的任意一道，或者给您一份现成的套餐」，客人当场就能做一个确定的选择，这顿饭照样吃得下去。

这里的对应关系很具体：厨房设备故障就是下游超时或异常；把问题原样丢给客人，就是让异常一路抛到用户面前；那张备用菜单，就是事先定义好的兜底结果；「同价可换、或给现成套餐」是兜底里写清楚的可选项；「照样吃得下去」表示系统虽然能力降级了，会话却能继续。关键有两点：备用菜单是**提前印好的**，不是设备坏了才临时编，所以每次给出的话术一致；而且它会**明确标出「这是替代方案」**，不把降级结果伪装成正常结果骗人。放到程序里，就是兜底结果要带一个能被上层判定的标记，比如 `degraded`，让调用方知道「这份数据能力较弱，别拿它去做需要精确值的决策」。

## 自绘示意图

:::figure 一次带兜底的调用
@flow
发起调用|正常则返回真实结果|异常或超时|构造确定兜底|标记降级后返回
:::

注意中间那次分岔：正常和故障走的是两条不同的路，但最后都汇到「返回一个结构一致的结果」上。上游只认这一种返回体，就不用为每种坏法各写一套处理。

:::figure 抛异常与确定性降级的差别
@compare
把异常抛给上层::表现随错误类型变|用户看到空白或堆栈|上游要分情况硬扛
返回确定兜底::任何坏法同一结构|用户得到可继续的结果|上游只需认一种返回
:::

左边是「把意外往外丢」，右边是「把意外收编成一种正常返回」。二者对下游的要求一样高，但对上游和用户的友好程度差了一大截。

:::figure 兜底返回体该带哪几层信息
@stack
结论字段 ok::表明这次调用是否算走通，布尔值，上层好判定
降级标记 degraded::明确这是替代结果，别当精确数据用
数据字段 data::即使降级也给一个合法默认值，不让下游解析报错
来源标记 source::写明来自真实下游还是兜底，便于追溯与统计
:::

这四层是一份兜底结果的常见骨架：能判定、能识别、能解析、能追溯。少了 `degraded`，上层会把兜底误当真值；少了 `source`，事后就无法统计到底有多少流量走了降级。

## 层层追问

:::ask 那如果不同下游各有各的超时原因，兜底要不要跟着分那么多种？
:::

恰恰相反，这正是要收敛的地方。超时、连接被拒、抛异常、返回半截内容，从下游看是四种故障，但对「这次要不要继续会话」这个决策来说，答案是同一个：拿不到可信的真实结果，就退回兜底。所以兜底结果应当**按能力分档，而不是按错误类型分档**——比如「完全可用」「只有缓存旧值可用」「只有默认建议可用」三档，每档一个固定返回体，至于触发它的是超时还是异常，只记在日志和 `source` 里供排查，不影响返回结构。这样上游永远只处理少数几个档位，坏法再多也不会把分支撑爆。这一点和 [重试、指数退避与抖动](./k108-retry-backoff.md) 是配套的两步：能自愈的临时故障先退避重试，重到上限仍不行，才由这里给出确定兜底，而不是无限重试下去。

:::ask 那如果用户正在做的事本来就不允许用「默认值」凑合呢？
:::

问到了降级最该守住的边界。兜底不是万能膏药，有些场景**宁可明确失败、转人工，也不能给一个看起来合理的假结果**。典型的是涉及钱、涉及不可逆写操作、涉及医疗或合规判断的环节：库存查不到就回「0」可能导致超卖，余额读不到就回默认值可能酿成错账。对这些地方，正确的「确定返回」不是编一个数据，而是返回一个结构完整的「无法完成」状态，把会话干净地交给人工或让用户稍后重试，并且要在 [健康检查与 SLO](./k114-health-slo.md) 里把这类「主动不算成功」的比例单独统计，别让它悄悄混进成功率。换句话说，确定性降级给的是**确定的处置**，不一定是**确定的数值**；该拒绝时要能确定地拒绝。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用「模拟耗时」代替真实等待，演示正常、异常、超时三种情况如何收敛到同一个兜底返回体，并用断言验证兜底的确定性、结构完整性和可序列化。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
from dataclasses import dataclass


@dataclass(frozen=True)
class Reply:
    """对外统一的返回体：无论走真实结果还是兜底，字段都固定。"""
    ok: bool
    degraded: bool
    data: str
    source: str


FALLBACK_TEXT = "服务暂忙，已返回默认结果"


def deterministic_fallback():
    """确定性兜底：同样的输入永远得到同样的、结构完整的结果。"""
    return Reply(ok=True, degraded=True, data=FALLBACK_TEXT, source="fallback")


class Downstream:
    """本地模拟下游：用可控的「模拟耗时」表示一次调用花了多久。"""

    def __init__(self, cost_ms):
        self.cost_ms = cost_ms

    def call(self):
        return Reply(ok=True, degraded=False, data="真实结果:" + str(self.cost_ms), source="downstream")


def call_with_deadline(downstream, cost_ms, deadline_ms):
    """模拟时钟：耗时超过阈值就当超时，返回兜底而不是抛异常。"""
    if cost_ms > deadline_ms:
        return deterministic_fallback(), "timeout"
    return downstream.call(), "normal"


def main():
    deadline = 200
    r_normal, mode_normal = call_with_deadline(Downstream(80), 80, deadline)
    r_timeout, mode_timeout = call_with_deadline(Downstream(900), 900, deadline)

    checks = [
        ("正常调用返回真实结果", mode_normal == "normal" and r_normal.source == "downstream"),
        ("正常调用不带降级标记", r_normal.degraded is False),
        ("超时返回兜底而非异常", mode_timeout == "timeout" and r_timeout.degraded is True),
        ("兜底返回体 ok 仍为 True", r_timeout.ok is True),
        ("兜底内容与来源固定", r_timeout.data == FALLBACK_TEXT and r_timeout.source == "fallback"),
        ("兜底可确定性复现", deterministic_fallback() == deterministic_fallback()),
        ("返回体可序列化为 JSON", json.dumps(r_timeout.__dict__, ensure_ascii=False).find("degraded") >= 0),
    ]

    r_edge, mode_edge = call_with_deadline(Downstream(200), 200, deadline)
    checks.append(("耗时恰等于阈值时按正常处理", mode_edge == "normal"))

    many = [call_with_deadline(Downstream(1000 + i), 1000 + i, deadline)[0] for i in range(5)]
    checks.append(("连续多次超时结果完全一致", all(x == many[0] for x in many)))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Reply` 用 `frozen=True` 的数据类（dataclass，一种自动生成构造与比较方法的类装饰器）定义统一返回体，四个字段 `ok`、`degraded`、`data`、`source` 对所有情况都固定存在；`frozen` 让实例不可改，从结构上保证兜底结果不会被中途偷偷篡改。
2. `deterministic_fallback` 是全文的重心：它不带任何随机、不看时间、不查状态，每次调用都返回同一个 `Reply`。这正是「确定」两个字的落点——同样的坏情况，永远得到逐字段相同的结果。
3. `Downstream.call` 返回一个 `degraded=False` 的正常结果，用 `cost_ms` 拼进 `data` 表示这份数据来自真实下游。这里刻意不去真的等待，而是把「耗时」当成一个传入的数，方便可复现地制造超时。
4. `call_with_deadline` 用 `if cost_ms > deadline_ms` 把超时判定收成一次比较：超过阈值就 `return deterministic_fallback()`，绝不 `raise`。边界用严格大于，所以「恰好等于阈值」仍走正常分支，随后有专门断言验证这一点。
5. `main` 里构造正常（80）、超时（900）两种调用，再列一组断言：正常结果不带降级标记、超时结果 `degraded=True` 但 `ok=True`（表示会话可继续）、`data` 与 `source` 固定不变、兜底可被比较相等、返回体能序列化成 JSON（JavaScript Object Notation，一种纯文本数据格式）且含有 `degraded` 字段。
6. 最后连续制造五次超时，断言五份兜底结果完全一致——把「确定性」用最直接的方式钉死；再验证「耗时恰等于阈值按正常处理」这条边界。结尾 `assert` 保证任何性质被破坏就非零退出。

## 踩坑与边界

- **把异常一路抛给用户**：现象是页面空白、堆栈外泄、会话直接断掉 → 原因是没把故障收编成一等返回 → 在调用边界用超时判定和兜底函数挡住，永远返回结构一致的返回体。
- **兜底里掺随机或时间**：现象是同样的故障两次返回不一样，上游时好时坏、极难复现 → 原因是兜底函数读了当前时间或随机数 → 兜底只用常量和固定默认值，把「可变」全部留给真实结果。
- **降级结果不带标记**：现象是上层把默认值当成精确数据，拿去做了不该做的判断 → 原因是返回体缺 `degraded` 之类的可判定字段 → 明确标出这是替代结果，并要求上游据此限制后续动作。
- **每种坏法各写一套兜底**：现象是分支越加越多，超时、异常、半截内容各有各的返回，上游撑不住 → 原因是按错误类型而非能力分档 → 收敛成少数几档固定返回体，故障细节只进日志和 `source`。
- **在绝不能凑合的地方硬给默认值**：现象是查不到库存就回零导致超卖、读不到余额就按默认算酿成错账 → 原因是把「确定」误解成「一定要给个数」 → 这类场景改为返回结构完整的「无法完成」状态，把会话干净转人工或稍后重试。

再补一个容易忽略的尺度：降级是「能力变弱但会话继续」，它和 [超时与确定性降级](./k109-timeout-fallback.md) 里讨论的重试是两条不同的路，别把「一直重试直到成功」当成降级；也别把降级结果悄悄计入成功，否则 [健康检查与 SLO](./k114-health-slo.md) 里的成功率会被粉饰。什么时候该给兜底、什么时候该干脆拒绝，最好在 [成本优化与发布清单](./k116-cost-checklist.md) 里逐项写死，避免临场拍脑袋。

## 三句话小结

超时与确定性降级，是把下游超时、报错这类无法消灭的故障，收编成一种结构固定、可判定、可复现的正常返回。

关键做法是用超时判定挡在调用边界、以不带随机与时间的兜底函数构造结果、并显式标出降级状态供上游识别。

当环节涉及钱、不可逆写入或合规判断时，不该用默认值凑合，而应确定地返回「无法完成」并转人工或稍后重试。

# 职责边界：模型只说要调什么，动手的永远是宿主

## 场景提问

你给助手接了一个「查余额」的工具，测试时随口问一句「帮我看看还剩多少钱」，界面上却什么都没发生，数据库里也没有任何查询记录。你翻代码，发现自己在模型返回之后就直接把结果渲染给用户了，中间压根没有一段真正去执行查询的代码。更让人困惑的是，同事说「开了函数调用模型不就自己去查了吗」，于是你开始怀疑是不是接口没连对、参数没开全，折腾半天仍不知道东西到底卡在哪一步。

## 破误解

**不是接口没连对，是你把「模型说了一句话」当成了「系统做了一件事」——模型从头到尾没有执行任何函数。**

函数调用（Function Calling，指模型按约定格式输出「要调用哪个工具、带哪些参数」的一种能力）最容易被讲反的一点，就是执行权的归属。模型被训练成在某个时机切换输出格式，吐出一段形如「工具名 + 参数」的文本；它既没有能跑代码的运行时，也没有连接数据库的凭证，更碰不到你的文件系统。它做的只是「声明意图」，就像一个人隔着玻璃指了指菜单上的某一道菜。真正把这道菜做出来、端上桌的，是玻璃这边一直站着的宿主程序（host，指承载模型、握有真实资源并运行你那份业务代码的进程）。解析这段文本、判断工具名是否存在、校验参数能不能用、调用本地函数、把结果整理好再送回下一轮，全都是宿主里一行行普通代码完成的。把这层分工讲反了，后面所有的安全设计都会跟着错：你会以为「模型别乱调就行了」，而实际上该设防的地方根本不在模型这一侧。关于解析之后该怎么校验参数，可以顺着看 [工具 Schema 设计](./k032-tool-schema.md)；这一篇先把「谁有权动手」这条线画清楚。

## 生活类比

把它想成一家只做外卖、不许顾客进后厨的小馆子。顾客（模型）手里只有一张点单纸，他能写「宫保鸡丁、少辣」，但厨房在哪、煤气怎么开、锅在哪儿，他一概不知道，也不允许知道。写好的单子从窗口递出去，服务员（宿主）接过来先做三件事：看这道菜在不在菜单上（工具名是否登记）、看「少辣」这种写法厨房认不认（参数是否合法）、看这桌客人有没有点这道菜的资格（权限）。三关都过了，服务员才转身把单子交给后厨真正开火（执行副作用），最后把做好的菜和一句「您要的菜好了」一起送回窗口（结果回填）。

对应关系要一一摆出来才讲得透：点单纸就是那段调用意图文本；菜单就是宿主维护的工具登记表；「少辣」这类要求就是参数；后厨开火就是对外部世界造成的真实改动，工程上叫副作用（side effect，指会改变系统状态、花掉钱、发出消息或写入数据的动作）；送回窗口的菜就是给模型下一轮看的结果。这里最要紧的一点是：顾客哪怕在单子上写「我自己已经把菜炒好了」，服务员也绝不会因此就少炒一盘——因为炒没炒，只以后厨的记录为准，从来不以顾客单子上的自述为准。模型输出里带着「已完成」「成功」「approved=true」也一样，那些都只是文本，不是事实。想让文字安全地碰真实世界，唯一办法是在宿主这一侧立一道只认结构化指令、不做语义联想的关卡，这一点在 [权限矩阵与最小权限](./k037-permission-matrix.md) 里会展开成一张可以逐格核对的表。

## 自绘示意图

:::figure 一次工具调用里两侧各干什么
@flow
模型产出意图文本|宿主解析并校验|宿主查登记表|宿主执行真实动作|结果回填下一轮
:::

这五格里，只有第一格属于模型，后面四格全在宿主里。很多链路出毛病，就是因为有人把第一格和第二格之间的「递单子」这一步省了，直接把模型吐出的文本当成执行结果往页面上贴。

:::figure 模型这一侧与宿主这一侧的差别
@compare
模型这一侧::只产出文本|没有运行时|碰不到真实资源
宿主这一侧::握有凭证与连接|解析校验分发|决定是否放行
:::

左边那列是模型的全部能力，右边那列是宿主的全部责任。两列之间没有任何重叠，也不该有：一旦让模型直接拿到右边任何一项，比如把密钥写进提示词让它自己去请求，安全边界当场就消失了。

## 层层追问

:::ask 那如果模型输出的参数看着完全合法，是不是宿主就可以直接执行了？
:::

不能，而且这恰恰是最该停一下的地方。「参数合法」只说明这段文本能被解析、字段类型对得上；它完全没有回答「这个动作该不该被允许」。一份格式挑不出毛病的退款参数，可能退的是别人的订单、金额超出可退额度、或者这个会话根本没通过身份核验。所以宿主在解析之后，还要再走结构校验、语义校验、资源鉴权、风险策略这几道关，任何一道不过就拒绝执行，并把具体原因结构化地送回去。换句话说，模型输出一律按不可信输入对待，跟网页表单里用户随手填的东西是同一个待遇。这一层「合法不等于合业务」的展开，放在 [参数有效不等于业务合法](./k034-param-validity.md) 里专门讲。

:::ask 那把校验也交给模型自己写一句「我保证参数没问题」，是不是就省事了？
:::

更省不得。保证书本身还是文本，还是出自那个我们刚刚定性为「不可信」的来源，让不可信的一方替自己背书，等于没有校验。这里要追到第二层：既然执行权在宿主，那么「谁说了算」就必须落到一个不能被调用意图影响的地方。做法是把校验写成宿主里的确定性代码——查表、比大小、判权限，输入相同输出必然相同，不掺任何对语义的理解。模型可以建议、可以解释、可以重试，但放不放行由代码说了算。再往深一层，如果连「要不要执行」都让模型在一次调用里既读外部文档又顺手决定，那么外部内容里夹带的一句话就可能驱动一个写动作；更稳的切法是先只抽取事实、后端校验后再决定动作，两件事分开做。这就是为什么讲职责边界时，总要顺带强调「逻辑层与执行层分开」——它们分开，模型才真的只是那个隔着玻璃点菜的人。

## 可运行代码与逐行解释

下面这段程序只用 Python 标准库，用一段假模型输出和一份本地工具登记表，把「模型只产出文本、宿主独占执行权」这条边界跑成可核对的事实。复制到任意装了 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json


def fake_model(user_text):
    """假模型：只吐出描述调用意图的文本，绝不执行任何动作。"""
    intent = {"tool": "get_weather", "arguments": {"city": "北京"}}
    return json.dumps(intent, ensure_ascii=False)


class Host:
    """宿主程序：握有工具登记表与副作用计数，独占执行权。"""

    def __init__(self):
        self.registry = {"get_weather": self._weather}
        self.call_log = []
        self.side_effect_count = 0

    def _weather(self, city):
        # 真实动作只在这里发生，用计数器把它标记出来
        self.side_effect_count += 1
        return {"city": city, "temp": 22, "unit": "celsius"}

    def dispatch(self, raw_text):
        intent = json.loads(raw_text)          # 宿主负责解析文本
        name = intent["tool"]
        args = intent["arguments"]
        if name not in self.registry:         # 宿主负责查登记表
            return {"success": False, "error": "未登记的工具: " + name}
        self.call_log.append(name)
        data = self.registry[name](**args)    # 宿主负责执行
        return {"success": True, "data": data}


def main():
    host = Host()
    raw = fake_model("今天北京天气怎么样")
    checks = []

    # 模型阶段：只有一段文本，没有任何执行痕迹
    checks.append(("模型输出是字符串文本", isinstance(raw, str)))
    checks.append(("模型阶段未产生副作用", host.side_effect_count == 0))
    checks.append(("模型阶段登记表未被触碰", len(host.call_log) == 0))

    # 宿主阶段：解析后分发，副作用才第一次发生
    result = host.dispatch(raw)
    checks.append(("宿主执行返回成功", result["success"] is True))
    checks.append(("宿主执行后副作用计数为 1", host.side_effect_count == 1))
    checks.append(("返回的数据来自宿主工具", result["data"]["city"] == "北京"))

    # 模型凭空写一个工具名，宿主不认，动作不会发生
    forged = json.dumps({"tool": "delete_all", "arguments": {}}, ensure_ascii=False)
    denied = host.dispatch(forged)
    checks.append(("伪造的工具名被宿主拒绝", denied["success"] is False))
    checks.append(("被拒后副作用计数不增加", host.side_effect_count == 1))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `import json` 引入标准库里的 JSON 处理模块。JSON（JavaScript Object Notation，一种纯文本的数据表示格式）在这里刻意承担一个角色：它是模型唯一能产出的东西——文本，不是动作。
2. `fake_model` 无论收到什么输入，都固定返回一段序列化后的文本。它叫「假模型」，是因为真实模型在这里也只做同样的事：输出结构化文本。函数体里没有任何读写文件、请求网络、改动全局变量的代码，这从构造上保证了「模型不能执行」。
3. `Host.__init__` 里放了两样只有宿主才有的东西：`registry` 是工具登记表（菜单），`side_effect_count` 是副作用计数器。把计数器放在宿主而不是模型，是为了让「动作到底发生没有」有一个可核对的观察点。
4. `_weather` 是真正的本地工具函数，它做的第一件事就是给计数器加一。这一行就是「后厨开火」——任何真实系统里的查询、扣款、写入，都相当于这一行的位置。
5. `dispatch` 按顺序做四件事：`json.loads` 解析、取工具名、`name not in self.registry` 查登记表、最后才 `self.registry[name](**args)` 执行。注意查不到名字时直接返回失败，不会有任何动作发生——这就是执行权牢牢攥在宿主手里的样子。
6. `main` 前半段的三个断言专门盯模型阶段：输出必须是字符串、副作用计数必须是零、登记表必须是空的。它们把「模型说了」和「系统做了」这两件事明确地拆成两个时刻。
7. 后半段调用 `host.dispatch(raw)` 之后，计数才变成 1，返回的数据也确实来自宿主工具。最后再伪造一个 `delete_all` 工具名，验证宿主不认账、计数不增加——模型就算写下再吓人的动作名，也越不过登记表这一关。
8. 结尾把每条断言的名字与结果逐行打印，并汇总成「通过 N/N 项」，`assert` 保证只要有一条不成立程序就以非零状态退出。这样读者跑一遍，就能亲眼看到边界在哪，而不是记住一句口号。

## 踩坑与边界

- **把模型输出直接当结果**：现象是界面显示了「查询成功」但数据库里查不到任何记录 → 原因是从模型返回到渲染之间缺了解析与执行代码 → 在宿主里补一段 dispatch，明确「解析—校验—执行—回填」四步，一步都不能省。
- **把凭证写进提示词让模型自己请求**：现象是密钥出现在日志、检索片段甚至模型回话里 → 原因是误以为模型能替宿主发请求 → 密钥只留在宿主进程，工具只暴露一句「查什么」，由宿主拿着凭证去调，模型连地址都不该看见。
- **相信模型自报的成功**：现象是参数里写着 `approved=true` 就放行了危险动作 → 原因是把不可信文本当成了授权结论 → 审批、身份、权限一律由宿主按会话注入并核对，模型填的这些字段直接忽略。
- **让模型一次里既读外部内容又决定写动作**：现象是文档里夹一句话就触发了对外发送 → 原因是把「读」和「决定」放在同一次调用 → 拆成两阶段：先只抽取受约束的事实，后端校验通过后再判断候选动作。
- **登记表用字符串拼出来的名字去索引**：现象是模型写个近似的工具名就撞进了别的分支 → 原因是没有显式白名单校验 → 执行前用 `if name not in registry` 这类确定性判断拦一道，只放行明确登记过的名字。

还要说清一个尺度：本文演示的是单进程里的职责切分，用一段假模型把边界跑通足够建立直觉，但它不负责参数合不合法、权限够不够、动作会不会重复——那分别是另外几层的事。把「谁能动手」和「动手前查什么」混为一谈，是这一章最常见的连锁错误。若想看看解析之后紧接着该写的那道校验器，接着读 [工具 Schema 设计](./k032-tool-schema.md)；若想从整体上先认清这份教程怎么组织，回到 [从这里开始](./00-start-here.md) 更省事。

## 三句话小结

函数调用里的职责边界，是模型只按格式产出「调哪个工具、带什么参数」的文本，解析、校验、执行与回填全部由宿主程序完成。

关键做法是在宿主里立一段确定性的分发代码，用登记表限定可用工具、把模型输出当不可信输入、让每道校验和每次真实动作都只发生在这一侧。

当你只想让模型生成一段供人阅读的文字、或根本不需要触碰外部系统时，不必引入这套执行链路；但只要动作会产生真实副作用，这条边界就必须画死，不能让模型跨过玻璃自己去开火。

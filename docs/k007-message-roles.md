# 消息角色与对话拼装：拼错顺序会改变行为

## 一、只挪了挪位置，行为就变了

同一句"回答一律用一句话"，你原本写在最前面，它守得好好的；后来你把这句挪进用户消息里、跟问题挤在一起，它偶尔就不守了。还有一次，你把工具查回来的结果贴在了它开口提问之前，结果它像没看见那条数据似的，又把同一个问题问了一遍。你没换模型、没改参数、连措辞都没动，只是把几段文字的先后调了调，行为就变了。

这不像是"内容"的问题，倒更像是"位置"的问题。可几句同样的话，换个位置怎么就不一样了？

## 二、先破误解

**不是模型把每段文字一视同仁地读懂了意思，它是看着一整段"带角色标记的文字"往下接续的；谁标成什么身份、排在前还是后，都会改变它下一步接什么。**

先把四种角色讲白。系统（system）是常驻规则：它是谁、能干什么、不许干什么、输出要什么格式，每轮都带，放在最前。用户（user）是这一轮真正要处理的事。助手（assistant）是它此前说过的话，让对话接得上、知道从哪儿往下写。工具（tool）是外部动作查回来的结果，不是模型自己编的，它要紧跟在"触发了这次动作的那轮助手发言"后面。所谓"对话拼装"，就是把这四类按规矩排好、拼成一整段送进去——它不是四个分开的格子，[上下文窗口](./k003-context-window.md)里说过，模型这一眼看到的是首尾相接的一整段。

"优先级"不是玄学，有两层很朴素的道理。一层是位置：规则放在整段最前、且每轮都在，更容易在整段续写里持续生效；越靠后、离"下一个要猜的词"越近的内容，对紧接着那一步影响越大，所以当前问题通常放最后。另一层是身份标记：标成系统的文字和标成普通闲聊的文字，在模型读过的文本里"该怎么对待"本就不一样。于是开头两件别扭就通了：把规则抄进用户消息中间，它就从"统摄全段的常驻条款"降格成"某次对话里的一句普通内容"，被后面的文字一挤，偶尔就不守了；把工具结果排在提问之前，模型看不出这段数据是在回哪一句，自然可能把那个问题重新问一遍。

:::warn 别把"位置"当小事
同一批内容换个排法，就是另一份输入；排查行为异常时，先把拼装顺序打出来看一眼。
:::

## 三、生活类比：一张带固定栏目的会诊单

想象医院里一张会诊单，栏目是印死的。最上面一栏是科室的固定规则：每位病人都必须记过敏史、结论不得超过三行；中间按时间顺序贴着之前几次问诊的记录；某次开了化验，化验单就贴在"开化验单"那一条后面；最下面一栏，是病人这次新说的不舒服。医生看的是这整整一张单子，但他很自然地把几件事分开对待：顶上那栏印死的规则对全程有效；化验单贴在哪条后面，就说明它是对哪一次的回复；最下面那句，才是这回要处理的。

对应关系逐条摆出来：

- 顶部印死的固定栏，是 system，每轮都在最前；
- 历次问诊记录，是 user 与 assistant 的历史；
- 贴在某一轮后面的化验单，是 tool 结果，位置绑定触发它的那轮；
- 最下面那句新诉求，是这一轮的 user；
- 把顶部规则抄进某次问诊里，等于把 system 混到中间，失去了统摄力；
- 化验单贴错位置，等于 tool 顺序错，医生不知道它在答什么；
- 医生通读整张单，等于模型看到的是拼好的一整段，不是四个格子。

这个类比好用的地方，是它把"顺序"变成了看得见的东西：单子上每条记录都有它该待的位置，挪一下就会读错。你不会把化验单夹到最前面，也不会把科室规则当成某位病人的一句闲话；拼消息时同理，别图省事把所有文字倒进一个筐里。

## 四、画出来：四种角色各自站哪儿

先看四类角色的分工与位置，这一层定了，后面拼装才有依据：

:::figure 四种角色各自的位置
@stack
system::常驻规则，每轮最前，管身份与格式
user::本轮要处理的事，离回答最近
assistant::此前说过的话，用来接得上
tool::动作查回的结果，紧跟触发它的那轮
:::

四行里最该记住的是第一行和第四行：前者必须恒定、必须最前；后者必须"有主"，也就是能追溯到是哪一轮助手发言把它叫出来的。一旦这两条松了，就会出现"规则时守时不守""数据像没看见"这类怪现象。

再看一轮消息是怎么从头拼到尾的：

:::figure 一轮消息是怎么拼起来的
@flow
放好系统规则|按序接历史|插入工具结果|追加本轮问题|整段送进去
:::

五步里没有一步是"随便找个地方塞进去"。系统规则先落位，历史按原本的先后接上，工具结果插在触发它的那轮之后，当前问题放最后，最后作为一整段送出去。把这两张图对起来看就清楚：角色分工是规矩，拼装顺序是把规矩兑现的动作，二者缺一，行为就会飘。

## 五、顺着追问两层

:::ask 那如果我把所有内容都塞进一条用户消息里，用文字写清"下面是规则、下面是历史"，是不是也行？
:::

能跑，但会丢两样东西。第一样是角色标记带来的区分度：模型只看到一大段连成片的文字，"规则"和"某次闲聊"在它眼里都是等着被接续的文本，规则很容易被当成普通内容，越往后越管不住。第二样是工具结果的归属：一旦没有"紧跟触发它的那轮"这个位置，一段数据到底在回哪句提问就没了凭据，模型可能把它当背景略过，也可能因此重复提问——这跟[幻觉为什么必然存在](./k005-hallucination.md)里那件事是连着的，真实性靠的是外部依据被摆在对的位置上，而不是堆在旁边。所以真要图省事，也得在代码里把几类内容分开存、拼的时候再按规矩合上，别在源头就搅成一团。

:::ask 那如果系统规则和本轮用户的要求冲突，谁说了算？
:::

别指望光靠"位置"把所有冲突都摆平。位置上 system 更靠前、更该被守住，但模型看的是一整段续写，谁压过谁并不是一条能打包票的硬规则；更麻烦的是，两条 system 各说各话时，连"哪条算数"都成了模糊的事。稳妥的做法是把判定权收回到代码：拼装前强制把系统规则放到最前、且只留一条；把可能与它冲突的内容显式检出来，由你的逻辑决定取舍或报错，而不是赌模型会自己分辨。这也是下面那段代码里 `validate` 和 `prepend_system` 存在的原因。再往下一层，这一整段拼好之后怎么送出去、其中"消息体"占哪一块，是[一次请求拆成五块](./k008-request-anatomy.md)要接着讲的事。整条线从哪起步，可以看[从这里开始](./00-start-here.md)。

## 六、跑一段代码，把顺序守住

下面这段只用标准库，不联网、不装包、不要账号。它把四种角色拼成一整段，并演示怎么校验顺序、怎么在调用方乱传时兜底修正。

```python
ROLES = ("system", "user", "assistant", "tool")


def validate(messages):
    """system 只能有一条且必须在最前；其余角色按给定顺序保留。"""
    seen_body = False
    sys_count = 0
    for role, _ in messages:
        if role not in ROLES:
            raise ValueError("未知角色：" + role)
        if role == "system":
            sys_count += 1
            if seen_body or sys_count > 1:
                raise ValueError("system 只能有一条且必须在最前")
        else:
            seen_body = True
    return True


def prepend_system(messages, rule):
    """无论调用方传了什么，都把系统规则强行放到最前、只留一条。"""
    body = [(r, c) for r, c in messages if r != "system"]
    return [("system", rule)] + body


def assemble(messages):
    validate(messages)
    return "\n".join("[%s] %s" % (r.upper(), c) for r, c in messages)


if __name__ == '__main__':
    checks = 0
    legal = [
        ("system", "回答要简短"),
        ("user", "帮我查一下订单"),
        ("assistant", "需要订单号"),
        ("tool", "订单号 9527"),
        ("assistant", "查到了"),
    ]

    # 1) 合法序列通过校验
    assert validate(legal) is True
    checks += 1

    # 2) 拼装后 system 在最前，且四种角色标签都出现
    text = assemble(legal)
    lines = text.split("\n")
    assert lines[0].startswith("[SYSTEM]")
    assert all("[%s]" % r.upper() in text for r in ROLES)
    checks += 1

    # 3) 顺序被保留：tool 结果排在触发它的 assistant 之后
    assert text.index("[TOOL]") > text.index("[ASSISTANT]")
    checks += 1

    # 4) system 出现在中间会被拒绝
    bad_mid = [("user", "问题"), ("system", "插进来的规则")]
    try:
        validate(bad_mid)
        raise AssertionError("应当抛错")
    except ValueError:
        checks += 1

    # 5) 两条 system 也会被拒绝
    bad_two = [("system", "A"), ("system", "B")]
    try:
        validate(bad_two)
        raise AssertionError("应当抛错")
    except ValueError:
        checks += 1

    # 6) 调用方乱传时，prepend_system 兜底修正
    messy = [("user", "问题"), ("system", "乱入"), ("assistant", "答")]
    fixed = prepend_system(messy, "统一规则")
    assert fixed[0] == ("system", "统一规则")
    assert sum(1 for r, _ in fixed if r == "system") == 1
    assert validate(fixed) is True
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `ROLES` 用四个字符串定死合法角色；消息统一用 `(角色, 内容)` 这样的小对子表示，简单但足够把"身份"和"文字"分开。
2. `validate` 靠两个变量守规矩：`seen_body` 记录是否已经出现过非系统内容，一旦出现过又冒出 system，就说明规则被塞到了中间；`sys_count` 保证 system 至多一条。未知角色也在这里拦下。
3. `prepend_system` 是兜底：不管调用方传得多乱，先把所有 system 剔掉，只保留其余内容，再把一条统一的系统规则顶到最前。判定权在代码，不在模型自觉。
4. `assemble` 先校验再拼装，把每个对子写成带方括号标签的一行，例如 `[USER] 帮我查一下订单`。这正是"带角色标记的一整段"的样子。
5. 断言一、二、三钉住正常情况：合法序列能过、拼出来 system 在首行、四种标签齐全、工具结果排在触发它的那轮助手之后。
6. 断言四、五、六钉住异常：system 出现在中间、出现两条，都会被明确拒绝；调用方乱传时 `prepend_system` 能修正成"一条且最前"，再过一次校验仍然成立。

这里的标签格式只是演示用的一种写法，重点不在方括号，而在"校验在拼装之前、修正由代码完成"。真实调用里消息体怎么组织、这一整段以什么字段送出去，接着看[一次请求拆成五块](./k008-request-anatomy.md)；至于这些文字最终按什么切成片、占多少额度，回看[Token 与分词](./k001-token.md)。

## 七、踩坑与边界

- **把 system 混进中间**：现象是规则时守时不守 → 原因是它降格成某轮里的普通内容，被后面文字挤淡 → 恒放最前、单独一栏，拼装前校验。
- **多条 system 各说各话**：现象是行为在两套要求之间摇摆 → 原因是连"哪条算数"都不确定 → 只留一条，冲突内容由代码显式取舍。
- **tool 结果贴错位置**：现象是数据像没看见、模型重复提问 → 原因是结果没绑定到触发它的那一轮 → 紧跟那轮 assistant 之后，按原顺序插入。
- **全塞进一条 user**：现象是格式要求渐渐失效 → 原因是角色区分度与归属信息都丢了 → 分开存、拼装时按规矩合上。
- **指望模型自己裁决冲突**：现象是两条要求打架时结果随机 → 原因是续写里没有硬性优先级 → 把冲突检出并判定收回到代码层。

## 九、三句话小结

消息角色是给一整段输入里的每块文字标上身份，系统规则、历史、工具结果与当前问题各有该待的位置。
要紧的做法是拼装前先校验顺序，把常驻规则固定在最前且只留一条，工具结果绑定触发它的那轮。
当两条要求冲突、或需要"谁说了算"能打包票时，别指望位置和模型自觉，把取舍写成代码里的显式判定。

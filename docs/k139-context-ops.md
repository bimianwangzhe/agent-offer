# 写选压隔四类操作与不可压缩项

## 场景提问

你为了「把上下文管好」，写了压缩函数、也接了摘要，可越管越乱：每轮工具结果、检索片段、反思、报错全都往里塞，明明不相关的内容也占着位置；更离谱的是，刚在另一个任务里查过的账单明细，竟出现在这一轮工单整理的上下文里，模型顺手把两个任务的数字混着用了；还有一次压缩之后，「不得编造工单编号」变成了「尽量别编编号」，边界一松，后面全歪。你回头看自己的代码，发现来来去去只有两个动作：往里加，和把它变短。管上下文真的就这两件事吗？

## 破误解

**不是压缩做得不够勤，是你把上下文管理当成了「往里加」和「变短」两个动作，缺了「挑哪些进来」和「按谁隔开」，也没给最不能动的东西划一块保护区。**

先把这件事拆开。上下文管理其实是四件互相独立、各管一件事的操作。「写」（write）负责把新信息落进候选池：一条工具结果、一段检索片段、一次用户补充，都算写。「选」（select）负责按当前问题的相关性，从候选池里挑出这一轮真正要带上的少数几条——它管的是**准不准进来**。「压」（compress）负责把已经选中、但太长的条目缩短——它管的是**占多少地方**。「隔」（isolate）负责先按会话、任务、子任务分区，让各区的内容互不可见——它管的是**谁的东西别串到谁那儿**。多数人只做了「写」和「压」：因为没「选」，什么都往里塞，于是越滚越大，这正是 [上下文膨胀与中间遗失](./k049-context-bloat.md) 里那四类增量的来源；因为没「隔」，跨任务的资料串味，这和 [会话隔离与租户边界](./k105-session-isolation.md) 讲的是同一条边界，只是发生在上下文这一层。

第五件事同样关键：有一类内容**不能被压**。系统约束、安全规则、用户明确指令、当前目标、不可变标识、审计锚点，这些一旦被摘要改写成「大意差不多」，边界就松、追溯就断。它们该被显式列进一份封闭的白名单，压缩函数遇到就逐字放过，而不是靠一句「请保留重要信息」的提示去碰运气。这也回应了 [压缩后信息丢失怎么验证](./k048-compression-verify.md) 里那句「抽不全时不要指望抽取兜住一切」——最不能丢的项，根本不该参与「抽没抽到」的赌博。

四类操作之外还得记住顺序有讲究：隔在最外层，先分区，否则「选」的时候会把别的任务的资料一起挑进来；写在最前面，数据先落地才谈得上挑；选要在压之前，先挑再压，别把压根没选中的条目也白压一遍、白花一次开销；压只在被选中的那一小撮上做。把顺序反过来，结果不是「慢一点」，而是「选出来的集合本身就脏了」。本文讲透的就是这一个点：把这四件正交的事分开、排好序，再给不可压缩项划一块谁都不许动的地方。至于什么时候触发压，是 [压缩触发阈值与时机](./k047-compression-trigger.md) 的活；压完怎么摆位、怎么留稳定前缀，见 [前缀缓存与即时注入](./k050-prefix-cache.md)。

## 生活类比

把它想成一家编辑部的资料桌。每天会有成堆的新材料送进来：采访记录、剪报、读者来信、报表——这是「写」，先收下、先登记，别急着判断。编辑做一期专题时，不会把整桌东西都摊开，只从里面挑出和这期题目最相关的几份放上手边——这是「选」；被挑中的那份几十页的行业报告太厚，他让人做成一页要点，但**报告原本仍归档在柜子里**——这是「压」；同时，别的专题组正在做的另一期稿子，材料放在另一张桌、另一个抽屉，绝不混进这一期——这是「隔」；而墙上贴着的那张盖了章的合规条款，塑封起来，谁都不许摘录、不许改写、不许拿去当草稿纸——这就是不可压缩项。

对应关系很具体：成堆送来的材料，是每轮新到的工具结果与检索片段；「只挑和题目相关的几份」，是按相关性分数选前几条；「做成一页要点但原件归档」，是压缩后仍可按标识取回原文，而不是删掉；「另一张桌另一个抽屉」，是按会话或任务分区，取用时看不到别区内容；「盖章塑封的条款」，是白名单里逐字常驻的系统约束。这四件事看着都在「整理资料」，但各自动作不同：收、挑、缩、分，谁也替不了谁。

这个比喻还点出两处细节。第一，塑封的那张纸之所以可靠，不是因为它写得特别清楚，而是因为**它被明确标成「不许动」**，且这类纸数量很少——要是编辑把桌上每份材料都塑封一遍，等于没有塑封。对应到系统里，白名单必须短、封闭、每条写得出理由，绝不能开出「备注」「其他」这种万能标签，否则用不了几轮所有内容都成了不可压缩项，压缩彻底失效。第二，抽屉是**先分好再放东西**的，不是等一桌混了再事后挑；对应「隔在最外层」，分区要在写入之前就声明，否则选的时候根本分不清哪条属于哪个任务。

## 自绘示意图

:::figure 四类操作该走的先后
@flow
先按任务分区|新信息写入池|按相关性挑少数|只压被选中的|组装成上下文
:::

五格里最容易被人省掉的是第一格和第四格。「先按任务分区」若不做，后面「按相关性挑」会从一池混着多个任务的材料里挑，挑得再准也串味；「只压被选中的」若做成「先把全池压一遍再挑」，等于给一堆最终没用上的条目白花了压缩开销，还把原文改坏了一遍。顺序不是风格问题，是结果对不对的问题。

:::figure 四类操作各自解决什么
@stack
写::把新到的结果、片段、补充登记进候选池
选::按相关性分数只挑这一轮要用的少数几条
压::把选中的长条目缩短，原件仍按标识可取回
隔::按会话与任务分区，各区内容互不可见
护::不可压缩项逐字放过，不参与任何改写
:::

五行里前四行是四个动词，第五行「护」不是第五种操作，而是横在四类之上的一条约束：无论写、选、压、隔怎么走，命中白名单的条目都得原样通过。把它单列一行，是想强调保护不是某一步的附属动作，而是贯穿全程的规则。

:::figure 两种管理姿势的差别
@compare
只写加压::什么都往里塞|跨任务会串味|约束被改软
写选压隔加保护::先挑再压不浪费|分区互不串|白名单逐字常驻
:::

左边只用了两个动词，代价是准不准进来、谁的东西、能不能改三样全失控；右边多了两件操作和一条规则，换来的是「进来的都相关、别人的不来、最要紧的不动」。二者差距不在压缩算法，全在有没有把管理拆成几件独立的事。

## 层层追问

:::ask 那如果不可压缩项越标越多，最后整份上下文都动不了，不就等于没压缩了吗？
:::

会，而且这是白名单最自然的退化路径——每样东西都「挺重要」，标着标着就没得压了。所以白名单得立三条规矩。第一，**短而封闭**：只用少数几个明确标签，比如系统约束、安全规则、用户指令、当前目标、不可变标识、审计锚点，不开放任意自定义标签，代码里遇到不在白名单的标签想标成不可压缩就直接报错，演示代码 `write` 里那句 `raise ValueError` 做的就是这件事。第二，**每条写得出理由**：判断该不该进白名单，只问一句「它是否需要被单独校验、单独覆盖、单独回答还在不在」；答不上来，就说明它只是过程记录，该作为轨迹外置、用时按标识取回，见 [Push 与 Pull 按需拉取](./k140-push-pull.md)。第三，**绝不开万能标签**：「备注」「其他」「重要信息」这类口袋一开，等于给自由文本开了后门，几轮之后又回到「什么都塞进去」的老路，这和 [结构化状态摘要](./k046-structured-state.md) 里反对开「备注」万能字段是同一个道理。

再往下一层：那些没进白名单、但确实要紧的内容怎么办？靠两样，不是靠无限加白名单。一样是**常驻槽位**：把目标与约束做成字段固定的状态对象，每轮必带、类型可查，见 [结构化状态摘要](./k046-structured-state.md)；另一样是**压后核对**：压缩前后抽探针逐项比对，发现精确值被改写就按原文回填复验，见 [压缩后信息丢失怎么验证](./k048-compression-verify.md)。换句话说，白名单只守最硬的一小撮，其余靠结构与验证兜，三层叠起来才不用把整份上下文都塑封。

:::ask 那四类操作的顺序能随便换吗，比如先压再选、或者最后再分区？
:::

不能，顺序错一步，结果就脏了。先说「压在选前」：把整池材料先压一遍再挑，一是给大量最终没被选中的条目白花了压缩开销，二是这些条目被改写过一遍，万一后面又要用原文，还得回头找；更要紧的是，压缩本身有损，把不该进来的东西也压坏，纯属浪费。正确是**先选后压**，只对被挑中的那一小撮动手。再说「隔在最后」：分区如果等选完才做，选的时候面对的是一池混着多个任务的材料，相关性分数一比，很可能把别的任务里分数更高的片段挑进来——分都分不清，谈何选得准。所以**隔必须在最外层**，写入之前就声明分区。最后「写」天然排第一，数据都没落地，后面三件无从谈起。

再追一层：压完之后还能不能再选一次、迭代几轮？可以，但得守两条。第一，**留痕**：每一步是哪类操作、作用在哪个分区、挑了几条，都要记下来，事后才能回答「这条为什么在这里」，演示代码用 `ops` 列表做这件事，思路和 [结构化日志与轨迹回放](./k095-structured-log.md) 一致。第二，**别把已压条目当原文再压一次**：压缩过的条目要打标记，重复执行时跳过或按同一口径处理，否则同一段内容被截了又截，越截越短；这种「重复执行不产生二次破坏」的要求，和 [幂等落盘](./k107-idempotent-persist.md) 是同一套稳标识思路。至于整体该占多少、四类各分到多少份额，交给 [上下文预算表](./k041-context-budget.md) 与 [四重预算](./k103-four-budgets.md) 去定，别靠压缩次数硬凑。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「隔、写、选、压」四类操作做成一个 `ContextManager`，并用一份封闭白名单保护不可压缩项，结尾用一组断言逐条验证顺序、隔离、准入、保护与预算。所有条目都是本地构造的字典，复制即跑，不需要第三方包、账号或网络。

```python
import json

# 不可压缩白名单：短、封闭、每条职责明确，不开"备注/其他"这类口袋
PINNED_TAGS = ("系统约束", "安全规则", "用户指令", "当前目标", "不可变标识", "审计锚点")


class ContextManager:
    """把上下文管理拆成写、选、压、隔四类正交操作，并留操作痕迹。"""

    def __init__(self, budget):
        self.budget = budget
        self.pools = {}       # 分区名 -> 条目列表
        self.ops = []         # 操作留痕，便于回看"这条为什么在这"

    def isolate(self, pool):
        """隔：先声明分区，之后写入都落在各自分区，互不可见。"""
        if pool not in self.pools:
            self.pools[pool] = []
            self.ops.append(("isolate", pool))
        return pool

    def write(self, pool, tag, text, score, pinned=False):
        """写：往指定分区追加一条，标注类型、相关性分数、是否不可压缩。"""
        self.isolate(pool)
        if pinned and tag not in PINNED_TAGS:
            raise ValueError("不在白名单的标签不能标为不可压缩")
        self.pools[pool].append({
            "tag": tag, "text": text, "score": score, "pinned": pinned,
        })
        self.ops.append(("write", pool, tag))
        return len(self.pools[pool])

    def select(self, pool, top_k):
        """选：不可压缩项永远入选，其余按相关性分数挑前 top_k 条。"""
        items = self.pools.get(pool, [])
        must = [x for x in items if x["pinned"]]
        rest = sorted((x for x in items if not x["pinned"]),
                      key=lambda x: (-x["score"], x["text"]))
        self.ops.append(("select", pool, top_k))
        return must + rest[:top_k]

    def compress(self, items, shrink_to):
        """压：只缩短可变条目并打标记；不可压缩项逐字放过。"""
        out = []
        for it in items:
            kept = dict(it)
            if it["pinned"]:
                out.append(kept)                 # 原样放过，一个字不动
            else:
                kept["text"] = it["text"][:shrink_to]
                kept["compressed"] = True        # 标记已压，避免重复压
                out.append(kept)
        self.ops.append(("compress", len(items)))
        return out

    def total(self, items):
        """按文本长度估算占用（示意），用于和预算比对。"""
        return sum(len(x["text"]) for x in items)


def main():
    checks = []
    cm = ContextManager(budget=200)

    # 工单整理分区：四条不可压缩 + 四条分数不同的可变条目
    cm.write("工单整理", "当前目标", "整理近一年售后工单", 1.0, pinned=True)
    cm.write("工单整理", "系统约束", "只统计近一年", 1.0, pinned=True)
    cm.write("工单整理", "安全规则", "不得编造工单编号", 1.0, pinned=True)
    cm.write("工单整理", "审计锚点", "工单编号=GD-2025-0917", 1.0, pinned=True)
    cm.write("工单整理", "工具结果", "工单列表完整原文很长很长", 0.9)
    cm.write("工单整理", "检索片段", "退款政策原文也很长", 0.6)
    cm.write("工单整理", "反思", "刚才归类可能要拆开", 0.3)
    cm.write("工单整理", "错误回传", "超时堆栈全文", 0.2)

    # 另一个任务分区：内容完全独立
    cm.write("账单核对", "当前目标", "核对本月账单", 1.0, pinned=True)
    cm.write("账单核对", "工具结果", "账单明细原文", 0.8)

    # 一、隔：分区互不串味
    checks.append(("隔：两个分区彼此独立", set(cm.pools) == {"工单整理", "账单核对"}))
    other = cm.select("账单核对", 3)
    checks.append(("隔：别区看不到本区条目", all(
        x["text"] != "只统计近一年" for x in other)))

    # 二、选：不可压缩项永远入选，其余按分数挑
    sel = cm.select("工单整理", 2)
    checks.append(("选：不可压缩项永远入选", all(x["pinned"] for x in sel[:4])))
    checks.append(("选：只挑分数最高的可变条目",
                   [x["tag"] for x in sel[4:]] == ["工具结果", "检索片段"]))
    checks.append(("选：低分条目不进上下文",
                   "反思" not in [x["tag"] for x in sel]))
    checks.append(("顺序：先隔再选，取的是本分区条目", all(
        x["text"] != "核对本月账单" for x in sel)))

    # 三、压：不可压缩项逐字放过，其余截短并打标记
    packed = cm.compress(sel, shrink_to=6)
    before = [x["text"] for x in sel if x["pinned"]]
    after = [x["text"] for x in packed if x["pinned"]]
    checks.append(("压：不可压缩项逐字不变", before == after))
    checks.append(("压：可变条目被截短", all(
        len(x["text"]) <= 6 for x in packed if not x["pinned"])))
    checks.append(("压：被压条目有标记", all(
        x.get("compressed") for x in packed if not x["pinned"])))
    checks.append(("顺序：没选中的条目不浪费压缩", all(
        t not in [x["tag"] for x in packed] for t in ("反思", "错误回传"))))

    # 四、预算与白名单约束
    checks.append(("四类组合后不超预算", cm.total(packed) <= cm.budget))
    checks.append(("普通条目默认可压缩", not any(
        x["pinned"] for x in cm.pools["工单整理"] if x["tag"] == "工具结果")))
    checks.append(("白名单不含备注类万能标签",
                   "备注" not in PINNED_TAGS and "其他" not in PINNED_TAGS))
    rejected = False
    try:
        cm.write("临时分区", "随手备注", "内容", 0.5, pinned=True)
    except ValueError:
        rejected = True
    checks.append(("不可压缩项必须来自白名单", rejected))

    # 五、四类操作与组装结果都可回看
    checks.append(("四类操作都留痕可审计", set(
        op[0] for op in cm.ops) == {"isolate", "write", "select", "compress"}))
    snapshot = json.dumps({"pool": "工单整理", "items": packed},
                          ensure_ascii=False, sort_keys=True)
    checks.append(("组装结果可落盘回看", json.loads(snapshot)["pool"] == "工单整理"))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `PINNED_TAGS` 是一份**封闭**白名单，只有六个明确标签。`ContextManager` 用 `pools` 按分区存条目、用 `ops` 记每一步操作，前者对应「隔」的落点，后者让「这条为什么在这里」事后可查。
2. `isolate` 在写入前声明分区，`write` 里第一句就调它——这就是「隔在最外层」：分区不是选完再补的，而是数据落地前就定好的。`write` 还有一道硬校验：想标成不可压缩的条目，标签不在白名单就直接抛错，避免白名单被随意撑大。
3. `select` 把条目分成两队：命中白名单的 `must` 无条件入选、不参与分数竞争；其余按 `(-score, text)` 排序后只取前 `top_k`，`text` 作为次级键保证同分时顺序稳定可复现。它管的是「准不准进来」，和压缩完全分开。
4. `compress` 只处理**已经被选中**的那一小撮：不可压缩项用 `dict(it)` 原样放过、一个字不动；可变条目截短并打上 `compressed` 标记，避免同一段被反复截。`total` 用文本长度示意占用，最后和预算比对。
5. `main` 构造两个任务分区，第一组验隔离：账单分区里绝不会出现「只统计近一年」这条本区约束。第二组验准入：四条不可压缩项全在，可变条目只留下分数最高的两条，低分的反思与报错回传进不来，也不会混进别区内容。
6. 第三组验保护与顺序：压缩前后不可压缩项文本逐字相等，可变条目被截到六个字且都带标记，而没被选中的两条根本没进压缩结果——「先选后压」省下的就是这部分白花的开销。
7. 结尾几组验预算、默认可压缩、白名单不含「备注」「其他」口袋、越界标注会被拒、四类操作都有留痕、组装结果能落成 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）快照。`assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：这里的相关性分数是手工填的，压缩被简化成「按字符数截断」，预算也只是长度估算。它演示的是四类操作的分工、顺序与白名单保护，不是任何具体检索打分或压缩算法的实现。

## 踩坑与边界

- **只写不加选**：现象是工具结果、检索片段、反思、报错全进上下文，越滚越长、当前问题反而被摊薄 → 原因是把「收到」当成了「该带」 → 按相关性分数只挑这一轮要用的少数几条，见 [上下文膨胀与中间遗失](./k049-context-bloat.md)。
- **不分区，选完才想起隔离**：现象是一个任务里冒出另一个任务的数字，模型混着用 → 原因是选的时候面对一池混料，分不清哪条属于谁 → 写入之前先声明分区，各区互不可见，见 [会话隔离与租户边界](./k105-session-isolation.md)。
- **先压全池再挑**：现象是压缩开销高、没用上的条目也被改坏一遍 → 原因是顺序颠倒 → 先选后压，只对被选中的一小撮动手，压过的条目打标记防重复，见 [幂等落盘](./k107-idempotent-persist.md)。
- **把约束交给压缩改写**：现象是「不得编造工单编号」变成「尽量别编」，边界松了还查不出 → 原因是没划保护区，指望提示词自己守住 → 白名单逐字放过，配合 [压缩后信息丢失怎么验证](./k048-compression-verify.md) 做压后逐项比对。
- **白名单越标越多**：现象是几乎所有条目都不可压，压缩形同虚设 → 原因是开了「备注」「其他」这类万能标签 → 白名单短而封闭、每条写得出理由，其余靠常驻槽位与压后核兜，别靠无限加白名单。

还要分清一道边界：这四类操作管的是「一条信息从进池到进上下文的路径」，管不了「什么时候该触发压」，那是 [压缩触发阈值与时机](./k047-compression-trigger.md) 的判定；也管不了「压完怎么摆位、前缀稳不稳」，那是 [前缀缓存与即时注入](./k050-prefix-cache.md) 和 [四层上下文结构](./k042-context-layers.md) 的事。另一头，白名单再严也只是「哪些内容不许动」，容量该分多少、四类和四重限制怎么叠加，得靠 [上下文预算表](./k041-context-budget.md) 与 [四重预算](./k103-four-budgets.md) 给数，别指望靠多压几次把装不下的东西压进去。把「准入、隔离、缩短、保护、预算」各归各管，才不会出现治好这边、弄坏那边的情况。

## 三句话小结

写选压隔四类操作与不可压缩项，是把上下文管理从「往里加、变短」两个动作，拆成按任务分区、按相关性准入、只压被选中的条目、并给最硬的一小撮内容划一块逐字不许改的保护区。

关键做法是隔在最外层、选在压之前、白名单短而封闭且每条写得出理由、命中白名单的条目无条件入选并原样放过、每一步都留痕可回看。

当任务只有一个分区、候选条目本来就少而短、且没有任何丢了就出事的硬约束时，不必上这套分工；但只要一轮会长出多类增量、或同时服务多个任务，缺了「选」和「隔」就迟早会膨胀或串味。

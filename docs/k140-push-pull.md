# Push 与 Pull 按需拉取

## 场景提问

你怕 Agent 回答时「手边没资料」，于是每轮都先把检索到的几段原文、相关记忆、工具说明一股脑塞进上下文，觉得料备齐了总没错。结果大半段压根没用上，预算被吃得死死的，真正要答的那件事反而被挤到角落。你改成另一种做法：只给它一份资料目录，让它自己判断要哪条再取。桌面确实清爽了，可新问题又冒出来——它有时把「退款政策」点成「发票开具」，有时干脆一条都不取，还每回多等一轮工具往返才肯开口。省了地方，却把不准和多等一起请了进来。资料到底该主动推给它，还是让它自己拉？

## 破误解

**不是检索做得不准，是你把「资料怎么进上下文」当成了只有一种方向，Push 猜错就白占预算，Pull 省下地方却把判断与往返成本转嫁给了模型。**

先把两个方向说清。Push（推）是系统主动：每轮不等模型开口，先按某种规则把「觉得相关」的资料预取回来塞进上下文——检索片段、记忆注入、预取的工具说明都算。它的好处是模型一开口料就在眼前、不用多跑一轮；代价是**系统在替模型猜**，猜错的那部分照样占着预算、摊薄注意力，猜得越多越膨胀，这正是 [上下文膨胀与中间遗失](./k049-context-bloat.md) 里「检索片段重复叠加」的来源。Pull（拉）是模型主动：只给它一份小而短的目录或索引，外加一个「按标识取回原文」的工具，它需要哪条自己点、自己取。好处是桌上只放真正要用的，代价是三样：多一轮工具往返的延迟、模型可能判断错或干脆不取、以及取回来之前它眼前其实没有原文。

把两者摆在一起看，会发现它们不是「谁更好」，而是**把成本挪到了不同地方**：Push 把成本花在「多塞的内容」上，Pull 把成本花在「多一轮往返 + 判断风险」上。多数人一上手全用 Push，因为实现最省事；吃了膨胀的亏之后又想全切 Pull，结果撞上取错和冷启动。稳的做法是混合：小而高价值的**常驻目录**用 Push 每轮必带——它短、稳定、还能顺带满足 [前缀缓存与即时注入](./k050-prefix-cache.md) 里「前缀逐字固定」的规矩；**大块原文**用 Pull，需要时按标识取回；同时给取用次数设上限、每笔取用留痕，防止模型反复拉同一批东西。

这里要先给个全称：检索增强生成（Retrieval-Augmented Generation，RAG）指「先从资料库检回相关内容、再让模型据此作答」这套做法，[为什么需要 RAG](./k051-why-rag.md) 有展开。本文讲的 Push 与 Pull，是这套做法里「检回来的东西以什么姿态进上下文」这一步，和 [检索式召回压缩](./k045-retrieval-compression.md) 讲「怎么把召回内容压短」是相邻但不同的两件事。另外要如实说明：后面演示里的「本轮真正需要哪些资料」是手工构造的标准答案，只为把两种策略的差别算清楚，**不代表任何实测结论**，也不含任何真实评估数据。

## 生活类比

把它想成两种吃饭方式。一种是自助取餐：不管你今天想吃什么，服务员先按「大多数客人会拿的」往你桌上摆一摞——汤、沙拉、面包、甜点全上齐。好处是你一坐下就有得吃，坏处是桌子被占满，真正想吃的那盘反而没地方放，没动过的那些最后全撤走，白摆一趟。另一种是照菜单点菜：桌上只放一张薄薄的菜单，写明每道菜是什么、编号多少，你看完点哪道，厨房才做哪道端上来。桌子清爽、不浪费，可你得先读菜单、再等一道菜的时间，还可能把菜名看岔、点成别的，或者菜单写得含糊干脆不知道点什么。

对应关系很具体：那一摞先摆上桌的菜，就是 Push 预取回来的检索片段与记忆；「被占满的桌子」，就是被无关内容吃掉的上下文预算；那张薄菜单，就是常驻的目录与索引，每条写清「是什么、编号多少」；「照编号点菜、厨房才端」，就是 Pull 按标识取回原文；「读菜单再等一道菜」，就是多一轮工具往返；「把菜名看岔」，就是索引描述含糊导致取错；「菜单写得含糊不知道点什么」，就是命中不到、需要兜底。老练的馆子会折中：菜单常备在桌上（Push 一小份），大菜现点现做（Pull 大块），一桌既清爽又不至于让客人干等。

这个比喻还点出两处细节。第一，菜单本身必须**短而清楚**：把整本菜谱连做法都印上去，等于又变回自助餐那一摞；对应目录只放标识加一句描述，别把原文塞进去。第二，点菜得有个数：客人一口气点二十道，后厨和桌子都受不了；对应 Pull 要有取用次数上限与留痕，别让模型无限拉。这两条正是混合策略能不能成立的关键，比「选推还是选拉」更常被忽略。

## 自绘示意图

:::figure 两种方向各自进上下文的路径
@flow
系统预取一批|不问就塞进来|或给常驻目录|模型按标识点|取回原文再用
:::

五格里前两格是 Push、后三格是 Pull，中间用「或」隔开是想强调它们是两条并列的路，不是同一条路的两个步骤。「不问就塞进来」是 Push 的成本所在，「模型按标识点」是 Pull 的判断风险所在；两者各有代价，混合就是把第一格换成「只塞一份薄目录」，保留后面的按需取回。

:::figure 混合策略该备好的几样东西
@stack
常驻目录::标识加一句描述，短而稳定每轮必带
取用工具::按标识取回原文，不返回全文清单
命中依据::查询词与描述怎么对上，要写清
取用上限::一轮最多取几条，防止反复拉
取用留痕::哪一轮取了哪条，事后可回看
:::

五行里「命中依据」和「取用上限」最容易缺。前者决定模型能不能从目录里点对条，涉及 [查询改写与指代补全](./k059-query-rewrite.md) 把「那个政策」「它」补成可检索的词；后者决定 Pull 会不会反过来变成新的膨胀，和 [四重预算](./k103-four-budgets.md) 里「给动作设硬上限」是同一套思路。

:::figure 两种姿势的差别
@compare
全量预取::猜错也占预算|桌面越堆越满|无需多跑一轮
常驻目录加按需取::只带用的进来|占用可控可查|多一轮且可能取错
:::

左边省一轮往返，代价是白占和膨胀；右边省了地方，代价是判断与延迟。二者不是优劣关系，是成本落点不同——所以真正该问的是「哪些东西值得每轮在场，哪些值得用时再取」，而不是「哪个更好」。

## 层层追问

:::ask 那如果 Pull 要模型自己判断，它判断错了、或者干脆一条都不取，怎么办？
:::

这是把 Pull 用起来之后最先撞上的问题，答案是别把「点对条」全押在模型临场发挥上，补三层。第一层是**把目录写清楚**：每条只放标识加一句不含糊的描述，让「退款要什么凭证」能对上「退款政策与凭证要求」；描述怎么写，可对照 [工具描述写法](./k033-tool-description.md)，标识怎么带回原文，见 [切分元数据与父块回溯](./k056-chunk-metadata.md)。用户问「那个政策怎么办」这种带指代的，先做 [查询改写与指代补全](./k059-query-rewrite.md)，把「那个」补成具体词再匹配。第二层是**兜底**：命中不到时要有一条明确的路——要么按 [溯源、拒答与零召回兜底](./k062-citation-abstain.md) 老实说「资料里没有」，要么退回一份最小常驻集，而不是硬塞一堆无关内容充数；允许重试一次，但重试也要留痕。第三层是**关键项不靠 Pull**：系统约束、当前目标、不可变标识这类丢了就出事的，仍用 Push 每轮常驻，这在 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 里就是白名单那条规矩。

再往下一层：取用次数该不该限？该，而且要限得比想象中早。模型可能因为不确定反复拉同一批资料，或一次点回十几条把上下文又撑满；所以一轮最多取几条、总共能取几轮、取到重复标识怎么处理，都得写成硬上限并记下来。演示代码里 `max_calls` 和 `ledger` 做的就是这件事。这不只是省钱——取用留痕还能在事后回答「它当时到底看了哪几份资料」，和 [压缩后信息丢失怎么验证](./k048-compression-verify.md) 里「要有独立于被验证对象的锚点」是同一类可回看要求。

:::ask 那既然 Pull 更省地方，是不是全用 Pull、一点都不预取最划算？
:::

不划算，而且冷启动就会卡住。全用 Pull 至少要付四笔账。第一，**每轮多一次往返**：哪怕只是取一条很常见的资料，也得先查目录、再取原文，首字延迟摆在那儿，见 [流式输出与首字延迟](./k009-streaming.md)。第二，**小东西反复取反而贵**：一条几十字的常驻说明，每轮都走一轮工具去取，比直接放在上下文里更费。第三，**没有目录就无从判断**：总得有点东西每轮在场，模型才知道「有哪些可取、按什么标识取」，这个最小集合本身就是 Push。第四，**有些内容必须在场**：系统约束、当前目标、不可变标识不允许「这一轮没取到就算了」。所以答案是混合，不是二选一：短而稳定的目录、约束与状态用 Push 常驻，大块原文与低频资料用 Pull 按需取回；前者还顺带保住了稳定前缀，见 [前缀缓存与即时注入](./k050-prefix-cache.md)。

再追一层：混合里的目录会不会自己也膨胀？会，所以目录要**只放标识和一句描述**，绝不放全文；条目多了就按 [元数据过滤前置](./k060-metadata-filter.md) 先缩小范围，或按 [粗排 + 精排与重排后截断](./k061-rerank.md) 只留最该露出的几条，再按 [上下文预算表](./k041-context-budget.md) 给常驻层定一份固定份额。换句话说，Push 的那一小份要「小到可以忽略、稳到可以复用」，混合才成立；一旦目录写成一大本，等于把全量预取换了个名字搬回来。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用本地构造的资料库和一份手工标注的「本轮真正需要哪些资料」，把「Push 按固定规则预取、Pull 按目录命中取回、两者装入量与精度对比、取用上限与留痕、无命中兜底、混合策略」逐条演示。它是**可手算的构造场景，不是任何实测评估**，复制即跑，不需要第三方包、账号或网络。

```python
import json

DOCS = {
    "d01": "退款政策：七天无理由，需保留凭证",
    "d02": "物流时效：同城次日，跨省三日",
    "d03": "工单分级：按影响面分三级",
    "d04": "发票开具：每月首周统一开",
    "d05": "会员权益：积分可抵现",
    "d06": "账号安全：异地登录需二次验证",
}

# 常驻目录：标识 + 一句描述，短而稳定
INDEX = {
    "d01": "退款政策与凭证要求",
    "d02": "物流时效说明",
    "d03": "工单分级规则",
    "d04": "发票开具时间",
    "d05": "会员积分权益",
    "d06": "账号安全与验证",
}

VOCAB = ["退款", "凭证", "物流", "发票", "积分", "安全", "分级"]
QUERY = "退款要几天、要什么凭证"
RELEVANT = {"d01"}          # 构造场景里的标准答案，不代表实测
ORDER = sorted(DOCS)        # 固定顺序，便于手算 Push 预取了哪几条


def keywords_of(query, vocab):
    """从查询里挑出词表中出现的词，纯规则、可手算。"""
    return [w for w in vocab if w in query]


def push_prefetch(docs, k, order):
    """Push：不判断，按固定顺序先取 k 条塞进上下文。"""
    return {i: docs[i] for i in order[:k]}


def pull_fetch(query, docs, index, vocab, max_calls):
    """Pull：先查目录定位标识，再按需取回原文，取用有上限且留痕。"""
    keywords = keywords_of(query, vocab)
    hits = sorted(i for i, desc in index.items()
                  if any(w in desc for w in keywords))[:max_calls]
    fetched = {i: docs[i] for i in hits}
    ledger = [("lookup", "index")] + [("fetch", i) for i in hits]
    return fetched, ledger


def precision(fetched, relevant):
    """取回的里面有多少是相关的。"""
    return len(set(fetched) & relevant) / len(fetched) if fetched else 0.0


def recall(fetched, relevant):
    """该取的里面有取回多少。"""
    return len(set(fetched) & relevant) / len(relevant) if relevant else 1.0


def chars(items):
    """按文本长度示意装入量。"""
    return sum(len(t) for t in items.values())


def hybrid(query, docs, index, vocab, max_calls, char_budget):
    """混合：短目录常驻推送，大块原文按需拉取，总量受预算卡住。"""
    catalog = json.dumps(index, ensure_ascii=False)
    fetched, ledger = pull_fetch(query, docs, index, vocab, max_calls)
    total = len(catalog) + chars(fetched)
    return {"catalog_chars": len(catalog), "fetched": fetched,
            "total": total, "ledger": ledger, "within_budget": total <= char_budget}


def main():
    checks = []
    pushed = push_prefetch(DOCS, 4, ORDER)
    pulled, ledger = pull_fetch(QUERY, DOCS, INDEX, VOCAB, 3)
    kw = keywords_of(QUERY, VOCAB)

    checks.append(("词表匹配确定性可复现",
                   kw == ["退款", "凭证"] and keywords_of(QUERY, VOCAB) == kw))
    checks.append(("Push 按固定规则预取固定条数",
                   list(pushed) == ["d01", "d02", "d03", "d04"]))
    checks.append(("Pull 只取命中索引的条目", set(pulled) == {"d01"}))
    checks.append(("Pull 装入量不超过 Push", chars(pulled) <= chars(pushed)))
    checks.append(("Pull 精度高于 Push",
                   precision(pulled, RELEVANT) > precision(pushed, RELEVANT)))
    checks.append(("Pull 召回不低于 Push",
                   recall(pulled, RELEVANT) >= recall(pushed, RELEVANT)))
    checks.append(("Push 会装入无关条目", any(i not in RELEVANT for i in pushed)))
    checks.append(("Pull 有取用留痕", ("fetch", "d01") in ledger))
    checks.append(("Pull 取用次数不超过上限",
                   sum(1 for x in ledger if x[0] == "fetch") <= 3))
    checks.append(("Pull 先查目录再取原文多一步", ledger[0] == ("lookup", "index")))

    # 无命中时不硬塞内容，交给兜底处理
    miss_query = "随便问一句不含词表的话"
    empty_fetch, empty_ledger = pull_fetch(miss_query, DOCS, INDEX, VOCAB, 3)
    checks.append(("查询无命中时不硬塞内容", empty_fetch == {} and
                   sum(1 for x in empty_ledger if x[0] == "fetch") == 0))

    # 目录描述含糊，会让 Pull 漏取
    bad_index = dict(INDEX)
    bad_index["d01"] = "一些通用说明"
    bad_fetch, _ = pull_fetch(QUERY, DOCS, bad_index, VOCAB, 3)
    checks.append(("索引描述含糊会导致漏取", "d01" not in bad_fetch))

    # 混合：短目录常驻、原文按需、总量受预算
    mix = hybrid(QUERY, DOCS, INDEX, VOCAB, 3, char_budget=220)
    checks.append(("混合策略索引常驻、原文按需",
                   mix["catalog_chars"] > 0 and set(mix["fetched"]) == {"d01"}))
    checks.append(("混合策略总量不超预算", mix["within_budget"]))
    checks.append(("混合策略仍取回相关原文",
                   recall(mix["fetched"], RELEVANT) == 1.0))
    checks.append(("混合策略也留取用痕迹", ("fetch", "d01") in mix["ledger"]))

    snapshot = json.dumps({"pushed": sorted(pushed), "pulled": sorted(pulled)},
                          ensure_ascii=False)
    checks.append(("两种策略结果可落盘回看", json.loads(snapshot)["pulled"] == ["d01"]))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `DOCS` 是资料库（标识到原文），`INDEX` 是常驻目录（标识到一句描述），`VOCAB` 是可用于匹配的词表，`RELEVANT` 是本轮构造出来的标准答案。把「真正需要哪些」显式写出来，是为了让精度和召回能逐条手算，而不是靠感觉说「Pull 好像更准」。
2. `keywords_of` 用最朴素的「词在不在查询里」抽关键词，纯规则、无随机量；`push_prefetch` 按 `ORDER[:k]` 取前四条，故意**不看查询内容**，模拟「不管问什么先塞一批」的预取。
3. `pull_fetch` 分两步：先拿关键词去目录描述里找命中的标识，再按标识把原文取回；`ledger` 第一条固定是 `("lookup", "index")`，后面才是取用记录，这一步之差就是 Pull 多出来的那轮往返。`max_calls` 用切片直接卡住取用条数。
4. `precision` 与 `recall` 分别算「取回的里面多少相关」和「该取的取回多少」，`chars` 用文本长度示意装入量。有了这三把尺子，两种策略才有得比，而不是各说各话。
5. `hybrid` 把目录序列化成 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）常驻，原文仍走 `pull_fetch`，最后用 `len(catalog) + chars(fetched)` 和预算比对。它演示的是「Push 一小份 + Pull 大块」怎么在一份预算里共存。
6. `main` 前几组验核心对照：Push 固定取四条、含三条无关；Pull 只取一条且正好相关，装入量更小、精度更高、召回不吃亏。随后几组验 Pull 的代价与边界：多一步查目录、取用有上限、有留痕、无命中时不硬塞、目录描述含糊会漏取。
7. 最后几组验混合策略与可回看性，结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。整段只有 `json` 一个标准库依赖，所有数值可手工推算。

有一处如实说明：这里的「相关性」是手工标注的一个集合，命中靠词表字符串匹配，目录也只有六条。真实系统里命中要靠检索与排序，判断由模型完成；这段代码演示的是两种方向在**装入量、精度、往返、上限、留痕**上的差别，不是任何检索质量或收益的评估结论。

## 踩坑与边界

- **全量预取不问相关性**：现象是每轮塞回一大堆片段，大半没用上，预算被吃满 → 原因是让系统替模型猜、且猜错也照占 → 改成短目录常驻加按需取回，或先按 [元数据过滤前置](./k060-metadata-filter.md) 缩小范围。
- **目录写得含糊**：现象是「退款要什么凭证」匹配不到「一些通用说明」，Pull 一条都取不回 → 原因是描述没写清能对上的词 → 每条给一句不含糊的描述，先做 [查询改写与指代补全](./k059-query-rewrite.md)，见 [工具描述写法](./k033-tool-description.md)。
- **零命中时硬塞内容**：现象是没匹配到就随手把前几条原文塞进去充数，又回到膨胀 → 原因是没有明确的兜底路径 → 老实拒答或退回最小常驻集，见 [溯源、拒答与零召回兜底](./k062-citation-abstain.md)。
- **不设取用上限**：现象是模型反复拉同一批资料，一轮取十几条，上下文又撑满 → 原因是把 Pull 当成免费动作 → 一轮最多取几条写成硬上限，每笔取用留痕，见 [四重预算](./k103-four-budgets.md)。
- **把关键约束也交给 Pull**：现象是这一轮没取到「不得编造工单编号」，边界就松了 → 原因是允许「取不到就算了」发生在不能丢的项上 → 约束与目标用 Push 每轮常驻，见 [写选压隔四类操作与不可压缩项](./k139-context-ops.md)。

还要分清一道边界：Push 与 Pull 管的是**资料以什么姿态进上下文**，管不了「检回来之后排得对不对」，那是 [粗排 + 精排与重排后截断](./k061-rerank.md) 的活；也管不了「取回的长原文怎么压短」，见 [检索式召回压缩](./k045-retrieval-compression.md)。三者共用「检索」这个词，但一个管方向、一个管顺序、一个管长度。另一头，混合策略里的常驻目录会占常驻份额，得和 [上下文预算表](./k041-context-budget.md) 一起定数，还要保持逐字稳定才谈得上 [前缀缓存与即时注入](./k050-prefix-cache.md) 的复用；别为了「目录更全」把它写成一大本，那等于把全量预取换个名字搬回来。

## 三句话小结

Push 与 Pull 按需拉取，讲的是资料进上下文的两种方向：系统主动预取省一轮往返却容易白占预算，模型按需取回省地方却要多等一轮并承担判断风险。

关键做法是用短而稳的常驻目录配大块原文按需取回、把命中依据写清、给取用设次数上限并留痕、零命中走明确兜底、关键约束仍每轮常驻。

当资料库小到可以整份常驻、或一轮里几乎每条都会用到时，不必硬套按需取回；但只要原文又多又长、真正用得上的只是少数几条，混合就比「先塞一批」或「全靠现取」都稳。

# 什么时候才该拆多智能体

你接了一个「自动整理用户反馈」的活，第一反应是：这活有好几步，不如拆成三个智能体，一个分类、一个摘要、一个写回复，看起来专业又清楚。真跑起来却发现回复老是接不上分类的结果，三个角色互相等、互相覆盖，改一处规则要动三份说明，最后连「这单到底算做完了没有」都说不清。

**不是拆得不够细，是把「步骤多」误当成了「该拆成多个智能体」。** 步骤多只说明任务有流程，流程完全可以由一个智能体按轮次走完；拆开是另一种成本更高的结构，只有当某些条件真的成立时才划算。把结构复杂度提前扛上身，等于给自己加了一份协调工作，却没换来对应的收益。

先把词说清。智能体（Agent）指能自己决定下一步做什么、并按需调用工具的程序，它跟「按固定顺序执行的代码」不一样，路径会随输入变。多智能体（Multi-Agent）是把一个任务交给几个这样的程序协作完成，彼此通过消息传递结果。上下文（context）是某一轮里模型能看到的那一段文字，包含目标、已发生的轨迹和工具结果。提示词（prompt）是写给模型的规则与任务说明。请记住「智能体」的要害在「自己选下一步」，而不是「跑得快」；这一点后面判断该不该拆时会反复用到。

## 一、生活类比：什么时候才该多雇一个人

想象你开一家小面馆，只有一个厨师。订单来了，他煮面、加浇头、装碗、收台，一单接一单，忙是忙，但从不出错，因为所有信息都在他一个人脑子里。什么时候你会真的再雇一个人？大概只有三种情况：第一，煮面和做浇头需要两套完全不同的手艺，一个人兼顾不过来；第二，两个灶台的配料绝不能混，必须物理隔开，各看各的单子；第三，煮好的面能不能出餐，浇头合不合格，可以分别验收，不用等整碗端上桌才知道。

如果只是为了「看起来像两条流水线」而雇人，你会发现多出来的不是产能，是传话：谁先做、谁等谁、两边说法不一致听谁的、一个人请假整单怎么办。厨房里多一个人，就多一份沟通成本。**拆多智能体跟雇人是同一笔账：只有「手艺真不同、材料要隔开、能分别验收、同时做确实省时间」这几条里至少占住两条，多出来的那份协调成本才被抵掉。** 对应关系是：厨师对应一个智能体，灶台上的单子对应上下文，分开的配料对应彼此不该看见的材料，出餐前的检查对应验收条件，多雇的厨师之间互相喊话对应消息传递。

## 二、把「该不该拆」变成四个可勾选的信号

拆解的理由必须能被别人复核，不能凭一句「感觉挺复杂的」。把判断收成四个信号，每个只回答是或否：职责差异是不是真的、上下文是不是必须隔离、每块结果能不能独立验收、同时跑是不是真有并行收益。前两条说的是「不拆会出问题」，后两条说的是「拆了确实有好处」，缺了前两条里的任意一条，拆分往往只是把复杂度搬了个位置。

:::figure 判断该不该拆的四个信号
@stack
职责差异 真::几块活真需要不同角色与知识，不是换个名字
上下文隔离 真::彼此不该看见对方材料，避免互相污染
独立验证 真::每块结果能单独判真假，不靠整单猜测
并行收益 真::同时跑确实省时间，而不是串行加协调
:::

这里有个容易被忽略的次序：四个信号不是平权投票。「上下文隔离」和「独立验证」是两条硬理由，它们直接对应厨房里「配料不能混」和「出餐前能分别检查」。只有「职责差异」和「并行收益」成立、却既不需要隔离也不能分别验收时，拆开通常得不偿失——因为所有子结果最后还是要回到同一个地方汇总，等于多绕了一圈。这也是为什么单智能体在多数真实任务里更稳：工具设计得好的单智能体，本来就能在一轮一轮里换角色，不必真的切成几个进程。

:::ask 那如果四个信号都成立，是不是拆得越细越好？
不一定。拆得越细，消息条数、共享字段、失败分支都会跟着涨，而收益并不会一直往上走。细到「每块产出一句话」时，协调开销往往已经超过并行省下的时间。合理的做法是拆到「每块能独立验收」为止就停，再细只会让「完成没有」更难判断——这一点会在[任务拆分与完成标准](./k119-task-decomposition.md)里展开。
:::

:::ask 那如果只有「想让回答快一点」这一个理由呢？
那更不该拆。想快可以先把工具调用做幂等、把检索结果缓存起来、把不相关的工具从上下文里拿掉，这些动作都在单智能体内部就能完成，不需要引入消息传递。代码里那个「只是想让回答快一点」的用例被判成不拆，理由正是这个：**速度问题优先在单体内解决，别用结构改动去补性能。**
:::

:::figure 为拆而拆与有理由地拆
@compare
先拆再说::角色名起了三个|材料还是同一份|完成与否靠感觉
先问信号::隔离或验收成立|至少命中两条|收益能说清出处
:::

真正决定拆不拆的，不是「任务有几步」，而是右边这三条能不能逐条指给人看。指得出来，讨论就落在工程上；指不出来，讨论就会滑向「哪个框架支持几个角色」这种跟任务无关的话题。后面讲[主从 / 流水线 / 辩论三种模式](./k118-multi-patterns.md)时你会看到，三种模式都是在「已经决定要拆」之后才谈的消息怎么走，顺序反了就会白做很多设计。

## 三、把判断写成能跑的程序

下面的脚本零依赖、不需要账号、不需要联网，用一个本地构造的判定器把上面四个信号变成可复核的结果。它不调用任何模型，只做确定性判断，所以你随时可以重跑核对。

```python
# k117.py —— 拆不拆多智能体的判定器（零依赖，python k117.py）
SIGNALS = ("职责差异", "上下文隔离", "独立验证", "并行收益")


def decide(signals):
    """signals 每个信号给 0 或 1；返回 (是否该拆, 理由)。"""
    present = [s for s in SIGNALS if signals.get(s, 0) == 1]
    # 两条硬理由：上下文确实要隔离，或每块结果能独立验收
    foundation = (signals.get("上下文隔离", 0) == 1
                  or signals.get("独立验证", 0) == 1)
    if not present:
        return False, "四个信号一个都不成立，属于为拆而拆"
    if not foundation:
        return False, "既不需要隔离上下文，也不能独立验收，拆只是把复杂度挪了个位置"
    if len(present) < 2:
        return False, "只命中一个信号，协调开销大于收益"
    return True, "命中 %d 个信号且含隔离/验收需求，可以拆" % len(present)


CASES = [
    ("把长文压成三句话",
     {"职责差异": 0, "上下文隔离": 0, "独立验证": 0, "并行收益": 0}, False),
    ("两块材料互相不能看见，各自出结论再合并",
     {"职责差异": 1, "上下文隔离": 1, "独立验证": 1, "并行收益": 1}, True),
    ("只是想让回答快一点",
     {"职责差异": 0, "上下文隔离": 0, "独立验证": 0, "并行收益": 1}, False),
    ("角色名不同但干的是同一件事",
     {"职责差异": 1, "上下文隔离": 0, "独立验证": 0, "并行收益": 0}, False),
    ("两道校验互不共享草稿，各自能单独判定",
     {"职责差异": 1, "上下文隔离": 1, "独立验证": 1, "并行收益": 0}, True),
]

if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    for name, sig, expect in CASES:
        got, reason = decide(sig)
        check(name + " -> " + ("拆" if got else "不拆"), got == expect)
        check("  给出理由", bool(reason))
    check("零信号默认单 Agent", decide({})[0] is False)
    check("理由里带命中数量", "命中" in decide(CASES[1][1])[1])
    print("通过 %d/%d 项" % (passed, total))
```

跑一遍会打印出每条用例被判成「拆」还是「不拆」，最后一行是断言汇总：

```text
  [通过] 把长文压成三句话 -> 不拆
  [通过] 两块材料互相不能看见，各自出结论再合并 -> 拆
  [通过] 只是想让回答快一点 -> 不拆
通过 12/12 项
```

逐段解释关键行在做什么：

1. `SIGNALS` 把四个理由写成固定元组，顺序即后面打印和统计的顺序，避免每次判断时临时想「是不是漏了一条」。
2. `present = [s for s in SIGNALS if signals.get(s, 0) == 1]` 只收集被勾成 1 的信号；用 `get(..., 0)` 是为了缺字段时按「没这条理由」处理，而不是抛异常。
3. `foundation` 单独把「上下文隔离」与「独立验证」拎出来做或运算，这就是前面说的两条硬理由；它和 `present` 分开算，正是为了表达「不是平权投票」。
4. `decide` 里三个 `return False` 按代价从大到小排：一个信号都没有、没有硬理由、只命中一条。每条都带一句中文理由，方便把判定结果直接贴进评审记录，而不是只给一个布尔值。
5. `CASES` 是五个本地构造的场景，每个都写死了期望结果。注意「角色名不同但干的是同一件事」和「只是想让回答快一点」这两条，专门用来挡住最常见的两种误判。
6. 主程序里的 `check` 用 `assert` 兜底，任何一条不符会直接让脚本失败；最后打印 `通过 N/N 项`，把「判定器本身对不对」也变成可复核的一行输出。

:::warn 别把判定器当成打分模型
这份代码只是把「你有没有想清楚」显式化，它不会替你判断业务上是否真的需要隔离。四个信号的值仍要由人来填，填错了它照样给出整齐的结论。**工具的用处是逼你把理由写出来，不是替你给理由。**
:::

## 四、踩坑与边界

- **按步骤数拆**：现象是「流程有五步，就建五个角色」→ 原因把流程步骤误当成职责边界，步骤之间共享同一份上下文 → 怎么改：先让单智能体按轮次走完五步，只有当某两步确实需要隔离材料或分别验收时才切开。
- **角色名替代职责**：现象是起了「分析员、审核员、撰写员」三个名字，三者看的却是同一段材料、用同一套说明 → 原因是只做了命名拆分，没做信息隔离 → 怎么改：回去核对「上下文隔离」与「独立验证」两条，任一不成立就合并回单智能体。
- **为速度而拆**：现象是拆完反而更慢，大量时间花在等消息和合并结果上 → 原因是并行收益只在子任务真能同时跑且互不依赖时成立 → 怎么改：先做工具幂等、结果缓存、无关工具不进上下文，把优化留在单体内。
- **拆完没有整单结论**：现象是每个子结果都「看着完成了」，但没人能说清整单做完没有 → 原因是缺少统一的完成判定，只靠观察各角色的输出 → 怎么改：给整单也写一条可判定的收尾条件，具体做法见[状态共享、冲突处理与失败恢复](./k120-shared-state.md)。
- **把例外当常态**：现象是为了一个罕见分支专门加一个角色，日常任务全都要多绕一次 → 原因是按最复杂的情况设计结构 → 怎么改：让单智能体在遇到该分支时临时切换处理方式，别为低频路径长期付协调成本。

:::figure 一次必要性判定的顺序
@flow
列出四信号|查隔离验收|数命中条数|给出拆不拆|留一行理由
:::

这张图里最容易被跳过的是最后一步「留一行理由」。没有那行字，判定就只是个开关；有了它，后面被追问「当时为什么这么定」时才拿得出东西。面试里被追问的往往正是这行字，相关展开放在[四层追问链与转行者三问](./k125-followup-chain.md)。

:::quote
拆分不是把任务切小，是给「谁必须看不见谁、谁的结果能单独算数」这两个问题一个明确的答案。答不上来，就先别切。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能说清「步骤多」和「该拆多智能体」不是一回事
- [ ] 能背出四个信号，并指出哪两条是硬理由
- [ ] 面对「只是想快一点」能给出不拆的理由与替代做法
- [ ] 能解释为什么命中信号少于两条时仍优先单智能体
- [ ] 每次给出拆或不拆，都能留下一行可复核的理由
:::

是什么：这是一套把「要不要拆成多个智能体」变成四个可勾选信号的判断方法，默认答案是先用单智能体。
关键做法：先核对上下文隔离与独立验证这两条硬理由，再数命中条数，把结论连同理由一起留下来。
什么时候不该用：任务路径固定、材料本来就共享、各块结果无法分别验收时，别拆，也别用拆开来解决速度问题。

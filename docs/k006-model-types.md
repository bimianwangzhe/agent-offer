# 基础模型 / 指令模型 / 推理模型：按任务挑，不按参数挑

## 一、"大的那个"反而不太好使

你手上有几个可选的模型，名字后面都跟着一串参数规模。你挑了数字最大的那个，心想"个头大的总归更聪明"。结果让它续写一段小说开头，它老老实实回了一句"好的，请问希望什么风格"，就是不往下接；让它做一道要分几步核算的题，它秒回一个结论，看着利落，中间哪一步算错了你根本看不出来。反过来，换个数字小得多的来回答直白问答，反倒干脆好用。

你会纳闷：明明参数差了好几倍，怎么"大"的还不好使？其实它没答错什么，它答的"形态"压根不是你要的那种。

## 二、先破误解

**不是参数越大越适合，这三类的差别在训练目标，不在个头；选型看的是"这件事要它产出什么"，不是谁的数字好看。**

先把三类讲白。基础模型（base model）的训练目标最朴素：给一段文字，把它接下去。你给它半句开头，它顺着往下写最拿手；你给它一句提问，它也可能接着"续写出更多提问"，而不是回答你——因为在它读过的文本里，问句后面常常还是问句。指令模型（instruct model）是在这个基础上再调一调，让它学会"听懂请求、直接给答复"，所以一问一答、按格式办事最利落。推理模型（reasoning model）训练时更偏向把中间步骤展开、再收口给结论，多步核算、需要拆解的任务更稳，代价是文字更长、更慢、更贵。

参数规模是另一个维度上的信息，说的是模型里那批可调数值的量级，跟"被训练成干什么"不是一回事。宣传口径常把两者混着讲，容易让人把"个头大"直接读成"什么活都干得好"。可一旦分清楚，开头那三件别扭就全说得通了：让续写见长的基础模型去问答，它会把你的问题当开头接着写；让问答见长的指令模型去多步核算，它会直接蹦结论、把中间过程省掉，错了也不留痕迹；让爱展开步骤的推理模型去写一句告示，它能给你列上六步工序，慢且啰嗦。三类都不差，只是被训练成了干不同的事，用错的表现是"形态不对"，不是"能力不行"。

:::tip
先问"这一步要它产出什么"，再问"哪类模型擅长产出这种东西"，参数规模留到最后看。
:::

## 三、生活类比：三位师傅，三种干法

想象你要装修，手里有三位师傅。一位临摹老画习惯了，你递给他半幅画，他会顺着笔意往下补；一位是前台接待，你问一句他答一句，利落、照规矩来；一位是老监理，动手前先把料、工序、验收一条条写清楚，再开始干。

你把"把这幅画补完"交给前台，他会礼貌地问"您想补成什么风格"；把"核算这面墙要多少料"交给前台，他张口就给一个数，中间怎么算的不写；把"门口贴张告示"交给老监理，他能给你排出六步工序。三位都不差，只是练出来的手艺方向不同。对应关系逐条摆：

- 半幅画顺着往下补，是基础模型的续写；
- 问一句答一句，是指令模型的问答；
- 先列工序再动手，是推理模型的分步；
- 师傅的资历年限，是参数规模，属于另一个维度；
- "那就找资历最老的那位吧"，是按参数挑；
- 活儿干得别扭，是类型和任务不匹配，不是手艺不行。

这个类比最该带走的，是"资历"和"工种"分开看。你不会按谁年纪大来派活，你会按这活是补画、答疑还是核算来派人。模型选型同理：先把任务翻译成"要续写、要直答、还是要展开步骤"，再去对哪一类擅长，最后才轮到看个头与价格。

## 四、画出来：差别在哪一层

先看三类各自被训练去做什么，这一层决定了输出的形态：

:::figure 三类模型各自的训练目标
@stack
基础模型::把文字接着往下写，续写最顺手
指令模型::听懂请求直接给答复，问答最利落
推理模型::先展开中间步骤再收口，多步核算更稳
:::

三类不是"程度高低"，是"方向不同"。同一个输入交给它们，得到的不是同一个答案的三种质量，而是三种压根不同的东西：一段续写、一句结论、一串步骤加结论。

再把两种选型依据摆在一起：

:::figure 两种选型依据的差别
@compare
按参数挑::只看个头|形态常不对|贵还未必合用
按任务挑::先看要什么|形态对得上|成本可控
:::

左边那行的麻烦在于，它省掉了"这活要什么"这一步，直接跳到"谁更大"，于是形态对不上，钱还多花了。右边那行多问一句，反而更容易一次挑对。两张图合起来只说一件事：训练目标决定形态，任务决定该选哪一类；参数规模是附带信息，不是判据。

## 五、顺着追问两层

:::ask 那如果我只留一个"最全能"的，是不是就不用选了？
:::

可以当省事的做法，但要清楚付的是什么代价。让偏展开步骤的那类去处理直白问答，它常常绕一圈、慢一拍、字更多，单次成本也跟着上去；而"全能"这个词本身多半来自宣传口径，不是你能核对的性质。稳妥的做法是拿自己的几类真实任务各试一组，看形态对不对、能不能解析、耗时和用量是多少，而不是听一句"什么都行"。这也和[采样参数与不确定性](./k004-sampling.md)里那句提醒同源：别把一句描述当成保证，判定要落在能查的地方。至于成本怎么按任务记下来，[用量统计与计费口径](./k010-usage-billing.md)会讲那条账。

:::ask 那如果同一个任务里既有直白问答、又有多步核算，怎么办？
:::

把它拆成步骤，按每一步分别路由：先判断这一步属于哪一类，再交给擅长它的实现，而不是整单挑一次就定死。这里有个容易被忽略的点——"按任务匹配"这个判断是在每一步发生的，不是开局做一次。比如先用一个利落的问答把用户要什么问清楚，再把需要核算的那段单独交给会展开步骤的实现，最后把结果整理回一句答复。这样做还有个附带好处：将来换掉某一类实现时，业务那几步不用跟着重写，只要替掉"这一步交给谁"的映射就行。要把这种"可替换"落到实处，得先把一次调用拆成能逐项换掉的几块，那是[一次请求拆成五块](./k008-request-anatomy.md)接着讲的事。整条线从哪里起步，可以看[从这里开始](./00-start-here.md)。

## 六、跑一段代码，把"按任务挑"摸实

下面这段只用标准库，不联网、不装包、不要账号。它用三个本地桩模拟三类模型对同一句输入的不同反应，并演示选型只看任务类型、不看参数量。

```python
# 三类模型：训练目标不同 -> 擅长的任务不同；参数量只是附带信息。
MODELS = [
    {"kind": "基础", "params_b": 70, "good_at": "续写"},
    {"kind": "指令", "params_b": 7, "good_at": "问答"},
    {"kind": "推理", "params_b": 32, "good_at": "多步计算"},
]


def choose(task):
    for m in MODELS:
        if m["good_at"] == task:
            return m
    raise ValueError("没有匹配的任务类型：" + task)


def respond(kind, prompt):
    if kind == "基础":
        return prompt + "，接着往下写……"
    if kind == "指令":
        return "结论：已按要求完成。"
    if kind == "推理":
        return "步骤1 拆解｜步骤2 校验｜结论：已按要求完成。"
    raise ValueError("未知模型种类：" + kind)


if __name__ == '__main__':
    checks = 0

    # 1) 按任务匹配选型，而不是按参数量挑最大的
    m = choose("问答")
    assert m["kind"] == "指令"
    checks += 1
    assert m["params_b"] != max(x["params_b"] for x in MODELS)
    checks += 1

    # 2) 同一句输入，三类模型的输出形态明显不同
    outs = {k: respond(k, "写一段开头") for k in ("基础", "指令", "推理")}
    assert outs["基础"].startswith("写一段开头")
    checks += 1
    assert outs["指令"].startswith("结论")
    checks += 1
    assert "步骤1" in outs["推理"] and "结论" in outs["推理"]
    checks += 1
    assert len(set(outs.values())) == 3
    checks += 1

    # 3) 任务类型没登记时，明确报错而不是随便挑一个
    try:
        choose("闲聊")
        raise AssertionError("应当抛错")
    except ValueError:
        checks += 1

    print("通过 %d/%d 项" % (checks, 7))
```

逐段看它在做什么：

1. `MODELS` 里每个条目带三个字段：`kind` 是哪一类、`good_at` 是它擅长的任务类型、`params_b` 是参数规模的示意数字。要留意 `params_b` 只是摆在那儿的附带信息，`choose` 从头到尾没看它一眼。
2. `choose` 只按 `good_at` 匹配任务，匹配不到就 `raise ValueError`，绝不"随便挑一个凑合"。这对应"先看这活要什么"。
3. `respond` 是三个本地桩：基础类把 `prompt` 原样接在前面往下写，指令类直接给结论，推理类先列步骤再收口。同一句输入得到的三份输出形态完全不同，正是第二张图里"方向不同"那件事。
4. 断言一、二合起来最贴题：选"问答"选中的是"指令"，而且它的 `params_b` 并不是三者里最大的——这就把"按参数挑"直接否定掉了。
5. 断言三到六逐个钉住三种形态：续写以原文开头、直答以"结论"开头、分步既含"步骤1"又含"结论"，且三份输出互不相同。
6. 最后一段验证未知任务会明确报错，而不是悄悄回退到某个默认实现；接着打印通过项数。

必须说清边界：`params_b` 和三个 `respond` 里的话全是为演示现编的，不代表任何真实模型的规模或表现，也不构成任何比较结论。这段代码只演示"选型依据是任务类型"这一条。想看清"接着往下写"到底是怎么一步步发生的，回看[下一个词预测](./k002-next-token.md)最顺。

## 七、踩坑与边界

- **按参数规模挑**：现象是数字最大却答得别扭、还更贵 → 原因是参数与训练目标是两回事 → 先把任务翻成"续写、直答、还是分步"，再对类型。
- **拿续写见长的当问答用**：现象是你提问、它接着写出更多提问 → 原因是它的目标是"接下去"不是"回答" → 换对齐到听指令的那类，或把输入改写成明确的续写开头。
- **让直答型硬做多步核算**：现象是秒回结论、错了查不出在哪 → 原因是中间步骤被省掉 → 交给会展开步骤的那类，并让代码核对每个中间量。
- **用宣传口径代替自己的任务验证**：现象是"全能"听着好、上手不合用 → 原因是描述不是可核对的性质 → 拿自己几类真实任务各试一组，看形态与用量。
- **换一类实现就重写业务**：现象是选型一变，业务代码跟着大改 → 原因是"交给谁"和"业务逻辑"缠在一起 → 把按任务路由单独隔一层，替换只改映射。

## 九、三句话小结

基础、指令、推理三类的差别在训练目标，决定了输出是续写、直答还是分步加结论。
要紧的做法是先把任务翻译成要产出什么形态，再按这个去选，参数规模只当附带信息。
当你面对一句"什么都行"的宣传口径、或需要逐字确定与可核对的中间步骤时，别指望挑个大的糊过去，改用任务匹配加代码校验。

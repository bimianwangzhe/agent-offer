# 版本漂移与升级策略

## 一、场景提问

你写好了一个能查资料、能调工具、会返回结构化结果的 Agent，本地挑了十几条用例跑得稳稳的，于是放到对外服务里，之后一个多月都没动过一行代码。某天早上，用户开始反馈：有的回答里凭空少了引用来源，有的工具调用直接报「字段解析失败」，还有人说答案的语气和以前不一样了。你翻自己的提交记录，确实是空的；再把同样的输入喂进去，有时又正常了。更让人发懵的是，同一个功能昨天还好好的，今天却像换了个脾气。你明明什么都没改，它怎么就自己变了？

## 二、破误解

**不是你的代码坏了，也不是模型突然变笨，而是你依赖的那几样东西在你看不见的地方悄悄换了版本，你写死的假设随之失效了。**

先把「版本漂移」这个词说清：版本漂移（version drift）指你不曾主动改动，但所依赖的外部对象——模型的具体快照、工具返回的结构、框架与依赖库、主体间约定的消息字段——随着时间发生了改变，于是原本贴合的代码和这些对象之间出现了缝隙。它和「你主动升级」是两件事：升级是你知情、选了时机、可以回退的动作；漂移是你不知情、没得选、往往在出错之后才被发现的被动变化。很多初学者只把「版本」理解成自己代码仓库里那个数字，于是把代码锁得很牢，却把真正决定行为的外部契约完全敞开。要补的不是「把测试写得再多一点」——固定用例全过，也挡不住供应方在同名版本号下换一份快照、给工具多加一个字段、改一处默认参数；要补的是把「外部依赖到底是哪一套」当成一件需要显式记录、显式校验、显式切换的事。这里有两个词先说在前面：契约（contract，指你对某个返回值「必须有哪些字段、各是什么类型」的明确约定），以及契约校验（拿真实返回逐条比对这份约定，不合就当场报错，而不是等下游用到时才崩）。所谓抗漂移，本质就是让任何一次「悄悄变化」都必须先过契约这一关，再谈要不要接受它。还有一句容易被忽略：漂移不一定是变坏，也可能是「变得不一样」——答案更啰嗦、字段顺序换了、数值从数字变成字符串，业务没崩，但下游按老格式解析就错了，这类不报错的坏最难查，因为它不会给你一条异常堆栈。

顺着这个思路再往下理一层：漂移之所以难缠，是因为它跨越了你和供应方之间的责任边界。你自己能决定的只有「我认哪一套」，决定不了「对面什么时候改」。所以能做的不是去阻止对面改，而是在自己和对方之间加一道可检查的关口，把「对面变了」这件事从一次事故，变成一条你能看见、能选择、能退回的记录。这也解释了为什么光靠盯日志不够：日志记的是「结果坏了」，契约记的是「约定被破了」，后者比前者早一步、也更贴近根因。

## 三、生活类比

把它想成一家做定制柜的木工坊。师傅手里有一张下料单，写着「侧板按 18 毫米厚的板材裁、孔位距边 32 毫米」，这套尺寸是他反复试过、装起来严丝合缝的。他按单子接了半年的活，一直没出问题。后来板材供货商没打招呼，把同一型号标称 18 毫米的板子实际压到了 17.5 毫米，孔距标准也微调了一点。下料单一个字没改，师傅的手法一个动作没变，可裁出来的板子拼上去就是有缝、螺丝对不上孔，客户开始投诉「你们工艺退步了」。

对应关系很具体，值得逐条对上：那张下料单，就是你的代码与提示里写死的假设——按什么字段名取值、期望什么类型、走哪套解析；供货商「同型号、悄悄换了实际规格」，就是供应方在同名版本号下更新了模型快照、改了工具结构、动了默认参数；裁好的板子拼不严，就是结构化结果解析失败、引用来源丢失、答案风格偏移这类对外可见的异常；而「客户投诉工艺退步」，恰恰对应误把外部漂移当成自己代码变笨。这个比喻还点出最要命的一处：最怕的不是板材变了，而是师傅既没在每批来料上卡一下厚度、也没留一张旧板做对照，等缝出现了根本说不清「是这批料变了，还是我裁错了」。

所以一家稳当的作坊会做三件小事，正好对应系统里的三件大事：每批来料先验规格再上架，就是拿契约校验逐条比对真实返回；留一块旧板当样板、新板先拿去试装不正式出货，就是影子对比——让候选版本照常产出、但先不切真实流量，只比和旧版差多少；把「这批用的是哪家的哪一规格」记在单据上，就是版本锁定与快照。哪天真要换供货商，师傅还得有一套能重新校准孔距的垫片和量具，这就是适配层：把新结构的差异吸收在一处，而不是让每张下料单都去改一遍。放到框架里，这层隔离的意义在 [解耦适配层](./k077-adapter-layer.md) 里讲得更细；工具那侧字段该怎么定才不容易漂，可对照 [工具 Schema 设计](./k032-tool-schema.md) 与 [工具协议与标准化接入](./k078-tool-protocol.md)。

## 四、自绘示意图

:::figure 一次版本漂移怎样演变成对外故障
@flow
依赖未锁定|上游悄悄改版|契约被破坏|行为偏移|对外服务出错
:::

这张图里每一格都是一次「本可以拦住」的机会，而不是同一件事的五种说法。「依赖未锁定」是最靠前、也最常被跳过的一格：很多人觉得版本是部署时才要操心的事，于是从写代码起就没把「我认哪一套」记下来，等到第三格「契约被破坏」时才第一次察觉。中间那格「行为偏移」尤其阴险——它未必抛异常，可能只是答案变啰嗦、少了个字段、数值换了类型，等它走到最后一格被用户发现，往往已经过去好几天，排查时还得倒着把这四格重走一遍。

:::figure 版本漂移的四个常见来源
@stack
模型快照::同版本号下的后台更新，行为悄悄变
工具结构::字段增减、改名、类型调整，解析即失效
框架与库::小版本升级改了默认参数或返回格式
协议字段::消息字段改名，主体间约定对不上
:::

四格里最容易被漏掉的是「模型快照」：很多人以为只要不主动换型号就万事大吉，却没意识到同名版本号背后那份实际权重可能已被替换。第二、四格属于结构性漂移，最硬也最好查——字段一改名，契约校验当场就能报出来；第一、三格属于行为性漂移，不报错，只能靠影子对比和一批固定输入去照出差异。分清这两类，才知道该用契约还是用对比去兜。

:::figure 两种版本管理姿势的差别
@compare
跟着最新走::改动无感知|出错难归因|退回没落点
显式锁加适配::变化先被校验|契约兜住结构|按版本号升级
:::

左边是「默认用最新」的省事做法，风平浪静时最轻松，一旦对面改了就是全书最贵的那种排查；右边把「变化」从一次被动事故，改写成一道有校验、有对照、有版本号可退的关口。二者的差距，全在出问题的那一刻你能不能说清「是哪一套变了、退到哪一套去」。

## 五、层层追问

:::ask 那如果我全程只用一个模型、一个框架，索性永远不升级，是不是就不会漂移了？
:::

这个想法很自然，但只挡住了一半。要先分清「你不主动升级」和「对面保持不动」是两件完全不同的事：即便你一个版本号都不改，供应方仍可能在同名版本号下更新快照、调整默认采样参数、给工具返回值补一个字段，甚至在某个时间点把旧端点退役。你能锁住的只有自己的选择，锁不住对面的日历。所以「永远不升级」并不能消灭漂移，它只是把漂移从「看得见的一次升级」变成了「看不见的一次后台变化」，反而更难察觉。再往下一层问：那长期不动是不是更安全？也不尽然。依赖放着不动，会一点点攒下兼容与安全方面的欠账，等哪天因为旧端点下线被迫一次跨好几个版本，改动面反而比小步跟进大得多，排查难度陡增。真正稳的做法不是假装一切不变，而是把版本显式化：记清楚「当前认哪一套」，用契约校验盯住结构、用影子对比照出行为差异，再由你自己挑时机决定要不要换。这样对面的任何一次「悄悄变化」，都会先撞上一道关口，而不是直接撞上用户。至于这套固定输入与阈值怎么组织成「能不能换」的判定，[回归门禁与基线](./k091-regression-gate.md) 里有展开；把提示词、策略这类同样会悄悄改的东西也纳入版本管理，可对照 [提示与策略版本化](./k113-prompt-versioning.md)。一句话：不升级不等于不漂移，能选时机地升级才叫管理。

:::ask 那如果我真把版本锁死了，供应方哪天把旧版整个下线，锁死不就反而把我卡住了吗？
:::

这一问问到了「锁」的真正含义，也是最容易被误解的地方。锁版本从来不是为了永久不动，而是为了让「变化」从一个你被动承受的事件，变成一个你主动安排、且随时能退回的动作。换句话说，锁定买到的不是「不变」，而是「选择权」：在对面改动的那一刻，你手里仍有一套已知可用、可对外交代的配置在跑，不必被牵着当场跟着切。想让这份选择权真的能用，得配齐三样东西。第一是适配层：新版的字段改名、类型调整，都收在一处归一回旧契约，业务代码不用满世界改 `if-else`，这层的取舍和 [框架选型与自研编排的取舍](./k083-build-vs-framework.md) 是同一套思路。第二是升级前的对照：拿同一批输入让候选版先影子跑一遍，结构和行为都比过、一致率达标才放行，别把「装得上」当成「跑得对」，这一步和 [影子模式、灰度与回滚](./k112-shadow-canary.md) 的闸门是一回事。第三是可回退的落点：万一新版在真实流量里露出问题，得能按事先记好的版本号退回上一套，且提示、模型、路由都一起退。再往下一层：旧版被下线这种「不得不换」的情形，恰恰说明当初更该把版本快照、契约定义、适配规则都留成可查的记录——否则临时被迫跨版本时，你连「旧版到底返回什么结构」都还原不出来，只能靠猜。让外部能探知当前状态、给关键指标定好可守护的线，可参考 [健康检查与 SLO](./k114-health-slo.md)（SLO，Service Level Objective，服务等级目标）；把每次返回的结构留痕、事后能倒着重放，思路和 [结构化日志与轨迹回放](./k095-structured-log.md) 相通。把「升级」做成一个写进记录、可校验、可重放、可退回的确定性动作，锁版本才不会变成锁死自己。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一段本地桩函数模拟「同一工具在旧版与悄悄漂移后的新版」两种返回结构，完整演示「契约校验抓到漂移 → 适配层归一回契约 → 影子对比整批一致率 → 达标才按版本号升级、不达标就停在锁定版」。所有输入都由请求编号确定性生成，结果可手工推算、可复现；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path


# 契约：对返回值「必须有哪些字段、各是什么类型」的明确约定
CONTRACT = {
    "answer": str,
    "score": float,
    "sources": list,
}


def tool_response(version, req_id):
    """本地桩函数：模拟同一工具在不同版本下的返回结构。"""
    n = int(req_id.split("-")[1])
    answer = "答案-%03d" % n
    if version == "v1":
        return {
            "answer": answer,
            "score": round(0.5 + (n % 5) * 0.1, 2),
            "sources": ["doc-%d" % (n % 3)],
        }
    # v2 悄悄漂移：数值变字符串、字段改名、还多带一个字段
    return {
        "answer": answer,
        "score": "%.2f" % (0.5 + (n % 5) * 0.1),
        "citations": ["doc-%d" % (n % 3)],
        "extra": True,
    }


def check_contract(resp, contract):
    """返回 (是否合规, 问题描述列表)：逐字段查存在与类型。"""
    problems = []
    for field, expected in contract.items():
        if field not in resp:
            problems.append("缺字段 %s" % field)
            continue
        value = resp[field]
        # 用 type 精确比对，避免 int/bool 之类子类关系造成误判
        if type(value) is not expected:
            problems.append("字段 %s 类型应为 %s，实为 %s" % (
                field, expected.__name__, type(value).__name__))
    return (len(problems) == 0, problems)


def adapt(resp):
    """适配层：把漂移后的新结构归一回旧契约，不改动业务语义。"""
    return {
        "answer": resp["answer"],
        "score": float(resp["score"]),
        "sources": list(resp.get("citations", resp.get("sources", []))),
    }


def shadow_compare(req_ids, old_version, candidate_version):
    """升级前影子对比：同一批输入，比较归一后关键字段是否一致。"""
    same = 0
    for r in req_ids:
        old_ok, _ = check_contract(tool_response(old_version, r), CONTRACT)
        if not old_ok:
            continue
        normalized = adapt(tool_response(candidate_version, r))
        new_ok, _ = check_contract(normalized, CONTRACT)
        if new_ok and normalized["answer"] == tool_response(old_version, r)["answer"]:
            same += 1
    return same / len(req_ids) if req_ids else 0.0


class VersionLock:
    """显式版本锁：把生效版本写进可查快照，升级须过契约与影子两关。"""

    def __init__(self, path, active="v1"):
        self.path = Path(path)
        self.active = active
        self.pinned = active
        self._write()

    def _write(self):
        self.path.write_text(json.dumps({
            "active": self.active,
            "pinned": self.pinned,
        }, ensure_ascii=False, sort_keys=True), encoding="utf-8")

    def try_upgrade(self, candidate, req_ids, threshold):
        """返回 (是否升级, 原因)：候选版须能归一进契约，且影子一致率达标。"""
        sample = adapt(tool_response(candidate, req_ids[0]))
        norm_ok, problems = check_contract(sample, CONTRACT)
        if not norm_ok:
            return (False, "候选版无法归一进契约：" + "; ".join(problems))
        ratio = shadow_compare(req_ids, self.active, candidate)
        if ratio < threshold:
            return (False, "影子一致率 %.2f 低于阈值 %.2f" % (ratio, threshold))
        self.active = candidate
        self.pinned = candidate
        self._write()
        return (True, "影子一致率 %.2f 达标" % ratio)


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "version.json"
        req_ids = ["req-%03d" % i for i in range(40)]
        lock = VersionLock(path, active="v1")

        v1_sample = tool_response("v1", req_ids[0])
        v2_sample = tool_response("v2", req_ids[0])
        v2_adapted = adapt(v2_sample)

        checks = []
        ok1, _ = check_contract(v1_sample, CONTRACT)
        checks.append(("旧版返回满足契约", ok1))

        ok2, problems2 = check_contract(v2_sample, CONTRACT)
        checks.append(("漂移后的原始返回被契约抓到", not ok2))
        checks.append(("漂移问题至少两处", len(problems2) >= 2))

        ok3, _ = check_contract(v2_adapted, CONTRACT)
        checks.append(("适配层把新结构归一回契约", ok3))
        checks.append(("适配后分数恢复为数值", isinstance(v2_adapted["score"], float)))
        checks.append(("适配后来源字段归位", "sources" in v2_adapted))

        ratio = shadow_compare(req_ids, "v1", "v2")
        checks.append(("影子对比一致率为满分", ratio == 1.0))

        # 不经过适配、直接把漂移结构当新版升级：契约校验应挡下
        raw_ok, _ = check_contract(tool_response("v2", req_ids[0]), CONTRACT)
        checks.append(("直接升级会被契约挡下", not raw_ok))

        upgraded, _ = lock.try_upgrade("v2", req_ids, threshold=0.95)
        checks.append(("影子达标后允许升级", upgraded))
        checks.append(("升级后生效版本为 v2", lock.active == "v2"))
        checks.append(("锁定版本同步更新", lock.pinned == "v2"))
        snap = json.loads(path.read_text(encoding="utf-8"))
        checks.append(("生效版本写进可查快照", snap["active"] == "v2"))

        # 把阈值抬到不可能达到，验证会被拒绝且版本停在原地
        lock2 = VersionLock(Path(d) / "lock2.json", active="v1")
        blocked, _ = lock2.try_upgrade("v2", req_ids, threshold=1.01)
        checks.append(("一致率不达标时拒绝升级", not blocked))
        checks.append(("被拒后仍停在锁定版本", lock2.active == "v1"))

        # 确定性：同一请求两次返回完全一致
        checks.append(("同一请求返回确定",
                       tool_response("v2", req_ids[7]) == tool_response("v2", req_ids[7])))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `CONTRACT` 用「字段名 → 期望类型」的字典写死约定：答案必须是字符串、分数必须是浮点数、来源必须是列表。`tool_response` 是本地桩函数（桩函数，指用一段确定性代码顶替真实外部服务的假实现），`v1` 按契约返回，`v2` 故意把分数从数值改成字符串、把 `sources` 改名成 `citations`、还多塞一个字段，以此模拟一次悄悄漂移。两版答案都由请求编号算出来，完全确定、可手算。
2. `check_contract` 是全流程的关口：逐字段查「在不在、类型对不对」，用 `type(value) is not expected` 精确比对，避免布尔值被当成整数这类子类关系误判；它返回「是否合规」和「问题描述列表」，让漂移不只是被发现，还能说清具体坏在哪几处。
3. `adapt` 是适配层：把 `citations` 归位成 `sources`、把字符串分数转回浮点数、丢掉多余字段，把新结构折回旧契约。关键在于「差异只在这一处吸收」，业务代码不必为每个下游分支写判断。它同时兼容新旧两版（`get` 层层回落），所以旧结构喂进来也不会出错。
4. `shadow_compare` 是影子对比：拿同一批请求，让候选版照常产出、先归一、再逐条和旧版比关键字段，算出一致率。它只做观察和计数，不切换任何生效状态——这正是「先看差异再决定」和「直接跟着切」的分界。
5. `VersionLock` 把「当前生效版、锁定版」写进一份可查的 JSON 快照（JSON，JavaScript Object Notation，一种纯文本的数据表示格式）。`try_upgrade` 串起两道关：候选版得能归一进契约，且影子一致率达标，才把生效版与锁定版一起更新并写回文件；任一关不过，就原样返回、版本一动不动。注意它写的是配置记录，不是改代码，这正是「按版本号切换」的落点。
6. `main` 先断言旧版满足契约、漂移后的原始返回被抓到且至少两处问题、适配后重新合规、分数与来源都归位；再断言整批影子一致率满分，以及「不经适配直接升级」会被契约挡下。两段一正一反，分别对应「有适配层的正规升级路径」和「没有适配层时契约能拦住漂移」。
7. 随后断言达标时升级生效、生效版与锁定版都变成 `v2`、且写进了快照；又特意把阈值抬到 1.01（不可能达到），验证会被拒绝、版本停在 `v1`；最后确认同一请求两次返回完全一致。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出，打印「通过 N/N 项」把每条性质的结果逐行列出来。

有一处要如实说明：这里用确定性桩函数代替真实模型与工具、用本地文件代替配置中心、用一段手工构造的「改名加换类型」代替真实的后台更新，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是契约校验、适配归一、影子对比与按版本号切换的顺序，不是任何具体平台的实现。异常该分流成「可重试」还是「必须改契约」，可另对照 [异常分类与可重试判定](./k131-error-classify.md)。

## 七、踩坑与边界

- **只锁自己的代码、不锁外部契约**：现象是仓库一个多月没提交，功能却自己变了 → 原因是把「版本」只当成代码仓库里的数字，模型快照、工具结构、默认参数全敞开着 → 把「当前认哪一套」显式记成配置，并对返回值立契约、逐条校验，参考 [提示与策略版本化](./k113-prompt-versioning.md)。
- **把同名版本号当成永不改变**：现象是型号没换，答案风格、字段类型却慢慢不一样了 → 原因是供应方会在同名版本号下更新实际快照与默认参数 → 别信「名字没变」，用一批固定输入定期做影子对比，让差异自己浮出来，见 [回归门禁与基线](./k091-regression-gate.md)。
- **升级只挑一条用例跑通就切**：现象是单条示例过了，真实流量里长尾输入、脏数据一上来就解析失败 → 原因是单点用例覆盖不了整批分布 → 用整批固定输入算一致率并设阈值，达标才放行，别把「装得上」当成「跑得对」，思路同 [影子模式、灰度与回滚](./k112-shadow-canary.md)。
- **把适配逻辑散进业务代码**：现象是每加一个下游版本，业务里就多一堆 `if-else`，改一处漏三处 → 原因是差异没有被收在一层 → 让适配层统一把新结构归一回旧契约，业务只认契约，参考 [解耦适配层](./k077-adapter-layer.md)。
- **锁死之后没有升级与回退通道**：现象是旧版被下线时被迫跨好几个版本，改动面巨大、又退不回去 → 原因是把「锁定」理解成永久不动 → 锁定买的是选择权，须同时备好适配层、影子对比和按版本号可退的落点，让外部能探知状态可对照 [健康检查与 SLO](./k114-health-slo.md)。

还要分清两件事：契约校验盯的是「结构有没有被破坏」，影子对比盯的是「行为有没有偏移」，前者抓字段改名、类型变化这类硬漂移，后者抓答案风格、数值口径这类不报错的软漂移，谁都替代不了谁；而「拒绝升级」与「回退」也不是一回事，前者是根本没把新版本放进来，后者是已经在用新版了再拨回上一版，退得更靠后。阈值要提前写进配置并留出可查记录，别等有人盯着才发现对面变了。

## 八、三句话小结

版本漂移与升级策略，是把「外部依赖悄悄变了」从一次被动事故，改写成一件被显式记录、被契约校验、被影子对照、由自己选时机的确定动作。

关键做法是给模型与工具认准并锁定具体版本、对返回值立契约逐条校验、把结构差异收在一处适配层、整批影子对比达标才按版本号升级，并留好可退回的落点。

当系统完全离线、依赖全是自己构建且不会变化，或只是临时跑一次的脚本时，不必硬套这套关口；但只要行为由你管不到的外部对象决定，它就该被当成一件需要一直照看的事。

# 摘要式压缩：留下决策和承诺，别留寒暄

## 压完之后，它把谈好的地址忘了

长会话撑不住，你加了压缩：把前面十几轮交给一段处理，换成几句摘要接着聊。窗口确实瘦下来了，可用户问「按之前说的寄到哪」时，助手答不上来，或者干脆编一个。你把压缩结果翻出来一看，是一句「用户此前就订单问题进行了咨询，双方进行了友好沟通」——字数省了，信息全没了。另一种翻车是压出来的摘要比原文还长，等于没压。

## 先破一个误解

**不是压缩得不够狠，是压错了对象：你丢掉的是决定，留下的却是客套。**

摘要式压缩要做的事，是把早期对话从一大段原文，换成一小段仍然能支撑后续决策的事实。它和[滑动窗口裁剪](./k043-sliding-window.md)的区别在于：窗口是直接丢弃，被丢的原文不再进任何一轮输入；压缩是替换，用更短的表示接着参与后面的推理。既然是替换，就必须回答一个窗口不必回答的问题——**哪些事实绝不能丢**。

会话里的话大致分三类。第一类是决策、承诺、约束和数字，比如「决定改发顺丰」「地址改成某路八号」「金额不能改」「不能发普通快递」，它们会直接影响后面每一步；第二类是寒暄和客套，比如「你好」「谢谢」「辛苦了」，删掉对后续毫无影响；第三类是既不像决策也不像客套的中性句，比如「想问下订单的事」，信息量低但不能一概当垃圾。摘要压缩的成败，几乎全看这三类判得准不准，而不是看压到了原来的几分之一。

## 用会议纪要来理解

把早期对话想成一场开了两小时的会，原始录音就是历史原文，逐字稿厚厚一沓。你不会把逐字稿原样转给没参会的人，也不会写一句「大家聊了两小时」就算交差，你会写一份会议纪要。

对应关系很清楚：纪要里必写的是「定了哪个方案、谁承诺做什么、截止哪天、金额多少、明令不许做什么」，对应要留的决策与约束；「早上好」「先寒暄两句」「中途跑题聊了会儿天气」一概不写，对应要丢的客套；而那些听着中性、其实含着事实的句子，比如「顺便提了下上次的单号」，得先判断它到底有没有可引用的信息，再决定留不留。

要害在于：纪要不是「把录音变短」，而是「把会开完后仍然要兑现的东西单独拎出来」。写成「进行了友好沟通」之所以没用，正因为它是过程的概括，不是结果的记录。同样，摘要压缩也不是「把话缩短」，而是把决策与承诺从聊天里择出来，用紧凑格式重新摆放。

:::quote
压完之后还能不能回答「之前定的是什么」，是判断摘要合不合格的唯一标准；字数只是副产品。
:::

## 该留什么，画出来

先看摘要里应当稳定出现的四类事实，再看压缩动作本身的链路。

:::figure 摘要里该留下的四类事实
@stack
决策::选了哪个方案，为什么改
承诺与约束::答应过什么，明令禁止什么
数字与标识::金额、日期、地址、单号
未完成事项::还欠哪一步，由谁来接
:::

:::figure 一次摘要压缩的处理链路
@flow
取早期对话|逐句分类|留决策承诺|丢寒暄客套|拼成紧凑摘要
:::

:::figure 整段复述与按事实压缩的差别
@compare
整段复述::字数没降多少|客套混在中间|关键事实被稀释
按事实压缩::只剩紧凑几句|决策与承诺清晰|丢了多少可核对
:::

四类事实里最容易漏的是「未完成事项」。一句「我待会儿把单号补给你」在当时看不出分量，可它其实是一条待兑现的承诺，压掉之后后面就没人记得该追问了。另外，数字与标识这类内容必须连同它所属的对象一起留：「三百元」单独留着没用，「这单金额约好三百元、不能改」才有用。这也是为什么压缩结果更适合写成短句条列，而不是揉成一段流畅的自然语言——条列能让每条事实各自独立、可逐条核对，这一点在[压缩后信息丢失怎么验证](./k048-compression-verify.md)里会变成一组能跑的断言。

## 再往深问两层

:::ask 那如果一句话里既有寒暄又夹着决策，比如「谢谢，那就按三百元定吧」，该怎么判？
:::

顺序很重要：**先判保留，再判丢弃**。若规则先扫到「谢谢」就把它归成客套扔掉，那句最要紧的「按三百元定」也一起没了。稳妥做法是给两类词各设一份标记，只要命中任一保留标记就整句留下，只有在完全没命中保留标记、且命中了客套标记时才丢。宁可把一句带客套的话多留半句，也别把一条承诺误删。这也是下面那份实现里 `classify` 把保留判断放在最前面的原因。

:::ask 再深一层：中性句怎么办？一律丢会不会把有用信息也筛掉？
:::

会，所以「一律丢」只是可以显式配置的严格档，不是唯一答案。中性句里常藏着需要回查的线索，比如「上次那份材料我放共享目录了」，既没决策词也没客套词，却在后面可能被引用。三种处理由松到紧：全留，最稳但省不下多少；先留并标成「待确认」，让后续轮次有机会再筛；全丢，最省但要配一组必须保留的事实做回归检查，一旦少了就报警。更根本的解法是别把这类半结构化信息塞进自由文本摘要，而是写成字段明确的紧凑状态，那是[结构化状态摘要](./k046-structured-state.md)的路子；要是原文压根不该被替换、只想按需取回，则走[检索式召回压缩](./k045-retrieval-compression.md)。

## 一份能跑的压缩器

下面这份实现只用标准库和内置函数，用确定性的词表规则模拟「逐句分类」，把保留、丢弃、中性三类分开处理，复制成文件直接运行即可。它没有接任何模型，因此每次运行结果都一致，适合拿来验证分类逻辑本身。

```python
# summary.py —— 只用标准库，python summary.py

KEEP_MARKERS = ("决定", "必须", "不能", "约好", "承诺", "退回", "改为", "地址", "金额")
DROP_MARKERS = ("你好", "谢谢", "在吗", "哈哈", "好的呀", "辛苦了")


def classify(sentence):
    # 保留优先：命中任一决策/约束标记就整句留，避免误删夹在客套里的事实
    if any(m in sentence for m in KEEP_MARKERS):
        return "keep"
    # 完全没命中保留标记、又命中客套标记，才判为可丢
    if any(m in sentence for m in DROP_MARKERS):
        return "drop"
    return "neutral"


def compress(sentences, neutral_policy="drop"):
    kept, dropped = [], []
    for s in sentences:
        tag = classify(s)
        if tag == "keep" or (tag == "neutral" and neutral_policy == "keep"):
            kept.append(s)
        else:
            dropped.append(s)
    # 用紧凑分隔符拼成条列，不铺陈成自然段
    return "；".join(kept), dropped


if __name__ == '__main__':
    early = [
        "你好，在吗",
        "想问下订单的事",
        "我们决定改用顺丰发货",
        "退货地址改为朝阳区某路八号",
        "金额约好是三百元，不能改",
        "谢谢，辛苦了",
        "哈哈好的呀",
        "另外记得不能发普通快递",
    ]
    text, dropped = compress(early)
    assert "我们决定改用顺丰发货" in text                    # 决策留下
    assert "退货地址改为朝阳区某路八号" in text             # 事实与地址留下
    assert "金额约好是三百元，不能改" in text               # 数字与约束留下
    assert "不能发普通快递" in text                         # 明令禁止留下
    assert "你好，在吗" not in text and "谢谢，辛苦了" not in text  # 客套被丢
    assert "哈哈好的呀" not in text
    assert len(text) < sum(len(s) for s in early)          # 摘要短于原文
    assert len(dropped) == 4                               # 丢了几条可核对
    text_loose, _ = compress(early, neutral_policy="keep")
    assert "想问下订单的事" in text_loose                   # 宽松档留住中性句
    print("通过 9/9 项：决策承诺保留、客套过滤、摘要变短且档位可切换")
```

1. 开头两份词表把「该留」和「该丢」的信号写成数据，而不是散在判断里。真实场景里这份词表会复杂得多，但结构不变：判定依据必须摊开、可逐条检查。
2. `classify` 的顺序是整份代码的要点。它先查保留标记，命中就直接返回 `keep`；只有完全没命中保留标记、又命中客套标记时才返回 `drop`；其余归为 `neutral`。把「谢谢，那就按三百元定吧」这类混合句放进来，会因为命中「金额」或「约好」而被整句留下。
3. `compress` 逐句调用 `classify`，把留下的放进 `kept`、其余放进 `dropped`，并用 `neutral_policy` 这个参数决定中性句的去留。返回丢弃清单和摘要一样重要：它让「到底删了什么」变成可核对的数据，而不是一次静默操作。
4. 拼接用「；」而不是自然段，是为了让每条事实各自独立。摘要越像一整段流畅的话，越容易在后续被当成背景略过；条列则天然便于逐条比对。
5. 主函数构造了八句早期对话，覆盖决策、地址、金额、禁令、客套与中性句。九条断言分别验证四类事实都在、两类客套都不在、摘要确实比原文短、丢弃条数正好是四、以及切到宽松档后中性句被留住，最后打印通过项数。

想看分类边界，可以往 `early` 里加一句「谢谢，那就按三百元定吧」再跑：它会因为命中保留词而留在摘要里，客套词没能把它带走。这正是「保留优先」想守住的底线。

## 踩过的坑

- **压成过程概括**：现象是摘要写着「进行了咨询与沟通」，后面一问三不知 → 原因是概括了过程而不是记录结果 → 怎么改：只写决策、承诺、数字、待办这四类可兑现的事实。
- **先判客套再判决策**：现象是夹在客套里的承诺被一起删掉 → 原因是分类顺序反了 → 怎么改：保留判断放在最前，命中即整句留。
- **中性句一律丢**：现象是后面要引用某条线索却找不到 → 原因是把信息量低误判成没有信息 → 怎么改：设可切换档位，或先留并标「待确认」，并配保留事实回归检查。
- **只留数字不留对象**：现象是摘要里孤零零一个「三百元」 → 原因是把数值和它所属的事拆开了 → 怎么改：整句保留，让数字和主语、约束待在一起。
- **丢完不留清单**：现象是答案变差却查不出少了哪句 → 原因是压缩静默发生 → 怎么改：同时返回丢弃清单，把删除变成可核对的记录。

## 三句话

摘要式压缩是把早期对话换成一小段仍能支撑后续决策的事实，而不是把过程概括成一句空话。
关键做法是保留优先地逐句分类、只留决策承诺数字与待办，并同时输出丢弃清单供核对。
当早期内容后面随时要按原文逐字引用时，别压成摘要，改用外置留存按需取回更稳。

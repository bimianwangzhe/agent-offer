# 循环状态该存什么

## 场景提问

你照着教程写了一个能自己调工具的小程序，让它「把几份账单整理出总额」。前几轮挺顺：读文件、算金额、往下列步骤。可跑到第七八轮它开始犯迷糊——把刚才读过的文件又读一遍，把上一轮自己临时编的一个数字当成已经确认的事实，你问它「一开始到底要干嘛」，它答得含含糊糊，还有几回干脆卡在同一个动作里反复打转出不来。你回头翻代码，发现每轮之间的衔接就是一个越堆越长的列表，里面塞满了工具返回的整段原文、报错时的堆栈、你顺手加的调试打印。你隐约觉得是「状态没管好」，可到底该往这个列表里放什么、坚决不该放什么，一句都答不上来。

## 破误解

**不是模型记性变差了，是你把「状态」和「历史记录」揉成了一坨，让下一轮决策既要从里面翻答案、又要被里面的噪声牵着走。**

先把「状态」这个词钉死。这里的循环指 Agent 反复执行的「决策—行动—观察」闭环（关于这个闭环本身的拆解，见 [决策—行动—观察闭环](./k023-decision-loop.md)）：每一轮模型先看当前情况决定做什么，做完拿到一个观察结果，再据此决定下一轮。所谓状态，就是「下一轮要做出正确决策，所必须知道的最小一组事实」。这句话里有四个词都得较真：「下一轮」说明它服务于紧接的那次决策，不是服务于将来复盘；「决策」说明它的价值在于能改变接下来要做的动作；「最小」说明多存一条无关信息都是负担；「必须」说明少了它决策就会出错或者变得含糊。

而历史记录（轨迹、日志）回答的是另一个问题:「从头到尾发生过什么」。它的读者是人、是排查问题的工程师、是给整条过程打分的评测脚本，唯独不该是决策那一刻的模型。把两种东西塞进同一个列表，代价是双向的：一方面，越堆越长的原文会把真正要紧的几条事实淹没，模型在长上下文里对中间位置的注意力本来就弱，塞得越多越容易「看得见却用不上」（这层机制在 [结构化状态摘要](./k046-structured-state.md) 里还会展开）；另一方面，历史里那些报错、调试打印、临时猜测会伪装成事实混进来，模型分不清哪句是观测、哪句是自己的随口一说，于是把临时数字当结论、把重复动作当新任务。

那到底该留哪几条？有一个很实用、能当场自问的判据：把某条信息从状态里删掉，下一轮的决策会不会因此改变？会变，就必须存；不会变，就该外置到轨迹或文件里去，等真要用时按标识取回。顺着这个判据往下捋，状态通常会自然分成几类：不能改的目标与约束（比如「不得外发数据」这类红线，绝不因为交班就变）、随观察推进的工作记忆（待办步骤、已确认的事实、已经执行过的动作清单）、控制循环本身的变量（第几轮、还剩多少预算、累计失败几次、该不该停），以及指向外部大块内容的引用（某个结果的编号，而不是结果本身）。这里还有一层容易被跳过的要求：状态得能序列化成纯文本、能从纯文本恢复，因为它常常要跨一次进程重启、跨一次中断续跑继续存在；一条只能活在内存里、或者存成了某个打开的文件句柄、某个数据库连接的状态，等于没有状态。想清楚「哪些事实跨轮仍然成立」和「哪些只是一去不返的过程」，也可以对照 [记忆不是日志](./k065-memory-vs-log.md) 里对这两类信息的划分。

## 生活类比

把它想成医院病房的值班护士交接班。交班时，下班的人不会把一整天里跟病人、家属、医生说的每一句话都复述一遍，而是填一张交班本：病人现在各项指标是多少、这一班已经给过哪些药、下一班必须复查什么、还剩几支药可以用、有没有什么特别要注意的过敏史。上班的人扫一眼这张纸，就知道接下来该做什么。

对应关系相当整齐。那张交班本就是状态，它的全部意义在于让下一班立刻能做对动作。病房里的全天监控录像和厚厚一摞护理记录，就是轨迹和日志，出了纠纷才调出来逐帧看，平时不摆在手边。医生开好的医嘱单是不可变的目标与约束：交班只换执行的人，不换医嘱内容，谁都不能顺手把「每次 5 毫克」改成「每次 50 毫克」。「本班已给过某某药、几点给的」是已执行动作清单，它最现实的作用是防止下一班重复给药——这正对应程序里防止重复扣款、重复发信的去重依据。「下一班要复查血糖」是待办计划，「本班还剩三小时、还剩两支药」是轮次与预算，「病人当前血压 120/80」才是已确认事实。

这个比喻还点破了两件常被忽略的事。第一，交班本是有固定栏目的：谁乱加一栏「今天心情如何」，真正的当班人反而要在无关内容里翻找。状态也该有固定字段，而不是一个什么都能往里丢的自由文本。第二，交班本必须写得让接班的人看懂、且能被存档复查；一张只有交班人自己才认得的潦草便签，跟写进内存里、进程一退就没了的状态一样，都算不上合格。真要追溯「为什么当时那么决定」，靠的是那摞完整记录，不是这张精简的纸——这也是为什么 [结构化日志](./k095-structured-log.md) 和状态该分开存，各管一件事。

## 自绘示意图

:::figure 一轮循环里状态怎么流动
@cycle
读取当前状态|生成本轮动作|执行并观察|按观察更新状态|写回供下一轮读取
:::

这五个格子说的是同一份状态在一轮里的两次露面：轮首要「读」，轮末要「写」。最容易出事的是「按观察更新状态」这一格——它应当是把本轮的观察按固定字段合并进去，而不是把整段观察原文追加到列表尾巴上。只要这一步变成「追加」，循环转上几圈，状态就会退化成一坨流水账，前面讲的所有毛病会一起回来。

:::figure 状态该分成的几层
@stack
锚点层::目标与红线约束，只读，任何一轮都不许改写
工作层::待办步骤、已确认事实、已执行动作清单，随观察推进
控制层::轮次、剩余预算、累计失败数、终止标志
外置层::大段原文与完整轨迹落盘，状态里只留取回用的编号
:::

四层里最常被漏掉的是「控制层」。很多人只在模型觉得「做完了」时才停，可一旦模型判断失误，循环就没有第二个刹车了。把轮次、预算、失败数放进状态，[四个终止条件](./k028-stop-conditions.md) 才有可判定的依据，预算该怎么设、几道闸一起守住，可对照 [四重预算](./k103-four-budgets.md)。「锚点层只读」也不是一句口号：它是防止长循环里目标被悄悄替换的唯一硬保障。

:::figure 两种存法的差别
@compare
历史全量当状态::越跑越长|噪声淹没要点|不可恢复且难复盘
只存最小充分集::体量稳定|决策只看到该看的|可序列化可续跑
:::

左边是「反正都记着，用得上就用」的朴素想法，顺的时候最省事；右边是先把状态当成一份要设计的数据结构。二者的差距不在存得多不多，而在「下一轮能不能靠它稳定做对动作」。真需要回头看全过程时，右边那套反而更清楚——因为完整轨迹被规规矩矩留在了外置层，没有被精简状态搅乱。

## 层层追问

:::ask 那如果把所有信息都外置、状态里只留一句「目标」，岂不是最干净？
:::

不行，而且这个念头很值得拆开看，因为「最小」最容易被误解成「最少」。最小指的是「刚好够下一轮做对决策」，不是「越少越好」。缺了哪一样，会缺出很具体的毛病：没有「已执行动作清单」，同一笔扣款、同一封通知会在重试或恢复时被再做一遍，这类去重要靠 [幂等落盘](./k107-idempotent-persist.md) 那套稳定标识；没有「已确认事实」，程序会把上一轮刚查过的东西再查一次，白烧预算还把轨迹拉长；没有「待办步骤」，模型每轮都得重新猜「下一步干嘛」，最容易原地打转；没有「预算与轮次」，判断失误时没有任何东西能强制它停。反过来，把「工具返回的整段原文」「报错堆栈」「我自己的想法草稿」外置掉，决策一点不会变差，因为下一轮真正需要的是原文里提炼出的那一两条事实，外加一个能按编号取回原文的引用。所以判据始终是那条：删掉它，下一轮决策变不变，而不是「它看起来重不重要」。至于「什么时候才值得把一条事实写进长期记忆」，是另一个尺度的问题，[什么时候该记](./k070-write-decision.md) 里单独讲。

:::ask 那这份状态该由谁来写？让模型每轮输出一份完整状态，不是更省事吗？
:::

这是第二层、也是更要紧的一问。看着省事，其实埋了三个雷。其一，模型输出的状态会「漂」：这一轮把目标写成「整理账单」，下一轮可能写成「整理并记录账单」，再几轮就变成了别的意思，锚点层一旦允许被重写，长任务几乎必然跑偏。其二，它会漏字段、改类型，明明说好是列表却给了个字符串，而状态是要被代码读、被断言校验、被序列化落盘的，一个字段不合规整轮就废了。其三，模型会把「它以为发生了什么」当成「确实发生了什么」写进去，可真正的观测结果只有执行层拿得到。更稳的分工是：模型只产出本轮的动作，状态由代码按结构化观察机械地合并——目标与约束设为只读字段，工作层按固定槽位写入，同一份观察重复到达时靠去重集合保证只算一次。这种「分槽写入、按规则合并」的做法，在 [分槽写入与合并语义](./k144-reducer-slot.md) 和 [状态机与图编排](./k076-state-machine.md) 里有更完整的讲法。还有个附带好处：状态由代码写、轨迹由代码记，[检查点与轨迹回放](./k030-checkpoint-replay.md) 才能做到「从某一步接着跑」和「照着记录重看一遍」两件事都可靠；而当某一轮执行失败，需要把失败整理成能让下一轮改动作的信息，则交给 [错误回传](./k029-error-feedback.md)。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「状态」做成一份字段固定、可序列化、可恢复、带去重与终止判定的数据结构，并用本地构造的观察数据演示一轮轮怎么推进。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络；结尾用一组断言逐条验证性质。

```python
import json
from dataclasses import dataclass, field, asdict

MAX_FACT_LEN = 40  # 超过这个长度的结果不进状态，只该外置留引用


@dataclass
class LoopState:
    goal: str                                   # 锚点层：只读目标
    constraints: list = field(default_factory=list)   # 锚点层：红线约束
    plan: list = field(default_factory=list)          # 工作层：待办步骤
    done: list = field(default_factory=list)          # 工作层：已执行动作
    facts: dict = field(default_factory=dict)         # 工作层：已确认事实
    applied: list = field(default_factory=list)       # 工作层：已处理动作，用于去重
    step: int = 0                                    # 控制层：轮次
    budget: int = 6                                  # 控制层：剩余预算
    status: str = "running"                          # 控制层：running/done/abort

    def snapshot(self):
        """把状态序列化成纯文本，便于落盘、跨进程恢复。"""
        return json.dumps(asdict(self), ensure_ascii=False, sort_keys=True)

    @classmethod
    def restore(cls, text):
        """从纯文本把状态完整还原回来。"""
        return cls(**json.loads(text))

    def apply(self, action, observation):
        """把一轮观察按固定槽位并入状态；重复到达的动作只算一次。"""
        if action in self.applied:
            return False
        self.applied.append(action)
        self.step += 1
        self.budget -= 1
        if action not in self.done:
            self.done.append(action)
        if action in self.plan:
            self.plan.remove(action)
        for k, v in observation.items():
            if len(str(v)) <= MAX_FACT_LEN:
                self.facts[k] = v
        return True

    def should_stop(self):
        """按计划是否清空、预算是否耗尽给出终止判定。"""
        if not self.plan:
            self.status = "done"
        elif self.budget <= 0:
            self.status = "abort"
        return self.status != "running"


def main():
    s = LoopState(
        goal="整理季度账单并给出总额",
        constraints=["不得外发数据", "金额保留两位小数"],
        plan=["读取账单", "校验金额", "汇总"],
    )
    checks = []
    s.apply("读取账单", {"账单编号": "bill-001", "原文": "x" * 200})
    checks.append(("目标未被改写", s.goal == "整理季度账单并给出总额"))
    checks.append(("大结果未进状态", "原文" not in s.facts))
    checks.append(("短事实已入状态", "账单编号" in s.facts))

    restored = LoopState.restore(s.snapshot())
    checks.append(("快照可完整恢复", restored.snapshot() == s.snapshot()))

    before = s.step
    s.apply("读取账单", {"账单编号": "bill-001"})
    checks.append(("重复动作不重复计数", s.step == before))

    restored.apply("校验金额", {"是否通过": "是"})
    restored.apply("汇总", {"总额": "1234.56"})
    checks.append(("计划清空即完成", restored.should_stop() and restored.status == "done"))

    t = LoopState(goal="探测", plan=["a%d" % i for i in range(9)], budget=3)
    for i in range(9):
        if t.should_stop():
            break
        t.apply("a%d" % i, {})
    checks.append(("预算耗尽即中止", t.should_stop() and t.status == "abort"))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks)


if __name__ == "__main__":
    main()
```

1. `import json` 引入标准库里处理 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）的模块，`dataclasses` 用来声明字段固定的结构；二者都在 Python 自带范围内，不需要额外安装。`MAX_FACT_LEN` 是一个门槛常量：超过它长度的结果不进状态，这一条正是「大块原文外置、状态里只留引用」的落地。
2. `LoopState` 用 `@dataclass` 把状态声明成一组固定字段，并按前面的分层加注释：`goal` 与 `constraints` 是只读锚点，`plan`/`done`/`facts`/`applied` 是工作层，`step`/`budget`/`status` 是控制层。`default_factory=list` 保证每个实例的空列表互不共享，避免几个状态偷偷串数据。
3. `snapshot` 用 `asdict` 把结构转成字典再写成 JSON 文本，`sort_keys=True` 让字段顺序稳定、便于比对与存档；`restore` 是它的逆操作，用 `cls(**json.loads(text))` 把文本还原成一个全新的实例。这一对方法保证状态能跨一次中断、跨一次重启继续存在，而不是只活在内存里。
4. `apply` 是「按观察更新状态」那一格的具体实现。开头先查 `applied`：这个动作处理过就直接返回 `False`，于是同一份观察重复到达时，轮次、预算、已完成清单都不会被重复计入——这是防止恢复或重试时把一件事算两遍的关键。
5. `apply` 后半段把观察里的短事实逐条写进 `facts`，把已完成动作补进 `done`、从 `plan` 里移除；`len(str(v)) <= MAX_FACT_LEN` 这道判断让整段原文被挡在状态之外。注意目标字段 `goal` 从头到尾没有任何写入路径，锚点只读是靠「不提供改它的代码」实现的，不靠一句约定。
6. `should_stop` 把终止判据收敛成两个可判定的条件：待办清空即 `done`，预算耗尽即 `abort`。它读的都是控制层字段，因此哪怕模型自己觉得「还没做完」，循环也有独立刹车。
7. `main` 依次验证：目标不被改写、大结果被挡在状态外、短事实确实入状态、快照往返后完全相等、重复动作不重复计数、计划清空后判定完成、预算先于计划耗尽时判定中止。最后 `print("通过 %d/%d 项" % ...)` 汇总、`assert` 保证任何一条性质被破坏都会以非零状态退出。`t` 那段构造了九个待办却只给三次预算，专门演示「不是做完了才停，预算也能让它停」。

有一处要如实说明：这里用本地构造的字符串和字典代替了真实工具返回，用一份内存结构代替了真正的落盘存储，为的是让整条「读状态—动作—观察—按槽位合并—判定终止」不依赖联网、账号或第三方包就能独立跑通并手算验证。它演示的是状态该分几层、谁该来写、怎么去重与怎么停，不是任何具体框架里的状态实现。

## 踩坑与边界

- **把整段工具结果塞进状态**：现象是循环跑十几轮后开始丢三落四、把无关内容当事实 → 原因是大段原文既挤占位置又混入噪声，状态退化成流水账 → 只把提炼出的事实和一个取回编号写进状态，原文按编号外置，用长度门槛把长内容挡在外面。
- **让模型每轮重写整份状态**：现象是跑着跑着目标变了味、字段偶尔缺一个或类型不对 → 原因是锚点被允许改写、且「以为发生」被当成「确实发生」写进去 → 模型只产动作，状态由代码按结构化观察合并，目标设为只读字段，字段类型由代码校验。
- **状态只能活在内存里**：现象是进程一崩、或想从中间接着跑，之前几轮全丢，只能从头再来 → 原因是状态里存了打开的文件句柄、集合或某个运行时对象，没法序列化 → 状态字段只用能写成纯文本的基本类型，配一对 `snapshot`/`restore`，并验证往返后完全相等，思路同 [检查点与轨迹回放](./k030-checkpoint-replay.md)。
- **重复观察重复计数**：现象是恢复或重试之后，同一笔动作被算了两轮，预算白白少一截、甚至重复产生副作用 → 原因是没有记录「哪些动作已经处理过」 → 状态里留一个已处理标识清单，合并前先查，命中就跳过，稳定标识的做法见 [幂等落盘](./k107-idempotent-persist.md)。
- **状态与轨迹不分家**：现象是想排查「当初为什么这么决定」时翻不出来，或者一精简状态就把复盘要用的记录也删了 → 原因是两类信息共用一个容器、职责混淆 → 精简状态只服务下一轮决策，完整轨迹单独留，二者用同一个轮次或动作标识对得上，参考 [结构化日志](./k095-structured-log.md)。

还要分清两条边界。「状态最小」是相对「下一轮决策」而言的，同一份信息在这个任务里是可省的噪声、换个任务可能就是必须存的事实，别把某篇里列的那几个字段当成放之四海的固定表。另一条是：这里讲的是一轮一轮之间怎么衔接，至于整段过程该如何被打分、哪一步开始跑偏，属于轨迹评测的范畴，可对照 [结果评测与轨迹评测](./k089-trajectory-eval.md)；而动作本身合不合法、越没越权，是执行层要独立校验的事，不能指望状态里记一笔就算数。

## 三句话小结

循环状态是「下一轮要做出正确决策所必须知道的最小一组事实」，它服务紧接的那次动作，不服务事后复盘，完整历史另存为轨迹与日志。

关键做法是把它做成字段固定、目标只读、按槽位由代码合并、带去重清单与控制层的数据结构，并配好序列化与恢复，让轮次、预算、失败数都能当独立刹车。

当程序根本不循环、一次调用就出结果时，不必硬设计这套状态；但只要一轮要依赖上一轮的观察、或存在中断续跑与重试，状态就值得单独立一份，而不是继续往那个越堆越长的列表里追加。

# 上下文膨胀与中间遗失

## 场景提问

你怕 Agent「忘了前面说过的话」，于是把每一轮的工具结果、检索片段、反思、报错回传，全都原样塞回上下文里，心想塞得越全它越不容易漏。结果上下文一轮比一轮长，账单肉眼可见地涨，回答却越来越迟钝：早先定好的硬约束它像没看见，反复问已经答过的问题，还偶尔把两轮之前的数据张冠李戴。你特意把那条「不得编造工单编号」放在上下文靠中的位置，翻日志确认它确实在里面，可模型就是表现得好像从没读过。明明内容一条没少，怎么反而更不准了？

## 破误解

**不是模型记性变差，是你把「塞得全」当成了「看得见」，而长上下文里位置本身就会让夹在中间的内容被忽略。**

这里其实藏着两件不同的事，很多人把它们混成一句「上下文太长效果不好」，于是药也开错了。第一件叫膨胀（bloat）：每轮把工具结果、检索片段、反思、错误回传无差别追加，占用随轮次一路上涨。它是**量**的问题——单价变贵、注意力被摊薄到更多条目上、留给真正当前问题的份额反而变小，这部分和 [上下文预算表](./k041-context-budget.md) 里「把每一轮输入当资源管」直接相关。第二件叫中间遗失（lost in the middle）：一段很长的上下文里，靠前和靠后的内容更容易被顾及，夹在正中间的那段容易被忽略。它是**位置**的问题，跟总量够不够无关——就算窗口还有富余，把关键约束放在中段，也可能等于没放。

把两者分开，对策才立得住。膨胀靠「少塞」治：给单轮增量设份额、把可压的历史压短、把暂时用不上的原文外置按需取回，[滑动窗口裁剪](./k043-sliding-window.md) 和 [Push 与 Pull 按需拉取](./k140-push-pull.md) 都是这条路上的手段；中间遗失靠「摆位」治：把不能丢的约束与目标放在每轮固定的最前面、并在末尾做一句简短重述，按相关性而不是单纯按时间顺序排布检索片段，必要时周期性重述目标，这在 [目标漂移与周期性重述](./k135-goal-drift.md) 里有展开。少塞解决不了摆位，摆位也解决不了越滚越大——指望「压一压」顺手把中间遗失治好，是最常见的错位。

还有一层要先说清：本文后面会用一个确定性函数来演示「首尾权重高、中间权重低」，那是**为了把道理讲直观而构造的教学示意，不代表任何真实模型的测量结果**，也不含任何实测数字。真实系统里位置带来的影响受任务、内容、排布共同作用，没法用一个固定公式概括；但「别把关键项埋在长上下文正中间」这条工程经验，是能靠排布直接落地的，跟那个公式准不准无关。

## 生活类比

把它想成两件叠在一起的事：一个越塞越满的书包，和一叠摊在桌上的文件。

先说书包。每天早上你都把当天新收到的资料整叠塞进去，从不清理，几天之后书包鼓得拉不上拉链。要找一张上周的收据，得把里面所有东西倒出来翻一遍，翻得越久越容易拿错——书包越满，找东西越慢、越容易出错。这就是膨胀：每一轮追加都不痛不痒，累加起来却让「翻找」这件事本身变贵，注意力被摊到一大堆无关条目上。

再说那叠文件。你把十几页纸按顺序摊在桌上，最上面那一页和最下面那一页，眼睛一抬一低就能看到；偏偏夹在正中间那几页，翻的时候最容易被一带而过。你把「不得编造工单编号」这张便利贴夹在中间，它确实在这叠纸里，可你每次扫视都跳过了它——这就是中间遗失：内容在不在是一回事，被不被顾及是另一回事。

对应关系很具体：每天整叠塞进书包，就是四类增量无差别追加；倒出来翻找变慢，就是注意力被摊薄、单轮成本上涨；摊在桌上被跳过的一叠纸中间，就是长上下文的正中段；最上面和最下面那两页，就是每轮固定的常驻前缀与末尾重述；把不常用的整叠资料放回书架、要用时按编号抽一本，就是历史外置按需取回。这个比喻还点出两处细节：第一，把重要那页同时放一份在最上面、一份在最下面，比只放中间稳得多，对应「开头常驻 + 末尾重述」的双保险；第二，书架不是把资料扔了，只是不摊在桌上占地方，对应外置之后仍可按标识取回，而不是真删。

## 自绘示意图

:::figure 两类问题各自的成因与对策
@flow
每轮无差别追加|占用线性上涨|注意力被摊薄|中段被忽略|少塞加摆位
:::

五格里最容易看错的是「注意力被摊薄」和「中段被忽略」挨在一起却不是一回事：前者是总量太大导致每份分到的关注变少，后者是位置靠中导致被跳过。最后一格把两类对策并列写出来，是想强调它们得一起做——只做「少塞」，摆位不对照样漏；只做「摆位」，总量照样滚上去。

:::figure 膨胀的四个来源
@stack
工具结果::一次调用就几百上千字，最常超份额
检索片段::每轮拉回的原文，容易重复叠加
反思文字::模型自我复述，越写越长却未必有用
错误回传::报错与重试轨迹，留全文性价比低
:::

四行对应的都是「一轮里新塞进来的东西」，不是「已有历史」。治膨胀第一刀就该砍在单轮增量上：给这四类各设份额、超限先裁剪或转摘要，而不是等总量涨上去再一次性大压。把「报错全文」留成一行结论加一个可回溯标识，往往比留整段堆栈划算得多。

:::figure 两种装法的差别
@compare
全量堆历史::占用越滚越大|关键项埋在中段|找东西越来越慢
预算裁剪加头尾重述::占用封顶可控|约束每轮都在首尾|旧文按需取回
:::

左边顺手，代价是量、位置、成本三样一起失控；右边多了预算表和一点摆位规矩，换来的是「装得下、看得见、查得回」。二者差距不在内容多少，全在有没有把上下文当成一份要分配的资源。

## 层层追问

:::ask 那把上下文窗口开到最大，是不是就既装得下、又不会漏了？
:::

恰好相反，而且这正是「越大越好」最贵的误会。窗口开大只解决「装不装得下」，它同时抬高三样东西：请求变长，单次成本随之上涨；条目变多，注意力被摊得更薄；中段变得更长，中间遗失反而更明显。中间遗失是**位置**问题，不是**容量**问题——把关键项埋在一万字的正中间，并不会因为窗口还有富余就被看见。更现实的是，窗口再大也有上限，[max_tokens 与停止条件](./k127-max-tokens.md) 和 [上下文窗口](./k003-context-window.md) 管的就是这条硬边界，靠加容量永远追不上无差别追加的速度。

再往下一层：既然越大越差，那直接砍到很短行不行？也不行。砍太狠会把「上一轮为什么这么决策」「那个编号是哪来的」这类必要依据一起丢掉，模型就开始凭空补。所以答案不是一味求大或一味求短，而是**分配**：把有限的容量切成几份——常驻约束与目标写死在最前、近期轨迹留最近几轮、大块原文外置按需取回、再留一份余量给下一轮增量，这正是 [四层上下文结构](./k042-context-layers.md) 和 [上下文预算表](./k041-context-budget.md) 的思路。演示代码里那张四项预算表，加总正好等于容量、且预留份额大于单轮增量，讲的就是「够用」比「够大」更重要。

:::ask 那既然中间容易丢，把重要的全搬到末尾，不就都看得见了？
:::

这一问比上一问更细，答案是：短期有效，长期会出新问题。末尾确实是高权重位置，但「末尾」是**每轮都在变**的——这一轮你刚把约束放到最后，下一轮新消息、工具结果、检索片段一追加，它就被顶到中间去了。想靠「每次都放末尾」维持，就得每轮重写一遍上下文，既费事又容易把别的内容挤掉。更要命的是，值得放末尾的东西一多，末尾自己也会变成长长的一段，于是「末尾里夹在中间的那几条」又开始被忽略，等于把问题复制了一遍，只是换了个位置。

所以稳的做法是两处固定、一处动态。最前面留一份**常驻槽位**：系统约束、当前目标、不可变标识每轮必带、写死不压缩，位置永远在最前，这部分和 [结构化状态摘要](./k046-structured-state.md) 里约束槽的保护是同一套；末尾只放一句**简短重述**：周期性把当前目标与硬约束用一两行再说一遍，而不是把全文重述一遍，重述占的是常驻份额，不该变成新的膨胀来源，见 [目标漂移与周期性重述](./k135-goal-drift.md)；中间那些检索片段按**相关性**排布，把最贴当前问题的往两端靠，而不是按抓取时间机械堆。还有个顺带的好处：常驻前缀逐字稳定，才谈得上 [前缀缓存与即时注入](./k050-prefix-cache.md) 里那种复用计算的优化——把动态信息塞进前缀，等于同时把缓存也搅失效了。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「单轮四类增量线性累积、算出越预算轮次、外置后占用封顶、位置权重示意、关键项挪位后得分变化、四项预算分配」做成可手算的确定性演示。再次说明：`attention_weight` 是纯教学示意函数，用来把「首尾易顾及、中段易忽略」讲直观，**不是任何真实模型的测量结论**。复制即跑，不需要第三方包、账号或网络。

```python
import json


def attention_weight(index, total):
    """教学示意：位置越靠首尾权重越高、越靠中间越低，不代表真实模型测量。"""
    if total <= 1:
        return 1.0
    mid = (total - 1) / 2.0
    distance = abs(index - mid) / mid
    return round(0.4 + 0.6 * distance, 4)


def score_of(items, key_text):
    """返回关键条目在 items 里所处位置拿到的示意权重。"""
    return attention_weight(items.index(key_text), len(items))


def accumulate(base, per_round, rounds):
    """朴素做法：每轮把四类增量全追加，占用线性上涨。"""
    return [base + per_round * (i + 1) for i in range(rounds)]


def with_external(base, per_round, rounds, keep_recent):
    """每轮只留最近 keep_recent 轮增量，更早的按标识外置、用时取回。"""
    series = []
    for i in range(rounds):
        active = min(i + 1, keep_recent)
        series.append(base + per_round * active)
    return series


def over_budget(used, capacity):
    return used > capacity


def main():
    checks = []
    capacity = 1000
    base = 200
    parts = {"工具结果": 50, "检索片段": 40, "反思": 20, "错误回传": 10}
    per_round = sum(parts.values())

    # 一、朴素追加：线性上涨，并能定位第几轮越预算
    series = accumulate(base, per_round, 10)
    checks.append(("单轮增量是四类之和", per_round == 120))
    checks.append(("占用随轮次线性上涨",
                   series == [320, 440, 560, 680, 800, 920, 1040, 1160, 1280, 1400]))
    first_over = next((i + 1 for i, u in enumerate(series) if over_budget(u, capacity)), None)
    checks.append(("能定位到越预算的轮次", first_over == 7))

    # 二、历史外置：占用封顶，不再越预算，但近期轨迹仍在
    kept = with_external(base, per_round, 10, keep_recent=2)
    checks.append(("外置后占用封顶", kept[-1] == base + per_round * 2))
    checks.append(("外置后不再越预算", not any(over_budget(u, capacity) for u in kept)))
    checks.append(("外置后仍保留近期轨迹", kept[5] == base + per_round * 2))

    # 三、位置权重示意：首尾高、中间低、对称且可手算
    n = 11
    weights = [attention_weight(i, n) for i in range(n)]
    checks.append(("首尾权重高于中间", weights[0] > weights[5] and weights[-1] > weights[5]))
    checks.append(("首与尾权重相等", weights[0] == weights[-1]))
    checks.append(("权重可手算复现", weights[0] == 1.0 and abs(weights[5] - 0.4) < 1e-9))
    checks.append(("权重随位置对称", weights == weights[::-1]))

    # 四、同一条关键事实，放中段得分低，挪到末尾得分升
    base_items = ["资料%02d" % i for i in range(10)]
    key = "不得编造工单编号"
    at_middle = base_items[:5] + [key] + base_items[5:]
    at_tail = base_items + [key]
    score_middle = score_of(at_middle, key)
    score_tail = score_of(at_tail, key)
    checks.append(("关键事实放中段得分低", abs(score_middle - 0.4) < 1e-9))
    checks.append(("挪到末尾得分提升", score_tail > score_middle))

    # 五、开头常驻加末尾重述，两处都拿高权重
    headed = [key] + base_items + [key]
    w = [attention_weight(i, len(headed)) for i in range(len(headed))]
    checks.append(("开头一份末尾一份都拿高权重", w[0] >= 0.9 and w[-1] >= 0.9))

    # 六、预算分配：四项之和等于容量，预留份额大于单轮增量
    budget = {"常驻约束": 200, "近期轨迹": 240, "按需取回": 400, "预留": 160}
    checks.append(("预算四项之和等于容量", sum(budget.values()) == capacity))
    checks.append(("预留份额大于单轮增量", budget["预留"] >= per_round))

    # 七、占用曲线可落盘回看
    snapshot = json.dumps({"series": series, "kept": kept, "weights": weights},
                          ensure_ascii=False)
    checks.append(("占用曲线可落盘回看", len(json.loads(snapshot)["series"]) == 10))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `attention_weight` 用「离中点的距离」算一个 0.4 到 1.0 之间的数：正中间取 0.4，两端取 1.0。它只有一句公式、没有随机量，取值可手算、可复现。**务必把它当教具**：它只是把「首尾易顾及、中段易忽略」画成一条对称曲线，不是任何模型的注意力分布，也不该被拿去当调参依据。
2. `score_of` 找出关键条目在列表里的下标，再取该位置的示意权重；`accumulate` 与 `with_external` 分别模拟「无差别追加」和「只留近期、其余外置」两条占用曲线，都是纯算术，便于逐轮核对。
3. `main` 第一组先把四类增量加总成单轮 120，再验十条占用曲线是否严格线性、以及第几轮首次越过 1000。把「越预算轮次」算出来，是为了说明膨胀不是模糊感觉，而是可以提前定位的量的问题。
4. 第二组验外置：只保留最近两轮增量，占用稳定在 `base + 120*2`，十轮里一次都不越预算，同时第五轮仍保留着近期轨迹。外置不是删除，旧内容按标识还能取回，这点在 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 里归到「隔」与按需取回那一类操作。
5. 第三、四组是位置演示：十一个位置的权重首尾为 1.0、中间为 0.4、整体对称；同一条「不得编造工单编号」放在第五位得 0.4，挪到末尾得 1.0。它讲的不是「末尾一定安全」，而是「同一个内容，摆在哪儿待遇不同」——正因为末尾会随新消息不断后移，才需要第五组那种开头常驻加末尾重述的双份。
6. 第六组是预算表：常驻约束、近期轨迹、按需取回、预留四项加总正好等于容量，且预留 160 大于单轮增量 120，保证下一轮塞得进来。这呼应 [压缩触发阈值与时机](./k047-compression-trigger.md) 里「给下一轮留余量」的同一笔账。
7. 结尾把两条占用曲线与权重落成 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）快照，说明这些量该能回看、能比对；`assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：这里的 token 数是抽象数字，外置被简化成「只留最近两轮」，位置权重是一条构造曲线。它演示的是「量」和「位置」两条独立的成因、以及预算与摆位两类对策，不代表任何具体模型在长上下文上的表现。

## 踩坑与边界

- **把「塞得全」当成「看得见」**：现象是关键约束确实在上下文里，模型却像没读过，反复违反 → 原因是忽略了位置带来的忽略效应，且内容埋在中段 → 常驻约束放最前、末尾做一句简短重述、检索片段按相关性往两端靠。
- **只算一次调用、不算累加**：现象是单轮看着都不长，几轮之后账单和延迟一起跳 → 原因是把工具结果、检索片段、反思、错误回传分开看、没加总 → 给四类增量各设份额并加总核对，见 [按成功任务核算成本](./k096-metrics-cost.md)。
- **靠加大窗口解决一切**：现象是换了更大窗口，成本涨了、中段漏得更多 → 原因是中间遗失是位置问题，不是容量问题 → 转向预算分配与摆位，窗口只当硬上限，见 [上下文窗口](./k003-context-window.md)。
- **把重要内容全堆到末尾**：现象是刚放好，下一轮就被新消息顶到中间，末尾自己也变长了 → 原因是末尾位置每轮都在变 → 开头固定常驻槽位加末尾一句短重述，重述只占常驻份额，别重述全文。
- **外置当成删除**：现象是历史被移走后再也取不回来，模型开始凭空补细节 → 原因是只做了「移出」没做「按标识取回」 → 外置必须配可查标识与取用入口，见 [Push 与 Pull 按需拉取](./k140-push-pull.md)。

还要分清一道边界：本文讲的两件事都发生在「内容已经进上下文之后」，治法是少塞和摆位；而「哪些内容压根不该进来」属于 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 里「选」的职责，「压完有没有把精确值改坏」属于 [压缩后信息丢失怎么验证](./k048-compression-verify.md)。三者共用「上下文」这个词，但一个管排布、一个管准入、一个管改写后的核对。另一头，常驻前缀要逐字稳定才谈得上缓存复用，动态信息别往前缀里塞，这是 [前缀缓存与即时注入](./k050-prefix-cache.md) 的规矩；把预算、排布、缓存三样一起考虑，才不会「治好了这边、弄坏了那边」。

## 三句话小结

上下文膨胀与中间遗失，是两件叠在一起却不同的事：前者是每轮无差别追加让占用越滚越大、注意力被摊薄，后者是关键内容夹在长上下文正中段而被忽略。

关键做法是给单轮四类增量设份额并把历史外置按需取回、把约束与目标放在每轮固定的开头并做一句末尾短重述、按相关性排布中间内容、用一张四项预算表把容量分明白。

当任务只有一两轮、上下文短到首尾中段几乎没差别时，不必硬套这套排布；但只要一轮会长出多份工具结果、或存在丢了就出事的硬约束，就不能再靠「全塞进去」求稳。

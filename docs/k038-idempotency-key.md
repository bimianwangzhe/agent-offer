# 幂等键与副作用防重

## 场景提问

你让 Agent 帮用户下单买一张票，工具调用发出去之后网络抖了一下，迟迟没等到返回。控制循环判断「这次大概没成」，于是按重试逻辑又发了一次同样的调用。结果用户收到两条扣款短信、两张订单，跑来问为什么点了一次却付了两遍。你翻日志，看到两次调用的参数一模一样，时间只差几秒，却分不清这到底是「一次动作被发了两遍」还是「用户真的想买两张」。更麻烦的是，你想补一句「别再扣了」，系统里根本没有一样东西能代表「就是这一笔」，于是只能人工去对账、退款。明明每一次请求都合法，为什么合起来就错了？

## 破误解

**不是重试逻辑写错了，是把「一次请求」和「一次业务动作」当成了同一件事——网络层允许重发，业务层却没给「同一笔」配一个能被认出来的标识。**

先把三个词说清。幂等（idempotent，指同一个操作执行一次和执行 N 次，对外部状态的影响完全相同）是很多接口希望具备的性质：查询余额、读一篇文章，重复多少次都不会改变什么，天然幂等。副作用（side effect，指会真实改变外部世界、且不能随手撤销的动作，比如扣款、下单、发邮件、写一行数据库记录）恰恰相反，多执行一次就多一份后果，存款少一笔、收件箱多一封信。幂等键（idempotency key，由调用方生成、随请求携带、对「同一次业务动作」保持稳定不变的唯一标识）就是用来把「会闯祸的动作」也变得近似幂等的那把钥匙：服务端第一次见到某个键时真正执行并把结果记下来，之后再见到同一个键，不再执行、直接把首次结果原样返回。

很多人第一反应是「那就别重试」。可这既不现实也不对。超时、断连、下游没回应是分布式环境里的常态，[指数退避与重试预算](./k108-retry-backoff.md) 讲的就是这类「不确定要不要再发一次」的处理；[超时对账](./k039-timeout-reconcile.md) 更直白地指出，没等到回执不等于对方没做事。只要你还想让 Agent 在弱网下把事情办成，重发就不可避免。真正要补的不是「把重试关掉」，而是让「重发」这件事对业务无害：无论同一个动作被发起一次、三次、还是跨进程重启后再发一次，外部世界只被改动一次，而且每次都能拿到一致的答案。还有一层容易被忽略：这里的「一致」不只是「都返回成功」，而是要返回**首次那一次**的完整结果——订单号、回执、生成的主键，都得是同一个，否则上层拿到的记录彼此对不上，等于换了一种形式的重复。

## 生活类比

把它想成去快递点寄件。你填好一张寄件单，柜员给你一个单号，扫单号揽收、打印回执，这一个包裹才真正进了物流。假如你怕他没扫上，又把这单号报了一遍，柜员不会因此再收你一份钱、再打包一个一模一样的包裹——他查一下系统，发现这个单号已经揽收过了，就把原来那张回执再给你看一眼。可要是你重新填了一张新单号，那就是另一个包裹、另一次计费，谁也不会把它和前一个混为一谈；要是你拿着原来那个单号、却把收件地址改了，柜员一定会拦下来，因为同一个单号不能对应两份不同的东西，否则包裹到底寄去哪儿就说不清了。

对应关系很具体：那个单号就是幂等键，用来指认「就是这一笔」；单上填的收件人、重量、地址就是参数，把它们抄成一份规范摘要就是参数指纹；「扫单号、把包裹收进物流、扣一次费」是不可随意重来的副作用；那张回执就是必须连同单号一起留存的首次结果；柜员查系统发现「已揽收」再退给你原回执，就是重放（replay，指不重新执行、直接返回历史结果）。这个比喻还点出三处最要紧的细节。其一，单号得跟着「这一笔业务」走，不能每次去柜台现换一个，否则系统认不出是同一件——这正是幂等键必须由业务意图决定、而不是每次请求临时随机生成的原因。其二，柜员在包裹真正进物流之前，得先在系统里把这个单号标成「处理中」，不然同一瞬间两个窗口各扫一次，就会各收一个包裹——这对应记录里要有状态、且要先占位再执行。其三，回执必须留得住，哪怕柜员换班、系统重启，凭单号还能查到当初那张，否则「已揽收」这句话就没人能证明。

## 自绘示意图

:::figure 一次带幂等保护的调用链
@flow
生成稳定键|查账本|命中就重放|未命中先占位|执行并回写结果
:::

这五个格子是严格有序的，顺序错了就挡不住重复。「先占位」必须在「执行」之前：如果先扣款再去写账本，中间那道极短的窗口里第二个请求进来，会看到账本为空、于是也去扣一次。把「查账本」放在最前面、「命中就重放」作为一条提前返回的分支，才能让绝大多数重发连执行的边都碰不到。

:::figure 一条幂等记录该存下的四样东西
@stack
业务标识::按动作意图生成，重试时保持不变
参数指纹::参数的规范化摘要，用来发现串单
处理状态::进行中或已完成，挡住并发重复
首次结果::连同键一起存，重发时原样返回
:::

四格里最常被漏掉的是「参数指纹」和「首次结果」。只存一个键、见到就返回成功，会带来两种坏味道：同一把键被拿去配了另一份参数，系统却当成同一笔悄悄放过；以及重发时只回一个布尔值，上层拿不到订单号，只好自己再查一遍，等于把不确定性又推回给调用方。

:::figure 有幂等键与没幂等键的差别
@compare
不带键直接重试::重复扣款|重复发信|结果无从对齐
带稳定键重试::只执行一次|返回首次结果|可跨重启去重
:::

左边是「请求即动作」的朴素做法，链路短、看着省事；右边多了一次查账本和一份落盘记录，换来的是重发无害。二者的分水岭，全在「外部状态会不会被改动第二次」。

## 层层追问

:::ask 那如果每次重试都现生成一个新键，会怎么样？
:::

那防重就整个失效了，而且失效得很隐蔽。系统每次都看到一个从没见过的键，都当成「第一次」，于是老老实实执行一次副作用——三次重发就是三次扣款，和你不做任何防护一模一样，只是账本里多了三条互不相关的记录，事后更难查。所以幂等键的生成时机很讲究：它要在「决定做这个动作」的那一刻算出来，之后无论重试几次、退避多久、甚至换了一台机器重发，都复用同一把。常见的做法是把「谁、要做什么、针对哪个对象」拼成一个稳定串，比如「用户编号 + 目标订单号 + 动作名」，必要时再对参数算摘要；关键是它由业务意图决定，而不是由「这是第几次网络请求」决定。

这里要分清两个很容易混的标识。[工具调用 id](./k136-tool-call-id.md) 是协议层给「这一轮这一次调用」发的编号，一轮对话里每次发起都不同，它用来把返回和请求对上号；幂等键是业务层给「这一笔动作」起的名字，跨多轮重发保持不变。前者管「回执别接错」，后者管「动作别做重」，层次不同、谁也替代不了谁。也正因为键要跨请求存活，它就不能只放在某次调用的内存变量里，得和记录一起落盘——这正是 [幂等落盘](./k107-idempotent-persist.md) 里那套「稳标识 + 可重放」的思路；[结构化日志](./k095-structured-log.md) 则负责把「哪把键、什么状态、返回了什么」留成可查的痕迹，真出问题时才答得上「刚才那两笔到底是不是同一笔」。

:::ask 那如果同一把键被拿去配了不同参数，或者两个重发同时到达呢？
:::

这是两问，但都指向「光有一个键还不够」。先说参数。假设第一次用「pay-A-1001」这把键下了 30 元的单，第二次又用同一把键、参数却改成 999 元，如果系统只比对键就直接返回首次结果，那 999 元这笔要么被悄悄吞掉、要么挂到 30 元那张订单上，账面从此对不上。正确做法是给记录存一份参数指纹：把参数按键排序后规范化，再压成定长摘要，重发时一并比对；键相同但指纹不同，要明确拒绝并报错，而不是含糊地「当作成功」。这跟 [参数合法性](./k034-param-validity.md) 里「先校验再执行」是同一条纪律，只是这里校验的是「和第一次是否一致」。

再说并发。两个携带同一把键的请求几乎同时到达，如果都是「查完发现没有、就去执行」，就会各执行一次。所以写入账本不能是「执行完再补一条」，而要分两步：先原子地占一个「处理中」的位，谁先占到谁去执行，后来者看到「处理中」就返回「尚在进行、稍后再问」，绝不并发地再动一次副作用。等执行完成，再把这条记录从「处理中」改写成「已完成」并附上首次结果。这里「稍后再问」不是含糊其辞——调用方可以拿同一把键再查一次，等状态变成已完成就能取到结果，这正是 [工具失败分类与重试策略](./k040-tool-failure.md) 里把「暂时不确定」和「确定失败」分开处理的原因。还有一道边界要守住：账本得有个作用域，同一个键在 A 用户和 B 用户下应当互不干扰，通常把「租户或用户 + 键」一起作为内部标识，这与 [权限矩阵](./k037-permission-matrix.md) 强调的「动作要在谁的范围内成立」是一致的；否则 A 的一把键会莫名其妙挡住 B 的正常操作。至于记录保留多久，则要看业务能接受「过了多久之后再重发就算新动作」，按 [停止条件](./k028-stop-conditions.md) 的思路给个明确的窗口，别让账本无限膨胀。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一份落盘的账本模拟「带幂等保护的写动作」。它演示四件事：同一把键重发三次只执行一次、进程重启后仍能去重、换键代表另一笔动作会真正执行、同一把键配不同参数会被拒绝。结尾用一组断言逐条验证，复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import hashlib
import json
import tempfile
from pathlib import Path


def fingerprint(params):
    """把参数规范化后算指纹，用来发现同一把键配了不同参数。"""
    canonical = json.dumps(params, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()


class Ledger:
    """账本：落盘保存每把幂等键的状态与结果，重启后仍可读回。"""

    def __init__(self, path):
        self.path = Path(path)
        self.records = {}
        if self.path.exists():
            self.records = json.loads(self.path.read_text(encoding="utf-8"))

    def _flush(self):
        self.path.write_text(
            json.dumps(self.records, ensure_ascii=False, sort_keys=True),
            encoding="utf-8")

    def slot(self, scope, key):
        """内部标识带上作用域，免得一个用户的键挡住另一个用户。"""
        return scope + "|" + key

    def get(self, scope, key):
        return self.records.get(self.slot(scope, key))

    def begin(self, scope, key, fp):
        self.records[self.slot(scope, key)] = {
            "fp": fp, "state": "in_flight", "result": None}
        self._flush()

    def finish(self, scope, key, result):
        rec = self.records[self.slot(scope, key)]
        rec["state"] = "done"
        rec["result"] = result
        self._flush()


class Conflict(Exception):
    """同一把幂等键却配了不同参数时抛出。"""


def execute(ledger, scope, key, params, action):
    """带幂等保护的调用入口，返回状态与结果，命中就不执行副作用。"""
    fp = fingerprint(params)
    rec = ledger.get(scope, key)
    if rec is not None:
        if rec["fp"] != fp:
            raise Conflict("幂等键复用但参数不一致")
        if rec["state"] == "in_flight":
            return {"status": "in_flight", "result": None}
        return {"status": "replayed", "result": rec["result"]}
    ledger.begin(scope, key, fp)
    result = action(params)
    ledger.finish(scope, key, result)
    return {"status": "executed", "result": result}


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "ledger.json"
        ledger = Ledger(path)
        effects = []

        def charge(params):
            """本地桩：模拟一次真实扣款，往外部账本追加一笔副作用。"""
            effects.append((params["order"], params["amount"]))
            return {"receipt": "R-" + params["order"], "amount": params["amount"]}

        params = {"order": "A-1001", "amount": 30}
        r1 = execute(ledger, "user-7", "pay-A-1001", params, charge)
        r2 = execute(ledger, "user-7", "pay-A-1001", params, charge)
        r3 = execute(ledger, "user-7", "pay-A-1001", params, charge)

        checks = [
            ("首次真正执行", r1["status"] == "executed"),
            ("第二次重放不执行", r2["status"] == "replayed"),
            ("第三次重放不执行", r3["status"] == "replayed"),
            ("三次返回值一致", r1["result"] == r2["result"] == r3["result"]),
            ("副作用只发生一次", len(effects) == 1),
            ("副作用内容正确", effects[0] == ("A-1001", 30)),
        ]

        restarted = Ledger(path)  # 模拟进程重启：从磁盘重新读回账本
        r4 = execute(restarted, "user-7", "pay-A-1001", params, charge)
        checks.append(("重启后重发仍被去重", r4["status"] == "replayed"))
        checks.append(("重启后副作用未增加", len(effects) == 1))

        other = {"order": "A-1002", "amount": 45}
        r5 = execute(restarted, "user-7", "pay-A-1002", other, charge)
        checks.append(("换键是另一笔动作会执行", r5["status"] == "executed"))
        checks.append(("两笔动作共两次副作用", len(effects) == 2))

        try:
            execute(restarted, "user-7", "pay-A-1001",
                    {"order": "A-1001", "amount": 999}, charge)
            checks.append(("同键异参被拒绝", False))
        except Conflict:
            checks.append(("同键异参被拒绝", True))
        checks.append(("拒绝后副作用未增加", len(effects) == 2))

        r6 = execute(restarted, "user-8", "pay-A-1001", params, charge)
        checks.append(("换作用域互不干扰", r6["status"] == "executed"))

        passed = sum(1 for _, ok in checks if ok)
        for name, ok in checks:
            print(("通过 " if ok else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `fingerprint` 把参数用 `sort_keys=True` 规范化成稳定字符串，再用 SHA-256（Secure Hash Algorithm 256-bit，一种把任意长度数据压成固定长度摘要的算法）算出指纹。先排序是关键：字典的键顺序不该影响「这两份参数是否相同」的判断，否则同一份参数因为书写顺序不同就会误判成串单。
2. `Ledger` 是一份落盘账本，内部用「作用域 + 竖线 + 幂等键」拼成存储用的标识。`begin` 先把记录写成 `in_flight`（在途、处理中），`finish` 再改写成 `done` 并附上结果；每次改动都 `_flush` 写回文件，这样「换一个 `Ledger` 实例」就等于模拟了一次进程重启，账本内容仍然读得回来。
3. `execute` 是整段的要害。它先查账本：若记录已存在且指纹不同，抛 `Conflict` 拒绝；若状态是 `in_flight`，返回「处理中、稍后再问」；若状态是 `done`，直接把 `result` 包成 `replayed` 返回，**根本不调用** `action`。只有账本里查不到这条时，才 `begin` 占位、执行 `action`、`finish` 回写，返回 `executed`。「重放不执行」和「首次真执行」的分界，就落在 `action` 这一行有没有被调到。
4. `charge` 是本地桩函数，模拟一次真实扣款：往 `effects` 里追加一笔。它没有联网、没有密钥、没有外部依赖，纯粹用来让「副作用发生了几次」变得可数。账本记录的是「决策与结果」，`effects` 记录的是「外部世界被改动了几次」，二者分开，才能验证去重到底有没有生效。
5. `main` 前半段连发三次同一把键 `pay-A-1001`，断言首次 `executed`、后两次 `replayed`、三次返回值完全相同、`effects` 长度为 1。注意比对的是 `r1["result"] == r2["result"] == r3["result"]`，验的是「重发返回的是首次那份完整结果」，而不只是「都成功了」。
6. 随后用 `Ledger(path)` 重新从磁盘读回，再发一次，断言仍是 `replayed`、`effects` 没有增长——这对应「跨重启去重」。换键 `pay-A-1002` 时是全新的内部标识，断言会 `executed`、`effects` 变成 2，说明防重没有误伤另一笔正常业务。
7. 最后两处验边界：同一把 `pay-A-1001` 却把金额改成 999，应被 `Conflict` 拦下且 `effects` 不增长；同一把键换到 `user-8` 作用域，应作为独立动作执行。结尾 `assert passed == len(checks)` 保证任何一条性质被破坏都会以非零状态退出，并打印「通过 N/N 项」。

有一处要如实说明：这里用本地字典加一个 JSON（JavaScript Object Notation，一种纯文本数据格式）文件代替了真实数据库，用 `begin`/`finish` 两步代替了数据库里的原子占位，用一个追加列表的桩函数代替了真实扣款，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通、且每次结果可手工推算。它演示的是「稳定键 + 参数指纹 + 先占位 + 存首次结果」这四件事怎么配合，不是任何具体支付或存储系统的实现。真实环境里，「先占位」应当交给具备唯一约束或原子写入能力的存储来保证，不能靠两个分开的 Python 语句硬凑。

## 踩坑与边界

- **每次重试现生成新键**：现象是加了幂等机制却照样重复扣款，账本里多出几条互不相关的记录 → 原因是把键当成了「这次网络请求的编号」，而不是「这一笔业务的编号」 → 在决定做动作的那一刻按业务意图生成并复用，别在每次请求里临时取随机值，分清它与 [工具调用 id](./k136-tool-call-id.md) 的层次。
- **只存键、不存参数指纹**：现象是同一把键被拿去配了另一份参数，系统却返回首次成功，账面悄悄对不上 → 原因是把「键相同」直接等同于「动作相同」 → 记录里带上规范化参数摘要，键同指纹不同要明确报错，参考 [参数合法性](./k034-param-validity.md)。
- **执行完才写账本**：现象是平时都正常，偶尔并发重发就出现两份副作用 → 原因是「查为空」和「执行」之间留了一道谁都能挤进来的窗口 → 先原子地占「处理中」位再执行，后来者见到在途就返回稍后再问，别把顺序倒过来。
- **重发只回一个成功布尔**：现象是没有重复扣款，但上层拿不到订单号，只好再查一遍、甚至再发起一次动作 → 原因是只记了「做过」没记「做成了什么」 → 把首次完整结果连同键一起存下，重发原样返回，见 [幂等落盘](./k107-idempotent-persist.md)。
- **账本不设作用域和保留窗口**：现象是 A 用户的一把键挡住了 B 用户的正常操作，或记录无限膨胀 → 原因是键在全系统里被当成全局唯一、且永不清理 → 内部标识带上用户或租户范围，并按业务约定给记录一个明确的有效窗口，与 [权限矩阵](./k037-permission-matrix.md) 的范围约束对齐。

还要分清一对概念：幂等键管的是「动作别做重」，[指数退避与重试预算](./k108-retry-backoff.md) 管的是「还值不值得再发、隔多久发」，二者是配合关系而不是替代关系——没有预算，重发会没完没了；没有幂等键，每一次重发都可能闯一次祸。而「暂时不确定对方做没做」这件事本身，正是 [超时对账](./k039-timeout-reconcile.md) 要专门处理的：拿同一把键去查，比凭猜测重新做一遍安全得多。至于什么时候不必上这套机制：只读的查询、可以随便重算的纯函数，本身幂等，加键只是白增加一次查账本的开销；但凡一次动作会改动外部状态、且改动不容易撤销，它就值得配一把稳定键。把这件事和 [工具结果](./k035-tool-result.md) 里「返回给模型的内容要可核对」合起来看，会更清楚为什么「返回首次完整结果」比「返回成功」重要得多。

## 三句话小结

幂等键是给每个会改动外部状态的动作配的一把稳定标识，让「重发」这个躲不掉的网络行为不再等于「再做一遍」，服务端认出同一笔就直接返回首次结果。

关键做法是键按业务意图生成并跨重试复用、记录里同时存参数指纹与处理状态与首次完整结果、执行前先原子占位、账本带上作用域并落盘可查。

当工具只是只读查询、或结果可以随意重算、外部状态根本不会被改动时，不必加这层机制；但只要一次调用会扣款、下单、发信或写库且不便撤销，它就不该被当成「发一次就完事」的普通请求。

# 回归门禁与基线

## 一、场景提问

你改了几行提示词，顺手把模型换成新出的那个，挑了二十来条用例跑一遍，通过率比上一版还好看一点，于是放心发了出去。半天之后，客服转来一堆抱怨：有几类问题原本一直稳稳地答对，现在要么该拒答时硬给了一个数，要么把该带上的出处漏了，要么绕了一大圈才做完。你回头翻那次评测记录，只有孤零零一行「通过率提升」，根本答不上来「到底是哪几条从能过变成了不能过」。更别扭的是，你想退回去，却发现连上一版逐条的表现都没存下来，压根不知道该把哪条捞回来重点盯。一个分数涨了，怎么反而放进来一批新毛病？

## 二、破误解

**不是这一版整体变差了，是你只盯着一个被平均掉的总分，把「某几条原本能过、现在过不了」的退化给盖住了。**

先把三个词说清。回归（regression，白话讲：改了甲处，原本好端端的乙处反而坏了）指的不是「新版本普遍更差」，而是「具体某几条用例从通过变成了失败」。基线（baseline，把上一版被认可的那组结论冻结下来、随时能拿来逐条对照的一份参照）是拿来比的对象，它必须细到「每条用例是达成还是未达成」，而不是一个笼统的通过率。回归门禁（regression gate，在改动进入下一环节之前自动跑一遍比对、一旦发现退化就拦住不放行的那道关卡）则是把「比」这件事变成有判定、有理由、能卡住的动作，而不是有人看一眼分数拍板。三者连起来才是完整的意思：先有一份细到逐条的冻结参照，再有改动后对同一组输入重跑出的逐条结果，最后按「有没有由通过转失败」给出放行或拦下。

这里最容易被绕进去的一处是「总分」。平均分天然会把改动的正负抵消掉：修好了三条旧毛病、同时弄坏了一条要紧的，通过率照样往上走，可那条被弄坏的如果正好是「该拒答时拒答」「不越权」「给得出出处」这类不能退的性质，涨的那点分数根本补偿不了。所以回归门禁看的是「逐条的差」，不是「总的和」；它把每条用例都当成一条独立的承诺——上一版答应过能过，这一版就不许悄悄反悔。修好的那些单独记成「修复」，是好事，但不拿来抵掉退化，两笔账分开算。还有一层常被忽略：判定「达成」的标准本身也得冻住。写的是性质（有没有给出处、该拒答时拒没拒），而不是和标准答案一字不差，否则换个措辞就被误判成失败，基线也就跟着抖了，这部分见[性质断言](./k088-property-assertion.md)。再往深一层，用来比对的那组输入必须是同一组、编号固定、判定线固定，否则「这一版比那一版」根本无从谈起，用例集该怎么构造见[评测用例集怎么构造](./k086-eval-dataset.md)。

## 三、生活类比

把它想成一家老字号每批货出厂前的封样对照。老师傅手里留着一件当年被认定合格的样件，锁在柜子里，贴上封条、写明日期和批号，谁都不许随手换。每批新货下线，检验员不看「这批整体感觉不错」，而是照着一张固定的检验单，逐项拿新货和封样比：尺寸、色泽、封口、标签，一项一项打勾或打叉。只要有一项从合格变成了不合格，这批就不放行，哪怕另外几项比封样还漂亮，也不能拿去抵。真要改标准，得由老师傅当着人把旧样件归档、把新样件重新封进柜子、换一张写明日期的新封条，而不是检验员嫌这批过不了就把封样悄悄磨掉一点。

对应关系一条条对上。柜子里那件贴了封条的样件，就是基线；检验单上逐项的勾叉，就是逐条结论，而不是一个「综合评分」；固定那一套检验项目，就是编号固定、判定线固定的用例集；「有一项从合格变不合格就整批不放行」，就是回归门禁的退化零容忍；「另外几项更漂亮也不能抵」，就是修好与退化分两笔账；「旧样归档、新样重封、换封条」，就是基线的显式更新与留痕。这个比喻还点出两处最要命的细节：一是封样若只写「总体合格」而没有逐项勾叉，检验员根本说不出是哪一项坏了，正如只存一个通过率就答不上「哪几条退化了」；二是封样若能被随手改动，门禁就成了摆设——跑不过就磨一点封样，永远都能「合格」，却再没有一把稳定的尺子。

## 四、自绘示意图

:::figure 回归门禁一次比对的顺序
@flow
冻结旧基线|改动后重跑|逐条比对|退化即拦下|放行并留痕
:::

五格里最关键的是「逐条比对」这一格：它决定了后面判的是「有没有哪条坏了」，而不是「总分涨没涨」。最后一格「放行并留痕」也别省，这次跑出的逐条结果，就是下一版的基线候选，不留下来就又回到「只剩一个分数」的老路。

:::figure 一份基线里该冻住什么
@stack
用例集::固定编号的一组输入，改动前后跑同一组
逐条结论::每条是达成还是未达成，不是笼统总分
判定线::凭什么判达成，写性质不写字面
版本与来源::哪版提示模型工具、哪天冻的，可追溯
:::

四行其实在回答同一个问题：拿什么比、比到多细、凭什么判、这一参照是谁。第三行「判定线」最容易被跳过，一旦判定线随版本漂移，逐条结论就跟着抖，比对出来的「退化」可能是尺子变了而不是东西坏了，见[版本漂移与升级策略](./k084-version-drift.md)。第四行则是事后追责的依据：没有版本与来源，就答不上「这一版到底和哪一套提示、哪个模型比」。

:::figure 只看总分与逐条门禁的差别
@compare
只看平均分::一处退化被掩盖|修好抵掉变坏|说不清哪条坏了
逐条对基线::精确定位退化|关键用例零容忍|修好单独记录
:::

左边三点是连着的：只算一个总数 → 正负被平均掉 → 于是既看不出退化、也指不出是哪条。右边三点也是连着的：逐条比 → 精确定位到编号 → 于是能给要紧的用例单独设零容忍。两行的差别不在统计口径，而在「出问题那一刻能不能说清坏在哪、能不能拦得住」。

## 五、层层追问

:::ask 那把阈值调高一点，比如要求通过率不许低于某个数，是不是就能挡住退化了？
:::

挡不住，因为阈值管的是「总量」，退化是「结构」。举个能手工推算的构造场景：六条用例里，上一版过四条、差两条；新版本修好了那两条差的、却弄坏了一条原本能过的，达成条数从四条变成五条，明明涨了，却有一条由通过转失败。你把通过率下限设到多高都拦不住它，除非设到「一条都不许坏」——而那本质上已经是逐条比对了。真正管用的做法是给每条用例留一个上一版的达成标记，改动后逐条对，只要出现「上一版达成、这一版没达成」就单独列出来，再看它属不属于不能退的那一类。要紧的用例可以标成关键项，一条退化都不许有；其余的退化也要写明理由，由人决定是否接受，而不是被分数自动放过。判定线该写成性质而不是字面答案，否则措辞一变就被误判成退化，见[性质断言](./k088-property-assertion.md)；几类用例该怎么配比、才不至于全挤在最好过的那类，见[正常 / 边界 / 注入 / 回归配比](./k087-case-mix.md)。再往下追一层：那如果退化那条恰好是模型随机抖了一下呢？这时候该做的不是把阈值放宽，而是让判定本身可复现——同一条固定输入多跑几次取稳定的结论，或把随机性固定住，再谈它是不是真退化；把不确定性当噪声放过去，和把退化平均掉，是同一种将就。评测里让另一个模型来打分也有类似的抖动，见[用模型当裁判的偏差](./k090-llm-judge.md)。

:::ask 那基线冻久了会不会过期？总得跟着更新吧，怎么区分「该更新」和「偷偷放水」？
:::

会过期，而且必须能更新，否则基线自己就成了拦路石。业务会加新主题，旧卷子里没有对应章节；语料会改版，去年的标准答案今年可能变了数；线上冒出来的坏例若不收进来，同一种错误可以一直犯而分数毫无反应，见[Badcase 回收闭环与分级评测](./k093-badcase-loop.md)。但「更新基线」和「跑不过就改基线」是两件相反的事，分界线有三条。第一，更新要显式：由一个明确的动作产生新版本号，而不是某次比对顺手把旧结论覆盖掉。第二，旧参照要留档：历史里应能查到上一版的逐条结论，这样「为什么这条以前算达成」有据可查，也方便把某次改动前后并排看。第三，更新要有理由：通常是因为判定标准或用例集本身变了，而不是因为这一版恰好过不了。三条齐了，更新就是「柜子里换一件新封样、旧样归档」；缺了任何一条，就成了「检验员嫌这批不过，把封样磨掉一点」。再往下追一层：那更新之后，之前被拦下的那版还拦不拦？按新基线重新判即可，但判定记录要能回答「当时是按哪一版基线、哪套判定线判的」——所以基线、用例集、判定线都得各自带版本，这和[提示与策略版本化](./k113-prompt-versioning.md)里「每样可部署产物各自版本化」是同一套思路。还有一处边界要承认：门禁卡的是「相对上一版别退步」，它不负责证明「这一版在真实链路里就好用」，固定用例集覆盖不到的脏数据与长尾输入，得靠[离线好、线上差的成因](./k092-offline-online-gap.md)和发布后的小流量观察接着管，见[影子模式、灰度与回滚](./k112-shadow-canary.md)。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把「冻结基线 → 逐条比对 → 退化即拦 → 显式更新留档」写成一份可运行的小门禁。用例是本地构造的固定编号结论，不涉及任何真实模型调用；复制到文件直接运行即可，不需要联网、账号或第三方包，也不依赖文章前面定义过的变量。每条用例的达成与否都是可手工推算的构造取值，不代表任何真实评测结果。

```python
# -*- coding: utf-8 -*-
"""回归门禁与基线：冻结旧结论、逐条比对、退化即拦、显式更新留痕。"""
import json


class Baseline:
    """一份冻结的参照：某版在固定用例集上逐条的达成情况。"""

    def __init__(self, version, results, critical):
        self.version = version
        self.results = dict(results)          # 用例编号 -> 是否达成
        self.critical = set(critical)         # 不许退化的用例编号
        self.history = [(version, dict(results))]

    def freeze_new(self, version, results):
        """只有显式调用才产生新基线，旧参照仍留在历史里。"""
        self.version = version
        self.results = dict(results)
        self.history.append((version, dict(results)))
        return self


def snapshot(baseline):
    """把基线序列化成可存档、可逐字比对的文本。"""
    return json.dumps(
        {"version": baseline.version, "results": baseline.results},
        ensure_ascii=False, sort_keys=True)


def pass_rate(results):
    """只看总量的口径：达成条数除以总条数。"""
    vals = list(results.values())
    return sum(1 for v in vals if v) / len(vals) if vals else 0.0


def compare(baseline, current):
    """逐条比对：由达成转未达成算退化，漏跑按未达成处理。"""
    regressed = []
    fixed = []
    for cid, was in baseline.results.items():
        now = bool(current.get(cid, False))
        if was and not now:
            regressed.append(cid)
        elif (not was) and now:
            fixed.append(cid)
    return regressed, fixed


def gate(baseline, current):
    """门禁判定：只要出现一条退化就拦下，并写明理由。"""
    regressed, fixed = compare(baseline, current)
    reasons = []
    if regressed:
        reasons.append("由通过转失败 %d 条" % len(regressed))
        hit = [c for c in regressed if c in baseline.critical]
        if hit:
            reasons.append("其中关键用例 %d 条" % len(hit))
    verdict = "拦下" if regressed else "放行"
    return verdict, regressed, fixed, reasons


def main():
    checks = []

    def ok(cond, name):
        checks.append((name, bool(cond)))

    base = {
        "c01": True, "c02": True, "c03": True,
        "c04": False, "c05": False, "c06": True,
    }
    baseline = Baseline("v1", base, critical={"c01", "c03"})

    same = dict(base)
    v, reg, fix, _ = gate(baseline, same)
    ok(v == "放行" and reg == [], "与基线一致时放行")
    ok(fix == [], "没有凭空多出修复")

    sneaky = dict(base)
    sneaky["c01"] = False        # 一条关键用例由达成转为未达成
    sneaky["c04"] = True         # 修好一条旧毛病
    sneaky["c05"] = True         # 再修好一条，把总体通过率抬上去
    ok(pass_rate(sneaky) > pass_rate(base), "这版总体通过率反而更高")
    v2, reg2, fix2, why2 = gate(baseline, sneaky)
    ok(v2 == "拦下", "总体通过率变高仍被门禁拦下")
    ok(reg2 == ["c01"], "退化点被精确定位到那一条用例")
    ok("c01" in baseline.critical, "被定位的正是关键用例")
    ok(set(fix2) == {"c04", "c05"}, "修好的用例单独记为修复，不拿来抵退化")
    ok(any("关键用例" in r for r in why2), "拦下理由写明含关键用例")

    missing = {k: v for k, v in base.items() if k != "c02"}
    v3, reg3, _, _ = gate(baseline, missing)
    ok("c02" in reg3 and v3 == "拦下", "漏跑的用例被当成退化拦下")

    old_len = len(baseline.history)
    baseline.freeze_new("v2", sneaky)
    ok(baseline.version == "v2", "显式更新后版本号推进")
    ok(len(baseline.history) == old_len + 1, "旧参照仍留在历史里")
    ok(baseline.history[0][1]["c01"] is True, "历史首版记录未被就地改写")
    ok(json.loads(snapshot(baseline))["version"] == "v2", "基线可序列化存档并读回版本号")
    v4, reg4, _, _ = gate(baseline, sneaky)
    ok(v4 == "放行" and reg4 == [], "新基线之下与它一致即可放行")

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Baseline` 把三样东西收在一起：`results` 是「用例编号 → 是否达成」的逐条结论，`critical` 是不许退化的用例编号集合，`history` 是历次冻结的存档。构造函数里用 `dict(results)` 造副本，是为了让外部那份字典之后被改动时，不会连带着把已冻结的参照也改了。
2. `freeze_new` 是唯一能推进基线的入口：它更新版本号、替换逐条结论，并把旧参照以 `(版本, 结论副本)` 的形式留在 `history` 里。把「更新」收成一个显式方法，正是为了和「跑不过就悄悄改基线」划清界限。
3. `snapshot` 用 `json`（JavaScript Object Notation，一种纯文本的数据表示格式）把当前基线转成可存档、可逐字比对的文本，`sort_keys=True` 让键顺序固定，两次序列化结果能直接对照。
4. `pass_rate` 是刻意摆出来做对照的「只看总量」口径：达成条数除以总条数。它不算错，只是回答不了「哪条坏了」，后面会用它演示总分涨了却仍该拦下。
5. `compare` 是整段的关键：遍历基线里的每条用例，用 `current.get(cid, False)` 取新结果，取不到就按未达成处理——于是漏跑的用例不会被当成「没关系」，而是落在退化里。由 `True` 变 `False` 记进 `regressed`，由 `False` 变 `True` 记进 `fixed`，两笔账分开返回。
6. `gate` 把比对结果变成判定：只要 `regressed` 非空就判「拦下」，并往 `reasons` 里写清退化条数、以及其中是否含关键用例。注意它没用通过率做任何判断，退化归退化、修复归修复，互不抵消。
7. `main` 先构造六条固定编号的基线，验证「与基线一致时放行」；再构造 `sneaky`：弄坏一条关键用例、同时修好两条旧毛病，于是 `pass_rate` 确实变高，却被 `gate` 拦下、且退化被精确定位到 `c01`、修复单独记为 `c04` 与 `c05`、理由里点名含关键用例。这一组正是开头那个场景的最小复现。
8. 接着验证「漏跑 `c02` 被当成退化拦下」，再用 `freeze_new("v2", ...)` 显式更新基线，断言版本号推进、旧参照仍在历史、历史首版记录未被就地改写、序列化后能读回版本号、新基线之下与它一致即可放行。结尾用 `ok` 收集全部性质，逐条打印并输出「通过 N/N 项」，`assert`（断言，把「应该成立的性质」写成一行检查，不成立就让程序以非零状态退出）保证任一条不成立都会被看见。

有一处要如实说明：这里用六个固定编号和一组手工取定的布尔值代替真实用例与真实模型，用内存里的列表代替评测平台，纯粹是为了让「逐条比对 → 退化判定 → 显式留档」这条链不需要联网、账号或第三方包就能独立跑通，且每一步结论都能手工推算。它演示的是门禁该判什么、基线该怎么冻、更新为什么要显式，不是任何具体评测系统的实现，那些布尔取值也不对应任何真实表现。

## 七、踩坑与边界

- **只存一个通过率**：现象是分数涨了，却答不上「哪几条从能过变成了不能过」，也没法针对性修 → 原因是把逐条结论压成了一个总量 → 怎么改：基线冻到「每条达成与否」，比对逐条做，退化单列，见[评测用例集怎么构造](./k086-eval-dataset.md)。
- **用修好去抵退化**：现象是几条旧毛病修好、一条要紧的性质被弄坏，总分仍达标就放行了 → 原因是正负被平均抵消，门禁只看了总量 → 怎么改：修复与退化分两笔账，关键用例退化零容忍，其余退化写明理由由人定夺。
- **判定线随版本漂移**：现象是这一版突然冒出一批「退化」，查下来其实是判达成的标准变了 → 原因是判定线没和基线一起冻住，或写成了字面答案比对 → 怎么改：判定线写性质、随基线版本化，见[性质断言](./k088-property-assertion.md)与[提示与策略版本化](./k113-prompt-versioning.md)。
- **漏跑被当成没事**：现象是某个用例这轮没跑，门禁却放行了 → 原因是取不到结果时默认按达成或跳过处理 → 怎么改：缺失即视为未达成，落在退化里被拦下。
- **跑不过就改基线**：现象是每次改动都能「通过」，门禁形同虚设，坏例照旧复发 → 原因是把更新基线当成了躲开拦截的捷径 → 怎么改：更新收成显式动作、旧参照留档、更新要有理由，见[Badcase 回收闭环与分级评测](./k093-badcase-loop.md)。

还要说清边界。回归门禁卡的是「相对上一版别退步」，它证明不了「这一版在真实链路里就好用」：固定用例集覆盖不到的脏数据、长尾问法、并发与下游状态，得靠发布后的观察接着管，见[离线好、线上差的成因](./k092-offline-online-gap.md)与[影子模式、灰度与回滚](./k112-shadow-canary.md)。另一个常见误会是「退化一条都不许有才叫严」——真实系统里输出本就带不确定性，判定时要让同一条固定输入的结论可复现，别把随机抖动当成结构性退化，也别为了显得严而把噪声算成事故，这一点与[轨迹字段](./k094-trace-fields.md)里「每次判定要能回答当时用的是哪套输入与配置」相接。还有一层：一次性、无状态、输入被程序严格限死、也根本不需要比较版本的小工具，铺一整套冻结基线与门禁反而是负担，写清几条判定线、跑一组固定输入就够了；但要长期改动、需要反复比较版本的系统，基线就得细到逐条、版本化、可追溯。至于按成功任务核算成本那类不该被平均掩盖的指标怎么定义，可对照[按成功任务核算成本](./k096-metrics-cost.md)；把过程是否合理也算进评价，见[结果评测与轨迹评测](./k089-trajectory-eval.md)。

## 九、三句话小结

回归门禁与基线，是把上一版逐条的达成结论冻结成可对照的参照，改动后对同一组输入重跑并逐条比对，一旦出现由通过转失败就拦住不放行。

关键做法是判定线写性质并随基线版本化、修复与退化分两笔账、关键用例零容忍、漏跑按未达成处理、更新基线走显式动作且旧参照留档。

当系统一次性、无状态、输入被严格限死、也无需比较版本时，不必铺这套冻结与门禁；但只要要长期改动、需要反复确认「没有把原本能过的弄坏」，基线就得细到逐条、可追溯。

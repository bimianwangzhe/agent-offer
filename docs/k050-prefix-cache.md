# 前缀缓存与即时注入

## 场景提问

你想让 Agent 「知道现在几点、这是哪个会话」，于是顺手把当前时间和会话编号拼进了系统提示的最开头，觉得这样最省事。上线没几天你发现一件怪事：明明每一轮的系统提示、工具定义、几个示例几乎一模一样，首字延迟和账单却一点没降，换个更长的系统提示反而更慢。你怀疑缓存没生效，翻配置又看不出开关在哪。更糟的是，有人为了「让提示更准」，每轮还往开头加一句带随机编号的说明，结果连原本能省的那点也省不下来了。明明是同一套提示，怎么复用不起来？

## 破误解

**不是缓存没开，是你在每轮都改动了请求最前面那几个字，让「可复用的那一段」从根上就不存在了。**

先把机制说清。前缀缓存（prefix cache）指的是：服务端对一次请求里**从头开始、逐字节相同**的那一段，可以把已经算过的中间结果留着复用，下一轮碰到同样的开头就不必从头再算，于是省时间、也省一部分开销。这里最要命的四个字是「从头开始」——它是按前缀匹配的，不是按「内容大体相似」匹配的。只要最前面有一个字不一样，后面哪怕几千字完全相同，也接不上前面那块缓存，整段得重算。所以上下文排布有一条很硬的规矩：**稳定不变的内容放在最前面且一字不改，每轮变化的内容放到后面**。

系统提示、工具定义、少样本示例（few-shot，给模型看几个输入输出样例来定输出风格）属于前者，它们该是逐字固定的常驻前缀；当前时间、会话编号、用户这一轮的话、刚检索回来的片段、任何带随机数或动态拼装的东西，属于后者，该作为消息追加在尾部。把动态信息塞进开头这件事有个专门的说法叫即时注入，它看起来只是「加一行」，代价却是把整块前缀缓存作废。很多人以为「就改一句话，能有多大影响」，可缓存认的是整段前缀的指纹，改第一个字和改最后一个字，在它眼里一样是全新的一段。

这也解释了为什么「换个更长的系统提示」不解决问题：长而稳定，本来正是缓存最划算的情形；可只要前缀每轮都在变，越长越亏，因为每轮要重算的字符更多。真正要补的不是「再优化一下措辞」，而是把上下文按「会不会变」重新切一遍，这件事和 [四层上下文结构](./k042-context-layers.md) 里「常驻层写死不压缩」是同一条原则，只是这里多了一层收益：稳定前缀除了好管，还能被复用。至于动态信息该以什么形式放到尾部、怎么和正文定界，可对照 [分隔符与输入定界](./k133-delimiter.md)；模板本身怎么分块，见 [结构化提示词模板六模块](./k132-prompt-template.md)。

## 生活类比

把它想成印刷厂印一批通知。通知有个固定抬头：单位名、格式说明、几条不变的规则，这些刻在一块印版上，一次刻好，印几万份都不用动。真正每份不同的，只有正文里填的日期和编号，工人用可擦的章另盖上去，不碰印版。稳妥的老师傅绝不会把「今天几号」刻进印版——那就得每天重刻一整块版，昨天印过的几万份全白搭，前面那些固定内容等于每份都从零刻起。

对应关系很具体：那块固定印版，就是常驻前缀；印版上刻的抬头与规则，就是系统提示、工具定义和少样本示例；每份另盖的日期和编号，就是当前时间、会话编号、用户这一轮的输入；「另盖章而不改版」，就是把动态信息作为尾部消息注入，而不是改写前缀；「每天重刻整版」，就是每轮前缀都变、缓存整段失效。缓存服务留着的那块版也不是永久的：印版放太久会被清走或氧化，对应缓存有存活时间（TTL，Time To Live，一段缓存被保留的有效期），隔太久再来，即使是同一块版也得重刻。

这个比喻还点出两处细节。第一，判断「能不能复用」看的是印版整块是否逐字一样，不是看两份通知像不像——正好对应缓存按前缀指纹精确匹配，改一个字就全废。第二，印版越长、印的份数越多，复用越划算；只印两三个字的小戳子，省不了多少刻版功夫，管理它反而麻烦——对应短前缀收益有限，只有足够长、且反复出现的前缀才值得为它安排排布。还有一层：把日期刻进版里的人往往不是不懂印刷，只是觉得「反正只加一行」，这和工程里顺手往系统提示开头塞一句动态信息，是同一种图省事。

## 自绘示意图

:::figure 一次命中前缀缓存的请求
@flow
稳定前缀|算指纹比对|命中即复用|只算增量尾|动态放尾部
:::

五格里「算指纹比对」和「只算增量尾」最容易被忽略。命中不是自动发生的，得先把前缀算成一个指纹去比对；命中之后也**不是整次请求都不算**——尾部那些每轮不同的内容和后面的生成，照样要算，省下的只是前缀重算那一段。把「命中」理解成「整轮免费」，就会在估算成本时算错账。

:::figure 上下文按会不会变分块
@stack
常驻前缀::系统规则，逐字固定，每轮不改
工具定义::全部工具的稳定描述，不随轮次变
少样本示例::固定样例，决定输出风格
半静态清单::可能变的清单放尾部，别动前缀
动态尾部::时间、编号、用户话、检索片段
:::

五行里「半静态清单」是最容易放错位置的一类：工具清单、可用知识条目这类东西看着像「配置」，其实常常随任务变。一旦把它们挂进前缀，前缀就不再稳定；稳妥做法是前缀保留全集稳定描述，把「这一轮选中了哪几项」作为尾部参数传进去，别改前缀本身。

:::figure 两种注入位置的差别
@compare
动态信息注入头部::前缀每轮都变|整段缓存作废|越长越亏
动态信息注入尾部::前缀逐字稳定|命中可复用|只算增量尾
:::

左边只差「加一行」的手感，代价是整块前缀白算；右边多了点排布规矩，换来的是同一套提示能被反复复用。二者差距不在内容多少，全在那一行动态信息落在哪一端。

## 层层追问

:::ask 那如果工具清单本来就会变，比如按任务分层挂载，前缀不就稳不住了吗？
:::

会，而且这是把前缀缓存真正用起来后最常撞上的第二层问题。很多人一遇到「清单要动态选」，就把整份清单连同选中结果一起重拼进系统提示，前缀于是每轮不同。更稳的做法是拆成两层：前缀里放**全集的稳定描述**——每个工具叫什么、参数怎么填、返回什么，逐字固定；至于「这一轮只开放哪几个」，作为一条尾部消息或参数传进去，不改前缀一个字。这正是 [工具清单减肥与分层路由](./k036-tool-routing.md) 里「先路由、再挂载」的思路，只是这里多了一条约束：路由结果要走尾部通道。

再往下一层：把全部工具描述都摆进前缀，会不会太长、太贵？恰好相反。长而稳定的前缀是缓存最划算的情形——一次算过，后面许多轮都复用；短而每轮都变的前缀才最亏，省不下重算，还把整段缓存搅没。真正要控制的是「动态选择」别渗进前缀，而不是压缩前缀本身。若全集确实大到离谱，也该按 [上下文预算表](./k041-context-budget.md) 给常驻层定份额，把不常用的描述外置按需取回，而不是每轮重拼一份新前缀。

:::ask 那命中了缓存，是不是就一定省钱、省时间？
:::

不一定，这一问值得拆成三笔账。第一笔是**前缀够不够长、够不够重复**：只有一段足够长、且反复出现的前缀才值得为它安排排布；短短一句系统提示，省下的重算量有限，演示代码里专门对比了长前缀和两字短前缀省下的量差距。第二笔是**缓存还在不在**：服务端保留缓存有存活时间，两次请求隔太久、或中间插了别的前缀把旧缓存挤掉，就得重算，`expire` 演示的就是这件事；所以它更利好「连续多轮、同一会话」的场景，零散发一次的请求享受不到。第三笔是**省的是哪一段**：命中只省前缀那部分的重算，尾部动态内容、以及后面的生成，一次都不少，这部分和 [流式输出与首字延迟](./k009-streaming.md)、[用量统计与计费口径](./k010-usage-billing.md) 里的口径要对齐，别把「命中」当成「整轮不花钱」。

再追一层：那要不要把所有内容都塞进前缀，把前缀做得又长又稳？不行。前缀必须**真的稳定**，而系统约束、当前目标这类不可压缩项数量有限，硬塞动态内容进去只会让它每轮都变，等于自毁缓存；上下文还要受预算与摆位约束，关键项得在首尾、大块历史得外置，这些在 [上下文膨胀与中间遗失](./k049-context-bloat.md) 里讲过。换句话说，前缀缓存是「稳定前缀」带来的**额外收益**，不是让你为了它去牺牲排布的理由；先把内容按会不会变切对、按预算摆好，缓存自然就顺了。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一个极简的缓存模拟器把「稳定前缀全命中、头部注入动态信息零命中、动态信息移到尾部仍命中、改一个字指纹就变、短前缀收益小、存活时间过期后需重算」逐条演示。命中收益用「省下的前缀字符数」示意，**不是任何真实服务的计费或延迟数据**。复制即跑，不需要第三方包、账号或网络。

```python
import hashlib
import json

STABLE_PREFIX = "\n".join([
    "你是售后工单整理助手。",
    "只输出结构化结论。",
    "工具：拉取工单列表、归类高频问题。",
    "示例：输入三个月工单，输出三类问题与依据。",
])


def fingerprint(text):
    """把任意文本映射成固定长度摘要（SHA-256 前 12 位），逐字节相同才同值。"""
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]


class PrefixCache:
    """极简模拟：只对完全相同的前缀指纹命中，命中就不重算前缀。"""

    def __init__(self):
        self.seen = set()
        self.hits = 0
        self.misses = 0
        self.saved_chars = 0        # 命中省下的前缀重算字符数（示意）
        self.recomputed_chars = 0   # 未命中白算的前缀字符数（示意）

    def request(self, prefix, tail):
        fp = fingerprint(prefix)
        if fp in self.seen:
            self.hits += 1
            self.saved_chars += len(prefix)
        else:
            self.seen.add(fp)
            self.misses += 1
            self.recomputed_chars += len(prefix)
        # 动态尾巴每轮都要算，不计入前缀缓存
        return fp

    def expire(self):
        """模拟存活时间到期：记住的前缀全部作废，下次需重算。"""
        self.seen.clear()


def main():
    checks = []

    # 一、稳定前缀 + 逐轮变化的尾巴：除首次外全命中
    cache = PrefixCache()
    reqs = [{"prefix": STABLE_PREFIX, "tail": "第%d轮用户问题" % i} for i in range(8)]
    for r in reqs:
        cache.request(r["prefix"], r["tail"])
    checks.append(("稳定前缀除首次全命中", cache.hits == 7 and cache.misses == 1))
    checks.append(("前缀与动态尾巴分开存", all(r["prefix"] == STABLE_PREFIX for r in reqs)))
    tails = ["第%d轮用户问题" % i for i in range(8)]
    checks.append(("动态尾巴逐轮不同", len(set(tails)) == 8))

    # 二、把时间戳注入头部：前缀每轮都变，零命中
    cache2 = PrefixCache()
    for i in range(8):
        bad_prefix = "当前时间 12:%02d\n" % i + STABLE_PREFIX
        cache2.request(bad_prefix, "第%d轮用户问题" % i)
    checks.append(("头部注入动态信息零命中", cache2.hits == 0 and cache2.misses == 8))

    # 三、同一条动态信息移到尾部，前缀不动：照样命中
    cache3 = PrefixCache()
    for i in range(8):
        tail = "当前时间 12:%02d；第%d轮用户问题" % (i, i)
        cache3.request(STABLE_PREFIX, tail)
    checks.append(("动态信息移到尾部前缀仍全命中", cache3.hits == 7))
    checks.append(("两种排布命中数差距明显", cache3.hits - cache2.hits == 7))

    # 四、指纹精确匹配：改一个字就变，同一文本可复现
    fp1 = fingerprint(STABLE_PREFIX)
    fp2 = fingerprint(STABLE_PREFIX.replace("只输出", "请只输出"))
    checks.append(("前缀改一字指纹就变", fp1 != fp2))
    checks.append(("同一前缀指纹可复现", fingerprint(STABLE_PREFIX) == fp1))
    checks.append(("指纹长度固定便于比对", len(fp1) == 12))

    # 五、命中省下的是前缀重算量，且长前缀比短前缀划算
    checks.append(("命中省下前缀重算量", cache.saved_chars == 7 * len(STABLE_PREFIX)))
    checks.append(("未命中才重算前缀", cache.recomputed_chars == len(STABLE_PREFIX)))
    checks.append(("省下的量超过白算的量", cache.saved_chars > cache.recomputed_chars))
    short_cache = PrefixCache()
    for i in range(8):
        short_cache.request("助手", "第%d轮" % i)
    checks.append(("短前缀省下的量明显更少", short_cache.saved_chars < cache.saved_chars))

    # 六、存活时间到期后需重算；命中情况可落盘核对
    cache4 = PrefixCache()
    cache4.request(STABLE_PREFIX, "第一轮")
    cache4.request(STABLE_PREFIX, "第二轮")
    cache4.expire()
    cache4.request(STABLE_PREFIX, "第三轮")
    checks.append(("缓存过期后需重算", cache4.hits == 1 and cache4.misses == 2))
    snapshot = json.dumps({"hits": cache.hits, "misses": cache.misses,
                           "saved": cache.saved_chars}, ensure_ascii=False)
    checks.append(("命中情况可落盘核对", json.loads(snapshot)["hits"] == 7))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `STABLE_PREFIX` 把系统规则、工具描述、一个示例拼成一段逐字固定的文本，模拟常驻前缀；`fingerprint` 用 `hashlib.sha256`（一种把任意文本映射成固定长度摘要的算法）取前 12 位，保证「逐字节相同才得到同一个值」——这正是缓存按前缀精确匹配、而非按相似度匹配的简化表达。
2. `PrefixCache.request` 只做一件事：算前缀指纹，命中就累加 `hits` 与省下的字符数，未命中就记住指纹并累加 `misses` 与白算的字符数。注意它**完全不看 `tail`**——动态尾巴每轮都不同，但既不参与指纹、也不影响命中，这就是「把动态信息放尾部」在代码里的落点。
3. `expire` 清空已记住的指纹，模拟存活时间到期：同一段前缀隔太久再来也得重算。它演示的是「命中不是永久保证」，而不是任何具体服务的过期策略。
4. `main` 前两组是全文最关键的对照：同样八轮请求，稳定前缀除首次外命中七次；把 `当前时间 12:0x` 拼进头部后，八次全部未命中。第三组把**完全相同**的那条时间信息挪到尾部，前缀不动，命中数又回到七次。内容一点没少，只换了位置，结果天差地别。
5. 第四组验指纹的性质：把「只输出」改成「请只输出」，指纹立刻变；同一段文本反复算指纹恒定；长度固定便于比对。它对应的是「改一个字整段缓存作废」这条硬规矩。
6. 第五组把收益量化成示意字符数：命中省下的正好是七次前缀长度，未命中只白算一次；再用两字短前缀做同样八轮，省下的量明显更少，讲清「只有长而重复的前缀才划算」。
7. 结尾把命中、未命中、省下的量落成 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）快照，说明这些量该能回看核对；`assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：真实服务的前缀匹配单位、保留时长、计费口径都比这个模拟器复杂，这里用「字符数」代表重算量、用 `set` 代表缓存，全是为了让命中与失效可逐条手算。它演示的是排布与命中的因果关系，不是任何具体服务的实现或收益数字。

## 踩坑与边界

- **把时间、编号、会话号拼进系统提示开头**：现象是每轮提示几乎一样，首字延迟和账单却不降 → 原因是前缀从第一个字起就变了，整段缓存作废 → 动态信息一律作为尾部消息注入，前缀逐字固定，见 [系统提示该写什么](./k011-system-prompt.md)。
- **每轮重拼工具清单或示例**：现象是明明只换了选中的几个工具，缓存却全失效 → 原因是把动态选择结果写进了前缀 → 前缀放全集稳定描述，选中项走尾部参数，见 [工具清单减肥与分层路由](./k036-tool-routing.md)；示例本身怎么定，见 [少样本示例](./k012-few-shot.md)。
- **以为命中就整轮免费**：现象是按「全免」估算成本，实际账单对不上 → 原因是命中只省前缀重算，尾部与生成照算 → 按 [用量统计与计费口径](./k010-usage-billing.md) 分段核算，别把缓存收益算到生成头上。
- **为求长把动态内容塞进前缀**：现象是前缀做得很长却一轮都命中不了 → 原因是长的前提是稳定，塞了动态内容反而每轮都变 → 先按会不会变切块，再谈长度，配合 [上下文预算表](./k041-context-budget.md) 给常驻层定份额。
- **忽略存活时间与间隔**：现象是同一会话隔了很久再问，本以为能复用却重算了 → 原因是缓存保留有有效期，隔太久或被别的前缀挤掉 → 把「连续多轮」当作主要受益场景，零散发一次的请求别指望它，过期后按未命中估。

还要守住一条边界：前缀缓存是**排布正确之后附带的好处**，不是排布的目标本身。上下文首先得满足内容准入、预算分配、关键项摆位、不可压缩项保护，这些在 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 和 [上下文膨胀与中间遗失](./k049-context-bloat.md) 里各管一段；把这些都做对了，稳定前缀自然成形，缓存才谈得上命中。反过来，若为了命中而把不该常驻的内容钉在开头，既占了常驻份额、又埋下了每轮变动的隐患，等于两头都亏。另一头，命中率该和延迟、成本一起看：按 [按成功任务核算成本](./k096-metrics-cost.md) 的思路，评价的是「一个任务做成花了多少」，而不是「某次请求的缓存命中了没」。

## 三句话小结

前缀缓存与即时注入，讲的是把稳定不变的系统提示、工具定义、示例固定成逐字不变的前缀，把时间、编号、用户输入、检索片段这些每轮变化的东西放到尾部消息里，好让同一段前缀能被反复复用。

关键做法是按「会不会变」切块、动态信息绝不改写前缀、命中只当省下前缀重算那一段、并记住缓存有存活时间、只有长而重复的前缀才划算。

当每次请求都是零散单发、前缀短到复用收益有限，或内容本身每轮都完全不同、根本凑不出稳定开头时，不必为它硬做排布；但只要一个会话里连续多轮共用同一套提示，把动态注入从头部挪到尾部就是最省事的一处改动。

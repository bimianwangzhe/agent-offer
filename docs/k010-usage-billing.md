# 用量统计与计费口径

## 一、一个绕不过去的月底问题

你做了一个内部问答助手，跑了一个月，负责人来问三句话：这个月模型一共花了多少、哪个功能最费钱、有没有哪个用户用得异常多。你打开账单，只看到一笔汇总金额，再翻代码，调用散落在四五个文件里，每次都是打一行日志就完事。于是「一共花了多少」勉强能答，「哪个功能最费钱」得靠猜，「哪个用户异常」根本无从下手。更麻烦的是，等到有人抱怨开销突然翻倍，你连「是哪一类请求涨了」都说不清，只能笼统地回一句「最近用量有点大」。

## 二、先破一个最贵的误解

**不是模型乱扣费，也不是接口算错了账，而是你从一开始就把每一笔调用记成了一个没有归属的总数，等到要归因时，信息早就被抹平了。**

很多人以为计费是账期到了去看一眼账单的事，其实账单只是结果，能不能回答上面那三个问题，取决于调用发生的那一刻你往账本里写了什么。模型服务通常按输入与输出分别计量，两者单价不同，如果一个请求只留下一个总数，这两部分就永久地混在了一起；如果连「这次是谁、为哪个任务发的」都没记，那么按人、按功能、按意图去拆就全部成了事后拼凑。换句话说，账单粒度不是月底决定的，是写代码那一行决定的。想理解一次请求里这些字段是怎么来的，可以先看 [一次请求拆成五块](./k008-request-anatomy.md)，本篇关心的是其中「用量」这一块该怎么落账。

## 三、把它想成一栋楼里的分电表

先说一个概念：Token（模型读写文本的最小计量单位，可以理解成模型眼里的「字块」，它既不等于字数，也不等于词数）。计费就是数一次请求里进去多少字块、出来多少字块，再各自乘单价。

把它类比成公寓楼的水电收费。整栋楼总表能告诉物业这个月用了多少电，但物业没法拿总表去跟每一户收钱，因为不知道谁用了多少。真正能收费的做法，是给每户装一块分表，每块表再分「照明」和「空调」两个回路，月底按户、按回路分别抄表。这里有一一对应关系：一次模型调用等于某一户某一次用电；用户 ID（Identifier，标识符，用来唯一指认一个对象的一串编号）与任务编号合起来等于「哪一户 + 哪个回路」；输入 Token 与输出 Token 等于两个回路分别走的度数；单价等于每度电价；而账单告警等于「某户本月突然比上月多用了三倍」时自动贴一张提醒单。

这个类比还点出了两件容易被忽略的事。第一，分表要在用电的当下就装好，事后再补是补不回来的——总表读数一旦汇总，各户的比例就消失了，这正对应「日志只打一个总用量」的毛病。第二，分回路不是为了好看，而是因为两个回路单价不同、涨价的成因也不同：输入涨了通常是提示词或检索片段变长，输出涨了往往是模型话变多了或者循环没刹住。把两者分开，排查方向立刻就窄了一半。关于 Token 本身为什么和字数对不上，[Token 与分词](./k001-token.md) 有更细的展开。

## 四、两张图看清账本长什么样

:::figure 一次调用的用量从产生到入账
@flow
拼装请求|发往模型|回收输出|分别计量|按桶累加
:::

第一张图是一条请求的生命周期。关键在最后两步：计量要「分别」做，输入一次、输出一次，不能合起来数；累加要「按桶」做，也就是先决定这次属于哪个用户、哪个任务，再往上加。顺序反了会出事——先加进一个大总数、再想分桶，就和总表抄完再想分户一样无解。

:::figure 记账口径的两种做法
@compare
只记总数::只有一个月底数字|分不清功能与用户|超额无从预警
分桶记账::按用户任务双维度|输入输出分开算|随时可查可告警
:::

第二张图把两种口径摆在一起。左边那种不是「错」，而是它只能回答一个问题：一共多少。右边那种麻烦一点，要维护一张按「用户 × 任务」组织的账本，但它同时把归因、异常发现、预算告警三件事都变成了查表操作。多出来的成本只是几个字典和几行累加，换来的却是从「靠猜」到「可查」的差别。

## 五、顺着追问把边界推出来

:::ask 那如果一次任务里模型被反复调用了十几轮呢？
:::

那就更不能只按「请求次数」记账了。一个带循环的任务（比如自动排查问题的助手）可能在一个任务编号下连着调十几次模型，每次都带上一轮的历史当输入，输入 Token 会越滚越大。如果账本只记「调用一次」，你会严重低估这类长任务的开销；如果记「这个任务总共用了多少」，又看不出是哪一轮开始膨胀的。稳妥的做法是两层都留：任务桶里累加总量，同时留一串按轮次的小记录，至少要能回答「第几轮输入突然翻倍」。这也是为什么前面强调按桶累加时，桶的键里要带任务编号——它是把十几轮归到同一个目标下的唯一线索。

:::ask 再追一层：那如果同一个提示词被上百个用户各问一遍，账单会不会重复算？
:::

会，而且这是分桶记账最容易踩的空子。缓存命中的请求，服务端可能不再重复计算那段稳定前缀，账单口径上应当和全新请求区别对待；但你的客户端如果照着「每次都记一遍完整输入」去累加，就会把命中缓存的请求也算成全额，账本和真实账单对不上。所以账本里除了输入、输出两项，最好再留一个「是否命中复用」的标记，让按人汇总时能区分「新算的」和「复用的」。这不是要你去实现缓存，而是提醒一件事：账本的字段设计要跟着计费口径走，口径里有区别，账本里就得有位置。相关的复用思路可以对照 [流式输出与首字延迟](./k009-streaming.md) 之后的成本讨论，这里先把「口径要能对齐」这条记住。

## 六、用一段可运行代码把账本立起来

下面这段不联网、不装任何第三方包，用一个确定性的假模型模拟「输入进去、输出出来」，再用一张按「用户 × 任务」分桶的账本把用量记下来。复制成文件直接运行即可。

```python
from collections import defaultdict
from dataclasses import dataclass, field

def fake_count_tokens(text):
    # 纯本地的粗略计量：中文按字，其余按每 4 个字符折 1 个字块
    zh = sum(1 for ch in text if '\u4e00' <= ch <= '\u9fff')
    other = len(text) - zh
    return zh + (other + 3) // 4

def fake_model(prompt):
    # 假模型：按输入长度拼一段确定性的回复，模拟输出用量，不发任何请求
    return "已收到 {} 字的问题，答复如下：处理结果正常。".format(len(prompt))

@dataclass
class Usage:
    input_tokens: int = 0
    output_tokens: int = 0
    calls: int = 0

@dataclass
class Ledger:
    # 账本：按 (用户, 任务) 双维度分桶，输入与输出分开累加
    buckets: dict = field(default_factory=lambda: defaultdict(Usage))
    price_in: float = 0.005    # 构造用的每千输入字块单价
    price_out: float = 0.015   # 构造用的每千输出字块单价

    def record(self, user_id, task_id, prompt, reply):
        u = self.buckets[(user_id, task_id)]
        u.input_tokens += fake_count_tokens(prompt)
        u.output_tokens += fake_count_tokens(reply)
        u.calls += 1

    def cost(self, u):
        return (u.input_tokens * self.price_in + u.output_tokens * self.price_out) / 1000

    def report(self):
        rows = []
        for (user_id, task_id), u in sorted(self.buckets.items()):
            rows.append((user_id, task_id, u.input_tokens, u.output_tokens,
                         u.calls, round(self.cost(u), 6)))
        return rows

    def user_total(self, user_id):
        return sum(u.input_tokens + u.output_tokens
                   for (uid, _), u in self.buckets.items() if uid == user_id)

def main():
    ledger = Ledger()
    # 用户 u1 在任务 t1 里连问 3 次，在任务 t2 里问 1 次
    for i in range(3):
        p = "查询订单状态 第{}次".format(i)
        ledger.record("u1", "t1", p, fake_model(p))
    p = "退货政策是什么"
    ledger.record("u1", "t2", p, fake_model(p))
    # 另一个用户 u2 只在 t1 里问 1 次
    p = "查询订单状态 单次"
    ledger.record("u2", "t1", p, fake_model(p))

    rows = ledger.report()
    t1 = next(r for r in rows if r[0] == "u1" and r[1] == "t1")

    results = []
    results.append(("按用户与任务分桶共 3 个桶", len(ledger.buckets) == 3))
    results.append(("u1 的 t1 累计 3 次调用", t1[4] == 3))
    results.append(("输入与输出分开记录且都大于零", t1[2] > 0 and t1[3] > 0))
    results.append(("用户用量等于其下各任务之和",
                    ledger.user_total("u1") ==
                    sum(r[2] + r[3] for r in rows if r[0] == "u1")))
    results.append(("连问多次的 u1 用量高于只问一次的 u2",
                    ledger.user_total("u1") > ledger.user_total("u2")))
    results.append(("输出单价高于输入单价，可分口径核算",
                    ledger.price_out > ledger.price_in))

    passed = sum(1 for _, ok in results if ok)
    for name, ok in results:
        print(("通过" if ok else "未通过") + "：" + name)
    print("通过 {}/{} 项".format(passed, len(results)))
    assert passed == len(results)

if __name__ == '__main__':
    main()
```

逐段看关键行在做什么：

1. `fake_count_tokens` 把一段文本折成字块数。它只是本地估算，用来演示「输入与输出要分开数」，真实计量由服务端返回，不该自己拿字数硬算——这里用假函数纯粹是为了不联网也能跑。
2. `fake_model` 按输入长度拼一段固定回复。它是「本地确定性桩函数」：同样的输入永远给同样的输出，于是断言才可复现，不会出现这次跑过、下次跑不过。
3. `Usage` 用三个字段装一个桶：累计输入、累计输出、调用次数。把次数单列出来，是为了能算「平均每次用量」，进而发现某一类任务忽然变啰嗦。
4. `Ledger.buckets` 用 `defaultdict(Usage)`，键是 `(用户, 任务)` 元组。这一行就是整篇的题眼：桶的键决定了你事后能按什么维度拆账。
5. `record` 先定位桶，再分别累加输入、输出、次数。注意顺序是先分桶后累加，正是第一张图最后两步的顺序。
6. `cost` 用两个不同单价分别加权，演示「输入与输出口径不同」该怎么落到金额上；`report` 按桶排序输出，`user_total` 演示按用户再聚合一层。
7. `main` 造了「一个用户跨两个任务、其中一个任务连问三次、另一个用户只问一次」的小场景，用六条断言分别验证分桶、累计、双口径、聚合、横向比较与单价区分，最后打印 `通过 N/N 项`。

跑通时你会看到六个「通过」和一行 `通过 6/6 项`。这六条断言其实对应了负责人那三个问题的机器版：能不能拆桶、能不能聚合、能不能比出异常。

:::tip
账本的粒度不是月底调出来的，是 `record` 那一行写死的。想按功能、按意图、按提示词版本拆账，就在键里多带一维，代价只是多一个字段。
:::

## 七、踩过的坑与它的边界

- **只记一个总用量**：现象是月底只有一个数字，问「哪个功能费钱」答不上来 → 原因是计量时没带用户与任务归属 → 在调用发生的那一刻就把「用户 + 任务 + 意图」写进桶的键，别指望事后补。
- **输入与输出合并计**：现象是开销涨了却分不清是提示词变长还是模型话变多 → 原因是两项单价不同、成因也不同，合起来就丢了排查线索 → 分成两个字段累加，金额用两个单价分别加权。
- **鉴权串被算进账单**：现象是自己估的用量和服务端账单一一对不上 → 原因是把「接口鉴权用的凭证」和「文本计量单位」都叫一个名字，混成了一笔 → 记住计费只数文本字块，凭证在网关层，既不计入也不进窗口。
- **按调用次数估成本**：现象是带循环的长任务严重超支 → 原因是一次任务可能连调十几轮、每轮输入还越滚越大 → 同时留总量与按轮次的小记录，至少能定位「第几轮开始膨胀」。
- **复用请求按全额记**：现象是客户端账本比真实账单高出一截 → 原因是命中稳定前缀复用的请求被当成全新请求重复计 → 加一个「是否复用」标记，让汇总时能区分新算与复用。

还有一个边界要说清：这套账本解决的是「可归因、可预警」，它不能替你决定花多少钱合适，也不等于强制限流。真要在超支那一刻掐断请求，得由调用前的检查去执行，账本只提供「已经用了多少」这个判断依据。告警贴出来不等于刹车踩下去，这是两件事。

## 九、三句话小结

用量统计与计费口径，是在每次调用发生时按「用户 × 任务」分桶、把输入与输出分开累加的一套记账方法，让开销能归因、聚合、预警。

关键做法是把归属写进桶的键、把两项用量写进不同字段、把单价与复用标记留进账本，全部在调用那一刻完成，而不是月底补。

当你只是本地跑一次性实验、既没有多用户也没有预算约束时，不必上这套账本，随手打印一个总数就够了。

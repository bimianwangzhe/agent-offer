# 自动纠正与重试上限

## 一、场景提问

你让模型从一段简历里抽出姓名和年龄，约定用 JSON（JavaScript Object Notation，一种用花括号和键值表示数据的纯文本格式）返回，并且 `age` 必须是整数。程序拿到结果就直接 `json.loads` 往下解析。头几次都挺顺，某天它少返回了一个字段，或者把年龄写成了字符串 `"28"`，甚至在正确对象后面多补了一句解释，解析当场抛错，整条链路卡住。你想：既然它能把话说清楚，那把报错贴回去让它「再给一版」不就行了？于是你把异常原样贴回对话里重试——这一次它换了个错法，你再贴，它又绕回第一个错，来来回回好几次，任务没成，调用次数和花费倒翻了几倍。到底是「再试一次」这个思路不对，还是这次重试少了点什么？

## 二、破误解

**不是「模型不会改」，而是把「重试」当成了「把同一句话原样再发一遍」，既没给它可操作的错因，也没给次数和刹车。**

先把混在一起的三件事拆开。第一件是校验：拿到一段输出，先用代码判定它哪里不合格，并且把「哪里不合格」压成一条机器和人都能读懂的诊断。这一步不是一句「不对」就完事，而是分层定位的——先查它是不是一段能解析的文本，这是 [语法层校验](./k016-syntax-check.md)；再查顶层结构、字段有没有缺、类型对不对，这是 [结构层校验](./k017-structure-check.md)；最后查值本身合不合业务约定，比如年龄是不是落在合理区间、布尔值有没有冒充数字，这是 [语义层校验](./k018-semantic-check.md)。三层各管一段，报出来的错才具体。第二件是纠正：把这条具体诊断回灌给模型，让它只针对被圈出来的那一处改，别的地方照旧，而不是从头重写一遍整份输出。第三件才是重试上限：给「最多改几次、改不好就别改了」画一条事先写死的线。

很多人只做了「再发一次」，等于把三件事压成一件：报错没被翻译过、模型不知道该改哪、次数也没人管。为什么上限非有不可？因为模型输出本身带随机性，同一句请求每次抽样都可能给不同结果，这一点在 [采样参数与不确定性](./k004-sampling.md) 里讲得很清楚；「请只输出 JSON」这类叮嘱从来就不是保证，[「请只输出 JSON」为什么不是保证](./k014-json-request.md) 专门拆过这个误会，就算加了 [JSON Schema 约束](./k015-json-schema.md) 也只是把出错的概率收窄、收不到零。更要紧的是，有些错根本不是「格式写歪了」，而是内容层的矛盾——比如字段值本身就是编的、和原文对不上，这种错你让它改一百遍也改不出一个诚实的答案。没有上限，程序就会在这类错上无限打转，一边烧调用、一边把同一份坏数据反复往下游送。

还得分清两类失败：语法错、结构错这类「看得见、改得动」的，适合自动纠正；语义层里需要重新判断事实、甚至需要外部信息的，不该让模型自己悄悄改。而「重试耗尽之后怎么办」不是本篇的终点，它是 [果断降级与兜底返回](./k020-graceful-fallback.md) 接手的下一棒；至于网络抖动、限流这类和「输出写歪了」完全不同的「再试」，归 [重试、指数退避与抖动](./k108-retry-backoff.md) 管，别把两套重试混成一个开关。本篇只盯一件事：输出不合契约时，怎么带错因改、改几次、什么时候必须停。

## 三、生活类比

把它想成去窗口办一张证件，表格填错了要退回重填。一个靠谱的窗口不会每次只丢给你一句「不行，重填」，而是在表单上用笔圈出来：第 3 栏空着、第 5 栏要填数字你填了汉字。这张被圈过的表，就是校验层产出的具体诊断——它把「不对」翻译成了「哪一栏、错在哪」。你拿回座位，只改被圈的那两栏，其余照抄，不会把整张表撕了重写，这就是「最小纠正」：改动范围越小，越不容易在别处引出新错。

窗口还有一条规矩：同一张表最多退三次，第三次还不对，就请你转到旁边的人工柜台专门处理，不再让你在自助窗口反复排队。这条「最多三次」就是重试上限，「转人工柜台」就是超限之后的兜底出口。为什么非得有这条线？因为排队的人越多、队伍越堵，而有些表格错在根上——比如你压根没带齐材料，改格式永远改不出来，该做的是换通道而不是继续排。

最要命的是第三种情况：窗口每次都圈第 3 栏，你也每次都改了，可下一轮还是被圈第 3 栏。这时候继续排第十次毫无意义，说明你和窗口对这一栏的理解根本没对齐，得停下来问清楚「这栏到底要什么」。这就是重复检测要提前刹车的原因——连续两次给出同一个错，不是在靠近成功，而是在原地打转，再试也榨不出新信息。

对应关系逐条对齐：笔圈出的一栏 = 分层校验给出的具体诊断；只改被圈处 = 带诊断的最小纠正；最多退三次 = 重试上限；转人工柜台 = 超限转兜底；反复圈同一栏就停下去问 = 对重复错误的提前熔断。这个类比还点破一件常被忽略的事：真正让重试变有效的，不是「多给几次机会」，而是每一轮都带着上一轮的诊断往前走一点；没有诊断的重复，只是把同一句请求念了好多遍。

## 四、自绘示意图

:::figure 一次带刹车的纠正回路
@cycle
校验输出|定位错因|回灌纠正|计数判定
:::

这张图故意画成回路而不是直线：改完必须回到「校验输出」重新验一遍，因为纠正本身也可能改坏别处，不回验就等于闭着眼放行。四格里最容易被省掉的是「定位错因」——省了它，「回灌纠正」就退化成把报错整段倒回去；以及「计数判定」——省了它，这条回路就没有任何出口，会一直转到超时。

:::figure 两种重试姿势的差别
@compare
无上限反复重发::次数失控花费涨|同一错误反复出现|错误带进下游
带诊断与上限重试::每轮只改被定位处|失败有明确出口|超限转兜底可交代
:::

左边是「再发一次」的朴素做法，顺风顺水时看不出毛病；右边把每一轮都变成「带诊断、有计数、到点就停」的动作。二者真正的差距不在多试了几次，而在出问题的那一刻：左边只会一直转，右边能干净地交出一句「改了三次没改好，已按兜底处理」，并且说清是卡在哪一种错上。

## 五、层层追问

:::ask 那如果把完整报错连同上一版输出一起回灌，改得会更准吗，为什么还要限制次数？
:::

会更准，而且「带上一版输出做对照」本来就是该做的：模型得看见自己刚才交了什么，才知道该改哪一处。但这里有个分寸——回灌的是「一条定位过的诊断」，不是把整份异常栈、整段历史、甚至好几轮对话一股脑倒回去。原因有三。其一，诊断越短越具体，模型越容易只动该动的那一处；把一大堆无关上下文塞回去，它反而可能去「迎合」报错里的某句话，把本来对的地方改歪，这在 [错误回传](./k029-error-feedback.md) 里被反复强调过。其二，每一轮回灌都会让下一次请求的输入变长，轮数一多，上下文被这些反复的失败样本占满，真正要办的事反而被挤到边缘。其三，也是最容易被忽略的：回灌只提高「单轮改对的概率」，它并不改变「有些错本来就改不对」这个事实。所以诊断要精准，次数仍要设限——这两件事一个管质量、一个管边界，谁都替代不了谁。判断哪些错值得回灌重试、哪些该当场放弃，正是 [异常分类与可重试判定](./k131-error-classify.md) 要立的规矩；而从源头减少这类格式错，还可以往生成端想办法，[约束解码原理](./k134-constrained-decoding.md) 讲的就是让不合规的输出压根生成不出来，能少纠一次是一次。

:::ask 那如果连着两次报的是同一个错，是不是说明它快改对了，该再多给几次机会让它自己绕出来？
:::

恰恰相反，重复同一个错是最该踩刹车的信号，不是「快好了」的信号。往深一层想：一次纠正之所以有价值，是因为它带来了新信息——上一轮缺字段，这一轮补上了却写成字符串，诊断变了，说明确实在往前挪。可如果两轮的诊断一模一样，说明前一轮的纠正没有任何效果，模型对这条反馈要么没理解、要么理解了也做不到，继续给同样的机会只是在重复同一个动作。这时还要防一种更隐蔽的情况：模型学会了「照着报错说好话」，输出里写满「已按要求修正」，实际内容纹丝不动——诊断文本没变、或干脆被它复述了一遍，光看「有没有重试」根本发现不了，必须比对每一轮的诊断指纹。所以成熟的做法是同时挂两条出口：一条数「总共试了几次」，到点转兜底；一条盯「错误有没有重复或原地踏步」，一旦重复就提前停。二者合起来，才既不会因为上限太大而空耗，也不会因为上限太小而把本可修好的也判死——后一种代价在演示代码里会被专门测出来：同一份能改好的输出，只因把上限从三调成一，就从「成功」变成了「兜底」。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一个完全由「上一次反馈」决定产物的本地桩函数来模拟模型，完整演示「三层校验 → 带诊断回灌 → 重复错误提前刹车 → 次数耗尽转兜底」。桩是确定性的，同一输入每次结果一样，可手工推算、可复现；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json

REQUIRED = {"name": str, "age": int}


def validate(text):
    """分层校验一段文本，返回 (是否通过, 诊断, 解析后的对象)。"""
    try:
        data = json.loads(text)
    except ValueError:
        return False, "语法错误：不是合法 JSON", None
    if not isinstance(data, dict):
        return False, "结构错误：顶层应是对象", None
    for key, typ in REQUIRED.items():
        if key not in data:
            return False, "结构错误：缺少字段 %s" % key, None
        if not isinstance(data[key], typ) or isinstance(data[key], bool):
            return False, "语义错误：字段 %s 类型不对" % key, None
    return True, "通过", data


def converging_model(feedback):
    """桩 A：会一次比一次好，第三次给出合格输出。"""
    if feedback is None:
        return '{"name": "阿明"}'
    if "缺少字段 age" in feedback:
        return '{"name": "阿明", "age": "28"}'
    if "字段 age 类型不对" in feedback:
        return '{"name": "阿明", "age": 28}'
    return '{"name": "阿明"}'


def looping_model(feedback):
    """桩 B：无论怎么反馈都给同一份坏输出，模拟原地打转。"""
    return '{"name": "阿明"}'


def repair(model, max_retries=3):
    """带诊断回灌、重复检测与次数上限的纠正循环，返回结构化结果。"""
    text = model(None)
    seen = []
    log = []
    for attempt in range(max_retries + 1):
        ok, reason, data = validate(text)
        log.append(reason)
        if ok:
            return {"status": "ok", "data": data, "tries": attempt + 1, "log": log}
        if reason in seen:
            return {"status": "stalled", "data": None, "tries": attempt + 1, "log": log}
        seen.append(reason)
        if attempt >= max_retries:
            return {"status": "fallback", "data": None, "tries": max_retries + 1, "log": log}
        text = model(reason)
    return {"status": "fallback", "data": None, "tries": max_retries + 1, "log": log}


def main():
    checks = []
    ok1, _, _ = validate('{"name": "阿明", "age": 28}')
    checks.append(("合法对象通过校验", ok1 is True))
    ok2, r2, _ = validate('{"name": "阿明",')
    checks.append(("残缺文本被判语法错误", (not ok2) and "语法" in r2))
    ok3, r3, _ = validate('{"name": "阿明", "age": true}')
    checks.append(("布尔值不冒充整数", (not ok3) and "类型" in r3))

    recovered = repair(converging_model, max_retries=3)
    checks.append(("带反馈纠正最终成功", recovered["status"] == "ok"))
    checks.append(("成功结果字段类型正确", recovered["data"]["age"] == 28
                   and isinstance(recovered["data"]["age"], int)))
    checks.append(("纠正恰好用了三轮", recovered["tries"] == 3))
    checks.append(("过程中缺字段与类型错都被反馈过",
                   any("缺少字段 age" in x for x in recovered["log"])
                   and any("类型不对" in x for x in recovered["log"])))

    stuck = repair(looping_model, max_retries=3)
    checks.append(("重复同一错误被判打转", stuck["status"] == "stalled"))
    checks.append(("打转时提前刹车未耗满上限", stuck["tries"] < 4))

    cut = repair(converging_model, max_retries=1)
    checks.append(("上限过小把可修好的判成兜底", cut["status"] == "fallback"))
    checks.append(("兜底时次数恰为上限加一", cut["tries"] == 2))
    checks.append(("各场景次数都不超各自上限加一",
                   recovered["tries"] <= 4 and stuck["tries"] <= 4 and cut["tries"] <= 2))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `REQUIRED` 用字段名到类型的映射写出契约，`validate` 分三层落地：先 `json.loads` 抓语法错，再查顶层是不是对象、字段有没有齐，最后逐个核类型。注意 `or isinstance(data[key], bool)` 这一截——Python 里布尔值算整数的子类，不排除它，`true` 就会被当成合法的 `age` 放过去，这正是语义层要挡的那种「格式对、意思错」。
2. `converging_model` 与 `looping_model` 是两个本地桩，产物完全由传入的 `feedback` 决定，不联网、不带随机。前者模拟「缺字段 → 补了却写成字符串 → 改对」这条会收敛的路径；后者永远交同一份坏输出，模拟怎么纠都原地打转。用桩而不是真模型，是为了让每一步都能手算、可复现。
3. `repair` 把「是否通过、诊断文本、解析结果」三样一起从 `validate` 拿回，每轮把诊断追加进 `log`。三条出口写得很直白：通过就返回 `ok`、诊断在 `seen` 里出现过就返回 `stalled`（重复检测）、轮数到顶就返回 `fallback`（次数上限）。返回的是带 `status` 的结构化字典，而不是一个含糊的 `None`——超限之后下游能据这个词决定怎么兜底。
4. 只有诊断是「没见过的新错」时，才把它当反馈交给 `model(reason)` 产出下一版，并且下一轮一定会重新走 `validate`。这就把「带诊断的最小纠正」和「改完必须回验」两件事都钉死在循环结构里，而不是靠口头约定。
5. `main` 先用三条断言单测 `validate`：合法对象要过、残缺文本要报语法错、`true` 不能冒充整数。接着验证收敛桩能在三轮内改对、结果字段类型正确、且 `log` 里确实留下过「缺字段」和「类型错」两条不同诊断——后者用来证明它是一步步往前挪，不是一次蒙对。
6. 再验证打转桩会被判 `stalled` 且提前停（次数小于四），以及把上限从三调到一时，同一份本可修好的输出被判成 `fallback`、次数恰为二。这两条合起来说明：上限太大靠重复检测补，上限太小会误杀，得配合着调。
7. 结尾把每条性质逐行打印，统计通过条数输出「通过 N/N 项」，并用 `assert passed == len(checks)` 兜底：只要有一条性质被破坏，程序就以非零状态退出，绝不会「看起来跑完了其实悄悄错了」。

有一处如实说明：这里的模型是确定性桩、契约只有两个字段、诊断也只有寥寥几种，全是为了让整条链路不依赖任何外部服务就能独立跑通、逐行手算。它演示的是「带诊断、有计数、到点就停」的顺序与出口，不是任何具体接口的用法；真实场景里的诊断种类、上限取值、兜底形态都要按业务另定。

## 七、踩坑与边界

- **把整段异常栈倒回去当反馈**：现象是越改越乱、本来对的字段被改歪 → 原因是回灌内容又长又杂，模型去迎合报错里的只言片语而非只修一处 → 只回灌一条定位到「哪个字段、哪层错」的短诊断，并附上上一版输出做对照，见 [错误回传](./k029-error-feedback.md)。
- **重试不设次数上限**：现象是某类输入上程序长时间不返回、调用量飙升、坏数据反复进下游 → 原因是有些错属于内容层矛盾，改多少遍都改不好 → 事先写死 `max_retries`，到点无条件转兜底，并按 [异常分类与可重试判定](./k131-error-classify.md) 只把可重试类送进这个循环。
- **只数次数、不查重复错误**：现象是明明每次都「重试了」，诊断却从头到尾一模一样，纯属空耗 → 原因是没比对每一轮的错因指纹，甚至被「已按要求修正」这类口头表态糊弄 → 记录每轮诊断，重复即提前停，别等次数耗尽。
- **纠正完不回验就放行**：现象是补丁把缺字段补上了，却顺手改坏了另一个字段，坏结果照样流到下游 → 原因是把「改了一次」当成「改对了」 → 每轮纠正后必须重新跑完整三层校验，通过才返回。
- **把语义错也交给模型自己悄悄改**：现象是缺的是事实、模型就编一个看起来合理的值补上，格式全对、内容是假的 → 原因是自动纠正只适合看得见改得动的格式问题 → 语义层需要重新判断或补外部信息的，判为不可自动修补、直接转人工或兜底，参看 [语义层校验](./k018-semantic-check.md)。

还要分清两条出口的分工：「次数耗尽」是兜底的总闸，「重复错误」是提前刹车，二者不该混成一个 `if`；也别把本篇的「输出写歪了再改」和限流、超时那类「请求没成功再发」的重试共用一个计数器，后者的退避与抖动是另一套做法，见 [重试、指数退避与抖动](./k108-retry-backoff.md)。而一旦判定「不纠了」，接下来该给出怎样一个诚实、可用、说得出来源的结果，就是 [果断降级与兜底返回](./k020-graceful-fallback.md) 接手的事。

## 八、自检清单

:::check 学完自检
- [ ] 能说清校验、纠正、重试上限这三件事各自解决什么，为什么说「再发一遍」不等于重试
- [ ] 能徒手画出「校验—定位错因—回灌纠正—计数判定」这条回路，并指出改完为什么要回验
- [ ] 能解释重复同一个错为什么该提前停，而不是当作「快改好了」
- [ ] 能说出上限太大、太小分别会带来什么问题，以及兜底结果为什么要带状态标识
- [ ] 能判断哪些错适合自动纠正、哪些语义错必须转人工，不与网络重试混为一谈
:::

## 九、三句话小结

自动纠正与重试上限，是在输出不合契约时，先用分层校验把错定位成具体诊断，再带着它做最小纠正、每轮回验，并用次数上限和重复检测两条出口保证「改不好就停」的一套做法。

关键做法是回灌短而具体的诊断、改完必须重新校验、返回带状态的兜底结果，并把可重试与不可重试的错误分开对待。

当错误出在事实与业务判断、根本无法靠改格式补回来，或 retries 的代价高过直接转人工时，就别再自动纠正，果断走兜底更稳。

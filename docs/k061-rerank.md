# 粗排 + 精排与重排后截断：先别漏，再排准

## 二十段全塞进去，答案反而更糊

你怕漏，把召回的候选从五段加到二十段一股脑塞进上下文，结果答案开始东拼西凑，明明第一段就写对了限额，模型却把后面某段的旧口径混了进来，延迟也明显变长。你试着只留前五段，旧口径是不见了，可有时真正带限定条件的那段恰好排在第七、又被砍掉了。

## 先破一个误解

**不是候选太多或太少，是你让一次检索同时扛起「别漏」和「排准」两个相反的诉求。**

先把词说清楚。粗排（也叫召回阶段）指用便宜、能预计算的方法快速从大量片段里捞出较多候选，求的是「该找的尽量别漏」；精排，也就是重排（rerank），指对这几十条候选再用更重、更贴切的判断重新打分，求的是「排得准」。重排后截断指精排完只把最前面的少数片段送进生成，并顺手控制一下多样性，别让同一份材料的几个近似块把名额占满。这里常见的两类模型也顺带说清：双塔（Bi-Encoder）把查询和文档分别压成向量、算个相似度即可，文档向量能离线算好，所以能撑起大库里的毫秒级检索，但把一整段压成固定长度后细粒度差别会被抹平；交叉编码器（Cross-Encoder）把查询与文档拼在一起做充分交互，判断更细，却没法预计算，只适合对少量候选在线打分。

为什么必须分两步？因为这两类方法的成本差着数量级。粗排要扫的是全库，只能便宜、可预计算；精排看得细，但只能对几十条候选做。于是自然形成「先廉价召回 40 条上下 → 再精排到三五条」的漏斗：粗排保召回率，精排保精确率，各司其职。把它们合成一步，要么为了快牺牲精度，要么为了准把延迟拖垮。

截断为什么也不能省？因为上下文不是免费的：候选越多，无关块越容易稀释当前问题的权重，模型也越容易在几段之间自由发挥，把新旧口径混在一起。少而准的几段，通常比一大堆「可能相关」更可靠。但截断有个前提——精排得把真正带限定条件的片段提到前面来，否则一砍就砍掉了要害。两路粗排的结果怎么合成一份候选，见[混合检索与 RRF 融合](./k058-hybrid-rrf.md)；精排分还能顺手当拒答的闸门，见[溯源、拒答与零召回兜底](./k062-citation-abstain.md)。

## 用筛简历的两轮来理解

把找片段想成招聘时筛简历，粗排和精排就是两轮性质完全不同的筛选。

第一轮是机器初筛：按关键词、年限这些硬条件，从几千份里快速捞出几十份。它必须便宜、必须快，标准可以放宽——宁可多捞几份看起来沾边的，也别把合适的人一开始漏掉。这一轮对应召回，求的是「别漏」。

第二轮是用人部门细读：把捞上来的几十份逐份看项目、看匹配度，排个先后，最后只请前几位来面谈。这一轮慢、贵，但判断细，能把初筛里混进来的「词对上了其实不对」的挑出去。面谈名额有限，对应上下文预算，所以读完就得截断，不能把几十份都带进会议室。

对应关系：几千份简历是全库，硬条件初筛是粗排，逐份细读是精排，排先后是重排打分，只请前几位是重排后截断，「同一个学校投了好几份差不多的简历只留一份」是多样性控制。这个比喻还解释了一个常见错觉：把二十份初筛结果全带进会议室，并不会让决策更稳，只会让讨论发散、重点模糊。

:::quote
粗排求「别漏」，精排求「排准」，截断求「别撑爆」。三件事目标不同，就该分三步做，别指望一步到位。
:::

## 把漏斗画出来

先看一次检索从全库到少数片段，经过哪些动作。

:::figure 从全库到少数片段的漏斗
@flow
廉价粗排|取较多候选|精排重打分|按分截断|控多样性送生成
:::

第二个节点「取较多候选」是有意留的余量：粗排宁可宽松，因为漏掉的东西精排再也救不回来。

两阶段各管什么，可以列成清单：

:::figure 粗排与精排的分工
@stack
粗排::便宜可预计算，扫全库求别漏
精排::判断细但贵，只对少量候选在线打分
截断::只留最前面少数片段，受上下文预算约束
多样性::同源或近似块限量，别占满名额
:::

第四行常被忽略：几条候选若来自同一份文档、内容高度相似，全留着等于把一个证据重复计了好几遍，还把别的证据挤出去。

再看两种做法的差别：

:::figure 召回完直接塞，与粗排后精排再截断
@compare
召回完直接塞::无关块稀释注意力|新旧口径易混|延迟变长
精排后截断::要害片段被提到前面|只带少数证据|多一次打分开销
:::

第二行最后一格是代价：重排通常多一次判断、多一些延迟。所以别每次都无条件触发，分数本来就很分明时可以直接沿用粗排顺序。

:::tip 一条立刻见效的规则
把粗排候选数和最终送入数设成两个独立参数：前者放宽到几十条求「别漏」，后者按上下文预算定成三五条求「别撑爆」。两者之间的差值，就是精排真正发挥作用的空间。
:::

## 再往深问两层

:::ask 那如果延迟扛不住，是不是只能把精排整个去掉？
:::

不必二选一，有三条退路，而且可以叠加。一是把候选数从一百降到四十，精排要打分的条目少了，开销直接下来；二是换用更轻的打分方式，用规则或蒸馏过的小判断替代大模型打分；三是把重排与生成流水线错开，让前几名的片段先开始处理，不必等全部候选打完分。真到了连这些都扛不住的地步，至少保留一个用途：把精排的最高分当作「有没有依据」的闸门——分数低于阈值就直接走「未找到依据」分支，比让模型面对一堆含糊候选自己判断可靠得多，这一点在[溯源、拒答与零召回兜底](./k062-citation-abstain.md)里会接着讲。最不推荐的是「跳过精排、把二十条粗排结果直接塞进提示词」，那既没省下多少延迟，又把无关材料的干扰全请了进来。

:::ask 再深一层：截断时按精排分从高到低取，为什么还要管多样性？
:::

因为精排分高的几条，很可能是同一份材料的几个近似块。切分带重叠、同一制度被复制了几个版本、或者父子块同时混进候选，都会造成这种「高分扎堆」。若纯按分数取前几名，名额会被同一来源吃满：上下文里反复出现几乎一样的话，模型既得不到新信息，又容易被重复出现的口径带偏，答案里还可能出现重复引用。所以截断不该只是 `top-n`，还得加一条约束：同一文档、同一父块、或内容近似的块，最多保留一两条；被挡下来的名额让给别的来源。实现上很朴素——按精排顺序往下走，用来源标识记数，超限就跳过，直到凑够条数。这要求片段带着来源与父块编号，见[切分元数据与父块回溯](./k056-chunk-metadata.md)。至于「精排到底有没有把好片段提前」，别凭感觉，用固定的一组评测问题分别看粗排与精排后的排序差别，见[检索排序指标与 RAG 四项核心指标](./k142-retrieval-metrics.md)。

## 一份能跑的对照

下面这段只用标准库，把粗排（词项重合）、精排（更重的桩：额外奖励整段贴合）、按来源限量的截断都写出来，用构造片段演示「精排把信息更完整的那条提到前面」以及「同源块不占满名额」。

```python
# rerank.py —— 只用标准库，python rerank.py
import re

DOCS = [
    {"id": "d1", "src": "制度A", "text": "一线城市住宿每晚 600 元"},
    {"id": "d2", "src": "制度A", "text": "住宿标准 一线城市每晚 600 元 超标不予报销"},
    {"id": "d3", "src": "制度A", "text": "住宿标准补充说明"},
    {"id": "d4", "src": "制度B", "text": "其他城市住宿每晚 400 元"},
    {"id": "d5", "src": "制度C", "text": "发票报销七个工作日"},
]
Q = "一线城市住宿每晚 600 元"
KEY_PHRASE = "一线城市每晚 600 元"


def terms(t):
    return re.findall(r"[a-z0-9]+|[\u4e00-\u9fff]", t.lower())


def coarse(c):
    # 便宜的粗排：只数查询词项命中了多少
    return len(set(terms(Q)) & set(terms(c["text"])))


def rerank_score(c):
    # 更重的桩：额外奖励「整段贴合」的完整表述
    s = coarse(c)
    if KEY_PHRASE in c["text"]:
        s += 10
    return s


def truncate(ranked, k, max_per_src):
    out, seen = [], {}
    for c in ranked:
        n = seen.get(c["src"], 0)
        if n >= max_per_src:
            continue
        out.append(c)
        seen[c["src"]] = n + 1
        if len(out) == k:
            break
    return out


if __name__ == '__main__':
    coarse_rank = [c["id"] for c in sorted(DOCS, key=lambda c: -coarse(c))]
    rerank_rank = sorted(DOCS, key=lambda c: -rerank_score(c))

    assert coarse_rank[0] == "d1"              # 粗排把短而全的那条排第一
    assert rerank_rank[0]["id"] == "d2"        # 精排把带限定条件的提到前面
    assert coarse_rank[0] != [c["id"] for c in rerank_rank][0]

    final = truncate(rerank_rank, k=3, max_per_src=1)
    assert len(final) == 3
    assert len({c["src"] for c in final}) == 3   # 三个不同来源
    assert len(rerank_rank) > len(final)         # 精排候选多于最终送入的
    print("通过 6/6 项：粗排别漏、精排排准、截断控量与控多样性")
```

1. `DOCS` 是本地构造的五条片段，前三条同属「制度A」。`d1` 短而词面齐全，`d2` 多了「超标不予报销」这个限定条件，正是我们希望精排把它捞上来的那条。
2. `coarse` 是最便宜的粗排：数查询词项与片段词项的交集。`rerank_score` 是精排桩：在粗排分之上，额外奖励含完整短语 `KEY_PHRASE` 的片段。真实系统这里会是一次更重的在线判断，但「粗排便宜、精排更贴切」这个分工不变。
3. `truncate` 是截断加多样性控制：按精排顺序往下走，用 `seen` 记每个来源已取几条，超过 `max_per_src` 就跳过，凑够 `k` 条停。注意它跳过的正是「分数也高、但来源重复」的块。
4. 前三条断言演示重排的价值：粗排头名是 `d1`，精排头名变成信息更完整的 `d2`。如果只有粗排又只取一条，那条带限定条件的片段就被砍掉了。
5. 后三条断言演示截断：`final` 三条来自三个不同来源，说明同源块没有占满名额；精排候选总数仍多于最终送入数，漏斗确实收敛了。六条断言跑完打印通过项数。

想看得更清楚，可以把 `max_per_src` 改成 3，会看到 `final` 里挤满「制度A」的三条，而「制度B」「制度C」进不来；或者把 `rerank_score` 里那句奖励去掉，会看到精排与粗排给出同一份次序，重排就白做了。

## 踩过的坑

- **跳过精排直接塞一大堆**：现象是新旧口径混进答案、延迟变长 → 原因是无关的粗排候选稀释了当前问题的权重 → 怎么改：先精排收敛到少数片段，再受预算约束送入。
- **把父块也放进粗排候选**：现象是高分扎堆在整章大块上 → 原因是父子块混在同一份索引里 → 怎么改：粗排只放子块，命中后按编号回填父块。
- **截断不控多样性**：现象是前几名几乎都是同一段话的变体 → 原因是重叠块或同文档多版本高分扎堆 → 怎么改：按来源标识限量，被挡下的名额让给别的来源。
- **每次都无条件触发重排**：现象是分数本就很分明时仍白付一次延迟 → 原因是没判断是否需要精排 → 怎么改：分数含糊或候选来源杂时才启用，分明时沿用粗排顺序。
- **只调最终送入数**：现象是砍到三五条仍常漏掉要害片段 → 原因是粗排顺序没把好片段提前、截断只是砍尾部 → 怎么改：把候选数与送入数设成两个独立参数，让精排有空间 reordering。

## 三句话

粗排加精排与重排后截断，是先用便宜方法召回较多候选，再用更重的判断把要害片段提到前面、只留少数送入生成。
关键做法是把候选数与送入数分开设、截断时按来源限量，并让精排分顺手充当有无依据的闸门。
当库很小、候选本就只有三五条且分数分得很开时，直接沿用召回顺序即可，不必再叠一道重排。

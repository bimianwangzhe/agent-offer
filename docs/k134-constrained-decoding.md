# 约束解码原理

## 一、重试到第三次，格式还是错了一回

你给下游写了个解析程序，模型要回一个只含 `level` 字段的对象，取值限定三选一。你按[起步说明](./00-start-here.md)把提示写清楚，又加了 [JSON Schema 约束](./k015-json-schema.md)做校验，失败就把具体错处回传让它改，还守着[自动纠正与重试上限](./k019-auto-repair.md)。大多数时候都顺，可总有那么几回，它带出一句解释、漏了个花括号、把取值写成别处看来的词，重试一次两次才对。你算了下：这些本可以不发生的往返，每一次都在按输入加输出计费。后来听人提过一种办法——在它「张嘴」的那一刻就不许吐错字。你想弄明白，这跟「生成完再检查」到底差在哪，是不是等于换了个更听话的模型。

## 二、不是模型更聪明，是候选词被逐个掐掉了

**不是模型变得更听话了，是生成过程被一份外部规格锁住了：每一步只有合规格的候选词还在场，其余的被提前屏蔽，于是非法输出在构造上就不可能出现。**

先把几个词摆平。token（模型读写文本的最小单位，约等于一个汉字或半个英文词，不等于字数）是它一次吐出的东西。采样（sampling，从一批候选里按分数挑下一个 token）是它做选择的动作。logit 是模型给每个候选词的原始打分，分数越高越可能被挑中；把某个候选的 logit 压到极低，就等于这一位不许选它。Schema 是一份描述「数据该长什么样」的机器可读规格。约束解码（constrained decoding）指的是：把这份规格先编译成一套规则，在每一步采样之前，用它算出「当前位置还允许哪些 token」，把不允许的候选屏蔽掉，让模型只能在剩下的里面挑。

这件事和「拿到结果再校验」的分别很根本。事后校验是等整段文字写完，再拿规格去对，不对就打回重来；约束解码是不等写完，在每一位上就把岔路封掉。前者允许错字先出现、再被逮住，后者让错字连被挑中的资格都没有。所以它不是「模型学乖了」，也不是「原来偶尔错、现在几乎不错」这种程度上的改善，而是换了一条路：**输出不是被检查成合法的，是被构造成合法的**。理解了这句，就知道它为什么和重试不是一回事，也为什么它管不了所有问题。

那套规则通常有两种写法。有限状态机（Finite State Machine，按「当前状态加一个输入字符」决定下一状态的最简模型）适合表达「先花括号、再引号、再三选一取值」这种一路向前、不走回头路的结构；上下文无关文法（Context-Free Grammar，能表达嵌套与成对括号的一套规则）则用来对付带自引用、需要记住「开了几层括号就得还几层」的递归结构。前者轻快，后者表达力更强，选哪种取决于你的规格里有没有需要配对和递归的部分。无论哪种，运行时都要跟着已生成的前缀动态更新允许集合：已经写出 `{"level":"` 之后，左花括号就不再是合法候选了。

## 三、活字印刷里，只翻得出这一位需要的字模

想象一台老式活字印刷机，但做过一个改动：字盘不是把几千个字模全摊开任你拿，而是跟着「已经印出的内容」联动。你要印的是一句固定句式，比如一个等级对象。刚起头，字盘上只翻得出一枚左花括号，别的字模全被卡住按不下去；印完左花括号，字盘切换到下一档，只翻得出双引号；一路印到取值那一格，字盘上只翻得出 low、medium、high 三枚字模，写着 urgent 的那枚压根没升上来。排版工的手再随便、再想偷懒，也按不出一枚没被翻上来的字模——不是他不想，是那一位物理上够不着。

对应关系一条条摆出来：那台联动的字盘，就是每一步的候选词表；「只翻得出某几枚」，就是按规格算出的允许集合；被卡住按不下去的字模，就是 logit 被压到极低的非法候选；已经印出的半句，就是已生成的前缀；排版工就是那个按概率挑词的模型；整版印完的句子，就是最终输出。而「写张纸条叮嘱排版工别拿错字」，是提示词里的「请只输出 JSON」；「印完再逐字校对、错了重印」，是事后校验加[自动纠正](./k019-auto-repair.md)；那台会联动的字盘，才是约束解码。

想明白这层就该看出，反复把纸条写得更狠有多徒劳：你换的是纸和语气，没换字盘的形状。而活字印刷这个办法真正厉害的地方、和真正局限的地方，都来自同一件事——它管得住「这一位该是哪类字」，管不住「这句话说得对不对」。字盘能保证最后那枚是三选一之一，保证不了这一单到底该选哪一档。这个分界，后面要用代码亲手跑一遍才算真懂。

:::tip
一句话记住：**事后校验是「错了再抓」，约束解码是「错不了」**。判断一句话属于哪条路，只问一句：不合法的字符，是被写出来之后才拦下的，还是连被选中的机会都没有？
:::

## 四、把「生成时」这三个字拆开看

把一次生成从规格到成品中间发生的事拆开，就知道闸门装在哪一步。

:::figure 生成时逐步屏蔽的链路
@flow
编译规格为规则|算本步允许集|屏蔽非法候选|挑下一个词|输出必合法
:::

第一步把 Schema 编译成前面说的规则；第二步读取已生成前缀，算出这一位还允许哪些字符；第三步把不在允许集合里的候选分数压到极低；第四步模型在剩下的候选里照常按概率挑；第五步整段写完时，它必然落在规格里。整条链子的要害在第三步：闸门装在「挑词之前」，而不是「写完之后」。这也解释了为什么它不需要重试——岔路在走到之前就被封了。

:::figure 三种做法各自站在链路的哪一段
@stack
提示词请求::写「只输出 JSON」，靠模型自觉，压不到零
事后校验重试::结果出来才按规格查，脏了打回重来
生成时约束::采样前屏蔽非法候选，构造上不可能非法
:::

三条不是互相替代的关系，而是站在链路不同位置的三道闸门。第一条成本最低、最该写，却最没强制力；第二条谁都能自己实现，还能一路查到字段和取值；第三条要模型侧提供相应能力，管得住形状，管不住含义。真实系统里更稳的姿态是叠着用：把格式说清楚、把值再查一遍，中间能卡死形状就卡死。

:::figure 事后校验与生成时约束的差别
@compare
事后校验再重试::结果出来才拦|能查值的含义|偶尔要付往返成本
生成时约束解码::采样时就拦|只保形状不管含义|依赖模型侧能力
:::

右边那三点值得逐字读。「采样时就拦」是它省下往返的原因；「只保形状不管含义」是它最容易被高估的地方；「依赖模型侧能力」则意味着并非每处调用环境都提供同等强度的这一层。把这三点连起来看，得出的结论不是「有了它就删掉别的」，而是「它补上了别的补不了的那一段」。

## 五、那如果开了它，是不是就万事大吉

:::ask 既然输出在构造上就合法，那服务端校验是不是可以删了
:::

恰恰相反，这是最危险的一步。约束解码保证的是「取值属于枚举」「编号是规定形状」「括号成对」这类结构事实，保证不了「这一单该选 high 还是 low」「这个编号在系统里真实存在」「金额算对了」。语法掩码管不到值的业务含义，因为业务含义不在规格里，在别处的数据和规则里。顺着再追一层：那把业务规则也写进规格行不行？多数情况不行——「这个订单存在」要查库，「该选哪一档」要按金额判断，这些是运行时的事实，不是一份静态形状描述能穷举的。所以[语义层校验](./k018-semantic-check.md)那一关仍然要有，而且因为输入格式更干净了，它反而更好写。

:::ask 那它和「事后校验再重试」能互相替代吗
:::

不能，也不该二选一。一条路让非法输出在构造上不可能出现，另一条路让「形式上挑不出毛病、意思却错」的结果被查出来，两者守的是不同层。再追一层：那是不是每条链路都得把两条都上齐？也不必。内部调用、工具少、结构简单的场合，靠提示词加[语法层校验](./k016-syntax-check.md)与服务端校验就够；对外、关键路径、嵌套复杂的场合，才值得付这一层的代价去把形状钉死。追到最后你会发现，值得纠结的从来不是「哪条路更强」，而是「我这条链路上，错误最可能从哪一层漏进来」。

## 六、一段能直接跑的最小可视化

下面这段只用 Python 标准库。它把「一个只含 `level`、取值三选一的对象」编译成一棵合法前缀树，每一步列出当前还允许的下一个字符，把其余候选屏蔽掉，再让一个本地假模型在允许集合里挑词。样本与假模型都是构造的，不联网、不调用任何真实模型。

```python
# 约束解码的最小可视化：把规格编译成「合法前缀树」，逐位屏蔽非法候选。
# 只用标准库；候选词与假模型都是本地构造，不联网、不调用真实模型。

import json

# 目标结构：只含 level 字段、取值三选一的对象。
ENUMS = ("low", "medium", "high")
LEGAL = tuple('{"level":"' + e + '"}' for e in ENUMS)

# 假模型「想得到」的全部字符：合法串用得到的，外加几个它本来想吐的非法字符。
BASE = sorted({ch for s in LEGAL for ch in s})
EXTRA = ["x", " ", "\n", "'", "u", "!"]
ALPHABET = list(dict.fromkeys(BASE + EXTRA))  # 去重且保持顺序


def allowed_next(prefix):
    """给定已生成前缀，返回这一位还允许的下一个字符集合。
    这正是规格被编译成有限状态机后，『当前状态』允许的输出。"""
    nxt = set()
    for s in LEGAL:
        if s.startswith(prefix) and len(s) > len(prefix):
            nxt.add(s[len(prefix)])
    return nxt


def is_complete(text):
    return text in LEGAL


def mask(prefix):
    """把不合法候选的分数压成负无穷，等价于采样前屏蔽。"""
    allow = allowed_next(prefix)
    return {c: (0.0 if c in allow else float("-inf")) for c in ALPHABET}


def fake_model(masked, preference):
    """假模型：按自己的偏好挑第一个『还没被屏蔽』的字符。
    它并不懂规格，是掩码替它挡掉了错字。"""
    for c in preference:
        if masked.get(c, float("-inf")) > float("-inf"):
            return c
    for c, score in masked.items():
        if score > float("-inf"):
            return c
    raise RuntimeError("没有合法候选，规则写错了")


def constrained_generate(preference):
    out = ""
    while not is_complete(out):
        m = mask(out)
        ch = fake_model(m, preference)
        assert ch in allowed_next(out), "约束解码产出了非法字符"
        out += ch
    return out


def free_generate():
    """不设掩码的对照：凭习惯吐出语法合法、取值却越界的结果。"""
    return '{"level":"urgent"}'


if __name__ == '__main__':
    checks = []

    # 1. 三条枚举串的每一步前缀都落在合法前缀树上
    tree_ok = True
    for s in LEGAL:
        for i in range(len(s)):
            if s[i] not in allowed_next(s[:i]):
                tree_ok = False
    checks.append(("合法串逐位都在前缀树上", tree_ok))

    # 2. 换几种『模型偏好』，输出都必然落在 LEGAL 里
    prefs = [
        ["x", "!", "\n", "'", "u", " "] + ALPHABET,
        ["h"] + ALPHABET,
        ["l"] + ALPHABET,
        ["m"] + ALPHABET,
    ]
    outs = [constrained_generate(p) for p in prefs]
    checks.append(("多种偏好下输出都合法", all(o in LEGAL for o in outs)))
    checks.append(("能覆盖多个枚举取值", len(set(outs)) >= 2))
    checks.append(("非法取值 urgent 从未出现", all("urgent" not in o for o in outs)))

    # 3. 掩码确实把非法字符屏蔽了：起手只剩左花括号可选
    start_mask = mask("")
    checks.append(("起手非法字符被屏蔽", start_mask.get("x") == float("-inf")))
    checks.append(("起手只剩花括号可选",
                   [c for c, v in start_mask.items() if v > float("-inf")] == ["{"]))

    # 4. 对照：不掩码时输出『语法合法』却取值越界
    parsed = json.loads(free_generate())
    checks.append(("自由输出语法上能解析", isinstance(parsed, dict)))
    checks.append(("但取值不在枚举里", parsed["level"] not in ENUMS))

    # 5. 约束解码把取值锁进枚举，却回答不了『这一单该选哪一档』
    def business_rule(amount):
        return "high" if amount > 1000 else "low"

    shaped = json.loads(constrained_generate(["h"] + ALPHABET))
    expected = business_rule(50)  # 这单业务上该判 low
    checks.append(("约束版取值属于枚举", shaped["level"] in ENUMS))
    checks.append(("形状合法却与业务期望不符", shaped["level"] != expected))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `LEGAL` 把规格展开成三条具体合法串，`BASE` 收集它们用得到的字符，`EXTRA` 再补几个「假模型本来想吐」的非法字符，合起来就是候选词表 `ALPHABET`。这一步对应「把规格编译成规则」。
2. `allowed_next` 是整套机制的心脏：给定已生成前缀，遍历所有合法串，凡是以前缀开头的，把它的下一位收进允许集合。前缀树的性质保证了只要每步都从允许集合里挑，就一定能走到某条完整合法串，不会卡死。
3. `mask` 把允许集合以外的候选分数压成负无穷，这正是「采样前屏蔽」；`fake_model` 完全不懂规格，只按偏好挑第一个还没被屏蔽的字符——错字是掩码挡掉的，不是模型避开的。
4. `constrained_generate` 逐位循环，每步断言挑出的字符确实在允许集合里，写完即停。主函数换四种偏好各跑一次，验证输出都合法、能覆盖多个枚举值、且 `urgent` 从不出现。
5. 最后两段是边界演示：`free_generate` 给出一个「能解析但取值越界」的对照；`business_rule` 则用一个纯业务判断说明，即便形状被锁死，选档对不对仍要另一层来管。十二项断言跑完打印「通过 12/12 项」，任一项不成立就报错退出。

顺带一提，这段把「当前位置的允许集合」用穷举合法串的方式算了出来，真实实现里它由编译好的规则直接给出；但机制是一样的：每一步先问「现在还允许什么」，再让模型在剩下里面挑。

## 七、踩坑与边界

- **开了强约束就删服务端校验**：现象是格式再没错过，却把不存在的编号、算错的金额照单写库 → 原因是掩码只管形状，管不到值的业务含义 → 怎么改：把[语义层校验](./k018-semantic-check.md)留着，顺序放在解析之后、写库之前。
- **把枚举写进描述里**：现象是描述里明写「只能传 A 或 B」，字段仍声明成自由字符串，模型继续自造取值 → 原因是文字说明不参与编译，掩码对它无感 → 怎么改：闭集合一律声明为枚举类型，让规则看得见。
- **拿它去套递归结构却用了最简规则**：现象是深层嵌套或成对括号偶尔半截截断 → 原因是有限状态机表达不了需要记住层数的递归 → 怎么改：含自引用、深层配对的规格改用上下文无关文法级的表达，并压浅嵌套层数。
- **以为它零成本**：现象是新规格头一回请求明显慢一拍，且开着强约束时并行调用不顺 → 原因是规格要先编译成规则、且部分环境与并行调用不兼容 → 怎么改：让规格稳定复用编译结果，按链路风险分档决定是否启用这一层。
- **拿「结构合法」当事实用**：现象是拿到能解析的对象就直接入库，值其实不合适 → 原因是把「形状对」误当成「意思对」 → 怎么改：分清语法、结构、语义三层，分别放到[语法层校验](./k016-syntax-check.md)与业务规则里去守。

还要说清一个边界：约束解码并非处处可用，它依赖调用环境提供相应的生成期能力，不同环境强度也不一致。因此它更像是「在能用的地方把格式钉死」，而不是「从此不用再管格式」。真正稳妥的姿态是：规格负责说清形状，掩码负责在生成时守住形状，校验负责在拿到后查清含义，三者各归其位。

## 九、三句话小结

约束解码是把输出规格编译成规则，在每一步采样前屏蔽不合法候选词，让非法输出在构造上就不可能出现。
关键做法是让它守住形状，再叠一层服务端校验去查值的含义，两条路叠着用而不是互相替代。
当有人因为「格式再没错过」就想删掉业务校验、或拿它去保证事实正确时，就该停下——那种场合缺的是语义判断，不是更硬的掩码。

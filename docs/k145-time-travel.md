# 时间旅行、重放与分叉

## 一、场景提问

你接手一个会连着跑十几步的任务型程序：它先检索、再摘要、再算分、最后给出一句结论。某天它算错了，你盯着记录发现毛病出在第六步——那一刻它挑了个不该挑的工具，后面全跟着歪了。你很自然地想：「能不能回到第六步，换成另一个工具，再往下走一遍看看会不会好？」可真动手才发现，程序里那些变量是「活」的：第六步的状态早被第七步覆盖，工具当时已经真调用过、外部记录也写进去了，压根没有一份「第六步时系统长什么样」的存档。你只好从头再跑一遍，偏偏这一遍模型给出的措辞和上一遍不同，走到一半就拐去了别的岔路，连「同一个第六步」都到不了。明明只是想回到某一步换个选择，怎么比从头做还难？

## 二、破误解

**不是「再跑一次」就等于「回到过去」；真正的重放要求历史状态被整份存档、且每一步拿到的外部结果都记了下来，否则你重放出来的是另一条轨迹，不是原来那条。**

先把三个词分清楚。检查点（checkpoint，在某一刻把系统的全部状态整份拍下来存好，像游戏里的一张存档）解决的是「那一刻到底什么样」。重放（replay，从某张存档出发，按当时记下的事件一步步重新推进）解决的是「沿原路再走一次、且走得一模一样」。分叉（fork，从某张存档另起一条分支，用不同的事件往下探）解决的是「如果当时换个选择会怎样」。三者合起来常被叫作时间旅行：不是真让时间倒流，而是让状态变得可回退、可复制、可比较。很多人把「重放」理解成「把整件事重新执行一遍」，这是最要命的误会。重新执行会再问一次模型、再调一次工具，而模型输出带不确定性、下游状态此刻也变了，你得到的是一条新轨迹；重放不该重新去问谁，它读的是当时存下来的那份结果，然后本地把状态推过去。换句话说，重放考的是「记录得够不够全」，不是「跑得够不够快」。想做到这一点，光存变量不够，还得把「这一步凭什么这么走」的外部依据——模型当时吐出的原文、工具当时返回的值、用的哪套提示和哪个模型版本——一并记进事件。少了这些，状态就算存下来了，也推不回原来的下一步。还有一层容易漏：状态必须是深拷贝（deep copy，把里面嵌套的列表、字典也整份复制，而不是只复制一个引用），否则后面几步改的还是同一份对象，所谓「第六步的存档」其实早被改花了。

## 三、生活类比

把它想成一款带多个存档位的单机游戏，你在打一段有分支的剧情。每走到一个关键选择前，你手动存一次档：这一存，人物位置、背包、任务进度、当前好感度全被写进那张卡里——这就是检查点。后来你选错了对话，剧情崩了，于是读回那张卡重新选，这就是重放：起点完全一样，只是你现在能换一条路。更妙的是，你没舍得覆盖原卡，而是把同一张卡复制到另一个存档位，在第二个位子里选了完全不同的对话往下打，两条剧情从此各走各的、互不打扰，这就是分叉。

对应关系要落到细节才有用。存档卡是「那一刻的完整状态」，不是「你按过哪几个键」的流水账——只记按键、不记状态，读档时就得靠游戏重新算一遍当时的局面，一旦中间有随机判定就对不上了；这正对应「检查点要存状态快照，而不只是一行文字日志」。存档位互不覆盖，对应分叉必须各自拿到一份独立拷贝，共用同一个可变对象是分叉最常见的 bug。游戏里有个特别坑人的设定：某些宝箱掉落是随机的。你想复现「那次开箱出了什么」，光读档没用，得把当时开出的东西也记下来，否则重开一次可能掉出完全不同的物品——这就是外部结果必须记进事件的原因。放到程序里，「随机掉落」就是模型某次的具体输出、某次接口的具体返回；不把它们记下来，重放就永远差一口气。这个比喻还顺带说明了一件事：存档越密，你能回退的落点越多，但每张卡都占地方，所以真实系统往往只在关键步存档，而不是每一步都拍一张——这是空间与精度的取舍，跟游戏里「存档位有限」是一回事。

## 四、自绘示意图

:::figure 一次执行留下的检查点链
@flow
初始状态|事件一存档|事件二存档|事件三存档|末状态
:::

这条链里每个格子都是一张完整快照，箭头只表示先后顺序，绝不表示「后一张把前一张改掉了」。真正让时间旅行成立的关键，恰恰是任何一张存档写下去之后就不再被改动：你可以随时点中「事件二存档」当新起点，前两张还老老实实待在那儿等着被比较。如果嫌存档太占空间只在关键步拍，链就变短，能回退的落点也变少，但每一步该记什么仍然一样都不能少。

:::figure 一个检查点该装进哪些东西
@stack
状态快照::当前全部变量的一份深拷贝
事件序号::这是第几步、属于哪条轨迹
外部输入::当时工具返回或模型输出的原文
配置版本::提示、模型、工具清单各自的版本号
:::

四样里最常被漏的是「外部输入」和「配置版本」。前者决定重放时能不能不走样地推到下一步，后者决定你事后能不能回答「当时到底跑的是哪一套」。只有一份孤零零的变量快照，就像一张不知道是哪个版本、也记不得当时发生了什么的存档，回得去也用不上。把状态和当时用到的提示、模型、工具结构对上号，是 [提示与策略版本化](./k113-prompt-versioning.md) 要处理的事；这些描述随时间悄悄变化带来的偏差，则是 [版本漂移与升级策略](./k084-version-drift.md) 关心的。

:::figure 重放与重新跑一次不是一回事
@compare
重放::读存档与外部记录|结果可复现|不产生新副作用
重新跑::再问一次模型与工具|结果可能不同|可能重复写外部
:::

左边是重放：它只从本地存档里读，不再惊动模型和下游，所以同样的输入永远推出同样的状态，也不会把外部又写一遍。右边是重新执行：看似「重来一次」，其实每个带不确定性的环节都可能给出不同答案，还可能把已经做过的动作再做一次。把这两件事混为一谈，是重放类功能最难查的一类错——表面上都叫「再来一遍」，一个可复现，一个不可复现。

## 五、层层追问

:::ask 那如果工具调用是有副作用的，重放会不会把外部又写一遍？
:::

会，但前提是你在重放里真的又去调了工具——而这恰恰是不该做的。要分清两种「走」：只读重放，和真执行。只读重放的目的是复盘和比较，它遇到「调用工具」这一步时，不去真的调用，而是把当时那次调用的返回值从事件记录里取出来，直接当作本步结果喂给状态。这样既复现了当时的走向，又完全不碰外部。如果某条分支确实要真往下执行、真去写外部，那就不再是复盘而是另一次任务了，得给它新的任务标识，并且靠幂等键（idempotency key，给一次动作配一个全局唯一的编号，重复到达时凭编号认出是同一件事、只做一次）兜住重复写，这部分在 [幂等键与副作用防重](./k038-idempotency-key.md) 里讲得细，落盘那侧对应 [幂等落盘](./k107-idempotent-persist.md)。还有个更隐蔽的点：分叉出来的分支如果和主线共用同一套外部标识，两边一真执行就会互相认领对方的写入，所以分支要么只在只读层试探，要么必须换一套属于自己的标识。一句话，重放默认只读，凡是会改外部的动作都要显式地、带保护地重新授权，不能因为「反正是重放」就顺手执行了。

:::ask 那如果模型本身每次输出都不一样，怎么保证能走到「同一个第六步」？
:::

这把问题又往里推了一层，答案是：重放根本不该在第六步重新去问模型。回想那张存档卡——你要复现「那次开箱出了什么」，靠的是记下当时开出的物品，而不是再开一次箱。同理，第六步那次模型给出的具体文本、或者它选了哪个工具，都是已经发生过的事实，应该在发生时就被写进事件；重放到这一步，直接读那条记录，而不是再发起一次请求。所以「模型不确定」并不会破坏重放，破坏重放的是「你没把不确定的那次结果记下来」。真正需要额外处理的是采样（sampling，模型按概率挑下一个词的配置）本身：如果你希望连重新生成都能复现，就得把随机种子这类参数也固定并记档，见 [采样参数与不确定性](./k004-sampling.md)。再追一层：「我怎么知道当时用的是哪套提示、哪个模型版本？」——这就回到检查点里的「配置版本」那一栏，把提示、模型、工具清单各自的版本号随事件一起存，才能事后准确回答。于是整条要求串起来了：状态要深拷贝、外部结果要记原文、配置要记版本、重放只读不重问。做到这四点，「走到同一个第六步」才不是碰运气。至于循环里究竟哪些变量值得进这份状态、哪些只是临时中间量，可以对照 [循环状态该存什么](./k027-loop-state.md)；把这些状态按结构化方式组织，思路和 [结构化状态摘要](./k046-structured-state.md) 一致。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一份纯函数式的状态推进加一条「事件表 + 检查点表」，完整演示「逐步存档—回到任意步重放—从某步分叉不污染主线」。所有状态变化都发生在本地内存里，没有模型、没有网络、没有账号，复制到任何装了 Python 的机器上直接运行即可。

```python
import copy
import json


def apply(state, event):
    """把一个事件作用到状态上：返回新状态，绝不改动传入的旧状态。"""
    nxt = copy.deepcopy(state)
    kind = event["kind"]
    if kind == "add":
        nxt["items"].append(event["value"])
    elif kind == "score":
        nxt["score"] += event["value"]
    elif kind == "label":
        nxt["label"] = event["value"]
    nxt["step"] += 1
    return nxt


class TimeMachine:
    """用「事件列表 + 每步检查点」记录一次可回退的执行。"""

    def __init__(self, init_state):
        self.events = []
        self.checkpoints = [copy.deepcopy(init_state)]
        self.state = copy.deepcopy(init_state)

    def commit(self, event):
        """走一步：先更新状态，再同时记事件与检查点，三者对齐。"""
        self.state = apply(self.state, event)
        self.events.append(copy.deepcopy(event))
        self.checkpoints.append(copy.deepcopy(self.state))

    def replay(self, up_to):
        """只按前 up_to 条事件，从初始检查点重新推进，重建当时的状态。"""
        s = copy.deepcopy(self.checkpoints[0])
        for e in self.events[:up_to]:
            s = apply(s, e)
        return s

    def fork(self, at, alt_events):
        """从第 at 步检查点分叉：换成另一串事件往下走，主线一行都不动。"""
        s = copy.deepcopy(self.checkpoints[at])
        for e in alt_events:
            s = apply(s, e)
        return s


def same(a, b):
    """用稳定的序列化比较两个状态，避免受字典键顺序影响。"""
    left = json.dumps(a, sort_keys=True, ensure_ascii=False)
    right = json.dumps(b, sort_keys=True, ensure_ascii=False)
    return left == right


def main():
    init = {"items": [], "score": 0, "label": "start", "step": 0}
    tm = TimeMachine(init)
    plan = [
        {"kind": "add", "value": "检索"},
        {"kind": "add", "value": "摘要"},
        {"kind": "score", "value": 3},
        {"kind": "label", "value": "done"},
    ]
    for e in plan:
        tm.commit(e)

    checks = [
        ("主线走到第四步", tm.state["step"] == 4),
        ("主线末状态含两步产物", tm.state["items"] == ["检索", "摘要"]),
        ("检查点比事件多一个含初始", len(tm.checkpoints) == len(tm.events) + 1),
        ("全部重放与主线一致", same(tm.replay(4), tm.state)),
        ("部分重放与对应检查点一致", same(tm.replay(2), tm.checkpoints[2])),
        ("初始检查点未被改动", tm.checkpoints[0] == init),
    ]

    alt = [
        {"kind": "add", "value": "翻译"},
        {"kind": "label", "value": "branch-b"},
    ]
    branch = tm.fork(2, alt)
    checks.append(("分叉继承了第二步产物", branch["items"] == ["检索", "摘要", "翻译"]))
    checks.append(("分叉从第二步往后重新计数", branch["step"] == 4))
    checks.append(("分叉标签与主线不同", branch["label"] != tm.state["label"]))
    checks.append(("分叉不污染主线事件", len(tm.events) == 4))
    checks.append(("分叉不污染主线状态", tm.state["items"] == ["检索", "摘要"]))
    checks.append(("再分一次仍从同一检查点起步", same(tm.fork(2, alt), branch)))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `apply` 是整个设计的地基：先用 `copy.deepcopy` 把传入状态整份复制，再在副本上按事件类型改动，最后返回副本。因为是纯函数、从不碰旧对象，任何一步的历史状态都能被安全留下——这正是「存档写下去就不再被改」在代码里的落点。若图省事直接在 `state` 上 `append`，所有检查点会指向同一个列表，一改全改，回退当场失效。
2. `kind` 三类事件对应三种典型动作：往列表里加一项、累加一个分数、改一个标签；末尾统一把 `step` 加一，保证「走了几步」和状态始终同步。事件用字典表示，字段名固定，方便后面序列化与比较。
3. `TimeMachine.__init__` 同时建立三样东西：空的事件表、含初始状态一个元素的检查点表、以及当前状态。检查点表比事件表永远多一个，正是因为它把「还没走任何一步」的起点也存了进去；没有这张零号存档，`replay(0)` 和「从最开头重来」就无从下手。
4. `commit` 把「推进一步」和「记一笔」绑成原子动作：先用 `apply` 得到新状态，再把事件深拷贝进事件表、把新状态深拷贝进检查点表。两处都用 `copy.deepcopy`，是为了防止外部之后修改传进来的 `event` 或 `state` 时把历史一起带歪。
5. `replay(up_to)` 是只读重放的骨架：从零号检查点出发，只取前 `up_to` 条事件逐条 `apply`，全程不重新调用任何真实动作。它读的是记下来的事件，所以同样的 `up_to` 永远重建出同样的状态——这也是「重放不等于重新跑一次」的可执行证据。
6. `fork(at, alt_events)` 从 `checkpoints[at]` 拿一份深拷贝当起点，换一串替代事件往下推。起点是拷贝、替代事件也只作用于这份拷贝，因此主线的 `events`、`state` 一个字都不会变；两条分支共享 `at` 之前的前缀，之后的走向各归各。
7. `main` 先按四步计划提交，再用一组断言分别验证：主线步数与产物正确、检查点数量关系成立、整体重放等于主线、部分重放等于对应检查点、零号检查点未被污染；随后从第二步分叉，验证分叉继承前缀、步数从该点续算、标签与主线不同、主线事件与状态都未被改动、以及同一检查点再分一次结果一致。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：`apply` 里那几个事件、以及 `plan` 与 `alt` 的内容都是本地构造的确定数据，用来演示「存档—重放—分叉—隔离」这条链的性质，不是任何真实任务的记录，也不对应任何具体框架的实现。整段只依赖标准库、可独立运行。

## 七、踩坑与边界

- **存档只存了引用没存内容**：现象是明明存了检查点，回退后状态却和末态一模一样 → 原因是把可变对象直接塞进表、后面几步仍在同一份对象上改 → 用 `copy.deepcopy` 存整份快照，并像代码里那样断言零号检查点没被改动。
- **重放时又去问了一次模型或工具**：现象是同一存档读两次得到两种结果，外部记录还被重复写 → 原因是把重放实现成了重新执行 → 重放只读事件里记下的返回原文，不发起真实调用；确实要真执行的分支另给标识并配幂等键。
- **外部结果没记进事件**：现象是状态能重建，却推不出「当时为什么走到下一步」 → 原因是只存了变量、漏了模型输出与工具返回 → 事件里一并记下这些外部输入原文，重放时直接取用。
- **配置版本没随状态存档**：现象是复盘时说不清当时用的哪套提示、哪个模型，改了提示后旧存档再也复现不出来 → 原因是把状态和配置分家 → 每个检查点带上提示、模型、工具清单各自的版本号，见 [提示与策略版本化](./k113-prompt-versioning.md)。
- **分叉和主线共用一套标识**：现象是两条分支一真执行就互相覆盖、外部记录串味 → 原因是分支没有独立的任务或幂等标识 → 只读试探优先；必须真执行时给分支换一套属于自己的标识。

还要分清两件事：检查点解决「回到某个状态」，日志解决「看懂发生过什么」，谁也替代不了谁，把两者按同一条轨迹串起来的做法在 [检查点与轨迹回放](./k030-checkpoint-replay.md) 里有展开。时间旅行也不是越细越好：每一步都拍一张完整快照，长任务会把内存和磁盘吃得很紧，所以通常只在关键决策点存档，中间靠事件重放补齐，这与 [状态机与图编排](./k076-state-machine.md) 里「把状态与转移显式建模」是同一套思路；进程被中断后从最近检查点接上，则属于 [优雅中断与断点恢复](./k110-graceful-resume.md) 的范围。想从整体看这类能力在编排框架里处在什么位置，可对照 [框架六大件](./k075-framework-six.md)；多条分支的结果若要合并回一份状态，怎么合不打架是 [Reducer 合并语义与分槽写入](./k144-reducer-slot.md) 要回答的。

## 九、三句话小结

时间旅行是把每一步的状态整份存档、把当时的外部结果和配置版本一并记进事件，从而能回到任意历史节点重放、或另起一条分支试探不同走法的一套能力。

关键做法是状态深拷贝后只读不再改、重放读记录而不重新问模型或工具、分叉各自拿独立拷贝且不共用外部标识。

当任务只有一两步、或状态里全是无法复制的外部资源时，不值得为它搭整套存档机制；但只要一次执行长到「错一步全盘歪」，可回退、可比较的状态记录就省不掉。

# Agent 开发高频面试题精讲

先还原一个特别真实的面试现场。

面试官翻着你的简历，指着「基于大模型搭建的智能助手」问：「我在页面里放个输入框、接一下模型，也能聊、也能查资料。你这个『Agent』到底多做了什么？」

你答：「我让它能调工具，还写了循环，用了推理与行动交替的模式，加了检索增强和记忆。」

面试官点点头，追了一句：「那如果一次工具调用超时了，你怎么知道这次调用**到底有没有真的发生**？」

……沉默。

这不是你不会，是你只准备到了第一层。这一篇不讲怎么背名词，讲怎么把十道必考题答到第四层：先给能脱口而出的 30 秒答案，再给工程上真正怎么做的推导，最后把面试官的下一句、下下句提前摆出来。想练「追问链」本身的读法，可以配合[面试追问链](./15-interview.md)一起看；这一篇负责把知识点补厚。

## 一、先破三个误解

准备面试题时，最容易把力气花错地方。下面三个误解，几乎每个转行者都中过至少一条。

**误解一：能调工具就是 Agent。** 工具调用只是手段，不是身份。一个写死流程的脚本也能调工具：查天气、查完就返回，中间没有任何「自己决定下一步」的余地。反过来，一个不调任何外部工具、但会把自己写的草稿反复核对到满足代码断言才停的系统，反而更接近 Agent 的内核。

**误解二：会循环就是 Agent。** 这里有个特别隐蔽的范畴错误，一定要掰清楚：**模型自回归地一个 token 一个 token 生成文字，是模型内部的机制；系统要不要把执行结果读回来再决策，是应用架构的选择**。这俩根本不在同一层。模型吐字时本来就在「循环猜下一个词」，不能拿它当「我的系统是 Agent」的证据。想弄清这层机制，回看[大模型到底在干什么](./01-how-llm-works.md)。

**误解三：用了某个模式、某个框架就是 Agent。** 框架名和模式名是给别人看的标签，不是给系统定的性质。面试官追问时，标签一个都救不了你。

那到底拿什么判？只留一条判据：**最终交付的是不是「可验证的任务结果」**。

「可验证」的意思是，你能写出一条不靠人眼看、代码就能判真假的验收条件：订单号存在不存在、账户余额变没变、文件生成没生成、这三条引用在原文里找不找得到。写得出这种判据，说明系统对结果负责；写不出，多半只是个聊天框。

:::warn 别把「生成了答案」当成「完成了任务」
模型输出「已为您预订」这六个字，和订单库里真的多了一条记录，是两件完全不同的事。前者是文字，后者是**外部状态被改变且可被查证**。面试里把这句话说清楚，比报十个名词都管用。
:::

## 二、一个生活类比：查字典的人，和跑腿的实习生

把两种系统想成两个人。

**查字典的人**：你问他「这句话什么意思」，他翻一下，给你一段解释，结束。他再博学，也只交付了一段文字，对不对得你自己判断。这就是大多数「输入一段、输出一段」的应用。

**跑腿的实习生**：你说「帮我把明天去出差不淋雨的通勤定下来」。他会先看天气，发现下雨，去查车次，发现没票，自己去换方案，订完把单号发给你，还自己核了一遍「日期对不对、有没有真的出票」。中途每一步都依赖上一步的结果，而且**最后交给你的是一个可以被查证的东西**。

差别不在「谁更聪明」，在于有没有这条链：**看清现状 → 决定下一步 → 动手去做 → 核对结果 → 不对就再来一轮**。

:::figure 一个靠谱办事员的一次循环
@cycle
看清现状|决定下一步|动手去做|核对结果
:::

这张图里最容易被忽略的是最后那一格「核对结果」。没有它，前面三格只是「忙」；有了它，系统才知道自己**到没到终点**。而 `@cycle` 画出来的那条回流箭头，就是「没到终点，带着新观察再走一轮」——这正是决策—行动—观察—校验闭环。想把它写成代码，见[手写第一个 Agent 循环](./05-agent-loop.md)。

:::quote
普通应用把输入映射成一段输出；Agent 把输出变成动作，再把动作的结果读回来，决定下一段输出。**闭环，才是那条分界线。**
:::

## 三、什么叫「答到第四层」

先建立一个刻度，后面十道题都按它来量：

| 层 | 面试官在验证什么 | 典型回答长什么样 |
|---|---|---|
| 第一层 | 你知不知道这个名词 | 「就是让模型调工具，循环执行」 |
| 第二层 | 你写没写过 | 「宿主解析参数、校验、执行、回写观察，有四个终止条件」 |
| 第三层 | 你踩没踩过坑 | 「只设轮数上限时，出过一轮狂调工具的事故，后来补了成本和时间两道闸」 |
| 第四层 | 你有没有做过设计决策 | 「因为我这个任务的分支能枚举，所以八成走固定流程，只有跨系统查证那一小段交给模型决定；代价是多维护一套路由，换来的是延迟可控」 |

看出来了吗？第四层的句式永远是「**因为……所以选了 A 而不是 B，代价是……，什么情况下我会改**」。它不需要你背更多名词，需要你对一个具体场景有过判断。所以这一篇每题都给四段：**面试官怎么问 / 30 秒该答什么 / 工程上具体怎么做 / 继续追问会问到哪**。

:::tip 这一篇怎么读
别顺着背。挑一道你最虚的题，先只看「30 秒该答什么」，合上文档自己讲一遍，讲不顺就回到「工程上具体怎么做」补推导，最后用「继续追问会问到哪」自问自答。**能讲出「为什么」的那一天，才算会了。**
:::

## 第 1 题：Agent 和普通 LLM 应用差在哪

**面试官怎么问**：「你说做了个 Agent，它跟套个提示词做多轮聊天，本质区别在哪？」「是不是调了工具就算？」「那带检索的问答算不算 Agent？」——最后这句是陷阱，专门钓只背了「会调工具」的人。

**30 秒该答什么**：区别不在组件，在有没有「决策—行动—观察—校验」闭环，以及最后交的是不是可验证的任务结果。普通应用是输入到输出的一次映射；Agent 会拿输出去改变外部状态，再把改变后的结果读回来决定下一步，直到任务被代码验证完成、或明确失败。工具调用只是让「行动」这一格能碰到真实世界的手段，不是判据本身。

**工程上具体怎么做**：把这条闭环落成四个可检查的部件，缺一个就不算闭环。

1. **决策**：下一步做什么由谁定。若写代码时就能定死，那是流程不是 Agent；若运行时才依据观察决定，才进循环。
2. **行动**：调工具、写文件、发请求，动作要有明确的副作用边界（能读、能写、能删，分级）。
3. **观察**：动作的结果必须结构化地回写进状态，而不是打印在日志里就算完。错误也要回写，因为**失败是一次观察**。
4. **校验**：用代码判「任务到没到终点」，判据就是开头那条可验证结果。

再补一个面试官爱听的推导：为什么「工具调用只是手段」？因为工具解决的是「模型只能生成文字、不能真的动手」这个能力缺口，而闭环解决的是「系统凭什么相信自己办成了」这个可信度缺口。两个缺口不在一个维度，填了前者不自动填上后者。

至于「带检索的问答算不算 Agent」：一次检索、一次生成、结果由模型自己说了算，通常算「带检索的应用」；但如果它会判断证据够不够、不够就换关键词再检、直到证据充分或触顶才作答，那它已经长出闭环的雏形了——这条边界在[检索增强](./08-rag.md)里会被叫做「检索是不是一次性的」。

**继续追问会问到哪**：

1. 「循环一定要写成 `while True` 吗？」→ 不一定。固定 N 步的状态机、事件驱动的回调，只要存在「观察回写后重新决策」，都是闭环。闭环是逻辑概念，不是代码形状。
2. 「你怎么向面试官证明它是 Agent？」→ 亮两样东西：一条结构化轨迹，和一条代码可判的验收断言。别亮框架名。
3. 「那什么场景不该用 Agent？」→ 分支能枚举、结果确定的请求，写死流程更快更便宜。能主动说出「这里不该用」，反而是加分项，见[什么是 Agent](./04-what-is-agent.md)。

## 第 2 题：Workflow、单 Agent、多 Agent 怎么选

**面试官怎么问**：「这个需求你为什么上多 Agent？单 Agent 不够吗？」「什么时候该把流程写死？」——他真正在问的是：你有没有能力**不做过度设计**。

**30 秒该答什么**：只看一条主干判据——**下一步能不能在写代码时就确定**。能确定就用固定流程（Workflow）；不能确定、但探索空间属于同一个角色，用单 Agent；不能确定、且确实需要不同上下文、不同职责、还能各自独立验证，才考虑多 Agent。多 Agent 不是技术勋章，它带来的是延迟、成本、调试和归因难度的实打实上升。

**工程上具体怎么做**：把「要不要拆」拆成四道判断题，逐条过，任何一条不成立就别拆。

:::figure 选型的四道判断题
@flow
下一步能否写死|是否需要上下文隔离|子结果能否独立验证|收益能否覆盖成本|定下形态
:::

| 选型标准 | 具体在问什么 | 不成立时会怎样 |
|---|---|---|
| 任务可枚举 | 分支、异常、顺序能不能列全 | 列得全还交给模型，等于每次重新发明流程，稳定性白丢 |
| 上下文隔离 | 子任务之间会不会互相污染 | 一个读了几十页材料、一个只要一句结论，塞一起互相干扰 |
| 独立验证 | 每个子结果能不能单独判对错 | 不能独立验证就拆开，只会把错误往下游扩散 |
| 收益覆盖成本 | 省下的时间/提上去的质量，够不够付多出来的调用与排障 | 说不清收益，就是为复杂而复杂 |

推导一下第四条的「为什么」：多 Agent 把一个决策点变成 N 个决策点加 N-1 条消息契约，轨迹从一条线变成一张网。一旦结果不对，你要先判断是「哪个节点错了」还是「消息传丢了」——**归因成本是超线性涨的**。所以收益必须是能写下来的、可测的东西（比如并行把耗时从 20 秒压到 8 秒），不能是「看起来更先进」。

:::figure 单 Agent 与多 Agent，各自贵在哪
@compare
单 Agent::一条轨迹好归因|上下文一处膨胀|调试只需跟一条线
多 Agent::并行能压耗时|消息契约要自己定|归因与标注成本抬得快
:::

生活类比：做一份固定套餐是流水线（Workflow）；处理一通说不清诉求的客诉，是一个老练实习生（单 Agent）；要同时出市场调研、法务意见、财务模型，而且三份材料互不通气、各自能被单独审核，才值得成立项目组（多 Agent）。你不会为了「点一杯咖啡」成立项目组。框架层怎么对应这些部件，见[框架六大件](./10-framework.md)。

**继续追问会问到哪**：

1. 「多 Agent 之间怎么传消息？」→ 定显式消息契约（谁给谁、带哪些字段、缺字段怎么办）；共享黑板方便但容易互相覆盖；最怕两个节点互相等对方确认，所以消息也要计预算。
2. 「拆错了会怎样？」→ 错误放大：上游一个节点编了个数据，下游全信，最后没人怀疑源头。所以「独立验证」那条标准一票否决。
3. 「怎么证明拆得值？」→ 同一份评测集分别跑单、多两版，比通过率、耗时、成本三项；凭感觉不算证据，方法见[评测](./11-eval.md)。

## 第 3 题：ReAct / CoT / Plan-and-Execute / Self-Refine 怎么组合

**面试官怎么问**：「你用的是 ReAct 还是 Plan-and-Execute？为什么？」「这四个是不是选一个就行？」——第二句是陷阱，它默认了「四选一」。

**30 秒该答什么**：它们解决的是四个不同问题，工程上是**组合**，不是互斥。CoT 解决「一步想不清」，ReAct 解决「需要边做边看」，Plan-and-Execute 解决「步数多容易跑偏」，Self-Refine 解决「初稿质量不够」。真正要守的原则只有一条：**能用代码确定性检查的，绝不交给模型自审**。

**工程上具体怎么做**：先弄清各自补的是哪个缺口，再谈怎么拼。

| 方法 | 补的缺口 | 代价 / 陷阱 |
|---|---|---|
| CoT 思维链 | 把推理摊开，让复杂一步拆成几步 | 输出更长更贵；推理链写得再顺也不等于事实 |
| ReAct 推理与行动交替 | 用工具结果纠正臆测，观察会改变下一步 | 每轮都要回写观察，轨迹膨胀快 |
| Plan-and-Execute 先计划后执行 | 长任务先有骨架，可中途重规划、预算可控 | 计划本身可能一开始就错，需要有推翻机制 |
| Self-Refine 自我修订 | 对表达质量、完整性做最后一轮打磨 | **模型会重复自身偏见**：它觉得对的地方，再审一遍往往还觉得对 |

第四行是这题的分水岭。为什么模型自审不可靠？因为它审的是「自己生成的分布里最像样的那段」，没有引入任何新信息。让它检查「这句话通不通顺」可以；让它检查「这个金额算错了没」「这个编号存不存在」「这次调用越权了没」，是用一个不确定的组件去验证同一个不确定的组件，错误会原样通过。

所以要立一条规矩，按可判定性分流：

- 格式对不对 → 解析器判，见[结构化输出](./03-structured-output.md)；
- 数字对不对、编号存不存在、有没有越权 → 代码和业务规则判；
- 只有「措辞是否得体、解释是否顺」这类没有客观判据的，才交给模型再过一遍。

一个能落地的组合是这样转的：

:::figure 四种方法拼成的一个可用闭环
@cycle
先出计划|按步调用工具并观察|代码做确定性校验|带着失败信息重规划
:::

也就是：Plan 拆任务 → 每一步 ReAct 调工具 → 输出前代码校验 → 只对表达质量做一次 Self-Refine → 校验没过就带着**错误信息**（不是带着「请再试一次」）回到 Plan 重规划。CoT 不作为独立阶段，而是藏在每一步决策内部。

:::tip 让「反思」有外部信号才有效
别写「请检查上面有没有错」，要写「校验器报了：字段 `amount` 与计算结果不符，差 30，请只修这一处」。**有具体外部信号的修订是收敛的，没有信号的自我欣赏是发散的。**
:::

**继续追问会问到哪**：

1. 「Self-Refine 会不会越改越差？」→ 会。用「只有校验器报错才允许改、最多改 2 次」限住，且每次把旧版存进轨迹便于对比。
2. 「CoT 要不要展示给用户？」→ 内部推理与对外解释分开：给用户的是结论与依据，中间推演留轨迹里做排障。
3. 「计划中途发现错了怎么办？」→ 设重规划触发条件（连续两次校验失败 / 关键工具持续报错），且重规划本身也计入步数预算，否则会无限重来。

## 第 4 题：Function Calling 的真实链路

**面试官怎么问**：「模型说要调 `get_weather`，是不是模型自己把接口调了？」「模型给的参数不合法，你怎么处理？」——第一句几乎能筛掉一半只会调封装好的接口、没看过链路的人。

**30 秒该答什么**：**模型只提出调用意图，它从头到尾没碰过你的数据库和网络**。它输出的是一段结构化的「我想调哪个工具、传什么参数」，真正解析、校验、执行、把结果回填进上下文的，全是宿主程序。这条链路上要过三道闸：参数有效、业务合法、有权限，最后还有一条「不可逆操作不许自动执行」的红线。

**工程上具体怎么做**：把一次调用摊开成五步，每一步都有明确的负责人。

:::figure 一次工具调用真正走过的路
@flow
模型给出调用意图|宿主解析并对照 Schema|权限与幂等校验|执行工具|把观察回填进上下文
:::

1. **意图**：模型按工具描述输出工具名与参数。描述是写给模型看的，让它选得对。
2. **解析与 Schema**：宿主把输出解析成结构，检查必填、类型、枚举、取值范围。这一步是代码做的，不靠模型自觉。
3. **权限与幂等**：查这个用户/这次会话有没有资格做这个动作；给有副作用的动作算幂等键，防止重试重复执行。
4. **执行**：真正调用外部系统，处理超时、报错、返回体过大。
5. **回填**：把结果（**包括错误**）作为一条观察写进状态，下一轮决策才看得见。

:::warn 模型从来没有「执行」过任何东西
把这句刻进脑子里：模型输出的是**申请单**，不是动作本身。很多转行者以为「模型调了函数」，是因为封装把它藏起来了。面试时主动把宿主这一侧讲出来，立刻和背八股的人分开。
:::

三道闸加一条红线，层层递进，每一层都能单独拦下：

| 闸 | 判的是 | 由谁判 | 典型反例 |
|---|---|---|---|
| ① 参数有效 | 类型、必填、范围、枚举 | Schema 校验代码 | 金额字段给了个字符串 |
| ② 业务合法 | 参数合规但业务上不成立 | 业务规则代码 | 退一张不存在的订单、往已注销账户转账 |
| ③ 有权限 | 这个人/这次会话能不能做 | 权限表、最小权限 | 普通角色调到了管理接口 |
| ④ 不可逆红线 | 即便前三关全过，能不能自动放行 | 二次确认 / 人在回路 | 删库、真实转账、对外发邮件 |

注意这四个不是并列的：`参数有效 ≠ 业务合法 ≠ 有权限 ≠ 可以自动执行不可逆操作`。Schema 只能判第一层，判不了「这笔退款合不合规」；权限过了也不代表「删掉全表」这种动作可以让循环自己按下去。生活类比就是填报销单：你（模型）只填了「报销 500 元」这张单子，财务系统（宿主）依次查格式、查制度、查你的报销权限、超额度还要领导签字——**你填单子，不等于钱到账**。链路细节见[工具调用](./06-tool-calling.md)，权限分级见[安全与护栏](./12-safety.md)。

**继续追问会问到哪**：

1. 「模型输出的参数格式坏了怎么办？」→ 不执行，把「解析失败、缺哪个字段」作为观察回填让模型改，但这次重试必须计入预算，否则坏输出能拖出死循环。
2. 「Schema 该写多细？」→ 描述写给模型看（让它选对工具）、校验写给代码看（让它拦住坏参数），两份别混成一份。
3. 「工具返回特别大，怎么回填才不炸上下文？」→ 只回传必要字段、截断长文本、大对象外置留引用，做法在[上下文工程](./07-context.md)。

## 第 5 题：工具协议解决什么，又不解决什么

**面试官怎么问**：「你们接工具用了统一的接入规范吗？它到底解决了什么问题？」「工具一多，模型就选错，怎么办？」——这题考的是你能不能分清「模型侧」和「应用侧」。

**30 秒该答什么**：工具协议主要解决的是**应用侧**接线问题，不是让模型更会调工具。模型侧要解决的是「能不能把调用意图稳定地表达出来」，那是结构化输出那一层的事；协议解决的是「有哪些能力、怎么描述、怎么鉴权、怎么传输、怎么审计」的标准化发现与接入。它把 N 个工具对 M 个应用的适配成本，从 N×M 降到 N+M。工具多了要分层路由、按需展示；而且服务端同样是一条权限边界，必须独立鉴权与审计。

**工程上具体怎么做**：先做一道算术题，这是「为什么会这样」的关键推导。

没有统一规范时，每个应用都要给每个工具写一套专用胶水代码：N 个工具 × M 个应用 = N×M 份适配。工具一多，光维护这些胶水就够呛。有了统一规范后，工具按规范暴露一次（N 份），应用按规范接一次（M 份），总共 N+M 份。**协议不生产任何能力，它省的是接线成本**——就像插座标准不生产电器，它只规定插头长什么样，于是电器厂和插座厂可以各干各的。

协议上常见的能力，抽象成三类原语就够用了：

:::figure 工具协议站在哪一层
@stack
模型侧::把「想调什么、参数是什么」稳定表达出来，靠结构化输出契约
协议层::统一能力的发现、描述、鉴权与传输格式，省下接线胶水代码
应用与服务端::真正执行、独立鉴权、限流与审计，是最后一道权限边界
:::

三类原语分别是「读」「写」「怎么干」：

- **数据类原语（读）**：查文档、查记录、取配置，作用是给模型补上下文，通常只读、风险低。
- **动作类原语（写）**：下单、发信、改状态，会改变外部状态，必须走第 4 题那三道闸。
- **模板类原语（怎么干）**：可复用的任务骨架与检查单，把「处理退款先查单、再核额、再走审批」这类流程固化下来，减少模型每次自由发挥。

接着答「工具一多选错」：别把上百个工具描述全塞进上下文。原因有三——描述本身占预算、候选越多选择越难、无关工具还会诱导误调。做法是**分层路由 + 按需展示**：先用一次轻量判断把请求分到某个领域组，本轮只把该组十来个工具带进去；随着轨迹推进再动态换组。这跟[上下文工程](./07-context.md)里的预检路由是同一套思路。

最后补一句很多人漏掉的：**服务端同样是权限边界**。绝不能因为「调用是从本地客户端发起的」就信任它带过来的用户身份，服务端要独立鉴权、限流、记审计日志。插头标准不保证电器安全，安全靠的是保险丝。相关背景见[框架与适配层](./10-framework.md)。

:::quote
协议统一的是「怎么接」，不是「能不能信」。接线成本和信任边界，是两笔账。
:::

**继续追问会问到哪**：

1. 「工具描述到底写给谁看？」→ 给模型看的描述负责「选得对」，给代码看的校验负责「拦得住」，别指望一段描述兼两份职。
2. 「几十个工具怎么不把上下文撑爆？」→ 分组路由、按需展示，再进一步可以用检索式挑工具：先按语义检索出候选工具，只把候选带进去。
3. 「统一接入会不会带来新风险？」→ 会：工具描述本身可能被夹带注入内容、权限边界容易因为「反正有协议」而后移、审计缺口变大。所以描述要做来源标记，服务端鉴权不能省，见[安全与护栏](./12-safety.md)。

## 第 6 题：工具超时、死循环、高风险操作怎么兜底

**面试官怎么问**：「工具调用超时了你怎么处理？会不会重复扣款？」「Agent 停不下来怎么办？」「模型说它快好了，你信吗？」——这题是十道里最见工程功底的一道。

**30 秒该答什么**：先别急着重试，**先判断失败发生在哪个阶段**。有副作用的调用超时，不等于没发生：很可能是服务端已经执行完、回包丢了。所以要用幂等键加状态对账，查清楚再决定重试还是采信旧结果。停不下来靠三重预算兜底：步数抓来回拉扯、成本抓偷偷烧钱、墙钟时间抓单步卡死，三者抓的是不同失控形态；再叠一层重复动作检测判断状态有没有收敛。高风险、不可逆动作一律不自动放行。

**工程上具体怎么做**：把「超时」拆成五个阶段，含义完全不同。

:::figure 一次调用超时，可能停在这五处
@flow
还没发出去|请求在路上|服务端执行中|回包在路上|结果回填时
:::

前两段超时，动作确实没发生，可以重试；中间「服务端执行中」和「回包在路上」最要命——**动作已经落地，客户端却只看到超时**。这时盲目重试就是第二次下单、第二次扣款。所以正确顺序是：发起时带一个由「工具名 + 参数」算出的稳定幂等键；服务端拿它去重并记账；超时后先拿这个键去查账（我这边到底记没记上），再决定重试还是直接采信。生活类比就是刷卡没出小票：正确做法不是再刷一次，而是先查银行流水。

三重预算为什么不能只留一个？因为三种失控在指标上长得不一样：

| 预算 | 抓的失控形态 | 只留它会漏掉什么 |
|---|---|---|
| 步数 | 反复试错、来回拉扯 | 一轮里疯狂调工具、或每步换参数绕过去重 |
| 成本 | 每步换点参数、不重复但疯狂消耗 | 步数没超但单价极高的调用 |
| 墙钟时间 | 单次调用卡死、下游假死 | 步数和成本都正常，就是干等不动 |

再加**重复动作检测与状态收敛**：按幂等键计数，同一动作连续出现几次就判定「状态没朝目标前进」。但要注意它能被「每次换个参数」骗过去，所以必须和成本预算配合。更本质的判据不是「动作一不一样」，而是「状态有没有离目标更近」——这也是为什么轨迹里要存每一步的观察，而不只是存动作名。

高风险操作单独一条规则：删除、真实转账、对外发送这类不可逆动作，不因「模型很有把握」就自动执行，要么二次确认、要么人在回路、要么先写「待执行」单据再异步处理。设计目标是**模型被完全带偏时，损失仍有上界**，而这个上界由权限、预算和确认决定，不由提示词决定。

### 把上面这些写成一段能跑的代码

下面这份脚本只用 Python 标准库，不联网、不调模型、不需要任何账号。它把三重预算、重复动作检测、结构化轨迹、幂等键与状态对账全塞进一个最小循环里，并且用三个场景分别演示「正常收敛」「原地打转」「偷偷烧钱」。复制保存成 `loop_demo.py`，直接运行即可。

:::steps 跟着跑一遍
1. 新建文件 `loop_demo.py`，把下面整段代码原样粘进去。
2. 在命令行执行 `python loop_demo.py`（不需要安装任何东西）。
3. 看三段输出：第一段自然完成，第二段被重复动作检测拦下，第三段被成本预算拦下。
4. 把 `Budget(max_cost=2.0, max_steps=20)` 里的数值改一改，观察判定怎么变。
:::

```python
"""最小 Agent 循环：三重预算 + 重复动作检测 + 结构化轨迹 + 幂等键。
只用标准库，不联网、不调模型。保存为 loop_demo.py 后运行：
    python loop_demo.py
"""
from dataclasses import dataclass, field
from typing import Callable
import hashlib
import json
import time

# ---------- 1. 幂等键 ----------
def idem_key(tool: str, args: dict) -> str:
    """同一工具 + 同一参数 -> 同一键。超时后靠它对账『到底发生过没有』。"""
    raw = json.dumps({"t": tool, "a": args}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:12]

# ---------- 2. 结构化轨迹 ----------
@dataclass
class Step:
    i: int
    decision: str
    tool: str
    args: dict
    idem: str
    observation: str
    cost: float

@dataclass
class Trace:
    rows: list = field(default_factory=list)
    def add(self, s: Step) -> None:
        self.rows.append(s)
    def dump(self) -> str:
        return json.dumps([r.__dict__ for r in self.rows],
                          ensure_ascii=False, indent=2)

# ---------- 3. 三重预算 ----------
@dataclass
class Budget:
    max_steps: int = 8
    max_cost: float = 3.0
    max_seconds: float = 1.0
    def hit(self, steps: int, cost: float, secs: float) -> str:
        if steps >= self.max_steps:
            return "步数预算"
        if cost >= self.max_cost:
            return "成本预算"
        if secs >= self.max_seconds:
            return "墙钟时间预算"
        return ""

# ---------- 4. 带账本的工具箱（幂等 + 可查账）----------
class ToolBox:
    def __init__(self):
        self.ledger: dict = {}
    def run(self, tool: str, args: dict, key: str) -> str:
        if key in self.ledger:                 # 同一键：不再真正执行
            return "[幂等命中] " + self.ledger[key]
        result = f"{tool}{args} -> ok"
        self.ledger[key] = result             # 服务端记账
        return result

# ---------- 5. 三种决策器，模拟模型不同状态 ----------
def normal(trace: Trace):
    plan = [("查订单", "search", {"q": "订单"}),
            ("核对金额", "verify", {"t": "金额"}),
            ("确认", "finish", {})]
    k = len(trace.rows)
    return plan[k] if k < len(plan) else ("确认", "finish", {})

def spinning(trace: Trace):
    # 模型卡住了，永远重复同一个动作
    return ("再查一次", "search", {"q": "订单"})

def burning(trace: Trace):
    # 每步都换点参数，绕开简单去重，但成本飞涨
    return ("换个词再查", "search", {"q": f"订单-{len(trace.rows)}"})

PLANNERS = {"正常收敛": normal, "原地打转": spinning, "偷偷烧钱": burning}

# ---------- 6. 主循环 ----------
def run(name: str, decide: Callable, budget: Budget) -> None:
    tools, trace, seen = ToolBox(), Trace(), {}
    t0, steps, cost, verdict = time.time(), 0, 0.0, "未触发"
    while True:
        # 每轮开头先验三道预算
        hit = budget.hit(steps, cost, time.time() - t0)
        if hit:
            verdict = f"被「{hit}」拦下"
            break
        decision, tool, args = decide(trace)
        if tool == "finish":
            verdict = "任务完成"
            break
        key = idem_key(tool, args)
        seen[key] = seen.get(key, 0) + 1
        if seen[key] >= 3:                    # 重复动作检测
            verdict = "重复动作，状态不收敛"
            break
        obs = tools.run(tool, args, key)
        cost += 0.8                          # 假设每步花 0.8 个单位
        steps += 1
        trace.add(Step(steps, decision, tool, args, key, obs, round(cost, 2)))
    print(f"\n### 场景：{name}")
    print(trace.dump())
    print(f"判定：{verdict} | 步数={steps} 成本={round(cost, 2)} "
          f"耗时={round(time.time() - t0, 3)}s 账本条目={len(tools.ledger)}")

if __name__ == "__main__":
    run("正常收敛", normal, Budget())
    run("原地打转", spinning, Budget())
    run("偷偷烧钱", burning, Budget(max_cost=2.0, max_steps=20))
```

### 逐行解释

**第 1 段 · 导入。** `dataclasses` 用来声明只存数据的类，`field(default_factory=list)` 保证每个 `Trace` 有自己独立的空列表（写成 `rows: list = []` 会让所有实例共享同一个列表，是经典坑）。`Callable` 只是类型标注。`hashlib`、`json`、`time` 分别负责算哈希、序列化、计时。全部是标准库，没有一行需要安装东西。

**第 2 段 · `idem_key()`。** `json.dumps(..., sort_keys=True)` 先把参数字典按 key 排序再序列化，这样 `{"a":1,"b":2}` 和 `{"b":2,"a":1}` 会得到同一个键——**顺序不同但语义相同的调用，必须算作同一次**，这就是「稳定」二字的含义。再用 `sha256` 取前 12 位当标识。特别注意：键里绝不能塞时间戳或随机数，否则每次重试都算出新键，幂等直接失效。

**第 3 段 · `Step` 与 `Trace`。** 一条轨迹存七样东西：第几步、当时为什么这么决定、调了哪个工具、传了什么参数、幂等键是什么、观察到什么、累计花了多少。`dump()` 用 `r.__dict__` 把每条记录转成字典再 `json.dumps`，`ensure_ascii=False` 让中文原样输出。这份结构同时服务于答辩、排障和评测——**循环写完当天就定轨迹结构**，别等出事再补。

**第 4 段 · `Budget.hit()`。** 三个上限分别对应步数、成本、墙钟秒数，按顺序检查，返回「撞到哪一道」或空字符串（还有余量）。注意 `max_seconds` 要覆盖「单次调用卡死」这种形态：步数和成本都正常、但就是干等，只有墙钟能抓。真实系统里这个值要按业务标定，别照抄这里的 1.0。

**第 5 段 · `ToolBox.run()`。** `ledger` 就是服务端那本账。`if key in self.ledger` 表示这个键已经执行过，直接返回旧结果、不再真正执行——这正是「超时后重试不会重复下单」的实现。`result` 落地前先记账，顺序不能反：万一记完账、返回前崩了，账本里也查得到，对账才有依据。

**第 6 段 · 三个决策器。** 真实系统里这一步是模型输出，这里用规则代替以保证零联网可跑。`normal` 按计划队列走三步后输出 `finish`；`spinning` 永远返回同一个动作，模拟卡住；`burning` 每步把参数里的序号换掉，模拟「绕开去重但持续烧钱」。这三个不是玩具，它们分别对应面试里最常被问的三种失控。

**第 7 段 · `run()` 主循环，逐句看。**

- `tools, trace, seen = ToolBox(), Trace(), {}`：账本、轨迹、以及「每个幂等键出现过几次」的计数器，三个场景各自新建，互不污染。
- `t0, steps, cost, verdict = ...`：记起始时刻、步数、累计成本、最终判定。
- `hit = budget.hit(steps, cost, time.time() - t0)`：**每轮开头先验预算**，而不是出事后才查。因为「已经失控了一轮」和「这轮不许开始」是两回事。
- `if hit: verdict = ...; break`：撞到哪道闸就记下来，退出。注意给的是结构化失败结论，不能把半截结果当成功返回。
- `decision, tool, args = decide(trace)`：拿决策。这里把整条轨迹传进去，对应真实系统里「模型看得到历史」。
- `if tool == "finish": verdict = "任务完成"; break`：显式列出终止动作，别指望模型自己发明退出方式。
- `key = idem_key(tool, args)`：执行前先算幂等键。
- `seen[key] = seen.get(key, 0) + 1` 与 `if seen[key] >= 3`：重复动作检测。阈值取 3 而不是 2，是为了给「带退避的合法重试」留一次余地，别把正常重试误杀。
- `obs = tools.run(tool, args, key)`：真正执行，返回观察（可能是 `[幂等命中]`）。
- `cost += 0.8`、`steps += 1`：更新两项预算计数。
- `trace.add(Step(...))`：把这一步完整落进轨迹，包括观察和累计成本。
- 最后 `print` 三段：轨迹、判定、以及四个汇总数字。其中 `账本条目` 是关键——它揭示「重复动作到底有没有真的执行第二次」。

**第 8 段 · 入口。** `if __name__ == "__main__":` 保证直接运行才执行，被别的文件导入时不会乱跑。三次 `run` 分别给默认预算、默认预算、以及「放宽步数、压低成本上限」的预算——第三个场景特意把 `max_steps` 放到 20，就是为了证明**只靠步数抓不住偷偷烧钱**。

把输出读一遍，三段判定正好对上三种机制：

| 场景 | 判定 | 步数 | 账本条目 | 说明了什么 |
|---|---|---|---|---|
| 正常收敛 | 任务完成 | 2 | 2 | 有 `finish` 且校验通过，闭环自然结束 |
| 原地打转 | 重复动作，状态不收敛 | 2 | 1 | 三次相同键被拦下；账本只有 1 条，说明幂等挡住了重复副作用 |
| 偷偷烧钱 | 被「成本预算」拦下 | 3 | 3 | 换参数骗过了去重，但成本闸照样抓住它 |

第二段的「账本 1 条」值得多想一秒：动作被请求了三次，真正落地的只有一次。这就是超时对账想拿到的效果——**重试可以随便来，副作用只能发生一次**。

:::tip 为什么三重预算缺一不可
看第三段就够了：它步数才 3、每步参数都不同（去重抓不到）、但累计成本已经 2.4 超过上限 2.0。**三种失控在指标上长得不一样，所以要用三把不同的尺子量。** 这段脚本的价值就是把这句抽象话变成能亲眼看到的输出。
:::

**继续追问会问到哪**：

1. 「重试会不会造成重复副作用？」→ 幂等键 + 服务端去重 + 先查账再重试；账本必须落盘，只放内存里进程一重启就全失效，见[从 Demo 到上线](./13-production.md)。
2. 「模型一直说『快好了』怎么办？」→ 不信自述。只信状态与预算：观察里有没有可验证的完成标志、预算还剩多少。自然语言里的乐观不是终止条件。
3. 「预算触发后怎么收场？」→ 返回结构化失败（撞了哪道闸、已走几步、已完成到哪），并保留轨迹供回放；千万别把半截结果包装成成功。

## 第 7 题：记忆分几层，聊天记录为什么不是记忆

**面试官怎么问**：「你们的记忆怎么做的？是不是把聊天记录存库里就行？」「用户改主意了怎么办？」——第一问专门钓「把日志当记忆」的人。

**30 秒该答什么**：聊天记录是**流水**，不是记忆。原样回放既贵又吵，还会把早期一句错结论一直带在身上。记忆至少分四层：工作、情景、语义、程序性；工程上真正要做的是三件事——**写入判定、冲突消解、召回**，而不是「全存下来」。并且非必需信息不得挤占上下文。

**工程上具体怎么做**：先分清四层各管什么。

:::figure 记忆的四层，各管一件事
@stack
工作记忆::当前这一轮正在用的东西，对应上下文窗口，任务一结束就清
情景记忆::哪天发生过什么，带时间与来源，可追溯、可回放
语义记忆::提炼后的稳定事实与偏好，去掉了时间，比如「偏好简洁回答」
程序性记忆::做事的固定套路，能复用不必重想，比如「先查单再核额再走审批」
:::

生活类比：桌上的便签是工作记忆（干完就扔），日记是情景（哪天发生了啥），通讯录是语义（不管哪天记的，号码就这个），骑车不用想是程序性。你不会每天早上把整本日记背一遍再去上班——**「全存下来」叫日志，不叫记忆**。

为什么原样回放会出事？推导一下：早期对话里有个被推翻的旧结论，只要它还在历史里，模型每轮都能看见，就可能重新捡起来用；历史越长，无关内容越挤占本该给当前任务的位置（这正是第 8 题要讲的）。所以记忆的价值不在「存得多」，在「**该出现时才出现、且只有一条**」。

三个工程动作，一个都不能少：

- **写入判定**：不是什么都记。判据是「将来会不会再用、是不是稳定事实、有没有被验证过」。带情绪的、一次性的、没核实的，不写；敏感信息直接不进库。
- **冲突消解**：新事实和旧事实打架时，用代码按规则判（带来源的优先、时间新的优先、或直接标「待确认」而不是悄悄覆盖）。**别让模型自由发挥决定信哪个**。
- **召回**：什么时候取、取哪几条、按什么排序塞回上下文。召回太多等于没压缩，所以要有条数和相关性上限。

一条铁律收尾：**记忆库可以很大，但每轮注入上下文的必须极少**。记忆负责「长期保管」，上下文负责「这一眼能看到什么」，两者分工不能混，见[记忆](./09-memory.md)与[上下文工程](./07-context.md)。

:::ask 停下来想一步
用户第一句说「预算 500」，第十句改成「其实按 800 来」。如果你的系统只是把聊天记录一路累加，模型会看到两个互相矛盾的数字。你打算让谁来决定信哪个？答案应该是**代码按规则判**，不是让模型看着两段文字自己猜。
:::

**继续追问会问到哪**：

1. 「怎么判断一条该不该写？」→ 三条判据：可复用、够稳定、已验证；再叠加一条「不写敏感信息」。
2. 「用户改主意了 / 记忆过期了怎么办？」→ 冲突消解加版本与失效标记，保留旧值可回滚，别物理删除。
3. 「记忆被污染了怎么回滚？」→ 每条记忆带来源、时间与版本，能定位到是哪次写入带进来的，再按版本退回。

## 第 8 题：上下文为什么越聊越笨、越贵

**面试官怎么问**：「多轮之后效果变差、账单变高，怎么解释？怎么治？」「换更大窗口的模型是不是就没事了？」——最后一句是陷阱。

**30 秒该答什么**：不是模型「累了」，是**你把每轮历史都累加回去了**。越贵是因为输入按 token 计费、每轮都要重发前面的历史，累计量近似平方级增长；越笨是因为注意力被摊薄，关键信息淹没在长历史里，早期错话还会被反复引用。治法是先算预算表，再按场景选摘要、裁剪、外置三种压缩策略。

**工程上具体怎么做**：先把「为什么会这样」算清楚，这比背结论有用。

**越贵**：假设第 n 轮要把前 n−1 轮全带上，那么 n 轮下来累计送进去的输入大约是 1 + 2 + … + n，接近 n²/2。**钱不是线性涨的，是随着轮数平方涨的**——这就是为什么「才聊了二十轮」账单就吓人。生活类比：开会不做纪要，每次开会都把之前所有录音重放一遍，越开越慢。

**越笨**：模型对一整段文字的注意力是有限的，塞得越长，分给每个位置的关注就越薄；无关历史还会抢走本该给当前问题的位置；更糟的是早期一句错结论会被后续反复引用，形成错误累积。所以「换更大窗口」只能缓解，治不了根：**窗口变长不等于注意力不摊薄，而且更贵**。

先算账，再动手：

| 上下文组成 | 该占多少 | 处理原则 |
|---|---|---|
| 系统指令与规则 | 固定一小块 | 稳定前缀放最前，可复用、不随轮数涨 |
| 工具描述 | 按需、尽量少 | 分组路由，只带本轮相关的十来个 |
| 召回的记忆 | 极少几条 | 只注入当下用得上的，不把库搬进来 |
| 最近对话与轨迹 | 有硬上限 | 只留最近 k 轮，更早的压缩 |
| 当前用户输入 | 完整保留 | 放最后，离模型最近权重最高 |
| **给输出预留的余量** | 必须留出 | 忘了留，模型会写到一半被截断 |

一句话公式：**总量 − 已用 = 可用余量**，所有压缩动作都是在这个余量下做取舍。

:::figure 上下文预算怎么算出来
@flow
列出上下文的组成部分|给每块定上限|总量减已用得余量|按余量选压缩策略
:::

三种压缩策略，各自适用不同场景，别一招用到底：

| 策略 | 怎么做 | 适合 | 风险 |
|---|---|---|---|
| 摘要 | 把旧轮次压成几句话 | 话题连续、细节不重要的长聊 | 容易丢掉一个关键数字 → 结构化字段单独保真，不进摘要 |
| 裁剪 | 按规则丢最老的 / 丢低价值的 / 只留最近 k 轮 | 历史与当前任务无关 | 可能丢掉后面还要用的约束 → 系统规则不参与裁剪 |
| 外置 | 细节挪到外部存储，需要时召回几条 | 细节多但用得少 | 多一次检索、可能召不回 → 留零召回兜底 |

实践中是**组合**着来：先裁剪掉明显无关的，再把剩下的旧轮次做摘要，原文外置留档以备回溯。完整做法见[上下文工程](./07-context.md)。

**继续追问会问到哪**：

1. 「摘要把关键数字弄丢了怎么办？」→ 金额、编号、日期这类结构化字段单独存、原样注入，绝不交给摘要重写。
2. 「怎么知道压缩没伤效果？」→ 用同一份评测集跑压缩前后，比通过率；别凭「读起来还行」判断，见[评测](./11-eval.md)。
3. 「长窗口模型是不是就不用管了？」→ 不是。注意力摊薄仍在、成本更高、而且很多内容本来就不该带；顺序永远是先减工具数量、再压历史、最后才考虑换模型。

## 第 9 题：RAG 怎么从「搜得到」走到「答得准」

**面试官怎么问**：「我们搜出来看着都对，但答案就是不准，怎么调？」「把返回条数调大点行不行？」——第二句是陷阱，调大往往更糟。

**30 秒该答什么**：「搜得到」是检索指标，「答得准」是生成指标，中间还隔着排序、上下文组织、拒答三道关，调大返回条数只会塞进更多无关片段、摊薄注意力还更贵。要走完这条链：切片策略 → 稠密加稀疏混合检索 → 倒数排名融合 → 粗排加精排 → 查询改写 → 溯源与拒答阈值 → 零召回兜底。

**工程上具体怎么做**：顺着一条流水线走，每一站解决一个具体的错。

:::figure 从一句提问到一句带出处的回答
@flow
查询改写|混合检索与倒数融合|粗排加精排|组装上下文并留出处|生成或按阈值拒答
:::

**第一站：切片三策略。**

| 策略 | 做法 | 取舍 |
|---|---|---|
| 固定长度 | 按固定字数切 | 简单可预测，但常在句子中间切断，语义不完整 |
| 语义切片 | 按段落、标题、句子边界切 | 语义完整，但块大小不均、实现稍复杂 |
| 层级切片 | 小块用于命中，同时保留父块 / 摘要块 | 实现最复杂，但兼顾命中率与上下文完整 |

为什么「层级」要小块检索、大块生成？推导一下：块越短，语义越聚焦，检索命中越准；但短块本身缺上下文，直接喂给模型容易断章取义。所以命中后**回溯到它的父块**再送进上下文，鱼和熊掌就都拿到了。这一步的基础见[检索增强](./08-rag.md)。

**第二站：稠密 + 稀疏混合检索，以及倒数排名融合。** 稀疏检索（关键词加权）抓专有名词、编号、精确词，但换个说法就漏；稠密检索（语义向量）抓「意思相近」，却可能漏掉一个精确编号。两者盲区不重叠，所以一起用。融合时别把两路分数直接相加——**两路分数的量纲不同，加起来没有意义**，要按名次投票：

`score(d) = Σ 1 / (k + rank_i(d))`

`rank_i(d)` 是文档 d 在第 i 路结果里的名次，k 是个常数（常取 60 左右），用来压低「第一名」的绝对优势。生活类比：一个人按关键词找、一个人按意思找，两人各排一份候选名单，**谁在两份名单里都靠前谁优先**，而不是比各自打的分。

:::tip 为什么「按名次」比「按分数」稳
稀疏那路可能给 12.7 分，稠密那路给 0.86 分，直接相加等于让其中一路说了算；但「第 2 名」「第 3 名」是可比的。倒数排名融合不关心绝对分，只关心「排在第几位」，天然免疫量纲差异。
:::

**第三站：两阶段粗排 + 精排。** 先用便宜的检索从海量资料里捞几十条（粗排），再用更重的打分给这几十条重新排序、取前几（精排）。为什么分两段？因为贵的打分**不可能对全库做**，成本不允许；先便宜地缩小候选集，是把钱花在刀刃上。

**第四站：查询改写四类**，专门治「用户问得含糊」：

1. **补全指代**：把「它多少钱」补成上文提到的产品名，否则检索串里只有一个代词。
2. **拆分多问**：一个问题里藏了三个子问题，拆开各查再合并，别指望一次检索全命中。
3. **同义扩展**：用户说「退钱」，补上「退款 / 返还 / 撤销」等说法，缩小口语与书面语的落差。
4. **反向改写**：把问句改写成陈述式检索串（或先生成一段「假想答案」再去比对），让查询和资料的文体更接近。

**第五站：溯源与拒答阈值。** 每句话都要能指回「哪几段支撑了它」；证据得分低于阈值就明确说「资料里没有」，而不是硬编一段。**能拒答比答得全更重要**，因为大多数幻觉事故都来自「弱相关时硬答」。这一站是「答得准」的最后一道闸，也是敢上生产的前提，配合[安全与护栏](./12-safety.md)看更清楚。

**第六站：零召回兜底。** 一条都没捞到时，别让模型自由发挥：走固定话术、或转人工、或降级到通用能力，并记一条日志用于补语料、监控零召回率。

**继续追问会问到哪**：

1. 「怎么定位是检索错了还是生成错了？」→ 分开评测：先看召回的证据里**有没有**正确答案，有而答错是生成问题，没有是检索问题。口径见[评测](./11-eval.md)。
2. 「切片大小、返回条数怎么定？」→ 用评测集扫参数，别拍脑袋；调大条数常因塞进无关片段反而变差。
3. 「资料更新了 / 有过期版本怎么办？」→ 增量索引加版本与生效日期，重排时用代码判版本，不靠提示词；过期片段要有失效标记。

## 第 10 题：怎么证明改了一版没变差

**面试官怎么问**：「你优化了一版提示词 / 加了个机制，怎么证明没把别的场景搞坏？」「你怎么衡量一个 Agent 好不好？」——这题决定面试官把你归到「跑过 Demo」还是「能交付系统」。

**30 秒该答什么**：靠评测集加回归门禁，不靠「我试了几个例子感觉更好」。断言写**性质**而不是写死文本（能不能解析、字段齐不齐、有没有越权、有没有引用出处），新版本全量跑评测集、关键指标不许低于基线，不达标就卡住发布。结果评测管「对不对」，轨迹评测管「错在哪一步」，两者都要；而且**先有评估再加复杂度**，不然你连新机制有没有用都不知道。

**工程上具体怎么做**：四件事，按顺序做。

**① 评测集**：一批固定输入 + 期望满足的性质，覆盖四类样本——典型场景、边界情况、对抗输入（诱导越权、夹带注入）、以及**历史上踩过的每个坑**（每个 bug 固化成一条用例）。要版本化、能重复跑，从二三十条起步持续攒坏例。

**② 性质断言，而非文本断言**：别断言「输出必须等于『已为您预订成功』」，措辞一变就误报，而且答对了换个说法也算失败。要断言的是性质：

| 别这么断言 | 改成这样的性质断言 |
|---|---|
| 输出等于某句话 | 是合法 JSON，且必填字段齐全 |
| 答案包含某段原文 | 每个引用编号都能在召回片段里找到 |
| 回复里有「无法回答」 | 证据分低于阈值时确实没编造具体内容 |
| 模型说「已完成」 | 订单库里真的多了一条记录 |
| 感觉没越权 | 这次轨迹里没有出现越权工具名 |

生活类比：验收快递不是看外包装那句印刷字一不一样，是看「东西到没到、数量对不对、有没有破损」。

**③ 回归门禁**：新版本上线前全量跑评测集，通过率、越权次数、平均步数、平均成本几项不许低于基线（允许微小波动，但要有明阈值），不达标就拦下。关键是把它挂进提交 / 发布流程，**靠机器不靠自觉**。方法见[评测](./11-eval.md)与[从 Demo 到上线](./13-production.md)。

**④ 结果评测与轨迹评测分工**：

:::figure 结果评测与轨迹评测，各管一段
@compare
结果评测::只问最终答案对不对|贴近用户真实体感|说不清错在哪一步
轨迹评测::检查每一步决策与工具|能定位崩在哪一环|标注贵且易误判不同但合理的路径
:::

- **结果评测**：看目标有没有达成，贴近用户体感，但失败时只知道「错了」，不知道哪一步错。
- **轨迹评测**：看每一步决策、工具选择、参数是否合理，能定位崩点；代价是要人标注，而且「条条大路通罗马」时容易把合理但不同的路径误判为错。

结论是两者都要，但用法不同：**用结果评测卡门禁，失败了再调轨迹做归因**。

最后一条最容易被跳过，却最值钱：**先评估，再加复杂度**。每加一个机制（多 Agent、记忆、重规划、自我修订）之前，先有一版能跑的基线评测；否则新机制到底带来了提升还是悄悄拖慢了、烧钱了，你完全没有证据。

:::quote
没有评测，所有「优化」都是玄学；而 Agent 的随机性和长轨迹，会让直觉比在普通后端里更不可信。
:::

**继续追问会问到哪**：

1. 「模型输出不稳定，怎么比？」→ 固定采样参数、每条样本多次运行看**通过率**而不是单次结果，比较的是分布不是某一次。
2. 「评测集会不会被调过拟合？」→ 会。留一份不公开的盲测集，只在最终验收时用，平时照着可见集优化。
3. 「离线评测过了，线上还是出问题？」→ 线上轨迹要留存回放、抽检、监控指标漂移，把线上坏例持续回流进评测集，形成闭环。

## 十一、转行者专属三问

这三问几乎必问，而且问的不是知识点，是「凭什么信你」。和[面试追问链](./15-interview.md)里那版偏简历表达的三问不同，这里三问更偏**技术底气**，可以叠着准备。

| 问题 | 别这么答 | 这么答 |
|---|---|---|
| 「你没做过线上 Agent 项目，怎么答这些工程题？」 | 「我看过很多资料」 | 直接打开那段能跑的最小循环：三重预算、幂等键、结构化轨迹都在里面，讲清「我为什么加成本这道闸」——因为只留步数抓不住偷偷烧钱。**能跑的代码 + 说得出取舍**，比编一段经历可信得多。 |
| 「问到你没用过的框架 / 协议怎么办？」 | 硬背几个名字，或干脆说没听过 | 先讲这一层要解决的问题（比如「统一发现与接入，省的是 N×M 的接线成本」），再讲你会怎么用标准库实现一个最小版本，最后补「具体工具上手快，因为链路是通的」。**回到原理层，不装**。 |
| 「零基础最该先补哪一块？」 | 「先把概念都过一遍」 | 先跑通一个「决策—工具—观察—校验」的最小循环，并且给它写一条代码可判的验收断言。概念是在改这份代码的过程中长出来的，不是先背下来的。 |

:::tip 转行者最大的优势不是「学得快」
是你原来那套工程本事——拆流程、定契约、做校验、加日志、限重试、控权限、写回归测试——**一项都没作废**。这个岗位八成的工作，是给一个不确定的组件搭这层确定的壳。把原有经验翻译成这套语言，比假装做过项目有用得多，见[写给想转 Agent 开发的你](./00-start-here.md)。
:::

## 十二、15 分钟讲项目的节奏

给你一张掐过表的时间分配。重点是：**把时间花在轨迹和失败上，不是花在架构图上**。架构图谁都会画，一次真实事故怎么定位、怎么补评测用例，才证明你真做过。

:::figure 15 分钟怎么分
@stack
0~2 分::场景与硬约束，一句话说清「绝对不能出什么事」
2~5 分::闭环与数据流，边画边说谁决定下一步，别念名词
5~9 分::拿一条真实轨迹逐步讲，重点讲一次失败与怎么改主意
9~12 分::兜底与评测：三重预算、幂等对账、门禁数据
12~14 分::主动说不足与边界，把话题引到你准备最充分的那条链
14~15 分::留白给面试官追问，别急着收尾客套
:::

每一段面试官在听什么：前两分钟听你有没有**判据**（什么算完成、什么算不能出事）；中间七分钟听你有没有**证据**（轨迹、数字、事故）；最后几分钟听你有没有**分寸**（知道哪里没做好、什么条件下会换方案）。项目素材怎么攒，见[三个能写进简历的项目](./14-projects.md)。

:::ask 想一步
如果把「2~5 分的架构图」压到 1 分钟，多出来两分钟你会放到哪？建议放到「5~9 分的轨迹复盘」——因为架构可以照着图讲，而**一次失败怎么从日志定位到代码第几行，是没法临场编的**。
:::

## 十三、踩坑与边界

把十道题里最容易翻车的边界收个尾，面试时主动提一两条，比等被问出来强：

1. **幂等键里别塞时间戳或随机数**。那就不幂等了，重试每次都算出新键，重复副作用照样发生。
2. **账本要落盘**。只放内存里，进程一重启保证全失效；跨重启的对账要靠持久化加过期时间，见[从 Demo 到上线](./13-production.md)。
3. **超时不等于没发生**。先判断失败在哪个阶段、拿幂等键查账，再决定重试；盲目重试是重复扣款的头号原因。
4. **预算数值按业务标定**。示例里的 8 步、3.0、1.0 秒只是为了跑出对比，照抄到生产会误杀正常任务或拦不住失控。
5. **墙钟预算要覆盖单次调用超时**，而不只是整段会话时长；否则一个卡死的接口能把整轮拖住。
6. **重复检测阈值别太紧**。取 3 而不是 2，是给带退避的合法重试留余地；同时它会被「每步换参数」骗过，必须配成本预算。
7. **预算触发后要给结构化失败结论**，别把半截结果包装成成功，也别让用户只看到一个笼统的报错。
8. **能确定性检查的别交给模型自审**；模型自审会重复自身偏见，格式、数字、权限、编号存在性一律用代码判。
9. **记忆库大不等于每轮都能塞**。非必需信息不得挤占上下文，注入窗口的永远只是极少数几条。
10. **摘要别吞掉结构化字段**。金额、编号、日期单独保真原样注入，不进摘要重写。
11. **拒答阈值不是越低越好**。太低会硬答、太高会滥拒，要用评测集扫出来，见[安全与护栏](./12-safety.md)。
12. **没有评测就别加机制**。每加一层复杂度前先有基线，否则「优化了」三个字没有证据支撑。

:::warn 别把「主动说取舍」演成抬杠
上面每一条加分项的前提，都是你能立刻拿出对应的代码、轨迹或评测数字。**没有证据的「我做过权衡」，比不说更伤**。
:::

## 十四、临走前的自检清单

- [ ] 我能说出 Workflow / 单 Agent / 多 Agent 的四条选型标准

## 三句话小结

1. **闭环是分界线**：模型只负责生成意图，系统负责解析、校验、执行、回填与终止；能交付「可验证的任务结果」，才叫 Agent。
2. **不确定性要关进笼子**：三道闸、三重预算、幂等对账、性质断言、回归门禁——这些不是加分项，是把一个会发挥的组件装进确定系统的骨架。
3. **答到第四层靠取舍不靠名词**：每句话都带上「因为……所以选 A 不选 B，代价是……，什么情况下我会改」，并随时能掏出轨迹、代码和评测数字。

:::quote
面试官从头到尾只在一件事上打分：**当模型不按你想的来时，你搭的那层壳还剩多少管用。**
:::

想继续练，回[手写第一个 Agent 循环](./05-agent-loop.md)把那份循环改成自己的场景，再拿[评测](./11-eval.md)里的方法给它补上二十条用例——能把一条轨迹讲清楚、能把一次改动证明没变差，这十道题就真成了你的东西。

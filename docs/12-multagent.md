# 多智能体：什么时候真的需要拆

多智能体是 Agent 领域最容易被过度使用的设计。教程里「研究 Agent + 写作 Agent + 审阅 Agent」看着很漂亮，上线后往往变成：调试难度翻倍、token 翻倍、出错时不知道是谁的锅。

**先记住结论：单 Agent 跑不稳，拆成多个只会让问题乘以 N。**

## 三个真正该拆的信号

只有出现下面任一瓶颈，才值得拆：

| 信号 | 具体表现 |
|---|---|
| **上下文容量** | 单个 Agent 要同时装下几套互不相关的工具与知识，工具描述就吃掉大半窗口 |
| **职责边界** | 不同动作需要不同权限（检索只读 vs 转账高危），混在一起没法做最小权限 |
| **吞吐 / 隔离** | 某些子任务要独立并发、独立限流、独立降级，不能互相拖死 |

如果只是「任务看起来能分成几步」，用 [04 上下文工程](./04-context-engineering.md) 里的路由 + 状态机就够了。

## 三种拓扑

```
① 主管式 Supervisor
        ┌──────────┐
        │  主管 Agent │ ── 分派 ──→ 检索 / 分析 / 写作
        └──────────┘ ←── 汇总 ──────┘
   优点：可控、易审计   代价：主管是瓶颈，且它得懂所有子任务

② 流水线 Pipeline
   检索 → 分析 → 写作 → 审阅 → 交付
   优点：可预测、好测、好重试   代价：本质更像 Workflow，别硬叫 Agent

③ 对等式 Peer / 群聊
   Agent 之间互相交接、可互相质疑
   优点：适合探索与辩论   代价：终止条件难设，最容易烧钱和死循环
```

**生产系统里 ① 和 ② 占绝大多数。** ③ 更适合研究和实验，上线前必须加硬性的轮数与预算上限。

## 交接：多智能体的真正难点

拆开之后，问题从「模型聪不聪明」变成「状态怎么传」。交接必须带**类型化状态**，而不是一段自然语言：

```json
{
  "task_id": "T-2026-1125-01",
  "from": "research",
  "to": "writer",
  "status": "partial",
  "artifacts": [
    { "type": "citation", "url": "...", "chunk_id": "c-17", "quote": "..." }
  ],
  "known_unknowns": ["毛利率口径未确认"],
  "budget_left": { "rounds": 3, "tokens": 4200 }
}
```

四个字段是必需的：`artifacts`（产物，别让下游重做）、`known_unknowns`（明确没查到什么，防止下游编）、`budget_left`（预算要传递）、`status`（可恢复）。

> 面试加分点：能说出「我们不让 Agent 之间用自由文本聊天，而是传结构化状态对象」。

## 冲突与共识

多个 Agent 结论不一致时的处理顺序：

1. **先看证据**：谁能给出可校验的引用 / 工具结果，谁优先
2. **再看规则**：预先定义裁决策略（主管裁决 / 多数投票 / 置信度加权）
3. **最后才升级**：仍冲突就交人工，别让模型无限辩论

「让两个 Agent 互相说服对方」是很贵的，而且没有收敛保证。

## 共享状态的坑

- **共享一份大上下文**：每个 Agent 都把全部历史塞进去，成本随数量线性甚至平方增长
- **各自记各自的记忆**：同一事实在不同 Agent 里版本不一致
- 做法：**单一事实源（state store）+ 按需投影**，每个 Agent 只拿自己需要的视图

配套要有：全局 trace（一次请求一条链，跨 Agent 串起来）、按 Agent 的成本与耗时聚合、以及一次「全局最大轮数」的硬熔断。

## A2A 与 MCP 的分工

| | 解决什么 | 别混为一谈 |
|---|---|---|
| **MCP**（[MCP 与协议生态](./06-mcp-protocol.md)） | Agent ↔ 工具 / 数据源 | 不是 Agent 之间的协议 |
| **A2A** | Agent ↔ Agent 的发现、交接、状态传递 | 不是单 Agent 内部编排 |

只有当系统里真的存在**独立部署、彼此需要发现**的 Agent 时，A2A 才有意义。同一个进程里的几个节点，用函数调用就行。

## 面试追问链

```
「你做了多智能体吗？」
→ 「为什么不用单 Agent？瓶颈具体是哪个？」
→ 「Agent 之间怎么传状态？冲突了怎么裁决？」
→ 「全局 token 和轮数怎么控制？」
→ 「哪个 Agent 出错时，怎么定位到具体那一步？」
```

能主动说「我们评估后没上多智能体，因为三个瓶颈都不成立」，通常比硬讲一个群聊架构得分更高。

## 验收点

- 能说出三个该拆的信号，并判断一个给定场景该不该拆
- 能画出主管式拓扑并写出交接状态对象
- 能回答「两个 Agent 结论冲突怎么办」

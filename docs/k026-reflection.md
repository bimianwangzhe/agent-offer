# 反思与自我修正

## 场景提问

你让程序产出一份符合规则的配置文件：名称不能空、重试次数只能是 1 到 5、运行方式只能取两个固定值之一。第一版交上来三个字段全错。你说「再试一次」，它又原样交了一遍；你说「先自己检查下哪里不对」，它回了一句「我仔细复核过，没有问题」，可校验器一跑，还是那三条错。你让它「改」，这回它确实动了，却把上一轮刚改对的名称又写回空值，来来回回三遍，错处数量一点没少。明明每一步都有「检查」「修改」这些字眼，为什么结果始终不往前走？

## 破误解

**不是重试次数不够，是把「再做一遍」当成了「反思」，缺了由外部证据指出、具体到某一处的修改点。**

先把词说清。反思（Reflection）指的是：在拿到一版结果之后，单独用一步「评估」写下「哪里不对、为什么不对、下一轮具体改哪一处」，再把这个结论喂回产出环节，形成「产出 → 校验 → 反思 → 修正」的循环。它和「重试」的分界非常硬：重试不改变下一轮的输入，指望换个随机结果碰对；反思必须改变下一轮的输入，而且这个改变要有依据。它和「自查」的分界同样硬：裁判必须是外部的校验器、断言或测试用例，不能是产出方自己说「我觉得没问题」——让生成的一方给自己打分，很容易两边一起确认同一个错误，越检查越笃定。

所以一次有用的反思至少有三样东西。第一是外部证据：校验器要返回可读的问题清单，比如「名称栏为空」「次数 9 超出 1 到 5」「方式不在允许的取值内」，而不是一句笼统的「不合格」。第二是具体修改点：把每条问题翻成一条能执行的指令，标明改哪个字段、改成什么，一次只改一处，而不是「重写一遍」。第三是收敛约束：通过即停、轮数有上限、已经改对的字段不能回退。少了任何一样，都会退化成场景里那三种空转。还要补一句常被忽略的：反思本身也可能改错，甚至把对的地方改坏，所以每轮修正之后都必须重新跑一遍完整校验，不能因为「刚反思过」就默认这版没问题。这套循环其实就是 [决策—行动—观察闭环](./k023-decision-loop.md) 在「产出质量」上的一个特例：校验结果就是观察，反思把它变成了下一轮的决策依据；和 [自动修复](./k019-auto-repair.md) 相比，自动修复偏向按固定规则修补结构，反思更强调把一段可读的批评翻成可执行的改动，语义层面的问题也能覆盖。

## 生活类比

把它想成会计填一张申报表，再交给复核员过一遍。复核员不负责重填，他的活儿是拿红笔圈出问题，而且圈得具体：「名称栏空着」「次数填了 9，规定是 1 到 5」「类型那格写了不允许的值」。会计也不会把整张表撕了从头填，更不会看都不看红笔就再抄一遍；他按圈注一条条改：先补名称，再改次数，再改类型，每改完一轮就把表重新递回复核员，直到本子上一个红圈都没有。

对应关系要一句句对上：红笔圈注是校验器返回的问题清单，它来自复核员、不来自填表人的自我感觉；「把次数改成 3」是反思翻出来的具体修改点，指名了字段与目标值；只动那一格、其余照旧，是「一次只改一处、已改对的不回退」；每轮重新递回复核，是「修正后必须重新全量校验」；复核员说「可以了」，是停止条件。比喻里还藏着三个反面教材：一是复核员只写「不合格」三个字，会计根本无从下手，对应反馈太笼统；二是会计每轮把整张表重填，很可能把上一轮改对的又写错，对应「改动不单调」；三是让填表人自己给自己复核，那等于没有复核，对应自评代替外部校验。还有一层：复核员手里得有明确规则才知道什么算错，正如校验器必须先有可判定的条件，反思才有对象。

## 自绘示意图

:::figure 反思循环的四个节点
@cycle
产出结果|外部校验|写下错处|定点修正
:::

回箭头的关键在于：回到「产出结果」时，手里的输入已经和上轮不同——多了那条「改哪个字段」的指令。四格里「外部校验」和「写下错处」必须分开：前者只负责判对错、给事实，后者负责把事实翻译成动作；合成一格，就又变成「模型自己说哪里不对」了。

:::figure 一条有用反思该写清的四件事
@stack
证据::校验器指出的那一条具体问题
定位::错在哪个字段或哪一步
改法::改成什么值、由谁来执行
验收::下一轮用哪条判据确认改好
:::

四行里最容易缺的是「验收」。没有它，改完之后没人说得清「这条到底算不算改好了」，下一轮又会把同一个问题再报一遍，或者干脆跳过验证。把四件事写成结构化的一条记录，还能留下「第几轮、因为什么、改了什么」的痕迹，这和 [压缩后校验](./k048-compression-verify.md) 里「改动之后要重新确认」是同一套要求。

:::figure 重试与反思的差别
@compare
原样再来一次::输入不变|靠碰运气|旧错反复出现
按证据定点改::每轮输入变|改哪处有依据|逐步收敛
:::

左边不是「没做事」，它也很忙，只是每轮的局面一模一样；右边多出来的成本是一次外部校验加一条翻译，换来的是错处数量一轮比一轮少。判断有没有真反思，看相邻两轮的输入是否因为上轮的证据而改变就够了。

## 层层追问

:::ask 那如果校验器只说「不合格」，或者压根没有校验器呢？
:::

那要先补的是「可判定的条件」，而不是急着加反思轮数。校验器得把规则拆成一条条能当场验证的项：字段在不在、类型对不对、数值在不在范围内、取值属不属于允许集合、几处之间是否互相一致，失败时明确指出是哪一条没过。这样反思才有下手处。没有现成校验器时，就自己把规则写成断言或属性检查——注意这仍然是**独立于产出方**的一段代码，不是让产出方顺带自评一句。格式层面可对照 [结构校验](./k017-structure-check.md)，含义与业务规则层面对照 [语义校验](./k018-semantic-check.md)，把「应该满足什么性质」写成可复用的检查，见 [属性断言](./k088-property-assertion.md)；失败信息怎么措辞才能被下一轮直接利用，则和 [错误如何回喂](./k029-error-feedback.md) 是一回事。再往下一层要留个心眼：校验器本身可能不全。它查得出「次数是整数且在 1 到 5」，未必查得出「这个次数对当前任务其实偏大」；查得出格式，未必查得出内容自相矛盾。所以「通过了校验」只等于「没触发已写的规则」，不等于「真的对了」，重要产出仍要留抽样复核或另一个视角的检查，别把校验器当成真理。

:::ask 那如果越改越糟，或者几轮之间来回打转呢？
:::

这是反思最典型的两种失控，根源都在「改动不收敛」。第一种是每轮把整版推倒重写，于是上一轮修好的字段被重新摇骰子，错处数量忽上忽下；对策是让改动最小化且单调：一次只动被点名的那一处，已通过的字段冻结，每轮只做增量修正。第二种是两条批评互相打架，比如一轮说「名称要短」、下一轮说「名称要完整」，程序在两者之间来回摆；对策是给反思结论留痕，能看出「这条修改是回应哪一条问题」，并检查同一字段是不是被反复改回旧值。两种都要配轮数上限与「连续几轮问题清单没变短就退出」的判定，见 [停止条件](./k028-stop-conditions.md)；有上限才不会把「反思」变成无限循环。还有一层更根本的：如果批评本身来自另一个生成式判断，而不是确定的校验器，那它也可能编造问题、把对的地方指成错的，于是修完反而更糟——这类自评的可信度边界在 [模型作为裁判](./k090-llm-judge.md) 里讲得更细，凭空生出的错处则和 [幻觉](./k005-hallucination.md) 同源。所以顺序要记牢：先有确定的外部证据，再谈反思；反思完必须重新校验，且校验通过不等于万事大吉。反复出现同一类错处时，把它收成固定用例回填检查集，是 [坏例闭环](./k093-badcase-loop.md) 要做的事。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一份本地字典模拟待产出的配置，用一个确定性的校验器返回可读问题清单，再把每条问题翻成「改哪个字段、改成什么」的指令，循环修正直到通过。另外做一个「原样重试」的对照，验证只重交不改输入确实过不了。结尾用一组断言检查逐轮收敛、每轮只改一处、已修字段不回退与轮数上限。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json


ALLOWED_MODES = ("fast", "safe")


def validate(cfg):
    """外部校验器：返回可读的问题清单，空清单表示通过。"""
    issues = []
    if not isinstance(cfg.get("name"), str) or not cfg.get("name"):
        issues.append("name 缺失或不是非空文本")
    r = cfg.get("retries")
    if not isinstance(r, int) or isinstance(r, bool) or not (1 <= r <= 5):
        issues.append("retries 必须是 1 到 5 的整数")
    if cfg.get("mode") not in ALLOWED_MODES:
        issues.append("mode 不在允许的取值内")
    return issues


def reflect(issues):
    """把校验器的话翻成一条具体、可执行的修改指令。"""
    for issue in issues:
        if "name" in issue:
            return {"field": "name", "value": "worker"}
        if "retries" in issue:
            return {"field": "retries", "value": 3}
        if "mode" in issue:
            return {"field": "mode", "value": "safe"}
    return None


def apply(cfg, patch):
    """只改指令指明的那一个字段，其余原样保留。"""
    new = dict(cfg)
    new[patch["field"]] = patch["value"]
    return new


def generate_with_reflection(initial, max_rounds=5):
    """校验—反思—修正反复推进，直到通过或撞上限；每轮留痕。"""
    cfg = dict(initial)
    trace = []
    for i in range(1, max_rounds + 1):
        issues = validate(cfg)
        trace.append((i, dict(cfg), list(issues)))
        if not issues:
            return cfg, trace
        patch = reflect(issues)
        if patch is None:
            return cfg, trace
        cfg = apply(cfg, patch)
    return cfg, trace


def blind_retry(initial, rounds=4):
    """对照：每轮原样重交，输入一点不变。"""
    for _ in range(rounds):
        if validate(dict(initial)) == []:
            return True
    return False


def main():
    initial = {"name": "", "retries": 9, "mode": "turbo"}
    final, trace = generate_with_reflection(initial)
    checks = []
    checks.append(("最终版本通过全部校验", validate(final) == []))
    checks.append(("最终三个字段都修对了",
                   final == {"name": "worker", "retries": 3, "mode": "safe"}))
    checks.append(("初始版本本来就通不过", validate(initial) != []))
    checks.append(("恰好四轮收敛且末轮无问题",
                   len(trace) == 4 and trace[-1][2] == []
                   and all(t[2] for t in trace[:-1])))
    changes_ok = all(
        sum(1 for k in set(trace[i][1]) | set(trace[i + 1][1])
            if trace[i][1].get(k) != trace[i + 1][1].get(k)) == 1
        for i in range(len(trace) - 1))
    checks.append(("相邻两轮只改了一个字段", changes_ok))
    checks.append(("每轮反思指令都来自当轮问题",
                   reflect(trace[0][2])["field"] == "name"
                   and reflect(trace[1][2])["field"] == "retries"
                   and reflect(trace[2][2])["field"] == "mode"))
    checks.append(("已修好的字段没有被改回去",
                   trace[1][1]["name"] == "worker" and final["name"] == "worker"))
    checks.append(("原样重试始终过不了", blind_retry(initial) is False))
    limited, short = generate_with_reflection(initial, max_rounds=2)
    checks.append(("反思也有轮数上限", len(short) == 2 and validate(limited) != []))
    checks.append(("结果可序列化并读回一致",
                   json.loads(json.dumps(final, ensure_ascii=False, sort_keys=True)) == final))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `validate` 是**独立于产出方**的外部校验器，逐条检查三件事：名称是非空文本、次数是 1 到 5 的整数（特意用 `isinstance(r, bool)` 排除布尔值混进来）、方式属于允许集合。它返回的是可读的问题清单而不是一个真假值，因为反思需要「哪条没过」才能下手。
2. `reflect` 把问题清单翻成一条修改指令：按清单顺序取第一条能识别的问题，返回「改哪个字段、改成什么」。它就是「红笔圈注 → 具体动作」那一步，刻意做成一条只含 `field` 与 `value` 的小字典，避免出现「重写一遍」这种无法执行的模糊结论。
3. `apply` 复制一份当前配置，只覆盖指令指明的那个字段。复制而不是原地改，是为了让上一轮的版本完整留在 `trace` 里，后面才能逐轮比对「到底动了几处」。
4. `generate_with_reflection` 是主循环：先校验，把「轮次、当前版本、问题清单」记进 `trace`；没有问题就立刻返回（通过即停）；有问题就反思出一条指令、定点修正，再进入下一轮。`max_rounds` 是硬上限，防止问题清单不变短时无限转。
5. `blind_retry` 是对照组：每轮都用 `dict(initial)` 原样重交，输入从头到尾不变。它存在的意义是证明「多试几次」在这类确定性错误上毫无作用——错误是规则性的，不靠碰运气消失。
6. `main` 先断言最终通过且三个字段都修对、初始版本确实通不过、恰好四轮收敛且末轮问题清单为空、前三轮都有问题。其中 `changes_ok` 逐轮比对相邻版本，要求差异恰好一个字段，这正是「改动最小化、已修字段不回退」的可验证形式；再断言三轮的反思指令依次对应 name、retries、mode，说明每条修改都来自当轮的证据。
7. 最后验证「原样重试过不了」、`max_rounds=2` 时确实停在上限且仍未通过、以及结果能用 `json`（JavaScript Object Notation，一种纯文本的数据表示格式）序列化再读回一致，便于把每轮产物落盘留痕。结尾打印每条性质并汇总为 `通过 N/N 项`，`assert` 保证任何一条被破坏都以非零状态退出。

有一处要如实说明：这里用固定字典代替了真实产出、用三条明确规则代替了真实校验器、用查表式分支代替了真正的反思判断，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是「证据 → 定位 → 定点改 → 重新校验」的次序与收敛约束，不是任何具体框架的实现；文中也没有给出任何运行结论。

## 踩坑与边界

- **把重试当反思**：现象是「再试一次」跑了好几轮，错处一模一样 → 原因是下一轮输入完全没变，只换了个重交动作 → 每轮必须把上轮的问题清单变成可见输入，并用「相邻两轮输入是否不同」验一遍。
- **让产出方给自己打分**：现象是它回答「我复核过，没问题」，校验器一跑还是三条错 → 原因是裁判与产出同源，双方一起确认了错误 → 校验器独立成一段确定性代码，规则写成断言，参考 [结构校验](./k017-structure-check.md) 与 [语义校验](./k018-semantic-check.md)。
- **反馈太笼统**：现象是只拿到「不合格」，程序只能瞎改或整版重写 → 原因是失败没有定位到具体条目 → 校验器逐条返回「哪条规则、哪个字段没过」，见 [错误如何回喂](./k029-error-feedback.md)。
- **整版重写导致来回打转**：现象是这轮改对的字段下轮又错了，错处数量忽上忽下 → 原因是改动不单调、已通过部分被重新生成 → 一次只改一处、冻结已通过字段、每轮重新全量校验，配合 [自动修复](./k019-auto-repair.md) 的定点思路。
- **反思无上限也不留痕**：现象是循环停不下来，事后说不清第几轮因为什么改了哪里 → 原因是没有轮数上限与轨迹记录 → 设上限和「问题清单不再变短就退出」的判定，把每轮证据、定位、改法、验收落成结构化记录，见 [停止条件](./k028-stop-conditions.md) 与 [压缩后校验](./k048-compression-verify.md)。

还要分清「通过校验」和「真的对了」：前者只说明没触发已写下的规则，规则之外的语义错误它一个也照不见。也别把反思当成免费的提质手段——每一轮都多一次校验、多一次产出、多一段轨迹，规则本身写错了的话，反思只会更快地收敛到一个错答案。当一次就能写对、或根本没有可判定的对错标准时，硬加反思循环只是增加开销。

## 三句话小结

反思与自我修正，是拿外部校验器指出的具体错处，翻成「改哪个字段、改成什么」的指令再喂回下一轮，让产出逐轮收敛的循环。

关键做法是证据独立于产出方、反馈定位到条目、一次只改一处并冻结已通过字段、每轮重新全量校验，同时配好轮数上限与轨迹留痕。

当一次就能写对、或根本没有可判定的对错标准时，不必硬套反思；但只要错误是规则性的、能被逐条指出来，原样重试再多次也不会自己变对。

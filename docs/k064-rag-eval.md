# 多轮检索与检索质量评测：不够就再查，错了先分层

## 答案错了，你却不知道该改哪儿

用户问了个稍绕的问题，助手答错。你把提示词改了三遍、换了一次模型，错误依旧；有人提议「再加大候选数」，延迟上去了，还是错。最后把日志摊开才看到：第一轮检索根本没捞到那段关键证据，后面所有环节都是在没有依据的情况下认真工作。你这才意识到，从头到尾没人回答过一个更基本的问题——这次错，是「没找到」还是「找到了却答错」？

## 先破一个误解

**不是模型不够强，是你把两种性质完全不同的失败混成一个「答不准」，于是改哪儿都像在碰运气。**

先把词说清楚。多轮检索指一次检索拿不到足够证据时，不急着生成，而是把问题改写、换个角度再查一轮；每一轮都能看到「这轮捞回了什么」，够不够有明确判据。检索质量评测指单独衡量「该找的片段找回来没有、排得靠不靠前」，与「最终答案对不对」分开算。常见的检索侧指标有 Recall@K（前 K 条里找回了多少该找的片段，白话叫「召回率」）、MRR（Mean Reciprocal Rank，平均倒数排名，看第一个相关结果排在第几位）、NDCG（Normalized Discounted Cumulative Gain，归一化折损累计增益，看相关片段是不是排在前面）；生成侧则看答案正确率、引用准确率、有没有编造。这些指标的算法见[检索排序指标与 RAG 四项核心指标](./k142-retrieval-metrics.md)。

为什么必须分开测？因为链路是串起来的，而检索是上游的闸门。召回率低时，下游所有指标都被封顶：证据压根没进上下文，模型再好也只能凭参数知识补，此时改提示词、换模型、加大生成预算都救不回来。反过来，若召回率满分、答案却错，问题就在生成侧——读错了、合并了、篡改了数字。两种情形的解法完全相反，不分开测就只能靠猜。这也是「答不准先分清是召回错还是生成错」这句话的落点。

多轮检索则是另一半：第一轮的查询往往不完整（代词、口语、复合句），或者措辞跟材料里的说法对不上，这时与其硬生成，不如换个问法再查一次，见[查询改写与指代补全](./k059-query-rewrite.md)。但「再查」要有刹车：限定轮数、每轮都记录改写了什么、捞回了什么，别让「不够就再查」变成一个没有终点的循环。评测集本身也得配齐：要覆盖正常、边界、已知失败、应当拒答、以及「语料里根本没有答案」的问题，否则永远测不出系统在「该说不知道」时的表现。评测集怎么构造见[评测用例集怎么构造](./k086-eval-dataset.md)，整套顺序可以从[从这里开始](./00-start-here.md)看起。

## 用带复核的查档流程来理解

把回答一个问题想成去档案室查档、再写一份回函，整个过程分两道关。

第一道关是查档：你递进去一张写着问题的单子，管理员抱回几份卷宗。合格的流程不是抱回什么就用什么，而是先核对「我要的那份在不在」；不在就换种措辞、把指代补全、或者把一句里问的两件事拆成两张单子再递一次。每次递单子、抱回什么，都记在登记簿上。这一步对应多轮检索，判据是「该找的找到没」，跟写回函的水平无关。

第二道关才是写回函：卷宗齐了，执笔人照着写。写完之后另外有人复核，逐条看「回函里这句能不能在卷宗里找到依据」。卷宗齐、回函却写错，是执笔的问题；卷宗根本没找齐，回函再漂亮也是空中楼阁。

对应关系：单子是查询，抱回的卷宗是召回片段，登记簿是检索日志，核对卷宗齐不齐是召回率评测，写回函是生成，复核是答案正确率与引用校验。这个比喻点出了「分开测」的必要性：档案室和执笔人是两拨人，出了错得先分清是谁那一环，不能把回函打回给档案室重写，也不能让执笔人去补本来就缺的卷宗。

:::quote
召回率是上游闸门。证据没进来，下游所有指标都被封顶；先查「找到没」，再谈「答得对不对」。
:::

## 把两件事画出来

先看一次「不够就再查」的动作顺序。

:::figure 证据不足时的多轮检索
@flow
首轮检索|判断证据够不够|改写再查一轮|合并各轮候选|达标才生成
:::

第二步「判断证据够不够」是刹车的落点：没有明确判据，「再查一轮」就会变成无限循环。

评测该分成哪两笔账，可以列成清单：

:::figure 检索侧与生成侧分开记
@stack
检索侧::该找的片段找回没有、排得靠不靠前
生成侧::答案对不对、引用准不准、有没有编造
无答案题::语料里本就没有，看系统会不会老实拒答
分层归因::召回低先修检索，召回满再修生成
:::

第三行常被漏掉：评测集里若全是「有答案」的题，系统只要逢问必答就能拿高分，反而掩盖了最危险的失败。

再看两种排查方式的差别：

:::figure 只看最终答案，与分层评测
@compare
只看答案对错::召回漏了也查不出|改哪层全靠猜|换模型常白费
分层测::能定位是召回还是生成|改动可归因|坏例可回收入用例
:::

第二行三格是同一件事：分层把「答不准」拆成两个可分别验证的问题，改动的因果链才看得见。

:::tip 一条立刻见效的规则
每次坏例复盘，先打印「这一轮改写后的查询、两路各自的候选、融合结果、最终进了上下文的证据编号」。看不到这条链，就只能对着最终答案猜是哪一环坏了。
:::

## 再往深问两层

:::ask 那如果第一轮就召回了东西，只是不太确定，要不要直接再查一轮？
:::

别用「感觉不太确定」当判据，要写死可判定的条件：证据数量够不够、最高分有没有过阈值、命中的片段是不是真的含回答问题所需的实体、复合问题的每个子问题是不是都各自有证据。满足不了就改写再查，但轮数要有上限，超过就走「未找到依据」的兜底，绝不能无限追加。这里有个值得记住的分寸：不要一上来就盲目增大候选数。候选从五段加到二十段，常常因为无关块稀释注意力，反而让忠实性下降；更划算的是先把查询写对、再查一轮。另外，多轮里每一轮的查询与候选都要留痕，既能解释「为什么第二次才找到」，也能把这些坏例收成新的评测用例，见[Badcase 回收闭环与分级评测](./k093-badcase-loop.md)。

:::ask 再深一层：召回率满分，答案还是错，这时该怎么继续定位？
:::

说明闸门过了，问题在生成侧，接下来要分得更细。第一类是忠实性问题：证据明明在上下文里，模型却把两段各取一半拼成一句原文没有的话，或者把数字、条件、否定读错；这类要拆成断言逐条核对被引原文，见[溯源、拒答与零召回兜底](./k062-citation-abstain.md)。第二类是答案相关性：每句都有出处，合起来却答非所问，说明选证据时挑错了重点，得回头看重排与截断，见[粗排 + 精排与重排后截断](./k061-rerank.md)。第三类是材料本身有问题：多版本冲突、生效时间不对、解析时把表格拆散了，这些看着像生成错，根子却在入库侧，见[索引更新、增量与知识冲突](./k063-index-update.md)与[文档解析与清洗](./k053-doc-cleaning.md)。把「忠实度、答案相关性、上下文精确率、上下文召回率」四项分开看，指标一掉就知道该修哪层；具体算法见[检索排序指标与 RAG 四项核心指标](./k142-retrieval-metrics.md)。评测集也要跟着长：线上每出现一个坏例，就补一条用例并标清它属于哪一类失败，否则下次同样的坑还会再踩一遍。

## 一份能跑的对照

下面这段只用标准库，构造一个小材料库与一组评测问题，实现「证据不足就改写再查」的多轮检索，并把召回率与答案正确率分开计算，演示「检索没问题不代表答案对」。

```python
# rag_eval.py —— 只用标准库，python rag_eval.py
import re

DOCS = {
    "d1": "差旅制度 一线城市住宿每晚 600 元",
    "d2": "差旅制度 其他城市住宿每晚 400 元",
    "d3": "报销细则 发票七个工作日内提交",
}
GOLD = {
    "一线城市住宿多少钱": {"d1"},
    "发票几天内交": {"d3"},
    "公司有食堂吗": set(),          # 语料里无答案的题
}


def terms(t):
    return set(re.findall(r"[a-z0-9]+|[\u4e00-\u9fff]", t.lower()))


def retrieve(q, k=2):
    qts = terms(q)
    scored = [(len(qts & terms(v)), key) for key, v in DOCS.items()]
    scored.sort(key=lambda x: -x[0])
    return [key for s, key in scored[:k] if s > 0]


def recall_at_k(q, k=2):
    hit = set(retrieve(q, k)) & GOLD[q]
    return len(hit) / len(GOLD[q]) if GOLD[q] else 1.0


def multi_round(question, variants):
    # 每轮改写后都记下「查了什么、捞回什么」，命中依据才停
    trace = []
    for v in variants:
        got = retrieve(v)
        trace.append((v, got))
        if GOLD[question] and GOLD[question] & set(got):
            return trace, got
    return trace, []


if __name__ == '__main__':
    trace, got = multi_round(
        "一线城市住宿多少钱", ["那个金额", "一线城市住宿"])
    assert len(trace) == 2                     # 首轮证据不足才触发第二轮
    assert trace[0][1] == []
    assert "d1" in got

    assert recall_at_k("一线城市住宿多少钱") == 1.0
    assert recall_at_k("发票几天内交") == 1.0
    assert not retrieve("公司有食堂吗")        # 无答案题不该硬凑证据
    assert GOLD["公司有食堂吗"] == set()

    # 检索侧与生成侧分开算：(召回率, 答案是否正确)
    RECORDS = [
        {"recall": 1.0, "correct": 1},
        {"recall": 1.0, "correct": 0},       # 检索对了，答案却错了
        {"recall": 0.0, "correct": 0},       # 坏在检索
    ]
    r_mean = sum(x["recall"] for x in RECORDS) / len(RECORDS)
    a_mean = sum(x["correct"] for x in RECORDS) / len(RECORDS)
    assert a_mean < r_mean                   # 召回没问题不代表答案对
    print("通过 8/8 项：多轮再查、无答案题拒答、检索与生成分层评测")
```

1. `DOCS` 是本地构造的三段材料，`GOLD` 是每题「该找的片段编号」。第三条「公司有食堂吗」的标准答案是空集，专门代表语料里没有答案、系统该老实拒答的题。
2. `retrieve` 是最朴素的召回：数查询词项与片段词项的交集，取前 `k` 条且分数大于 0。`recall_at_k` 单独算检索侧：该找的片段找回了几成，与答案写得对不对毫无关系。
3. `multi_round` 是「不够就再查」：逐个尝试改写后的问法，每轮把「用了什么问法、捞回了什么」记进 `trace`，只有命中 `GOLD` 才停。这里刻意让第一轮「那个金额」零命中，好把第二轮逼出来。
4. 前五条断言验证多轮检索与评测集覆盖：确实查了两轮、首轮为空、第二轮命中；两道有答案题召回率都是 1；无答案题既召回不到东西、标准答案也是空集。
5. `RECORDS` 是构造的一组演示记录，把「召回率」与「答案是否正确」并列。第二条记录正是「检索满分、答案却错」的情形，最后一条断言说明两者均值不相等，两层必须分开测。八条断言跑完打印通过项数。

想看得更清楚，可以把 `variants` 里第二个问法删掉，会看到 `multi_round` 走完所有轮次仍返回空——这就是「不够就再查」必须配一个兜底终点的原因。真实系统里 `GOLD` 会是标注好的评测集，`retrieve` 会换成两路召回加分重排，但「先算召回、再算答案、按差值定位」这套分层不变。

## 踩过的坑

- **只盯最终通过率**：现象是反复换模型、改提示词，答案依旧错 → 原因是证据根本没被召回，问题在检索侧 → 怎么改：先单独量召回率，确认闸门过了再谈生成。
- **盲目增大候选数**：现象是候选加多了，忠实性反而下降 → 原因是无关块稀释注意力，模型在各段之间自由发挥 → 怎么改：先把查询写对、再查一轮，而不是一味调大 K。
- **评测集里没有无答案题**：现象是系统逢问必答却拿高分 → 原因是所有题都有标准答案，测不出该拒答时的表现 → 怎么改：显式放入「语料中无答案」的题并标空集。
- **多轮没有刹车**：现象是「不够就再查」变成停不下来的循环 → 原因是没有明确判据与轮数上限 → 怎么改：写死证据数量、分数阈值、子问题覆盖度，超限走兜底。
- **坏例不回流**：现象是同一个坑反复踩 → 原因是坏例只修了当下、没变成新用例 → 怎么改：每例标注属于哪层失败，收进评测集并按改动范围分级跑。

## 三句话

多轮检索与检索质量评测，是证据不足就改写再查一轮，并把「该找的找到没」与「答案答得对不对」分开衡量。
关键做法是每轮留痕、限定轮数与判据，用召回率与答案正确率的差值定位该修检索还是该修生成。
当问题单轮就能稳定命中、且答案质量没有争议时，不必引入多轮与分层评测这套开销。

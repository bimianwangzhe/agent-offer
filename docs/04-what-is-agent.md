# 什么是 Agent：一条线划清边界

面试里有个特别爱问、也特别容易翻车的问题：

> **「你说你做了个 Agent，它凭什么算 Agent？」**

很多人答「我用了大模型、接了工具、能查资料」。面试官再追一句「那你把它写成固定流程也能查资料，区别在哪」，就卡住了。

这一篇把这条线画死，然后讲一个更有价值、也更显工程判断的问题：**什么时候不该用 Agent**。

## 一、先破误解：接了工具不等于 Agent

先看三个长得有点像、本质完全不同的东西。

假设需求是「读一份财报，找出毛利率异常的原因」。

**做法 A：固定流程**

```
上传文件 → 切分文本 → 逐段总结 → 拼成报告 → 发邮件
```

每一步都是你写在代码里的 `if / for`，顺序永远不变。模型只负责其中「逐段总结」那一步的文字活。

**做法 B：多轮问答**

用户问一句，模型答一句；用户再追问，模型再答。**下一步做什么，由用户决定**。

**做法 C：Agent**

你只给它目标和一组可用动作（检索财报、查行业数据、跑一段计算、翻历史公告）。它自己决定先查哪份、发现毛利率异常后要不要再查应收账款、算完发现对不上要不要换个口径重来。**下一步做什么，由模型在运行时决定。**

:::figure 三种形态：谁在决定下一步
@compare
固定流程 / 多轮问答::流程写死在代码里|下一步由用户点|可预测、好测、便宜|模型只做文字活
Agent::运行时由模型选动作|能根据结果改计划|多轮循环直到达成目标|必须配护栏与预算
:::

所以判据只有一条，别的都是表象：

:::quote
**控制流是不是在运行时由模型决定的。** 是，就是 Agent；不是，就是固定流程——哪怕你用了十个模型调用、接了八个工具。
:::

反过来立刻要补一句，否则容易走火入魔：

:::tip 固定流程不是低级
生产环境里**大量场景应该用固定流程**：步骤确定、要可审计、要低延迟、要成本可控的时候，把控制权交给模型反而是给自己找麻烦。面试时能主动说「这个场景我们最后选了固定流程，因为……」，比硬说自己用了 Agent 更显判断力。
:::

## 二、把 Agent 拆开看：不是模型变强了，是外面多了一层

新手常以为 Agent 是「更聪明的模型」。其实模型还是那个只会接着往下写的模型，真正变化的是**外面多了一整套壳**。

:::figure 一个 Agent = 模型 + 外壳
@stack
模型::只负责「给一段文字，产出下一步动作」
循环::把动作执行后的真实结果，重新拼回上下文，再问一次
工具::让文字能真正碰到数据库、接口、文件系统
状态::记住走到第几步、已经查过什么、还剩多少预算
终止条件::目标达成 / 轮数用尽 / 花费超限 / 人工中断
护栏::权限、参数校验、幂等、危险动作二次确认
:::

业内有个很实用的心智模型：**模型大概只贡献两成，外面这层壳贡献八成**。原因上一篇已经推导过——模型既不能验证自己，也不能真的动手，还不知道你们公司的真实数据。这三件事全得靠壳补齐。

这条结论直接影响你怎么分配学习时间：

:::warn 别把八成时间花在调提示词和换模型上
换成更强的模型能抬高上限，但**决定系统能不能上线的是那层壳**：循环会不会死、工具会不会重复执行、上下文会不会爆、出错能不能恢复。本教程后面八篇，讲的全是这层壳。
:::

## 三、最小可用的循环长什么样

不看定义，看形状。一个 Agent 的每一轮都在重复同一件事：

:::figure Agent 的最小循环
@cycle
组装上下文|模型决策|执行动作|观察结果
:::

四个词，但每个词背后都藏着一个必须回答的工程问题：

| 环节 | 必须回答的问题 | 答不上来的后果 | 对应篇章 |
|---|---|---|---|
| 组装上下文 | 这一轮该带哪些历史？超预算了砍谁？ | 越聊越贵、越聊越笨 | [上下文工程](./07-context.md) |
| 模型决策 | 允许它选哪些动作？输出不合法怎么办？ | 乱调工具、参数幻觉 | [工具调用](./06-tool-calling.md) |
| 执行动作 | 重复执行会不会下两单？越权怎么办？ | 真实世界被改坏 | [工具调用](./06-tool-calling.md) |
| 观察结果 | 工具报错了，是把错误喂回去还是直接退出？ | 卡死或一条错路走到底 | [手写循环](./05-agent-loop.md) |
| 终止条件 | 凭什么停？ | 死循环烧钱 | [手写循环](./05-agent-loop.md) |

:::ask 想一个具体场景
用户说「帮我查一下 A 公司近三年毛利率，异常的话找出原因」。如果「查数据」这个工具连续三次返回超时，你希望系统怎么做？先别看答案，想三十秒——这道题在下一篇的手写循环里会变成一个明确的分支。
:::

## 四、三个必要条件，缺一个就不是 Agent

把上面的形状收成可检查的清单：

1. **循环**：不是一次调用，是「观察 → 决策 → 行动 → 再观察」的多轮。
2. **选择权**：模型在运行时从一组动作里挑，而不是代码写死顺序。
3. **终止条件**：最大轮数、预算上限、目标达成、人工中断，**至少有一个**。否则不是 Agent，是定时炸弹。

再加两个「虽然不进定义、但不上线就出事」的：

4. **状态可恢复**：进程崩了，能从检查点接着走，而不是从头再来。
5. **动作有副作用管控**：重试、幂等、权限、审计日志，一样不能少。

:::figure 从「能跑」到「敢上线」
@stack
能跑 Demo::循环 + 工具 + 终止条件
能演示::状态可查、轨迹可回放、错误有提示
能上线::幂等、权限、预算上限、降级、评测回归
能答辩::每条设计都能说出「为什么」和「不用会怎样」
:::

这四层，正好对应后面四篇的节奏。

## 五、什么时候坚决不用 Agent

这是这一篇最值钱的部分，也是转行者最容易在面试里出彩的地方。把下面这张表记牢：

| 场景特征 | 应该选 | 理由 |
|---|---|---|
| 步骤固定、顺序不变 | 固定流程 | 可预测、好测、便宜、可审计 |
| 要求 100% 一致的输出 | 固定流程 + 模板 | 模型随机性无法消除 |
| 延迟要求很紧（< 1s） | 固定流程 | 多轮循环天然慢 |
| 每一步都要人工签字 | 固定流程 + 审批节点 | 自主决策反而添乱 |
| 任务边界模糊、需要临场查资料 | **Agent** | 正是运行时决策的价值 |
| 需要根据中间结果改计划 | **Agent** | 固定流程写不出这种分支 |
| 工具很多、组合方式无法穷举 | **Agent** | 穷举 if-else 不可维护 |

:::quote
**能写死的，就别交给模型决定。** Agent 的价值在于处理「你事先写不出流程」的任务，不在于显得高级。
:::

一个真实的判断例子：很多团队做「智能客服」，一上来就上 Agent。但客服八成问题是「查订单状态」「查退款进度」——步骤完全确定，固定流程又快又准还不出错。只有剩下那两成「我上周买的那个东西，发票抬头好像写错了，能不能帮我改一下顺便看看能不能补开」才需要 Agent。**正确做法是先用固定流程兜住八成，Agent 只接剩下两成**，成本、延迟、稳定性全都最优。

:::tip 面试加分说法
「我们先用规则路由把确定性流量挡掉，只有识别到多意图、需要跨系统查证的请求才进 Agent 循环，所以整体 P95 延迟和成本都可控。」——这句话里藏着分层、评测、成本意识三个考点。
:::

## 六、一张自测表：你的项目算不算

拿你打算写进简历的项目，逐条打勾：

- [ ] 下一步动作是模型在运行时选的，不是代码里写死的
- [ ] 有一组明确的可用动作，每个都有参数说明
- [ ] 动作执行后的结果会回到上下文，影响下一轮决策
- [ ] 有至少两个终止条件（轮数 / 预算 / 目标达成 / 人工）
- [ ] 状态存在明确的数据结构里，能打印、能回放
- [ ] 工具执行有幂等或去重保护
- [ ] 有一份评测集能证明「改了一版没变差」

前四条勾不上，就别叫 Agent，叫「带模型调用的流程」更诚实——**诚实本身也是加分项**。

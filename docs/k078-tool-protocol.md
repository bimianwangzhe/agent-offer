# 工具协议与标准化接入：统一的是接入层，不是模型表达

## 场景提问

你陆陆续续接了四五个外部能力：查订单、查库存、改地址、发通知。每个都有自己的注册写法、参数命名和错误格式，加一个就得重写一遍胶水代码。有人说「用一套统一的工具协议就都解决了」，你照着把发现、描述、调用都收拢成一种格式，接新能力确实快了；可模型那边该乱调还是乱调，参数缺字段、类型写错、把不该调的工具也调了，一样没少。说好的「统一」，到底统一了哪一半？

## 破误解

**不是协议没用，是它统一的是「接入」这一层，而模型侧「怎么表达要调什么」是另一层问题**，两层混为一谈就会失望。

先把几个词说明白。工具协议（tool protocol，把外部能力的发现、描述、调用与错误约定成同一套格式的一种约定；白话讲像统一插座规格）关心的是「有哪些能力、各要什么参数、按什么形状调用、失败怎么报」。发现（discovery，问一句「现在有哪些能力、每个要什么参数」并拿到统一格式的清单）是它的第一件事。结构描述（schema，用机器可读的方式写清字段、类型、必填项；白话讲是一张填表说明）是第二件事。而模型侧的调用表达，指的是模型输出的那段文字到底长什么样、能不能被稳定解析成一次调用意图——这归提示与输出契约管，协议管不着。JavaScript 对象标记（JavaScript Object Notation，简称 JSON，一种用花括号和键值对表示数据的文本格式）常用来承载调用意图，但「文本能不能被解析」并不是协议能担保的事。

## 生活类比

把接入层想成「海关报关单」，把模型想成「决定发哪批货的工厂」：

- **工厂**自己决定这批发什么、发给谁，这是模型侧的调用表达；
- **报关单**规定不管哪家工厂、什么货，都填同样的栏目：品名、数量、规格，这是统一描述；
- **单子上的必填栏**没填、规格写成文字而不是数字，海关直接退单，这是结构校验；
- **查验规则**还会看「这批货允不允许进」，数量合规也可能因为有管制而不放行，这是业务规则；
- **回执**盖一个统一的章，写清放行还是扣留，这是统一返回格式。

对应关系要点在「工厂」和「海关」的分工：报关单让查验这件事变得高效、可批量，却不能替工厂决定发哪批货，更不能保证工厂一定把单子填对。工厂递来一张手写的便条，海关只能退回，不会替它重填——这正对应「模型输出一段自由文本，解析失败得自己处理」。很多人的失望就来自这里：把「插座规格统一了」误当成「电器会自己按规格工作」。规格统一解决的是插头插得上，不是电器想不想插、会不会插错孔。

## 层层追问

:::ask 那统一之后，模型输出的那段自由文本谁负责，协议不能顺手管了吗？
不能，也不该。协议假设拿到的已经是一个结构化的调用意图——有工具名、有参数字典；至于这段意图是怎么从一段文字里得来的，是解析层的事。硬把它塞进协议，等于要求协议兼容各种随便写的文本，协议很快会变成一堆特判，反而失去「统一」的意义。干净的做法是像代码里那样，`parse_model_output` 与 `ToolProtocol` 两个东西分开：解析失败就明确返回「无法解析」，由上层决定是纠正、重问还是降级，绝不假装解析成功。追问到这一层还有个额外好处：换模型、换提示写法时，改的是解析层，已登记的几十个能力一个都不用动。
:::

:::ask 那如果参数结构完全合法，可业务上根本不允许这次操作呢？
这正是接入层最容易被高估的地方。结构描述能挡住「缺字段」「类型错」，挡不住「合法结构指向越权动作」：一个账号字段填得规规矩矩，可能是别人的账号；一个金额是合规整数，可能超出这次会话的限额。这类判断依赖「谁在请求、额度多少、允许操作谁的数据」，属于业务规则，必须另做一层，且要放在分发执行之前。代码里用 `policy` 这个可传入的判定函数演示了这一层：结构校验全过，业务规则仍能把「金额 900」挡下。追到第二层可以归纳成一句：有效不等于合法，协议只回答「格式对不对」，业务规则回答「这件事准不准」。这也和[主体间消息契约](./k081-agent-message.md)里强调的「字段显式定义、完成标准可判定」是同一种思路——把可判定的东西明确提出来，别指望某一层顺手兜住。
:::

## 可运行代码并逐行解释

下面用标准库搭一个极简接入层，外加一个独立的文本解析函数，两层分开，复制即可运行。

```python
"""标准化接入层：统一发现、描述、校验、调用；但不负责模型侧的调用表达。"""
import json


class ToolProtocol:
    def __init__(self):
        self._tools = {}

    def register(self, name, spec, handler, policy=None):
        """spec 描述参数结构：required 是必填字段，types 是字段到类型的映射。"""
        self._tools[name] = {"spec": spec, "handler": handler, "policy": policy}

    def discover(self):
        """统一发现：任何接入方看到的都是同一种描述形状。"""
        return [
            {"name": name, "required": list(t["spec"]["required"]),
             "types": dict(t["spec"]["types"])}
            for name, t in sorted(self._tools.items())
        ]

    def invoke(self, intent):
        """intent 是模型调用意图被解析之后的结构化字典。"""
        if not isinstance(intent, dict) or "tool" not in intent or "args" not in intent:
            return {"ok": False, "error": "意图缺少 tool 或 args"}
        name, args = intent["tool"], intent["args"]
        if name not in self._tools:
            return {"ok": False, "error": "未登记的工具"}
        t = self._tools[name]
        for field in t["spec"]["required"]:
            if field not in args:
                return {"ok": False, "error": "缺字段 " + field}
        for field, typ in t["spec"]["types"].items():
            if field in args and not isinstance(args[field], typ):
                return {"ok": False, "error": "类型不符 " + field}
        if t["policy"] is not None and not t["policy"](args):
            return {"ok": False, "error": "业务规则不允许"}
        return {"ok": True, "data": t["handler"](args)}


def parse_model_output(text):
    """模型侧的表达是自由文本，把它转成协议意图这一步独立于接入层。"""
    try:
        data = json.loads(text)
        if isinstance(data, dict) and "tool" in data and "args" in data:
            return {"ok": True, "intent": data}
        return {"ok": False, "error": "文本不是合法调用意图"}
    except (ValueError, TypeError):
        return {"ok": False, "error": "文本无法解析为 JSON"}


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    p = ToolProtocol()
    p.register("查余额", {"required": ["账号"], "types": {"账号": str}},
               lambda a: {"余额": 100 if a["账号"] == "A" else 0})
    p.register("转账", {"required": ["账号", "金额"], "types": {"账号": str, "金额": int}},
               lambda a: {"状态": "已受理"},
               policy=lambda a: a["金额"] <= 500)

    desc = p.discover()
    ok(len(desc) == 2 and desc[0]["name"] == "查余额", "发现接口返回统一描述清单")
    ok(p.invoke({"tool": "查余额", "args": {"账号": "A"}})["data"]["余额"] == 100,
       "按标准形状调用成功")
    ok(p.invoke({"tool": "转账", "args": {"账号": "A"}})["ok"] is False,
       "缺字段被接入层拦下")
    ok(p.invoke({"tool": "转账", "args": {"账号": "A", "金额": "100"}})["ok"] is False,
       "类型不符被拦下")
    ok(p.invoke({"tool": "转账", "args": {"账号": "A", "金额": 900}})["ok"] is False,
       "结构合法也可能被业务规则拒绝")

    ok(parse_model_output('{"tool":"查余额","args":{"账号":"A"}}')["ok"] is True,
       "合规文本能解析成调用意图")
    ok(parse_model_output("我想查一下余额")["ok"] is False,
       "自由文本无法解析，这层不归接入协议管")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `register` 把每个能力登记成三样东西：`spec`（结构描述）、`handler`（真正执行的函数）、`policy`（可选的业务规则）。登记一次，发现、校验、调用就都有了依据，不必为每套外部写法单独写胶水。
2. `discover` 是「统一发现」：按名字排序后，给每个能力产出同样形状的清单——名字、必填字段、字段类型。任何调用方看到的都是这一种格式，与背后实现无关。
3. `invoke` 开头先核对意图本身：不是字典、缺 `tool`、缺 `args`，直接回一张带 `ok` 与 `error` 的表，绝不抛含糊的异常。统一回执让上层能判定下一步。
4. 接着查 `name not in self._tools`，把「编了个不存在的工具名」挡在分发之前；这与[解耦适配层](./k077-adapter-layer.md)里「名字到函数的映射」是同一件工作，只是这里收进了协议内部。
5. 两个 `for` 循环分别做必填校验与类型校验：注意用 `isinstance(args[field], typ)` 判类型，于是 `"100"` 这个字符串会被 `int` 挡下。这是结构描述的价值——把「格式对不对」变成机器能判的事。
6. `if t["policy"] is not None and not t["policy"](args)` 是业务规则那一层：结构全过也可能被拒。演示里「金额 900」是合法整数，却超出允许范围。它和结构校验并排写，但职责分明。
7. `parse_model_output` 完全独立于 `ToolProtocol`：用标准库的 `json.loads` 解析文本，解析失败或形状不对都明确返回失败。它演示的正是第二张图前两步——协议从第三步才接手。
8. `main` 用七条断言分别核对发现、正常调用、缺字段、类型错、业务拒绝、可解析、不可解析，最后打印 `通过 7/7 项`。这些都是构造出来的确定场景，用来把两层边界一条条验清楚。

把代码和第一张图对照着看会发现，协议真正做的四件事都不涉及「模型怎么想」。它只保证：能力按统一格式登记、按统一格式被看见、按统一规则被验、按统一格式回执。至于那段文本从哪来、写得规不规矩，是另外一层要回答的问题。

## 踩坑与边界

- **把协议当万能**：现象 → 接了统一协议后，模型乱调工具的问题一点没少 → 原因 → 误以为协议会约束模型侧的表达 → 怎么改 → 解析层独立出来，解析失败明确回退；协议只处理已经结构化的意图。
- **描述写得含糊**：现象 → 必填、类型都登记了，模型仍常传错参数 → 原因 → 描述只写了字段名，没说清取值范围与适用场合 → 怎么改 → 描述里补上「什么时候该用、什么时候不该用、边界值是什么」，把它当成给调用方看的接口文档来写。
- **错误格式不统一**：现象 → 上层要写好几套判断才能知道失败原因 → 原因 → 每个能力各用自己的报错方式 → 怎么改 → 所有失败都回同一张表，至少包含是否成功与可判定的错误类别。
- **把业务规则塞进结构描述**：现象 → 换个会话额度就得改一遍结构描述 → 原因 → 把「谁有权、限额多少」这种随会话变化的东西写进了协议层 → 怎么改 → 结构描述只放稳定的形状，随请求变化的规则作为独立判定传入。
- **把模型输出直接当意图用**：现象 → 一段带解释文字的输出被当成调用参数，执行出一串怪结果 → 原因 → 少了解析与形状核对 → 怎么改 → 先解析、再校验、最后分发，任何一步不过都不进入执行。

边界要说清：协议统一的是接入层，不解决模型侧的调用表达，也不解决权限本身。业务规则那一层能挡住「金额超额」，但「这个请求的人是谁、能看哪些数据」需要在请求开始时确定作用域，属于更外围的护栏话题。另外，能力数量很少、且短期内不会增加时，专门搭一套协议未必划算——直接登记几个函数可能更省事，[框架选型与自研编排的取舍](./k083-build-vs-framework.md)里谈的正是这类「值不值得多一层」的判断。反过来，能力会持续增加、要被多个调用方复用时，统一格式省下的是每一处都要重写胶水的重复劳动。能力再多还会引出下一个问题：说明怎么给才不撑爆上下文，那是[三类能力原语与渐进披露](./k079-primitives-skills.md)要处理的。

## 三句话小结

工具协议与标准化接入，是把外部能力的发现、描述、校验、调用收拢成同一种格式，解决接入层的重复劳动。
关键做法是把文本解析独立出去、结构校验与业务规则分层，并让所有失败回同一种可判定的格式。
当能力很少、也不会被多个调用方复用时，直接登记几个函数比搭一套协议更省事。

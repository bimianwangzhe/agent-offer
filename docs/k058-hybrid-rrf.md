# 混合检索与 RRF 融合：只比名次，不比分数

## 两路都召回了，合起来反而更乱

你按前面讲的把稠密与稀疏两路都搭好了，各自单独跑都挺像样。可一到「合起来」就卡住：余弦相似度是 0.8 上下，BM25 分数动辄十几，直接相加等于让数值大的那一路说了算。你试着先归一化再加权，结果换一个问题、换一批候选，权重效果就变了，昨天调好的参数今天又不对。更别扭的是，明明两路都把某个片段排得很靠前，合完却掉到了后面。

## 先破一个误解

**不是权重没调好，是这两路分数根本不在同一把尺子上，加权这条路从一开始就走歪了。**

先把词说清楚。混合检索指同时跑多路召回（典型是稠密一路、稀疏一路），再把各路的候选合成一份统一排名。RRF 是 Reciprocal Rank Fusion（倒数排名融合）的缩写，做法很朴素：不看每路给了多少分，只看每个片段在这一路排第几，把「名次倒数」累加起来当最终得分。常用写法是 `score += 1 / (k + rank)`，其中 `rank` 是从 1 开始数的名次，`k` 是一个常数（习惯取 60），用来压平第一名与后面几名的差距。另一个要区分的词是 BM25（Best Matching 25，基于词项频次与逆文档频率的排序函数），它是稀疏那一路的打分方式，跟融合不是一回事。

为什么只比名次反而稳？因为名次是跨路可比的：不管一路用余弦、一路用 BM25，「排第 1」就是排第 1，含义完全一致。分数则不然，量纲、分布、是否归一化，全都会随查询和候选集变化。直接加权会被量纲带偏；先做 min-max 或 z-score 归一化，又依赖「当前这批候选的分数分布」——换一个问题，最小值最大值就变了，同一套权重表现跟着飘，很难调稳，也多了个要维护的参数。RRF 彻底绕开分数，因此既不受量纲影响，也少一个要调的权重；某一路偶然给了个异常高分，只要名次没动，融合结果就不动，抗噪性也更好。

k 不是不能改，但要知道它调的是什么：k 越大，各名次之间的得分差距越小，头部优势被摊平，多路「都排过」的片段更容易靠累积胜出；k 调小，第一名的权重更突出，适合两路排名分布差异大、想让各自头部说话的场景。它调的是「名次怎么折算成分数」，不是「哪一路更重要」——想偏向某一路，得在生成排名时处理，而不是拿 k 当权重旋钮。两路各自的盲区见[稠密检索与稀疏检索](./k057-dense-sparse.md)，融完之后候选通常还偏多，需要再收敛，见[粗排 + 精排与重排后截断](./k061-rerank.md)。

## 用两场独立评审来理解

把多路召回想成一场比赛有两位评委，各自独立给选手排了个名次，现在要合成一份总榜。

一位评委按「表达像不像」排，另一位按「关键字对不对」排。他们的打分习惯差得远：一位习惯给 0 到 1 的小数，另一位习惯给十几分。若把两人的原始分直接相加，等于让打分范围大的那位独揽决定权，另一位形同虚设。就算先把各自分数拉到 0 到 1，也会出问题——今天选手整体水平高、明天整体水平低，归一化后的相对位置就变了，同一套「加权」今天公平明天偏。

更稳妥的办法是让两位评委只交名次：第一名、第二名、第三名……再按「第 1 名得最多、越往后越少」把名次折成贡献，同一个选手在两份榜单里的贡献相加，就是总榜。谁给 0.8、谁给 12.3 完全不进计算，评分习惯再也带不偏结果。

对应关系：两位评委是稠密与稀疏两路，各自的榜单是两路排名，选手是片段，名次折成贡献就是 `1/(k+rank)`，总榜是融合结果。这个比喻还解释了一个细节：一位评委给某选手打了个离谱的高分，只要他仍把该选手排在第 4，名次不变，总榜就不变——这就是只比名次带来的抗噪性。

:::quote
名次是跨路通用的语言，分数不是。RRF 把融合问题从「怎么把两把尺子对齐」变成「怎么把两份名单叠起来」。
:::

## 把融合画出来

先看一次混合检索从头到尾的动作。

:::figure 两路召回到一份统一排名
@flow
问题输入|稠密出排名|稀疏出排名|倒数名次累加|得到统一排名
:::

第二、三步并列且互不知情，正是这点让「只比名次」成为必要：两路连分数口径都没商量过。

融合时每一步该做什么，可以列成清单：

:::figure 融合的四步
@stack
各取自排::每路独立给一份有序名单，不交换分数
编号对齐::两路必须用同一个片段编号，才认得出是同一个
倒数累加::按 1/(k+rank) 把名次折成贡献并相加
按分排序::累加分从高到低排，得到最终候选顺序
:::

第二行常被忽略却最要命：两路若各自用了不同的编号体系，融合时会把同一个片段当成两个，累加全乱。编号统一是[切分元数据与父块回溯](./k056-chunk-metadata.md)那一步就该定好的。

再看两种合并取向的差别：

:::figure 分数加权，与倒数名次融合
@compare
分数加权::量纲不可比|归一化随查询飘|多一个权重旋钮
倒数名次::跨路可比|不受分数缩放影响|无需归一化
:::

第二行三格是同一件事的三个侧面：因为只吃名次，所以天然可比、天然抗缩放、天然少一个参数。

:::tip 一条立刻见效的规则
让每一路召回函数只返回「有序的片段编号列表」，把分数留在各自内部。融合函数看不到分数，就没机会被量纲带偏——这个接口约定比任何权重技巧都管用。
:::

## 再往深问两层

:::ask 那如果某一路明显更靠谱，RRF 不给它加权，会不会埋没了好结果？
:::

会有这个顾虑，但解法不在融合公式里。RRF 里两路是平等的，想让更靠谱的一路更有话语权，通常有三种做法：让那一路多贡献几份名单（比如对问题做几种改写，各自召回一份，再一起参与累加）；在融合之后加一道精排，用更重的判断重新给候选定序；或者按查询类型决定要不要让某路参与——问编号就侧重字面，问口语就侧重语义。这些都是「生成哪些排名」或「排名之后怎么处理」层面的事，比在分数上乘系数干净得多。真正不建议的是回头去做分数加权：一旦开了这个口，量纲、归一化、权重漂移这些问题会一起回来。顺带说，保留一份「未经改写的原问题」也常一起参与召回，避免改写把问题带偏，见[查询改写与指代补全](./k059-query-rewrite.md)。

:::ask 再深一层：k 到底该怎么定，会不会又变成一个要反复调的参数？
:::

它确实是个参数，但比权重好调得多，因为它不随查询变化。k 控制的是「第一名比第十名领先多少」：k 取大，各名次贡献接近，一个在两路都排中段但都出现过的片段，可能靠累积超过只在单路排第一的片段；k 取小，头部权重集中，更看重「有没有哪一路把它排到最前」。所以判据是两路排名的分布：如果两路常常给出很不一样的头部（比如字面那路总把标题排第一），把 k 调小些更合适；如果两路比较一致、想稳一点，默认的大 k 就够。定法也朴素：拿一组固定的评测问题，扫几档 k，看该找的片段有没有稳定排到前面，而不是凭手感选一个「看着整」的数。评测怎么组织见[多轮检索与检索质量评测](./k064-rag-eval.md)，排序指标怎么算见[检索排序指标与 RAG 四项核心指标](./k142-retrieval-metrics.md)。整套顺序可以从[从这里开始](./00-start-here.md)顺着看。

## 一份能跑的对照

下面这段只用标准库，造两路排名与两路分数，实现 RRF，并把「直接加权被量纲带偏」摆在一起对照。全程本地数据、无第三方包。

```python
# hybrid_rrf.py —— 只用标准库，python hybrid_rrf.py


def rrf(rankings, k=60):
    # 只吃名次：每路按 1/(k+rank) 给片段累加贡献
    score = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            score[doc_id] = score.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(score, key=lambda d: -score[d])


def naive_weighted(dense, sparse, w=0.5):
    # 对照：直接把两路原始分数加权
    keys = set(dense) | set(sparse)
    total = {d: w * dense.get(d, 0) + (1 - w) * sparse.get(d, 0)
             for d in keys}
    return sorted(total, key=lambda d: -total[d])


dense_rank = ["d2", "d1", "d4", "d3"]      # 语义路的名次
sparse_rank = ["d4", "d2", "d3", "d1"]     # 字面路的名次
dense_s = {"d2": 0.80, "d1": 0.78, "d4": 0.75, "d3": 0.70}   # 0~1
sparse_s = {"d4": 15.0, "d2": 14.9, "d3": 13.0, "d1": 12.0}  # 0~15


if __name__ == '__main__':
    fused = rrf([dense_rank, sparse_rank])
    assert fused[0] == "d2"                       # 两路都靠前的片段胜出
    assert set(fused) == {"d1", "d2", "d3", "d4"}
    assert rrf([dense_rank, sparse_rank], k=25)[0] == "d2"

    n1 = naive_weighted(dense_s, sparse_s)
    assert n1[0] == "d4"                         # 直接加权被 0~15 量纲带偏
    assert fused != n1                           # 两种合并给出不同结果
    big = {d: v * 1000 for d, v in sparse_s.items()}
    assert naive_weighted(dense_s, big)[0] == "d4"
    print("通过 6/6 项：RRF 只按倒数名次融合，规避了两路分数的量纲差异")
```

1. `rrf` 是融合主体：`enumerate(..., start=1)` 拿到从 1 开始数的名次，对每个片段累加 `1.0 / (k + rank)`，最后按累加分降序。函数里完全没有「分数」这个输入，这正是接口的约定。
2. `naive_weighted` 是刻意留的对照组：把两路原始分数按 `w` 加权。它没做任何归一化，用来直观展示量纲差异会怎样主导结果。
3. `dense_rank` 与 `sparse_rank` 是两路各自的有序名单；`dense_s` 与 `sparse_s` 是它们对应的原始分数，量纲故意差了一个量级。注意两路用的是同一套片段编号 `d1`~`d4`。
4. 前三条断言验证 RRF 的结果：两路都排得靠前的 `d2` 胜出，四个片段都在融合结果里，把 k 从 60 换成 25 头部也不变（这个构造里排名一致，改的是分差不是次序）。
5. 后三条断言是对照的重点：`naive_weighted` 因为稀疏那路分数是十几，直接把语义那路压没了，头名变成 `d4`；把稀疏分数整体乘 1000，结论更偏；而 RRF 从输入上就不看这些分数，怎么缩放都与它无关。六条断言跑完打印通过项数。

想看得更清楚，可以打印 `rrf` 里 `score` 字典，看 `d2` 靠两路名次累加怎么胜过只在单路排第一的 `d4`；或者把 `sparse_rank` 里 `d4` 挪到末尾，会看到融合头名随之改变——这提醒我们 RRF 并非偏袒某一路，它只是忠实反映两份名单。

## 踩过的坑

- **两路编号不统一**：现象是同一片段被当成两个，累加分被摊薄 → 原因是各路用自己的临时下标当编号 → 怎么改：全链路用同一个片段编号，切分时定好就不许改。
- **直接加权原始分数**：现象是某一路常年压过另一路，调权重也调不稳 → 原因是余弦与 BM25 量纲不可比 → 怎么改：改用只比名次的融合，或让每路只返回有序名单。
- **归一化后加权**：现象是昨天调好的权重今天又不对 → 原因是 min-max 之类依赖当前候选的分数分布 → 怎么改：避开依赖分布的口径，固定用名次折算。
- **把 k 当权重旋钮**：现象是想偏向语义路却去调 k，效果不随预期变化 → 原因是 k 调的是名次间距，不是路的重要性 → 怎么改：在「生成哪些排名」或「融合后精排」层面处理偏重。
- **改写出多路后忘了保留原问题**：现象是融合结果被改写带偏 → 原因是所有名单都来自改写版本 → 怎么改：把原问题那一路也一并纳入累加。

## 三句话

混合检索与 RRF 融合，是同时跑多路召回，再按每个片段在各路里的名次倒数累加出一份统一排名。
关键做法是让每路只交有序的片段编号名单、把分数留在内部，融合时不看分数也不做归一化。
当只跑单路召回、或两路结果的先后其实无所谓时，不必引入融合，直接按那一路的排名取用即可。

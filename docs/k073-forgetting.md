# 遗忘、过期与 TTL：给错误和临时信息一条明确的退出通道

## 场景：三个月前的一句误记，到现在还在带偏回答

用户某次随口说了句「这次先按纯文本给我」，被当成长期偏好存了下来。三个月过去，助手每次整理材料都照着它走，用户早就改了口径，它却怎么都扭不过来。你翻库还发现一条更早写进去的临时令牌，早该作废了，仍安安静静躺在可用条目里；另有一条带敏感字段的记录，当初没人清过。你不是没想过删，可又不清楚哪条能删、哪条该留，一犹豫就都留着了。结果库越攒越杂，而真正在起作用的，偏偏是几条最不该留的。

## 先破一个最常见的误解

**不是记得久就好，是没有退出机制的错误会永久影响决策。** 只加不删会带来三种后果，它们表面上不相干，根子是同一个：一条误记被反复当成前提引用，越引用越像真的；一次性的临时取值被熬成了长期事实；涉及敏感字段的内容一直躺着，谁也没去碰它。日志里的错误可以靠「再翻一遍当时的记录」发现，记忆里的错误却会直接参与每一次判断，所以危害大得多。这里先解释一个缩写：TTL 全称 Time To Live，直译是「生存时长」，白话就是「这条记录允许活多久，到点就失效」。遗忘不是把东西弄丢，而是事先设计好的退出机制：到期的自动失效，被标错的立刻停用，用户或系统明确撤销的当场撤下。三类退出各有各的触发条件，合起来才撑得住一句「取回时看到的都是还活着的」。

## 用生活里的事打个比方：定期清理的药箱

家里的药箱每盒都贴着有效期，到月的就扔；有一回拿错了药，家里人立刻在盒上贴张纸写「这盒别吃」，先停用再说；医生后来明确说「这个药停了」，那就整盒撤下。每隔一阵清一次药箱，把过期的、贴了停用纸的、医生撤掉的都挑出去。对应关系逐条对一遍：有效期就是 TTL，到点即失效；那张「别吃」的纸就是标错；医生说停就是主动撤销；定期清箱就是扫描动作；留在箱子里的，才是当下还能用的。为什么不能「先留着说不定哪天有用」？过期药不但帮不上忙，还可能被顺手拿去吃，风险比空着一格大得多。记忆也一样：一条已经失效却没被打标记的条目，会被当成仍然成立的前提，比没有这条更糟。

## 画出来看

先看一条记录从写入到被移出可用集合的过程，留意「写入带有效期」发生在最前面。

:::figure 一条记录怎么退出可用集合
@flow
写入带有效期|定期扫描|到期或标错|移出可用集|长期事实留下
:::

「长期事实留下」这一格很重要：退出机制不是把库清空，而是把该走的挑走、把真正稳定的留下。扫描动作要能反复跑，多跑一次结果不变，否则定时执行两遍就可能误伤。再看两种做法的差别。

:::figure 有没有退出机制的差别
@compare
只加不删::错误永久在|临时当长期|敏感字段留着
有退出机制::到期即失效|可标记可撤销|占用可控
:::

右边那行「可标记可撤销」把两种退出分开了：标错是先停用、留着线索；撤销是明确撤下；到期是自动失效。三者别混成一个「删」字，否则想撤一次误写时，连当初为什么写错都查不回来了。

## 再往下追两层

:::ask 追问一
那干脆设个短一点的有效期，到点全清掉，不是最省事？
:::

不省事，还会把成本推到别处。稳定事实之所以值得长期记，正是因为它不该反复重问；给它配个很短的生存时长，就等于每次会话都得重新问一遍「您偏好什么格式」，用户烦，系统也多走许多轮。合理的做法是按类别配不同的生存时长：一次性的临时取值给短的、到点自动走；确认过的稳定事实给长的、甚至不设到期，改由标错和撤销来管；涉及敏感字段的根本别往里放。另外要分清「退出」和「作废」：作废更像是给一条声明打标记、留着版本链以便回溯，见[冲突消解与版本](./k071-conflict-resolution.md)；到期清除是另一回事。把两者分开，才不会为了撤一次误写把审计线索一起删光。

:::ask 追问二
那扫描该在什么时候做？
:::

关键是守住一条性质：取回时看到的必须都是还活着的。所以最稳的位置是在「取回之前」过一遍，其次才是定时跑一遍；只在写入时判断一次是不够的，因为条目会随时间过期，写入那一刻它还活着。扫描本身要写成可反复执行的动作：同一批数据跑一次和跑两次，剩下的内容完全一样。下面那段代码就把时间做成一个显式传入的数，而不是去读机器上的真实时钟，这样断言才可复现——同一个 `now` 永远得到同一个结论。至于哪些内容压根不该进来，得在更前面拦住：写入门槛见[写入判定：什么时候该记](./k070-write-decision.md)，敏感字段与外来内容的处理见[隐私脱敏、同意与记忆污染](./k074-memory-privacy.md)；取回时按什么顺序摆、限几条，见[召回排序与相关性](./k072-memory-recall.md)。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，实现「到期自动失效、标错即停用、主动撤销」三类退出，并验证稳定事实会留下。时钟用显式传入的整数，保证可复现。复制成 `.py` 直接运行会打印清理结果。

```python
from dataclasses import dataclass


@dataclass
class MemoryItem:
    key: str
    value: str
    created: int
    ttl: int                 # 生存时长；到期即失效
    wrong: bool = False        # 被标记为错误信息


class ForgettingStore:
    def __init__(self, now):
        self.now = now
        self.items = []

    def put(self, key, value, ttl, created=None, wrong=False):
        self.items.append(MemoryItem(key, value,
                          self.now if created is None else created,
                          ttl, wrong))

    def expire(self):
        """三类退出：到期、标记错误、手动撤销。"""
        def alive(it):
            if it.wrong:
                return False
            return self.now - it.created < it.ttl
        before = len(self.items)
        self.items = [it for it in self.items if alive(it)]
        return before - len(self.items)

    def drop(self, key):
        self.items = [it for it in self.items if it.key != key]

    def live_keys(self):
        return [it.key for it in self.items]


if __name__ == '__main__':
    store = ForgettingStore(now=100)
    store.put("临时令牌", "abc", ttl=5, created=90)     # 已过期
    store.put("用户时区", "东八区", ttl=1000)            # 长期有效
    store.put("误记格式", "XYZ", ttl=1000, wrong=True)   # 标错
    store.put("旧偏好", "A", ttl=1000)

    removed = store.expire()
    keys = store.live_keys()
    assert removed == 2                    # 过期的 + 标错的都被清走
    assert "临时令牌" not in keys
    assert "误记格式" not in keys
    assert "用户时区" in keys              # 未过期稳定事实保留
    store.drop("旧偏好")                  # 主动撤销也走得通
    assert "旧偏好" not in store.live_keys()
    print("清理掉", removed, "条；存活：", store.live_keys())
    print("通过 4/4 项")
```

1. `MemoryItem` 用 `@dataclass` 描述一条记录：`created` 是写入时刻，`ttl` 是允许存活的时长，`wrong` 是被标记为错误的开关。把这三样跟着记录一起存，退出判断才有依据，不用临场猜。
2. `ForgettingStore.__init__(now)` 把当前时刻当参数传进来，而不是读系统时钟：所有判断都基于这个显式数字，同一批数据每次运行结果一致，断言才写得稳。
3. `put` 里 `created` 允许显式指定，是为了能构造「一条已经过期」的记录；不传就取当前时刻。示例里「临时令牌」写入时刻是九十、当前一百、生存时长五，一眼可算出它早已到期。
4. `expire` 内部的 `alive`：标错的一律停用，其余按 `now - created < ttl` 判断是否还在有效期内。用列表推导重建可用集合，动作可反复执行、多跑一次结果不变。
5. `drop` 是第三类退出——主动撤销，按名字把条目移出；`live_keys` 只返回还活着的条目名，相当于取回前的那道过滤。
6. 四条构造数据分别覆盖已过期、长期有效、被标错、待主动撤销；五条断言钉住「清掉两条」「两类确实不在」「稳定事实留下」「撤销生效」。末尾 `print` 打出清理条数与存活列表供核对。

## 踩过的坑与边界

- **压根没有生存时长**：现象是三个月前一句误记还在影响回答 → 原因是只加不删，错误没有退出通道 → 写入时按类别配上有效期，取回前统一扫描一遍。
- **给稳定事实也配短有效期**：现象是用户每次来都被重新问一遍偏好 → 原因是把「该清理」做成了「一律定期清空」 → 临时取值给短时长，确认过的稳定事实不设到期、改由标错与撤销管理。
- **把撤销做成物理删除且不留痕**：现象是想查「这条为什么没了」查不回来 → 原因是「作废」「到期」「清除」混成一个动作 → 作废打标记留版本链，到期才真正移出可用集合。
- **扫描时读真实系统时钟**：现象是本地跑通、换个时间跑断言就挂 → 原因是判断依赖了不可控的外部状态 → 把时刻做成显式传入的量，构造场景可复现。
- **只在写入时判断一次**：现象是写入时还活着的条目，过了一阵过期了却仍在被取回 → 原因是没在取回前复检 → 把扫描放到取回路径上，并写成可反复执行的动作。

边界也讲清楚：退出机制是为「会过期、可能写错、或涉及敏感字段」的内容准备的。若某条事实本来就长期稳定、且经过明确确认，给它频繁设到期只会增加重记的开销。还有一类内容根本不该走到这一步——写入前就该被挡住，见[写入判定：什么时候该记](./k070-write-decision.md)；「全存下来为什么也不叫记忆」，可回到[记忆不是日志](./k065-memory-vs-log.md)再对一遍。

## 三句话小结

遗忘是给过期、标错、被撤销的内容设计明确的退出机制，让取回时看到的都是还活着的条目。
做法是写入时按类别配生存时长，取回前做一次可反复执行的扫描，并把作废、到期、撤销分成三个动作。
事实本身长期稳定、且已经过明确确认时，别频繁设到期，改由标错与撤销来管理。

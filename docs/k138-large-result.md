# 超大工具结果裁剪与二级工具

## 场景提问

你给助手接了一个查订单的工具，测试时用只有三条记录的小表，一切正常。换成真实数据后，用户随口问「上个月华东区有哪些订单金额异常」，工具一次查回两万行、好几兆文本。你把这坨东西原样塞回对话，结果下一轮直接报错说超出长度上限；好不容易截短一点塞进去，模型又开始答非所问——它把注意力摊在两万行里，反而漏掉了真正异常的那几行，还因为反复带着这坨文本多花了不少钱。更别扭的是，用户接着追问「把第 3000 行附近那几笔展开看看」，你发现被截掉的原文根本没地方找了。明明工具已经把数据取回来了，怎么「取回来」反而成了一场灾难？

## 破误解

**不是模型读不下长文本就该换个更贵的模型，是把「工具返回什么」直接当成了「该进上下文什么」，中间少了一道裁剪和一层按需取回。**

先把一个常被忽略的事实摆出来：工具的结果大小和上下文能装多少，是两件互不相干的事。工具背后可能是一张表、一个日志系统、一次批量查询，它返回两万行是它的本职；而上下文窗口（context window，模型一次能读进去的文本上限，用 token 计，token 是文本被切分后的最小计费与处理单位）是另一头有限的资源。很多人默认「工具返回了就该全给模型看」，于是把两万行直接往窗口里倒，等于让一个容量固定的杯子去接一整桶水。溢出只是最表面的症状，更隐蔽的伤害有三层：一是长度超限直接报错；二是就算截到能塞下，无关行把注意力摊薄，真正要紧的几行权重反而被压低；三是这坨文本会在后续每一轮被反复带上，成本按轮累积，见 [上下文预算表](./k041-context-budget.md)。

正确的拆法是把「取回」分成两级。第一级工具不返回全量，只返回一份被裁到预算内的摘要，外加两样东西：一个总数（让模型知道全量有多大），一个句柄（handle，一个短标识，凭它能找回落在外面的完整原文）。完整原文不进上下文，而是落到外置的地方——可以是磁盘文件、一个键值存储、或本次会话里的一块暂存区。第二级工具则是专门用来「按句柄加区间，把需要的那一小段原文再取回来」的工具，它接收的参数形如「句柄、起始位置、取几条」或「句柄、某个筛选条件」，返回的只有那一小段。这样模型先看到摘要判断「全量大概是什么、我该往哪儿看」，再决定要不要用第二级工具去取细节，全程进窗口的文本始终很小。

这里要分清三种听起来像、其实完全不同的做法。裁剪（truncation）是把长文本截短，被截掉的部分如果没别处留存，就是永久丢了；落盘（把完整原文写到上下文之外、可随时取回的地方）保证「没进窗口≠不存在」；二级工具则是在前面两者之上，给模型一个可控的取回入口。只裁剪不落盘，用户一追问细节就抓瞎；只落盘不给取回入口，等于把数据存进了没有钥匙的柜子；三者齐了，才既撑不爆窗口、又丢不了原文、还能按需展开。这套「先给摘要、需要再拉细节」的思路，和 [推与拉](./k140-push-pull.md) 里讲的分工是同一回事：不该一次把全部推给模型，而该让模型有能力主动拉。

## 生活类比

把它想成去档案馆查一批老档案。管理员不会把整整一库房的卷宗全搬到你桌上——桌子就那么大，摊开了连走路的地方都没有。他先推来一张清单：这批一共多少箱、每箱大概是什么年份、他随手抽出三份放在桌角给你翻两眼，清单上还写着一个编号。你看完清单，心里有了数，说「把第 12 箱里 1988 年那几份拿给我」，管理员便凭那个编号进库，只抱回你要的那一小叠。剩下的卷宗始终在库里，一份没丢，也一份没堆到你桌上。

对应关系很具体：那一库房卷宗，就是工具查回的全量结果；桌面，就是容量有限的上下文窗口；那张写着总数与三份样例的清单，就是裁剪后的一级摘要；清单上的编号，就是句柄，凭它能定位到外置的原文；管理员按你的要求进库取那一小叠，就是二级工具按「句柄加区间或条件」精确取回片段。这里最值得品的一点是「没搬上桌」和「不存在」是两回事：卷宗好好待在库里，只要有编号就随时能取，所以摘要里必须带总数和句柄，而不能只甩一句「内容太多已省略」。

这个比喻还点出两个容易翻车的细节。其一，管理员第一次给你的绝不能是「前三千箱全搬上桌、后面的扔了」——那是只裁剪不落盘，等你真要第 12 箱时，它已经被当垃圾清走了。其二，也不能图省事把每次都取回的片段又原样贴回清单、越积越厚，那样桌子迟早还是被堆满，这正是 [上下文膨胀](./k049-context-bloat.md) 讲的现象。清单要一直保持薄，取回的片段用完就该能收回去。

## 自绘示意图

:::figure 一次大结果的处理链路
@flow
工具查回全量|裁出一级摘要|原文落盘留句柄|二级按区间取|片段进窗口
:::

五格是一条链，重点在第三格「原文落盘留句柄」：它把「全量」和「进窗口」这两件事彻底拆开。少了这一格，第一格查回多少就得往窗口塞多少；有了它，后面两格才能做到「先看摘要、再按需取一小段」。注意最后一格进窗口的是「片段」，不是「全量」。

:::figure 一级摘要要带齐的四样
@stack
总数::告诉模型全量有多大，好判断值不值得细看
样例::给前几行的原样，够认出字段与格式
句柄::一个短标识，凭它能找回落在外面的原文
取回方式::写明二级工具叫什么、要传哪些参数
:::

四格里最常被漏掉的是「总数」和「取回方式」。没有总数，模型无法分辨「这就是全部」还是「只是冰山一角」，容易拿三行样例当全量来下结论；没有取回方式，句柄就成了没有钥匙的柜门，模型知道有原文却不知道怎么拿。

:::figure 两种做法的差别
@compare
全量直接回传::一次就顶满窗口|注意力被无关行摊薄|细节无处可追
裁剪落盘加二级::进窗口的始终很小|原文无损留在外面|按需精确取回
:::

左边是把「工具返回什么」等于「该进上下文什么」的朴素做法，顺风时（结果很小）最省事，一旦结果变大就全线崩；右边多了一道裁剪和一层取回入口，换来的是窗口平稳、原文不丢、还能按用户追问随时展开。

## 层层追问

:::ask 那如果我只是把结果截断到能塞下的长度，不落盘也不做二级工具，不是更简单吗？
:::

确实更简单，但代价是「丢掉的部分再也回不来」。截断是有损操作，被砍掉的行如果没在别处留存，就等于永久删除；而用户偏偏最爱追问细节——「第 3000 行附近展开看看」「刚才那批里金额最大的三笔是哪几笔」，问的往往正是被截掉的那一段。落盘加句柄的做法，让「没进窗口」只表示「暂时没桌面放」，不表示「不存在」，这两者的差别全在有没有一个可凭之取回的标识。可以顺着再想一层：那是不是可以干脆分页、让模型一轮轮把全量都读一遍？也不行——那就把裁剪省下的长度又原样花回去了，注意力重新被两万行摊薄，成本按轮累积，等于绕一圈回到原点。真正的分寸是「按需」：先给足以判断的摘要，模型要哪段才取哪段，取回的片段用完能收回，见 [上下文分层](./k042-context-layers.md) 与 [检索片段压缩](./k045-retrieval-compression.md)。把「数据取回」和「数据进窗口」分开管，是这套做法的骨头；原文该以什么结构存、取回片段怎么保证和原文一致，可对照 [结构化状态](./k046-structured-state.md) 与 [数字完整性](./k124-number-integrity.md)。

:::ask 那如果摘要本身也是模型生成的，会不会把关键数字写错、反而带偏后面所有判断？
:::

这一问很要紧，因为它把风险从「长度」推到了「可信度」。如果一级摘要是让模型读完两万行再自由发挥写出来的，那摘要里的总数、金额、日期都可能被写错，而后面对话全建立在这份摘要上，错一处就一路错下去。稳妥的做法是：能由程序确定的字段，绝不让模型去「概括」——总行数直接数出来，样例直接取原文的前几行原样搬运，句柄直接由存储层生成，这些都该是确定性的代码片段，而不是一段自然语言总结。摘要里真正留给模型的，只有「下一步该不该取、取哪一段」这个判断，不是数字本身。这条「可程序确定的部分用确定性代码、只把判断交给模型」的分工，在 [属性断言](./k088-property-assertion.md) 和 [工具结果回传](./k035-tool-result.md) 里也有呼应；如果确实需要压缩原文成一段话，那也得留一份可核对的原文在，见 [摘要压缩](./k044-summary-compression.md) 与 [压缩校验](./k048-compression-verify.md)。再补一层：句柄必须稳定且可重复取回，同一个句柄两次取同一区间应得到完全相同的内容，否则用户追问时前后对不上，这和 [幂等落盘](./k107-idempotent-persist.md) 讲的是同一套稳标识思路。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「全量落盘、一级只回摘要与句柄、二级按区间精确取回」完整演示一遍，结尾用一组断言逐条验证。全量结果是本地构造的确定性记录，取回结果可以手工推算、完全可复现；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。它演示的是裁剪、落盘、取回这三件事的性质，不是任何真实数据库或存储组件的实现。

```python
import json


def make_big_result(n):
    """构造一份确定性的大结果：n 行记录，每行有编号、金额、标签。"""
    return [{"id": i, "amount": i * 7 % 100, "tag": "row-%04d" % i}
            for i in range(n)]


def spill(store, rows, handle):
    """把完整原文落到外置存储（这里用 dict 模拟），只登记一次，返回句柄信息。"""
    store[handle] = [dict(r) for r in rows]  # 存副本，避免之后被改动
    return {"handle": handle, "total": len(store[handle])}


def summarize(rows, handle, head=3):
    """一级视图：只回总数、前 head 行样例、句柄、取回方式；绝不回传全量。"""
    return {
        "handle": handle,
        "total": len(rows),
        "sample": rows[:head],
        "has_more": len(rows) > head,
        "how_to_fetch": "用 fetch_range(handle, start, size)",
    }


def fetch_range(store, view, start, size):
    """二级工具：按句柄 + 起始位置 + 条数，精确取回一小段原文。"""
    rows = store.get(view["handle"])
    if rows is None:
        return []
    if start < 0 or size <= 0:
        return []
    return rows[start:start + size]


def main():
    store = {}
    rows = make_big_result(500)
    info = spill(store, rows, "h-001")
    view = summarize(rows, info["handle"], head=3)

    checks = [
        ("全量确有 500 行", info["total"] == 500),
        ("落盘后原文无损留存", len(store["h-001"]) == 500),
        ("一级视图只带 3 行样例", len(view["sample"]) == 3),
        ("一级视图标出还有更多", view["has_more"] is True),
        ("一级视图带总数", view["total"] == 500),
        ("一级视图带句柄", view["handle"] == "h-001"),
        ("一级视图不含全量字段", "rows" not in view),
        ("样例与原文前 3 行一致", view["sample"] == rows[:3]),
        ("一级视图远小于全量",
         len(json.dumps(view, ensure_ascii=False))
         < len(json.dumps(rows, ensure_ascii=False)) // 10),
    ]

    seg = fetch_range(store, view, 100, 5)
    checks.append(("二级按区间取回 5 行", len(seg) == 5))
    checks.append(("取回内容对应原文第 100 起",
                   seg[0] == rows[100] and seg[-1] == rows[104]))
    checks.append(("越界起点返回空", fetch_range(store, view, 9999, 5) == []))
    checks.append(("负起点返回空", fetch_range(store, view, -1, 5) == []))
    checks.append(("零条数返回空", fetch_range(store, view, 0, 0) == []))
    checks.append(("未知句柄返回空",
                   fetch_range(store, {"handle": "nope"}, 0, 5) == []))
    checks.append(("同一区间重复取回一致",
                   fetch_range(store, view, 100, 5) == seg))
    checks.append(("二级取回不改动原文",
                   fetch_range(store, view, 0, 500) == rows))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `make_big_result` 用一行列表推导构造 500 行记录，每行的编号、金额、标签都由行号确定性算出（`amount` 用 `i * 7 % 100`），不依赖随机数，所以任何一次运行结果都一模一样，便于手算核对。
2. `spill` 代表「原文落盘」这一步：把完整结果存进 `store`（这里用字典模拟磁盘或键值存储），存的是 `[dict(r) for r in rows]` 这样的副本，防止后续对 `rows` 的改动污染已落盘的原文。它只返回句柄和总数，不把任何一行塞回对话。
3. `summarize` 是一级视图：返回的字段里，`total` 是数出来的总数、`sample` 是原文前 3 行原样搬运、`how_to_fetch` 写明二级工具怎么调——这些全是确定性内容，刻意不让模型去「概括」，正是为了避开摘要写错数字的风险。注意它完全没有 `rows` 这个键，断言里专门验了这一点。
4. `fetch_range` 是二级工具：先按 `view["handle"]` 从 `store` 取回原文，句柄不存在就返回空列表；再对 `start < 0` 或 `size <= 0` 这类非法参数挡一道；最后用切片 `rows[start:start + size]` 精确取回一小段。它返回的只有这一段，不会把全量带出来。
5. `main` 第一组断言验证「全量与一级视图」：全量 500 行确实无损落盘、一级视图只有 3 行样例、带总数带句柄标了「还有更多」、且序列化后的体积不到全量的十分之一。`json`（JavaScript Object Notation，一种纯文本的数据表示格式）在这里只用来量体积。
6. 第二组断言验证「按需取回」：从原文第 100 行起取 5 行，内容与 `rows[100]` 到 `rows[104]` 逐一对应；越界起点、负起点、零条数、未知句柄都安全返回空而不报错；同一个区间取两次结果完全一致（幂等）；最后把整段原文取回，仍与最初的 `rows` 相等，证明落盘与取回全程无损。
7. 结尾 `passed` 统计通过项、逐条打印结果，再用 `assert` 保证任何一条性质被破坏都会以非零状态退出。整段只用了 `json` 这一个标准库模块，没有文件读写、没有网络、没有外部依赖。

有一处要如实说明：这里用字典代替了真实的外置存储、用构造的 500 行代替了两万行数据库结果、用简单切片代替了真实的分页查询，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手工推算。它演示的是「全量与进窗口分离、句柄稳定、取回无损」这几条性质，不是任何具体存储或查询接口的实现；代码本身经过逐行静态复核到「复制即跑、逻辑自洽」，并未在此环境里实际启动执行。

## 踩坑与边界

- **把工具返回直接塞回上下文**：现象是结果一大就超长报错，或勉强塞下后模型答非所问 → 原因是把「工具返回什么」当成了「该进上下文什么」 → 先裁成摘要，原文落盘留句柄，见 [上下文预算表](./k041-context-budget.md) 与 [上下文窗口](./k003-context-window.md)。
- **只裁剪不落盘**：现象是用户一追问被截掉的那几行，原文已无处可找 → 原因是截断是有损的，丢了就真丢了 → 全量务必存到上下文之外并给句柄，细节见 [工具结果回传](./k035-tool-result.md)。
- **摘要里的数字交给模型概括**：现象是总数、金额被写错，后面整段对话跟着错 → 原因是把本可程序确定的字段交给了自然语言生成 → 总数直接数、样例原样搬、句柄由存储层给，见 [数字完整性](./k124-number-integrity.md)。
- **句柄不稳定或取回有副作用**：现象是同一区间两次取回内容不一致，用户追问前后对不上 → 原因是取回时顺手改了原文或句柄每次现生成 → 落盘存副本、句柄固定、取回只读，见 [幂等落盘](./k107-idempotent-persist.md)。
- **分页把全量又读了一遍**：现象是窗口没炸，但成本按轮上涨、注意力仍被摊薄 → 原因是把裁剪省下的长度原样花回去了 → 坚持按需取回、片段用完能收，见 [上下文膨胀](./k049-context-bloat.md) 与 [检索片段压缩](./k045-retrieval-compression.md)。

还要说清一条边界：这套做法不是所有工具结果都需要。当结果本来就小、几行就能完整带上时，多加一层落盘和二级工具反而把简单事做复杂了，直接回传更清爽；它真正值钱的场景，是结果大小不可控、且用户很可能就其中局部追问的时候。另外，一级视图里那个「总数」要和落盘的真实条数一致，否则模型会误判「值不值得细看」，这和 [元数据过滤](./k060-metadata-filter.md) 里「先靠可靠字段缩小范围」是同一套思路；若想从整体上看上下文该怎么分层管理，可对照 [上下文分层](./k042-context-layers.md)。

## 三句话小结

超大工具结果裁剪与二级工具，是把「工具查回的全量」和「真正进上下文的内容」拆开：全量无损落在外面，一级只回摘要、总数与句柄，二级按区间或条件精确取回片段。

关键做法是能由程序确定的字段一律确定性生成、句柄稳定且取回只读无损、进窗口的始终是摘要加少量片段、取回的片段用完能收回。

当结果本来就小、几行就能完整带上，或用户根本不会就局部追问时，不必硬套落盘与二级工具；但只要结果大小不可控又可能细问，就别再把全量直接倒进窗口。

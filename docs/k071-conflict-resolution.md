# 冲突消解与版本：新旧事实打架时别急着覆盖

## 场景：同一个问题，两次回答用了两个值

库里关于「用户所在时区」静静躺着两条：一条是很早以前从设置里读来的「东八区」，另一条是上周闲聊时用户随口说的「西五区」。助手这次抽到东八区、下次抽到西五区，同一个问题给出两个答案，用户觉得它记性时好时坏。你打算清理一下，顺手写了句「用新的覆盖旧的」，结果更麻烦：那句闲聊把正式设置顶掉了，而且原来的值被抹得干干净净，想查「到底什么时候改过、凭什么改」已经查不回来了。你原本只想留一个准数，却把整个过程弄丢了。

## 先破一个最常见的误解

**不是「该留哪条」难选，是「用新的覆盖旧的」这个动作本身就不对。** 覆盖会做两件坏事：它把历史抹平，事后既说不清曾经约定过什么，也没法把一次误写撤回去；它还把裁决压在了写入的那一瞬间，而那一瞬间往往信息最少——你还不知道这条来路可不可靠、以后会不会被发现是错的。正确的做法是只追加：每次新观察都存成一条带版本的声明，谁也不删谁；等真正要用的时候，再按明确的规则从版本链里挑出「当前有效值」。裁决依据主要是三样：时间戳（什么时候说的）、来源权威级别（这条从哪来、有多可信）、以及显式撤销（有没有一份明确的作废声明）。这三点合起来，才回答得了「现在该信哪条」；单独拿「新」这一个字，是回答不了的。

## 用生活里的事打个比方：合同原件与补充协议

一份正式签过的合同，原件不会被撕掉重写。后来要变更，就附一份补充协议，写明签署日期、由谁签的；要是某份补充协议签错了，再出一份声明把它作废，而不是拿涂改液把原件抹了。真到要判断「现在按哪条执行」，得看三件事：哪份日期在后、签署方有没有这个权限、有没有一份明确的作废声明。对应关系逐条对一遍：合同原件加一串补充协议就是版本链；签署日期就是时间戳；签署方权限就是来源权威级别；那份作废声明就是显式撤销；法官据这三点下结论就是「裁决当前有效值」。为什么不能拿涂改液直接改？改完你再也说不清「当初到底约定的是什么」，也没办法只把某一次误签撤掉而不动其余各份。保留全部版本看着占地方，换来的却是两样很实在的能力：能回溯、能撤销。

## 画出来看

先看一条新观察进来之后，系统怎么把它变成一次「追加」而不是「覆盖」。

:::figure 一条新事实如何进版本链
@flow
新观察|只追加成新版本|按权威与时间裁决|显式撤销|得出当前有效值
:::

「只追加成新版本」这一格是整套做法的地基：只要写入端保证不删旧条目，后面的裁决和撤销才有东西可用。「显式撤销」也画在链上，是想强调它同样是一条记录，不是一次删除。再看两种处理方式的差别。

:::figure 两种处理矛盾的方式
@compare
直接覆盖::旧值被抹掉|无法回溯|误写难撤回
留版本链::历史完整|可裁决可撤销|要定裁决规则
:::

右边最后那个要点是留版本链的代价，得老实承认：历史留全了，就必须把「凭什么信这条」写成明确的规则，不能临场拍脑袋。规则本身反而是好事——它可测、可回滚、能被质疑。

## 再往下追两层

:::ask 追问一
那「越新越对」这条规则，简单明了，为什么不行？
:::

因为它把「什么时候说的」误当成了「有多可信」。用户上周随口一句「这次先按西五区算」，未必比很久以前从正式设置里读出来的东八区更算数；一次工具报错里带出来的旧取值，也可能因为是最近写入的而被顶成有效值。稳妥的次序是先比来源权威级别、再比时间戳：来自正式设置或明确声明的，优先于从文本里推测的；同级别之间才让较新的那条胜出。权威级别怎么定，得在写入时就把「从哪来」记清楚，见[写入判定：什么时候该记](./k070-write-decision.md)；把分散的版本收敛成某个对象的一份记录，见[实体摘要与画像更新](./k069-entity-summary.md)。裁决规则要写成一段能单测的代码，而不是一句口号。

:::ask 追问二
那撤销之后，那条错误的记录还留着吗？
:::

留着，这正是它和「删除」的区别。撤销是给那条打一个「已作废」的标记，版本链一条不少，随时能说清「这条什么时候、因为什么被撤了」；裁决时把带标记的版本排除掉，结果自然回退到剩下那些里最可信的一条。什么时候才真的物理清除？那是另一套机制的事：过了有效期、被确认写错、或涉及敏感字段，需要明确的退出通道，见[遗忘、过期与 TTL](./k073-forgetting.md)。把「作废」和「清除」分成两个动作，就不会出现「想撤一次误写、结果连审计线索一起删光」的情况。另外，被撤回的若是外部带进来的内容，还要回头看看当初为什么能写进来，见[隐私脱敏、同意与记忆污染](./k074-memory-privacy.md)。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，实现一个「只追加、按权威与时间裁决、可显式撤销」的版本化记忆，用构造用例验证四条性质。复制成 `.py` 直接运行会打印当前有效值。

```python
from dataclasses import dataclass


@dataclass
class Claim:
    key: str
    value: str
    stamp: int          # 时间：越大越新
    authority: int     # 来源权威级别：越大越可信
    revoked: bool = False


class VersionedMemory:
    def __init__(self):
        self.claims: list = []

    def add(self, key, value, stamp, authority):
        # 只追加，不覆盖：每次观察都是一条带版本的声明
        self.claims.append(Claim(key, value, stamp, authority))

    def revoke(self, key, value, stamp):
        for c in self.claims:
            if c.key == key and c.value == value and c.stamp == stamp:
                c.revoked = True

    def resolve(self, key):
        live = [c for c in self.claims if c.key == key and not c.revoked]
        if not live:
            return None
        # 先比权威，再比时间；两者都相同保留后写入的
        return max(live, key=lambda c: (c.authority, c.stamp)).value


if __name__ == '__main__':
    mem = VersionedMemory()
    mem.add("时区", "东八区", stamp=1, authority=1)
    mem.add("时区", "西五区", stamp=2, authority=1)   # 新但同权威
    # 断言 1：新事实没有覆盖旧的，版本链完整保留
    assert len(mem.claims) == 2
    # 断言 2：同权威下较新的胜出
    assert mem.resolve("时区") == "西五区"
    # 断言 3：更高权威的旧事实反超
    mem.add("时区", "东八区", stamp=3, authority=5)
    assert mem.resolve("时区") == "东八区"
    # 断言 4：显式撤销让该版本失效，结果回退到次优
    mem.revoke("时区", "东八区", stamp=3)
    assert mem.resolve("时区") == "西五区"
    print("当前有效值：", mem.resolve("时区"), "；版本链共", len(mem.claims), "条")
    print("通过 4/4 项")
```

1. `Claim` 用 `@dataclass` 描述一条声明：除了键和值，还带上时间戳、来源权威级别和一个 `revoked` 作废标记。这三个附带字段就是上一节说的裁决依据，缺一个都会让裁决变成猜测。
2. `VersionedMemory.add` 里只有一句 `append`：写入端保证「只追加不覆盖」，这是整套机制的地基。它连「有没有同名的旧值」都不查，因为查了就容易顺手改掉。
3. `revoke` 遍历找到匹配的那条，把 `revoked` 置为真：注意它不删除任何元素，只是打标记，所以版本链始终完整。
4. `resolve` 先把带作废标记的排除，再用 `max(..., key=lambda c: (c.authority, c.stamp))` 挑当前有效值：元组比较先比权威级别、再比时间戳，正好实现「先比来源、同级才比新旧」。返回的是值，历史一条没动。
5. 四步构造：先写同权威的两条，再补一条更高权威的，最后把那条撤销。断言依次钉住「版本没被覆盖」「同权威较新胜出」「高权威反超」「撤销后回退到次优」。
6. 末尾 `print` 把最终有效值和版本链条数打出来：一眼能看到「有效值是一个、历史有三条」，这正是留版本链想要的效果。

## 踩过的坑与边界

- **用新值直接覆盖旧值**：现象是想查「什么时候改过、凭什么改」时查不回来 → 原因是写入端把历史抹平了 → 改成只追加，取用时再裁决。
- **只按时间裁决**：现象是一句闲聊把正式设置顶掉了 → 原因是把「新」误当成「可信」 → 先比来源权威级别、同级别才比时间戳，并在写入时记清来路。
- **把撤销做成物理删除**：现象是撤回一次误写之后，连审计线索也没了 → 原因是「作废」和「清除」混成一个动作 → 撤销只打标记，清除另走过期与退出通道。
- **不存来源与时间**：现象是两条矛盾摆在一起，谁也说不出该信谁 → 原因是落盘时省了附带字段 → 时间戳、来源、权威级别随每条一起存，缺一不可。
- **裁决规则散落在各处**：现象是同一批数据，不同调用点算出的有效值不一样 → 原因是各处各写了一套判断 → 收拢到一个具名函数里，写成可回归的断言；取回后按什么顺序摆，见[召回排序与相关性](./k072-memory-recall.md)。

边界也讲清楚：留版本链适合「会反复被引用、且可能被推翻」的稳定事实。若某条内容本来就是一次性的临时取值，或者属于敏感字段、外部带进来的内容，就别给它建版本链——前者不必留，后者根本不该进来，见[记忆不是日志](./k065-memory-vs-log.md)。另外，版本留全了会占空间，所以还要配一套明确的退出机制，把确实该清的清掉。

## 三句话小结

冲突消解是让新旧事实只追加成版本链，取用时按时间、来源权威级别与显式撤销裁决出当前有效值，而不是覆盖。
做法是写入端只追加，裁决收拢到一个具名函数，撤销只打标记，让回溯和撤回都留得下。
内容只是一次性临时取值、或属于本就不该写进来的敏感与外部信息时，不必建版本链。

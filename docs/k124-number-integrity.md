# 数字口径与统计范围

你在项目描述里写「准确率 95%」，看起来比「效果不错」扎实得多，心里也踏实一点。面试时对方却只问了三句：「95% 是拿多少条算出来的？算的是哪一种正确？统计的是哪一段时间、哪一批用例？」你发现自己一个都答不上——那个数字是跑过一次之后凭印象写的，连分母是多少都没记。

**不是数字不够漂亮，是它缺了口径、范围、时间窗，成了核对不了的孤证。** 一个能被信的数字，必须能说清「分子是什么、分母是什么、统计了哪些、什么时候统计的」；说不清这四样，写得再精确也只是一个形容词换了件衣服。

先把词说清。口径指这个指标到底怎么算：分子是什么、分母是什么、什么才算「成功一次」。统计范围指参与计算的用例集合，比如本地构造的若干条固定用例。时间窗指这些数据来自哪一次运行、哪一段时间。分母（denominator）是比率里作除数的那个总量，分子（numerator）是被计数的那部分。可核对指别人按你写的方法重跑，能得到同样的数。评测（evaluation）指用一批用例批量跑、按指标打分来判版本好坏的做法。断言（assertion）是程序里一条「必须成立」的检查。智能体（Agent）是能自己决定下一步并调用工具的程序。这些词先分清，才不会把「一个数字」和「一次可复现的统计」混为一谈。

## 一、生活类比：体检报告上的一个百分比

想象体检报告写着「某项指标合格率 95%」。单看这个数你不会当真，一定会翻到附注：这一项一共测了多少人、合格怎么定义、测的是哪天的样本、有没有把复查的算进去。如果附注写着「本地 50 份样本，40 份达标，单次采样」，你立刻能自己算一遍：40 除以 50 正好是八成，跟报告写的对得上，这才放心。

对应关系是：合格率对应项目里的成功率，50 份样本对应分母与统计范围，「达标」的定义对应口径，「哪天采样」对应时间窗，你自己拿计算器复核对应可复跑的核对。**报告上那个数之所以可信，不是因为它带了百分号，而是因为附注让人能把它重算出来。** 反过来，一个没有附注的 95%，无论写得多工整，都只是让人选择信或不信，而不是让人判断。

## 二、一条数字要带齐哪几样

把类比收成可操作的清单：分母口径、统计范围、时间窗，三样缺一不可；再加一条内部自洽——分子不能大于分母，百分比要和分子分母算得对得上。前两样管「这个数怎么来的」，第三样管「这批数什么时候有效」，自洽检查管「有没有算错或写错」。四样齐了，数字才从印象变成可核对的记录。

:::figure 一条数字要带齐的四样
@stack
分母口径::说清分母是什么、什么算成功一次，别只给结果
统计范围::写明参与计算的用例集合与排除条件
时间窗::标明来自哪次运行、哪一段时间
内部自洽::分子不超分母，百分比与二者算得对
:::

这里要特别区分「统计范围」和「时间窗」：范围回答「算了哪些」，时间窗回答「这些数据是什么时候产生的」。同一批固定用例，在不同版本、不同运行里会得到不同的数，不标时间窗就没法做回归对比。另一个常见混淆是把「每次调用的成本」当成「每成功任务的成本」——口径一换，数字的含义就全变了，所以口径必须写在数字旁边，不能留给读者猜。三要素陈述里怎么把这类数字嵌进句子，见[约束、权衡与可验证结果](./k123-tradeoffs.md)。

:::ask 那如果数据是构造出来的、不是真实业务跑出来的呢？
那就照实写「本地构造的 N 条固定用例」，别让它看起来像真实流量。构造数据完全可以拿出来讲，只要范围标清楚：它说明「在这些条件下脚本能跑通」，不说明「在真实环境里也是这个数」。**诚实标明来源，构造样例一样有价值；含糊其辞地让它像实测，反而会把整段描述的可信度拖下去。** 全站都要求举例用可复现的构造场景，正是这个道理。
:::

:::ask 那如果同一批用例，换个版本数字变好了，能直接写「提升多少」吗？
先确认两次统计的口径、范围、时间窗是不是一致。若一次算的是「单轮成功」、另一次算的是「整单成功」，或者范围里悄悄换了用例，两个数字根本不能相减，写出来就是一个看着精确、其实无意义的差值。正确做法是把两次记录并排放：版本、用例集合、指标定义、各自的值，让人看到变化发生在同一把尺子上。**能对比的前提是「同一口径」，不是「都有数字」。** 这类记录留痕怎么支撑答辩，见[四层追问链与转行者三问](./k125-followup-chain.md)。
:::

:::figure 光秃秃的数字与带口径的数字
@compare
只给结果::95% 一个孤数|没说分母是谁|不知来自哪批用例
带齐口径::分子分母写明|范围时间窗齐全|可当场重算核对
:::

左边三点其实是同一个问题的三面：只有结果 → 分母不明 → 无法定位到具体用例，于是被追问时只能含糊。右边三点也是连锁的：写明分子分母 → 范围与时间窗才有落点 → 别人才能当场重算。两种写法差的不多，就是一句附注，但可信度的差别很大。

## 三、把口径检查写成能跑的程序

下面的脚本零依赖、不需要账号、不需要联网。它把一条数字表示成「值 + 分子 + 分母 + 范围 + 时间窗」，逐项检查缺口，并验证百分比与分子分母是否对得上。所有数字都是本地构造的样例，不来自任何真实测量。

```python
# k124.py —— 数字口径与统计范围的体检（零依赖，python k124.py）


def claim(name, value, numerator=None, denominator=None, scope="", window=""):
    return {"名": name, "值": value, "分子": numerator, "分母": denominator,
            "范围": scope, "时间窗": window}


def audit(c):
    problems = []
    if c.get("分母") is None:
        problems.append("缺分母口径")
    if not c.get("范围"):
        problems.append("缺统计范围")
    if not c.get("时间窗"):
        problems.append("缺时间窗")
    d = c.get("分母")
    if d is not None and d <= 0:
        problems.append("分母必须为正")
    n = c.get("分子")
    if d and n is not None:
        if not (0 <= n <= d):
            problems.append("分子超出分母")
        elif abs(round(100.0 * n / d, 1) - c["值"]) > 0.05:
            problems.append("百分比与分子分母对不上")
    return problems


def cite(c):
    """把一条数字写成带口径、范围、时间窗的完整说法。"""
    return "%s %.1f%%（%d/%d；%s；%s）" % (
        c["名"], c["值"], c["分子"], c["分母"], c["范围"], c["时间窗"])


if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    bare = claim("准确率", 95.0)
    good = claim("单轮成功率", 80.0, numerator=40, denominator=50,
                 scope="本地构造的 50 条固定用例", window="单次本地运行")
    check("光秃秃的数字被指出三处缺口", len(audit(bare)) == 3)
    check("带口径、范围、时间窗的数字合格", audit(good) == [])
    check("分母为零会被拦下",
          "分母必须为正" in audit(claim("比率", 0.0, 0, 0, "构造", "单次")))
    check("分子大于分母会被拦下",
          "分子超出分母" in audit(claim("比率", 120.0, 60, 50, "构造", "单次")))
    check("百分比与分子分母对不上会被拦下",
          "百分比与分子分母对不上" in audit(claim("比率", 90.0, 40, 50, "构造", "单次")))
    line = cite(good)
    check("完整说法里含统计范围", "固定用例" in line)
    check("完整说法里含时间窗", "单次本地运行" in line)
    check("完整说法里含分母口径", "40/50" in line)
    print("通过 %d/%d 项" % (passed, total))
```

运行后打印每条断言与汇总：

```text
  [通过] 光秃秃的数字被指出三处缺口
  [通过] 带口径、范围、时间窗的数字合格
  [通过] 百分比与分子分母对不上会被拦下
通过 8/8 项
```

逐段解释关键行在做什么：

1. `claim` 把一条数字固定成六个字段：名字、值、分子、分母、范围、时间窗。分子分母默认为 `None`，正好表示「没写口径」，后面检查会把这个缺口抓出来。
2. `audit` 前三段依次查分母有没有、范围空不空、时间窗空不空，缺一项就往 `problems` 里记一条文字，而不是只返回真假——能点名缺什么才好补。
3. `d <= 0` 挡住分母为零或负数；随后 `0 <= n <= d` 挡住分子超出分母。这两条是内部自洽的底线，防止出现「120% 用 60/50 算出来」这类明显错误。
4. `abs(round(100.0 * n / d, 1) - c["值"]) > 0.05` 用分子分母反算百分比，跟写下来的值比对，差太多就判「对不上」。这是把「能不能当场重算」直接写成了断言。
5. `cite` 把合格的一条拼成「指标 值（分子/分母；范围；时间窗）」的完整说法，演示怎么把附注写进句子，而不是让读者去别处找口径。
6. 主程序构造了光秃秃的 `bare`、合格的 `good`，以及分母为零、分子超分母、百分比不符三条反例；`check` 用 `assert` 兜底，末尾打印 `通过 N/N 项`。

:::tip 每次评测顺手记全这几栏
别等写简历时再回忆分母是多少。**跑评测的当天就把版本、用例集合、口径、时间窗、值一起记下来**，后面做回归对比、答辩、排障都吃同一份记录，不用临场凑数字。
:::

## 四、踩坑与边界

- **只给结果**：现象是「准确率 95%」，被问「多少条算的」答不上 → 原因是没写分子分母与口径 → 怎么改：像 `cite` 那样把「40/50」和指标定义写在数字旁边。
- **口径偷偷换**：现象是两次版本对比的「提升」看着很大，细看一次算单轮、一次算整单 → 原因是两把尺子相减 → 怎么改：对比前先核对指标定义、用例集合是否一致，不一致就分开写。
- **构造数据装成实测**：现象是本地跑的样例被写得像真实流量，一追问来源就含糊 → 原因是没标统计范围 → 怎么改：照实写「本地构造的 N 条固定用例」，并说明它只证明这些条件下跑得通。
- **分子大于分母**：现象是比率超过百分之百却没被发现 → 原因是数字凭印象填，没做自洽检查 → 怎么改：加 `0 <= n <= d` 与反算百分比两道断言。
- **时间窗缺失**：现象是同一批用例不同版本得到不同数，没法判断是变好还是数据换了 → 原因是没记来自哪次运行 → 怎么改：每次记录都带版本与运行标识，回归对比才成立。

:::figure 一条数字从记录到可核对
@flow
记录分子分母|写明统计范围|标清时间窗|反算百分比|拼成完整说法
:::

图里第四环「反算百分比」是最省事的一道保险：写下来之前用分子分母重算一遍，很多凭印象填的数当场就能被挡住。把这张图养成习惯，讲项目里那些数字时就不必临场心虚；整个讲述怎么排进有限时间，见[15 分钟讲项目的节奏](./k126-project-pitch.md)；作品里该有哪些数字，见[三个能写进简历的项目](./k122-three-projects.md)。

:::quote
数字可不可信，不看它带不带百分号，看别人能不能按你写的口径、范围、时间窗，把它重算出来。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能说出分母口径、统计范围、时间窗、内部自洽这四样
- [ ] 能把「95%」改写成带分子分母与范围时间窗的完整说法
- [ ] 知道构造数据要照实标来源，不能写得像真实流量
- [ ] 能解释为什么不同口径的两个数字不能直接相减
- [ ] 养成了写下来之前用分子分母反算一遍的习惯
:::

是什么：这是给每个数字配上口径、统计范围、时间窗并做自洽核对，让它可被重算的方法。
关键做法：记录时就把分子分母、用例集合、运行标识一起存下，写进句子前反算一遍百分比。
什么时候不该用：拿不出可核对的原始记录时，别写数字，改成如实说明「尚未测量」或只讲做了哪些检查。

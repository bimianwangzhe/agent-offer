# 最小权限与双层校验

## 场景提问

你给内部知识助手接了一整套工具：读文档、查报表、发通知、删账号、导出名单。图省事，所有工具挂在同一份清单里，谁都能调。某天有人在输入框里贴了一段看着像工单的文字，助手读完转身就调用了「导出全部用户」，把一份本不该外流的名单整理了出来。你翻日志，参数格式规规矩矩，字段类型全对，结构校验也顺顺当当过了——每一步都没报错，可它就是做了一件这个助手根本不该有权做的事。问题到底出在哪一段？

## 先破一个误解

**不是模型学坏了，也不是参数没校验，而是你把「能不能做」这件事交给了模型自己声明，等于让等着被审批的人自己盖了章。**

先把两件常被混为一谈的事分开。一件叫「参数有效」：一段调用意图是不是合法的结构、字段齐不齐、类型对不对。另一件叫「业务合法」：这个动作在当前这个身份、这个任务、这个额度下，到底该不该发生。前者是形状问题，后者是权力问题。你写再严的结构描述，也只挡得住形状不对的输入；一段格式完美的请求，照样可能去删别人的数据、操作别人的订单、把额度撑爆。很多团队把结构校验做得很细，就以为权限也一起管住了，其实那道门从来没装上。

这里要立两个概念。第一个叫最小权限（Least Privilege，白话讲：只给完成当前任务必需的那一丁点能力，多一点都不给，用完就收）。它追求的不是「保证模型绝不被骗」——那做不到——而是「万一它被说动了，能捅的娄子有多小」，这个范围叫损失半径，也有人叫爆炸半径。把半径压小，是所有护栏里性价比最高的一道。第二个叫双层校验：模型只是「声明」自己想调什么、想要什么权限，这份声明一律按不可信输入处理；另有一个独立的系统，按已经确认过的会话身份，实际核定到底给不给。两道一道都不能省，也绝不能由同一个主体兼任。

为什么非得两道？因为声明是意图，不是授权。一个被注入内容诱偏的意图，会把自己写成管理员、会把身份字段填成别人、会顺手勾上「已批准」。如果系统直接拿这份自报去执行，就等于让申请人自己批准自己。真正可信的授权，只能来自宿主程序里那份写死的、按当前登录会话取出的清单。想继续往「身份从哪来」这条线深挖，可以读 [用户身份服务端注入](./k137-identity-injection.md)；而把这份核定放在程序里、而不是写在提示词里，正是 [护栏放在代码里](./k106-guardrail-in-code.md) 要讲的事。

## 用大楼门禁来类比

把这套助手想成一栋写字楼，工具就是楼里一扇扇门：资料室、财务室、机房、档案库。模型是每天来办事的访客，它每次会递一张自己填的申请单，写上「我要去机房」。

问题在于，很多系统把这当成一张门禁卡用了——申请单上写去哪儿，就放它去哪儿。这栋楼真正的做法应该是两层。第一层：访客确实要填单，说清想办什么事，这是「声明」。第二层：前台另有一本台账，按这个人的工号事先登记好了他能刷开哪几层，闸机读的是台账里那张卡，不是申请单上那行字。两样对齐，门才开。访客在申请单上把职务写成「总裁」没用，闸机根本不看这一栏；他填「已获批准」也没用，因为章不在他手里。至于机房这种特别敏感的地方，光是卡对上了还不够，还得值班经理当场再签一次。

对应关系逐样拆开：访客填的申请单 = 模型产出的调用意图，属于不可信输入；台账里按工号登记的楼层 = 权限矩阵，是宿主程序里写死的授权清单；闸机读卡 = 双层校验里的第二道，按已认证会话身份取真实权限；「两样对齐才开门」= 声明与授权取交集，谁也别想单方面说了算；值班经理签字 = 危险动作的人工确认；而「申请单上自封职务不作数」，对应的就是身份绝不能让模型填进参数，只能服务端注入。

这栋楼还有个容易忽略的细节：门禁卡是按「这趟来办什么事」发的，不是按「这个人是谁」永久发的。今天来送文件，就只给大厅和收发室的权限；明天来修空调，再单独给机房。事情办完，卡就收回。这就是按任务粒度、用短期凭据授权，而不是给每人配一张万能通卡。银行不会因为有位老客户就给他一把开所有保险柜的钥匙，道理是一样的。

## 把这条链画出来

先看一次越权请求该被哪几道关卡挡住。

:::figure 一次越权请求的判定链
@flow
模型声明动作|宿主查权限矩阵|取授权交集|敏感动作复核|放行或拒绝
:::

图的要害在第二格和第三格：绝大多数事故不是「形状不对」被放过去，而是压根没有「查台账」这一站。一旦宿主把授权清单请出来，再和模型的声明取个交集，绝大多数自报的高权限会当场塌回原形——因为交集的上限是台账，不是申请单。第四格是另一道独立的门：即便动作在授权范围内，只要属于不可逆、高金额、对外这类敏感动作，还得再过一次人工确认，不能自动放行。

再看两种做法的差别，体会「声明即授权」错在哪。

:::figure 只信声明 与 声明授权双校验
@compare
只信模型声明::自报身份就生效|越权动作直接落地|损失半径无限大
声明授权双校验::身份只认宿主会话|动作必须落在交集|半径被台账锁死
:::

左边那一行，等于把审批权交给了被审批者，改再多提示词也补不上这个结构洞；右边那一行，关键在于「身份只认宿主会话」——模型说什么都不改变台账，能做什么由那张卡决定。两行的根本分界是：授权这个动作，发生在模型内部，还是发生在包住模型的程序里。

一次权限收敛通常要叠好几层，分开写才不会互相顶掉。

:::figure 权限收敛的四层
@stack
身份层::按已认证会话取身份，模型自报字段一律作废
能力层::按当前任务发短期权限，读写与执行分桶划开
动作层::声明与授权取交集，不在交集内的动作直接拒
敏感层::不可逆与对外动作另加人工确认，不自动放行
:::

## 层层追问

:::ask 那我把每个工具的结构描述写得特别严，参数校验做足，是不是就够了？
:::

不够，而且这正是最常见的错位。结构描述管的是「形状」：字段在不在、类型对不对、取值是不是落在枚举里。它完全不知道「这单是不是这个用户的」「这次退款有没有超额度」「这个动作当前任务用不用得上」。一段格式无可挑剔的调用，照样可以带一个属于别人的订单号、一个超出的金额、一个本不该出现的删除动作。所谓「合法 JSON 也可能越权」，说的就是这件事。所以结构校验是第一道筛子，不是最后一道门；后面必须另叠一层业务规则与资源鉴权，逐项问「这个身份能不能操作这个对象、这个额度、这个状态」。把四道关按什么顺序排，可以对照 [参数有效不等于业务合法](./k034-param-validity.md) 来看。

:::ask 那我干脆一刀切，只给只读权限、把所有写工具都摘掉，总该绝对安全了吧？
:::

方向对，但别把它当成终点。收窄权限确实把损失半径压小了一大截，可「只读」和「安全」之间还隔着两道缝。第一道缝：只要这个助手还能把内容对外发出去，它读到什么就能捎出去什么。既能碰私有数据、又暴露在不可信内容里、还能对外通信，这三样凑齐时，光是「不能写」并挡不住数据外流，得靠 [代码沙箱与隔离](./k101-sandbox.md) 把出网通道和 [输出扫描与内容过滤](./k099-output-scan.md) 一起管住。第二道缝：权限范围内的破坏依然可能发生——一个被允许改配置的助手，被说动后照样能把配置改坏，这不算越权，却照样是事故。所以只读是很好的起点，不是可以就此收工的结论；真正稳的做法是按「最终效果」而不是按「工具名字」去评估每一份授权，再看它和别的能力叠起来会不会放大。多用户之间还得各守各的边界，那是 [会话隔离与租户边界](./k105-session-isolation.md) 要补的另一半。

## 一段能跑的代码

下面这段程序只用 Python 标准库，把「声明层 + 授权层 + 敏感动作门」跑成可核对的判定。越权请求全部本地构造，不联网、不读环境变量、不装任何第三方包，复制成 `.py` 直接运行即可。

```python
from dataclasses import dataclass, field

# 权限矩阵：按角色预先划定「实际允许」的动作，写死在宿主程序里
ROLE_MATRIX = {
    "viewer":   {"read_report"},
    "analyst":  {"read_report", "search_doc"},
    "operator": {"read_report", "search_doc", "refund_small"},
    "admin":    {"read_report", "search_doc", "refund_small",
                 "delete_account", "export_all_users"},
}

# 每个动作的敏感级别，用于叠加危险动作门
ACTION_LEVEL = {
    "read_report": "read",
    "search_doc": "read",
    "refund_small": "write",
    "delete_account": "danger",
    "export_all_users": "danger",
}

# 模型不许在参数里自带的字段：身份与授权只能由宿主注入
FORBIDDEN_PARAMS = {"user_id", "role", "approved", "is_admin"}

@dataclass
class Intent:
    """模型产出的调用意图，一律按不可信输入处理。"""
    actor_role: str
    action: str
    params: dict = field(default_factory=dict)

@dataclass
class Decision:
    allowed: bool
    reason: str

def declared_permission(intent):
    """第一层：模型「声明」想要的权限，只是意图，不构成授权。"""
    return set(ROLE_MATRIX.get(intent.actor_role, set()))

def granted_by_host(session_role):
    """第二层：宿主按已认证的会话身份，独立给出真实授权。"""
    return set(ROLE_MATRIX.get(session_role, set()))

def validate(intent, session_role, approved=False):
    """双层校验：先挡身份字段，再取声明与授权的交集，最后叠敏感动作门。"""
    if FORBIDDEN_PARAMS & set(intent.params):
        return Decision(False, "参数里夹带了身份或授权字段")
    # 身份只认宿主会话，不认模型自报角色
    effective = declared_permission(intent) & granted_by_host(session_role)
    if intent.action not in effective:
        return Decision(False, "动作不在有效授权交集内")
    if ACTION_LEVEL.get(intent.action) == "danger" and not approved:
        return Decision(False, "危险动作缺少人工确认")
    return Decision(True, "放行")

if __name__ == '__main__':
    checks = []
    d = validate(Intent("viewer", "read_report"), session_role="viewer")
    checks.append(("合法只读动作放行", d.allowed and d.reason == "放行"))
    d = validate(Intent("admin", "export_all_users"), session_role="viewer")
    checks.append(("模型自报高权限被交集挡下", not d.allowed))
    d = validate(Intent("analyst", "refund_small"), session_role="analyst")
    checks.append(("越权写动作被挡下", not d.allowed))
    d = validate(Intent("viewer", "read_report", {"user_id": "admin"}),
                 session_role="admin")
    checks.append(("参数夹带身份字段被挡下", not d.allowed))
    d = validate(Intent("admin", "delete_account"),
                 session_role="admin", approved=False)
    checks.append(("危险动作未确认被挡下", not d.allowed))
    d = validate(Intent("admin", "delete_account"),
                 session_role="admin", approved=True)
    checks.append(("危险动作经确认才放行", d.allowed))
    passed = sum(1 for _, ok in checks if ok)
    for label, ok in checks:
        print(("通过" if ok else "未通过") + "：" + label)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks)
```

逐段看它在做什么：

1. `ROLE_MATRIX` 就是那本台账，按角色把「实际允许的动作」写死在宿主程序里。它不随模型输出变化，是整个判定唯一的可信来源。`ACTION_LEVEL` 给每个动作标了敏感级别，供最后一道门用。
2. `FORBIDDEN_PARAMS` 列出模型不许自带的字段。身份、角色、是否已批准，这些只能由宿主按会话注入；一旦在参数里出现，说明有人想自己填自己的权限，`validate` 第一步就把它挡回去。
3. `Intent` 是模型产出的调用意图，`actor_role` 特意留在里面，就是为了演示「自报角色」这一路。注意它是数据，不是授权——`declared_permission` 只是把这份声明翻译成一个集合，函数名里的「声明」二字是提醒：这层不构成批准。
4. `granted_by_host` 是第二层，输入只有 `session_role` 这一个来自已认证会话的参数，完全不看 `Intent`。`validate` 里那句取交集 `&` 是整套设计的要害：有效权限的上限被台账锁死，声明再大也大不过授权。这正好把「申请单上自封总裁」在代码里变成了不可能。
5. 危险动作那道门是叠加的，不是替代的：即便动作确实落在交集里，只要级别是 `danger` 且没有人工确认，依然拒绝。这样「list 在授权内」和「这次要不要放行」就是两个独立判断，不会被一次授权永久买断。
6. 末尾六条断言分别验证正常放行、自报高权限被压回、越权写被挡、身份字段被挡、危险动作未确认被挡、确认后才放行，最后打印「通过 6/6 项」。注意所有断言都落在「放行还是拒绝」这个系统状态上，而不是看模型有没有说漂亮话——这是安全测试与普通文本测试最要紧的分界。

## 踩坑与边界

- **把权限字段交给模型填**：现象是工具参数里留了 `user_id`、`role`、`approved`，模型或被注入内容一填就越权 → 原因是把身份和授权当成了可以协商的普通参数 → 怎么改：这几类字段一律从工具定义里删掉，由宿主按已认证会话注入，参数里出现即拒绝，见 [用户身份服务端注入](./k137-identity-injection.md)。
- **按工具名字而不是最终效果估权限**：现象是单看每个工具都「只是读一下」，串起来却能导出全量名单 → 原因是按声明逐项打勾，没看组合后的实际效果，形成级联授权 → 怎么改：按「这套权限最终能碰到什么数据、能造成什么副作用」评估，能读私有数据又对外通信的组合要拆开。
- **双层塌成单层**：现象是让同一个模型先声明权限、再判断自己有没有权限，看着像是两道 → 原因是声明与核定是同一个主体、共享同一批盲区，被说动时两道一起失守 → 怎么改：核定必须落在不具备语义理解、只认清单的宿主程序里，两道由不同主体做出。
- **所有助手共用一张长期凭据**：现象是图省事给每个助手都配同一份管理员令牌，一个被攻破全线失守 → 原因是权限没有按任务与会话分开，凭据也不会过期 → 怎么改：每个助手独立作用域、按任务发短期凭据，用完即失效，密钥始终留在应用侧不进上下文。
- **以为只读就万事大吉**：现象是摘掉所有写工具后放松了其它层，数据仍被读走外发、或授权范围内的配置被改坏 → 原因是把「不能写」等同于「不会出事」 → 怎么改：把出网通道、对外输出、会话边界一并管住，并承认权限范围内的破坏依然可能，见 [会话隔离与租户边界](./k105-session-isolation.md)。

## 三句话小结

最小权限与双层校验，是只给完成当前任务必需的那点能力，并让模型的「声明」与宿主的「授权」各自独立、两道都过才放行。

关键做法是把身份只认已认证会话、把动作限制在声明与授权的交集内、把危险动作再叠一道人工确认，且全部落在包住模型的程序里。

当系统只是个纯文本生成器、背后既没有可调用的工具也没有私密数据时，不必为它堆整套权限台账；但只要模型能碰到真实动作或敏感信息，这一层一步都不能省。

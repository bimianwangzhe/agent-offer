# Token 与分词：模型眼里的字，不是你眼里的字

## 一、从一个对不上的账单说起

你写了个小脚本，先把一段中文数出一百二十个字，再按"一个字多少钱"估了这次调用的花费，觉得是几厘钱的小事。结果返回之后一看用量，数字和你估的差了一截。你把同一段话译成英文再数，字数明明变少了，用量却又涨了回去。更让你别扭的是：你只让它回一句话，账单里却连你发给它的那一大段背景材料一并算了进去——你原本以为输入是不花钱的。

三件事对不上，都指向同一个地方：你用"字数"这把尺子，去量了一个根本不按字数运转的东西。

## 二、先破误解

**不是模型把你的中文按"字"读进去、按"字"吐出来的，它眼里的最小单位叫词元，token，跟你熟悉的汉字、单词、字符都不是一回事。**

先把词元讲白：一段文字送到模型之前，会先被一个分词器切开，变成一串整数编号；模型整段整段处理的，是这串编号，不是原文。你可以把词元理解成"编号之前的一小片文本"——它可能是一个常见词、一个汉字、一个标点、一个数字串，也可能只是一个词的一截，甚至是一个字节片段。分词器有一张固定的对照表，把每一片映射成一个编号，模型只跟编号打交道。

这样一来，"这段有多少字"和"这段有多少词元"就成了两把不同的尺子。常见英文单词往往一个词元就够，生僻词会被拆成好几片；一个汉字可能是一个词元，也可能因为不在表里而被拆成三片；标点和换行也要占位置。所以你数出一百二十个汉字，模型看到的可能是另一串长度完全不同的编号。换成英文，字符少了，切出来的片数却未必少，这正好解释了前面那个"字数降了、用量反而涨"的别扭现象。

至于"输入也计量"，同样顺理成章：模型得先把你发的整段背景读成编号，才能开始算后面的东西，读进去的每一片都要占计算，自然要计进去。它读多少、写多少，都按同一串词元来算。这也是为什么后面谈[上下文窗口](./k003-context-window.md)时，说的是"能装多少词元"，而不是"能装多少字"。

## 三、生活类比：快递按件不按斤

寄过一箱书就懂了。快递员不按"这堆书有多重"给你算一件，而是按"你打成了几个包"算件数。同样六本书，你塞进一个结实的大箱子，是一件；你怕压坏，分装成三个小包，就成了三件；你在箱子里塞满泡沫防震，泡沫不值钱，但占了体积、一样影响能装几件。运费跟着件数走，收件要算，派件也要算。

把这套对应过来，几乎一一落实：

- 你写的原文，就是要寄的那一堆东西；
- 分词器，是那个决定"怎么打包"的打包员，切法由它的对照表定，不由你定；
- 词元，就是打包之后的"一件"；
- 每个词元对应的整数编号，是贴在这一件上的面单号，模型全程只认面单号；
- 上下文长度上限，是车厢一次能装多少件；
- 账单，是按件数结的账，收进来的（输入）和发出去的（输出）都一件一件数。

这个类比最有用的地方，是它解释了"为什么我改了点格式，费用却变了"：你没换东西，只是换了个打包方式，件数就变了。往句子里多加一个空格、一个换行、一个全角标点，在打包员眼里都是要单独处理的料，片数可能就多一片。想省钱，与其斤斤计较写了几个字，不如少塞没用的东西进去——那是后文谈用量时最实在的一招。

:::tip
词元不是字符，也不是字数，它是"分词器切出来、能查到一个编号"的那一小片文本。
:::

## 四、画出来：一段文字怎么变成编号

先看它走的路。从你敲下的一段话，到模型真正读到的东西，中间隔着一次切割和一次查表：

:::figure 一段文字从原文到模型输入
@flow
原文|分词器切片|查表换编号|模型逐个读|生成编号还原成字
:::

每个节点不超过十个字，但顺序不能乱：先切、再换号、再进模型；出来的时候是反着走一遍，模型吐的是编号，得由同一张表还原成你能读的字。这也顺带说明，为什么"分词器"和"模型"必须配套——换一张对照表，同一句话的编号就全变了，模型会认不出。

再把两种估算口径摆在一起，差别就很直观了：

:::figure 按字数估与按词元估
@compare
按字数估::中英文尺子不一|生僻字被低估|输入常被漏算
按词元估::统一编号计量|切法决定多少|输入输出都计
:::

左边那条路之所以处处别扭，是因为它拿"给人看的字"去量"给机器看的编号"；右边那条路虽然也只是一个便于理解的模型，但它至少跟真实计量的口径是同一回事。这两张图合起来，其实已经把这一篇要讲的事说完了：先在脑子里把"字"换成"片"，后面所有关于长度、费用、截断的判断才不会一错再错。

## 五、顺着追问两层

:::ask 那如果只是粗略估个量，用字符数乘个固定系数行不行？
:::

当"粗估"用，可以，但得把"粗"字说在前面。不同语言、不同题材的切法差别很大，中英混排、带大量代码或标点的文本，和一段干净散文，折算出来的片数能差出不少。更关键的是，粗估只能拿来"心里有数"，不能拿来当硬上限：真正决定会不会被截断、会不会报错的，是实际切出来的词元数，而不是你乘出来的那个近似值。一旦你要卡死预算，就必须换成能查到的真实用量，[用量统计与计费口径](./k010-usage-billing.md)那一篇讲的就是怎么把它记准。

:::ask 那如果同一句话，我只加了个空格、换了个标点，片数会变吗？
:::

会。这正是最容易忽略的一层。空白、换行、全角半角标点，在分词器眼里都不是"没有"，它们要么单独成一片，要么改变相邻两片怎么切。所以两段读起来几乎一样的提示词，切出来的片数可能不同，成本和留给回答的余量也跟着变。再往深想一步：既然连一个空格都能影响切分，那就别指望靠"手动数一数"去精确控制长度。稳妥的做法只有两个——要么在提交前用同一个分词口径先数一遍，要么干脆以返回里附带的用量为准。手动臆测这件事，从原理上就靠不住，它和[采样参数与不确定性](./k004-sampling.md)里"别拿确定性断言去测一个本身不确定的东西"是同一种思路：拿一把不合适的尺子，量得再仔细也是错的。

## 六、跑一段代码，把"片"摸实

下面这段只用标准库，不联网、不装包、不要账号。它把分词器简化成四条规则，专门用来看清"字数不等于词元数"这件事。复制到任意一台装了 Python 的机器上都能跑。

```python
import re

# 一个确定性的分词桩：连续字母、连续数字、单个汉字、单个标点各算一个词元（token）。
# 空白不单独算词元，直接跳过。
TOKEN_RE = re.compile(r"[a-zA-Z]+|\d+|[\u4e00-\u9fff]|[^\sa-zA-Z0-9\u4e00-\u9fff]")


def tokenize(text):
    """把一段文字切成词元列表，纯本地规则，不联网不装包。"""
    return TOKEN_RE.findall(text)


def token_count(text):
    return len(tokenize(text))


if __name__ == '__main__':
    checks = 0

    # 1) 连续英文字母合成一个词元
    assert tokenize("Agent") == ["Agent"]
    checks += 1

    # 2) 每个汉字单独成一个词元（这是简化桩，便于看清"字数≠词元数"）
    assert tokenize("中国") == ["中", "国"]
    checks += 1

    # 3) 连续数字合成一个词元
    assert tokenize("2026") == ["2026"]
    checks += 1

    # 4) 混合文本：可见片段共 5 个 -> 5 个词元
    mixed = "Hi 中国 2026!"
    assert tokenize(mixed) == ["Hi", "中", "国", "2026", "!"]
    assert token_count(mixed) == 5
    checks += 1

    # 5) 分词不丢字：把词元接回去，等于原文去掉空白
    assert "".join(tokenize(mixed)) == mixed.replace(" ", "")
    checks += 1

    # 6) 计数随内容变化，输入与输出都按它计量
    assert token_count("今天天气不错") == 6
    assert token_count("") == 0
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `TOKEN_RE` 是四条切分规则，按顺序尝试：连续英文字母合一片、连续数字合一片、单个汉字一片、其余标点一片；空白不匹配任何规则，会被自然跳过。这就是那个"打包员"的极简版。
2. `tokenize` 把原文交给正则，返回一串词元；`token_count` 只是数这串有多长，对应"按件结账"。
3. 断言一、二、三分别钉住三件事：`Agent` 是一片、`中国` 是两片、`2026` 是一片。同样"两个字符"，切法完全不同，这就是两把尺子对不上的根源。
4. 断言四用一句中英数符混排的话，验证可见片段共五个、词元数就是五；断言五再把这些片接回去，确认分词没有偷偷丢字——切得细可以，丢字不行。
5. 断言六说明计数随内容变化，空文本是零；最后打印通过项数，让"跑没跑对"一眼可见。

要提醒一句：这是**教学用的简化桩**，真实分词器比它复杂得多，切法也不一样，别拿这里的数字去当任何真实报价。但它演示的那件事是真的——模型按片读写，片数由切法决定，输入输出都算。想继续看模型拿着这串编号做什么，接下去读[下一个词预测](./k002-next-token.md)最顺。

## 七、踩坑与边界

- **拿字数当片数**：现象是估算和账单总差一截 → 原因是汉字、单词、字符与词元是不同口径 → 改成用统一分词口径计数，或直接读返回里的用量字段。
- **只算输出不算输入**：现象是"只回一句话却扣了不少" → 原因是发进去的背景也要切成编号读一遍 → 记账时把输入与输出分开两栏，都记。
- **以为格式不花成本**：现象是多加几处换行空格后余额掉得快 → 原因是空白与标点同样参与切分 → 精简提示时连格式一起精简，别只删字。
- **跨语言套同一个系数**：现象是中文估得准、英文和代码全估偏 → 原因是不同字符分布的切法差异大 → 按文本类型分别校准，且只当粗估。
- **把简化桩的结果当真**：现象是拿本地演示数字去卡硬上限，线上却超限 → 原因是桩的切法和真实分词器不一致 → 桩只用来理解机制，卡预算以真实用量为准。

## 九、三句话小结

词元是模型读写文本的最小单位，切出来的每一片对应一个编号，输入输出都按它计量。
要紧的做法是统一用词元口径去估算与记账，别拿字符数硬套。
当预算要卡死、或文本跨语言混排时，别再用字符数估算法，换成真实用量来核对。

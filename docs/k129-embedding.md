# Embedding 与向量化

## 一、一个「明明该搜到却搜不到」的下午

你做了个资料问答，把文档切成小段存起来，用户问「怎么申请退款」，系统却翻出一段讲「如何修改收货地址」的文字，而真正讲退款流程的那段排在了很后面。你换个问法「退钱要多久」，结果又不一样。你怀疑切分切坏了，去重做了、长度调了、排序也改了，问题还是时好时坏。最后发现，根子不在这些环节，而在最开始那一步：你是怎么把一段文字变成「可比较的东西」的。如果这一步没做对，后面所有排序都是在错误的尺度上比。

## 二、先破这个把方向带偏的误解

**不是检索排错了序，也不是文档切得不对，而是你把「字面像不像」和「意思近不近」当成了同一件事，而这两者要靠向量化才对得上。**

先说清主角：Embedding（词向量嵌入，指把一段文本映射成一串固定长度的实数，也就是一个稠密向量）。「稠密」是相对「稀疏」说的：稠密向量里几乎每一维都有非零值，整串数字共同编码语义；它不像关键词表那样只有命中的词才亮一个 1。有了这串数字，两段文字「意思近不近」就变成了一个可计算的几何问题——方向越接近，语义通常越接近。这一步是检索、长期记忆、去重、语义缓存共同的地基：它们都先要把文本变成同一种可比的数值形式，才谈得上「找相似的」。关于检索整条链怎么走，[为什么需要 RAG](./k051-why-rag.md) 有整体脉络，本篇只讲最前面这一块「文本怎么变成向量」。

## 三、把它想成给每本书编一组坐标

打个比方：图书馆不给每本书贴「有没有某个词」的标签，而是给每本书定一组坐标，比如「主题偏实用还是偏理论」「面向新手还是面向熟手」「讲流程还是讲原理」等等，一本书对应空间里的一个点。想找和某本书相近的书，就看看哪些点和它挨得近。这里有一一对应关系：一段文本等于一本书；向量的每一维等于一个「隐含的语义刻度」；整串数字等于这本书在空间里的坐标；两段文本的语义相近等于两个点在空间里离得近；而查询「怎么申请退款」等于把这句话也定成一个点，再去附近找邻居。

这个类比点破了三件事。第一，为什么关键词匹配会失灵：讲「退款流程」的段落和问「退钱要多久」在字面上几乎不重叠，但它们在同一套坐标里挨得很近，所以能被找到；反过来，一堆都含「地址」二字的段落字面很像，意思却可能差很远。第二，为什么这套坐标必须由一个统一的「编目规则」产生：所有书都得按同一组刻度、同一把尺子定位，否则 A 书的第 3 维表示「面向新手」、B 书的第 3 维表示「讲原理」，坐标就没法比了。第三，也是最容易吃大亏的一件：一旦换了编目规则——刻度变了、维数变了、含义变了——旧书全得按新规则重新定位。拿新规则下的查询去翻旧规则下编好的书，等于在两个不同的空间里找邻居，结果自然诡异。这正是「换向量模型必须全量重建索引」的来由。

## 四、两张图看清向量化在哪一步

:::figure 一段文本从原文到可比向量
@flow
清洗文本|选定模型|映射成向量|落进索引|按距召回
:::

第一张图把位置摆明。向量化是「选定模型 → 映射成向量 → 落进索引」这中间三步，它夹在原始文本和后续检索之间。关键在「选定模型」这一步要固定下来：整个索引里每一个向量都必须出自同一个模型、同一套维度，否则这张图从第三步起就失去了可比性。

:::figure 换模型却不重建索引的后果
@compare
只改查询侧模型::旧向量与新查询不同空间|相似度数值失去意义|召回结果看似合理实则错乱
连同索引全量重建::文档与查询同尺|距离可比较|结果稳定可复现
:::

第二张图是本篇最该记牢的一条。只把查询那侧悄悄换成新模型，文档侧还留着旧模型产出的向量，是最隐蔽的错误：程序不报错、分数照样给、结果照样返回，但那些相似度数值已经不代表任何真实的「相近」了。全量重建的代价是一次性重算所有向量，换来的是文档与查询重新回到同一把尺子上。

## 五、顺着追问把边界推出来

:::ask 那如果我只想加几篇新文档，也要把整个索引重算一遍吗？
:::

不用，这要分清两种「变」。文档内容变了、但模型没换，属于增量：只把新增或改动的这几篇按同一模型映射成向量、写进索引，旧向量原封不动，因为它们本来就在同一空间里。模型换了、维度变了，属于全量重建：旧向量一律作废，全部文档重新映射。把这两者混为一谈是高频事故——有人把「换模型」当成「改一行配置」，只让新文档用新模型、旧文档沿用旧向量，索引里就悄悄混进了两种空间的坐标，检索结果时好时坏、极难排查。判据很简单：只要「把文本变成向量」的那个函数或它的输出维度变了，就是全量重建；否则才是增量。相关的索引更新策略在 [索引更新、增量与知识冲突](./k063-index-update.md) 里还会展开。

:::ask 再追一层：那向量本身要不要存下来、要不要标记它是谁产出的？
:::

要，而且这件事比想象中重要。每个向量都该带着「出自哪个模型、哪个版本、多少维」的元数据一起存，检索前先校验「查询向量的来源」和「索引里向量的来源」是否一致，不一致就直接拒绝，而不是硬算一个似是而非的分数。原因有两层：其一，不同模型产出的向量，即便维数碰巧相同，各维的含义也完全不同，距离没有意义；其二，灰度切换模型时，如果旧索引没标版本，你根本无法回答「这次请求到底比的是哪一套坐标」。再往深一层，向量化编码的是语义相似度，不是任务相关性，也不是事实正确性：「支持退货」和「不支持退货」在向量空间里可能挨得极近，光靠距离判断会把意思相反的两段当成一回事。所以向量只是「找候选」的手段，找到之后还得有重排、引用校验乃至业务规则去断定它到底对不对。把相似度分数当成正确性证明，是这一步最容易被带偏的地方。关于「相近」该怎么算、为什么度量方式也得和模型口径对齐，[相似度度量对齐](./k130-similarity.md) 专门讲。

## 六、用一段可运行代码把「换模型必须重建」演出来

下面这段不联网、不装任何第三方包，用两个确定性的假向量模型把同一批文本映射成不同维度、不同含义的向量，再让「索引校验器」判断能不能安全检索，亲眼看看只换查询侧会怎样被拦下。

```python
import hashlib

# 两个本地假向量模型：把文本按字符哈希折算成固定维度的稠密向量
# 关键设定：模型 A 产出 4 维、模型 B 产出 3 维，且各维含义不同
def make_embedder(dim, salt):
    def embed(text):
        vec = []
        for d in range(dim):
            h = hashlib.sha256((salt + str(d) + text).encode("utf-8")).digest()
            val = (h[0] - 127) / 127.0   # 折到约 -1~1 的一个实数
            vec.append(round(val, 4))
        return vec
    return embed

model_a = make_embedder(4, "A")
model_b = make_embedder(3, "B")

def cosine(x, y):
    if len(x) != len(y):
        return None            # 维度不同，根本无法比较
    dot = sum(a * b for a, b in zip(x, y))
    nx = sum(a * a for a in x) ** 0.5
    ny = sum(b * b for b in y) ** 0.5
    if nx == 0 or ny == 0:
        return None
    return dot / (nx * ny)

class VectorIndex:
    def __init__(self, embedder, version, dim):
        self.embedder = embedder
        self.version = version
        self.dim = dim
        self.docs = {}         # 文档编号 -> (原文, 向量)

    def add(self, doc_id, text):
        self.docs[doc_id] = (text, self.embedder(text))

    def check_query(self, query_version, query_dim):
        # 检索前先校验来源与维度是否一致，不一致直接拒绝
        if query_version != self.version or query_dim != self.dim:
            return False, "查询与索引不同源，必须重建索引"
        return True, "同源可比"

    def search(self, query_vec):
        scored = []
        for doc_id, (text, vec) in self.docs.items():
            s = cosine(query_vec, vec)
            if s is not None:
                scored.append((s, doc_id))
        return sorted(scored, reverse=True)

def main():
    docs = {"d1": "如何申请退款流程", "d2": "修改收货地址的方法",
            "d3": "退钱一般要多久到账"}
    idx = VectorIndex(model_a, "model-A-v1", 4)
    for k, v in docs.items():
        idx.add(k, v)

    # 场景一：同模型同维度查询，允许检索
    ok_same, msg_same = idx.check_query("model-A-v1", 4)
    hits_same = idx.search(model_a("退钱要多久"))

    # 场景二：只把查询侧换成模型 B，来源与维度都变了
    ok_diff, msg_diff = idx.check_query("model-B-v1", 3)
    q_b = model_b("退钱要多久")
    blocked = (ok_diff is False)

    # 场景三：按模型 B 全量重建索引后，文档与查询重新同源
    idx2 = VectorIndex(model_b, "model-B-v1", 3)
    for k, v in docs.items():
        idx2.add(k, v)
    ok_rebuilt, _ = idx2.check_query("model-B-v1", 3)
    hits_rebuilt = idx2.search(model_b("退钱要多久"))

    results = []
    results.append(("模型 A 产出 4 维向量", len(model_a("任意")) == 4))
    results.append(("模型 B 产出 3 维向量", len(model_b("任意")) == 3))
    results.append(("同模型同维度允许检索", ok_same is True))
    results.append(("同源检索能返回结果", len(hits_same) == 3))
    results.append(("跨模型查询被校验器拦下", blocked is True))
    results.append(("维度不同的两向量无法算余弦", cosine(q_b, idx.docs["d1"][1]) is None))
    results.append(("重建后查询与索引同源", ok_rebuilt is True))
    results.append(("重建后同源检索可正常返回", len(hits_rebuilt) == 3))

    passed = sum(1 for _, ok in results if ok)
    for name, ok in results:
        print(("通过" if ok else "未通过") + "：" + name)
    print("通过 {}/{} 项".format(passed, len(results)))
    assert passed == len(results)

if __name__ == '__main__':
    main()
```

逐段看关键行在做什么：

1. `make_embedder` 造一个假的向量化函数：用标准库 `hashlib` 把「盐 + 维号 + 文本」做哈希，折成一个 -1 到 1 的实数，凑成固定维度的向量。它不含任何真实语义，只是确定性的本地桩函数——同样的文本永远得到同样的向量，断言才可复现。两个模型分别给 4 维和 3 维、不同的盐，用来模拟「换了模型、维度和各维含义都变」。
2. `cosine` 计算两段向量的余弦相似度，开头就判断 `len(x) != len(y)` 直接返回 `None`。这一行是全篇的题眼：**维度不同，连「比一比」这个动作都不成立**，更别提得到一个分数。
3. `VectorIndex` 在建立时就把 `embedder`、`version`、`dim` 固定下来，每个向量随文档一起存。`check_query` 在检索前校验查询侧的版本与维度，不同源就返回 `False` 加一句明确原因，而不是硬算。
4. `main` 造三篇文档，用模型 A 建索引；先做同源查询（放行、返回三条），再模拟「只把查询换成模型 B」（被拦下），最后用模型 B 全量重建索引（重新同源、可正常检索）。
5. 八条断言分别钉住：两个模型维度不同、同源可检索且能返回、跨模型被拦、异维向量余弦返回 `None`、重建后恢复可比。尤其「异维返回 None」这条，把「换模型不重建」为什么会产生看似合理的错乱分数讲透了——若不拦，程序会拿一串毫无意义的数字照样排个序出来。

:::warn
向量化编码的是语义相近，不是事实正确，也不是任务相关。「支持退货」和「不支持退货」可能在向量空间里挨得很近。别把相似度分数当成「找到了正确答案」的证明，它只负责找候选。
:::

## 七、踩过的坑与它的边界

- **换模型当成改配置**：现象是检索结果时好时坏、分数看着正常却不对 → 原因是只让查询侧用新模型，旧向量仍留在索引里，两种空间混在一起 → 把「向量化函数或输出维度变了」判为全量重建，旧向量一律作废重算。
- **增量与重建混淆**：现象是灰度切换模型后结果诡异且无法归因 → 原因是只给新文档用新模型、旧文档沿用旧向量 → 文档内容变而模型没变才算增量，模型变了就必须全量，判据写进代码而非口头约定。
- **向量不带来源元数据**：现象是答不出「这次请求比的是哪套坐标」 → 原因是入库时没记模型、版本、维度 → 每个向量随文档带上这些字段，检索前先校验来源一致。
- **拿相似度当正确性**：现象是召回一段意思相反的文字还给了高分 → 原因是向量只编码语义相近，不辨真伪与否定 → 找到候选后再加重排、引用校验与业务规则。
- **字面相似误当语义相似**：现象是关键词堆得多的段落排前面，真正相关的靠后 → 原因是用词面重合而非向量距离排序 → 统一用同一模型产出的向量做距离比较，别把两套尺度混用。

还有边界要说清：向量化只是「把文本变成可比数值」，它不负责切分好不好、材料干不干净、答案对不对，那些是各自环节的事。而且这里的假模型没有真实语义，演示的是「同源才可比」这条机制；真实向量模型能捕捉同义改写，但也仍编码不了事实正确性与权限边界。当你的场景是精确匹配型号、编号、错误码这类强标识符时，纯向量反而几乎没区分度，得叠一路关键词检索，这也是 [稠密检索与稀疏检索](./k057-dense-sparse.md) 要解决的问题。

## 九、三句话小结

Embedding 与向量化，是把文本按统一模型映射成固定长度稠密向量、让语义相近变成可计算距离的一套方法，是检索、记忆与去重的共同地基。

关键做法是让文档与查询始终出自同一模型同一维度、给每个向量标好来源元数据、模型一变就全量重建，并把相似度只当作「找候选」而非「判对错」。

当任务只需精确匹配型号、编号、错误码等强标识符时，别指望纯语义向量，用关键词匹配更直接。

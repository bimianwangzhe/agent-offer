# 思维链与分步引导

## 一、一口报出来的账，错了都不知道错在哪

你让助手算一笔实付金额：原价 320 元，满 300 减 50，会员再打九折，另加 8 元运费，问最后要付多少。它几乎不假思索地回你「233.2 元」，语气笃定。你自己拿笔一算是 250.2 元，让它重算，它这回报了 243 元，再问一次又变成 250.2 元，每次都斩钉截铁，每次都可能不一样。你在提示词里补上「请仔细一点」「务必算对」「你是很擅长算术的」，一点用也没有。更让人头疼的是，你根本没法从那个孤零零的数字里看出它到底漏了运费、还是把折扣乘错了位置。你开始琢磨是不是该换个更贵的模型。如果你刚照着[起步说明](./00-start-here.md)把第一个脚本跑起来，这种「给得又快又自信、却不敢信」的别扭，多半不是算力不够，而是你把好几步压成了一次脱口而出。

## 二、不是算不动，是把多步压成了一口价

**不是模型算不动这道算术，是它把好几步并成了一次「张口就给」，而张口就给既没法复核，也没法定位错在哪一步。**

先把词说清。思维链（Chain of Thought，缩写 CoT）是让模型先把中间的推理步骤一步步写出来、最后再给结论的做法；分步引导就是在提示词里明确要求它这么做。采样（sampling）指模型按概率挑下一个词的过程，天生带随机性；Token（模型读写文本的基本计量单位）是它一字一字往外吐的东西。

一道「满减 → 会员折 → 加运费 → 得实付」的题，本来有四步。一口气报数，等于让模型在看不到中间量的情况下，把四步的结果一次性猜出来：满减后的数、折后的数、加完运费的数，全都没有落成文字，只留在看不见的计算里，哪一步偏了都无处对账。让它分步写，等于逼着它把三个中间量逐个写出来，每一个都成为后面能读到的文字；写出来的那一刻，你（或一段校验代码）就能拿计算器逐行核，错的那一行的位置立刻清楚。所以分步真正的价值，是把「黑箱一口价」换成「可逐行审计的流水」。

但这里必须点破最容易走偏的期待：分步改善的是「过程可见、错误可定位、少犯累积误差」，它给不了确定性。模型仍然是逐词采样，同一道题多跑几次仍可能得到不同结论；中间步骤写得再漂亮，也只是让这次推理更容易被检查，不是给结果盖了个「必然正确」的章。把「让它一步步想」理解成「从此输出就确定了」，是这一整段最要紧的误解。也正因如此，[采样参数与不确定性](./k004-sampling.md)里讲的那层随机性，分步并没有把它消掉。顺带一提，思维链还有些更复杂的变体，比如树状搜索（Tree of Thoughts，缩写 ToT，把推理铺成多条分支再剪枝）、图式合并（Graph of Thoughts，缩写 GoT，把分支按依赖关系并成一张图）；工程上多数场景用线性的分步就够，不必一上来就上复杂的。

## 三、心算报数与草稿纸对账

把这件事想成让一位会计结账。你站在旁边，让他心算一长串折扣，他抬头发呆两秒，报你一个数。这个数对不对？你无从查起，只能选择信或者不信，再问一遍他可能又报一个略有不同的数。

换个做法：递给他一张草稿纸，请他一行写一步、每行末尾留个中间小计。于是纸上有了「原价 320」「满减后 270」「会员折后 243」「含运费 251」四行。你拿计算器从第一行核到最后一行，哪行对不上当场就能圈出来；就算他手滑抄错了一行，你也知道错在第三行，而不是笼统地说「这账算错了」。

对应关系一条条摆出来：抬头报出的那个数，就是不分步的一次输出；草稿纸上的每一行，就是思维链里的一个中间步骤；行尾的小计，就是可被核对的中间量；你手里的计算器，就是外部的校验代码；而「他偶尔还是会抄错一行」，对应的正是采样随机性——分步让他更不容易错，却没让他变成不会错的机器。

还有一层常常被忽略：草稿纸是给会计自己理思路、给你复核用的，不该原样贴到客户面前当账单。纸上有试探、有划掉重写的痕迹、有自言自语；客户要的是干净的结论和必要的依据。对应到系统里就是：中间推理留在日志里供排障，给终端用户的应当是整理后的答复，两者分开。把长长的思考过程一股脑端给用户，既不体面，也可能把内部规则一并暴露出去。

:::tip
一句话记住：**分步不是让模型变聪明，是让它的活儿变得可查。** 判断该不该引导分步，只问一句：我更需要一个「看着对」的结论，还是一条「错在哪一步能指出来」的流水？
:::

## 四、把一次分步推理拆成几段来看

一次像样的分步，不是笼统地加一句「请仔细思考」，而是有它自己的结构。

:::figure 一次分步推理的展开顺序
@flow
拆出小步|写中间量|逐步推进|汇出结论|外部复核
:::

第一步先把任务切成一件件小事；第二步每做一件就把结果落成文字；第三步沿着这些中间量往下走，而不是凭记忆重算；第四步把结论单独成行，和过程分开；第五步用外部那段确定的代码去核。少了最后一步，前面写得再细，也还是「自己说自己是对的」。

:::figure 分步里该留下的四样东西
@stack
已知条件::把题目给的数原样抄清，别凭记忆改
每步算式::一步只做一件事，写清算了什么
行尾小计::每步结果留成可核对的中间量
最终结论::单独一行给答案，与过程分开
:::

「已知条件」那一行尤其容易被省掉，一省掉，模型就可能在后面悄悄把 320 记成 302，而你还以为它一直用的是原数。「最终结论」单独成行，是为了让下游程序能稳定地只取这一行，不必从一整段思考里去找答案在哪。

:::figure 一口给结论与分步写过程的差别
@compare
一口给结论::中间量看不见|错了定位不到|随机性被藏起来
分步写过程::每步能复核|错在哪步清楚|随机性仍存在
:::

注意右边最后一项：即便分步，随机性依旧在。要把「过程可查」真正变成「结果可信」，得把那些中间量交给一段确定性代码去比对，也就是[语义层校验](./k018-semantic-check.md)里那种「按业务规则复查值」的做法；发现问题再带着具体错处回传，是[自动纠正与重试上限](./k019-auto-repair.md)要接着讲的。分步负责把线索摊开，后面几关负责把线索用起来。

## 五、那如果不保证对、或者干脆把过程给用户看呢

:::ask 既然分步也不保证对，那还分步干什么
:::

价值从「求一次算对」换成了「让过程可复核、让错误可定位、让下游能逐项核」。这三件事在复杂任务里比「碰运气一次蒙对」值钱得多：一次蒙对下次未必还对，而一条能查的流水每次都能查。顺着再追一层：那能不能干脆让模型自己检查自己？不太稳。它复核自己写的步骤时，往往顺着原来的思路一路点头，共享同一套盲区，容易变成「没有证据的自夸」。更稳的做法是把中间量交给一段确定性代码去算、去比，模型只负责「下一步该做什么、这一行的依据是什么」。追到这层你会发现，分步和校验是分工：分步把隐式的过程显性化，校验用不容商量的规则给这个过程盖章。

:::ask 那把推理过程原样展示给用户不是更透明吗
:::

透明和体面不是一回事。过程里常夹着试探、自我纠正、废话，甚至可能带出内部规则；用户要的是结论、以及支撑结论的必要依据，不是一份涂改过的草稿。把过程留在日志里供排障，把整理后的答复交给用户，两边都照顾到。再追一层：那是不是步子拆得越细越好？也不是。拆得越细，输出越长、要付的 Token 越多、中途写歪的机会反而越多，还容易把简单任务拖成一长串啰嗦。工程上够用的线性分步即可，判断标准很简单：拆到「每一步的结果都能被独立核对」就该停手，不必再往下切。

## 六、一段能直接跑的分步复核器

下面这段只靠 Python 标准库。模型用本地确定性桩函数模拟：同一道题问三次，构造出三个可能不同的结论，用来演示采样带来的非确定性；分步那一侧则算出一条每步都能重算核对的流水。数字全是本地构造的，不是对任何真实模型的统计。

```python
# 思维链与分步引导：演示「分步让过程可复核」，以及「分步不消除随机性」。
# 只用标准库；模型用本地确定性桩函数模拟，不联网、不调用真实模型。

import json

# 金额一律用整数「分」，避开小数误差；这是一笔构造出来的账。
ORIGINAL = 32000      # 原价 320.00 元
FULL_CUT = 5000       # 满 300 减 50
MEMBER_NUM = 9        # 会员九折，即乘 9 / 10
MEMBER_DEN = 10
SHIP = 800            # 运费 8.00 元


def solve_with_steps():
    """把整笔账拆成几步，每步留下一个可核对的中间量。"""
    steps = []
    after_full = ORIGINAL - FULL_CUT                     # ① 满减
    steps.append(("满减后", after_full))
    after_member = after_full * MEMBER_NUM // MEMBER_DEN  # ② 会员折
    steps.append(("会员折后", after_member))
    after_ship = after_member + SHIP                    # ③ 加运费
    steps.append(("含运费", after_ship))
    steps.append(("实付", after_ship))                   # ④ 结论单独一行
    return steps


def solve_direct():
    """桩函数：模拟『一口报价』，本地故意漏掉运费，用来对比。"""
    return (ORIGINAL - FULL_CUT) * MEMBER_NUM // MEMBER_DEN


def fake_model_replies(correct):
    """桩函数：构造『同一道题问三次』的三个结论，模拟采样的非确定性。
    这是构造场景，不是真实模型的统计结果。"""
    return [correct, correct - SHIP, correct]   # 第二次把运费漏了


if __name__ == '__main__':
    steps = solve_with_steps()
    correct = steps[-1][1]

    checks = []
    # 1. 分步的每一步都能被独立重算核对
    checks.append(("满减步可核对", steps[0][1] == ORIGINAL - FULL_CUT))
    checks.append(("会员步可核对",
                   steps[1][1] == steps[0][1] * MEMBER_NUM // MEMBER_DEN))
    checks.append(("运费步可核对", steps[2][1] == steps[1][1] + SHIP))
    # 2. 一口报价因漏了运费而算错，且错误能定位到具体那一步
    checks.append(("一口报价算错", solve_direct() != correct))
    checks.append(("错在运费这一步", correct - solve_direct() == SHIP))
    # 3. 分步的中间量每次都一样，是确定的、可复核的
    checks.append(("中间量确定", solve_with_steps() == steps))
    # 4. 但结论经过采样，同一题多跑几次并不全相同
    replies = fake_model_replies(correct)
    checks.append(("采样带来非确定", len(set(replies)) > 1))
    # 5. 拿分步算出的确定值当标尺，外部复核能抓出被扰动的那次
    wrong = [v for v in replies if v != correct]
    checks.append(("外部复核能抓错",
                   len(wrong) == 1 and wrong[0] == solve_direct()))
    # 6. 结论单独成行，用 JSON 交给下游，便于稳定取用
    report = json.dumps({"实付": correct}, ensure_ascii=False)
    checks.append(("结论可交给下游", json.loads(report)["实付"] == correct))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. 金额全部用整数「分」表示，是为了避开小数运算的舍入误差；这是一笔本地构造的账，不对应任何真实订单。
2. `solve_with_steps` 把四步各留一个中间量，用 `("这一步叫什么", 值)` 成对存下来，正是「每步留个行尾小计」那条对应的实现。
3. `solve_direct` 是本地桩函数，故意漏掉运费来模拟「一口报价」的典型错法；有了分步流水，这个错能被 `correct - solve_direct() == SHIP` 精确定位到运费这一步。
4. `fake_model_replies` 用构造好的三个结论模拟「同一题多跑几次不完全一样」，全程没有随机数、没有联网，只是把采样非确定性这件事摆成看得见的数据。
5. 主函数前几项断言验证每一步都能被重算、中间量确定；后几项验证结论仍可能不同、而拿分步的确定值当标尺能把错的那次抓出来；最后把结论单独导出成 JSON（JavaScript Object Notation，用花括号和键值对表示数据的文本格式），让下游稳定取用。跑完打印「通过 9/9 项」，任一项不成立就报错退出。

## 七、踩坑与边界

- **把分步当确定性保证**：现象是写了「一步步想」就删掉了下游校验，偶尔算错直接流到用户 → 原因是分步只让过程可见，采样随机性仍在 → 怎么改：过程归过程，结果一律再过一层确定性校验。
- **让模型自己复核自己**：现象是它把刚写错的步骤又夸了一遍，错误没被拦下 → 原因是复核者与被复核者共享同一套思路和盲区 → 怎么改：把中间量交给独立的代码去比对，模型别既当运动员又当裁判。
- **把推理过程原样端给用户**：现象是答复又长又啰嗦，还夹着试探与自我纠正 → 原因是把草稿当成了成品 → 怎么改：过程留在日志，答复只给结论与必要依据。
- **步子拆得没完没了**：现象是简单任务被拖成一长串，Token 涨了、中途写歪的机会也多了 → 原因是误以为越细越稳 → 怎么改：拆到「每步结果能被独立核对」就停。
- **只加一句「请仔细思考」**：现象是输出还是一口价，没有可核对的中间量 → 原因是笼统的催促没有规定要留下什么 → 怎么改：明确要求分步、每步写出中间结果、结论单独成行。

还要说清一个边界：分步引导对「多步推理、需要算账、需要按条件推导」这类任务帮助明显，对「凭一句话就能答、或纯靠记忆复述」的任务则帮不上什么，反而徒增长度。它也不替代少样本示例定格式、不替代结构描述定字段——三件事各管一段，别指望用一个「请一步步想」把输出契约的全部问题都包圆。

## 九、三句话小结

思维链与分步引导是让模型先把中间推理步骤写出来、再单独给结论，把一次脱口而出的黑箱结果变成可逐行核对的流水。
关键做法是每步只做一件事并留下可重算的中间量，结论单独成行，再用独立的确定性代码去核这些中间量。
当任务一步就能答、或你要的是「必然正确」的保证时，就别指望分步——它给不了确定性，那种场合该靠结构描述与外部校验。

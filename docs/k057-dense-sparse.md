# 稠密检索与稀疏检索：两路各有各的盲区

## 型号差一个字母，答案就串了

用户问「XJ-2200B 质保多久」，助手却把 XJ-2200A 的两年质保答了上来。你查召回日志，两个型号的片段在语义排序里挨得极近——都是「设备、质保、年限」，几乎分不开。反过来，用户换个说法问「不满意能退回吗」，关键词那一路却什么都没捞到，因为库里写的是「三包服务」「七天无理由」，一个字都对不上。两路各翻一次车，方向还正好相反。

## 先破一个误解

**不是某一路算错了，是「意思相近」和「字面精确」本来就是两种不同的相近。**

先把两路的说法讲清楚。稀疏检索指按词项来匹配：把文档和查询都拆成词，数哪些词出现了、出现几次、这个词在多少文档里出现过，据此打分。之所以叫「稀疏」，是因为任意一篇文档只含有词表里极小一部分词，整张词—文档表几乎全是空的。它的代表是 BM25（Best Matching 25，一种基于词项频次与逆文档频率的排序函数）；里面用到的 IDF 是 Inverse Document Frequency（逆文档频率），白话讲就是「一个词越罕见，它命中时越值钱」，配套的 TF 是 Term Frequency（词频，指这个词在这篇里出现几次），合起来常写作 TF-IDF（Term Frequency–Inverse Document Frequency，词频—逆文档频率）。

稠密检索走的是另一条路：先把文本做向量化（Embedding，指把一段文字映射成一串固定长度的数字，让语义相近的文字数字也相近），再比较查询向量与文档向量靠得多近，常用余弦相似度衡量。之所以叫「稠密」，是这串数字每一位通常都有值，不像词项表那样大片空白。它擅长同义、改写、口语化：问「不满意能退回吗」也能对上「七天无理由」，因为两者被压到了相近的方向。

两路的盲区恰好互补。稠密那串数字是有损压缩，把一整段压成固定长度，细粒度的差别容易被抹平：型号只差一个字母、法条编号只差一位、错误码只差一个后缀，向量里几乎看不出区别，于是「XJ-2200B」和「XJ-2200A」会挨得很近；更麻烦的是「支持退货」和「不支持退货」也极像，一个否定词在整段的语义里权重太小。稀疏检索反过来，它认死字面：编号、型号、缩写、罕见词，只要写得精确就能命中，可一旦用户换了说法，词项对不上就完全捞不到。所以真实查询往往同时需要两种信号，谁也别想单独扛下来。把两路结果合到一起的办法见[混合检索与 RRF 融合](./k058-hybrid-rrf.md)，向量是怎么来的见[Embedding 与向量化](./k129-embedding.md)。

## 用查字典与问图书管理员来理解

把找资料想成在一间大阅览室里找一句话，你有两种求助方式。

第一种是查索引卡：柜子里一格一格按词排好，你报一个词，管理员翻到那一格，把写着这个词的卷宗抽给你。精确、可核对、报编号特别快；但你若换个说法，比如把「三包」说成「不满意能退吗」，管理员翻遍卡片也找不到对应那格——词不对，就没有这一格。

第二种是问一位熟读全部藏书的图书管理员：你不用报准词，把意思讲一遍，他凭印象把「讲得跟这意思最近」的几本递给你。同义、口语、绕弯子都不怕；可你要的是一本编号只差一个字母的特定卷册，他很容易把相邻的那本一起递来，因为在他印象里两本讲的是同一件事。

对应关系：索引卡的格子是词项，卡片柜是倒排索引，按词抽卷宗是稀疏检索；管理员的印象是向量，凭印象挑书是稠密检索，相邻卷册被一起递来就是型号区分不开。这个比喻说明了一件事：两路翻车时都不报错，都给你几本「看着挺像」的卷宗，所以光看结果很难发现，得靠构造的例子把它们各自的盲区逼出来。

:::quote
稀疏认的是「字面有没有这个词」，稠密认的是「意思像不像」。型号编号靠前者，同义口语靠后者，缺一路就有一类问题永远答不好。
:::

## 把两路画出来

先看一次查询同时走两路、各自产出候选的样子。

:::figure 一次查询同时走两路召回
@flow
问题输入|按词项打分|按语义打分|各出一份排名|合并成候选
:::

第二、三步是并列的，谁也不是谁的预处理；正因为它们各算各的，后面才需要专门处理「两份分数怎么合」。

两路各自擅长与害怕什么，可以列成清单：

:::figure 两路检索各自的地盘
@stack
稀疏 擅长::型号编号错误码，字面精确就能命中
稀疏 害怕::同义改写口语，词项对不上就零命中
稠密 擅长::换个说法也能对上，语义泛化好
稠密 害怕::只差一字母的编号，以及否定词
:::

第二行与第四行是设计混合方案时最该记住的两句：一个怕「换说法」，一个怕「差一点」。

再看两种做法的差别：

:::figure 只建一路，与两路都在
@compare
只建向量库::同义问法好办|型号编号易串|否定词被抹平
两路都在::精确词项有人管|改写问法也有人管|多一份索引要养
:::

第二行最后一格是代价：两路意味着两份索引、两套打分、以及一次合并。但这份代价换来的覆盖面，靠单路调参数是补不回来的。

:::tip 一条立刻见效的规则
把型号、文号、部门代码、错误码这些强标识符单独保护起来：切词时整体保留，别让通用分词把它们拆成 `XJ` / `2200` / `B`。稀疏检索的全部价值就在这些词上，拆碎了等于自己把精确匹配能力废掉。
:::

## 再往深问两层

:::ask 那如果库里全是自然语言、没有型号编号，是不是稠密一路就够了？
:::

多数时候够用，但别把「没有编号」当成「不需要字面信号」。自然语言里同样有稠密不擅长的东西：否定词（「不得」「不予」「仅限」）在整段语义里权重很小，容易被「支持/不支持」一起压到相近方向；专有名词的缩写、内部项目代号、人名简称，向量里也常常区分度不足；还有一类是「问题问的是某个具体数字」，向量更像在表达「这一章讲费用」，未必落在那个数字上。所以判据不是「有没有型号」，而是「有没有必须逐字吻合的词」。哪怕只有几百份文档，只要存在这类词，字面那一路就值得留；它代码量很小，收益却很直接。顺带一提，稠密这路还有个隐蔽坑：有些向量模型要求查询侧加一段固定前缀、文档侧不加，漏了不报错、只表现为「有时候搜不到」，换模型时尤其要核对这份配置。

:::ask 再深一层：既然两路都要，能不能把两路的分数直接加权平均？
:::

这正是最容易踩的坑。两路分数的量纲根本不可比：余弦相似度常落在 0 到 1 之间，BM25 分数却可能到十几甚至更大，直接加权等于拿苹果加梨，数值大的那一路天然压过另一路。有人想到先归一化再加权，可 min-max、z-score 这类做法依赖当前这批候选的分数分布，换一个问题、换一批候选，归一化结果就变了，权重跟着飘，很难调稳。更省事也更稳的是别比分数、只比名次：每一路各给一份有序排名，按名次的倒数把同一片段在多路里的位置加起来，名次靠前就多得分。这个办法不关心分数是 0.8 还是 12.3，自然规避了量纲问题，还少一个要调的权重。具体公式与实现见[混合检索与 RRF 融合](./k058-hybrid-rrf.md)。另外，两路召回出的候选通常偏多，接下来还需要一道更重的精排把它们收敛到少数，见[粗排 + 精排与重排后截断](./k061-rerank.md)。

## 一份能跑的对照

下面这段只用标准库，自己实现 BM25 打分骨架，再写一个确定性的「语义桩」模拟稠密检索（把词项折成概念计数），用构造的小文档把两路各自的盲区摆出来。不装任何包、不连任何服务。

```python
# dense_sparse.py —— 只用标准库，python dense_sparse.py
import math
import re
from collections import Counter

DOCS = {
    "d1": "退换货政策 七天无理由 三包服务",
    "d2": "设备 XJ-2200B 质保三年 上门检修",
    "d3": "设备 XJ-2200A 质保两年",
    "d4": "发票 报销 七个工作日",
}
ENTITIES = ["XJ-2200B", "XJ-2200A", "E-1024"]
CONCEPT = {
    "退": "售后", "换": "售后", "货": "售后", "包": "售后",
    "服": "售后", "务": "售后", "理": "售后", "由": "售后",
    "售": "售后", "后": "售后",
    "质": "质保", "保": "质保", "检": "质保", "修": "质保",
}


def tokenize(text):
    # 强标识符整体保留，再退回单字与英文数字串
    t = text.lower()
    found = []
    for e in ENTITIES:
        low = e.lower()
        if low in t:
            found.append(low)
            t = t.replace(low, " ")
    return found + re.findall(r"[a-z0-9]+|[\u4e00-\u9fff]", t)


def bm25_index(docs):
    toks = {k: tokenize(v) for k, v in docs.items()}
    df = Counter()
    for ts in toks.values():
        df.update(set(ts))
    avg = sum(len(ts) for ts in toks.values()) / len(docs)
    return toks, df, len(docs), avg


def bm25_score(q, doc_id, idx, k1=1.5, b=0.75):
    toks, df, N, avg = idx
    tf, L = Counter(toks[doc_id]), len(toks[doc_id])
    s = 0.0
    for t in set(tokenize(q)):
        if t not in tf:
            continue
        idf = math.log(1 + (N - df.get(t, 0) + 0.5) / (df.get(t, 0) + 0.5))
        s += idf * tf[t] * (k1 + 1) / (tf[t] + k1 * (1 - b + b * L / avg))
    return s


def dense_vec(tokens):
    # 桩：把词项折成概念计数，模拟「语义被压进向量」
    c = Counter()
    for t in tokens:
        for ch in t:
            if ch in CONCEPT:
                c[CONCEPT[ch]] += 1
    return c


def cosine(a, b):
    keys = set(a) | set(b)
    dot = sum(a.get(k, 0) * b.get(k, 0) for k in keys)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0


if __name__ == '__main__':
    idx = bm25_index(DOCS)
    q = "XJ-2200B"
    assert bm25_score(q, "d2", idx) > bm25_score(q, "d3", idx)
    assert bm25_score(q, "d3", idx) == 0.0          # 稀疏把两个型号分开了

    vb = dense_vec(tokenize("XJ-2200B 质保三年"))
    va = dense_vec(tokenize("XJ-2200A 质保两年"))
    assert vb == va                                # 稠密桩把两者压成同一概念
    assert cosine(vb, va) == 1.0

    vq = dense_vec(tokenize("不满意能退回吗"))
    vd = dense_vec(tokenize(DOCS["d1"]))
    assert vq and vd and cosine(vq, vd) > 0.99    # 换说法仍对得上同一方向
    print("通过 6/6 项：稀疏认精确词项，稠密认语义方向，盲区互补")
```

1. `ENTITIES` 是那份「强标识符保护名单」，`tokenize` 先把型号整体抽出来，剩下的才退回单字与英文数字串。这一步对应前面那条规则：拆碎型号，稀疏检索就白建了。
2. `bm25_index` 统计每个词项出现在多少文档里（`df`）与平均文档长度；`bm25_score` 按 IDF 与词频、文档长度打折算出分数。这就是稀疏一路的骨架，只用 `math` 和 `Counter`。
3. `dense_vec` 是稠密那一路的桩：用 `CONCEPT` 表把单字折成「售后」「质保」这类概念计数，模拟「整段被压成少数几个方向」。`cosine` 算两个概念向量的夹角余弦。真实系统这里会是向量模型，但盲区的形状一样：细节被压掉，只留下大致方向。
4. 前两条断言演示稀疏的长处、稠密的盲区：查 `XJ-2200B` 时，`d2` 有分而 `d3` 精确为 0，可两个型号的稠密桩向量完全相同、余弦等于 1，分不开。
5. 后几条断言演示反过来的一面：口语问法「不满意能退回吗」与「三包服务」被折到同一个「售后」方向，余弦为 1——这正是稠密补上稀疏盲区的样子。六条断言跑完打印通过项数。

想看得更清楚，可以把 `ENTITIES` 里的 `XJ-2200B` 删掉，会看到它被切成 `xj`、`2200b` 之类，精确命中的优势立刻削弱；或者在 `CONCEPT` 里加一个否定词映射，观察「不予」「不得」这类字在概念计数里被稀释得有多快。这些结论都出自这份构造场景，可复现，不依赖任何外部数据。

## 踩过的坑

- **把型号交给通用分词**：现象是 `XJ-2200B` 与 `XJ-2200A` 都命中，答案串了 → 原因是强标识符被切成碎片，字面区分度没了 → 怎么改：型号、文号、错误码整体保留，前置正则抽实体或灌进自定义词典。
- **只建向量库就对外服务**：现象是同义问法答得好，一问编号就错 → 原因是稠密压不掉「差一个字母」的区别 → 怎么改：叠一路字面检索，让精确词项有人管。
- **拿相似度当正确性证明**：现象是「不支持退货」的片段因语义相近排到前面 → 原因是相似度衡量的是语义近，不是任务相关 → 怎么改：把否定词、版本、生效时间当硬条件，别让一个分数定生死。
- **查询侧前缀配置漏了**：现象是「有时候就是搜不到」，不报错也无异常 → 原因是部分向量模型要求查询侧加固定指令前缀、文档侧不加 → 怎么改：把前缀写进检索封装并加单测，换模型时重新核对。
- **两路分数直接加权**：现象是某一路常年压过另一路，调权重也调不稳 → 原因是余弦与 BM25 量纲不可比 → 怎么改：改用只比名次的融合方式，见[混合检索与 RRF 融合](./k058-hybrid-rrf.md)。

## 三句话

稠密检索与稀疏检索，是分别按语义向量相近、按词项字面精确两种标准来找片段的两路召回。
关键做法是两路都留着，强标识符整体保留给字面那一路，换说法的问法交给语义那一路。
当库里全是短小、用词固定、且不存在任何必须逐字吻合的标识符时，单留字面一路也够用。

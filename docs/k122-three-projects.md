# 三个能写进简历的项目

你准备把做过的东西整理成简历，写了三条：「智能客服助手」「知识库问答系统」「多智能体协作平台」。自己读着都觉得空，却又不知道该补什么；面试时对方翻了一遍，问「这三个有什么不一样」「哪个是你自己定的边界」，你发现自己只能重复「用了某某技术」。三条看起来是三件作品，讲起来却像同一句话换了三次说法。

**不是项目不够多，是每件都缺四样东西：边界、架构、关键取舍、可验证结果。** 少了这四栏，项目名就只是标签，面试官无从判断你到底做过决策，还是只把别人的示例跑通了一遍。

先把词说清。边界（boundary）指这个项目明确处理什么、明确不碰什么，先说「不做什么」比说「做了什么」更能划清范围。架构（architecture）指状态放在哪、消息怎么走、失败往哪退。关键取舍（trade-off）指你放弃了哪一条同样可行的路，以及为什么放弃。可验证结果指能被别人现场重跑核对的检查，而不是「效果不错」这类形容词。智能体（Agent）是能自己决定下一步并调用工具的程序，多智能体（Multi-Agent）是几个这样的程序协作。断言（assertion）是程序里一条「必须成立」的检查，跑不过就直接报错。这些词先立住，后面填四栏时才不会写成名词堆砌。

## 一、生活类比：三件带说明卡的作品

想象你去参加一个手作展，带了三件作品。每件旁边都贴一张说明卡：第一栏写「只用了回收木料、没上漆」，这是边界，先划死范围；第二栏画一张简图，说清榫卯怎么咬合、承重落在哪，这是架构；第三栏写「没用金属连接件，因为想让拆装可逆」，这是取舍，必须点出那条没走的路；第四栏写「现场可以拆开再装回去，卡扣次数随便数」，这是可验证结果，别人当场就能核对。

对应关系要讲透：说明卡四栏对应项目的四栏，「现场拆装一遍」对应可复跑的断言，「没用金属连接件」对应放弃的那条路。**如果三件作品的说明卡都只写「做得很用心」，观众分不清它们解决的是不是同一个问题，也会怀疑是不是只做了一件换了三个摆法。** 简历上的三条同理：三件要各自卡在不同的约束上，别让它们互为改名版。

## 二、四栏为什么缺一不可

四栏是连在一起的：先划边界，才知道架构是在什么限制下选的；有了架构，取舍才有对照物；有了可复跑的检查，前面三栏说的话才有人能核对。只写架构不写取舍，别人看不出哪个决定是你做的；只写结果不写边界，数字就失去了适用范围，容易被一句「在什么条件下」问倒。

:::figure 每个项目说明卡的四栏
@stack
边界::限定处理范围与不碰的动作，先说清不做什么
架构::状态放哪、消息怎么走、失败往哪退
关键取舍::写明不选的另一条路与不选的理由
可验证结果::给能现场重跑的检查，不写笼统评价
:::

一个很实际的建议：三件作品分别卡在三种不同的约束上，比如一件刻意压在「单智能体、窄范围」，一件卡在「材料本地、不能联网」，一件卡在「两个角色互不看对方草稿」。这样三件天然不重样，讲起来各有各的取舍，不会互相抢台词。约束、取舍与结果怎么进一步写成不心虚的句子，见[约束、权衡与可验证结果](./k123-tradeoffs.md)；数字怎么写才站得住，见[数字口径与统计范围](./k124-number-integrity.md)。

:::ask 那如果三个项目其实是同一个系统换了三个名字呢？
那最好合并成一件讲深，而不是凑成三条。改名版会带来两个麻烦：一是三件的取舍其实相同，被追问「这个和上一个差在哪」时答不出；二是对方会怀疑你是否只跑通了一个示例。要么把它当一件作品，把边界、故障、复盘讲透；要么让三件各自解决不同约束，比如一件限单库、一件限离线、一件限角色隔离。**数量不重要，约束不重样才重要。**
:::

:::ask 那如果其中一件没有真能重跑的结果呢？
别硬凑一个数字。可以改成「做了哪些检查、哪些情况还没覆盖」，把边界诚实写出来；或者干脆只留两件，把第三件的位置让给一件能复跑的。简历最怕的不是项目少，是写了一个当场核对不到的数字——那会把前面三栏的可信度一起拖下水。**宁可少写一件，也别写自己复现不了的结果。** 这类数字被追问时怎么答，见[四层追问链与转行者三问](./k125-followup-chain.md)。
:::

:::figure 项目描述两种写法
@compare
只写做了什么::智能助手一句话|没有限制条件|结果全靠形容词
写清四栏::范围先划死|取舍有对照|结果可复跑
:::

左边三点是同一个毛病的连锁表现：只有标签 → 没范围 → 结果只能靠形容词撑着。右边三点也是连锁的：范围划死 → 取舍才有对照物 → 结果才能被人复跑核对。两种写法差的不是文采，是「别人能不能据此判断你做过决策」。

## 三、把四栏写成能跑的结构检查器

下面的脚本零依赖、不需要账号、不需要联网。它把三个项目表示成四栏字段，再检查：是否恰好三件、每件四栏是否齐全、取舍有没有点明「不选什么」、结果里有没有可复跑的口径。示例代码里的断言条数是本地构造的占位写法，用来演示结构，换成你自己的项目时要填真实能重跑的数字。

```python
# k122.py —— 三个项目的结构检查器（零依赖，python k122.py）
FIELDS = ("边界", "架构", "关键取舍", "可验证结果")


def project(name, **kw):
    d = {"名": name}
    d.update(kw)
    return d


def inspect(p):
    missing = [f for f in FIELDS if not p.get(f)]
    trade = p.get("关键取舍", "")
    return {
        "四要素齐全": not missing,
        "缺": missing,
        "写明了不选什么": ("不选" in trade or "改为" in trade or "而不是" in trade),
        "结果可复跑": any(ch.isdigit() for ch in p.get("可验证结果", "")),
    }


PROJECTS = [
    project("有界工单助手",
            边界="只处理单库固定四类工单，不接支付动作",
            架构="单循环加四字段状态，工具层做参数校验与幂等",
            关键取舍="不选多智能体，改为单循环带终止条件",
            可验证结果="随文脚本断言 11/11 通过，可现场重跑"),
    project("带检索的问答链路",
            边界="语料限定为本地构造的 40 段文本，不联网",
            架构="切分后召回，元数据过滤前置，再拼装作答",
            关键取舍="不选全量塞入，改为按本轮需要即时取回",
            可验证结果="随文脚本断言 8/8 通过，含缺字段时主动追问"),
    project("双角色评审原型",
            边界="两个角色互不看对方草稿，只做只读评议",
            架构="各自出结论，由裁决节点按版本合并并记录轨迹",
            关键取舍="不选自由讨论，改为固定两轮后强制裁决",
            可验证结果="随文脚本断言 7/7 通过，含冲突与回滚样例"),
]

if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    check("恰好三个项目", len(PROJECTS) == 3)
    for p in PROJECTS:
        r = inspect(p)
        check(p["名"] + "：四要素齐全", r["四要素齐全"])
        check(p["名"] + "：写明了不选什么", r["写明了不选什么"])
        check(p["名"] + "：结果带可复跑口径", r["结果可复跑"])

    broken = project("缺字段样例", 边界="只处理一类", 架构="单循环")
    check("缺关键取舍与结果会被拦下", not inspect(broken)["四要素齐全"])
    check("能指出具体缺哪几项", set(inspect(broken)["缺"]) == {"关键取舍", "可验证结果"})
    print("通过 %d/%d 项" % (passed, total))
```

运行后打印每条断言与汇总：

```text
  [通过] 恰好三个项目
  [通过] 有界工单助手：四要素齐全
  [通过] 缺关键取舍与结果会被拦下
通过 12/12 项
```

逐段解释关键行在做什么：

1. `FIELDS` 把四栏写成固定元组，顺序即检查顺序；`project` 用 `**kw` 收集四栏字段，缺哪一栏会自然落成 `None`，不需要额外占位。
2. `inspect` 里 `missing` 用列表推导找出空栏，返回「四要素齐全」和「缺哪几项」两项——后者很关键，能指出具体缺什么，而不是只给一个不通过。
3. `写明了不选什么` 检查取舍字段里有没有「不选 / 改为 / 而不是」。这是在强制你写出那条没走的路；只写「用了单循环」不算取舍。
4. `结果可复跑` 检查可验证结果里有没有数字。它只是个粗糙的占位检查，用来提醒「别写形容词」，真实项目应换成能现场重跑的断言或评测口径。
5. `PROJECTS` 三件各自卡在不同约束上：单库窄范围、本地离线、角色隔离。三件的取舍也互不相同，正是为了避开「改名版」。
6. 主程序先用 `assert` 逐件核对四栏，再故意造一个 `broken` 缺两栏的样例，验证检查器能拦下并说清缺什么；最后打印 `通过 N/N 项`。

:::tip 结果写「可复跑」比写「效果好」更稳
「效果好」没法核对，「断言 11/11 通过、可现场重跑」当场就能验。**把结果写成一句别人能动手复核的话，前面三栏的可信度会一起被抬起来。**
:::

## 四、踩坑与边界

- **三件同质**：现象是三条项目其实是一个系统换名字，被问「差在哪」答不出 → 原因是按功能命名而不是按约束区分 → 怎么改：让三件各自卡在不同限制上，取舍也各不相同。
- **只写架构不写取舍**：现象是画了很细的结构图，却看不出哪个决定是自己做的 → 原因是没点明放弃的那条路 → 怎么改：每个架构选择后面补一句「没选什么、为什么没选」。
- **结果写形容词**：现象是「效果不错」「体验流畅」这类话，被追问「怎么测的」就卡住 → 原因是结果不可核对 → 怎么改：换成能重跑的检查、用例条数或评测口径，并说明统计范围。
- **边界不写「不做什么」**：现象是数字被一句「在什么条件下」问倒 → 原因是只写了处理范围、没写排除项 → 怎么改：边界栏先写清不碰的动作与不覆盖的情况。
- **数字核对不到**：现象是写了一个自己复现不了的数字，可信度全被拖下水 → 原因是为显得好看硬凑 → 怎么改：只留能现场重跑的结果，其余诚实写成「尚未覆盖」。

:::figure 从项目到能讲清的项目
@flow
划定边界|画清架构|写出取舍|补可复跑检查|按四栏复核
:::

图里最后一环「按四栏复核」是交付前的自查：把三条项目逐条对一遍，缺哪栏当场补，别等被问出来。补完之后还得练怎么在有限时间里讲完，节奏安排见[15 分钟讲项目的节奏](./k126-project-pitch.md)；讲的时候被一层层追问怎么办，见[四层追问链与转行者三问](./k125-followup-chain.md)。

:::quote
三条项目不是三个名字，是三种不同的约束、三种不同的取舍、三份都能现场重跑的检查。分不清这三样，写得再多也像同一句。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能说出四栏分别是什么，以及为什么缺一不可
- [ ] 能让自己三个项目卡在三种不同约束上，不是改名版
- [ ] 每个取舍都能点明「没选哪条路、为什么没选」
- [ ] 结果写成能现场重跑的检查，而不是形容词
- [ ] 知道数字核对不到时该诚实收窄，而不是硬凑
:::

是什么：这是用边界、架构、关键取舍、可验证结果四栏，把做过的东西整理成可讲清作品的方法。
关键做法：三件卡不同约束、逐件写明放弃的路、结果给能复跑的检查，最后按四栏逐条复核。
什么时候不该用：只有一段跑通示例、说不出边界与取舍时，别硬凑成三个项目，先把一件讲透更稳。

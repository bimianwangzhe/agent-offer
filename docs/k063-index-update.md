# 索引更新、增量与知识冲突：让知识库不越滚越脏

## 改了十次的制度，库里躺着十个版本

一份报销制度今年改过十次。用户问现行标准，助手有时答 600、有时答 400，语气都很笃定。你翻索引才发现，十个历史版本全都在库里、全都可召回，谁排前面全看那次查询碰巧跟哪版更贴。更糟的是，你把明显作废的那版从界面里删了，可检索还是能把它捞回来——删除动作只改了列表，没碰索引里的活动状态。

## 先破一个误解

**不是检索排序不稳，是「写新版本」和「让旧版本失效」被当成了两件事，只做了前一件。**

先把词说清楚。增量更新指文档变化时只重算真正变了的那些片段，没变的跳过，而不是每次把整库推倒重建。内容指纹常用 SHA-256（Secure Hash Algorithm 256 位，一种把任意内容映射成定长字符串的散列算法，白话叫「给内容算个指纹」）：入库前对片段原文算一次指纹，与上次一致就跳过重算，变了才更新，重复投递也靠它挡住。失效指旧版本不再参与检索，常见做法是打标记而不是立刻物理删除。知识冲突指同一问题命中了互相矛盾或不同版本的材料，需要按规则裁决谁说了算。

为什么「只写新不删旧」这么常见？因为写新版本是一次顺向的追加，容易做；让旧版本失效却涉及状态、版本、并发与回滚，容易漏。漏了之后表现得很隐蔽：库里同一个文档挂着好几个可召回版本，索引越滚越大，答案在几个版本之间随机漂移，而且没有任何报错。删除也一样：只在某个列表里把条目划掉，检索侧按自己的活动状态照旧召回，于是「界面里已经删了、答案里还活着」。

正确的形状是「先建后切」：新版本先以「构建中」的状态写进去但不参与检索，校验通过后一次性把活动版本切过去，旧版本再慢慢清理；删除的可见性则由一份可靠的状态记录兜底，物理清理交给可失败可重试的后台任务。至于冲突，不能指望模型面对三条矛盾条款自己挑一条：要把来源权威级别、生效日期、版本号、适用范围作为元数据带进来，在检索侧就对同一制度的多个版本去重或降权，让裁决规则可解释、可追溯。字段该怎么跟着块存，见[切分元数据与父块回溯](./k056-chunk-metadata.md)；裁决不了的场合该走拒答，见[溯源、拒答与零召回兜底](./k062-citation-abstain.md)。整套顺序可以从[从这里开始](./00-start-here.md)看起。

## 用换新版员工手册来理解

把知识库想成公司前台那摞员工手册，把提问想成员工来前台问一条规定。

不称职的管理员每次收到新版，就把新册子往那摞最上面一放了事，旧册子一本不收。结果前台同时摆着十个版本，谁来问就随手抽最上面一本，答案自然时新时旧。合格的做法是：新册子先在里间核对装订无误，确认是最终版，再把前台那本正式替换下来，旧册子收进档案柜标上「已废止」——前台永远只有一本现行版。

对应关系：新册子是待写入的新版本，里间核对是「构建中」状态，正式替换是原子切换活动版本，标「已废止」是软失效，档案柜是历史版本留痕。这个比喻还解释了两件事。第一，为什么不能「先撤旧的再放新的」：中间会有一小段空窗，员工来问时前台什么都没有；所以顺序必须是先备好新的、再一次性替换。第二，为什么旧册子不直接扔掉：出了纠纷要能回答「某年某月公司认为规定是什么」，物理覆盖或删除就再也查不回来了。

:::quote
更新不是「追加一条新记录」，是「备好新版本、原子切换、让旧版本失效」。少了后两步，库就会自己长出多个真相。
:::

## 把更新链路画出来

先看一次文档变更从被检测到可检索，经过哪些动作。

:::figure 一次文档变更走过哪些动作
@flow
检测变更|算内容指纹|构建新版本|校验后原子切换|旧版失效清理
:::

第二步「算内容指纹」是增量的开关：指纹没变就直接结束，不必往下走；第五步「旧版失效」绝不能省，否则就回到十个版本并存的局面。

一次更新该记哪些状态，可以列成清单：

:::figure 更新时要守住的几件事
@stack
内容指纹::判定是否真变了，没变就跳过重算
版本标记::新旧向量不能混用，查询只认当前版本
活动状态::前台只有一份现行版，切换要原子
生效时间::冲突裁决与时效过滤都靠它
:::

第二行尤其要命：换向量模型或换维度等于换了一套坐标系，新老向量放一起比较会得出莫名其妙的结果，这属于必须整体重算的那类变更，跟「单篇文档改一行」完全不是一回事。

再看两种更新习惯的差别：

:::figure 只追加，与先建后切
@compare
只追加新版本::库里多版并存|答案随机漂移|界面删了仍能召回
先建后切::活动版只有一份|切换可校验可回退|旧版留痕可审计
:::

第二行三格对应三种常见事故，恰好都是「只追加」会同时踩到的。

:::tip 一条立刻见效的规则
让检索查询永远带一个「当前活动版本」条件。删除的可见性只认一份可靠的状态记录，物理清理当后台任务慢慢做——宁可后台慢一点，也别让界面删掉的内容和索引里的状态对不上。
:::

## 再往深问两层

:::ask 那如果文档天天变，是不是每次都得把整库重算一遍？
:::

不必，而且整库重算恰恰是最该避免的常态做法。先按内容指纹把「真变了」的部分挑出来：一篇文档改了一段，只重算那一段及其派生数据，其余片段指纹一致就跳过；同一批内容被重复投递、后台任务重跑，也靠指纹加唯一约束挡住，不产生重复记录。变更检测优先用事件驱动，再配一个轮询兜底，防止事件漏投递。整库重算只留给两类场合：换了向量模型或维度（坐标系变了，必须重来），以及事故后的整体回退。把这两类混淆是最常见的坑——单篇编辑走增量，坐标系变更走全量，二者不可互换。还要留意并发：同一文档两版被两个任务同时处理，可能后写的旧版反而盖掉了新版，按文档编号固定分区让同一文档的事件有序，能挡住这类乱序。

:::ask 再深一层：两份材料真的打架了，裁决规则该怎么写才不会又变成一笔糊涂账？
:::

先分清「冲突」的两种来源，别一概算成矛盾。一种是同一制度的新旧版本，处理办法是按生效日期与版本号只留现行版，其余作为历史降权；另一种是不同来源对同一问题给出不同口径（比如集团制度与部门细则），这需要显式定义权威顺序：谁级别高、是否带适用范围、有没有生效与失效时间。裁决规则要写成可解释的确定性判断——比日期、比版本、比权威级别，这些由代码算好再写进上下文，别指望模型读完三段提示词自己选。还有个容易忽略的分支：两条其实不是矛盾而是补充（「一般情况」与「重要客户例外」），硬按「留最新」会把例外抹掉，所以要允许带条件的并列，并把条件一起带进上下文。无论哪种，都要把「当时选中了哪一版、依据哪条规则」记进日志，否则事后无法复盘；日志该记什么见[Trace 该记什么](./k094-trace-fields.md)。裁决之后若仍没有一条能撑住答案，就老实走[溯源、拒答与零召回兜底](./k062-citation-abstain.md)，别选一条凑数。

## 一份能跑的对照

下面这段只用标准库，演示内容指纹做增量判定、「只追加不失效」导致多版本并存、「先建后切」只留一份活动版，以及按权威级别与生效时间裁决冲突。

```python
# index_update.py —— 只用标准库，python index_update.py
import hashlib
from dataclasses import dataclass


def content_hash(text):
    # 给内容算定长指纹，用来判定「到底变没变」
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]


@dataclass
class Version:
    doc_id: str
    version: str
    text: str
    effective: str       # 生效日期，格式 YYYYMMDD
    authority: int       # 权威级别，越大越权威
    active: bool = True


def upsert_naive(store, v):
    # 错法：只追加新版本，不失效旧版本
    store.append(v)
    return store


def upsert_switch(store, v):
    # 对：同 doc_id 的旧版本全部失效，只留新的活动版本
    for old in store:
        if old.doc_id == v.doc_id:
            old.active = False
    store.append(v)
    return store


def active_of(store, doc_id):
    return [v for v in store if v.doc_id == doc_id and v.active]


def resolve(store, doc_id):
    # 裁决：先比权威级别，再比生效日期，最后比版本号
    cands = active_of(store, doc_id)
    return max(cands, key=lambda v: (v.authority, v.effective, v.version))


if __name__ == '__main__':
    v1 = Version("doc3", "v1", "一线城市每晚 400 元", "20230101", 1)
    assert content_hash(v1.text) == content_hash("一线城市每晚 400 元")
    assert content_hash(v1.text) != content_hash("一线城市每晚 600 元")
    h_old = content_hash(v1.text)

    naive = []
    upsert_naive(naive, v1)
    upsert_naive(naive, Version("doc3", "v2", "一线城市每晚 600 元", "20240101", 1))
    assert len(active_of(naive, "doc3")) == 2       # 多版并存，答案会漂移

    switched = []
    upsert_switch(switched, Version("doc3", "v1", "一线城市每晚 400 元", "20230101", 1))
    upsert_switch(switched, Version("doc3", "v2", "一线城市每晚 600 元", "20240101", 1))
    assert len(active_of(switched, "doc3")) == 1   # 活动版只有一份

    conflict = switched + [Version("doc3", "v3", "一线城市每晚 600 元",
                                   "20230101", 2)]
    winner = resolve(conflict, "doc3")
    assert winner.authority == 2                   # 权威级别高于日期
    assert content_hash(v1.text) == h_old           # 指纹稳定，增量可跳过
    print("通过 6/6 项：内容指纹、先建后切、活动版唯一与冲突裁决")
```

1. `content_hash` 用标准库 `hashlib` 对原文算 SHA-256 并截前 12 位，够用来判定「这段和上次是不是一样」。它把「文档改没改」变成一次确定性比较，而不是靠时间戳或文件名猜。
2. `Version` 把文档编号、版本号、原文、生效日期、权威级别、是否活动固定成字段。生效日期与权威级别是后面裁决的依据，得在建索引时就带上。
3. `upsert_naive` 是刻意留的反面：只 `append`，旧版本照样 `active=True`。`upsert_switch` 是正确做法：先把同 `doc_id` 的旧记录全部标记失效，再放进新版本，保证活动版唯一。
4. 中间两条断言把现象摆出来：只追加时同一文档有两个活动版本，先建后切后只剩一个。这正是「答案时新时旧」与「界面删了仍召回」的共同根因。
5. `resolve` 用 `max` 按「权威级别 → 生效日期 → 版本号」的次序裁决，是确定性判断，可解释也可记进日志。六条断言跑完打印通过项数。

想看得更清楚，可以把 `conflict` 里那份 `v3` 的 `authority` 改成 1，会看到胜出者变成生效更晚的 `v2`——裁决顺序一变，选中的版本就变，所以这条规则必须写死、写明、可回溯，绝不能让模型临场挑。

## 踩过的坑

- **只写新版本不失效旧版本**：现象是同一文档多个版本都可召回、答案随机漂移 → 原因是把更新当成顺向追加，漏了失效那一步 → 怎么改：先建后切，同文档旧记录统一标记失效，活动版唯一。
- **删除只改列表不改状态**：现象是界面里已删、检索仍能召回 → 原因是删除的可见性依赖了可丢的标记 → 怎么改：以可靠状态记录为准，物理清理交给可失败可重试的后台任务。
- **增量与全量混淆**：现象是换向量模型后召回结果诡异 → 原因是新老向量不在同一坐标系却混着比 → 怎么改：单篇编辑走增量，换模型或换维度必须整体重算并标记版本。
- **每晚清空重建**：现象是文档一多重建跑几小时、开销失控 → 原因是把全量重算当日常手段 → 怎么改：事件驱动加轮询兜底，只处理指纹变化的部分。
- **冲突全押在生成端**：现象是面对三条矛盾条款，提示词怎么写都只选一个或全罗列 → 原因是检索侧没做版本去重与降权 → 怎么改：把生效日期、版本、权威级别带进上下文，在检索侧先裁决。

## 三句话

索引更新、增量与知识冲突，是在文档常变时只重算变过的部分、让旧版本可靠失效，并按权威级别与生效时间裁决矛盾材料。
关键做法是内容指纹做增量、先建后切保活动版唯一、删除以可靠状态为准，裁决规则写成可解释的确定性判断。
当材料几乎不变、每次整体重算的代价也能接受时，不必专门做增量与版本裁决，直接重来更简单。

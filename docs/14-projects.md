# 三个能写进简历的项目

先看一句几乎每份转行简历上都有的话：

> 「基于大模型开发了智能客服系统，实现了自动问答与意图识别。」

面试官看到这句，内心是没波澜的。因为**它只说了「做了什么功能」，没说「在什么约束下、做了什么取舍、结果怎么验证」**。而后者才是这个岗位真正要考的东西。

:::quote
简历项目不是功能清单，是**一份能被追问四层的设计说明**。写的时候就要想好：对方会从哪几个方向追，你每一层拿什么证据接住。
:::

## 一、先破误解：项目要靠「约束」立住

对比两种写法：

| | 弱写法 | 强写法 |
|---|---|---|
| 功能 | 实现了自动问答 | 在「答案必须带出处、材料不足必须拒答」的约束下实现问答 |
| 技术 | 用了检索增强 | 双路检索 + 业务重排，解决新旧制度版本混用 |
| 结果 | 效果良好 | 30 条评测用例引用有效率 100%、应拒答场景拒答率 100% |
| 权衡 | 无 | 八成确定性查询走固定流程，仅两成多意图请求进循环，单次成本降 X |

差别不在文采，在**有没有可被验证、可被追问的锚点**。

一个通用的五段式讲法，三个项目都用它：

:::figure 讲项目的五段式
@stack
① 场景与约束::谁用、什么情况下用、硬约束是什么（不能编 / 不能越权 / 必须可恢复）
② 架构::分几层、每层职责、数据怎么流
③ 关键决策::至少两个「为什么选 A 不选 B」，带上取舍代价
④ 验证::用什么评测、多少条、看哪些指标、结果如何
⑤ 复盘::哪里没做好、线上踩过什么坑、下一版怎么改
:::

第 ⑤ 段最容易被省，但它最加分——**只有真做过的人才会讲「哪里没做好」**。

## 二、项目一：制度问答助手（检索 + 溯源 + 拒答）

**适合的定位**：入门项目，用来证明你懂「检索增强不是塞文档」和「语义校验」。

### 场景与约束

内部制度问答，硬约束三条：答案必须带段落编号；材料不足必须明确说缺什么；新旧版本并存时不能拿废止条款作答。

### 架构

:::figure 项目一架构
@flow
文档切分编号|双路索引|混合检索|版本重排|生成带引用|语义校验|降级或交付
:::

### 关键决策（面试要主动讲）

- **为什么双路检索**：只做关键词，用户换个说法（「没休的假能不能换钱」）就查不到；只做语义，精确条款号反而排不上去。混合 + 权重，并在评测集里专门留了「同义改写」用例。
- **为什么把版本规则放在重排而不是提示词里**：提示词只是提高胜率（第一篇结论），「2026 生效」是硬事实，必须由代码判定。
- **为什么设拒答阈值**：弱相关也硬答是幻觉事故的主要来源，宁可返回 `need_clarify`。

### 代码骨架

```python
def answer(query, index, blocks, contract):
    ranked = rerank(index.hybrid(query), blocks, query)   # 混合 + 业务重排
    picked = [(bid, s) for bid, s in ranked[:3] if s >= MIN_SCORE]
    if not picked:
        return {"answer": "", "citations": [], "need_clarify": True,
                "degraded": False, "reason": "材料不足"}
    material = "\n".join("[%d] %s" % (bid, block_text(bid)) for bid, _ in picked)
    # 交给模型前：包来源边界，防止文档里夹带指令
    ctx = build_context(SYSTEM, wrap_material(material), query)
    obj = call_with_contract(model, contract, ctx)       # 结构自纠，最多 2 次
    if obj is None:
        return structured_degrade("输出契约未通过")
    errs = semantic_check(obj, valid_ids={b.id for b in blocks})
    if errs:
        return {"answer": "", "citations": [], "need_clarify": True,
                "reason": "；".join(errs)}
    return obj
```

### 评测口径

30 条用例：正常路径 12、同义改写 6、版本冲突 4、材料不足 5、注入试探 3。看**引用有效率、应拒答拒答率、结构合法率**，不看「答案和标准答案像不像」。

### 追问预判

> 「怎么证明不是碰巧答对的？」→ 打印 top-k 及分数，展示相关段落稳定排第一。
> 「文档更新了怎么办？」→ 索引带版本号，增量重建；旧块标记废止而非删除，保证历史答案可追溯。
> 「用户问的跨了三段怎么办？」→ top-k 取 3~5，输出契约里 `citations` 是列表。

## 三、项目二：多步排障 Agent（循环 + 工具 + 可恢复）

**适合的定位**：主项目，用来证明你能手写循环、管状态、控副作用。这是三个里最值钱的一个。

### 场景与约束

运维排障：给一句「昨晚订单接口报错变多」，系统自己决定查日志、查链路、比对发布记录，最后给结论。**硬约束**：只读优先、任何写操作需人工确认、进程崩溃能从检查点继续、全程可回放。

### 架构

:::figure 项目二架构
@stack
接入层::限流 / trace_id / 幂等检查
循环层::State + build_context + 四类终止条件
工具层::Schema 校验 / 权限矩阵 / 幂等落盘 / 结果裁剪
存储层::检查点 + 轨迹 + 幂等表
观测层::结构化日志 / 指标 / 回放
:::

### 关键决策

- **为什么手写循环而不是直接用框架**：要逐条审计每一步、要自定义「证据不足就停」的终止条件；同时加一层适配，业务不依赖框架类型（[框架与工具协议](./10-framework.md)）。
- **为什么错误要进轨迹而不是抛异常**：失败是一次观察，模型看到「日志源超时」才会改查发布记录（[手写循环](./05-agent-loop.md)）。
- **为什么幂等要落盘**：进程重启后重试不会重复建工单。

### 代码骨架

```python
def run_incident(goal, trace_id):
    state = restore(trace_id) or State(goal)      # 崩溃恢复
    budget = Budget(max_rounds=8, max_calls=12,
                    max_seconds=10, max_cost=1.0)
    while True:
        stop = budget.check(state)
        if stop:
            return degrade(trace_id, stop)
        ctx = ContextBuilder.build(state)          # 带预算与摘要
        decision = model.decide(ctx)               # 输出契约校验
        if decision.action == "finish":
            return finalize(state, decision)
        obs = tools.execute(decision, state,       # 校验 / 权限 / 幂等
                            role="viewer")
        state.trace.append(observe(decision, obs))
        save_checkpoint(trace_id, state)           # 每轮原子落盘
        state.rounds += 1
```

### 评测口径

轨迹层为主：平均轮数、重复动作率、危险动作提议数、单次成本、崩溃恢复成功率。结果层用 8 条人工评分的排障结论做抽样。

:::tip 这个项目最容易出彩的一句话
「我们给循环设了轮数、调用数、耗时、金额四个独立上限——只设轮数时，出现过『轮数还早但一轮里调了 40 次工具』的情况。」**踩过坑并修好，比一开始就完美可信得多。**
:::

### 追问预判

> 「模型一直重复同一个动作怎么办？」→ 连续两轮 `动作+参数` 相同就强制换策略，并把「预算快用完」写进上下文。
> 「状态存哪？并发呢？」→ 检查点按 `trace_id` 分区，原子写；同一 id 加互斥，避免两个进程互相覆盖。
> 「怎么防止它删库？」→ 默认 viewer，权限本地判定，危险动作模型只能提议、人工批准。

## 四、项目三：批量内容处理流水线（分层 + 评测 + 成本）

**适合的定位**：进阶项目，用来证明你**知道什么时候不该用 Agent**——这是区分度最高的一点。

### 场景与约束

每天处理上千条用户反馈：分类、抽取要点、生成回复草稿。硬约束：单条成本上限、P95 延迟、结果可回归。

### 关键决策（全篇最重要）

:::figure 项目三的分层：不是所有流量都进 Agent
@compare
固定流程（约八成）::规则明确|单轮调用|模板化输出|便宜、可预测、好测
Agent 循环（约两成）::多意图 / 需跨系统查证|运行时决策|多轮|只在识别到复杂请求时启用
:::

- **为什么分层**：八成请求是「查进度」「改地址」这类确定任务，交给循环纯属浪费；分层后单次成本和 P95 都可控（[什么是 Agent](./04-what-is-agent.md)）。
- **为什么评测门禁接进发布**：提示词和输出模板都版本化，每次改动先跑 100 条用例，通过率不得低于基线才允许灰度。
- **为什么盯轨迹层的成本指标**：答案正确率会掩盖「绕远路蒙对」。

### 代码骨架

```python
def handle(item):
    # 预检路由：一次轻量判断，决定走哪条路
    if is_deterministic(item):
        return fixed_pipeline(item)        # 模板 + 单轮调用 + 结构校验
    return agent_run(item)                 # 带预算的循环

def fixed_pipeline(item):
    obj = call_with_contract(model, CONTRACT, render_template(item))
    return obj or structured_degrade("契约未通过")
```

### 评测口径

100 条用例（正常 60 / 边界 20 / 注入 10 / 历史回归 10），看通过率、平均轮数、单次成本、降级率。发布走「门禁 → 5% 灰度 → 观察三个指标 → 全量或回滚」（[从 Demo 到上线](./13-production.md)）。

### 追问预判

> 「怎么判断哪条该走 Agent？」→ 预检路由看意图数与是否需要跨系统查证，路由本身也被评测覆盖。
> 「分层会不会漏判？」→ 漏判走固定流程会返回 `need_clarify`，由人工兜底，不静默出错。
> 「成本降了多少？」→ 只说你实测过的口径和测量方法。

## 五、数字怎么说：只写可验证的口径

简历里最容易翻车的就是数字。三条原则：

:::warn 别编，也别写「显著提升」这种没法核的话
- **能复现**：写清「多少条用例、什么指标、怎么测的」，而不是一个孤零零的百分比；
- **能追溯**：数字来自哪次评测、哪一版，自己要能当场翻出记录；
- **说方法**：「30 条用例里引用有效率 100%」比「准确率 95%」可信得多，因为前者口径明确。
:::

| 别这么写 | 这么写 |
|---|---|
| 准确率大幅提升 | 30 条评测用例，引用有效率从 83% → 100% |
| 响应速度很快 | 固定流程分支 P95 320ms（1000 条抽样） |
| 成本降低明显 | 分层后单次平均调用轮数 4.2 → 1.3 |
| 系统稳定可靠 | 幂等落盘 + 四道预算，灰度期间降级率 < 1% |

## 六、简历对照：把一句话改到能追问

**改前**

> 负责智能客服开发，使用大模型与检索增强实现自动问答。

**改后**

> 制度问答助手：在「答案必须带出处、材料不足必须拒答」约束下，实现切分编号 → 双路混合检索 → 版本业务重排 → 输出契约自纠 → 语义校验链路；新旧版本冲突由代码判定而非提示词。30 条评测用例覆盖同义改写与版本歧义，引用有效率 100%、应拒答场景拒答率 100%；上线前接入回归门禁与结构化降级。

后面这段里，**每一句都能被追问，也每一句都有对应代码**。这就是目标。

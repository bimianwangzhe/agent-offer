# 结构层校验

## 场景提问

你让模型「只输出一个 JSON（JavaScript Object Notation，一种用花括号和方括号表示数据的纯文本格式）」，代码里写了 `data = json.loads(text)`，本地试了几条都没报错，于是直接把 `data["items"][0]["qty"]` 拿去算钱。推给真实用户没多久就炸了：有时报 `KeyError`，说 `status` 这个键不存在；有时报 `TypeError`，说某个数字其实是字符串；还有一次数量写成了 `true`，被当成 1 悄悄算进了总额。你翻回原始返回一看，每一条都是合法 JSON，括号配对、引号完整，`json.loads` 一次都没失败。明明解析全过了，怎么下游还是一地异常？

## 破误解

**不是解析函数失灵了，是把「能解析成数据」当成了「已经是我们约定的那个形状」。**

先把两层分清楚。语法层校验管的是「这段文本合不合 JSON 的语法」：括号有没有闭合、字符串有没有正确转义、逗号有没有多写。它答的是「能不能把字符串变成一个 Python 对象」，在 [语法层校验](./k016-syntax-check.md) 里已经讲过。结构层校验管的是完全不同的另一件事：这个对象里该有的字段在不在、每个字段的类型对不对、嵌套进去的数组和对象形状对不对、枚举类的值有没有落在允许集合里、有没有多冒出没约定的键。它答的是「这份数据能不能被下游按假设安全地读下去」。这两层是串联的两道闸门，不是同一件事的两种说法。很多人只在提示词里加一句「请严格按照下面的格式输出」，就以为格式有保障，可 [「请只输出 JSON」为什么不是保证](./k014-json-request.md) 已经说明过：提示词是请求，不是约束，模型偶尔漏字段、把整数写成带引号的字符串、给状态编一个新词，都属正常波动。真正兜住这些波动的，是解析之后你自己在代码里跑的那一段校验。这里要引出一个词：结构约定，也就是常说的 schema（读「斯基玛」，一份用数据描述「数据该长什么样」的清单），它把「必填哪些键、每个键是什么类型、允许哪些取值」写成机器能逐条核对的东西；[JSON Schema 约束](./k015-json-schema.md) 讲的就是这类约定的标准写法。本篇不依赖任何标准库之外的东西，用十几行递归代码把这份约定落实成一次可执行的检查，重点不在「用哪个库」，而在看清结构层到底检查了哪几类问题、以及它吐出来的错误为什么要带字段路径。

## 生活类比

把它想成网购到货后的验收。快递员把箱子递给你，箱子没破、胶带完整、面单能扫——这是语法层：包裹能被正常打开、内容能被读出来。你拆开箱子，对照订单清单开始清点：要买的是三节五号电池，箱里是不是三节、型号是不是五号、有没有把赠品当成正品混进来、有没有少一张发票——这是结构层。清点完你还得判断「这三节电池是不是同一个订单里的、保质期能不能对上发票日期」，那属于下一篇要讲的语义层，这一层先不管。

对应关系要落到具体动作上，不能只停在「像验收」这句话。箱子完好对应「字符串能被 `json.loads` 解析」；订单清单上列名的品项对应结构约定里的必填字段，少一件就当场登记；「五号」这个规格对应字段类型和枚举取值，型号不对不是「差不多能用」，而是明确的规格不符；箱里那件没下单的赠品对应额外字段，它不一定有害，但必须被识别出来再决定收不收；而验收单上写「第 2 格，型号不符」而不是只写「这箱不对」，对应的正是本篇最看重的产出——带字段路径的错误清单。这个类比还点破一件事：验收是收货方的动作，不是发货方的自我声明。卖家在商品页写「我们绝不发错」相当于提示词里的格式要求，可靠与否最终仍取决于你拆箱后有没有真的清点。把校验放在自己的代码里，而不是寄希望于对方守约，才是这一层存在的理由。

## 自绘示意图

:::figure 从一段文本到可用数据的两道闸门
@flow
拿到模型文本|语法层解析|结构层逐字段|收集路径错误|放行或退回
:::

五格里最容易被跳过的是「收集路径错误」。很多实现只返回一个布尔值，说「不合法」就结束了，结果下一环无论是退回给模型重生成、还是记进日志供人排查，都拿不到「到底哪儿不对」。结构层真正的价值一半在拦，另一半在把问题描述清楚。

:::figure 结构层要验的六件事
@stack
必填字段::约定里列名的键是否都在，缺一个就拦
字段类型::字符串、整数、数值、布尔、数组、对象各归各位
取值集合::枚举类的值只能落在允许列表里
嵌套形状::数组每个元素、对象每个子层都要单独验
数值范围::上下限与数组元素个数下限也要卡住
额外字段::没约定的键按白名单策略拒绝或显式忽略
:::

六件事里，「嵌套形状」和「额外字段」最常漏。前者是因为只验了最外层几个键就收工，数组里装的每一个元素其实都是一份独立的子数据，得递归进去各验一遍；后者是因为默认觉得多给点信息无所谓，可多出来的键往往是模型自由发挥的产物，放任它进门就等于默许输出契约可以被悄悄改写。

:::figure 只过语法层与加结构层的差别
@compare
只过语法层::能解析就放行|缺字段漏到下游|坏了只能运行时才炸
语法层加结构层::形状不对当场拦|错误定位到字段|下游拿到可预期数据
:::

左边那条路顺风顺水时最省事，代价是错误被推迟到下游某行取值代码才暴露，那时它已经不是「这次输出不合规」，而是一次带着业务后果的异常；右边把同样的错误提前到刚拿到文本的一刻，且明确告诉你坏在哪个字段。

## 层层追问

:::ask 那如果字段都在、类型也对，是不是就能直接拿去用了？
:::

还不能，这正是结构层的边界。它检查的是「局部形状」：某个键在不在、这一处的值是什么类型、这个数组有几个元素。它检查不了「跨字段是否说得通」。举个能自己构造的例子：一份报销汇总里 `start_date` 是「2026-03-10」、`end_date` 是「2026-03-08」，两个字段都是合法字符串，结构层挑不出任何毛病；`items` 里三项金额分别是 30、20、50，`total` 写着 120，四个数都是合法整数，结构层同样全过。可前者时间倒着走，后者分项加不出总额，这种「单看每格都合规、合起来却荒唐」的问题，得靠 [语义层校验](./k018-semantic-check.md) 里那种跨字段勾稽与跟外部参照对齐的规则来抓。还有一类结构层够不着的：某个引用的编号是否真的存在于本次给定的名单里、某个状态与另一个字段是否互斥、某个数值是否符合业务上限——这些都需要「参照数据」或业务规则参与，不是光看形状能断定的。所以三层是递进的：语法层保证读得开，结构层保证装得下，语义层保证说得通，谁也不能顶替谁。另外，把规则固化成可复用的断言，思路与 [性质断言](./k088-property-assertion.md) 是同一套，别让「这次好像没问题」替代一条写死的检查。

:::ask 那如果模型多塞了几个没约定的字段呢，一定要拒绝吗？
:::

要分情况，但第一步永远是「先识别出来」，而不是装作没看见。结构约定里有个开关叫「是否允许多余字段」：设成不允许多余字段，就是白名单（只放行清单上列名的键，其余一律算错）；设成允许，则多出来的键被忽略，不参与后续处理。什么时候该严？当输出会流进一个对键名敏感的下游，比如要按字段名拼进数据库列、或某个多出来的键恰好和下游保留字撞上，多一个键就可能引发越权或覆盖，这时必须拒绝，因为「宽容」等于把不可信输入放进了一条你没检查过的通道，这与 [参数有效不等于业务合法](./k034-param-validity.md) 里「合法格式不代表合法意图」是同一个道理。什么时候可以松？当输出只是给人看的展示文本，且下游代码明确只按白名单取自己要的几个键、其余根本不读，那么多塞的字段可以忽略——但要在日志里记一笔，让「模型又自由发挥了」这件事可见，否则契约被慢慢稀释都没人察觉。无论选哪种，都别用「把整个对象原样透传」来图省事：那等于让结构层白做。还有个细节：认出多余字段后，把「未约定字段 X」这样带名字的错误回给模型，比笼统说「格式错了」更容易让下一轮改对，这就接上了 [自动纠正与重试上限](./k019-auto-repair.md) 要讲的诊断信息怎么组织。

## 可运行代码与逐行解释

下面这段只用 Python 标准库里的 `json`，把一份结构约定写成一个普通的嵌套字典，再用一个递归函数逐字段核对。它接收的是字符串，因此顺带演示了「语法层过了才轮到结构层」这个顺序；所有错误都拼上 `$.items[0].qty` 这样的字段路径（`$` 表示根，点号表示进入子字段，方括号表示数组下标），方便直接回传或记日志。复制到任意装有 Python 的机器上可直接运行，不需要第三方包、账号或网络。

```python
import json


def is_int(value):
    """布尔是整数子类，需显式排除，否则 True 会被当成合法整数。"""
    return isinstance(value, int) and not isinstance(value, bool)


def validate(node, schema, path="$", errors=None):
    """按结构约定递归校验，把错误连同字段路径一起收集。"""
    if errors is None:
        errors = []
    kind = schema.get("type")

    if kind == "object":
        if not isinstance(node, dict):
            errors.append(path + " 应为对象")
            return errors
        for key in schema.get("required", []):
            if key not in node:
                errors.append(path + " 缺少必填字段 " + key)
        props = schema.get("properties", {})
        for key, sub in props.items():
            if key in node:
                validate(node[key], sub, path + "." + key, errors)
        if schema.get("additionalProperties") is False:
            for key in node:
                if key not in props:
                    errors.append(path + " 出现未约定字段 " + key)
        return errors

    if kind == "array":
        if not isinstance(node, list):
            errors.append(path + " 应为数组")
            return errors
        item_schema = schema.get("items")
        if item_schema:
            for i, item in enumerate(node):
                validate(item, item_schema, "%s[%d]" % (path, i), errors)
        if "minItems" in schema and len(node) < schema["minItems"]:
            errors.append(path + " 元素个数不足")
        return errors

    if kind == "string":
        ok = isinstance(node, str)
    elif kind == "integer":
        ok = is_int(node)
    elif kind == "number":
        ok = isinstance(node, (int, float)) and not isinstance(node, bool)
    elif kind == "boolean":
        ok = isinstance(node, bool)
    else:
        ok = True
    if not ok:
        errors.append(path + " 类型不符合 " + str(kind))
        return errors

    if "enum" in schema and node not in schema["enum"]:
        errors.append(path + " 取值不在允许集合")
    if "minimum" in schema and isinstance(node, (int, float)) and not isinstance(node, bool):
        if node < schema["minimum"]:
            errors.append(path + " 小于下限")
    return errors


CONTRACT = {
    "type": "object",
    "required": ["task", "items", "total", "status"],
    "additionalProperties": False,
    "properties": {
        "task": {"type": "string"},
        "items": {
            "type": "array",
            "minItems": 1,
            "items": {
                "type": "object",
                "required": ["name", "qty"],
                "additionalProperties": False,
                "properties": {
                    "name": {"type": "string"},
                    "qty": {"type": "integer", "minimum": 1},
                },
            },
        },
        "total": {"type": "number", "minimum": 0},
        "status": {"type": "string", "enum": ["ok", "pending", "failed"]},
    },
}


def check_text(text):
    """先过语法层（能否解析），再过结构层（形状是否符合约定）。"""
    try:
        data = json.loads(text)
    except json.JSONDecodeError as exc:
        return False, ["语法层解析失败：" + str(exc)], None
    errors = validate(data, CONTRACT)
    return len(errors) == 0, errors, data


def main():
    good = ('{"task":"盘点","items":[{"name":"螺丝","qty":3}],'
            '"total":12,"status":"ok"}')
    broken = '{"task":"盘点",'
    missing = '{"task":"盘点","items":[{"name":"螺丝","qty":3}],"total":12}'
    bool_qty = ('{"task":"盘点","items":[{"name":"螺丝","qty":true}],'
                '"total":12,"status":"ok"}')
    bad_enum = ('{"task":"盘点","items":[{"name":"螺丝","qty":3}],'
                '"total":12,"status":"done"}')
    extra = ('{"task":"盘点","items":[{"name":"螺丝","qty":3}],'
             '"total":12,"status":"ok","note":"顺手加的"}')
    nested = ('{"task":"盘点","items":[{"name":"螺丝"}],'
              '"total":12,"status":"ok"}')
    empty_items = '{"task":"盘点","items":[],"total":12,"status":"ok"}'

    ok1, e1, d1 = check_text(good)
    ok2, e2, d2 = check_text(broken)
    ok3, e3, _ = check_text(missing)
    ok4, e4, _ = check_text(bool_qty)
    ok5, e5, _ = check_text(bad_enum)
    ok6, e6, _ = check_text(extra)
    ok7, e7, _ = check_text(nested)
    ok8, e8, _ = check_text(empty_items)

    checks = [
        ("合法文本通过且错误为空", ok1 and e1 == [] and d1["status"] == "ok"),
        ("语法坏文本停在语法层", not ok2 and d2 is None and "语法层" in e2[0]),
        ("缺必填字段被拦并点名", not ok3 and any("缺少必填字段 status" in x for x in e3)),
        ("嵌套元素类型错误带路径", not ok4 and any("$.items[0].qty" in x for x in e4)),
        ("布尔不被当成整数", not is_int(True) and is_int(3)),
        ("枚举越界被拦", not ok5 and any("允许集合" in x for x in e5)),
        ("未约定字段被拦", not ok6 and any("未约定字段" in x for x in e6)),
        ("嵌套对象缺字段带下标路径", not ok7 and any("$.items[0]" in x for x in e7)),
        ("空数组触发个数下限", not ok8 and any("元素个数不足" in x for x in e8)),
        ("错误清单都是路径化字符串", all(isinstance(x, str) for x in e3 + e4 + e5 + e6)),
    ]
    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `is_int` 单独拆出来，是因为 Python 里布尔值属于整数的子类，`isinstance(True, int)` 会返回真。若不排除，模型把数量写成 `true` 会被当成合法整数 1 悄悄算进业务，比直接报错更危险。`number` 分支也做了同样的排除。
2. `validate` 是整套检查的主体，`errors` 用 `None` 作默认值再在函数内创建列表，避免可变默认参数在多次调用间串数据。`path` 从 `$` 起步，每进一层就拼上 `.键名` 或 `[下标]`，于是错误天然带上位置。
3. `object` 分支先确认这一处确实是字典，再逐条查必填字段，然后只对「约定里写了、且数据里确实存在」的键递归下去——缺的键只登记一次缺失，不会再去解引用它而抛出额外异常。最后若 `additionalProperties` 为 `False`，就遍历实际键，把不在白名单里的那些记成「未约定字段」。
4. `array` 分支把 `items` 当成「每个元素都要遵守的子约定」，用 `enumerate` 带着下标递归；`minItems` 卡的是元素个数下限，空数组不该被当成合法清单放行。这两处合起来，就是图里「嵌套形状」那一格的实现。
5. 标量部分用一个 `ok` 变量统一判定四种基本类型，类型不符时把带路径的说明追加进列表并提前返回；通过后才继续查 `enum`（允许取值集合）与 `minimum`（数值下限）。顺序是有意的：先确定类型，再做依赖类型的比较，免得拿字典跟数字比大小。
6. `CONTRACT` 把契约写成纯字典：顶层四个必填键、不允许多余字段、`items` 是一个至少含一个元素的数组、其元素又是一个带 `name` 与 `qty` 的小对象、`status` 只能取三个词之一。它既是校验依据，也是一份人能读的输出契约，改格式时只改这一处。
7. `check_text` 把顺序钉死：先 `json.loads`，解析失败就返回「语法层解析失败」且数据为 `None`，绝不进入结构层；解析成功才跑 `validate`。返回值是「是否通过、错误清单、解析后的数据」三元组，通过时下游可以直接用数据，不通过时错误清单就是回传给模型的诊断材料。
8. `main` 用八段手工构造的字符串覆盖八类情况：完全合法、JSON 本身写坏、缺字段、布尔冒充整数、枚举越界、多字段、嵌套对象缺字段、空数组。每组断言都只核对「该不该被拦」和「错误里有没有点到具体位置」，结果可逐条手算；结尾统计通过项数并 `assert` 全部成立，任何一条性质被改坏都会以非零状态退出。

有一处要如实说明：这里的文本都是手工构造的样例，用 `json.loads` 代替了真实模型返回，用普通字典代替了配置中心里的契约，全是为了让整条链路不联网、不装第三方包就能独立跑通并手工核对。它演示的是「语法层之后还要逐字段核对、且错误要带路径」这件事，不是任何具体校验库的实现。

## 踩坑与边界

- **只 try 解析不验字段**：现象是 `json.loads` 从没报错，下游却时不时 `KeyError` → 原因是把「能解析」当成了「字段齐全」 → 解析之后固定跑一遍结构层，必填键逐个确认，再允许下游取值。
- **用 `type(x) == int` 判整数**：现象是 `true` 被当成 1 算进金额，或者反过来把合法数值误判 → 原因是 Python 里布尔是整数子类、且子类关系让朴素比较失真 → 整数判定显式排除布尔，数值判定也一并排除，必要时区分「整数」与「可有小数」两种约定。
- **用 `obj.get("k")` 把缺失当正常值**：现象是字段不存在时拿到 `None`，一路传下去才在很后面炸，日志里看不出源头 → 原因是 `get` 把「缺失」和「确实为 None」混成了一件事 → 缺失必须在校验阶段作为一条独立错误登记，别靠取值时的默认值兜着。
- **只验最外层、不进数组**：现象是顶层几个键都对，数组里某个元素少字段或类型错，照样漏到下游 → 原因是把数组当成一个整体看了一眼 → 把 `items` 当成每个元素都要遵守的子约定递归校验，并给错误拼上下标路径。
- **多余字段一律放行**：现象是模型慢慢往输出里加键，某天某个键和下游保留字撞上，引发覆盖或越权 → 原因是对键名敏感的下游默认信任了整份对象 → 敏感链路设成不允许多余字段；可宽容的链路也要显式按白名单取键并记日志，别原样透传。

还要划清两道边界。一是结构层管不到的那些「合起来才看得出」的错，前面追问里已经举过日期倒挂、分项对不上总额的例子，它们属于语义层，也需要外部参照数据参与，别指望加几条类型规则就能顺带解决；把这件事做扎实可对照 [语义层校验](./k018-semantic-check.md)。二是别把约定定得过严：把「可有可无」的字段全列成必填、把允许取值收得比业务还窄，会让大量本来可用的输出被误杀，反而推高重试次数和成本，这与 [自动纠正与重试上限](./k019-auto-repair.md) 里「先分清什么值得重试」相呼应。校验的目标不是追求零错误返回，而是让「放行的一定能用、拦下的一定说得清为什么」。三段合起来看，输出契约的可信度来自 [语法层校验](./k016-syntax-check.md) 到本篇再到语义层的逐层收紧，而不是提示词里那句格式要求写得够不够重。

:::check 学完自检

- [ ] 能列出结构层至少要验的六类问题，并解释为什么数组元素要递归
- [ ] 能说明错误为什么要带字段路径，而不只是返回一个「不合法」

- [ ] 能徒手举出一个「每格都合规、合起来却荒唐」的例子，并说清该由哪一层拦
:::

## 三句话小结

结构层校验是解析成功之后的一道闸门，按事先写好的结构约定逐字段核对必填、类型、取值集合、嵌套形状与多余字段，把「能读」推进到「能被下游按假设安全使用」。

关键做法是让校验跑在自己的代码里、让错误带上 `$.items[0].qty` 这样的路径、让数组与子对象都递归受检，并据此决定放行还是把具体诊断回传给模型。

当数据要跨字段核对、要和外部名单对齐、或要判断业务上是否说得通时，这一层不该被当成终点；而当输出只是给人看的自由文本、根本没有固定形状可验时，也不必硬套一份结构约定。

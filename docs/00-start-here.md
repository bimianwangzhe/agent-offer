# Agent 开发学习路线一条龙：要掌握的全部知识点

打开招聘软件搜「Agent 开发」，那串要求里同时写着大模型、工具调用、检索增强、上下文工程、评测、多智能体、生产落地。第一反应往往是「完了，我得先把大模型学一遍」，于是去搜学习路线，收藏一张密密麻麻的名词清单，第二天再打开，还是不知道第一步该敲什么。

**这份清单要破的误解只有一个：这个岗位不考你造模型，考的是把一个不确定的组件，装进一个确定的系统里。**

把它想成开一家小餐馆。模型是那位手艺很好但记性一般、偶尔会自由发挥的厨师；提示词是你贴在墙上的出餐标准；工具是厨房里的设备；上下文是灶台上那块有限的案板——放不下就得把东西挪到架子上，要用时再取；检索是冰箱和库房；记忆是那本写满了老顾客口味的笔记；评测是每道菜出餐前的尝一口；护栏是燃气阀和灭火器；生产化是备料、排队、断电时怎么办。厨师再厉害，没有后面这些，餐馆开不过第三天。

所以「要学什么」不是背名词，而是把这家餐馆从灶台到打烊的每一个环节都摸一遍：知道每个环节解决什么问题、不做会出什么事、做错了怎么发现。下面按这个顺序，把全部知识点逐条列出来。

:::figure 一条龙主线：从一次调用到能讲清楚的作品
@flow
可信的调用|自己决定下一步|安全地碰到世界|管住上下文与知识|证明它靠谱|串成作品并讲清楚
:::

:::tip 这份清单怎么用
**每一条知识点后面都有一个链接，点开就是本站一篇完整正文**：有场景提问、有推导、有自绘示意图、有可运行代码、有踩坑边界、有自检清单。不是让你再去别处搜。按顺序读，读完用每篇末尾的自检清单自问一遍，答得上来再往下走。

## 第 1 组 · 模型与调用（15 条）

先别急着写 Agent。你得先知道一次调用里到底发生了什么：模型不是在「理解」你，它是在按已有文字猜下一个词；你给的每一段文字都要占额度、都要花钱、都可能在长到一定程度后被挤走。把这一层拆开，后面所有「输出不稳、越聊越贵、答非所问」才有解释。这一篇不要求你懂训练，只要求你能把一次请求拆成能逐项排查的五块。

**学完能做什么**：能独立写出一个带超时、重试、用量统计的调用脚本，并说清模型为什么会出错。

| 编号 | 知识点 | 它是什么 / 不做会怎样 |
|---|---|---|
| K001 | [Token 与分词](./k001-token.md) | 模型读写的基本单位，输入输出都按它计量，也是上下文长度的度量。 |
| K002 | [下一个词预测](./k002-next-token.md) | 模型只在做一件事：根据已有文字猜下一个最可能的 token，循环到该停为止。 |
| K003 | [上下文窗口](./k003-context-window.md) | 一次调用里模型这一眼能看到的全部文字，超了会截断或报错。 |
| K004 | [采样参数与不确定性](./k004-sampling.md) | 温度、top_p 控制随机程度；调到 0 也不等于确定，因此不能用确定性断言去测。 |
| K005 | [幻觉为什么必然存在](./k005-hallucination.md) | 不是模型坏了，是它把话接得太像真的；真实性必须由系统外部补上。 |
| K006 | [基础模型 / 指令模型 / 推理模型](./k006-model-types.md) | 三者的训练目标不同，选型看任务匹配而不是参数或宣传口径。 |
| K007 | [消息角色与对话拼装](./k007-message-roles.md) | system / user / assistant / tool 各自的位置与优先级，拼错顺序会改变行为。 |
| K008 | [一次请求拆成五块](./k008-request-anatomy.md) | 地址、鉴权、消息体、参数、返回；拆开才能逐项排查与替换实现。 |
| K009 | [流式输出与首字延迟](./k009-streaming.md) | 边生成边返回降低等待，但要处理半截内容、中断与拼接。 |
| K010 | [用量统计与计费口径](./k010-usage-billing.md) | 按任务、按用户记录输入与输出用量，是成本优化与账单告警的前提。 |
| K127 | [max_tokens 与停止条件](./k127-max-tokens.md) | 输出长度上限配合结束符与停止词控制生成边界；设太小会截断成半截 JSON。 |
| K128 | [流式断线恢复与分片校验](./k128-stream-recovery.md) | 事件 ID、分片排序与断点续传；只做前端拼接会产生残缺或重复文本。 |
| K129 | [Embedding 与向量化](./k129-embedding.md) | 把文本映射为稠密向量，是检索、长期记忆、去重的共同地基；换模型必须重建索引。 |
| K130 | [相似度度量对齐](./k130-similarity.md) | 余弦、点积、欧氏距离代表不同的「相近」；度量方式必须与向量模型训练口径一致。 |
| K131 | [异常分类与可重试判定](./k131-error-classify.md) | 区分瞬时网络错、限流、参数错、服务故障；盲目重试会放大限流与账单。 |

:::warn 这一组最容易踩的三个坑
- 以为温度调到 0 就完全确定，于是用「输出必须一字不差」去写断言
- 把上下文窗口当成「能装多少字」而不是「每轮都要重新读一遍的输入」
- 把幻觉当成模型坏了，试图靠换模型解决，而不是在系统外部补事实校验
:::

## 第 2 组 · 提示与输出契约（13 条）

模型返回的东西不能直接拿去用。很多人第一周的坑都长在同一个地方：写了「请只输出 JSON」，然后某天模型多说了一句「好的」，整条流水线就崩了。这一组把「希望」变成「契约」：先写清结构，再分三层校验，最后让不合法的输出自动纠正、超过次数果断降级。核心思想只有一句——约束由代码执行，不由模型自觉。

**学完能做什么**：能让不合法输出自动纠正、超过次数果断降级，而不是靠祈祷模型听话。

| 编号 | 知识点 | 它是什么 / 不做会怎样 |
|---|---|---|
| K011 | [系统提示该写什么](./k011-system-prompt.md) | 常驻声明身份、能力边界、输出格式与禁止事项；别把业务事实写死在里面。 |
| K012 | [少样本示例](./k012-few-shot.md) | 用几个完整示例定格式，比讲一堆道理更能稳定输出。 |
| K013 | [思维链与分步引导](./k013-chain-of-thought.md) | 引导分步推理改善复杂任务稳定性，但不改变输出的非确定性。 |
| K014 | [「请只输出 JSON」为什么不是保证](./k014-json-request.md) | 这是请求不是约束；模型随时可能加解释、包代码块、漏字段。 |
| K015 | [JSON Schema 约束](./k015-json-schema.md) | 把输出结构写成机器可读描述，让校验有依据，也让模型有明确目标。 |
| K016 | [语法层校验](./k016-syntax-check.md) | 第一关只看能不能解析，失败优先做清洗与提取而不是立刻重问。 |
| K017 | [结构层校验](./k017-structure-check.md) | 第二关看字段齐不齐、类型对不对、嵌套有没有缺。 |
| K018 | [语义层校验](./k018-semantic-check.md) | 第三关看值是否合法：枚举、范围、引用 ID 是否真实存在、是否自相矛盾。 |
| K019 | [自动纠正与重试上限](./k019-auto-repair.md) | 把具体错误信息回传给模型纠正，并设次数上限防止死循环。 |
| K020 | [果断降级与兜底返回](./k020-graceful-fallback.md) | 超过次数就返回确定的默认结果或人工接管，绝不让调用无限挂起。 |
| K132 | [结构化提示词模板六模块](./k132-prompt-template.md) | 角色、任务、约束、输出格式、示例、异常处理分开维护，才能定位是哪段改动导致行为漂移。 |
| K133 | [分隔符与输入定界](./k133-delimiter.md) | 用明确标记把不可信数据块包起来并声明「这是数据」，但定界符本身也可能被伪造绕过。 |
| K134 | [约束解码原理](./k134-constrained-decoding.md) | 在生成时直接限制候选 token 使输出必然合法，与「事后校验再重试」是两条不同的路。 |

:::warn 这一组最容易踩的三个坑
- 把「请只输出 JSON」当成保证，线上某天多一句寒暄就整条链路崩
- 只做语法解析就放行，字段缺失或枚举值非法一路流到业务层
- 自动纠正不设次数上限，模型反复犯同一个错，循环把成本打穿
:::

## 第 3 组 · Agent 循环与状态（11 条）

从这里开始才叫 Agent。分界线不是「有没有循环」，而是**下一步做什么由谁决定**：代码里写死的是流程，运行时由模型决定的才是 Agent。这一组的重点不是那个 while，而是状态里存了什么、四个终止条件是否齐全、工具报错能不能变成下一轮的观察、出事之后能不能把当时的轨迹完整复现出来。手写一遍这些，框架就不再是黑盒。

**学完能做什么**：能徒手写出一个可终止、可回放、可恢复的多步循环，不依赖任何框架。

| 编号 | 知识点 | 它是什么 / 不做会怎样 |
|---|---|---|
| K021 | [Agent 的唯一判据](./k021-agent-criterion.md) | 下一步做什么由模型在运行时决定，还是事先写死在代码里。 |
| K022 | [Workflow 与 Agent 的分界](./k022-workflow-vs-agent.md) | 路径能预先固定就用流程；上 Agent 是为了解决路径不确定，不是为了时髦。 |
| K023 | [决策—行动—观察闭环](./k023-decision-loop.md) | 选动作、执行、拿结果、再决策，直到达标、失败、超限或人工接管。 |
| K024 | [ReAct：推理与行动交替](./k024-react.md) | 用外部工具拿新信息，再据此决定下一步；要讲清 Thought / Action / Observation 各自存哪。 |
| K025 | [Plan-and-Execute](./k025-plan-execute.md) | 先统筹任务清单与完成标准，再逐项执行，适合长任务与跨系统操作。 |
| K026 | [反思与自我修正](./k026-reflection.md) | 按评价标准回看并修改产物；弱点是重复自身偏见，必须配外部验证器。 |
| K027 | [循环状态该存什么](./k027-loop-state.md) | 目标、历史、观察、轮数、预算、已完成步骤用结构化字段存，不靠聊天记录。 |
| K028 | [四个终止条件](./k028-stop-conditions.md) | 完成、超预算、重复动作、不可恢复错误，缺一个就可能跑飞。 |
| K029 | [错误回传](./k029-error-feedback.md) | 工具报错不是抛异常结束，而是变成下一轮的观察交给模型决策。 |
| K030 | [检查点与轨迹回放](./k030-checkpoint-replay.md) | 每一步状态与观察落盘，出事后能复现当时到底发生了什么。 |
| K135 | [目标漂移与周期性重述](./k135-goal-drift.md) | 长任务里模型会逐渐偏离原始目标，需要周期性把目标与完成标准重新写回上下文。 |

:::warn 这一组最容易踩的三个坑
- 把 while 循环当核心，状态里却只存了对话历史，没有目标、轮数与预算
- 终止条件少一个「重复动作检测」，模型在两个工具之间来回弹
- 工具报错直接抛异常结束，而不是把错误变成下一轮的观察
:::

## 第 4 组 · 工具与函数调用（13 条）

让文字碰到真实世界，代价是它真的能改数据、发消息、下订单。所以工具从来不是一个函数列表，而是一份契约：模型只负责声明「调哪个、传什么」，执行与放行永远在宿主程序。这一组把 Schema、描述、参数校验、权限矩阵、幂等键、超时对账、失败分类逐项拆开。记住一条：一个语法完全合法的 JSON，也可能是一次越权操作。

**学完能做什么**：能设计带参数校验、权限分级、幂等防重的工具层，且不因一个合法 JSON 就放行危险动作。

| 编号 | 知识点 | 它是什么 / 不做会怎样 |
|---|---|---|
| K031 | [Function Calling 的职责边界](./k031-fc-boundary.md) | 模型只声明调哪个工具、传什么参数，真正执行永远在宿主程序。 |
| K032 | [工具 Schema 设计](./k032-tool-schema.md) | 类型、枚举、必填、取值范围写清楚，能挡掉大半参数错误。 |
| K033 | [工具描述写法](./k033-tool-description.md) | 描述是给模型看的接口文档：说清适用与不适用，比函数名重要得多。 |
| K034 | [参数有效不等于业务合法](./k034-param-validity.md) | 合法 JSON 也可能越权、超限额、操作别人的数据；业务规则要另做一层。 |
| K035 | [工具返回格式设计](./k035-tool-result.md) | 结构化、可判定、不冗长；错误信息要让模型能据此改参数。 |
| K036 | [工具清单减肥与分层路由](./k036-tool-routing.md) | 工具太多时先做轻量判断，只把本轮相关的几个带进上下文。 |
| K037 | [权限矩阵与最小权限](./k037-permission-matrix.md) | 读、写、危险动作分级；按用户与会话授予，不按模型意愿授予。 |
| K038 | [幂等键与副作用防重](./k038-idempotency-key.md) | 为每个有副作用的动作分配稳定标识，重试前先查执行状态。 |
| K039 | [超时不等于没执行](./k039-timeout-reconcile.md) | 网络超时时动作可能已经生效，必须先对账再决定是否允许重试。 |
| K040 | [工具失败分类与重试策略](./k040-tool-failure.md) | 区分可重试、不可重试、需人工三类，别把所有错误都交给模型碰运气。 |
| K136 | [tool_call_id 配对与并行调用](./k136-tool-call-id.md) | 每次调用结果必须严格对应发起时的 id；并行调用前要判断动作之间有没有依赖。 |
| K137 | [用户身份服务端注入](./k137-identity-injection.md) | 身份与权限不能让模型填进参数，必须由服务端按会话注入，否则参数篡改就是越权。 |
| K138 | [超大工具结果裁剪与二级工具](./k138-large-result.md) | 原始返回撑爆上下文时，先裁剪或落盘，再提供按 id 取详情的二级工具。 |

:::warn 这一组最容易踩的三个坑
- 参数通过类型校验就执行，忘了业务层的越权、限额与归属判断
- 网络超时就重试，没先对账，结果同一笔动作执行了两次
- 把所有工具描述一次性塞进上下文，模型选错工具的概率反而更高
:::

## 第 5 组 · 上下文工程（12 条）

Demo 很聪明、上线聊二十轮就变笨，几乎都不是模型退化，而是把上下文当成了无限容器。上下文不是聊天记录，是每轮都要重新组装的一份有限预算的输入。这一组教你先算账、再分层，然后分别处理滑动窗口、摘要、检索式召回、结构化状态，并且**验证压缩没把关键信息弄丢**。先做预算和裁剪，再考虑换更大的窗口。

**学完能做什么**：能给长对话做预算、分层与压缩，并验证压缩没把关键信息弄丢。

## 第 6 组 · 检索增强 RAG（16 条）

模型不知道你公司的制度、昨天的工单、这份 PDF 里写了什么。把外部知识塞进提示词既贵又不可更新，检索增强是让答案能带出处、可控可更新的那条路。这一组从离线索引与在线检索两段讲起，逐个拆切分、双路召回、融合、查询改写、过滤前置、重排、溯源、拒答、索引更新，最后强调一件事：检索质量和答案质量必须分开评测，否则你永远不知道是搜错了还是答错了。

## 第 7 组 · 记忆系统（11 条）

把发生过的事全存下来，那叫日志，不叫记忆。记忆是「会影响未来决策的那一小部分」，所以难点从来不是存，而是写入判定、冲突消解、召回排序和遗忘退出。这一组会反复追问：这条该不该记？两份事实矛盾听谁的？过期或敏感信息怎么退出？以及最容易被忽略的——外部内容能不能被写进长期记忆。

**学完能做什么**：能设计分层记忆，并说清哪些东西坚决不该记。

## 第 11 组 · 生产化与成本（12 条）

从 Demo 到敢开给别人用，差的是一整套确定性：同一个请求重放不能重复产生副作用、下游抽风要有退避与兜底、长任务中断后能从检查点续跑、凭据过期要有刷新路径、新版本先影子再灰度、提示与策略要能版本化和回滚、并发打满要排队而不是一起超时。最后给一份能照着勾的发布清单。

**学完能做什么**：能照着一份上线检查清单逐项勾完，并给出故障时的兜底与回滚路径。

| 编号 | 知识点 | 它是什么 / 不做会怎样 |
|---|---|---|
| K107 | [幂等落盘](./k107-idempotent-persist.md) | 动作与状态持久化，重放同一请求不会重复产生副作用。 |
| K108 | [重试、指数退避与抖动](./k108-retry-backoff.md) | 间隔翻倍、加上限与随机抖动，避免下游恢复瞬间被重试打垮。 |

| K110 | [优雅中断与断点恢复](./k110-graceful-resume.md) | 从检查点续跑、处理过期凭据、避免重复已完成动作。 |
| K111 | [凭据过期与刷新](./k111-credential-expiry.md) | 长任务里凭证会失效，要有刷新与明确的重新授权路径。 |

## 第 12 组 · 多智能体与项目表达（12 条）

先把「该不该拆多智能体」判断清楚：多数真实任务里，工具设计良好的单 Agent 比多 Agent 更稳，拆开只会把状态、冲突与成本一起放大。判断完再把做过的东西讲成作品——简历不写「做了智能助手」，写清边界、为什么不选另一条路、结果怎么验证。最后练追问链：面试官追的从来不是知识点，是决策链。

## 三、知识点之间的依赖关系

顺序不是随便排的：后一组一定要用到前一组给出的东西。跳着读不会立刻出错，但会在某个环节「怎么调都不对」，然后回来补。

| 先解决什么 | 对应分组 | 为什么必须在这个位置 |
|---|---|---|
| 先有可信的调用 | 模型与调用基础 → 提示词与输出契约 | 连一次请求会返回什么都不确定、输出不能解析，后面所有设计都悬空 |
| 再让模型能自己决定下一步 | Agent 循环与状态 → 工具与函数调用 | 循环能转、能停、能回放，才有资格谈「让它碰到真实世界」 |
| 然后管住它看什么、知道什么 | 上下文工程 → 检索增强 → 记忆系统 | 先有预算与裁剪，再补外部知识与跨会话事实，顺序反了会越做越贵 |
| 接着解决「怎么规模化、怎么换实现」 | 框架与协议 | 手写过一遍之后再看框架，才分得清它替你做了什么 |
| 能跑之后才谈「怎么证明靠谱」 | 评测与可观测性 → 安全与护栏 → 生产化与成本 | 没有评测就不知道改动是变好还是变坏；没有护栏与幂等就不敢开放给别人 |
| 最后串成作品并讲清楚 | 多智能体与项目表达 | 先有约束、评测与故障复盘，简历与追问链才有内容可讲 |

:::figure 依赖不是并列，是层层踩上去
@stack
调用与输出契约::不确定性能不能变成可解析、可校验的结果
循环与工具::有了可信结果，才谈得上让模型自己决定下一步
上下文与知识::能动手之后，才需要管住它看什么、记得什么
评测与护栏::能跑了，才谈得上证明靠谱、敢开放给别人
生产化与表达::能交付了，最后串成作品并讲清决策链
:::

## 五、怎么用这份清单自检

不要以「看完了」为结束。每读完一组，用下面四个问题自问一遍，答不上来就回到对应正文，别硬往下走。

- [ ] 能不能不看资料，把这一组解决的问题用一句大白话讲给完全不懂的人听？
- [ ] 能不能徒手画出这一组的示意图，并说明每个箭头代表什么数据？
- [ ] 能不能说出「不做这一条，线上会出什么具体事故」？说不出就是没理解。
- [ ] 能不能把每篇末尾的可运行代码改一个参数、加一个用例，并预测输出会怎么变？

:::tip 关于动手
文中所有示例只用 Python 标准库，零账号、零联网、复制保存就能跑。先跑通，再改参数，再故意制造一个坏输入看它怎么兜底——这三步比读三遍正文管用。
:::

## 六、常见误区（提前说清，省得绕路）

| 想法 | 为什么不对 |
|---|---|
| 「先把大模型原理学透再动手」 | 这个岗位考的是把不确定的组件装进确定的系统，用到的是契约、校验、状态、权限、评测这些工程能力 |
| 「装个框架就会做 Agent 了」 | 框架只是把状态、循环、工具分发、追踪、重试、持久化包起来；没手写过一遍，出问题只能换提示词 |
| 「上下文不够就换更大窗口」 | 单价与延迟一起涨，注意力被摊薄，很多内容本来就不该带进这一轮 |
| 「评测等做完再补」 | 没有用例集与回归门禁，你无法证明任何一次改动是变好还是变坏 |
| 「多智能体更先进」 | 职责、上下文、验证或并行收益不真实存在时，拆开只会把状态冲突与成本一起放大 |
| 「先收集更多教程」 | 缺的不是资料是动手；这一份清单每一条都直接点开正文，够走完全程 |

## 七、三句话小结

这份清单把 Agent 开发要掌握的知识拆成十二组、153 条，每一条都对应一篇有推导、有图、有可运行代码的完整正文。
顺序按依赖关系排：后一组必须踩在前一组上，所以别跳着读，也别急着上框架。
真正要带走的不是名词，而是「不做这一条会出什么事故、怎么验证做对了」这套判断力——它既是工程能力，也是面试里被追到第四层时唯一靠得住的东西。

# 框架与工具协议：它们到底替你做了什么

先说一个转行路上特别容易掉进去的坑：

你花两周学会一个框架，能跑 Demo 了。换到下一家公司，用的是另一套，于是又从零学一遍。学第三个的时候开始怀疑人生——**「我到底在学什么？」**

答案是：你在学「某一个团队对若干问题的一种选择」，而不是在学 Agent 本身。选择会换，问题不会。

:::quote
框架不是知识，是**别人替你做掉的一堆决策**。手写过一遍循环之后，你要做的是把它当成「可替换的部件清单」来看，而不是当成要背的 API。
:::

## 一、先把框架拆回你认识的东西

回到[手写循环](./05-agent-loop.md)那 200 行。任何一个 Agent 框架，本质上都在接管下面这六件事：

:::figure 框架的六大件，全部能在手写循环里找到对应
@stack
状态管理::对应 State / trace，框架通常叫 State + Checkpointer
上下文组装::对应 build_context，框架叫 Prompt / Message 编排
动作注册::对应 ToolBox.spec()，框架叫 Tool / Function 注册
循环驱动::对应 while + stop_reason，框架叫 Graph / Executor
持久化::对应 save_checkpoint，框架叫 Persistence / Store
可观测::对应 replay，框架叫 Tracing / Callback
:::

看清楚这张表之后，学新框架就变成了一件很省力的事：不再是「从零学一套」，而是**逐个问「这六件它怎么做的、我认不认可这个做法」**。

:::tip 一个立刻能用的学习方法
拿到任何新框架，先只找三个东西：**状态存在哪、循环怎么停、轨迹怎么拿**。这三个找到了，剩下的 API 用到再查。找不到「怎么停」的，先别上生产。
:::

## 二、框架分四类，别拿错工具

按「接管了多少」分，比按名字记有用得多：

| 类型 | 接管了什么 | 适合 | 风险 |
|---|---|---|---|
| **轻量调用库** | 只包请求/响应、重试、流式 | 固定流程、只要稳 | 不解决循环与状态 |
| **编排 / 状态图** | 循环、分支、状态、检查点 | 多步任务、需要可恢复 | 概念多，容易把业务写进图里 |
| **多角色协作** | 多个角色的分工与交接 | 确实需要不同视角时 | 常被滥用，成本翻倍 |
| **低代码 / 可视化** | 连界面一起包了 | 快速验证、给非开发者用 | 难做评测与版本管理 |

:::warn 最常见的选型错误
需求明明是「查订单状态」这种固定流程，却因为「想做 Agent」上了多角色协作框架。结果是四个角色互相转交、延迟翻三倍、日志看不懂、评测没法写。**先按[什么是 Agent](./04-what-is-agent.md)那张表判断该不该用 Agent，再选框架。**
:::

## 三、工具协议：解决什么，不解决什么

项目做大了会遇到一个很实际的问题：你写了 20 个工具，另一个团队也写了 20 个，第三个团队想复用，得把你的代码复制过去、改路径、改鉴权、改返回格式…… 于是大家开始约定一套**统一的「工具怎么描述、怎么被发现、怎么被调用」的规范**。

这类规范（业内常叫工具协议）的价值只有一句话：

:::quote
**把「工具怎么接」从「每个项目各写一遍」变成「按同一份契约接一次」。** 它解决的是互通，不是智能。
:::

一条完整的协议调用长这样：

:::figure 一次协议化工具调用
@flow
发现能力|读取参数说明|发起调用|拿到结果|结果裁剪入上下文
:::

必须清醒地知道它**不解决**什么，否则会踩大坑：

| 协议解决了 | 协议**没**解决（仍要你自己做） |
|---|---|
| 工具怎么描述与发现 | 参数校验是否够严 |
| 调用格式统一 | 权限分级与二次确认 |
| 跨项目复用 | 幂等与重复执行 |
| 传输与会话 | 返回结果会不会撑爆上下文 |
| — | 工具太多时怎么分组路由 |
| — | 危险动作谁能批准 |

也就是说，[工具调用](./06-tool-calling.md)里那七格链路，协议只覆盖了最外面的一两格。**接了协议不等于有了安全边界**——这是最容易产生的错觉。

四个接入坑：

1. **把远端返回原样塞进上下文** → 用第 07 篇的裁剪；
2. **信了远端的参数说明，没做本地二次校验** → 任何外部说明都要过自己的 Schema；
3. **没设超时和熔断** → 远端卡住会拖死整个循环，必须给单次调用独立超时；
4. **把远端能力全部暴露给模型** → 还是要路由分组，别一口气给 40 个。

:::ask 想一步
如果远端工具声称「这个动作是只读的」，你的系统会完全相信吗？正确答案是不信——**权限级别由你本地的注册信息决定，不由远端声明决定**。否则一个标错级别的远端删除接口，就能被 viewer 角色调到。
:::

## 四、什么时候框架在帮倒忙

把判断条件写成一张可以直接照着查的表：

| 信号 | 建议 | 理由 |
|---|---|---|
| 流程完全确定 | 不用框架，普通函数即可 | 框架只增加间接层 |
| 需要逐条审计每一步 | 用手写循环 / 显式状态 | 框架的隐式行为难解释 |
| 团队要长期维护、多人协作 | 用成熟编排框架 | 检查点、可观测、社区经验值钱 |
| 需要崩溃恢复 | 用带持久化的框架，或自己落盘 | 自己写容易漏并发与幂等 |
| 只是想快速验证一个想法 | 随便，能跑就行 | 别在选型上耗时间 |
| 已经用了框架但说不清「怎么停」 | **先停下来补这一课** | 上线必出事 |

:::quote
**框架的价值在「接管你不擅长、也不想重复造的东西」；代价是「你看不见它做了什么」。** 手写过一遍，你就知道哪些可以放心交出去、哪些必须攥在自己手里。
:::

## 五、解耦：让业务代码不认识框架

不管最后选了什么，都建议加一层薄薄的适配层。它的作用是把框架的状态翻译成你自己定义的 `State`，这样换框架时业务代码一行不动。

```python
# adapter.py —— 零依赖示意，python adapter.py
import json

# 你自己的、和任何框架无关的业务状态
class BizState:
    def __init__(self, goal):
        self.goal = goal
        self.rounds = 0
        self.trace = []
        self.done = False

    def observe(self, action, result):
        self.trace.append({"round": self.rounds, "action": action,
                           "result": result})
        self.rounds += 1

    def to_dict(self):
        return {"goal": self.goal, "rounds": self.rounds,
                "done": self.done, "trace": self.trace}

# 适配层：把「外部框架给的东西」翻译成 BizState
class FrameworkAdapter:
    def __init__(self):
        self.biz = None

    def start(self, goal):
        self.biz = BizState(goal)

    def on_step(self, framework_event):
        """只认一种自定义事件结构，框架怎么变都不影响业务。"""
        self.biz.observe(framework_event["action"],
                         framework_event.get("result", {}))
        if framework_event.get("type") == "finish":
            self.biz.done = True

    def export(self):
        return self.biz.to_dict()

# 模拟两种「框架」的事件格式，业务侧完全无感
FRAMEWORK_A = [
    {"type": "node", "action": "search", "result": {"ok": True}},
    {"type": "node", "action": "rerank", "result": {"ok": True}},
    {"type": "finish", "action": "finish", "result": {"answer": "完成"}},
]
FRAMEWORK_B = [
    {"type": "node", "action": "search", "result": {"ok": True}},
    {"type": "node", "action": "verify", "result": {"ok": True}},
    {"type": "finish", "action": "finish", "result": {"answer": "完成"}},
]

if __name__ == "__main__":
    for name, events in [("框架 A", FRAMEWORK_A), ("框架 B", FRAMEWORK_B)]:
        ad = FrameworkAdapter()
        ad.start("核对制度版本")
        for e in events:
            ad.on_step(e)
        d = ad.export()
        print("%s -> %d 轮 / 轨迹 %s / done=%s" %
              (name, d["rounds"], [t["action"] for t in d["trace"]], d["done"]))
```

两种框架事件喂进来，`BizState` 的形状完全一致。**这一层就是你的护城河**：评测、审计、回放、简历里的架构图，全部建立在自己的状态定义上，不随框架版本漂移。

:::tip 面试里怎么讲这件事
「我们在框架和业务之间加了一层状态适配，业务只依赖自定义的 State 与 trace 结构；所以换编排框架、加评测、做回放都不用改业务代码。」——这句话同时体现了分层、可测性、和迁移经验。
:::

## 六、一份选型自检表

- [ ] 先判断过「这个场景到底该不该用 Agent」
- [ ] 能说清框架接管的六件事分别是什么
- [ ] 找到并验证过「循环怎么停」
- [ ] 轨迹能导出成自己的格式，不锁死在框架里
- [ ] 业务代码不 import 框架的类型
- [ ] 协议接入仍保留本地参数校验、权限、幂等、裁剪、超时
- [ ] 有一份评测集，能证明换框架后没变差（[评测](./11-eval.md)）

:::check 学完这一篇，你要能回答
- 框架接管的六件事，分别对应手写循环里的哪个部件？
- 工具协议解决了什么？至少说三件它**没**解决的事。
- 远端工具声称「只读」，你的系统该不该信？为什么？
- 什么情况下框架是在帮倒忙？举两个信号。
- 适配层解决了什么问题？为什么它是护城河？
:::

## 小结

:::figure 这一篇的产物
@stack
一张对照表::框架六大件 ↔ 手写循环部件
一条界线::协议管互通，不管安全与预算
一张判断表::什么时候用、什么时候别用
一层适配::业务只认自己的 State，换框架零改动

到这里，系统已经「能跑、能接真实数据、能换框架」了。剩下的三篇解决同一件事：**怎么证明它靠谱，以及怎么敢让它上线**。

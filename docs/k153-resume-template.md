# 简历四行模板、STAR(L) 与讲清失败案例

## 场景提问

你做了一个自己挺满意的 Agent 项目，写进简历时恨不得把用过的东西全列上：拆了任务、加了并行、做了部署、还处理过一次事故，密密麻麻七八行。可投出去没什么回音；好不容易进了面试，对方顺着第三行问「这个提升是怎么算出来的、分母是什么」，你支吾两句；再问「为什么不用更简单的那套」，你说「当时没多想」；最后问「讲一次搞砸的」，你只答得出「那次下游有点慢，后来修好了」。走出门你才发现，项目明明是自己一行行做下来的，怎么一被追问就像没做过？问题到底出在写得不够多，还是别的什么地方？

## 破误解

**不是「写得不够多、技术栈不够亮」，是四行里每一行都没认领自己该回答的那一问：谁在用、你做了什么判断、结果凭什么可信、踩过的坑后来怎么挡住；而面试官真正想验的，恰恰是最后那两行经不经得起追问。**

先把两套说法拆清楚，它们其实是同一件事的两面。简历四行模板是「落笔格式」：一个项目只占四行，第一行交代场景与约束，第二行写你做的判断与取舍，第三行给能核对的结果，第四行写复盘、边界与学到的东西。STAR(L) 是「口述骨架」：S 是 Situation（情境），T 是 Task（任务），A 是 Action（动作），R 是 Result（结果），末尾多出来的 L 是 Learning（学到的东西，也就是复盘）。把两者对上就明白了——第一行装 S 和 T，第二行装 A，第三行装 R，第四行装 L。四行不是把 STAR(L) 压缩成四句话，而是让五个要素各自有一处固定落点，写的时候不漏、讲的时候不乱。很多人只写到 R 就停了，简历看起来全是「做成了什么」，一问「那次失败呢」就断线；补上 L，才是把一次经历讲成闭环。

这里有个很实在的判断缺口：面试官不是在验收功能清单，而是在判断「这些事是不是你真的做过、并且下次还能兜住」。列工具名谁都会列，能答出「为什么这么选而不是那么选」的才是做过取舍的人，见 [取舍怎么讲清](./k123-tradeoffs.md)。数字也一样，「效果明显提升」不携带信息，「从多少到多少、分母是什么、从哪条记录取的、统计了哪段时间」才携带信息；数字若查无出处，被追问一句就会把整段经历的可信度一起带塌，见 [数字与事实的完整性](./k124-number-integrity.md)。还有一层容易被忽略：岗位描述，也就是 JD（Job Description，招聘方写明职责与要求的那段文字），决定了该挑哪个项目、把哪处取舍放在第二行，见 [JD 怎么拆](./k121-jd-analysis.md) 与 [三个项目怎么选](./k122-three-projects.md)。四行模板的价值，正在于它逼你提前把这四处想明白，而不是到了面试现场临时组织语言。至于怎么把整段经历讲成一段能接住追问的叙述，是 [项目怎么讲](./k126-project-pitch.md) 要展开的；这篇只盯死一件事：四行各写什么，以及失败案例怎么讲到「讲清」为止。

## 生活类比

把它想成一张设备维修工单。老师傅交上来的单子永远是四段，一段都不多。第一段写「哪台设备、什么时候、给谁用、什么现象」，比如「三号包装线夜班，卡料报警，一小时停了四次」——这是场景与约束。第二段写「查了什么、换了什么、为什么判断是这儿」，他会写「先断开了上游供料再单独试传送，判断是传感器积灰，而不是整条线提速不够」——这是动作与取舍。第三段写「换完之后测了什么、读数是多少、怎么测的」，比如「连续跑两小时，同样工况下报警从四次降到零次」——这是结果，连口径一起给。第四段写「为什么会积灰、后来加了什么检查让它不再犯、什么工况下这套不适用」——这是复盘。

对应关系可以逐条对上。「四段工单」就是四行模板：第一段装情境与任务，第二段装动作，第三段装结果，第四段装学到的东西。「先断开上游再单独试」这句话最值钱，它不是罗列用过的扳手，而是交代「怎么把范围一点点缩到某处」，也就是面试官想听的判断过程。「同样工况下从四次降到零次」之所以可信，是因为给了分母（两小时、同一工况）和读数来源（现场记录），而不是一句「好多了」；换成项目表达，就是 [按成功任务核算成本](./k096-metrics-cost.md) 里强调的「分子分母都要记全」。第四段里的「加了每班吹扫一次」，才是老师傅和新人的分水岭：新人写「以后注意」，老师傅写「加了一道动作，下次不靠人记得」。

这个比喻还点出两处最容易翻车的地方。一是最怕工单上写「已修复」三个字、却没有任何读数——面试官就像来验收的甲方，看不到读数，只能当你没测过。二是讲故障不等于认错：甲方并不因为设备坏过就否定师傅，反而会因为「他能说清怎么定位、怎么让它不再犯」而放心把下一台交给他。放到面试里也一样，被问「讲一次搞砸的」时，真正被评估的是你能不能把一次失败变成可复用的防复发动作，见 [生产失败模式清单](./k150-failure-modes.md) 与 [坏例子回收闭环](./k093-badcase-loop.md)。而那张工单上每一段，甲方都可能沿一句往下追：「四次是怎么数的」「为什么先断上游」「换个工况还成立吗」——这就该提前预演，见 [追问链怎么接](./k125-followup-chain.md)。

## 自绘示意图

:::figure 从读岗位到能接住追问的顺序
@flow
读岗位要求|选一个项目|按四行落笔|补失败案例|预演追问链
:::

五格里有两格常被整个跳过。「读岗位要求」决定第二行该放哪处取舍，不读就写，等于把同一段话说给所有岗位听。「预演追问链」决定第三行的数字和第四行的复盘能不能被追到底；很多人四行写完就交，从没自己扮演过一次追问的人。中间三格是落笔本身：选项目、写四行、把失败案例单独补成能讲的四步。顺序上补失败案例放在四行之后，是因为它要给第四行供料，而不是另起一段自说自话。

:::figure 简历四行各认领哪一问
@stack
第一行 场景::交代背景与约束，一句话说清给谁用、难在哪
第二行 动作::写自己做的判断与取舍，不罗列用过的东西
第三行 结果::给能核对的数字，连同分母、来源、时间窗
第四行 复盘::写踩过的坑、后来怎么改、什么时候不适用
:::

四行可以当成四道必答题：谁在用、你凭什么这么选、结果凭什么可信、下次怎么不重犯。最容易写废的是第二行和第四行。第二行一旦滑成「用了某某、加了某某」，就退回了功能清单，读的人看不出任何判断；第四行一旦滑成「整个过程按计划完成」，L 就丢了，STAR(L) 只剩 STAR。第三行则最容易「有数字、没口径」：数字孤零零摆着，分母、来源、时间窗一样没给，被追问时无从答起。

:::figure 两种写法的差别
@compare
只讲做成了什么::像功能清单|数字查无出处|一被追问就断线
四行加失败案例::取舍说得清|数字可复核|坑能讲成闭环
:::

左边不是「写得少」，是把所有篇幅都押在了 R 上，S、T、A 一笔带过，L 直接缺席；顺风顺水时看着挺满，一旦对方沿任一句往下追就没有落脚处。右边并没有多写多少字，只是把四行各自要回答的那一问答上，并额外备好一段能讲清的失败。二者的差距，全在「被追问时还站不站得住」。

## 层层追问

:::ask 那如果项目没那么亮眼、数字也不好看，是不是就只能含糊过去？
:::

不必，也不该。要先把「结果」这一行从「比别人强多少」里解放出来：它回答的是「改动前后，哪件可观察的事变了」，而不是「成绩漂不漂亮」。可以是从慢到快，可以是从「失败了看不出来」到「失败能被逐条认出」，可以是从「只在本地跑得通」到「重启之后还能接着跑」，见 [服务化封装与部署](./k151-service-wrap.md) 与 [轨迹评测](./k089-trajectory-eval.md)。哪怕数值平平，只要分母、来源、时间窗齐全，这段话依然可信；反过来，一个很漂亮却查无出处的数字，是唯一真正不能碰的东西——它不只是「可能不准」，而是会让面试官把前面三行一并重新怀疑。口径怎么说清、为什么不按单次调用算账，见 [按成功任务核算成本](./k096-metrics-cost.md)；改动前那套固定参照怎么建立，见 [评测数据集](./k086-eval-dataset.md) 与 [性质断言](./k088-property-assertion.md)。

再往下一层：不好看的数字往往还藏着一段更值得讲的话——「什么时候不该用这套做法」。能主动说出边界的人，比只会报提升的人更像真的用过。比如扇出并行在子任务互相依赖时就不该硬套，见 [扇出并行与 workers 上限](./k152-fanout.md)；离线跑通和真实流量里的表现之间本来就有一段差距，如实讲清它，比含糊带过更稳，见 [离线与线上的落差](./k092-offline-online-gap.md)。还有个常被忽略的细节：同一组数字换个统计窗口就会变，所以「统计了哪段时间」必须和分母一起写出来；评测口径若可被随意挑，结论就不可复核，见 [用例配比](./k087-case-mix.md) 与 [评分与裁判](./k090-llm-judge.md)。一句话：数字小不丢人，查无出处才丢人；含糊不是保护，是把整段经历的可信度押在「对方别追问」上。

:::ask 那失败案例讲到什么程度算「讲清」，会不会越讲越像在暴露短板？
:::

有个很好用的四步尺子：现象、定位、修复、复盘。现象要可观察、最好带得数，比如「十二份里少了一份，总结果却照样输出」；定位要交代「怎么把范围缩到某处、凭什么认定是这儿」，比如「沿轨迹发现第三路超时未返回，归约只按完成顺序拼接、没查缺」，见 [轨迹该记什么](./k094-trace-fields.md) 与 [结构化日志与轨迹回放](./k095-structured-log.md)；修复要说清改了什么、以及为什么这样改就够；复盘要落到「后来加了哪道闸，让它下次被自动挡住」，比如补一条回归断言或把阈值写进可查的配置，见 [回归门禁与基线](./k091-regression-gate.md) 与 [提示与策略版本化](./k113-prompt-versioning.md)。这四步恰好就是 STAR(L) 里那个 L 的内容，所以「讲清失败」不是四行之外的附加题，它就是第四行的原料。

再追一层，面试官真正在看的不是「你有没有失败过」——谁都有——而是「你能不能把一次失败变成可复用的防复发动作」。两种讲法分野很清楚：「下游有点慢，都怪它，后来修好了」是甩锅加一句空话，听完仍不知道你做了什么；「现象是什么、我怎么把范围缩到第三路、改成按原编号收齐、再补一条断言让缺一路就整体判不完整」是闭环，见 [生产失败模式清单](./k150-failure-modes.md) 与 [坏例子回收闭环](./k093-badcase-loop.md)。所以讲失败不是认错，是展示定位能力；真正暴露短板的是停在「已修复」却讲不出证据和防复发动作。还要提前把追问链接上：这个数怎么数的、为什么不用另一套、换个场景还成立吗，见 [追问链怎么接](./k125-followup-chain.md) 与 [取舍怎么讲清](./k123-tradeoffs.md)。把这些接得住，四行就从「写过了」变成「讲得清」；怎么把整段串成开场那几十秒，见 [项目怎么讲](./k126-project-pitch.md)。

## 可运行代码与逐行解释

下面这段只用 Python 内置功能，做一个「简历四行校验器」：把四行文本、STAR(L) 五要素、失败案例四步、以及一张「数字出处表」放进同一个结构里，逐条检查四行是否各司其职、L 有没有缺席、失败案例有没有甩锅或停在已修复、第三行里每个数字是否都能在出处表里查到分母与来源。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
import re
from dataclasses import dataclass, field


@dataclass
class Case:
    """一条项目经历：四行文本、五要素、失败四步、数字出处表。"""
    name: str
    lines: list
    starl: dict
    failure: dict
    evidence: dict = field(default_factory=dict)


REVIEW_WORDS = ("复盘", "学到", "后来", "改", "下次", "不再")
BLAME_WORDS = ("都怪", "运气", "别人的错", "没办法", "不关我")
LINE_TO_STARL = {1: ("S", "T"), 2: ("A",), 3: ("R",), 4: ("L",)}
FAILURE_STEPS = ("现象", "定位", "修复", "复盘")


def has_number(text):
    """文本里是否出现了阿拉伯数字。"""
    return re.search(r"\d", text) is not None


def numbers_in(text):
    """用正则取出文本里的所有整数，供逐一对账。"""
    return [int(x) for x in re.findall(r"\d+", text)]


def check_four_lines(case):
    """四行齐全、第三行有可核对数字、第四行是复盘而非复述。"""
    if len(case.lines) != 4:
        return False
    if any(not s.strip() for s in case.lines):
        return False
    if not has_number(case.lines[2]):
        return False
    if not any(w in case.lines[3] for w in REVIEW_WORDS):
        return False
    if case.lines[3] == case.lines[1]:
        return False
    return True


def check_starl(case):
    """STAR(L) 五要素都要有内容，且 L 不能是空话。"""
    if not all(k in case.starl for k in ("S", "T", "A", "R", "L")):
        return False
    if any(not str(case.starl[k]).strip() for k in ("S", "T", "A", "R", "L")):
        return False
    return any(w in case.starl["L"] for w in REVIEW_WORDS)


def check_failure(case):
    """失败四步齐全、不甩锅、且带着可观察的数字。"""
    if not all(k in case.failure for k in FAILURE_STEPS):
        return False
    if any(not str(case.failure[k]).strip() for k in FAILURE_STEPS):
        return False
    joined = "".join(str(v) for v in case.failure.values())
    if any(w in joined for w in BLAME_WORDS):
        return False
    return has_number(joined)


def check_numbers(case):
    """第三行里每个数字，都要在出处表里查得到分母与来源。"""
    for n in numbers_in(case.lines[2]):
        entry = case.evidence.get(str(n))
        if entry is None:
            return False
        if "分母" not in entry or "来源" not in entry:
            return False
    return True


def good_case():
    return Case(
        name="合格样例",
        lines=[
            "给内部同事用的材料整理服务，受单次四路并行的约束",
            "把顺序处理改成按上限扇出，而不是开更多路一起跑",
            "失败定位耗时从 20 降到 6（分母：同一组固定用例，单位：分钟）",
            "复盘发现缺一路曾被静默吞掉，后来加了按编号归约，少于三份时不再套",
        ],
        starl={
            "S": "内部材料整理，十二份一起处理太慢",
            "T": "在不打满下游的前提下缩短等待",
            "A": "按上限扇出，归约时按原编号查缺",
            "R": "定位耗时从 20 降到 6",
            "L": "学到要先查缺再报完整，后来补了按编号归约",
        },
        failure={
            "现象": "有一轮 12 份里少了 1 份，总结果却照样输出",
            "定位": "沿轨迹发现第 3 路超时未返回，归约只按完成顺序拼接",
            "修复": "改成按原编号收齐，缺路与失败各自显式列出",
            "复盘": "补了 1 条回归断言，之后缺一路就整体判不完整",
        },
        evidence={
            "20": {"分母": "同一组固定用例", "来源": "改动前轨迹记录"},
            "6": {"分母": "同一组固定用例", "来源": "改动后轨迹记录"},
        },
    )


def main():
    checks = []
    good = good_case()
    checks.append(("四行与 STAR(L) 的对应关系固定",
                   LINE_TO_STARL == {1: ("S", "T"), 2: ("A",),
                                     3: ("R",), 4: ("L",)}))
    checks.append(("合格样例四行过关", check_four_lines(good)))
    checks.append(("合格样例五要素过关", check_starl(good)))
    checks.append(("合格样例失败案例过关", check_failure(good)))
    checks.append(("合格样例数字全部有出处", check_numbers(good)))

    only_star = good_case()
    del only_star.starl["L"]
    checks.append(("缺 L 被认出来", not check_starl(only_star)))
    checks.append(("缺 L 不影响四行判定", check_four_lines(only_star)))

    flat_review = good_case()
    flat_review.lines[3] = "整个过程按计划执行完毕"
    checks.append(("第四行写成复述被认出来", not check_four_lines(flat_review)))

    no_number = good_case()
    no_number.lines[2] = "效果有明显提升，同事反馈不错"
    checks.append(("第三行没有数字被认出来", not check_four_lines(no_number)))

    unsourced = good_case()
    del unsourced.evidence["6"]
    checks.append(("数字查无出处被认出来", not check_numbers(unsourced)))
    checks.append(("查无出处不影响四行判定", check_four_lines(unsourced)))

    shaky = good_case()
    shaky.evidence["6"] = {"来源": "改动后轨迹记录"}
    checks.append(("有来源却缺分母也被认出来", not check_numbers(shaky)))

    blame = good_case()
    blame.failure["定位"] = "都怪下游太慢，运气不好，没办法"
    checks.append(("甩锅的失败案例被认出来", not check_failure(blame)))

    stopped = good_case()
    del stopped.failure["复盘"]
    checks.append(("停在已修复、缺复盘被认出来", not check_failure(stopped)))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Case` 用 `dataclass`（数据类，标准库里用来少写样板代码的工具）把一条经历的四种材料收在一处：`lines` 是四行文本，`starl` 是五要素，`failure` 是失败四步，`evidence` 是数字出处表。`field(default_factory=dict)` 保证每条样例拿到的是自己独立的一张表，改动一张不会串到另一张。
2. `REVIEW_WORDS` 与 `BLAME_WORDS` 是两个可判定的词表：前者判第四行是不是真的在复盘，后者判失败案例有没有把原因推给外部。`LINE_TO_STARL` 把「四行」和「五要素」的对应关系写成常量——第一行装 S、T，第二行装 A，第三行装 R，第四行装 L，这张表正是「两套说法其实是同一件事」的落地。
3. `has_number` 与 `numbers_in` 用正则（regular expression，按模式从文本里找出片段的规则）：前者只判有没有数字，后者把第三行里的整数全取出来，交给 `check_numbers` 逐一对账。取的是 `\d+` 这样的整数片段，所以「20」「6」会被拿到，而「同一组固定用例」这种中文表述不会干扰对账。
4. `check_four_lines` 依次卡四道：恰好四行、每行非空、第三行带可核对的数字、第四行含复盘词且不等于第二行。最后一条专门防「把动作抄一遍当复盘」——L 必须是新内容，不是 A 的复述。
5. `check_starl` 要求 S、T、A、R、L 五个键都在且都不为空，并额外要求 L 里出现复盘词。只写「已完成」「已修复」不算 L，因为它没有任何「后来怎么改」的信息；这正是 STAR 与 STAR(L) 的差别所在。
6. `check_failure` 把「讲清」拆成四条可判定的性质：现象、定位、修复、复盘四步齐全；四步都不空；拼起来的文本里没有甩锅词；并且带着可观察的数字。数字这一条对应追问里那句「现象要可观察、最好带得数」——没有数，往往说明当时根本没留下记录，见 [轨迹该记什么](./k094-trace-fields.md)。
7. `check_numbers` 是最硬的一道：第三行出现的每个整数，都要能在 `evidence` 里查到条目，且条目必须同时有「分母」和「来源」。少任一样就判不合格。它把「不编造数字」从一句劝告变成了一个可执行的检查——数字小没关系，查无出处不行，见 [数字与事实的完整性](./k124-number-integrity.md)。
8. `good_case` 是一组完全确定的构造数据：四行、五要素、失败四步、两个数字各带分母与来源。`main` 先断言这组样例四项全过，再造出七组「只坏一处」的样例——删掉 L、第四行写成复述、第三行去掉数字、删掉一个出处、出处缺分母、失败案例甩锅、失败案例缺复盘——逐条断言校验器能准确认出坏在哪，同时用「缺 L 不影响四行判定」这类断言确认各项检查彼此独立、不会一坏全坏。结尾统一统计通过项数，任何一条性质被破坏都以非零状态退出。

如实说明一句：这里的四行文本、五要素、失败四步和所有数字，都是为讲清校验规则构造的教学例子，不是任何真实简历、真实成绩或真实项目的采样；词表也只是把「有没有复盘、有没有甩锅」这类要求做成可判定的近似，不能替代人对内容的判断。它演示的是四行各司其职、L 不能缺席、失败四步要闭环、数字要有出处这四件事怎么被逐条检查，不是任何简历筛选工具的实现，也不据此推断真实面试中的评价结果。

## 踩坑与边界

- **四行写成功能清单**：现象是第二行列了一串用过的东西，被问「你做的判断是什么」答不上 → 原因是把「列工具」当成了「写动作」 → 第二行只写一处关键取舍，并带上「为什么这么选而不是那么选」，见 [取舍怎么讲清](./k123-tradeoffs.md)。
- **第三行只有数字没有口径**：现象是写了个挺好看的百分比，一被追问分母和时间窗就含糊 → 原因是数字没有分母、来源、统计窗口，等于查无出处 → 一个指标连同分母与来源一起写，必要时补上统计了哪段时间，见 [数字与事实的完整性](./k124-number-integrity.md) 与 [按成功任务核算成本](./k096-metrics-cost.md)。
- **第四行复述动作、L 缺席**：现象是整段只讲做成了什么，被问「讲一次搞砸的」直接断线 → 原因是写到 R 就收尾，把复盘当成了可有可无的补充 → 第四行固定写踩过的坑、后来怎么改、什么时候不适用，让 STAR(L) 的 L 有落点。
- **失败案例甩锅或停在已修复**：现象是「都怪下游慢，后来修好了」，听完仍不知道你做了什么 → 原因是没有定位过程和防复发动作 → 按现象、定位、修复、复盘四步讲，定位给证据、复盘给那道后来加上的闸，见 [生产失败模式清单](./k150-failure-modes.md) 与 [回归门禁与基线](./k091-regression-gate.md)。
- **不预演追问链**：现象是四行都写了，被连追三句「怎么算的」「为什么不用另一套」「换场景还成立吗」就卡住 → 原因是只准备了陈述、没准备被追问 → 按每个数字、每处取舍、每条边界各预演一问，见 [追问链怎么接](./k125-followup-chain.md) 与 [JD 怎么拆](./k121-jd-analysis.md)。

还要分清两组容易混说的事。一组是「四行模板」与「STAR(L)」：前者是落笔格式，后者是口述骨架，不是两套要分别背的东西——四行就是五个要素的固定落点，见 [项目怎么讲](./k126-project-pitch.md)。另一组是「讲失败」与「认错」：前者展示的是怎么把范围缩到某处、怎么让它下次被自动挡住，后者只是一句态度；被评估的从来不是有没有失败过，而是能不能形成闭环，见 [坏例子回收闭环](./k093-badcase-loop.md) 与 [提示与策略版本化](./k113-prompt-versioning.md)。也别把「结果」窄化成「比别人强多少」：从看不见失败到能逐条认出、从重启即失忆到能接着跑，同样是可核对的变化，见 [轨迹评测](./k089-trajectory-eval.md) 与 [服务化封装与部署](./k151-service-wrap.md)；离线跑通与真实流量之间有落差，如实讲清反而更稳，见 [离线与线上的落差](./k092-offline-online-gap.md)。挑哪个项目、把哪处取舍放在第二行，仍要回到 [三个项目怎么选](./k122-three-projects.md) 与 [扇出并行与 workers 上限](./k152-fanout.md) 里那些真实做过的判断上去。

## 三句话小结

简历四行模板、STAR(L) 与讲清失败案例，是把一个项目压成场景、动作、可核对的结果、复盘四行，让口述五要素各有落点，并把一次失败讲成现象、定位、修复、复盘都能接住追问的闭环。

关键做法是第二行只写判断与取舍、第三行连分母与来源一起给、第四行补上 L 和防复发动作，再对每个数字和每处「为什么不用另一套」预演一遍追问。

当只是在内部同步进度、或对方明确要的是完整设计文档而非一段简短经历时，不必硬套四行；但只要是要被人顺着一句句追问的场合，这四行和那段能讲清的失败就不该缺席。

# 幂等落盘：让同一请求重放也不重复扣款

## 场景提问

你写的下单助手帮用户提交一笔订单，界面转了两圈没反应，用户又点了一次；或者网络抖了一下，客户端自动重试了一次。等你去查账，发现同一个用户、同一件商品，被扣了两次款、生成了两笔订单。用户来问「我明明只买了一件，怎么付了两回」，你翻日志看到两次请求长得一模一样，参数、金额、时间几乎都相同，却都在数据库里留下了真实记录。更麻烦的是，这类问题平时手动测根本测不出来，只有在超时、重启、重试凑到一起的时候才冒出来。

## 破误解

**不是重试机制写坏了，是那个动作本身没有「记忆」——它分不清这次是不是做过了。**

很多人的第一反应是去堵重试：把重试次数调小、把超时调短、在上游加个「请勿重复点击」。这些都只是让重复来得少一点，堵不住根。真正的问题是：一个会改动外部世界的动作，比如扣款、发短信、写一条订单记录，如果它每次被调用都老老实实再干一遍，那么只要有任何一个环节让同一个请求到达两次，它就必然干两遍。重试、超时、进程重启、消息队列重投、用户手抖，这些都会制造「同一个意图到达两次」，而且它们无法被彻底消灭。所以该改的不是这些来源，而是让动作自己具备一种性质：做一次和做很多次，对外部世界的效果完全相同。这个性质叫幂等（idempotent，指一个操作重复执行多次，与只执行一次产生的结果一致）。要做到它，光靠内存里一个变量不行，得把「做过没有」和「当时的结果」写到断电也丢不掉的地方，也就是落盘持久化。

## 生活类比

把它想成一家老式铺子的收据存根。收银员每做成一笔生意，都开一张带唯一编号的收据，并把存根按编号钉在本子上。顾客拿着编号 `A-001` 的收据回来说「我这张是不是还没结账，再帮我结一次」，收银员不会立刻再收一遍钱，而是先翻存根本：如果 `A-001` 已经钉在里面，就把当时那张收据的复印件递给顾客，说「这笔早就结过了，结果是这样」，绝不再点一次钞票；只有翻遍本子确认没有这个编号，才真正收钱、开新收据、钉新存根。

这里的对应关系很具体：收据编号就是幂等键（idempotency key，给每个业务意图分配的稳定标识，同一个意图永远用同一个键）；那个钉存根的本子就是持久化的状态文件；递出去的复印件就是缓存下来的首次结果；「再收一次钱」就是副作用（side effect，对外部系统造成的真实改动，钱少了、短信发了、库里多了一行）。整个机制的关键动作只有一个：**先查存根，再决定要不要动手**。而且存根本必须是纸质的、放在店里的，不能只记在收银员脑子里——因为收银员会换班、会走神，相当于程序会重启、内存会清空。只记在脑子里的去重，一换班就全忘了。

## 自绘示意图

:::figure 一次幂等动作的处理顺序
@flow
收到请求|计算幂等键|查状态文件|命中返回旧结果|未命中执行并落盘
:::

这张图里最容易看漏的是最后两格的先后顺序：不是「执行完再顺手记一笔」，而是「查完确认没做过，才执行，并且把执行结果和这条记录一次性写进同一个文件」。先查、后做、同一次写入，这三件事凑齐，才挡得住重放。

:::figure 两种动作面对重放的差别
@compare
无记忆动作::每次都真扣款|重启后认不出|结果可能不一致
幂等落盘::命中即返回旧结果|重启仍能识别|结果完全可复现
:::

左边那一行是默认写法：动作被调用就干，重复调用就重复干，一旦进程重启连「刚才干过」这件事都丢了。右边那一行是我们想要的：重放时拿到的不是一份新结果，而是首次那份结果的原样拷贝，连结果本身都稳定可复现。

## 层层追问

:::ask 那如果动作刚执行完、还没来得及写状态就崩了呢？
:::

这是最尖锐的一问，也是这套机制的软肋所在。如果「扣款」和「写状态」是分开的两步，中间恰好断电，就会出现钱扣了、存根没钉上的窗口：下次重放查不到记录，于是又扣一次。要收紧这个窗口，思路是让「动作」和「它的记录」尽量成为一次不可分割的写入。放到本地文件这个尺度，做法是先把完整的新状态写到临时文件，再用一次原子替换（把临时文件整体改名覆盖正式文件，操作系统保证这次改名要么全成、要么全不成），避免出现写了一半的残破状态。放到真实的下游系统，更可靠的做法是让下游自己也认这个幂等键，由它在扣款那一步就完成去重——也就是两边对同一把钥匙达成共识。这一点和 [重试、指数退避与抖动](./k108-retry-backoff.md) 里「超时不等于没执行」是同一个道理：你没收到回执，不代表对方没做。

:::ask 那如果两个一模一样的请求同时到达、都查到「没做过」呢？
:::

查和写之间如果有空隙，两个并发请求就可能双双判定「未命中」，然后各执行一次。单进程里可以用一把互斥锁把「查—做—写」整段包起来；跨进程、跨机器时，就得依赖支持原子写入或唯一约束的存储，让「插入这条幂等键」这件事本身具备排他性——谁先插进去谁执行，后到的那个插入失败，就转为读取既有结果。换句话说，去重的判定权最终要落到一个大家共用的、能串行化的地方，而不是各进程自己内存里的一份拷贝。

还有一个更细的追问：同一个幂等键，第二次却带了不同金额，该怎么办？正确做法是明确报错，而不是闷头返回首次结果。因为「键相同、参数变了」通常意味着调用方逻辑有 bug，或者是有人拿旧编号办新业务，静默放行会把错误藏得更深。判定时要比对的不仅是「键在不在」，还要看「这次的参数和历史是否一致」。这些边界，在 [优雅中断与断点恢复](./k110-graceful-resume.md) 里会以另一种形式再出现一次。

## 可运行代码与逐行解释

下面这段程序只用 Python 标准库，把状态写进一个本地临时文件，完整演示「查存根—决定做不做—把参数与结果一起落盘」，并在结尾用一组断言把每条性质都验一遍。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path


class Ledger:
    """带幂等落盘的账本：每个动作先查状态文件，命中就直接返回旧结果。"""

    def __init__(self, state_path, initial_balance=100):
        self.state_path = Path(state_path)
        if not self.state_path.exists():
            self._write({"balance": initial_balance, "records": {}})
        self.side_effect_count = 0

    def _read(self):
        return json.loads(self.state_path.read_text(encoding="utf-8"))

    def _write(self, state):
        self.state_path.write_text(
            json.dumps(state, ensure_ascii=False, sort_keys=True), encoding="utf-8"
        )

    def transfer(self, idempotency_key, amount):
        state = self._read()
        records = state["records"]
        if idempotency_key in records:  # 命中：动作已做过，绝不重复
            return dict(records[idempotency_key]), False
        # 未命中：真正执行副作用，并把「参数+结果」一次性落盘
        state["balance"] -= amount
        record = {
            "key": idempotency_key,
            "amount": amount,
            "balance_after": state["balance"],
            "result_id": "r-" + str(len(records) + 1),
        }
        records[idempotency_key] = record
        self._write(state)
        self.side_effect_count += 1
        return dict(record), True


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "ledger.json"
        ledger = Ledger(path, initial_balance=100)

        r1, did1 = ledger.transfer("order-A", 30)
        r2, did2 = ledger.transfer("order-A", 30)  # 网络重试：同一幂等键再来一次
        r3, did3 = ledger.transfer("order-B", 20)  # 不同键，正常执行

        checks = [
            ("首次执行产生副作用", did1 is True),
            ("重放不再产生副作用", did2 is False),
            ("重放返回与首次完全相同的结果", r1 == r2),
            ("不同键正常执行", did3 is True),
            ("余额只被扣了两次", ledger._read()["balance"] == 50),
            ("真实副作用次数为 2", ledger.side_effect_count == 2),
            ("状态文件里只有两条记录", len(ledger._read()["records"]) == 2),
        ]

        # 重新开一个实例读同一个状态文件，模拟进程重启后重放
        fresh = Ledger(path, initial_balance=100)
        r4, did4 = fresh.transfer("order-A", 30)
        checks.append(("进程重启后重放仍不重复", did4 is False))
        checks.append(("进程重启后返回原结果", r4["result_id"] == r1["result_id"]))

        passed = sum(1 for _, ok in checks if ok)
        for name, ok in checks:
            print(("通过 " if ok else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Ledger.__init__` 只在状态文件不存在时初始化一份余额与空记录表，已有文件绝不覆盖——这一句保证了「进程重启后还能读到历史」，是持久化和内存变量的根本区别。
2. `_read` / `_write` 用 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）在文件和字典之间来回转换，`sort_keys=True` 让同样的状态每次写出的文本完全一致，便于比对和排查。
3. `transfer` 的第一件事是 `state = self._read()` 把状态读进来，然后 `if idempotency_key in records` 立刻判断这个键是否做过；命中就直接 `return` 旧记录，并把第二个返回值设为 `False`，表示「这次没有真正动手」。这就是「先查存根再决定」。
4. 未命中分支里，先 `state["balance"] -= amount` 执行真实副作用，再把 `key`、`amount`、`balance_after`、`result_id` 打包成一条记录塞进 `records`，最后用一次 `_write` 把整份状态写回文件。注意记录里连「当时扣了多少、扣完剩多少」都存了下来，所以重放时能原样交还，而不是重新现算一份。
5. `side_effect_count` 是一个纯粹的观察计数器，专门用来证明副作用到底发生了几次；它不参与逻辑，只服务于断言。
6. `main` 里连续用同一个键 `order-A` 调两次，再换 `order-B` 调一次，随后构造一组 `(名称, 布尔值)` 断言：余额应为 50（只扣 30 和 20 各一次）、副作用计数为 2、记录表恰好两条、两次 `order-A` 返回完全相同。
7. 最后重新 `new` 一个 `Ledger` 指向同一文件，模拟程序崩溃重启后再收到一次老请求，断言它依旧不重复执行、且吐出的 `result_id` 与首次一致——这一步把「落盘」相对「内存」的价值钉死了。结尾 `assert` 保证只要有一条性质被破坏，程序就以非零状态退出。

## 踩坑与边界

- **用随机值当幂等键**：现象是同一笔业务每次重试反而去重失败、越重试扣越多 → 原因是键没有绑定业务意图，每次现生成一个全新编号 → 改成用订单号、业务流水号这类稳定标识，且同一次意图的所有重试必须复用同一个键。
- **去重表只放内存**：现象是单进程内测试全过，一重启或多开几个进程就重复执行 → 原因是内存状态随进程消亡、进程之间也不共享 → 改成写共享的状态文件或带唯一约束的存储，让判定落在所有实例都能看见的地方。
- **只记「做过没」不记结果**：现象是重放时重新拼了一份返回值，与首次对不上，调用方拿到两个不同结果 → 原因是状态里没存首次产物 → 把参数与完整结果一起持久化，命中时原样交还，必要时连时间戳一起存。
- **键相同但参数变了却静默放行**：现象是拿旧编号办新金额，被悄悄返回旧结果，错误被掩盖很久 → 原因是判定只查键在不在 → 命中后追加校验本次参数与历史是否一致，不一致就明确报错。
- **把所有动作都做成幂等**：现象是连纯查询、只读计算也套上落盘，反而拖慢系统、把状态文件撑得很大 → 原因是没区分有无副作用 → 幂等只针对会改动外部世界的动作；纯读取天然重复无害，不必这套开销。

还要留意一个尺度问题：上面演示的是单机单文件的最简形态，用它建立直觉足够，但它并不解决多机并发下的严格排他。真到分布式部署，去重的判定权要交给支持原子操作的共享存储，并且最好让下游系统也认同一个幂等键，形成两端共识。什么时候该把这套机制做得更重、什么时候够用，可以结合 [成本优化与发布清单](./k116-cost-checklist.md) 一起权衡——每一分可靠性都是要付出写入与存储成本的。若想从整体上先看这套教程的组织方式，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

幂等落盘，是让会改动外部世界的动作先查持久化状态、命中就交还首次结果，从而做一次和做多次效果相同。

关键做法是给每个业务意图绑定稳定的幂等键，把参数与结果一次性写入共享且可持久的存储，并收紧「执行」与「写状态」之间的空隙。

当动作只是纯查询、或者系统根本没有重试与重放来源时，不必套上这套写入开销；但只要有真实副作用，它就该是默认配置。

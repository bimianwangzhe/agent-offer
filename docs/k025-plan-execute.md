# Plan-and-Execute

## 场景提问

你交给程序一件要分好几步办的活儿：把一批文档列出来、逐个读、分好类、写一份汇总、再存到指定位置。你让它「自己看着办」，结果第三步之后它忽然跑去润色其中一份文档，把后面两步忘了；你翻日志，发现「写汇总」被做了两遍、「存到指定位置」一次都没出现。你改成每一步都重新问一遍「接下来做什么」，这回步骤没漏，可每轮都要把前面全部记录重新塞进去，越到后面越慢越贵，还偶尔把已经做过的事又判断成没做。明明任务本身步骤挺清楚，为什么一会儿漏步骤、一会儿又反复重判全局？

## 破误解

**不是把步骤写下来就叫有计划，是把「一次性排好全程」当成了「从此不用再看结果」，缺了执行中按观察修订计划的能力。**

先把这套做法拆开。Plan-and-Execute 是「先规划、再执行」：规划步把任务拆成一份有顺序、有前置关系、有完成判据的步骤清单（Plan，计划），执行步按顺序把清单里下一个未完成的步骤做掉（Execute，执行），每一步的结果回来看一眼，若与预期不符就在**附近**修订计划（Replan，重规划）。它和 [ReAct：推理与行动交替](./k024-react.md) 那种「走一步看一步」的差别不在谁更聪明，而在把判断花在哪儿：逐轮决策每轮都要重新扫一遍全局，灵活，但长任务里目标容易被新观察挤走，轨迹也越滚越长；先规划再执行把全局判断集中做一次，之后每轮只认「清单里下一个没打勾的」，步骤可检查、可保存、断了能接着跑，代价是遇到意外必须显式改计划。两者都是 [决策—行动—观察闭环](./k023-decision-loop.md) 的具体组织方式，只是闭环的粒度不同。

有三处最常被读歪。第一，计划不是许愿清单：只写「整理文档」不算步骤，每一步要写清「做到什么样算完成」，而且这个判据得能被程序判定，不能是「差不多了」。第二，计划不是铁板一块：某步失败了，正确做法是只在这步附近插入补救或换一条路，已完成的部分原样保留，而不是把整张单子撕了重排。第三，计划和执行要分开存：执行器只该读当前计划的下一个未完成步骤，不该顺手改写计划本身，否则事后连「当时到底排了什么」都答不上来。把这三处补上，才谈得上「有计划」；否则只是把一次性推理换了个更长的排版。

## 生活类比

把它想成一次装修。靠谱的工长不会一边刷墙一边临时决定要不要先把水电改了。开工前他先出一张施工单：拆旧、水电、泥瓦、刷墙、装灯、验收，顺序写死，每一项后面还跟着一句「做到什么样算完」——水电要打压合格、墙面要干透、灯要逐个点亮。这张单子就是计划。施工队按单推进，做完一项划掉一项，划掉的那笔就是步骤状态。到了刷墙那步，师傅发现墙面返潮、腻子贴不住，他不会把整套施工单撕掉从拆旧重来，而是在「刷墙」前面插一项「除湿找平」，已经做完的拆旧和水电照旧算数——这就是局部重规划。最后一项「验收」，是整张单子的完成判据，也是收工条件。

对应关系要一句句对上：施工单上的条目是计划里的步骤；「打压合格」「墙面干透」是完成判据，它们必须是能当场验证的事实，而不是一句感觉；墙面返潮是执行时拿到的观察，来自墙、不来自工长的乐观；插一项除湿是重规划，注意它只动未完成的那一段；划勾的动作最容易被忽略，它决定「哪些已经做过」有没有被记住。比喻里还藏着两个常见翻车：一是施工单只写「装修」两个大字，没有分步、没有验收标准，等于没计划，工人只能边干边猜；二是有人把「改施工单」做成了每次重新写一张全新的单子，已完成的工作被重复计费、甚至重复砸墙。放到程序里，前者是「计划太粗、判据不可判定」，后者是「一失败就推倒重排，副作用被做了两遍」，后者还得配合 [幂等落盘](./k107-idempotent-persist.md) 的稳标识才不会真把动作重复执行。

## 自绘示意图

:::figure 先规划再执行的完整顺序
@flow
拆解任务|排出步骤|逐步执行|按结果修订|验收收工
:::

五格里最容易被跳过的是「按结果修订」。很多人以为先规划就意味着「计划定死、照着跑完」，其实这一格才是它能在真实环境里活下来的原因：执行拿到的观察，必须有机会反过来改计划。另外「验收收工」不能并进「逐步执行」，因为最后一步做完和整件事达成目标不是一回事，得有一个独立的判定。

:::figure 计划里每一步该写清的四样东西
@stack
步骤名::用动词开头，说明这一步做什么
前置::依赖哪几步已完成才能开始
完成判据::怎样算做完，能被程序判定
失败处置::不达标时重试还是插补救步骤
:::

四行里最常缺的是「前置」和「失败处置」。缺前置，就会出现前置还没做完、后面那步已经开跑，或者两个步骤抢同一份数据；缺失败处置，某步一失败执行器就只能原地卡住或者把整张计划推翻。四样都写进结构化字段，计划才能被检查、被保存、被重放，这部分与 [结构化状态](./k046-structured-state.md) 是同一套思路。

:::figure 逐轮决策与先规划再执行的差别
@compare
走一步看一步::每轮重判全局|长任务易丢目标|灵活但费上下文
先排程再执行::骨架一次成形|步骤可查可续跑|遇变要改计划
:::

左边适合「下一步完全取决于上一步看到了什么」的探索型任务；右边适合「步骤大体可预见、每步都不便宜」的活儿。右边那句「遇变要改计划」不是缺点，而是它必须付的成本——不付，计划就成了最先过时的那份文档。

## 层层追问

:::ask 那如果计划排错了，或者做到一半环境变了呢？
:::

这正是重规划存在的理由，而且它应该被当成这套方法的正常组成，不是出事后的补丁。触发重规划的情形通常有三类：某一步执行失败或结果不达标；某一步的前置不再成立（比如原本要读的文件被移走了）；任务目标本身被改动。三类都要求「只改未完成部分」：已完成步骤的状态和产出保留，改动落在出问题的那一步附近——换工具、插一个补救步骤、或者把后面几步换个顺序。这样做有两个好处，一是不会把已有成果和已花的钱推倒重来，二是轨迹里能清楚看出「在哪一步、因为哪条观察、改了什么」，便于复盘，可对照 [轨迹评测](./k089-trajectory-eval.md)。再往下一层，重规划自己也得有规矩：要有触发判据，不能每轮都重排一次，否则就退化成「逐轮决策还多一层规划开销」；也要有次数上限，反复插步骤却始终不收敛，说明任务拆得不对或者环境根本不支持这种规划，该退出而不是继续加步骤。失败信息怎么变成可执行的修订线索，见 [工具失败](./k040-tool-failure.md)；「改完接着跑、不用从头来」依赖计划被保存下来，见 [检查点与重放](./k030-checkpoint-replay.md)；把「哪里不对、怎么改」写得更具体，则和 [反思与自我修正](./k026-reflection.md) 是同一套动作。

:::ask 那如果步骤之间有依赖，还有几步其实能同时做呢？
:::

这一问把「线性清单」的局限逼出来了。真实计划往往不是一列，而是一张有依赖关系的网：某步要等两三步都完成才能开始，另外几步彼此不依赖、可以并行。所以计划里必须显式写「前置」，执行器每轮挑的是「前置都已满足且自己未完成」的步骤，而不是简单的下一行；否则就会出现「汇总先于读取完成」这种看着按顺序、其实逻辑错乱的结果。一旦允许并行，又多出两个新问题：并行的步骤可能同时改同一份状态，得约定谁写、按什么规则合并，可对照 [共享状态](./k120-shared-state.md)；以及「整件事做完了」不能再靠「最后一行打勾了」，而要判「所有步骤都完成且所有完成判据都通过」，这与 [停止条件](./k028-stop-conditions.md) 里的收工判据是同一件事。任务怎么拆、拆到多细才既可执行又不互相牵扯，是 [任务分解](./k119-task-decomposition.md) 要展开的。还有个很实际的边界：拆得越细，步骤之间的协调开销越大；拆得越粗，每步失败时重规划的粒度就越笨。没有通用答案，判断依据是「这一步失败了，能不能只重做这一小步」。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用本地确定性桩模拟一个四步任务：取清单、核对、贴标、归位，其中「贴标」在表面未清洁时必然失败。代码完整演示「排好计划 → 逐步执行并划状态 → 失败时只在失败步骤前插入一个补救步骤 → 全部完成并验收」，并用一组断言检查已完成步骤没有被重做、重规划只发生一次、以及不允许重规划时任务确实做不完。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
from dataclasses import dataclass, field


@dataclass
class Step:
    """计划里的一步：名字与是否完成。"""

    name: str
    done: bool = False


@dataclass
class Plan:
    """有序步骤清单，以及它被修订过几次。"""

    steps: list = field(default_factory=list)
    revisions: int = 0

    def remaining(self):
        return [s for s in self.steps if not s.done]

    def snapshot(self):
        return "|".join(s.name + ("/完成" if s.done else "/待办") for s in self.steps)


class World:
    """本地模拟的执行环境：贴标这一步在表面未清洁时会失败。"""

    def __init__(self):
        self.clean = False
        self.log = []

    def execute(self, name):
        if name == "清洁表面":
            self.clean = True
            self.log.append(name)
            return True, "表面已清洁"
        if name == "贴标":
            if not self.clean:
                self.log.append(name + ":失败")
                return False, "有灰尘贴不住"
            self.log.append(name)
            return True, "标签已贴好"
        self.log.append(name)
        return True, "完成:" + name


def make_plan():
    return Plan([Step("取清单"), Step("核对"), Step("贴标"), Step("归位")])


def replan(plan, failed_name):
    """只在失败步骤前插入一个补救步骤，保留其余已完成部分。"""
    idx = next(i for i, s in enumerate(plan.steps) if s.name == failed_name)
    plan.steps.insert(idx, Step("清洁表面"))
    plan.revisions += 1


def run(plan, world, allow_replan=True, max_steps=10):
    """按计划顺序执行；某步失败就局部重规划一次，再继续。"""
    for _ in range(max_steps):
        todo = plan.remaining()
        if not todo:
            return "成功"
        step = todo[0]
        ok, _ = world.execute(step.name)
        if ok:
            step.done = True
        else:
            if not allow_replan:
                return "失败:未重规划"
            if plan.revisions >= 1:
                return "失败:反复重规划"
            replan(plan, step.name)
    return "失败:超出步数"


def main():
    plan = make_plan()
    world = World()
    result = run(plan, world)
    names = [s.name for s in plan.steps]
    checks = []
    checks.append(("计划最终执行成功", result == "成功"))
    checks.append(("只局部重规划了一次", plan.revisions == 1))
    checks.append(("已完成的步骤没有被重做",
                   world.log.count("取清单") == 1 and world.log.count("核对") == 1))
    checks.append(("失败确实发生过并被记下", "贴标:失败" in world.log))
    checks.append(("补救步骤插在失败步骤之前",
                   "清洁表面" in names and "贴标" in names
                   and names.index("清洁表面") < names.index("贴标")))
    checks.append(("所有步骤都已完成", len(plan.remaining()) == 0))
    checks.append(("快照能读出每一步状态",
                   "/完成" in plan.snapshot() and "归位/完成" in plan.snapshot()))
    strict = run(make_plan(), World(), allow_replan=False)
    checks.append(("不允许重规划时任务做不完", strict == "失败:未重规划"))
    short = run(make_plan(), World(), max_steps=2)
    checks.append(("步数上限真的生效", short == "失败:超出步数"))
    replay = make_plan()
    checks.append(("同样的计划与环境重放结果一致",
                   run(replay, World()) == "成功" and replay.snapshot() == plan.snapshot()))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Step` 与 `Plan` 用 `dataclasses`（Python 标准库里快速定义数据类的模块）声明。每步只带「名字、是否完成」两列，完成状态是计划自带的，不靠执行器另外记一份草稿——这正是「做完就划掉」能落地的原因；`revisions` 记重规划次数，用来给它设上限。
2. `Plan.remaining` 每轮重新算出还没完成的步骤，`snapshot` 把整张计划导成可读的一行文本，便于保存、比对和事后回答「当时排的是什么」。两者都不改状态，纯读取。
3. `World.execute` 是外部世界的替身：`清洁表面` 会把 `clean` 置为真，`贴标` 在没清洁时返回失败并往日志里记「贴标:失败」，其余步骤一律成功。它刻意做成确定性的，好让「失败 → 插补救 → 再成功」这条路径稳定发生，不靠碰运气；`log` 同时充当副作用账本，后面用来检查有没有把已完成的步骤重做一遍。
4. `make_plan` 给出四步的初始清单；`replan` 是局部修订的落点：找到失败步骤的位置，只在它前面 `insert` 一个「清洁表面」，并把修订次数加一。注意它**没有**清空或重建 `steps`，所以前三步里已完成的两步仍带着 `done=True` 留在原位。
5. `run` 是执行器：每轮取 `remaining()` 的第一个，调用 `world.execute`，成功就把这一步标成完成；失败时按 `allow_replan` 与 `revisions >= 1` 两道闸门决定是局部重规划、还是明确返回失败。`max_steps` 是步数上限，防止反复插步骤把循环拖成死循环；全部完成时返回「成功」，这就是独立的验收判据。
6. `main` 先跑一遍完整流程，断言最终成功、只重规划一次、取清单与核对各只执行一次、失败确实被记下、补救步骤排在贴标之前、所有步骤都完成、快照里能读出「归位/完成」。这几条合起来验的是「保留已完成部分」而不是「碰巧跑通」。
7. 接着做两个对照：`allow_replan=False` 时任务应停在「失败:未重规划」，说明「计划不随结果调整」就走不通；`max_steps=2` 时应返回「失败:超出步数」，说明上限真的生效；最后用全新计划和新环境重放一遍，断言结果与快照一致。结尾打印每条性质的「通过 / 失败」并汇总为 `通过 N/N 项`，`assert` 保证任何一条被破坏都以非零状态退出。

有一处要如实说明：这里用四步搬运任务代替了真实业务、用固定分支代替了真实工具、用一个插入动作代替了真实的重规划判断，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是计划、执行、局部修订、验收四者的顺序，不是任何具体框架的实现；文中也没有给出任何运行结论。

## 踩坑与边界

- **计划写成愿望清单**：现象是清单上只有「整理文档」五个字，执行器每轮都在猜下一步 → 原因是步骤没有动词、没有完成判据 → 每步写清「做什么、怎样算做完」，判据要能被程序判定，配合 [停止条件](./k028-stop-conditions.md) 定收工线。
- **做完不划状态**：现象是同一步被做了两遍、断点重启后又从头来 → 原因是完成状态散在日志里、没写回计划 → 把 `done` 作为计划自带的字段，执行成功即落盘，见 [检查点与重放](./k030-checkpoint-replay.md)。
- **一失败就推倒重排**：现象是某步失败后整张计划重生成，已完成步骤被重复执行、副作用重复产生 → 原因是把重规划做成了「重新规划一次全局」 → 只改未完成部分、保留已完成产出，重做类动作还要带稳标识，见 [幂等落盘](./k107-idempotent-persist.md)。
- **不设修订与步数上限**：现象是反复插入补救步骤，循环一直不结束 → 原因是没有「改几次就退出」的闸门 → 给重规划次数和总步数各设上限，超出就明确失败并交回人看，参考 [工具失败](./k040-tool-failure.md)。
- **步骤依赖没表达**：现象是汇总先于读取完成、并行步骤同时改同一份数据 → 原因是把计划当线性列表，没写前置 → 每步显式记前置集合，执行器挑「前置齐备且未完成」的步骤，见 [任务分解](./k119-task-decomposition.md) 与 [共享状态](./k120-shared-state.md)。

还要分清「计划过时」和「计划错误」：前者是环境变了，局部修订即可；后者是一开始拆错了，再怎么插补救步骤都别扭，这时该退出重新拆，而不是让执行器硬撑。也别把「先规划」理解成「不再需要观察」——观察只是从「每轮决定全局」挪到了「决定要不要改计划」，位置变了，作用没少。至于执行与计划共用一段可变文本、导致事后说不清当时排了什么，那是 [结构化状态](./k046-structured-state.md) 要解决的存储边界。

## 三句话小结

Plan-and-Execute 是先把任务拆成带前置与完成判据的步骤清单，再逐步执行、按观察局部修订、最后独立验收的一套组织方式。

关键做法是计划与执行分开存、做完即划状态、失败只在出问题的步骤附近插入补救，并给重规划次数与总步数都设上限。

当下一步完全取决于上一步看到什么、环境高度不确定时，不必硬套先规划；但只要步骤大体可预见、每步代价不低，把全局判断集中做一次就比每轮重判更稳更省。

# 提示与策略版本化

## 一、场景提问

你的智能体跑得好好的，某天有人反馈「它最近回话变啰嗦了，还偶尔多做一步动作」。你回想半天，只记得前天顺手把系统提示里一句「简洁作答」删了、又给提示模板加了个字段；可到底是哪次改动引起的，没人说得清。更麻烦的是复盘：上周那批失败的请求，到底用的是哪版提示、配的哪个模型、挂的工具清单是不是已经改过、护栏阈值是多少，日志里统统没有，只能翻聊天记录和代码提交历史瞎猜。你想退回「出问题之前那一套」，却发现提示是散在三个文件里的字符串、工具定义在另一个模块、模型名写在配置里，退了这头漏了那头，所谓「退回上一版」根本拼不出一个完整组合。明明改的都是几行字，怎么就既说不清、也退不回？

## 二、破误解

**不是提示词太难管，是把「会变的内容」当成了「代码里顺手写的一段字符串」，既没给它单独编号，也没把一次请求真正用到的那一整套东西当成一个整体记下来。**

先把要管的东西列清楚。一个智能体的行为，不只由一段提示决定：系统提示、提示模板、工具描述与入参结构、路由规则、护栏阈值、模型版本与采样参数、检索配置、评测用例集，任何一样变了，输出都可能变。这些统称为「产物」（artifact，可独立部署、独立编号的一块内容），它们的共同特点是变更频繁、常常由不同人改、且不需要重新编译代码就能改变对外行为。版本化（versioning，给每份会改动的内容编上可追溯的号，改一次留一次痕迹，随时能取回旧的那份）要解决的，就是给这些产物各自一个稳定身份，再把某一次请求真正用到的那一组，打成一个可复现的「组合快照」。

很多人以为「跟着代码一起发版」就够了，其实差得远。代码提交号回答的是「逻辑长什么样」，回答不了「这次请求用的是提示 A 加模型 B 加工具 C 加阈值 D 的哪种搭配」；而一旦出问题，你追问的恰恰是这个搭配。另一层更隐蔽的误解，是把「退回上一版」理解成改代码——可真正改变行为的往往压根不在代码里。这正是 [影子模式、灰度与回滚](./k112-shadow-canary.md) 反复强调的：回滚退的是整套配置组合，不是某个提交。所以这件事的目标可以收成两句：第一，让每份产物的改动都留下不可伪造的痕迹；第二，让每一条请求都能回答「它当时绑的是哪一整套」。前者靠内容寻址，后者靠组合指纹加请求留痕，两者合起来，才谈得上「说清」和「退回」。

## 三、生活类比

把它想成一家中央厨房的配方管理。厨师长不会把「今天放几克盐」记在脑子里、也不允许谁随手在便签上改一笔就完事。规范做法是：每份标准配方有一个编号，写清楚用了哪种酱油、哪个批次的香料、烤箱温度多少；改一个字，就生成一张新配方卡，旧卡归档不撕；每天每道菜出餐时，出餐单上印着「按第几号配方做的」。客人吃坏了肚子，一查出餐单就知道是哪些菜用了同一张配方卡，能立刻把那张卡停掉、退回上一张。

对应关系很具体：那张带编号的配方卡，就是一份登记过的产物；「改一个字就换新卡、旧卡不撕」，就是只追加不覆盖的版本化；「第几号配方」，就是内容寻址算出来的稳定标识；「出餐单上印着配方号」，就是每条请求都带上组合指纹；「一查就知道哪些菜用了同一张卡」，就是按版本聚合失败、做责任归因。这个类比还点出两处最容易翻车的细节。其一，配方卡上得写全：只记盐放了几克、却没记换过酱油牌子，等于漏了「依赖」，客人照样吃出问题却查不出原因——对应到系统里，就是模型悄悄升级、工具描述被别人改了却没纳入版本体系。其二，别手写一个「大概第 3 版」：两个人各改一处都叫「第 3 版」、改了忘改号、退回时旧卡已经被涂掉，这套编号就撒谎了。稳妥办法是让编号从配方内容本身算出来，内容一样号必然一样，改一个字号必然变，谁也没法一边偷改一边沿用旧号。

## 四、自绘示意图

:::figure 一次请求如何被组合指纹串起来
@flow
登记各类产物|生成组合指纹|请求带上指纹|失败按版本归因|按指纹退回上一版
:::

这五格是一条不能断的链。「登记各类产物」意味着每份内容先进登记处、拿到自己的标识；「生成组合指纹」把这一整套的标识再压成一个短编号；「请求带上指纹」是让每条日志只记这一个编号，而不必塞进全文；有了它，「失败按版本归因」才能把散落的失败聚到同一套配置上，最后「按指纹退回上一版」才是把一个完整的、当初真的跑过的组合重新设为生效。少了中间任何一格，退回都会变成「凭印象拼一套」。

:::figure 一个组合快照该收哪些产物
@stack
提示与策略文本::系统提示、模板、路由与护栏规则
模型与参数::模型版本、采样参数、停止条件
工具定义清单::工具名、描述、入参结构
检索与评估配置::切分方式、召回参数、评测集版本
组合指纹::以上各项标识整体算出的稳定编号
:::

五行里最容易漏的是后两行。「检索与评估配置」常被当成「不算代码、不用管」，可切分方式或评测用例集一变，同一段提示的表现就变了，不登记进去，指纹是干净的、行为却悄悄偏了，这属于 [版本漂移与升级策略](./k084-version-drift.md) 要对付的情况。而「组合指纹」这一行的意义是：它是一个整体编号，不是四个散号 —— 只有整体编号才能回答「这次请求用的是哪一套搭配」。每次改动都追加、不覆盖，才能像 [结构化日志与轨迹回放](./k095-structured-log.md) 那样还原出「先用了 A 套、后切到 B 套」的完整经过。

:::figure 两种管理方式的差别
@compare
散落字符串::改了难察觉|说不清用的哪套|只能退代码
版本化产物::改动即留痕|每次请求可归因|按指纹快退
:::

左边是「顺手写在代码里」，改起来最快，出事最慢；右边多了一道登记与编号，看着繁琐，价值全在「出问题的那一刻」：能不能立刻圈定影响面、能不能拼出一个完整可退的组合。这道差别和 [护栏放在代码里](./k106-guardrail-in-code.md) 的主张一致 —— 靠约定和记忆管不住的东西，就得变成可检查、可断言的结构。

## 五、层层追问

:::ask 那如果把提示写死在代码里、跟着代码一起发版，不也等于有版本吗？
:::

有，但管的是另一回事。代码版本记录的是「逻辑长什么样」，它能回答「这个函数是哪次提交改的」，却回答不了「上周三那批失败请求，配的是哪版提示、哪个模型、哪份工具定义、护栏阈值多少」。这几样东西变更频率不同、改的人不同、往往根本不需要重新编译就能改变对外行为，硬绑在一个提交号上，等于把四个独立变化的维度压成一个，事后必然拆不开。更关键的是，回滚的粒度对不上：你可能只想退一句提示，却被迫整包重发一次代码。

那退一步想，给每个文件手动编个 v1、v2，不就能拆开了吗？手动编号会撒谎，这才是要害：改了内容忘了改号、两个人各改一处都叫 v2、退回时发现 v1 那份早被覆盖掉了 —— 号是人写的，就永远可能对不上内容。稳妥做法叫内容寻址（content-addressed，用内容本身算出标识）：把内容做一次摘要运算（hash，这里用 SHA-256，Secure Hash Algorithm 256-bit，一种把任意长度内容压成定长「指纹」的算法），内容不变则标识不变，改动哪怕一个字，标识也必然不同，谁都没法一边偷改一边沿用旧号。再把某次用到的各份标识按名字排好、整体再算一次哈希，就得到一个「组合指纹」。这样「改回原文」会精确复现最初那一套，而不是得到一个「看着差不多」的新版本 —— 这份可复现性，正是 [幂等落盘](./k107-idempotent-persist.md) 里「同一输入只对应一个稳定结果」的同一套思路。

:::ask 那要是模型悄悄升了级、工具描述被别人改了，压根没进我这套登记呢？
:::

问到了第二层，也就是漂移。版本化要覆盖的是「所有会改变行为的输入」，而不只是自己写的那几段文字：模型版本串、工具定义摘要、检索参数、评测用例集版本，都得作为产物登记进组合，否则指纹看起来干干净净，行为却已经偏了，排查时会对着一份「没改过」的配置百思不得其解。做法是把这些依赖边界都收进登记处，并对外部实际返回的东西做一次校验，发现与登记的不符就报警，别默默继续用 —— 这部分和 [版本漂移与升级策略](./k084-version-drift.md) 讲的一回事。至于「每条日志都记这么全会不会太重」，答案是不必记全文：请求日志只存一个短指纹，明细放在登记处，靠指纹回查即可，既控住日志体积，又保住可归因，见 [Trace 该记什么](./k094-trace-fields.md)。把这套编号与门禁连起来，还能让「这版能不能进小流量」有明确的比较基准，也就是 [回归门禁与基线](./k091-regression-gate.md) 在做的事。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把「内容寻址登记 — 生成组合指纹 — 请求带指纹 — 按版本聚合失败 — 按指纹回滚」完整走一遍。哈希用标准库里的 `hashlib`，产物只追加不覆盖，所有指纹都由内容算出、可手工复算；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import hashlib
import json
import tempfile
from pathlib import Path


def content_id(kind, text):
    """内容寻址：对『类型 + 内容』算摘要，内容不变则标识不变。"""
    raw = (kind + "\n" + text).encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:12]


def bundle_id(parts):
    """把一组产物标识按名字排序后整体再算一次摘要，得到组合指纹。"""
    ordered = sorted(parts.items())
    raw = json.dumps(ordered, ensure_ascii=False, sort_keys=True).encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:12]


class Registry:
    """版本登记处：产物只追加不覆盖，组合可复现，请求可打标签。"""

    def __init__(self, path):
        self.path = Path(path)
        self.artifacts = {}   # 内容标识 -> {kind, text}
        self.bundles = {}     # 组合指纹 -> 各产物标识
        self.active = None    # 当前生效的组合指纹
        self.previous = None
        self.requests = []    # (request_id, bundle_id, outcome)
        self._write()

    def _write(self):
        self.path.write_text(json.dumps({
            "active": self.active,
            "previous": self.previous,
            "bundles": self.bundles,
        }, ensure_ascii=False, sort_keys=True), encoding="utf-8")

    def register(self, kind, text):
        """登记一份产物，返回它的内容标识；同样的内容得到同样的标识。"""
        cid = content_id(kind, text)
        self.artifacts.setdefault(cid, {"kind": kind, "text": text})
        return cid

    def make_bundle(self, items):
        """items 是 [(kind, text), ...]，登记全部产物并生成一个组合指纹。"""
        parts = {kind: self.register(kind, text) for kind, text in items}
        bid = bundle_id(parts)
        self.bundles[bid] = parts
        return bid

    def activate(self, bid):
        """把某个组合设为生效；旧组合记为上一版，便于回滚。"""
        self.previous = self.active
        self.active = bid
        self._write()

    def rollback(self):
        """回滚：把生效指针退回上一组合，产物内容一律不删。"""
        self.active = self.previous
        self._write()

    def record(self, request_id, outcome):
        """每条请求只记『用了哪个组合指纹 + 结果』，事后可按版本聚合。"""
        self.requests.append((request_id, self.active, outcome))

    def outcomes_of(self, bid):
        """按组合指纹聚合结果，用于定位『哪套组合出问题』。"""
        return [o for _, b, o in self.requests if b == bid]


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "registry.json"
        reg = Registry(path)
        checks = []

        prompt_v1 = "请只输出 JSON，字段为 summary 与 score。"
        prompt_v2 = "请只输出 JSON，字段为 summary 与 score，不要多余说明。"
        model = "model-x@2026-01"
        tools = "search,calculator"
        guard = "max_cost=5"

        base = [("prompt", prompt_v1), ("model", model),
                ("tools", tools), ("guard", guard)]
        bid1 = reg.make_bundle(base)
        reg.activate(bid1)

        checks.append(("登记后四类产物可查", len(reg.artifacts) == 4))
        checks.append(("组合指纹是定长字符串", isinstance(bid1, str) and len(bid1) == 12))

        bid1_again = reg.make_bundle(list(reversed(base)))
        checks.append(("顺序无关，同样内容得同一指纹", bid1_again == bid1))

        changed = [("prompt", prompt_v2), ("model", model),
                   ("tools", tools), ("guard", guard)]
        bid2 = reg.make_bundle(changed)
        checks.append(("改一个字后提示标识变化",
                       reg.bundles[bid2]["prompt"] != reg.bundles[bid1]["prompt"]))
        checks.append(("改提示后组合指纹变化", bid2 != bid1))
        checks.append(("未改动的产物标识保持不变",
                       reg.bundles[bid2]["model"] == reg.bundles[bid1]["model"]))

        bid_back = reg.make_bundle(base)
        checks.append(("改回原文可复现最初组合", bid_back == bid1))

        guard_changed = [("prompt", prompt_v1), ("model", model),
                         ("tools", tools), ("guard", "max_cost=9")]
        bid3 = reg.make_bundle(guard_changed)
        checks.append(("只改护栏阈值也算新组合", bid3 != bid1))
        checks.append(("策略项变化不改其它产物",
                       reg.bundles[bid3]["tools"] == reg.bundles[bid1]["tools"]))

        reg.activate(bid2)
        checks.append(("激活新组合后上一版被记住", reg.previous == bid1))

        for i in range(6):
            reg.record("req-%02d" % i, "OK" if i < 4 else "FAIL")
        checks.append(("每条请求都带组合指纹",
                       all(b == bid2 for _, b, _ in reg.requests)))
        checks.append(("按版本聚合能数出失败",
                       reg.outcomes_of(bid2).count("FAIL") == 2))

        n_before = len(reg.artifacts)
        reg.rollback()
        checks.append(("回滚后生效退回上一组合", reg.active == bid1))
        checks.append(("回滚不删任何产物内容", len(reg.artifacts) == n_before))
        checks.append(("旧组合四份产物仍齐备", len(reg.bundles[bid1]) == 4))
        checks.append(("旧提示原文可从登记处还原",
                       reg.artifacts[reg.bundles[bid1]["prompt"]]["text"] == prompt_v1))
        checks.append(("回滚写进快照可查",
                       json.loads(path.read_text(encoding="utf-8"))["active"] == bid1))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `content_id` 把「类型 + 内容」拼起来做 SHA-256 摘要，取前 12 位当标识。拼上类型是为了让「同样一句话分别当提示和当工具描述」得到不同标识；截断只是为了让日志里的指纹短一点，不影响「内容变则标识变」这个性质。
2. `bundle_id` 先把各产物标识按名字排序，再对整个字典做一次摘要。`sorted` 这一手很要紧：它让组合指纹与登记顺序无关，只要搭配一样就是同一个号，不然两份内容完全相同、只是写法顺序不同的清单会被误判成两个版本。
3. `Registry` 里 `artifacts` 是「内容标识到原文」的登记处，`bundles` 是「组合指纹到各产物标识」的清单，`active` 与 `previous` 分别记当前生效组合与上一组合，`requests` 只存「请求号、指纹、结果」三元组。`register` 用 `setdefault` 实现「只追加不覆盖」—— 同一份内容重复登记不会改动旧记录，这正是版本可复现、旧版不会被涂掉的前提。
4. `make_bundle` 一次收进多份产物，逐份登记后生成组合指纹并存档；`activate` 把某个组合设为生效、同时把旧的存进 `previous`；`rollback` 只把 `active` 拨回 `previous`，**不删任何产物**。断言里「旧提示原文可从登记处还原」验证的就是这条：退回去的是当初真的跑过的那一整套，而不是重新拼一个近似的。
5. `record` 让每条请求只带一个短指纹，`outcomes_of` 按指纹把结果聚起来。这就是「日志不塞全文、靠指纹回查明细」的落地：六条请求里有两条失败，按 `bid2` 一聚合就能定位到「是这套组合」，而不是翻遍全文去猜。
6. `main` 先验证登记数量、指纹格式、以及「顺序变了指纹不变」；再验证「改一个字 → 提示标识变 → 组合指纹变、但模型标识不变」，说明版本粒度精确到单份产物；接着验证「改回原文精确复现最初组合」和「只动护栏阈值也算新组合」，说明策略任何一项变化都逃不过登记。
7. 后半段激活 `bid2`、记录请求并按版本数出失败，最后回滚：断言生效退回 `bid1`、产物数量不减、旧组合四份齐备、原文可还原、结果写进配置快照。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。
8. 这里用短字符串模拟提示与工具定义、用本地临时文件模拟登记处、用确定性摘要代替真实版本库，全是为了让整条链路不联网、不要账号和第三方包就能独立跑通并手算核对。JSON（JavaScript Object Notation，一种纯文本的数据表示格式）只用来把组合清单写成可查的快照，它演示的是「内容寻址 + 组合指纹 + 按版本归因」的顺序，不是任何具体配置中心的实现。

## 七、踩坑与边界

- **提示写死在代码里靠提交号追溯**：现象是问「这次失败用的哪版提示」答不上来，只能翻提交历史瞎猜 → 原因是把内容变更和逻辑变更压成了一个版本号 → 每份产物单独登记编号，每条请求带组合指纹，明细放登记处、日志只存指纹，见 [结构化日志与轨迹回放](./k095-structured-log.md)。
- **手写 v1、v2 会撒谎**：现象是改了内容忘了改号、两人改出两个 v2、退回时旧版已被覆盖 → 原因是编号由人写、与内容无强绑定 → 改用内容寻址，让标识由内容摘要算出，改一个字必变号。
- **只登记自己写的文字、漏掉依赖**：现象是配置显示「没改过」，行为却悄悄偏了 → 原因是模型版本、工具描述、检索参数、评测集没纳入组合 → 把所有会改变行为的输入都当产物登记，并对外部实际返回值做校验，见 [版本漂移与升级策略](./k084-version-drift.md)。
- **回滚只退一处**：现象是提示退了、模型和工具清单还停在新版，跑出一个谁都没测过的搭配 → 原因是各管各的、没有一个整体编号 → 用组合指纹当回滚单位，一次退回整套，思路同 [影子模式、灰度与回滚](./k112-shadow-canary.md)。
- **覆盖式改配置**：现象是想退却发现旧内容已经被抹掉、无法复现当初那一套 → 原因是把配置当成可随手改写的一个当前值 → 只追加不覆盖，旧产物与旧组合永久保留，参照 [幂等落盘](./k107-idempotent-persist.md)。

还要划两道边界。其一，版本化管的是「可追溯、可复现、可退回」，它不负责判断改动本身好不好 —— 那要交给评测用例集和门禁，见 [回归门禁与基线](./k091-regression-gate.md)；给一份烂配置编上再规范的号，它照样是烂配置。其二，别把这套做成负担：对纯本地、一次性、没有真实用户的实验脚本，逐份登记、打指纹、写快照反而拖慢手脚，徒手改字符串完全够用；只有当一次改动会影响对外行为、且事后需要回答「用的哪一套」时，这套机制才值得上。换句话说，它的价值密度和「需要归因的请求量」成正比，这一点和 [成本优化与上线检查清单](./k116-cost-checklist.md) 里「按真实需要决定做到多细」是同一种分寸。

## 九、三句话小结

提示与策略版本化，是把提示、模型、工具定义、护栏与评测配置各自编号、再打成可复现组合指纹，让每条请求都能回答「用的是哪一套」的一套管理办法。

关键做法是内容寻址让改动必留痕、组合指纹当唯一归因单位、请求日志只存短指纹、产物只追加不覆盖、回滚一次退回整套。

当脚本纯本地、一次性、没有真实流量需要归因时，不必上这套；但只要一次改动会改变对外行为、且事后要说得清、退得回，它就该被当成可部署的产物认真管起来。

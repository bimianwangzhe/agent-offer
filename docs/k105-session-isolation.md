# 会话隔离与租户边界

## 场景提问

你做的一个客服 Agent 同时给两家公司用，本来相安无事。某天 B 公司的用户随口问了一句「上次那份报价怎么定的」，Agent 张口就报出了 A 公司内部的合同金额和折扣，还顺带把 A 那边检索到的文档片段引了出来。你查日志，两家的请求时间根本不挨着，代码里也没有任何一处写着「把 A 的数据给 B」。更蹊跷的是，这类串味时有时无：偶尔正常，偶尔又冒出来，重启一下好像就好了，过一阵又犯。明明每次请求都带着会话号，怎么数据还是跑到别人那儿去了，而且问题还这么难复现？

## 破误解

**不是会话号不够长，也不是模型记混了，是把「一次推理」当成了「一次自带归属的读写」，让租户这个维度在缓存、记忆、检索、临时文件这些旁路上悄悄丢了。**

先把两个词说清楚。租户（tenant，共用同一套系统但彼此该完全隔开的一个客户或组织）是最大的那道边界；会话（session，一个用户和系统之间一次连续的交互）是租户内部再切一刀的单位。真正的隔离要求是：任何一次读写，都得能回答「这份数据属于哪个租户、哪个会话」，而且这个归属不能靠调用方记得传，得由存储结构本身强制。很多人以为「我给每个会话生成了全局唯一的编号」就够了，其实那只解决了「两个会话撞名」这一种情况。数据串味绝大多数不发生在会话号上，而发生在你没想到的旁路上：一个用裸键索引的字典缓存、一份按用户抽出来却忘了标租户的长期记忆、一次忘了按租户过滤的检索、一个模块级的全局变量、一个所有请求共用的临时目录。这些东西的共同点是——它们不在主流程的入参里，于是「租户」这个维度压根没被带进去。

还要点破「时有时无、重启就好」这个现象的根子：那通常意味着有状态被放在了跨请求复用的地方。进程活着时，某个全局字典或单例里残留着上一个租户写进去的值，下一个租户恰好命中同一把键，就读到了；重启清空了这块内存，看起来就「好了」，等再攒几次又复现。这类问题用随机性解释不通，用「模型不稳定」更解释不通，它是纯粹的归属缺失。所以这道题的解法不是「测得更勤」，而是把归属做成结构：所有键值都带租户与会话前缀、所有检索先按租户元数据过滤、租户标识取自已认证的身份而不是请求里声称的字段、上下文只从本会话的命名空间拼。哪一层省了这四件事里的任何一件，边界就漏在哪一层。这也解释了为什么它属于护栏而不是功能：功能写对了主流程就能跑，边界漏了却要等到两家数据撞上才暴露，见 [护栏放在代码里](./k106-guardrail-in-code.md)。

## 生活类比

把它想成一栋写字楼里的快递收发室。楼里驻着好几家公司，这就是多个租户；每家公司里，某个员工这阵子在收一批件，相当于一次会话。快递面单上原本该写三段地址：哪栋楼、哪家公司、哪位收件人。收发室图省事，只按「收件人姓名」分拣，把件往写着名字的格子里一塞。于是 A 公司的「张工」和 B 公司的「张工」，件全进了同一个格子；B 公司的人来取件，顺手就把 A 公司那份合同也拿走了。

对应关系要一条条对上。整栋楼，是共用的一套 Agent 服务；楼里的公司，是租户；公司里那位收件人，是会话或用户；面单上被省略的「公司名」，正是代码里没带上的租户标识；只按姓名分的格子，就是那个用裸键索引的缓存或字典；B 取走了 A 的件，就是串味。还有几处特别贴切：收发室墙上有块谁都能写的公共白板，谁顺手记一句「张工的包在左边第三格」，下一个人照着拿就错了——这就是模块级全局变量和单例缓存，进程不重启它就不清，正好对应「时有时无、重启就好」。楼里还有个档案室，本该按公司分区上锁，若管理员只按文件标题找、不看分区，一样会把别家的档案递出去——这就是检索时忘了按租户元数据过滤。正规收发室怎么改？面单强制三段地址齐了才收件，取件时核的是前台系统里已登记的公司工牌，而不是来人自己嘴里报一句「我是 A 公司的」，并且每个公司的件只放进各自上锁的分区。这三件事，正好对应「复合命名空间」「身份绑定取值」「逐层过滤」。

## 自绘示意图

:::figure 一次请求要过的几道归属关卡
@flow
认证拿身份|绑定租户标识|读写带命名空间|检索按租户过滤|上下文按会话拼
:::

五格是一整条链，缺一格就在那一格漏。最容易被跳过的恰恰是第二格「绑定租户标识」：很多实现拿到请求就直接读写了，租户字段是从请求体里随便取的一个字符串，既没和已认证的身份核对，也没在后续每一层强制携带。一旦这一格松了，后面四格再漂亮也只是把错误归属照着执行了一遍。

:::figure 需要按归属隔开的几处状态
@stack
会话上下文::每一轮对话只从本会话的命名空间取
长期记忆::写入即带租户与用户归属，读取按归属过滤
检索索引::文档带租户元数据，查询先过滤再匹配
工具凭证::每个租户各自的票据，绝不复用同一份
缓存与临时文件::键里含租户与会话，避免公共区残留
:::

这五格里，前三格大家通常想得到，后两格最常出事。「工具凭证」若全系统共用一份，等于所有公司拿同一把钥匙开同一个柜子，越权根本无从拦起，这与 [最小权限](./k100-least-privilege.md) 和 [权限矩阵](./k037-permission-matrix.md) 是同一回事；「缓存与临时文件」若键里不含租户，就是收发室那块公共白板，谁写谁读全凭先后顺序。记忆为什么要写入即带归属，可对照 [记忆与隐私](./k074-memory-privacy.md)。

:::figure 两种归属做法的差别
@compare
只换更长会话号::撞名变少|越权照样能读|旁路仍会串
租户即命名空间::读写强制带|身份绑定取值|每层都过滤
:::

左边是「把编号弄复杂点」，它只压低了碰撞概率，压根没有回答「B 能不能读 A」这个问题：只要键里没有归属、检索不过滤，越权读取照样成立。右边把归属做成结构的一部分，读写两端都绕不开，才是真正的边界。

## 层层追问

:::ask 那如果给每个会话都用足够长、全局唯一的随机编号，是不是就不会撞、也就不用管租户了？
:::

撞名确实能压到极小，但这只解决了一类问题，而且是这类问题里最不要紧的一个。串味的根子不是「两个会话恰好同名」，而是「一次读写没有强制携带归属」。举三种绕开会话号的情形：其一，缓存用的是业务键，比如按「用户手机号」或「合同编号」做索引，压根没走会话号，两个租户只要业务键相同就撞上了；其二，检索索引里文档带的元数据没写租户，查询时也没过滤，B 的提问照样能召回 A 的文档片段，这部分正是 [元数据过滤](./k060-metadata-filter.md) 与 [分块元数据](./k056-chunk-metadata.md) 要管的；其三，长期记忆在抽取事实时把「某公司折扣是八五折」存成了一条通用知识，没标是谁的，之后谁问都往外掏。这三种都不经过会话号，编号再长也拦不住。反过来说，只要每一处读写都强制带归属，会话号就算在同一个租户内重复，也不会出事——真实系统里会话号往往只在租户内部唯一，跨租户本来就可能重名。所以别把力气花在「让编号更难猜」上，那属于防猜测，不属于防串味；防串味靠的是命名空间与逐层过滤，两者不是一回事。上下文该从哪几层取、常驻层与按需层怎么分，可以对照 [上下文分层](./k042-context-layers.md)。

:::ask 那如果把租户标识放进请求参数，让每个函数自己读一下再带上，够不够？
:::

不够，而且这一问才是整套边界最要害的地方，它有两个独立的漏洞。第一个漏洞是来源：请求参数来自不可信输入，是可以被改的。调用方在请求体里把租户字段从 B 改成 A，如果代码照单全收，就等于让来人自己嘴里报一句「我是 A 公司的」便取走了 A 的件——这正是 [身份注入](./k137-identity-injection.md) 里那类问题的变形。正确做法是「身份绑定取值」：请求一进来先做认证，得到一个已经核实过的身份对象，之后所有读写里的租户标识都从这个身份对象取，忽略请求里声称的那个字段；存储层甚至不该暴露一个能由调用方随意指定租户的接口。第二个漏洞是散落：把「记得带租户」这件事交给每个函数各自去做，几十处里总有一处会漏——新加的一个检索分支、一个临时加的缓存、一次图省事直接查库的写法，边界就漏在那儿。所以归属不能靠自觉，得收口到唯一入口：存储、检索、记忆、缓存各自只有一个对外读写通道，通道内部强制拼命名空间、强制过滤，业务代码拿不到「裸键」这种能绕过归属的能力，这与 [逻辑层与执行层解耦、动作白名单](./k148-decouple-allowlist.md) 是同一套「把约束收口到执行层」的思路。还有一层要补：光有隔离不够，越权尝试得能被看见。被拒绝的读写留一条结构化记录，才能事后回答「谁在什么时候试图读别家的数据」，见 [结构化日志](./k095-structured-log.md) 与 [轨迹字段](./k094-trace-fields.md)；而「身份到底是什么、票据什么时候过期」本身也得盯住，参考 [凭证过期与轮换](./k111-credential-expiry.md)。一句话：归属要取自身份、由结构强制、在执行层收口，再配上可观察的拒绝记录，才算真的有边界。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「裸键会串味」和「把租户做成命名空间之后怎么挡住」两边对照演示一遍：复合键隔离、身份绑定取值、同租户不同会话隔离、缺归属的写入被拒、检索先过滤再匹配、上下文只从本会话拼。数据全是本地构造，不联网、不装包、不需要账号，键的取值可手工推算；复制到任意装有 Python 的机器上直接运行即可，结尾用一组断言逐条验证并打印通过项数。

```python
class NaiveStore:
    """反面教材：只用会话内键做索引，租户维度被丢掉。"""

    def __init__(self):
        self.data = {}

    def put(self, session, key, value):
        self.data[(session, key)] = value

    def get(self, session, key):
        return self.data.get((session, key))


class TenantStore:
    """把租户标识做成不可省略的命名空间，读写都必须带。"""

    def __init__(self):
        self.data = {}
        self.audit = []

    def put(self, tenant, session, key, value):
        if not tenant or not session:
            self.audit.append(("reject_put", tenant, session))
            return False
        self.data[(tenant, session, key)] = value
        return True

    def get(self, tenant, session, key):
        if not tenant or not session:
            self.audit.append(("reject_get", tenant, session))
            return None
        return self.data.get((tenant, session, key))

    def read_as(self, identity_tenant, session, key, claimed_tenant=None):
        """读取时租户取自已认证身份，忽略请求里声称的那个字段。"""
        return self.get(identity_tenant, session, key)

    def search(self, tenant, docs, query):
        """先按租户元数据过滤，再匹配内容，绝不返回别家文档。"""
        hits = []
        for doc in docs:
            if doc["tenant"] != tenant:
                continue
            if query in doc["text"]:
                hits.append(doc["text"])
        return hits


def build_context(store, identity_tenant, session):
    """按会话拼上下文：只从本租户本会话的命名空间取值。"""
    ctx = []
    for key in ("profile", "history"):
        value = store.get(identity_tenant, session, key)
        if value is not None:
            ctx.append(value)
    return ctx


def main():
    checks = []

    naive = NaiveStore()
    naive.put("s1", "profile", "A 的合同金额")
    leaked = naive.get("s1", "profile")
    checks.append(("裸键存储让别的会话读到同一份值",
                   leaked == "A 的合同金额"))

    store = TenantStore()
    store.put("tenant_a", "s1", "profile", "A 的合同金额")
    store.put("tenant_b", "s1", "profile", "B 的报价单")
    checks.append(("同名会话下两租户的值互不覆盖",
                   store.get("tenant_a", "s1", "profile") == "A 的合同金额"
                   and store.get("tenant_b", "s1", "profile") == "B 的报价单"))
    checks.append(("B 用自己的身份读不到 A 的值",
                   store.get("tenant_b", "s1", "profile") != "A 的合同金额"))

    spoof = store.read_as("tenant_b", "s1", "profile", claimed_tenant="tenant_a")
    checks.append(("冒用租户参数仍只读到本租户的值",
                   spoof == "B 的报价单"))

    store.put("tenant_a", "s2", "profile", "A 另一会话的草稿")
    checks.append(("同租户不同会话彼此隔离",
                   store.get("tenant_a", "s1", "profile") == "A 的合同金额"
                   and store.get("tenant_a", "s2", "profile") == "A 另一会话的草稿"))

    ok_missing_tenant = store.put("", "s1", "k", "v")
    ok_missing_session = store.put("tenant_a", "", "k", "v")
    checks.append(("缺租户或缺会话的写入被拒",
                   (not ok_missing_tenant) and (not ok_missing_session)))
    checks.append(("被拒动作留有审计记录", len(store.audit) == 2))

    docs = [
        {"tenant": "tenant_a", "text": "A 的合同条款"},
        {"tenant": "tenant_a", "text": "A 的交付安排"},
        {"tenant": "tenant_b", "text": "B 的合同条款"},
    ]
    a_hits = store.search("tenant_a", docs, "合同")
    b_hits = store.search("tenant_b", docs, "合同")
    checks.append(("A 只检索到自己的合同文档", a_hits == ["A 的合同条款"]))
    checks.append(("B 检索不到 A 的合同文档", b_hits == ["B 的合同条款"]))

    store.put("tenant_a", "s1", "history", "A 上一轮的追问")
    a_ctx = build_context(store, "tenant_a", "s1")
    b_ctx = build_context(store, "tenant_b", "s1")
    checks.append(("A 的上下文含本会话的历史",
                   "A 上一轮的追问" in a_ctx and "A 的合同金额" in a_ctx))
    checks.append(("B 的上下文不含 A 的任何内容",
                   "A 的合同金额" not in b_ctx and "A 上一轮的追问" not in b_ctx))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `NaiveStore` 是刻意留的反面教材，它的 `put` 和 `get` 只接 `session` 与 `key`，压根没有租户这个参数。于是两个租户只要用了同一个会话名 `s1`、同一个键 `profile`，写进去的值就落在同一格，谁都能读出来——这几行复现的正是开头那种「没写任何一句把 A 给 B、数据却串了」的现象。
2. `TenantStore` 把键改成 `(tenant, session, key)` 三元组，租户成为命名空间不可省略的一维。`put` 与 `get` 开头先检查租户、会话是否为空，缺一样就往 `audit` 记一条并返回失败或空值——「归属必须带」不是靠注释约定，而是写进了数据结构和入口判断里，漏带就写不进去。
3. `read_as` 演示身份绑定取值：它接收 `identity_tenant`（已认证身份里的租户），另外那个 `claimed_tenant` 参数被有意忽略，只是为了让「请求里声称的租户」这个不可信输入露个脸。无论调用方声称自己是 A 还是别的，实际读的都是身份里核实的那个租户，堵住了改请求体越权的路子。
4. `search` 把检索拆成两步：先 `continue` 掉所有 `doc["tenant"] != tenant` 的文档，再对剩下的做内容匹配。顺序很要紧——先过滤再匹配，别家文档连被匹配的机会都没有；若反过来先全局匹配再「结果里挑一挑」，只要某个环节漏挑就会泄出去。
5. `build_context` 只按 `identity_tenant` 与 `session` 去取 `profile`、`history` 两类值，拼出来的上下文天然只属于这一个会话。它没有任何「全局上下文」或「公共缓存」参数，就是为了避免把跨租户残留带进提示里。
6. `main` 先把反面教材的串味验一遍，再用一组断言逐条核正面实现：同名会话下两租户互不覆盖、冒用参数读不到别家、同租户不同会话隔离、缺归属的写入被拒且留审计、检索各自只命中自己的文档、B 的上下文里不含 A 的任何内容。最后统计通过项并断言全部成立，任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用字典代替数据库、用字符串元组代替真实的复合主键、用本地列表里的字典代替带元数据的检索索引，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是归属该怎么进键、怎么从身份取、怎么在检索和上下文两处收口，不是任何具体存储或检索产品的实现；文中也没有声称这段代码被实际运行过或给出任何实测结论。

## 踩坑与边界

- **裸键缓存**：现象是某个字典或缓存只按业务键索引，两个租户业务键一相同就互相读到对方的值，重启后暂时正常、攒几次又复现 → 原因是键里没有租户与会话维度，状态还跨请求复用 → 复合键强制含租户与会话，或给每个租户独立的命名空间实例，别用模块级全局字典。
- **租户标识取自请求参数**：现象是调用方把请求体里的租户字段一改，就读到了别家数据 → 原因是把不可信输入当成了已核实的身份 → 认证后从身份对象取租户，忽略请求里声称的字段，存储层不暴露可随意指定租户的接口，见 [身份注入](./k137-identity-injection.md)。
- **只在入口校验一次**：现象是主流程查得很严，新加的检索分支、临时缓存、直接查库的写法却绕过了归属 → 原因是「记得带租户」散落在每个函数里，总有一处漏 → 收口到存储、检索、记忆、缓存各自的唯一读写通道，业务代码拿不到裸键能力。
- **检索忘了过滤元数据**：现象是提问里带了别家才有的关键词，Agent 把那家的文档片段引了出来 → 原因是索引文档没带租户元数据、查询也没先过滤 → 写入即标归属，查询先按租户过滤再匹配，见 [元数据过滤](./k060-metadata-filter.md)。
- **长期记忆抽成通用事实**：现象是把「某公司折扣八五折」存成了一条不带归属的知识，之后谁问都往外掏 → 原因是抽取事实时丢了来源与归属 → 记忆写入即带租户与用户标识，读取按归属过滤，参考 [记忆与隐私](./k074-memory-privacy.md) 与 [事实抽取](./k143-fact-extraction.md)。

还要分清两道不同的边界。「隔离」管的是「B 不能读到 A」，「最小权限」管的是「B 就算读到自己那部分，也不能做超出授权的动作」，前者是数据边界、后者是动作边界，二者叠着用，见 [最小权限](./k100-least-privilege.md) 与 [权限矩阵](./k037-permission-matrix.md)。也别把隔离和加密混为一谈：加密解决的是「数据被拿走也看不懂」，隔离解决的是「根本不该被拿到」，只做了加密而键里没有归属，串味照样发生。「会话」本身怎么建立、标识怎么在一连串请求里稳定传下去，属于 [传输与会话](./k080-transport-session.md) 的范围；而公共区残留、别家文档被召回这类问题，追根到底都是「内容带着旧归属活了下来」，与 [持久化后门与来源信任标注](./k147-persistent-backdoor.md) 里「来源要一路跟着数据」是同一套思路。真出了越权，还得靠 [结构化日志](./k095-structured-log.md) 把「谁在什么时候试图读别家」记下来。若想从整体上看这套护栏怎么组织，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

会话隔离与租户边界，是把「租户」做成不可省略的命名空间，让每一次上下文、记忆、检索、缓存与凭证的读写都带着归属，A 的数据在任何旁路都到不了 B 面前。

关键做法是归属取自已认证身份而非请求参数、键值强制含租户与会话、检索先过滤再匹配、把约束收口到唯一读写通道，并给被拒的越权尝试留下可查记录。

当系统只服务单一租户、且没有任何跨请求复用的状态时，这套命名空间可以简化；但只要不止一方共用一套服务、或有缓存与长期记忆在跑，归属就不该靠调用方自觉携带。

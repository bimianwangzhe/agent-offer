# 超时不等于没执行

## 场景提问

你给工具调用设了五秒超时。某次下单请求等满了五秒没回来，程序抛出一个超时异常，控制循环顺手按「失败」处理，重新发了一次同样的调用。没过多久用户来问，为什么只点了下单、却收到两条扣款。你去查下游，发现第一次请求其实在第三秒就已经处理完了，只是返回那段回执在网络里多绕了一会儿、没赶上客户端那五秒的窗口。也就是说，你以为的「没做」，在服务端那边是「早做完了」。更让人头疼的是另一次：同样的超时，你照旧重试，可这次下游当时正在排队、根本还没轮到第一笔，两次请求前后脚都进了队列，最后各扣了一次。两次现象一模一样，都是「等了五秒没回」，真实结果却一个是做完了、一个是还没做。凭「超时」这两个字，你根本分不清眼前是哪一种，凭什么就敢直接重试？

## 破误解

**超时是「我这侧没等到回执」，不是「对方没执行」——把发生在客户端本地的一个等待事件，错当成了发生在服务端的一个执行结论。**

先把位置摆正。超时（timeout，指调用方为「等多久算太久」设的一个本地上限，到点就放弃继续等）是调用方自己的决定：它只说明「在我划定的这段时间内，没有收到一个完整的返回」，对服务端此刻究竟处在什么状态，一个字都没交代。服务端那边至少有三种可能，而且这三种对应的正确动作完全不同。第一种，请求在路上就丢了，服务端从没见过这笔，状态为空；第二种，请求到了，服务端受理了，但还在排队或等依赖，状态是「进行中」；第三种，请求早就处理完、副作用已经落下，只是返回的那段回执被丢包、被网关截断、或在客户端放弃之后才慢悠悠到达。这三种里，只有第一种适合「安全地再发一次」，第二种需要继续等，第三种必须拿已有结果继续、绝不能再发。

把「超时」直接接一句「那就重试」，等于默认真相永远是第一种，可现实里最常惹祸的恰恰是第三种：动作已经成了，你又补了一刀。[工具失败分类与重试策略](./k040-tool-failure.md) 会把失败拆成可重试与不可重试，但超时连「失败」都算不上，它是一种**状态未知**——既不能判成功，也不能判失败，得先想办法把「未知」变成「确定」。这个把不确定变确定的动作叫对账（reconciliation，指用一个稳定的业务标识，回过头去查下游对这笔到底处在什么真实状态，再据此决定下一步）。还有一层常被漏掉：超时这个判断是分层的，客户端放弃等待，不代表服务端停手了；很多服务端有自己的截止时间（deadline，允许这次处理最长耗到几点的绝对时限），客户端超时之后它照样会把活干完。所以「我这边超时了」和「那笔没发生」之间，隔着整整一个需要查证的距离，[超时兜底](./k109-timeout-fallback.md) 讲的就是这段距离里该安排什么动作，而不是简单抛个异常了事。

## 生活类比

把它想成去窗口交一份加急材料。你把材料递进窗口，工作人员接过去、盖了章、录入了系统，然后打印机卡纸、回执一时半会儿没打出来。你在外面盯着表，等了自己定的五分钟，没拿到那张回执，就转身走了——注意，你「没拿到回执」只发生在你这侧，窗口里那份材料该录入的早就录入了。这时候最稳的做法，不是重新排队再递一份（那样系统里会出现两份一样的申请），也不是回去跟人说「没办成」（人家明明办了），而是拿着你的业务受理号问一句：「我这个号，现在到哪一步了？」查到「已办结」，就把原来的结果领走；查到「还没这个号」，才重新递一次；查到「正在审」，就再等一会儿，别动第二份材料。

对应关系很具体：递进窗口的材料，就是那次工具调用；盖章录入系统，就是下游真实落下的副作用；那张卡纸没打出来的回执，就是丢在网络里的返回；你盯着表等满五分钟就走，就是客户端超时；受理号，就是跨重试稳定不变的幂等键或业务标识；「拿号去问现在到哪一步」，就是对账查询。这个比喻点破了三处要害。其一，「没拿到回执」和「没办」是两回事，前者是你这边的观察，后者是对方的史实，中间必须靠查证连起来。其二，为什么对账要拿「号」而不是拿「我又来了一趟」——因为只有稳定标识才能指回同一笔，重新填一张表在系统眼里就是另一笔新申请，这正是 [幂等键与副作用防重](./k038-idempotency-key.md) 里那把钥匙在这里的用处。其三，对账这件事可以问很多次：问一句「到哪一步了」不会让材料被录入第二遍，它是只读的、问多少次都无害，这和「再递一份材料」有本质区别。放到系统里，就是「查询类动作可以放心重试，写入类动作超时必须先查后定」。

## 自绘示意图

:::figure 超时之后该走的决策链
@flow
本地超时|标记状态未知|按稳定标识对账|查得真实状态|复用或安全重发
:::

这五格里，最容易被跳过、也最不该跳过的，是「标记状态未知」和「按稳定标识对账」两格。很多人从「本地超时」直接跳到「复用或安全重发」，可没有中间那次查证，「复用」和「重发」该选哪个根本没有依据。把状态显式记成「未知」，是为了让后续决策不能假装它已经是「失败」——一旦记成失败，接下来的重试就顺理成章，祸根也就此埋下。

:::figure 一次超时背后的三种下游真相
@stack
请求未到达::服务端从未见过这笔，状态为空
正在执行::已受理仍在排队，状态为进行中
已执行回执丢::状态已改，只是返回那段没送回来
:::

三种真相里，只有第一行适合「安全地再发一次」。第二行若盲目重发，等于在旁边又排一份队；第三行若盲目重发，副作用直接翻倍。把它们摆在一起看就明白：真正决定该不该重试的，从来不是「我等多久了」，而是「对方现在到底处于哪一种」。

:::figure 见到超时就重发与先对账的差别
@compare
见到超时就重发::重复副作用|可能串单|越等越乱
超时先对账::把未知变确定|该复用就复用|确无才发
:::

左边把「超时」一刀切成「失败」，链路短、代价高；右边多了一次只读查询，换来的是三种真相被分开处理。分水岭不在于重试得多不多，而在于重试之前有没有先弄清事实。

## 层层追问

:::ask 那如果对账查询本身也超时了呢，岂不是又回到老问题？
:::

不会，因为对账和写动作的性质根本不同。写动作每多发一次就可能多一份副作用，所以怕重复；对账是一次只读查询，问「这个号现在到哪一步」，问一次、问十次，下游状态都不会被改动半分，天然幂等。所以对账超时可以带着预算反复查，这正是 [指数退避与重试预算](./k108-retry-backoff.md) 适用的场景——注意它适用的是「查」，不是「重做那笔写」。这里的第二层是：查询也得有尽头。给整个「查清真相」的过程设一个总的截止时间或尝试次数，一旦用尽仍是「未知」，正确的落点不是擅自判成功、也不是擅自判失败，而是把这笔挂起、留下可追溯的记录并升级给人处理或告警，让后续从一个明确的「待定」状态继续，而不是从一个被猜出来的「失败」继续。这和 [优雅恢复](./k110-graceful-resume.md) 里「带着未完结的状态续跑」、[检查点与重放](./k030-checkpoint-replay.md) 里「把断点记清楚再恢复」是同一套思路。若是把这份「未知」误当成确定的错误反馈塞回给模型，模型很可能据此重新规划、再发起一次写动作，[错误反馈给模型](./k029-error-feedback.md) 里强调「反馈要如实反映状态」正是为了堵住这条链：一个被写死的「失败」，会诱出一串本不该有的重试。

:::ask 那如果下游压根没有「按标识查状态」这个能力呢？
:::

那就说明重新发起写动作的前提还不具备，得先把它补出来，而不是硬着头皮重试。对账的前提是「存在一个稳定标识，且能用它问出这笔的当前状态」，这两样都不是凭空来的：前者要求每次写动作都带一个按业务意图生成、跨重试不变的幂等键，后者要求服务端在真正执行前后把「进行中 / 已完成 / 结果是什么」记成一份可查的记录。缺了前者，两次请求在系统眼里就是两笔，查无可查；缺了后者，就算拿着键也问不出个所以然。所以 [幂等落盘](./k107-idempotent-persist.md) 和 [结构化日志](./k095-structured-log.md) 在这里不是锦上添花，而是对账能成立的地基：把「哪把键、什么状态、产生过什么结果」留成可读的痕迹，超时之后才有得查。这也解释了为什么 [工具调用 id](./k136-tool-call-id.md) 那类协议层编号帮不上忙——它标识的是「这一轮这一次调用」，而你要查的是「这一笔业务」，两者层次不同。再退一步，如果某个外部服务确实既不提供查询、也不接受幂等键，那么对它发起的写动作一旦超时，唯一稳妥的姿态就是「停、记、交给人」，绝不盲发第二次；宁可留一笔待核实的悬账，也不要制造一笔确定重复的扣款。[链路追踪字段](./k094-trace-fields.md) 能帮你把这次超时前后的来龙去脉串起来，但它替代不了「查得到状态」这件事本身。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一个会真实改状态的本地下游，模拟「客户端等待超时、回执可能丢失、状态可能仍在进行中」的三种真相，并演示超时之后先对账再决策。所有耗时都用预设的确定性数值，不靠随机数，结果可手工推算。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path

STILL_RUNNING = 999  # 代表处理永不结束，模拟长时间排队


class Downstream:
    """模拟服务端：真实状态与副作用次数都落盘，重启后读得回。"""

    def __init__(self, path, durations, deliver):
        self.path = Path(path)
        self.durations = durations   # 每个业务标识的处理耗时
        self.deliver = set(deliver)  # 哪些请求的回执能顺利送回
        self.state = {}
        self.effects = 0
        if self.path.exists():
            saved = json.loads(self.path.read_text(encoding="utf-8"))
            self.state = saved["state"]
            self.effects = saved["effects"]

    def _flush(self):
        self.path.write_text(json.dumps(
            {"state": self.state, "effects": self.effects},
            ensure_ascii=False, sort_keys=True), encoding="utf-8")

    def submit(self, key, amount):
        """真正受理：先占进行中，再按耗时决定能否办结并记副作用。"""
        if key not in self.state:
            self.state[key] = "pending"
            self._flush()
        cost = self.durations.get(key, 0)
        if cost < STILL_RUNNING:
            self.state[key] = "done"
            self.effects += 1
            self._flush()
        return {"receipt": "R-" + key, "amount": amount, "cost": cost}

    def query(self, key):
        """只读对账：返回该标识在服务端的真实状态，问多少次都不改状态。"""
        if key not in self.state:
            return {"status": "absent", "receipt": None}
        if self.state[key] == "pending":
            return {"status": "pending", "receipt": None}
        return {"status": "done", "receipt": "R-" + key}


def call_with_timeout(down, key, amount, timeout):
    """客户端视角：一旦回执迟到或丢失，就只看到 TIMEOUT。"""
    cost = down.durations.get(key, 0)
    receipt = down.submit(key, amount)
    if key not in down.deliver or cost > timeout:
        return {"status": "TIMEOUT", "receipt": None}
    return {"status": "OK", "receipt": receipt}


def settle(down, key, amount, timeout):
    """超时后的正确动作：先对账，再决定复用、等待还是安全重发。"""
    view = down.query(key)
    if view["status"] == "done":
        return {"action": "reuse", "receipt": view["receipt"]}
    if view["status"] == "pending":
        return {"action": "wait", "receipt": None}
    r = call_with_timeout(down, key, amount, timeout)
    return {"action": "resend", "status": r["status"]}


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "downstream.json"
        durations = {"ord-1": 8, "ord-2": 3, "ord-3": STILL_RUNNING}
        deliver = {"ord-2"}  # 只有 ord-2 的回执能顺利送回客户端
        down = Downstream(path, durations, deliver)
        timeout = 5
        checks = []

        # 真相一：其实早办结了，只是回执丢了（耗时 8 > 超时 5）
        r1 = call_with_timeout(down, "ord-1", 30, timeout)
        checks.append(("ord-1 客户端只看到超时", r1["status"] == "TIMEOUT"))
        checks.append(("但服务端其实已办结", down.state["ord-1"] == "done"))
        checks.append(("办结记下一次副作用", down.effects == 1))
        s1 = settle(down, "ord-1", 30, timeout)
        checks.append(("对账后复用首次结果", s1["action"] == "reuse"))
        checks.append(("复用拿到正确回执", s1["receipt"] == "R-ord-1"))
        checks.append(("复用没有新增副作用", down.effects == 1))

        # 真相二：请求在链路上丢了，服务端从没见过这笔
        s2 = settle(down, "ord-2", 20, timeout)
        checks.append(("查到确无才安全重发", s2["action"] == "resend"))
        checks.append(("重发这次回执正常返回", s2["status"] == "OK"))
        checks.append(("重发后服务端已办结", down.state["ord-2"] == "done"))
        checks.append(("两笔合计两次副作用", down.effects == 2))

        # 真相三：仍在进行中，既不能复用也不能重发
        r3 = call_with_timeout(down, "ord-3", 10, timeout)
        checks.append(("ord-3 客户端也只看到超时", r3["status"] == "TIMEOUT"))
        checks.append(("但服务端仍在排队", down.state["ord-3"] == "pending"))
        s3 = settle(down, "ord-3", 10, timeout)
        checks.append(("进行中只继续等待", s3["action"] == "wait"))
        checks.append(("等待没有新增副作用", down.effects == 2))

        # 换个进程视角读回账本，对账结论仍然成立
        restarted = Downstream(path, durations, deliver)
        s4 = settle(restarted, "ord-1", 30, timeout)
        checks.append(("重启后仍认出已办结并复用", s4["action"] == "reuse"))
        checks.append(("重启没有改动副作用次数", restarted.effects == 2))

        # 反面：不做对账、见到超时就盲发，副作用被又加了一次
        call_with_timeout(restarted, "ord-1", 30, timeout)
        checks.append(("盲目重发让副作用从两次涨到三次",
                       restarted.effects == 3))

        passed = sum(1 for _, ok in checks if ok)
        for name, ok in checks:
            print(("通过 " if ok else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `STILL_RUNNING = 999` 是一个远大于超时值的哨兵，代表「处理永远没轮到、仍在进行中」。用预设数值而不是 `time.sleep` 或随机数，是为了让三种真相稳定发生、每一步都能手算，不靠碰运气。
2. `Downstream` 把「每个业务标识的真实状态」和「副作用发生了几次」都写进一份落盘的账本，`__init__` 会从磁盘读回，于是「重新构造一个 `Downstream`」就等价于换一个进程视角继续，用来验证对账结论跨重启仍成立。
3. `submit` 模拟服务端真正受理：先占一个 `pending`（进行中），再按耗时判断能否办结，办结就把状态改成 `done` 并让 `effects` 加一。注意这里**没有**做幂等判断——它是刻意被写成「再受理一次就再记一次副作用」的，这样最后那段反面演示才能真实暴露盲目重发的代价。
4. `query` 是对账入口，纯只读：状态为空返回 `absent`，仍在排队返回 `pending`，已办结返回 `done` 并带回回执。它不调用 `submit`、不改 `effects`，这正是「查询可以反复重试、写入不能」的分界。
5. `call_with_timeout` 站在客户端一侧：它照常让服务端 `submit`，但只要回执属于丢失名单、或耗时超过 `timeout`，就只把 `TIMEOUT` 抛给上层。关键就在这里——**服务端的状态已经被改动了，客户端却一无所知**，超时与真实执行被这一行彻底分开。
6. `settle` 是整段要害，也是「先查后定」的落点：先 `query`，查到 `done` 就 `reuse`（复用首次结果、绝不重发），查到 `pending` 就 `wait`（继续等、也不重发），只有查到 `absent` 才 `resend`（确无此笔，安全地发一次）。三种真相被显式分流，而不是被一句「重试」抹平。
7. `main` 依次构造三种真相并逐条断言：第一笔验「超时但已办结、对账后复用不增副作用」，第二笔验「查到确无才重发且只办结一次」，第三笔验「进行中只等待」，再用重启后的实例验结论可跨进程成立；最后故意不做对账、盲发一次，断言 `effects` 从 2 涨到 3，把「见到超时就重试」的代价摆到台面上。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用预设耗时表代表网络往返、用一张名单决定是否送回回执、用本地 JSON 文件代表下游状态库，全是为了让「回执丢了但事情办成了」这类最反直觉的情形能稳定复现、且不需要联网、账号或第三方包。它演示的是「把超时记为未知 → 按稳定标识查真实状态 → 分三种真相决策」这条链路，不是任何具体服务的实现。真实系统里，对账查询应当打到与那次写入同源的状态库，并且要带着总预算反复查、查不尽就挂起升级，而不是像演示里只查一次就下结论。

## 踩坑与边界

- **把超时当成确定的失败**：现象是超时后直接重试，重复的扣款、重复的通知接踵而来 → 原因是把「我这侧没等到」等同于「对方没做」，默认真相永远是最安全的那一种 → 把状态显式记为「未知」，先对账再定，参考 [工具失败分类与重试策略](./k040-tool-failure.md) 里对状态的分流。
- **对账没有稳定标识可查**：现象是拿着请求参数去查、或干脆重填一份，结果查出来的根本不是同一笔 → 原因是用了协议层的调用编号或每次现生成的值 → 每次写动作带按业务意图生成的幂等键，见 [幂等键与副作用防重](./k038-idempotency-key.md)，别把它和 [工具调用 id](./k136-tool-call-id.md) 混用。
- **对写操作套用查询的重试规则**：现象是「查询能反复重试」被照搬到下单、发信上，越重试副作用越多 → 原因是没分清只读与写入对重复动作的容忍度 → 只读对账可带退避反复查，写动作在查清之前一律不再发，按 [指数退避与重试预算](./k108-retry-backoff.md) 给「查」设预算而不是给「做」设预算。
- **查询无止境、或猜一个结论收场**：现象是对账也超时，程序要么无限打转，要么随手判成功 / 判失败，后续全建立在猜测上 → 原因是「未知」没有合法的处理出口 → 设总截止时间，用尽就挂起、留痕并升级给人，见 [优雅恢复](./k110-graceful-resume.md) 与 [结构化日志](./k095-structured-log.md)，绝不把猜测写回状态。
- **客户端超时就以为服务端收手了**：现象是本地放弃等待后，下游照样把活干完、副作用迟到落下 → 原因是把本地超时和服务端截止时间当成同一件事 → 给整条链路传一个统一的截止时间，让下游也知道「过了这个点就别白干」，并用 [链路追踪字段](./k094-trace-fields.md) 把超时前后串起来核对。

还要分清两处边界。其一，「超时」和「失败」不是一回事：失败是拿到了一个明确的否定结论，超时是压根没拿到结论，[超时兜底](./k109-timeout-fallback.md) 处理的是后者该安排哪些动作，别用处理失败的那套去套它。其二，「对账」和「重放」也不是一回事：对账是回过头查「现在是什么状态」，重放是拿历史结果直接接着用，后者要以 [幂等落盘](./k107-idempotent-persist.md) 里留下的首次结果为依据。至于什么时候不必对账：只读工具、或能随便重算且天然幂等的动作，超时直接重试即可，多查一次纯属浪费；但凡一次调用会改动外部状态、且改动不便撤销，超时之后就必须先把「未知」查成「确定」。把这件事和 [数字与事实完整性](./k124-number-integrity.md) 合起来看会更清楚：一笔钱、一条记录到底发没发生，靠猜是要出账目问题的，靠稳定标识查证才答得准。

## 三句话小结

超时只是调用方本地「没等到回执」的等待事件，它对应三种可能的下游真相，本身既不等于成功、也不等于失败，而是一种需要查证的状态未知。

关键做法是先把状态显式记为未知、再用跨重试稳定的标识去只读对账，查到已完成就复用首次结果、查到进行中就继续等、只有查到确无此笔才安全重发，并给整个查证过程设总预算、查不尽就挂起升级。

当工具是只读查询、或结果可随意重算且天然幂等时，超时直接重试即可，不必多一次对账；但只要一次调用会改动外部状态且不便撤销，就绝不许把「超时」直接接成「再做一遍」。

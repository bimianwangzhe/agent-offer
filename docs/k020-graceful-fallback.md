# 果断降级与兜底返回

## 一、场景提问

你写了个查询助手：主链路是让模型读一段材料、返回一个带答案和依据清单的结构化结果，下游拿到就直接往页面渲染。平时都好，某天模型接口超时，你的代码 `try` 里抛了异常，`except` 里图省事写了句 `return None`。页面那头照常按「结果里一定有 `answer` 和 `items` 两个字段」去取，当场报 `NoneType` 没有属性，整页白屏。你改成返回空字符串，页面不崩了，可用户看到的是一片空白，既不知道是没查到、还是系统坏了，客服那边也说不清刚才那笔到底成没成。明明只是一次超时，怎么就变成了「要么整条链路崩、要么给个谁都不敢信的空白」？降级到底该降成什么样，才算真的兜住了？

## 二、破误解

**不是「降级就是随便返回点什么让程序别崩」，而是到点就果断切换、返回一份与正常结果同一副骨架、且诚实标明来源和原因的可用结果，绝不伪装成成功。**

先把三个词说清。降级（fallback，主链路达不到预期时，改用一条更保守、更确定的备用路径继续给出结果）解决的是「别让一次失败把整条链路掀翻」。兜底返回（fallback result，这条备用路径最终交出去的那份数据）解决的是「交出去的东西下游能不能照常接住、人能不能看懂它是什么」。「果断」是这篇最容易被漏掉的一半：不是「再等等看会不会自己好」，而是失败判定一旦成立就立刻切，不反复刷主链路、不把重试拖到超时之后才想起来降级。很多人把降级理解成「给个 `None` 或者空串顶一下」，这其实是把崩溃从当前这一步挪到了下游——下游往往是按「字段一定在」来写的，少一个键、换一种类型，照样炸。

再往深一层：兜底结果必须和正常结果「同形状」。所谓形状，就是键的集合、每个键的类型、以及「哪些字段永远存在」这件事。下游不该为「这次是不是降级了」多写一整套 `if` 分支，它应该拿到任何结果都能用同一段代码解析，只是多读几个字段知道「这是降级的、原因是超时、来源是离线默认值」。而「诚实」是另一条不能省的线：降级结果得明确标出自己不是正常结果，写清失败原因和它从哪来，否则下游会把一个保守的默认值当成模型算出来的真答案，一路用到 decisions 里去。最危险的不是干脆失败，是「格式全对、内容是编的」——为了不让页面报错，随手填一个看起来合理的答案，这等于用降级之名行伪造之实。

所以本篇要立的规矩是三条一起守：形状一致，让下游不用改代码；诚实标注，让谁都看得出这是兜底、为什么兜底；保守取值，宁可给空列表、给「未取得」，也不编一个业务值。至于「什么时候判定该降」，和 [自动纠正与重试上限](./k019-auto-repair.md) 是前后脚：那一篇管「还能改就带诊断改几次、改不好就停」，本篇管「停了之后具体交出什么」。而「超时这一类失败怎么定性」在 [超时与确定性降级](./k109-timeout-fallback.md) 里展开，「彻底断了之后怎么保住现场、回头接着跑」是 [优雅中断与断点恢复](./k110-graceful-resume.md) 的事，三者别混成同一个 `except`。

## 三、生活类比

把它想成超市收银台突然断网。收银系统平时能查会员价、核积分、打机打小票——这是主链路。断网这一刻，店员不会站在那儿一遍遍刷新屏幕等它自己恢复，也不会两手一摊说「今天不卖了」；按店里写好的规矩，一次判定断网就立刻切到手工小票，让顾客照样能把东西买走——这就是「果断」：到点就切，不恋战。

关键在于那张手工小票长什么样。它跟机打小票是同一副骨架：日期、品名、数量、金额、付款方式，一栏不少，栏位含义完全一样——这就是「形状一致」，财务拿回去照样能按同一套流程入账，不用为「今天是不是手工单」单独写一套账。小票上还手写了一行「离线单，未核会员价，请保留此单稍后补差」——这就是「诚实标注」：明说了这单没能走完整流程、缺了什么、来源是手工兜底、以及后续怎么补。最要紧的是店员绝不随口编一个会员价填上去，金额栏要么按无会员的公开价、要么明确留白待补——这就是「保守取值、不编造」。

对应关系逐条对齐：断网 = 主链路失败；一次断网就切手工 = 果断、不反复刷主链路；手工小票 = 兜底返回；和机打单栏位一致 = 形状一致、下游照常接；那行手写说明 = 状态、原因、来源的标注；不编会员价 = 保守默认、宁缺勿造；顾客仍能完成结账 = 任务没被一次失败掀翻。这个类比还点破一件常被忽略的事：真正兜住场面的不是「店员反应快」，而是那张空白手工单、那套栏位、那行说明都是事先备好、写进规矩的；临场才想「要不要给个空串」，往往就给了个谁都不敢信的空白。

## 四、自绘示意图

:::figure 一次失败到兜底返回的动作顺序
@flow
主链路调用|判定失败类型|选降级档位|同形状组装|标注来源返回
:::

这五格是顺序动作，不是同一个动作的五种说法。「判定失败类型」这一格最容易被省：不同失败对应不同档位，超时和彻底不可用不该给同一种兜底。「同形状组装」和「标注来源返回」必须成对——只组装不标注，等于把兜底伪装成正常结果；只标注不按同一副骨架组装，下游又接不住。

:::figure 降级阶梯的四档
@stack
完整结果::主链路成功，字段齐全，标记为 ok
带缺的部分结果::次要字段缺失，标明缺了哪几项
保守静态答案::给安全默认值，不猜不编
明确拒答::附失败原因，交回人或上游
:::

四档是按「还能保住多少」从多到少排的，越往下越保守、也越诚实。选档的依据是「这次失败吃掉了哪部分信息」，不是「哪个返回起来最省事」。最下面那档常被误当成「降级失败」，其实「明确说做不到」本身就是一种合格且必要的兜底。

:::figure 两种兜底姿势的差别
@compare
伪装成正常结果::字段看似齐全|藏着编造的值|下游误当真
诚实标注的降级::形状与正常一致|标明降级与原因|给保守默认值
:::

左边看着最省事、页面也不报错，可它把风险悄悄转给了下游和用这个结果做判断的人；右边多写三个标注字段，换来的是「谁都知道这份数据能信到什么程度」。二者的差距不在降级那一刻，而在后续有没有人把兜底值当成真答案用出去。

## 五、层层追问

:::ask 那如果降级直接返回 None 或空字符串，让上游自己判断，不是更简单吗？
:::

短期看是简单，代价全在下游。下游代码通常是照着「结果里一定有 `answer`、一定有 `items` 这个列表」来写的，`None` 会让它在取字段时直接抛异常，空字符串会让「判断是不是查到了」的逻辑误判成「查到了、答案是空的」——一个把崩溃挪到下游，一个把失败伪装成了空结果。更麻烦的是这两种返回都不带任何说明，出了事没人能回答「刚才那笔是没查到、还是系统降级了、降的是哪一档」。所以兜底不是「少返回点东西」，恰恰要「按同一副骨架把东西返回全」：键一个不少、类型一个不变，另外多加几个字段写明状态、原因、来源。这样下游那套解析代码一个字都不用改，只是多读到 `degraded` 为真，愿意的话再决定要不要提示用户。判断「哪些字段是下游眼里的必填」得回到契约本身，[结构层校验](./k017-structure-check.md) 讲的就是怎么把「形状」这件事写死、验出来。

:::ask 那如果形状对上了，但为了「不让下游报错」就顺手填一个看起来合理的默认值，算不算合格降级？
:::

这是最该警惕的一问。往深一层想：形状一致解决的是「下游能不能解析」，它管不了「这个值能不能信」。一个格式全对、内容却是随手编的答案，比空白危险得多——下游会把它当正常结果一路用下去，页面不报错、日志不报警，错得安安静静。所以「保守取值」不是一句风格建议，而是硬约束：默认值必须是「安全的、且一眼能认出是默认的」，比如空列表、明确的「未取得」、事先写死的离线常量，而且必须同时挂上 `degraded` 标记和一句原因，让下游有机会选择「不用这个值、改走提示」。真到了连保守值都给不出的时候，就该选最下面那档——明确拒答，把失败原因交回人或上游，这跟 [溯源、拒答与零召回兜底](./k062-citation-abstain.md) 里「宁可说不知道，也不编一条出处」是同一条底线。还要分清两个动作：「降级」是这次请求仍给出一份可用结果，「熔断」（连续失败到一定程度就暂时不再打这个下游，避免把故障放大）是切断流量、连请求都不发了，见 [熔断与 kill switch](./k104-circuit-breaker.md)；而「失败到底值不值得先重试、还是直接降」属于 [工具失败分类与重试策略](./k040-tool-failure.md) 和 [异常分类与可重试判定](./k131-error-classify.md) 要定的规矩。别让一个「兜底」把这几件不同的事全糊过去。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一个完全确定性的本地桩模拟主链路的四种结局，完整演示「一次失败立即切档 → 所有返回共用同一副骨架 → 诚实标注状态、原因、来源 → 绝不编造业务值」。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json

SHAPE = ("answer", "items", "confidence", "status", "reason", "source", "degraded")
CALLS = []


def blank():
    """所有返回共用的一副骨架：键固定、值保守、不含任何编造。"""
    return {
        "answer": "",
        "items": [],
        "confidence": 0.0,
        "status": "",
        "reason": "",
        "source": "",
        "degraded": True,
    }


def primary(key):
    """本地桩：模拟主链路成功、超时、部分缺失、彻底不可用四种结局。"""
    CALLS.append(key)
    if key == "good":
        return {"answer": "已排好三件事", "items": ["整理", "核对", "归档"], "confidence": 0.9}
    if key == "slow":
        raise TimeoutError("主链路超时")
    if key == "partial":
        return {"answer": "查到一部分", "items": [], "confidence": 0.4}
    if key == "broken":
        raise RuntimeError("下游不可用")
    return None


def build(status, reason, source, data=None):
    """把成功或降级都装进同一副骨架，绝不新增键、绝不缺失键。"""
    r = blank()
    if data:
        r["answer"] = str(data.get("answer", ""))
        items = data.get("items", [])
        r["items"] = list(items) if isinstance(items, list) else []
        r["confidence"] = float(data.get("confidence", 0.0))
    r["status"] = status
    r["reason"] = reason
    r["source"] = source
    r["degraded"] = (status != "ok")
    return r


def serve(key):
    """主链路失败就按档位果断降级；任何返回都是同一副骨架。"""
    try:
        data = primary(key)
    except TimeoutError:
        return build("partial", "主链路超时，改用离线默认答案", "offline_default",
                     {"answer": "暂无法联网核对", "items": [], "confidence": 0.0})
    except RuntimeError:
        return build("abstain", "下游不可用，未取得答案", "none")
    if data is None:
        return build("abstain", "输入无法处理，未取得答案", "none")
    if not data.get("items"):
        return build("partial", "次要信息缺失，主答案保留", "primary_partial", data)
    return build("ok", "", "primary", data)


def types_ok(r):
    """校验每个字段的类型，确保下游用同一段代码就能解析。"""
    return (isinstance(r["answer"], str) and isinstance(r["items"], list)
            and isinstance(r["confidence"], float) and isinstance(r["degraded"], bool)
            and isinstance(r["reason"], str) and isinstance(r["source"], str))


def main():
    checks = []
    results = {}
    for key in ("good", "slow", "partial", "broken", "weird"):
        CALLS.clear()
        results[key] = serve(key)
        checks.append(("%s 只调用主链路一次" % key, len(CALLS) == 1))

    good = results["good"]
    checks.append(("正常结果状态为 ok", good["status"] == "ok"))
    checks.append(("正常结果不带降级标记", good["degraded"] is False))
    checks.append(("正常结果保留完整答案", good["answer"] == "已排好三件事" and len(good["items"]) == 3))

    slow = results["slow"]
    checks.append(("超时切到部分结果档", slow["status"] == "partial"))
    checks.append(("超时结果带降级标记与原因", slow["degraded"] is True and bool(slow["reason"])))

    part = results["partial"]
    checks.append(("次要信息缺失仍保留主答案", part["status"] == "partial" and part["answer"] == "查到一部分"))

    broken = results["broken"]
    checks.append(("彻底失败明确拒答", broken["status"] == "abstain"))
    checks.append(("拒答不编造答案与条目", broken["answer"] == "" and broken["items"] == []))
    checks.append(("未知输入也走拒答", results["weird"]["status"] == "abstain"))

    checks.append(("所有返回键集合完全一致",
                   all(tuple(sorted(r.keys())) == tuple(sorted(SHAPE)) for r in results.values())))
    checks.append(("所有返回字段类型一致", all(types_ok(r) for r in results.values())))
    checks.append(("所有降级都写明来源与原因",
                   all((not r["degraded"]) or (bool(r["reason"]) and bool(r["source"]))
                       for r in results.values())))
    checks.append(("所有结果都能直接序列化给下游",
                   all(isinstance(json.dumps(r, ensure_ascii=False), str) for r in results.values())))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `SHAPE` 用一组键名把「形状」写死，`blank()` 则是所有返回共用的底稿：键固定、值一律取最保守的空串、空列表、零和 `degraded=True`。正常结果和兜底结果都从这份底稿长出来，所以「少一个键」「类型突变」这两类把崩溃挪给下游的问题，从结构上就不可能发生。
2. `primary` 是本地桩，`CALLS.append(key)` 记下每一次调用，四种 `key` 分别对应成功、`TimeoutError`、`items` 为空的部分缺失、`RuntimeError` 彻底不可用，其余返回 `None`。用它代替真实接口，是为了让「一次失败立刻切、不反复刷主链路」能被 `len(CALLS) == 1` 直接验出来。
3. `build` 是整套做法的关键：无论成功还是降级，都先拿 `blank()`，再按 `data` 覆盖业务字段，最后统一写 `status`、`reason`、`source`、`degraded`。注意 `r["degraded"] = (status != "ok")` 这一行——降级标记由状态算出，不许调用方自己传，免得有人「降了级却忘了标」。
4. `serve` 体现「按失败类型选档」：超时和彻底不可用分别落到 `partial` 与 `abstain` 两个不同档位，`None` 与次要信息缺失也各有去处；每个 `except` 只做一次返回，没有任何「再试一次」的回环，这就是「果断」。拒答那档只给了原因、没给 `data`，于是答案保持空串、条目保持空列表——绝不编造。
5. `types_ok` 把「同形状」从「看着像」变成可检查的性质：答案必须是字符串、条目必须是列表、置信度必须是浮点数、降级标记必须是布尔。下游据此可以放心用同一段解析代码，不必为每个 `status` 分叉。
6. `main` 先对每个 `key` 清空 `CALLS` 再调用，断言主链路恰好被碰一次；随后逐条验证正常结果、超时档、部分缺失档、拒答档各自的状态与取值，特别断言「拒答时答案与条目都是空的」——把「不编造」钉成一条能失败的检查。
7. 最后四条是全局性质：所有返回键集合完全相同、字段类型一致、凡是降级都写明了原因和来源、每份结果都能被 `json.dumps` 直接序列化交给下游。结尾逐行打印每条性质、统计通过条数输出「通过 N/N 项」，并用 `assert passed == len(checks)` 保证任何一条被破坏都会以非零状态退出。

有一处如实说明：这里的四种结局是构造出来的确定性场景，档位、默认值、字段名也都是为讲清顺序而设的最小例子，不代表任何具体业务该取什么值。它演示的是「同形状、诚实标注、保守取值、一次就切」这四条怎么落到同一份返回里，而不是某个框架的接口用法。

## 七、踩坑与边界

- **兜底返回 None 或空字符串**：现象是当前这步不报错、下游取字段时整页崩，或把失败误判成「答案是空的」 → 原因是少返回了下游眼里的必填键，也没带任何说明 → 按 `blank()` 那副骨架把键返回全、类型不变，另加状态与原因字段，见 [结构层校验](./k017-structure-check.md)。
- **形状随档位变化**：现象是正常结果有五个键、降级结果只剩两个，下游被迫写一堆 `if` 分支，还总有漏网的 → 原因是每个 `except` 各写各的返回字面量 → 所有出口统一走一个 `build`，从同一份底稿长出结果。
- **编个合理值伪装成成功**：现象是页面不报错、日志不报警，可一个随手填的答案被一路当成真结果用出去 → 原因是只顾「不让下游报错」，没守住「不编造」 → 默认值只取空列表、明确的「未取得」这类一眼可辨的值，并强制挂上 `degraded` 标记与原因，参看 [溯源、拒答与零召回兜底](./k062-citation-abstain.md)。
- **恋战不切、反复刷主链路**：现象是超时之后还在重试、等降级动作时整笔请求早已过了用户能忍的时间 → 原因是把「降级」排在「重试拖到极限」之后，且没有一次判定的规矩 → 失败类型一判定就切档，重试归重试、降级归降级，各管一段，见 [自动纠正与重试上限](./k019-auto-repair.md) 与 [超时与确定性降级](./k109-timeout-fallback.md)。
- **在高风险动作上盲目降级**：现象是转账、删数据这类不可逆操作，主链路失败却「兜」出一个默认值继续执行，造成更难收拾的后果 → 原因是把「别让链路崩」凌驾于「别做错动作」之上 → 涉及资金、权限、不可逆写入时，宁可明确拒答、停下交人确认，护栏要落在代码里而非指望返回值，见 [护栏放在代码里](./k106-guardrail-in-code.md) 与 [四重预算](./k103-four-budgets.md)。

还要分清三件常被混为一谈的事：本篇的「降级」是这次请求仍交出一份可用结果；「熔断」是暂时不再往故障下游发请求，见 [熔断与 kill switch](./k104-circuit-breaker.md)；「断点恢复」是保住现场、回头接着跑，见 [优雅中断与断点恢复](./k110-graceful-resume.md)。三者可以接连发生，但不该由同一个 `except` 糊过去。而兜底结果该带哪些标注字段、下游怎么据它决定要不要提示，本质上仍是一道输出契约，和 [结构层校验](./k017-structure-check.md) 里「把形状写死再验」是同一套思路。

## 九、三句话小结

果断降级与兜底返回，是主链路失败时立刻切到一条更保守的备用路径，交出一份与正常结果同形状、诚实标明状态与原因、且绝不编造业务值的可用结果。

关键做法是所有出口统一从同一副骨架组装、按失败类型选档、强制挂降级标记，并让默认值保守到一眼可辨，使下游无需改代码也能照常解析。

当动作涉及资金、权限或不可逆写入，或一次失败宁可让人介入也不该继续时，就别兜出默认值，明确拒答、停下交人更稳妥。

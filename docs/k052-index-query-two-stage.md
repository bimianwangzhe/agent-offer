# 离线索引与在线检索两段：把「编目录」和「翻目录」分开

## 改了一处切分，整套问答都跟着翻车

你只是把切分粒度从「整节」改成「按句」，想让命中更准。结果第二天，连那些压根没动过的文档也开始答得驴唇不对马嘴；你想退回前一版，却发现建库和查询写在同一个函数里，改一处两头都动，根本没有「只退一半」的余地。更麻烦的是排查：答案错了，你说不清是目录编错了，还是取书取错了。

## 先破一个误解

**不是切分参数调坏了，是你没在「编目录」和「按目录取书」之间留一道能单独替换的边界。**

先把两段的词说清楚。索引（index）是为快速查找预先整理好的结构，白话讲就是一张「按某个词能查到第几段」的表；常见的倒排索引（inverted index）把关系倒过来存：不是「某段里有哪些词」，而是「某个词出现在哪几段」，这样查一个词不必逐段扫描。离线（offline）指写时，也就是文档进来那一刻做的事；在线（online）指读时，也就是用户提问那一刻做的事。检索增强这套办法之所以好用，很大程度就因为它是两段：写时把材料解析、切分、登记成索引，读时把问题改写、召回、重排、拼装，两段中间只隔着一份谁都能读的数据结构。

为什么要特意拆开？因为两段的脾气完全不一样。离线段可以慢，可以重跑，可以在半夜跑一整批，出错了大不了重建；在线段必须快，被用户等着，改动一次就影响所有问题。把它们塞进一个函数，等于让「慢的那部分」和「快的那部分」共享同一份状态、同一次发布、同一个出错现场：改切分要动查询，查不准又回去改切分，最后谁也退不回去。拆开之后，三段收益立刻出现——各自独立优化、各自独立回滚、坏例能定位到具体哪一段。回滚尤其值钱：给索引带一个版本号，退回旧版本只是切一个指针，查询代码一行都不用碰。

那条边界上到底传什么，也有讲究：只传稳定的东西，片段编号、原文、来源、版本、权限这类元数据，不传「这段是哪个模型算出来的」之类依赖实现细节的隐含约定。一旦在线段偷偷假定「每块都是固定字数」，离线段换切分就会悄悄出问题，边界就破了。元数据该怎么跟着块走，见[切分元数据与父块回溯](./k056-chunk-metadata.md)；整套材料的组织顺序可以从[从这里开始](./00-start-here.md)看起。

## 用图书馆编目来理解

把材料想成一批刚送到馆里的新书，把提问想成一位来借书的读者。

编目员在后台做一件事：拆包、给每本书登记、写索书号、按规则上架，最后产出一套卡片目录。这些活儿跟「今天谁来、想借什么」毫无关系，可以关起门慢慢做，做错了把卡片重印一遍就行。读者进门做的是另一件事：说出想找的主题，管理员按卡片目录查到索书号，去架上把那几本抽出来递过去。这两拨人在不同时间、不同房间干活，中间只隔着一套卡片目录——谁都不需要知道对方具体怎么干。

对应关系一一对上：新书是文档，拆包登记是解析与切分，索书号是片段编号，卡片目录是索引，读者的主题是查询，抽书是召回，管理员顺手在小票上写下书名和架号，就是溯源。这个比喻解释了一件容易被忽略的事：编目规则换了（比如从按作者排改成按主题排），只要卡片目录还是那套「主题 → 索书号」的接口，读者找书的方法一点不用改；反过来，读者今天问得刁钻，也不必把书架重排一遍。

:::quote
两段之间只隔着一份谁都读得懂的数据结构。边界越窄、越稳定，两边就越敢各自改、各自退。
:::

## 把两段画出来

先看一次完整动作里，哪些发生在材料进来时，哪些发生在用户提问时。

:::figure 从文档进来到片段被取走
@flow
文档写入|解析切分|建立索引|问题到来|按索引取片段
:::

前三个节点是写时，后两个是读时。中间「建立索引」的产物，就是两段唯一的交接物。

两段各自要管的事，可以列成一张清单：

:::figure 离线段与在线段各自负责什么
@stack
写时 离线::解析切分登记，产出自包含的索引
交界 边界::只认片段编号与元数据，不认内部实现
读时 在线::改写召回重排，读索引但不改索引
回退 单位::换一版索引即可退回，查询侧无感
:::

第三行要特别留意：在线段对索引只读不写。一旦查询过程里顺手往索引里塞了点临时状态，这份索引就再也不是「可以整份替换」的纯产物了，回滚会变得又慢又脏。

再看两种组织方式的差别：

:::figure 搅在一起，与拆成两段
@compare
搅在一起::改切分要动查询|无法单独回退|坏例难以归因
拆成两段::各自独立优化|换索引不动问答|可逐段定位问题
:::

第二行三个要点是同一件事的三个侧面：因为中间只剩一份稳定数据，所以能分别改、能按版本退、能在出错时把范围缩到「目录编错了还是取书取错了」。

:::tip 一条立刻见效的规则
给每一版索引一个明确版本号，并且让查询函数只接收「索引」这一个参数。想退回旧效果时，把参数换成旧索引即可，绝不去动查询代码——能不能做到这一点，就是两段有没有真分开的试金石。
:::

## 再往深问两层

:::ask 那如果文档天天变，离线段是不是要一直整批重建？
:::

不用，而且这正是两段分开带来的好处：重建是离线段内部的事，不该牵动读时。频繁变动时，正确做法是在离线段里做增量——只处理内容真的变了的那些片段，没变的跳过重算；再进一步用「先建好新版本、校验通过再原子切换」的方式换索引，避免出现两版并存或中途查不到的空窗。这些都属于写时段的内部策略，在线段照旧只读那份索引。真把两段合并了，每次文档小改都得连查询逻辑一起回归一遍，才是灾难。增量怎么做、换版本怎么切，见[索引更新、增量与知识冲突](./k063-index-update.md)。

:::ask 再深一层：两段之间到底传什么，才能真的做到互不影响？
:::

核心是「只传数据，不传假设」。离线段交出来的应当是自包含的：每个片段有稳定编号、有原文、有来源与页码、有版本、有可见范围，还有一份「词项 → 片段编号」的查找表。在线段只能依赖这些字段，不能依赖「切分器一定按句号切」「编号一定连续」「每块不超过某个长度」这类没写进数据的内部约定。举一个反例：如果在线段为了省事，直接用「编号减去一」去推算上一段原文，那么离线段哪天删了作废片段、编号不再连续，查询就会静默地取错内容——不报错，只是答案悄悄变味。这类越界的依赖最隐蔽，排查时你会一直盯着查询逻辑，怎么也找不到问题。把边界写窄、把字段写全，配合[切分元数据与父块回溯](./k056-chunk-metadata.md)里那套做法，才能真正做到换索引不动问答。脏数据也会顺着这条边界一路污染到答案，所以写时段还得先把[文档解析与清洗](./k053-doc-cleaning.md)做扎实。

## 一份能跑的对照

下面这段只用标准库，把「建索引」和「查索引」写成两个互不依赖的函数，再演示三种独立改动：在线段换查询、离线段换切分、离线段按版本回退。全程不联网、不装包，复制成文件直接运行。

```python
# two_stage.py —— 只用标准库，python two_stage.py
import re

DOCS = [
    ("d1", "一线城市住宿每晚 600 元 其他城市每晚 400 元"),
    ("d2", "差旅发票需七个工作日内提交"),
    ("d3", "设备型号 XJ-2200B 质保三年 含上门检修"),
]


def tokenize(text):
    # 演示用切分：英文数字整体保留，相邻汉字两两成词
    text = text.lower()
    words = re.findall(r"[a-z0-9]+", text)
    han = re.findall(r"[\u4e00-\u9fff]", text)
    words += [han[i] + han[i + 1] for i in range(len(han) - 1)]
    return words


def build_index(doc_list, version):
    # 离线段：把文档变成倒排表，产出自包含的数据结构
    postings = {}
    for doc_id, text in doc_list:
        for t in set(tokenize(text)):
            postings.setdefault(t, []).append(doc_id)
    return {"version": version, "postings": postings,
            "texts": dict(doc_list)}


def query(index, question):
    # 在线段：只读索引，不碰原始文档，也不改索引
    hits = {}
    for t in set(tokenize(question)):
        for doc_id in index["postings"].get(t, []):
            hits[doc_id] = hits.get(doc_id, 0) + 1
    return sorted(hits, key=lambda d: -hits[d])


if __name__ == '__main__':
    v2 = build_index(DOCS, version="v2")
    q = "一线城市住宿每晚多少钱"
    r = query(v2, q)
    assert r[0] == "d1"                       # 命中最相干的片段排最前
    assert "600" in v2["texts"][r[0]]

    # 在线段单独改动：换成查型号，索引一个字都不用动
    assert "d3" in query(v2, "XJ-2200B 质保多久")

    # 离线段单独回退：换回旧版索引，在线代码原封不动
    v1 = build_index(DOCS[:1], version="v1")
    assert "d3" not in query(v1, "XJ-2200B 质保多久")
    assert v2["version"] != v1["version"]
    assert "d3" in v2["texts"] and "d3" not in v1["texts"]
    print("通过 6/6 项：离线段与在线段可各自改动、各自回滚")
```

1. `TOKENIZE` 那一段前面几行是 `tokenize`，它是最朴素的演示用切分：型号、数字整体留着，汉字两两成词。真实系统会换分词器，但只要接口还是「文本进、词项出」，离线段怎么换都不影响在线段。
2. `build_index` 是离线段的全部：遍历文档，把每个词项登记到「词项 → 片段编号列表」，连同原文一起打包成一份字典，还带一个 `version`。注意它返回的是纯数据，没有任何函数、句柄或隐含状态，所以能整份替换。
3. `query` 是在线段的全部：只读 `index`，把问题拆成词项、累加每个片段被命中几次、按次数排序。它不接收原始文档，也从不写索引——「只读」这条纪律是两段能分开的前提。
4. 第一轮断言验证按相关度把写有一线城市标准的 `d1` 排在最前，并且从索引自带的原文里能取回答案所需的数字。
5. `if __name__ == '__main__':` 后半段是三次独立改动：换一个查型号的问题、`query` 一行没改；把索引换成只含 `d1` 的旧版本、再查型号就查不到新增文档；两版 `version` 不同，说明回退只是换一个对象。六条断言跑完打印通过项数。

想看得更清楚，可以试着把 `query` 里累加改成「命中即停」，或者把 `build_index` 的切分换成按单字登记——你会发现这两处改动彼此完全不干扰，各自的结果都能单独验证。这就是分两段的意义：改动半径被关在了自己那一段里。

## 踩过的坑

- **建库与查询共用一个全局状态**：现象是换一版索引后旧问题答案全变、还退不回去 → 原因是查询过程里往索引写了临时数据，索引不再是可整份替换的纯产物 → 怎么改：索引当只读数据交接，任何临时状态放在查询这一次调用的局部里。
- **在线段依赖隐含假设**：现象是删了作废片段后答案悄悄变味、却不报错 → 原因是用编号做算术推算相邻片段，而编号并不保证连续 → 怎么改：只依赖写进索引的字段，需要相邻关系就显式存父子编号。
- **把增量重建做成全量重建**：现象是文档只改一行，整批重跑几小时、账单跟着涨 → 原因是没按内容变化判定，改动一次重建一次 → 怎么改：先算内容指纹，只处理真正变了的片段。
- **索引不带版本**：现象是新旧两版并存，同一问题这次查到新文档、下次查到旧文档 → 原因是切换没有原子性，中途出现了混合状态 → 怎么改：先建好新版本并校验，再原子切换活动版本，查询侧只认当前版本。
- **两段一起发布**：现象是只想调召回排序，却不得不把建库流程也回归一遍 → 原因是没有独立边界，发布单位捆在一起 → 怎么改：把索引当可部署产物，带版本号单独发布与回退。

## 三句话
离线索引与在线检索两段，是把「写时把材料编成目录」和「读时按目录取片段」拆成互不依赖的两件事。
关键做法是让中间只交接一份带版本号、带片段编号与元数据的只读数据，两边都不得越过这条边界。
当材料极少、切分与查询本就写在一个小脚本里时，硬拆两段反而多一层间接，不必强求。

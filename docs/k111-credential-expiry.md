# 凭据过期与刷新

## 场景提问

你写了一个要跑很久的批处理助手：启动时一切正常，取数、清洗、汇总都顺顺当当。可跑到第四步，下游接口突然回了一句「令牌已过期、未授权」，后面每一步都跟着失败。你确认过启动时凭据是好的，也试着加了重试，结果连着重试几次还是同样的错，任务要么卡死在那里，要么被自动重跑、把前面做过的动作又来了一遍。你翻日志才发现，这个任务前后横跨的时间，已经比那张凭据的有效期还长。为什么会「刚开始能用、跑着跑着就不能用了」，而且重试一点忙都帮不上？

## 破误解

**不是下游忽然翻脸，也不是重试次数不够，是凭据有寿命，而这个任务活得比它长。**

先把词说清：凭据（credential，用来证明「我是谁、被允许做什么」的一小段令牌）几乎都带着一个有效期，过了那个刻度就作废，这叫过期（expiry）。刷新（refresh）是指拿一张寿命更长、被妥善收着的凭证，去换一张新的短期凭据，让任务能接着走。很多人在程序启动时取一次凭据，就把它当成一个从此不变的常量传下去：短请求里这没问题，因为一次调用在有效期内就结束了；可一旦任务要跑几十步、中间还要停下来等人审批、或从检查点恢复，时间就悄悄爬过了有效期，那张常量凭据早成了废纸。这时候重试毫无意义——这是一个确定性错误，不是临时抖动，重试一万次下游也只会回同一句「未授权」，反而把前面做过的动作又推了一遍。真正要做的，是把「凭据是否有效」从启动时的一次判断，改成每次要碰下游之前的例行动作：先查、过期就刷新、刷新不了就明明白白地停下来走重新授权，而不是硬闯或假装没事。这套动作必须放在包住任务的服务代码里，凭据本身也绝不该被塞进模型能读到的上下文。

## 生活类比

把它想成一张多日景区的入园手环。你买的是一张长期购票凭证，它不直接用来过闸机；每天早上进园前，你拿它到闸口换一张「当日有效」的手环，戴着手环才能坐项目。手环一到当天午夜就自动失效，第二天得再拿购票凭证换一张新的。这里还有个细节：换手环的窗口并不是无限次随便换，某些票种限定了次数，或者换到一半闸机要求你重新出示证件核验；一旦走到这一步，你就得去人工窗口办一次，办完从刚才停下的那个项目接着玩，而不是被赶出园区从头排一遍队。

对应关系很具体：长期购票凭证就是那张寿命较长、被妥善收着的刷新凭证；当日手环就是每次调用带的短期访问凭据；午夜就是到期刻度；闸口换手环就是刷新动作；换不了要去人工窗口就是「待授权」与重新授权路径；「刚才停下那个项目」就是恢复时该接着走的进度。这个比喻还顺带说清了一件常被忽略的事：短请求像「只玩一个上午」，一张手环从头用到尾没问题；长任务像「连玩三天」，中途必然跨过午夜，不设计换手环的流程就一定会卡在闸机前。还有一层：手环该由游客自己拿着、到闸口出示，而不是把购票凭证的原件到处递给别人看——对应到系统里，就是短期凭据放在服务侧、按会话使用，而那张长期凭证要收在更严的地方，不能让任何不可信内容接触到它。

## 自绘示意图

:::figure 每次动作之前的凭据检查顺序
@flow
动作前查凭据|未过期直接执行|已过期尝试刷新|刷新成功续期执行|额度耗尽转待授权
:::

这张图的关键是「动作前查凭据」这一格的位置：它不是只在启动时查一次，而是每准备碰一次下游都先查一遍。因为过期是按时间发生的，跟任务做没做完无关，只有把检查铺到每一步前面，才能在过期那一拍就地接住。「刷新成功续期执行」和「额度耗尽转待授权」是同一处判断的两个出口：能续就原地续了接着做，不能续就干脆停，绝不带着废凭据硬闯。

:::figure 凭据状态里该记哪些字段
@stack
到期刻度::凭据在哪一刻失效，判断要不要刷新
刷新额度::还能续几次，用尽就转人工
待授权进度::停在第几步、已完成动作与恢复位置
重新授权入口::让人知道去哪续、续完从哪接着跑
关联标识::哪次运行、哪个会话，便于事后对账
:::

五格里最容易被漏掉的是「待授权进度」。很多程序一发现凭据不能用了就抛个异常结束，进程里记着的「做到第几步」随即蒸发，人补完授权回来只能整单重来。把停下的位置一起存下来，重新授权后才能从断点接着走，而不是从头重跑。

:::figure 两种凭据用法的差别
@compare
启动取一次用到尾::长任务中途必然过期|刷新无处触发|失败只能整单重来
每步前查并按需刷新::过期就地续期|进度不丢|耗尽才转人工
:::

左边把凭据当成常量，短请求里看不出毛病，一旦任务跨过有效期就全线崩；右边把凭据当成一份会变化的状态来管。二者的差别全攒在「任务比凭据活得更久」这件事上。

## 层层追问

:::ask 那如果刷新本身失败，或者刷新额度用完了呢？
:::

这时候最忌讳两件事：一是拿旧凭据继续硬试，二是静默地把任务杀掉让人一头雾水。正确做法是把它变成一个明确的、能停能续的状态，通常叫「待授权」：立刻停止执行有副作用的动作，把「停在第几步、已完成哪些、恢复位置、为什么停」连同状态一起持久化，再给出一个明确的重新授权入口。注意这里的状态转换不该由模型自己声称「我已经授权好了」就放行，而应由服务代码验证：只有真正拿到新的有效凭据，才允许从「待授权」转向「执行中」。恢复之后先展示当前进度让人确认，再接着跑剩余步骤——这与 [优雅中断与断点恢复](./k110-graceful-resume.md) 里「从检查点续跑、不重复已完成动作」是同一套纪律。还有个容易被忽略的默认值：如果重新授权一直没人处理、超时了，必须默认「不动」，而不是默认放行，尤其当等待中的动作涉及资金或对外发送时，这条在 [审批超时默认拒绝与责任归因](./k149-approval-timeout.md) 里会被讲透。把「停下来等授权」设计成系统里正式的一种状态，而不是异常分支，长任务才不会在凭据这道坎上丢进度。

:::ask 那如果好几个步骤并发跑，都在同一刻发现过期、一起刷新呢？
:::

这会撞出另一种麻烦：几个执行单元同时判定「过期了」，各自去换一张新凭据，后写回的那张把先写回的覆盖掉，先完成的单元手里就攥着一张已经被作废的凭据，接下来又是一片未授权。更糟的是，如果刷新也有次数上限，这一波齐刷刷的刷新会把额度瞬间烧光，直接把任务逼进待授权。解法思路和 [重试、指数退避与抖动](./k108-retry-backoff.md) 同源：让「查过期—刷新—写回」这段由一个持有者串行完成，其他人发现凭据过期时先等这个持有者把新凭据写好再读；刷新同样要有次数上限，必要时加一点随机抖动，别让所有单元踩同一刻。再往深一层是边界问题：凭据属于服务侧的敏感状态，身份与权限要由服务端按会话注入，绝不让模型在参数里自报或自行填写，否则参数被篡改就等于凭据被冒用，这一点和 [用户身份服务端注入](./k137-identity-injection.md)、[护栏放在代码里](./k106-guardrail-in-code.md) 是同一条原则。不同会话、不同租户的凭据也要各归各的，别共用一份，免得一个任务的刷新把另一个任务的凭据搅乱，这是 [会话隔离与租户边界](./k105-session-isolation.md) 要守的线。这些机制叠起来，说的其实是同一件事：把「会过期、会被并发争抢、又绝不能外泄」的东西，交给一层确定性的代码来管，而不是散落在任务逻辑里各管各的。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一个整数刻度模拟时间流逝、用本地状态文件记录待授权进度，完整演示「每步前查凭据—过期就地刷新—刷新额度耗尽则停在待授权并把进度落盘」，结尾用一组断言逐条验证。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络，也不会真的等待时间。

```python
import json
import tempfile
from pathlib import Path


class Clock:
    """用整数刻度模拟时间流逝，避免真实等待。"""

    def __init__(self, start=0):
        self.now = start

    def advance(self, n=1):
        self.now += n


class Credential:
    """一份带到期刻度与刷新次数的访问凭据。"""

    def __init__(self, expiry, refresh_left, refresh_span):
        self.expiry = expiry
        self.refresh_left = refresh_left
        self.refresh_span = refresh_span
        self.refreshes = 0

    def valid(self, now):
        return now < self.expiry

    def refresh(self, now):
        if self.refresh_left <= 0:
            return False
        self.refresh_left -= 1
        self.refreshes += 1
        self.expiry = now + self.refresh_span
        return True


def persist(state, state_path):
    Path(state_path).write_text(
        json.dumps(state, ensure_ascii=False, sort_keys=True), encoding="utf-8"
    )


def ensure_valid(cred, clock, state):
    """动作前先保证凭据有效；刷新耗尽就转入待授权并停。"""
    if cred.valid(clock.now):
        return True
    if cred.refresh(clock.now):
        state["refreshes"] += 1
        return True
    state["status"] = "awaiting_authorization"
    return False


def run_task(cred, clock, state, steps, state_path):
    for step in steps:
        clock.advance(2)
        if not ensure_valid(cred, clock, state):
            persist(state, state_path)  # 待授权状态也要落盘，供恢复时读取
            break
        state["done"].append(step)
        state["effects"] += 1
        persist(state, state_path)
    return state


def main():
    with tempfile.TemporaryDirectory() as d:
        state_path = Path(d) / "auth_state.json"
        steps = ["取数", "清洗", "汇总", "核对", "归档"]

        state = {"status": "running", "done": [], "effects": 0, "refreshes": 0}
        cred = Credential(expiry=3, refresh_left=3, refresh_span=3)
        clock = Clock()
        final = run_task(cred, clock, state, steps, state_path)
        checks = [
            ("长任务跑完全部五步", len(final["done"]) == 5),
            ("期间确实触发了刷新", final["refreshes"] > 0 and cred.refreshes == final["refreshes"]),
            ("刷新后凭据仍有效", cred.valid(clock.now) is True),
            ("状态文件已落盘", state_path.exists()),
        ]

        state2 = {"status": "running", "done": [], "effects": 0, "refreshes": 0}
        cred2 = Credential(expiry=3, refresh_left=0, refresh_span=3)
        final2 = run_task(cred2, Clock(), state2, steps, state_path)
        checks.append(("刷新耗尽转入待授权", final2["status"] == "awaiting_authorization"))
        checks.append(("待授权后不再执行副作用", final2["effects"] < 5))
        checks.append(("待授权时已完成步骤不再增加", len(final2["done"]) < 5))
        checks.append(("待授权状态被写进文件", "awaiting_authorization" in state_path.read_text(encoding="utf-8")))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Clock` 用整数 `now` 加 `advance` 来推进时间，纯粹是为了让「长任务跨过有效期」这件事在瞬间可复现，不依赖真实时钟、也不需要任何等待。JSON（JavaScript Object Notation，一种纯文本的数据表示格式）在 `persist` 里负责把状态写成断电也丢不掉的文本。
2. `Credential` 存三个数：到期刻度 `expiry`、剩余刷新次数 `refresh_left`、每次刷新续多久 `refresh_span`，外加一个只用于观察的 `refreshes` 计数。`valid` 就是一句 `now < expiry`，`refresh` 在额度够时把额度减一、把到期刻度往后挪，额度为零则明确返回 `False`。
3. `ensure_valid` 是整个机制的心脏，也是图里那一排判断的落点：先查是否还有效，有效就放行；过期了先试刷新，刷新成功记一笔并放行；刷新不了就把状态置成 `awaiting_authorization` 并返回 `False`，绝不带着废凭据继续。
4. `run_task` 每步先 `clock.advance(2)` 让时间往前走（模拟步骤耗时），再调 `ensure_valid`。这里特意把「待授权」分支也 `persist` 一次——很多人只在中途成功时存状态，一遇到停下来反而忘了存，进度就丢了。这一行正是本篇最想钉死的细节。
5. `main` 的第一个场景给足刷新额度（`refresh_left=3`、`expiry=3`、`refresh_span=3`），五步里会自然跨过有效期两次，断言任务跑完五步、期间确实刷新过、刷新后凭据仍有效、状态文件存在。
6. 第二个场景把刷新额度设成零（`refresh_left=0`），凭据一过期就再也续不了，断言状态转入待授权、副作用不再增加到五、已完成步骤停在过期那一拍、并且「待授权」这个状态确实被写进了文件，而不是只留在内存里。
7. 结尾用一组 `(名称, 布尔值)` 汇总，打印每条是否通过、再打印「通过 N/N 项」，最后 `assert` 保证只要有一条性质被破坏，程序就以非零状态退出。

有一处要坦白说明：为了把「长任务比凭据活得久」压缩进几行代码，这里用整数刻度代替了真实时间、用本地文件代替了真正的凭据存储，刷新也是一段确定性的模拟，没有网络、没有账号、没有第三方包。它演示的是判断的顺序和状态的去留，不是任何真实授权协议的实现。

## 踩坑与边界

- **启动时取一次凭据当成常量**：现象是短请求全过、长任务跑到中途集体未授权 → 原因是有效期短于任务时长，且判断只做了一次 → 改成每次碰下游之前都查一次，过期就地刷新，别把凭据当不变值传到底。
- **把「未授权」当临时错误去重试**：现象是连着重试几次全是同样的错，前面做过的动作又被推了一遍 → 原因是没区分确定性错误与临时抖动 → 先分类，未授权走刷新或重新授权，不进通用重试，这一点与 [异常分类与可重试判定](./k131-error-classify.md) 一致。
- **刷新耗尽就抛异常了事**：现象是任务突然消失，人补完授权回来只能整单重跑，已完成的动作又做一次 → 原因是停下时没保存进度与恢复位置 → 把「待授权」做成正式状态并持久化，重新授权后从断点续跑，配合 [优雅中断与断点恢复](./k110-graceful-resume.md)。
- **多个执行单元同时刷新**：现象是后写回的新凭据把先写回的覆盖，先完成的单元手里攥着作废凭据，或刷新额度被一波烧光 → 原因是「查—刷新—写回」没串行化 → 交给单一持有者完成，其余单元等新凭据写好再读，必要时给刷新加次数上限与抖动。
- **把凭据放进模型能看见的地方**：现象是长期凭证被写进上下文、日志或工具参数，一旦内容外泄或被篡改就等于授权被冒用 → 原因是把敏感状态交给了不可信链路 → 凭据只在服务侧持有，身份与权限由服务端按会话注入，参考 [用户身份服务端注入](./k137-identity-injection.md)。

还要分清两层：自动刷新解决的是「凭据正常老化」，它能无声地续上；重新授权解决的是「刷新这条路也走不通了」，它必须有人明确参与，并且超时默认不动。二者不能混成一句「出错就重试」。另外，长任务恢复时除了进度，还得连「预算累计、结构版本号」一起读回来，别让重启把额度清零；这些在 [检查点与轨迹回放](./k030-checkpoint-replay.md) 里会以更一般的形态出现。若想从整体上看这套教程怎么组织，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

凭据过期与刷新，是把「我是谁、能做什么」这段有寿命的令牌当成一份会变化的状态来管，每次碰下游之前先查、过期就地续、续不了就明确停下。

关键做法是每步前检查有效期、给刷新设次数上限并由单一持有者串行完成、把「待授权」连同进度与恢复位置一起持久化，重新授权后从断点续跑。

当任务短到一次调用就结束、或凭据压根不会过期时，不必套这套流程；但只要任务可能跨过有效期、又带着会改动外部世界的动作，它就是绕不开的一环。

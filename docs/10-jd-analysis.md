# 岗位 JD 拆解：把招聘要求翻译成能力矩阵

大部分人读 JD 是「看看会不会」，然后按关键词补知识点。更有效的方式是：**把每一条要求翻译成「面试官会用什么问题验证它」**，再反推自己缺哪一格。

> 本篇给的是拆解方法与能力矩阵，不编造具体公司数据。岗位情报会单独持续更新，见 [15 一手资料地图](./15-resources.md)。

## 三类岗位画像

市面上的「Agent 开发岗」其实混着三种完全不同的工作，投错方向比能力不足更常见：

| 类型 | 常见 title | 主要产出 | 最看重 |
|---|---|---|---|
| **A 应用层** | 大模型应用开发 / AI 应用工程师 | 业务里的 RAG、助手、工作流 | 检索质量、上下文、评测、成本 |
| **B 平台层** | Agent 平台 / Agent 基础设施 | 编排框架、工具网关、MCP Server、可观测平台 | 状态机、幂等、权限、多租户、稳定性 |
| **C 模型层** | 算法 / Agentic RL / 微调 | 让模型本身更会用工具 | 训练、对齐、评测基准、推理优化 |

这份知识库（以及绝大多数 Agent 岗）面向 **A 与 B**。投 C 需要补训练与对齐，那是另一条路线，别用应用项目去硬投。

## JD 高频要求 → 真实考察点

| JD 里写的 | 表面理解 | 面试官实际验证 |
|---|---|---|
| 「熟悉 LangChain / LangGraph」 | 会用框架 API | 为什么选它、换掉成本、框架没替你做什么 |
| 「熟悉 RAG」 | 搭过向量库 | 召回不准怎么定位、怎么防幻觉、怎么证明没变差 |
| 「有 Agent 项目经验」 | 跑通过 Demo | 上线过吗、怎么评测、成本多少、出过什么事故 |
| 「了解 MCP / Function Calling」 | 接过工具 | 参数幻觉怎么防、重复调用怎么办、权限怎么收 |
| 「有工程化 / 性能优化经验」 | 会 Docker | 熔断降级、限流、追踪、单任务成本怎么算 |
| 「关注大模型安全」 | 知道提示注入 | 外部内容夹指令时，具体在哪一层被挡住 |
| 「良好的沟通与协作」 | 软技能 | 能不能 15 分钟把一个技术决策讲清楚 |

**规律**：JD 写的是名词，面试考的是「出问题怎么办」。准备时把每个名词配一个故障场景。

## 简历对照表

把 JD 的每条要求，在简历里对应到一条**带数字、带口径**的证据：

| JD 要求 | 简历证据写法 |
|---|---|
| 熟悉 RAG | 「50 条标注集 + 回归门禁，引用命中率 95%，正确拒答率 92%」 |
| 有工程化经验 | 「幂等 key + 检查点，故障注入后重复执行 0 次」 |
| 性能优化 | 「四层上下文 + 预检路由，单轮 token 下降 X%，20 轮完成率无下降」 |
| 关注安全 | 「高危动作 HITL 覆盖率 100%，恶意指令样本纳入发布回归」 |

没有数字就先去做评测集——这是把「参与过」变成「负责过」的最短路径。

## 笔试与面试的情报差异

Agent 岗的筛选常常混着两套东西，准备方式完全不同：

- **笔试**：算法题、行测、专业选择，平台多为北森 / 智鼎 / 牛客等，题型与计时规则差异大
- **面试**：项目深挖 + 场景追问（见 [面试考点](./09-interview.md) 的四条追问链）

> 情报类内容（各公司题型、网申时间线、平台规则）会持续更新在资料包与网站上，仓库里只保留方法论，避免过期信息误导。

## 建立自己的情报更新机制

不要等别人整理。给自己搭一个最小流程：

1. 每周固定抓一批目标岗位 JD，存原文与日期
2. 抽取高频名词，与上表对照，看有没有新原语出现（如某协议、某评测方式）
3. 新名词出现时，先判断它是「生命周期长的原语」还是「季度性热词」，只补前者
4. 把变化写进能力矩阵，缺哪格补哪格

这一步本身也可以写进内容工厂的选题——「我把 30 份 Agent 岗 JD 拆了」这类内容天然有流量，且素材是一手的。

## 验收点

- 能说出三类岗位画像的区别，并判断自己投哪一类
- 能把一条 JD 要求翻译成面试官的验证问题
- 能力矩阵里每一格都能举出一条带口径的证据

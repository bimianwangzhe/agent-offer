# 语法层校验

## 一、一解析失败就重问，账单涨了毛病没少

你给解析脚本加了个「保险」：只要这段回复读不成 JSON，就把原来的提示再发一遍，让模型重新给。想法挺朴素，跑起来却不是那么回事——费用涨得很快，问题一点没少。因为它这次又用三个反引号把结果包了起来，或者同一个尾随逗号又冒了出来；更冤的是有些回复明明只是前后多了句「好的，以下是结果」，里面那段 JSON 一个字都没错，你却把整轮重发、把前面已经算对的内容也一起重算了一遍。偶尔连着重问几次还是同样毛病，程序就卡在那儿空转。你想要的其实很简单：能就地救回来的就救，救不回来再说，别动不动推倒重来。如果你刚照着[起步说明](./00-start-here.md)把第一版脚本跑通，这种「一有脏东西就整轮重来」的浪费，多半是把两层不同的事混成了一件。

## 二、不是这次特别不听话，是把语法小毛病当成了大事

**不是模型这次格外不听话，是你把「语法小毛病」当成了「得重来一遍」的大事；语法层该做的第一件事是清洗和提取，不是立刻重问。**

先把词摆平。JSON（JavaScript Object Notation，用花括号和键值对表示数据的文本格式）是下游爱读的那种文本。解析（parse）指把一段文本按格式规则还原成程序里的数据对象；语法层校验是输出契约的第一关，它只回答一个是非题——「这段文本能不能按 JSON 规则解析」，别的概不负责。清洗（cleaning）是把明显多余的包装剥掉，提取（extraction）是从混杂文字里把 JSON 那一段捞出来；重问（re-ask）则是重新发起一次调用。

为什么该先清洗？因为绝大多数「脏」是包装问题，不是内容问题：前后一句客套话、一层代码块围栏、末尾多一个逗号，这些都不改动里面的数据，剥掉之后内容原封不动就变干净了，代价几乎为零。重问可就贵了：重新付一次调用、重新等一次、还得重新面对一次采样随机性，而且老毛病常常原样重现——你并没有改变会产生它的条件。把「剥个包装」升级成「整轮重来」，是这段最典型的错位。

这一关的职责窄，恰恰是它可靠的原因：它不查字段齐不齐，不查值对不对，只管能不能读。清洗也有清楚的边界，只做确定、可逆、说得清后果的动作：去首尾空白、剥前后解释、去围栏、截取花括号之间那段、修掉尾随逗号。一旦动作需要「猜」——比如猜这个字段本该是什么、猜被截断的嵌套该怎么补——就已经越过语法层了，那属于结构或语义的事，该交给后面几关。还有一类反面动作要警惕：无脑把单引号全换成双引号，会把字符串里正常的撇号也改坏；无脑截「第一个左括号到第一个右括号」，遇到嵌套对象会拦腰截断。清洗越贪心，把本来合法的内容改坏的风险越高。这也接上了[「请只输出 JSON」为什么不是保证](./k014-json-request.md)那句结论：请求没有强制力，兜住结果得靠代码，而代码第一下该做的不是重问，是就地清洗。

## 三、拆快递，而不是退货重下单

把这件事想成收一件网购的书。包裹送到，外面套了个纸箱，箱里塞了张广告单，缠了几圈胶带，还贴了张「亲，记得好评哦」的便签。你不会因此打电话给商家说「这单不算，重新给我寄一本」吧？你会拆箱、把广告单扔掉、撕开胶带、撕掉便签，把书拿出来——书本身好好的，一个字没少。

对应关系一条条摆出来：纸箱、广告单、胶带、便签，就是前后解释、代码块围栏、尾随逗号、首尾空白这些包装；箱里那本书，就是本来合法的那段 JSON；拆包这一串动作，就是清洗与提取；打电话要求重寄，就是重问。什么时候才真该退货？拆开发现书缺了半本、或者印错了内容——那对应的是字段缺失、值不对，属于另外两关要判的事，语法层看不出来，也不该由它硬猜。

想明白这层，就该看出「一失败就重问」有多不划算：书没坏，你却付了两次运费、多等两天，还可能收到一本同样裹着纸箱的书。更稳妥的姿态是分两步：先花几毫秒把包装拆干净，能读就用；真拆不出书来，再干净利落地交上去，让上层决定是带着错处补一次，还是直接走兜底。

:::tip
一句话记住：**先拆包，别急着退货。** 判断该清洗还是该重问，只问一句：这段文本里的「数据」有没有坏？只是外面裹了东西，就清洗；数据本身残缺，才交上去。
:::

## 四、语法层这一道关内部怎么走

把一次「拿到回复 → 决定放不放行」拆开，顺序其实很固定。

:::figure 语法层一道关的处理顺序
@flow
拿到原始文本|直接试解析|失败先清洗|再试解析|仍失败才上报
:::

第一步先老实试一次直接解析，能过就别多动；第二步失败才进清洗；第三步清洗后再试；仍失败才把「这段救不回来」这个事实报给上层。注意整条链子没有「立刻重问」这一步——重问是上层的决定，不是语法层自己偷偷发起的。

:::figure 清洗动作按改动从小到大排
@stack
去首尾空白::只删两端空格换行，最安全
剥前后解释::去掉「好的，以下是」这类客套前缀
去代码块围栏::剥掉三反引号与语言标记
截取花括号段::从首个左括号到最后一个右括号之间取出
修尾随逗号::删掉右括号前多出的逗号
:::

从上往下，动作越往下改动越大、越要小心；每加一条规则，都要能单独验证「它没有把合法内容改坏」。最下面那条修尾随逗号看着简单，也得限定只在右括号前动手，不能满文本乱删逗号。

:::figure 一律重问与先清洗提取的差别
@compare
一律重问::多付一次调用|旧毛病常重现|已算对内容也重来
先清洗提取::几乎零成本|只动包装不动内容|救不回再升级
:::

把「能不能读」这一关守住之后，读出来的东西形状对不对，是[结构层校验](./k017-structure-check.md)接着查的；要是清洗也救不回来，才轮到[自动纠正与重试上限](./k019-auto-repair.md)那种带具体错处的限次重来，再不行就走[果断降级与兜底返回](./k020-graceful-fallback.md)。语法层的正确姿态是「能救就救、救不了就干净上交」，绝不自己硬猜内容。

## 五、那如果清洗堆得很多、或者洗完就能用了呢

:::ask 那是不是把所有能想到的清洗都堆上去，一次洗到干净
:::

不是，规则越多越危险。每加一条，就多一分「把本来合法的内容改坏」的机会：单引号替换会伤到字符串里的撇号，只截第一对花括号会在嵌套对象处截断，全局替换某个词可能正好命中数据里的正常文字。清洗只该做确定、可逆、能说清边界的动作，而且每一步都要能单独验证。顺着再追一层：那怎么证明清洗没把数据改坏？办法很朴素——清洗前后把业务字段做个对比，包装随便动，字段一个都不能变；只要有一条断言发现字段被改了，就说明这条清洗规则越界了。这种「改动后配一组必须保留的事实做回归」的思路，在别处压缩历史时也用得上。

:::ask 那清洗完能解析了，是不是就可以直接用了
:::

还不能。能解析只过了第一关，字段齐不齐、类型对不对是结构层的事，值是否合法、编号是否真实存在是语义层的事。把「读得进来」当成「可以放心用」，是紧接着最容易踩的坑。再追一层：那清洗也救不回来的那些怎么办？这时候才该把「哪里不对」说清楚、交给上层限次重来，重来还不行就返回确定的兜底结果，绝不让调用挂在那里空转。追到最后你会发现，这一关的价值不在「洗得多干净」，而在「把该自己解决的廉价问题解决掉，把不该自己猜的问题清清楚楚交出去」。

## 六、一段能直接跑的清洗与提取器

下面这段只靠 Python 标准库。它本地构造一批带包装的脏输出，对比「直接解析」与「先清洗再解析」，并用一个确定性流程演示：能清洗救回的都不需要重问，只有真救不回的才上报。样本全是构造场景，不是对任何真实模型的统计。

```python
# 语法层校验：第一关只看「能不能解析」，失败优先清洗与提取，不立刻重问。
# 只用标准库，脏输出本地构造，不联网、不调用真实模型。

import json
import re

DIRTY = [
    '好的，以下是结果：{"item":"牛奶","qty":2,"urgent":false}',
    '```json\n{"item":"牛奶","qty":2,"urgent":false}\n```',
    '{"item":"牛奶","qty":2,"urgent":false,}',
    '{"item":"牛奶","qty":2,"urgent":false} 供参考',
    '   {"item":"牛奶","qty":2,"urgent":false}   ',
]


def direct_parse(raw):
    """最朴素的做法：直接解析，失败就抛。"""
    return json.loads(raw)


def clean_and_extract(raw):
    """按改动从小到大的顺序做确定性清洗，只动包装，不碰业务字段。"""
    text = raw.strip()                                  # ① 去首尾空白
    if "```" in text:                                   # ② 去代码块围栏
        parts = text.split("```")
        inner = parts[1] if len(parts) > 1 else text
        text = re.sub(r"^\s*json\s*", "", inner).strip()  # 去掉 json 语言标记
    # ③ 截取首个 { 到最后一个 } 之间，顺带剥掉前后解释
    start, end = text.find("{"), text.rfind("}")
    if start != -1 and end != -1 and end >= start:
        text = text[start:end + 1]
    # ④ 修掉右括号前多出的尾随逗号
    text = re.sub(r",\s*([}\]])", r"\1", text)
    return text


def syntax_pass(raw):
    """返回 (数据对象或 None, 是否需要交上层重问)。
    先试直接解析；失败只做清洗再试；仍失败才如实上报。"""
    try:
        return direct_parse(raw), False
    except (ValueError, TypeError):
        pass
    cleaned = clean_and_extract(raw)
    try:
        return json.loads(cleaned), False                # 清洗救回，不重问
    except (ValueError, TypeError):
        return None, True                                # 救不回，交给上层


if __name__ == '__main__':
    checks = []
    direct_ok, clean_ok, reask_count = 0, 0, 0
    for raw in DIRTY:
        try:
            direct_parse(raw)
            direct_ok += 1
        except (ValueError, TypeError):
            pass
        obj, need_reask = syntax_pass(raw)
        if obj is not None:
            clean_ok += 1
        if need_reask:
            reask_count += 1

    checks.append(("直接解析大面积失败", direct_ok < len(DIRTY)))
    checks.append(("清洗后全部可解析", clean_ok == len(DIRTY)))
    checks.append(("清洗救回不需要重问", reask_count == 0))

    # 关键：清洗只动包装，业务字段一个都不能变
    unchanged = all(
        syntax_pass(raw)[0] == {"item": "牛奶", "qty": 2, "urgent": False}
        for raw in DIRTY
    )
    checks.append(("清洗不动业务字段", unchanged))
    checks.append(("围栏被剥掉", "```" not in clean_and_extract(DIRTY[1])))

    clean_text = '{"item":"牛奶","qty":2,"urgent":false}'
    checks.append(("合法文本不被改写", clean_and_extract(clean_text) == clean_text))

    broken = '这里只有一句话，没有花括号，也没法解析'
    obj2, need2 = syntax_pass(broken)
    checks.append(("救不回才上报重问", obj2 is None and need2 is True))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `DIRTY` 是五条本地构造的回复，把解释前缀、代码块围栏、尾随逗号、后赘说明、首尾空白各摆一条；它们里面的 JSON 其实完全一样，正好用来验证「只动包装、不动数据」。
2. `clean_and_extract` 严格按改动从大到小的反面、也就是从小到大依次做：去空白、去围栏（顺手用标准库 `re` 的正则表达式剥掉 `json` 这个语言标记）、截取花括号之间那段、修尾随逗号。它不碰任何字段名和值。
3. `syntax_pass` 是本关的主流程：先直接解析，失败才清洗再试，两次都不成才返回「需要交给上层」。注意它自己从不发起重问，只把判断结果交出去。
4. 主函数先统计直接解析与清洗后各自能过几条、重问次数是多少；再用一条 `all(...)` 断言逐条确认清洗后的业务字段和预期完全一致，也就是包装随便动、数据不许变。
5. 后面几项分别验证围栏确实被剥掉、本来合法的文本不会被改写、以及真正救不回的那条被如实上报。七项断言跑完打印「通过 7/7 项」，任一项不成立就报错退出。

顺带一提，这段只解决「能不能读」；读出来的对象里字段齐不齐、类型对不对，是[结构层校验](./k017-structure-check.md)的活——它接在语法层后面，两者顺序不能颠倒：先能读，才谈得上查形状。

## 七、踩坑与边界

- **一失败就整轮重问**：现象是费用涨、旧毛病反复出现、已算对的内容被重算 → 原因是把包装问题当成了内容问题 → 怎么改：先做确定性清洗与提取，救不回再交上层。
- **清洗规则太贪心**：现象是本来合法的字符串被改坏，或嵌套对象被拦腰截断 → 原因是动作需要「猜」，越过语法层了 → 怎么改：只留确定、可逆、能单独验证的几条，并配字段对比断言。
- **截取只认第一对花括号**：现象是带嵌套的结果被截断 → 原因是把「最后一个右括号」写成了「第一个」 → 怎么改：从首个左括号取到最后一个右括号，并对嵌套另做验证。
- **拿默认值掩盖缺失**：现象是解析后字段没了也不报警，继续拿 0 往下算 → 原因是把「语法层放行」混成了「结构层兜底」 → 怎么改：缺失交给结构层明确判不合格，别在语法层悄悄补值。
- **清洗完就直接用**：现象是能解析的结果里字段类型不对、值离谱 → 原因是把「读得进来」当成「可以放心用」 → 怎么改：语法、结构、语义三层依次过，缺一层都不往下交。

还要说清一个边界：清洗能救的是「数据没坏、只是裹了层东西」的情况；要是内容本身残缺、字段被吞、值被改，清洗再花哨也救不回，硬猜只会把错误藏得更深。也别因为有了清洗就把提示词写得乱七八糟——脏输出越少，需要清洗和上报的次数就越少，两边是互相省事的关系，而不是谁替代谁。

## 九、三句话小结

语法层校验是输出契约的第一关，只判断回复能不能按 JSON 规则解析，失败时优先做清洗与提取，而不是立刻重问。
关键做法是按改动从小到大依次去包装、截取正文、修尾随逗号，并用字段对比断言证明清洗没动数据。
当内容本身残缺、或需要猜某个字段本该是什么时，就别在语法层硬撑，该把具体错处交给结构、语义乃至限次重来。

# 三类能力原语与渐进披露：说明别一次全塞进上下文

## 场景提问

你把手上能用的东西整理成一份说明：二十来个工具的完整参数、几份价目与规则文档、七八套话术模板，全贴进每轮输入里，图个「万一要用呢」。结果输入又长又贵，模型反而老选错工具，把只读的资料当成能改的动作，或者把模板里的占位符原样念了出来。你想删一些说明，又怕真要用时缺了参数细节。给多了出乱子，给少了不敢删，这个结怎么解？

## 破误解

**不是说明写得太少，是「一次性全给」把本轮根本用不到的东西也塞了进来**，还把性质完全不同的三类能力混成了一张平铺清单。

先把词说清。能力原语（capability primitive，按性质把对外能力分成的最小类别；白话讲像把货架分成「能动手的」「只读的资料」「现成话术」三格）在这里分三类：工具（tool，会执行动作、可能产生副作用的那一类，例如改地址）、资源（resource，只读的数据或文档，可能很长，例如价目表）、提示模板（prompt template，可复用的话术骨架，含若干占位符）。渐进披露（progressive disclosure，先给一份轻量目录，确定要用哪一条时再取完整说明；白话讲像先看菜单、点菜才上详细做法）是给这三类说明的发放方式。上下文窗口（context window，一次调用里能被看到的全部文字，额度有限，白话讲就是桌面大小）决定了「全塞」为什么不可行：桌面被无关材料占满，真正要用的那张纸反而被挤到看不见的地方。

## 生活类比

把这套机制想成一座「图书馆」：

- **大厅的目录卡片**只写书名、类别、一句话提要，随手就能翻完，这是轻量目录；
- **三排书架**按性质分区：动手操作的工具书、只供查阅的资料、可直接抄用的表格范文，这是三类原语；
- **书库里的正本**内容完整、可能很厚，管理员按你填的索书号取来，这是按需加载的完整说明；
- **阅览桌**只放当前真的在看的几本，这是上下文；
- **还书**看完就归架，桌上不堆旧书，这是用完即弃。

对应关系要点在「桌子大小有限」：把整座书库搬上阅览桌，看似什么都备齐了，实际桌上堆满无关卷册，找一本书要翻半天，还容易把范文当成可执行的规程。目录卡片只占一张，却能告诉你「有没有、属于哪排、大概讲什么」，足够支撑「本轮该取哪一本」的判断。另一个对应关系是分区：动手的书和只读的资料混放，读者会误以为翻到就能改；分成三排，性质一眼可辨，选错的机会就少得多。所以这套做法解决的不是「记得更多」，而是「让该出现的出现、不该出现的别占位置」。

## 层层追问

:::ask 那怎么判断「本轮需要哪几条」，总不能让模型把完整说明都读一遍再挑吧？
确实不能，那又绕回全量塞入了。判断必须只依赖目录：类别、名字、一句话摘要，必要时加几个稳定标签（例如「只读」「需审批」「涉及金额」）。这些字段要写得能支撑筛选——摘要若是「处理相关事务」这种含糊话，就判不出该不该取。轻量匹配可以由规则完成，例如按任务里的动作词找工具类、按涉及的实体找资源类；也可以先做一次只带目录的挑选，再对选中的少数几条取完整说明。关键约束是：挑选阶段看到的信息量必须远小于完整说明的总量，否则「按需」就名存实亡。代码里的 `catalog` 正是只返回名字、类别与摘要，且断言摘要都很短。
:::

:::ask 那如果挑错了，或者一次加载太多，会不会比全量塞入还糟？
有可能，所以要有两样东西兜着。一是上限：本轮允许加载几条、完整说明总长多少，超过就退回目录重新挑，不让「按需」变成「按心情全要」。二是记录：把本轮实际加载了哪些条目记下来，事后能复盘「为什么当时取了这条、是不是根本没用上」，再回头修摘要或标签。还有个更隐蔽的情形：加载进来的说明若不退出，几轮累积下来和全量塞入没差别，所以「用完即弃」要落实成一句明确的规则，比如每轮按当前任务重新组装上下文，而不是在旧上下文后面继续追加。追到第二层可以看出，渐进披露不是一次性的加载动作，而是一条「目录—挑选—加载—退出」的循环纪律；它和[框架六大件](./k075-framework-six.md)里「状态」那件要分开存，道理相同：临时进入的材料不该混进长期状态。
:::

## 可运行代码并逐行解释

下面用标准库把三类原语分格登记，并演示「先给目录、按需才加载完整说明」，复制即可运行。

```python
"""三类能力原语分开登记；能力说明按需加载而不是一次全塞进上下文。"""


class CapabilityHub:
    def __init__(self):
        self.tools = {}
        self.resources = {}
        self.templates = {}
        self.context = set()  # 当前真正进入上下文的完整说明

    def add(self, kind, name, summary, detail):
        table = {"tool": self.tools, "resource": self.resources,
                 "template": self.templates}[kind]
        table[name] = {"summary": summary, "detail": detail}

    def catalog(self):
        """渐进披露第一步：只给名字、类别和一句话摘要。"""
        out = []
        for kind, table in (("tool", self.tools), ("resource", self.resources),
                            ("template", self.templates)):
            for name, item in table.items():
                out.append((kind, name, item["summary"]))
        return out

    def load(self, kind, name):
        """第二步：真要用时，才把完整说明加入上下文。"""
        table = {"tool": self.tools, "resource": self.resources,
                 "template": self.templates}[kind]
        detail = table[name]["detail"]
        self.context.add(kind + ":" + name)
        return detail


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    hub = CapabilityHub()
    hub.add("tool", "查订单", "按编号查订单", "入参 编号:字符串；返回 状态与金额；只读")
    hub.add("tool", "改地址", "修改收货地址", "入参 编号与新址；需要人工审批")
    hub.add("resource", "价目表", "当前价格清单", "最新版价目，含全部条目，体积较大")
    hub.add("template", "催办函", "催办话术模板", "含称呼、缘由、时限三段的完整模板")

    cat = hub.catalog()
    ok(len(cat) == 4, "能力目录一次性列出全部条目")
    kinds = {c[0] for c in cat}
    ok(kinds == {"tool", "resource", "template"}, "三类原语分开登记，互不混淆")
    ok(len(hub.context) == 0, "初始上下文没有塞入任何完整说明")
    ok(all(len(s) <= 8 for _, _, s in cat), "目录里只有短摘要，不夹带长说明")

    d = hub.load("tool", "查订单")
    ok("只读" in d, "按需加载才拿到完整说明")
    ok("tool:查订单" in hub.context, "只把用到的能力放进上下文")
    ok("tool:改地址" not in hub.context, "没用到的工具说明仍不进上下文")
    ok("resource:价目表" not in hub.context, "大体积资源默认不占用上下文")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `CapabilityHub` 用三个独立字典分别装工具、资源、模板，而不是一张平铺大表。分区本身就是信息：调用方看到「这是资源」就知道它只读、可能很长，不必读完整说明才反应过来。
2. `self.context` 是一个集合，专门记录「此刻真正进入上下文的完整说明」。把它单独拎出来，才能验证「哪些进来了、哪些没进来」，而不是靠感觉说「应该没全塞」。
3. `add` 接收四样东西：类别、名字、摘要、完整说明。摘要与完整说明分开存，是渐进披露能成立的前提——若只存一份长文本，就无从只给目录。
4. `catalog` 遍历三格，每条只产出「类别、名字、摘要」三元组。注意它连 `detail` 的字段都不读，从机制上保证挑选阶段看不到长内容。
5. `load` 是第二步：按类别和名字取出完整说明，同时把 `类别:名字` 记进 `context`。加载与记录写在同一处，避免「用了却没记、事后查不出」。
6. 四条 `hub.add(...)` 是构造样例：两条工具（一条只读、一条需审批）、一条大体积资源、一条含占位符的模板。性质差异刻意做明显，方便断言验证「分开登记」。
7. `ok(all(len(s) <= 8 ...))` 把「摘要要短」变成可核对的约束。摘要一长，目录就退化成第二种全量塞入，这条断言是最便宜的防线。
8. 后面四条断言分别验证：只有用到的那条进了上下文、没用到的工具没进、大体积资源默认不占位置、加载确实拿到了完整说明。最后打印 `通过 8/8 项`。这些断言回答的都是同一个问题——「上下文里到底有什么」。

读完代码再看第一张图会发现，「目录」被单列成一类说明，其实它不算能力，而是能力的索引。把它与三类原语分开，正是[工具协议与标准化接入](./k078-tool-protocol.md)里「发现」那件事在这里的延续：先让调用方知道有什么，再决定取什么，两步不要合并。

## 踩坑与边界

- **摘要写得像说明**：现象 → 目录本身就长到读不完，按需加载省下的额度又被吃回去 → 原因 → 摘要里塞了入参、限制、例外 → 怎么改 → 摘要只回答「这是什么、什么时候用」，细节一律留给完整说明，并给长度设上限。
- **三类混成一张表**：现象 → 把只读价目当成能执行的动作，或把模板占位符原样输出 → 原因 → 类别没随条目传下去，调用方无从分辨性质 → 怎么改 → 每条都带类别标签，目录、加载、记录三处都保留它。
- **加载后不退出**：现象 → 前几轮还好，跑久了上下文又鼓起来 → 原因 → 每轮在旧上下文后面追加，没做重新组装 → 怎么改 → 每轮按当前任务重新组装，本轮用不到的条目不带入，落实「用完即弃」。
- **大资源默认进上下文**：现象 → 一份长文档每轮都占掉大半额度 → 原因 → 把「可能用到」当成「本轮要用」 → 怎么改 → 资源默认只给摘要，真需要时按标识取片段，配合[传输、会话与网关限流](./k080-transport-session.md)里对长内容的分块处理。
- **挑错了没记录**：现象 → 说不清某轮为什么加载了一堆没用上的说明 → 原因 → 没留加载轨迹 → 怎么改 → 记下每轮实际加载的条目，回头修摘要与标签，让下一轮挑得更准。

边界说清楚：能力只有三五条、完整说明加起来也没多长时，分层与按需加载都是多余动作，一次给全反而更省心，也少一层要维护的目录。它真正划算的场合是能力会持续增加、说明长短差别大、或者同一套能力要被多种任务复用。还有一点：渐进披露省的是上下文额度，不改善能力本身写得对不对——描述含糊、参数不合理，取不取都照样出错，那部分得回到[工具协议与标准化接入](./k078-tool-protocol.md)去修。另外，「用完即弃」不等于「记不住」：稳定事实该进记忆，临时说明只是本轮材料，两者别混为一谈，这一点可以顺着[起点说明](./00-start-here.md)的脉络往下对照。

## 三句话小结

三类能力原语与渐进披露，是把能力按工具、资源、提示模板分格登记，先给轻量目录、要用时才取完整说明。
关键做法是摘要与完整说明分开存、类别随条目传递、每轮重新组装并记下实际加载了什么。
当能力很少、说明总量本来就不长时，一次给全更省事，不必加目录与加载这层间接。

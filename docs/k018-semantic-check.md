# 语义层校验

## 场景提问

你给模型定了一份报销汇总的输出格式，语法层和结构层都过了：每个键都在、每个值类型都对、数组里每个元素也逐个验过，日志里干干净净零错误。可财务一核对就退回三笔：有一笔「结束日期」比「开始日期」还早两天；有一笔三项金额分明是 30、20、50，末尾的总额却写着 120；还有一笔状态标成「已完成」，完成时间却是空的，错误信息栏还留着一句报错。你回头翻校验代码，发现它确实一条规则都没违反——因为每一条规则都只在看「这一格装得下吗」，从没人问过「这几格摆在一起说得通吗」。单看全对、合起来荒唐，这种错误到底该由谁拦？

## 破误解

**不是校验漏了某个字段，是把「局部合规」当成了「整体可信」；语义错误恰恰是形状完全合法、却能算出荒唐结论的那种错。**

先把三层的分工摆齐。语法层答「这段文本能不能解析」，结构层答「字段齐不齐、类型对不对、嵌套形状对不对」，这两层在 [语法层校验](./k016-syntax-check.md) 和 [结构层校验](./k017-structure-check.md) 里已经讲透。语义层答的是第三个问题：这些值彼此之间、以及跟本次任务给定的参照数据之间，是否自洽、是否符合业务约束。它有三个和前两层很不一样的特点。第一，它是跨字段的：金额勾稽（「勾稽」是记账里的说法，白话就是几个数之间本该对得上的关系）要拿分项之和跟总额比，日期顺序要拿结束跟开始比，单独盯着任何一个字段都看不出问题。第二，它依赖上下文，也就是 context（白话：本次校验要用到的外部参照，随这次调用一起传进来的那一小包数据）：某个类别是否合法，得看本次允许的类别名单；某个负责人是否合规，得看本次的人员名单；这些名单不在输出里，光验输出本身永远判不了。第三，它依赖业务规则：标成「完成」就必须有完成时间且不能还挂着错误、折扣不能超过总额、比例合计不能越过 100，这些是「这家业务怎么算才对」，不是「JSON 该怎么写」。很多人试图把这类要求全塞进提示词，写成「请确保金额正确、日期合理」，可模型既不知道本次允许哪些类别，也不会稳定地自己做加法；指望它自查，等于让被检查的人自己填检查表。[性质断言](./k088-property-assertion.md) 里那句「把要求写成机器能逐条判定的性质」，正是这一层的落脚处：语义规则必须在你自己的代码里，用确定性的比较写成一条条能复现的断言。

## 生活类比

把它想成一张报销单交到会计手上。单据能读、每一栏都填了、金额栏写的是数字、日期栏写的是日期——这是语法层和结构层，相当于「单子格式没问题，收下了」。会计接下来做的才是语义层：把出差起止日期对一下，看结束是不是晚于开始；把车票、住宿、餐费三项加起来，看等不等于申请人填的总额；拿报销人姓名去本部门名单里查一下，看是不是本部门的人；再看看状态栏勾了「已结清」的，后面有没有附上打款时间、有没有还留着「待补发票」的备注。哪一步对不上，单子就得退回去，哪怕它每一栏都填得工工整整。

对应关系得落到具体物件上。「三项加起来等于总额」就是跨字段勾稽，判据不在某一格，而在几格之间；「本部门名单」就是本次给定的参照数据，它是校验时临时带进来的，不是单据自带的；「勾了已结清就得有打款时间」就是状态互斥，一个字段的取值会约束另一个字段该不该出现；而「起止日期谁先谁后」是时序规则，得把字符串还原成真正的日期才能比，不能只按字符顺序看。这个类比还点出一件最要紧的事：会计手里必须有那份名单。没有名单，他既不能说报销人合规，也不能说违规，只能把单子挂起来等名单送来——这正对应工程里「参照数据缺失时默认不放行」，而不是想当然地当作通过。另外，会计做加法和比日期靠的是算盘和日历，不是「感觉这数差不多」，这也说明了为什么语义层要用确定性的比较、而不是再问模型一次「你觉得对吗」。

## 自绘示意图

:::figure 三层收紧之后才轮到语义层
@flow
过了结构层|带入参照数据|跑跨字段规则|收集语义错误|通过或退回
:::

五格里「带入参照数据」是语义层独有的动作。语法层和结构层只需要拿到输出本身就能判，语义层不行：没有本次允许的名单，就没法判断一个值是不是越了界。把这一步画出来，是为了提醒别把参照数据当成可选配件。

:::figure 语义层常查的五类规则
@stack
跨字段勾稽::分项合计要等于总额，单件金额要等于数量乘单价
时序与顺序::结束时间不得早于开始，步骤不能倒着走
参照对齐::类别、编号、负责人要落在本次给定的名单里
状态互斥::标完成就必须有完成时间且不带错误，未完成则相反
取值合理::折扣不得超过总额，比例合计不得越界
:::

五类规则有个共同点：判据都落在「两个以上的量」或「量与外部名单」之间。这也解释了为什么结构层那份逐字段的约定再细，也覆盖不到它们——它描述的是每一个格子，不是格子之间的关系。

:::figure 只验形状与验到说得通的差别
@compare
只验到结构层::每格都合规|合起来荒唐也放行|错误到业务里才爆
加语义层::跨字段当场对账|越出名单能拦截|错误定位到规则
:::

左边那条路的危险在于「零错误」的假象：日志里一片干净，错误却被推迟到财务、结算、下游统计这些真正产生后果的地方才爆出来。右边把同样的错误提前到刚拿到输出的一刻，而且能说清是违反了哪条规则。

## 层层追问

:::ask 那如果把这些规则也写进结构约定里，是不是就不用单独一层了？
:::

能写进去的只是一部分，而且恰恰是最不像「语义」的那部分。像「状态只能是这三个词之一」「数值不得小于零」「数组至少有一个元素」，这些确实是单字段或单集合能判定的，用 [JSON Schema 约束](./k015-json-schema.md) 那类结构约定表达很自然，严格说它们处在结构层与语义层的交界。真正麻烦的是三类：跨字段比较，比如「结束 ≥ 开始」「分项和 = 总额」，标准结构约定要么不支持、要么得绕很别扭的写法；依赖外部集合，比如「类别在本次允许名单里」，名单是运行时才有的，没法预先写死在静态约定里；依赖业务状态，比如「这个编号对应的单据当前是否已作废」，那得查本次带进来的状态快照。这三类硬塞进结构约定，通常会退化成「写一堆谁也读不懂的表达式」或者「干脆放弃」。所以务实的划分是：形状类规则交给结构约定，关系类规则用代码里的确定性断言补齐，两边共用同一份错误清单格式，别让它们各说各话。还有个容易踩的点：把「参数长得对」当成「业务上合法」，[参数有效不等于业务合法](./k034-param-validity.md) 讲的就是这道坎，语义层很多时候正是在补这一步。至于规则该怎么起名字、怎么组织成可复用的集合，可以对照 [性质断言](./k088-property-assertion.md)，那里强调的「一条规则只判一个可证伪的性质」在这里同样适用。

:::ask 那如果语义校验要查名单、查状态，是不是就得联网、就会拖慢还不可靠？
:::

不必，而且恰恰不该让校验器自己跑去取数据。稳妥的做法是「把参照数据随请求一起带进来」：调用方在发起这次任务时，就把允许类别名单、人员名单、需要对齐的状态快照整理成一小包 context，连同模型输出一起交给校验函数；校验器只读这包传入的数据，不读文件、不查远端、不碰网络。这么做有三个好处。其一，校验变成纯函数，同样的输入永远得到同样的结论，规则可以拿固定用例集反复验，这部分和 [评测用例集怎么构造](./k086-eval-dataset.md) 里「用例要可复现」是同一套要求。其二，校验不会引入新的失败源：网络抖动、权限失效、对方超时，都不会让「这次输出合不合规」变得忽是忽否。其三，边界清楚：参照缺失时就明确报一条「缺少类别参照，无法判定」，并按「默认不放行」处理，而不是悄悄当成通过——这正是下面演示代码里的一条断言。把「取数」和「判定」拆成两件事之后，语义层就能像结构层一样离线、确定性、可复现；真正需要联网取数的动作留在调用方，取回来之后仍以入参形式交给校验器。若某条规则无论如何都拿不到参照，那也别硬判「合规」，该走的是 [果断降级与兜底返回](./k020-graceful-fallback.md) 那条路：明说「这项没能核实」，把不确定性显式交出去，而不是编一个看起来合理的值。

## 可运行代码与逐行解释

下面这段只用 Python 标准库的 `datetime.date`，把一份已经通过结构层、键与类型都合规的报销汇总，连同本次给定的参照数据一起做语义核对。金额一律用整数「分」表示，避开十进制小数在二进制浮点里的尾差；日期用 `date.fromisoformat` 还原成真正的日期对象再比较。所有规则都返回带说明的错误字符串，参照缺失时默认不放行。复制到任意装有 Python 的机器上可直接运行，不需要第三方包、账号或网络。

```python
from datetime import date


def base():
    """构造一份形状合规、语义也自洽的基准报告，供各条规则改动一处来验证。"""
    return {
        "start_date": "2026-03-08",
        "end_date": "2026-03-10",
        "category": "差旅",
        "owner": "A",
        "status": "done",
        "finished_at": "2026-03-10 18:00",
        "error": "",
        "discount": 10,
        "total": 100,
        "items": [
            {"name": "车票", "qty": 2, "unit_price": 30, "amount": 60},
            {"name": "住宿", "qty": 1, "unit_price": 40, "amount": 40},
        ],
    }


CONTEXT = {
    "allowed_categories": ["差旅", "办公"],
    "staff": ["A", "B"],
}


def check_semantics(report, context):
    """跨字段与参照数据核对；report 假定已过结构层，键与类型都合规。"""
    errors = []

    parts = sum(item["amount"] for item in report["items"])
    if parts != report["total"]:
        errors.append("金额勾稽不符：分项合计 %d，总额 %d" % (parts, report["total"]))

    try:
        start = date.fromisoformat(report["start_date"])
        end = date.fromisoformat(report["end_date"])
        if end < start:
            errors.append("日期顺序错误：结束早于开始")
    except ValueError:
        errors.append("日期格式不合规，应由结构层先卡住")

    for i, item in enumerate(report["items"]):
        if item["qty"] * item["unit_price"] != item["amount"]:
            errors.append("第 %d 行金额与数量单价不符" % (i + 1))

    allowed = context.get("allowed_categories")
    if allowed is None:
        errors.append("缺少类别参照，无法判定")
    elif report["category"] not in allowed:
        errors.append("类别不在允许集合：" + report["category"])

    staff = context.get("staff")
    if staff is None:
        errors.append("缺少人员参照，无法判定")
    elif report["owner"] not in staff:
        errors.append("负责人不在名单：" + report["owner"])

    if report["status"] == "done":
        if not report.get("finished_at"):
            errors.append("标记完成却缺少完成时间")
        if report.get("error"):
            errors.append("标记完成却仍带着错误信息")
    elif report.get("finished_at"):
        errors.append("未完成却填了完成时间")

    if report["discount"] > report["total"]:
        errors.append("折扣大于总额")

    return errors


def main():
    good = base()
    sum_bad = base()
    sum_bad["total"] = 90
    date_bad = base()
    date_bad["end_date"] = "2026-03-01"
    row_bad = base()
    row_bad["items"][0]["amount"] = 50
    cat_bad = base()
    cat_bad["category"] = "招待"
    owner_bad = base()
    owner_bad["owner"] = "C"
    done_bad = base()
    done_bad["finished_at"] = ""
    pending_bad = base()
    pending_bad["status"] = "pending"
    discount_bad = base()
    discount_bad["discount"] = 200

    checks = [
        ("合法报告零语义错误", check_semantics(good, CONTEXT) == []),
        ("分项对不上总额被抓", any("金额勾稽不符" in x for x in check_semantics(sum_bad, CONTEXT))),
        ("时间倒挂被抓", any("日期顺序错误" in x for x in check_semantics(date_bad, CONTEXT))),
        ("单行数量单价不符被抓", any("第 1 行" in x for x in check_semantics(row_bad, CONTEXT))),
        ("类别越出参照被抓", any("类别不在允许集合" in x for x in check_semantics(cat_bad, CONTEXT))),
        ("负责人越出名单被抓", any("负责人不在名单" in x for x in check_semantics(owner_bad, CONTEXT))),
        ("完成却缺完成时间被抓", any("缺少完成时间" in x for x in check_semantics(done_bad, CONTEXT))),
        ("未完成却填完成时间被抓", any("未完成却填了完成时间" in x for x in check_semantics(pending_bad, CONTEXT))),
        ("折扣超过总额被抓", any("折扣大于总额" in x for x in check_semantics(discount_bad, CONTEXT))),
        ("参照缺失默认不放行", len(check_semantics(base(), {})) == 2),
        ("金额用整数精确勾稽", isinstance(good["total"], int)
         and sum(i["amount"] for i in good["items"]) == good["total"]),
    ]
    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `base` 造一份「形状合规、语义也自洽」的基准数据：分项 60 加 40 恰好等于总额 100，起止日期顺序正常，类别与负责人都在名单内，状态为完成且填了完成时间、没有错误信息，折扣 10 小于总额。后面每个坏样例都只改动其中一处，好让「哪条规则被触发」可以逐条手算。
2. `CONTEXT` 是本次给定的参照数据，一个普通字典，装着允许类别与人员名单。它不来自文件、不来自网络，纯粹随调用传入——这就是追问里「把取数和判定拆开」的落点，也保证整段代码离线可跑。
3. `check_semantics` 开头先做金额勾稽：用 `sum` 把各分项金额加起来跟总额比。金额全部是整数分，所以这里是精确相等比较，不会出现十进制小数那种尾差；若把 0.1 与 0.2 这类小数直接相加再比，就可能得到一个「明明该相等却不相等」的结果，这正是踩坑里要单列的一条。
4. 日期部分用 `date.fromisoformat` 把字符串还原成日期对象，再用 `<` 比先后，而不是按字符串字典序比。外面套 `try/except ValueError`，把「格式本身不合规」变成一条明确的错误并顺带说明它该由结构层先卡住，避免语义层因为一个格式问题直接抛异常中断。
5. 接着逐行核对「数量 × 单价 = 单件金额」，这是另一条跨字段规则，只是发生在数组元素内部。`enumerate` 带出行号，错误里写「第 1 行」，回传给模型或记进日志时都能直接定位。
6. 参照对齐分两段：先取 `allowed_categories`，取不到就报「缺少类别参照，无法判定」，取到了再判断类别在不在集合里；人员名单同理。注意这里的分支是「缺失即报错」而不是「缺失即跳过」，也就是默认不放行。
7. 状态互斥用一个 `if/elif` 表达：标成完成，就必须有完成时间、且不能还挂着错误信息；没标完成，就不该出现完成时间。这类「一个字段的取值约束另一个字段该不该存在」的规则，是逐字段的结构约定最难表达、而语义层最擅长的一类。
8. 最后一条是取值合理性：折扣不得超过总额。函数返回的是错误字符串列表，和 [结构层校验](./k017-structure-check.md) 那份带路径的清单可以拼成同一份诊断，供 [自动纠正与重试上限](./k019-auto-repair.md) 里的下一轮使用；它「可组合」比它「多严格」更要紧。
9. `main` 里九份样例各改动一处，覆盖五类规则；断言只核对「该不该被抓」和「抓到的是不是这条规则」，外加「参照缺失时报两条」与「整数勾稽精确」两个性质。结尾统计通过项数并 `assert` 全部成立，任何一条规则被改坏都会以非零状态退出。

有一处要如实说明：这里的数据与名单都是手工构造的样例，用普通字典代替了业务系统里的真实单据和名单，全是为了让语义规则不联网、不装第三方包就能独立跑通并手工核对。它演示的是「跨字段、依赖参照、状态互斥」这三类判定怎么写，不是任何具体财务系统的实现。

## 踩坑与边界

- **用浮点小数做金额勾稽**：现象是 0.1 加 0.2 跟 0.3 比不相等，明明对得上的账被判成不符 → 原因是十进制小数在二进制浮点里存不精确，误差会累积 → 金额一律换算成整数最小单位（如分）再比较，或改用标准库里按十进制运算的类型。
- **按字符串比日期**：现象是把「2026-3-8」和「2026-03-10」当字符串比，得出荒唐的先后，换个写法结论就变 → 原因是字典序不等于时间序，且不补零的格式本身就不稳定 → 结构层先用固定格式（ISO 8601，国际标准化组织订的日期写法，形如「年-月-日」并补零）卡住格式，语义层还原成日期对象再比先后。
- **把语义规则全塞进提示词让模型自查**：现象是提示词写了「请确保金额正确」，模型照样算错且每次错得不一样 → 原因是模型既拿不到本次参照名单，也不保证稳定做算术 → 规则写进自己的代码，用确定性比较逐条判定。
- **校验器自己联网取参照**：现象是网络一抖，同一份输出一会儿判合规、一会儿判不合规，还多出一类超时故障 → 原因是把「取数」和「判定」揉在了一起 → 参照数据由调用方整理好随请求传入，校验器只读入参，成为纯函数。
- **参照缺失时默认放行**：现象是名单没传进来，校验一条错都没报，越界的类别就这么进了下游 → 原因是把「无法判定」错当成「判定通过」 → 缺参照就明确报一条错误并按不放行处理，或走显式降级把「未核实」标出来。

还要划清两道边界。一是语义层不该重复结构层的活：键在不在、类型对不对、格式合不合，交给前两层，语义层假定拿到的是形状合规的数据，专管「关系」与「业务」；把日期格式塞进语义层、把金额勾稽塞进结构约定，都会让两边的规则越来越难维护。二是别把语义规则定得比业务还细、还僵：把「允许类别」写死在校验器里，换个部门就得改代码；把「完成时间必须当天」当成死规矩，跨时区或跨天结算的正常单据会被误杀，反而推高重试次数，这与 [自动纠正与重试上限](./k019-auto-repair.md) 里「先分清什么值得重试」相呼应。校验的目标不是让返回零错误变得好看，而是「凡是放行的，都能说清它按哪几条规则被判为可信」。三层合起来看，[语法层校验](./k016-syntax-check.md) 保证读得开、[结构层校验](./k017-structure-check.md) 保证装得下、本篇保证说得通，任何一层被跳过，后面那句「输出没问题」都站不住。

## 三句话小结

语义层校验是三层校验的最后一道，专门核对跨字段勾稽、时序先后、与外部参照的对齐、状态互斥和取值合理性，把「装得下」推进到「说得通」。

关键做法是让规则跑在自己的代码里用确定性比较逐条判定、把参照数据随请求一起带进来保持校验是纯函数、并在缺参照时按不放行处理。

当输出只是形状固定的展示数据、根本没有跨字段关系可查时，不必硬加语义规则；而当一次判断需要依赖本次才有的名单或状态，却拿不到这些参照时，也不该硬判合规，该明说「未核实」。

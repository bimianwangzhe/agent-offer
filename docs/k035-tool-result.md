# 工具返回格式设计：让模型看得懂、改得动

## 场景提问

用户问「订单 A-99 到哪了」，你的查询工具查不到这个单号，却在异常处理里顺手 `return {}`。下一轮模型拿着这个空对象，客客气气地编了一句「您的订单已发货，预计明天送达」——查无此单被它补成了一个自信的假答案。另一次工具超时，你把一整段原始堆栈回灌进上下文，几百行报错把前面用户刚说的约束全挤到了后面，模型开始胡乱调别的工具。你去查问题，发现每次失败返回的东西都不一样：有时是空对象，有时是一句「执行失败」，有时是一大串 traceback，模型根本没法据此判断下一步该做什么。

## 破误解

**不是模型爱编造，是你回给它的结果里没有任何「失败」这个事实——空结果在它眼里和「成功但没数据」长得一模一样。**

工具返回不是给运维看的调试日志，也不是给人看的原始行集，它是喂给模型下一轮决策的输入。这句话决定了返回格式的全部要求：它必须能被模型判定「成功还是失败」，失败时必须带清楚原因和可操作的建议，还要尽量短、不把无关噪声塞进本就有限的上下文。最危险的不是返回报错，而是「沉默的失败」——`null`、`{}`、空字符串、或者被 `catch` 之后随手回的一个空对象。模型看到一片空白，又天生被训练成要接话，就会基于空白把后续结论编出来。真正稳的做法是永远回一个固定形状：`{success, data}` 或 `{success, error, code, retry_hint}`，让模型能确定地分出「重试 / 换工具 / 改参数 / 放弃」四条路。前面 [参数有效不等于业务合法](./k034-param-validity.md) 讲的是执行前怎么拦，这一篇讲拦下之后、以及成功之后，该把什么交回给模型。

## 生活类比

把它想成化验室回报告单。医生（模型）不进实验室，只能读那张纸决定下一步。最糟的回执是一张白纸：医生既不知道「没做成」，也不知道「做成了但指标全阴」，只能凭经验猜——这就是空结果诱发编造。稍好一点是直接把仪器打印的三百行原始日志甩过去：里面全是时间戳和内部编号，医生得自己在噪声里翻那一行关键值，还容易把上一份报告的残留当成这次的。规范的回执应该长这样：顶部一行「本次检测：成功」或「本次检测：未成功」，成功就给整理好的几项指标加单位，未成功就写「样本量不足」，再补一句「建议重新采样后复查」。

对应关系很清楚：那行「成功 / 未成功」就是 `success` 布尔字段；整理好的指标就是 `data` 摘要；「样本量不足」就是给模型看的错误原因 `error`；「建议重新采样」就是 `retry_hint`（可操作建议，告诉模型下一步能做什么）；三百行原始日志就是不该整段回灌的原始返回。这里有个细节值得停一下：回执是给医生看的，所以要用医生能据以行动的语言，而不是仪器自己的语言。工具报错也一样，「城市名不正确，支持列表：北京、上海」能让模型一次改对，而一个 `500` 状态码或一段堆栈不能。至于原始行集为什么该在应用侧先加工成「共 3 条，平均 22 度」这类摘要，以及结果太大时怎么裁剪，留给 [超大工具结果裁剪与二级工具](./k138-large-result.md) 专门处理。

## 自绘示意图

:::figure 一份合格返回该有的四个部件
@stack
判定标志::成功还是失败，用一个固定字段说死，不让模型去猜
数据摘要::成功时给加工过的紧凑结果，不回原始行集
错误原因::失败时点明哪个字段或哪种条件不满足
可操作建议::告诉模型能重试、能改参数、还是该转人工或换工具
:::

四行合起来定义一个固定形状。哪怕失败，也照样把这四个位置填齐——尤其是「判定标志」绝不能因为出错就省略，省略就等于退回白纸。

:::figure 结果从工具回到下一轮的顺序
@flow
工具产出原始结果|宿主加工成固定形状|判定成功或失败|附原因与建议|回填进下一轮输入
:::

第二格是关键：加工发生在宿主，不是让工具把内部对象直接丢出去。固定形状由宿主统一封装，模型每轮看到的格式才一致。

:::figure 沉默失败与结构化错误
@compare
回空对象或 null::模型分不清失败|基于空白编造|排查无迹可循
回结构化错误::明确标出失败|带原因与建议|一次就能改对
:::

左列是白纸，右列是规范回执。差别不在模型能力，而在你有没有把「这次没做成」这个事实写进它读得到的输入里。

## 层层追问

:::ask 那把失败原因写得越详细越好，直接把整段堆栈回灌是不是最省事？
:::

恰恰相反。堆栈里绝大部分是内部路径、行号、框架调用链，对「下一步该做什么」毫无帮助，却会实打实占掉上下文额度，把用户前面说的约束和本轮目标挤到不被注意的位置；更糟的是，长串报错里那些看起来像指令的片段，还可能诱发模型去调一些并不存在的工具。正确做法是在宿主里做一次翻译：把异常归类成一个简短的 `code`（比如 `INVALID_CITY`、`UPSTREAM_TIMEOUT`、`PERMISSION_DENIED`），配一句人能读懂的 `error`，再加一条 `retry_hint`。这就要追到第二层：不同失败该给不同的建议，而不是所有异常都映射成同一句「工具执行失败」。参数格式错 → 建议改哪个字段；临时超时 → 建议稍后重试并给等待时间；权限不足 → 明确说不可重试、需要授权；高风险动作 → 暂停转人工。模型只有拿到「哪类错 + 能做什么」，才能选对那条路；这一层分类的细化，正是 [工具失败分类与重试策略](./k040-tool-failure.md) 要展开的。

:::ask 那成功的时候，把数据库原始行集整个回给模型不是信息最全吗？
:::

信息全不等于有用，还可能有害。原始行集往往带着内部字段、重复值、无关注释，体积大、噪声多。两件事会同时发生：一是上下文被撑大、成本与延迟上升；二是关键值被埋在一堆字段里，模型反而更容易漏读。更稳的是在宿主里按本轮目标加工：用户问平均温度，就回「共 3 条，平均 22 度」；用户问有没有某条记录，就回「存在，取回 1 条」并给句柄，需要详情时再用二级工具按标识取。再往深一层，如果失败要触发重试，那么「改参数后重试」必须带来实质不同的新参数——把上一次的调用原样复制一遍，只会得到同样的错误，白烧一轮额度。所以结构化返回里最好连「上次用了什么参数、错在哪个字段」都带上，让模型有依据改出一份不一样的。这类「结果也要被设计」的意识，和 [超大工具结果裁剪与二级工具](./k138-large-result.md) 是同一条思路的两端：小了要清楚，大了要收敛。

## 可运行代码与逐行解释

下面这段程序只用 Python 标准库，用一个本地假工具演示两种返回：结构化错误能让模型一次改对参数，空结果则诱发编造；并验证固定形状、原因与建议都在。复制到任意装了 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json

CITIES = {"北京": 22, "上海": 25, "广州": 28}


def wrap_ok(data):
    """宿主统一封装的成功形状。"""
    return {"success": True, "data": data, "error": None, "retry_hint": None}


def wrap_error(code, error, retry_hint):
    """宿主统一封装的失败形状，四个位置照样填满。"""
    return {"success": False, "data": None, "code": code, "error": error,
            "retry_hint": retry_hint}


def weather_tool(args):
    """假工具：城市存在就给摘要，不存在就回结构化错误。"""
    city = args.get("city")
    if city not in CITIES:
        supported = "、".join(sorted(CITIES))
        return wrap_error("INVALID_CITY", "城市名 " + str(city) + " 不被支持",
                          "改用支持列表里的城市：" + supported)
    return wrap_ok({"city": city, "temp": CITIES[city], "unit": "celsius"})


def empty_tool(args):
    """对照组：沉默的失败，回一个空对象。"""
    return {}


def fake_model_decide(result):
    """假模型下一轮决策：只依据返回里能读到的字段。"""
    if result.get("success") is True:
        return "answer", result["data"]
    if result.get("success") is False and result.get("retry_hint"):
        # 有原因有建议 → 按建议改参数重试
        return "retry", result["retry_hint"]
    # 读不到任何失败标志 → 基于空白编一个答案
    return "fabricate", "您的查询已成功，结果为默认值"


def main():
    checks = []
    ok = weather_tool({"city": "北京"})
    checks.append(("成功返回有 success=True", ok["success"] is True))
    checks.append(("成功返回带紧凑 data", ok["data"]["temp"] == 22))
    checks.append(("成功形状四个字段齐全", set(["success", "data", "error", "retry_hint"]) <= set(ok)))

    bad = weather_tool({"city": "火星"})
    checks.append(("失败明确标出 success=False", bad["success"] is False))
    checks.append(("失败带错误码", bad["code"] == "INVALID_CITY"))
    checks.append(("失败原因点名了城市", "火星" in bad["error"]))
    checks.append(("失败带可操作建议", "北京" in bad["retry_hint"]))

    action, payload = fake_model_decide(bad)
    checks.append(("结构化错误让模型选择改参重试", action == "retry"))

    silent = empty_tool({"city": "火星"})
    checks.append(("空对象里没有失败标志", "success" not in silent))
    action2, payload2 = fake_model_decide(silent)
    checks.append(("空结果诱发模型编造答案", action2 == "fabricate"))

    # 改参数后确实带来不同输入，重试才有效
    fixed = weather_tool({"city": "上海"})
    checks.append(("按建议改参后成功", fixed["success"] is True))
    checks.append(("成功结果可被序列化成稳定文本",
                   json.dumps(fixed, ensure_ascii=False, sort_keys=True).startswith("{")))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `CITIES` 是假工具背后的本地数据，模拟「城市名不被支持」这类可复现的失败条件，不联网、不查库。
2. `wrap_ok` 与 `wrap_error` 是宿主里两个统一封装函数，成功和失败都填齐 `success / data / error / retry_hint` 四个位置。让封装只在一处发生，模型每轮看到的形状才不会随工具变来变去。
3. `weather_tool` 命中城市时回的是加工过的摘要（城市、温度、单位），不是把 `CITIES` 整个字典丢出去；未命中时回一个带 `code`、`error`、`retry_hint` 的结构化错误，建议里还列出了支持的城市。
4. `empty_tool` 是对照组，只回 `{}`。它存在的意义是把「沉默的失败」单独摆出来，让读者看到它的后果。
5. `fake_model_decide` 用一个确定性的分支模拟模型下一轮：`success=True` 就作答，`success=False` 且有建议就改参重试，两样都读不到就「编一个默认答案」。真实模型复杂得多，但用来演示「返回里有没有失败这个事实」足够了。
6. 前半段断言确认成功形状四字段齐全、数据紧凑；后半段确认失败明确标 `success=False`、带错误码、原因点名了城市、建议可操作。关键一条是：结构化错误让假模型选了 `retry`，而空对象让它选了 `fabricate`——同一场失败，只因返回写法不同，走向了编造。
7. 最后验证「按建议把城市改成上海后成功」以及结果能被 `json.dumps` 序列化成稳定文本（JSON，JavaScript Object Notation，纯文本数据格式），`sort_keys=True` 让输出顺序固定，便于比对与落日志。
8. 结尾逐行打印并汇总「通过 N/N 项」，`assert` 兜底。跑一遍能亲眼看到：把失败写清楚，模型就改得动；留一张白纸，它就自己把故事补圆。

## 踩坑与边界

- **沉默的失败**：现象是查不到数据时模型反而给出自信答案 → 原因是 `catch` 后回 `{}` 或 `null`，模型读不到失败标志 → 永远回固定形状，失败也明确写 `success=False` 加原因。
- **把整段堆栈回灌**：现象是上下文被撑大、模型开始乱调工具 → 原因是原始报错噪声多、还夹着像指令的片段 → 宿主翻译成简短 `code` + 一句 `error` + 一条 `retry_hint`。
- **所有异常映射成同一句话**：现象是权限不足被当成临时错误反复重试 → 原因是错误没分类、没给差异化建议 → 按可重试 / 改参数 / 不可重试 / 需人工分类，各配对应提示，见 [工具失败分类与重试策略](./k040-tool-failure.md)。
- **成功也回原始行集**：现象是关键值被埋在大量字段里、成本还涨 → 原因是没在应用侧加工 → 按本轮目标给紧凑摘要，详情用二级工具按需取，见 [超大工具结果裁剪与二级工具](./k138-large-result.md)。
- **改参重试却复制了上一次调用**：现象是反复得到同一个错误、白烧额度 → 原因是建议里没带上「上次参数错在哪」 → 错误里点名字段与实际值，逼出一份实质不同的新参数。

还要留意一处边界：本文谈的是「单个工具的返回形状」，不含「一轮里并行发起多个调用时，结果该按哪个标识回填」——那属于 [tool_call_id 配对与并行调用](./k136-tool-call-id.md) 的范围；也不含「返回里夹带的外部内容可能反过来驱动动作」，那是把不可信数据挡在决策之外的另一条线，可结合 [参数有效不等于业务合法](./k034-param-validity.md) 一起看。返回写得再规范，也替代不了执行前的几道关。整体脉络回到 [从这里开始](./00-start-here.md)。

## 三句话小结

工具返回格式设计，是把工具结果加工成结构化、可判定、不冗长的固定形状，成功给紧凑摘要，失败给原因、错误码与可操作建议。

关键做法是在宿主里统一封装成功与失败两种形状、把异常翻译成模型能据以行动的语言、并让「改参数重试」确实带来不同的新参数。

当结果只在程序内部流转、根本不回灌给模型时，不必讲究这套形状；但只要它要成为下一轮的输入，尤其涉及失败与重试，就绝不能回空对象或整段原始噪声。

# 实体摘要与画像更新：把分散事实收敛成一份可更新的记录

## 场景：同一个人的三句话，取回时互相打架

你翻记忆库，关于同一个人散着好几条：上周记了「老王偏好导出成 PDF」，这周又记了「老王要带页码」，还有一条更早的「老王说这次先给纯文本」。用户问「给老王整理一份材料用什么格式」，助手这次抽到「纯文本」，下次抽到「带页码的 PDF」，两次答案对不上。更离谱的是，你把「小李偏好纯文本」也存着，某次召回时把称呼和格式拼错了对象，回了一句「老王偏好纯文本」。每条记录单看都没错，凑在一起却谁也说不清哪条算数。

## 先破一个最常见的误解

**不是记得少，是没有把「关于同一个对象的分散事实」收敛成一份可更新的东西。** 先解释两个词：「实体」就是能被反复提到的一个对象，可能是一个人、一份文档、一台设备，只要系统需要持续记住关于它的事，它就算一个实体；「画像」或「实体摘要」是关于这个对象的一份紧凑字段表，比如「称呼」「输出格式」「所在时区」各占一格。逐条散存看起来最全，实际有两个硬伤：同一个字段会被写好几遍，取回时不知道该以哪条为准；不同对象之间没有明确边界，稍不留神就把别人的字段串过来。合并成画像之后，每个实体只有一份记录，同一字段后写更新、不堆叠，取回即用，不用临场拼。注意「可更新」三个字是关键——画像不是一份写完就封存的描述，而是一份能随新观察改字段、又始终只保留一行的活动记录。

## 用生活里的事打个比方：一人一本的病历

医院里每个病人只有一本病历，按一个稳定的编号归档。每次看诊，医生不另开一本，而是往这本里加一行或改某一格：这次补了「过敏史」，下次把「常用药」换成新开的那种。不同病人各有一本，柜子按编号隔开，绝不会把甲的化验单夹进乙的本子。对应关系逐条对一遍：病人就是实体，编号就是实体标识；那本病历就是画像；每一格（过敏史、常用药）就是结构化字段；「把常用药换成新的」就是同字段更新而非追加；按编号分柜就是不同实体彼此隔离。为什么不能每次看诊都写张散纸丢进抽屉？找的时候得把十几张纸拼起来，还容易把别人的那张夹进来，更没法一眼看出「现在到底对什么药过敏」。一本病历的价值，恰恰在于它把散在各处的事实收敛成一份当下有效的记录。

## 画出来看

先看一条新观察进来之后发生了什么，留意「按实体归拢」这一步发生在更新之前——先认出这说的是谁，才谈得上改哪一格。

:::figure 一条观察收敛成画像的过程
@flow
分散观察|按实体归拢|同字段更新|合并成一份|按标识取回
:::

「同字段更新」是这张图最该留意的一格：新观察写到「输出格式」这一格时，是把原来那格换掉，不是在底下再贴一张。再看它和逐条散存的差别。

:::figure 两种存法的差别
@compare
逐条散存::同字段反复堆|取回要临场拼|容易串对象
合并画像::同字段只一条|取回即用|按标识隔离
:::

两行对照的其实是「取回那一刻谁省心」。散存把判断成本推给了每次取回：要临场决定哪条算数、会不会拼错对象；画像把这份成本提前付掉了，代价是写入时得多做一步归拢与更新。

## 再往下追两层

:::ask 追问一
那同一格后写的那条，就一定比先写的那条对吗？
:::

不一定，这里得把两件事分开。「可更新」说的是结构上同字段只留一行、能被改，并不等于「无条件相信最新一条」。用户随口一句「这次先给我纯文本」，和从一份长期设置里读出来的稳定偏好，可信程度并不一样；一条带来源和时间的正式观察，也不该被一句闲聊顶掉。真遇到新旧打架，正确做法是保留版本、按来源权威级别与时间戳裁决，而不是简单覆盖，见[冲突消解与版本](./k071-conflict-resolution.md)。本篇演示的是「同一主题只留一条、可以更新」这个结构，裁决规则是另一层的事——结构先立住，规则才有地方挂。

:::ask 追问二
那干脆让模型每次读完所有历史，重新生成一份画像，不是更省事？
:::

不省事，还更危险。全量重生成有两个毛病：一是同样一批历史，每次生成出的措辞和字段都可能不同，画像就不稳定了；二是模型很容易把一次偶发事件抬成长期字段，把「这次先给纯文本」写成「该用户偏好纯文本」，随后一路沿用。稳妥的做法是增量合并：新观察进来，先由规则判定够不够格、说的是哪个实体，够格才合并到对应那一格，见[写入判定：什么时候该记](./k070-write-decision.md)。这样每次改动都有据可查，也容易定位是哪次观察把字段改坏了。合并出来的紧凑字段，落在[工作 / 情景 / 语义三层记忆](./k066-memory-types.md)的语义层；取回时按什么顺序摆、限几条，见[召回排序与相关性](./k072-memory-recall.md)；改错了要能撤，见[遗忘、过期与 TTL](./k073-forgetting.md)。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，把三次分散观察合并成同一个对象的一份画像，并验证另一个对象彼此隔离。复制成 `.py` 直接运行会打印画像内容与通过项。

```python
from dataclasses import dataclass, field


@dataclass
class Profile:
    entity_id: str
    fields: dict = field(default_factory=dict)

    def merge(self, patch: dict):
        for key, value in patch.items():
            # 同名字段以最新观察覆盖，并累计合并了多少条
            self.fields[key] = value
            self.fields.setdefault("_已合并条数", 0)
            self.fields["_已合并条数"] += 1


class ProfileBook:
    def __init__(self):
        self.book = {}

    def observe(self, entity_id: str, patch: dict):
        p = self.book.setdefault(entity_id, Profile(entity_id))
        p.merge(patch)
        return p


if __name__ == '__main__':
    book = ProfileBook()
    # 三次分散观察，都指向同一个对象 E1
    book.observe("E1", {"称呼": "老王"})
    book.observe("E1", {"输出格式": "PDF"})
    p1 = book.observe("E1", {"输出格式": "PDF 带页码"})
    # 另一个对象 E2 单独成册
    book.observe("E2", {"称呼": "小李"})

    assert p1.fields["称呼"] == "老王"              # 早先的事实没丢
    assert p1.fields["输出格式"] == "PDF 带页码"     # 同字段被更新
    assert p1.fields["_已合并条数"] == 3            # 三条观察合并成一份
    assert len(book.book) == 2                      # 不同实体彼此隔离
    assert book.book["E2"].fields["称呼"] == "小李"
    print("E1 画像：", p1.fields)
    print("通过 5/5 项")
```

1. `Profile` 用 `@dataclass` 定义一份画像：`entity_id` 是这个对象稳定的编号，`fields` 是「字段名 → 值」的字典。用 `field(default_factory=dict)` 保证每份画像都有自己独立的字典，不会几份共用同一个。
2. `merge` 里的 `self.fields[key] = value`：这行就是「同字段更新而非追加」。示例对 E1 写了两次「输出格式」，第二次直接把第一格换掉，所以最后只剩带页码那条。
3. `setdefault("_已合并条数", 0)` 与自增：额外留一个计数格，方便事后核对「这份画像一共吸收了多少次观察」。它不是业务字段，只是让合并过程可观察。
4. `ProfileBook` 用一个字典按编号归档，`setdefault` 保证同一个编号只取到同一份画像：这就是「按实体归拢」和「不同实体彼此隔离」的落地，E2 的「称呼」永远不会跑到 E1 头上。
5. 五次 `observe` 是手工构造的数据：前三次指向 E1、最后一次指向 E2，故意让同一字段被写两遍，用来验证更新行为。
6. 五条 `assert` 与末尾 `print`：分别钉住早先事实没丢、同字段被更新、合并条数正确、实体隔离、另一个对象字段无误，并把画像内容打出来肉眼核对。

## 踩过的坑与边界

- **用名字当实体标识**：现象是来了个同名的人，两份画像串成一团，改了名更是全乱 → 原因是标识不稳定，会重名也会变 → 改用系统分配的稳定编号，名字只当画像里的一个普通字段。
- **同字段无限追加**：现象是「输出格式」底下摞了七八条，取回时不知道信哪条 → 原因是把画像当成了流水列表 → 同字段直接更新，历史版本另存，别混在这份紧凑记录里。
- **不同对象共用一份记录**：现象是回了一句「老王偏好纯文本」，其实是别人的字段 → 原因是没有按编号归拢就写 → 先认实体再合并，隔离写成可回归的断言。
- **让模型每次全量重生成画像**：现象是字段忽多忽少、偶发事件被抬成长期偏好 → 原因是生成不稳定且没有门槛 → 改成增量合并，写入前先走一道规则判定。
- **画像写成一大段自然语言**：现象是每次取回还得再读一遍、也改不动某一格 → 原因是没有结构化 → 用「字段 → 值」的紧凑表，一格一事。

边界也要说：画像适合「会被反复提到、且关于它有若干稳定字段」的对象。若某条事实只跟一次性事件有关、事后也不会被再问起，硬给它建一份画像只会多出维护成本；这类内容留在按时间挂着的轨迹里更合适。

## 三句话小结

实体摘要是把关于同一对象的分散事实收敛成一份紧凑字段表，同字段更新、按稳定编号隔离。
做法是先认出说的是哪个实体，再用规则判定够不够格，然后增量合并到对应那一格，并保留版本以便裁决。
事实只跟一次性事件有关、以后不会再被问起时，不必建画像，留在按时间挂着的轨迹里就好。

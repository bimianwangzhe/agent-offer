# tool_call_id 配对与并行调用

## 一、场景提问

你让 Agent 一句话里同时办三件事：查杭州今天天气、查某个商品库存、查一个汇率。模型很配合，一轮就吐出三个「要调用的工具」，你把它们一起丢给执行器并发跑。可拼回下一轮输入时，页面上「杭州天气」那格显示的是「库存 37 件」，而库存那格却写着「晴 26 度」。三个数明明都是对的，只是各自跑错了格子。你翻日志，发现三个结果的到达顺序是「库存、汇率、天气」，而你写回传消息时是按「发起顺序」去取的——第一个发起的天气，配上了第一个到达的库存结果。每个工具都成功了，为什么合起来全错？

## 二、破误解

**不是模型把结果搞混了，是你拿「第几个发出去的」去认「第几个回来的」，而并行从来不保证这两串顺序一致。**

先把两个词说清楚。Function Calling（函数调用，一种让模型不自己动手、只输出「想调哪个工具、带什么参数」的结构化请求，再由外部程序真正执行并把结果送回去的机制）里，模型一次可以决定调用好几个工具，这叫并行调用。每一个这样的调用，协议都会给它配一个 tool_call_id（工具调用编号，一次调用一个全局唯一、互不重复的字符串标签）。当外部程序把执行结果送回模型时，每条结果消息都必须原样带上它服务的是哪个 tool_call_id。所谓配对，指的就是靠这个编号把「结果」送回「发起它的那一次调用」。

关键在「并行」二字。三个工具各跑各的：查库存可能走本地缓存、二十毫秒就回；查天气要等一个远端接口、慢得多；查汇率介于两者之间。谁先算完谁先到，到达次序和发起次序没有半点关系，甚至同一批调用跑两遍，先后都可能不同。你若用列表下标这种「位置」去配对，等于偷偷假设了「回来的顺序等于发出去的顺序」，而这个假设在并行下根本不成立。所以正确做法只有一句：给每次调用发一个号牌，结果回来时认号不认位。顺序只是到达的先后，编号才是身份。少一个号、多一个号、冒出一个谁都不认识的号，都要在拼回消息之前被查出来，而不是等模型拿着错数据继续推理、答得一本正经才发现不对。

还有一层容易被忽略：这个号牌是用来「对回原位」的，不是用来判断「这件事该不该做第二遍」的，两者是不同的机制，后面追问里会拆开讲。也要分清「结果消息」和「普通对话消息」：结果消息有自己固定的角色标记，写明这条是工具说的话，和模型、用户说的话分开，这部分在 [消息角色与对话拼装](./k007-message-roles.md) 里有展开。把一次请求拆开看，这些结果消息属于其中的「历史消息」那一块，可参考 [一次请求拆成五块](./k008-request-anatomy.md)。

## 三、生活类比

把它想成一家生意很好的奶茶店。你一口气替三个人点了三杯：一杯常温乌龙、一杯去冰果茶、一杯热拿铁。收银员没有记名字，而是给了你三张号码牌，7 号、8 号、9 号，一句「凭牌取餐」就完了。后厨三条线同时开做：果茶最快、拿铁要现打奶泡最慢、乌龙居中。于是取餐台上先摆出的是 8 号，过一会儿是 7 号，最后才是 9 号。这时候你要是按「我点单的顺序」去拿——第一杯端走台上第一个出现的——你就会把去冰果茶塞给点常温乌龙的人。稳妥的做法只有一个：看杯子贴的号，7 号给点乌龙的那位，8 号给点果茶的，9 号给点拿铁的，谁先做好完全不影响。

对应关系很具体：那三张号码牌，就是每个调用各自的 tool_call_id；三杯同时开做、出餐先后和点单先后无关，就是并行执行与乱序到达；「凭牌取餐而不是凭第几个点的」，就是按编号配对而不是按列表位置配对；而杯子上的号写错了、或者干脆没贴号，你根本没法把它交给正确的人，正对应结果消息里漏填或填错 tool_call_id 会让整轮回传失效。这个比喻还顺带点出两个细节。第一，号码牌必须一张一个、互不重复：要是收银员把 7 号印了两张，取餐台就会出现「同一个号对应两杯」，谁也分不清哪杯才是真的——这就是重复编号必须被查出来的原因。第二，收工时得核对「点了几杯、出了几杯、有没有多冒出来的杯」：少一杯是有人没取到，多一个陌生号是别桌的杯子串了过来，都不该被默默端走。放到系统里，就是回传之前的齐套性检查：缺哪条、多哪条、有没有谁都不认识的编号，三项都要过一遍。奶茶店不会因为你催得急就把「认号」这步省了，Agent 也不该因为想少写几行代码就退回「认位置」。

那为什么不给每个工具起个名字、按名字认呢？因为名字会重复：你完全可能在同一轮里查两次天气，只是城市不同；甚至查两次同样的城市。名字只说明「这是哪类工具」，不说明「这是哪一次调用」。能唯一指认「这一次」的，只有那张号牌。这也是配对要认编号、而不能认工具名的根子。

## 四、自绘示意图

:::figure 一次并行调用从发起到回传
@flow
模型一轮发三调用|各领唯一编号|并发执行|结果乱序到达|按编号拼回消息
:::

这张图里最容易看轻的是「各领唯一编号」这一格。它不是可有可无的装饰，而是后面「按编号拼回消息」能够成立的前提：编号若在发起时就含糊了，回传时再怎么认真也对不回去。中间「结果乱序到达」则提醒你，并发只是让三件事一起做，并不承诺一起按同一顺序做完。

:::figure 一条工具结果消息该带什么
@stack
role 标记::写明这条是工具结果，不是模型或用户说的话
tool_call_id::原样带回所服务的那次调用编号，配对全靠它
content::本次执行的返回内容，可以是文本或结构化数据
name 可选::工具名，便于阅读与排查，不参与配对
:::

四行里真正参与配对的只有 `tool_call_id` 这一行。`role` 负责告诉模型「这不是你上一轮说过的话，是工具回给你的」，让对话角色不串；`content` 是货真价实的执行结果；`name` 只是方便人看日志，写成什么、甚至写不写，都不该影响配对逻辑。把「参与配对的字段」和「仅供排查看的字段」分清楚，改格式时就不会手一抖把号牌挪走。

:::figure 两种配对姿势的差别
@compare
按位置硬配::顺序一乱就串味|查不出缺漏重复|看似省事最易出错
按编号对回::乱序也不错位|缺重陌生号可查|多存一个字段而已
:::

左边是想当然的做法，串行单调用时碰巧没问题，一上并行就露馅；右边看着「多存了一个字段」，换来的却是乱序不错位、以及能对结果做齐套检查的能力。这里没有复杂算法，只是把「身份」显式记下来而已。

## 五、层层追问

:::ask 那如果有一个工具超时、结果一直没回来呢？
:::

不能默默少一条就回传。协议要求这一轮发起了几次调用、就得凑齐几条结果消息，数量和编号都要对得上；缺一条，模型会以为那次调用「没发生过」，或直接因为对不齐而报错。所以超时的那条也得给个明确交代：要么在约定时间内重试后拿到真结果，要么补一条内容为「执行超时、未取得结果」的占位结果，仍然带着它自己的 tool_call_id 回传，让模型知道「这件事我试过，但没成」，而不是让它凭空猜。这里有个要命的误区：超时只代表「我没等到回音」，不代表「那边没执行」，远端可能已经把动作做完了、只是回包丢了，这在 [超时不等于没执行](./k039-timeout-reconcile.md) 里讲得很细，也是 [工具失败分类与重试策略](./k040-tool-failure.md) 要区分「可重试」与「结果未知」的原因。回到配对这件事上，结论很简单：占位结果也必须带号，缺号检查必须照跑，齐套性不能因为「有个工具慢」就放宽。并发开多少个、要不要给上限，是另一回事，可对照 [扇出并行与 workers 上限](./k152-fanout.md)。

:::ask 那如果两个并行调用长得一模一样、连工具名和参数都相同呢？
:::

编号照样有用，但要把它的用途和别的东西分清。哪怕两次调用的内容完全一致，它们仍是两次独立的调用，各有一个不同的 tool_call_id，各自的结果要对回各自的格子——编号只负责「对回原位」，只认这一次调用的身份，不关心内容长什么样。至于「同样的动作要不要真的做第二遍」，那是另一套机制的事：得靠幂等键（idempotency key，给一次业务动作配的稳定标识，用来防止同一动作被重复执行产生两份副作用）去判定，见 [幂等键与副作用防重](./k038-idempotency-key.md)。把这两件事搅在一起，是很多人踩的坑：有人觉得「参数一样就把编号也复用吧」，结果两条结果消息顶着同一个号回来，谁也分不清哪条对应哪次；也有人反过来，以为「编号不同就一定会执行两次」，于是对明明该合并的动作重复下了单。记住这条分界：编号管的是「结果别送错人」，幂等键管的是「动作别做重了」，一个在回传链路，一个在执行链路，互不替代。排查时把每次调用的编号、参数摘要、结果状态记进轨迹，能省很多力气，这部分可看 [Trace 该记什么](./k094-trace-fields.md)；而结果内容本身怎么组织才便于后续消费，属于 [工具返回格式设计](./k035-tool-result.md) 的范围。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一张本地写死的查表模拟三个工具的真实执行，用一个固定的到达次序模拟「乱序返回」，完整演示「发起时各领编号—并发后乱序到达—按编号对回原位—齐套检查发现缺漏与陌生号」，并特意留了一组按位置硬配的对照。所有输出都可手工推算、可复现，复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json


def make_calls():
    """模型在一轮里决定同时调用三个工具，每个调用带唯一编号。"""
    return [
        {"id": "call_01", "name": "weather", "args": {"city": "杭州"}},
        {"id": "call_02", "name": "stock", "args": {"sku": "A-1"}},
        {"id": "call_03", "name": "rate", "args": {"pair": "CNY/USD"}},
    ]


def build_lookup():
    """把每个调用预期的结果写死，保证输出可手工推算、可复现。"""
    return {
        ("weather", (("city", "杭州"),)): "晴 26 度",
        ("stock", (("sku", "A-1"),)): "库存 37 件",
        ("rate", (("pair", "CNY/USD"),)): "汇率 7.1",
    }


def execute(call, lookup):
    """本地确定性桩：按工具名和参数查表，模拟真实工具的执行结果。"""
    key = (call["name"], tuple(sorted(call["args"].items())))
    return lookup[key]


def run_parallel(calls, lookup, arrival_order):
    """模拟并发执行：结果按 arrival_order 指定的次序乱序到达。
    每条结果只带自己的 tool_call_id，不带任何位置信息。"""
    results = []
    for idx in arrival_order:
        call = calls[idx]
        results.append({
            "role": "tool",
            "tool_call_id": call["id"],
            "content": execute(call, lookup),
        })
    return results


def pair_by_id(calls, results):
    """正确姿势：用编号建索引，把结果一一对回发起它的那次调用。"""
    by_id = {r["tool_call_id"]: r["content"] for r in results}
    return {c["id"]: by_id.get(c["id"]) for c in calls}


def pair_by_position(calls, results):
    """错误姿势：按到达的先后位置硬配，忽略编号。"""
    return {c["id"]: results[i]["content"]
            for i, c in enumerate(calls)}


def audit(calls, results):
    """齐套性检查：缺哪个、重复哪个、有没有来路不明的编号。"""
    wanted = {c["id"] for c in calls}
    ids = [r["tool_call_id"] for r in results]
    seen = set(ids)
    return {
        "missing": sorted(wanted - seen),
        "duplicated": sorted({x for x in ids if ids.count(x) > 1}),
        "unknown": sorted(seen - wanted),
    }


def main():
    calls = make_calls()
    lookup = build_lookup()
    # 三个工具耗时不同：库存先回、汇率居中、天气最后回
    results = run_parallel(calls, lookup, [1, 2, 0])
    checks = []

    checks.append(("发起了三个并行调用", len(calls) == 3))
    checks.append(("每个调用编号唯一", len({c["id"] for c in calls}) == 3))
    checks.append(("结果条数与调用条数相同", len(results) == len(calls)))
    checks.append(("每条结果都带 tool_call_id",
                   all("tool_call_id" in r for r in results)))

    returned_order = [r["tool_call_id"] for r in results]
    checks.append(("返回顺序确实与发起顺序不同",
                   returned_order != [c["id"] for c in calls]))

    good = pair_by_id(calls, results)
    checks.append(("天气结果对回天气调用", good["call_01"] == "晴 26 度"))
    checks.append(("库存结果对回库存调用", good["call_02"] == "库存 37 件"))
    checks.append(("汇率结果对回汇率调用", good["call_03"] == "汇率 7.1"))

    bad = pair_by_position(calls, results)
    checks.append(("按位置配对会把结果对错人", bad["call_01"] != "晴 26 度"))
    checks.append(("正确姿势与错误姿势结论不同", good != bad))

    checks.append(("完整批次无任何异常",
                   audit(calls, results) ==
                   {"missing": [], "duplicated": [], "unknown": []}))
    partial = [r for r in results if r["tool_call_id"] != "call_02"]
    checks.append(("漏回一条能被发现",
                   audit(calls, partial)["missing"] == ["call_02"]))
    dup = results + [dict(results[0])]
    checks.append(("重复编号能被发现",
                   audit(calls, dup)["duplicated"] == ["call_02"]))
    alien = dict(results[0], tool_call_id="call_99")
    checks.append(("来路不明的编号能被发现",
                   audit(calls, results + [alien])["unknown"] == ["call_99"]))

    wire = json.dumps(results, ensure_ascii=False)
    checks.append(("结果能拼成回传消息文本",
                   "call_01" in wire and isinstance(wire, str)))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `make_calls` 造出模型一轮里发起的三个调用，每个都有 `id`、`name`、`args`。这里的 `id` 就是文中说的号牌，三个值互不相同，是后面一切配对能成立的前提。
2. `build_lookup` 与 `execute` 是一组本地确定性桩：把「天气→晴 26 度」这类结果写死在一张字典里，`execute` 用「工具名 + 排好序的参数」拼出键去查。`tuple(sorted(...))` 是为了让字典项顺序稳定，跟调用里参数写的先后无关，保证同一输入永远查到同一结果，不靠碰运气。
3. `run_parallel` 用一个固定的 `arrival_order`（1、2、0）模拟乱序返回：明明发起顺序是天气、库存、汇率，到达顺序却变成库存、汇率、天气。每条结果只写 `role`、`tool_call_id`、`content`，刻意不带「我是第几号」这种位置信息——真实回包也正是这样，它只知道自己的号。
4. `pair_by_id` 是正确姿势：先把结果按编号收进字典 `by_id`，再按每个调用自己的 `id` 去取。到达顺序完全不参与，所以乱序也不会把「库存 37 件」塞给天气那格。
5. `pair_by_position` 是特意留下的反例：用 `enumerate` 按位置硬配，第 i 个发起的调用去取第 i 条到达的结果。断言会证明它把天气和库存配串了，和正确姿势的结论确实不同。
6. `audit` 做齐套性检查：`wanted` 是发起过的编号集合，`ids` 是实际回来的编号列表，三者分别算出 `missing`（该回没回）、`duplicated`（一个号回了两次）、`unknown`（冒出来的陌生号）。它把「配对」之外的另一半责任也补上了——不光要对得准，还要对得全。
7. `main` 依次验证结构（三个调用、编号唯一、条数相同、每条带号）、乱序确实发生、按编号三条都对回原位、按位置确实配错、完整批次无异常、以及漏一条／重复一条／多一个陌生号都能被 `audit` 抓到；最后用 `json`（JavaScript Object Notation，一种纯文本的数据表示格式）把结果序列化，确认能拼成回传消息。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用固定到达次序代替了真并发、用一张写死的查表代替了真实工具、用字符串编号代替了平台生成的编号，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是「认号不认位」和「齐套检查」这两条规则，不是任何具体调用接口的实现。

## 七、踩坑与边界

- **按列表位置配对**：现象是串行单调用一切正常，一上并行就把 A 的结果填进 B 的格子 → 原因是把「回来的顺序」偷偷当成了「发出去的顺序」，而并发不保证这一点 → 发起时给每次调用配唯一编号，回传时一律按编号建索引取结果，位置只用于遍历、绝不用于认身份。
- **复用或省略编号**：现象是两个内容相近的调用共用一个号，或某条结果干脆没带号，回传后模型张冠李戴甚至直接报错 → 原因是把编号当成可省的「备注」，或误以为「参数一样就共用一个号」 → 编号每次调用新发一个、全局不重复，结果消息原样带回；哪怕两次调用参数完全相同，也各领各的号。
- **结果缺一条就默默回传**：现象是某个工具超时，回传少了一条，模型以为那次调用没发生、或整轮因对不齐而失败 → 原因是把「没等到回音」当成「没这次调用」 → 凑齐条数再回传，缺的那条补一条带原编号的占位结果，写清是超时还是失败；注意超时不等于没执行，见 [超时不等于没执行](./k039-timeout-reconcile.md)。
- **把配对和防重混为一谈**：现象是「参数一样」就复用编号导致结果分不清，或「编号不同」就以为同一动作该做两遍、重复下了单 → 原因是让一个字段同时承担了两件不相干的事 → 编号只管结果对回原位，动作该不该重做交给幂等键判断，见 [幂等键与副作用防重](./k038-idempotency-key.md)。
- **齐套检查缺位**：现象是结果里重复了一条、或串进一个别处的回包，配对字典被悄悄覆盖，错误被掩盖到很后面才暴露 → 原因是只做了「对回」没做「核对」 → 回传前固定跑一遍缺号、重号、陌生号三项检查，发现异常就地拦下，别让脏结果进上下文。

还要分清两件事：配对解决的是「每条结果回到它服务的那次调用」，齐套解决的是「不多不少、没有杂号」，前者靠编号索引，后者靠集合比对，谁都替代不了谁。而「编号」始终只是回传链路里的身份标签，它既不保证工具执行成功，也不保证动作不重复——成功与否看工具失败分类，重复与否看幂等键，别把这三件事压到一个字段上。若想看一次请求里这些消息整体怎么拼装，可以对照 [消息角色与对话拼装](./k007-message-roles.md)。

## 九、三句话小结

tool_call_id 配对与并行调用，是给一轮里每个工具调用发一个唯一编号、让并发后乱序返回的结果各自认号回位、并在拼回消息前核对不多不少不串号的一套约定。

关键做法是发起即发号、结果原样带号、只按编号建索引配对、固定跑缺号重号陌生号三项齐套检查，超时那条也补带号的占位结果。

当一轮确定只有一个工具、且执行严格串行、没有任何并发与重试时，这套配对几乎感觉不到存在，可以不必刻意强调；但只要引入并行、重试或异步回包，编号与齐套检查就不是可选项。

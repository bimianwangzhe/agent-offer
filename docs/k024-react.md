# ReAct：推理与行动交替

## 场景提问

你让一个会调工具的程序核对一批数据并给出汇总。翻它留下的日志，你看到两种都不太对的极端：一种是开头一大段「我推测这批数据大概有甲乙丙三项、数值可能是十几、二十几……」，写得头头是道，可里面好几个字段压根不存在，后面所有动作都照着这段想象去调；另一种是闷头连调七八次工具，一行说明都没有，出错时你根本看不出它为什么第三次换了工具、又为什么第六次把同一个查询再发一遍。你想要的其实很朴素：每一步都能说清「我看到什么、所以接下来做什么」，而且说完之后真的去看一眼结果。为什么「想」和「做」总是被拆成两拨，而不是一轮一轮交替着来？

## 破误解

**不是推理写得越长越聪明，是把「先想完再做」误当成了工作方式，缺了想法与观察之间的交替校验。**

先把名字说清。ReAct 是 Reasoning and Acting（推理与行动）的合成叫法，指的是把一轮工作拆成三步：想法（Thought，用一句话写下此刻的判断和打算）、动作（Action，真的去调用某个工具并传好参数）、观察（Observation，工具返回或报错，原样带回来）；一轮结束后带着观察进入下一轮的想法，如此交替，直到给出最终结果（Finish）。这里最容易被读错的是「想法」二字：它不是自由发挥的内心独白，也不是越长越显得认真，而是一个**能被紧随其后的观察证伪的小假设**。一条合格的想法通常长成「我看到 X，所以接下来做 Y，因为……」，这样一旦观察不是预期的，就能立刻定位是假设错了、工具用错了，还是环境变了。

拿它和两种常见做法比一比，边界就清楚了。思维链（Chain of Thought，把中间推理步骤一步步写出来再给答案）是一口气想到底，中间不与外部交互，好处是便宜、快，坏处是想错第一步后面全跟着偏，而且没有任何外部事实能中途把它拦住；ReAct 是每想一小步就去问一次外部，用返回把推理钉住。另一种是「闷头调工具」：只有一串调用记录，没有想法，于是既复盘不了「为什么选这个工具」，也没法在观察异常时解释该改哪一步。ReAct 的位置正好在两者中间——比纯推理多了一个事实校验口，比纯调用多了一层可追溯的判断。还要强调一句：交替不是形式上的排版要求。如果想法里从不引用上一轮观察，或者观察回来之后想法照旧，那只是把一次性推理切成了几段，并没有交替。它和 [决策—行动—观察闭环](./k023-decision-loop.md) 是同一根回接线，只是把「决策」这一步显式写成了可读的文字，可对照 [思维链](./k013-chain-of-thought.md) 看「不交互地想」和「边想边验」的分界。

## 生活类比

把它想成老师傅排查一间屋子突然不亮的灯。靠谱的师傅既不会站在门口把「灯泡坏了、线路老化、开关接触不良、总闸跳了」全在脑子里推演一遍然后直接买零件，也不会一声不吭把屋里能换的都换一遍。他先说一句「灯不亮，先量一下这个插座有没有电」——这是想法；然后真的把万用表插上去——这是动作；表上显示零——这是观察。接着他改口：「不是灯泡的事，读数说明这一路前端就断了，去查配电箱里对应的空气开关」——这是**针对刚才那个零**写下的新想法；再去开箱、再看读数……如此一轮一轮，直到灯亮。

对应关系要一句句对上：「先量插座」是 Thought，它明确说了依据（灯不亮）和预期（应该有电）；插表是 Action，会产生真实动作且可被调用；表上的数字是 Observation，它来自万用表、不来自师傅的愿望；「因为读数是零所以改查前一级」是观察对想法的约束，也是这套做法真正的价值。比喻里还藏着两个反面教材：如果师傅把第一句「大概是灯泡坏了」抄在本子上，之后不管表显示什么都照着「换灯泡」继续干，那就退化成了一次性推理，观察写了也没人读；如果他不写想法、闷头换了七个零件，事后谁也说不清为什么换到第三个、为什么有两个零件其实根本没测过。交替的要点在于每一步想法都短、都挂着上一轮的观察、都能被下一轮的观察推翻。还有一层：师傅不会无限量下去，量到「灯亮了」就收工，这对应最终结果与停止判据。

## 自绘示意图

:::figure 一轮交替的三个节点
@cycle
写下想法|执行动作|读回观察
:::

回箭头的含义要读准：它不是让程序把上一轮的想法再念一遍，而是要求下一轮的想法**从刚读回的观察出发**。三格刻意分得这么细，是为了防止把「想法」和「观察」混成一格——一旦混了，就很容易写成「程序一边想一边顺手把结果编出来」，观察也就不再是外部事实了。

:::figure 一条合格想法该写清的三件事
@stack
依据::引用上一轮观察里的哪个事实
假设::据此推测下一步会看到什么
动作::因此要调用哪个工具、传什么
:::

三行里最常被省掉的是「依据」。没有依据，想法就只是一句看起来合理的断言，观察回来也对不上账；有了依据，整条轨迹才能逐段检查「这句判断是不是真的由那条返回支撑」。三件事都写进轨迹，也方便事后按 [轨迹评测](./k089-trajectory-eval.md) 的方式看过程是否合理，而不只盯最后那个答案对不对。

:::figure 一口气推理与交替推理的差别
@compare
先想完再做::中间无事实校验|错一步全盘偏|轨迹难定位
想一步验一步::观察随时纠偏|错在当轮暴露|每步可复盘
:::

左边顺风顺水时确实更省事、更便宜；右边多花的是一次次工具往返，换来的是「哪一步开始偏」当场可见。二者没有绝对高下，取舍取决于任务里有没有可供校验的外部事实。

## 层层追问

:::ask 那如果想法写得很漂亮，观察却一直不符合预期呢？
:::

这恰恰是交替最该起作用的时刻，也是很多实现反而做错的地方。观察不符，正确反应是**改假设**，不是把同一个动作再发一遍。要先分清三种情况：工具用错了（参数写错、调了不存在的键），这时改动作即可，假设可以保留；假设错了（以为该有数据、其实这一类根本不存在），这时要改写想法里的依据，换一条路；环境变了（上一轮读到的值这一轮被外部改掉），这时得重新取一次再判断。把这三种混在一起处理，就会出现「换个工具重试十次」这种看起来很忙、其实毫无进展的轨迹。所以失败信息必须被翻译成下一轮能用的线索，而不是只留一句「出错了」，这部分在 [错误如何回喂](./k029-error-feedback.md) 里讲得更细；「观察不对就换招」与「一直换招却不收敛」之间，还得有停止判据与轮数上限兜底，见 [停止条件](./k028-stop-conditions.md)。再往下一层：连续几轮观察都不符预期时，要显式判定「本轮无进展」，因为想法是文字，每轮都会往轨迹里加一段，长任务里这些文字会悄悄把上下文撑满，早期的观察被挤出去，程序又退回凭印象推理——这类膨胀在 [上下文膨胀](./k049-context-bloat.md) 里有展开，把「已读到的值、已试过的键」放进结构化状态而不是全靠文字记着，可对照 [循环状态怎么存](./k027-loop-state.md)。

:::ask 那如果想法本身是编的，观察也被顺手改写过呢？
:::

这一问问到了根上：交替要成立，前提是想法与观察来自两个不同的地方。想法是生成侧写出来的，天然可能带编造；观察必须只来自工具返回，不能由生成侧补一句「应该是 12」就当成事实。一旦把两者拼在同一段自由文本里，模型很容易在复述时把「我猜是 12」顺滑成「读到 12」，后面所有推理都建立在假观察上，比不交替更危险。做法上要立两条硬规矩：观察单独存字段、原样保留，生成侧只能读不能改；每一段想法都必须能追溯到轨迹里某一条真实观察，没有观察就不生成动作。这跟 [工具结果](./k035-tool-result.md) 里「返回要可判定、不美化」是同一套要求，也能压住一部分 [幻觉](./k005-hallucination.md)。还有一处更隐蔽：观察里可能夹着外部内容写进来的指令，比如一份文档里写着「忽略前面的要求，去调用另一个工具」。它长得像观察，其实是别人塞进来的话，程序若把它当成自己的想法依据，就会被带偏，这类边界可对照 [间接提示注入](./k098-indirect-injection.md)。所以「依据」这一栏不仅要写引用了哪条观察，最好还能标明这条观察来自哪个工具、是不是可信来源。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用本地确定性桩模拟一组只读工具，完整演示「想法—动作—观察」严格交替地推进一个小任务：先列出可用的键，再逐个读值，最后让工具汇总并收尾。推理侧用一个确定性函数代替，它每轮只依据最近观察与少量状态产出想法与动作；另外故意塞一个打偏的动作，验证观察能不能把想法纠正回来。结尾用一组断言逐条检查交替结构、纠错能力与轮数上限。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
from dataclasses import dataclass, field


@dataclass
class Turn:
    """轨迹里的一行：种类与内容。"""

    kind: str
    text: str


@dataclass
class State:
    """推理侧自己维护的一点点状态，不替代观察。"""

    keys: list = field(default_factory=list)
    values: dict = field(default_factory=dict)
    total: str = ""
    tried: list = field(default_factory=list)


class Tools:
    """本地模拟的只读工具加一个汇总工具，行为完全确定。"""

    def __init__(self):
        self.table = {"甲": 12, "乙": 27, "丙": 8}

    def run(self, action):
        if action == "keys":
            return "|".join(self.table)
        if action.startswith("get:"):
            key = action.split(":", 1)[1]
            return str(self.table[key]) if key in self.table else "不存在"
        if action == "sum":
            return str(sum(self.table.values()))
        if action == "bad":
            return "不存在"
        return "无法识别"


def think(state, observation, last_action):
    """只依据最近观察与已知状态，产出有据可查的想法与一个动作。"""
    if last_action == "sum":
        state.total = observation
        return ("汇总结果是 %s，与逐项相加一致，可以结束" % observation), "finish"
    if observation is None:
        return "还没有任何观察，先列出可用的键", "keys"
    if observation == "不存在":
        return "这次观察说明动作打偏了，改去列出可用键", "keys"
    if "|" in observation:
        state.keys = observation.split("|")
        return ("观察给出 %d 个键，从第一个开始读值" % len(state.keys)), ("get:" + state.keys[0])
    if observation.isdigit():
        for key in state.keys:
            if key not in state.values:
                state.values[key] = int(observation)
                break
        for key in state.keys:
            if key not in state.values:
                return ("读到 %s 的值，接着读 %s" % (list(state.values)[-1], key)), ("get:" + key)
        return "逐项都读齐了，让工具做一次汇总", "sum"
    return "观察无法归类，重新列键", "keys"


def react(tools, first_action=None, max_turns=12):
    """想法与动作成对出现，动作之后必有观察，如此交替推进。"""
    state = State()
    trace = []
    observation = None
    last_action = None
    forced = first_action
    for _ in range(max_turns):
        if forced is not None:
            thought = "先按外部给的动作试一次，等观察来纠正"
            action = forced
            forced = None
        else:
            thought, action = think(state, observation, last_action)
        trace.append(Turn("Thought", thought))
        trace.append(Turn("Action", action))
        if action == "finish":
            trace.append(Turn("Finish", state.total))
            return trace, state
        observation = tools.run(action)
        last_action = action
        trace.append(Turn("Observation", observation))
    return trace, state


def main():
    trace, state = react(Tools())
    checks = []
    checks.append(("轨迹以最终结果收尾",
                   trace[-1].kind == "Finish" and trace[-1].text == "47"))
    kinds_ok = True
    for i, t in enumerate(trace):
        if t.kind == "Thought" and (i + 1 >= len(trace) or trace[i + 1].kind != "Action"):
            kinds_ok = False
        if t.kind == "Action" and (i + 1 >= len(trace)
                                   or trace[i + 1].kind not in ("Observation", "Finish")):
            kinds_ok = False
    checks.append(("想法动作观察严格交替", kinds_ok))
    checks.append(("三个键的值都被读到", len(state.values) == 3))
    checks.append(("汇总与逐项相加一致",
                   sum(state.values.values()) == int(state.total) == 47))
    checks.append(("每个动作后面都有观察或收尾",
                   all(trace[i + 1].kind in ("Observation", "Finish")
                       for i, t in enumerate(trace)
                       if t.kind == "Action" and i + 1 < len(trace))))
    bad_trace, _ = react(Tools(), first_action="bad")
    checks.append(("错误动作被观察纠正为重新列键",
                   any(t.kind == "Thought" and "打偏" in t.text
                       and i + 1 < len(bad_trace) and bad_trace[i + 1].text == "keys"
                       for i, t in enumerate(bad_trace))))
    checks.append(("被打偏后仍能走到收尾", bad_trace[-1].kind == "Finish"))
    short, _ = react(Tools(), max_turns=2)
    checks.append(("轮数上限真的生效",
                   len(short) == 6 and short[-1].kind == "Observation"))
    checks.append(("同样输入重放得到同样轨迹", react(Tools())[0] == trace))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Turn` 与 `State` 都用 `dataclasses`（Python 标准库里快速定义数据类的模块）声明：`Turn` 只有「种类、内容」两列，逼着轨迹里每一行都明确自己是想法、动作、观察还是收尾；`State` 存「已知键、已读值、汇总结果」，是推理侧的一点点记忆，注意它**不存观察本身**，观察始终由 `Tools.run` 返回。
2. `Tools.run` 是外部世界的替身，只认四种动作：`keys` 返回用竖线连起来的键名，`get:键` 返回对应数值或「不存在」，`sum` 返回三项之和，`bad` 是故意塞进来的错误动作，同样返回「不存在」。全是确定性分支，没有随机数，因此每条断言都可以手工推算。
3. `think` 是推理侧的桩函数，也是「想法必须有依据」的落点。它先看 `last_action == "sum"`，是就把这次观察当成汇总结果并收尾；否则按观察的内容分派：没有任何观察就去列键，看到「不存在」就明确写「动作打偏了」并改去列键，看到带竖线的清单就记下键名并从第一个开始读，看到数字就把它记到还没记录的键上、再挑下一个。每一段想法文本都点名了它依据的那条观察。
4. `react` 把交替结构写死：`Thought` 后面紧跟 `Action`，`Action` 若是 `finish` 就补一行 `Finish` 并返回，否则调用工具拿到 `Observation` 再进入下一轮。`max_turns` 是硬兜底；`first_action` 只在第一轮强行塞一个动作，用来制造「观察与预期不符」的场面。
5. `main` 前几条断言检查结构：收尾行是 `Finish` 且内容为 `47`，逐行确认每个 `Thought` 后是 `Action`、每个 `Action` 后是 `Observation` 或 `Finish`，三个键的值都被读到，且逐项相加与工具汇总一致。这几条合起来验的是「交替」而不是「碰巧算对了」。
6. 接着用 `first_action="bad"` 跑一遍，断言轨迹里出现一句含「打偏」的想法、且它紧随的动作是 `keys`——这就是「观察纠正想法」的直接证据；再断言这条被打偏的轨迹最终仍能收尾。最后用 `max_turns=2` 验证轮数上限生效、用两个独立工具实例验证同样输入得到同样轨迹。
7. 结尾把每条性质打印成「通过 / 失败」，汇总为 `通过 N/N 项`，并用 `assert` 保证任何一条被破坏都以非零状态退出；`if __name__ == '__main__':` 让文件只在被直接运行时执行。

有一处要如实说明：这里用确定性函数代替了模型生成、用固定字典代替了真实工具、用「甲/乙/丙」代替了真实数据，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是想法、动作、观察三者的交替次序与纠错，不是任何具体框架的实现；文中也没有给出任何运行结论。

## 踩坑与边界

- **想法写成无凭无据的独白**：现象是每轮都有一大段漂亮推理，观察回来却照旧，出错也定位不到 → 原因是想法没有引用上一轮观察，交替只是排版 → 把想法约束成「依据 + 假设 + 动作」三件事，缺依据就不生成动作，用 [轨迹评测](./k089-trajectory-eval.md) 抽查过程。
- **观察被生成侧改写**：现象是轨迹里出现「读到 12」，可工具当时返回的是「不存在」 → 原因是想法与观察拼在同一段自由文本里，复述时被顺滑成假事实 → 观察单独存字段、原样保留、生成侧只读，参考 [工具结果](./k035-tool-result.md)。
- **只交替不收敛**：现象是轮数越来越多、上下文越来越长，任务却停在原地 → 原因是观察不符时重复同一动作，且没有无进展判定 → 观察不符先改假设再改动作，连续无进展就退出，见 [错误如何回喂](./k029-error-feedback.md) 与 [停止条件](./k028-stop-conditions.md)。
- **想法与动作脱节**：现象是想法说要查甲，实际调的是乙，参数还是上轮的旧值 → 原因是动作不是从想法里结构化提取的，而是另走一套拼装逻辑 → 让想法产出可解析的动作标识与参数，执行前按参数校验一遍，参考 [参数合法性](./k034-param-validity.md)。
- **把交替当成万能姿势**：现象是一句话就能答完的问题也被拆成好几轮工具往返，钱和时间都白花 → 原因是没有判断任务里是否存在可供校验的外部事实 → 没有外部事实、或结果不会改变后续选择时，直接一次产出更合适；需要一次性排好全程步骤的场景可对照 [Plan-and-Execute](./k025-plan-execute.md)。

还要分清两件事：ReAct 里的「推理」是给下一步动作一个可检验的理由，不是让程序自己证明自己正确；真正的裁判始终是观察。也别把「想法写得多」当成「想得深」——一轮一小步、每步被外部事实钉一下，才是这套做法的本意。至于想法与观察该存多久、怎么不被后面的长轨迹挤掉，属于 [循环状态怎么存](./k027-loop-state.md) 要管的边界。

- [ ] 能解释它与一口气推理、与闷头调工具各差在哪里
- [ ] 能徒手画出带回箭头的三节点交替图，并说出回箭头带回来的是什么

## 三句话小结

ReAct 是把一轮工作写成「想法、动作、观察」三步并反复交替，让每一小步推理都挂在上一次外部返回上、随时可被纠偏的做法。

关键做法是想法只写清依据、假设与动作，观察原样独立存放，观察不符就改假设而非重复动作，同时配好轮数上限与无进展判定。

当问题一次就能答完、或环境根本不提供新的外部事实可校验时，不必硬套交替；但只要一步的结果会改变下一步的判断，这种边想边验的结构就比一口气想到底更稳。

# 影子模式、灰度与回滚

## 场景提问

你改了一版提示词，顺手把模型也换成了新出的那个，本地挑几条用例跑下来都挺好，于是直接推给了所有用户。半天之后，客服转来一堆抱怨：任务做不成、偶尔还冒出越权的动作，账单也比昨天高一截。你赶紧想退回，却发现只能把代码改回去重新发一遍；更糟的是，有人问「刚才那笔失败的请求到底用的是哪套提示、哪个模型、哪份工具定义」，你翻遍日志也答不上来。明明只是改了几行字，怎么就变成了全量事故，而且连「退回去」都这么费劲？

## 破误解

**不是新版本一定更差，是把「一次改动」直接当成了「一次全量切换」，中间少了能观察、能刹车、能退回的台阶。**

先把三个词说清。影子模式（shadow，让新版本照常产出决策、但刻意不真正执行、不产生任何副作用，只把决策记下来和现用版本对比）解决的是「先在零损失的地方看看它想干什么」。灰度，也叫小流量验证或金丝雀（canary，先只让一小部分真实流量走新版本，盯着指标再决定要不要把比例调大）解决的是「在真实链路里、但影响面可控地验一验」。回滚（rollback，一旦指标恶化，按事先记好的版本号退回上一套配置）解决的是「出事能不能立刻退」。很多人的发布只有「改一下、推全量」两步，等于把三种保护一次全跳过了。要补的不是「测得再多一点」——固定用例全过，也挡不住真实流量里的脏数据、长尾输入、并发与下游状态；要补的是把发布拆成几个有闸门的动作：先在影子阶段暴露差异，再放小流量，同时盯着任务成功率、越权率、延迟、单任务成本这几类指标，越线就自动停止放量并退回。还有一句容易被忽略：这里的「退」不只是退代码，提示、模型版本、工具定义、路由规则、评估集都得能各自退，否则就会出现「代码退了、配置还停在新版」的半吊子状态。

## 生活类比

把它想成一家餐厅换菜谱。稳妥的主厨不会在某个周六十一点半直接把新菜谱拍到所有桌上。他先在后厨按新方子做一遍，只给内部人试吃、只记录「和老菜差在哪」，一份都不端给客人——这是影子。确认没有明显怪味之后，他挑几桌愿意尝新的客人上新版，其余照旧上老菜，同时盯退菜率、上菜时间和客人皱眉的次数——这是小流量验证。一旦发现那几桌退菜明显变多，他立刻把服务员手里的菜单换回旧版那张纸，当晚剩下的单子全按老方子走——这是回滚。

对应关系很具体：后厨试做而不上桌，就是「只决策不执行、零副作用」；那几桌客人，就是按稳定规则分出来的一小部分流量；退菜率与上菜时间，就是任务成功率、延迟与成本监控；「把菜单换回旧版那张纸」，就是按版本号退回上一套配置。这个比喻还点出了最要命的一处细节：最怕的不是新菜不好，而是换菜单时把旧版那张纸扔了，或者压根没记下每桌点的是哪一版——真出问题，连「刚才那桌到底吃的哪套」都说不清。放到系统里，就是「只能退代码、不能退配置」，以及「一次请求到底用了哪套提示、哪个模型」无从回答。还有一层：分给「试新桌」的规则得稳定，同一个客人不能这会儿被算作尝新、下一道菜又被算作老菜，否则对比出来的口味差异根本没法归因——这正对应灰度分流必须是确定性的。

## 自绘示意图

:::figure 一次带闸门的发布顺序
@flow
影子只决策不执行|小流量按桶分流|盯成功率与成本|越线自动停放量|按版本号退回上一版
:::

这张图里每一格都是一道独立的闸门，而不是一个动作的三个说法。「影子只决策不执行」这一格的意义常被低估：它让新版本在没有真实后果的环境里先暴露「想法」和旧版差多少。「盯成功率与成本」与「越线自动停放量」必须成对出现——只盯不自动停，等于把刹车交给人去盯盘，半夜出事没人踩。

:::figure 一次发布前要备好的五件事
@stack
版本组合清单::提示、模型、路由、工具结构各自的版本号
差异记录::影子阶段新旧决策不一样的地方逐条留痕
监控指标::任务成功率、越权率、延迟、单任务成本
停止放量阈值::指标恶化到什么程度就自动刹车
回退落点::退回后配置写在哪、由谁读得到
:::

五格里最容易缺的是「版本组合清单」和「回退落点」。前者决定事后能不能准确回答「某次请求用了哪一套」；后者决定回滚是不是真的落地了——只把内存里的指针拨回旧版，进程一重启又被新配置覆盖，等于没退。

:::figure 两种发布姿势的差别
@compare
一步切全量::出问题才被发现|影响所有请求|退回只能改代码
影子加灰度加回滚::先在无损失处暴露|影响面可控|按版本号快退
:::

左边是「改一下推全量」的朴素做法，顺风顺水时最省事；右边是把发布当成一段有观察、有刹车、有退路的路径。二者的差距，全在「出问题的那一刻能不能收得住」。

## 层层追问

:::ask 那如果影子阶段什么异常都没看出来，问题到小流量才冒出来呢？
:::

这完全正常，而且恰恰说明为什么影子之后仍要留一道小流量。影子覆盖的是「决策差异」：同样的输入，新版本打算做什么、和现用版本有没有不同。它照不到真实执行链路里的东西——下游此刻的状态、并发下的争抢、缓存是否命中、真实的副作用是否被接受、长尾输入长什么样。所以影子不能替代小流量，它只是把最粗暴的差异先筛掉一层。到了小流量这一步，盯什么指标就成了关键：只看请求量和通用错误率远远不够，Agent 更该盯的是「任务有没有做成、有没有越权、每成功一个任务花多少钱、尾延迟有没有恶化」，因为一次看似正常的返回，可能背后是绕了远路、重试了几次、把成本悄悄抬上去了。这几类指标怎么定义、为什么不按每次调用算账，在 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 里有展开；把「过程是否合理」也算进评价，可以对照 [结果评测与轨迹评测](./k089-trajectory-eval.md)。发布前那套固定用例集和阈值卡住「这版能不能进小流量」，则是 [回归门禁与基线](./k091-regression-gate.md) 要管的。一句话：影子看想法，小流量看后果，两者不能互相顶替。

:::ask 那如果出问题的其实是「配置」，而不是代码呢？
:::

这是最容易被漏掉、也最贵的一问。很多团队把「回滚」默认理解成「把代码退回上一个提交」，可真正改变 Agent 行为的，往往根本不在代码里：一段提示词、一次模型版本切换、工具描述的措辞、路由规则、甚至评估集本身。只退代码，配置还停在新版，服务会以「旧代码 + 新配置」这种谁都没测过的组合继续跑，比不回滚更难排查。所以提示、策略、结构描述、路由规则都要当可部署的产物各自版本化，并且要让每一条请求都能回答「它当时用的是哪一套组合」，这部分会在 [提示与策略版本化](./k113-prompt-versioning.md) 里单独讲；接口与结构随时间悄悄变化带来的漂移，也可对照 [版本漂移与升级策略](./k084-version-drift.md)。还有两个细节：回滚动作本身要留痕、且要能重复执行而不产生二次破坏，这点和 [幂等落盘](./k107-idempotent-persist.md) 的稳标识是同一套思路；分流规则也得稳定，同一个用户或同一笔请求不能一会儿被划到新版、一会儿被划回旧版，否则指标对比会被搅乱——演示代码里用「对标识取模得到固定的桶」而不是每次现抽一个随机数，正是为了这条。把「退回上一版」做成一个写进配置、可查、可重放的确定性动作，而不是有人临时敲几行命令，才算真的能退。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用本地模拟下游与一份配置快照，完整演示「影子零执行—按确定性桶放小流量—失败率越线自动按版本号回滚」，结尾用一组断言逐条验证。分流用请求编号取模，结果可手工推算、可复现；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path


def number_of(req_id):
    """从 req-007 这样的标识取编号，让分流结果可手工推算。"""
    return int(req_id.split("-")[1])


def bucket(req_id):
    """0~99 的分流桶；真实系统对标识做哈希，这里用编号便于复现。"""
    return number_of(req_id) % 100


def decide(version, req_id):
    """本地模拟下游：候选版对六成输入会出问题，其余与旧版一样正常。"""
    if version == "v2" and number_of(req_id) % 10 < 6:
        return "FAIL"
    return "OK"


def execute(req_id, version, outcome, ledger):
    """真正执行：把这次动作记进账本，产生一次可观察的副作用。"""
    ledger.append((req_id, version, outcome))


class Release:
    """版本生效状态，并把每次变更写进配置快照。"""

    def __init__(self, path, active="v1"):
        self.path = Path(path)
        self.active = active
        self.previous = None
        self.candidate = None
        self.candidate_percent = 0
        self._write()

    def _write(self):
        self.path.write_text(json.dumps({
            "active": self.active,
            "previous": self.previous,
            "candidate": self.candidate,
            "candidate_percent": self.candidate_percent,
        }, ensure_ascii=False, sort_keys=True), encoding="utf-8")

    def set_candidate(self, version, percent):
        """登记候选版与流量占比；占比为零时即影子：只决策不执行。"""
        self.previous = self.active
        self.candidate = version
        self.candidate_percent = percent
        self._write()

    def rollback(self):
        """撤掉候选版，按上一版版本号退回，并把生效版本写回配置。"""
        self.active = self.previous
        self.candidate = None
        self.candidate_percent = 0
        self._write()

    def version_for(self, req_id):
        """按确定性桶分流：命中的走候选版，其余走当前生效版。"""
        if self.candidate is not None and bucket(req_id) < self.candidate_percent:
            return self.candidate
        return self.active


def run_shadow(req_ids, candidate):
    """影子：候选版照常决策，但不调用 execute，账本一笔不动。"""
    decisions = []
    for r in req_ids:
        decisions.append((r, decide(candidate, r)))
    return decisions


def run_canary(release, req_ids, ledger):
    """小流量：按分流结果真正执行，并分版本统计处理数与失败数。"""
    stats = {"v1": [0, 0], "v2": [0, 0]}
    for r in req_ids:
        version = release.version_for(r)
        outcome = decide(version, r)
        execute(r, version, outcome, ledger)
        stats[version][0] += 1
        if outcome == "FAIL":
            stats[version][1] += 1
    return stats


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "release.json"
        req_ids = ["req-%03d" % i for i in range(200)]
        ledger = []
        release = Release(path, active="v1")

        release.set_candidate("v2", 0)
        decisions = run_shadow(req_ids, "v2")
        shadow_fail = sum(1 for _, outcome in decisions if outcome == "FAIL")
        checks = [
            ("影子阶段零副作用", len(ledger) == 0),
            ("影子阶段记录了全部决策", len(decisions) == len(req_ids)),
            ("影子阶段就发现候选版会失败", shadow_fail > 0),
            ("影子阶段候选占比为零", release.candidate_percent == 0),
            ("影子不改生效版本", release.active == "v1"),
        ]

        release.set_candidate("v2", 10)
        stats = run_canary(release, req_ids, ledger)
        seen = stats["v2"][0]
        fail_rate = stats["v2"][1] / seen if seen else 0.0
        checks.append(("候选版只分到二十条小流量", seen == 20))
        checks.append(("其余流量仍走稳定旧版", stats["v1"][0] == 180))
        checks.append(("旧版零失败", stats["v1"][1] == 0))
        checks.append(("候选版失败率明显恶化", fail_rate > 0.3))
        checks.append(("灰度阶段确实产生了副作用", len(ledger) == 200))
        checks.append(("同一请求分流结果稳定", all(
            release.version_for(r) == release.version_for(r) for r in req_ids)))

        if fail_rate > 0.3:
            release.rollback()
        checks.append(("越线后撤掉候选版本", release.candidate is None))
        checks.append(("回滚后生效版本退回 v1", release.active == "v1"))
        checks.append(("回滚写进配置快照", json.loads(path.read_text(encoding="utf-8"))["active"] == "v1"))

        after = run_canary(release, req_ids, ledger)
        checks.append(("回滚后全部请求走 v1", after["v1"][0] == 200))
        checks.append(("回滚后不再有失败决策", after["v1"][1] == 0))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `number_of` 与 `bucket` 用请求编号取模得到 0~99 的固定桶。真实系统会对标识做哈希再取模，免得调用方猜到规律、刻意挤进新版；这里用编号纯粹是为了让每个请求落在哪个桶可以手算、结果完全可复现。
2. `decide` 是本地模拟的下游：候选版 `v2` 对六成输入返回 `FAIL`，旧版 `v1` 一律 `OK`。它被刻意做成确定性的，好让「失败率越线」这件事稳定发生，不靠碰运气。
3. `execute` 代表真正产生副作用的那一步，往 `ledger` 里记一笔。`run_shadow` 从头到尾都不调用它，`run_canary` 每条都调用它——「影子零执行」和「小流量真执行」的对比，就落在这一行调用的有无上，而不是靠一个永远返回零的变量。
4. `Release` 把「当前生效版、上一版、候选版、候选占比」四样状态写进配置快照（JSON，JavaScript Object Notation，一种纯文本的数据表示格式）。`rollback` 做的事很朴素：把生效版拨回 `previous`、撤掉候选、占比归零、并把结果写回文件——注意它写的是配置，不是改代码，这正是「按版本号退回」的落点。
5. `set_candidate("v2", 0)` 把占比设成零，于是 `version_for` 里 `bucket < 0` 永不成立，影子阶段的候选版分不到任何执行流量；`set_candidate("v2", 10)` 之后，编号落在前 10 个桶的请求才走 `v2`。两百条请求里恰好二十条分到候选版，其余一百八十条仍走 `v1`。
6. `main` 先在影子阶段断言账本为空、决策被完整记录、且已经能看出候选版会失败、生效版本没被改动；再在小流量阶段断言分流条数、旧版零失败、候选版失败率越线、账本确实多了两百笔、同一请求两次分流结果一致。
7. 失败率超过 0.3 就触发 `rollback`，随后断言候选被撤、生效版本退回 `v1`、配置快照里也写成了 `v1`；最后再跑一遍，确认全部请求都走 `v1`、不再出现失败决策。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用编号取模代替了真实哈希、用本地文件代替了配置中心、用一段确定性函数代替了真实下游，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是停放量、分流稳定性与版本退回的顺序，不是任何具体发布平台的实现。

## 踩坑与边界

- **固定用例一过就切全量**：现象是本地挑的几条都对，真实流量里脏数据、长尾输入、并发一上来就翻车 → 原因是测试覆盖不了真实链路 → 先影子暴露差异，再小流量按指标逐步放量，别把「测过」当成「可以全上」。
- **影子阶段偷偷执行了副作用**：现象是号称只观察，结果新版本照样发了通知、写了记录，和「零损失」的预期相反 → 原因是影子路径复用了正常执行路径、忘了掐掉执行那一步 → 影子只产出决策并留痕，执行入口显式关闭，并用账本为空这类断言验一遍。
- **灰度只看请求量和错误率**：现象是错误率没变，任务却悄悄做不成、越权冒头、单任务成本翻倍 → 原因是盯的指标和 Agent 的成败不对齐 → 把任务成功率、越权率、尾延迟、按成功任务核算的成本一并纳入，参考 [核心指标与按成功任务核算成本](./k096-metrics-cost.md)。
- **只能回滚代码、不能回滚配置**：现象是代码退了，提示词、模型版本、路由规则还停在新版，跑出一个谁都没测过的组合 → 原因是把配置当成了散落的字符串 → 每样可部署产物各自版本化，回滚写进配置且可查，见 [提示与策略版本化](./k113-prompt-versioning.md)。
- **分流规则不稳定**：现象是同一用户一会儿在新版一会儿在旧版，指标对比被搅乱、体验割裂 → 原因是每次现抽随机数 → 对稳定标识做确定性分桶，同一请求始终落在同一个桶，必要时按用户而不是按请求分。

还要分清两道刹车：小流量阶段盯的是「这版在真实链路里的后果」，影子阶段盯的只是「它想干什么」，谁都替代不了谁；而「自动停放量」与「自动回滚」也不是一回事，前者只是不再把更多流量送进新版，后者是把已经在用新版的请求也拨回上一版，退得更彻底。指标越线要有明确的判定线并提前写进配置，别等有人半夜盯盘才手动踩刹车——这与 [健康检查与 SLO](./k114-health-slo.md) 里「让外部能探知状态、给目标定可守护的线」是同一套思路。若想从整体上看这套教程怎么组织，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

影子模式、灰度与回滚，是把「一次改动推给所有人」拆成先在零损失处看差异、再放小流量看后果、指标越线就按版本号退回上一套配置的一段有闸门的路径。

关键做法是影子只决策不执行、分流用稳定标识做确定性分桶、盯任务成功率与越权率与成本、把停放量阈值和回退落点都写进可查的配置。

当改动只影响离线产物、或系统根本没有真实流量可分时，不必硬套这套发布链路；但只要一次改动会改变对外行为，它就不该被当成一步到位的切换。

# 代码沙箱与隔离

## 场景提问

你给 Agent 加了一个「跑一小段代码来算数据」的能力，让它做统计、验算、把表格汇总成数字，用起来很顺手。可没过几天，一件让你后怕的事发生了：模型被用户贴进来的一段文本带着，拼出了一段会去翻环境变量、读同机其他配置、再往外发一次请求的脚本；更要命的是，这段脚本是在和你主服务共享磁盘、共享网络、共享登录凭据的那个进程里跑起来的，一旦执行，等于把整台机器的权限都交了出去。你复盘时想「我不是说过它只能做算术吗」，翻回去一看，那只是写在提示里的一句话，真正执行到那一刻，没有任何东西拦得住它。到底是哪里出了界，又该怎么把「跑代码」这件事真正关进笼子？

## 破误解

**不是限制写得不够细，是把「写在提示里的规矩」当成了「执行当刻真的存在的边界」——提示能劝，拦不住，代码跑起来的那一瞬间需要的是一道硬边界。**

先把「沙箱」这个词说清楚。沙箱（sandbox，一个与主系统隔开的受限运行环境）不是「换个文件夹放代码」，也不是「另起一个进程」这么简单；它要同时立起三道彼此独立的边界，缺一道就等于没有。第一道是能力边界：这段代码能碰什么、不能碰什么，得逐项列出来，文件读写、对外连接、进程创建、环境变量、模块导入、系统时间，凡没被明确允许的，一律不可达。第二道是资源上限：即便只允许它做算术，一个死循环、一次超大内存分配、一份把磁盘撑爆的输出，照样能把整台机器拖垮，所以运行时长、中央处理器（Central Processing Unit，CPU）时间、内存、输出体积都得有硬顶，超了就掐断。第三道是受控出口：代码算出来的结果不能由它自己想写到哪就写到哪，必须通过一条被登记的窄通道回传，而且执行过程中产生的副作用要能清零——临时文件要能收回，写过的东西要能撤销，连「它到底干了什么」都得逐条留痕。

很多人把这三道边界压成一句「我限制过它了」，可这句话如果落在提示里，就只是给模型的一个建议。模型会被绕、会理解偏、会在长上下文里把这条忘掉，甚至被一段外来文本牵着生成完全相反的代码，这类挟带在素材里的恶意指令属于 [间接提示注入](./k098-indirect-injection.md) 要处理的事。真正的边界必须由执行侧的代码来守，脚本走到哪一步都会被实际检查一次，而不是靠模型自觉。这也正是 [护栏放在代码里](./k106-guardrail-in-code.md) 反复强调的：能被一句话说服的都不算边界，能被 `if` 挡下来、能被断言验出来的才算。还有一层容易漏：隔离是「默认什么都不给、再按需发放」，不是「默认全给、再逐个去禁」。去禁的清单永远列不全，语言里能摸到系统的花样太多；反过来，只发放算数、读指定变量、返回数值这几样，剩下的天然不可达。这套「默认拒绝、按需授予」的思路，和 [最小权限与双层校验](./k100-least-privilege.md) 是同一件事的两种说法。

## 生活类比

把它想成化工厂里的隔离操作箱，也叫手套箱。操作员要处理一种不能暴露在车间空气里的物料，于是把它放进一个完全密闭的透明箱子：箱子有自己独立循环的一层气，不和外面的空气互通；操作员的双手通过箱壁上密封固定的橡胶手套伸进去摆弄，能做的动作就只有手套能完成的那些抓、挪、倒；想递进一把工具、取出一样成品，都得走侧面的传递窗，每进每出都要登记；箱内的压力被刻意调得比外面低，万一哪里有了缝隙，也只会是外面的气往里灌，箱里的东西漏不出去；正对操作员的那面是厚玻璃，全程看得见里面发生了什么。

对应关系一处一处摆出来：密闭箱体和独立气路，就是与主进程隔开的命名空间与运行环境，代码看不到宿主的文件树、网络和凭据；那双橡胶手套，就是被逐项发放的能力白名单——手能伸进去，但只能做手套允许的有限动作，摸不到箱壁之外的任何开关；箱内的负压，就是越权时影响被向内收束而不外溢，哪怕代码里藏了坏心思，破坏也被关在箱子里；侧面那道每进出都登记的传递窗，就是受控出口和副作用登记，算出来的结果只能从这里、以约定的格式送出来，顺带记下「谁在什么时候递出了什么」；那面厚玻璃，就是可观测性，执行过程要能被记录、被回放，可对照 [结构化日志与轨迹回放](./k095-structured-log.md)。这个比喻还点破了一个最容易被忽略的细节：安全的不是「操作员是个好人」，而是「就算操作员判断错了、或被外面的人骗了，箱子这个结构本身也兜得住」。放到系统里，就是别指望模型每次都生成规矩的代码，而要指望那道边界在任何一次生成失误时都还在。

## 自绘示意图

:::figure 一次受限执行的完整链路
@flow
接收不可信代码|静态检查语法白名单|按配额扣减资源|受控求值不碰系统|结果经窄口登记回传
:::

这张图里每一格都是一次真实的检查点，不是「隔离」这个词的四种说法。第二格最容易被跳过：在代码跑之前先把它的语法树整个扫一遍，凡出现导入、函数调用、属性访问这类节点就直接挡掉，比等它跑起来再抢着拦要稳妥得多。第三格和第四格要成对——先扣配额再求值，是为了让「跑得太久、算得太大」在动手之前就被掐住。

:::figure 隔离要同时立起的三道边界
@stack
能力边界::逐项发放可碰的东西，未列出的默认不可达
资源上限::时长、内存、输出体积各有硬顶，超了即掐断
受控出口::结果只走被登记的窄通道回传，格式受限
副作用清零::临时产物可回收，越权路径不产生真实写入
全程留痕::执行动作逐条记录，便于回放与归因
:::

五格里最常被漏掉的是「副作用清零」和「全程留痕」。前者决定一次被拒绝的尝试是不是真的零后果，后者决定出事之后能不能回答「它到底试过什么」。光有能力边界而没有清零，恶意代码被拦之前可能已经写下了东西；光有拦截而没有留痕，连该从哪查起都不知道。

:::figure 两种执行姿势的差别
@compare
主进程里直接跑::共享全部权限|出错即全量受损|事后无从回退
关进隔离沙箱::能力默认不给|影响收束在箱内|结果可查可撤销
:::

左边是「方便就行」的朴素做法，顺风顺水时最省事；右边是把执行当成一段有边界、有配额、有出口、有留痕的路径。二者的差距全在「代码不按你想的来」的那一刻兜不兜得住，而不是平时跑得有多快。

## 层层追问

:::ask 那如果把运行环境里的内建函数全清空，是不是就安全了？
:::

远远不够，而且这是个很典型的误会。清空内建函数只是收走了摆在最表面的一批工具，语言本身的对象模型还在：从一个普普通通的字面量出发，顺着它的类型、基类、子类这些关系往上摸，往往能重新够到模块加载、文件读写这类能力。这类「看着只是拿了个属性、其实绕到了系统」的路径，静态扫语法树时未必都能一眼认全。所以隔离不能只靠「在进程里做限制」这一层，得往上再叠一层真正独立的运行边界——独立进程、独立命名空间、受限的系统调用、与宿主不共享的文件与网络，让「就算在语言里绕出来了，绕出来也还是在一无所有的空房间里」。这里有个很实在的判据：如果一段代码能读到宿主的环境变量、能连到内网地址、能看到别的租户留下的文件，那不管你清了多少内建函数，隔离都是失败的。层数比技巧重要，一层被绕过还有下一层托着；只做一层，就等于把全部赌注押在「它绕不过去」上。也正因为进程内限制靠不住，把「决定要做什么」和「真正去做」拆到两个互不共享状态的地方才显得要紧，这是 [逻辑层与执行层解耦、动作白名单](./k148-decouple-allowlist.md) 里要展开的。

:::ask 那如果沙箱里的代码确实需要读一份文件、或者调一次工具呢？
:::

这就要把「隔离」和「断绝」分清楚：隔离不是什么都不让做，而是「只让你做被明确批准的那几样，且每一样都走被管住的通道」。需要读文件，就给它一个事先准备好的、只读的、只装着这一份数据的目录，而不是把整个家目录挂进去；需要一次外部能力，就把这次调用收敛成一个参数受限、目标受限的动作，由执行侧按白名单核对后再代办，结果按约定格式送回来，而不是把网络能力整个放开。关键在于「最小的一次授予」而不是「方便的一整片权限」：给的是一个具体的数据、一次具体的动作，不是一类资源、一个账户。这里还牵出一个容易被忽略的点——沙箱里用的身份不能是宿主的身份。若执行时继承了主服务的凭据，那么哪怕文件与网络都被挡了，代码也可能借着这份身份去访问本不该碰的东西，所以身份要在服务端按当次请求单独注入、且只带当次所需，这与 [用户身份服务端注入](./k137-identity-injection.md) 是同一套规矩；而资源那一头的时长、内存、调用次数分别与谁对齐、为什么不能只设一个总数，则是 [四重预算](./k103-four-budgets.md) 讲的事。还有一句要记牢：沙箱里算出来的结果依然是「不可信数据」，回传之后仍要按结构校验、按内容扫描，不能因为「它是自己跑出来的」就直接当成可信结论。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，做一个极小的「受限表达式求值器」来演示沙箱的三道边界。用抽象语法树（Abstract Syntax Tree，AST，把代码拆成一棵结构树便于逐节点检查）做静态白名单，自己写递归求值、绝不调用 `eval` 或 `exec`，再用节点预算模拟资源上限、用一个登记列表模拟受控出口。全程不碰文件、不联网、不需要任何第三方包或账号，复制到装有 Python 的机器上直接运行即可，结尾用一组断言逐条验证。

```python
import ast

ALLOWED_BIN = (ast.Add, ast.Sub, ast.Mult, ast.Div)
ALLOWED_UNARY = (ast.UAdd, ast.USub)


class SandboxDenied(Exception):
    """沙箱拒绝执行时抛出的受控异常，携带可读原因。"""


def check_tree(node, allowed_names, budget):
    """静态遍历语法树：任何不在白名单的节点或名字一律拒绝，同时累计节点预算。"""
    budget[0] += 1
    if budget[0] > budget[1]:
        raise SandboxDenied("节点数超出预算")
    if isinstance(node, ast.Expression):
        check_tree(node.body, allowed_names, budget)
        return
    if isinstance(node, ast.Constant):
        if isinstance(node.value, bool) or not isinstance(node.value, (int, float)):
            raise SandboxDenied("只允许数值字面量")
        if abs(node.value) > 10 ** 6:
            raise SandboxDenied("字面量超出数值上限")
        return
    if isinstance(node, ast.Name) and isinstance(node.ctx, ast.Load):
        if node.id not in allowed_names:
            raise SandboxDenied("引用了未登记的名字")
        return
    if isinstance(node, ast.BinOp) and isinstance(node.op, ALLOWED_BIN):
        check_tree(node.left, allowed_names, budget)
        check_tree(node.right, allowed_names, budget)
        return
    if isinstance(node, ast.UnaryOp) and isinstance(node.op, ALLOWED_UNARY):
        check_tree(node.operand, allowed_names, budget)
        return
    raise SandboxDenied("出现不允许的语法: " + type(node).__name__)


def evaluate(node, env):
    """静态检查通过后才调用：自己写递归求值，绝不把代码交给 eval/exec。"""
    if isinstance(node, ast.Constant):
        return node.value
    if isinstance(node, ast.Name):
        return env[node.id]
    if isinstance(node, ast.UnaryOp):
        v = evaluate(node.operand, env)
        return +v if isinstance(node.op, ast.UAdd) else -v
    left = evaluate(node.left, env)
    right = evaluate(node.right, env)
    if isinstance(node.op, ast.Add):
        return left + right
    if isinstance(node.op, ast.Sub):
        return left - right
    if isinstance(node.op, ast.Mult):
        return left * right
    if right == 0:
        raise SandboxDenied("除数为零")
    return left / right


def run(expr, env, ledger, node_limit=40):
    """一次受控执行：解析 → 静态检查 → 求值 → 结果只经被登记的窄口回传。"""
    try:
        tree = ast.parse(expr, mode="eval")
        check_tree(tree, set(env), [0, node_limit])
        value = evaluate(tree.body, env)
    except SandboxDenied as exc:
        return "拒绝", str(exc)
    except SyntaxError:
        return "拒绝", "语法错误"
    ledger.append((expr, value))
    return "通过", value


def main():
    env = {"x": 10, "y": 3}
    ledger = []
    checks = []

    ok, value = run("x * 2 + y", env, ledger)
    checks.append(("合法表达式能算出正确结果", ok == "通过" and value == 23))
    checks.append(("合法结果经窄口登记且仅一条", len(ledger) == 1))

    checks.append(("函数调用被静态检查拒绝", run("__import__('os')", env, ledger)[0] == "拒绝"))
    checks.append(("属性访问被静态检查拒绝", run("().__class__", env, ledger)[0] == "拒绝"))
    checks.append(("未登记的名字被拒绝", run("z + 1", env, ledger)[0] == "拒绝"))
    checks.append(("除数为零被受控拒绝", run("x / 0", env, ledger)[0] == "拒绝"))
    checks.append(("超出节点预算被拒绝", run("+".join(["1"] * 60), env, ledger)[0] == "拒绝"))
    checks.append(("超大字面量被拒绝", run("99999999", env, ledger)[0] == "拒绝"))
    checks.append(("字符串字面量被拒绝", run("'abc'", env, ledger)[0] == "拒绝"))
    checks.append(("所有拒绝都没有产生副作用", len(ledger) == 1))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `ALLOWED_BIN` 与 `ALLOWED_UNARY` 是能力白名单的具象：只允许加减乘除和正负号。除法、幂运算、位运算、比较、函数调用全都不在表里，这体现的是「默认什么都不给，只发放这几样」，而不是「先全给再逐个去禁」。
2. `SandboxDenied` 是统一的拒绝出口。所有越界都收敛成同一种受控异常，携带一句可读原因，既不把真实异常栈泄露给外面，也方便逐条留痕，这正对应「拒绝要能被记录、能被回放」。
3. `check_tree` 是能力边界的执行者：它把代码拆成语法树，从头到尾逐节点走一遍，`Expression`、`Constant`、`Name`（且只限读取）、白名单里的 `BinOp` 与 `UnaryOp` 才放行，其余一律抛拒绝。注意它是在「跑之前」检查，所以 `__import__` 这类调用连被执行的机会都没有。
4. 同一个函数开头的 `budget[0] += 1` 与 `budget[0] > budget[1]` 是资源上限的缩影：每经过一个节点就扣一点配额，超过上限立刻掐断。真实沙箱扣的是时长、内存、输出体积，这里用节点数代替，为的是让「算得太大就被拒」这件事不靠碰运气、可手工推算。
5. `Constant` 分支里那两道判断，分别把「非数值字面量」和「数值过大」挡在外面：布尔值因为属于整数的子类要专门排除，字符串、列表一律不要，绝对值超过上限也拒绝。这演示的是「连能输入什么都管住」，免得用一串超长常量把内存吃满。
6. `evaluate` 是受控求值的实现：只处理已经通过静态检查的几类节点，自己递归算出数值，**从头到尾不调用 `eval` 或 `exec`**。这一点很要紧——把不可信代码交给语言自带的执行入口，等于把前面辛辛苦苦立的边界又拆了；自己解释一棵受限的树，边界才真的握在手里。除数为零也在这里被收成受控拒绝，而不是让一次崩溃把流程带走。
7. `run` 把三道边界串成一条链：解析、静态检查、求值，任何一步拒绝都直接返回、不做任何登记；只有全部通过的结果才 `ledger.append` 进那条窄口。`ledger` 就是受控出口与副作用登记——被拒绝的尝试不会在里面留下一笔，这正是「越权路径零后果」的可验证形式。
8. `main` 用十条断言把性质逐条钉死：合法表达式算得对且只登记一条、函数调用与属性访问与未登记名字都被静态拒绝、除零与超预算与超大字面量与非数值字面量都被受控拒绝、最后确认所有拒绝加起来仍然「零副作用」。结尾 `assert` 保证任何一条边界被破坏都会以非零状态退出。

有一处要如实说明：这里用「节点数」代替真实资源配额、用「语法树白名单」代替独立进程与系统调用限制、用一个登记列表代替受控回传通道，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是「能力边界 + 资源上限 + 受控出口」这三道边界怎么配合，不是任何具体隔离产品的实现；真实环境里那道「独立运行边界」必须落在进程或更强的隔离机制上，不能只靠进程内的语法检查——这正是上一节追问里讲清楚的那层。

## 踩坑与边界

- **把提示里的限制当成执行边界**：现象是提示写了「只准做算术」，模型却生成了读文件、发请求的代码且真的跑了 → 原因是提示只能劝、没有任何代码在执行当刻拦截 → 把边界挪到执行侧，用语法白名单与动作白名单逐次核对，参照 [护栏放在代码里](./k106-guardrail-in-code.md)。
- **只清内建函数就以为安全**：现象是禁掉了一批常用函数，代码仍能顺着对象关系绕到模块加载或文件读写 → 原因是进程内的限制挡不住语言自身的对象模型 → 往上叠真正独立的运行边界，独立进程、不共享宿主文件与网络、受限系统调用，别把赌注全押在「它绕不过去」。
- **继承了宿主的身份与凭据**：现象是文件和网络都挡了，代码却借着主服务的凭据访问到了本不该碰的资源 → 原因是执行环境沿用了宿主的登录态 → 身份按当次请求由服务端单独注入、只带当次所需，见 [用户身份服务端注入](./k137-identity-injection.md)。
- **只设能力不设上限**：现象是没做任何越权动作，一个死循环或一份超大输出就把机器拖垮了 → 原因是「能碰什么」和「能花多少」是两回事 → 时长、内存、输出体积、调用次数各设硬顶，超了即掐断，思路见 [四重预算](./k103-four-budgets.md)。
- **把沙箱输出当成可信结论**：现象是「反正是在隔离环境里自己算出来的」，结果没校验就直接进了下一步甚至被写进长期记忆 → 原因是隔离只保证破坏被关住，不保证内容正确或无害 → 回传之后仍按结构校验、按内容扫描，并给它标上来源，别让不可信数据悄悄升级成可信指令。

还要分清三件容易混的事：隔离管的是「这段代码能造多大破坏」，最小权限管的是「该发给它哪几样能力」，结果校验管的是「它送出来的东西能不能信」，谁都替代不了谁。另外，沙箱不是越严越好——把能力收到连正事都办不了， Agent 就会绕开它去用别的工具，反而更危险；合理的做法是先想清楚这次执行到底需要哪几个具体的数据与动作，只发这几样，其余按默认拒绝处理。跨会话之间还得再隔一层，别让一次执行留下的临时产物被下一个用户读到，这是 [会话隔离与租户边界](./k105-session-isolation.md) 要接着讲的；而执行超时之后「到底算没算完、副作用发没发生」，则要和 [超时不等于没执行](./k039-timeout-reconcile.md) 一起看。

- [ ] 能解释为什么写在提示里的限制不算边界，以及「默认拒绝、按需授予」为什么比「逐个去禁」稳

## 三句话小结

代码沙箱与隔离，是把「让模型生成的代码直接跑在主服务里」改成「先收走全部能力、再只发当次所需、给它资源硬顶、结果只从被登记的窄口回来」的一段受控执行路径。

关键做法是边界落在执行侧的代码里而非提示里、用语法白名单与动作白名单逐次核对、叠一层真正独立的运行边界、身份按请求单独注入、结果回传后仍按结构校验与内容扫描。

当执行的是自己写的、完全可信且无需处理外部输入的一小段固定逻辑时，不必硬套这套隔离；但只要代码里有一字来自模型生成或用户输入，就不该让它和主服务共享文件、网络与凭据。

# 健康检查与 SLO

## 场景提问

你把一个 Agent 服务接到了对外入口，监控面板上一片绿：每个探测都秒回，接口也都返回了成功状态，看起来一切正常。可用户投诉不断涌进来，说「任务根本没办成」「等了很久才给一句答非所问的结果」。你正想解释，另一头又出事了：某个下游依赖只是慢了几秒，负责分发请求的部件把所有实例都判成「不健康」，挨个重启了一遍，本来只是慢一点，结果变成谁都接不了活。你盯着那块绿油油的面板发愣：明明每个探测都是好的，为什么既没发现「事情没办成」，又反过来把自己折腾垮了？

## 破误解

**不是监控没接，是把「进程还活着」当成了「服务在兑现承诺」，又把「依赖慢了一点」当成了「实例该重启」。**

先说清几个词。健康检查（health check）是一个轻量的探测接口，让负责分发请求的部件、编排系统或调用方能快速问一句「这个实例现在还能不能接活」；发起这一问的那一小段逻辑常叫探针（probe）。它通常分成两种，别混着用：存活（liveness，进程还在不在、能不能应答）答不上来，才该考虑把这个实例重启；就绪（readiness，能不能接新的请求，比如预热有没有做完、是不是正在被摘流量）不满足，只该把它从接活的名单里暂时摘掉，而不是重启。另一头，SLO（Service Level Objective，服务等级目标）是对外承诺的一段可量化目标，比如「一段窗口内，达成任务的请求占比不低于某个数、且延迟不超过某个上限」；量它的尺子叫 SLI（Service Level Indicator，服务等级指标），也就是「到底怎么算一次达标」。把目标换算成「这段时间还允许几次不达标」，得到的就是误差预算（error budget）。它们和纯监控的差别在于：监控只是把数字摆出来给人看，服务等级目标先定一条线，再围绕这条线算出还能花多少额度，额度充足才允许改动、额度快花完就先稳住。很多人把面板全绿当成「没问题」，可面板量的是「有没有返回」，不是「事情办成没有」——对 Agent（智能体，一类能自己决定下一步调用哪个工具、把任务接着往下做的程序）来说，一次看似正常的返回背后，可能是绕了远路、重试了几次、甚至悄悄越了权。还有一层同样常被忽略：探针自己也是程序，如果它在被问的时候要顺路把整条依赖链都查一遍，那么依赖一抖，所有实例会同时被判不健康，重启又带来更多压力，小抖动被放大成全站不可用。要补的不是「多接几个监控」，而是把两件事分开做对：让探活浅、快、结果确定、只回答「此刻能不能接活」；让服务等级目标按窗口、按「任务是否达成」来算，并把额度和发布动作绑在一起。

## 生活类比

把它想成一家餐厅开门与它门口贴的那张承诺。每天早上开门前，店员只做几下很快的检查：灯亮不亮、燃气有没有、门能不能推开、当班的灶是不是已经热好。这几下决定「今天能不能迎客」——灯不亮（存活出问题）得叫人修、先把店关一会儿；灶还没热（就绪没完成）就先别放客人进来，等热好再说，用不着把整间店拆了重装。店员绝不会在开门前把全城的供应商、冷链、支付通道逐个打电话核一遍，那样只要有一家电话占线，今天就被误判成「开不了门」。另一头，店门口贴着一张长期承诺：一个月里至少有多少比例的订单能在约定时间内上齐；店长手里还有个小本，记着「这个月还能允许几次没达标」。本子上的额度还宽裕，就敢试新菜、换供应商、调整排班；额度快见底了，就先别折腾，把稳定补回来。对应关系很具体：开门前那几下，就是浅层探活；「灯不亮要修」与「灶没热先别放人」的分别，就是存活判定与就绪判定分别触发重启和摘流量；顺手把全城供应商查一遍导致误判，就是探针引入的级联故障；门口那张承诺，就是服务等级目标；「订单按时上齐的比例」，就是服务等级指标；小本上「还能允许几次」，就是误差预算；额度决定敢不敢换菜谱，就是发布闸门。这个比喻最要命的一处是：灯亮着、门开着、店员也站在这儿，完全不等于客人吃上了饭——和系统里「接口返回成功状态、面板全绿，任务却没办成」是同一件事。只看前者，就会在最该发现问题的时候一片乐观。

## 自绘示意图

:::figure 一次探活判定该走的顺序
@flow
接到探测请求|查自身与本地态|就绪才放进流量|存活失败才重启|结果秒级返回
:::

中间三格的次序不能乱。「查自身与本地态」这一格被刻意写得很窄：它只看这个实例自己的进程与本地标记，不顺着去问数据库、模型服务、下游接口。第三格和第四格是两种完全不同的处置——没就绪只摘流量、不重启，存活真答不上来才重启；把它们合并成一个「健康 / 不健康」的开关，预热中的实例就会被反复重启、永远热不完。最后一格提醒探针要快，慢吞吞的探测本身会变成新的等待来源。

:::figure 两套机制分别要定清楚的事
@stack
存活判定::进程能否应答，长时间无响应才考虑重启
就绪判定::能否接新请求，未就绪只摘流量不重启
探测边界::不查外部依赖，防一处抖动放大成全站重启
服务等级指标::什么算有效请求、什么算一次成功
误差预算::允许不达标的额度，联动发布闸门
:::

五行里最容易被略过的是「探测边界」和「服务等级指标」。前者决定探针会不会把外部的一次抖动放大成自己的故障；后者决定你量的是「有没有响应」还是「事情办成没有」，口径一旦选错，后面算得再精确也只是在量错的东西。把「什么算有效、什么算成功」先写成一句不含歧义的话，比先挑图表样式重要得多。

:::figure 探活与服务等级目标各管什么
@compare
健康检查探活::秒级判此刻|只看单个实例|结果非此即彼
服务等级目标::按窗口看一段|覆盖整体请求|结果是达标比例
:::

左边是「此刻这一个还能不能接活」，右边是「一整段时间里整体有没有守住承诺」。二者粒度不同，谁都替代不了谁：探针全绿不代表目标达标，因为每个请求都可能返回了成功状态却没办成事；目标达标也不代表此刻没有实例该被摘掉。把它们当成同一件事，就会出现「面板很好看、用户很难受」或者「一处抖动、全站重启」这两种看似矛盾、其实同源的毛病。

## 层层追问

:::ask 那如果探针里顺手把数据库、模型服务、下游都查一遍，不是更准吗？
:::

恰恰相反，这会把一个局部的小抖动放大成全站故障。设想有十个实例，探针里都查了同一个下游；下游慢了几秒，十个探针几乎同时超时，分发部件于是判定「十个都不健康」，一起摘掉、甚至一起重启，重启后的实例又一起来查这个还没缓过来的下游，压力不降反增。本来只是「有点慢」，几步之后变成「谁都接不了活」，这类一环扣一环把故障放大的现象常叫级联故障。探针要浅，意思是它只回答「我这个进程还能不能应答、本地状态允不允许接新请求」，不回答「整条链路哪儿坏了」。再往下追一层：那如果只查自身，依赖真的挂了不就发现不了吗？不是不发现，是不交给探活去发现。依赖可达性该用带超时的独立诊断、结构化日志与轨迹记录去看，见 [结构化日志](./k095-structured-log.md) 和 [轨迹字段](./k094-trace-fields.md)；连续失败到了一定程度，用 [熔断](./k104-circuit-breaker.md) 把这个实例本地标成「暂时别接新活」，就绪探针读的是这个本地标记，而不是实时去探一遍下游。这样依赖出问题时，处置是「有序地少接活」而不是「集体重启」。探针的状态也要能被外部稳定读到，配合 [服务化封装](./k151-service-wrap.md) 把探测入口做成确定、无副作用的只读判断；至于超时与重试本身该怎么设限，可对照 [超时兜底](./k109-timeout-fallback.md) 与 [重试退避](./k108-retry-backoff.md)。

:::ask 那如果接口一直返回成功状态，服务等级指标里的「成功」该怎么算？
:::

这正是 Agent 场景里最容易算错的一处。返回成功状态只说明「有响应」，不说明「任务达成」：可能工具调用绕了远路、可能重试了几次才给个答非所问的结果、可能悄悄做了越权动作、也可能单任务成本翻了倍却仍返回正常。所以服务等级指标要先写死两件事：什么算一次有效请求（被取消的、明显无效的、探测请求本身要排除在分母外），以及什么算一次达标（任务被判定做成，且延迟不超过上限）。把「有没有响应」当成「有没有做成」，目标就会长期显示接近满分，而用户那边怨声载道。怎么把「做成」判准，可以参考 [按成功任务核算成本](./k096-metrics-cost.md) 与 [结果评测与轨迹评测](./k089-trajectory-eval.md)；把越权、绕路、成本异常一并算进评价，比只看一个非真即假的开关可靠得多。再往下追一层：那如果不同任务难度差很多，成功率放一起比会不会不公平？会，所以口径要分层：按任务类型或意图分组各自算，别用总量把难任务淹没；评估集的构成要稳定，否则这周简单用例多、下周难用例多，指标变化根本没法归因，这部分见 [评估数据集](./k086-eval-dataset.md) 与 [用例配比](./k087-case-mix.md)；口径定完还要用 [回归门禁与基线](./k091-regression-gate.md) 卡住它别悄悄漂。另外延迟别只看平均值，少数特别慢的请求会被平均值摊平，得把慢请求单独记一笔，或者看分位数（把耗时从快到慢排队，取靠后那一档的值），这在演示代码里就是把「达标」与「慢请求」分开统计的原因。窗口也要选滚动的一段，而不是自然月的月初到月末，免得月初的抖动和月底的补救被算成两个不同的世界。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一个本地类模拟实例的浅层健康状态，再用一批构造出来的观测记录演示「按滚动窗口算达标比例—扣误差预算—额度联动是否放行改动」，结尾用一组断言逐条验证。全文不读系统时钟、不联网、不用第三方包，记录里的时间与耗时都是构造的整数，结果可以手算核对；「每千次允许一次不达标」只是为了演示怎么算而设的目标，不代表任何真实系统的水平。

```python
import json

# 每千次有效请求里，最多允许几次「没达标」（这里取 1，相当于 99.9% 的目标）。
# 故意用整数千分比，避开小数浮点带来的边界误差，也方便手算。
ALLOWED_MISSES_PER_MILLE = 1
LATENCY_LIMIT_MS = 800


class Health:
    """一个服务实例的浅层健康状态。依赖状态只留作诊断，不参与探活判定。"""

    def __init__(self, alive=True, warm=True, dependencies_ok=True):
        self.alive = alive                      # 进程还能不能应答
        self.warm = warm                        # 是否完成预热、能否接新请求
        self.dependencies_ok = dependencies_ok  # 外部依赖，仅诊断用

    def liveness(self):
        """存活探针：只看自己还能不能应答，答不上才该被重启。"""
        return "UP" if self.alive else "DOWN"

    def readiness(self):
        """就绪探针：看能不能接新请求；刻意不查外部依赖，避免级联误判。"""
        return "READY" if (self.alive and self.warm) else "NOT_READY"

    def snapshot(self):
        """对外暴露的结构化状态，字段精简、结果确定、无副作用。"""
        return {
            "liveness": self.liveness(),
            "readiness": self.readiness(),
            "deep_dependency": self.dependencies_ok,
        }

    def action(self):
        """编排系统据探针该做的动作：重启 / 摘流量 / 正常接活。"""
        if self.liveness() == "DOWN":
            return "restart"
        if self.readiness() == "READY":
            return "serve"
        return "drain"


def valid_records(records, start_t, end_t):
    """按滚动窗口挑出有效请求：时间落在窗口内，且没被标成无效。"""
    return [r for r in records if start_t <= r["t"] <= end_t and r["valid"]]


def sli(records, start_t, end_t):
    """服务等级指标：窗口内「任务达成且延迟达标」占有效请求的比例。
    另返回慢请求数，专门盯被平均值藏起来的长尾。"""
    group = valid_records(records, start_t, end_t)
    good = sum(1 for r in group if r["ok"] and r["ms"] <= LATENCY_LIMIT_MS)
    slow = sum(1 for r in group if r["ok"] and r["ms"] > LATENCY_LIMIT_MS)
    ratio = good / len(group) if group else 0.0
    return {"total": len(group), "good": good, "slow": slow, "ratio": ratio}


def misses(records, start_t, end_t):
    """没达标次数 = 有效请求数 - 达标数；失败与超延迟都算没达标。"""
    m = sli(records, start_t, end_t)
    return m["total"] - m["good"]


def allowed_misses(total_valid):
    """误差预算：按整数千分比算，这一窗口允许几次不达标。"""
    return total_valid * ALLOWED_MISSES_PER_MILLE // 1000


def budget_left(records, start_t, end_t):
    """剩余误差预算：允许额度减去已经花掉的。"""
    m = sli(records, start_t, end_t)
    return allowed_misses(m["total"]) - misses(records, start_t, end_t)


def can_release(records, start_t, end_t):
    """发布闸门：预算还有剩才允许放量改动，超支就冻结。"""
    return budget_left(records, start_t, end_t) > 0


def make_records(n, bad_indices=(), slow_indices=(), invalid_indices=()):
    """构造一批可复现的观测记录：默认全部成功且很快。"""
    out = []
    for i in range(n):
        rec = {"t": i, "ok": True, "ms": 100, "valid": True}
        if i in bad_indices:
            rec["ok"] = False          # 接口照常返回，但任务没做成
        if i in slow_indices:
            rec["ms"] = 1500          # 任务做成了，但拖成了长尾
        if i in invalid_indices:
            rec["valid"] = False      # 被取消或无效，不计入分母
        out.append(rec)
    return out


def main():
    checks = []

    # --- 健康检查：存活与就绪分离、浅检查 ---
    normal = Health(alive=True, warm=True, dependencies_ok=True)
    checks.append(("正常实例存活探针为 UP", normal.liveness() == "UP"))
    checks.append(("正常实例就绪探针为 READY", normal.readiness() == "READY"))
    checks.append(("正常实例对外接活", normal.action() == "serve"))

    # 依赖抖动：浅检查刻意不看它，实例仍照常接活，不被误重启
    shaky = Health(alive=True, warm=True, dependencies_ok=False)
    checks.append(("依赖抖动时依旧 READY", shaky.readiness() == "READY"))
    checks.append(("依赖抖动不触发重启", shaky.action() == "serve"))
    checks.append(("依赖状态只体现在诊断字段",
                   shaky.snapshot()["deep_dependency"] is False))

    # 未预热：只摘流量，不重启
    warming = Health(alive=True, warm=False, dependencies_ok=True)
    checks.append(("未预热时不就绪", warming.readiness() == "NOT_READY"))
    checks.append(("未预热只摘流量不重启", warming.action() == "drain"))

    # 进程真没了才重启
    dead = Health(alive=False, warm=True, dependencies_ok=True)
    checks.append(("进程失联存活探针为 DOWN", dead.liveness() == "DOWN"))
    checks.append(("进程失联才触发重启", dead.action() == "restart"))

    # 探针状态可结构化、可复现
    snap = json.loads(json.dumps(normal.snapshot(), sort_keys=True))
    checks.append(("探针状态可结构化往返", snap["readiness"] == "READY"))

    # --- 服务等级目标：按窗口算达标、扣预算、联动闸门 ---
    # 干净窗口：一千条有效请求里零次不达标
    clean = make_records(1000)
    m = sli(clean, 0, 999)
    checks.append(("干净窗口有效请求为一千条", m["total"] == 1000))
    checks.append(("干净窗口达标比例为一", m["ratio"] == 1.0))
    checks.append(("每千次允许一次不达标", allowed_misses(1000) == 1))
    checks.append(("干净窗口预算还有剩", budget_left(clean, 0, 999) == 1))
    checks.append(("预算充足允许放量", can_release(clean, 0, 999) is True))

    # 脏窗口：两条不达标（一条任务失败、一条长尾超时），夹带两条无效请求
    dirty = make_records(1002, bad_indices=(7,), slow_indices=(8,), invalid_indices=(9, 10))
    md = sli(dirty, 0, 1001)
    checks.append(("无效请求被排除在分母之外", md["total"] == 1000))
    checks.append(("失败与超时共两次不达标", misses(dirty, 0, 1001) == 2))
    checks.append(("长尾慢请求被单独记下", md["slow"] == 1))
    checks.append(("接口秒回但任务失败也算不达标",
                   sli(dirty, 7, 7)["good"] == 0))
    checks.append(("脏窗口预算已超支", budget_left(dirty, 0, 1001) < 0))
    checks.append(("预算超支冻结放量改动", can_release(dirty, 0, 1001) is False))

    # 滚动窗口：窗口外的失败不混进统计
    checks.append(("滚动窗口按时间裁剪", sli(dirty, 100, 999)["total"] == 900))
    checks.append(("窗口外失败不混入统计", sli(dirty, 100, 999)["ratio"] == 1.0))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `ALLOWED_MISSES_PER_MILLE` 与 `LATENCY_LIMIT_MS` 先把「允许多少次不达标」和「延迟上限」写成整数常量。这里刻意用千分比而不是小数百分比：`1000 * 1 // 1000` 是整数运算，能避开小数在边界上的舍入误差，也让每一条结果都能手算复核；额度按整千向下取整，宁可偏保守，不会凭空多出一次放行。
2. `Health` 用三个字段区分状态：`alive` 是进程还能不能应答，`warm` 是预热有没有做完、能不能接新请求，`dependencies_ok` 代表外部依赖，但注释写明了它「仅诊断用」——它不会出现在任何判定分支里，这正是浅检查的落点。
3. `liveness` 与 `readiness` 分开实现，是为了让「重启」和「摘流量」这两种处置不被压成一个开关。`readiness` 只看 `alive` 与 `warm`，刻意不读 `dependencies_ok`；`action` 再把三种结果落成可断言的行为：存活失败才 `restart`，没就绪只 `drain`，都好才 `serve`。
4. `snapshot` 把探针状态收敛成三个精简字段，结果确定、只读、不产生副作用，便于外部稳定读取；`json`（JavaScript Object Notation，一种用纯文本表示数据的格式）在这里只做一次序列化往返，验证状态可以被结构化地传出与读回。
5. `valid_records` 先按滚动窗口裁时间、再剔除被标成无效的请求，把分母定干净。`sli` 里的 `good` 定义是「任务做成且延迟不超上限」，而不是「有没有返回」；`slow` 单独统计做成但拖成长尾的请求，正是为了不让平均值把少数极慢的体验摊平。
6. `misses` 用「有效数减达标数」得到花掉的额度，`allowed_misses` 按千分比算出允许额度，`budget_left` 相减得到剩余，`can_release` 只在还有剩时放行改动。把目标换算成额度再联动发布闸门，和 [影子模式、灰度与回滚](./k112-shadow-canary.md) 里「指标越线就停放量」是同一套思路，只是这里量的是一整段窗口而不是某一批次。
7. `make_records` 用构造出来的整数记录代替真实时钟与真实流量，让整段结果可复现、可手算。`main` 前半验健康检查的四种状态（正常、依赖抖动、未预热、进程失联），后半验干净窗口与脏窗口的达标比例、无效请求排除、慢请求单列、预算超支冻结，以及滚动窗口确实把窗口外的失败挡在外面。结尾先逐条打印通过与否，再打印「通过 N/N 项」，并用 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用构造记录代替了真实监控数据、用整数千分比代替了完整的分位数计算、用一个本地类代替了编排系统，全是为了让整段链路不联网、不装第三方包、不需要账号就能独立跑通并手算核对。它演示的是「浅探活—算达标—扣额度—联动闸门」的判定次序，不是任何具体监控系统的实现；文中的目标数值与耗时都是为讲解而构造的示例，不代表任何真实系统的水平。

## 踩坑与边界

- **探针里查了一整条依赖链**：现象是下游一抖，所有实例同时被判不健康、挨个重启，小故障变成全站不可用 → 原因是深检查进了摘流量路径，一处抖动被级联放大 → 浅检查只看自身与本地标记，深检查单独低频做、只用于诊断，依赖问题交给 [熔断](./k104-circuit-breaker.md) 与 [结构化日志](./k095-structured-log.md)。
- **存活和就绪合成一个开关**：现象是预热中的实例被反复重启、永远热不完，或该摘流量的实例仍带着新请求一起崩 → 原因是两种完全不同的处置被压成一个非真即假的值 → 分开两个判定，重启只对存活失败，摘流量只对未就绪。
- **拿返回成功状态当成功**：现象是面板全绿、达标比例接近满分，用户却说任务没办成 → 原因是服务等级指标的口径量的是「有没有响应」而不是「有没有做成」 → 按成功任务定义达标，把越权、绕路重试、成本异常一并算进来，见 [按成功任务核算成本](./k096-metrics-cost.md) 与 [结果评测与轨迹评测](./k089-trajectory-eval.md)。
- **只把目标写进文档、不算误差预算**：现象是贴了个百分比，出事时仍靠拍脑袋决定要不要继续放量 → 原因是目标没换算成可花的额度和能卡住动作的闸门 → 把额度按窗口算出来，和 [影子模式、灰度与回滚](./k112-shadow-canary.md) 里的停止放量阈值绑在一起。
- **用平均值掩盖长尾、用自然月当窗口**：现象是平均延迟很好看、少数用户却等得极久，且月初月底数字忽高忽低 → 原因是均值摊平了慢请求，固定窗口把不同时段的变化混成一段 → 慢请求单列或看分位数，改用滚动窗口，口径用 [回归门禁与基线](./k091-regression-gate.md) 卡住别悄悄漂。

还要分清两个时间尺度：探活是「此刻、这一个、能不能」，服务等级目标是「一段、整体、达不达标」；前者失灵会立刻放大故障，后者失灵会让人长期误判。目标定得越高也不等于越稳妥，因为额度越紧，任何一次改动都更容易触发冻结，得和发布节奏一起权衡；这和 [并发控制](./k115-concurrency.md)、[成本清单](./k116-cost-checklist.md)、[提示与策略版本化](./k113-prompt-versioning.md) 要连起来看——版本能各自退回，指标才有得复盘。想把「失败长什么样」补全到口径里，可以接着看 [失效模式清单](./k150-failure-modes.md)。

## 三句话小结

健康检查与 SLO，是用一个浅而快的探针回答「此刻这个实例能不能接活」，再用一段窗口里的达标比例和误差预算回答「整体有没有守住对外承诺」。

关键做法是存活与就绪分开处置、探针不查外部依赖、服务等级指标按「任务是否达成」定义、把额度算出来并和发布闸门绑在一起。

当程序只是一次性离线跑批、既没有持续流量也没有需要对外兑现的承诺时，这套长期守护可以简化；但只要有人持续依赖它办事，就不该只靠一块绿色面板来判断好坏。

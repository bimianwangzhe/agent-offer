# 生产失败模式清单与支出硬上限

## 场景提问

一个挺平静的下午，服务突然就不对劲了：先是几个请求变慢，接着大面积超时，然后错误数和账单一起往上蹿。你冲去看监控，每个组件都还「活着」——进程没挂、健康检查全绿、没有哪台机器掉线。事后一点点捋才发现是一串连锁：下游慢了一点，本地判定超时，调用方立刻重试，重试把请求量抬高，队列越堆越长，有个任务开始反复兜圈子调同一个工具，上下文越带越长，偏偏这时凭证到期又引来一批集中失败。每个环节单拎出来都不算「坏了」，串起来却滚成了事故。最让人后怕的是：整个过程中，没有任何一道线会在花到某个数时自己停下来。

## 破误解

**不是某个组件突然坏了，是失败会沿链路传染、彼此放大；而「有告警」跟「会刹车」是两码事，光有监控没有一道到线就自己切断的支出硬上限。**

先把两个词说清。失败模式清单（failure mode，反复出现、有固定形状的失效样子）不是一份「可能出问题的地方」的罗列，而是把生产环境里那些会重复出现的形状一条条认出来：重试风暴、级联超时、循环失控、上下文膨胀、凭证过期、状态串扰。列它的意义在于「按形状提前认出来」，而不是等它发生再从头查——因为这些形状有一个共同的讨厌之处：它们大多不表现为「服务挂了」，所以普通的存活检查一条都探不到。更麻烦的是它们会互相喂料：下游变慢 → 本地超时 → 触发重试 → 到达率升高 → 下游更慢，这是一个会自我加速的正反馈环，不打断就会一直转下去。

另一半是支出硬上限（hard spend cap，花到某个数就真的不再放行新动作的一道可执行约束）。它和「软预算」的区别不在数值大小，而在动作性质：软预算是超了记一笔、发个通知，服务照常继续跑；硬上限是到线就拒绝新任务或切断一路，是系统自己动手，不需要等谁来看告警。这里有个很实际的判断缺口——告警到处置之间永远隔着人：人不在、告警太多看不过来、几条告警同时炸互相掩盖，而失败放大的速度是秒级的。所以硬上限必须满足三条：判定发生在真正花钱的那一步**之前**、动作是拒绝或切断而不是写日志、可重复执行且不产生二次破坏。前者把「上限」从统计变成闸门，中者让它真的能刹车，后者保证它自己不会变成新的故障源。这两半合起来才是这篇要讲的东西：先能认出形状，再有一道不依赖人的最后防线。

## 生活类比

把它想成家里的电路。某个插座上插满了取暖器、电水壶、微波炉，是重试风暴和并发打爆；电线开始发热、灯忽明忽暗，是延迟升高、排队变长，这时候电器其实都还「能用」，只是越来越勉强。墙上装了个会响的烟雾报警器，是软预算：它响得很尽责，可电还在走，屋里没人去拉闸，热量照样一点点累积。真正救命的是配电箱里的空气开关——电流一超过它就「啪」地跳开，那一路直接断电，这就是支出硬上限：到线即断，不问有没有人在场。

对应关系可以逐条对上。空气开关按房间分路，客厅那路跳了不影响厨房，就是「按租户、按任务」分别设线，只切断出问题的那一路，而不是一刀把全屋电拉了；总闸一拉全屋黑，对应 kill switch（整体切断开关），更彻底、代价也更大，只在整体失控时才用。每路电表的读数，是结构化日志里必须记下的轮数、重试次数、输入长度、鉴权结果——没有读数，你连「是哪一路先超的」都说不清。还有一处最容易被忽略的细节：老式保险丝烧断得换新的，现代空开虽然能复位，但合格的做法是先查清为什么跳、排除故障再合闸，否则一合又跳、反复拉弧。放到系统里就是：硬上限触发之后不能自动无限重置继续跑，复位必须显式、留痕、先归因，见 [Badcase 回收闭环与分级评测](./k093-badcase-loop.md)。这个比喻还点出了「清单」的价值：电工上门不是靠灵光一现，而是按一张常见故障单逐项排查——短路、过载、漏电、接触不良各有各的形状和表征；失败模式清单干的就是这件事，让「认出来」变成可复用的动作，而不是每次都从头猜。

## 自绘示意图

:::figure 一次失败如何被放大成事故
@cycle
下游变慢|本地超时|触发重试|到达率升高|下游更慢
:::

这张图用循环而不是直线，是因为它本来就是个环：最后一格「下游更慢」又会回到第一格，转得越久越快。任何一格单独看都合理——超时就重试，是最自然不过的写法——可连成环之后，系统的行为就不再由某一处决定，而由整个正反馈驱动。硬上限的作用是从环外强行掐断一路：不管环转得多起劲，花到线就不再放行新的动作，环自然失去燃料。这也解释了为什么「把超时时间调长一点」往往没用：它只是把环转得慢一些，并没有断开。

:::figure 失败模式清单要覆盖的六类形状
@stack
重试风暴::退避缺失，被拒请求原地再来，把到达率抬高
级联超时::一处变慢沿调用链层层放大，排队越来越长
循环失控::轮数不封顶，反复调同一工具，烧钱不出结果
上下文膨胀::历史越带越长，输入计费与延迟一起涨
凭证过期::密钥到期后集中失败，失败又被当成需重试
状态串扰::共享缓存被交叉读写，出现串数据或越权
:::

六格有个共同点：单独看都不像「宕机」。循环失控时服务仍在勤快地调用工具，上下文膨胀时每次请求都正常返回，凭证过期时错误集中在同一个时间段，状态串扰更是偶发到难以复现。所以只盯「进程在不在、接口通不通」的存活检查，对这六类几乎全盲。要在日志里为每一类留一个可判定的字段，才能从「形状」上把它们认出来，见 [结构化日志与轨迹回放](./k095-structured-log.md)。

:::figure 软预算与硬上限的差别
@compare
只报警的软预算::超线继续跑|等人来处理|半夜没人踩刹车
会切断的硬上限::到线即拒新|动作可执行|按租户可隔离
:::

左边并非没用，它适合「需要人来判断」的场景；但当失败以秒级放大时，等人这一步就成了最慢的一环。右边把「超线」直接翻译成一个动作，代价是可能误伤正常请求，所以才要按维度分开设线、把粒度控制到「只拒新的、不杀在跑的」。两者可以并存，但不能互相替代：有告警不等于有刹车。

## 层层追问

:::ask 那如果我监控做得很全，每个指标都有告警，是不是就不需要硬上限了？
:::

需要，而且这正是最贵的一次误判。告警的语义是「让人知道」，硬上限的语义是「系统自己动手」，中间隔着一段无法压缩的延迟：夜里没人盯、告警太多导致疲劳、几条同时炸互相盖住、或者值班的人得先花几分钟弄清楚该动哪一个开关。可那个正反馈环不等人，它几秒钟就能把队列堆满。更隐蔽的是告警本身依赖指标口径可信——如果记账时只统计成功请求、把失败任务和重试藏了起来，那么支出明明在疯涨，对应曲线却可能纹丝不动，告警根本不会响，这正是 [成本优化与上线检查清单](./k116-cost-checklist.md) 里反复强调「分子要记全」的原因。

再往下一层：硬上限要真的能刹车，得经得起三个追问。第一，判定发生在哪一步？必须在真正花钱的动作**之前**预扣，超限就干脆不放行；若等调用返回后才累加计数，那只是事后统计，钱已经花了。第二，动作是什么？必须是「拒绝本次新任务」或「切断这一路」，而不是写一条日志、发一条通知；前者改变系统行为，后者只改变记录。第三，重复执行安不安全？上限被反复触发、复位、再触发是常态，计数与拒绝动作必须可重复且不产生二次破坏，这和 [幂等落盘](./k107-idempotent-persist.md) 里「用稳定标识去重复动作」是同一套思路：同一个请求被提交两次，只应扣一次账、只应给出一个结论。把这几条落到实处，离不开 [健康检查与 SLO](./k114-health-slo.md)（SLO，Service Level Objective，服务等级目标）提供的可观测依据；而「下游已经明显不健康时直接停止送流量」则是 [熔断与 kill switch](./k104-circuit-breaker.md)，它和硬上限是两道不同的闸——前者按健康状态切，后者按花了多少切。

:::ask 那如果硬上限设得太低，把正常任务也一并切了怎么办？
:::

这一问问到了要害：问题往往不在数值，而在「按什么维度切、切哪一刀」。三个维度不能互相替代。单任务上限专防死循环——某个任务反复调同一个工具，总花费却分散在很多轮里，只有按任务累计才能拦住；单租户上限专防一个使用方把共享资源吃满，见 [会话隔离与租户边界](./k105-session-isolation.md)；时间窗上限专防长时间满载，哪怕每个任务、每个租户都规规矩矩，持续跑满一样能把预算烧穿，它还和 [高并发与并发上限](./k115-concurrency.md) 里「同时在跑的数量 × 时长」直接相关。三类约束合起来看，就是 [四重预算](./k103-four-budgets.md) 的思路。只设其中一条，另两条的口子就一直开着。

再追一层，是「切哪一刀」的粒度。稳妥的做法是优先拒绝**新**任务、保留已经在跑的那些，而不是把进程杀掉——后者会让进行中的任务连收尾和对账的机会都没有。只有整体失控时才动用整体切断开关。还有触发之后怎么办：不能一触发就自动重置继续跑，那等于没有上限；复位要显式执行、留下痕迹、并且先归因，否则同一条失败路径会一遍遍把线撞开。这里还牵出两个容易被当成「新故障」的旧问题：凭证到期后的集中失败常常被误判成「需要重试」，于是在已经超线的基础上又叠一层重试，见 [凭证过期与轮换](./k111-credential-expiry.md) 和 [重试退避与抖动](./k108-retry-backoff.md)；上下文越长、输入计费越高、也越容易触发超时，见 [上下文膨胀与中间遗失](./k049-context-bloat.md)。所以硬上限不是孤零零一个数，它得和轮数封顶（[四个终止条件](./k028-stop-conditions.md)）、失败分类、以及一份写进配置、可查可重放的规则一起用，这部分和 [提示与策略版本化](./k113-prompt-versioning.md) 是同一个道理：能被查到的规则，才算真的生效了。

## 可运行代码与逐行解释

下面这段只用 Python 内置功能，做两件可手工推算的事：一是从一组记录里按形状认出四类失败模式；二是把支出硬上限做成「执行前预扣、到线即拒、三个维度各自独立、同一请求重复提交只扣一次、复位显式留痕」的确定性闸门。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
class SpendCap:
    """三维支出硬上限：判定在花钱之前，到线即拒，重复提交只认一次。"""

    def __init__(self, per_task, per_tenant, per_window):
        self.per_task = per_task
        self.per_tenant = per_tenant
        self.per_window = per_window
        self.task_spent = {}
        self.tenant_spent = {}
        self.window_spent = 0
        self.seen = {}
        self.blocked = 0
        self.resets = 0

    def charge(self, call_id, task_id, tenant, amount):
        """返回 (是否放行, 挡住它的维度)；同一 call_id 复用上次结论。"""
        if call_id in self.seen:
            return self.seen[call_id]
        task = self.task_spent.get(task_id, 0)
        used_tenant = self.tenant_spent.get(tenant, 0)
        if task + amount > self.per_task:
            result = (False, "单任务")
        elif used_tenant + amount > self.per_tenant:
            result = (False, "单租户")
        elif self.window_spent + amount > self.per_window:
            result = (False, "时间窗")
        else:
            self.task_spent[task_id] = task + amount
            self.tenant_spent[tenant] = used_tenant + amount
            self.window_spent += amount
            result = (True, "")
        if not result[0]:
            self.blocked += 1
        self.seen[call_id] = result
        return result

    def reset_window(self):
        """时间窗复位并留痕；复位不会替任何已被拒绝的请求翻案。"""
        self.window_spent = 0
        self.resets += 1


def detect(records):
    """按形状认出失败模式，返回识别到的名称列表。"""
    found = []
    if sum(r["retries"] for r in records) >= 8:
        found.append("重试风暴")
    if any(r["rounds"] > 12 for r in records):
        found.append("循环失控")
    ins = [r["tokens_in"] for r in records]
    growing = (len(ins) >= 3
               and all(ins[i] < ins[i + 1] for i in range(len(ins) - 1))
               and ins[-1] >= 60)
    if growing:
        found.append("上下文膨胀")
    if sum(1 for r in records if r["auth_fail"]) >= 3:
        found.append("凭证过期")
    return found


def normal_records():
    return [
        {"retries": 0, "rounds": 3, "tokens_in": 10, "auth_fail": False},
        {"retries": 1, "rounds": 4, "tokens_in": 12, "auth_fail": False},
        {"retries": 0, "rounds": 2, "tokens_in": 11, "auth_fail": False},
    ]


def storm_records():
    return [{"retries": 3, "rounds": 2, "tokens_in": 10, "auth_fail": False}
            for _ in range(4)]


def loop_records():
    return [{"retries": 0, "rounds": 15, "tokens_in": 10, "auth_fail": False}]


def bloat_records():
    return [
        {"retries": 0, "rounds": 3, "tokens_in": 20, "auth_fail": False},
        {"retries": 0, "rounds": 3, "tokens_in": 40, "auth_fail": False},
        {"retries": 0, "rounds": 3, "tokens_in": 70, "auth_fail": False},
    ]


def credential_records():
    return [{"retries": 0, "rounds": 2, "tokens_in": 10, "auth_fail": True}
            for _ in range(3)]


def main():
    checks = []

    checks.append(("正常记录不误报", detect(normal_records()) == []))
    checks.append(("重试风暴能被认出", "重试风暴" in detect(storm_records())))
    checks.append(("循环失控能被认出", "循环失控" in detect(loop_records())))
    checks.append(("上下文膨胀能被认出", "上下文膨胀" in detect(bloat_records())))
    checks.append(("凭证过期能被认出", "凭证过期" in detect(credential_records())))

    # 维度一：单任务上限，专防死循环把钱分散在很多轮里烧掉
    cap_task = SpendCap(per_task=20, per_tenant=1000, per_window=1000)
    a1 = cap_task.charge("a1", "task-a", "t0", 8)
    a2 = cap_task.charge("a2", "task-a", "t0", 8)
    a3 = cap_task.charge("a3", "task-a", "t0", 8)
    checks.append(("单任务前两次放行", a1[0] and a2[0]))
    checks.append(("单任务到线即拒", a3[0] is False and a3[1] == "单任务"))
    checks.append(("被拒请求不扣账", cap_task.task_spent["task-a"] == 16))
    again = cap_task.charge("a1", "task-a", "t0", 8)
    checks.append(("重复提交复用原结论", again == a1))
    checks.append(("重复提交不重复扣账", cap_task.task_spent["task-a"] == 16))
    checks.append(("被拒次数被记录", cap_task.blocked == 1))

    # 维度二：单租户上限，专防一个使用方吃满共享资源
    cap_tenant = SpendCap(per_task=20, per_tenant=50, per_window=1000)
    b1 = cap_tenant.charge("b1", "task-b", "t1", 20)
    b2 = cap_tenant.charge("b2", "task-c", "t1", 20)
    b3 = cap_tenant.charge("b3", "task-d", "t1", 20)
    checks.append(("单租户前两次放行", b1[0] and b2[0]))
    checks.append(("单租户到线即拒", b3[0] is False and b3[1] == "单租户"))
    checks.append(("单租户被拒后不扣账", cap_tenant.tenant_spent["t1"] == 40))
    checks.append(("换个租户仍可放行",
                   cap_tenant.charge("b4", "task-e", "t2", 20)[0] is True))

    # 维度三：时间窗上限，专防长时间持续满载
    cap_window = SpendCap(per_task=1000, per_tenant=1000, per_window=50)
    w1 = cap_window.charge("w1", "task-f", "t0", 30)
    w2 = cap_window.charge("w2", "task-g", "t0", 30)
    checks.append(("时间窗首次放行", w1[0]))
    checks.append(("时间窗到线即拒", w2[0] is False and w2[1] == "时间窗"))
    checks.append(("时间窗被拒后不扣账", cap_window.window_spent == 30))
    cap_window.reset_window()
    checks.append(("复位清零并留痕",
                   cap_window.window_spent == 0 and cap_window.resets == 1))
    checks.append(("复位后新请求可放行",
                   cap_window.charge("w3", "task-h", "t0", 30)[0] is True))
    checks.append(("复位不替被拒请求翻案",
                   cap_window.charge("w2", "task-g", "t0", 30)[0] is False))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `SpendCap` 用三本账表达三个维度：`task_spent` 按任务、`tenant_spent` 按租户、`window_spent` 按时间窗累计；另加 `seen` 记每个 `call_id` 的结论、`blocked` 记被拒次数、`resets` 记复位次数。这些字段都不是装饰，后面每条断言都会用到它们。
2. `charge` 的第一行就是幂等：若 `call_id` 已经见过，直接返回上次结论，既不重复扣账、也不重复增加被拒次数。这对应追问里那句「同一个请求提交两次只应有一个结论」，也呼应 [幂等键与副作用防重](./k038-idempotency-key.md)。
3. 三个 `if / elif` 的顺序体现了「判定在花钱之前」：先算出「假如放行会变成多少」，只有三个维度都不越线，才真正写回三本账并返回放行。任何一维越线，走的是返回 `(False, 维度名)` 的分支，三本账一分不动——断言「被拒请求不扣账」验的就是这一点。若把累加写在判定前面，上限就退化成了事后统计。
4. 返回的第二个值是「挡住它的维度」，不只是真或假。这看着是个小细节，实际决定了事后能不能回答「到底是哪条线先到的」；生产里这类归因信息应当连同结构化日志一起留下，见 [Trace 该记什么](./k094-trace-fields.md)。
5. `reset_window` 只把时间窗清零并给 `resets` 加一，别的都不动。它刻意不清理 `seen`：先前被拒的 `call_id` 依旧返回原来的拒绝结论，于是「复位不替被拒请求翻案」成立。复位要显式、要留痕，且不能悄悄把已发生的拒绝抹掉，这是硬上限不会自我失效的关键。
6. `detect` 是「按形状认出来」的落地：重试总数达到阈值认作重试风暴、单条轮数超过 12 认作循环失控、输入长度连续递增且末值过大认作上下文膨胀、鉴权失败达到条数认作凭证过期。四个判据都是可判定的布尔条件，不是「注意观察」这种没法自动执行的话。膨胀那条特意拆成 `growing` 一个变量，用括号分三行写，避免长表达式里悄悄漏掉一个条件。
7. `normal_records` 到 `credential_records` 五组构造数据各有分工：一组完全正常、四组各自只触发一种形状。全无随机数，所以「正常记录不误报」和「四种形状分别能被认出」都能手算核对；它们是为讲清判据构造的教学例子，不是任何真实系统的采样。
8. `main` 第二组用三个独立的 `SpendCap` 实例分别验证三个维度，而不是在一个实例上调参数。这样安排正是为了证明「三个维度不能互相替代」：把 `per_task` 设小、另两维放到极大，就只暴露单任务这一条线；租户与时间窗同理。每组都断言前几次放行、到线那次被拒、被拒后账目不变。
9. 最后一组专门验证复位语义：清零、`resets` 加一、复位后新请求可放行、但那个曾被拒的 `w2` 再次提交仍被拒。整段只用内置功能，把「预扣、到线即拒、三维独立、幂等、复位留痕」这五件抽象的事变成可复制、可手算、逐条可核对的确定性例子；结尾统一统计通过项数，任何一条不成立都以非零状态退出。

如实说明一句：这里的金额、阈值与记录都是为讲清机制而构造的教学例子，不是任何真实报价；全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算核对。它演示的是硬上限的动作顺序与失败模式的判定形状，不是任何具体监控或计费组件的实现，复制运行即可逐条看到这些性质是否成立。

## 踩坑与边界

- **把告警当成刹车**：现象是指标齐全、每条都有告警，事故却照样扩大 → 原因是告警只通知、不执行，且告警到处置隔着无法压缩的人工延迟 → 把「超线」翻译成到线即拒的可执行动作，让系统自己动手，告警保留作归因依据。
- **只在单个维度设线**：现象是设了总预算，某个任务死循环仍把钱烧穿，或一个使用方把共享资源吃满 → 原因是维度单一，另两处口子一直开着 → 单任务、单租户、时间窗三条各设一条，见 [四重预算](./k103-four-budgets.md) 与 [会话隔离与租户边界](./k105-session-isolation.md)。
- **判定发生在花钱之后**：现象是上限明明配了，支出还是超出去一大截 → 原因是等调用返回才累加计数，钱已经花了 → 改成执行前预扣、超限不放行，并用「被拒后账目不变」这类断言验一遍。
- **触发后自动复位继续跑**：现象是上限反复跳、反复自动恢复，成本持续上涨，日志里却看不出跳过几次 → 原因是复位没有留痕、也没有归因 → 复位显式执行、计数加一、先排除故障再放行，参考 [Badcase 回收闭环与分级评测](./k093-badcase-loop.md)。
- **只盯服务是否存活**：现象是健康检查全绿、进程都在，用户却大面积失败、账单异常 → 原因是清单里六类形状都不表现为宕机 → 按形状识别，日志里带上轮数、重试数、输入长度、鉴权结果，见 [结构化日志与轨迹回放](./k095-structured-log.md) 与 [Trace 该记什么](./k094-trace-fields.md)。

还要分清三道不同的闸：熔断按「下游健康不健康」切，硬上限按「已经花了多少」切，整体切断开关按「是不是全面失控」切，触发条件与处理对象都不一样，见 [熔断与 kill switch](./k104-circuit-breaker.md)。而「拒绝新任务」与「杀掉进程」也不是一回事：前者保留在跑任务的收尾与对账机会，后者会让进行中的事连核对都来不及，只有整体失控时才该动用。凭证到期后的集中失败尤其容易被误判成「需要重试」，务必和 [凭证过期与轮换](./k111-credential-expiry.md)、[重试退避与抖动](./k108-retry-backoff.md) 一起看；轮数封顶见 [四个终止条件](./k028-stop-conditions.md)，输入变长见 [上下文膨胀与中间遗失](./k049-context-bloat.md)。把这些阈值写进可查可重放的配置，属于 [提示与策略版本化](./k113-prompt-versioning.md)；发布前逐条确认有没有漏配，则是 [成本优化与上线检查清单](./k116-cost-checklist.md) 要过的那一遍。

## 三句话小结

生产失败模式清单与支出硬上限，是把反复出现、会互相放大的失效按形状认出来，再给支出设一道到线就自己切断、不依赖人来看告警的最后防线。

关键做法是把六类形状做成可判定的日志字段，让硬上限在执行前预扣、按单任务与单租户与时间窗分别设线、可重复执行不二次破坏、复位显式留痕且先归因。

当系统只在本地跑一次性的离线任务、既没有持续流量也没有按次计费时，不必硬套这套清单与闸门；但只要它会长时间连续对外服务，形状识别和那道能自己动手的线就不该缺席。

# max_tokens 与停止条件

## 一、一个让人抓狂的半截结果

你让模型返回一份结构化结果，拼好提示词、写好解析，本地试了几次都正常，心里挺踏实。上线到真实流量后，偶尔会抛出解析失败，日志里躺着一段这样的文本：`{"status": "ok", "items": [{"id": 1, "name": "苹果"}, {"id": 2, "name": "香` ——括号没闭合，字符串断在半个字上。你第一反应是模型又不听话了，于是加一句「请务必输出完整合法的 JSON」，重启，过两天它又断一次。翻遍提示词也找不出毛病，因为它压根不是提示词的问题。

## 二、先破这个最容易被冤枉的误解

**不是模型故意吐半截，也不是它忘了闭合括号，而是你给它划的输出额度不够，它在写到一半时被硬生生掐断了。**

这里要说清一个参数：`max_tokens`（单次调用允许模型生成的最大 Token 数，Token 是模型读写文本的最小计量单位，可以理解成模型眼里的「字块」）。它是生成端的一把尺子：模型每吐一个字块，计数加一，一旦撞到这个上限，无论这句话说到哪里，生成立刻停止。模型并不会「预感到快到上限了所以提前收尾」，它是逐字块往前走的，被叫停的那一刻可能正好停在一个字符串中间、一个数组中间、一个括号里面。于是你拿到的是一段语法上残缺的文本，解析当然失败。加提示词没用，因为约束作用在生成长度上，不在措辞上。想理解「请只输出 JSON」这种请求为什么本来就不构成保证，可以对照 [「请只输出 JSON」为什么不是保证](./k014-json-request.md)。

## 三、把它想成给打印店设的页数上限

打个比方：你让打印店把一份长稿印出来，但只买了固定张数的纸，跟店员说「最多印这么多张，用完就停」。这里有一一对应关系：模型逐字块生成等于打印机一行一行往外吐纸；`max_tokens` 等于你买的那叠纸的张数；正常写完并落款等于模型自己判断「答完了」并输出结束信号；而纸用完了停在半句上，就等于撞到上限被截断。

这个类比能解释三件常见困惑。第一，为什么断口总在奇怪的地方：店员不会挑一个段落末尾停，纸尽在哪一行就停在哪一行，模型也一样，它不会「挑个括号闭合处」停。第二，为什么加大纸量就好：稿子短、纸够，自然印得完整；额度给足，生成就能走到自然的结尾。第三，也是最容易被忽略的：光有页数上限还不够，你还得告诉店员「看到『全文完』就别往下印了」。这就是停止条件——除了硬上限，还需要一个「模型自己认为该结束」的信号，以及若干「碰到这几个字就停」的停止词。只设上限不设收尾信号，模型可能一直絮叨到撞上限；只设收尾信号不设上限，遇到收尾信号失灵时就会无限生成下去。

## 四、两张图看清边界怎么划

:::figure 一次生成从起点到停下的几种出口
@flow
开始生成|逐块累加|自然结束|命中停止词|撞到上限
:::

第一张图把生成的出口摊开。中间「逐块累加」是常态，右边三个都是可能的停下方式：模型自己判断答完并给出结束信号、命中了你预设的停止词、或者计数撞到 `max_tokens`。前两个是「体面地停」，最后一个是「被掐断」——只有最后一种会留下残缺文本。排查解析失败时，先分清是哪一种出口，方向完全不同。

:::figure 额度给得够与给得不够
@compare
额度偏小::结构性输出被截断|括号字符串不闭合|下游解析直接报错
额度留足::能走到自然结尾|结束信号有机会生效|结果完整可解析
:::

第二张图是本篇最该记住的取舍。额度偏小不是「省了成本」这么简单，它会把一份本来合法的结构化结果变成下游无法解析的半成品；额度留足的代价只是多预留了一些不会被用到的空间。注意这里说的是「预留」而非「一定花掉」：额度是上限不是目标，模型答完就停，并不会为了凑数把字数用满。

## 五、顺着追问把边界推出来

:::ask 那如果我把 max_tokens 调到非常大，是不是就一劳永逸了？
:::

不能，而且会引出两个新麻烦。其一是成本与延迟：额度本身不花钱，但一旦模型因为某种原因（比如收尾信号失效、或者陷入重复）真的开始絮叨，一个极大的上限就给了它把预算烧穿的空间，硬上限本就是防跑飞的刹车，调得过大等于把刹车松了。其二是「输入 + 预留输出」要一起算进窗口：一次调用能容纳的总量是有边界的，输出预留得越夸张，留给输入（提示词、历史、检索片段）的余量就被挤得越少，极端情况下请求会因为总量超限被直接拒绝。关于这层容量关系，[上下文窗口](./k003-context-window.md) 讲得更细。所以合理做法不是「越大越好」，而是按这类输出的历史长度留一个有余量但不离谱的值。

:::ask 再追一层：那如果我要的是 JSON，光把额度留足就够了吗？
:::

还不够，因为额度只保证「不被掐断」，不保证「写出来的形状对」。模型可能写满一整段合法文字，却不是你要的结构：少个字段、多个字段、类型不对。这三关是分开的：`max_tokens` 管的是「别断在半路」，结束信号与停止词管的是「该停就停」，而字段齐不齐、类型对不对要靠 [结构层校验](./k017-structure-check.md) 去查。三者是叠加关系，不能互相替代。还有一个隐蔽的坑：如果你设了停止词，而停止词恰好可能出现在结构化内容内部（比如某个字段值里正好有那几个字），生成会被提前截断，同样得到残缺结果。所以停止词要选那些几乎不会出现在正文里的标记，或者干脆只依赖模型自带的结束信号。

## 六、用一段可运行代码把「截断」演出来

下面这段不联网、不装任何第三方包，用一个假生成模型逐字符吐出一段固定的 JSON，分别用「额度不够」「额度留足」「命中停止词」三种设定跑一遍，亲眼看看半截结果是怎么产生的。

```python
import json

# 假生成模型：把目标文本拆成单字符当成一个个字块，逐块吐出，全本地确定性
TARGET = '{"status": "ok", "items": [1, 2, 3], "done": true}'
STOP_WORD = "END"  # 构造用的停止词，正常正文里不会出现

def fake_generate(target, max_tokens, stop_word=None):
    out = []
    for i, ch in enumerate(target):
        # 先判断是否命中停止词（用累积串做后缀匹配）
        if stop_word and "".join(out).endswith(stop_word):
            return "".join(out), "stop_word"
        if len(out) >= max_tokens:
            return "".join(out), "max_tokens"  # 撞到硬上限，被掐断
        out.append(ch)
    # 全部写完，模型判断答完并正常结束
    return "".join(out), "finished"

def try_parse(text):
    try:
        json.loads(text)
        return True
    except (ValueError, TypeError):
        return False

def main():
    need = len(TARGET)
    # 场景一：额度只给到一半，预期被截断
    short_text, short_reason = fake_generate(TARGET, max_tokens=need // 2)
    # 场景二：额度留足，预期正常写完
    full_text, full_reason = fake_generate(TARGET, max_tokens=need + 10)
    # 场景三：造一段带停止词的正文，且额度充足，预期命中停止词提前停
    with_stop = '{"status": "ok"}' + STOP_WORD + ',"tail": "不该出现"}'
    stop_text, stop_reason = fake_generate(with_stop, max_tokens=len(with_stop) + 10,
                                          stop_word=STOP_WORD)

    results = []
    results.append(("额度不足时确实因为上限停下", short_reason == "max_tokens"))
    results.append(("额度不足时长度恰好等于上限", len(short_text) == need // 2))
    results.append(("被截断的文本无法解析", not try_parse(short_text)))
    results.append(("额度留足时正常结束", full_reason == "finished"))
    results.append(("额度留足时文本完整可解析", try_parse(full_text)))
    results.append(("命中停止词提前停下", stop_reason == "stop_word"))
    results.append(("停止词之后的正文没有被吐出", '"tail"' not in stop_text))

    passed = sum(1 for _, ok in results if ok)
    for name, ok in results:
        print(("通过" if ok else "未通过") + "：" + name)
    print("通过 {}/{} 项".format(passed, len(results)))
    assert passed == len(results)

if __name__ == '__main__':
    main()
```

逐段看关键行在做什么：

1. `TARGET` 是一段合法的结构化文本，`fake_generate` 把它拆成单字符，用一个字符近似一个字块。这么简化是为了不联网也能把「逐块生成、逐块计数」这件事演清楚，真实字块和字符不是一回事，但计数的机制一致。
2. `fake_generate` 里的循环就是生成主过程：每轮先看有没有命中停止词，再看 `len(out) >= max_tokens` 有没有撞上限，都没触发才吐出下一个字符。注意「撞上限」的判断在 `append` 之前，所以返回的长度正好等于上限——这正是半截结果的由来。
3. 函数返回「文本 + 停下原因」两样东西。把原因显式带出来，是想强调排查解析失败时第一步该做的是分清出口：是 `finished`、`stop_word` 还是 `max_tokens`，三者的对策完全不同。
4. `try_parse` 用标准库 `json.loads` 做一次能否解析的判断，捕获解析异常返回 `False`。它就是下游解析器的最小替身。
5. `main` 里造了三个场景：额度砍半、额度留足、正文里带停止词。七条断言分别验证「上限确实生效」「截断长度正好等于额度」「截断后不可解析」「额度足能正常结束且可解析」「停止词会提前停」「停止词之后的内容没被吐出」。
6. 结尾打印 `通过 7/7 项`。这组断言把本篇的因果链钉死了：**额度不够 → 被掐断 → 括号字符串不闭合 → 解析失败**，中间任何一环都不是提示词能救的。

:::warn
停止词要挑几乎不会出现在正文里的标记。若停止词恰好落在某个字段值中间，生成会提前停，你同样拿到一份残缺结果，而且这种截断比额度截断更难查，因为它时有时无。
:::

## 七、踩过的坑与它的边界

- **额度设太小**：现象是结构化输出偶尔断在半个字上、解析抛异常 → 原因是生成被 `max_tokens` 硬掐断，模型不会挑括号闭合处停 → 按这类输出的实际长度留足余量，并把「停下原因」记进日志。
- **只靠提示词救截断**：现象是加了「请务必输出完整」仍然复发 → 原因是约束作用在生成长度上，措辞管不到 → 把额度当作工程参数来调，而不是当作话术问题。
- **把上限调得极大**：现象是成本与延迟偶发飙升，甚至请求因总量超限被拒 → 原因是硬上限本是防跑飞的刹车，调松等于取消保护，且输出预留会挤占输入余量 → 留有余量但不离谱，并配合窗口总量一起算。
- **输出长度与输入长度混算**：现象是「明明没超额度」却报超限 → 原因是一次调用的总量是输入加预留输出一起受窗口约束 → 预估时把提示词、历史、检索片段的长度一并计入。
- **拿额度当格式保证**：现象是文本完整却缺字段、类型错 → 原因是额度只保证「别断在半路」 → 生成后补一层结构校验，别把长度参数和格式契约混为一谈。

还要说清边界：`max_tokens` 是「最多生成多少」，不是「必须生成多少」，模型答完会自然结束，额度不会被凑数用满。它也不负责内容对不对、事实真不真，那是校验与业务规则的事。当你的输出是一段短文、没有解析方、截断也无所谓时，为它精调额度意义不大；真正需要认真设定这个参数的，是那些下游要机器解析、或生成可能失控的场景。

## 九、三句话小结

max_tokens 与停止条件，是约束一次生成「最多写多少、什么时候该停」的一组边界参数，硬上限防跑飞，结束信号与停止词负责体面收尾。

关键做法是按输出类型的实际长度留足额度、把停下原因记进日志、用几乎不出现在正文里的标记当停止词，并在生成后补一层结构校验。

当输出只是给人读的一段短文本、既不需要机器解析也没有失控风险时，不必为它反复精调这些参数，顺手给个宽松默认值即可。

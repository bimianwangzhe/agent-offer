# 下一个词预测：一整段回答是同一件小事重复了几百遍

## 一、一个越想越奇怪的现象

你让它"把这段需求写成三条要点"，它一条一条列得整整齐齐，看着像先在心里列好提纲、再一口气动笔。可你把需求里的一个词改掉，后面三条竟全跟着变了；你补一句"别写第三条"，它有时照办，有时照样写满三条。更怪的是，你回头问它"刚才你是怎么想的"，它能讲出一段像模像样的思路，可那段思路根本不是它当时真正走过的路。你忍不住会想：它是不是先想好了整段，才写出来的？

如果真是先想好再写，那"改一个词全篇都变""让它别写它偏写""事后能编出思路"这三件事，就凑不到一块儿了。

## 二、先破误解

**不是模型先规划好整段再输出，它一次只做一个动作：根据眼前已有的全部文字，猜下一个最可能的词元（token，文本被切开后的最小片），猜完把它补到末尾，再猜下一个，一个一个往外蹦。**

把这个动作拆开看。模型拿到的是一串已经写好的文字，它给"接下来可能接上的每一片"各估一个分数，分数来自它读过的大量文本里"这种地方通常接什么"。然后从这些候选里选出一片，接到末尾。此时"已有文字"变长了，下一步是在这个更长的上下文（context，当前这一眼能看到的全部文字）上，把同样的事重做一遍。所谓一段几百字的回答，就是这个动作重复了几百遍；所谓"提纲"，从来不存在，只有"这句话接下来最像什么"。

这个画面一下就能解释开头那三件怪事。改一个词，已有文字就变了，每一步重算出来的分数跟着变，后面自然全变——它不是推翻了提纲，是压根没有提纲。补一句"别写第三条"，也只是往已有文字里加了一句影响分数的话，加进去的效果是"更可能不写"，不是"保证不写"，所以它偶尔照办、偶尔不听。至于"你是怎么想的"，那是在新的一轮里，以"有人会怎样解释自己的思路"为开头往下续写，写出来的是一段通顺的解释，不是对刚才过程的回放。

循环总得有个头：要么它选出了一个表示"该停了"的停止信号，要么到达你设的长度上限。停不下来这件事本身就值得留意，后面谈[上下文窗口](./k003-context-window.md)时会看到，它跟"一共能装多少"是连在一起的。

## 三、生活类比：蒙着眼睛的接龙

想象一场蒙眼接龙。屋里坐一圈人，全蒙着眼，规则是：每个人只能听见前面所有人接出来的全部内容，然后凭语感接上"最顺的半句"，接完大声念出来，让这句话成为下一个人听到的内容的一部分。没有人手里握着完整大纲，每个人做的都是同一件小事——"顺着当前这句，往下接最顺的那句"。一段听着挺通顺的故事，就是这么半句半句滚出来的。

对应关系可以这样摆：

- 已有文字，是前面所有人接出来的全部内容，每轮都整段重听一遍；
- 给候选打分，是这个人心里的语感：他读过多少，就觉得哪种接法更顺；
- 猜下一个词，是他最终接出口的那一小片；
- 补到末尾，是把新接的念出来，让它变成下一轮的"已有内容"；
- 停止信号，是主持人喊一声"收"；
- 答非所问，是中间有人接偏了半句，后面所有人都在那个偏了的方向上继续接。

这个类比最好用的地方，是它让你直观感到"局部顺"和"整体对"不是一回事。每一环都接得很顺，整段却可能从某一步起悄悄跑偏；而且跑偏之后没人会主动回头，因为下一环只看"现在这句接什么顺"，不看"最初要干嘛"。这也解释了为什么长回答容易前面对、后面越写越松：不是后面偷懒，是约束写在最前面，越往后离得越远。

:::tip
模型没有"整段计划"，只有"当前这一步最像接什么"；把每一步接顺，是它全部的本职工作。
:::

## 四、画出来：一个词是怎么滚出来的

先看这个循环本身，它是个会绕回去的圈：

:::figure 一次回答就是同一个循环
@cycle
已有文字|猜下一个词|补到末尾|再猜下一个
:::

箭头绕回去的那一笔很要紧：新猜出的词不是"输出完就扔"，而是并回已有文字，成为下一轮的输入。正因为有这一笔，一个早期的微小偏差会被一路带下去，越滚越远。

再把单步里发生的事摊开看，它其实分四小层：

:::figure 一个词元被选出来的四小步
@stack
已有上下文::本轮之前的所有文字，整段重读
候选打分::给每个可能的下一片估一个分数
按参数抽样::不是永远取第一名，会带一点随机
补进上下文::选中的片接到末尾，成为下一轮输入
:::

四层里最容易被跳过的是第三层。"估分数"和"选哪片"是两件事：分数高的更可能被选，但不等于一定被选。留一点随机，回答才不会千篇一律；也正因为留了这点随机，同一个问题问两次，完全可能得到两份不一样的通顺文字。[采样参数与不确定性](./k004-sampling.md)整篇讲的就是这一点该怎么对待。把这两张图叠起来，机制就清楚了：外面是一个不断回卷的圈，圈里每一步都是"打分—抽样—补回"这四小层。

## 五、顺着追问两层

:::ask 那如果每一步都只挑"最可能"的那个词，为什么同一句提示两次回答会不一样？
:::

因为"最可能"从来不是一个唯一答案，而是一组带高低的分数。选的时候要做一次抽样（从一堆候选里按可能性大小随机取一个的可能性），参数只控制"有多偏向高分"，并不把随机彻底关掉。就算你把这种偏向调到最极端，真实系统里还有浮点计算、并行归并、版本差异这些细节，谁也不敢打包票说两次逐片完全一致。所以工程上正确的做法不是"让它确定"，而是"别把测试写成确定"：断言该写成"输出里有没有该有的性质"，而不是"输出必须等于这句固定的话"。这一步想通了，你会少踩一大半莫名其妙的偶发失败。

:::ask 那如果它根本没在想，为什么让它"一步步写出来"，复杂题反而答得更稳？
:::

因为中间步骤被写成文字之后，就并进了"已有文字"。下一步不再是从原题直接猜答案，而是在一串带着线索的更长文本上猜，等于它自己给自己铺了一段路：先写"先把总量拆成两项"，再写"第一项是多少"，到该给结论那一步，"已有文字"里已经摆着可用的中间结果，猜错的机会就小了。但要看清两件事。第一，这不改变机制，它仍然是在一步步猜下一个词，只是上下文被它自己喂得更有利；第二，这也不改变不确定性，铺路铺得再好，最后那一步仍是抽样，仍可能飘。更要紧的是，"把话接得像在推理"和"真的核对过"是两回事——一个听起来严丝合缝的推导，中间那个数也可能根本不存在，这正是[幻觉为什么必然存在](./k005-hallucination.md)要接着讲的事。

## 六、跑一段代码，把这个循环摸实

下面这段只用标准库，不联网、不装包、不要账号。它用一张手工的"下一个最可能词"表来模拟模型读过后形成的接续倾向，把"猜一个、补一个、再猜"完整跑一遍。

```python
# 一张手工的"下一个最可能词"表，模拟模型读过后形成的接续倾向。
STOP = "<停>"
NEXT = {
    "今天": "天气",
    "天气": "不错",
    "不错": "适合",
    "适合": "出去",
    "出去": "走走",
    "走走": STOP,
}


def predict_next(context):
    """只看已有文字的最后一个词元，给出最可能接上的下一个词。"""
    last = context[-1] if context else ""
    return NEXT.get(last, STOP)  # 表里查不到就停下


def generate(seed, max_steps=10):
    """把"猜一个词、补到末尾、再猜"循环起来，直到停或到达上限。"""
    context = list(seed)
    produced = []
    for _ in range(max_steps):
        nxt = predict_next(context)
        if nxt == STOP:
            break
        produced.append(nxt)
        context.append(nxt)
    return produced


if __name__ == '__main__':
    checks = 0

    # 1) 从"今天"出发，一步步接到该停为止
    assert generate(["今天"]) == ["天气", "不错", "适合", "出去", "走走"]
    checks += 1

    # 2) 换个起点，就从那个词继续往下接
    assert generate(["今天", "天气"]) == ["不错", "适合", "出去", "走走"]
    checks += 1

    # 3) 表里没有的词，第一步就停，不硬编
    assert generate(["陌生词"]) == []
    checks += 1

    # 4) 步数上限能强制终止，避免无限生成
    assert len(generate(["今天"], max_steps=3)) == 3
    checks += 1

    # 5) 同样的输入、同样的参数，结果确定（这是桩的性质）
    assert generate(["今天"]) == generate(["今天"])
    checks += 1

    # 6) 已写出的词会进入下一轮的"已有文字"
    assert predict_next(["今天", "天气"]) == "不错"
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `NEXT` 是那张打分表的极简替身：键是"当前最后一个词"，值是"最可能接的下一词"；`STOP` 就是那个停止信号。真实模型给的是一堆分数，这里收敛成唯一一个，纯粹为了把循环看清。
2. `predict_next` 只看 `context[-1]`，也就是已有文字的最后一片，查表给下一个；查不到就返回停止信号。它对应"根据当前文字猜下一个"。
3. `generate` 是那个会绕回去的圈：`for` 每转一轮，猜一个、追加到 `produced`、再用 `context.append` 把它并回已有文字；撞上 `STOP` 就 `break`。
4. 断言一、二验证两件事：从"今天"能一路接到"走走"，换个起点就从那个词接着走，说明每一步真的依赖于"当前已有文字"。
5. 断言三、四钉住边界：查不到就停，不硬编；`max_steps` 是兜底的长度上限，防止表被改成永远不停时程序挂住。
6. 断言五要特别留意：它写的是"这个桩确定"，**不是**"真实模型确定"。桩用查表代替抽样，当然两次一样；真实模型带随机，别把这个性质搬过去。断言六再确认补回动作生效，最后打印通过项数。

想看清这些"片"本身怎么来的，回看[Token 与分词](./k001-token.md)；想从整体上知道这套机制该怎么用、从哪里起步，可以看[从这里开始](./00-start-here.md)。

## 七、踩坑与边界

- **把"请只写三条"当保证**：现象是偶尔写满四条 → 原因是这句话只影响每一步的分数，不是硬开关 → 把条数当"要校验的性质"，输出后由代码检查并纠正。
- **拿一次输出写死断言**：现象是测试白天过、晚上挂 → 原因是每片都带抽样，逐片完全一致不可依赖 → 改成断言格式、范围、是否含关键字段这类性质。
- **以为它在回放思考过程**：现象是"你是怎么想的"答得头头是道，就信了 → 原因是那是以"解释思路"为开头的一段续写 → 需要过程就单独记结构化的轨迹，别用事后自述代替。
- **以为长回答是整体规划的结果**：现象是前段紧扣、后段渐渐跑题 → 原因是约束写在最前，越往后离得越远 → 把硬要求放在每轮都带的位置，长内容分段核对。
- **忘了设停止与长度上限**：现象是偶尔收不住、一直往下写 → 原因是循环只靠停止信号或上限收尾 → 显式给长度上限，并在代码里兜底截断。

## 九、三句话小结

模型一整段回答，只是"按已有文字猜下一个词元、补回去、再猜"这一个循环反复跑出来的。
要紧的做法是承认它按局部接续运转，用性质校验和长度上限把结果管住，而不是指望它自觉。
当你需要逐字确定、或需要可回放的真实推理过程时，别用这段续写来顶，改用代码里的确定性逻辑去补。

# 压缩触发阈值与时机

## 场景提问

你给 Agent 设了一条看起来很合理的规则：上下文快装不下时就压缩一次。结果它经常在两种难受之间来回跳——要么迟迟不压，等真到窗口上限，模型返回被截断、工具结果插不进去，一轮直接废掉；要么压得太勤，刚压完没两轮又触发，压缩本身要调一次模型、花一段 token 和延迟，账单一路涨，还把上一轮的结论改得七零八落。更隐蔽的一次，压缩恰好发生在工具调用进行到一半，把一条还没拼完的结构化消息切成两截，后面全乱了。你明明只是想问「什么时候压」，怎么牵出了这么多事？

## 破误解

**不是压缩算法不好，是把「什么时候压」当成了「装满了就压」这一个开关，既没留余量，也没挑时机，更没管压完会不会立刻又压。**

「装满了才压」为什么不行，得先算一笔账。上下文窗口（一次请求能装下的 token 总量上限，token 是模型处理文本的基本单位）不是水箱，压到最后一格才动作，会同时撞上三件事：第一，压缩这个动作本身要往请求里塞原文、再让模型产出摘要，它自己就要占一段 token，如果窗口已经满了，连「压」这个动作都塞不进去；第二，一轮里还可能叠加工具结果、检索片段、用户追问，这些增量是压完才来的，得给它们留出落脚的地方；第三，逼近上限时服务端可能直接截断或报错，那就不是「压得慢一点」，而是这一轮作废。所以阈值不是贴着上限设的，而是提前设一条软线，给「压缩开销 + 下一轮最大增量」留出余量，这部分和 [上下文预算表](./k041-context-budget.md) 里「把每一轮输入当资源管」是同一套算法。

第二件事是时机。压缩不是随时能做的纯计算，它会重排上下文、替换掉一部分历史。如果在工具调用中途、一条消息拼到一半、或一个 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）对象还没闭合时动手，切出来的就是半截结构，后面接什么都对不上。安全时机通常是「一轮结束、工具结果都收齐、模型该产出下一轮决策之前」这种明确节点，它和 [四个终止条件](./k028-stop-conditions.md) 里「一轮在哪个点算结束」是同一个判定。第三件事是频率：压缩完占用明明降下来了，如果判定只看「当前占用是否超过阈值」，而压缩又没能降得足够低，下一轮就会再触发、再压、再触发，形成抖动。要配一条低于触发线的复位线（这类「触发点与复位点分开」的做法叫滞回，hysteresis），压过之后必须等水位回落到复位线以下、再重新涨过软阈值，才允许下一次触发。

这篇讲透的就是这一个点：把「什么时候压」从一句「满了就压」，拆成「按软阈值提前触发、只在安全时机下手、用滞回防抖动、把阈值写进可查配置」四件有先后的事。至于压完丢了什么怎么查，是 [压缩后信息丢失怎么验证](./k048-compression-verify.md) 的活；压完上下文还是越滚越大的成因，在 [上下文膨胀与中间遗失](./k049-context-bloat.md) 里展开。三者各管一段，别混成一件事。

## 生活类比

把它想成开车跑长途看油表。老司机不会等油表指针彻底见底、警告灯亮红才去找加油站，那会儿可能正卡在隧道里、或离下一个出口还有几十公里。他会在油量掉到四分之一左右就开始留意，看到合适的高速服务区就进去加；加油这个动作本身要下匝道、排队、熄火，得留够时间和油，不能等到「刚好能开到加油站」才决定。而且他不会在隧道正中间、或正在连续变道时突然靠边停，一定挑路面宽、车流稳的地方。

对应关系很具体：四分之一那条线，就是软阈值——一条提前量，不是上限；红线见底，是硬阈值，属于兜底，真到了说明前面的提前量没设好；「合适的高速服务区」和「不在隧道中途停」，就是安全时机，压缩只能落在轮次边界这种结构完整、能干净重排的位置；「加油」这件事本身要耗时间和油，对应压缩自己要花 token 与延迟，所以阈值必须把这笔开销算进去，不能贴着窗口上限设。加完油油表指针抬上去，车载电脑不会刚出服务区又提示「该加油了」——这就是滞回：触发在四分之一，复位在更低的位置，中间留一段不动作的死区，避免反复提醒。还有一层容易漏：不同车油箱大小不一样，所以「四分之一」是个比例，不是「剩多少升」；窗口大小一换，阈值要跟着按比例走，写死一个绝对 token 数，换个模型就全乱了。最后，每次加油记一笔里程和油量，对应压缩动作要留痕、阈值要写进配置能事后核对，而不是散落在代码里谁也说不清当前是多少。

## 自绘示意图

:::figure 一次压缩该走的闸门顺序
@flow
累计占用上涨|过软阈值待压|等安全边界|执行压缩|水位回落重置
:::

这张图里「过软阈值待压」和「等安全边界」是两道独立的闸门，不能合成一格。越过软阈值只说明「该压了」，并不等于「现在就能压」；真正动手要等结构完整的那个节点。很多人把压缩写在「每轮开头无条件做一次」的位置，等于把两道闸门一起拆了，于是既不提前量、也不挑时机。末尾「水位回落重置」同样不能省：压缩完不把水位与冷却状态更新，下一次判定拿的还是旧账，抖动就是这么来的。

:::figure 三类触发与两道约束
@stack
水位触发::占用越过软阈值即进入待压，最常用
事件触发::一轮收尾或工具结果收齐等明确节点
定时触发::按轮数兜底，防长时间低水位也该压
安全时机::只在轮次边界动手，不切半条消息
硬线兜底::越过硬阈值先记待压，到边界立刻补压
:::

五行里前三个是「什么时候想起来要压」，后两个是「什么时候才真的准压」。把两类混在一起是常见错误：一看到越线就立刻压，恰好压在消息中途；或者一味等安全时机，结果硬线都越了还在等。正确关系是「越线先记着，边界一到补上」，硬线只决定优先级，不授权在非安全时机开刀。

:::figure 两种触发姿势的差别
@compare
满了才压::容易顶到窗口|压缩开销无余量|可能截断内容
软阈值加滞回::留足压缩余量|只挑安全时机下手|压完不反复抖动
:::

左边看起来判断最简单，代价是余量、时机、频率三样全失控；右边多了几条线和一个状态，换来的是「压得动、切得干净、不反复」。二者差距不在压缩质量，全在触发这一步有没有被当成一段有闸门的判定。

## 层层追问

:::ask 那如果安全时机很久才来一次，会不会一路涨到越过窗口？
:::

会，而且这正是「只讲时机不讲兜底」最典型的翻车。假设一轮里有好几次工具调用，边界只在一轮收尾出现，而每轮增量又大，那么从软阈值到下一个边界之间，占用可能继续往上冲，硬阈值被越过，甚至逼近窗口上限。所以完整判定里要有「硬线兜底」：一旦越过硬阈值，就把「必须压」记成一个待办标记，哪怕此刻不是安全时机也不动手，但下一个边界一到就无条件补压；同时把这条越线本身记进日志，事后用来回看「是不是阈值设太低、或增量估小了」。演示代码里 `pending_force` 这个标记做的就是这件事。更根本的修法不是把边界变密，而是回头调两个数：把软阈值往下挪，或把单轮最大增量估准——阈值应该等于「窗口减去压缩开销再减去一轮最大增量」对应的比例，而不是拍一个好看的整数。这也说明为什么 [滑动窗口裁剪](./k043-sliding-window.md) 这类「每轮都做一点小裁剪」的手段常和压缩配合：它把单轮增量压平，让阈值不必设得过于保守。

:::ask 那如果压缩完水位还是很高，比如一堆内容都不能压，会不会一直卡在冷却里再也不压了？
:::

这是第二层、也更容易被忽略的边界。滞回的设计是「压过之后进入冷却，等水位降到复位线以下才重新允许触发」，它默认压缩确实能把水位拉下来。可如果状态里有一大批不可压缩项——系统约束、当前目标、不可变标识——压缩能腾出的空间有限，压完占用仍停在软阈值之上，此时冷却不会解除，判定会一直返回「冷却中」，看起来像是「再也不压了」。这不一定是坏事：它至少避免了在同一堆压不动的内容上反复空转、反复花钱。但它会掩盖一个真问题：可用空间已经不够了，继续靠压缩解决不了，得换手段——把可压的历史外置按需取回、收紧预算、或明确告知「当前配置装不下这类任务」。判定要做的是把这个状态暴露出来，而不是默默卡住：冷却超过若干轮仍没解除，就该告警并带上「上次压缩留下了多少不可压缩项」，这属于 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 里「不可压缩白名单要短、要可审计」的理由。换句话说，滞回负责防抖动，不负责解决「压不动」；后者要靠预算和结构，不能指望触发逻辑兜底。演示代码里专门构造了「冷却中且水位仍高」这一组，验的就是「不重复触发」而不是「假装压好了」。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「软阈值提前触发、只在安全时机下手、硬线兜底、滞回防抖、阈值按比例、配置可查」做成一个纯判定的 `Trigger` 类，它不真的压缩内容，只回答「这一刻该不该压、为什么」。所有场景都是手工构造的确定性数值，可逐条手算，复制即跑，不需要第三方包、账号或网络。

```python
import json


class Trigger:
    """只判断"这一刻该不该压缩"，不真的压缩内容。"""

    def __init__(self, capacity, soft=0.7, hard=0.9, low=0.4):
        self.capacity = capacity          # 窗口能装下的 token 总量
        self.soft = soft                  # 软阈值：提前触发线
        self.hard = hard                  # 硬阈值：必须压的兜底线
        self.low = low                    # 复位线：水位降到它以下才解除冷却
        self.used = 0
        self.cooling = False              # 滞回：压过之后须等水位回落才重新允许触发
        self.pending_force = False        # 越硬线但还没到安全时机，先记着
        self.compress_count = 0

    def ratio(self):
        return self.used / self.capacity

    def add(self, tokens):
        """一轮里往上下文追加若干 token。"""
        self.used += tokens

    def observe(self):
        """每轮开头检查滞回状态：水位降到复位线以下才解除冷却。"""
        if self.cooling and self.ratio() <= self.low:
            self.cooling = False

    def decide(self, at_boundary):
        """返回 (是否压缩, 原因)。at_boundary 表示此刻是不是轮次边界这种安全时机。"""
        r = self.ratio()
        if r >= self.hard:
            self.pending_force = True
        if not at_boundary:
            return False, "非安全时机，先记着"
        if self.pending_force:
            return True, "越过硬阈值后到边界补压"
        if self.cooling:
            return False, "冷却中，等水位回落"
        if r >= self.soft:
            return True, "到软阈值且处于边界"
        return False, "未达阈值"

    def compress(self, keep_tokens):
        """模拟一次压缩：把占用降到保留量，进入冷却，清除强制标记。"""
        self.used = keep_tokens
        self.cooling = True
        self.pending_force = False
        self.compress_count += 1


def config_snapshot(trigger):
    """把阈值导出成可查的 JSON 文本，发布前能逐项核对数值。"""
    return json.dumps({
        "capacity": trigger.capacity,
        "soft": trigger.soft,
        "hard": trigger.hard,
        "low": trigger.low,
    }, ensure_ascii=False, sort_keys=True)


def main():
    checks = []

    # 一、没到软阈值不该压
    t = Trigger(1000)
    t.add(600)
    ok, _ = t.decide(True)
    checks.append(("未到软阈值不压", not ok))

    # 二、到了软阈值，但工具调用中途不是安全时机
    t = Trigger(1000)
    t.add(720)
    ok1, _ = t.decide(False)
    ok2, reason2 = t.decide(True)
    checks.append(("到软阈值但非安全时机不压", not ok1))
    checks.append(("安全时机一到立即补压", ok2 and "软阈值" in reason2))

    # 三、越过硬阈值也不能切在半条消息中间
    t = Trigger(1000)
    t.add(950)
    ok1, _ = t.decide(False)
    ok2, reason2 = t.decide(True)
    checks.append(("越硬线但非边界仍不切", not ok1 and t.pending_force))
    checks.append(("越硬线后到边界立刻压", ok2 and "硬阈值" in reason2))

    # 四、压缩把水位拉下来并进入冷却；冷却未解除时不重复触发
    t = Trigger(1000)
    t.add(720)
    t.decide(True)
    t.compress(300)
    checks.append(("压缩后水位回落到保留量", t.used == 300))
    checks.append(("压缩后进入冷却", t.cooling))
    checks.append(("每次压缩都计数留痕", t.compress_count == 1))

    t2 = Trigger(1000)
    t2.add(750)
    t2.cooling = True
    t2.observe()
    ok, reason = t2.decide(True)
    checks.append(("冷却需水位降到复位线才解除", t2.cooling))
    checks.append(("冷却中不重复触发", not ok and "冷却" in reason))

    # 五、滞回：压完不会立刻再压，要重新涨过软阈值
    t = Trigger(1000)
    t.add(700)
    t.decide(True)
    t.compress(300)
    fired_early = []
    for _ in range(3):
        t.observe()
        t.add(100)
        ok, _ = t.decide(True)
        fired_early.append(ok)
    checks.append(("压完连续几轮不再触发", not any(fired_early)))
    t.observe()
    t.add(100)
    ok, _ = t.decide(True)
    checks.append(("重新涨过软阈值才再次触发", ok))

    # 六、长循环：所有触发都在安全边界，且次数有限不抖动
    t = Trigger(1000)
    triggered = []
    for round_no in range(40):
        t.observe()
        t.add(100)
        at_boundary = (round_no % 2 == 1)
        ok, _ = t.decide(at_boundary)
        if ok:
            triggered.append((round_no, at_boundary))
            t.compress(300)
    checks.append(("所有触发都落在安全边界", len(triggered) > 0 and all(b for _, b in triggered)))
    checks.append(("触发次数有限不抖动", len(triggered) <= 12))

    # 七、阈值按容量比例缩放，配置可查
    t = Trigger(2000)
    t.add(1400)
    ok, _ = t.decide(True)
    checks.append(("阈值按容量比例而非绝对量", ok))
    checks.append(("阈值写进可查配置", json.loads(config_snapshot(t))["soft"] == 0.7))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Trigger` 把「窗口容量、软阈值、硬阈值、复位线」四个数当作可配置参数，全部用**比例**表示（0.7、0.9、0.4），而不是写死多少个 token。换模型、换窗口大小，只要改 `capacity`，三条线自动跟着缩放，这正是第七组断言要验的。
2. `ratio` 与 `add` 只维护当前占用，不碰内容——刻意把「判定」和「压缩」分成两件事，好让「什么时候压」能被单独验证。`observe` 每轮开头跑一次，负责滞回状态：只有冷却中的实例、且水位已经降到复位线以下，才把 `cooling` 拨回 `False`，表示「重新允许触发」。
3. `decide` 是整套逻辑的关键，判定顺序有讲究：先算占用比例，越过硬阈值就先点亮 `pending_force`；接着如果是非安全时机，**一律不压**，只回一句「先记着」——哪怕硬线越了也不破例，因为切在半条消息中间代价更大；到了边界再看，强制标记优先、冷却次之、软阈值最后。把「越线」和「准压」拆成两步，是这张表最值得记住的地方。
4. `compress` 模拟压缩后的收尾：把占用改成保留量、进入冷却、清掉强制标记、并把次数加一。它同时演示了为什么滞回能防抖——触发点在 0.7、复位点在 0.4，压完降到 0.3，中间有一段不动作的死区，必须重新累积到 0.7 才会再触发。
5. `config_snapshot` 用 `json.dumps` 把四条阈值导成可查文本。阈值不该散落在各处硬编码，发布前能逐项核对，出问题也能回答「当时那条线是多少」。
6. `main` 用七组互相独立的场景收集断言：软阈值之前、软阈值遇上非安全时机、硬线兜底、压缩后的水位与冷却、滞回的死区、四十轮长循环里「触发是否都落在边界、次数是否有限」、以及容量缩放与配置可查。每组都新建实例，数值可以手算，不靠碰运气。
7. 结尾统一打印每条结果并 `assert` 全通过，保证任何一条性质被破坏都会以非零状态退出。第四组里手工把 `t2.cooling = True`、占用设成 750，专门构造「压缩没把水位降下来」的边界，验的是「不重复触发」，而不是假装压好了。

有一处如实说明：这里的占用是抽象数字，压缩被简化成「把占用改成某个保留量」，安全时机也只是每两轮出现一次的规则。它演示的是阈值、时机、滞回、配置之间的判定关系，不代表任何具体窗口或框架的触发实现；真实系统里单轮增量是波动的，边界也更不规则。

## 踩坑与边界

- **阈值贴着窗口上限设**：现象是刚要压缩就报截断、工具结果插不进去，一轮作废 → 原因是没给压缩自身的开销和下一轮增量留余量 → 软阈值按「窗口减去压缩开销再减去一轮最大增量」对应的比例设，硬阈值只当兜底，见 [上下文预算表](./k041-context-budget.md) 与 [上下文窗口](./k003-context-window.md)。
- **越线就立刻压**：现象是压缩恰好落在工具调用中途或一个还没闭合的 JSON 里，后面对不上号 → 原因是把「该压了」当成「现在就能压」 → 越线先记待压，只在轮次边界这种结构完整处动手，配合 [max_tokens 与停止条件](./k127-max-tokens.md) 把一轮的完整边界定清。
- **压完立刻又压**：现象是刚压缩完没两轮又触发，token 与延迟白花，摘要被反复改写 → 原因是触发点和复位点重合，压完占用仍在触发线附近 → 设一条明显更低的复位线做滞回，压过之后必须重新涨过软阈值才允许下一次。
- **阈值写死成绝对 token 数**：现象是换个窗口更大的模型，同样的数要么从不触发、要么频繁触发 → 原因是把比例当成了固定量 → 全部用比例表达，只把 `capacity` 作为唯一随环境变化的量。
- **只盯触发、不看后续验证**：现象是压缩次数看着正常，任务却越跑越偏，回头发现关键约束被改没了 → 原因是把「压得勤不勤」当成了「压得对不对」 → 触发只管时机，压完丢了什么必须另做逐项核对，见 [压缩后信息丢失怎么验证](./k048-compression-verify.md)。

还要分清两件常被混为一谈的事：「压缩触发」管的是**什么时候动手**，「摘要式压缩」管的是**动手之后怎么把内容变短**，后者的方法在 [摘要式压缩](./k044-summary-compression.md) 里；两者共用「压缩」这个词，但一个属于调度判定，一个属于内容改写。另一条边界：触发逻辑再好，也解决不了「上下文本来就装了太多没用的东西」——那是 [上下文膨胀与中间遗失](./k049-context-bloat.md) 要治的，靠的是少塞、按需取回，而不是压得更频繁。把压缩次数、每次压缩前后的占用、越线记录都留下来，才能事后回答「到底该调阈值，还是该先给输入减肥」，这类按任务而非按单次调用核算开销的思路，可对照 [按成功任务核算成本](./k096-metrics-cost.md)。

## 三句话小结

压缩触发阈值与时机，是把「装满了就压」这一句开关，拆成按软阈值提前触发、只在结构完整的边界动手、用硬线兜底、靠滞回防反复抖动、并把阈值写成可查比例的一段判定。

关键做法是阈值按窗口比例而非绝对量设、判定与压缩分离、越线先记待压、压完更新水位与冷却状态、每次触发都留痕可回看。

当任务只有一两轮、上下文根本涨不到阈值，或所有内容都是不可压缩项、压缩腾不出空间时，这套触发就该让位给预算收紧与历史外置，而不是把线越调越低硬压。

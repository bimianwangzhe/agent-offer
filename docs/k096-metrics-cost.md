# 核心指标与按成功任务核算成本

## 一、场景提问

你换了一版提示词，账单上「每次调用的平均花费」从 100 降到了 60，看着省了四成，正打算报功。可同期客服转来的抱怨没少：任务做不成的比例明显变高，好几个请求绕了五六轮才勉强给出结果，还有一次冒出了越权动作。你回头一算才发现问题：新版单次调用确实便宜，但它更爱重试、失败了也要把几轮调用的钱全花掉，真正「做成一件事」的代价反而翻了一倍。更让人困惑的是，延迟报表上「平均耗时」平平无奇，用户却说有几个请求慢得离谱。到底该看哪个数，才不会被一个漂亮的单价哄过去？

## 二、破误解

**不是「把单次调用的花费压低」就等于省钱，也不是「平均耗时没涨」就等于不慢；真正该盯的是「每做成一个任务，总共花了多少」，而且分母只能是成功的那些任务。**

先把「指标」这个词落到具体几项上。任务成功率是「做成的事 ÷ 总共接的事」，这里「做成」必须有明确判定，不能拿「没抛异常」糊弄——一次返回了内容却答非所问、或者该写的数据没写进去，都不算做成，怎么给「做成」下可验证的定义可对照 [属性断言](./k088-property-assertion.md) 与 [结果评测与轨迹评测](./k089-trajectory-eval.md)。越权率是「出现越权动作的任务 ÷ 总任务」，它是安全护栏有没有生效的信号，权限怎么收窄见 [最小权限](./k100-least-privilege.md)。尾延迟要看高分位而不是平均值，常用 p95（第九十五百分位，把一组耗时排序后取靠后的那个值，代表「最慢的那一小撮有多慢」），因为少数卡住的请求会被平均值稀释掉。而成本这一项，最常见的错就是拿「总花费 ÷ 调用次数」当单价：这个式子的分母里混着失败任务和重试轮次，一个爱失败的版本反而会把分母做大、把单价压得很好看。

按成功任务核算，是把式子换成「全部投入的消耗 ÷ 成功任务数」。分子要包含**所有**任务的花费——成功的一次不落，失败的、重试的、被拦下的一律算进去；分母只数真正做成的那些。这个不对称正是要害：失败任务白花的钱不能凭空消失，它得摊到做成的任务头上，否则成本就像被藏进了地毯下面。于是会出现一个乍看反直觉、其实完全合理的现象：单次调用变便宜了，每成功任务的成本却涨了。原因就是失败与重试变多，把分母削薄了。想让这个指标变好，只有两条路——减少无谓的轮次与重试（压分子），或提高成功率（撑分母），光调单价没用。它也可以和 [回归门禁与基线](./k091-regression-gate.md) 绑在一起：新版能不能放量，不看某个漂亮的分项，看这几项合起来有没有守住事先定好的线，阈值怎么定、越线怎么自动刹车见 [健康检查与 SLO](./k114-health-slo.md)。

## 三、生活类比

把它想成一家按「修好一台机器」结账的维修店，而不是按「师傅上门几次」结账。老师傅一次带齐工具，上门一趟就修好，收两百；新手工具带不齐，跑三趟、每次只带一样，最后还把一台修坏了没修成，每趟看着只收六十，挺便宜。可月底一算：老师傅修好十台，一共收两千，摊下来每台两百；新手接了十台，跑了不少趟、每台都花了钱，最后只修好五台，店里的全部开销却一笔没少，摊到那五台上每台四百还多。

对应关系很具体。「每趟上门的收费」就是每次调用的花费，新手这项确实更低；「跑了好几趟」是重试与绕远路；「修坏没修成的那几台」是失败任务——它们的成本照样发生，不能因为没结账就从账本里划掉；「按修好一台摊全部开销」正是按成功任务核算。这个类比还点出平均值为什么骗人：如果只问「平均每次上门等多久」，大部分趟次都挺快，唯独有一趟等零件等了半天，平均值几乎不动，可那位客户体验极差——这就是尾延迟必须用高分位看的原因。

再补一层：老板真正关心的是「这个月做成多少单、每单赚不赚钱」，不是「师傅每趟跑得省不省」。指标要贴着业务价值定，而不是贴着最容易测的那个数字定。单看调用次数、单看 token 用量都省力，但它们都可能与「任务成没成」脱节，[三级评测](./k085-three-level-eval.md) 里把「结果对不对、过程好不好、代价高不高」分层来看，正是为了避免只盯其中一层就下结论。

## 四、自绘示意图

:::figure 一批任务汇成指标的顺序
@flow
接下一批任务|逐条判成功失败|汇总全部消耗|除以成功任务数|对照阈值下判断
:::

五格里最容易被跳过的是「逐条判成功失败」。很多人直接从账单汇总消耗，分母顺手就用了「总任务数」或「总调用次数」，指标当场失去意义。「对照阈值下判断」也不能省：算出一堆数字却没人事先说清「到什么程度算变差」，等于没有结论，这一步和 [回归门禁与基线](./k091-regression-gate.md) 是同一件事。

:::figure 一批任务该盯的几项指标
@stack
任务成功率::做成数除以总数，做成要有可验证的判定
每成功任务成本::全部消耗除以成功数，失败与重试的花费照样算
越权率::出现越权动作的任务占比，护栏失效的早期信号
尾延迟::看第九十五百分位而非平均值，盯住最慢那一小撮
平均轮数::每任务平均走几轮，绕远路与重试的体感指标
工具失败率::工具调用里失败的比例，定位下游抖动
:::

六项里「每成功任务成本」是唯一把分子和分母故意错开的一项，其余各项都规规矩矩用总任务数或总次数作分母。把它单列出来，是因为它最反直觉、也最容易被一个好看的单价掩盖。「平均轮数」和「工具失败率」是诊断项：前者涨了说明在绕路，后者涨了说明下游不稳，二者往往正是成本恶化的先兆，重试策略见 [重试与退避](./k108-retry-backoff.md)。

:::figure 两种成本口径的差别
@compare
按每次调用算::单价好看|失败拉大分母|绕路被隐藏
按成功任务算::含重试与返工|失败削薄分母|贴着做成的事
:::

左边那个「单价」不是错算，而是答错了问题：它回答「一次调用多少钱」，老板问的却是「做成一件事多少钱」。右边的口径把两件事重新对齐，代价是数字没那么好看，但它是能拿来做决策的那个数。

## 五、层层追问

:::ask 那如果把失败任务的花费干脆排除掉，只算成功任务自己的开销，不是更「干净」吗？
:::

恰恰相反，这一排除就把指标最该暴露的东西抹掉了。失败任务同样调用了模型、同样占用了上下文、同样可能触发了工具，钱是真花出去的；若把它们从分子里剔掉，一个成功率只有一半、却把大量消耗浪费在失败重试上的版本，会显得和稳妥版本一样便宜。按成功任务核算的全部意义，就是让「白花的钱」有个去处——它必须被摊到少数做成的任务上，于是失败越多、这个数越难看，指标才和「任务到底成没成」对齐。要再追一层：那失败任务该不该算进成功率的分母？必须算。成功率的分母是「总共接了多少事」，把失败的从分母里拿掉，成功率会永远漂亮，这和排除花费是同一种自欺。真正要区分的是两个位置：成功率用「成功数 ÷ 总任务数」，成本用「全部消耗 ÷ 成功数」，一个把失败算进分母、一个把失败的花费算进分子，各司其职。判定「成功」时若拿不准，别靠模型自己说「我完成了」，用可验证的属性去卡，见 [属性断言](./k088-property-assertion.md)；让模型互评或自评当辅助，边界见 [LLM 裁判](./k090-llm-judge.md)。

:::ask 那如果成本涨了，怎么知道是「模型变贵」还是「任务变绕」？
:::

这正是要同时盯多项、而不是只盯一个总数的原因。把「每成功任务成本」拆成「平均轮数 × 每轮用量 × 单价」三个因子，逐个看是谁动了：平均轮数涨、每轮用量没变，说明在绕路或反复重试，去查终止条件与错误反馈；每轮用量涨、轮数没变，可能是上下文越堆越厚，去查 [上下文预算](./k041-context-budget.md) 与 [前缀缓存](./k050-prefix-cache.md)；单价变了，才轮到核对 [用量与计费](./k010-usage-billing.md) 和 [最大输出长度](./k127-max-tokens.md) 的配置。没有这份拆分，只会得到一个「变贵了」的结论，却无从下手。再追一层：拆完之后怎么确认改动真的有效？要在同一批用例上比较，且这批用例得能代表真实分布——离线挑的几条简单用例全过，挡不住真实流量里的长尾输入，这个落差见 [离线在线差距](./k092-offline-online-gap.md)。发布时也一样：先在 [影子模式、灰度与回滚](./k112-shadow-canary.md) 里小范围观察这几项再决定放量，别等账单出来才发现绕路，日常该核对哪些条目可对照 [成本清单](./k116-cost-checklist.md)。而这些数能不能算得出来，前提又是 [Trace 该记什么](./k094-trace-fields.md) 里那几组用量字段当初一条没少记。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，构造两批可比的任务记录，把「按每次调用算」与「按成功任务算」两个口径并排算出来，再用一组断言验证「单价降了、真实成本却涨了」「失败任务的花费没被剔除」「尾延迟不能用平均值」这几条性质。数据全是手工可推算的整数，复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
import math
from dataclasses import dataclass, asdict


@dataclass
class Task:
    task_id: str
    success: bool
    calls: int
    tokens: int
    latency_ms: int
    violations: int = 0


def summarize(tasks, price_per_token=1):
    """把一批任务汇成指标；成本一律用全部消耗除以成功任务数。"""
    n = len(tasks)
    total_cost = sum(t.tokens for t in tasks) * price_per_token
    total_calls = sum(t.calls for t in tasks)
    success_cnt = sum(1 for t in tasks if t.success)
    success_rate = success_cnt / n if n else 0.0
    cost_per_call = total_cost / total_calls if total_calls else 0.0
    cost_per_success = total_cost / success_cnt if success_cnt else float("inf")
    violation_rate = sum(t.violations for t in tasks) / n if n else 0.0
    latencies = sorted(t.latency_ms for t in tasks)
    p95 = latencies[math.ceil(0.95 * len(latencies)) - 1] if latencies else 0
    avg_latency = sum(latencies) / len(latencies) if latencies else 0
    return {
        "task_count": n,
        "total_cost": total_cost,
        "total_calls": total_calls,
        "success_count": success_cnt,
        "success_rate": success_rate,
        "cost_per_call": cost_per_call,
        "cost_per_success": cost_per_success,
        "violation_rate": violation_rate,
        "p95_ms": p95,
        "avg_latency_ms": avg_latency,
    }


def make_baseline():
    """v1：每任务两轮、共 200 词元，十个任务全部做成。"""
    return [Task("v1-%02d" % i, True, 2, 200, 200) for i in range(10)]


def make_candidate():
    """v2：单轮更省，但一半任务反复调用后仍失败，还带一次越权。"""
    tasks = []
    for i in range(5):
        tasks.append(Task("v2-ok-%02d" % i, True, 3, 180, 150))
    for i in range(5):
        t = Task("v2-fail-%02d" % i, False, 4, 240, 2000 if i == 0 else 300)
        if i == 0:
            t.violations = 1
        tasks.append(t)
    return tasks


def main():
    baseline = make_baseline()
    candidate = make_candidate()
    v1 = summarize(baseline)
    v2 = summarize(candidate)

    checks = [
        ("两版任务数相同，口径可比", v1["task_count"] == v2["task_count"] == 10),
        ("v1 全部做成", v1["success_rate"] == 1.0),
        ("v2 成功率掉到一半", v2["success_rate"] == 0.5),
        ("v2 每次调用的花费确实更低", v2["cost_per_call"] < v1["cost_per_call"]),
        ("但 v2 每成功任务成本反而翻倍",
         v1["cost_per_success"] == 200 and v2["cost_per_success"] == 420),
        ("成本严格按全部消耗除以成功数核算",
         v2["cost_per_success"] == v2["total_cost"] / v2["success_count"]),
        ("失败任务的花费没有被剔除",
         v2["total_cost"] == 2100
         and v2["total_cost"] > sum(t.tokens for t in candidate if t.success)),
        ("两种口径会得出相反结论",
         v2["cost_per_call"] < v1["cost_per_call"]
         and v2["cost_per_success"] > v1["cost_per_success"]),
        ("尾延迟取第九十五百分位", v2["p95_ms"] == 2000),
        ("平均值掩盖了最慢那一小撮", v2["avg_latency_ms"] < v2["p95_ms"]),
        ("越权率单独统计", v2["violation_rate"] == 0.1),
        ("零成功时分母不让指标骗人", summarize(
            [Task("none", False, 1, 100, 100)])["cost_per_success"] == float("inf")),
        ("指标可序列化留痕", json.loads(json.dumps(v1)) == v1),
    ]

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `Task` 用 `dataclasses` 定义一条任务记录：`success` 是「做没做成」的可判定字段，`calls` 是轮数，`tokens` 是这一任务累计词元用量，`latency_ms` 是耗时，`violations` 记越权次数。把「做成」做成显式布尔值，正是为了不靠「没报错」去猜。
2. `summarize` 是整段的中心。`total_cost` 把**所有**任务的用量相加，一行都不筛；`success_cnt` 只数做成的。于是 `cost_per_call = 总消耗 ÷ 总调用次数`、`cost_per_success = 总消耗 ÷ 成功数` 这两个式子，分子完全相同、分母故意不同，后面所有的反差都从这一处不对称来。
3. `success_cnt` 为零时 `cost_per_success` 返回 `float("inf")`（无穷大），而不是返回一个 0 或者干脆跳过。一批任务一个都没做成，成本指标理应是「没法更差」，不该被粉饰成一个有限的漂亮数字。
4. 尾延迟用 `sorted` 加 `math.ceil(0.95 * n) - 1` 取出第九十五百分位，同时另算一份平均值。把两个值都留在结果里，才能直接比较「平均看着还行、高分位已经爆了」这种情况。
5. `make_baseline` 造十个全成功的任务，每个两轮、共 200 词元：总消耗 2000、总调用 20 次、成功 10 个，于是单价 100、每成功任务 200，全部可手工验算。
6. `make_candidate` 造另一批：五个成功任务各三轮 180 词元，五个失败任务各四轮 240 词元，其中一个带一次越权、一个耗时 2000 毫秒。总消耗 2100、总调用 35 次、成功 5 个，于是单价 60（更低）、每成功任务 420（更高），越权率 0.1。刻意用整数，是为了让每条断言都能手算核对。
7. `checks` 前四条先固定住「两版可比、成功率一个 1.0 一个 0.5、单价确实降了」这个前提；第五到第八条是重点：真实成本翻倍、成本按定义核算、失败任务的 1200 词元消耗**没有**被排除、以及两种口径得出相反的结论。第九到十一条验证尾延迟、平均值与越权率各自独立成立。
8. 最后三条查边界与可留痕：零成功时返回无穷大、指标字典能经 JSON 往返而不丢字段。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出，打印格式与逐条结果便于人工核对。

有一处要如实说明：这里用固定整数代替真实用量、用构造的任务列表代替线上流水、用 `price_per_token=1` 代替实际计价，全是为了让「两个口径的分母差在哪」不依赖联网、账号或第三方包就能独立跑通并手算。它演示的是指标的定义与核算顺序，不是任何具体计费平台的实现，也不是对真实系统表现的测量结论。

## 七、踩坑与边界

- **拿「没抛异常」当做成**：现象是成功率报表接近满分，用户却说答非所问、数据没落地 → 原因是成功判定只看了程序有没有崩 → 给「做成」下可验证的属性定义，见 [属性断言](./k088-property-assertion.md) 与 [结果评测与轨迹评测](./k089-trajectory-eval.md)。
- **用总调用次数作成本分母**：现象是单价一路走低，每成功任务的实际花费却悄悄涨 → 原因是失败与重试把分母做大、把单价压好看 → 改成「全部消耗 ÷ 成功数」，让失败的花费摊到做成的任务上。
- **把失败任务的花费剔掉**：现象是爱失败的版本和稳妥版本成本看起来差不多 → 原因是白花的钱被从分子里划走了 → 分子必须包含所有任务，一次不筛，越权与拦截的开销同理。
- **只看平均延迟**：现象是平均耗时平稳，少数请求却慢到不可用 → 原因是长尾被平均值稀释 → 补上第九十五百分位，并给它单独定可守护的线，见 [健康检查与 SLO](./k114-health-slo.md)。
- **离线挑简单用例就下结论**：现象是几条例例全过、指标漂亮，真实流量一进来就恶化 → 原因是那批用例盖不住长尾输入 → 用能代表真实分布的用例集比较，落差见 [离线在线差距](./k092-offline-online-gap.md)，放量节奏见 [影子模式、灰度与回滚](./k112-shadow-canary.md)。

还要划清两条边界。第一，这几项指标是「用来做决策的」，不是「用来证明某版更好的」：改动前后必须在同一批用例、同一套判定、同一份口径下比，否则数字没有可比性，基线怎么守住见 [回归门禁与基线](./k091-regression-gate.md)。第二，指标能算得出来的前提是字段齐——每轮的用量、耗时、成功失败、越权标记都得在事件产生当场记下，见 [Trace 该记什么](./k094-trace-fields.md) 与 [结构化日志与轨迹回放](./k095-structured-log.md)；成本上涨后的因子拆分，也依赖这些字段能按轮聚合。指标本身不负责省钱，它只负责把「贵在哪」指出来，具体压分子还是撑分母，得回到轮次控制、上下文管理与重试策略上去动手。

## 九、三句话小结

核心指标与按成功任务核算成本，是把「做成了多少、有没有越权、最慢的那批多慢、每做成一件花多少」摆在一起看，并用「全部消耗 ÷ 成功任务数」替掉那个会被失败拉低的漂亮单价。

关键做法是先给「做成」下可验证的判定，让分子包含所有任务的花费、分母只数成功的，再配上尾延迟与平均轮数做诊断，改动前后在同一批用例和同一套口径下比较。

当任务没有明确的「做成」定义、或者根本不追求任务级结果（只做一次性查询、按次计价即可）时，不必硬套按成功任务核算；但只要一次改动会同时影响成功率与轮数，单看调用单价就一定会把结论带偏。

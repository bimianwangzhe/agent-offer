# 采样参数与不确定性：调到 0 也不等于确定

## 一、一个白天过、晚上挂的测试

你写了个回归测试：给定一句提示，断言回答正好等于"晴天"。本地连着跑十次都过，你放心地把它留下了。第二天同一样例挂了，回答变成"多云转晴"，意思没错、字不一样。你把温度调到 0，心想这下总算锁死了，跑了一阵果然稳；可换个批次、换台机器，又冒出一次不一样。更让你困惑的是，让它"只输出 JSON"（JSON 全称 JavaScript Object Notation，一种用键值对组织数据的文本格式），它偶尔会在前面加一句"好的，结果如下"，而你明明一个参数都没动。

三件事看着各不相干，其实都在考同一个假设：你把输出当成了"给定输入就该逐字相同"的东西。

## 二、先破误解

**不是模型偶尔抽风，也不是把温度调到 0 就能锁死，输出天生是一次抽样，确定性从来不是它提供的保证。**

顺着[下一个词预测](./k002-next-token.md)那一步往下看：模型每步给"接下来可能接上的每一片"各估一个分数，把这些分数转成一组概率，再按概率抽一片。温度（temperature）和 top_p 就是在这中间动手脚的两个旋钮，而且动的是同一处——概率的形状。

温度管的是"差距"。低温把高分和低分的差距拉大，概率几乎全堆到头号候选上；高温把差距捏平，本来没什么机会的冷门候选也分到不小的一份。top_p 管的是"范围"：先按概率从高到低排队，只留累计概率够到某个比例（比如 0.8）的那一小撮头部候选，尾巴上那一长串直接盖掉，再只在留下的这撮里抽。两个旋钮一个改陡缓、一个改圈多大，但都没取消最后那一下"抽"。

理解了这点，"调到 0"的误会就好拆了。在一个干净的本地桩里，温度 0 可以简单实现成"总取最高分"，看着确实定；可真实系统里还有并列最高分怎么办、浮点计算怎么舍入、并行结果怎么归并、同一接口不同版本怎么算，任何一处都能让"最高"不唯一、或让两次结果飘开。把"我这边跑十次都一样"写成"所以它一定确定"，是把一次观察当成了保证。至于"只输出 JSON"那句，它只是写进文字里的一句请求，作用是让那种输出更可能出现，不是一道能强制生效的开关——它和"别写第三条"一样，改的是概率，不是规则。

:::warn 别把"参数"当成"约束"
旋钮只能让某种结果更可能，不能让它必然发生；能强制生效的东西，得写在代码里。
:::

## 三、生活类比：一个可以捏的转盘

想象一个转盘，每个扇区的大小代表某个候选词被选中的可能性。打分先定下扇区的初始大小；温度像一只手，把大小差距捏平或拉大——手一松（高温），小扇区也鼓起来，冷门词也有机会上榜；手一紧（低温），头号扇区几乎占满整盘。top_p 像先拿一块挡板，把尾巴上那堆碎小扇区盖掉，只在剩下的头部里转。

可无论你怎么捏、怎么盖，最后收尾那一下仍然是"转转盘"，不是"指定它停在哪一格"。就算头号扇区占了九成九，剩下那薄薄一片仍可能被指针扎中。对应关系逐条摆出来：

- 打分，是每个候选词拿到的初始扇区；
- 温度，是那只把差距捏平或拉大的手；
- top_p，是盖掉长尾碎扇区的挡板；
- 抽样，是最后转的那一下；
- 温度调到 0，是头号扇区几乎占满整盘——注意是"几乎"；
- 偶发的不一样，是指针恰好扎中了那一小片；
- 把测试写成"必须等于晴天"，等于断言指针每次都停在同一格。

这个类比还解释了一个常见纠结：既然总有随机，是不是就没法测了？不是。不能测的是"停在哪一格"，能测的是"指针有没有跑出盘面"——比如每次落地都必须是那几个候选之一、都必须满足某种格式。把断言从"哪一字"挪到"什么性质"，测试立刻就稳了。

## 四、画出来：从分数到一片文字

先看单步里这四层，旋钮加在哪一层一目了然：

:::figure 从分数到一片文字的四步
@stack
候选打分::每个可能的下一片得一个分数
温度整形::把分数差距捏平或拉大
top_p 截断::只留累计概率够数的头部候选
按概率抽样::转一下，落到哪片就用哪片
:::

前三层都在"准备盘面"，只有第四层真正在选。所以调参数其实是在调盘面，不是在调那一下的结果；把盘面调得再极端，第四层依旧是抽样。这也是为什么"温度 0 就确定"这句话在概念上就站不住：它把"准备"当成了"决定"。

再把两种测试写法摆在一起，差别就不只是措辞了：

:::figure 两种测试写法的差别
@compare
断言字面相等::偶发就挂|换了批次更悬|把随机当保证
断言输出性质::只在意该有的|容忍换种说法|测的是约束
:::

左边那条路把宝押在指针上，只要有一片飘了就报失败，可系统本身并没做错什么；右边那条路测的是你真正想守的东西——该有的字段在不在、格式能不能解析、取值有没有越界。这两张图合起来给出一句很实用的话：参数归参数，约束归约束，别指望用前者去兑现后者。

## 五、顺着追问两层

:::ask 那如果我就是要稳定格式，比如必须是 JSON，是不是只能靠调参数？
:::

调参数只能提高"更可能长成那样"，不能保证，所以正解不在旋钮上，而在把那句请求变成代码能强制执行的契约。具体顺序是：先把返回交给解析器看能不能读懂；读不懂，优先做清洗与提取（比如去掉多出来的开场白、把包在代码块里的内容取出来），而不是立刻重问；读懂了再核对字段齐不齐、类型对不对；实在改不好，超过次数就返回一个确定的默认结果或转人工，绝不让调用无限挂着。注意这条链里没有一步依赖"模型这次会听话"，每一步都是代码在判定。它和[用量统计与计费口径](./k010-usage-billing.md)里"别估、去读真实值"是同一种思路：把不确定的部分交给确定性逻辑去兜。

:::ask 那如果同一句提示跑很多次，结果会不会至少收敛到同一个分布？
:::

这个想法方向是对的，但要把话说准。"分布稳定"和"单次确定"是两件事：多次重复能让你看出"哪些性质几乎总成立"，却永远推不出"下一次逐字等于什么"。所以工程上正确的验证是跑一组、看性质是否每次都成立——每次都是可解析的、每次都含必需字段、每次取值都在合法范围——而不是看字面是否一致。这里要格外守住一条：别拿"我跑了几次都这样"去编一个百分比当结论，那是把有限观察包装成了保证。可复现的做法是构造一组固定的输入、固定的随机种子、固定的判定条件，把"通过几项"如实打印出来，谁都能照着重跑一遍。下面这段代码就是这么设计的，它不声称任何真实系统的表现，只把机制摆给你看。

## 六、跑一段代码，把"不确定"摸实

下面这段只用标准库，不联网、不装包、不要账号。它用固定随机种子把抽样过程复现出来，并对比"字面断言"与"性质断言"哪种站得住。

```python
import math
import random


def softmax(scores, temperature):
    """把一组分数转成概率；温度越低，概率越往最高分集中。"""
    if temperature <= 0:
        m = max(scores)
        return [1.0 if s == m else 0.0 for s in scores]  # 桩：全给最高分
    m = max(scores)
    exps = [math.exp((s - m) / temperature) for s in scores]
    total = sum(exps)
    return [e / total for e in exps]


def top_p_filter(words, probs, p):
    """只留累计概率达到 p 的候选，再重新归一化。"""
    order = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)
    kept, acc = [], 0.0
    for i in order:
        kept.append(i)
        acc += probs[i]
        if acc >= p:
            break
    s = sum(probs[i] for i in kept)
    return [(words[i], probs[i] / s) for i in kept]


def sample(pairs, rng):
    """按概率抽一个词；随机性来自传入的随机数发生器。"""
    r, acc = rng.random(), 0.0
    for w, pr in pairs:
        acc += pr
        if r <= acc:
            return w
    return pairs[-1][0]


if __name__ == '__main__':
    checks = 0
    words = ["晴", "阴", "雨", "雪"]
    scores = [3.0, 2.0, 1.0, 0.5]

    # 1) 温度低 -> 概率更集中；温度高 -> 更平
    low = softmax(scores, 0.2)
    high = softmax(scores, 2.0)
    assert low[0] > high[0]
    checks += 1

    # 2) top_p 截断后候选变少，概率重新加和为 1
    base = softmax(scores, 1.0)
    pairs = top_p_filter(words, base, 0.8)
    assert 1 <= len(pairs) < len(words)
    assert abs(sum(pr for _, pr in pairs) - 1.0) < 1e-9
    checks += 1

    # 3) 换随机种子，输出会变 -> 不确定性真实存在
    rng = random.Random(0)
    results = {sample(pairs, rng) for _ in range(60)}
    assert len(results) > 1
    checks += 1

    # 4) 正确的测法：断言性质（结果都在候选里），而不是字面相等
    assert results.issubset(set(words))
    checks += 1

    # 5) 反面教材：把输出写死成"晴"，换个种子就会挂
    hits = sum(1 for s in range(20) if sample(pairs, random.Random(s)) == "晴")
    assert 0 < hits < 20
    checks += 1

    # 6) 即便温度设 0，出现并列最高分时"确定性"仍有歧义
    tie = softmax([2.0, 2.0, 1.0], 0.0)
    assert tie[0] == tie[1] == 1.0
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `softmax` 把分数转成概率。先减掉 `max(scores)` 再取指数，是为了数值不溢出；温度越小，除出来的差距被放得越大，头号候选拿到的概率越高。`temperature <= 0` 那支是桩里的"总取最高"，不是真实模型的行为。
2. `top_p_filter` 按概率降序排好下标，累加到 `acc >= p` 就停，再把留下的候选重新归一化，让概率重新加和为一。它对应第二张图里"盖掉长尾的挡板"。
3. `sample` 用 `rng.random()` 落一个点，沿累计概率走，落到哪片就返回哪个词。随机性全部来自传入的 `rng`，所以换种子就能复现不同结果，这是"可复现的构造场景"，不是任何实测。
4. 断言一、二钉住两个旋钮确实改变了盘面：低温更集中、截断后候选更少且概率合法。
5. 断言三、四是这一篇的正反两面：换种子后结果不止一种（不确定性真实存在），但每种都落在候选集合里（性质断言成立）。断言五更直接——把输出写死成"晴"，二十个种子里既不是全中也不是全不中，说明这种断言一定会挂。
6. 断言六专门回应"调到 0"：当两个候选并列最高时，桩里那个"全给最高分"的写法会同时给出两个 1.0，"取最高"本身就不再唯一。它提醒你，即便在最简化的模型里，确定性也不是白给的。

要再强调一次：这里所有数字都来自固定种子下的构造，不代表任何真实服务的表现。把这套思路放回系统里，结论只有一个——测试去断言性质，格式去交给代码校验。至于"为什么这些看起来笃定的内容也可能根本不成立"，接着读[幻觉为什么必然存在](./k005-hallucination.md)最顺；整条线从哪起步，可以看[从这里开始](./00-start-here.md)。

## 七、踩坑与边界

- **把温度 0 当确定性保证**：现象是本地稳、换批次又飘 → 原因是并列最高、浮点与版本差异都能让结果不唯一 → 别把"十次一样"写成"必然一样"，测试只断言性质。
- **断言输出等于固定字符串**：现象是偶发失败、查来查去没改动 → 原因是每片都带抽样 → 改断言格式、字段、范围这类可判定的性质。
- **把"请只输出 JSON"当开关**：现象是偶尔多一句开场白或包了代码块 → 原因是那只是抬高概率的一句文字 → 用解析、清洗、结构校验和超次降级把它变成代码契约。
- **温度与 top_p 一起乱调**：现象是出问题分不清是谁引起的 → 原因是两个旋钮同时改了盘面 → 一次只动一个、留一份基线，改完逐项对比。
- **把本地桩的"确定"搬上真实系统**：现象是照桩写了断言，线上照样挂 → 原因是桩用查表或固定种子代替了抽样 → 桩只用来理解机制，判定条件按真实的不确定性来写。

## 九、三句话小结

采样参数只改变候选的概率形状，输出始终是一次抽样，确定性不是模型提供的保证。
要紧的做法是把断言写成性质、把格式交给代码校验，并用固定种子构造可复现的验证。
当你需要逐字固定、或需要对结果打包票时，别靠调旋钮，改用确定性的解析与校验逻辑去兑现。

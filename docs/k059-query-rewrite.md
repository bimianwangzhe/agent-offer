# 查询改写与指代补全：把「它多少钱」问完整

## 第二句话一问，助手就懵了

用户上一句问「XJ-2200B 这个型号怎么样」，助手答完；下一句紧接着问「它多少钱」，结果召回空空如也，助手只好编了个数。你翻日志发现，拿去检索的查询就是「它多少钱」这五个字——库里没有任何片段含「它」，自然一条都匹配不上。还有用户一句话里塞两个问题：「XJ-2200B 多少钱和质保多久」，一次检索只捞回价格，质保那段压根没进候选。

## 先破一个误解

**不是库里没这些内容，是拿去检索的那句话单独看根本不成问题。**

先把词说清楚。查询改写指在检索之前，把用户这一轮的自然语言加工成更适合查找的形式：纠错、把缩写展开、把口语换成材料里更常见的书面说法。指代补全（coreference resolution 这一层意思，白话叫「把『它』『这个』『上面说的』换成它真正指的东西」）是其中最要紧的一种，因为多轮对话里当前这一句往往借了上文的实体，脱离历史就不完整。此外还有拆子问题：一句里问了两件事，就拆成两个各自独立、各自能查的问法；以及生成几种变体：同一意图写出原问法、补实体版、抽关键词版等，多路召回再合到一起。

为什么这一步性价比高？因为它动的是整条链路的最前端。检索器再精妙，也只能按你递给它的那句话去找；递进去的是「它多少钱」，后面所有环节——两路召回、融合、重排、溯源——都在为一个不完整的问题卖力。改写不需要动索引、不需要重建任何数据，只是在提问那一刻多花一点判断，就能把「零命中」变成「命中正确片段」。这也是为什么不改写的代价常被误判成「检索不行」：日志里看到的是召回为空，根子却在查询这一侧。

不过改写有两个要守的边界。一是别把意思改偏：「它多少钱」补成「XJ-2200B 价格」是对的，补成「XJ-2200A 价格」就错了，所以原始问法那一路通常要保留，和改写版一起参与召回，避免一次改写把整条链路带沟里。二是拆开之后，每个子问题都要各自补齐实体：把「多少钱和质保多久」拆成两句，第二句「质保多久」若丢了型号，照样查不准。多路结果怎么合成一份排名，见[混合检索与 RRF 融合](./k058-hybrid-rrf.md)；改写本身算一步判断，预算与轮数怎么控制，见[多轮检索与检索质量评测](./k064-rag-eval.md)。整套顺序可以从[从这里开始](./00-start-here.md)看起。

## 用委托别人跑腿查资料来理解

把检索想成你托一位同事去档案室查一份材料，而你只能给他一张写着问题的便条。

你若随手写「它多少钱」就递过去，同事到了档案室会站在原地发愣：谁？哪个它？他不会去猜你五分钟前跟别人聊了什么，因为他手上只有这张便条。这正对应检索器——它只看这一轮递进去的查询，不会自动去翻聊天历史。

有经验的委托人会先把便条写完整：把「它」换成具体型号，把口语说法换成档案里用的正式名称，一句里问了两件事就写成两张便条分别去查，甚至同一件事多写两种措辞，让同事哪张顺手用哪张。最后还不忘附上原话那张：「万一我补错了，你照原话再查一遍」。

对应关系：便条是查询，档案室是索引，同事是检索器，聊天历史是对话上下文，换成型号是指代补全，改措辞是书面化，拆成两张是拆子问题，附上原话是保留原始问法那一路。这个比喻点出了关键：问题出在「递出去的那张纸」，不是档案室没料，也不是同事不卖力。

:::quote
检索器只认你这一轮递进去的那句话。多轮对话里，把「它」补成实体往往比换检索算法管用得多。
:::

## 把改写画出来

先看一轮提问从用户出口到真正进检索，中间经过哪些动作。

:::figure 一句话到多路可查的查询
@flow
读取当前句|补出指代实体|拆开复合问|生成几种问法|多路召回
:::

第二、三、四步都是「把一句话加工成几种能查的问法」，顺序上先补实体再拆句更稳，否则拆出来的子问题都缺主语。

改写这一步该产出什么，可以列成清单：

:::figure 改写要交出的几样东西
@stack
原问法::原样保留一路，防止改写把意思带偏
补全版::把代词换成上文实体，形成独立完整的问题
拆分版::复合问题拆成各自带实体的子问题
关键词版::抽掉寒暄只留型号编号等强线索
:::

第一行常被漏掉，却是兜底：改写是一次判断，判断就可能错，留原问法那一路相当于给自己留一次不依赖判断的机会。

再看两种做法的差别：

:::figure 直接拿原句查，与先改写再查
@compare
直接拿原句::代词查不到|复合问只中一半|坏例难定位
先改写再查::指代补全|子问题各自可查|保留原句兜底
:::

第二行三格对应三类高频坏例。尤其「坏例难定位」：改写后的查询会写进日志，一眼就能看出是补实体补错了，还是拆句拆漏了。

:::tip 一条立刻见效的规则
把改写后的每一种问法都记进当轮日志，连同原问法一起。召回为空时先看这份日志——多数「零命中」在这里就能看出原因，不必去翻索引。
:::

## 再往深问两层

:::ask 那如果改写也要多一次模型判断，会不会把延迟和成本推高了？
:::

会有开销，所以要把「值不值」算清楚。首先不是每轮都需要改写：用户这一句若是完整、独立、带实体的问题，直接查最省；只有出现代词、省略、明显口语、复合句时才触发，判断本身可以很轻。其次改写常常省下的是更贵的开销：一次零命中之后用户会追问、系统会重试、甚至再跑一轮生成，这些加起来远比一次轻量改写贵。真正要防的是「变体越多越好」——一次性生成十几种问法，会同时拉高召回噪声与后续重排的负担，也把上下文塞满。稳妥做法是控制数量：原问法一路、补全版一路、必要时加关键词版，两三路足够，靠[混合检索与 RRF 融合](./k058-hybrid-rrf.md)把多路结果合成一份排名，而不是把每种问法的结果都塞进上下文。

:::ask 再深一层：指代补全到底该从多久以前的历史里找实体？
:::

这是改写最容易出错的地方。找得太近，可能把上一句刚提的次要对象当成主语；找得太远，又会把早已翻篇的旧实体接回来。工程上别指望「让模型自己看着办」，要把范围写进规则：优先取最近一轮里被明确点名的实体，并带一份候选清单（编号、名称、这一轮是否还在讨论）；若出现多个候选且分不清，宁可把几种补全都作为变体去查，也不要武断选一个。还有两个隐蔽点：一是否定与转折，「不要 XJ-2200B，换个型号」里的实体是被排除的，不能拿来补全；二是改写要在过滤之前完成、但补全进来的实体必须受可见范围约束，否则可能借着历史把一个本不该查的编号带进检索，这一点要和[元数据过滤前置](./k060-metadata-filter.md)配合。最后，改写出的问题是否真的更准，不能凭感觉，得拿一组多轮评测问题看该找的片段回没回来，见[多轮检索与检索质量评测](./k064-rag-eval.md)。

## 一份能跑的对照

下面这段只用标准库，构造一段多轮对话，写指代补全、拆子问题、给子问题补实体，并演示「原句零命中、补全后命中、多路合并仍命中」。不装包、不联网。

```python
# query_rewrite.py —— 只用标准库，python query_rewrite.py
import re

DOCS = {
    "d1": "型号 XJ-2200B 售价 4800 元",
    "d2": "型号 XJ-2200B 质保三年 含上门检修",
    "d3": "型号 XJ-2200A 售价 3200 元",
}
ENTITY = "XJ-2200B"                      # 从上一轮对话里取出的实体
PRONOUNS = ("它", "这个", "那个", "上面说的", "这款")


def resolve(q, entity):
    # 指代补全：把代词换成上文实体
    for p in PRONOUNS:
        if p in q:
            return q.replace(p, entity, 1)
    return q


def terms(t):
    return set(re.findall(r"[A-Za-z0-9]+|[\u4e00-\u9fff]", t.lower()))


def retrieve(query):
    ts = terms(query)
    return [k for k, v in DOCS.items() if ts & terms(v)]


def split_compound(q):
    # 复合问题按「和 / 跟 / 以及」拆成子问题
    return [p.strip() for p in re.split(r"\s+(?:和|跟|以及|还有)\s+", q)
            if p.strip()]


def carry_entity(parts, entity):
    # 拆开后，每个子问题都要各自带实体
    return [p if entity in p else entity + " " + p for p in parts]


if __name__ == '__main__':
    raw = "它多少钱"
    assert retrieve(raw) == []                  # 原句含代词，零命中
    full = resolve(raw, ENTITY)
    assert full == "XJ-2200B 多少钱"
    assert "d1" in retrieve(full)                # 补全后命中价格片段

    # 多路召回：原句 + 补全版，避免改写引入偏差
    variants = [raw, full]
    merged = []
    for v in variants:
        for d in retrieve(v):
            if d not in merged:
                merged.append(d)
    assert len(variants) == 2
    assert "d1" in merged

    parts = split_compound("XJ-2200B 多少钱 和 质保多久")
    assert len(parts) == 2
    subs = carry_entity(parts, ENTITY)
    assert subs[1] == "XJ-2200B 质保多久"       # 第二个子问题也带上了实体
    print("通过 7/7 项：指代补全、复合拆句、多路召回与子问题补实体")
```

1. `DOCS` 是本地构造的三段小材料，`ENTITY` 是假装从上一轮里取出的实体。整套逻辑不读历史文件，取实体的动作用一个常量代替，好让结果可复现。
2. `resolve` 是最朴素的指代补全：命中 `PRONOUNS` 里任一个词就把它替换成实体。`terms` 把查询和文档折成词项集合，`retrieve` 只做「有没有交集」的判断——故意做得很笨，这样才能显出「递进去什么」有多要紧。
3. `split_compound` 按「和 / 跟 / 以及」把一句拆成子问题；`carry_entity` 给每个不带实体的子问题补回实体，对应前面那条「拆开之后各自补齐」的规则。
4. 中间那组断言把核心现象摆出来：`retrieve("它多少钱")` 返回空，补成 `"XJ-2200B 多少钱"` 后命中 `d1`。差别不在检索器，只在查询那一侧。
5. 后半段演示多路召回合并与复合问题拆分，七条断言跑完打印通过项数。可以自己把 `variants` 里的 `raw` 去掉，看看「只信改写」时少了哪一层兜底；或者把 `carry_entity` 那步注释掉，会看到第二个子问题退化成「质保多久」。

真实系统里 `resolve` 可能是一次轻量判断，也可能按规则从结构化对话状态里取；但「原句保留一路、补全版一路、拆句后各自补实体」这个形状不用变。

## 踩过的坑

- **拿当前句直接查**：现象是多轮里第二轮起频繁零命中 → 原因是代词脱离上下文没有指代 → 怎么改：检索前先结合历史补全实体，并把补全后的查询记进日志。
- **改写把意思带偏**：现象是补错了型号，答案看起来很顺却全错 → 原因是只信一次判断、没留原问法 → 怎么改：原始问法那一路始终参与召回，多路合并时一起累加。
- **拆句后丢实体**：现象是复合问题的第二个子问题查不到 → 原因是拆分时只有第一句带着型号 → 怎么改：拆完逐个子问题补齐实体再各自检索。
- **变体生得太多**：现象是候选噪声变多、延迟上升 → 原因是认为问法越多越好 → 怎么改：控制在两三路，靠融合合排名，而不是把每路结果都塞进上下文。
- **补全绕过可见范围**：现象是借历史把一个不该查的编号带进了检索 → 原因是补全发生在过滤之前却没受约束 → 怎么改：补全进来的实体也要经过滤前置那一层。

## 三句话

查询改写与指代补全，是在检索前把当前这句加工成补全实体、拆开复合、生成几种问法的一组完整查询。
关键做法是原问法始终留一路兜底、拆句后各自补实体，并把每一种改写问法都记进当轮日志。
当用户每轮都是完整独立的问题、不含代词也不含复合句时，直接检索即可，不必多此一举。

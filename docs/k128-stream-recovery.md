# 流式断线恢复与分片校验

## 一、一句读起来别扭的回答

你在页面上做逐字显示，模型一边生成、屏幕一边往外冒字，体验挺好。可某次网络抖了一下，用户看到回答里莫名多出半句重复的「因此需要因此需要」，另一次则是中间凭空少了一小段，语句接不上。你去查后端，服务日志显示这次生成其实完整又正常；去查前端，拼接代码也就是一句「把收到的文本往后追加」。两边都没错，错在中间那段路：长连接把整段文本切成许多小片分批发，分片会乱序、会重复、会中途断，而「收到就往后贴」这种最朴素的做法，默认了它们永远按序、不重、不丢一次到达。

## 二、先破这个把责任推错地方的误解

**不是模型把话说重复了，也不是前端拼接写错了，而是你把「一串有序、可靠、不重复的事件」当成了「一段可以直接往后贴的字符流」。**

先说清几个词。流式输出指的是模型边生成边返回，不用等整段写完，用户能更早看到第一个字，这个等待时间常叫首字延迟（Time To First Token，缩写 TTFT，指从发出请求到屏幕上出现第一个字块的时间）。承载它的常见做法是服务端推送事件（Server-Sent Events，缩写 SSE，一种让服务端持续往客户端推小段消息的长连接方式）或长连接。这里的关键在于：服务端发下来的不是「一段话」，而是「一批带编号的小事件」，每个事件里有一小片文本、一个事件编号（Identifier，标识符，用来唯一指认一个对象的一串编号）和一个递增的序号。关于流式本身为什么能降低等待却不省钱，[流式输出与首字延迟](./k009-streaming.md) 已经讲过；本篇只盯住最容易被忽略的一层：这些分片是会出问题的，而拼出正确全文需要一套校验，不是一句追加。

## 三、把它想成按编号寄出的一套书

打个比方：一本厚书被拆成几百页，一页一个信封分头寄给你，每个信封上写着「第几页」。你要做的事是把它们按页码排好、装订成册。这里有一一对应关系：每个分片等于一个装了一页纸的信封；序号等于信封上的页码；事件编号等于这封信的唯一挂号单号；你的客户端等于收信人；而「拼接成全文」等于按页码把书页装订好。

这个类比一下就把三类故障摆明了。第一，信件不一定按页码顺序到，先寄的第 3 页可能比第 1 页晚到，这就是乱序——若收到就往后贴，页码 3 会插到页码 1 前面。第二，邮局可能把同一封信投了两次，这就是重复——照单全收会多出一页，正对应开头那句「因此需要因此需要」。第三，某个信封可能在半路丢了，这就是缺失——不检查页码连续性，你根本不会发现中间少了一页，还以为书是完整的。此外还有一种更麻烦的：寄到第 50 页时邮路断了，这就是断连，你需要拿着「已收到的最大页码」去请对方从第 51 页继续寄，而不是从头重寄一遍。这四件事——乱序、重复、缺失、断连——正是「只做前端追加」完全没处理的。

## 四、两张图看清正确的拼法

:::figure 一个分片从到达到入册
@cycle
接收分片|查重去复|按序排号|检测缺口|按序装订
:::

第一张图用的是循环箭头，因为分片是一批批持续到达的，每一片都要过同一套流程。「查重去复」用事件编号判重，重复的直接丢；「按序排号」按序号归位，不依赖到达顺序；「检测缺口」看序号有没有跳号；「按序装订」才是真正拼成可读文本。注意顺序：先去复、再排序、再验缺口、最后拼，任何一步省了都会留下隐患。

:::figure 两种拼接思路的差别
@compare
收到就追加::乱序插错位置|重复叠出半句|缺页毫无察觉
校验后装订::按序号归位不惧乱序|按编号去重不叠字|跳号即发现再续传
:::

第二张图把差别摊开。左边那种不是「偶尔出错」，而是把正确性完全押在「网络永远理想」这个前提上，一旦前提不成立就以用户能读到的方式坏掉。右边那种多做的事其实就三件：编号去重、序号排序、连续性检查。这三件都不难，难的是意识到必须做。

## 五、顺着追问把边界推出来

:::ask 那如果分片只是乱序、没丢也没重，先攒齐再排序是不是就够了？
:::

对短回答，攒齐再排序确实能解决乱序，代价是丢失了逐字显示的意义——你得等最后一片到齐才敢展示，首字延迟的好处就被抵消了。更常见的做法是「边收边显示，但设一个有序窗口」：只把当前连续的那一小段往外推，跳号的部分先缓着，等缺的那片补上再一起放行。这样既保留了边生成边看的体验，又不会把乱序片段直接贴给用户。这里还牵出一个容易被忽略的点：判断「连续」靠的是序号，所以序号必须单调递增且可比较；如果服务端给的序号在不同重连段里会重置，你就得额外带一段「连接批次」的信息，否则两段的第 1 片会撞在一起。

:::ask 再追一层：断线重连时，怎么知道该从哪一片继续，才不会重复也不会漏？
:::

靠客户端自己记住「已成功装订到的最大序号」，重连时把它作为起点交给服务端，请对方从这个序号之后继续推。这里最微妙的是「已装订到」而不是「已收到」：如果第 40 片收到了但第 39 片还没到，你不能说自己续到了 40，因为 39 到 40 之间还有个洞没补上，正确做法是只承认连续段的末尾。否则重连后要么把 40 之后的重发一遍造成重复，要么跳过 39 造成永久缺失。另一个边界是副作用：重连续传只适用于「同一段生成」还在服务端缓存中可续的情形；如果服务端已经把这次生成丢弃了，你就只能明确地告诉用户「这段没接上」，而不是悄悄拼出一个看似完整、实则缺了一块的答案。把「残缺」伪装成「完整」，比直接报失败更危险，因为它让人信了一个错的结果。这也是为什么校验里「检测缺口」这一环不能省——它决定你有没有资格说「这次是完整的」。

## 六、用一段可运行代码把校验演出来

下面这段不联网、不装任何第三方包，用一串本地造的分片模拟乱序、重复、缺失与断连，再写一个「装订器」把它们还原成正确全文，并演示按最大连续序号做续传。

```python
# 假分片：(序号, 事件编号, 一小片文本)
# 故意打乱到达顺序、塞入一个重复、挖掉一个缺口，模拟真实长连接的三种故障
INCOMING = [
    (3, "e3", "，"),
    (1, "e1", "今天"),
    (2, "e2", "天气"),
    (2, "e2", "天气"),      # 重复投递的同一片
    (5, "e5", "适合"),      # 第 4 片暂缺
    (6, "e6", "出门"),
]
EXPECT_PARTS = {1: "今天", 2: "天气", 3: "，", 4: "不错", 5: "适合", 6: "出门"}

class Binder:
    def __init__(self):
        self.seen_ids = set()      # 已收过的事件编号，用来去重
        self.by_seq = {}           # 序号 -> 文本，按序号归位
        self.contiguous_upto = 0   # 已连续装订到的最大序号，续传起点

    def accept(self, seq, event_id, text):
        if event_id in self.seen_ids:
            return "duplicate"     # 编号见过，直接丢弃
        self.seen_ids.add(event_id)
        self.by_seq[seq] = text    # 不按到达顺序，按序号存放
        return "accepted"

    def recompute_contiguous(self):
        n = 0
        while (n + 1) in self.by_seq:
            n += 1
        self.contiguous_upto = n

    def contiguous_text(self):
        return "".join(self.by_seq[i] for i in range(1, self.contiguous_upto + 1))

    def missing_in(self, upto):
        return [i for i in range(1, upto + 1) if i not in self.by_seq]

def main():
    b = Binder()
    statuses = [b.accept(s, i, t) for s, i, t in INCOMING]
    b.recompute_contiguous()

    # 客户端只承认连续段的末尾，缺口被显式发现
    gap = b.missing_in(6)
    # 断线续传：拿连续段末尾当起点，请服务端补发缺的第 4 片
    resume_from = b.contiguous_upto
    b.accept(4, "e4", EXPECT_PARTS[4])
    b.recompute_contiguous()

    results = []
    results.append(("重复分片被识别并丢弃", "duplicate" in statuses))
    results.append(("去重后共接收 6 个不同编号", len(b.seen_ids) == 6))
    results.append(("乱序到达仍能按序号归位", list(sorted(b.by_seq)) == [1, 2, 3, 4, 5, 6]))
    results.append(("续传前能检测出第 4 片缺口", gap == [4]))
    results.append(("续传起点等于连续段末尾 3", resume_from == 3))
    results.append(("补齐后连续段推进到 6", b.contiguous_upto == 6))
    results.append(("最终全文正确且无重复字",
                    b.contiguous_text() == "今天天气，不错适合出门"))

    passed = sum(1 for _, ok in results if ok)
    for name, ok in results:
        print(("通过" if ok else "未通过") + "：" + name)
    print("通过 {}/{} 项".format(passed, len(results)))
    assert passed == len(results)

if __name__ == '__main__':
    main()
```

逐段看关键行在做什么：

1. `INCOMING` 是本地造的到达序列：顺序打乱、第 2 片重复一次、第 4 片故意缺着。它就是「网络不老实」的最小复现，全是写死的假数据，可复现、不联网。
2. `Binder` 有三个状态：`seen_ids` 用集合记事件编号判重，`by_seq` 用字典按序号归位，`contiguous_upto` 记「已连续装订到的最大序号」。这三个字段分别对应三类故障的对策。
3. `accept` 先查编号是否见过，见过就返回 `duplicate` 直接丢；否则把文本按 `seq` 存进字典。注意它完全不依赖到达顺序——这是治乱序的关键。
4. `recompute_contiguous` 从 1 开始往上数，遇到第一个不在字典里的序号就停。这个「数连续段」的动作，正是续传起点该怎么定的答案：只认连续段末尾，不认最大已收序号。
5. `missing_in` 列出给定范围内的缺口，`contiguous_text` 只拼连续段，保证推给用户的每一句都是接得上的。
6. `main` 先让乱序重复缺片的批次过一遍装订器，验证去重、归位、缺口检测与续传起点，再补发第 4 片，最后断言全文是 `今天天气，不错适合出门`，没有重复字、没有漏字。七条断言把「查重 → 归位 → 验缺口 → 续传 → 装订」整条链钉死。

:::tip
判断续传起点用「已连续装订到的最大序号」，别用「已收到的最大序号」。后者会把一个还没补上的洞当成已越过，重连后要么重复、要么永久漏一片。
:::

## 七、踩过的坑与它的边界

- **收到就往后贴**：现象是回答里冒出重复半句、或语句接不上 → 原因是默认分片永远按序、不重、不丢 → 先按事件编号去重、按序号归位、验连续性，再拼成可读文本。
- **按到达顺序排序**：现象是先到的高序号插到了低序号前面 → 原因是把「到达次序」当成了「内容次序」 → 用服务端给的递增序号做唯一顺序依据。
- **用最大已收序号续传**：现象是重连后少了中间一片且不自知 → 原因是中间缺口未越过却已被当成连续 → 用「连续段末尾」当起点，缺口没补上就不推进。
- **把残缺伪装成完整**：现象是用户读到一份看似通顺、实则缺了一块的答案还信以为真 → 原因是没做缺口检测就宣布完成 → 检测到跳号要么补发成功、要么明确告知没接上，绝不静默放行。
- **重连段序号重置**：现象是两次连接的第 1 片撞在一起、去重误杀 → 原因是序号只在单段内递增 → 给每段带连接批次标识，判重与排序都带上班次。

还有一层边界要说清：这套校验保证的是「字节层面把服务端发过的东西正确还原」，它不保证「生成内容本身对不对」——那是模型和校验器的事。而且续传有前提：同一段生成的分片在服务端还可取回。若服务端已经丢弃这次生成，正确反应是如实告知重来，而不是拿缓存拼出一个过期答案。另外，去重依赖事件编号全局唯一，如果编号只在单片意义下唯一，判重就会误伤，这是设计编号时要先约定的。

## 九、三句话小结

流式断线恢复与分片校验，是把一批带编号、带序号的小分片正确还原成完整文本的一套机制，覆盖乱序、重复、缺失与断连四类故障。

关键做法是用事件编号去重、用递增序号归位、用连续性检查发现缺口、用连续段末尾作为续传起点，并在无法补齐时如实告知而非伪装完整。

当输出是一次性同步返回、根本没有分片与长连接时，这套校验用不上，直接拿整段结果即可。

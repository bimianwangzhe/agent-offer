# Trace 该记什么

## 一、场景提问

线上一个任务做错了：用户让它「查一下订单，只在没发货的时候退款」，它却对一笔已经发货的订单发起了退款动作。你想复盘，翻日志只看到三行：`开始处理`、`调用工具`、`完成`。你连着问了三个问题——这次用的是哪版提示词、哪个模型、哪份工具定义？第三步凭什么把「已发货」判断成「未发货」？这一趟一共走了几步、烧了多少词元（Token，模型处理文本时按词元计量，是计费与上下文占用的基本单位）？日志一条都答不上来。更麻烦的是，当初有人为了「以后好查」，把用户输入和工具返回的原文一字不改全打进了日志，现在复盘要翻的那堆文本里混着联系号和收货地址，谁都不敢直接打开看。

## 二、破误解

**不是日志打得太少，也不是「把什么都打出来」就行，而是字段从一开始就没有挂到「事后要回答的那个具体问题」上。**

先分清两样东西。日志行是一次打印，比如 `调用工具`，它只说明「此刻发生了某件事」；而 Trace（追踪记录，把一个任务从发起到结束的全过程按时间顺序串成的一条完整记录）回答的是「这一趟从头到尾是怎么走成这样的」。单行日志天然回答不了「为什么」，因为「为什么」藏在它与前一步、与当时那套配置的关系里。很多人的第一反应是「那就多打点」，于是把原文、中间变量、整段返回一股脑塞进去；结果体积涨得飞快、敏感信息跟着落盘、真要找一句关键判断时还得在几千行里翻，仍然答不出「这一步凭什么这么选」。另一头的做法是「只记成功失败」，省是省了，可一旦指标波动，你只知道「坏了」，不知道「坏在哪一步、哪一版开始坏的」。

正确的顺序是倒过来：先列出复盘时一定会问的那几个问题，再让每个问题点名它需要哪些字段，字段清单就是这些依赖的并集。这样做有两个立刻见效的好处。其一，每个字段都有归属——你要能说出「这个字段是为了回答哪个问题」，说不出归属的字段要么是历史包袱，要么就是纯噪声，可以删。其二，缺口是可检测的——少记一个字段，就必定有一个问题从「能回答」变成「答不上来」，不用等到出事那天才发现。换句话说，字段清单不是一道「记得越多越安心」的填空题，而是一份「问题到字段」的映射表；判据只有一个：拿着这条 Trace，能不能把那几个复盘问题逐条答出来。

还要强调「在产生时结构化地记」。事后再从一堆文本里用正则去抠「这次用的哪个模型」，既脆弱又容易漏；字段要在事件发生的当场就以固定名字、固定类型写下来。这点和 [结构化日志与轨迹回放](./k095-structured-log.md) 是同一件事的两面：这一篇定「记哪些字段」，那一篇定「用什么形式记、怎么按序拼回来」。

## 三、生活类比

把它想成一件快递的运单轨迹。你在手机上点开物流详情，看到的不是「包裹里装了什么」的照片，也不是只有一句「已签收」，而是一串节点：几点几分、哪个中转场、谁扫的件、做了什么动作、下一站发往哪里；最后还有一个明确的终态——签收，或者「地址不详、退回」。要是中途改派过，还会多一条「因收件人要求改派」的记录，说明为什么路线变了。

对应关系很具体。运单号就是 Trace 的唯一编号，把散在不同环节的记录串成同一次任务；每一个节点就是 Trace 里的一条事件，带步号、时间、类型和动作；「改派记录」就是决策字段，回答「这一步为什么选这个工具、传了什么参数」；「重量体积、运费」对应每一步的词元用量与累计成本；「签收 / 退回」对应终态与终止原因。而「不把包裹里的东西拍照存档」这一条，正对应原文不落盘、敏感内容先脱敏；「不能只记已签收」对应只记成功失败不足以定位问题。

这个类比还点出两处容易被忽略的细节。第一，节点必须按序、且能追溯到同一个运单号，否则两条件号的轨迹混在一起，看着像一条，其实谁都对不上——这就是编号与关联字段的意义。第二，物流详情里记的是「动作和依据」，不是「包裹内容全文」；复盘需要的是可比对、可聚合的字段，不是一堆需要人肉再读一遍的长文本。把这两点记住，后面「该记什么」的清单几乎可以自己推出来。

## 四、自绘示意图

:::figure 一条 Trace 从产生到归档的顺序
@flow
接下任务|逐步记事件|记决策与用量|定终态|归档可复盘
:::

这五格不是五个动作的名字，而是五个「补字段」的时机。「接下任务」补的是身份与配置版本，这件事只在开头发生一次，漏了后面全程都补不回来；「逐步记事件」和「记决策与用量」是每一步都要做的，二者缺一就会退化成「知道走了几步，但不知道为什么走、花了多少」；「定终态」必须在最后显式写下成功或失败以及停下来的原因，不能靠「日志到这儿就没了」去猜。

:::figure 由复盘问题反推出的五组字段
@stack
身份与版本::唯一编号、会话号、提示词与模型与工具定义的组合版本号
事件序列::步号、时间、事件类型、动作名称、输入输出摘要
决策依据::本步选了哪个工具、传入参数、依据片段的稳定标识
用量与成本::每步输入词元、输出词元、耗时、累计成本单位
终态与护栏::成功或失败、终止原因、权限判定与脱敏标记
:::

五组字段各自挂着一个复盘问题：「这次是谁、哪套配置」「每一步发生了什么」「为什么这么选」「一共花了多少」「结果算不算成」。这里把「用量与成本」单列一组，是因为它既服务于排查绕远路，也服务于按成功任务核算账，口径必须和 [用量与计费](./k010-usage-billing.md) 一致，不能每处临时算一套。「终态与护栏」里那个脱敏标记容易被漏掉：它记的是「这条记录已经处理过敏感内容」，让后面读日志的人知道能不能放心打开。

:::figure 两种记法的差别
@compare
原文全量打印::体积涨得快|敏感跟着落盘|仍答不出为什么
按问题定字段::字段可枚举|敏感先脱敏|每个字段有归属
:::

左边是「先全打出来再说」，看似信息最全，实则三头不讨好：贵、不敢看、仍然答不出决策依据；右边是先定问题再定字段，信息量反而更够用，因为「为什么」这类关键字段被显式要求写下来，不会淹没在原文里。

## 五、层层追问

:::ask 那如果为了省钱，只记一个「成功 / 失败」字段呢？
:::

能算出一个成功率，但也仅此而已。成功率一掉，你只知道「变坏了」，不知道是第几步开始坏、哪一版配置开始坏、是不是某个工具突然多重试了几次。这时的 Trace 已经退化成一个计数器，失去了「可归因」这个它最该提供的价值。要补的也不是把原文找回来，而是把「每一步发生了什么」「为什么这么选」这两组字段加回去，让轨迹能被逐段比对——这正是 [结果评测与轨迹评测](./k089-trajectory-eval.md) 里「不只看最终结果，也看过程是否合理」的前提。字段齐了之后，坏例才能被稳定地收集、标注、复跑，形成 [坏例闭环](./k093-badcase-loop.md)；否则你连「这条坏例当时走的是哪条路径」都描述不出来，闭环根本转不起来。至于「成功率怎么定义才不骗人」「成本为什么按成功任务算而不是按每次调用算」，是 [核心指标与按成功任务核算成本](./k096-metrics-cost.md) 要展开的；这一篇只负责保证：算那些指标所需要的字段，当初一条都没少记。

:::ask 那如果把用户输入和工具返回原文整个记下来，复盘不就最全了吗？
:::

三个代价会同时找上门。一是体积：一次任务可能几十步、每步几千字，原文全留，存储与检索成本跟着步数翻。二是隐私：联系号、地址、凭证这类内容一旦落进日志，就会被复制到备份、导出、排查截图里，事后想收回几乎不可能。三是噪声：真正要找的那句判断，被埋在成堆的原文里，反而更难定位。所以更稳的做法是「原文不进 Trace，只留可比对的东西」：留一段定长指纹（把任意长度文本压成固定长度的唯一标识，用来判断两次内容是否相同）、留摘要长度、留一个稳定标识，原文另放到受控的地方，需要时按标识取回。这里要再追一层：脱敏之后还怎么复盘？答案是靠「标识 + 指纹」而不是靠原文——比对两次输入是否一致用指纹，定位到具体哪条原文用稳定标识，判断工具是否被重复调用用 [工具调用标识](./k136-tool-call-id.md)；超长返回只留引用与截断摘要，见 [大结果处理](./k138-large-result.md)。哪些内容必须遮、遮了以后还留什么，在 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md) 里有专门讲，隐私边界可对照 [记忆与隐私](./k074-memory-privacy.md)。一句话：复盘要的是「能还原决策链」，不是「把原文再读一遍」。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把「问题反推字段」这件事做成一个可验收的小工具：先声明五个复盘问题各自依赖哪些字段，再构造一条示例 Trace，最后用一组断言检查「字段不重不漏、每个字段都有归属、少一个字段就有问题答不上来、原文没落盘、能回答成本与工具序列」。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
import hashlib
from dataclasses import dataclass, field, asdict


# 五个复盘问题 -> 各自依赖的字段。字段清单不是拍脑袋列的，由问题反推。
QUESTIONS = {
    "这次是谁、用的哪套配置": ["trace_id", "session_id", "config_version"],
    "每一步发生了什么": ["events"],
    "为什么选这个工具": ["events.decision", "events.tool_args"],
    "一共花了多少": ["events.token_in", "events.token_out", "events.cost_unit"],
    "结果算不算成": ["terminal", "stop_reason", "guard_flag"],
}

# 一条 Trace 允许出现的全部顶层字段，多一个少一个都算清单没定稳
TOP_FIELDS = {
    "trace_id", "session_id", "config_version",
    "events", "terminal", "stop_reason", "guard_flag",
}


def fingerprint(text):
    """把可能含敏感信息的原文压成定长指纹，便于比对而不落原文。"""
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]


@dataclass
class Event:
    step: int
    kind: str
    decision: str
    tool_args: dict
    token_in: int
    token_out: int
    cost_unit: int
    raw_digest: str = ""


@dataclass
class Trace:
    trace_id: str
    session_id: str
    config_version: str
    terminal: str
    stop_reason: str
    guard_flag: str
    events: list = field(default_factory=list)

    def add(self, ev):
        self.events.append(ev)

    def total_cost(self):
        return sum(e.cost_unit for e in self.events)

    def used_tools(self):
        return [e.decision for e in self.events if e.decision]


def build_trace(raw_user_input):
    """构造一条示例 Trace：原文只以指纹形式留痕，不落盘。"""
    t = Trace(
        trace_id="tr-" + fingerprint("sess-7")[:8],
        session_id="sess-7",
        config_version="pv3/m1/td2",
        terminal="success",
        stop_reason="goal_reached",
        guard_flag="none",
    )
    t.add(Event(1, "plan", "search_order", {"order_id": "A1024"},
                120, 40, 2, fingerprint(raw_user_input)))
    t.add(Event(2, "tool_call", "search_order", {"order_id": "A1024"},
                60, 180, 3, fingerprint("订单 A1024 状态已发货")))
    t.add(Event(3, "tool_call", "refund", {"amount": 0},
                50, 30, 1, fingerprint("无需退款")))
    t.add(Event(4, "answer", "", {}, 90, 60, 2,
                fingerprint("已发货，无需退款")))
    return t


def covered_fields(d):
    """收集一条 Trace 实际出现的字段：顶层字段 + 用点号标出的事件子字段。"""
    result = set(d.keys())
    for ev in d.get("events", []):
        result |= {"events." + k for k in ev.keys()}
    return result


def missing_questions(d):
    """字段不够时，返回那些已经无法回答的复盘问题。"""
    present = covered_fields(d)
    return [q for q, fs in QUESTIONS.items() if not set(fs) <= present]


def main():
    raw = "示例用户，联系号 13800000000，帮我查订单 A1024"
    d = asdict(build_trace(raw))
    blob = json.dumps(d, ensure_ascii=False)
    needed = set()
    for fs in QUESTIONS.values():
        needed |= set(fs)

    broken = {k: v for k, v in d.items() if k != "config_version"}

    checks = [
        ("顶层字段不重不漏", set(d.keys()) == TOP_FIELDS),
        ("每个顶层字段都挂到至少一个复盘问题", all(f in needed for f in TOP_FIELDS)),
        ("齐备的 Trace 没有答不上来的问题", missing_questions(d) == []),
        ("缺一个字段就有一个问题答不上来",
         missing_questions(broken) == ["这次是谁、用的哪套配置"]),
        ("事件按步号严格递增",
         [e["step"] for e in d["events"]] == [1, 2, 3, 4]),
        ("用户输入原文没有落进任何字段", raw not in blob),
        ("联系号没有落进任何字段", "13800000000" not in blob),
        ("原文改以定长指纹留痕", len(d["events"][0]["raw_digest"]) == 12),
        ("能回答一共花了多少",
         sum(e["cost_unit"] for e in d["events"]) == 8),
        ("能还原走过的工具序列",
         [e["decision"] for e in d["events"] if e["decision"]]
         == ["search_order", "search_order", "refund"]),
        ("终态与终止原因齐备",
         d["terminal"] == "success" and d["stop_reason"] == "goal_reached"),
        ("序列化后可完整往返", json.loads(blob) == d),
    ]

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `QUESTIONS` 是整段的骨架：五行分别是五个复盘问题，值就是回答它必须读到的字段。注意「为什么选这个工具」依赖的是 `events.decision` 和 `events.tool_args` 这种带点号的写法，表示一个事件内部的字段；把「问题到字段」写成数据而不是写在注释里，后面才能自动验收。
2. `TOP_FIELDS` 是一条 Trace 允许出现的全部顶层字段。它和 `QUESTIONS` 是互相校验的两份东西：前者管「不许凭空多出字段」，后者管「不许漏掉该有的字段」。
3. `fingerprint` 用标准库 `hashlib` 把任意文本压成十二位定长指纹。原文可以很长、可以含敏感内容，但进 Trace 的只有这串用于比对的短标识，这正是「复盘要能比对、不要原文」的落点。
4. `Event` 与 `Trace` 用 `dataclasses` 定义成结构化的记录，而不是一段文本。`Event` 里同时有决策字段（`decision`、`tool_args`）、用量字段（`token_in`、`token_out`、`cost_unit`）和 `raw_digest`，一眼能看出「每一步都补齐了三类信息」。`Trace` 的 `total_cost`、`used_tools` 两个方法演示了字段齐备之后，回答「花了多少」「走了哪些工具」只是几行聚合。
5. `build_trace` 构造一条四步的示例轨迹，配置版本写成 `pv3/m1/td2` 这样的组合串，对应「提示词 / 模型 / 工具定义」各自的版本——这正是开头那个问题所要求的。用户输入原文只被送进 `fingerprint`，从没被写进任何字段。
6. `covered_fields` 把一条记录实际出现的字段收集成集合，顶层字段直接用键名，事件内部字段加上 `events.` 前缀，好和 `QUESTIONS` 里的写法对上；`missing_questions` 则逐个问题检查依赖是否被覆盖，返回「已经答不上来」的那些问题。这两个函数合起来就是字段清单的验收器。
7. `main` 里先用 `asdict` 把记录转成普通字典、用 `json.dumps` 序列化（JSON，JavaScript Object Notation，一种纯文本的数据表示格式）。`broken` 故意抽掉 `config_version`，用来验证「少一个字段就有一个问题答不上来」这条性质真的成立，而不是只写在嘴上。
8. `checks` 里的十二条断言分成四组：清单本身不重不漏且有归属；字段缺失可被检测；原文与联系号确实没落盘、只留了定长指纹；以及拿着这条 Trace 真能算出成本、还原工具序列、读齐终态，并且序列化往返不丢字段。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用固定的示例轨迹代替真实任务、用本地字典代替持久化存储、用定长指纹代替原文的受控存放，全是为了让「问题反推字段、缺口可检测」这条链路不需要联网、账号或第三方包就能独立跑通并手工核对。它演示的是字段清单的设计与验收顺序，不是任何具体日志平台的实现。

## 七、踩坑与边界

- **只记成功失败**：现象是成功率一波动就无从下手，只知道「坏了」 → 原因是把 Trace 当成了计数器、没记过程字段 → 补上事件序列与决策依据两组字段，让每一步都带步号、动作、参数与依据，参考 [结果评测与轨迹评测](./k089-trajectory-eval.md)。
- **原文全量落盘**：现象是日志体积暴涨、里面混着联系号和地址、谁都不敢打开排查 → 原因是把「好查」误解成「留全文」 → 原文不进 Trace，改留定长指纹与稳定标识，敏感内容按 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md) 处理，超长返回只留引用。
- **没有关联编号**：现象是并发时几条任务的记录交错混在一起，拼出来的「轨迹」其实属于好几个任务 → 原因是每条日志各自打印、没带同一次任务的唯一编号 → 接下任务时就生成编号并贯穿每一步，跨进程传递与父子关系见 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md) 和 [传输与会话](./k080-transport-session.md)。
- **字段随手加、名字随版本变**：现象是上个月的记录读不出来，同一个含义在不同版本叫三个名字 → 原因是字段清单没有固定下来、也没跟着配置一起版本化 → 把清单当契约维护，配置组合的记法对齐 [提示与策略版本化](./k113-prompt-versioning.md)。
- **事后从文本里正则抠字段**：现象是想统计「哪版模型出问题多」，结果一半记录抠不出模型名 → 原因是关键信息当初只写进了自由文本 → 在事件产生当场就以固定名字和类型结构化写下来，格式与回放见 [结构化日志与轨迹回放](./k095-structured-log.md)。

还要划清一条边界：字段清单解决的是「一条 Trace 内部记什么」，它不负责「一次请求的原始结构长什么样」（那是 [请求结构](./k008-request-anatomy.md) 的事），也不负责「循环该在什么条件下停」（那是 [循环状态](./k027-loop-state.md) 的事）。而「终态与护栏」里那个脱敏标记，是给读日志的人看的信号，不是权限控制本身；真正的拦截要落在 [代码内护栏](./k106-guardrail-in-code.md) 上，别把「记了一笔」误当成「挡住了一次」。字段齐了以后，下一步才是把它们按固定格式写成事件、按序拼回来，也就是 [结构化日志与轨迹回放](./k095-structured-log.md) 的内容。

- [ ] 能说清「日志行」和「一条 Trace」的区别，以及为什么单行日志回答不了「为什么」
- [ ] 能用「问题到字段」的映射推出五组字段，并说出每组挂在哪一个复盘问题上
- [ ] 能解释为什么原文全量落盘既贵又不敢看，指纹与稳定标识各自解决什么

## 九、三句话小结

Trace 该记什么，指的是用复盘问题反推出一份字段清单：身份与版本、事件序列、决策依据、用量与成本、终态与护栏，每个字段都要挂到一个具体问题上。

关键做法是先在事件产生当场结构化地写下固定字段，让原文只以定长指纹和稳定标识留痕，并用「少一个字段就有一个问题答不上来」来验收清单是否齐备。

当任务只是离线的一次性脚本、既不需要归因也不涉及敏感输入时，不必硬套这套清单；但只要一次结果可能被追问「为什么」，缺了对应字段的 Trace 就等于没记。

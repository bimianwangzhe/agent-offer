# LLM-as-Judge 与评分标准固化

## 一、场景提问

你要给一个会写答复的 Agent 做评测，任务是「根据一段材料回答用户问题」。麻烦在于这类开放题没有唯一标准答案：有人答得简洁，有人答得周全，你说不清哪个该给高分。请人逐条看，一百条要看一上午，改一版提示就得重看一遍，成本高到根本跟不上迭代。于是有人提议：让大语言模型（Large Language Model，LLM，一种按概率逐字生成文本的模型）来当裁判，把「候选答复」喂给它，让它直接打分。你照做了，结果第一次打 4 分、第二次打 3 分，换个说法又变 5 分；把两个答复的顺序对调，赢家居然跟着换。分数飘成这样，谁还敢拿它判断「新版到底比旧版好还是差」？

## 二、破误解

**不是模型打分不够聪明，而是你把「好不好」这种模糊感觉原样丢给了裁判；没被拆开、锚定、固定下来的评分标准，谁来打都会飘。**

先说清这个做法叫什么。LLM-as-Judge，就是让一个语言模型充当裁判，去给另一个模型（或同一个 Agent 的不同版本）的输出做评价。它之所以有用，是因为开放任务里「对不对」不好判，但「两份答复哪份更符合要求」相对好判，模型恰好擅长这种带语义的比较。可很多人把它用成了「把答复丢进去，请给 1 到 5 分」，这一步就埋下了所有问题：分档没有定义，4 分和 3 分的界限全凭裁判当场的感觉；维度没有拆开，覆盖全不全、有没有编造、格式对不对被揉成一个数字；输入顺序没约束，先出现的那份容易被偏爱；同一份量规今天写「请严格打分」、明天写「请宽松些」，两批分数根本没法比。真正要补的不是换个更强的裁判，而是把评分标准固化下来——固化（把标准写成一份明确的、带版本、可复用的说明）是这个知识点的题眼。所谓评分量规（rubric，把「好不好」拆成若干可判定的维度，每条写清什么算通过、各占多少权重、每个分档配一个标准样例），就是把主观感觉翻译成可执行的判定规则。一旦标准成了这样一份数据，裁判就只是「按规则读输入」的执行者，换谁打分、什么时候打，结论都应该一致；不一致，恰恰说明标准没写够或裁判有偏，值得查。这里还有个容易被忽略的前提：固化之后，裁判本身也要被校验——用一批已知该得几分的锚点样例去对，用人工标注的金标准去对齐，用「把两份答复对调位置结论是否翻转」去查偏心。评分标准固化，固化的既是「怎么算好」，也是「怎么确认打分这件事本身可信」。

## 三、生活类比

把它想成体操比赛的打分。裁判不会被告知「凭感觉给个分」，而是拿着一本厚厚的规则：一套动作拆成难度分、完成分、落地稳定性等若干项，每项写清加分和扣分的条件，比如「落地后退一步扣 0.1」「动作中断扣 0.5」；每个分档还有标准示范录像，让裁判知道「这样的完成度对应 8.5 分左右」。比赛前，裁判要拿几套录像试打，和专家组定的分对齐了才上场——这叫校准。正式打分时还要防偏心：中间分去掉、多个裁判独立给分再汇总，避免某一个人的偏好左右结果。

对应关系要逐条对上才有用。那本规则书，就是评分量规：把「好不好」拆成维度、定权重、写判定条件。分档的示范录像，就是锚点样例（anchor，已知应得满分的、应得零分的、应得中间分的几份标准答卷），用来钉住「4 分到底长什么样」。赛前试打对齐专家组，就是拿人工金标准（gold，由人判定、被当作参照答案的一批标注）算一致率，裁判和人分歧太大就得回炉。多个裁判独立给分、去掉极端值，对应「别只信一次打分，多跑几轮看波动」，也对应把同一个裁判里偷偷偏向某位置的毛病查出来——体操里叫防偏心，这里叫位置偏置（position bias，裁判因为一份答复排在前面就倾向判它赢）。最要命的一处细节：规则书是会改版的。今年把「落地」权重调高了，去年的 8.5 分和今年的 8.5 分就不是一回事；如果不给规则书编号、改版后不重新校准，跨版本比较分数就是在拿两把不同的尺子量东西。这正对应评分标准要带版本、一改就得重定基线——放到系统里，是 [回归门禁与基线](./k091-regression-gate.md) 要管的事。

## 四、自绘示意图

:::figure 一份评分量规该写清什么
@stack
维度与权重::把好不好拆成几条可判定的项
判定规则::每条写清什么算通过、什么算不通过
分档锚点::每个分数段配一份标准样例
位置处理::两份答复对调后结论须翻转
版本指纹::量规一改就重定基线
:::

五行里最容易漏的是「分档锚点」和「位置处理」。没有锚点，「4 分」只是一个谁都能往里塞解释的词；没有位置处理，裁判可能只是在奖励「先被看到的那份」，而你把这种偏心当成了质量差异。版本指纹听着最不起眼，却是跨批次可比的前提：把整份量规序列化后算一个短摘要，摘要没变才说明两次打分用的是同一把尺子。

:::figure 两种打分方式的差别
@compare
绝对打分::单条输入直接出分|跨批次可比|尺度易随措辞漂移
两两比较::一对输入比出胜负|更贴近人的偏好|须防位置偏置
:::

左边是「给这一份打几分」，好处是分数能攒起来跨批次看趋势，坏处是尺度很容易飘——同一份答复，提示里多一句「请严格些」就可能少一分。右边是「这两份哪个好」，判断更稳、更接近人实际做的比较，却多出一个必须处理的毛病：裁判可能偏爱排在前面的那份，所以正着比一次、倒着比一次、结论能翻转才算数。两种方式没有谁替代谁，常见做法是两两比较定胜负、绝对打分看长期趋势，各管一头。

:::figure 裁判投入使用前的一圈校准
@cycle
抽锚点样例|人工定标|跑裁判比对|查位置偏置|固化量规版本
:::

这一圈是个闭环，不是一条走完就结束的清单。跑裁判比对发现分歧，得回头补判定规则；查位置偏置发现结论不翻转，得改输入组织方式或换更稳的比较口径；量规一旦被改动，指纹随之改变，又要重新走一遍人工定标。把「校准」做成可重复的循环，评分才不会随着迭代悄悄失真，这一点和 [评测用例集怎么构造](./k086-eval-dataset.md) 里「用例要配期望、要能重跑」是同一套纪律。

## 五、层层追问

:::ask 那如果裁判和被测用的是同一个模型，分数还可信吗？
:::

可信度要打折，而且折扣来自一个很具体的毛病：自我偏好。模型容易给「读起来像自己会写的那种说法」更高分，于是被测方只要模仿裁判的语气、把答案写得更长更铺陈，就可能白捡分，哪怕内容没更对。这跟「同源必然全错」不一样——同源的真正问题是评价失去独立性，裁判和被评价者共享同一套偏好，偏差会朝一个方向系统性叠加，你看不出来。改法有几层：最省事的是让裁判和被测分开，用不同来源或不同配置的模型；做不到时，就把评价尽量从「整体印象」拉回「逐项核对」，因为「是否覆盖了这三个要点」「是否出现了材料里没有的数字」这类判定比「哪个更好」更不容易被文风带走，逐维度判定的思路和 [性质断言](./k088-property-assertion.md) 一脉相承；再用锚点样例和人工金标准定期对齐，一旦一致率下滑就说明自我偏好或措辞漂移混进来了。还有一句要记牢：无论同不同源，裁判给的分数都只是「按这份量规得到的一个近似判断」，不是事实本身。把它当绝对真值去卡改动，比不用裁判更危险。

:::ask 那如果量规本身写错了，或者过一阵子大家对「好」的标准变了呢？
:::

这问到了根上：量规不是天然正确的，它是一份人为约定，会被写错，也会过时。写错的典型样子是「维度和真正想要的目标不对齐」——比如真正在意的是「有没有编造」，量规却把大部分权重压在「格式是否整齐」，于是一个格式漂亮但内容造假的答复稳拿高分。这种错不会表现为「分数飘」，反而表现得非常稳定、非常自洽，只靠看分数永远发现不了，只能靠拿一批人工判过的样例去对：一致率低，先怀疑量规定错了，而不是急着调裁判。怎么防？把量规当作和提示、代码一样要评审、要版本化的产物，每次改动留痕、说明改了哪条为什么改，这与 [提示与策略版本化](./k113-prompt-versioning.md) 是同一种管理动作；改动之后，所有历史分数都要按新尺子重算，旧基线作废，否则「新版比旧版涨了 0.3 分」可能只是换了把尺。至于「标准变了」，那不是 bug，而是需求变化：这时该做的是显式地发布一版新量规、重新定标、重新跑基线，并如实承认新旧分数不可直接比较。把这两件事分开——量规写错要修、标准变了要换版——才不会把「我们对好的定义在变」误记成「模型突然变好了」。评测目标究竟是结果还是过程、该由哪些维度构成，可以回到 [三层评测](./k085-three-level-eval.md) 和 [结果评测与轨迹评测](./k089-trajectory-eval.md) 去看整体框架。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，把评分量规写成一份带版本的数据，用一个确定性的本地桩函数代替真实裁判（不联网、不调模型、不需要账号），演示「逐维度打分、锚点样例、两两比较、位置偏置自检、与人工金标准对齐、量规版本指纹」，结尾用一组断言逐条验证。复制到任意装有 Python 的机器上直接运行即可。

```python
import hashlib
import json


RUBRIC = {
    "version": "r1",
    "dimensions": [
        {"name": "覆盖要点", "weight": 3, "check": "covers"},
        {"name": "无编造", "weight": 3, "check": "no_fabrication"},
        {"name": "格式合规", "weight": 1, "check": "valid_format"},
    ],
}


def rubric_fingerprint(rubric):
    blob = json.dumps(rubric, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(blob.encode("utf-8")).hexdigest()[:12]


def max_score(rubric):
    return sum(d["weight"] for d in rubric["dimensions"])


def grade(answer, rubric):
    total = 0
    detail = {}
    for dim in rubric["dimensions"]:
        check = dim["check"]
        if check == "covers":
            passed = set(answer["key_points"]).issubset(set(answer["covered"]))
        elif check == "no_fabrication":
            passed = not answer["fabricated"]
        elif check == "valid_format":
            passed = answer["format_ok"]
        else:
            raise ValueError("未知判定规则: " + check)
        gained = dim["weight"] if passed else 0
        detail[dim["name"]] = gained
        total += gained
    return total, detail


def fair_pairwise(a, b, rubric):
    sa, _ = grade(a, rubric)
    sb, _ = grade(b, rubric)
    if sa > sb:
        return "A"
    if sb > sa:
        return "B"
    return "TIE"


def biased_pairwise(a, b, rubric):
    """演示用：偷偷给排在前面的 A 加一分，模拟位置偏置。"""
    sa, _ = grade(a, rubric)
    sb, _ = grade(b, rubric)
    sa += 1
    if sa > sb:
        return "A"
    if sb > sa:
        return "B"
    return "TIE"


def symmetry_holds(pair_fn, a, b, rubric):
    """两份对调后结论应翻转；不翻转说明裁判偏心某个位置。"""
    flip = {"A": "B", "B": "A", "TIE": "TIE"}
    return flip[pair_fn(a, b, rubric)] == pair_fn(b, a, rubric)


def agreement(judged, gold):
    if len(judged) != len(gold) or not judged:
        raise ValueError("标注数量不一致或为空")
    hit = sum(1 for j, g in zip(judged, gold) if j == g)
    return hit / len(judged)


def main():
    good = {"key_points": ["甲", "乙"], "covered": ["甲", "乙", "丙"],
            "fabricated": False, "format_ok": True}
    variant = {"key_points": ["丙"], "covered": ["丙"],
               "fabricated": False, "format_ok": True}
    bad = {"key_points": ["甲", "乙"], "covered": ["甲"],
           "fabricated": True, "format_ok": False}

    full = max_score(RUBRIC)
    s_good, d_good = grade(good, RUBRIC)
    s_bad, d_bad = grade(bad, RUBRIC)
    s_var, _ = grade(variant, RUBRIC)

    checks = [
        ("满分锚点样例得满分", s_good == full),
        ("低质锚点样例得零分", s_bad == 0),
        ("好样例严格优于差样例", s_good > s_bad),
        ("逐维度明细可解释", all(v > 0 for v in d_good.values()) and d_bad["无编造"] == 0),
        ("两两比较选出好样例", fair_pairwise(good, bad, RUBRIC) == "A"),
        ("同分两样例判平局", s_good == s_var and fair_pairwise(good, variant, RUBRIC) == "TIE"),
        ("公正裁判通过对称性校验", symmetry_holds(fair_pairwise, good, variant, RUBRIC)),
        ("带位置偏置的裁判被校验抓出", not symmetry_holds(biased_pairwise, good, variant, RUBRIC)),
        ("量规指纹可复现", rubric_fingerprint(RUBRIC) == rubric_fingerprint(RUBRIC)),
    ]

    edited = json.loads(json.dumps(RUBRIC, ensure_ascii=False))
    edited["dimensions"][0]["weight"] = 4
    checks.append(("改动量规后指纹变化提示需重定基线",
                   rubric_fingerprint(edited) != rubric_fingerprint(RUBRIC)))

    samples = [good, variant, bad, good]
    gold = [1, 1, 0, 1]
    judged = [1 if grade(s, RUBRIC)[0] == full else 0 for s in samples]
    checks.append(("与人工金标准完全一致", agreement(judged, gold) == 1.0))
    wrong = list(judged)
    wrong[2] = 1
    checks.append(("裁判判错时一致率下降", agreement(wrong, gold) < 1.0))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `RUBRIC` 把评分标准写成一份纯数据：一个版本号、三条维度，每条带名字、权重和判定规则标识。标准不再是提示里一段会随手改动的自然语言，而是一份能算指纹、能版本化、能被测的东西——这是「固化」最实在的一步。
2. `rubric_fingerprint` 用 `json.dumps(..., sort_keys=True)` 把量规稳定序列化，再用标准库的 `hashlib.sha256` 求摘要取前十二位（JSON 是 JavaScript Object Notation，一种纯文本数据表示格式；SHA-256 是一种把任意内容映射成定长摘要的算法，内容一变摘要就变）。它让「两次打分是否用了同一把尺子」变成可判定的。
3. `grade` 是本地确定性桩函数，代替真实裁判：按量规逐条维度判定，通过就记该维度权重、否则记零，最后返回总分和逐维度明细。它刻意不用任何随机性、不调用模型，好让「同输入必同分」稳定成立；真实裁判换成一次模型调用，外层这套校验逻辑不用改。返回 `detail` 是为了让分数可解释——差的样例到底差在哪一项，一眼能看出来。
4. `fair_pairwise` 实现两两比较，只按分数高低给 A 胜、B 胜或平局；`biased_pairwise` 是故意写坏的对照，给排在前面的 A 偷加一分，用来模拟位置偏置。把「好实现」和「坏实现」并排放，是为了让后面的自检看得见它确实能抓到问题，而不是空口说「要防偏置」。
5. `symmetry_holds` 是位置偏置的核心自检：把两份输入正着比一次、倒着比一次，结论必须翻转（A 变 B、B 变 A、平局仍平局）。公正裁判在同分时两次都是平局，通过；带偏置的裁判两次都判 A 赢、不翻转，被判失败。`flip` 字典就是把「该翻转成什么」写明的对应表。
6. `agreement` 算裁判与人工金标准的一致率：逐条比对、数命中数、除以总数，并在数量不一致或为空时直接报错，避免用空集合算出误导性的满分。
7. `main` 先构造三份本地样例（一份该得满分、一份同分但内容不同、一份该得零分），锚点样例在这里落地；断言依次验证满分与零分锚点、好坏可分、逐维度明细可解释、比较选出好样例、同分判平局、对称性校验能放行公正裁判且抓出带偏置裁判、量规指纹可复现；随后深拷贝一份量规改权重，断言指纹变化会提示「需重定基线」；最后用四条样例和人工标注算一致率，并故意改错一条，断言一致率确实下降。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：`grade` 是确定性桩函数，三份样例和四条标注都是本地构造的数据，用来演示评分标准如何被固化与校验，不是任何真实模型的打分，也不代表任何具体评测平台的实现。整段只依赖标准库、可独立运行。

## 七、踩坑与边界

- **只打一个笼统总分**：现象是分数忽高忽低、说不清差在哪 → 原因是把覆盖、编造、格式揉进一个数字、分档又没定义 → 拆成有判定规则和权重的维度，像代码里 `detail` 那样让每项可解释。
- **两份答复对调后赢家不翻转**：现象是同一对答复换个顺序结论就变 → 原因是裁判偏爱先出现或更长的那份 → 正倒各比一次要求结论翻转，用 `symmetry_holds` 这类自检定期查。
- **裁判和被测同源却当成独立评判**：现象是答案越写越长、越来越像裁判口吻，分就涨，内容并没更对 → 原因是评价失去独立性、自我偏好单向叠加 → 尽量分开来源，把判断拉回逐项核对，并用锚点与金标准盯住一致率。
- **量规改了却不重新定基线**：现象是「新版涨了 0.3 分」，其实是换了把尺 → 原因是量规没有版本、历史分数没按新尺重算 → 给量规算指纹、改动留痕、旧基线作废后重跑，见 [回归门禁与基线](./k091-regression-gate.md)。
- **把裁判分当绝对真值去卡改动**：现象是量规定错了维度，分数却稳定自洽，一路放行错误改动 → 原因是没人拿人工判过的样例去对 → 定期用金标准算一致率，一致率下滑先怀疑量规，再看裁判。

还要分清两条边界：裁判擅长的是「带语义的相对比较」，碰上「答案里有没有出现材料之外的数字」这种能直接判真假的事，用确定性的校验更稳，别什么都交给模型打分，这与 [语义层校验](./k018-semantic-check.md) 和 [性质断言](./k088-property-assertion.md) 分工一致；而「该用哪些维度、评测的是结果还是过程」属于评测设计，得先在 [三层评测](./k085-three-level-eval.md) 里定清楚，再谈谁来打分。评分标准固化还有个天然限度：它固化的是「当前我们认为什么叫好」，标准本身随需求变化，所以量规必须能版本化、能被推翻重定，而不是刻在石头上。用例集里正常、边界、异常各占多少、锚点样例怎么挑，可对照 [正常 / 边界 / 注入 / 回归配比](./k087-case-mix.md)。

## 九、三句话小结

LLM-as-Judge 与评分标准固化，是让语言模型按一份写死的量规去评价输出，并用锚点、金标准、位置对称性把「打分这件事本身」校验到可信的一整套做法。

关键做法是把「好不好」拆成带判定规则和权重的维度、给量规算版本指纹、正倒各比一次查偏心、拿人工标注算一致率，改动即重定基线。

当评测目标能用确定规则直接判真假时，不必请模型裁判；但只要任务开放到没有唯一答案、又需要跨版本反复比较，一套固化且可校准的评分标准就省不掉。

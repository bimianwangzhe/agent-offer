# 切分元数据与父块回溯：让每个片段自带出处

## 答对了数字，却答不出它归谁管

助手答「一线城市每晚 600 元」答得很准，用户接着问「这是哪一版制度、我能不能照着报」，它却支吾不出来：片段被切下来时只剩一句光秃秃的文本，来源是哪个文件、第几页、哪个版本、对谁可见，全都丢了。更麻烦的是，同一句数字在旧版制度里也出现过，用户其实想问的是「超标部分到底报不报」，而那句限定条件在被命中的那个小块里根本没有。

## 先破一个误解

**不是片段不够多，是把片段当成了一截纯文本，忘了它还得带着「我是谁、从哪来、归谁管」。**

先把词说清楚。元数据（metadata）指描述数据的数据，放在这里就是跟着每个块一起存的那组字段：来源文件名、文档编号、页码或位置、版本号、生效时间、可见范围、标题路径、父块编号。父块回溯指命中一个子块之后，顺着它身上的父块编号，把所属的更大块（完整小节或整章）取出来送进生成，让答案带得齐前后限定条件。这两件事常常一起出现，因为「小块命中、大块作答」本来就要靠编号这根线，而编号本身就是元数据的一员。

为什么非得让元数据跟着块走，而不是查到之后再回数据库补？因为检索链路里块会被反复搬运：进索引、被召回、被重排、被拼进上下文、被引用。任何一步只带文本、不带字段，出处就断了，后面再想补回来要么查不到、要么对不上。至少五件事全押在这组字段上：溯源时答案要指回具体文件与页码；过滤时要按可见范围、生效时间决定这块能不能给当前用户看；调试时要按文档编号定位是哪份材料出了问题；审计时要查「当时用的是哪个版本」；文档下架时要按编号同步清理派生数据。缺了血缘关系，这几件都做不了。

还有一层容易被忽略的：限定条件往往不在被命中的那个小块里。「一线城市每晚 600 元」和「超标部分一律不予报销」常常分属两个句子，甚至两个块；只把命中的小块递给模型，答案就丢了「超标不报」这个边界。父块回溯解决的就是这个：匹配用精准的小块，作答时把父块整段补上。切分怎么分出父子两层，见[语义切分与层级切分](./k055-semantic-chunking.md)；过滤为什么要趁早做，见[元数据过滤前置](./k060-metadata-filter.md)。整套顺序可以从[从这里开始](./00-start-here.md)看起。

## 用病历与检查单来理解

把每个片段想成一张从大病历里抽出来的检查单。

如果这张单子上只写了一行结论「指标 600」，医生拿到手根本没法用：谁的、哪天测的、哪个科室开的、参考范围是什么、有没有备注「超标需复核」，全不知道。真正能用的检查单一定带着表头——患者编号、日期、开单科室、版本号、以及一句「详见完整病历第几页」。这些表头不改变那行结论，却决定了这行结论能不能被采信、能不能据此下判断。

对应关系：患者编号与日期是文档编号与生效时间，开单科室是可见范围，「详见第几页」是父块编号，完整病历是父块，那行结论是子块文本。这个比喻还解释了两件事。第一，出处必须是跟着单子走的，不能指望医生事后跑去档案室翻——检索链路里块被搬来搬去，字段一丢就对不上。第二，单看一行结论常常不够：备注、参考范围、例外条件都在完整病历里，所以看到异常值要顺着「详见第几页」翻回整份病历，这正是父块回溯。

:::quote
片段不是一截文本，是一张带表头的单据：来源、版本、可见范围和「详见父块第几页」都得跟着它走。
:::

## 把元数据与回溯画出来

先看一个块从被切出来到最终带着出处进答案，经过哪些动作。

:::figure 从切块到带出处作答
@flow
切出小块|写入元数据|命中子块|按编号回溯父块|带出处作答
:::

第二步「写入元数据」必须紧跟切分：字段在块诞生时就写进去，之后每一步只许带着走，不许凭空补。

每个块该带哪些字段，可以列成一张清单：

:::figure 一个块该自带的字段
@stack
来源::文件名与文档编号，答案据此指回原件
位置::页码、标题路径，脱离原文也能判断适用范围
版本::版本号与生效时间，用于裁决新旧与时效
权限::可见范围与租户，过滤与审计的唯一依据
血缘::父块编号，命中后回填完整上下文的那根线
:::

第四行要特别当心：可见范围属于「不该等到检索完再看」的字段，它必须在打分之前就参与筛选，否则无权内容已经进了候选甚至进了上下文。

再看两种存法的差别：

:::figure 只存纯文本，与带元数据与父块
@compare
只存纯文本::说不出出处|无法按权限时效筛|缺限定条件
带字段与父块::答案指得回原件|过滤有依据|命中后可补全上下文
:::

第二行三格分别对应溯源、过滤、作答三件事，而它们靠的是同一组字段。少存几个字段，看着省事，其实是同时砍掉了三项能力。

:::tip 一条立刻见效的规则
把「片段编号、来源、页码、版本、可见范围、父块编号」做成切分器输出的固定结构，任何一步都只许传递这个结构、不许降级成裸字符串。一旦某个环节把块转成纯文本，出处就找不回来了。
:::

## 再往深问两层

:::ask 那如果一份材料根本没有版本号、也不分权限，是不是可以少存几个字段？
:::

可以少，但别把结构省掉。字段是「按需填」，结构是「必须有」：来源、位置、父块编号这三项几乎总要用——来源用于溯源，位置用于展示「查看原文」，父块编号用于补全上下文。版本和可见范围在单一版本、全员可读的小库里确实可以先留空，但位置要留着，因为材料迟早会改、迟早会分部门；等真需要时再回头给几万个块补字段，比一开始就多存两个空值麻烦得多。另外「留空」和「乱填」是两回事：留空要能被程序识别成「未知」，过滤时按最保守处理，别让一个空值被当成「对所有人都可见」。判断该不该按某个字段过滤，逻辑见[元数据过滤前置](./k060-metadata-filter.md)。

:::ask 再深一层：父块回溯是不是把所有命中块的父块都塞进上下文，越全越好？
:::

不是，回填也要有节制，而且要去重。多个子块可能同属一个父块，命中三条就把同一个父块拼三遍，既浪费长度又制造重复引用，正确做法是按父块编号去重后各回填一次。更要紧的是别把「补全」变成「灌满」：回溯的目的是补上被切掉的限定条件与前后文，不是把整章原文原样贴进来；贴进来的无关段落同样会稀释当前问题的权重。一个稳妥的次序是：先按命中子块收集父块编号、去重，再按相关度或原文顺序排好，最后受上下文预算约束取前几个，见[上下文预算表](./k041-context-budget.md)。还有个容易漏的点：父块回溯解决的是「上下文不够全」，解决不了「证据本身找错了」。所以命中之后仍要看一眼子块到底是不是答案所在，别因为回填了一整章，就把一个本来不相干的命中当成了依据；这一步的判断标准属于[溯源、拒答与零召回兜底](./k062-citation-abstain.md)。

## 一份能跑的对照

下面这段只用标准库，用 `dataclass` 定义带字段的块，构造父子两层，演示「命中小块 → 小块缺限定条件 → 按父块编号回溯 → 拿到完整上下文」，并顺带把出处拼成可展示的引用串。

```python
# chunk_meta.py —— 只用标准库，python chunk_meta.py
from dataclasses import dataclass


@dataclass
class Chunk:
    id: str
    text: str
    source: str        # 来源
    page: int          # 位置
    version: str       # 版本
    acl: str           # 可见范围
    parent_id: str = ""  # 血缘：父块编号


PARENTS = {
    "p3": "3.1 住宿标准：一线城市每晚 600 元，其他城市每晚 400 元；超标部分一律不予报销。",
    "p7": "第 7 章 报销：发票需在七个工作日内提交。",
}
CHILDREN = [
    Chunk("c3a", "一线城市每晚 600 元", "差旅制度.pdf", 12, "2024-v3", "全体员工", "p3"),
    Chunk("c3b", "其他城市每晚 400 元", "差旅制度.pdf", 12, "2024-v3", "全体员工", "p3"),
    Chunk("c3c", "超标部分一律不予报销", "差旅制度.pdf", 12, "2024-v3", "全体员工", "p3"),
    Chunk("c7a", "发票七个工作日内提交", "报销细则.pdf", 3, "2025-v1", "财务组", "p7"),
]


def search(children, term):
    return [c for c in children if term in c.text]


def small_to_big(hits, parents):
    # 命中子块 → 按父块编号去重 → 回填完整上下文
    ordered, seen = [], set()
    for c in hits:
        pid = c.parent_id
        if pid and pid not in seen:
            seen.add(pid)
            ordered.append(pid)
    return [(pid, parents[pid]) for pid in ordered]


if __name__ == '__main__':
    hits = search(CHILDREN, "600")
    assert len(hits) == 1 and hits[0].id == "c3a"
    assert "超标" not in hits[0].text              # 小块本身缺限定条件

    ctx = small_to_big(hits, PARENTS)
    assert len(ctx) == 1 and ctx[0][0] == "p3"
    assert "超标部分一律不予报销" in ctx[0][1]     # 回溯后补全了边界

    c = hits[0]
    assert (c.source, c.page, c.version, c.acl) == (
        "差旅制度.pdf", 12, "2024-v3", "全体员工")
    assert c.parent_id == "p3"
    cite = "[%s 第%d页 %s]" % (c.source, c.page, c.version)
    assert "差旅制度.pdf 第12页" in cite           # 可展示的溯源串
    print("通过 7/7 项：元数据随块走、父块按编号回填、引用可拼接")
```

1. `Chunk` 用 `dataclass` 把字段固定下来：`source`、`page`、`version`、`acl` 是描述信息，`parent_id` 是血缘线。写成结构而不是散落的字典键，是为了让任何一步都拿得到同一组字段。
2. `PARENTS` 与 `CHILDREN` 是本地构造的两层块。注意 `c3a` 里只有那句数字，「超标不予报销」在父块 `p3` 里——这是刻意造出的「小块缺限定条件」场景。
3. `search` 是最朴素的命中：按词面找子块。`small_to_big` 是回溯主体：收集命中块的 `parent_id`、用 `seen` 去重，再按编号从 `PARENTS` 取回整段。去重这一步不能省，多个子块同属一个父块时，不去重就会把整段拼好几遍。
4. 中间那组断言验证了整套链路：命中的确实是 `c3a`，它自身不含「超标」，回填后父块把这句边界补上了。
5. 最后三行验证字段齐全、血缘正确，并用字段拼出一个形如「[差旅制度.pdf 第12页 2024-v3]」的引用串——答案能给用户看的「查看原文」，靠的就是这几项。七条断言跑完打印通过项数。

想看得更清楚，可以把 `search` 的关键词换成「每晚」，会一次命中多个子块，而 `small_to_big` 仍只回填一个父块，正好演出去重的作用；或者把某个子块的 `parent_id` 清空，会看到它虽被命中却补不回上下文。真实系统里 `PARENTS` 会落在外部存储里按编号取，但「命中子块、按编号去重、回填父块」这三步不变。

## 踩过的坑

- **块降级成裸字符串**：现象是答案说不出出处、审计查不到版本 → 原因是链路中某一步只传了 `text`，字段全丢 → 怎么改：全链路只传带字段的结构，禁止降级。
- **父块回填不去重**：现象是同一段限定条件在上下文里出现三四遍 → 原因是多个命中子块同属一个父块 → 怎么改：按父块编号去重后各回填一次。
- **回溯变成灌满整章**：现象是无关段落挤进来，当前问题反而被淹没 → 原因是把补全当成越多越好 → 怎么改：只补限定条件与前后文，并受上下文预算约束。
- **可见范围留空被当成公开**：现象是无权内容被召回 → 原因是空值在过滤时被当作「不限制」 → 怎么改：把「未知」显式编码，过滤时按最保守处理。
- **文档下架只删原文**：现象是已作废的片段仍被召回 → 原因是派生块没有跟着编号清理 → 怎么改：按文档编号同步失效派生块，并保留血缘供审计。

## 三句话

切分元数据与父块回溯，是让每个片段自带来源、位置、版本、可见范围与父块编号，并在命中后按编号补全上下文。
关键做法是把字段做成切分器输出的固定结构全链路传递，回填时按父块编号去重、并受上下文预算约束。
当文档短到一整篇就能整体进上下文、又不需要逐条溯源时，不必拆父子两层，直接整篇给更省事。

# 优雅中断与断点恢复

## 场景提问

你让助手跑一个要十几步的批量任务：先取数、再清洗、再汇总、核对、归档。跑到第三步时容器被调度系统回收了，或者你手动按了停止想改个参数再继续。你重启程序，它却老老实实从第一步重来：已经发过的通知又发了一遍，已经扣过的记录又扣了一次，前面几步白做不说，还多出一堆重复的副作用。你去翻代码，发现「当前跑到第几步」只存在一个内存变量里，程序一停就没了；而那些真正改动过外部世界的动作，根本没有记录自己做过没有。为什么明明只是暂停一下，代价却像是把整件事重新做了一遍，甚至比重新做更糟？

## 破误解

**不是循环写得不稳，是把「进度」只留在了内存里，一停机它就跟着一起消失了。**

很多人遇到中断，第一反应是去加固那个循环：加个更大的超时、把异常抓得更全、给进程配个守护程序别让它死。这些能让中断来得少一些，却挡不住根。真正的分界线在于：进度到底是「程序此刻脑子里记得的东西」，还是「断电也丢不掉、换一个进程也能读到的东西」。只要进度只在内存里，进程重启、容器漂移、机器迁移、你手动停一下，都会把它清零；而一旦清零，程序无从知道「取数和清洗已经做过了」，只能从头再跑。更麻烦的是，重跑并不会把已经发生的副作用撤销——发过的信不会收回来，扣过的款不会自己退回。于是「从头再来」和「重复扣款」成了同一件事。要解开这个结，得把两样东西分开存：一是「哪几步已经做完了」，二是「每步做完时的状态」，并且让程序在恢复时先读这份记录，只接着做剩下的。前者叫检查点（checkpoint，把某一刻的任务状态整体拍下来存好的一份快照），后者叫断点续跑。这里必须顺带说清一个词：副作用（side effect，对外部系统造成的真实改动，比如多了一行记录、少了一笔钱、发出去一封信），它是这套机制真正要防的东西——纯计算重跑一百次都无害，有副作用的动作重跑一次就出事。

## 生活类比

把它想成一支装修队的交接班日志。一个工期好几天的活儿，工序是拆旧、走线、抹灰、刷漆、验收，每天换一班工人。老师傅不会让新来的班子进门就把墙重新砸一遍，他有一本放在工地、谁都拿得到的日志：每道工序后面有个签名和日期，还贴着当天完工的照片和用料记录。新班子上工第一件事是翻日志——「拆旧、走线已经签过字了」，就从抹灰接着干；绝不会把已经埋好的线再刨出来重铺。要是碰上下雨天停工，日志往铁盒里一锁，过几天回来照样接着干。

对应关系很具体：那本放在工地的日志，就是外置的检查点文件；每道工序后的签名，就是「已完成步骤」清单；照片和用料记录，是恢复到那一步时需要的状态；换班和下雨停工，就是进程重启与人为中断；「把埋好的线刨出来重铺」，就是重复已完成的副作用。这里有个容易忽略的细节：日志必须放在工地、不能只记在带班师傅脑子里，因为师傅会换班、会下班——这正对应「状态不能只在内存里」。还有一层：日志本自身也得分版式，早年的本子只有签名栏，后来加了用料栏，新工人翻到旧本子，得先按新格式把缺的栏补上、把旧格式认出来，不然会读错。这就是检查点要带结构版本号、并配一份把旧版本翻译成新版本的迁移逻辑。只记「做过哪几步」而不记「当时状态」，恢复出来的任务会像个失忆的人，知道干到哪了，却不知道干到那一步时的中间结果是什么。

## 自绘示意图

:::figure 一次可中断任务的推进顺序
@flow
读取检查点|跳过已完成|执行剩余步骤|每步完成即落盘|达标或再次中断
:::

这张图里最值钱的是「每步完成即落盘」这一格。不是「全部跑完再统一存一笔」，而是每做完一步就把「已完成清单 + 当前状态」立刻写回文件。因为中断从不挑时候，只有把安全的落脚点铺得足够密，恢复时才不会退回去太远。至于「跳过已完成」，靠的是恢复时先把已完成清单读成一份集合，遍历任务时遇到集合里已有的步骤直接略过。

:::figure 检查点里该装哪些东西
@stack
目标与完成标准::恢复后仍能判断这件事到底算不算做完
已完成步骤清单::去重依据，恢复时据此跳过做过的动作
关键状态快照::中间结果、引用编号、当前游标位置
预算与轮数::已花的钱、已用步数，别让恢复把额度清零
结构版本号::标明这份快照按哪套字段格式写就
:::

五格里最常被漏掉的是「预算与轮数」和「结构版本号」。前者防止一种隐蔽的跑飞：任务失败后自动重新入队，如果每次恢复都把「已用步数」清零，一个本来该停的循环会借着反复重启一直跑下去——重启过的循环还是循环。后者防止发版事故：代码改了字段，一堆在途任务的老快照突然全都读不出来。

:::figure 两种进度存法的差别
@compare
进度只在内存::重启即清零|已完成动作被重做|副作用重复发生
进度落成检查点::重启仍读得到|只做剩余步骤|副作用恰好一次
:::

左边是默认写法，单进程、一路顺跑时看着毫无问题，一遇到中断就露馅；右边是把进度当数据来管的写法。二者在「一路顺风」时几乎没差别，差别全攒在「停下来再起来」的那一刻爆发。

## 层层追问

:::ask 那如果动作刚做完、还没来得及写检查点就崩了呢？
:::

这是最尖锐的一问，也是这套机制的软肋。如果「执行动作」和「写快照」是分开的两步，中间恰好断电，就会留出一个窗口：动作已经生效，快照上却没有它，恢复时查不到，于是再做一次。要收紧这个窗口，一个思路是让「动作」与「它的记录」尽量成为一次不可分割的写入。放到本地文件这个尺度，做法是把新状态先写进临时文件，再用一次原子替换（把临时文件整体改名覆盖正式文件，操作系统保证这次改名要么全成、要么全不成），避免写出写了一半的残破快照。更可靠的做法是让下游自己也认同一个稳定标识，由它在执行那一步就完成去重，两边对同一把钥匙达成共识——这正是 [幂等落盘](./k107-idempotent-persist.md) 里那套幂等键要解决的同一件事：你没收到回执，不代表对方没做。换句话说，检查点负责「别退回去太远」，幂等负责「万一退回去了一步，也不重复」；两者叠起来，才把「恰好一次」这件事守住。还要记住一个前提：恢复之后别闷头就跑高风险动作，先把「当前进度、下一步打算做什么」摆出来让人确认一眼再继续，这一步能在配置错误时救回一整单。

:::ask 那如果恢复时代码已经改了，旧快照的字段对不上新程序呢？
:::

这就是结构版本号要在场的原因。快照里写死一个字段，标明「这份数据是按第几套格式存的」；程序加载时先比对版本，发现是旧版，就走一段专门的迁移逻辑，把缺的字段补上默认值、把改名的键映射到新名字，再交给主流程用。没有这层，一次看似无害的字段改名，会让所有在途任务在恢复的瞬间集体失败。再往深一层：长任务里除了进度，还常常带着会过期的访问凭据，恢复时它可能已经失效，得先刷新或重新授权才能往下走，这条边界在 [凭据过期与刷新](./k111-credential-expiry.md) 里会单独展开。若想看「每步状态与观察都落盘、出事能复现当时经过」的更一般形态，可以对照 [检查点与轨迹回放](./k030-checkpoint-replay.md)；而「做完、超预算、重复、不可恢复错误都要能停」的判定，和 [四个终止条件](./k028-stop-conditions.md) 是同一套思路。这些机制不是彼此独立的开关，而是同一件事的不同侧面：让一个会停、会重启、会被改动的程序，仍然表现得像是没被打断过。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把进度写进一个本地临时状态文件，完整演示「中途优雅中断—重建实例从断点续跑—旧版本快照被迁移」三件事，结尾用一组断言把每条性质都验一遍。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path


class CheckpointStore:
    """把任务进度存进本地状态文件，带结构版本号。"""

    def __init__(self, path, schema_version=2):
        self.path = Path(path)
        self.schema_version = schema_version
        if not self.path.exists():
            self._write({"schema": schema_version, "done": [], "effects": 0})

    def _read(self):
        return json.loads(self.path.read_text(encoding="utf-8"))

    def _write(self, state):
        self.path.write_text(
            json.dumps(state, ensure_ascii=False, sort_keys=True), encoding="utf-8"
        )

    def load(self):
        """读取并按需迁移旧版本状态，返回规整后的状态。"""
        state = self._read()
        if state.get("schema", 1) < self.schema_version:
            state = {
                "schema": self.schema_version,
                "done": list(state.get("done", [])),
                "effects": int(state.get("effects", 0)),
            }
            self._write(state)
        return state

    def commit(self, state):
        self._write(state)


def run_task(store, steps, interrupt_after=None):
    """从检查点续跑：已完成步骤直接跳过，只执行剩下的。"""
    state = store.load()
    done = set(state["done"])
    for step in steps:
        if interrupt_after is not None and len(done) >= interrupt_after:
            return state, False
        if step in done:
            continue
        state["effects"] += 1
        state["done"].append(step)
        store.commit(state)
        done.add(step)
    return state, True


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "checkpoint.json"
        steps = ["取数", "清洗", "汇总", "核对", "归档"]

        store = CheckpointStore(path)
        first, finished = run_task(store, steps, interrupt_after=2)
        checks = [
            ("中途被优雅中断", finished is False),
            ("已完成两步", len(first["done"]) == 2),
            ("已完成的动作只做过两次", first["effects"] == 2),
        ]

        resumed_store = CheckpointStore(path)
        second, completed = run_task(resumed_store, steps)
        checks.append(("断点续跑最终完成", completed is True))
        checks.append(("五步都只做一次", len(second["done"]) == 5))
        checks.append(("副作用总数恰为五", second["effects"] == 5))
        checks.append(("步骤没有重复", len(set(second["done"])) == len(second["done"])))

        store._write({"schema": 1, "done": ["取数", "清洗"]})
        migrated = CheckpointStore(path).load()
        checks.append(("旧版本状态被迁移到当前结构版本", migrated["schema"] == 2))
        checks.append(("迁移补出缺失字段", migrated["effects"] == 0))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `CheckpointStore.__init__` 只在状态文件不存在时写一份初始快照，已有文件绝不覆盖。这一句是「进程重启后还读得到历史」的根：JSON（JavaScript Object Notation，一种纯文本的数据表示格式）在这里充当了那份放在工地上的交接日志。
2. `_read` / `_write` 负责字典与文件之间的来回转换，`sort_keys=True` 让同样的状态每次写出的文本完全一致，便于比对，也避免字段顺序变化造成误判。
3. `load` 是迁移入口：读到 `schema` 比当前版本旧，就按新格式补齐 `done` 与 `effects` 两个字段并写回。它演示的是「代码改了字段、老快照仍能读」这件事，而不是让主流程去猜各种历史格式。
4. `run_task` 的第一步永远是 `store.load()`，再把已完成清单转成集合 `done`。遍历任务时 `if step in done: continue` 直接略过做过的步骤——这就是断点续跑的全部秘密：恢复时不从头，只补没做的。
5. 未跳过的分支里，先 `state["effects"] += 1` 记一次副作用，再把步骤名追加进 `done`，紧接着 `store.commit(state)` 立刻落盘。注意「执行」和「写快照」挨得极近，且每步都存一次，正是图里「每步完成即落盘」那一格。`interrupt_after` 用来模拟人为或调度造成的优雅中断，到量就返回 `False`。
6. `main` 先跑到两步被中断，断言只做过两次副作用；再用同一个文件 `new` 一个新 `CheckpointStore`，模拟进程重启后从断点续跑，断言五步各做一次、副作用总数恰为五、清单里没有重复项。这一组把「落盘相对内存」的价值钉死了。
7. 最后人为写入一份 `schema: 1` 的旧快照，验证 `load` 会把它升级成版本 2 并补出缺失字段。结尾 `assert` 保证只要有一条性质被破坏，程序就以非零状态退出。

## 踩坑与边界

- **进度只放内存变量**：现象是单进程内一路顺跑全过，一重启或容器漂移就从头再来 → 原因是内存状态随进程消亡 → 把「已完成清单 + 关键状态」写进所有实例都读得到的持久化存储，恢复时先读再跑。
- **只存「做到第几步」不存状态**：现象是恢复后知道干到第四步，却丢了第四步产生的中间结果与引用编号，后续步骤基于空白编造 → 原因是快照太薄 → 把恢复后必需的中间结果、游标、引用一并存下，只留逐字稿反而是浪费。
- **把「断点续跑」做成「断点重发」**：现象是恢复时把已经发过的通知、已经提交的写操作又发一遍 → 原因是清单没在动作发生前就写稳，或有副作用的动作没有稳定标识 → 每步完成即落盘，并让有副作用的动作配合 [幂等落盘](./k107-idempotent-persist.md) 的幂等键。
- **快照不带结构版本号**：现象是改了个字段名，一批在途任务恢复时集体报错 → 原因是旧数据与新代码格式不匹配 → 快照写入版本号，加载时走迁移函数补齐或改名，别让主流程兼容所有历史格式。
- **恢复把预算清零**：现象是任务失败后反复自动重新入队，每次恢复「已用步数、已花金额」都归零，一个该停的循环借着重启一直跑 → 原因是预算没算进快照 → 把累计轮数与花费一并持久化，跨重启仍累计，这一点与 [生产失败模式清单与支出硬上限](./k150-failure-modes.md) 里的累计上限是同一条纪律。

还要留意一个尺度问题：上面演示的是单机单文件的最简形态，用它建立直觉足够，但它并不解决「两个进程同时恢复同一份任务」的排他问题，也没覆盖「动作执行与写快照之间那一瞬断电」的严格原子性。真到多实例部署，快照的读写要落到支持原子操作的共享存储，并且最好让下游也认同同一把幂等键，形成两端共识。另外，恢复之后先展示「当前进度和下一步计划」让人确认再继续，而不是自动闷头跑高风险步骤，这一步在长任务里往往比技术机制更能止损。什么时候值得把这套机制做重、什么时候够用，可以结合 [成本优化与发布清单](./k116-cost-checklist.md) 一起权衡——每一分可恢复性都要付出写入与存储成本。若想从整体上看清这套教程的组织方式，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

优雅中断与断点恢复，是把任务进度写成断电也丢不掉的检查点，让程序停下再起来时只接着做剩下部分，而不是从头重来。

关键做法是每完成一步就把「已完成清单、关键状态、累计预算、结构版本号」一起落盘，恢复时先读快照跳过做过的步骤，并给有副作用的动作配上幂等兜底。

当任务全是纯计算、根本没有中断与重放来源时，不必套上这套写入开销；但只要存在会改动外部世界的动作，它就该是默认配置。

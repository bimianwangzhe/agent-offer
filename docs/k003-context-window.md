# 上下文窗口：模型这一眼能看到的全部文字

## 一、聊着聊着，它突然"变笨"了

前十几轮聊得好好的，问什么答什么，还一直记着你开头定下的"只回一句话"。聊到二十来轮，它开始答非所问，把早说好的格式忘了，甚至把前面某个例子当成这次要处理的问题。你没换模型、没改提示、没动代码，只是多聊了几轮。第一反应往往是"它怎么越聊越笨"，可你试着把最早那几轮手动删掉、只留最近几句再问，它又恢复正常了。

删掉几轮就好，说明问题不在模型身上，在"这一轮它到底看到了什么"上。

## 二、先破误解

**不是模型退化了，是"这一眼能看到的全部文字"装不下了，早先那条约束被挤出了视野。**

先把两个词讲白。上下文（context）指的是这一次调用里，模型拿到的那一整段文字；上下文窗口，是这段文字的长度上限，按词元（token，文本被切开后的最小片）来算，不是按字数。每一次调用，模型看到的都是一次性拼好的一整段：常驻的系统规则、之前聊过的历史、刚取回的工具结果、这一轮真正要问的问题，全都首尾相接塞在一起，它不是分几个格子分别读的。

这段话有两个后果，都很实在。第一，总量有上限，超了要么截断（丢掉一部分，通常是靠前的、早期的），要么干脆报错拒绝处理；第二，窗口是"读进去的"和"留给回答的"合起来算的，你给回答留的余量也要从同一份额度里出。于是就出现了开头那一幕：聊得越久，历史占的地方越大，当前问题被挤到一长段文字的末尾，权重被摊薄；而那条"只回一句话"写在最最前面，一旦截断先丢的正是它。模型没变，只是它这一眼看到的纸上，已经没有那行字了。

:::warn 别把"变笨"当成模型状态
多轮之后答得差，先去查这一轮拼进去的总量，而不是急着换模型或重写提示。
:::

## 三、生活类比：一张只能摊开那么大的桌子

你有一张桌子，桌面就那么大。写报告时，得把要用的资料全摊在桌面上，才能同时比对：写着格式要求的便签、前几页草稿、刚查回来的数据、这回要回答的那个问题。桌面摆满之后再想放一张新的，就必须先把最靠边、最早摊开的那张抽走。你没变笨，只是那张写着"只回一句话"的便签被抽走了；眼前摊着的纸上没写这条，你自然不会照着做。还有一处容易漏：桌面不能全铺满资料，得留一块空地用来写答案，那块空地也算在桌面面积里。

对应关系逐条落实：

- 桌面面积，是上下文窗口的额度，按片数算；
- 摊开的每一张纸，是拼进这一段的一块内容；
- 格式便签，是系统规则，最该一直在桌上；
- 前几页草稿，是历史对话，越聊越厚；
- 刚查回的数据，是工具结果，常常块头不小；
- 抽走最靠边那张，是截断，先牺牲早期内容；
- 留出来写答案的空地，是给输出预留的额度，不能拿去铺资料。

这个类比还顺带说明一件反直觉的事：不是"记得越多越好"。桌上每多一张旧纸，就会把当前那张问题纸往边上挤一点，你扫一眼时落在它上的注意力就少一点。所以真正省事的做法不是找张更大的桌子，而是别让没用的旧纸一直占着桌面。想更细地知道每块各占多少片，可以接着看[Token 与分词](./k001-token.md)里那把尺子怎么量。

## 四、画出来：这一眼到底拼了什么

先看一次调用里被拼在一起的几块，它们是首尾相接的一整段，不是分格存放：

:::figure 一次调用里拼在一起的几块
@stack
系统规则::身份与格式要求，每轮都要带上
历史对话::前面聊过的轮次，越积越长
工具结果::刚取回的真实数据，占位不小
当前问题::这一轮真正要处理的事，最该被看见
:::

顺序不是随便排的。系统规则放在最前，是希望它尽量不被挤掉；当前问题放在最后，是希望离"接下来要猜的那个词"最近。中间那两块最会膨胀：历史每轮累加，工具结果可能一大段就回来。所谓"窗口管理"，说白了就是盯住这两块别把额度吃光。

再看装不下时会发生什么，两种处理的差别很大：

:::figure 装不下时的两种处理
@compare
静默截断::早期约束先丢|当前问题还在|你未必察觉
显式报错::调用直接失败|问题立刻暴露|需要自己裁剪
:::

最麻烦的是左边那种：调用成功了、也没报错，只是悄悄丢了最前面几块，于是"只回一句话"这类要求无声失效，你还以为模型在闹脾气。右边那种反而好办，失败得明明白白，逼你回头算账。把这两张图合起来看，结论就一句话：窗口不是"聊到哪算哪"，是每轮都要重新组装、并且要提前算好额度的一份输入。

## 五、顺着追问两层

:::ask 那如果我换一个窗口更大的模型，是不是就不用管这些了？
:::

能缓解，不能不管。额度放大之后，同样的历史确实能多装几轮，但历史仍在累加、每轮拼进去的总量仍在涨，成本也跟着涨，注意力被摊薄这件事并不会因为额度变大就消失。更实际的是，"更大"从来不等于"无限"：只要还有上限，就得有人决定装不下时丢谁。而丢谁这件事，最好由你的代码说了算，而不是交给一句默认行为。再说，按片计费的账单不会因为窗口变大就变便宜，[用量统计与计费口径](./k010-usage-billing.md)里会看到，长输入本身就是持续的成本。所以换模型只是把"什么时候开始挤"往后推，没取消这道题。

:::ask 那如果我每轮把历史压成一句摘要，会不会把关键约束也一起压没了？
:::

会，这是真风险，而且很难靠"读一遍感觉没问题"发现。摘要天然偏向保留"聊了什么"，容易把"只回一句话""不许编造编号""必须给出出处"这类硬约束当成客套话略掉；一旦略掉，后面每一轮都在没有它的前提下继续，谁也不会提醒你。稳妥的拆法是分两层：把不会变的硬约束单独放在每轮都在最前的位置，压不进摘要里；摘要只负责压缩"发生过的事实与已定的决策"。这也正好是[消息角色与对话拼装](./k007-message-roles.md)要处理的分工——哪些内容恒在最前、哪些可以按需带。压完之后还要拿一组"必须保留的事实"逐条核对，确认没丢，而不是凭印象放行。往更远看，压缩本身也有代价和时机问题，但那是别的篇章细讲的事，这里先把"别把硬约束压没"这一条守住就够了。

## 六、跑一段代码，把额度算清

下面这段只用标准库，不联网、不装包、不要账号。它把"按空白切词"当作片数计数，演示装不下时怎么优先保住系统规则与当前问题、从最近的历史往回留。

```python
# 用"按空白切词"当词元计数，纯演示预算怎么算，不代表真实分词。
def ntok(text):
    return len(text.split())


# 系统提示与当前问题恒保留；历史从最近往前留，放不下就丢更早的。
def fit_window(system, history, question, limit):
    fixed = ntok(system) + ntok(question)
    if fixed > limit:
        raise ValueError("常量部分已超预算，必须显式报错而不是静默截断")

    used = fixed
    kept = []
    for h in reversed(history):
        c = ntok(h)
        if used + c <= limit:
            kept.insert(0, h)
            used += c
        else:
            break
    assembled = ["SYS " + system] + ["HIS " + h for h in kept] + ["Q " + question]
    return assembled, used


if __name__ == '__main__':
    checks = 0
    system = "你是 助手 请 简短"          # 4 个词元
    question = "今天 天气 怎么 样"          # 4 个词元
    history = ["第一轮 问 了 什么", "第二轮 答 了 什么", "第三轮 又 问 了 啥"]

    # 1) 预算够时，历史一条不少
    full, used = fit_window(system, history, question, limit=30)
    assert len([x for x in full if x.startswith("HIS ")]) == 3
    checks += 1

    # 2) 预算紧时，总用量始终不超过上限
    LIMIT = 13
    tight, used2 = fit_window(system, history, question, limit=LIMIT)
    assert used2 <= LIMIT
    checks += 1

    # 3) 被裁掉的是早期历史，最近一轮留下
    kept = [x for x in tight if x.startswith("HIS ")]
    assert len(kept) < len(history)
    assert "第三轮" in " ".join(kept)
    assert "第一轮" not in " ".join(kept)
    checks += 1

    # 4) 系统提示与当前问题无论多挤都在，且位置固定
    assert tight[0].startswith("SYS ") and tight[-1].startswith("Q ")
    checks += 1

    # 5) 常量部分本身就超预算时，明确抛错
    try:
        fit_window(system, history, question, limit=5)
        raise AssertionError("应当抛错")
    except ValueError:
        checks += 1

    # 6) 用量随保留的历史条数单调增加
    assert used2 <= used
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `ntok` 用空白切词当片数，是[Token 与分词](./k001-token.md)那把尺子的极简版，只为让预算看得见，不代表真实切法。
2. `fit_window` 开头先算 `fixed`：系统规则和当前问题这两块是每轮必带的，先把它们的片数扣掉。这一步对应"桌面上总得留着便签和问题纸"。
3. 如果连这两块都超过 `limit`，直接 `raise ValueError`。这是有意设计的：常量部分超了就该显式报错，不该靠静默截断蒙过去，正好对应前面第二张图右边那一行。
4. 历史用 `reversed` 从最近一轮往前试，放得下就 `insert(0, h)` 保留并累加 `used`，放不下就 `break`。所以被丢的一定是更早的，最近的优先留下。
5. 最后拼装顺序固定：系统规则在最前、历史居中、当前问题在最后，对应第一张图的四层顺序，也保证硬约束不落在容易被裁的位置。
6. 断言逐条钉住：够用时全留、紧时 `used2 <= LIMIT`、被裁的是"第一轮"而"第三轮"还在、首尾两块位置不变、常量超预算会抛错、用量随保留条数单调增加。

这段代码里最该带走的，不是那几个数字，而是"先算固定开销、再决定丢谁、常量超了就报错"这个顺序。至于这一整段拼好之后怎么送出去、又拆成哪几块，[一次请求拆成五块](./k008-request-anatomy.md)会接着往下讲。

## 七、踩坑与边界

- **把"变笨"当成模型问题**：现象是多轮后忽然不守格式 → 原因是早期约束被挤出这一眼 → 先查本轮拼进去的总量，把硬约束挪到每轮最前。
- **忘了输出也要占额度**：现象是输入刚好卡满，回答总被切一半 → 原因是窗口连"留给回答的部分"一起算 → 算账时先给输出预留一块，再把余下的分给历史。
- **只按字数算窗口**：现象是估着没超、实际却报错 → 原因是额度按词元片数算，字数不是那把尺子 → 用统一分词口径计数，或直接读返回里的用量。
- **静默截断却没留痕**：现象是调用成功但答案悄悄变味，排查无从下手 → 原因是丢了哪几块没有任何记录 → 每次裁剪都记下丢了几块、丢的是哪几轮。
- **把系统规则混进历史里**：现象是压缩或裁剪后规则随之消失 → 原因是它没被当成固定开销单独保护 → 规则恒在最前、单列一栏，不参与历史裁剪。

## 九、三句话小结

上下文窗口是一次调用里模型这一眼能看到的全部文字，按词元计量，读进去的和留给回答的合起来算。
要紧的做法是每轮重新组装这份输入，先扣掉必带的固定开销，装不下时明确决定丢谁并留下记录。
当硬约束绝不能丢、或需要长期保留早期信息时，别指望靠加大窗口蒙过去，改用分层与外置来管。

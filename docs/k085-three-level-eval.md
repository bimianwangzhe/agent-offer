# 三层评测：单步、任务级、系统级各看各的

## 场景：一个通过率，把三种失败全盖住了

你给助手做了一批回归用例，跑完只报一个数：通过率百分之八十几。看着还行，就把这一版放出去了。结果用户反馈分成了三拨，彼此还打架：有人说「每一步我看着都做对了，最后却没办成事」；有人说「事是办成了，可它绕了七八步，还反复查同一张表」；还有人说「单次挺快，一天下来账单和平均等待却涨了一截」。你回头翻那个通过率，三个问题它一个都没告诉你。因为它把所有「对」压成了一个数，而「对」其实至少有三种互不相干的含义。

## 先破一个最常见的误解

**不是模型时好时坏，是把三种不同高度的「好」压成了同一个通过率。** 评测，指用一组事先构造好的输入跑一遍系统，再按写死的标准判定好坏；指标，就是这套判定得出的可比较的数。这件事至少要回答三个不同问题：某一步动作做对没有、整件任务办成没有、整套系统许多趟叠起来划不划算。它们的观测对象、计量单位、能抓到的故障都不一样。把它们搅在一起，等于用一把尺子同时量长度、重量和时间：读数是有了，却不知道哪一项超标。更要紧的是，三层经常不同向——一步没错、整单却失败；整单成功、路径却绕得离谱；单趟都快、合起来的开销却涨了。一个标量数字装不下这种不同向，于是任何一处的退步都会被别处的进步平均掉，你看到的「稳」其实是互相抵消后的假象。

## 用生活里的事打个比方：柜员、办事人、大厅总账

把系统想成一家代办大厅。第一层像「每个柜员这一次操作合不合规」：章盖对没、表格填全没，这是单步层，盯着动作本身；第二层像「这位市民这趟事办成没」：证拿到手没有，这是任务级，盯着一整趟的目标，哪怕中间某个柜员多问了一句，只要证办下来就算成；第三层像「大厅这个月整体运营得怎么样」：平均等候多久、一天耗掉多少人力、有多少人白跑一趟，这是系统级，盯着许多趟叠起来的总账。对应关系要逐条对一遍。柜员次次合规，市民也可能因为缺一份材料白跑，所以第一层全对推不出第二层达标；证拿到了，也可能被来回踢了六个窗口，所以第二层达标推不出路径合理；每一趟都不算慢，架不住这个月单量翻倍、总共耗掉的人力翻着涨，所以单趟快推不出总账好看。体检单上每一项都正常，不等于这个人这一天把要办的事办成了；把事办成了，也不等于这一年没花冤枉钱。三层各管各的，谁也别替谁下结论。

## 画出来看

先看三层是怎么一层层聚合上去的。注意每一层的判定都只吃自己那一层的输入：单步层读逐步动作，任务级读整单结果，系统级读很多单的用量与耗时，谁也不越界去替下层算分。

:::figure 三层评测各自的观测范围
@flow
逐步动作|判定单步|整单结果|判定任务|聚合到系统
:::

这张图里最该留意的是「判定单步」和「判定任务」是两个分开的格子：一个逐条看动作对不对，一个整单看目标达没达成。把它们合成一步，就会丢掉「动作大多对、整单却没成」这类信息。再看只报一个数会损失什么。

:::figure 只报一个数与分三层报的差别
@compare
只报一个通过率::三种失败被平均|定位不到环节|改完不知有没有变好
分三层各报各的::单步看动作|任务级看目标|系统级看总账
:::

左边那行说的是压缩，右边那行说的是保留。两行放一起，不是想说「多算几个数更勤奋」，而是想说这三种数的验收办法根本不同：单步层的验收是「这一步的正确动作占多少」，任务级的验收是「整单目标达成的占多少」，系统级的验收是「成功率、平均耗时、平均用量合起来是否合理」。用错验收办法，就会拿「通过率没掉」去替「路径没绕、开销没涨」辩护。

## 再往下追两层

:::ask 追问一
那如果三层都达标了，是不是就能放心了？
:::

还不能，只能说「在跑的这批用例上」没露馅。三层解决的是「从哪几个高度看」，没解决「拿什么来看」。要是这批用例全是清清爽爽的单轮规范请求，三层再漂亮也证明不了多轮、口语、高负载下的表现，这正是[评测用例集怎么构造](./k086-eval-dataset.md)和[离线好、线上差的成因](./k092-offline-online-gap.md)要处理的事。所以三层是评测的骨架，用例是血肉；骨架对了，血肉不对，照样测偏。

:::ask 追问二
那如果把三层加权合成一个总分，不就既有全局又能定位了吗？
:::

可以额外算一份总分给看板用，但不能只留这一份。一旦加权，某一层的回退就可能被另一层的进步抵掉，这跟开头那个单一通过率是同一个毛病，只是换了个更精致的外壳。稳妥做法是分层各存各的原始数，聚合只作为展示层；而且门禁判定要按分组分别比，不能拿总分糊过去，见[回归门禁与基线](./k091-regression-gate.md)。再往下，任务级里「目标达成」和「路径合理」其实还该拆开看，那是[结果评测与轨迹评测](./k089-trajectory-eval.md)的话题；系统级里「每一趟花多少」和「每办成一件事花多少」也不是一回事，见[核心指标与按成功任务核算成本](./k096-metrics-cost.md)。分层不是为了把报告做长，是为了让每一处退步都有名字、能被点到。

## 一段能直接跑的代码

下面这段不联网、不装任何第三方包、不需要账号，只用标准库。它把四条构造出来的运行记录分别算出单步层、任务级、系统级三个数，结尾用一组断言钉住「三层确实是分开算的、且能区分不同向的情形」。复制成 `.py` 文件直接运行即可。

```python
# -*- coding: utf-8 -*-
"""三层评测：单步、任务级、系统级各算各的指标。"""
from dataclasses import dataclass


@dataclass
class Run:
    run_id: str
    steps: list            # 每一步是否正确
    task_done: bool        # 任务目标是否达成
    latency_ms: int        # 整单耗时
    tokens: int            # 整单用量


def step_level(runs):
    """单步层：所有步骤里正确的占比。"""
    total = sum(len(r.steps) for r in runs)
    ok = sum(sum(1 for s in r.steps if s) for r in runs)
    return ok / total if total else 0.0


def task_level(runs):
    """任务级：整单目标达成的占比。"""
    return sum(1 for r in runs if r.task_done) / len(runs) if runs else 0.0


def system_level(runs):
    """系统级：把成功率、平均耗时、平均用量合起来看。"""
    return {
        "success_rate": task_level(runs),
        "avg_latency_ms": sum(r.latency_ms for r in runs) / len(runs),
        "avg_tokens": sum(r.tokens for r in runs) / len(runs),
    }


def main():
    runs = [
        Run("r1", [True, True, True], True, 900, 1200),
        Run("r2", [True, True, False], False, 3100, 4800),  # 单步高但任务没成
        Run("r3", [True, False], False, 1500, 2100),
        Run("r4", [True, True, True, True], True, 1100, 1600),
    ]
    checks = []
    s, t, sysm = step_level(runs), task_level(runs), system_level(runs)
    checks.append(("三层都算出了数值", 0.0 <= s <= 1.0 and 0.0 <= t <= 1.0))
    checks.append(("单步层与任务级不是同一个数", abs(s - t) > 1e-9))
    checks.append(("r2 单步有对但任务失败被保留", runs[1].steps.count(True) > 0 and not runs[1].task_done))
    checks.append(("系统级含成功率字段", "success_rate" in sysm))
    checks.append(("系统级成功率等于任务级", abs(sysm["success_rate"] - t) < 1e-9))
    checks.append(("系统级含耗时与用量", "avg_latency_ms" in sysm and "avg_tokens" in sysm))
    passed = sum(1 for _, ok in checks if ok)
    print(f"单步层={s:.3f} 任务级={t:.3f} 平均耗时={sysm['avg_latency_ms']:.0f}ms")
    for name, ok in checks:
        print(f"  [{'OK' if ok else 'NG'}] {name}")
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks)


if __name__ == '__main__':
    main()
```

1. `@dataclass class Run`：一条运行记录，带编号、逐步对错列表、整单是否达成、整单耗时与用量。把「逐步」和「整单」放进同一个对象，是为了后面能分别从它取数，不用另造两份数据。
2. `step_level`：把四条记录的所有步骤摊平，数正确的占比，分母是总步数。这是单步层，只看动作对不对，完全不管这一单最后成没成。
3. `task_level`：数整单达成的条数占比，分母是记录条数。这是任务级，一单只贡献一个0或1，跟它走了几步无关。
4. `system_level`：返回一个字典，把成功率、平均耗时、平均用量并列摆出。系统级不是一个数而是一组数，因为它本来就要同时回答几件事。
5. `runs = [...]`：四条手工构造的数据，`r2` 特意设成「三步里对了两步、整单却失败」，`r1` 与 `r4` 是干净成功的，用量与耗时故意有大有小。它们都是可复现的构造场景，不是从哪份真实记录里摘的。
6. `checks` 里的几条断言：钉住「三层都算得出数」「单步层与任务级不是同一个数」「单步有对但整单失败这种情形没被抹掉」「系统级确实带着耗时与用量」。断言写的是性质，换一批构造数据也照样能当回归用。
7. 结尾 `print` 与 `assert passed == len(checks)`：把三个数和通过项打出来，肉眼能确认跑到了结尾；一旦某条性质不成立就直接抛异常，退出码不为零，不会悄悄过关。

## 踩过的坑与边界

- **只留一个总通过率**：现象是版本迭代后数字稳稳的，用户却分成几拨投诉 → 原因是不同高度的失败被平均掉了 → 三层各存原始数，聚合只作展示，门禁按分组比。
- **用任务级成功率冒充单步质量**：现象是工具明明常被调错，报告却显示一切正常 → 原因是整单有时会歪打正着地达成，把中间的错误盖住了 → 单步层单独算工具调用正确率，别让结果分替它背书。
- **系统级只算成功率**：现象是成功率没变，账单和平均等待却悄悄涨了 → 原因是把系统级也压成了一个数 → 把平均耗时、平均用量、每成功任务成本一起并列，见[核心指标与按成功任务核算成本](./k096-metrics-cost.md)。
- **三层用同一批切分口径聚合**：现象是分层数彼此对不上，复盘时互相打架 → 原因是单步按步数、任务按单数、系统按时间窗，分母没对齐也没写清 → 每层标注自己的统计范围与时间窗，别混用分母。
- **把分层当成多写几张表**：现象是报告很长，出了事仍定位不到环节 → 原因是各层只是罗列，没有各自的验收线 → 每层配一条明确的达标线，退化时能点名是哪一层破的线。

边界也要说清：分层评测适合「一次任务要走多步、且要长期运行」的系统。如果只是一个单步、无状态、一次调用就出结果的小工具，硬凑三层只会把简单问题做复杂，那时把单步层的口径定准就够了。

## 三句话小结

三层评测是把「好不好」拆成单步动作、整单目标、跨单总账三个不同高度分别计量。
做法是每层只吃自己那层的输入、各存各的原始数、各配一条达标线，聚合只用于展示。
只需要判一次单步调用对不对、且无多步无长期运行的场景，不必硬凑三层。

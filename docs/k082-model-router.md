# 多模型路由与网关

## 场景提问

你把系统里所有请求都发给了同一个能力最强、也最贵的模型。跑了一阵发现两件别扭事：一句「把这句话归到哪一类」这种轻活，也要排半天队、按大价钱计费；而真遇到需要多步推理的难题，偶尔又赶上这个模型限流超时，用户干等半天只等到一个空转的报错。于是你开始到处加判断，这里写一句「简单问题用小模型」，那里写一句「超时就换一个」，结果三处阈值都不一样，有个分支干脆忘了写兜底，异常直接抛到了界面上。同样是「按情况选模型」，怎么越改越乱？

## 破误解

**不是没挑到「最好的模型」，是把「分流」和「兜底」这两件入口纪律散落到了业务代码里**——该做的是收口到一个网关层，按任务特征查能力注册表选够用的档，再让下游异常时给出确定的结果，而不是把异常抛给用户。

先把词说清。路由（routing，按规则把一次请求分给某个具体处理者的动作）在这里不是网络寻路，而是「这活该交给哪一档能力」。网关（gateway，所有请求进出都先经过的入口层，白话讲像分诊台）是放分流规则的地方，和[传输、会话与网关限流](./k080-transport-session.md)里那个「唯一入口」是同一层。能力注册表（capability registry，一张登记「每档能力擅长什么、单价多少、此刻是否健康」的表）是路由的依据。适配器（adapter，把不同下游参差不齐的返回翻成统一形状的薄层）保证换档不改业务代码。下游（downstream，真正干活、被网关调用的一方）与兜底（fallback，下游不可用时返回的那个预先定好、可预期的结果）是一对：有前者就得有后者。延迟（latency，从发请求到拿到结果的时间）与成本（cost，一次调用按用量折算的开销）是分流时最常权衡的两个量。英文缩写顺带给全称：应用程序接口（Application Programming Interface，简称 API，程序之间调用彼此能力的约定）；本节全程用本地桩函数模拟下游，不碰任何真实接口。

常见的错有两种。一种是「一步到位选个最强模型」，把简单任务也按最贵口径算，钱和等待都白白付了；另一种是「到处加 if 判断」，把分流规则散进每个业务函数，标准必然不一，还会漏掉某个分支的兜底。两者共同的病根，是没意识到「按情况选谁、选不上怎么办」本来就该是一个入口层的统一动作，而不是每个调用点各自临场决定。

## 生活类比

把它想成医院的「分诊台」，而不是让病人自己挨个科室敲门。

病人进来，分诊护士不看病，只按几个可核对的特征分流：只是量个血压、开个常规单子的，去快速门诊，便宜、等待短；症状复杂、需要多科判断的，转去专家门诊，慢一些、费用高，但确实需要那个能力。护士手里有一张牌，写着「今天哪个诊室开着、各自大概排多久」——这就是能力注册表。关键在两处：分流标准由分诊台统一掌握，不交给每个科室自己定；万一专家门诊今天停诊，护士不会让病人站在走廊干等，而是明确给出备用安排（转值班医生，或告知改期），并把这次「没走成专家」记一笔——这就是确定性兜底与切换记账。

对应关系很具体。任务难度对应病情轻重，轻量档与强力档对应快速门诊与专家门诊，成本与延迟对应费用与候诊时间，能力注册表对应那张「诊室状态牌」，网关路由对应分诊动作。这个比喻还点出两个最容易被忽略的细节：其一，分流依据必须是「够用就好」，不是「越贵越好」——给量血压的病人挂专家号，是纯浪费，对应把一句分类请求喂给最强模型；其二，兜底必须是「预先定好、当场可执行」的动作，而不是「到时候再看」，对应代码里那张写死的兜底结构，绝不能是「再抛一次异常」。还有一层：如果护士分错了、把复杂病情当成轻症放去了快速门诊，得有回看机制——快速门诊发现拿不准就往回升级，并把「分诊分错了」记成一条可统计的信号，这正对应路由里的「存疑升档」与「分类错误可观测」。

:::figure 散落判断与收口网关的差别

第一张图是「按什么分」，第二张图是「怎么走」，第三张图是两种组织方式的代价。请留意第二张图里「查表选够用档」排在「调用下游」之前、「异常则兜底」是链路的最后一格：一旦把兜底写成「调用失败后再临时想办法」，就又退回到处处加 if 的老路。第三张图右边那句「换档不改业务」，靠的正是适配器——不管分发到轻量档还是强力档，返回给业务层的形状都一样，业务代码根本不必知道自己用的是哪一档。

## 层层追问

:::ask 那如果分流本身判断错了，把难题交给了轻量档怎么办？
:::

这恰恰说明「分类器本身也是一个部件」，不能把它当成不会错的真理。稳妥做法有两层。第一层是「存疑升档」：当任务特征模糊、或轻量档返回的结果明显撑不住（比如该给结构化结论却只回了半句），就把它升级到强力档重跑一次，而不是硬把不合格的结果交上去。第二层是「分类可观测」：把「升档发生过几次、集中在哪类任务」记成指标，若某类任务频繁升档，说明分流规则本身要调整，而不是每次都靠升级兜着。追到更细一层：分类规则要尽量简单、确定、可手工推算，别再套一个模型去判断「该用哪个模型」——那样等于引入新的单点故障和新的延迟，本末倒置。演示代码里分类器只用「是否需要推理」和「输入规模」两个可核对的特征，就是为了让分错时能一眼看出错在哪、能据以调规则。这条「用确定性规则守住入口」的纪律，和[异常分类与可重试判定](./k131-error-classify.md)里「先分清错误类型再决定动作」是同一种思路；把「分错档」也当成一类可统计的异常，才不会让它悄悄拖垮质量。

:::ask 那如果下游整片超时、或者连兜底档也不健康呢？
:::

追到第二层，问题就从「选谁」变成「选不上时给什么」。这里最要紧的一句：**兜底是确定性结果，不是异常**。下游超时、限流、全部档位都标记不健康时，网关应当返回一张预先定好、形状固定的结果表——写明「本次未能处理、原因类别、可稍后重试或转人工」，而不是把原始异常一路抛到界面。为什么强调「确定性」？因为上游业务要能对这张表做判断：能重试就排队重试，该降级就降级，而不是被一段堆栈文本噎住。第二层再往下一问：兜底会不会掩盖问题？会。所以切换与兜底的次数必须单独记账、纳入监控——若某档天天被兜底，说明它的健康标记或容量配置出了问题，该修的是下游，不是把兜底写得更好看。还要分清两道动作：路由管「进来之后去哪个下游」，限流管「让不让进」，两者都在入口层但职责不同，别写成一个函数，前者的分流、后者的计数应各自可查（可对照[传输、会话与网关限流](./k080-transport-session.md)）。而「下游异常时给确定的降级结果」这条，在[超时与确定性降级](./k109-timeout-fallback.md)里有更展开的讲法。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一张能力注册表、一个确定性分类器、一个网关和一个适配器，完整演示「按难度分档 → 成本记账 → 下游异常切兜底 → 返回形状统一」，结尾用一组断言逐条核验。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
"""多模型路由与网关：能力注册表 + 适配器 + 确定性兜底。"""


class CapabilityRegistry:
    """能力注册表：登记各档的单价、能力强度、此刻是否健康。"""
    def __init__(self):
        self.table = {}

    def register(self, name, cost, strength, healthy=True):
        self.table[name] = {"cost": cost, "strength": strength, "healthy": True if healthy else False}

    def mark_unhealthy(self, name):
        self.table[name]["healthy"] = False


def classify(task):
    """本地确定性分类器：只用可核对的特征判难度，不套模型。"""
    if task["need_reason"] or task["tokens"] > 100:
        return "hard"
    return "easy"


def pick(registry, min_strength):
    """在够强且健康的下游里，挑成本最低的一档。"""
    candidates = [(v["cost"], k) for k, v in registry.table.items()
                  if v["strength"] >= min_strength and v["healthy"]]
    if not candidates:
        return None
    return min(candidates)[1]


def route(task, registry):
    """网关路由：按难度给出所需的最低能力强度。"""
    return pick(registry, 3 if classify(task) == "hard" else 1)


def adapter_call(name, task, registry):
    """适配器：把不同下游的返回翻成统一形状，并逐次记账。"""
    if name is None:
        return {"ok": False, "by": "fallback", "cost": 0,
                "data": "下游不可用，返回确定兜底"}
    cost = registry.table[name]["cost"]
    return {"ok": True, "by": name, "cost": cost,
            "data": name + "处理:" + task["name"]}


def gateway(task, registry, ledger):
    """统一入口：路由 → 调用 → 无可用档时兜底；切换单独记账。"""
    try:
        name = route(task, registry)
        if name is None or not registry.table[name]["healthy"]:
            ledger.append((task["name"], "fallback"))
            return adapter_call(None, task, registry)
        ledger.append((task["name"], name))
        return adapter_call(name, task, registry)
    except KeyError:
        ledger.append((task["name"], "fallback"))
        return adapter_call(None, task, registry)


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    reg = CapabilityRegistry()
    reg.register("lite", cost=1, strength=1)
    reg.register("strong", cost=5, strength=3)
    ledger = []

    easy = {"name": "归类", "tokens": 20, "need_reason": False}
    hard = {"name": "多步推演", "tokens": 400, "need_reason": True}
    tricky = {"name": "短但要推理", "tokens": 10, "need_reason": True}

    r_easy = gateway(easy, reg, ledger)
    r_hard = gateway(hard, reg, ledger)
    r_tricky = gateway(tricky, reg, ledger)

    ok(r_easy["by"] == "lite", "简单任务分到够用的轻量档")
    ok(r_hard["by"] == "strong", "复杂任务分到强力档")
    ok(r_tricky["by"] == "strong", "需要推理时即便输入短也升档")
    ok(r_easy["cost"] < r_hard["cost"], "轻量档单价低于强力档")
    ok(r_easy["cost"] + r_hard["cost"] + r_tricky["cost"] == 11,
       "逐次成本被正确记账")

    shapes = [set(x.keys()) for x in (r_easy, r_hard, r_tricky)]
    ok(all(s == {"ok", "by", "cost", "data"} for s in shapes),
       "适配器把不同下游返回统一成同一形状")

    reg.mark_unhealthy("strong")
    r_down = gateway(hard, reg, ledger)
    ok(r_down["ok"] is False and r_down["by"] == "fallback",
       "强力档不健康时复杂任务走确定兜底")
    ok(r_down["cost"] == 0 and "data" in r_down,
       "兜底是固定形状且不产生下游计费")
    ok(not isinstance(r_down["data"], Exception), "兜底不把异常抛给上游")

    fallbacks = sum(1 for _, by in ledger if by == "fallback")
    ok(fallbacks == 1, "兜底次数被单独记账，便于监控掩盖的问题")
    ok(len(ledger) == 4, "每次请求都留下可查的分流记录")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `CapabilityRegistry` 是那张能力注册表：`register` 登记每档的单价 `cost`、能力强度 `strength`、是否健康 `healthy`；`mark_unhealthy` 用来模拟某档临时不可用。把「谁强、谁便宜、谁还开着」集中记在一处，路由才有可查的依据。
2. `classify` 是本地确定性分类器：只看 `need_reason`（是否需要推理）和 `tokens`（输入规模）两个可手工核对的特征。刻意不用模型来判断「该用哪个模型」，避免引入新的单点与延迟。
3. `pick` 在「够强且健康」的候选里按成本取最小：简单任务要求强度 ≥1，复杂任务要求 ≥3。这一行是「够用就好」的落点——不是选最强，而是选满足门槛里最省的那档。
4. `route` 把难度翻译成所需最低强度，再交给 `pick`。网关的分流规则就压缩在这一句里，业务代码完全不参与判断。
5. `adapter_call` 是适配器：无论分发到轻量档、强力档，还是走到 `name is None` 的兜底，都返回 `{ok, by, cost, data}` 四键的统一结构。这正是第三张图「换档不改业务」的实现——上游只认这张表。
6. `gateway` 是唯一入口：先路由，再判「无可用档或该档不健康」就切兜底，并把每次分流（含兜底）写进 `ledger`。`try/except KeyError` 兜住登记表缺项这类意外，保证异常不会裸奔到界面。
7. `main` 前五条断言验分流与记账：简单归轻量、复杂归强力、短但要推理也升档、单价有差、三次成本累加为 11（1+5+5）。最后一条把「成本被逐次记下」变成可核对的数字，而不是一句「大概省了钱」。
8. 中间两条验适配器形状统一，以及把 `strong` 标记不健康后，复杂任务确实走 `ok=False` 的固定兜底、零下游计费、且 `data` 不是异常对象。末两条验兜底被单独记账一次、四条请求条条留痕。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出，并打印 `通过 12/12 项`。

有一处如实说明：这里用两行规则代替真实分类器、用两个字典档位代替真实下游、用本地列表代替账单系统，全是为了让整条链路不联网、不依赖账号就能跑通并手算验证。它演示的是「分流、记账、兜底、形状统一」的顺序与性质，不是任何具体网关产品或接口的实现。真要按成功任务而不是按每次调用核算开销，口径在[核心指标与按成功任务核算成本](./k096-metrics-cost.md)里另讲。

## 踩坑与边界

- **简单任务一律喂最强模型**：现象 → 账单高、排队久，能力严重过剩 → 原因 → 没有按难度分流，把「越强越好」当默认 → 怎么改 → 定义可核对的任务特征，够用即选最省档。
- **判断散落在业务里**：现象 → 三处阈值不一，某个分支漏写兜底，异常抛到界面 → 原因 → 把入口纪律塞进了处理函数 → 怎么改 → 收口到网关，路由与兜底各一处，业务只认统一返回结构。
- **兜底其实是再抛一次异常**：现象 → 下游超时后用户看到一段堆栈 → 原因 → 把「兜底」写成了异常透传 → 怎么改 → 返回预先定好、形状固定的结果表，写明原因类别与可重试或转人工的下一步。
- **分类器本身成了新单点**：现象 → 为判断「用哪个模型」又调一次模型，延迟与故障面都变大 → 原因 → 分流逻辑过度复杂 → 怎么改 → 用确定性规则分类，存疑升档，并把升档次数记为可观测指标。
- **兜底悄悄掩盖下游故障**：现象 → 某档天天被兜底，服务看着「还行」，问题一直没修 → 原因 → 切换与兜底没有单独记账 → 怎么改 → 把兜底次数纳入监控，越线就查下游健康标记与容量配置。

还要分清几件都在入口层、却不该写成一个函数的事：路由管「进来之后去哪个下游」，限流管「让不让进」（见[传输、会话与网关限流](./k080-transport-session.md)），熔断管「连续失败要不要暂时切断」（见[熔断与 kill switch](./k104-circuit-breaker.md)），三者职责不同、判定点却应相邻且各自可查。边界也说明白：一个只在本地跑、只有一种任务、只用一档能力的小脚本，根本不需要网关与路由，加一层反而是负担；它划算的场合是「任务难度有明显差异、或下游不总是可靠、或需要按档核算开销」。等单价、字段名、可用档位随版本变化时，这张能力注册表也要被[版本漂移与升级策略](./k084-version-drift.md)的契约测试覆盖到，否则某天某档改了名字或退了场，路由会静默地把请求送去一个不存在的地方。整体脉络可回到[从这里开始](./00-start-here.md)。

## 三句话小结

多模型路由与网关，是把「按任务难度选哪一档能力、下游异常时给什么结果」这两件入口纪律，从散落各处的判断收口成一个统一动作。

关键做法是用能力登记表按「够用且最省」选档、用适配器统一返回形状、把超时的兜底写成预先定好的固定结果，并让分流与切换都留下可查的账。

当只有一种任务、只用一档能力、下游也始终可靠时，不必额外加一层网关路由，一个直接调用反而更清楚。

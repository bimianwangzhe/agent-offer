# 主从 / 流水线 / 辩论三种模式

你已经确认这个任务确实该拆成多个智能体，接下来却卡在另一个问题上：几个角色之间到底谁先说话、谁把结果交给谁、最后听谁的。有人把三个角色都塞进同一段提示词里轮流发言，跑出来的记录像一串闲聊，出了错根本找不到是哪一步开始偏的，也没人能说清最终结论是谁定的。

**不是模型配合得不好，是根本没定「消息怎么走、结果由谁裁决」。** 角色数量只是表面，真正决定协作能不能复盘的是消息的走向和收口位置；走向不固定，同样的输入每次都可能走出不同路径，评测和排障都无从下手。

先把词说清。消息契约（message contract）指一条消息必须带齐的字段约定，比如谁发的、发给谁、什么类型、带了什么内容，缺一项就算不合法。裁决者（adjudicator）指最后把各路结果收成一个结论、并对外负责的那个节点。多智能体（Multi-Agent）是把任务交给几个智能体（Agent，能自己决定下一步并调用工具的程序）协作完成。结构化消息常用 JSON（JavaScript Object Notation，一种用键值对写数据的文本格式）表示，本文的代码里用字典来承载同样的字段。提示词（prompt）是写给模型的规则说明。这些词先立住，后面讲三种模式才不会把「谁在说话」和「谁说了算」混成一件事。

## 一、生活类比：一间厨房的三种分工

同样三个师傅，可以有三种完全不同的组织方式。第一种是主厨派活：主厨把「切配」交给一个人、把「熬汤」交给另一个人，两人各干各的，做完都把半成品交回主厨，由主厨摆盘、定味道、端出去。这是主从，特征是消息从中心发出、又回到中心，谁说了算很明确。第二种是装配线：洗菜的人只交给切菜的人，切菜只交给炒锅，炒锅只交给装盒，装盒交给复核，谁也不往回传，一道工序的产出就是下一道的输入。这是流水线，特征是单向、首尾相接、最后一道工序负责放行。第三种是评审会：两个师傅各提一套方案，裁判看完不满意就追问依据，被追问的一方再补一轮材料，来回几轮之后裁判拍板。这是辩论，特征是同一对节点之间会往返，且必须有人在追问之后强制收口。

对应关系要讲透：师傅对应智能体，半成品对应消息里的载荷，主厨、复核台、裁判分别对应三种模式里的裁决者，「裁判追问」对应消息类型里的追问，「把菜端出去」对应最后那条裁决消息。**三种模式的差别不在有几个角色，而在消息有没有回程、以及收口发生在哪个节点。** 搞混这一点，就会出现「说是流水线，却让中间节点把意见发回上游」的怪结构，表面是三种之一，实际上谁都能改谁，复盘时自然理不清。

## 二、三种模式各自适合什么

选模式前先看任务本身。主从适合「有个节点能把活拆开、也能把结果合起来」的场景，子任务之间尽量不互相依赖；流水线适合步骤固定、单向流动、上一步产出正好是下一步输入的场景；辩论适合结论天然有分歧、需要经过质证才能定下来的场景，代价是消息条数和轮数都会变多。

:::figure 三种模式各自适合什么
@stack
主从::有个节点能拆活并汇总，子任务彼此不依赖
流水线::步骤固定且单向，上一步产出就是下一步输入
辩论::结论有分歧，需要来回质证后再裁决
:::

这里有个很实在的判断：如果任务里根本没有「分歧」，硬套辩论只会多出几轮无意义的往返；如果子任务之间要频繁互相看结果，主从里「都交回主控」的约定反而会变成瓶颈，那时更适合把它改成显式的消息链。模式不是身份，是一份关于「消息允许往哪走」的约定，约定写死了，系统才可测试。想回看「到底该不该拆成多个角色」，见[什么时候才该拆多智能体](./k117-when-multi-agent.md)；本篇只讨论已经决定拆之后的走法。

:::ask 那如果主从里的两个从节点也想直接互相说话呢？
那就已经不是主从了。主从的定义是「派单从主控出、结果回主控收」，一旦从节点之间开了直连通道，就多了主控看不见的消息，裁决时拿到的信息不全，出错也查不到那条私下传递。要么明确改成带消息链的结构并把新通道写进契约，要么把需要交换的内容抬到主控这一层统一转发。**别让约定之外出现第二条路，否则「谁说了算」会变成一笔糊涂账。**
:::

:::ask 那如果辩论里裁判一直追问、迟迟不肯拍板呢？
必须给轮数设上限，并在到达上限时强制裁决。追问的价值是把依据逼出来，不是无限延后结论；没有收口规则的辩论，在真实运行里会变成两个节点反复复述立场，成本一直涨而结论不动。代码里把「固定两轮后强制裁决」写成结构约定，正是这个意思：**往返要允许，但收口必须预先写死。** 收口之后谁有权改共享结果，是[状态共享、冲突处理与失败恢复](./k120-shared-state.md)要接着讲的事。
:::

:::figure 消息走法与裁决权的差别
@compare
主从与流水线::消息有明确去向|一次流转就结束|裁决在固定节点
辩论::消息会往返|同一对节点可能多轮|裁决前必须先收口
:::

左边两行之所以能放在一组，是因为它们都不需要「把消息发回已经说过的节点」；右边单独成组，是因为往返带来了两个新问题：同一对节点之间可能有多条消息，以及必须有人决定什么时候停止追问。这两个问题不解决，辩论模式就会退化成闲聊。

## 三、把三种走向写成能检查的消息契约

下面的脚本零依赖、不需要账号、不需要联网。它把三种模式各自的消息序列写成数据，再用几个确定性函数检查：字段齐不齐、收件人是不是合法节点、最终结论是不是由声明的裁决者给出、流水线是不是真的单向、辩论是不是真有往返。

```python
# k118.py —— 三种协作模式的消息契约检查器（零依赖，python k118.py）


def msg(sender, receiver, kind, payload):
    """一条消息契约：谁发的、发给谁、什么类型、带了什么。"""
    return {"发": sender, "收": receiver, "类型": kind, "载荷": payload}


MASTER = [
    msg("主控", "检索员", "派单", "查订单状态"),
    msg("主控", "拟稿员", "派单", "准备回复草稿"),
    msg("检索员", "主控", "回传", "订单已发货"),
    msg("拟稿员", "主控", "回传", "草稿一版"),
    msg("主控", "汇总", "裁决", "合并成最终回复"),
]
PIPELINE = [
    msg("入口", "切分", "流转", "原始反馈"),
    msg("切分", "归类", "流转", "三句话"),
    msg("归类", "拟稿", "流转", "投诉类"),
    msg("拟稿", "复核", "流转", "草稿"),
    msg("复核", "归档", "裁决", "通过并发出"),
]
DEBATE = [
    msg("正方", "裁判", "立论", "应退款"),
    msg("反方", "裁判", "立论", "不退款"),
    msg("裁判", "正方", "追问", "依据是什么"),
    msg("正方", "裁判", "答辩", "条款第七条"),
    msg("裁判", "归档", "裁决", "采纳正方"),
]


def validate(messages, decider, nodes):
    """契约完整、收件人合法、最终结论由裁决者以「裁决」类型给出。"""
    keys = ("发", "收", "类型", "载荷")
    assert all(all(k in m for k in keys) for m in messages), "消息缺字段"
    assert all(m["收"] in nodes for m in messages), "消息发给了未声明节点"
    assert messages[-1]["发"] == decider, "结论不是裁决者发出"
    assert messages[-1]["类型"] == "裁决", "缺少裁决消息"
    return True


def is_one_way(messages):
    """流水线特征：首尾相接，且没有任何一条消息回到起点。"""
    head = messages[0]["发"]
    if any(m["收"] == head for m in messages[1:]):
        return False
    return all(messages[i]["收"] == messages[i + 1]["发"]
               for i in range(len(messages) - 1))


def round_trips(messages):
    """辩论特征：裁决者发起追问的次数。"""
    return sum(1 for m in messages if m["类型"] == "追问")


def decider_of(messages):
    return messages[-1]["发"]


if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    check("主从：由主控派单并裁决",
          validate(MASTER, "主控", {"主控", "检索员", "拟稿员", "汇总"}))
    check("流水线：单向不回头", is_one_way(PIPELINE))
    check("流水线：由复核节点裁决",
          validate(PIPELINE, "复核", {"入口", "切分", "归类", "拟稿", "复核", "归档"}))
    check("辩论：存在往返追问", round_trips(DEBATE) >= 1)
    check("辩论：由裁判给出最终裁决",
          validate(DEBATE, "裁判", {"正方", "反方", "裁判", "归档"}))
    check("三种模式裁决者互不相同",
          len({decider_of(MASTER), decider_of(PIPELINE), decider_of(DEBATE)}) == 3)
    check("流水线里没有追问往返", round_trips(PIPELINE) == 0)
    print("通过 %d/%d 项" % (passed, total))
```

运行后打印的是每条检查的结论与断言汇总：

```text
  [通过] 主从：由主控派单并裁决
  [通过] 流水线：单向不回头
  [通过] 辩论：存在往返追问
通过 7/7 项
```

逐段解释关键行在做什么：

1. `msg` 把所有消息统一成四个字段，这一步就是消息契约本身；任何节点想加私货，都得先过「字段齐不齐」这一关，契约之外的信息没有落脚点。
2. `MASTER` / `PIPELINE` / `DEBATE` 三份常量把「消息怎么走」写成可读的数据，而不是散落在各处的调用。注意每条序列最后一条都是「裁决」类型，收口位置一眼可见。
3. `validate` 里 `keys` 定义了必备字段，随后依次检查字段完整、收件人在声明的节点集合内、最后一条由裁决者发出且类型为裁决。把「谁说了算」写进断言，而不是写进提示词里求模型自觉。
4. `is_one_way` 先用 `head` 记下第一条的发送者，再确认后面没有任何消息回到它，最后逐对检查「本条收件人 = 下条发送者」。这就是流水线「单向、首尾相接」的可执行定义。
5. `round_trips` 只数「追问」类型的消息，用它区分辩论与另外两种；`decider_of` 直接取最后一条的发送者，避免另开一份裁决者配置造成两处不一致。
6. 主程序的 `check` 用 `assert` 兜底，任何一条不符都会让脚本失败；`通过 N/N 项` 把「这套契约检查器本身对不对」也变成可复核的一行输出。

:::tip 先定契约，再谈角色性格
很多协作跑偏，是因为先给角色写了大段人设，却没规定消息字段和收口位置。**把「发、收、类型、载荷」和「最后一条必须是裁决」定死，剩下的措辞怎么改都不影响复盘。**
:::

## 四、踩坑与边界

- **收件人谁都能当**：现象是某个节点把结果发给一个从没声明过的名字，下游静默丢消息 → 原因是没有节点白名单，消息契约只管字段不管去向 → 怎么改：像 `validate` 那样把合法节点写成集合，写入前核对，不合法直接判失败。
- **把回传当回环**：现象是主从里「结果交回主控」被当成辩论的往返，于是加了不必要的追问轮数 → 原因是没区分「一次性回传」与「同一对节点多轮往返」 → 怎么改：用消息类型区分，回传只发生一次，追问才计往返次数。
- **流水线尾部没裁决**：现象是最后一道工序把草稿丢出来就结束，没人负责放行 → 原因是只画了流转链，没声明裁决者 → 怎么改：给链路补一条明确由裁决节点发出的「裁决」消息，`validate` 会强制检查最后一条的类型。
- **裁决者自己也下场争论**：现象是裁判一边追问一边给倾向性结论，两方开始迎合裁判 → 原因是裁决与质证混在同一节点、没有留痕 → 怎么改：把「追问」和「裁决」分成两类消息，裁决只在收口时出现，中间只发追问。
- **模式套错任务**：现象是本来步骤固定的活被做成辩论，往返几轮结论没变 → 原因是按「想显得严谨」选模式，而不是按任务有没有分歧 → 怎么改：回到本节的三行清单，步骤固定用流水线，有分歧才用辩论。

:::figure 一条消息的完整去向
@flow
构造消息|校验收件人|按模式流转|裁决节点收口|留下轨迹
:::

图里最后一步「留下轨迹」最容易被省掉，但它恰好是后面所有事情的地基：评测要拿它做样本，排障要靠它复现，答辩要现场把一条完整链打出来。讲项目时怎么把这条链在有限时间里说清，见[15 分钟讲项目的节奏](./k126-project-pitch.md)。

:::quote
模式不是「有几个角色」，是「消息允许往哪走、最后谁收口」。把这两句写进断言，协作才从闲聊变成可以复盘的系统。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能说出主从、流水线、辩论各自的消息走向与裁决者
- [ ] 能解释「一次性回传」和「多轮往返」的差别
- [ ] 面对步骤固定的任务，能判断不该套辩论并说出理由
- [ ] 能徒手写出消息契约的四个字段，并说明为什么最后一条必须是裁决
- [ ] 知道把「谁说了算」写成断言，而不是写进提示词
:::

是什么：这是把多智能体协作分成主从、流水线、辩论三种「消息走向 + 裁决位置」约定的方法。
关键做法：先定消息契约的节点白名单与字段，再声明收口节点，最后把单向、往返、裁决都写成可跑的检查。
什么时候不该用：任务没有分歧时别用辩论，子任务频繁互赖时别硬套主从，步骤本就固定时别为了显得复杂而加往返。

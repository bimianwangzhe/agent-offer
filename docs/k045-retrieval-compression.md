# 检索式召回压缩：原文外置，本轮只取回需要的片段

## 摘要里没有，它就说不知道

你把长会话压成几句摘要，窗口是瘦了，可用户忽然问「上回那单的发票到底按哪个流程开的」，助手答不上来——那件事在压缩时被当成不重要的细节抹掉了。你换个思路，干脆把全部历史工单原样贴进每一轮输入，这下细节是有了，可每轮都顶着一大段与当前问题毫无关系的文字，慢且贵，答案还常常被埋在中间的材料带偏。

## 先破一个误解

**不是摘要写得不够细，是「提前替未来决定该留什么」这件事本身就靠不住。**

[摘要式压缩](./k044-summary-compression.md)要在压缩的那一刻判断哪些事实以后会用，可你根本不知道用户第十几轮会问什么。检索式召回压缩换了个方向：历史原文不压、不丢，整份放到窗口之外存着；每一轮先拿当前问题当查询，按相关度只把最可能是答案来源的几小片取回来，用完即弃。于是「该留什么」不再由过去猜，而是由本轮问题当场决定。

这里补几个词。片段（chunk，指把长材料切成的一小块可独立取回的文字）是外置与召回的最小单位；id（identifier，标识）是给每片编的号，凭它能把原文完整取回；相关度是一个可以计算的分值，用来给候选片段排序；top_k（取前 K 条）则是召回条数的硬上限。所谓「压缩」，压的不是原文，而是每轮真正送进窗口的量：原文一份没删，进场的只有几片。

## 用图书馆的借书单来理解

把全部历史原文想成图书馆书架上那一排排书，窗口是你面前那张小书桌，一次只摊得开几页。

摘要式压缩像什么？像你提前把整架书的内容缩写成一张卡片，此后永远只带这张卡片。卡片轻便，可一旦有人问到卡片没写进去的细节，你就只能摇头。检索式召回则像正常的借书流程：书始终留在架上，读者每来一个问题，你先填一张借书单写清要查什么，按索书号找出最相关的几本，只把那几页复印摊到桌上，看完收走。对应关系是：书架对应外置存储，索书号对应 id，借书单对应本轮查询，复印的那几页对应注入的片段，而那张永远带着的卡片对应摘要。

要害在于：**你不可能预先知道读者明天会问什么，所以不该提前把答案定死**。把选择权留给本轮问题，既保住了原文里的全部细节，又不必每轮都把整架书搬上桌。当然，这套做法有前提：书得编好号、找得到。所以外置时每片材料都要随身带几项信息。

:::quote
检索式召回压缩省下的不是存储空间，而是**每一轮的注意力**：原文全在，只是绝大多数轮次用不着看。
:::

## 该带什么，怎么走，画出来

:::figure 外置片段要随身带的几项信息
@stack
编号::凭它把原文完整取回
来源与时间::判断这份材料是否还作数
权限范围::无权看的内容不该被召回
版本::同一事实改过几次要能分清
:::

这四项里「来源与时间」「权限范围」最容易被忽略。前者决定两份材料矛盾时该信谁——旧记忆不该盖过权威系统里的新记录；后者要求无权查看的内容在打分之前就被排除，而不是先召回、再发现不能看。版本则让「同一事实改过三次」这种情形可被辨认，不至于把最早那次当成现状。

:::figure 一次按需召回的完整链路
@flow
原文外置落盘|生成本轮查询|按相关度打分|取回前K片|注入上下文
:::

:::figure 提前压摘要与当场取片段的差别
@compare
提前压成摘要::过去替未来做决定|细节会被抹平|没料到的问法答不上
本轮按需召回::问题决定取什么|原文细节仍在|查得到才带进来
:::

五个环节里，第三步「按相关度打分」是整套做法的成败所在，而它算的是「像不像」，不是「对不对」。打分高只说明字面接近，不说明这段材料能回答问题。所以召回之后仍要过一遍[上下文预算表](./k041-context-budget.md)划的额度，以及[四层上下文结构](./k042-context-layers.md)里的按需准入：条数受上限约束，片段太长还要再裁，与本轮无关的一组都不给。别让「取回」变成「整份倒回窗口」的另一种说法。

## 再往深问两层

:::ask 那如果相关度算错了，把无关片段排到前面、该取的没取到，怎么办？
:::

先把两件事分开看：材料有没有被找回来，和答案有没有答对，是两个独立的问题。只盯最终答案，你永远分不清是「没搜到」还是「搜到了却答错」。稳妥做法是给召回单独留一组检查，比如固定几条「问这句必须命中哪片」的用例，每次改动打分方式都跑一遍。更要紧的是给零命中留明确出路：一片都没取到时，系统应当能直接说「现有材料里没有依据」，而不是拿几片勉强相关的文字硬凑一个答案。空结果不是故障，是一个必须被正确处理的正常分支。

:::ask 再深一层：取回来的片段会不会又把窗口撑满，跟整库贴入没区别？
:::

会不会撑满，取决于你有没有给「取回」加约束。三道约束缺一不可：一是条数上限，只取前 K 片，命中的再多也不全带；二是长度裁剪，单片过长就截成摘要并附一句「已截断」，原始全文仍留在外置存储里，需要时凭 id 再取；三是只带引用还是带原文的区分，多数轮次带一句「可凭某号取回」就够了，真要逐字引用时才展开。这三道约束合起来，就是[前缀缓存与即时注入](./k050-prefix-cache.md)里说的「只给本轮需要的信息」。另外要留意长材料中间的内容本来就更易被忽略，取回后别把关键事实摆在中间，这一点见[上下文膨胀与中间遗失](./k049-context-bloat.md)。

## 一份能跑的召回器

下面这份实现只用标准库，用「相邻两字一组」的确定性打分模拟相关度，把外置、召回、凭号取回与落盘还原都做进去，复制成文件直接运行即可。它不接任何模型或外部服务，每次运行结果一致。

```python
# recall.py —— 只用标准库，python recall.py
import json


def bigrams(text):
    # 把文字切成相邻两字一组的片段，作为可比较单元；零第三方
    chars = [c for c in text if not c.isspace()]
    return {chars[i] + chars[i + 1] for i in range(len(chars) - 1)}


def score(query, doc):
    # 查询与候选片段的二元组交集越大，认为越相关
    q, d = bigrams(query), bigrams(doc)
    return len(q & d) if q and d else 0


class ExternalStore:
    def __init__(self):
        self.docs = {}

    def put(self, key, text):
        self.docs[key] = text
        return key

    def recall(self, query, top_k):
        ranked = [(score(query, t), k, t) for k, t in self.docs.items()]
        ranked.sort(key=lambda x: (-x[0], x[1]))
        return [(k, t) for s, k, t in ranked[:top_k] if s > 0]

    def fetch(self, key):
        # 需要时凭编号把原文完整取回
        return self.docs[key]

    def dump(self):
        # 外置内容可整份序列化，便于落到外部存储
        return json.dumps(self.docs, ensure_ascii=False)


if __name__ == '__main__':
    store = ExternalStore()
    store.put("d1", "退货地址改为朝阳区某路八号，记得发顺丰")
    store.put("d2", "用户咨询过发票开具的时间与流程")
    store.put("d3", "本单金额约好三百元且不能修改")
    query = "之前说的退货地址发什么快递"
    hits = store.recall(query, top_k=2)
    keys = [k for k, _ in hits]
    assert "d1" in keys                                     # 相关片段被召回
    assert "d2" not in keys                                 # 讲发票的被挡住
    assert "d3" not in keys                                 # 讲金额的也没混进来
    assert len(hits) <= 2                                   # 条数受上限约束
    assert all("发票开具" not in t for _, t in hits)
    assert store.fetch("d1").startswith("退货地址")         # 凭编号取回原文
    snapshot = store.dump()
    assert json.loads(snapshot)["d1"].startswith("退货地址")  # 落盘可还原
    full = "\n".join(store.docs.values())
    injected = "\n".join(t for _, t in hits)
    assert len(injected) < len(full)                        # 注入量小于全量
    print("通过 8/8 项：按需召回、无关遮挡、条数受限、凭号取回与落盘还原均正确")
```

1. `bigrams` 把一串文字切成相邻两字一组的集合，作为可比较的最小单元。不用任何分词库，中文照常能比；用集合是为了去重，让重复出现的字不把分值虚高抬上去。
2. `score` 取查询与候选片段两个集合的交集大小当相关度。这只是个可复现的构造打分，真实系统里会更复杂，但「算的是字面接近程度」这件事不变，所以才需要单独检查召回质量。
3. `ExternalStore` 用一个字典当外置存储：`put` 存原文、`fetch` 凭编号取回、`dump` 用 JSON（JavaScript Object Notation，一种轻量级的结构化数据格式）把整份内容序列化，模拟落盘。注意存进去的动作完全不会让窗口变大。
4. `recall` 先给每片打分，按分值从高到低、同分时按编号排，再截前 K 条，最后用 `s > 0` 把零相关的挡掉。三道约束——上限、排序、零分过滤——都在这几行里，正是「别让取回变成整份倒回」的落点。
5. 主函数存了三片内容，只讲退货地址、发票流程、金额各一片，拿「之前说的退货地址发什么快递」当查询。八条断言分别验证相关片被召回、讲发票的没混进来、条数不超上限、注入文本里没有无关内容、凭编号能取回原文、落盘后能还原、以及注入量确实小于全量原文，最后打印通过项数。

想看零命中的分支，把 `query` 换成一句跟三片都无关的话再跑，`hits` 会是空列表——这正是系统该说「材料里没有依据」的时刻，而不是硬凑答案的时刻。

## 踩过的坑

- **取回即整份倒回**：现象是做了召回照样超支 → 原因是命中后把原文全量注入 → 怎么改：条数设上限、单片过长先裁、多数轮次只带引用编号。
- **先召回再查权限**：现象是无权内容差点被引用 → 原因是权限判断放在打分之后 → 怎么改：无权范围在打分前就排除，让不该看的片根本不进候选。
- **只看答案不看召回**：现象是答错时分不清是搜错还是答错 → 原因是两类质量混在一起评 → 怎么改：给召回单独留一组「问这句必须命中哪片」的检查。
- **零命中硬凑答案**：现象是没有依据却编出一套说辞 → 原因是把空结果当异常随便处理 → 怎么改：把零命中当正常分支，明确回复缺乏依据。
- **外置时忘了带元数据**：现象是两份材料矛盾时选了旧的 → 原因是没记来源、时间与版本 → 怎么改：编号、来源时间、权限、版本跟着片一起存，裁决时按权威与新旧判断。

## 三句话

检索式召回压缩是把历史原文外置留存，每轮按当前问题取回相关片段、用完即弃的做法。
关键做法是给外置片带齐编号与元数据，召回后仍受条数上限、长度裁剪与按需准入约束。
当材料总量很小、每轮几乎都会全用到时，别绕这一圈，直接带上原文更简单。

# 评测与生产化：从 Demo 到能上线

这一节是整份知识库里**最能拉开面试差距**的部分。绝大多数人停在「跑通了」，而岗位要的是「能稳定交付」。

## 三层评测

> 没有评测集的团队，几乎不可能交付稳定的 Agent。评测就是 AI 系统的单元测试。

| 层 | 测什么 | 起步做法 |
|---|---|---|
| 单元评测 | 单个工具、Schema 校验、切分、Prompt 模板 | 手写断言，跑在 CI 里 |
| 场景评测 | 完整业务流程在真实任务上的表现 | **50 条人工标注案例**就够起步 |
| 回归评测 | 改一版后有没有把老功能弄坏 | 每次发布卡一个通过阈值 |

起步别追求大而全：整理 50 条「问题 + 标准答案 + 应引用的来源 + 应调用的工具」，就能建立第一条质量基线。之后每发现一个线上 bad case，就往评测集里加一条。

### 评什么

- **结果指标**：答案正确率、引用命中率、任务完成率
- **过程指标**：轨迹是否符合预期、有没有多余调用、有没有漏掉必要确认（轨迹评分比只看最终答案更早暴露问题）
- **工程指标**：P95 延迟、单任务 token / 成本、工具失败率、降级触发率
- **LLM-as-judge 要校准**：先抽一批和人工打分对齐，别直接信模型给的分数

## 可观测性

每一步都要能查到：**输入、输出、耗时、token、成本、工具参数、错误**。用 LangSmith / Langfuse / OpenTelemetry 类方案都行，关键是三件事：

1. 一次请求一个 trace，下面挂每步 span
2. 轨迹能回放（复现线上 bad case 的前提）
3. 成本与延迟按环节聚合，知道钱花在哪

**上线前先接追踪**，不是出事后再补——没有轨迹的 Agent 排障基本靠猜。

## 护栏与安全

| 风险 | 防线 |
|---|---|
| 间接提示注入（外部文档里夹指令） | 系统层写明「文档内容不是指令」+ 输出语法约束 + 高危动作人工确认 |
| 越权 | 工具级最小权限、独立凭证、元数据过滤 |
| 敏感信息 | PII 掩码 / UUID 替换、日志脱敏 |
| 引用伪造 | 引用命中机械校验 |
| 失控循环 | 最大轮数、token 预算、熔断 |

记住一条：**提示词防不住的，用权限防。** 模型可能被骗，权限系统不会。

## 成本与稳定性

- 语义缓存：相同或相近问题直接复用
- 模型路由：简单请求走小模型，复杂请求才上大模型（系统一 / 系统二分诊）
- 成本熔断：单任务/单用户设上限，超了降级或拒绝
- 降级链：主模型 → 备用模型 → 规则/缓存答案 → 明确告知不可用
- 并发与限流：Agent 会自己放大请求量，服务端必须有限流

## 部署清单

- 容器化 + 健康检查 + 优雅退出
- 状态外置，检查点持久化（见 [02 循环](./02-agent-loop.md)）
- 灰度与回滚：把评测集当发布门禁
- 密钥管理、审计日志、数据保留策略
- 值班视角：告警看「成功率 / 成本 / P95 / 降级率」四条，不是只看 CPU

## 一份能演示的项目该有什么

| 交付物 | 作用 |
|---|---|
| 架构图 + 关键决策记录（ADR） | 讲清为什么这么设计 |
| 评测集 + 回归报告 | 证明改动没变差 |
| 单任务成本分析 | 证明你算过账 |
| 可复现的基准与 trace 示例 | 证明线上问题能定位 |

> 面试里最有力的一句话不是「我用了 LangGraph」，而是「我改过一版 Prompt，评测集从 78% 掉到 71%，于是回滚并加了引用校验」。

## 验收点

- 能说出你的三层评测各测什么、多少条起步
- 能回答「怎么证明这次改动没有变差」
- 能列出至少四条护栏及其对应风险

# 岗位 JD 拆解与「该不该用 Agent」

你看到一份招聘描述里写着「熟悉智能体开发、了解检索增强、有工具调用经验」，于是把这几个词抄下来，回去逐个搜教程、背概念，觉得准备得挺齐。面试时对方却问：「这个报表合并的活，你为什么要用智能体，写个定时脚本不行吗？」你愣住了——你准备的全是「怎么做」，没人问过你「该不该做」。

**不是知识点没背全，是把岗位描述当成了名词清单，没反推出它真正要考的工程判断力。** 描述里那些词是结果，不是要求本身；它背后藏着的是「面对一个具体场景，你能不能先判断值不值得用智能体」。这个判断力，比记住多少个术语更常被追问。

先把词说清。JD 是 Job Description（岗位描述）的缩写，就是那份列职责与要求的招聘文本。Agent（智能体）指能自己决定下一步做什么、并按需调用工具的程序。聊天机器人（Chatbot）是按一轮一轮对话回应、不一定承担多步任务的程序。工作流（Workflow）是按预先画好的固定顺序往下走的程序。RAG 是 Retrieval-Augmented Generation（检索增强生成）的缩写，指先从材料里检索、再把检索结果拼进上下文让模型作答的做法。API 是 Application Programming Interface（应用程序编程接口）的缩写，指程序之间约定好的调用方式。这些词第一次出现都给了白话，后面直接用不再重复解释。

## 一、生活类比：看菜谱而不是背菜名

想象你要去别人家厨房帮忙，主人递来一张纸条：「今晚做四菜一汤，有客人不吃辣，只有一个灶，冰箱里剩半棵白菜」。如果你把它当成菜名清单，就会去背「四菜一汤是哪四菜」；但真正有用的是反推：不吃辣意味着调味要分两份，一个灶意味着出菜顺序要排、不能同时开火，剩半棵白菜意味着得先确认够不够、不够要换做法。纸面上写的是菜，考的是你在这些约束下怎么安排。

岗位描述也是这张纸条。「检索增强」这个词背后要考的是切分、召回、过滤前置、冲突裁决；「工具调用」背后要考的是参数校验、失败分类、权限；「评测」背后要考的是指标口径、轨迹留痕、回归对比。**把名词翻译成「对方会拿什么场景来问你」，才叫拆解。** 反推出来的不是五个词，是五组可以预先准备的问题。

至于「该不该用智能体」，可以接着用厨房类比：如果客人点的是「每天中午固定热同一份盒饭」，写死一条定时流程就够了；如果客人说「你看着冰箱里剩什么，随机做两道不重样的」，路径随材料变、要不断查冰箱、还得记住前面用过什么——这才轮到能自己拿主意的做法。

## 二、从描述里反推什么

拆解落到这里，要做两件事：先把描述里的词映射成能力清单，再对每个候选场景做必要性判断。两者顺序不能反——先判断「用不用」，再谈「怎么用」，否则容易出现「技术很炫但场景根本不需要」的答案。必要性判断用三条：路径会不会随输入变、要不要查外部数据、是不是多步且要记状态。三条同时成立才值得上智能体，缺了就优先固定规则。

:::figure 岗位描述常映射到的五类能力
@stack
工具与协议::工具说明、参数校验、权限与失败分类
循环与状态::轮次、状态字段、可中断与检查点
检索::切分、召回、过滤前置与冲突裁决
评测::指标口径、轨迹留痕与回归对比
安全护栏::输入检查、动作校验与人工交接
:::

这五组能力里，「评测」和「安全护栏」最容易被漏掉，因为描述里往往不直接写，只会用「稳定」「可控」这类词带过。但面试追问最常落在这里：改了一版怎么证明没变差、动作要不要人确认、一个用户的操作会不会影响另一个。把这两组主动补进清单，比多背三四个名词有用。想看这些能力怎么落到具体作品上，见[三个能写进简历的项目](./k122-three-projects.md)。

:::ask 那如果描述里一个技术词都没提，只写「负责智能助手开发」呢？
那就别按关键词拆，按场景拆。把「路径会不会变、要不要外部数据、是不是多步有状态」这三问套到你能想到的真实任务上，逐个给答案，再看哪些答案指向「值得用」。描述越含糊，越要靠你自己把场景补出来，而不是等着对方把考点列清楚。**反推的起点是任务，不是词表。**
:::

:::ask 那如果某个场景三条都成立，是不是整条链都该用智能体？
不是。一条链里常常同时有「会变的部分」和「固定的部分」：格式转换、字段映射、按模板拼接这些环节路径固定，交给规则更稳；真正需要拿主意的那一两段才用智能体。把它们混在一起全交给模型，等于让不确定的部分去承担本来可以确定的工作，出错面变大、成本也上去。**必要性判断要落到「链里的哪一段」，而不是给整个系统贴一个标签。** 这段边界怎么讲清，见[约束、权衡与可验证结果](./k123-tradeoffs.md)。
:::

:::figure 固定规则与智能体的适用分界
@compare
固定规则::路径就那几条|不需要外部工具|一步出结果
智能体::路径随输入变|要查外部数据|多步要记状态
:::

左边三点是同一个判断的三面：路径固定、不查外部、一步到位，任一条成立都倾向于少用智能体。右边三点要同时成立才倾向用它。注意这张表不是在比谁更先进，而是在比「谁在这个场景下更省、更可预期」。把「为什么不用规则」答清楚，往往比把智能体讲得多炫更能说服人；这正是[什么时候才该拆多智能体](./k117-when-multi-agent.md)里那套判断的另一种问法。

## 三、把拆解与判断写成能跑的程序

下面的脚本零依赖、不需要账号、不需要联网。它用关键词把一段描述映射成能力清单，再用三条必要性条件对每个场景给出「用不用」和一句可复核的理由。

```python
# k121.py —— 从岗位描述反推能力，并判断该不该用 Agent（零依赖）
CAPABILITY = {
    "工具与协议": ("工具", "函数调用", "接口", "参数"),
    "循环与状态": ("循环", "状态", "编排", "重试", "中断"),
    "检索": ("检索", "召回", "向量", "切分"),
    "评测": ("评测", "指标", "轨迹", "回归"),
    "安全": ("权限", "护栏", "脱敏", "越权"),
}
NEED = ("路径不固定", "需要外部工具", "多步有状态")


def jd_to_capabilities(text):
    """把岗位描述里的词，映射到要考的工程能力。"""
    return [cap for cap, words in CAPABILITY.items()
            if any(w in text for w in words)]


def should_use_agent(signals):
    """三个条件同时成立才值得用 Agent，否则固定规则更稳。"""
    present = [s for s in NEED if signals.get(s, 0) == 1]
    return len(present) == len(NEED), present


def reason(signals):
    ok, present = should_use_agent(signals)
    if ok:
        return "路径会变，规则枚举不完，值得用 Agent"
    lack = [s for s in NEED if s not in present]
    return "缺 " + "、".join(lack) + "，固定规则更省"


if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    jd = ("负责 Agent 的工具函数调用、循环编排与状态管理，"
          "做检索召回切分，建设评测指标与轨迹回归，关注权限越权护栏")
    caps = jd_to_capabilities(jd)
    check("岗位描述映射到五类能力", len(caps) == 5)
    check("命中最容易漏的评测能力", "评测" in caps)
    check("命中安全护栏能力", "安全" in caps)

    fixed = {"路径不固定": 0, "需要外部工具": 1, "多步有状态": 0}
    free = {"路径不固定": 1, "需要外部工具": 1, "多步有状态": 1}
    check("固定格式报表不该用 Agent", should_use_agent(fixed)[0] is False)
    check("自由措辞查订单再回复值得用 Agent", should_use_agent(free)[0] is True)
    check("不用的理由点出缺哪些条件", "路径不固定" in reason(fixed))
    check("用的理由说明规则枚举不完", "规则枚举不完" in reason(free))
    print("通过 %d/%d 项" % (passed, total))
```

运行后打印每条断言与汇总：

```text
  [通过] 岗位描述映射到五类能力
  [通过] 固定格式报表不该用 Agent
  [通过] 自由措辞查订单再回复值得用 Agent
通过 7/7 项
```

逐段解释关键行在做什么：

1. `CAPABILITY` 把五类能力各自挂上一组关键词，这就是「名词 → 能力」的映射表；描述里出现任一词，就认为该能力被点到了。表是数据，不是散落的 if，改起来只动一处。
2. `NEED` 是三条必要性条件，顺序固定；`jd_to_capabilities` 用列表推导遍历映射表，命中即收录，返回能力名列表而不是原始词，完成「翻译」这一步。
3. `should_use_agent` 先收集被勾成 1 的条件，再用 `len(present) == len(NEED)` 要求三条同时成立。返回「判断 + 命中了哪些」两样，是为了后面能把理由写全。
4. `reason` 在不用的情况下把「缺哪几条」逐字列出来：`lack` 用集合差算出未命中的条件，拼成一句能贴进评审记录的话。这对应的正是「凭什么这么判断」。
5. `jd` 是本地构造的一段描述，故意把五类能力的词都放进去，用来验证映射没有漏项；两个场景 `fixed` 与 `free` 分别代表「路径固定」和「路径随输入变」。
6. 主程序的 `check` 用 `assert` 兜底，任何一条不符都会让脚本失败；`通过 N/N 项` 把「映射表和判断器本身对不对」也变成可复核的一行输出。

:::warn 关键词映射只是起点，不是判断本身
这份代码用命中词来演示「反推」，真实准备时别停在词上：命中「评测」之后，要能接着说出你打算怎么定义口径、留哪些轨迹、怎么回归对比。**映射负责提醒你别漏，答不答得出来靠场景准备。**
:::

## 四、踩坑与边界

- **抄名词当准备**：现象是把描述里的技术词抄一遍就以为齐了，被追问时说不出对应场景 → 原因是只做了词表、没做反推 → 怎么改：每个词后面补一句「对方可能拿什么场景问我」，再补一句自己会怎么答。
- **按框架名反推能力**：现象是准备内容全围绕某个工具怎么用，换个环境就答不上 → 原因是把工具当成了能力本身 → 怎么改：回到状态怎么管、失败怎么分、指标怎么算这些与工具无关的问题上。
- **把「用了 Agent」当答案**：现象是被问「为什么用智能体」时，只重复做法没有对比 → 原因是缺必要性判断这一环 → 怎么改：先答「不用规则会怎样」，用三条条件逐条对照，再讲实现。
- **整链一刀切**：现象是格式转换、字段映射这类固定环节也交给模型，出错面变大 → 原因是给整个系统贴了标签而不是逐段判断 → 怎么改：把链拆开，固定段落用规则，只在会变的那几段用智能体。
- **漏掉评测与护栏**：现象是描述没写这两个词就完全没准备，被问「怎么证明没变差」时卡住 → 原因是只按字面词拆解 → 怎么改：把「稳定」「可控」这类含糊表述主动翻译成评测口径与人工交接规则。

:::figure 一次必要性判断的顺序
@flow
读岗位描述|映射能力清单|逐场景问三条件|给出用不用|写下理由
:::

图里最后一步「写下理由」和前面同样重要：面试追的是决策链，不是结论那个字。把「缺哪三条、为什么规则枚举不完」留成一句能复核的话，被追问时才拿得出东西；追问会怎么一层层下来，见[四层追问链与转行者三问](./k125-followup-chain.md)。至于这些判断怎么组织成一件能讲的作品，见[三个能写进简历的项目](./k122-three-projects.md)。

:::quote
岗位描述写的是结果，考的是「这个场景到底该不该做」。先把必要性判断做出来，再谈怎么用，答案才不会停在名词上。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能把描述里的名词反推成「会被问到的场景」，而不是抄词表
- [ ] 能说出三条必要性条件，并解释为什么要同时成立
- [ ] 面对「写个定时脚本不行吗」能给出不用的理由与对比
- [ ] 知道判断要落到链里的哪一段，而不是给整个系统贴标签
- [ ] 能主动补上描述没写、却常被追问的评测与护栏
:::

是什么：这是把岗位描述反推成能力清单、并对每个场景先做「该不该用智能体」判断的方法。
关键做法：名词翻译场景，三条必要性条件逐场景对照，把用或不用的理由留成可复核的一句话。
什么时候不该用：路径固定、不查外部数据、一步就能出结果的任务，别用智能体，也别为显得先进而硬套。

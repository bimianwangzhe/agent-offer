# 扇出并行与 workers 上限

## 场景提问

一个任务要处理十二份材料，一份份顺序跑下来太慢，你想着「拆开一起跑不就快了」，于是把十二份各交给一路同时处理。结果比顺序跑还糟：下游瞬间被挤满开始超时，超时又触发重试，重试把到达量抬得更高；账单比预想的高出一截；更要命的是有几路悄悄失败了，最后拼出来的总结果缺了一块，却谁也没发现，看上去还挺完整。你想限一限，可又不知道该限几路、按什么定。明明是「让它们一起干」，怎么反而更慢、更贵、更不可信了？

## 破误解

**不是「开得越多越快」，是把「同时能跑几路」当成了没有代价的旋钮；扇出能成立的前提是子任务真的彼此独立，而 workers 上限的作用是给「同时进行」画一道硬边界，不是给速度调个参数。**

先把几个词说清。扇出（fan-out），是把一个大任务拆成多路子任务一起处理；扇入（fan-in），是把这些子任务的结果收拢回一处；归约（reduce），是按约定把多份结果合成一份，并顺带判断齐没齐、缺哪路。workers 在这里指工作槽位，也就是允许同时执行的路数上限。并发（concurrency）说的是「同一段时间里有多个活儿在推进」，并行（parallelism）说的是「同一时刻真有多路在跑」，对这篇而言要紧的是后者被卡在几个槽位里。很多人一听到「并行」就默认收益随路数线性增长，其实有三处先要过问。

第一处是独立性。拆分不是把清单切成几段就完事：如果几路要读写同一份可变状态，它们会互相覆盖；如果乙路的输入依赖甲路的输出，它们根本没法同时开始；如果最后必须合成一份总账，那么「怎么合、缺了怎么办」就得先定好。判断能不能拆，问三句就够：是否共享会被修改的状态、是否依赖彼此的中间结果、是否要按固定口径合并。这三问过不了，硬拆出来的并行只是把顺序执行的 bug 搬到了更难查的地方，见 [任务拆解的粒度](./k119-task-decomposition.md) 与 [共享状态与冲突](./k120-shared-state.md)；至于什么时候值得动用多个智能体，而不是把一个智能体的循环开得更快，见 [何时该用多智能体](./k117-when-multi-agent.md) 和 [多智能体协作模式](./k118-multi-patterns.md)。

第二处是上限为什么必须存在。同时跑的路数会同时啃四样东西：下游的连接数与限流额度、每一路都要带的上下文所占的内存与计费、某一路失败后被重试放大的倍数、以及归约时等待最慢那一路的尾延迟（tail latency，整体要等最慢的一路回来才能收工）。所以槽位不是「调性能的参数」，是把这四样开销封在一道边界里的闸门，见 [四重预算](./k103-four-budgets.md)。第三处最容易被忽略：真正的压力是「外部同时在跑多少个任务」乘以「每个任务内部扇出几路」。服务端允许五个任务同时进来，每个扇出八路，就是四十路一起打向下游；只给单个任务设八路上限、却不对相乘后的总量封顶，等于没设，见 [高并发与并发上限](./k115-concurrency.md)。

## 生活类比

把它想成办事大厅开窗口。一位市民要办十二项手续，一个人排队挨个办，慢是慢，但清清楚楚。大厅为了快，把十二项拆开、每个窗口办一项，一起办——这是扇出。可大厅物理上只有三个柜台（workers 上限），多出来的只能在候办区排队，这叫按槽放行。这时候有人提议「把柜台开到十二个不就完了吗」，问题就来了：所有窗口共用一个盖章台，十二个人同时挤过去，章盖不过来，队伍反而卡住；每开一个窗口都得领一套备用表格和零钱，开得多、备得多，成本跟着涨；有位窗口办错了要重办，重办又占着柜台，后面的人更堵；最后十二张回执要合成一份办结单，要是其中一张没交回来，合成时没核对，办结单看着整整齐齐，其实少了一项。

对应关系可以逐条对上。「十二项手续能不能各办各的」，就是独立性判定：有些手续本来就得先拿到前一项的编号才能办，硬拆只会让人白跑。「只有三个柜台」，就是 workers 上限，它决定同一时刻真正动手的路数，其余的进队列（queue，先来先排的等待区）。「共用的盖章台」是共享下游，路数一多先在这里打满，见 [熔断与 kill switch](./k104-circuit-breaker.md) 里「下游明显不健康时先别再送流量」的判断。「每开一窗口领一套东西」是单路开销，和 [按成功任务核算成本](./k096-metrics-cost.md) 里「别只盯单价、要看一共跑了多少路」是同一回事。「办错重办又占柜台」是失败被重试放大，见 [重试退避与抖动](./k108-retry-backoff.md)。「十二张回执合成一份办结单」是归约，而「少一张没被发现」正是最贵的坑：结果必须按原来的编号收齐，缺哪一路要显式看得出来，见 [归约槽与结果合并](./k144-reducer-slot.md) 与 [数字与事实的完整性](./k124-number-integrity.md)。这个比喻还点出一层：柜台数不是越多越好，它由盖章台、备料、大厅面积一起决定；同理，workers 该设几路，得看四样资源里最先顶不住的那一样。

## 自绘示意图

:::figure 一次受控扇出的完整顺序
@flow
判定可拆性|子任务入队|按上限放行|各自执行留痕|归约汇总
:::

五格里最容易被跳过的是第一格和第五格。「判定可拆性」要在动手之前做，它决定后面几格有没有意义；「归约汇总」不是简单地把返回值拼起来，而是按原编号收齐、把缺失和失败显式列出来。中间三格才是有上限的调度：入队、按空槽放行、各自执行。把第一格跳过，并行会放大顺序执行时看不出的冲突；把第五格跳过，就会得到一份「看着完整、其实缺了一块」的结果。

:::figure 设 workers 上限时要盯的五处
@stack
下游承受::连接数与限流，路数一多先在这里打满
单路开销::每路都带上下文，内存与计费随路数上涨
失败放大::一路超时触发重试，多路一起重试更猛
归约完整::结果按原编号收齐，缺一路必须看得出
内外相乘::外部任务数乘内部扇出，才是真在跑的量
:::

前三条是「为什么要封顶」：它们都会随路数一起涨，而且涨到某处会突然变陡。第四条是「封顶之后还要补什么」：上限管的是同时进行，管不了结果齐不齐。第五条最隐蔽，也是最该写进配置的一条——单个任务的上限和全局的上限是两回事，五个任务各扇出八路，真正压向下游的是四十路。只按单任务设线，另五个任务的口子一直开着，见 [四重预算](./k103-four-budgets.md)。

:::figure 放开跑与按槽跑的差别
@compare
不限路数全放开::瞬间打满下游|失败被重试放大|缺结果难察觉
设上限按槽放行::排队可控|总量封顶|归约能查缺
:::

左边并不是「更先进的并行」，它只是把队列和闸门都拆了：顺风顺水时确实最快，一旦下游吃紧或有一路失败，就没有任何一处能收得住。右边多了一层排队，换来的是总量可预期、事后能查缺。二者的差距不在速度公式，而在「出问题那一刻有没有边界」。

## 层层追问

:::ask 那如果把 workers 调大一点，是不是就按比例变快？
:::

不会，而且这正是最容易花冤枉钱的一处误判。整体耗时至少被三件事压着：最慢那一路总要跑完，归约得等它回来；共享的盖章台只有那么快，多路一起挤过去会排队；每多开一路就多一份准备与收尾开销。所以「路数翻倍、耗时减半」只在很理想的一段里成立，过了某一点，加槽位几乎只增加账单不减少等待。更要紧的是别把它和「外部同时进来多少请求」混为一谈：内部扇出调大，会把服务端并发一起放大，见 [高并发与并发上限](./k115-concurrency.md)；两边相乘才是真正在跑的量，见 [四重预算](./k103-four-budgets.md)。

再往下一层，是「该按谁设上限」。稳妥的做法是设一道全局槽位：无论外面来了几个任务、每个任务想扇出几路，先算出「外部任务数 × 每任务扇出」想要的量，再被这道全局槽位封顶，多出来的排队。这样单个任务不必知道别人在跑什么，总量却始终有边界。它和 [熔断与 kill switch](./k104-circuit-breaker.md) 是两道不同的闸：前者按「同时几路」封顶，后者按「下游还健康不健康」切断，触发条件不一样，别互相顶替。至于一个任务到底值不值得拆、拆到多细，仍要回到 [任务拆解的粒度](./k119-task-decomposition.md)；拆完每路要不要各自带完整上下文，则和 [共享状态与冲突](./k120-shared-state.md) 有关。把「先量瓶颈、再调槽位」写进可查的配置，还能避免有人凭感觉一路把数字往上抬，见 [成本优化与上线检查清单](./k116-cost-checklist.md)。

:::ask 那如果有一路失败了，或者干脆一直不返回，整批怎么办？
:::

先说结论：不能「少一路也照样输出」。一路失败、一路超时不返回，是并行里的常态而不是例外，所以归约必须承担两件事——按原编号收齐、把缺失与失败显式列出来。若只按「谁先回来就先拼谁」，结果顺序会随调度漂移，缺了哪一路也看不出来，见 [归约槽与结果合并](./k144-reducer-slot.md) 与 [数字与事实的完整性](./k124-number-integrity.md)。一直不返回的那一路尤其危险：它会一直占着一个槽位，后面的任务全堵在队列里，所以每路都得有超时与兜底，到点就按「这一路失败」收尾并释放槽位，见 [超时与兜底](./k109-timeout-fallback.md)；整体还要有轮数与终止条件，别让等待无限拖下去，见 [四个终止条件](./k028-stop-conditions.md)。

再追一层，是「失败之后怎么处理」这个更容易翻车的点。最常见的错误是把失败一律当成「需要重试」，多路一起重试，恰好凑成失败被放大的形状，见 [生产失败模式清单](./k150-failure-modes.md)；正确做法是重试带退避与抖动、按失败类型区分该不该重试，见 [重试退避与抖动](./k108-retry-backoff.md)，下游已经明显不健康时干脆停止送流量，见 [熔断与 kill switch](./k104-circuit-breaker.md)。还有一处并行特有的麻烦：几路若共享一份可变状态，交叉读写会串数据，这种错偶发到难以复现，见 [共享状态与冲突](./k120-shared-state.md)。所以「部分成功」要能被如实表达：哪几路成了、哪几路失败、哪几路没返回，各自留痕，而不是把它们抹平成一句「已完成」，见 [Trace 该记什么](./k094-trace-fields.md)。把这些取舍讲清楚，恰恰是项目表达里最见功夫的地方——面试官追问「为什么不是开更多路一起跑」时，能答出独立性、相乘后的总量、尾延迟与失败放大，比只报一个漂亮的速度数字更有说服力，见 [取舍怎么讲清](./k123-tradeoffs.md) 与 [项目怎么讲](./k126-project-pitch.md)。

## 可运行代码与逐行解释

下面这段只用 Python 内置功能，做一个确定性的调度模拟器：用逻辑时钟（logical clock，不靠真实时间、按步数推进的模拟时间）逐拍推进，每一拍先把空槽补上子任务，再推进一个时间单位、收尾到点的那些；借此验证「任意时刻在跑的路数不超过上限」「全放开时的耗时被最慢一路钉住」「路数翻倍并不带来线性提速」「外部并发与内部扇出相乘后要被全局封顶」「归约能查出缺失与失败」。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
from collections import deque


def make_jobs(specs):
    """specs 为 (名称, 耗时, 是否成功, 是否丢弃)；后两项可省略。"""
    out = []
    for i, s in enumerate(specs):
        name, cost = s[0], s[1]
        ok = s[2] if len(s) > 2 else True
        drop = s[3] if len(s) > 3 else False
        out.append({"id": i, "name": name, "cost": cost,
                    "ok": ok, "drop": drop})
    return out


def base_jobs():
    """六路子任务，耗时固定，全部成功；最慢的一路是四拍。"""
    return make_jobs([
        ("甲", 2), ("乙", 3), ("丙", 1),
        ("丁", 4), ("戊", 2), ("己", 3),
    ])


def schedule(jobs, workers):
    """按 workers 上限放行，返回 (总拍数, 峰值并发, 结果表, 每拍在跑数)。"""
    pending = deque(jobs)
    running = []
    results = {}
    clock = 0
    peak = 0
    trace = []
    while pending or running:
        while pending and len(running) < workers:
            job = pending.popleft()
            running.append([job["cost"], job])
        now = len(running)
        peak = max(peak, now)
        trace.append(now)
        clock += 1
        done = []
        still = []
        for left, job in running:
            left -= 1
            if left <= 0:
                done.append(job)
            else:
                still.append([left, job])
        running = still
        for job in done:
            if not job["drop"]:
                results[job["id"]] = {"ok": job["ok"], "name": job["name"]}
    return clock, peak, results, trace


def effective_slots(external, fanout, cap):
    """外部任务数乘内部扇出，才是想要的量；再被全局槽位封顶。"""
    wanted = external * fanout
    return wanted, min(wanted, cap)


def reduce_results(results, jobs):
    """按原编号收齐可用结果；缺失与失败分别显式列出，不静默补齐。"""
    missing = [j["id"] for j in jobs if j["id"] not in results]
    failed = [i for i, r in results.items() if not r["ok"]]
    ordered = [results[j["id"]]["name"] for j in jobs
               if j["id"] in results and results[j["id"]]["ok"]]
    return {"ordered": ordered, "missing": missing, "failed": failed,
            "complete": not missing and not failed}


def main():
    checks = []

    t1, p1, r1, _ = schedule(base_jobs(), 1)
    t2, p2, r2, trace2 = schedule(base_jobs(), 2)
    tall, pall, rall, _ = schedule(base_jobs(), 6)

    checks.append(("单路等于串行总耗时", t1 == 15))
    checks.append(("单路峰值恰为一", p1 == 1))
    checks.append(("全放开峰值等于任务数", pall == 6))
    checks.append(("全放开耗时被最慢一路钉住", tall == 4))
    checks.append(("两路峰值恰为上限", p2 == 2))
    checks.append(("两路耗时可手工推算", t2 == 8))
    checks.append(("两路全程不超上限", all(n <= 2 for n in trace2)))
    checks.append(("两路快于串行", t2 < t1))
    checks.append(("全放开快于两路", tall < t2))
    checks.append(("两路耗时也受最慢一路约束", t2 >= 4))
    checks.append(("槽位翻倍没带来线性提速", t1 / tall < 6))
    checks.append(("三种上限结果都收齐", len(r1) == len(r2) == len(rall) == 6))

    checks.append(("相乘后想要的量被算出", effective_slots(5, 8, 12)[0] == 40))
    checks.append(("全局槽位封住相乘后的量", effective_slots(5, 8, 12) == (40, 12)))
    checks.append(("未超限时按乘积放行", effective_slots(2, 3, 12) == (6, 6)))

    partial = make_jobs([
        ("甲", 1, True), ("乙", 2, False),
        ("丙", 1, True, True), ("丁", 1, True),
    ])
    _, _, res, _ = schedule(partial, 2)
    summary = reduce_results(res, partial)
    checks.append(("被丢弃那路确实没进结果", len(res) == 3))
    checks.append(("归约查出缺失一路", summary["missing"] == [2]))
    checks.append(("归约查出失败一路", summary["failed"] == [1]))
    checks.append(("可用结果按原编号收拢", summary["ordered"] == ["甲", "丁"]))
    checks.append(("部分成功不被标成完整", summary["complete"] is False))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `make_jobs` 把一组规格转成带稳定 `id` 的子任务字典。规格写成可变长度元组，后两项省略时默认「成功、不丢弃」，这样同一套数据既能表达全成功的基线，也能构造「某一路失败」「某一路不返回」。`id` 用 `enumerate` 的顺序号，正是后面归约要按它收齐的那个编号。
2. `base_jobs` 是六路固定耗时的构造数据：2、3、1、4、2、3，总和十五、最慢四拍。全无随机数，所以「单路耗时 15」「两路耗时 8」「全放开耗时 4」都能手工推算核对；它们是为讲清调度性质造的教学例子，不是任何真实任务的采样。
3. `schedule` 是整段最要紧的一处。外层 `while pending or running` 表示「还有没放行的、或还有在跑的」就继续；内层 `while pending and len(running) < workers` 是那道闸门——只有出现空槽才从队列头取一个放进 `running`。这一行就是 workers 上限的全部实现，也是「同时在跑的路数」唯一被约束的地方。
4. 每拍先记 `now = len(running)` 并追加到 `trace`、更新 `peak`，再 `clock += 1` 推进逻辑时钟，然后遍历 `running` 把剩余耗时减一：`left <= 0` 的进 `done`，其余留在 `still`。用 `<= 0` 而不是 `== 0`，是为了即使构造数据里出现零耗时也不会卡住循环。全程不真的起线程，因为要验证的正是「任意一拍在跑几路」，真实并发给不出可手算、可复现的轨迹。
5. 收尾时 `if not job["drop"]` 才写进 `results`：被标记为丢弃的那一路不产生结果，用来模拟「超时不返回」。失败那一路照常写入、但 `ok` 为假——这样归约能区分「没回来」和「回来了但结论失败」，两者处理方式并不相同，见 [生产失败模式清单](./k150-failure-modes.md)。
6. `effective_slots` 把「外部任务数 × 内部扇出」先算成想要的量，再用全局 `cap` 封顶。它对应追问里那句：五个任务各扇出八路想要四十个槽，全局只给十二个，就只能放行十二个，其余排队。把这道相乘写进代码，是为了提醒上限要按总量设，而不是每个任务各设各的，见 [高并发与并发上限](./k115-concurrency.md)。
7. `reduce_results` 做三件不能省的事：`missing` 按原编号找出没进结果的那几路，`failed` 找出结论失败的几路，`ordered` 只按 `jobs` 的原始顺序挑出可用结果——刻意不按完成顺序，因为完成顺序会随调度漂移。`complete` 只有「既没缺、也没败」才为真，缺一路就如实报缺，绝不静默补齐，见 [归约槽与结果合并](./k144-reducer-slot.md)。
8. `main` 用同一组 `base_jobs` 分别以 1、2、6 路上限跑三遍，断言单路等于串行总和、全放开耗时被最慢四拍钉住、两路峰值为 2 且每拍不超 2、两路比串行快但也没快到六倍（这道断言专门验「非线性提速」）；再用 `effective_slots` 验相乘与全局封顶；最后构造「乙失败、丙不返回」的四路数据，断言归约能把缺失、失败、可用结果、整体不完整四件事分别说清。结尾统一统计通过项数，任何一条性质被破坏都以非零状态退出。

如实说明一句：这里用逻辑时钟代替真实计时、用带 `drop` 标记的字典代替超时不返回、用固定耗时代替真实子任务，全是为了让整条链路不联网、不装第三方包、不依赖任何账号就能独立跑通并手算核对。它演示的是上限怎么约束「同时几路」、相乘后的总量、以及归约如何查缺，不是任何具体并发库或调度框架的用法；文中不涉及任何真实耗时、报价或运行记录，也不据此推断真实环境的表现。

## 踩坑与边界

- **不判独立性就硬拆**：现象是几路同时读写同一份状态，结果互相覆盖，偶发到难以复现 → 原因是有依赖或有共享可变状态的子任务被当成彼此独立 → 动手前按「是否共享状态、是否依赖彼此输出、是否要按固定口径合并」三问过一遍，见 [任务拆解的粒度](./k119-task-decomposition.md) 与 [共享状态与冲突](./k120-shared-state.md)。
- **上限只按单任务设**：现象是每个任务都规规矩矩扇出八路，下游却被瞬间打满开始超时 → 原因是外部并发与内部扇出相乘，真正压过去的是几十路 → 先算「外部任务数 × 每任务扇出」，再按一道全局槽位封顶，见 [高并发与并发上限](./k115-concurrency.md) 与 [四重预算](./k103-four-budgets.md)。
- **一路失败被静默吞掉**：现象是总结果缺了一块却照样输出，看上去完整，事后才发现少一路 → 原因是归约只按完成顺序拼接，没按原编号查缺 → 按稳定编号收齐，缺失与失败分别显式列出，见 [归约槽与结果合并](./k144-reducer-slot.md) 与 [数字与事实的完整性](./k124-number-integrity.md)。
- **超时与多路重试互相放大**：现象是一路变慢触发重试，多路一起重试把到达量抬高，下游更慢 → 原因是把失败一律当成需要重试、且没有超时释放槽位 → 每路设超时与兜底、重试带退避与抖动、必要时停止送流量，见 [超时与兜底](./k109-timeout-fallback.md)、[重试退避与抖动](./k108-retry-backoff.md) 与 [熔断与 kill switch](./k104-circuit-breaker.md)。
- **盲目调大 workers 求快**：现象是槽位翻倍耗时几乎没降，账单先涨一截 → 原因是整体被最慢一路、共享下游与单路开销一起约束 → 先量出最先顶不住的那处再调，按延迟与成本一起权衡，见 [取舍怎么讲清](./k123-tradeoffs.md) 与 [按成功任务核算成本](./k096-metrics-cost.md)。

还要分清两组容易混说的边界。一组是「扇出并行」与「服务端并发」：前者是一个任务内部拆出几路，后者是同时进来多少个任务，两者相乘才是真正在跑的量，见 [高并发与并发上限](./k115-concurrency.md)。另一组是「封顶」与「查缺」：全局槽位管的是同时进行的上限，管不了结果齐不齐；按编号归约管的是收得齐不齐，也拦不住下游被打满，谁都替代不了谁。至于「停放量」与「熔断」也不是一回事：前者按同时在跑几路封顶，后者按下游健康状态切断，见 [熔断与 kill switch](./k104-circuit-breaker.md)。每一路各自留下的痕迹该记哪些字段，见 [Trace 该记什么](./k094-trace-fields.md)；轮数与整体何时收工，见 [四个终止条件](./k028-stop-conditions.md)。把「为什么是这几路、为什么不全放开」讲成有边界、有代价的取舍，而不是一句「并行更快」，正是 [项目怎么讲](./k126-project-pitch.md) 和 [三个项目怎么选](./k122-three-projects.md) 里最该练的表达。

## 三句话小结

扇出并行与 workers 上限，是先判断子任务能不能彼此独立地拆开，再给「同时跑几路」设一道按相乘后总量计算的全局槽位，最后按原编号把结果收齐并如实报出缺失与失败。

关键做法是动手前过独立性三问、让队列只在出现空槽时放行、给每路设超时与带退避的重试、归约时按稳定编号收拢且不静默补齐，并把槽位与阈值写进可查的配置。

当子任务之间互相依赖、共享会被修改的状态，或总共只有两三路且拆开反而更慢时，不必硬套扇出；但只要一次要同时处理很多彼此独立的部分，那道上限和那次查缺就不该缺席。

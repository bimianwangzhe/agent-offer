# 四个终止条件

## 一、场景提问

你写了个能自己查资料、自己决定下一步调哪个工具的小助手（Agent，智能体：一种不必按固定脚本走、能反复「决策—行动—观察」直到把事情办完的程序）。本地挑了几条用例，都顺顺当当地收了尾，于是放心地让它去处理真实任务。结果有个稍绕一点的请求把它卡住了：它反复检索同一份材料、换个说法再查一遍、查完又觉得「还差一点」继续查，控制台刷个没完；账单上的调用次数一轮一轮往上叠；你想让它停，却发现整个循环里只有一句「模型说停就停」，既没有轮数上限，也没有任何花费上的封顶，更没有留给你手动叫停的入口，最后只能去杀进程。更别扭的是另一类任务：明明已经可以给出答案了，它却因为「再确认一次更稳妥」又多绕了七八轮。一个循环，怎么连「怎么结束」都这么难？

## 二、破误解

**不是模型判断力变差了，是把「何时停」整件事交给了模型的一句话，而代码里没有任何一条自己能拍板的退出规则。**

先把最容易混的两层分开。模型在回复里写「我认为任务已完成」，这是一句**软判断**：它只是文本，模型可能猜错、可能被上一轮的工具结果带偏、也可能为了显得谨慎而习惯性地再查一次，而且这句话本身还要靠你写解析代码去认。循环必须退出，这是一条**硬判断**：它必须由代码在某个明确的位置、用某个明确的数值或信号独立作出，不依赖模型那一刻的心情。把两者混为一谈，就等于把刹车装在了乘客嘴里——他喊不喊、喊得准不准，全凭运气。真正的做法是给循环装上四条各管一件事的硬规则，让「停」这件事在代码里有四个独立的落点。

第一条是**完成信号**：模型给出了最终答案、并且这一轮不再请求任何工具。它是唯一一条「达成型」退出，代表事情真的办成了。第二条是**步数封顶**：不管模型想不想继续，轮数一到某个硬上限就停，专治反复打转与绕圈。第三条是**预算封顶**：累计花掉的 token（词元，模型读写文本时计数与计费的基本单位，一段中文往往对应好几个）、累计耗时、累计金额，任何一个越过事先写好的线就停。第四条是**被动中止**：外部有人叫停、或者撞上不可恢复的错误，立刻刹车。后三条都不是「做完了」，而是「不能再做下去了」，属于保护型退出；把它们和「完成」分开记，是后面一切复盘的前提——否则一份被掐断的轨迹和一份真正做完的轨迹，在日志里长得一模一样。

顺序也不是随便排的。四条规则得有一个固定的优先级：被动中止最优先，其次是与预算、步数这类封顶，最后才轮到模型给出的完成信号。理由很实在：只有在没有被任何上限截断、没有被任何人叫停的前提下，「模型说完成了」才等价于「任务真做成了」。反过来，如果预算刚好耗尽、用户又刚好点了取消，这时候即便模型也写了「完成」，结果也只能算中止，不能算成功。还有一处细节常被忽略：这些检查要集中在「动手之前」做一次，而不是「做完之后再回头看」。做完再查，等于允许它多执行一步、多花一次钱、甚至多产生一次不可撤销的副作用；而像发通知、下单这类动作，多走一步就收不回来了。所以一轮循环的正确形态是：先集中判定「这一轮还准不准开始」，准了才去取决策、执行、记账，最后才判断是不是该以「完成」收尾。这套「决策—行动—观察」的基本形状，在 [决策—行动—观察闭环](./k023-decision-loop.md) 里有展开；而循环每一步该把哪些累计量记下来、才够支撑这四条判定，则和 [循环状态该存什么](./k027-loop-state.md) 是同一件事。

最后要说清「终止」不等于「跳出循环」。一次合格的终止得能回答四个问题：停在第几步、因为哪条规则停、累计消耗了多少、这一路的轨迹留没留痕。答不上来，就没法区分成功与被掐断，也没法把「为什么这轮没做成」讲清楚。判断一个程序算不算真的 Agent，看的就是它有没有这种自己决定「还要不要再跑一轮」的能力，这一点在 [Agent 的唯一判据](./k021-agent-criterion.md) 里说得很直白；而一旦有了这个能力，「谁来兜底让它停」就成了绕不开的设计问题，而不是可以后补的小细节。

## 三、生活类比

把它想成在厨房用燃气灶炖一锅汤，你一边炖一边还得盯着别的事。这锅汤有四种「关火」的理由，缺一样都不踏实。

汤炖到位了，你尝一口觉得咸淡正好，主动把火关掉——这是完成信号，是唯一一种「因为做好了所以停」。灶台边上另有个机械定时器，说好最多炖三十分钟，时间一到「咔」一声就断气，不管汤这时候是什么状态——这是步数封顶，它压根不看汤的心情。燃气表上只剩最后一格、或者今天买菜的钱就剩这么多，一看快见底了，也得提前关火——这是预算封顶，盯的是累计消耗，而且是**在火还烧着之前**就根据「再烧这一会儿要花多少」提前算出来的。最后一种最不讲道理：油烟报警器突然响了，或者家里人隔着客厅喊一声「别炖了快关火」，你必须立刻关，管它定时器到没到点、汤炖没炖好——这是被动中止，优先级最高。

对应关系可以逐条对上：机械定时器是硬件，不读汤的味道，正对应「硬判断写在代码里、不信模型那句自述」；燃气表与买菜钱是两类不同的累计量，对应 token、耗时、金额可以各自设线，任意一条越线都得停；报警器与那声喊，对应外部叫停和不可恢复错误，它们来自循环之外，必须由循环主动去查一个标志位才能感知，不会自己跳进来。这个比喻还点出了两处最容易被漏掉的细节。第一，报警器一响，其他三条都不用再讨论了——这就是优先级必须是代码里写死的固定顺序，而不是「看谁先到」，否则同时满足时结果全凭偶然。第二，关火之后最好顺手在便签上记一笔「今天这锅是到点关的，还是报警器关的，用了多少气」；不记，下回想复盘「为什么这锅没炖成」就说不清了，对应「终止原因、累计消耗、轨迹」必须落成可查的记录，而不是一个悄悄跳出的 `break`。顺带一提，那句「再确认一次更稳妥」的犹豫，其实就是人在接近定时器时想再尝一口——可以给它一次机会，但得规定这一口只能尝、不许再加料，这正是后面追问里要处理的收口问题。

## 四、自绘示意图

:::figure 一轮循环里四道出口的检查顺序
@flow
进入本轮|查中止信号|查步数与预算|取一个决策|判定终止并留痕
:::

这五格的关键不在画了什么，而在**顺序**：「查中止信号」和「查步数与预算」都排在「取一个决策」之前。也就是说，这一轮准不准开始，先由三条保护型规则拍板；只有它们都放行，才轮到去问模型下一步想干什么。把检查放到执行之后，就等于默认允许它多做一步，前面说的副作用问题就是从这儿漏进来的。

:::figure 四个终止条件各管一件事
@stack
完成信号::模型给出最终答案且不再请求工具，属于达成型退出
步数封顶::轮数到达硬上限就停，专治反复打转与绕圈
预算封顶::token 与耗时越过阈值即停，动手前先预测开销
被动中止::外部叫停或不可恢复错误，优先级最高、立即刹车
:::

四格里最容易被省掉的是「预算封顶」。很多人只设一个轮数上限就觉得够了，可每一轮的开销并不相同：一次轻飘飘的查询和一次拉回长文的工具调用，花掉的 token 差得很远，光数轮数根本挡不住花费悄悄涨上去。反过来，只盯钱不数轮数也不行——有些动作不怎么花钱，却会没完没了地绕。两样都留着，才叫封顶。

:::figure 软判断与硬规则的差别
@compare
只听模型说停::可能反复绕圈|花费没有上限|叫停没有入口
四条硬规则兜住::到点必停|越线提前刹车|原因可留痕复盘
:::

左边是「把刹车交给一句话」的朴素写法，顺风顺水时最省事；右边是把退出拆成四条独立规则、并给它们排好优先级。二者的差距，全在「它停不下来的时候，你收不收得住」以及「停下来之后，你讲不讲得清」。

## 五、层层追问

:::ask 那如果模型每次都「差一点点就快完成了」，步数封顶会不会把本来能做成的任务误杀？
:::

会，而且这是硬上限最真实的代价，不能装作没发生。要点在于：**保护线不是调度策略**。步数、预算这类线是用来兜住失控的，不是用来规定「一个正常任务该跑几轮」的；所以它们应当按任务类型分档设置，查资料的、要写长文的、要多轮试错的，不该共用一个数字，否则要么误杀要么形同虚设。更实用的做法是给「逼近上限」单独留一个收尾轮：当剩余额度只够再走一步时，不是冷冰冰地截断，而是明确告诉循环「这是最后一轮，只能交答案、交不出来就如实说明卡在哪」。这样即便没能真正完成，用户拿到的也是一句可解释的交代，而不是一段戛然而止的空白。但这里立刻冒出第二层问题：模型会不会把这次「收尾轮」又当成一次普通轮，照样发出工具调用、把额度耗光？所以收尾轮必须**收窄动作集合**——这一轮只允许输出最终答案或说明未完成，禁止再发起任何工具调用，最好在代码里直接把可用工具清单清空，而不是在提示里求它别调。换句话说，「再给一次机会」这件事本身也得是一条硬规则，不能又退化成一句软判断。收尾轮里那种「回头看看走到哪了、还差什么」的自查，和 [反思与自我修正](./k026-reflection.md) 是同一种动作；而「逼近上限时能立刻交出一份说得清的现状」，靠的是每一步都留了可回放的记录，见 [检查点与轨迹回放](./k030-checkpoint-replay.md)。至于怎么评价「过程合理但没做成」这类结果，可以对照 [结果评测与轨迹评测](./k089-trajectory-eval.md)。

:::ask 那如果四个条件同时满足呢，比如预算刚好耗尽、模型也刚好说完成、用户又刚好点了取消？
:::

这正是必须先定优先级的原因，而且答案不能是「看谁先跑到」那种随缘的结果。四条规则要在**代码里排成固定的一条判定链**：先查外部中止与不可恢复错误，再查步数与预算这类封顶，最后才认模型给出的完成信号。之所以把「完成」排在最后，是因为它是一句软判断，只有在没有被动中止、也没有被任何上限截断的前提下，才配得上「任务做成了」这个结论；只要前面任一保护规则命中，这轮就得记成中止或截断，哪怕模型那句话里写着「已完成」。把这些检查集中在「动手之前」一次性做完还有个好处：同一轮里不会出现在不同位置各查一半、查到一半状态又变了的情况，判定依据始终是本轮开始时那一帧快照。

被动中止还有两个容易被漏掉的性质。一是它通常来自循环之外——用户点了取消、看门的程序拉了闸、某个依赖彻底挂了——循环不会自动感知，必须每一轮主动去读一个标志位或状态；把它写成「模型在回复里提到取消才算」就完全错了。二是中止动作要能重复触发而不产生二次破坏：用户连点两次取消、或者取消信号和超时信号同时到，不该让清理逻辑执行两遍、把记录写重，这和 [幂等落盘](./k107-idempotent-persist.md) 里「同一动作只留一次结果」是同一套思路；真要中断一个长任务，怎么把现场保存好、下次接着跑，则属于 [优雅中断与断点恢复](./k110-graceful-resume.md)。最后，无论按哪条规则停，累计消耗都得当场结算清楚，事后才能回答「这轮到底算不算成功、花了多少」，这部分口径在 [按成功任务核算成本](./k096-metrics-cost.md) 里讲得更细；而给预算、轮数、时间分别设线并统一收口的思路，和 [四重预算](./k103-four-budgets.md)、[熔断与紧急开关](./k104-circuit-breaker.md) 一脉相承，需要人来判断要不要继续时则接上 [人在回路与高风险确认](./k102-human-in-loop.md)。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，用一串确定性的「决策桩」模拟模型每一轮想干什么，完整演示四个终止条件的判定顺序、优先级与留痕。没有真实模型、没有计时、没有网络：每一步的 token 与耗时都是写死的整数，因此每条性质都能手工推算、结果完全可复现。结尾用一组断言逐条验证，复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
import json
from dataclasses import dataclass

TERMINATIONS = ("DONE", "STEP_LIMIT", "BUDGET", "ABORT")


def tool_call(cost=10, seconds=1):
    """构造一次「还要继续调工具」的决策桩。"""
    return {"kind": "tool", "cost": cost, "seconds": seconds}


def final_answer(cost=5, seconds=1):
    """构造一次「给出最终答案、不再请求工具」的决策桩。"""
    return {"kind": "final", "cost": cost, "seconds": seconds}


@dataclass
class Limits:
    """三条保护线：轮数、token、虚拟耗时，全部是先写死再看。"""
    max_steps: int
    max_tokens: int
    max_seconds: int


@dataclass
class Outcome:
    """一次终止的完整交代：原因、累计量、逐轮轨迹。"""
    reason: str
    steps: int
    tokens: int
    seconds: int
    trace: list

    def as_json(self):
        return json.dumps({
            "reason": self.reason,
            "steps": self.steps,
            "tokens": self.tokens,
            "seconds": self.seconds,
            "trace": self.trace,
        }, ensure_ascii=False, sort_keys=True)


def run_loop(script, limits, abort_at=None, fatal_at=None):
    """带四个终止条件的循环，全部由确定性决策桩驱动。"""
    steps = tokens = seconds = 0
    trace = []
    for i, decision in enumerate(script):
        # 条件四：外部中止或不可恢复错误，优先级最高，动手前先查
        if abort_at == i or fatal_at == i:
            trace.append("ABORT:external" if abort_at == i else "ABORT:fatal")
            return Outcome("ABORT", steps, tokens, seconds, trace)
        # 条件二：步数封顶
        if steps >= limits.max_steps:
            return Outcome("STEP_LIMIT", steps, tokens, seconds, trace)
        # 条件三：预算封顶，用「本步开销」提前预测，不透支
        if (tokens + decision["cost"] > limits.max_tokens
                or seconds + decision["seconds"] > limits.max_seconds):
            return Outcome("BUDGET", steps, tokens, seconds, trace)
        # 三条保护线都放行，才真正执行这一步并记账
        steps += 1
        tokens += decision["cost"]
        seconds += decision["seconds"]
        trace.append(decision["kind"])
        # 条件一：模型给出最终答案，属于达成型退出
        if decision["kind"] == "final":
            return Outcome("DONE", steps, tokens, seconds, trace)
    # 四个条件都没兜住属于设计缺陷，正常参数下不应走到这里
    return Outcome("NO_TERMINATION", steps, tokens, seconds, trace)


def main():
    checks = []
    long_script = [tool_call(5) for _ in range(20)]

    # 场景一：正常完成
    done = run_loop(
        [tool_call(10), tool_call(15), final_answer(5)],
        Limits(max_steps=10, max_tokens=100, max_seconds=10),
    )
    checks.append(("给出最终答案时以 DONE 终止", done.reason == "DONE"))
    checks.append(("完成后不多跑一轮", done.steps == 3))
    checks.append(("完成累计 token 为 30", done.tokens == 30))
    checks.append(("轨迹逐轮留痕", done.trace == ["tool", "tool", "final"]))

    # 场景二：步数封顶
    capped = run_loop(long_script, Limits(3, 1000, 1000))
    checks.append(("轮数到上限以 STEP_LIMIT 终止", capped.reason == "STEP_LIMIT"))
    checks.append(("一步都不多做", capped.steps == 3))
    checks.append(("封顶后不继续消耗", capped.tokens == 15))

    # 场景三：预算封顶（token 与耗时各算一次）
    budget_tokens = run_loop(
        [tool_call(40), tool_call(40), final_answer(5)],
        Limits(10, 70, 1000),
    )
    checks.append(("token 越线以 BUDGET 终止", budget_tokens.reason == "BUDGET"))
    checks.append(("越线那步根本没执行", budget_tokens.steps == 1))
    checks.append(("预算判定用预测值不透支", budget_tokens.tokens == 40))

    budget_time = run_loop(
        [tool_call(5, seconds=6), tool_call(5, seconds=6), final_answer(5)],
        Limits(10, 1000, 8),
    )
    checks.append(("虚拟耗时越线也归预算终止", budget_time.reason == "BUDGET"))
    checks.append(("时间预算提前一步刹车", budget_time.steps == 1))

    # 场景四：被动中止的两个来源
    aborted = run_loop(long_script, Limits(10, 1000, 1000), abort_at=2)
    fatal = run_loop(long_script, Limits(10, 1000, 1000), fatal_at=4)
    checks.append(("外部叫停以 ABORT 终止", aborted.reason == "ABORT"))
    checks.append(("不可恢复错误也以 ABORT 终止", fatal.reason == "ABORT"))
    checks.append(("中止后不再继续", aborted.steps == 2))
    checks.append(("中止来源被留痕", aborted.trace[-1] == "ABORT:external"))
    checks.append(("错误来源被留痕", fatal.trace[-1] == "ABORT:fatal"))

    # 优先级：中止最优先，压过同时命中的步数与预算
    priority = run_loop(long_script, Limits(1, 1, 1), abort_at=0)
    checks.append(("中止优先于步数与预算", priority.reason == "ABORT"))

    # 总检
    results = [done, capped, budget_tokens, budget_time, aborted, fatal, priority]
    checks.append(("所有结果都落在四个终止条件内",
                   all(r.reason in TERMINATIONS for r in results)))
    checks.append(("四类终止条件都被触发过",
                   {r.reason for r in results} == set(TERMINATIONS)))
    checks.append(("每次终止都能序列化留痕",
                   all(isinstance(json.loads(r.as_json()), dict) for r in results)))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `tool_call` 与 `final_answer` 是两个决策桩，返回结构相同的字典，只靠 `kind` 区分「还要调工具」和「给最终答案」。`cost` 是本步要花多少 token，`seconds` 是本步的虚拟耗时；它们都是写死的整数，不读时钟、不联网，所以每一步落在哪、什么时候停，都能手算出来，不靠碰运气。
2. `Limits` 把三条保护线收在一起：`max_steps` 属于步数封顶，`max_tokens` 与 `max_seconds` 属于预算封顶。把耗时单列出来，是为了说明「预算」不止钱和 token 一种维度；真实系统里金额、并发数也常各自设线，道理相同。
3. `Outcome` 是一次终止的完整交代，而不是光秃秃一个原因字符串。`steps`、`tokens`、`seconds`、`trace` 一起回答了「停在第几步、花了多少、这一路做了什么」；`as_json` 把它转成 JSON（JavaScript Object Notation，一种纯文本的数据交换格式）方便落盘，用的是标准库 `json`。
4. `run_loop` 是整篇的关键。循环体一开头就按固定顺序查三条保护型规则：先 `abort_at` / `fatal_at` 对应的被动中止，再 `steps >= max_steps` 的步数封顶，再「累计量加上本步开销会不会越线」的预算封顶。注意预算用的是 `tokens + decision["cost"] > max_tokens` 这种**预测式**判断，而不是先把这一步做掉再回头看——这正是「动手前先查」的落点，越线那一步根本不会执行。
5. 三条都放行，才 `steps += 1`、累加消耗、`trace.append`，然后判断 `kind == "final"` 决定是不是以 `DONE` 收尾。也就是说「完成」排在整条判定链的最后，只有当没有任何中止或截断命中时，它才被当作真的做成了。`abort_at` / `fatal_at` 两个参数模拟外部叫停与不可恢复错误这两个不同来源，但都归到同一个 `ABORT`，并在轨迹里用 `ABORT:external` / `ABORT:fatal` 区分，对应正文说的「同一类退出、两个来源」。
6. `main` 用六组脚本分别触发四类终止：正常完成、步数封顶、token 越线、耗时越线、外部叫停、不可恢复错误；再加一组「三条保护线同时命中但外部叫停也在」的场景，专门验证优先级。`Limits(1, 1, 1)` 那组里步数和预算其实都已越线，结果仍是 `ABORT`，就因为中止检查排在最前。
7. 结尾三条总检分别确认「所有结果都落在这四个条件里」「四类都被真正触发过」「每次终止都能序列化留痕」，最后 `assert` 保证任何一条性质被破坏都会以非零状态退出。最后那个 `NO_TERMINATION` 分支是故意留的防御：如果四条规则全没兜住，就会掉出这个不属于四类之一的原因，被总检当场抓出来。

有一处要如实说明：这里用一串写死的决策桩代替了真实模型、用整数代替了真实计时与计费、用内存里的列表代替了落盘存储，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是四条退出规则的判定顺序、优先级与留痕方式，不是任何具体编排框架的实现；这是可独立运行的示例。

## 七、踩坑与边界

- **把「停」全交给模型一句话**：现象是任务反复检索、说法换个不停，或者明明能答了还多绕好几轮 → 原因是「完成」只是一句需要解析的软判断，代码里没有独立拍板的硬规则 → 把完成信号、步数封顶、预算封顶、被动中止拆成四条，在循环开头集中判定，并把「完成」排在最后。
- **先执行后检查**：现象是明明已经越线，还是多跑了一步、多花一次钱，甚至多发了一条通知 → 原因是检查写在动作之后，判定依据已经是「做完了」的既成事实 → 改成动手前用「累计量 + 本步开销」预测，越线就不执行；有副作用的动作尤其要这样。
- **只设轮数不设预算**：现象是轮数看着不多，账单却悄悄涨上去，一次拉回长文的调用把额度吃光 → 原因是每一轮开销并不相同，光数轮数挡不住花费 → token、耗时、金额分别设线，任意一条越线即停，并把这几条线按任务类型分档。
- **同时满足时结果随缘**：现象是预算耗尽、模型说完成、用户取消撞在一起，这轮到底算成功还是算中止，换个运行顺序就不一样 → 原因是四条规则散落在循环各处、没有约定优先级 → 写成一条固定顺序的判定链：中止最优先，其次封顶，最后才认完成；判定统一用本轮开始时的快照。
- **终止不留原因与轨迹**：现象是成功做完的和被掐断的日志长得一样，事后说不清「为什么这轮没成、花了多少」 → 原因是循环里只有一个光秃秃的跳出 → 每次终止都结算原因、累计量与逐轮轨迹，并让中止动作可重复触发而不写重记录。

还要分清两件事。封顶线是兜住失控的底线，不是「正常任务该跑几轮」的规定，所以别把它们调得太紧去误杀本该做成的任务；真遇到逼近上限，正确做法是给一次只准交答案、不准再调工具的收尾轮，而不是直接截断。反过来，条件也不是越多越好：一次没有循环、没有工具、没有花费的单次问答，硬套这四条只会徒增复杂度；但只要程序开始自己决定「还要不要再跑一轮」，只要这一轮会调工具、会花钱、会产生收不回的动作，这四条就得各就位，缺一条，循环就会从那个方向漏出去。想退一步看清「能自己决定跑几轮」到底意味着什么，可以回到 [Agent 的唯一判据](./k021-agent-criterion.md)；若要把这四条线连同金额、并发一起统一收口，接上 [四重预算](./k103-four-budgets.md) 与 [熔断与紧急开关](./k104-circuit-breaker.md) 那一套更完整的安排。

## 九、三句话小结

四个终止条件，是给「能自己决定再跑一轮」的循环装上完成信号、步数封顶、预算封顶、被动中止这四条由代码独立拍板的硬规则，让它停得下、也说得清为什么停。

关键做法是把四条排成固定优先级的判定链、集中在动手前用累计量加本步开销预测着查，并让每次终止都结算原因、消耗与轨迹；逼近上限时只给一次不许再调工具的收尾轮。

当程序没有循环、不调工具、也不产生花费时，不必硬套这四条；但只要它开始自己决定要不要继续、且每轮都有代价，缺任何一条都会让循环从那个方向漏出去。

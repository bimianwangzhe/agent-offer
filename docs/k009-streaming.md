# 流式输出与首字延迟：边生成边返回，也要会拼半截

## 一、快是快了，麻烦也跟着来了

同一段回答，非流式时你得盯着空白屏幕等上好几秒，文字才一下子整段蹦出来；换成流式，几乎立刻就冒出第一个字，后面一个字一个字往外淌，感觉快得多。可新麻烦很快来了：界面上偶尔出现半截词、两个片段接在一起多了个怪符号；网络一抖，文字停在半句就不动了，你的程序却把它当成"回答完成"存进了库。更隐蔽的是，你原本按"整段文本"写的解析逻辑，一到流式就时不时报错。

快是真的快了，但你手里拿到的东西，已经从"一份完整文本"变成了"一串陆陆续续到达的片段"。

## 二、先破误解

**不是流式把整段回答简单地切成小块发给你，它改变的是"什么时候能开始看到"；一旦变成一片一片到达，拼接、半截、中断这三件事就得由你的代码接手，没人替你兜。**

先把"首字延迟"讲白：从你发出请求，到屏幕上看得见第一片内容，中间等的那一小段时间。非流式要等整段都生成完才一次性返回，这段等待差不多等于生成全文的时间；流式是每生成一小片就发一小片，第一片几乎立刻到。注意，全文生成完所需的总时长并没有因此变短，变短的是"开始看到"的等待——体感上的快，来自这里。流式常常表现为一行行的数据事件，服务器发送事件（Server-Sent Events，SSE）就是描述这种"服务端一小段一小段推过来"的说法；每行里装的可以是一小片文本，用 JSON（JavaScript Object Notation，一种用键值对组织数据的文本格式）之类的格式写着。

代价也正来自"一片一片"这四个字。第一，半截内容：一次到达的片不等于一个完整的词，可能是词的一半，甚至一个多字节字符的一段，把它当独立文本去解析或显示就会出怪符号。第二，中断识别：流得有个明确的结束标记；没收到结束标记就到尾，属于不完整，必须标出来，绝不能当成功结果入库。第三，拼接：得按到达顺序把片累加成全文，不能用"最后一片覆盖"，也不能边到边就急着做只能对整段做的事。

:::warn 别把"没有更多了"当成"正常结束"
连接断掉和对方说"我说完了"是两件事，缺了结束标记就该判为不完整。
:::

## 三、生活类比：传送带上一块块送来的拼图

以前是等整幅拼图装好框，一次递到你手上；现在改成传送带，拼好一块就送一块。好处显而易见：你几乎马上就能看见第一块，能边看边判断方向对不对，觉得不对还能提前喊停。但麻烦也跟着来了。送来的不一定是完整一块，可能是半块，得等下一块才凑得齐（半截内容）；传送带中途停了，你得分辨是"送完了"，还是"卡住了"（中断识别）；而且你得按到达顺序把块拼回去，不能拿最后到的那一块当成整幅画（拼接）。

对应关系逐条摆出来：

- 装好框整幅递来，是非流式；
- 一块一块往外接，是流式；
- 第一块到手那一刻，就是首字延迟；
- 送来的半块，是一片不完整的片段；
- 没有挂出"送完"的牌子就停了，是缺结束标记；
- 按到达顺序拼回整幅，是累加拼接；
- 把半幅当整幅收进库房，是没识别不完整就采信。

这个类比最该带走的，是"快"和"完整"分属两件事。传送带让你更早开工，却把"凑齐没凑齐"的判断交给了你。你不会在只收到半幅时就签字验收；程序也不该在只收到半截、又没见到结束标记时，把结果当成完成。

## 四、画出来：片段怎么来、要管哪几件事

先看一次流式回答从发出到拼成全文的过程：

:::figure 流式一次回答的到达过程
@flow
发出请求|首片很快到|逐片累加|收到结束标记|拼成完整文本
:::

五步里"收到结束标记"是分水岭：在它之前，你手里的一切都只是"进行中的半成品"；只有过了它，那份拼好的文本才算可以拿去解析、入库、展示为完成。少了这一步，前面四步做得再顺也不算完。

再把两种返回方式摆在一起，看清省下的到底是什么：

:::figure 整块返回与流式返回
@compare
整块返回::等到全部生成|一次拿到全文|解析最省事
流式返回::首片几乎立到|片片累加|要认半截与中断
:::

右边那行多的不是速度优势，而是三份额外的活。第三张图把它们单独列出来：

:::figure 流式里要由代码接手的三件事
@stack
拼接::按到达顺序把片累加成全文
半截::别把一片当成完整词去处理
中断::缺结束标记就判为不完整
:::

三张图合起来其实是一句话：流式把"等待"挪走了，把"组装与判定"留给了你。谁接手这三件，谁才真正把流式用起来；只把界面改成逐字显示、却没管这三件，迟早会在网络一抖时存进半截结果。

## 五、顺着追问两层

:::ask 那如果流式并没有让总时长变短，为什么还值得用？
:::

省下的是"从发出到开始看到"的那段空白，而不是总账。人能提前看见方向：开头两句就跑偏了，可以当场打断，不必等整段写完才发现白等；长回答尤其明显，逐字出现比干等几秒舒服得多。但要说清代价：生成总量没变，按片计的用量也不会因为流式就少，[用量统计与计费口径](./k010-usage-billing.md)里那笔账该怎么记还怎么记；而客户端这边多出了拼接、半截、中断三件事，解析逻辑得重写一遍。所以它是"体验与可控性"的取舍，不是"更省"的捷径。顺带一提，返回作为一次调用的一块，本来就该单独处理，[一次请求拆成五块](./k008-request-anatomy.md)讲的就是这个分法。

:::ask 那如果我在中途已经拿到够用的信息，能不能直接断掉？
:::

能，主动中断正是流式一个很实用的好处：既然方向已经清楚，剩下的片就没必要再等。但要把它和"被动断线"严格分开。主动停是你自己决定的，剩余内容本就不需要，状态里记"到此为止"即可；被动断线是异常，拿到的半截不能当完整结果用，得标记失败、决定重来还是降级。两者在界面上都是"不往下出了"，在状态里却必须是两种，混成一个"结束"就会出开头那种"半句被当成完成入库"的事。还有一层得守住：半截内容本身仍在按[采样参数与不确定性](./k004-sampling.md)那套机制往外冒，别拿一段没写完的话去下结论——它可能正要说"但是"。下面这段代码用 `cut_at` 专门模拟被动断线，就是为了让这两种"停"在结构上能被分清。整条线从哪起步，可以看[从这里开始](./00-start-here.md)。

## 六、跑一段代码，把拼接与中断摸实

下面这段只用标准库，不联网、不装包、不要账号，也不真的等待。它用"首个有效字到达前累计等了多少字"这个确定性的量，来对比整块与流式，并把半截、中断、拼接都跑一遍。

```python
import json


def stream_events(full_text, cut_at=None):
    """逐字发一段数据事件，最后发结束事件；cut_at 模拟中途断线。"""
    for i, ch in enumerate(full_text):
        if cut_at is not None and i >= cut_at:
            return
        yield json.dumps({"delta": ch}, ensure_ascii=False)
    yield json.dumps({"done": True}, ensure_ascii=False)


def batch_events(full_text):
    """非流式：等全部生成完，一次性发回。"""
    yield json.dumps({"delta": full_text}, ensure_ascii=False)
    yield json.dumps({"done": True}, ensure_ascii=False)


def chunked_events(full_text, size=2):
    """按固定大小切块，可能把一个词切成两半。"""
    for i in range(0, len(full_text), size):
        yield json.dumps({"delta": full_text[i:i + size]}, ensure_ascii=False)
    yield json.dumps({"done": True}, ensure_ascii=False)


def consume(lines):
    """把半截片段拼起来，并判断是否完整收尾。"""
    parts, done = [], False
    for line in lines:
        obj = json.loads(line)
        if obj.get("done"):
            done = True
            break
        parts.append(obj.get("delta", ""))
    return "".join(parts), done


def wait_chars(lines):
    """首个有效字送达前，客户端累计等了多少字。"""
    total = 0
    for line in lines:
        obj = json.loads(line)
        if obj.get("done"):
            break
        d = obj.get("delta", "")
        total += len(d)
        if d.strip():
            return total
    return total


if __name__ == '__main__':
    checks = 0
    text = "今天天气不错"

    # 1) 逐字流能完整拼回原文，并正常收尾
    assert consume(stream_events(text)) == (text, True)
    checks += 1

    # 2) 切成半截的片段，拼接后一个字不丢
    assert consume(chunked_events(text, 2))[0] == text
    checks += 1

    # 3) 中途断线：只拿到半截，且没有结束标记
    assert consume(stream_events(text, cut_at=3)) == ("今天天", False)
    checks += 1

    # 4) 空文本也能正常收尾，不会误判成中断
    assert consume(stream_events("")) == ("", True)
    checks += 1

    # 5) 流式首字几乎立刻到，整块要等全部生成完
    assert wait_chars(stream_events(text)) == 1
    assert wait_chars(batch_events(text)) == len(text)
    checks += 1

    # 6) 首字等待量：流式明显小于整块
    assert wait_chars(stream_events(text)) < wait_chars(batch_events(text))
    checks += 1

    print("通过 %d/%d 项" % (checks, 6))
```

逐段看它在做什么：

1. `stream_events` 是生成器，逐字发出一行行数据，末尾再发一个 `done` 结束事件；`cut_at` 一旦触发就提前 `return`，于是不会再有结束事件——这正是被动断线的样子。
2. `batch_events` 是非流式：一行就把整段全发回来，再发结束事件。`chunked_events` 按固定大小切，故意让一个词可能落在两片里，模拟半截内容。三者和真实网络无关，只是可复现的构造。
3. `consume` 承担拼接与判定：用 `parts` 按到达顺序累加，见到 `done` 才把 `done` 置为真；返回的是"拼好的文本"和"是否完整"两个值，缺一不可。
4. `wait_chars` 衡量首字等待量：沿着事件累加已经生成的字数，遇到第一个非空片就返回。流式第一行只有"今"，返回 1；整块第一行是整段，返回 6。这里没用真实计时，也不声明任何实测数字，比较的只是这个确定性的量。
5. 断言一、二钉住拼接：逐字流和切块流都能一字不丢地拼回原文；断言三钉住中断，断线时返回的是半截且 `done` 为 `False`；断言四确认空文本也正常收尾，不会被误判成断线。
6. 断言五、六把"体感更快"落成可核对的比较：流式首字等待量小于整块。注意这只说明"开始看到"更早，不说明总时长更短、也不说明用量更少。

把这三件带回系统里，顺序很朴素：先累加、再等结束标记、最后才把拼好的文本交给只接受整段的解析逻辑；没等到结束标记，就明确记为不完整，绝不入库。至于这些文字最初是怎么一片一片被选出来的，回看[下一个词预测](./k002-next-token.md)最顺。

## 七、踩坑与边界

- **把每片当完整词处理**：现象是界面冒出半截词或怪符号 → 原因是一片可能只是词或字符的一半 → 只做累加，等凑齐或收尾再解析与展示。
- **没有结束标记就当成功**：现象是网络一抖，半句被当成完整结果入库 → 原因是把"没有更多了"读成了"正常结束" → 显式认结束标记，缺失即判不完整。
- **拿最后一片覆盖全文**：现象是最后只剩一两个字 → 原因是用了覆盖而非累加 → 按到达顺序拼接，保留全部片段。
- **把主动中断和被动断线混为一谈**：现象是两种"停"都记成完成，事后分不清 → 原因是状态里没区分 → 主动停记"到此为止"，断线记失败并决定重来或降级。
- **以为流式更省钱**：现象是账没变少却以为省了 → 原因是生成总量没变、按片计的用量也没变 → 只把它当体验取舍，成本仍按[用量统计与计费口径](./k010-usage-billing.md)核对。

## 九、三句话小结

流式把整段回答改成一片一片到达，省下的是"开始看到"的等待，总生成量并没有变少。
要紧的做法是按序累加、认准结束标记，缺标记就判不完整，再把拼好的全文交给只接受整段的逻辑。
当你的解析只接受完整文本、或需要把结果可靠入库时，别直接消费零散片段，先拼齐并确认收尾。

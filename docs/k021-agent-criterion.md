# Agent 的唯一判据

## 一、一段谁也说不服的争论

团队里两个人争一个程序算不算智能体。一个说「它调了模型、挂了工具、还有个循环，当然是」；另一个说「它每一步干嘛都是我代码里写死的，模型只负责把话填进空里，换个说法就是个脚本」。两人翻配置、数工具、看有没有 `while`，谁也说服不了谁。更让人犯嘀咕的是，你照着[起步说明](./00-start-here.md)跑通的第一版脚本也会调模型，那它是不是也算？争到后来，问题变成了「到底该看哪一眼才能一眼定下来」。

## 二、判据不看零件，看「决定权」在谁手里

**判断一个程序是不是 Agent，不看它用没用模型、有没有循环、挂了几个工具，只看一件事：下一步做什么，是模型在运行时看着结果定，还是你事先在代码里写死。**

先把两个词摆平。Agent（智能体，指能自己决定下一步动作、并用这些动作去达成目标的一段程序）的关键不在「智能」两个字，而在「自己决定下一步」。Workflow（流程编排，指事先把步骤、顺序和分支写成代码，由程序决定下一步）则相反：路怎么走，在动手写之前就定好了。两者的分界，落在「决定权何时、由谁行使」这一处，跟用了哪些零件无关。

为什么其他特征统统不算数？模型只是一个零件，脚本照样可以调它把一句话润色一下；循环只是一副骨架，`for` 转十次也可以每一步都写死；工具只是手脚，挂十个也仍可以按固定顺序依次调。把这些凑齐，得到的可能是「一个会调接口的聊天应用」，但它一问一答、不保留状态、下一步永远由代码指定，遇到意外不会改道。反过来，哪怕只挂一个工具、只给两个可选动作，只要「选哪个」是在运行时、依据刚拿到的观察做出的，决定权就已经交出去了。判断时把「用了什么」换成「谁在定下一步」，争论立刻就没有了含糊地带。

这里要特意说清「运行时」三个字。它不是「程序运行的时候」这句废话，而是强调：做决定的那一刻，手里已经握着前面几步真实拿回来的东西——工具返回、用户补充、一段报错；并且换一份这样东西，它会做出不同的选择。若一个选择在任何输入下都指向同一个动作，那它只是被摆在了运行时，决定其实早在写代码时就做完了。

:::tip
一句话记住：**看决定权，别看零件。** 拿到一个程序，只问一句：把预设的那几行顺序去掉，它还知不知道下一步该干什么、遇到异常会不会改道？答不上来，就还没跨过那条线。
:::

## 三、跟团游与自助探险

想象两种出门方式。跟团游的行程表在出发前就印好了：周一到甲城、周二逛乙馆、周三坐车去丙镇，导游举着小旗照表走。哪怕周一艳阳高照、乙馆临时闭馆、去丙镇的桥断了，他还是按表执行；游客问「能不能改改」，回答是「表上没写」。表可以做得极复杂——二十个景点、三套雨天备选、每餐两个选项——但决定权始终在出发前那张纸上。

自助探险只定一个大方向：「往西，去看海」。每天早晨根据天气、体力、前一天向当地人打听到的路况，临时决定今天走哪条路、在哪歇脚。走到半途发现桥断了，就绕一条没走过的路，而不是硬闯；听说隔壁镇有集市，也能顺路拐过去。它带的东西可能比跟团游还少，一张地图而已，可决定权在当天现场，在每一个看到新情况的清晨。

对应关系一条条摆出来：行程表，就是事先写死的执行顺序；导游与那套雨天备选，就是代码里枚举好的分支；艳阳、闭馆、断桥，就是运行时拿回来的观察；「今天走哪条路」，就是下一步动作；那个每天早晨重新盘算的人，就是在运行时做决定的模型。看清楚这层就该明白：分界不在「走了多少地方、带了多少装备」，而在「决定是何时、由谁做出的」。跟团游再花哨，也是纸在定；自助者再简陋，也是人在现场定。前面那场争论里，两个人数的全是装备，没人去问那张纸。

## 四、把「写死」和「运行时定」摆在一起看

:::figure 顺序写死的一次执行
@flow
读输入|查资料|汇总格式|返回结果|结束
:::

五个格子从头走到尾，中间没有任何一处会「看一眼结果再改主意」。第三步汇总格式，不因为第二步查到的是空是满而变；第四步返回，也不因为汇总得顺不顺而变。整条链子在写下第一行代码时就已经封死，输入换了，路还是这条路。

:::figure 三个最常被误当成判据的特征
@stack
用了模型::模型只是零件，脚本也能调它说句话
有循环::while 只是骨架，顺序照样可以写死
挂了工具::工具是手脚，不带来下一步的决定权
:::

这三样之所以容易被误认，是因为它们常和真正的智能体一起出现，于是被当成了标志。可「一起出现」和「构成判据」是两回事：抽掉任意一样，只要决定权还在运行时，它依旧是；三样全在，决定权若在代码里，它依旧不是。

:::figure 两种「决定」的差别
@compare
代码写死下一步::路径出发前定|结果不影响顺序|可逐行验收
运行时决定下一步::路径看观察定|结果改变后续|验收要跑轨迹
:::

右边那三点是同一件事的三个侧面：因为路径是看着观察定的，所以换一份观察后续就变；因为会变，所以没法靠「读一遍代码」验收，得把一次运行完整记下来回看。这也解释了为什么决定权一交出去，可测性和可排障性就要跟着换一套做法——不是变麻烦了，是保证方式变了。

## 五、那如果分支写得特别多，或者只让模型选一个按钮呢

:::ask 那 if/else 写了一大堆、分支看着特别灵活，算不算自己决定
:::

不算。分支再多，也是动手前把「遇甲走一、遇乙走二」枚举完了，运行时只是查表；决定权仍停在写代码那一刻，观察只负责选中已有的某一行，不会生出表外的新走法。顺着再追一层：那如果把所有可能路径都枚举全了呢？那恰恰说明「路径可以预先写清」——这是[流程编排](./k022-workflow-vs-agent.md)最擅长的事，交给代码更可测、更可排障，不需要把决定权让给一个每步都要重新判断的东西。分支数量从来不是判据，能不能穷举才是。

:::ask 那模型只是从两个按钮里选一个，也算「自己决定」吗
:::

算，只要这个选择是在运行时、依据刚拿到的观察做出的，而且换一份观察它会选另一个。决定空间可以小到只有两项，要紧的是「何时由谁定」。再追一层：怎么证明它真的在决定，而不是我把答案偷偷写死了？做一个对照实验就够了——固定流程把输入换掉，轨迹不该有任何变化；而把观察换掉，轨迹若跟着变，就说明决定权确实在运行时。这个实验不需要真模型，下面那段代码就跑给你看。

## 六、一段能直接跑的判据实验

下面这段只用 Python 标准库。它用一份本地确定的决策表充当假模型，把「顺序写死」和「看观察再定」两个执行器摆在一起，换几种构造出来的观察，看轨迹变不变。样本全是本地小数据，不联网、不调用任何真实模型。

```python
# Agent 的唯一判据：下一步由谁决定。
# 只用标准库；「假模型」是一张本地决策表，不联网、不调真实模型。

# 决策表：键是 (刚执行的动作, 刚拿到的观察)，值是下一步动作。
# 它只依赖运行时拿回来的两样东西，不含任何「第几步」信息。
DECIDE = {
    ("look_up", "found"): "summarize",
    ("look_up", "missing"): "search_more",
    ("search_more", "found"): "summarize",
    ("search_more", "missing"): "give_up",
    ("summarize", "ok"): "finish",
    ("give_up", "ok"): "finish",
}


def fake_model(action, observation):
    """本地确定性桩：模拟『模型看着本步观察决定下一动作』。"""
    return DECIDE.get((action, observation), "finish")


def fixed_workflow(observations):
    """顺序写死的执行器：不管观察是什么，都按同一步骤列表跑完。
    observations 参数故意只取用一下，不影响路径。"""
    _ = observations
    return ["look_up", "summarize", "finish"]


def agent_like(observations):
    """运行时决定的执行器：每步把观察交给假模型，由它定下一动作。"""
    trace = []
    action = "look_up"
    for _ in range(8):
        trace.append(action)
        observation = observations(action)      # 本步真实拿回来的结果
        action = fake_model(action, observation)  # 下一步由观察决定
        if action == "finish":
            trace.append("finish")
            break
    return trace


def obs_first_found(action):
    return {"look_up": "found", "summarize": "ok"}.get(action, "missing")


def obs_need_search(action):
    return {"look_up": "missing", "search_more": "found",
            "summarize": "ok"}.get(action, "missing")


def obs_always_missing(action):
    return {"look_up": "missing", "search_more": "missing",
            "give_up": "ok"}.get(action, "missing")


if __name__ == '__main__':
    checks = []
    cases = [obs_first_found, obs_need_search, obs_always_missing]

    # 1. 写死流程：换掉所有观察，轨迹始终一模一样
    fixed = [fixed_workflow(f) for f in cases]
    checks.append(("写死流程轨迹不随输入变化",
                   all(t == fixed[0] for t in fixed)))
    checks.append(("写死流程从不含临时插入的动作",
                   all("search_more" not in t for t in fixed)))

    # 2. 运行时决定：换观察，轨迹跟着变
    runs = [agent_like(f) for f in cases]
    checks.append(("运行时决定随观察分叉", len({tuple(t) for t in runs}) == 3))

    # 3. 三种观察各自走出合理的路
    checks.append(("一次就查到不补查", "search_more" not in runs[0]))
    checks.append(("查不到会插入补查", "search_more" in runs[1]))
    checks.append(("一直查不到会走到放弃", "give_up" in runs[2]))

    # 4. 三条轨迹都能收尾，没有跑飞
    checks.append(("每条轨迹都终止", all(t[-1] == "finish" for t in runs)))

    # 5. 决策只依赖 (动作, 观察)，与『第几步』无关：同键必同结果
    checks.append(("同一观察给出同一决定",
                   fake_model("look_up", "found") ==
                   fake_model("look_up", "found")))
    # 6. 换观察会换决定，证明决定权在运行时而非写死
    checks.append(("换观察确实改了下一动作",
                   fake_model("look_up", "found") !=
                   fake_model("look_up", "missing")))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `DECIDE` 是那张本地决策表，键刻意写成「刚执行的动作 + 刚拿到的观察」，不带任何「现在是第几步」的字段。这一点很重要：真正的运行时决定，靠的是眼前这份新信息，而不是数到自己走到了第几格。
2. `fake_model` 只是查表返回下一个动作名，用来代替不可复现的真模型；它足够透明，读者能一眼看清「下一步到底由什么算出来」。
3. `fixed_workflow` 把三步写死，`observations` 参数取用一下却完全不参与路径——这正是「决定权在代码里」的样子：观察来了也不改道。
4. `agent_like` 每步先记录动作，再取回本步观察，把这两样交给假模型定下一动作，直到它给出 `finish`。轨迹里会不会多出 `search_more`、`give_up`，取决于观察，不取决于写死的列表。
5. 三个 `obs_*` 函数构造了「一次查到」「要补查」「一直查不到」三种观察序列，全是本地字典，没有随机数。主函数先证明写死流程在三份输入下轨迹全同，再证明运行时版本分出三条不同的路，并逐条核对补查与放弃确实出现、都能收尾。
6. 最后两项断言单独盯住「决定权」本身：同一观察必给同一决定（可复现），换观察必改决定（不是写死）。十项断言跑完打印「通过 10/10 项」，任一项不成立就报错退出。

这段代码没有证明「哪个更好」，只证明「判据能动手验」：把一个执行器的观察换掉，看它改不改道，就知道了。

## 七、踩坑与边界

- **把固定顺序的链条包装成智能体**：现象是几个步骤依次调模型，对外却说成自主智能体 → 原因是把「用了模型」当成了判据 → 怎么改：回到决定权，问「去掉预设顺序还能不能应变」。
- **以「有没有 while」为判据**：现象是看见循环就认定是、没循环就认定不是 → 原因是循环只是骨架，顺序仍可写死 → 怎么改：看循环体里那一步是查表还是看观察，别看关键字。
- **以「挂了几个工具」为判据**：现象是工具越挂越多，以为离智能体更近了 → 原因是工具是手脚，不带来决定权 → 怎么改：工具清单按当前步骤收敛，判定仍只看下一步谁定。
- **把「完全自主」当卖点**：现象是去掉预设逻辑后，既不处理异常也不重新规划，卡在原地 → 原因是决定权让出去了，却没有配套的观察与终止 → 怎么改：先补上[决策—行动—观察闭环](./k023-decision-loop.md)与[终止条件](./k028-stop-conditions.md)，再谈自主。
- **拿掉预设才发现不会应变**：现象是宣称能应对未知，一遇到工具报错就整段结束 → 原因是报错没有被当成下一轮的观察 → 怎么改：让错误回传参与决定，见[错误回传](./k029-error-feedback.md)。

还要说清一个边界：这条判据只回答「是不是」，不回答「该不该」。很多任务的路径本来就能写清，用代码决定更稳、更好测、更好查；把决定权交给运行时，换来的是应变能力，付出去的是可测性、成本与排障难度。所以判据是描述性的，选型是另一回事，那笔账放在[Workflow 与 Agent 的分界](./k022-workflow-vs-agent.md)里算。别因为「是智能体」就觉得更先进，也别因为「只是流程」就觉得拿不出手——两者不在一条高低线上。

## 九、三句话小结

Agent 的唯一判据是：下一步由模型在运行时看着观察决定，而不是事先写死在代码里。
关键做法是把「用了什么零件」换成「谁在定下一步」，并用换观察看轨迹是否改道来动手验证。
当有人拿循环、工具数量、模型调用次数来争论是不是智能体时，就该停下——那种场合缺的是决定权这一问，不是更多证据。

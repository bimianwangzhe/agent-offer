# 传输、会话与网关限流：把限流放在网关而不是模型里

## 场景提问

同一个能力，有时一次调用就返回，有时要连着聊好几轮、记着前面说过什么，有时还得边生成边把字一个个吐出来。后来请求一多，大家在模型处理函数里各加了一句「太频繁就拒绝」，结果三处判断标准不一样，有的把拒绝混进了正常结果里，有的在流式输出到一半时突然断掉，客户端拿到半截内容当成了完整答案。同样是「挡一下」，为什么挡得这么乱？

## 破误解

**不是限流写得不够严，是把它放错了层**——限流属于请求进出的入口，不属于模型处理函数，更不该和传输形态缠在一起。

先把词说清。传输（transport，数据从一方到另一方的方式，白话讲就是「怎么把话送过去」）在这里有三种常见形态：本地进程调用（一次进、一次出，办完就散）、长连接会话（连上不马上断，多轮往来共享同一份状态）、流式会话（不等全部生成完，边生成边分块送）。会话（session，多次往来共享同一段上下文状态的关系）是第二种形态的关键：轮次、身份这些状态得跟着这段关系走。网关（gateway，所有请求进出都先经过的入口层，白话讲像写字楼闸机）是放限流的地方。限流（rate limiting，单位时间内允许通过的请求数上限，超了就明确拒绝）是一道入口纪律。顺带说两个全称：超文本传输协议（HyperText Transfer Protocol，简称 HTTP，网页与服务之间常用的一种请求应答约定）、服务器发送事件（Server-Sent Events，简称 SSE，服务端把内容分块持续推给客户端的一种方式），它们是流式形态常见的承载方式，但本篇讲的是边界，不依赖任何具体协议实现。

## 生活类比

把整套系统想成一栋「写字楼」：

- **一次性访客**在前台登记、办完事就走，没有后续，这是本地进程调用；
- **持门禁卡的员工**刷同一张卡进出多轮，卡里记着身份、闸机记着第几次进出，这是长连接会话；
- **边走边讲的导览机**不一口气把整段讲解念完，而是一段一段播，你边走边听，这是流式会话；
- **入口闸机**每分钟只放固定人数，超了就在门口礼貌拦下，这是网关限流；
- **各个房间**只管办自己的事，从不自己数「今天进多少人」，这是模型处理函数。

对应关系要点在「谁数人」：如果让每个房间的秘书各自计数，标准必然不一，还会漏掉从别的门进来的人；闸机在唯一入口统一数，房间完全不必知道这件事。第二个对应关系是「半截讲解」：导览播到一半信号断了，正确做法是从已听到的段落接着拼、或明确告诉你这段不完整，而不是把半截当成整段讲完了。第三个对应关系是「拦下不等于办砸」：闸机拒绝是一次明确的回执，房间里的活根本没开始，别把「被拦」混进业务结果里报成失败处理。

## 层层追问

:::ask 那如果流式输出到一半断了，客户端怎么知道拿到的不是完整答案？
靠两样东西：分块要能按序拼，以及中断要有明确标记。每一块带上顺序，客户端按序拼接后再和「是否收齐」的标记核对；若中途断开，要么从断点续传后继续拼，要么明确返回「不完整」，由上层决定重来还是降级。最忌讳的是把「连接断了」悄悄当成「生成完了」——半截文本看起来很像完整答案，尤其当它恰好在句号处断开时。代码里 `stream` 用生成器逐块产出，断言再用 `"".join(chunks)` 验证拼回来与完整结果一致，演示的就是「分块可拼」这个前提；真实链路还需要额外的收齐标记，这里用可控的构造场景把道理讲清。
:::

:::ask 那如果限流到底按用户、按租户还是按全局算，网关该按哪个口径？
这恰恰说明「作用事先确定」必须写在入口，而不是等请求进到业务里再猜。按用户算，一个人刷太快要被挡；按租户算，一个组织下所有人共用额度；按全局算，保护的是后端总容量。三者可以叠加，但判定点必须是同一个网关，且要能识别请求属于哪个作用域。更细一层：被拒的请求不能累加到后端调用数、也不能触发业务侧的重试，否则「挡住了」却仍把压力传了下去。代码里 `Gateway.count` 只在放行时自增，断言专门核对被拒的第三次请求没有把计数推到 3，验的就是这条。追到第二层会得到一句可以带走的判断：限流不只是「数个数」，还包括「数谁的数、在哪儿数、拒了之后会不会偷偷继续」。作用域这件事，和[主体间消息契约](./k081-agent-message.md)里「请求开始就确定字段」是同一种纪律。
:::

## 可运行代码并逐行解释

下面用标准库模拟三种传输形态与一个入口网关，复制即可运行，全程不联网、不调外部服务。

```python
"""三种传输形态与网关限流：限流放在网关，不放在模型里。"""


def model_echo(text):
    """本地确定性桩函数，代表一次后端处理，不联网、不调外部服务。"""
    return "回声:" + text


class Session:
    """长连接：同一个会话保持状态，多轮复用同一个标识。"""

    def __init__(self, sid):
        self.sid = sid
        self.rounds = 0

    def send(self, text):
        self.rounds += 1
        return {"sid": self.sid, "round": self.rounds, "data": model_echo(text)}


def stream(text, size=2):
    """流式：把结果切成小块逐块产出，由调用方拼接。"""
    full = model_echo(text)
    for i in range(0, len(full), size):
        yield full[i:i + size]


class Gateway:
    """固定窗口计数限流，放在调用链入口，而不写进模型处理函数。"""

    def __init__(self, limit):
        self.limit = limit
        self.count = 0

    def allow(self):
        if self.count >= self.limit:
            return False
        self.count += 1
        return True

    def call(self, text):
        if not self.allow():
            return {"ok": False, "error": "网关限流拒绝"}
        return {"ok": True, "data": model_echo(text)}


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    ok(model_echo("甲") == "回声:甲", "本地进程调用一次进一次出")

    s = Session("S-1")
    r1 = s.send("甲")
    r2 = s.send("乙")
    ok(r1["sid"] == r2["sid"] == "S-1", "长连接复用同一会话标识")
    ok(r2["round"] == 2, "长连接保持累计轮次状态")

    chunks = list(stream("甲乙丙"))
    ok(len(chunks) > 1, "流式结果被切成多块")
    ok("".join(chunks) == model_echo("甲乙丙"), "分块拼回后与完整结果一致")

    gw = Gateway(limit=2)
    a = gw.call("甲")
    b = gw.call("乙")
    c = gw.call("丙")
    ok(a["ok"] and b["ok"], "前两次请求被网关放行")
    ok(c["ok"] is False and c["error"] == "网关限流拒绝",
       "超阈值在网关被挡，模型处理函数没被调用")
    ok(gw.count == 2, "被拒的请求没有累加到后端调用数")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `model_echo` 是一个本地确定性桩函数（桩函数，用固定行为替代真实外部服务的替身）：输入什么就回「回声:什么」。它代表后端处理，函数体里完全没有限流判断——这一点是刻意留白的。
2. `Session` 用 `sid` 与 `rounds` 两个字段承载会话状态。每次 `send` 先把轮次加一，再把标识、轮次、结果一起返回，于是「第几轮」这件事跟着这段关系走，不靠调用方自己记。
3. `stream` 是生成器：用 `yield` 把完整结果按固定大小切块逐块产出。生成器（generator，白话讲：一边算一边给、不一次算完的函数）正好对应「边生成边送」的形态。
4. `Gateway.allow` 是唯一的计数点：只在放行时 `self.count += 1`。把自增放在 `allow` 里而不是 `call` 末尾，就保证了被拒请求不会污染计数。
5. `Gateway.call` 先问 `allow`，不通过就立刻回一张 `ok=False` 的表，并写清原因。注意它连 `model_echo` 都没调用，这正是第二张图里「限流在分发之前」的落点。
6. 三条本地断言分别核对：一次进一次出、长连接复用同一标识、轮次累计到 2。它们是三种形态最小可核对的性质，不涉及任何真实网络。
7. 流式两条断言先看「确实切成了多块」，再用 `"".join(chunks)` 验证拼回来与完整结果逐字一致。后者是流式最该守住的一条：分块只是传输方式，不该改变内容。
8. 网关三条断言验的是「放行两次、第三次被明确拒绝、计数仍为 2」，最后打印 `通过 8/8 项`。把限流放在入口，好处在这三条里一目了然：拒绝是确定回执，后端既没被调用，账也对得上。

把代码与第一张图对照，「三种形态」其实共用同一个后端桩函数，差别只在「怎么送、状态放哪」。这也解释了为什么限流不该长在模型函数里：它是三种形态共用的入口纪律，写在任何一处处理函数里都会漏掉另外两处。真要按任务难度把请求分给不同后端，那是[多模型路由与网关](./k082-model-router.md)接着做的事，同样放在这一层。

## 踩坑与边界

- **限流写进模型函数**：现象 → 三处入口各有一套阈值，有的还把拒绝混进业务结果 → 原因 → 把入口纪律塞进了处理逻辑 → 怎么改 → 统一提到网关，判定点只留一处，拒绝回固定的 `ok=False` 结构。
- **长连接状态丢失**：现象 → 聊到第三轮，对方像第一次见你 → 原因 → 会话标识与轮次没跟着关系存，每轮都当新请求 → 怎么改 → 显式维护会话字段，并在每轮回执里带上标识与轮次，方便核对。
- **流式半截当完整**：现象 → 断线后客户端把半截文本当最终答案继续用 → 原因 → 分块没有顺序与收齐标记 → 怎么改 → 分块带序号、按序拼接，中断明确返回「不完整」，由上层决定续传或重来。
- **超时当成没执行**：现象 → 一次超时后又发了一遍，动作做了两次 → 原因 → 把「没收到回执」等价于「后端没做」 → 怎么改 → 重试前先按稳定标识对账，配合幂等（idempotency，白话：同一动作做几次结果一样）判断能否重发。
- **窗口计数不复位**：现象 → 运行一段时间后所有请求都被拒 → 原因 → 计数只增不清，没有时间窗口概念 → 怎么改 → 明确窗口边界并按窗口清零，或用滑动口径，且把口径写在设计说明里。

边界说清楚：一个只在本地跑、单人单进程的小脚本，根本不需要网关，加一层限流反而是负担；它划算的场合是「多个调用方共用同一后端、需要保护容量」的时候。阈值本身也不要拍脑袋：先明确保护的是谁（用户、租户还是后端总容量），再定数值，并让被拒请求有确定回执。还有一点容易混：限流管「让不让进」，路由管「进来之后去哪个后端」，两者都在入口层但职责不同，别写成一个函数；前者的计数、后者的分流与兜底应各自可查。等接口形状随版本变化时，网关这层也要能被[版本漂移与升级策略](./k084-version-drift.md)里的契约测试覆盖到，否则某天字段改了名，限流还在按旧口径数人。

## 三句话小结

传输、会话与网关限流，是分清一次调用、长连接、流式三种送法，并把计数与拒绝统一放在入口层。
关键做法是先限流再分发、分块按序可拼、被拒给确定回执且不污染后端计数。
当只有单人单进程、也没有共用的后端需要保护时，不必额外加一层网关限流。

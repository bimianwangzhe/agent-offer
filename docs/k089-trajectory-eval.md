# 结果评测与轨迹评测

## 场景：两版成功率一样，用户却只骂其中一版

你拿同一批题比了两个版本，最终答案都对，任务成功率一模一样，报表上两条线几乎重合，看不出该留哪版。可放到真实流量里，反馈分成了两边：一版三步就收尾，干净利落；另一版为了拿到同一个答案，把一张表反复读了五六遍，绕去查了一份已经过期的材料，中途还碰了一个本不该碰的工具，偶尔顺手改了不该改的东西。用户抱怨「慢、账单高、有时候它动了我没让它动的地方」，可是成功率一直是满分。你翻报表，那个满分只回答了「事办成没有」，对「怎么办成的」一个字都没记。

## 先破一个最常见的误解

**不是两版一样好，是你只看了终点、没看怎么走到终点的。** 结果评测，说白话就是判目标达成与否：这单任务最后做成了没有，一单只贡献一个「成 / 不成」。轨迹评测，判的是路径合理与否：轨迹（trajectory，一次运行里按时间先后排好的逐步动作、参数与观察）里，工具选对没有、有没有原地打转、有没有踩禁止动作、走了几步、耗了多少。两者盯的是完全不同的东西，而且经常不同向——目标达成了，路径可能绕得离谱甚至危险；路径干净漂亮，也可能因为最后一环出错没办成。只留结果层，等于把「靠运气成功」「歪打正着」「代价大到不划算」这几种情形全压成了同一个「成」。更实际的是成本：一次任务为了拿到答案多跑了好几轮，这些轮次都实打实计费，可它们全被那一个成功标记盖住了。所以要回答「这版到底值不值」，得把「成没成」「怎么走的」「花了多少」三件事分开算，再合起来看；这正是[三层评测](./k085-three-level-eval.md)里任务级与系统级为什么要分开的理由。

## 用出租车司机打个比方

把一次运行想成司机送乘客到目的地。乘客只看一件事：到没到站，这是结果层；公司还要调行车记录仪看另一件事：这一路怎么开的，这是轨迹层。对应关系逐条对一遍：到站对应任务目标达成，行车路线对应工具与步骤的先后顺序，禁行路段对应被禁止的工具或数据范围，绕远与反复兜圈对应重复动作与无效空转，油表对应这一步步累出来的用量与耗时，行车记录仪对应把整条链记下来的轨迹日志。一位司机把乘客送到了，不代表他该那么开：闯了禁行、绕了三圈、油钱翻倍，到站这个结果一个都盖不住；反过来，路线挑得再漂亮，最后停错一栋楼，乘客也没到。公司不会只因为「都送到了」就给两位司机一样的评价，也不会只因为「路线好看」就忽略没到站。评测也一样：结果和路径各管各的账，谁都别替谁下结论，油钱还得单列一笔。

## 画出来看

先看一次判定要同时走两条线。注意「判达成」和「判路径」是并列的两格，各自吃不同的输入：前者只读终态，后者读整条逐步动作，合成一步就会把「结果对、过程危险」这类信息丢掉。

:::figure 结果线与轨迹线并行判定
@flow
目标输入|逐步动作|判达成|判路径|合并结论
:::

这张图里最容易被跳过的是「逐步动作」这一格。很多人只存最终答案，于是「第几步走偏、是选错工具还是参数填错还是观察被截断」全都无从回答；没有轨迹，路径判定根本无从下手。轨迹层具体要盯四件事，摊开看是这样。

:::figure 轨迹评测要盯的四件事
@stack
工具选择::该调的调了没、有没有调错对象
重复与空转::同一动作反复出现却毫无进展
禁止动作::有没有碰不该碰的工具或范围
步数与用量::走了几步、耗了多少才算值
:::

四格不是要一次全判死，而是提醒你「路径合理」至少由这几种性质拼成：动作对不对、有没有进展、有没有越界、代价大不大。再看只判结果与两层一起判差在哪。

:::figure 只判结果与结果加轨迹的差别
@compare
只判结果::绕路被掩盖|越权看不见|成本涨了无感
结果加轨迹::过程能点名|危险路径被拦|开销一起入账
:::

左边那行说的是「把整条链压成一个点」，右边那行说的是「把链保留下来」。两行放一起，重点不是想说多算几个数更勤奋，而是想说这两种判定能抓到的故障根本不重叠：只判结果，越权、绕路、成本失控这三类问题在报表上是隐形的。

## 再往下追两层

:::ask 追问一
那是不是把路径也判上，就一定能挑出更好的那版？
:::

方向对了，但参考路径本身有个坑：同一件任务合理的走法往往不止一条。有人先查再读，有人读错一次换个工具再查，两条路都能到站。要是拿一条写死的「标准步骤」去硬比对，合法的不同走法会被误判成偏差，反而逼着系统去模仿某一条固定路线。所以轨迹判该优先判「性质」而不是「字面对齐」：有没有重复空转、有没有踩禁止动作、有没有超步数与用量、该调的工具调了没，这些是换个走法也照样成立的硬规矩，正是[性质断言](./k088-property-assertion.md)那一套。至于「和理想计划差多少」，只能当辅助线索看，不能当唯一标尺。

:::ask 追问二
那路径合理、结果也达成，是不是就稳了？成本那笔账又该怎么记？
:::

还不能只看一单，得把许多单叠起来看，而且成本口径特别容易记错。按「每次调用多少钱」算，会得到一句挺好看的均价；可真正该问的是「每办成一件事花了多少」——失败的单、绕路的单、重试的单，它们烧掉的资源一样要摊进来。一版成功率没变、每单却多跑两轮，按调用均价几乎看不出变化，按成功任务摊就能立刻显形，见[核心指标与按成功任务核算成本](./k096-metrics-cost.md)。再往深处追一层：路径判定依赖的「走了哪些动作、各耗多少」，到底从哪来？得靠运行时把每一步连同输入输出摘要、耗时、用量记下来，见[Trace 该记什么](./k094-trace-fields.md)与[结构化日志与轨迹回放](./k095-structured-log.md)；再往下，一次运行内部那些嵌套的调用怎么串成一棵树，是[Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md)的话题。门禁里也该把结果分与轨迹分分开比，别揉成一个总分互相抵消，见[回归门禁与基线](./k091-regression-gate.md)。结果层给的是「有没有做成」，轨迹层给的是「值不值这么做」，两笔账合起来才够做决定。

## 一段能直接跑的代码

下面这段不联网、不装任何第三方包、不需要账号，只用标准库。它把四条构造出来的运行记录分别算出结果层成功率与轨迹层合理性，再把总用量按「成功任务」摊一遍；断言钉住「存在目标达成但轨迹不合理的运行」「重复动作与越权能被点名」「按成功任务摊的成本高于按调用摊的均价」。复制成 `.py` 文件直接运行即可，所有数值都是构造示例。

```python
# -*- coding: utf-8 -*-
"""结果评测与轨迹评测：终点、路径、成本三笔账分开算。"""
from dataclasses import dataclass


@dataclass
class Run:
    run_id: str
    goal_done: bool       # 结果层：目标是否达成
    steps: tuple          # 轨迹层：逐步动作名
    forbidden: frozenset  # 本次运行禁止的动作
    tokens: int           # 该运行总用量


def result_score(runs):
    """结果层：目标达成的占比，一单只贡献一个 0 或 1。"""
    return sum(1 for r in runs if r.goal_done) / len(runs) if runs else 0.0


def trajectory_check(run, max_steps=4, token_cap=3000):
    """轨迹层：返回 (是否合理, 被点名的问题列表)。"""
    problems = []
    if len(run.steps) > max_steps:
        problems.append("步数超限")
    if len(set(run.steps)) < len(run.steps):
        problems.append("重复动作")
    if any(s in run.forbidden for s in run.steps):
        problems.append("走了禁止动作")
    if run.tokens > token_cap:
        problems.append("用量超预算")
    return (len(problems) == 0, problems)


def main():
    forbidden = frozenset({"export_all", "read_secret"})
    runs = [
        Run("r1", True, ("search", "read", "answer"), forbidden, 1200),
        Run("r2", True, ("search", "read", "read", "read", "read", "answer"), forbidden, 4200),
        Run("r3", True, ("search", "read_secret", "answer"), forbidden, 1500),
        Run("r4", False, ("search", "answer"), forbidden, 900),
    ]
    traj = {r.run_id: trajectory_check(r) for r in runs}
    checks = []
    score = result_score(runs)
    checks.append(("结果层成功率算得出", 0.0 <= score <= 1.0))
    checks.append(("r1 轨迹合理", traj["r1"][0] is True))
    checks.append(("r2 结果达成但轨迹不合理", runs[1].goal_done is True and traj["r2"][0] is False))
    checks.append(("r2 被点名重复动作", "重复动作" in traj["r2"][1]))
    checks.append(("r2 被点名用量超预算", "用量超预算" in traj["r2"][1]))
    checks.append(("r3 结果达成却走了禁止动作", runs[2].goal_done is True and "走了禁止动作" in traj["r3"][1]))
    checks.append(("存在结果对但路径危险的运行", any(r.goal_done and not traj[r.run_id][0] for r in runs)))

    total_tokens = sum(r.tokens for r in runs)
    success = sum(1 for r in runs if r.goal_done)
    cost_per_success = total_tokens / success
    cost_per_call = total_tokens / len(runs)
    checks.append(("按成功任务摊成本算得出", cost_per_success > 0))
    checks.append(("成功任务均摊高于调用均价", cost_per_success > cost_per_call))
    checks.append(("r4 结果未达成被保留", runs[3].goal_done is False))

    passed = sum(1 for _, ok in checks if ok)
    print(f"结果层成功率={score:.2f}  总用量={total_tokens}  成功数={success}")
    print(f"每成功任务成本={cost_per_success:.0f}  每次调用均价={cost_per_call:.0f}")
    for r in runs:
        ok, problems = traj[r.run_id]
        print(f"  {r.run_id}: 达成={r.goal_done} 轨迹合理={ok} 问题={problems}")
    for name, ok in checks:
        print(f"  [{'OK' if ok else 'NG'}] {name}")
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks)


if __name__ == '__main__':
    main()
```

1. `@dataclass class Run`：一条运行记录带编号、目标是否达成、逐步动作元组、禁止动作集合、总用量。把「终态」和「逐步动作」放进同一个对象，是为了两条线能从同一份数据分别取数，不用另造两份。
2. `result_score`：数达成条数占比，一单只贡献一个 0 或 1，跟它走了几步、花了多少完全无关。这就是结果层故意「看不见过程」的地方。
3. `trajectory_check`：查四件事——步数是否超限、动作是否重复、有没有踩禁止动作、用量是否超预算，返回「是否合理 + 问题名单」。判的是性质而非某条标准路线，所以换个合法走法照样成立。
4. `runs = [...]`：四条构造记录。`r1` 干净成功；`r2` 目标达成却反复读、用量超预算；`r3` 目标达成但调了禁止工具；`r4` 没办成。它们是专门用来演示「结果对、路径危险」与「两层不同向」的，不是摘来的真实数据。
5. `traj` 与几条断言：钉住「r1 合理」「r2 结果对但轨迹不合理、且原因被点名」「r3 越权被抓」「确实存在结果达成却路径危险的运行」。最后一条正是结果层单看会漏掉的那类。
6. `cost_per_success` 与 `cost_per_call`：把总用量分别按成功数与按调用数摊。断言「前者高于后者」，是因为失败与绕路的开销都摊进了成功任务里，这个差额就是那一个成功率盖住的成本。
7. 结尾 `print` 与 `assert passed == len(checks)`：把两条线的结果、成本与通过项打出来，肉眼确认跑到结尾；任一性质不成立就抛异常、退出码不为零，不会悄悄过关。

## 踩过的坑与边界

- **只存最终答案**：现象是出了问题只能靠猜「第几步走偏」 → 原因是没记逐步动作与观察 → 把每步的输入输出摘要、耗时、用量落下来，见[Trace 该记什么](./k094-trace-fields.md)。
- **拿一条标准步骤硬比对**：现象是合法的不同走法被判成偏差 → 原因是把路径当字面对齐 → 改判重复、越界、超预算这类性质，见[性质断言](./k088-property-assertion.md)。
- **结果分与轨迹分揉成总分**：现象是路径退步被结果进步抵掉，报表一片稳 → 原因是两笔账互相抵消 → 各存各的原始数，门禁按分组比，见[回归门禁与基线](./k091-regression-gate.md)。
- **按每次调用算成本**：现象是成功率没变、账单悄悄涨了却看不出 → 原因是失败与重试的开销没摊进成功任务 → 改按成功任务核算，见[核心指标与按成功任务核算成本](./k096-metrics-cost.md)。
- **只看终态漏掉越权**：现象是回答很得体，中途却读了不该读的 → 原因是结果层对路径隐形 → 把禁止动作检查放进轨迹判定，配合[结构化日志与轨迹回放](./k095-structured-log.md)复核。

边界也要说清：轨迹评测适合「一次任务要走多步、会调工具、有副作用」的系统。若只是一个单步、无状态、一次调用即出结果的小工具，路径就是那一调用本身，硬铺一套轨迹判定没有意义，把结果层的口径定准就够。另外轨迹判定依赖「记得下」：日志没记全，再好的判定规则也是空转。

## 三句话小结

结果评测判目标达成与否，轨迹评测判路径合理与否，两者分开算、还要把用量成本一并入账。
做法是用结果分、路径性质名单、按成功任务摊的成本三笔账并列，失败能点名是哪一环破的。
只在单步、无状态、一次调用即出结果、也没有工具与副作用的小工具上，不必铺轨迹评测。

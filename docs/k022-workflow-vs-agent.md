# Workflow 与 Agent 的分界

## 一、三步就能写死的事，为什么想做成会规划的

「每天拉一次数据、算几个指标、排版成一张日报、发到群里」——需求清楚得几乎不用讨论。有人却提议：别写成固定脚本了，做一个能自己规划的智能体吧，以后要加字段、换数据源都省事，说出去也更像样。你隐约觉得哪里不对：明明四步就能写死、每天走同一条路的东西，为什么要交给一个每步都要重新判断、还可能走出岔路的执行者？可一时又讲不清「不对」落在哪，只觉得「为了灵活而灵活」好像也不算个理由。

## 二、分界不是谁高级，是路径写不写得清

**不是智能体比流程编排更高级，也不是流程编排落后；分界只有一条：下一步的路径能不能在动手之前写清楚。能写清就让代码决定，写不清才把决定权交给运行时。**

先把两个词再说准一点。Workflow（流程编排，把步骤、顺序与分支事先写成代码，由程序决定下一步）的价值在于同一份输入必然走同一条路；Agent（智能体，下一步由模型在运行时看着观察决定）的价值在于路径事先数不清时仍能往前走。用[Agent 的唯一判据](./k021-agent-criterion.md)先看清两者差在决定权，接着要算的是另一笔账：可控性、可测性、可排障性。

这三笔账是选型真正的依据。路径写死时，出错能按行号定位，改完能拿同一组输入重跑一遍确认，验收就是逐条对步骤；路径交给运行时，同一次请求跑两遍可能走不同的路，出事得把整条轨迹记下来回看，验收也从「读代码」变成「跑轨迹」。这不是说后者不好，而是它用可控性换了应变能力。当路径本来就固定，这笔交换是白付的：你既没得到新能力，还把可测性丢了。工程上「能用流程就别上自主循环」之所以被反复强调，正因为追新名词的成本很实、收益很虚。

还要留意一个常被忽略的事实：这两个词不在同一条进化线上，不是「先学流程、再升级成智能体」。它们是按任务形状挑的两种组织方式，同一套系统里完全可以一部分写死、一部分交出去。把它们排成高低等级，会让人下意识往复杂的那边靠，而复杂本身从来不是目标。

:::tip
一句话记住：**写不清才交出去。** 拿到需求先问「下一个动作能不能在动手前列成一张固定表」；能，就别让运行时替你临场决定。
:::

## 三、地铁与出租车

想象每天早上去同一个地方。坐地铁：轨道铺好、站序定死、时刻表可查，出发前就能算出第几分钟到哪一站、在哪换乘；正因为一切都固定，App 才敢给出精确到分钟的到站预报，一旦晚点，也能立刻查出是哪一段信号出了问题。坐出租车：只知道起点和终点，走哪条街由司机看着实时路况临时定，前面堵了就绕，路口封了就换，灵活得很；可你没法在出发前给朋友一个「第三分钟一定经过某路口」的保证，事后再想复盘他为什么在那个口拐了弯，也得调出行车记录才说得清。

对应关系一条条摆出来：轨道与时刻表，就是事先写死的步骤和顺序；那份精确到分钟的到站预报，就是可测、可验收；「哪一段信号故障」的定位，就是按行号排障；实时路况，就是运行时拿回来的观察；司机临场拐的那个弯，就是模型动态做出的决定；事后要调行车记录，就是自主路径必须留轨迹才能查。

想清楚这层，开头那个提议的问题就具体了：这是趟天天走、站点固定的通勤，铺轨道比雇司机更便宜、更准、更好查。只有当「哪条路今天能走通」事先根本不知道——路况会变、得走一段看一段——才值得付司机那份钱和那份不确定。路线固定时非要雇司机，付了钱买到的只是「今天可能走了另一条街」，而这恰恰是通勤最不想要的。

## 四、同一件事的两种走法

:::figure 一天的日报按固定顺序跑完
@flow
拉取数据|计算指标|排版成文|发送|结束
:::

五个格子首尾相接，第二步不会因为第一步拉到的是空表而改，第四步也不会因为第三步排得顺不顺而改。这样的链子有一桩好处：出问题你能直接指着某一格说「就是这里」，改完拿昨天的输入重跑一次就知道修没修好。

:::figure 决定用哪一个之前先问三句
@stack
路径能写死吗::能就交给代码，别让运行时临场判断
每步结果会改后续吗::会才需要看着观察再决定下一动作
出错要怎么查::按行号查用流程，靠轨迹查用自主循环
:::

三句是按顺序问的。第一句答「能」，后面两句基本不用问了；第一句答「不能」，才轮到第二句确认那种不确定是不是真的来自「上一步结果」；第三句则提醒你，一旦选了右边，验收与排障的做法要整套换掉，不能还按读代码的老习惯来。

:::figure 同一件事的两种做法
@compare
流程编排::顺序预先定|同输入同路径|按行号排障
自主循环::路径看结果定|两次可能不同|要留轨迹
:::

两行摆在一起，取舍就很直白：左边那三点是确定性的红利，右边那三点是应变能力的代价。没有哪一行全好，选的是「这个任务更需要哪一列」。日报需要的是「每天都一样、错了好查」，于是左边全中；若换成「查一个从没见过的故障，得看一步日志再决定下一步查哪」，右边才对得上。

## 五、那流程里要判断一下，或者以后会变呢

:::ask 那流程里某一步确实要「判断一下」，是不是就得改成自主循环
:::

不必。局部加一个写死的判断点就行，比如「数据为空就改拉备用源」，这是一个事先列好的二选一，整条链仍是流程；它和「让运行时自己决定下一步」差在选项是不是事先穷举完的。顺着再追一层：那要是判断的依据会变、二选一根本不够用呢？那说明这一段的路径确实写不清，可以只把这一段单独换成运行时决策，其余四格保持固定。这种混合形态反而是常态，要紧的是把边界划明白：哪几段可以逐行验收，哪几段得靠[轨迹回放](./k030-checkpoint-replay.md)来查，别混成一笔糊涂账。

:::ask 那「以后需求可能变」，要不要现在就提前用自主循环
:::

不该。变化是将来重构的理由，不是现在预先堆复杂度的理由。今天能写清的部分今天就写清，等真出现「下一步取决于上一步结果、且合理走法不止一种」的那一段，再把它单独让出去，改动面还更小。再追一层：怎么识别那一刻真的来了？看有没有冒出这句话——「同一个输入，合理下一步却有好几种，选哪种要等结果回来才知道」。有，才是自主循环该接手的信号；只是「将来可能加个字段」，那是加一格的事，不是换执行者的事。真正为不确定准备的，是[决策—行动—观察闭环](./k023-decision-loop.md)那套结构，不必提前供着。

## 六、一段能直接跑的选型对照

下面这段只用 Python 标准库。它拿同一份「日报」小数据，写一个步骤恒定的流程版本，再写一个由本地假模型「看着观察决定要不要插一步」的版本，用几组构造数据看看两者差在哪。全部本地运行，不联网、不调用任何真实模型。

```python
# Workflow 与 Agent 的分界：同一任务，路径写死 vs 看结果再定。
# 只用标准库；小数据与「假模型」都是本地构造，不联网、不调真实模型。

def workflow(records):
    """流程编排：步骤与顺序写死，与 records 的内容无关。"""
    _ = records  # 故意只取用一下，强调内容不改变路径
    return ["pull", "compute", "render", "send"]


def observe(records):
    """把本步拿到的『观察』压成一个可直接判断的本地标签。"""
    if not records:
        return "empty"
    if any(r.get("value") is None for r in records):
        return "has_gap"
    return "clean"


def decide(observation):
    """本地确定性桩：模拟『模型看着观察决定下一动作』。
    只依赖观察，不依赖『第几步』。"""
    return {
        "empty": "fallback_pull",
        "has_gap": "recheck",
        "clean": "compute",
    }.get(observation, "compute")


def agent(records):
    """自主风格：拉完数据先看观察，再决定要不要插一步。"""
    trace = ["pull"]
    nxt = decide(observe(records))     # 下一步由运行时观察决定
    trace.append(nxt)
    if nxt in ("fallback_pull", "recheck"):
        trace.append("compute")        # 处理完异常再回到主路
    trace += ["render", "send"]
    return trace


CLEAN = [{"value": 3}, {"value": 5}, {"value": 7}]
GAP = [{"value": 3}, {"name": "缺值"}]
EMPTY = []


if __name__ == '__main__':
    checks = []
    datasets = [CLEAN, GAP, EMPTY]

    # 1. 流程版本：三份数据走出完全相同的轨迹
    flows = [workflow(d) for d in datasets]
    checks.append(("流程路径与数据无关", all(t == flows[0] for t in flows)))
    checks.append(("流程始终是四步", all(len(t) == 4 for t in flows)))

    # 2. 数据干净时，两个版本走同一条路
    checks.append(("干净数据下两者一致", agent(CLEAN) == workflow(CLEAN)))

    # 3. 数据有缺口或为空时，自主版本按观察插入额外步骤
    checks.append(("空数据会插入备用拉取",
                   "fallback_pull" in agent(EMPTY)))
    checks.append(("有缺口会插入复核", "recheck" in agent(GAP)))
    checks.append(("流程版本从不插入这些动作",
                   all("fallback_pull" not in t and "recheck" not in t
                       for t in flows)))

    # 4. 自主版本随观察分叉，且都比干净那条长
    runs = [agent(d) for d in datasets]
    checks.append(("自主版本随观察分叉", len({tuple(t) for t in runs}) == 3))
    checks.append(("异常数据路径更长",
                   len(runs[1]) > len(runs[0]) and len(runs[2]) > len(runs[0])))

    # 5. 决策只依赖观察：同观察必同动作，换观察可换动作
    checks.append(("同一观察给出同一决定",
                   decide("clean") == decide("clean")))
    checks.append(("换观察确实改了下一动作",
                   decide("clean") != decide("empty")))

    # 6. 两边都收尾，没有跑飞
    checks.append(("每条轨迹都发送收尾",
                   all(t[-1] == "send" for t in flows + runs)))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `workflow` 把四步写成一个固定列表，`records` 取用一下却完全不参与路径——这就是「同输入同路径」最直白的形态，也顺带说明了它为什么好验收：轨迹永远只有那四格。
2. `observe` 把一堆记录压成 `empty` / `has_gap` / `clean` 三种本地标签，相当于运行时真实拿回来的观察；用标签而不是原始数据，是为了让「看结果再定」这件事看得清楚。
3. `decide` 是那张本地决策表，只认观察、不认「第几步」，模拟模型在运行时给出的判断；它足够透明，读者能一眼看出哪一步会分叉。
4. `agent` 先 `pull`，把观察交给 `decide`，若判断需要补拉或复核就插一步再回主路，最后照旧 `render`、`send`。轨迹长不长、多哪一步，取决于数据，不取决于写死的列表。
5. `CLEAN` / `GAP` / `EMPTY` 是三组构造数据，没有随机数。主函数先证明流程版本在三份数据上轨迹全同且恒为四步，再证明干净数据下两个版本一致、异常数据下自主版本插入额外动作并分出三条路。
6. 最后几项断言盯住决定权与收尾：同一观察必给同一决定、换观察必改决定、两边都走到 `send`。十二项断言跑完打印「通过 12/12 项」，任一项不成立就报错退出。

这段要演示的不是「自主版本更强」，而是那笔交换：它多出来的每一步都对应一份真实的不确定性，若数据天天干净，这些分支一次也用不上，只剩更长的轨迹要留、更多路径要查。

## 七、踩坑与边界

- **为显得先进而上自主循环**：现象是三步能写死的事改成每步都问一次模型 → 原因是把「说出去更像样」当成了选型依据 → 怎么改：按「路径能否写清」判，见[唯一判据](./k021-agent-criterion.md)。
- **路径本可枚举却放开自主**：现象是同一请求两次走出不同路径，验收无从下手 → 原因是把本该写死的表格交给了临场判断 → 怎么改：能列成固定表的部分收回到代码里。
- **把两者当进化等级**：现象是认定流程低级、智能体高级，凡事往复杂靠 → 原因是把两种组织方式排成了一条升级线 → 怎么改：按任务形状组合，允许一部分写死一部分交出去。
- **完全自主等于完全不可控**：现象是长链路放开后既难验收也难排障 → 原因是决定权全让出去，却没有边界与终止 → 怎么改：只在写不清的段落让出，并配齐[四个终止条件](./k028-stop-conditions.md)。
- **混合时不划清边界**：现象是一半固定一半自主，出事分不清该看代码还是看轨迹 → 原因是没标注哪段靠逐行验收、哪段靠回放 → 怎么改：把两类段落显式分开，各自用对应的保证方式。

还要说清一个边界：这不是劝人别用自主循环。当「下一步取决于上一步结果、且走法无法预先枚举」真实存在时——排障、开放调研、多轮检索——它是对的，而且为这种不确定准备的结构本来就该上。取舍的落点始终是那句：可控性、可测性、可排障性优先于灵活性。灵活只在不确定真的出现时才有价值，其余时候它只是成本。

## 九、三句话小结

Workflow 与 Agent 的分界，在于下一步路径能否在动手前写清：能写清就用流程编排，写不清才把决定权交给运行时。
关键做法是按可控性、可测性、可排障性算这笔交换，只在不确定真实出现的段落让出决定权，其余保持固定。
当有人因为「更像样」「以后可能变」就想把一条天天相同的通勤改成临场探路时，就该停下——那种场合缺的是路径清点，不是更自主的执行者。

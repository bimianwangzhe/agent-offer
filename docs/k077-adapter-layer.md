# 解耦适配层：换框架时不重写业务逻辑

## 场景提问

你的业务代码里到处是某个框架的方法名：调工具用它给的写法，读记忆用它给的字段，连异常类型都是它定义的。某天要换一套框架，你全局搜了一遍改了几十处，运行时却仍有一处行为对不上——漏改的地方藏在一个不常走的分支里。改动量这么大，究竟是换框架本身麻烦，还是当初代码就不该长成这样？

## 破误解

**不是换框架太麻烦，是业务代码直接长在了框架接口上**，接口一变，整片业务跟着被连根拔起。

先把词说清。应用编程接口（Application Programming Interface，简称 API，白话讲：一段代码提供给另一段代码的「可调用入口和规矩」）是框架暴露给你的那组名字。适配层（adapter layer，夹在业务与框架之间、把两边形状翻译一致的一层薄代码，白话讲像出国带的电源转换插头）则是你自己加的一道隔离：业务只认你定的一组方法，框架的形状由适配层翻译过去。端口（port，业务侧自己定义、与任何框架无关的一组方法约定）就是这份「我自己定的规矩」。这么一隔，业务与框架不再直接互相认识，两边都只依赖中间那份约定。回头看[框架六大件](./k075-framework-six.md)：六件里任何一件的具体形状都可能随版本变，适配层挡的正是这种变化。

## 生活类比

把业务代码想成一台只认两个扁孔的笔记本电源，框架想成各国形状不同的墙上插座：

- **笔记本**只认「两个孔、这个电压」，它不关心墙里是什么标准，这是端口；
- **甲国插座**是三脚方头，**乙国插座**是两脚圆头，形状全不一样，这是两套框架接口；
- **转换插头**一头接墙、一头接笔记本，把形状翻译过去，这是适配层；
- **插头里**只有铜片和弹片，不会替笔记本决定充不充电、充到多少，这是「适配层只做翻译、不做业务」。

对应关系要点在最后一条：换国家时你只换一个转换头，笔记本一个螺丝都不用动；可要是当初把电源线直接焊死在甲国插头上，换国家就得连机器一起换——这正是「业务里写满框架方法名」的处境。还有个容易忽略的细节：转换头必须很薄。要是你在插头里塞进稳压、计时、计费一堆逻辑，它自己就长成了新的绑定点，下次换插座连插头也得重做。适配层越薄、职责越单一，能挡住的变化反而越多。

## 自绘示意图

:::figure 从业务到框架之间隔着什么
@stack
业务层::只按自己定的端口方法写，代码里不出现框架专有名字
端口::一组极少的自定义方法，例如调工具与读记忆
适配层::把端口方法翻译成当前框架的接口形状
框架实现::真正的状态、循环、分发等能力，形状随版本变
:::

:::figure 一次调用穿过适配层
@flow
业务调端口|适配层翻译|框架接口执行|结果翻译回|交还业务
:::

:::figure 直接调框架接口与走适配层的差别
@compare
业务直接调框架接口::改动散落几十处|漏改藏在不常走分支|换实现要重写业务
业务只认自定义端口::改动集中在一层|业务源码可验证解耦|换实现不动业务
:::

三张图叠起来看：第一张是分层，第二张是一次调用的来回，第三张是两种写法的代价。请特别注意第二张图里「结果翻译回」这一步——适配不只是把调用送出去，还得把返回值、错误类型统一回业务认的形状，否则业务照样会被框架的错误定义渗进来。

## 层层追问

:::ask 那如果适配层只暴露业务用得到的少数方法，会不会把框架的能力「削平」了？
会，而且这是刻意的。收窄不是损失，是保护：端口里每多一个方法，业务就多一处与框架绑定的可能。真正需要用到框架某个特殊能力时，做法不是把这些方法全塞进端口，而是另开一个可选的、命名清楚的能力端口，由用到的那一小块业务单独依赖。这样主端口保持又薄又稳，特殊能力有明确的归属，日后换实现时你能一眼看出「哪些业务会被影响」。判断标准很简单：这个方法是「多数业务都要」，还是「只有一处要」——前者进主端口，后者单独放。
:::

:::ask 那如果两套框架连错误类型、返回值字段都不一样，适配层要管到什么程度？
管到「业务侧看到的是同一套分类」为止，再多就越界了。举例来说，甲框架把「工具不存在」抛成一种异常，乙框架返回一张带状态字段的表，业务不该分别认识这两样东西；适配层把它们都翻译成业务侧统一的几类结果，例如「成功」「可重试」「需人工」「参数非法」。但「遇到可重试该重试几次」属于业务策略，不该写在适配层里，否则适配层就悄悄变成了策略层。追到这一层可以看出一条分界线：适配层负责形状的翻译与分类的统一，策略的取舍仍归业务。这条线一旦划清，[版本漂移与升级策略](./k084-version-drift.md)里那套契约测试才有可比对的对象——端口就是那份契约。
:::

## 可运行代码并逐行解释

下面用标准库演示：同一份业务函数，接两套形状完全不同的接口，结果一致；还用源码检查证明业务里没有任何具体框架名。

```python
"""解耦适配层：业务只认自定义接口，换框架只换适配器。"""
import inspect


class RuntimePort:
    """业务侧唯一认识的接口：只有两个方法，不含任何框架专有形状。"""

    def invoke_tool(self, name, args):
        raise NotImplementedError

    def read_memory(self, key):
        raise NotImplementedError


class AdapterOne(RuntimePort):
    """模拟第一种框架接口：工具叫 call，存储叫 store。"""

    def __init__(self):
        self._tools = {
            "sum": lambda p: sum(p["nums"]),
            "tag": lambda p: "标签:" + p["text"],
        }
        self._store = {"prefix": "汇总="}

    def invoke_tool(self, name, args):
        return self._tools[name](args)

    def read_memory(self, key):
        return self._store[key]


class AdapterTwo(RuntimePort):
    """模拟第二种框架接口：方法名与字段形状都不同，业务侧无需知道。"""

    def __init__(self):
        self._tools = {
            "sum": lambda p: sum(p["nums"]),
            "tag": lambda p: "标签:" + p["text"],
        }
        self._kv = {"prefix": "汇总="}

    def invoke_tool(self, name, args):
        return self._tools[name](args)

    def read_memory(self, key):
        return self._kv[key]


def business(runtime, nums, text):
    """业务函数：只经由 RuntimePort 的两个方法，不碰任何框架接口。"""
    total = runtime.invoke_tool("sum", {"nums": nums})
    tag = runtime.invoke_tool("tag", {"text": text})
    prefix = runtime.read_memory("prefix")
    return prefix + str(total) + "|" + tag


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    r1 = business(AdapterOne(), [1, 2, 3], "甲")
    r2 = business(AdapterTwo(), [1, 2, 3], "甲")
    ok(r1 == "汇总=6|标签:甲", "适配器一给出正确业务结果")
    ok(r1 == r2, "换成另一套框架接口后，业务结果完全一致")

    src = inspect.getsource(business)
    ok("AdapterOne" not in src and "AdapterTwo" not in src, "业务源码不含具体框架适配器名")
    ok("invoke_tool" in src and "read_memory" in src, "业务只经由自定义端口的两个方法")
    ok(business(AdapterTwo(), [10, 20], "乙") == "汇总=30|标签:乙", "换输入与适配器结果仍稳定")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `RuntimePort` 是那份「自己定的规矩」：只有 `invoke_tool` 与 `read_memory` 两个方法，方法体直接抛 `NotImplementedError`（表示这是约定，具体实现由子类给）。业务侧认识的全部东西就这两个名字。
2. `AdapterOne` 与 `AdapterTwo` 模拟两套形状不同的接口：一个把存储叫 `_store`，另一个叫 `_kv`；注释里也点明它们的方法名原本可以完全不同。差异被关在这两个类里。
3. 两个适配器都实现同一组端口方法，于是对业务来说它们可以互换。`business` 收到的 `runtime` 是谁，它完全不关心。
4. `business` 是纯业务：求和、打标签、取前缀、拼结果，四行里只出现端口方法名，没有一处框架专有名字。
5. `inspect.getsource(business)` 是这段代码最巧的一行：它把业务函数自己的源码取出来当文本检查（标准库自带能力），断言里面不含两个适配器的名字。这就把「解耦」从一句口号变成了可复现的核对——若哪天有人图省事在业务里直接写了框架名，断言立刻失败。
6. `ok("invoke_tool" in src and "read_memory" in src, ...)` 从正面确认业务只经由端口，与上一行一反一正，把「只依赖约定」钉死。
7. `r1 == r2` 验证行为等价：换实现不改结果。这一条是适配层有没有写对最直接的证据，比读代码可靠。
8. 最后一条换输入又换适配器，说明稳定性不是碰巧在某组数据上成立；`main` 结尾打印 `通过 5/5 项`，每条断言对应一个可回答的问题。

读完回头看第三张图：「业务源码可验证解耦」不是形容词，就是第 5、6 行那两条断言。顺带一提，端口定义得越窄，这层检查越好写；若端口膨胀到十几个方法，源码检查就只能查「有没有出现某个名字」，查不出「是不是只经由端口」。

## 踩坑与边界

- **适配层里写业务**：现象 → 换框架时连适配层一起重写，隔离等于白做 → 原因 → 稳压、计费、重试策略都被塞进了翻译层 → 怎么改 → 适配层只留形状翻译与错误分类，策略回到业务侧，让这层薄到能一眼看完。
- **端口照抄框架**：现象 → 端口方法与框架方法一一对应，换个框架端口也得改 → 原因 → 把「翻译」写成了「改名」 → 怎么改 → 端口按业务动作命名，例如「取数」「核对」，不按框架的动作命名。
- **返回值不翻译**：现象 → 业务里出现两套错误判断，分支越写越乱 → 原因 → 只翻译了调用方向，没翻译回来 → 怎么改 → 把返回与错误统一成少数几类结果，业务只处理分类，不认识框架异常类型。
- **漏改藏在不常走的分支**：现象 → 全局替换后，某个少见的输入仍走旧形状 → 原因 → 业务里散落的框架名没被逐一收拢 → 怎么改 → 用源码级断言守住边界，并给不常走的路径补一条用例。
- **一层适配扛所有变化**：现象 → 换了框架还要换模型服务，适配层被迫塞进两套翻译 → 原因 → 把不同方向的变化压进同一层 → 怎么改 → 按变化来源分层，工具接入那一层单独放，可对照[工具协议与标准化接入](./k078-tool-protocol.md)。

边界说清楚：适配层不是免费的。它多一层间接、多一份要维护的约定，若只是写一个一次性的小脚本，直接调接口反而更直白，加这层纯属负担。它划算的场合是「同一份业务要长期活下去、而底下的实现可能换」：换框架、换模型服务、同一套业务跑在两种运行环境里。还有一层它管不了：接口字段本身悄悄变了含义却没改名字，这种漂移要靠[版本漂移与升级策略](./k084-version-drift.md)里的契约测试才发现。适配层挡的是「形状变化」，契约测试挡的是「含义变化」，两件事别混。

## 三句话小结

解耦适配层，是让业务只认自己定的一组端口方法，由一层薄翻译去对接框架的具体形状。
关键做法是端口按业务动作命名、双向翻译调用与结果，并用源码断言验证业务不含框架名。
当脚本一次用完、底层实现根本不会换时，直接调接口更直白，不必加这层间接。

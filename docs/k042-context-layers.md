# 四层上下文结构：谁常驻、谁按需、谁用完即弃

## 一删就出错，一留就超支

你接手一个跑得不太稳的助手，想给它瘦瘦身：把历史砍掉一半，结果它把用户开头声明的「只回答中文」给忘了；把工具说明删了，它又开始乱调接口；可要是不删，长一点的会话每轮都顶到窗口上限。你发现自己陷在一个两难里，好像每块内容都不能少，可加在一起又装不下。

## 先破一个误解

**不是内容太多，是你把所有内容都当成了同一种东西，用同一套规则去留或删。**

上下文里的文字，生命周期根本不一样。有一类每轮都必须原样在场，比如身份、边界、输出格式；有一类只有本轮相关才该出现，比如这次要用到的工具清单和取回的材料；有一类是最近几轮的完整轨迹，过期就该滚动淘汰；还有一类压根不该进窗口，只要留个能取回的标识就够了。把这四类混成一锅，裁剪时就只能「从第几轮开始切」这种粗暴办法，切早了丢约束，切晚了超预算。

所以先补几个词。上下文窗口（context window，指一次调用里模型这一眼能看到的全部文字）是那份有限的空间；上下文预算表（见[上下文预算表](./k041-context-budget.md)）负责算出这份空间总共多大、各类能占多少；而四层结构负责回答另一个问题：在额度之内，谁排队靠前、谁用完即弃、谁根本不进场。前者管「多少」，后者管「谁」。还要记一个缩写：id（identifier，标识），指给一段外置内容编的号，凭它可以在需要时把原文取回来。

## 用办公桌来理解四层

把一次调用想成你坐到办公桌前处理一件事。桌面就那么大，是上下文窗口。你会发现桌上的东西天然分成四堆：

第一堆是贴在桌角的便签，写着「本岗只处理本部门的单、答复一律用中文」，从早到晚一直贴着，从不撤走，对应常驻层；第二堆是今天这一单才摊开的资料，办完就收进抽屉，对应按需层；第三堆是手边最近几张刚写过的便条，还热乎、随时要瞟一眼，但过一阵就被新的压到下面，对应近期层；第四堆根本不在桌上，是档案柜里编好号的文件，桌面上只留一张写着编号的小纸条，真要用时凭号去柜里取，对应外置层，那张小纸条就是前面说的 id。

对应关系里最要紧的一句是：**不是所有「需要」的内容都必须摊在桌面上**。档案柜里的文件你确实需要，但需要的只是「在要用时能取回」，不是「这一秒就摊在眼前」。很多人一听说某段历史后面可能有用，就把它整段留在窗口里，等于把整个档案柜搬到桌上，桌面自然不够用。四层结构就是把「搬上桌」和「留个号」这两件事分开。

:::quote
分层不是为了好看，是为了让裁剪有个确定的顺序：**先动的永远是低优先级的那一端，常驻层一个字都不动**。
:::

## 四层对照与两张图

先用一张表把四层的准入、每轮是否必带、裁剪方式列清楚。

| 层 | 装什么 | 每轮 | 裁剪方式 |
|---|---|---|---|
| 常驻层 | 身份、边界、输出格式 | 必带 | 不裁剪，尽量写短写死 |
| 按需层 | 本轮相关工具、取回材料 | 相关才带 | 先判相关，不相关整组挡在门外 |
| 近期层 | 最近几轮完整轨迹 | 必带 | 按轮数滚动淘汰最旧的 |
| 外置层 | 历史原文、大对象 | 不进场 | 只带标识，需要时按号取回 |

再看一次组装时四类内容是怎么排队的：

:::figure 四层内容进入窗口的先后顺序
@flow
常驻层入场|按需层筛选|近期层滚动|外置层留号|按额度截断
:::

注意最后一环：分层本身不保证不超额，它只保证「超了先丢谁」有规矩。真正动刀的是末尾那次按额度截断，从优先级最低的一端开始丢，而常驻层因为有「必带」标记，永远不进被丢的候选。这也解释了开头那个两难：你之前一刀切历史，把本该常驻的约束和本该滚动的轨迹一起切了，自然会丢掉「只回答中文」这句。

:::figure 两种组装方式的差别
@compare
全量摊在桌面::无关内容也占额度|裁剪没有先后顺序|常驻约束容易被切掉
按四层排队::每类有明确准入|先丢低优先级那端|外置原文不进窗口
:::

:::warn 顺序也会影响效果
同一批内容，摆法不同结果也不同。常驻层放在最前头定调，用户本轮的问题放在末尾离模型最近的位置，早期历史压成摘要夹在中间。别把大段旧材料铺在最前面、把当前问题埋进中段，长材料中间的内容本来就更易被忽略，这一点在[上下文膨胀与中间遗失](./k049-context-bloat.md)里会展开。
:::

## 再往深问两层

:::ask 那如果外置层的内容本轮真的要用，取回来之后不就又占满窗口了吗？
:::

取回不等于整段倒进来。外置层的设计里，取回动作应当带两个约束：一是按相关度只取需要的那几片，而不是把整份历史原文搬回来；二是取回后仍要过一遍按需层的准入，超预算照样先裁。也就是说 id 解决的是「能不能找到」，不是「找到就全用」。真正省额度的地方在于：绝大多数轮次里，你只需要那张写着编号的小纸条，压根用不着开柜。只在本轮明确点名某份材料时，才把相关的片段取出来，用完即弃。这套「按相关度取片段」的做法，会在[检索式召回压缩](./k045-retrieval-compression.md)里单独讲。

:::ask 再深一层：四层是固定的吗？长任务里能不能把某段历史从近期层挪成常驻层？
:::

不建议在运行时随意挪动。常驻层的定义就是「写死、每轮必带、不随会话增长」，一旦允许把历史挪上来，它就会像滚雪球一样越积越多，把预算表的固定份额撑破，分层也就失去了意义。真有「必须长期记住的一件事」，正确做法不是塞进常驻层，而是把它抽成一条紧凑的结构化字段，用很省的字数稳定携带，这是[结构化状态摘要](./k046-structured-state.md)的职责。判断标准很简单：会随轮数增长的内容，一律不进常驻层；常驻层只放那些从第一帧到最后一帧都不变的东西。

## 一份能跑的四层组装器

下面这份实现只用标准库，把四层的准入、排队、外置留号和按额度截断都做进去，复制成文件直接运行即可。

```python
# layers.py —— 只用标准库，python layers.py
import json


class LayeredContext:
    def __init__(self, limit):
        self.limit = limit
        self.always = []       # 常驻层：每轮必带
        self.on_demand = []    # 按需层：本轮相关才带
        self.recent = []       # 近期层：最近几轮原文
        self.external = {}     # 外置层：只存原文，不直接注入

    def put_external(self, key, text):
        # 存进外置层，返回编号；这个动作本身不会让窗口变大
        self.external[key] = text
        return key

    def assemble(self, need_keys, recent_rounds):
        # 常驻层无条件进入，优先级最高
        blocks = list(self.always)
        # 按需层只挑本轮点名的编号，不相关的整组挡在门外
        picked = [t["text"] for t in self.on_demand if t["key"] in need_keys]
        # 近期层只取最后若干轮
        recent = list(self.recent[-recent_rounds:])
        # 外置层只生成一张写着编号的小纸条，绝不带原文
        refs = ["引用:" + k for k in need_keys if k in self.external]
        ordered = blocks + picked + recent + refs
        # 超额度时从队尾开始弹，且保证常驻层永远不被弹出
        while sum(len(s) for s in ordered) > self.limit and len(ordered) > len(blocks):
            ordered.pop()
        return ordered


if __name__ == '__main__':
    c = LayeredContext(limit=120)
    c.always = ["你是客服助手，只回答与本单有关的问题"]
    c.recent = ["用户问运费", "答：包邮", "用户问时效", "答：三天到"]
    c.on_demand = [{"key": "f1", "text": "工单要点：已同意退货"},
                   {"key": "f2", "text": "无关工具说明"}]
    c.put_external("f1", "一份很长的历史工单原文" * 20)
    out = c.assemble(need_keys=["f1"], recent_rounds=2)
    joined = "".join(out)
    assert "你是客服助手" in joined                        # 常驻层永远在
    assert "很长的历史工单原文" not in joined             # 外置原文不进窗口
    assert "引用:f1" in joined                            # 只带编号小纸条
    assert "无关工具说明" not in joined                   # 不相关项被挡住
    assert sum(len(s) for s in out) <= 120               # 总量受限
    assert json.loads(json.dumps({"out": out}))["out"] == out  # 可序列化
    print("通过 6/6 项：常驻必带、外置只带引用、按需遮挡与总量受限均正确")
```

1. 用四个字段分别表示四层：`always` 是常驻层列表，`on_demand` 是按需层的候选，`recent` 是近期层轨迹，`external` 是外置层的字典，只存原文而不直接注入。
2. `put_external` 把一段大原文存进外置层，返回它的编号。注意存进去的动作本身不会让窗口变大，这正是外置层省额度的关键。代码里那段重复了很多次的长原文只是构造场景，用来验证「它确实没进窗口」。
3. `assemble` 先无条件把常驻层放进结果；再从 `on_demand` 候选中只挑本轮点名的编号，不相关的整组挡住；近期层只取最后若干轮；外置层则只生成一条「引用:编号」的小纸条，绝不带原文。
4. 组装顺序是常驻、按需、近期、引用，优先级从高到低。末尾那个循环在超额度时从队尾开始弹，直到总量回到限额以内，循环条件里带着 `len(ordered) > len(blocks)`，保证常驻层那几项永远不会被弹出。
5. 主函数里构造一个限额一百二十单位的小窗口，六条断言分别验证常驻必带、外置原文不进窗口、只带引用、不相关项被遮挡、总量不越界、结果可被 JSON（JavaScript Object Notation，一种轻量级的结构化数据格式）序列化，最后打印通过项数。

想看得更清楚，可以把 `need_keys` 改成空列表再跑一次：引用和按需项都会消失，只剩常驻层和近期层，说明按需层确实是「相关才带」；再把 `limit` 调得非常小，会看到队尾内容被逐个弹掉，而常驻层始终在。这些都可以自己复现，不需要任何外部服务。

## 踩过的坑

- **把常驻层当记事本**：现象是系统提示越写越长、每轮都跟着涨 → 原因是把会话里冒出来的新约束不断追加进常驻层 → 怎么改：常驻层只放全程不变的内容，会增长的改用结构化字段携带。
- **外置层存了却整段注入**：现象是做了外置照样超支 → 原因是取回时把整份原文倒回窗口 → 怎么改：按相关度只取片段，取回后仍过按需准入与额度截断。
- **按需层判相关判得太松**：现象是工具清单还是一大串 → 原因是把「可能用得上」当成相关 → 怎么改：只带本轮明确点名的，与本轮无关的工具一组都不给，既省额度也少选错。
- **近期层滚动时把约束一起滚掉**：现象是聊久了忘了开头的语种要求 → 原因是把用户首轮的声明当成普通历史 → 怎么改：把这类长期约束抽到常驻层或结构化状态，不参与滚动淘汰。
- **四层之外又私自加层**：现象是组装逻辑自己都绕不明白 → 原因是每层都配了特例 → 怎么改：先严格按四类归并，确有需要再在某一层内部分组，不要平铺出更多层。

## 三句话

四层上下文结构是按生命周期把输入分成常驻、按需、近期、外置四类，分别规定谁进场、谁滚动、谁只留编号。
关键做法是组装时按优先级排队、超额度从低端裁起，并让常驻层永远不被裁。
当任务只有一两轮、内容天生很短时，不必分层，直接拼装再配一张简单预算表就够。

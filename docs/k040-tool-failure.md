# 工具失败分类与重试策略

## 场景提问

你给工具调用写了一句「出错就重试三次，还不行就报错」。上线后怪事接连冒出来：用户把日期填成了「下周三」，工具明确回了「参数格式不对」，程序却老老实实又试了三次，三次都错，白白多烧了三轮调用；另一个接口被限流，明明回执里写着「请稍后再来」，你的三次重试却一股脑挤了上去，越挤越堵，把对方推得更慢；还有一次请求在半路断连，状态根本说不清，程序照样「重试三次」，结果同一笔动作被做了两遍。三次重试，一次都没帮上忙。你盯着日志里那一串几乎一样的报错，忽然意识到：它们长得像，性质却完全不同，可你的代码从头到尾只把它们当成了一个词——「失败」。

## 破误解

**不是重试次数设得不够或太多，是压根没给失败分类——把所有报错塞进同一个「再试几次」，等于假定每种失败都值得重发、且重发一定无害。**

先把「错误」和「失败」拆开看。工具返回一句报错，是一个携带信息的信号：它往往已经告诉你「这是哪一类问题」，甚至是「你该等多久」。所谓失败分类（error classification，指按错误的来源与可否自行恢复，把五花八门的报错归到少数几类，再给每类配固定动作），要做的第一件事就是别把这信号扔掉。最少要分四类。可重试的瞬时错误：连接被重置、网关临时报错，特点是「这次没成，但同样的请求过一会儿很可能成」，适合退避后再发。限流错误：对方明确要求「慢一点」，它自带节奏信息，该等更久、且别一窝蜂挤上去。永久错误：参数非法、越权、目标不存在，特点是「同样的请求再发一万次也不会变好」，重发纯属浪费，还可能把越权动作重复触发。状态未知：超时、半路断连，你连「对方做没做」都不知道，这类根本轮不到谈重试，得先查清真相——这正是 [超时不等于没执行](./k039-timeout-reconcile.md) 要处理的那一类。

很多人把「重试」当成一个单独开关，其实它是一串受约束的决策：这次错误属于哪一类、这类允许重试吗、重试前要不要退避、退避多久、总共允许试几次、这动作重试安不安全。[错误分类与用户可读报错](./k131-error-classify.md) 讲的是怎么把底层五花八门的异常收敛成稳定类别，本篇讲的是收敛之后每一类各走哪条路。还有一层最容易被漏掉：重试的前提是「再做一次不会闯祸」。只读查询、天然幂等的动作，重发无妨；可一次下单、一次发信、一次写库，若无 [幂等键与副作用防重](./k038-idempotency-key.md) 那把稳定标识兜着，重试就是拿重复副作用冒险。所以「该不该重试」从来不是只看错误类型就能拍板，还得看这次动作本身怕不怕被做两遍。把这两件事叠在一起，才是一张能用的分类表。

## 生活类比

把它想成医院的分诊台。病人来了，护士不会给每个人发同一张「再去排三次队」的条子。她先看症状：只是有点低烧、化验要等一会儿的，安排「过半小时回来复查」——这是可重试的瞬时错误，等一等大概率就好；抽血处贴着「当前人多，请错峰」的，会给你一个更靠后的号、让你别挤在窗口——这是限流，对方已经把节奏告诉你了；材料根本没带齐、或者挂错了科室的，护士会直接说「这个不用再排，先把材料补齐 / 换到对的科室」——这是永久错误，重复排队一万次也办不成；还有一类最特殊，病人说自己「刚才好像做过检查了，但单子找不到了」，护士绝不会让他重新抽一次血，而是先去系统里查「到底查没查、结果是什么」——这就是状态未知，得先对账再定。

对应关系很具体：症状与分诊单，就是错误码及其类别；「过半小时回来复查」，是带退避的重试；那个错峰的号，是限流给的最长等待；「把材料补齐再来」，是把「参数不对」这类信息反馈回去改输入，而不是原样重发；「去系统里查有没有做过」，是拿稳定标识对账；「重复排队也办不成」，点破了永久错误为什么必须立即停。这个比喻还藏着两处要害。其一，分诊必须先于处置：不先看清是哪一类，就谈不上「该等还是该停」，把状态未知的病人直接送去重新抽血，等于制造一次本可避免的重复动作。其二，就算都归到「可以再来」那一类，也不是无限次：复查三次还不见好，护士会转给医生、不会让你一直排下去——这就是重试预算，试到头得有个收场，[指数退避与重试预算](./k108-retry-backoff.md) 讲的就是「等多久、最多几次、怎么别同时挤」。

## 自绘示意图

:::figure 一次报错之后该走的分类链
@flow
读到错误码|归入四类之一|按类决定动作|退避或停|留痕并反馈
:::

五格里最容易被跳过的是「归入四类之一」。很多人从「读到错误码」直接跳到「退避或停」，于是「参数不对」和「网络抖了一下」被同一套逻辑处理。补上分类这一格，后面的动作才有依据：不是所有错误都进退避，也不是所有错误都该停，得按类分流。

:::figure 工具报错最少要分的四类
@stack
可重试瞬时错::连接重置临时报错，退避后再发
限流错::对方要求慢一点，等更久且别扎堆
永久错::参数越权不存在，重试也不会变好
状态未知::超时或半路断连，转对账查真相
:::

四行里，「状态未知」最不该被当成可重试。它的正确动作不在这一列里往下走，而是拐去对账——因为连「做没做」都没确定，谈「再做一次」为时过早。把四类并列摆出来，正是为了看清哪些能就地重试、哪些必须拐去别的路径。

:::figure 一律重试与先分类再决策的差别
@compare
一律重试到上限::永久错白等|未知态被重做|限流被挤兑
先分类再决策::永久错立即停|未知态先对账|按类给退避
:::

左边把重试当成一个不管不顾的循环，看着省事，代价是把永久错误拖成浪费、把未知状态拖成重复；右边多了一次分类，换来的是四种错误各归各位。差别不在重试得多不多，而在重试之前有没有先弄清「这错误到底是哪一类」。

## 层层追问

:::ask 那如果错误码看不懂、或者对方只回了一句含糊的文本呢？
:::

这正是分类要「结构化」的原因。靠在异常文本里找有没有「超时」「失败」这类字样来判断，非常脆：换个措辞就失效，同一句话在不同接口含义还可能相反。稳的做法是让工具层把底层异常收敛成一小撮稳定的类别或错误码，分类表只认这个结构化的值；遇到表里没有的码，保守地当成「不可重试」并留痕，而不是乐观地当成「再试试看」——猜错方向的代价不对称，把永久错误误判成可重试只是多花点钱，把未知状态误判成可重试却可能重复扣款。第二层是：同一个码在不同动作上也可以有不同的处置。「连接被重置」落在只读查询上，退避重发毫无风险；落在一次写库上，若这动作没有幂等保护，就应当直接停下、不重试。也就是说，分类不能只查一张全局表，还得叠上「这次动作是不是幂等 / 只读」这个维度，[参数合法性](./k034-param-validity.md) 里的「先校验再执行」和 [权限矩阵](./k037-permission-matrix.md) 里的「这个动作在不在许可范围内」，都是这张表在写入前该一起过一遍的前提。至于怎么把这些收敛后的类别、原始码、重试了几次记成可查的记录，交给 [结构化日志](./k095-structured-log.md) 与 [链路追踪字段](./k094-trace-fields.md)，事后才答得上「当时为什么判成可重试」。

:::ask 那可重试的错误就多试几次总没坏处吧？退避是不是随便设个固定值就行？
:::

恰恰相反，可重试这一类最容易闯祸，因为它「多半能成功」会让人放松警惕。第一层是预算与节奏：重试得有上限和总截止时间，退避要随次数拉长，让压力别叠在下游最难受的时刻；固定间隔的一串重试，在很多人同时出错时会整齐地撞在一起，把一次小抖动放大成挤兑，所以退避还要带一点错开的抖动，别让所有调用步调一致。[指数退避与重试预算](./k108-retry-backoff.md) 讲的就是「等多久、最多几次、怎么给这串动作封顶」。第二层是收场：预算用尽仍不成功，不能悄悄返回一个含糊的失败就完事，得有个明确落点——降级到一个较简的结果、把状态挂起留待人处理、或触发 [熔断器](./k104-circuit-breaker.md) 在连续失败到阈值后先别再往下游打，让对方喘口气；这三者在 [优雅降级](./k020-graceful-fallback.md) 与 [优雅恢复](./k110-graceful-resume.md) 里各有位置。第三层常被忽略：还有一类「失败」根本不该由重试来解决，而是该把信息送回去改输入。工具回「日期格式不对」，正确动作是把这句可读的报错反馈给模型、让它重新给一个合法参数，这属于 [错误反馈给模型](./k029-error-feedback.md) 的活；把它当瞬时错误原样重发三次，参数一次都没变，三次结果自然一模一样。所以「重试」和「改了输入重新决策」是两件事：前者是同一个请求再发一次，后者是换一个请求，把两者混为一谈，就会出现开头那种「明明报错写得很清楚，却白试三轮」的浪费。至于把一次次失败摆在一起看哪些是成片出现的，可以对照 [失败模式清单](./k150-failure-modes.md)。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一串预设的错误码模拟工具的多次返回，演示「先分类、再按类决策」：可重试的退避后成功、限流的等待逐次拉长、永久错误一次就停、状态未知转对账、预算用尽会停下、写操作没有幂等保护就不重试，最后用一个轻量熔断状态演示连续失败到阈值后不再往下游打。全程确定性、不真的等待、不联网，复制到任意装有 Python 的机器上直接运行即可。

```python
from collections import Counter

RETRYABLE = "retryable"
RATE_LIMITED = "rate_limited"
FATAL = "fatal"
UNKNOWN = "unknown"

ERROR_KIND = {
    "conn_reset": RETRYABLE,
    "gateway_5xx": RETRYABLE,
    "too_many_requests": RATE_LIMITED,
    "bad_param": FATAL,
    "no_permission": FATAL,
    "not_found": FATAL,
    "timeout": UNKNOWN,
    "conn_dropped_mid": UNKNOWN,
}


def classify(code):
    """把具体错误码归到四类之一；表里没有的码保守地当作致命。"""
    return ERROR_KIND.get(code, FATAL)


def backoff(kind, attempt):
    """确定性的等待秒数：普通可重试线性拉长，限流指数拉长，都不真的睡。"""
    if kind == RATE_LIMITED:
        return 2 ** attempt
    return attempt


def run_with_policy(codes, max_attempts=4, idempotent=True):
    """按分类决定动作，返回最终结论、逐步轨迹与每次等待。"""
    trace = []
    waits = []
    for i, code in enumerate(codes[:max_attempts], start=1):
        if code == "ok":
            trace.append((i, code, "done"))
            return {"result": "success", "trace": trace, "waits": waits}
        kind = classify(code)
        trace.append((i, code, kind))
        if kind == FATAL:
            return {"result": "fatal", "trace": trace, "waits": waits}
        if kind == UNKNOWN:
            return {"result": "reconcile", "trace": trace, "waits": waits}
        if not idempotent:
            return {"result": "need_idempotency", "trace": trace, "waits": waits}
        if i == max_attempts:
            break
        waits.append(backoff(kind, i))
    return {"result": "budget_exhausted", "trace": trace, "waits": waits}


class Breaker:
    """连续失败到阈值就打开，之后直接拒绝，别再冲击下游。"""

    def __init__(self, threshold):
        self.threshold = threshold
        self.consecutive = 0
        self.open = False

    def record(self, ok):
        if ok:
            self.consecutive = 0
            self.open = False
        else:
            self.consecutive += 1
            if self.consecutive >= self.threshold:
                self.open = True

    def allow(self):
        return not self.open


def main():
    checks = []

    # 分类表本身：每个码都要落到预期的类别
    checks.append(("连接重置归为可重试", classify("conn_reset") == RETRYABLE))
    checks.append(("网关报错归为可重试", classify("gateway_5xx") == RETRYABLE))
    checks.append(("限流单独成一类", classify("too_many_requests") == RATE_LIMITED))
    checks.append(("参数错误归为永久", classify("bad_param") == FATAL))
    checks.append(("越权归为永久", classify("no_permission") == FATAL))
    checks.append(("超时归为状态未知", classify("timeout") == UNKNOWN))
    checks.append(("看不懂的码保守当永久", classify("brand_new_error") == FATAL))

    # 可重试的瞬时错误：退避两次后成功，且等待逐次拉长
    r1 = run_with_policy(["conn_reset", "conn_reset", "ok"])
    checks.append(("瞬时错误最终成功", r1["result"] == "success"))
    checks.append(("瞬时错误试了三次", len(r1["trace"]) == 3))
    checks.append(("普通退避线性拉长", r1["waits"] == [1, 2]))

    # 限流：等待按指数拉长，别一窝蜂挤上去
    r2 = run_with_policy(["too_many_requests", "too_many_requests", "ok"])
    checks.append(("限流最终成功", r2["result"] == "success"))
    checks.append(("限流退避指数拉长", r2["waits"] == [2, 4]))
    checks.append(("限流等得比普通久", r2["waits"][0] > r1["waits"][0]))

    # 永久错误：一次就停，后面就算摆着成功也不重试
    r3 = run_with_policy(["bad_param", "ok", "ok", "ok"])
    checks.append(("永久错误立即停", r3["result"] == "fatal"))
    checks.append(("永久错误只试一次", len(r3["trace"]) == 1))
    checks.append(("永久错误不产生等待", r3["waits"] == []))

    # 状态未知：拐去对账，绝不盲目重发
    r4 = run_with_policy(["timeout", "ok", "ok"])
    checks.append(("状态未知转对账", r4["result"] == "reconcile"))
    checks.append(("状态未知只试一次", len(r4["trace"]) == 1))
    checks.append(("状态未知不产生等待", r4["waits"] == []))

    # 写操作没有幂等保护：连可重试错也不重发
    r5 = run_with_policy(["conn_reset", "ok"], idempotent=False)
    checks.append(("非幂等写动作用可重试错也停", r5["result"] == "need_idempotency"))
    checks.append(("非幂等判断发生在退避之前", r5["waits"] == []))

    # 预算用尽：到上限就停，最后一次不再白等
    r6 = run_with_policy(["conn_reset"] * 6, max_attempts=4)
    checks.append(("预算用尽会停下", r6["result"] == "budget_exhausted"))
    checks.append(("尝试次数不超过预算", len(r6["trace"]) == 4))
    checks.append(("最后一次不再安排等待", r6["waits"] == [1, 2, 3]))

    # 四类结论确实各走各的路，不是同一个循环
    tally = Counter([r1["result"], r2["result"], r3["result"],
                     r4["result"], r5["result"], r6["result"]])
    checks.append(("六组场景落到五种不同结论", len(tally) == 5))
    checks.append(("成功结论出现两次", tally["success"] == 2))

    # 连续失败到阈值后熔断打开，后续请求直接被挡
    breaker = Breaker(threshold=3)
    rejected = 0
    for ok in [False, False, False, False, False]:
        if not breaker.allow():
            rejected += 1
            continue
        breaker.record(ok)
    checks.append(("连续三次失败后熔断打开", breaker.open is True))
    checks.append(("熔断后两次请求被挡下", rejected == 2))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `ERROR_KIND` 是整段的分类表，把八个具体错误码收敛成四个类别。分类只认这个结构化映射，不去异常文本里找关键字；`classify` 用 `dict.get` 给一个默认值，凡表里没有的新码一律当 `FATAL` 保守处理，避免把陌生错误乐观地送去重试。
2. `backoff` 给出确定性的等待秒数：普通可重试错误按第几次尝试线性拉长（1、2、3……），限流按指数拉长（2、4、8……），从而让「对方要求慢一点」这一类真的等得更久。这里只返回数字、不调用 `time.sleep`，是为了让整段可复现、可手算，也不占用真实时间。
3. `run_with_policy` 是分类驱动的执行器，分支顺序就是策略本身：成功直接返回；`FATAL` 立即停，一步都不重试；`UNKNOWN` 拐去 `reconcile` 对账，同样不重发；接着检查 `idempotent`，写动作没有幂等保护就连可重试错误也停下；只有既属于可重试 / 限流、又带幂等保护时，才在未到预算上限前记一次退避并继续。
4. 注意 `FATAL` 与 `UNKNOWN` 的返回都发生在 `waits` 被写入之前，所以「永久错误」和「状态未知」不会产生任何等待，也不消耗重试预算——这两类本来就不该进入重试循环。`i == max_attempts` 时直接 `break`，因此最后一次失败后不再安排一次没有下文的等待。
5. `main` 先逐条验分类表本身，再验四类各自的处置：瞬时错误三次成功且等待为 `[1, 2]`，限流等待为 `[2, 4]` 且比普通更久，永久错误「后面摆着三个 ok 也只试一次」，状态未知只试一次便转对账，`idempotent=False` 时在退避之前就停下。这几组断言把「一次就停」和「退避后再发」的差别钉死。
6. 预算场景用六个连续的 `conn_reset` 配 `max_attempts=4`，断言轨迹恰好四条、等待为 `[1, 2, 3]`；再用 `Counter` 统计六组场景的结论，断言确实落到五种不同结果、其中成功两次，说明这不是「同一个循环跑六遍」，而是四类各归各位。
7. `Breaker` 是收场那一层：连续失败达到阈值就把 `open` 置真，`allow` 随后直接拒绝，五次连续失败里有两次被挡在门外。结尾 `assert passed == len(checks)` 保证任何一条性质被破坏都会以非零状态退出，并打印「通过 N/N 项」。

有一处要如实说明：这里用预设的错误码序列代表工具的多次返回，用一串整数代表退避秒数（不真的等待、也不加错开用的抖动），用一个计数对象代表熔断状态，全是为了让四种错误的分流不依赖网络、账号或第三方包就能独立跑通。它演示的是「结构化分类 → 按类决策 → 幂等前提 → 退避与预算 → 熔断收场」这条链，不是任何具体请求库的实现。真实系统里，退避要落在真实时间上并带一点抖动以免调用扎堆，重试预算还要受一个总的截止时间约束，熔断打开后也要有探测恢复的办法，不能像演示里一开就永远不关。

## 踩坑与边界

- **不分类、一律重试到上限**：现象是参数错白试三轮、越权被重复触发、限流被越挤越堵 → 原因是把所有报错当成同一种「失败」 → 先按结构化错误码分成可重试、限流、永久、状态未知，每类配固定动作，见 [错误分类与用户可读报错](./k131-error-classify.md)。
- **把状态未知当成可重试**：现象是超时后照常重发，同一笔动作被做了两遍 → 原因是没分清「没拿到回执」和「没执行」 → 这类拐去按稳定标识对账，见 [超时不等于没执行](./k039-timeout-reconcile.md)，绝不进入重试循环。
- **靠异常文本猜类别**：现象是对方换个措辞，原本该停的错误突然被送去重试 → 原因是分类依据是不可靠的字符串匹配 → 让工具层收敛成稳定错误码，表外的码保守当不可重试，并用 [结构化日志](./k095-structured-log.md) 留痕。
- **给写操作套只读动作的重试规则**：现象是查询重试没事，下单重试却重复扣款 → 原因是只看错误类型、没叠上「这动作怕不怕被做两遍」 → 写动作先有 [幂等键与副作用防重](./k038-idempotency-key.md) 再谈重试，没保护就停。
- **有退避却没预算、没收场**：现象是失败时无限打转，或预算用尽后悄悄返回含糊失败 → 原因是把重试当成不用封顶的循环 → 设最大次数与总截止时间，按 [指数退避与重试预算](./k108-retry-backoff.md) 封顶，用尽就降级、挂起或交给 [熔断器](./k104-circuit-breaker.md)。

还要分清两处近似概念。「重试」和「改输入重新决策」不是一回事：前者是同一请求再发一次，适用于可重试的瞬时错误；后者是把「日期格式不对」这类可读报错送回模型重给参数，属于 [错误反馈给模型](./k029-error-feedback.md)，对永久错误才对路。「重试」和「兜底」也不是一回事：重试是「再争取一次成功」，[超时兜底](./k109-timeout-fallback.md) 与 [优雅降级](./k020-graceful-fallback.md) 是「争取不到时给一个交代」，前者有上限，后者是上限之后的落点。至于什么时候不必上这套分类：一个工具如果只有只读、无副作用、且调用量极小，一句简单重试也许够用；但只要它可能被限流、可能改外部状态、或返回的报错还会被模型拿去改下一步动作，就值得先把失败分清楚——把 [工具结果](./k035-tool-result.md) 里「返回给模型的内容要可核对」和这里合起来看会更明白：一句被抹平类别的「失败」，会让模型错把该改参数的情形当成该等等看。

## 三句话小结

工具失败分类是先把五花八门的报错收敛成可重试、限流、永久、状态未知四类，再给每类配上退避重发、等更久、立即停下或转对账这些不同动作，而不是一律「再试几次」。

关键做法是分类只认结构化错误码、永久与未知一步都不重试、写动作先有幂等保护才准重发、退避随次数拉长并封顶预算、预算用尽就降级挂起或熔断收场。

当工具只读、天然幂等且失败形态单一时，简单重试也许够用；但只要报错可能被模型拿去改下一步、或动作会改动外部状态，就别把「失败」当一个词草草处理。

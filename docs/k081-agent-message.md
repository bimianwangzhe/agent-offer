# 主体间消息契约

## 场景提问

你做了一个能查资料、能写摘要的助手，单独跑得挺稳。后来需求变成「查完资料先交给一个专门做审校的助手，审校通过再交给第三个负责归档的助手」。你图省事，把第一环最后那段输出原样转发给下一环，结果第二环不知道「到底什么算审完」，第三环把中间的讨论草稿当成了要归档的正式正文，最后交出来的东西，谁也说不清是从哪一步开始跑偏的。明明每一环单独看都在正常干活，串起来怎么就失控了？

## 破误解

**不是哪个助手不够聪明，是把「一段自然语言」当成了「一份移交契约」**——把任务交给另一个能自己拿主意的决策主体，靠的不是把聊天记录转发出去，而是一份字段明确、完成标准可判定的结构化消息。

先把几个词说清。决策主体，白话讲就是「一段能自己决定下一步做什么的程序」，它和一段被动等参数的函数不同，它拿到任务后会自行判断、拆解、调用工具。契约（contract，双方事先约定好的字段清单与各自含义）是这次移交的规矩：写清楚要转交什么、不许转交什么、什么算做完。完成标准，也叫验收条件（acceptance criteria，一条能用「是或否」回答的判定，而不是「做得好一点」这种模糊话），是整份契约里最容易被漏掉、又最要紧的一格。移交（handoff）指任务连同必要上下文从一个主体转到另一个主体；回执（reply / callback，做完之后把结果按约定形状交还给指定一方）决定这条链能不能合上。还有两个后面代码里会用到的词：能力注册表（capability registry，一张登记「谁会处理哪类任务、认识哪一版消息格式」的表）与适配器（adapter，把一种字段形状翻译成另一种形状的薄薄一层）。这里说的都是通用做法，不绑定任何具体的通信协议或产品。

很多人以为「把上一个助手说过的话贴给下一个」就等于交接了，其实丢的正是那些没被说出口的东西：原始目标、硬性约束、判定做完的条件、结果该交给谁。自然语言里这些往往隐含在语气里，转一次手就淡一层，转两次就几乎没了。

## 生活类比

把它想成医院里的「转诊单」，而不是病人自己拎着一沓病历去下一个诊室口头复述。

主诊医生把病人转给专科医生时，不会只说「这人你看看」，而是填一张单子：病人标识（对账用，保证转的是同一个人）、初步诊断与已做检查（必要上下文，只带相关的，不带全部闲聊）、请专科解决什么问题（任务目标与边界）、什么情况算处理完毕（完成标准，比如「明确给出可否手术的结论」）、结论回写给谁（回执地址）。专科医生照单处理后，不是在病历上随意写两句，而是按单子上的每一条判定逐项回填，再把结果送回主诊那里归档。

对应关系要点在三处。第一处是「只带必要上下文」：转诊单不会把病人从挂号起说的每句话都复印一遍，那样专科医生反而淹在噪声里；放到系统里，就是只把关键事实与原始材料的存储位置传过去，而不是把整个过程日志整段塞进下一个窗口。第二处是「完成标准可判定」：「你看着办」和「明确给出可否手术的书面结论」差别巨大，后者能被核对，前者只能靠猜；结构化消息要求每条完成标准都写成能回答「是或否」的判定项。第三处是「按标识对账」：病人标识从头到尾不变，哪怕中途又转了一次诊，也能凭它把几段结论拼回同一个人的完整病历；系统里这个标识就是任务标识（task id），它保证任务不会在转手中被认成另一件事。

最怕的不是转错科室，而是把转诊单弄丢了、只剩一句「按刚才那个思路继续」——下一个医生根本不知道「刚才」指什么。这正对应场景里那个「转发整段输出」的做法：话是传过去了，规矩没传过去。

## 自绘示意图

:::figure 一份移交契约里必须写明的字段
@stack
任务标识::全程不变的对账键，链式移交也靠它认回同一件事
目标与边界::要对方解决什么，以及明确不做什么
必要上下文::只带关键事实与材料引用，不转发全程对话
完成标准::逐条可判定的验收条件，而非模糊期望
回执地址::结果交给谁、用什么形状交还
:::

:::figure 一次移交从打包到回执的完整链路
@flow
约定字段|打包必要上下文|声明完成标准|接收方执行|按标识回执
:::

:::figure 转发对话与结构化契约的差别
@compare
转发整段对话::约束层层丢失|完成标准含糊|无法按标识对账
结构化消息契约::字段可校验|验收可判定|结果能归并归因
:::

第一张图是「写什么」，第二张图是「怎么走」，第三张图是两种做法的代价。请留意第二张图里「声明完成标准」排在「接收方执行」之前：一旦顺序反了，接收方只能凭自己的理解猜「做完」是什么样，回执也就无从逐条核对。第三张图右边那句「结果能归并归因」，说的是当任务又转了第二手、第三手，仍可凭同一个任务标识把各段结论拼回一条完整链路——这正是场景里最缺的东西。

## 层层追问

:::ask 那如果接收方是另一个人写的、字段叫法完全不一样呢？
:::

这恰恰是「能力注册表 + 适配器」要解决的。别指望所有主体都用同一套字段名：一个把「完成标准」叫 `done_criteria`，另一个可能叫 `acceptance`；一个用 `reply_to` 记回执方，另一个用 `report_to`。硬要求大家改名既不现实，也容易在改动中悄悄串味。稳妥做法是给每个主体在能力注册表里登记两件事：它能处理哪类任务、它认识哪一版消息格式。移交时先查表，确认对方确实能接这类任务，再由适配器把消息从当前版本翻译成对方认识的形状——注意是「翻译字段、保留内容」，不是重新解释任务。翻译规则集中在一处，字段映射写死、可测试，而不是散落在每个主体里各改一遍。这么做的额外好处是契约测试有了抓手：只要断言「翻译前与翻译后，任务标识、完成标准条数、回执地址都不变」，就能挡住绝大多数改名改漏的低级错误。这条纪律和[解耦适配层](./k077-adapter-layer.md)里「把业务代码与框架接口隔开」是同一套思路，只不过这里隔开的是「两个决策主体」。

:::ask 那如果任务做到一半，接收方还要再转给第三个主体呢？
:::

追到第二层，问题就从「一次移交」变成「链式移交」，风险也随之放大。最典型的翻车是「转述失真」：第一手把原始完成标准写成了「给出可否手术的结论」，第二手怕麻烦只留了句「按上一步继续」，到第三手就彻底没了判定依据，于是各自凭感觉收尾。所以链式移交有一条硬规矩：任务标识与原始完成标准是 immutable 的（不可改写），每个中间主体只能往「必要上下文」里追加自己的结构化结果，不能删改原始目标与验收条件。第二层再往下一问：结果怎么合上？答案是回执沿原路归并——每一跳都把「本次由谁处理、逐条判定结果如何」结构化回填，最终由一个归集方按同一个任务标识把各段拼齐。这样出问题时能定位到「是第几跳、哪个主体、哪条判定」没达标，责任可归因。若不做这件事，就会像场景里那样：三环都在干活，却没人能回答「到底哪儿开始偏的」。链式结构下共享哪些字段、谁有权改哪一格，可以对照[状态共享、冲突处理与失败恢复](./k120-shared-state.md)；而把这段移交当成一次可回放的动作记录下来，则是[时间旅行、重放与分叉](./k145-time-travel.md)要处理的事。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一张能力注册表、一个字段适配器和几个本地假决策主体，完整演示「契约校验 → 按能力派发 → 字段翻译 → 逐条判定 → 链式移交保留原标准」，结尾用一组断言逐条核验。复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。

```python
"""主体间消息契约：能力注册表 + 适配器 + 链式移交。"""
from dataclasses import dataclass, asdict

REQUIRED = ("task_id", "goal", "context", "done_criteria", "reply_to", "version")


@dataclass
class Contract:
    """一份移交契约：字段显式、完成标准可判定。"""
    task_id: str
    goal: str
    context: dict
    done_criteria: list
    reply_to: str
    version: str


def validate(msg):
    """契约校验：必填字段齐全，且完成标准非空、逐条带判定项。"""
    missing = [k for k in REQUIRED if k not in msg or msg[k] in (None, "", [], {})]
    if missing:
        return False, "缺少字段:" + ",".join(missing)
    if not isinstance(msg["done_criteria"], list) or not msg["done_criteria"]:
        return False, "完成标准需为非空列表"
    for c in msg["done_criteria"]:
        if "check" not in c:
            return False, "每条完成标准要带 check 判定项"
    return True, "契约合法"


class CapabilityRegistry:
    """能力注册表：登记每个主体能处理哪类任务、认识哪版消息。"""
    def __init__(self):
        self.table = {}

    def register(self, agent_id, task_type, understands):
        self.table[agent_id] = {"task_type": task_type, "understands": understands}

    def can_handle(self, agent_id, task_type):
        return agent_id in self.table and self.table[agent_id]["task_type"] == task_type

    def understands(self, agent_id):
        return self.table[agent_id]["understands"]


FIELD_MAP = {"done_criteria": "acceptance", "reply_to": "report_to", "version": "schema"}


def adapt(msg, target, registry):
    """适配器：目标只认 v2 字段名时把 v1 翻译过去，内容一条不丢。"""
    if registry.understands(target) == "v1":
        return dict(msg)
    return {FIELD_MAP.get(k, k): v for k, v in msg.items()}


def fake_agent(msg, registry, agent_id, task_type):
    """本地假决策主体：按完成标准逐条产出可判定的结构化结果。"""
    assert registry.can_handle(agent_id, task_type), "主体未登记或不处理该任务"
    adapted = adapt(msg, agent_id, registry)
    criteria = adapted.get("acceptance", adapted.get("done_criteria"))
    verdicts = [{"check": c["check"], "passed": True} for c in criteria]
    return {"task_id": adapted["task_id"], "by": agent_id,
            "verdicts": verdicts, "all_passed": all(v["passed"] for v in verdicts)}


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    reg = CapabilityRegistry()
    reg.register("search", "summary", "v1")
    reg.register("review", "summary", "v2")   # 审校方只认 v2 字段名
    reg.register("archive", "summary", "v1")

    base = Contract(
        task_id="T-1001",
        goal="整理报告摘要并归档",
        context={"sources": ["doc-3", "doc-7"], "facts": ["已确认 A 与 B"]},
        done_criteria=[{"check": "摘要含全部已确认事实"}, {"check": "审校标注无遗漏"}],
        reply_to="orchestrator",
        version="v1",
    )
    msg = asdict(base)

    good, _ = validate(msg)
    ok(good, "完整契约通过校验")

    broken = dict(msg)
    broken.pop("done_criteria")
    bad, why = validate(broken)
    ok(not bad and "done_criteria" in why, "缺完成标准的消息被拦下")

    ok(not reg.can_handle("ghost", "summary"), "未登记主体不被派发")
    ok(reg.can_handle("review", "summary"), "已登记主体可承接任务")

    r2 = fake_agent(msg, reg, "review", "summary")
    ok("acceptance" not in r2, "回传是对账形状，不是原文转发")
    ok(r2["task_id"] == "T-1001", "移交后任务标识保持不变")
    ok(r2["all_passed"], "审校按完成标准逐条判定")

    hop = dict(msg)
    hop["context"] = dict(msg["context"])
    hop["context"]["review_verdict"] = r2["verdicts"]
    r3 = fake_agent(hop, reg, "archive", "summary")
    ok(r3["task_id"] == "T-1001", "第二跳仍保留原始任务标识")
    ok(len(r3["verdicts"]) == len(msg["done_criteria"]), "完成标准在链式移交中未被削减")
    ok(hop["reply_to"] == "orchestrator", "回执地址沿链路保留")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `REQUIRED` 与 `validate` 是整份契约的守门人：必填字段一个都不能缺、不能为空，而且每条完成标准必须带一个 `check` 判定项。把「完成标准」写成可判定的列表，而不是一句自然语言，是这份契约和「转发对话」最本质的区别。
2. `Contract` 用 `dataclass`（数据类，标准库里专门用来声明「只存字段」的对象的装饰器）把六个字段显式列出来，`asdict` 再把它转成普通字典，方便后续移交与翻译。字段显式，才能被校验、被翻译、被对账。
3. `CapabilityRegistry` 是那张能力注册表：`register` 登记「主体能处理哪类任务、认识哪版消息」，`can_handle` 在派发前拦住未登记或接错任务的主体。没有这一步，消息会被丢给一个根本不处理这类任务的主体，还往往不报错。
4. `FIELD_MAP` 与 `adapt` 组成适配器：审校方登记的是 `v2`，于是把 `done_criteria` 翻成 `acceptance`、`reply_to` 翻成 `report_to`。注意它只改键名、不改内容，任务标识、完成标准、回执地址原样带过去；`fake_agent` 里用 `adapted.get("acceptance", adapted.get("done_criteria"))` 兼容两种字段名，读的是同一份判定依据。
5. `fake_agent` 是本地假决策主体：它不联网、不调模型，只按契约里的完成标准逐条产出 `{check, passed}` 的结构化判定，并给出 `all_passed`。它演示了「回执按约定形状交还」，而不是把一堆自由文本丢回去。
6. `main` 里前四条断言验契约本身：完整契约通过、缺完成标准被点名拦下、陌生主体不被派发、已登记主体可承接。这四条对应第一张图的五格字段。
7. 中间三条验一次移交：审校回执是对账形状而非原文转发、任务标识不变、按标准逐条判定通过。这里刻意断言 `"acceptance" not in r2`，是为了证明回传的是「结果结构」而不是「收到的原文」。
8. 最后三条验链式移交：把审校结果作为结构化字段追加进 `context` 再转给归档方，第二跳任务标识仍是 `T-1001`、完成标准条数没被削减、回执地址仍指向归集方。这正是层层追问里「原始目标与完成标准不可改写」的落地。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出，并打印 `通过 11/11 项`。

有一处如实说明：这里的主体是几行确定性函数，字段翻译也只是一张写死的映射表，全是为了让整条链路不联网、不依赖账号就能跑通并手工验算。它演示的是「契约字段、能力登记、字段翻译、链式保留」的顺序与性质，不是任何具体通信协议的实现。

## 踩坑与边界

- **把整段对话当交接**：现象 → 第二环不知道完成标准，第三环把草稿当正文归档 → 原因 → 隐含约束藏在语气里，转手即丢 → 怎么改 → 用显式字段契约，只带必要上下文与材料引用，完成标准逐条写死。
- **完成标准写成模糊期望**：现象 → 「你看着办」「做得好一点」，各家收尾口径不一，无法判定做完没做完 → 原因 → 判定条件不能用是或否回答 → 怎么改 → 每条标准写成带 `check` 的判定项，回执按条回填 `passed`。
- **任务标识中途被改写**：现象 → 转了两手后，几段结论拼不回同一件事 → 原因 → 中间主体另起了新标识或覆盖了原标识 → 怎么改 → 全程复用同一个任务标识，链式移交只允许追加上下文，不改原目标与验收条件。
- **派发给不处理该任务的主体**：现象 → 消息丢过去没有报错，却得到一句答非所问的结果 → 原因 → 派发前没查能力注册表 → 怎么改 → 登记「能处理哪类任务」，派发前 `can_handle` 校验，不匹配就明确拒绝而非静默接收。
- **字段各自改名却没翻译**：现象 → 一方叫 `done_criteria`、另一方叫 `acceptance`，完成标准被当成无关字段丢掉 → 原因 → 缺少集中适配层 → 怎么改 → 用适配器把字段映射写在一处，并加一条「翻译前后标识与标准条数不变」的契约测试。

还要分清两件事：主体间消息契约管的是「任务怎么连同规矩交给另一个决策主体」，而[工具协议与标准化接入](./k078-tool-protocol.md)管的是「怎么统一接入外部能力」——前者面对一个有自己计划的自主过程，后者面对一个被动等参数的函数，别把两者写成同一层。边界也说清楚：只有单个助手、路径完全写死、不存在「交给别人拿主意」的情况，根本不需要这套契约，一张简单参数表就够；它划算的场合，是任务会跨多个能自主决策的主体流转、且需要事后说清「哪一步谁做的、按什么标准判定」。当任务标识要贯穿多跳还涉及权限与作用域时，[会话隔离与租户边界](./k105-session-isolation.md)讲的是「一次请求的作用域不能串到别的用户」，和这里的「一次移交的字段不能串味」是两种不同边界，别混。另外，若某天字段或工具形状随版本悄悄改名，也要让[版本漂移与升级策略](./k084-version-drift.md)里的契约测试覆盖这张映射表，否则翻译规则会先一步失效。站内目录可回到[从这里开始](./00-start-here.md)。

## 三句话小结

主体间消息契约，是把「把一个任务连同必要上下文交给另一个能自主决策的主体」这件事，从转发自然语言变成一份字段显式、完成标准可判定、按任务标识对账的结构化消息。

关键做法是用能力注册表先确认谁能接、用适配器翻译字段而不改内容、逐条回填判定、并让任务标识与原始完成标准贯穿整条链路不被改写。

当只有单个助手、路径完全写死、不存在跨主体流转时，不必引入这套契约，一张简单参数表反而更省事。

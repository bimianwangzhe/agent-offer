# 异常分类与可重试判定

## 一、一次「越修越糟」的小故障

你给调用加了个重试，心想「网络抖一下，多试几次总有一次能成」。某天下午下游开始限流，你的程序对每个失败请求连试五次，请求数瞬间翻了几倍，限流更狠、失败更多、账单跟着往上蹿，原本几分钟能自己恢复的小抖动被拖成一场谁也下不来的拥堵。更冤的是同一批里还混着一批参数写错的请求——它们重试一百次也不会成功，却老老实实陪着跑了五轮，白烧了一堆调用。你本来想让系统更稳，结果亲手做了个放大器。

## 二、先破这个把「重试」当万灵药的误解

**不是下游太脆弱，也不是重试次数不够，而是你把性质完全不同的失败都当成同一种「再试一次就好」，把限流和参数错一起塞进了同一个重试循环。**

先说清常见的四类失败，它们长得很像（都表现为「这次没成功」），可该不该重试完全不同。瞬时网络错：连接断了、超时了，过一会儿大概率自己好，适合重试。限流：对方明确说「太快了，慢点来」，通常对应状态码 429（超文本传输协议 HTTP，HyperText Transfer Protocol，状态码是服务端回的一个三位数字，429 表示请求过多被限），要排队退避后再试，硬顶着重试只会更糟。确定性错误：参数写错、字段非法、请求体不合规，常对应 400（表示请求本身有问题），重试多少次结果都一样，纯属浪费。服务级故障：对方内部出错，常对应 5xx（表示服务端一侧出问题），可以有限次重试并配合退避，但持续故障要尽快停。把一次请求里这些状态怎么来的拆清楚，能对照 [一次请求拆成五块](./k008-request-anatomy.md)；本篇关心的是失败回来之后，怎么给它归类、怎么决定下一步。

## 三、把它想成打一通总占线的电话

打个比方：你要给一个业务窗口打电话办件事，会遇到四种「没办成」。第一种是信号突然断了，你会稍等再拨一次，多半能通——这是瞬时网络错。第二种是对方说「现在打进来的人太多，请过几分钟再拨」，这时候你若一秒一次连拨十遍，只会让线路更堵、自己也一直占线——这是限流，正确做法是拉开间隔、耐心等。第三种是你把表格编号填错了，接线员说「这个号不存在」，你再拨几遍、用同样的错号，人家还是说不存在——这是确定性错误，问题在你手里，重拨无解，得改数据。第四种是对方说「我们系统这会儿坏了」，你可以过一阵再试，但要是坏一整天，你不会一直拨到天黑——这是服务级故障，得有次数上限和收手的时候。

这里有一一对应关系：一次模型调用等于一通电话；失败返回等于「没办成」的四种答复；重试等于「再拨一次」；退避间隔等于「过几分钟再拨」的耐心；重试次数上限等于「不一直拨到天黑」的自我约束；而账单等于你为这些电话付的通话费。

这个类比点破了那场小故障的根因：你把所有「没办成」都归成「信号断了、再拨一次」，于是限流被连拨、参数错被陪跑、服务故障被无限拨。真正该做的，是听清对方给的是哪一种答复，再决定拨不拨、隔多久拨、最多拨几次。四类答复对应四种动作，一步都不能省。

## 四、两张图看清判定发生在哪

:::figure 一次失败从返回到下一步动作
@flow
拿到失败|读取类别|判可否重试|算退避间隔|执行或收手
:::

第一张图里，「判可否重试」是一道闸门，卡在「读类别」和「算退避」之间。很多事故就是少了这道闸门，直接从「拿到失败」跳到「再试一次」。正确顺序是：先看清是哪类、再决定试不试、只有决定试的才去算间隔、再执行；判定为「不可重试」的当场收手，返回明确原因。

:::figure 盲目重试与分类重试
@compare
一律重试五次::限流被放大成拥堵|参数错陪跑白烧钱|账单与失败率齐涨
按类分别判定::限流退避削峰|确定错立即停|故障有限次即收手
:::

第二张图把代价摊开。一律重试不是「更稳」，而是把限流放大、把确定错陪跑、把成本顶上去；按类判定多写的只是几行分支，换来的却是「该等的时候等、该停的时候停」。这张图还藏着一个要点：重试不是免费的，每一次都要算进成本与限流预算，凭「多试几次总有一次成」的直觉，恰恰是最贵的一种乐观。

## 五、顺着追问把边界推出来

:::ask 那如果我就想「稳妥点」，对可重试的错误也统一退避三天再说，不是更安全？
:::

不是，退避的目的是「错开重试的浪头」，不是「越久越安全」。这里有两层。第一层是节奏：限流时要的是指数退避（间隔按次数翻倍，比如 1、2、4 秒）加一个封顶，还要带一点随机抖动——如果所有失败请求都在同一秒失败、又都用固定间隔重试，它们会在同一瞬间一起再涌上去，形成新的尖峰，把刚恢复的下游又压垮。抖动就是把这些重试时刻打散。第二层是预算：一次任务往往有整体的时间或金额上限，首次调用已经耗掉一大半，剩下的余量可能只够一次快速重试，再机械地试满三次就把预算吃光了。所以「间隔」和「次数」都要受「这一步还剩多少预算」约束，而不是各自定死。关于退避与抖动的细节，[重试、指数退避与抖动](./k108-retry-backoff.md) 有专门展开。

:::ask 再追一层：那怎么保证「分类」本身没分错，以及分错之后不至于又变回放大器？
:::

靠两件事：分类依据要结构化，收手要可观测。其一，别靠匹配错误文案里的某句话来判类别——文案会变、会被本地化成不同说法，一句「稍后重试」里含不含某个词都脆弱。稳妥做法是用稳定的错误码或错误类型字段来判定，让分类建立在一个明确的枚举上（比如 `timeout` / `rate_limit` / `invalid_request` / `provider_error`），并把「是否可重试、建议等待多久、下一步是什么」直接写进判定结果，而不是散落在调用处的 if 里。其二，给重试设一个不可绕过的总上限，并且无论重试成功失败都留下一条结构化记录：哪一类、第几次、等了多久、最终是成功还是收手。这样一旦某类错误突然变多，你能从记录里看出「是限流被放大了」还是「有一批参数错在陪跑」，而不是只看到一个含糊的「调用失败」。再往深一层，分类只对「无副作用」或「已保证幂等」的动作才允许自动重试；一个会真实扣款或发信的动作，超时重试可能已经执行过一次却没收到回执，盲目再试就是重复副作用。这类动作要么先查执行状态再决定，要么干脆不自动重试、转人工。这已经越过本篇范围，属于 [超时不等于没执行](./k039-timeout-reconcile.md) 要处理的事。把「能不能重试」和「重试安不安全」分开判，才不会把分类做对、却仍闯出别的祸。

## 六、用一段可运行代码把分类判定演出来

下面这段不联网、不装任何第三方包，用一个确定性的假下游按写好的脚本返回不同类别的失败，再用一个分类器判定可否重试、算退避、并在总预算内收手。

```python
from dataclasses import dataclass
from enum import Enum

class Kind(Enum):
    TIMEOUT = "timeout"              # 瞬时网络错，可重试
    RATE_LIMIT = "rate_limit"        # 限流，退避后可重试
    INVALID_REQUEST = "invalid_request"  # 确定性错误，不可重试
    PROVIDER_ERROR = "provider_error"    # 服务级故障，有限次可重试

@dataclass
class Failure:
    kind: Kind

@dataclass
class Decision:
    retryable: bool
    wait_seconds: float
    reason: str

def classify(f):
    if f.kind == Kind.INVALID_REQUEST:
        return Decision(False, 0.0, "请求本身不合法，重试无意义")
    if f.kind == Kind.RATE_LIMIT:
        return Decision(True, 2.0, "被限流，需退避削峰")
    if f.kind == Kind.TIMEOUT:
        return Decision(True, 1.0, "瞬时断连，稍后重试")
    return Decision(True, 1.5, "服务侧故障，有限次重试")

def backoff(wait, attempt, cap=8.0):
    # 指数退避加封顶；抖动在演示中用固定增量近似，避免引入随机不可复现
    return min(wait * (2 ** attempt), cap)

def handle(failures, max_retries=3):
    logs = []
    retries = 0
    for idx, f in enumerate(failures):
        d = classify(f)
        if not d.retryable:
            logs.append((f.kind.value, "stop", d.reason))
            break                       # 确定性错误，当场收手
        if retries >= max_retries:
            logs.append((f.kind.value, "budget_stop", "重试次数已达上限"))
            break
        w = backoff(d.wait_seconds, retries)
        logs.append((f.kind.value, "retry", round(w, 2)))
        retries += 1
    return logs, retries

def main():
    # 场景一：一批参数错，期望一次都不重试
    logs_bad, n_bad = handle([Failure(Kind.INVALID_REQUEST)] * 5)
    # 场景二：连续限流，期望有限次退避后收手，且间隔递增
    logs_rate, n_rate = handle([Failure(Kind.RATE_LIMIT)] * 10)
    # 场景三：瞬时断连后恢复（脚本里只有一次失败），期望只重试一次
    logs_timeout, n_timeout = handle([Failure(Kind.TIMEOUT)])

    waits = [x[2] for x in logs_rate if x[1] == "retry"]

    results = []
    results.append(("确定性错误判定为不可重试",
                    classify(Failure(Kind.INVALID_REQUEST)).retryable is False))
    results.append(("限流判定为可退避重试",
                    classify(Failure(Kind.RATE_LIMIT)).retryable is True))
    results.append(("参数错陪跑零次重试", n_bad == 0))
    results.append(("参数错当场收手", logs_bad[0][1] == "stop"))
    results.append(("限流重试不超过上限 3 次", n_rate == 3))
    results.append(("限流退避间隔逐次递增", waits == sorted(waits) and waits[0] < waits[-1]))
    results.append(("退避有封顶不超 8 秒", all(w <= 8.0 for w in waits)))
    results.append(("单次瞬时断连只重试一次", n_timeout == 1))
    results.append(("收手时留有明确原因",
                    any(x[1] == "budget_stop" for x in logs_rate)))

    passed = sum(1 for _, ok in results if ok)
    for name, ok in results:
        print(("通过" if ok else "未通过") + "：" + name)
    print("通过 {}/{} 项".format(passed, len(results)))
    assert passed == len(results)

if __name__ == '__main__':
    main()
```

逐段看关键行在做什么：

1. `Kind` 用标准库 `Enum` 定义四类稳定的错误类别。刻意用枚举而不是错误文案，是想把「分类建立在结构化字段上」这条原则落到代码里——判定的依据不会随文案措辞变化而失效。
2. `Failure` 封装一次失败，`Decision` 封装判定结果：是否可重试、建议等待多久、原因是什么。把这三样一起返回，调用处就不必再自己散着写 if，避免「同一个类别在 A 处判可重试、在 B 处判不可重试」。
3. `classify` 是本篇的题眼：参数错直接返回 `retryable=False`，其余三类各有不同的等待与理由。注意「不可重试」是一个明确分支，不是「可重试次数为 0」的副作用。
4. `backoff` 按次数翻倍并封顶到 8 秒。这里用固定增量近似抖动、不引入随机数，是为了让断言完全可复现；真实场景要加一点随机把重试时刻打散。
5. `handle` 把判定和「总次数上限」放在一起执行：遇到确定性错误立刻 `break`，重试次数触顶也 `break` 并留下 `budget_stop` 原因。这两处收手，正是「该停的时候停」。
6. `main` 造三个场景：一批参数错、连续限流、一次瞬时断连。九条断言分别验证「参数错零重试且当场停」「限流有限次且间隔递增有封顶」「瞬时错只试一次」「收手留原因」。尤其是 `n_bad == 0` 与 `n_rate == 3` 两条，把开头「参数错陪跑白烧钱、限流被放大」两个毛病用可运行的方式证伪了正确做法的效果。

:::warn
「能不能重试」和「重试安不安全」是两件事。会真实扣款、发信、改数据的动作，超时后可能已经执行过，盲目重试会造成重复副作用，必须先查状态或转人工。
:::

## 七、踩过的坑与它的边界

- **一律重试 N 次**：现象是限流演变成拥堵、账单翻倍 → 原因是不分性质把所有失败塞进同一循环 → 先分类，只对可重试类开重试闸门。
- **参数错陪跑**：现象是明明改数据就能好的请求反复失败还照试 → 原因是把确定性错误当瞬时抖动 → 400 类立即停并返回明确原因，一次都不重试。
- **固定间隔无抖动**：现象是下游刚恢复又被一波请求压垮 → 原因是失败请求同刻失败、同刻重试形成尖峰 → 指数退避加封顶、加随机抖动打散重试时刻。
- **靠文案判类别**：现象是错误说明改了措辞分类就失灵 → 原因是拿自然语言匹配当判据 → 用稳定枚举或错误码判定，别匹配文案。
- **重试不设总上限**：现象是服务坏一整天程序拨到天黑 → 原因是只有单次间隔、没有整步预算 → 间隔与次数都受剩余预算约束，触顶收手并留原因。

还有边界要说清：分类与退避解决的是「别把小抖动放大成事故、别让确定错白烧钱」，它不负责「失败的根因是什么」，也不负责保证有副作用的动作重试安全。而且本篇的假下游是按脚本返回失败，演示的是判定逻辑，不含任何真实网络或实测数据；真实系统里类别可能更细（鉴权失败、上下文超限、策略拦截等），都应各自补进枚举并明确可重试性。另外，重试即便判对了，也仍要面对「输出本身带随机性」——同一请求重试不保证变好，这属于另一层问题，不能靠重试次数去赌质量。

## 九、三句话小结

异常分类与可重试判定，是把「这次没成功」先归成瞬时、限流、确定错、服务故障四类，再决定试不试、隔多久、最多几次的一道闸门。

关键做法是用稳定枚举做分类、把可重试性与建议等待一并写进判定结果、配指数退避加抖动与不可绕过的总上限，并在收手时留下明确原因。

当动作带真实副作用且没做幂等保证时，别让分类结果直接触发自动重试，先查执行状态或交给人工处理。

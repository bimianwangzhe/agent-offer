# 熔断与 kill switch

## 场景提问

你给 Agent 接了一个外部查询工具，某天下午那个工具开始持续报错。你的循环里写了重试，于是它一遍又一遍地重发，下游越堵越慢，几分钟里把调用额度烧掉一大截，还把同一笔动作重复提交了好几次。你赶紧想让它停，却发现只能改代码重新发一版；更让人心里发凉的是，你试着把「别再调这个工具了」写进提示词，模型下一轮照样又发起了一次调用。一个下游抖动，怎么就拖成了烧钱加重复提交的事故，而且连「先停一下」这个最朴素的动作都做不到？

## 破误解

**不是下游不够稳，是缺少一层「累积到一定程度就主动切断、而且人能随时一键全停」的保护，把重试当成了唯一的应对办法。**

先把三件容易被混为一谈的东西拆开。重试与退避解决的是「单次偶发失败，隔一会儿再试一次」，超时与兜底解决的是「这一次卡住了别一直等」，它们都盯着单次调用；熔断（circuit breaker，这个名字借自电路里的断路器）盯的是跨很多次调用的累积状态：当某个出口的错误率、连续失败次数、越权动作次数或单任务成本累计越过一条线，就判定这个出口「此刻不健康」，主动把闸拉断，后续请求不再触达下游，直接快速失败（fail fast，连试都不试就返回失败结果）。它有三个状态：闭合态正常放行，断开态快速失败，半开态只放一个探测请求去试下游好没好，探测成功才回闭合。这跟「重试」的方向恰好相反：重试是「再试一次」，熔断是「别再试了」，两者得配合，见 [重试与指数退避](./k108-retry-backoff.md) 与 [超时与兜底](./k109-timeout-fallback.md)。

另一件东西是 kill switch，可以直接理解成「急停总开关」：一个独立于被保护系统之外、由人触发、拉下之后所有动作（或某一整类危险动作）立刻被拒、并且必须人工复位的开关。它和熔断不是一回事，区别有三条要记牢。第一，熔断是局部的、按出口计的，急停是全局的、一次拉下覆盖全部。第二，熔断是自动触发、能自恢复的，急停是人工触发、默认不自动恢复——因为「系统自己决定把保护关掉」这件事本身就很危险。第三，也是最容易被忽略的：急停必须放在动作真正执行之前的确定性代码里，不能写在提示词里，更不能由模型自己判断该不该停，否则一段被污染的输入就能诱导它把保护撤掉，这跟 [护栏放在代码里](./k106-guardrail-in-code.md) 是同一条原则。熔断负责「机器按信号自动把某条线路掐了」，急停负责「人看情况不对，一把拉下总闸」，少了哪一层，你都会遇到开头那种「想停停不下来」的窘境。别把「多写几行重试」当成护栏，那只是让失控跑得更快一点。

## 生活类比

把它想成家里配电箱加燃气总阀。某条插座线路上插了太多大功率电器，电线发热，管这一路的空气开关「啪」一声自己跳了——只有这一路没电，冰箱、灯、别的房间照常工作。过一会儿你估计线路凉下来了，把开关试着合上去一次：如果电器正常转起来，说明故障是暂时的，恢复供电；要是「啪」又跳了，说明问题还在，那就别再反复合闸，得去查线路。这就是熔断：按过载（累积失败）自动跳闸、只断一条线路（一个出口）、冷却之后只试探一次再决定恢复还是继续断开。

燃气总阀是另一回事。闻到异味、或者要动管路时，人走过去手动把总阀一拧，全屋所有灶具立刻断气，不管哪一路的空气开关当时是合是断；处理完、确认安全了，还得人再手动拧回去，它绝不会自己悄悄通气。这就是 kill switch：全局、人工、独立、必须手动复位。

对应关系要一条条对上才有用。某条线路，对应系统里某个工具、某类动作或某个下游；电线发热，对应连续失败、错误率、越权次数、成本与步数的累积，也就是 [四类预算](./k103-four-budgets.md) 里那些能数出来的量；空气开关跳闸，对应断开态快速失败，请求根本不再打到下游，也就不烧钱、不产生副作用；「凉一会儿」，对应冷却窗口；「试着合一次闸」，对应半开态只放行一个探测；「又跳了就去查线路」，对应探测失败后回到断开并把冷却拉长，而不是傻傻地反复试探。至于总阀是机械的、装在管道上、跟灶具本身没关系的这一点，正对应急停最关键的性质：它不能由被它管的对象自己决定开关，得是一个外部的、默认可用的、独立的开关。还有个细节：总阀拉下之后，哪怕某一路空气开关看起来是好的，气也不会通——这就是急停的优先级高于熔断，拉下之后管你哪个出口是不是闭合态，一律拒绝。

## 自绘示意图

:::figure 熔断的三态循环
@cycle
闭合放行|失败累积跳闸|断开快速失败|冷却转半开|探测成功复位
:::

这张图里最容易被跳过的是「冷却转半开」和「探测成功复位」这两格。只画「失败就断开」是不够的：断开之后如果没有一条受控的恢复路径，要么永远不恢复（等于把功能废了），要么一恢复就全量放行（下游刚缓过来又被压垮）。半开态只放一个探测，就是让恢复这件事也变成可观察、可回退的。

:::figure 一次动作要过的几层闸
@stack
动作入口::每个动作执行前都要过闸，不靠模型自觉
全局急停层::人可一键拉下，拉下后所有动作直接被拒
熔断层::按出口统计连续失败，跳闸后快速失败不触达下游
恢复探测层::冷却结束只放一个探测，据此回闭合或再断开
下游执行层::真正调用工具、花钱、产生副作用的地方
:::

五层里最常被漏掉的是「全局急停层」和「恢复探测层」。很多实现只有「调用—失败—重试」三格，既没有一个人能按的总闸，也没有断开之后怎么回来的规矩，于是要么停不下来，要么停下来就起不来。注意「动作入口」这一层：闸要卡在动作真正执行之前，而不是等副作用都产生了再事后补救。

:::figure 两种做法的差别
@compare
只靠提示词劝阻::被注入就失效|模型输出不稳定|没有累积状态
代码里熔断加急停::确定性拦截|按失败累积跳闸|人工全局可停
:::

左边是把「别再调了」写进提示词，指望模型自觉：它既没有跨请求的计数能力，输出又带随机性，遇到 [间接注入](./k098-indirect-injection.md) 里那种藏在工具返回里的指令还可能被直接顶掉。右边把判断放进确定性代码：按可数的信号累积、到线就跳，并且留一个模型碰不到、人能按的总开关。

## 层层追问

:::ask 那如果下游只是抖了一下、马上就好了，熔断会不会把本来能成的好请求也一起挡掉？
:::

会，如果只有「失败就断开」这一半的话，这正是半开态要解决的问题。断开态不该是终点，而是一段带冷却窗口的观察期：冷却结束先切到半开，只放行一个探测请求，让真实下游去跑一次；探测成功，说明故障是暂时的，立刻回闭合并把连续失败计数清零；探测失败，说明下游还没好，回到断开并把冷却窗口拉长一些，别马上又来试。这个「拉长」的思路和重试里的指数退避是同源的，可以避免下游刚恢复就被一波探测压回去。还有两处能减少误伤：阈值别设成「错一次就跳」，而要用连续失败次数或一段时间窗内的错误率，偶发单点失败不该触发跳闸；触发信号也要分类型，参数写错这类调用方自己的问题，和下游超时、限流这类「下游不健康」的信号要分开统计，否则一个格式错误就把整个出口掐了。这些信号怎么归类、怎么计数，可以对照 [失败模式](./k150-failure-modes.md) 与 [指标与按成功任务核算成本](./k096-metrics-cost.md)。快速失败期间也别把异常裸抛给用户，返回一个明确的降级结果更好，见 [超时与兜底](./k109-timeout-fallback.md)。

:::ask 那如果触发熔断的信号本身来自模型或被污染的数据，急停能不能也交给系统自动判断？
:::

这一问戳到了整套设计最要紧的地方。先说熔断信号的来源：能用来跳闸的，必须是确定性的、外部可核对的量——工具返回的失败标记、超时次数、步数计数、成本累计、被拒动作的次数。不能取模型自己那句「我觉得现在没问题」或者「这个失败可以忽略」，因为模型输出是采样出来的，而且可能被输入里夹带的内容影响。把「是否健康」交给被保护的那一层自述，等于让嫌疑人自己签无罪证明。再说急停为什么必须人工、必须独立：如果让系统自动判断「要不要把总闸拉下」，那么一段精心构造的注入内容就可能诱导它在该停的时候不停、或者在不该停的时候反复停，把保护本身变成攻击面。所以急停开关的状态要放在模型改写不到的地方，走 [护栏放在代码里](./k106-guardrail-in-code.md) 那条路；它的取值还要默认安全——开关读取失败、配置缺失时，应当倾向于「停止」而不是「放行」，这叫失效导向安全。开关状态本身得持久化并幂等，不能进程一重启就被新配置覆盖成「放行」，这部分和 [幂等落盘](./k107-idempotent-persist.md) 是同一套稳标识思路；同时要能被外部探知「现在到底是停还是放」，别出现运维以为拉下了、实际还在跑的情况，这属于 [健康检查与 SLO](./k114-health-slo.md) 里「让状态可被观察」的范围。最后一句要记牢：熔断可以自动，急停必须留给人。自动的部分负责快，人工的部分负责在信号本身都不可信时还能收得住。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「按连续失败跳闸—断开快速失败—冷却后只放一个探测—探测成功复位／失败再断开」以及「人工急停优先于一切状态」完整演示一遍。时间用逻辑步数代替，不读真实时钟、不联网、不需要任何账号或第三方包，结果可手工推算、可复现；复制到任意装有 Python 的机器上直接运行即可，结尾用一组断言逐条验证并打印通过项数。

```python
class KillSwitch:
    """人工急停：独立于熔断状态，拉下后所有动作被拒，必须手动复位。"""

    def __init__(self):
        self._engaged = False

    def engage(self):
        self._engaged = True

    def release(self):
        self._engaged = False

    @property
    def engaged(self):
        return self._engaged


class CircuitBreaker:
    """三态熔断：闭合、断开、半开；冷却用逻辑步数，便于复现。"""

    def __init__(self, threshold=3, cooldown=2):
        self.threshold = threshold
        self.cooldown = cooldown
        self.state = "closed"
        self.consecutive_failures = 0
        self.cool_left = 0
        self.probe_sent = False
        self.downstream_calls = 0

    def allow(self):
        """返回 (是否放行到下游, 这次是不是半开探测)。"""
        if self.state == "open":
            return (False, False)
        if self.state == "half_open":
            if self.probe_sent:
                return (False, False)
            self.probe_sent = True
            return (True, True)
        return (True, False)

    def record(self, ok, probing):
        """把一次真实调用的结果回写给状态机。"""
        if probing:
            if ok:
                self.state = "closed"
                self.consecutive_failures = 0
                self.cool_left = 0
            else:
                self.state = "open"
                self.cool_left = self.cooldown
            self.probe_sent = False
            return
        if ok:
            self.consecutive_failures = 0
        else:
            self.consecutive_failures += 1
            if self.consecutive_failures >= self.threshold:
                self.state = "open"
                self.cool_left = self.cooldown

    def tick(self):
        """推进一个逻辑步；冷却归零时从断开进入半开。"""
        if self.state == "open" and self.cool_left > 0:
            self.cool_left -= 1
            if self.cool_left == 0:
                self.state = "half_open"
                self.probe_sent = False


def attempt(switch, breaker, downstream_ok):
    """一次动作：先过急停，再过熔断，最后才可能触达下游。"""
    if switch.engaged:
        return "blocked_by_kill_switch"
    allowed, probing = breaker.allow()
    if not allowed:
        return "fast_fail"
    breaker.downstream_calls += 1
    breaker.record(downstream_ok, probing)
    if downstream_ok:
        return "ok"
    return "downstream_error"


def main():
    switch = KillSwitch()
    breaker = CircuitBreaker(threshold=3, cooldown=2)
    checks = []

    results = [attempt(switch, breaker, False) for _ in range(3)]
    checks.append(("连续三次失败都返回下游错误",
                   all(r == "downstream_error" for r in results)))
    checks.append(("失败累积到阈值后跳闸为断开态", breaker.state == "open"))
    checks.append(("跳闸恰好触达下游三次", breaker.downstream_calls == 3))

    r = attempt(switch, breaker, True)
    checks.append(("断开态即使下游会成功也快速失败", r == "fast_fail"))
    checks.append(("快速失败不触达下游", breaker.downstream_calls == 3))

    breaker.tick()
    checks.append(("冷却未结束仍是断开态", breaker.state == "open"))
    breaker.tick()
    checks.append(("冷却归零进入半开态", breaker.state == "half_open"))

    r = attempt(switch, breaker, True)
    checks.append(("半开探测成功", r == "ok"))
    checks.append(("探测成功回到闭合态", breaker.state == "closed"))
    checks.append(("恢复后连续失败计数清零", breaker.consecutive_failures == 0))

    for _ in range(3):
        attempt(switch, breaker, False)
    breaker.tick()
    breaker.tick()
    r = attempt(switch, breaker, False)
    checks.append(("半开探测失败回到断开态", breaker.state == "open"))

    breaker2 = CircuitBreaker(threshold=3, cooldown=2)
    r_before = attempt(switch, breaker2, True)
    checks.append(("急停未拉下时正常放行", r_before == "ok"))
    calls_before = breaker2.downstream_calls

    switch.engage()
    r = attempt(switch, breaker2, True)
    checks.append(("急停拉下后动作直接被拒", r == "blocked_by_kill_switch"))
    checks.append(("被急停拦下时不触达下游", breaker2.downstream_calls == calls_before))
    checks.append(("急停不改变熔断自身状态", breaker2.state == "closed"))

    switch.release()
    r = attempt(switch, breaker2, True)
    checks.append(("人工复位后恢复放行", r == "ok"))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `KillSwitch` 只有「拉下」和「复位」两个动作，以及一个只读的 `engaged` 属性。它被刻意做成完全独立于熔断状态机：类里没有任何地方引用 `CircuitBreaker`，就是为了保证「人按总闸」这件事不被系统的其它状态悄悄改写，也不会因为程序自己觉得「现在好了」就自动复位。
2. `CircuitBreaker` 用 `state` 记三态、`consecutive_failures` 记连续失败、`cool_left` 记还剩几步冷却、`probe_sent` 保证半开态只放行一个探测、`downstream_calls` 数真正触达下游的次数。最后这个计数器很重要：它是验证「快速失败到底有没有省下下游调用」的证据，而不是靠一句注释声称省了。
3. `allow` 只回答「这次放不放行、是不是探测」，不产生任何副作用：断开态一律拒绝，半开态在探测还没放出时放一个、放出后拒绝后续，闭合态正常放行。把「决定」和「执行」分开，急停才能插在两者之间。
4. `record` 把一次真实调用的结果回写状态机，分两条路径：探测调用成功就回闭合、清零，失败就回断开并重新计时；普通调用则累加连续失败，达到 `threshold` 才跳闸。注意成功一次就把连续失败清零，这样偶发失败不会攒够触发线，正是前面说的减少误伤。
5. `tick` 用逻辑步数推进冷却，归零时切到半开并把 `probe_sent` 重置。用「步」而不是真实秒数，是为了让整段代码不依赖时钟、可手工推算——真实系统里这里会换成时间戳比较，但状态跳转的顺序不变。
6. `attempt` 是唯一的动作入口，顺序写死：先查急停，再问熔断，最后才可能给 `downstream_calls` 加一并调用下游（这里用一个布尔量 `downstream_ok` 模拟下游结果，不联网、不装包）。急停之所以排第一，是因为它的优先级高于熔断的所有状态；「执行前拦截」也就落在这一行顺序上。
7. `main` 用一组 `(名字, 布尔表达式)` 的检查项串起整条链路：连续三次失败跳闸、断开态快速失败且下游计数不增、两步冷却后进半开、探测成功复位、探测失败再断开；然后换一个干净的熔断器验证急停——拉下后即便闭合态也直接被拒、且下游计数不增、熔断状态不被改动，人工复位后恢复。结尾统计通过项并断言全部成立，任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用布尔量代替真实下游、用文件外的内存状态代替持久化的开关、用逻辑步代替真实时钟，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并手算验证。它演示的是急停优先级、三态跳转与探测恢复的顺序，不是任何具体服务框架里的现成实现；文中也没有声称这段代码被实际运行过或给出任何实测结论。

## 踩坑与边界

- **把熔断写进提示词**：现象是提示里明明写了「别再调了」，模型下一轮照样发起调用，遇到藏在工具返回里的指令还会被顶掉 → 原因是提示词是建议不是约束，没有跨请求的计数能力，输出还带随机性 → 把跳闸判断放进执行前的确定性代码，模型只负责产出意图，见 [护栏放在代码里](./k106-guardrail-in-code.md)。
- **只有一个全局计数器**：现象是某个冷门工具一出错，把系统和它无关的调用也一起掐了，或者反过来某条线路疯狂报错却因为总量被摊薄而迟迟不跳 → 原因是所有出口共用一个计数，粒度太粗 → 按工具、动作类型、租户分别计数，各自维护状态，边界划分可对照 [会话隔离与租户边界](./k105-session-isolation.md)。
- **把所有失败都算作下游不健康**：现象是调用方把参数写错一次，出口就被跳闸，正常请求跟着遭殃 → 原因是没区分错误来源，把格式问题、权限拒绝和服务超时混在一起累加 → 先做错误分类，只把「下游不健康」那类信号计入跳闸，参考 [失败模式](./k150-failure-modes.md)。
- **断开后直接全量恢复**：现象是冷却一到就把请求全放过去，下游刚缓过来又被压垮，反复横跳 → 原因是缺了半开态与单探测这层缓冲 → 冷却结束只放一个探测，成功再回闭合，失败就回断开并拉长冷却。
- **急停状态只在内存里**：现象是运维以为拉下了总闸，进程一重启又被新配置覆盖成「放行」，事故继续跑 → 原因是开关状态没持久化、读取失败时还默认放行 → 状态落盘且幂等、读取失败时失效导向安全，并让外部能探知当前取值，见 [幂等落盘](./k107-idempotent-persist.md) 与 [健康检查与 SLO](./k114-health-slo.md)。

还要分清几组边界。熔断和重试不是替代关系：重试处理偶发单点失败，熔断处理「这个出口整体不健康」，两者叠着用，见 [重试与指数退避](./k108-retry-backoff.md)。熔断和限流也不是一回事：限流管的是「单位时间最多放多少个」，即便每个请求都成功也会限；熔断管的是「失败累积到线就别再打」，触发依据是错误信号。「自动停放量」与「人工急停」更要分清：前者只是不再把新流量送进有问题的版本，后者是连正在跑的动作也一起拦下，范围更彻底，前者可参看 [影子模式、灰度与回滚](./k112-shadow-canary.md)。恢复之后别忘了把被快速失败挡下的请求怎么补、怎么不重复提交安排好，这与 [优雅恢复](./k110-graceful-resume.md) 和 [服务封装](./k151-service-wrap.md) 相关。若想从整体上看这套护栏怎么组织，可以回到 [从这里开始](./00-start-here.md)。

## 三句话小结

熔断与 kill switch，是给 Agent 装的两道刹车：前者按失败累积自动把某个出口跳闸、冷却后受控恢复，后者由人一键全停、必须手动复位且模型碰不到。

关键做法是把判断放进执行前的确定性代码，按出口分别计数、用连续失败或错误率触发、半开只放一个探测，并让急停优先级最高、状态持久化且失效导向安全。

当系统只有一次性的离线调用、没有重复提交风险、也没有需要人工兜底的危险动作时，不必硬套这套状态机；但只要一个动作会花钱、有副作用、或错了会反复重来，这两道刹车就不该省。

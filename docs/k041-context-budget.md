# 上下文预算表：把每一轮输入当资源来管

## 一个越聊越贵的助手

你写了一个帮人处理订单的助手，试运行时问什么答什么，干脆利落。可用户连着追问到第十五轮，它开始把先前谈妥的退货地址说错，回答明显变慢，这一天的账单还比试运行时高出一大截。你把日志从头翻到尾：模型没换，代码没改，工具调用也没报错，唯一一直在变的是每轮送进去的那段文字越来越长。

## 先破一个误解

**不是模型记性变差了，是你把每轮输入当成了一份可以无限往后追加的清单。**

要讲清这件事，得先说几个词。模型读文字时并不是按「字」来读，而是按 token（token 指模型读写的最小单位，白话叫「字块」，一个汉字大致对应一到两个）来读；每生成一个新的字块，它都要把这一次请求里的全部文字重新过一遍。这一次请求里它能看到的文字总量，叫上下文窗口（context window，指一次调用中模型这一眼能看到的全部文字），超了要么被悄悄截断，要么直接报错。既然总量有上限，就该像管钱一样管它：先定一份账，写清各类内容最多占多少，再按账去拼装。这份账，就是上下文预算表。

很多人把「上下文不够用」直接理解成「窗口太小」，于是第一反应是换个能看更多字的模型。这条路的代价是三重的：每轮单价跟着涨；当前问题被埋在一大段旧记录中间而权重下降；更麻烦的是那些根本不该带的东西，比如上一轮工具的原始返回、三页前失败的尝试、和本轮无关的分支，照样每轮都跟着走。预算表要解决的不是「装得下装不下」，而是「谁有资格占这一格」。关于长材料中间更容易被忽略的现象，可以接着看[上下文膨胀与中间遗失](./k049-context-bloat.md)。

## 用每天重新装箱的行李箱来理解

把一次调用想成一次出差：行李箱容量固定，就是上下文窗口。你不是把家里所有东西搬上箱，而是每天早上按一张装箱清单决定谁进谁不进，晚上回酒店再把箱子清空重来。这正对应模型「每轮都重新组装一遍输入，并不真正记得上一轮」这件事。

清单上的对应关系是这样的：证件和常用药每趟必带，对应系统提示这类常驻规则；今天要拜访的客户资料，对应本轮检索到的片段；前几天开会发的材料，对应历史轨迹，绝大多数该留在家里；而你还必须给箱子留出一格空位，用来装当天买的东西带回去，这一格就是留给输出的额度。预算表就是那张写死「证件一格、资料两格、旧材料不超过一格」的清单。

要害不在于「东西装不下就换个更大的箱子」，而在于先按清单决定谁进谁不进。行李箱再大，把整个家塞进去你也找不到今天要用的那份合同。同理，先做预算和裁剪，再考虑换能看更多字的模型，顺序不能颠倒。

:::quote
上下文不是聊天记录，是**每轮都要重新组装的一份有限输入**。预算表把「有限」这两个字变成了可以核对的数字。
:::

## 把额度画出来

下面这张图把一份八千单位的总额度切成六格，注意最后一行不是某类输入，而是专门留给答案的空间。

:::figure 一次调用的额度分配示例（总额八千单位）
@stack
系统规则 800::身份与边界，每轮必带，写死不压缩
工具清单 600::只列本轮相关的，不相关的一概不带
历史摘要 1200::早期对话压成几句，不保留原文
最近轨迹 2400::最近几轮完整保留，含工具结果
当前输入 1600::本轮问题加本轮取回的材料
留给输出 1000::别把额度吃光，否则答案被拦腰截断
:::

最后一格最容易被漏掉。很多人把输入一直加到贴着上限，结果答案写到一半被截断，末端既没有收尾也没有该有的格式，因为生成出来的字同样要占窗口，输入吃满了，输出就没地方落。稳妥的做法是把输出份额当成一条不可借用的红线，组装时先把这部分扣掉，剩下的才分给各类输入。

再看两种做法的差别：

:::figure 想到什么拼什么，与先做预算再组装
@compare
想到什么拼什么::额度无账可查|旧记录越堆越多|常在超限时才报错
先做预算再组装::每类有硬上限|当前问题权重高|输出份额被保住
:::

这两行不只是风格不同。前者出问题时你只能对着一长串文字猜「到底是哪块撑爆的」，后者能在超支的那一刻就报出「摘要类超了一千八」，排查路径完全不一样。至于每一格具体该给多少，不该拍脑袋写绝对值，而该按占比写：系统规则约一成、最近轨迹约三成、输出预留约一成二，换一个窗口更大的模型时按比例放大即可，清单结构不用重写。分层之后各格怎么摆、谁先谁后，是[四层上下文结构](./k042-context-layers.md)要讲的事。

:::tip 一条立刻见效的规则
工具返回的原始内容**永远不整段进上下文**。先裁成结构化摘要，保留关键字段外加一句「已截断，共若干条」，原始大对象落到外置存储里，需要时再按标识取回。这一条往往就能把每轮的输入压下一大截。
:::

## 再往深问两层

:::ask 那如果某一类临时超了，能不能借用别类没用完的额度？
:::

能借，但要「先登记再借」，而且有一条绝不能碰的线：输出预留不可出借。做法是给每类设一个硬上限，组装时先按上限裁，再统计各类省下来的余量，允许历史或检索这类弹性内容在余量里多占一点，同时把「借了多少、从哪借的」记进当轮账目。为什么不许动输出份额？因为借的时候看着只是几百单位，一旦这轮答案偏长，被截断的就是结尾，而结尾恰恰常是结论和格式标记所在，损失远比省下的输入大。

:::ask 再深一层：预算表写死之后，长对话里历史一直在涨，难道每轮都要把整张表重算一遍？
:::

不用。预算表是一份静态清单，变动的是每轮的实际用量，不是清单本身。每轮真正要做的只有三件小事：按清单给各类内容量一次长度、超限就裁、把裁掉的量记下来。也就是说重算是「逐类量长度」这种常数级的动作，不是把历史从头读一遍。历史持续上涨这件事，该由压缩时机去管：设一个占比阈值，用量触线就提前压缩，别等真超限报错了才动手，这正是[压缩触发阈值与时机](./k047-compression-trigger.md)的内容。预算表负责「上限是多少」，触发规则负责「什么时候开始裁」，两者分工不同，别混在一起。

## 一份能跑的预算表

下面这份实现只用标准库，把「先定上限、按上限裁、丢量记账、输出份额不可挤占」四件事都做进去，复制成文件直接运行即可。

```python
# budget.py —— 只用标准库，python budget.py
from dataclasses import dataclass


@dataclass
class Budget:
    total: int
    caps: dict
    reserve: int = 1000

    def __post_init__(self):
        # 各格硬上限之和加上输出预留，构造时就必须不超过总额度
        assert sum(self.caps.values()) + self.reserve <= self.total

    def assemble(self, pieces: dict) -> dict:
        # pieces 是本轮各类的原始长度，先按各自上限裁剪
        clipped = {k: min(v, self.caps[k]) for k, v in pieces.items()}
        # 统计因裁剪被丢掉的量，便于事后排查
        dropped = {k: pieces[k] - clipped[k] for k in pieces}
        used = sum(clipped.values())
        free = self.total - self.reserve - used
        return {
            "clipped": clipped,
            "dropped": dropped,
            "used": used,
            "free": max(free, 0),
            "reserve_kept": self.reserve,
        }

    def charge(self, used: int, wanted: int) -> int:
        # 想追加的量不能超过「总额减输出预留」后剩下的空间
        room = self.total - self.reserve - used
        return min(wanted, max(room, 0))


if __name__ == '__main__':
    b = Budget(
        total=8000,
        caps={"system": 800, "tools": 600, "summary": 1200,
              "recent": 2400, "input": 1600},
    )
    # 构造一组「历史明显超支」的输入
    raw = {"system": 800, "tools": 600, "summary": 3000,
           "recent": 2400, "input": 1600}
    r = b.assemble(raw)
    assert r["clipped"]["summary"] == 1200           # 摘要被裁到上限
    assert r["dropped"]["summary"] == 1800           # 丢掉的量被记账
    assert r["reserve_kept"] == 1000                 # 输出份额没被挤占
    assert r["used"] + r["reserve_kept"] <= b.total  # 总量不越界
    assert b.charge(used=7000, wanted=500) == 0      # 逼近上限时不再追加
    assert b.charge(used=5000, wanted=500) == 500    # 空间充足时全额放行
    print("通过 6/6 项：预算裁剪、丢量记账、输出预留与追加限额均正确")
```

1. 开头用 `dataclass` 声明一张预算表：`total` 是总额度，`caps` 是各类的硬上限，`reserve` 是留给输出的份额。把账写成一份数据，而不是散落的常量，后面才能整张替换、整张校验。
2. `__post_init__` 里的断言是「先算账再写代码」这句话的落点：各格上限之和加上输出预留，构造时就必须不超过总额度。很多人是运行时才发现输入塞满，这里把错误提前到对象创建的一刻。
3. `assemble` 逐类用 `min` 把原始长度裁到上限，同时用 `dropped` 记录每类被丢掉多少。这份丢量清单就是超支时的排查依据，比事后对着长文本猜强得多。`free` 是扣掉输出预留后还剩多少可用空间，供弹性借调参考。
4. `charge` 处理「想临时追加一段」的情形：可用空间一律按「总额减输出预留再减已用」算，逼近上限时返回零，从代码上杜绝把输出份额吃掉。
5. `if __name__ == '__main__':` 里构造一组「历史明显超支」的输入，六条断言分别验证裁剪到上限、丢量记账、输出预留保持、总量不越界、逼近上限时拒绝追加、空间充足时全额放行，最后打印通过项数。

跑通之后可以自己改 `raw` 里的数字：把 `summary` 调到上限以内，会看到 `dropped` 全变零；把 `total` 调小而 `caps` 不变，构造阶段就会直接报错，提醒你清单本身已经不自洽。这类可复现的构造场景，比任何「感觉够用」都可靠。

## 踩过的坑

- **忘了留输出份额**：现象是答案写到一半突然断掉、末尾没有结论 → 原因是输入贴着窗口上限，生成出来的字块没有落点 → 怎么改：在总额里先扣一条不可借用的输出预留，组装时把它当作硬红线。
- **只按字数算，低估工具返回**：现象是某轮调用后额度突然爆掉 → 原因是工具返回一大段原始文本，比预估长几倍 → 怎么改：工具结果进上下文前先裁成结构化摘要，原始大对象外置，只带引用。
- **把额度写成绝对字数**：现象是换一个能看更多字的模型后清单全乱 → 原因是各格写死成固定数值 → 怎么改：按占比写清单，换模型时整体按比例缩放，结构保持不变。
- **裁完不留痕**：现象是答案变差却查不出少了什么 → 原因是裁剪静默发生，没有记录丢掉的内容 → 怎么改：每轮输出一份丢量清单，至少记清是哪一类、丢了多少。
- **分格越分越细**：现象是清单长到自己也维护不动 → 原因是把每个工具、每段历史都单列一格 → 怎么改：先按常驻、按需、近期、外置四类归并，够用之后再加，不要一上来就摊成十几格。

## 三句话

上下文预算表是把一次调用能看到的文字总量，事先切给各类内容、并单独留出输出份额的一张账。
关键做法是先定硬上限再按清单裁剪，同时把每轮丢掉的量记进账目以便回查。
当任务只有一两轮、输入天生很短时，不必专门做预算表，直接拼装反而更省事。

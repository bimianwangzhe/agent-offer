# 元数据过滤前置：先划范围，再谈相关

## 明明有可公开的政策，却一条都答不出来

用户是外部客户，问「VIP 投诉怎么处理」，系统回「未找到依据」。你翻库，明明有一份对外退款政策写得清清楚楚；再翻日志，召回出来的前三名全是内部升级流程——它们因为用词太贴切，把名额占满了，等过滤规则一跑，候选直接清零。更让人后背发凉的是另一种情形：如果哪天过滤那道检查漏了一处，越权的那段内部文本就已经躺在上下文里了。

## 先破一个误解

**不是过滤规则写错了，是它站错了位置——放在召回之后，等于先让不该看的进屋，再请它出去。**

先把词说清楚。元数据过滤指按片段自带的字段（可见范围、租户、生效时间、文档类型、语言等）先圈出「本次允许看哪些块」，再在这个范围内做匹配。前置（pre-filter）指这道圈选发生在打分之前，作为检索条件的一部分；与之相对的是后置（post-filter），即先按相关度取回若干条，再逐条筛掉不合规的。ACL 是 Access Control List（访问控制列表）的缩写，白话讲就是「谁能看哪份」的那张表，这里泛指可见范围。租户指多用户共用一个系统时，各家数据必须彼此隔开的那个归属标记。

为什么位置这么要命？有两个原因，一个关于效果，一个关于安全。效果上，索引只知道「两段文本离得近」，完全不知道「谁能看哪份」；把内部升级流程和对外退款政策嵌进同一个索引，客户一问投诉，语义上最贴的恰恰是内部文档。若先取回前若干名再过滤，这些无权文本会挤满名额，把真正合规的片段挤出候选，结果常常是「所剩无几甚至为零」——不是没资料，是资料根本没轮到参与打分。安全上更严重：后置过滤意味着那条不该被看到的文本已经进了候选、甚至已经拼进了上下文窗口，此后只要有一条代码路径漏了检查，就是一次真实的数据外泄，而不是「效果差一点」。

所以正确顺序是：请求一进来就确定作用域，把它变成检索条件，让索引在打分之前就只考虑合规的块；过滤字段必须在入库时就跟着块写好，见[切分元数据与父块回溯](./k056-chunk-metadata.md)。多用户系统里这个作用域还要贯穿记忆与工具调用，不能只在检索这一环做，相关背景见[会话隔离与租户边界](./k105-session-isolation.md)。整套顺序可以从[从这里开始](./00-start-here.md)看起。

## 用进阅览室前的登记来理解

把检索想成进一间分层开放的阅览室查资料，过滤就是门口那道登记。

合理的做法是：进门时先核验身份，管理员按你的证件把能进的区域划出来，发一张只在这些区域有效的借阅牌；你之后所有的查找都只在这片区域里进行，架子上根本没有你看不到的书。这样既不会白跑一趟，也不存在「先看见再装作没看见」的尴尬。

后置过滤相当于另一种安排：先放你进所有区域，任你在整间阅览室里挑出最贴合的十本抱到桌上，等你抱好了，管理员才过来把其中不合规的抽走。两个麻烦立刻出现。一是你可能挑了半天、抱回的全是内部资料，抽完之后桌上一本不剩；二是那些内部资料你确实已经翻开看过了，抽走只是补救，不是没发生。

对应关系：证件是用户身份，可进区域是作用域，借阅牌是带进检索的过滤条件，整间阅览室是未隔离的索引，抽走是后置过滤。这个比喻点明了「前置」的实质：它不是把筛选做快一点，而是把「不可见」这件事变成查找范围本身。

:::quote
过滤条件要长在检索请求里，不能长在检索结果之后。范围先划好，相关度才有意义。
:::

## 把前置画出来

先看一次请求从进来到取回合规片段，条件在哪一步生效。

:::figure 带作用域的一次检索
@flow
确认身份|生成过滤条件|在范围内召回|按相关度排序|返回合规片段
:::

第二步「生成过滤条件」排在第三步之前，是这一整篇的要害：条件一旦成了范围，后面排序再怎么算都不会碰到范围外的块。

过滤该管哪些字段，可以列成清单：

:::figure 检索期该带上的过滤字段
@stack
租户::本次请求属于哪家，索引级或文档级隔离都靠它
可见范围::按用户与会话判定，只读的人不该召回内部件
时效::生效日期与失效日期，过期政策不参与现行答案
类型::文档类型与语言，避免把别的业务线材料混进来
:::

第二行与第三行是两类最容易漏的：一个关于「谁能看」，一个关于「还算不算数」。两者都该在打分前生效，而不是答案生成时靠提示词叮嘱模型别用。

再看两种顺序的差别：

:::figure 后置过滤，与前置过滤
@compare
召回后再筛::候选常被挤空|越权文本已进窗口|漏一处即外泄
先划范围再查::合规片段参与打分|范围外的根本不进|安全性不依赖下游
:::

第二行三格对应效果与安全的两面：合规片段能正常参与竞争，范围外的文本从一开始就不存在，安全性不指望后面每一条代码路径都记得检查。

:::tip 一条立刻见效的规则
把作用域做成检索函数的必填参数，不给默认值。谁要查，就得显式交出「租户、可见范围、当前时间」；函数内部第一件事就是按它圈范围，别留「先查了再说」的口子。
:::

## 再往深问两层

:::ask 那如果过滤字段写得不全，前置会不会反而把该找的也挡在外面？
:::

会，这正是前置的代价：它很硬，条件写错就是直接查不到，而且不报错、只表现为「零命中」。所以字段要跟代码一起被验证：入库时给每块写全租户、可见范围、生效与失效时间、文档类型，缺的显式标成「未知」；检索时按最保守处理「未知」（宁可不召回，也不要猜成公开）。还要留一组固定的评测问题，专门覆盖「该可见的能查到、不该可见的查不到」两类，每次改过滤逻辑都跑一遍。另外别把「时效过滤」当成一次性配置：政策有生效日期，今天不可见的版本明天可能可见，条件里必须带「当前时间」这个变量，而不是写死一份名单。这类确定性判断——日期比较、版本新旧、权限核验——应该由代码算好再写进上下文，别交给模型去判断。检索质量怎么分开测，见[多轮检索与检索质量评测](./k064-rag-eval.md)。

:::ask 再深一层：索引级的租户隔离、文档级的标签过滤，该怎么选？
:::

按规模与运维能力选，三档强度不同。索引级是每家一套独立集合，物理上就分开，最彻底，漏带过滤条件也串不了，代价是集合数量多、运维与成本都高，适合租户少、合规要求高的场景。文档级是大家共用一个集合，每块带租户与可见范围标签，靠强制过滤条件隔开，省钱，但强度取决于「每一条检索路径都带对了条件」——包括改写后的多路召回、缓存命中、以及内部调试工具，漏一条就破。字段级更细，极少用，除非同一文档里不同字段的可见性都不同。无论选哪档，有两条要一起做：给缓存键、记忆命名空间、日志索引也带上同样的作用域，否则检索没越权，却可能在缓存命中时把别人的结果返回去；以及把每次检索用的过滤条件记进日志，回放时能核对「当时到底按什么范围查的」。缓存那部分与[前缀缓存与即时注入](./k050-prefix-cache.md)有关，日志留痕的思路见[Trace 该记什么](./k094-trace-fields.md)。

## 一份能跑的对照

下面这段只用标准库，构造一批带租户、可见范围、时效字段的片段，分别实现前置与后置过滤，把「后置候选清零、前置仍能答」的差别摆出来。

```python
# meta_filter.py —— 只用标准库，python meta_filter.py
import re
from dataclasses import dataclass


@dataclass
class Chunk:
    id: str
    text: str
    tenant: str
    acl: str
    valid: bool


POOL = [
    Chunk("c1", "VIP 投诉升级流程（内部）", "A", "internal", True),
    Chunk("c2", "VIP 投诉升级流程（内部副本）", "A", "internal", True),
    Chunk("c3", "VIP 投诉处理时限", "A", "internal", True),
    Chunk("c4", "对外退款政策", "A", "public", True),
    Chunk("c5", "过期退款政策", "A", "public", False),
    Chunk("c6", "B 租户退款政策", "B", "public", True),
]


def terms(t):
    return set(re.findall(r"[A-Za-z0-9]+|[\u4e00-\u9fff]", t.lower()))


def relevance(q, c):
    return len(terms(q) & terms(c.text))


def pre_filter(q, pool, tenant, acl, k):
    # 先圈范围，再在范围内排序
    cand = [c for c in pool if c.tenant == tenant and c.acl == acl and c.valid]
    cand.sort(key=lambda c: -relevance(q, c))
    return cand[:k]


def post_filter(q, pool, tenant, acl, k):
    # 先取回前 k 名，再逐条筛掉不合规的
    ranked = sorted(pool, key=lambda c: -relevance(q, c))[:k]
    return [c for c in ranked if c.tenant == tenant and c.acl == acl and c.valid]


if __name__ == '__main__':
    q = "VIP 投诉"
    pre = pre_filter(q, POOL, tenant="A", acl="public", k=3)
    post = post_filter(q, POOL, tenant="A", acl="public", k=3)

    assert len(pre) == 1                         # 前置：仍有合规片段可答
    assert post == []                            # 后置：前 k 名全被筛光
    assert all(c.acl == "public" and c.tenant == "A" and c.valid for c in pre)
    assert "B 租户" not in "".join(c.text for c in pre)   # 租户隔开

    top = sorted(POOL, key=lambda c: -relevance(q, c))[:3]
    assert all(c.acl == "internal" for c in top)          # 越权文本排在前面
    assert relevance(q, POOL[0]) > relevance(q, POOL[3])  # 正是它挤掉了合规件
    print("通过 6/6 项：前置过滤保住候选，后置过滤清零且越权件已进候选")
```

1. `Chunk` 把租户、可见范围、是否有效三个字段固定下来，模拟入库时就写好的元数据。`POOL` 里前三块是内部文档、用词与问题高度贴合，第四块才是能对外说的政策，第五块已失效，第六块属于别家。
2. `relevance` 是最朴素的相关度：数查询词项与片段词项的交集个数。故意做得很笨，好让「谁排前面」完全由词面决定，便于复现。
3. `pre_filter` 与 `post_filter` 只差一个顺序：前者先把 `tenant`、`acl`、`valid` 三个条件套上再排序；后者先按相关度取前 `k` 名再逐条筛。这一行先后，就是整篇要讲的事。
4. 前两条断言把现象摆出来：同一个问题、同一批数据、同一个 `k`，前置仍能返回一份合规片段，后置返回空。第三、四条验证返回的确实合规、且没串到别家。
5. 后两条断言解释原因：相关度最高的前几名清一色是内部文档，正是它们把合规片段挤出了名额；而它们一度进入了候选，就是后置过滤的安全隐患。六条断言跑完打印通过项数。

想看得更清楚，可以把 `k` 从 3 调到 6，会看到后置过滤终于能留下一条——但这恰恰说明它依赖「取得够多才碰得到合规件」，而取得越多、越权文本进候选也越多，不是个能靠调参数解决的办法。

## 踩过的坑

- **检索后再过滤**：现象是候选常被清空、答案变成「未找到依据」 → 原因是不合规却高相关的片段占满了名额 → 怎么改：把条件变成检索请求的一部分，在打分前圈范围。
- **越权文本已进窗口**：现象是某条路径漏了检查，内部内容被写进答案 → 原因是过滤放在结果侧，依赖每条路径都记得检查 → 怎么改：范围外的块根本不参与召回，安全性不押在下游。
- **字段缺失被当成公开**：现象是「未知可见范围」的旧片段被谁都能查到 → 原因是空值在条件里被当作「不限制」 → 怎么改：显式编码「未知」，过滤时按最保守处理。
- **时效条件写死**：现象是政策生效后仍查不到，或过期件还在被引用 → 原因是过滤没带「当前时间」这个变量 → 怎么改：生效与失效日期跟着块存，检索时按当前时间比较。
- **缓存键不带作用域**：现象是检索没越权，缓存命中时却返回了别家结果 → 原因是缓存、日志、记忆没沿用同一套隔离 → 怎么改：所有派生索引的键都带上租户与可见范围。

## 三句话

元数据过滤前置，是把租户、可见范围、时效这些条件变成检索范围本身，在打分之前就圈定合规片段。
关键做法是让作用域成为检索函数的必填参数，并给缓存、日志、记忆沿用同一套隔离边界。
当系统只有单一用户、全部材料都同等可见且无需区分时效时，可以省掉这层过滤。

# 框架六大件：看清框架替你接管了哪几件事

## 场景提问

你照着一段示例写了个能自己调工具的小程序，跑通了，心里挺踏实。过阵子换了个框架，同样是「创建、塞工具、开跑」那几行，行为却变了：重试次数对不上，中途断了接不回来，出了问题翻不到当时到底调了哪个工具。你以为是新框架不好用，于是再换一个，结果还是在这几件事上纠结。明明代码没怎么改，差别到底出在哪？

## 破误解

**不是哪个框架更好用，是你把「框架替你做的那几件事」当成了空气**——看不见，就没法比较，没法替换，更没法排查。

框架的便利来自「接管」。框架（framework，把一组通用能力打包好、只留业务细节给你填的可复用代码，白话讲像一台预装好流水线的机器）替你保存了状态、替你转起了循环、替你把工具名分到具体函数、替你记了轨迹、替你重试、替你把状态落盘。这六件事并没有凭空消失，只是被收进了框架内部。你写的那几行其实是「配置」，真正干活的仍是这六件。把它们逐件点名，框架就从一个黑盒变成一张清单：每一件谁在管、默认值是什么、能不能改，都能问出答案。反过来，只记住「在某家框架里怎么点菜」，换一家就得从头学，因为菜名没变，厨房的规矩全变了。

## 生活类比

把框架想成一家「代客中央厨房」。你点一道菜，厨房替你做六件事，你只看得见端上桌的成品：

- **备料台**记着「这桌菜做到哪一步、还差几样料」，这是状态；
- **灶台**按「炒完尝味、不够再补」反复转，直到达标或火候到点，这是循环；
- **传菜口**把「宫保鸡丁」这张单子递给对应厨位，而不是随便哪个灶，这是工具分发；
- **墙上的小票**逐笔记下每道菜每一步用了什么、出了什么，这是追踪；
- **一锅糊了**不直接倒掉，按规矩重做一次、最多两次，这是重试；
- **打烊台账**抄下「做到第几步、用了哪些料」，明天接着做，这是持久化。

对应关系要说清楚：你以为自己只做了「点菜」，可这六件决定了菜能不能出、糊了怎么办、明天能不能续。换厨房时，菜名（你的业务目标）没变，备料台怎么记、糊了重做几次、台账留不留，可能全变了——这正是换框架后行为变样的根源。看懂「厨房干了什么」，比记住「在某家厨房怎么点菜」有用得多，因为前者能迁移，后者不能。

## 层层追问

:::ask 那如果把框架全拆掉，六件都自己写，是不是就一定更好？
不一定。这里要分清「看懂」和「自己实现」是两回事。看懂六件，是为了能判断框架给的默认规矩合不合你的场景：重试几次才合理、状态该不该跨进程、轨迹要留多久、落盘是每次都写还是只在检查点写。如果框架给的默认规矩正好合适，直接用它省下的工作量是实打实的，没必要重造一遍。只有当某一件的规矩与你的要求冲突、而框架又不让你改时，把那一件拿回来自己管才划算。这也是[框架选型与自研编排的取舍](./k083-build-vs-framework.md)里那条判断线的起点：先问「哪一件我必须自己握着」，再决定用不用框架。
:::

:::ask 那如果六件里只想换掉一件，比如自己管重试，其余还用框架，行不行？
行，而且这恰恰是最常见的做法，前提只有一个：框架允许把那一件单独替换。这就引出一个比功能数量更有用的评估标准——「能不能逐件替换」。能替换，说明六件之间的边界清楚，交互走的是明确接口；不能替换，说明它们被缠在一起，动一件会牵动全身，改重试次数结果连循环终止条件都跟着变。所以看一个框架，与其数它有多少现成能力，不如问一句「这六件我能不能各自拿回来」。这个答案会直接决定后面要不要加一层隔离，也就是[解耦适配层](./k077-adapter-layer.md)专门要解决的麻烦。追到这一层你会明白：所谓「不被版本牵着走」，靠的不是选对框架，而是让业务代码不直接依赖这六件的具体形状。
:::

## 可运行代码并逐行解释

下面这段用标准库把六件都摆到台面上，复制成文件直接运行即可，不联网、不需要任何账号或第三方包。

```python
"""框架六大件的最小可运行骨架：状态、循环、工具分发、追踪、重试、持久化。"""
import json


class TransientError(Exception):
    """代表一次临时故障：重试有机会成功。"""


def make_flaky_add(fail_times=2):
    """构造一个前几次失败、之后成功的确定性工具，用来观察重试。"""
    counter = {"n": 0}

    def add():
        counter["n"] += 1
        if counter["n"] <= fail_times:
            raise TransientError("临时故障")
        return 1

    return add


class MiniFramework:
    def __init__(self, tools, max_steps=10, max_retries=2):
        self.state = {"done": False, "value": 0, "step": 0}  # ① 状态
        self.tools = tools
        self.trace = []                                       # ④ 追踪
        self.max_steps = max_steps
        self.max_retries = max_retries

    def dispatch(self, name, **kwargs):                       # ③ 工具分发
        if name not in self.tools:
            raise KeyError("未知工具: " + name)
        return self.tools[name](**kwargs)

    def call_with_retry(self, name, **kwargs):               # ⑤ 重试
        last = None
        for attempt in range(self.max_retries + 1):
            try:
                result = self.dispatch(name, **kwargs)
                self.trace.append((name, "ok", attempt))
                return result
            except TransientError as exc:
                last = exc
                self.trace.append((name, "retry", attempt))
        raise last

    def persist(self):                                       # ⑥ 持久化
        return json.dumps(self.state, sort_keys=True)

    def restore(self, blob):
        self.state = json.loads(blob)

    def run(self, plan):                                     # ② 循环
        while not self.state["done"] and self.state["step"] < self.max_steps:
            action = plan(self.state)
            value = self.call_with_retry(action["tool"], **action["args"])
            self.state["value"] += value
            self.state["step"] += 1
            if self.state["value"] >= 3:
                self.state["done"] = True
            self.trace.append(("step", self.state["step"], self.state["value"]))
        return self.state


def make_plan(_state):
    """计划函数：本例固定要求调用 add 工具。"""
    return {"tool": "add", "args": {}}


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    fw = MiniFramework(tools={"add": make_flaky_add(2)}, max_steps=10, max_retries=2)
    state = fw.run(make_plan)
    ok(state["done"] is True, "循环达到完成条件后终止")
    ok(state["value"] == 3, "状态里累计值正确")
    retries = [t for t in fw.trace if t[1] == "retry"]
    ok(len(retries) == 2, "追踪记录了两次重试")
    ok(any(t[0] == "add" and t[1] == "ok" for t in fw.trace), "工具分发确实调用了目标工具")
    ok(state["step"] <= fw.max_steps, "步数没有越过上限")

    blob = fw.persist()
    fw2 = MiniFramework(tools={"add": make_flaky_add(2)}, max_steps=10, max_retries=2)
    fw2.restore(blob)
    ok(fw2.state == state, "持久化快照可还原出同一状态")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `self.state = {...}` 是六件里的**状态**：把完成标志、累计值、轮数写成结构化字段。任何一步都能直接读，不用回头翻聊天记录去猜「做到哪了」。
2. `dispatch` 是**工具分发**：先查工具名有没有登记，再把参数交给对应函数。它把「要调 add」翻译成「真正执行哪个函数」，这一层永远在你自己的代码里，不交给模型。
3. `call_with_retry` 是**重试**：只针对 `TransientError`（临时故障）重试，次数受 `max_retries` 约束，且每次成功或重试都往追踪里写一条，让重试不是悄悄发生的。
4. `self.trace` 是**追踪**：用元组列表记下工具名、结果类型、第几次尝试。出问题时，它是唯一能回答「当时到底发生了什么」的依据。
5. `persist` 与 `restore` 是**持久化**：把状态序列化成字符串（序列化，指把内存里的对象转成能存储、能再读回的文本），换一个新实例也能还原出同一份状态。
6. `run` 是**循环**：`while` 同时看完成标志与步数上限，两个条件一起保证不会跑飞；每轮末尾把进度写进追踪，供回放时对齐。
7. `make_flaky_add` 是本地确定性桩函数（桩函数，指用一段固定行为替代真实外部服务的替身）：前两次故意抛临时故障，让「重试」这件事在断言里看得见，全程不联网、不调外部地址。
8. `main` 里用一组 `ok(...)` 断言逐件验收：完成条件、累计值、重试次数、分发命中、步数上限、快照还原，最后打印 `通过 6/6 项`。断言的意义是把「六件确实都在工作」变成可复现的核对，而不是靠读一遍觉得没问题。

这段代码想说明的其实很简单：六件全都出现在这不到百行里，没有一件是魔法。框架做的，是把它们包得更整齐、默认值给得更全、边界情况处理得更细。再看第二张图，你可能已经注意到「循环」这一件还有别的写法——用节点和边来表达，正是[状态机与图编排](./k076-state-machine.md)要讲的事。

## 踩坑与边界

- **把配置当成全部**：现象 → 只会写「创建、塞工具、开跑」三行，一出问题就无从下手 → 原因 → 六件被框架默认值接管，你没意识到它们存在 → 怎么改 → 逐件问一句「这件事现在谁在管、默认值是多少」，把答案写在自己的设计说明里。
- **重试掩盖了副作用**：现象 → 一次超时后，同一条数据被写了两遍 → 原因 → 重试件不知道动作是否已经生效，网络超时不等于没执行 → 怎么改 → 给有副作用的动作配一个稳定标识，重试前先查执行状态，也就是幂等（idempotency，白话讲：同一个动作做一次和做几次，结果都一样）。
- **追踪只记结果不记选择**：现象 → 出问题时只看到最终答案，看不到为什么选了这个工具、传了什么参数 → 原因 → 追踪件留得太粗，只存了输出 → 怎么改 → 把每轮的输入、选中的工具、参数、返回结果都记成结构化行，能按任务编号串起来。
- **状态靠聊天记录复原**：现象 → 中断后接不上，或者接上了却把做过的事又做一遍 → 原因 → 状态件没有独立的结构化字段，也没落盘 → 怎么改 → 目标、已完成、轮数、预算分别存字段，落盘后按字段续跑，已完成清单用来跳过重复动作。
- **六件缠成一团**：现象 → 只想改重试次数，却连带改了循环和分发 → 原因 → 六件之间没有明确边界，互相直接读写对方的内部变量 → 怎么改 → 让六件各通过一个明确接口交互，必要时加[解耦适配层](./k077-adapter-layer.md)把业务代码与框架形状隔开。

还要说清边界：六件是一副观察框架用的眼镜，不是必须全部显式实现的一套零件。一个只读、单轮、跑完即弃的小脚本，追踪和持久化可能根本用不上，硬加反而是负担；反过来，只要涉及写操作、跨进程或长任务，「持久化」与「重试」就必须自己设计清楚，不能指望默认配置替你兜住。另一个常见误会是「框架会替我决定何时该停」——终止条件属于业务判断，框架最多提供上限，标准还得你给。顺着[起点说明](./00-start-here.md)往下读，你会看到这六件在不同话题里反复出现，只是每次换了个名字。

## 三句话小结

框架六大件，是状态、循环、工具分发、追踪、重试、持久化这六件被打包接管的通用能力。
看懂它的做法是逐件点名默认值，并用断言验证每件确实在工作。
当某件的默认规矩与场景冲突、又不让你单独替换时，才需要把那一件拿回来自己管。

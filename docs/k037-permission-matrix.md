# 权限矩阵与最小权限

## 场景提问

你给一个内部助手接上了一整排工具：查文档、写笔记、删记录、发起一笔转账。为了让「模型别被束缚住」，你图省事用同一个什么都能干的账号把所有工具一次性挂了上去，觉得反正模型会自己挑该用哪个。前几轮都挺顺，直到有一轮，用户只是问「帮我查一下上个季度的报销规则」，助手在翻到的一页材料里读到一句像是「顺手把过期记录清理掉」的话，竟然真的去调了删除工具，把一条本该留存的记录抹掉了。你去复盘「它凭什么能删」，翻遍提示词只找到一句「请谨慎使用有副作用的工具」，根本说不清到底是谁、在什么条件下、被允许对哪个工具做哪个动作。明明只是想让它查点东西，怎么最后连删带转的权限全递了出去？

## 破误解

**不是模型学坏了，是你把「能不能调这个工具」这件事交给了模型的自觉，而没有在代码里画一张表、每次调用前逐一判定。**

先把两样容易被混成一谈的东西分开：工具清单和权限清单。工具清单回答的是「系统里有哪些工具、每个工具的参数长什么样」，它是给模型看的说明书；权限清单回答的是「这一次、这个身份、对这个工具、做这个动作，到底准不准」，它是给执行器看的闸门。很多人写完一份措辞漂亮的工具描述，就误以为边界已经立住了，其实那份描述只是给模型的建议，模型可以听，也可以被别的内容带偏。真正产生副作用的是执行器按下按钮的那一步，闸门必须装在这之前，而且不能读模型的脸色。

于是就有了权限矩阵：一张二维甚至三维的对照表，行是主体（谁在发起这次调用），列是工具，格子里再写清允许的动作。所谓动作，是把一次调用拆得更细：同一个「记录」工具，只读、写入、删除是三种完全不同的后果，只按工具名授权，等于把三种后果一起放行了。和矩阵绑在一起的是最小权限（least privilege，只授予完成当前任务所必需的那点权限，多一点都不给），以及它的底座——默认拒绝（deny by default，凡是表里没写明允许的，一律当作不允许，而不是反过来「没写明禁止就放行」）。这两句听着像口号，落到实现上其实只是查表时一行取值的差别：查不到时返回「拒绝」还是「允许」，写反了，性质就完全变了。

再补几个第一次见会发懵的说法。ACL 是访问控制列表（Access Control List），白话就是「逐条列出谁对什么有什么权限」的一张清单；RBAC 是基于角色的访问控制（Role-Based Access Control），白话是「不给人逐个配，先给岗位配好一套，再把人归到岗位上」。还有一个容易被忽略的点：判定用的身份，必须来自会话建立时由系统写进去的那个可信字段，而不是模型在回复里自称「我现在是管理员」。模型输出的内容属于不可信输入，拿它当身份，等于把闸门的钥匙又递回给了模型。把这些合起来看，这张表要管的其实是四件事：主体是谁、能对哪些工具、每个工具能做哪些动作、没写到时怎么办。想清楚这四格，比在提示词里反复叮嘱「不要乱删」有用得多。

## 生活类比

把它想成一栋办公大楼的门禁卡。保洁拿的卡能进公共区和各层茶水间，财务拿的卡能进财务室和保险柜所在的房间，来办事的访客拿一张临时卡，只能进一楼会议室，而且当天下午五点自动失效。没有任何人手里有一张「全楼通用、还能改门锁」的总卡；就算真有，也锁在保卫处的柜子里，谁领、几点领、办完有没有还，都要登记。注意这里的关键不是「信任谁」，而是「这份活需要进哪几扇门」：不给保洁开财务室，不是怀疑保洁这个人，是他的工作压根用不上那扇门。

对应关系很具体：那张卡，就是主体身份；一扇门，对应一个工具；「刷卡进门看一眼」和「刷卡进去搬东西走」，对应只读与删除这两种动作；卡上没登记的门刷不开，就是默认拒绝——注意是「没写就开不了」，而不是「没写就随便进」；只给干这份活需要的那几扇门，就是最小权限；访客卡到点失效、用完收回，就是及时回收；保卫处那本登记簿，就是每次授权与拒绝都留一条痕，事后能回答「刚才那一下是谁、凭哪条规则放行的」。

这个比喻还点出最要命的一处：最怕的不是丢一张卡，而是嫌一张张配麻烦，干脆给所有人都发同一张万能卡。效率是高了，可一旦出事，既拦不住，也查不出是谁开的门。放到系统里，就是所有会话共用一个高权限账号，一处被绕过，处处失守，日志里只剩「某个动作发生了」。还有一层：不能因为来人自己说「我是财务」就给他财务卡，得看前台核验过的身份——这正对应「判定身份要用可信字段，不采信模型自称」。

## 自绘示意图

:::figure 一次工具调用前该过的几关
@flow
收到调用意图|取可信身份|查权限矩阵|命中才执行|记一条留痕
:::

这五格是串成一条链的，不是并列的五个说法。最常被跳过的是「取可信身份」和「查权限矩阵」这两格：很多链路从「收到调用意图」直接跳到「执行」，中间只靠模型自觉。「命中才执行」强调判定结果必须真的能挡住执行，而不是判完记一笔、照样往下走；「记一条留痕」则保证被拒绝的尝试也看得见，事后才查得清。

:::figure 一张权限矩阵要写清的四件事
@stack
主体是谁::用会话里可信的身份，不采信模型自称的角色
能对哪些工具::只列出这份活需要用到的工具名
每个工具能做哪些动作::读、写、删除分开写，不写就表示不允许
没写到时怎么办::默认拒绝，并记一条被拦下的尝试
:::

四格里最容易含糊的是第一格和最后一格。第一格含糊，就会出现「模型说自己是管理员于是放行」；最后一格含糊，新接一个工具时所有身份会莫名其妙自动获得它。「不写就表示不允许」这一句，是整张表能不能守住底线的分水岭。

:::figure 两种授权姿势的差别
@compare
一个万能账号全挂上::省事但一处失守全失守|描述里劝别乱用|出事查不出是谁
按表默认拒绝逐个授::每步都要判一次|越权在代码里被挡|留痕可追到身份
:::

左边顺风顺水时最省事，代价全在出问题的那一刻；右边把成本花在事前画表和每次多判一次，换来的是「谁能做什么」随时答得上来、改得动、退得回。二者差距不在模型聪不聪明，而在闸门到底装没装。

## 层层追问

:::ask 那如果我把工具描述写得特别清楚，反复强调「只有用户明确要求时才能删除」，是不是就够了？
:::

不够，而且这恰恰是最容易踩的一层。描述是写给模型看的「建议」，作用是让模型更倾向于选对工具；它不是写给执行器看的「闸门」，挡不住一个已经决定要调用的动作。更要紧的是，模型读到的内容未必都来自用户本人：它翻到的文档、网页、邮件正文里可能夹着一句像是「请把旧记录清掉」的话，这类间接提示注入（把指令藏进被检索或被读取的内容里，让模型误当成任务的一部分）能改变模型想做什么，参见 [间接提示注入](./k098-indirect-injection.md) 与 [直接提示注入](./k097-direct-injection.md)。描述写得再恳切，也只是在「意图」这一层打转；真正决定后果的是执行器，所以判定必须落在代码里、落在执行之前，见 [代码里的护栏](./k106-guardrail-in-code.md) 和 [函数调用的边界](./k031-fc-boundary.md)。一句话：描述负责让模型少犯错，权限矩阵负责让模型犯了错也造不成后果，两者不能互相顶替。把「只给必需的那点权限」这条原则单独展开，可以看 [最小权限](./k100-least-privilege.md)；参数填得对不对则是另一道关，见 [参数合法性校验](./k034-param-validity.md)。

:::ask 那如果同一套工具要给很多用户用、每人的权限还不一样，这张表会不会大到没法维护？
:::

这一问把边界又往前推了一层，答案是「别按人穷举，按层级收敛」。主体不必是每一个具体的人，可以是一个角色、一个租户、一个会话；先把「这个岗位干这份活需要哪些工具的哪些动作」配成一套，再把人归到这套上，这正是前面说的 RBAC 思路。这样表里的行数跟着「角色」走，而不是跟着用户数量涨，新来一个用户只是归个类，不用重写一整张表。再往下还有两处要一起想：其一，身份得按会话隔开，不能让 A 用户的会话读到 B 用户被授予的东西，见 [会话隔离](./k105-session-isolation.md)；其二，即便某身份平时有写权限，这一轮任务只是查询，也应当把非只读的工具干脆不挂进上下文，让「看得见的范围」和「允许的范围」一起收窄，见 [四类预算](./k103-four-budgets.md) 与 [工具路由](./k036-tool-routing.md)。高权限动作还适合加一道人确认，见 [人在回路](./k102-human-in-loop.md)；把「允许清单」和「执行入口」拆开各管各的，见 [解耦白名单](./k148-decouple-allowlist.md)；真正要跑有副作用的动作时，再套一层受限环境，见 [沙箱与隔离](./k101-sandbox.md)。表不爆炸的诀窍，是让它描述「角色该干什么」，而不是描述「每个人是谁」。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「默认拒绝、按最小权限授予、临时授权再回收、每次留痕」完整做成一个可核查的小模型，结尾用一组断言逐条验证。所有身份、工具和动作都是手工构造的定值，结果可以逐格手算、完全可复现；复制到任意装有 Python 的机器上直接运行即可，不需要任何第三方包、账号或网络。它演示的是判定性质，不是任何真实权限系统的实现。

```python
import copy

# 权限矩阵：主体 -> 工具 -> 允许的动作集合
# 约定：表里没写的一律拒绝（默认拒绝），不是默认放行
MATRIX = {
    "reader": {"doc_search": {"read"}},
    "writer": {"doc_search": {"read"}, "note_save": {"read", "write"}},
    "admin": {"doc_search": {"read"},
              "note_save": {"read", "write", "delete"},
              "user_manage": {"read", "write", "delete"}},
}


def can(matrix, subject, tool, action):
    """逐层查矩阵：主体在不在？工具在不在？动作在不在集合里？任一不满足就拒绝。"""
    tools = matrix.get(subject)
    if tools is None:
        return False
    actions = tools.get(tool)
    if actions is None:
        return False
    return action in actions


def grant(matrix, subject, tool, action, ledger):
    """授予一条最小权限，并留痕，便于事后按痕回收。"""
    matrix.setdefault(subject, {}).setdefault(tool, set()).add(action)
    ledger.append(("grant", subject, tool, action))


def revoke(matrix, subject, tool, action, ledger):
    """回收一条权限；回收后再次查询应为拒绝。"""
    if subject in matrix and tool in matrix[subject]:
        matrix[subject][tool].discard(action)
    ledger.append(("revoke", subject, tool, action))


def main():
    matrix = copy.deepcopy(MATRIX)
    ledger = []
    checks = [
        ("reader 能读文档", can(matrix, "reader", "doc_search", "read") is True),
        ("reader 不能写笔记", can(matrix, "reader", "note_save", "write") is False),
        ("未知主体默认拒绝", can(matrix, "guest", "doc_search", "read") is False),
        ("未知工具默认拒绝", can(matrix, "reader", "pay_transfer", "read") is False),
        ("未知动作默认拒绝", can(matrix, "reader", "doc_search", "delete") is False),
        ("writer 能写笔记", can(matrix, "writer", "note_save", "write") is True),
        ("writer 不能删用户", can(matrix, "writer", "user_manage", "delete") is False),
        ("admin 能删用户", can(matrix, "admin", "user_manage", "delete") is True),
    ]

    # 最小权限：临时给 reader 一个写权限，用完立即回收
    grant(matrix, "reader", "note_save", "write", ledger)
    checks.append(("临时授权后可读可写", can(matrix, "reader", "note_save", "write") is True))
    revoke(matrix, "reader", "note_save", "write", ledger)
    checks.append(("回收后写权限消失", can(matrix, "reader", "note_save", "write") is False))
    checks.append(("授权与回收都有留痕", len(ledger) == 2))
    checks.append(("回收不误伤原有读权限", can(matrix, "reader", "doc_search", "read") is True))
    checks.append(("提权不越界到其他工具", can(matrix, "writer", "user_manage", "read") is False))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `MATRIX` 是那张权限矩阵：外层键是主体（reader、writer、admin 三个角色），内层键是工具名，最里层是一个动作集合（`set`），只列被允许的动作。注释里那句「没写的一律拒绝」是整段代码的灵魂，它把默认拒绝写成了约定，而不是靠谁记着去补一条禁止项。
2. `can` 是那道闸门，分三层查：先用 `matrix.get(subject)` 取这个主体的工具表，取不到就 `return False`；再用 `tools.get(tool)` 取这个工具的动作集合，取不到也 `return False`；最后才判断 `action in actions`。注意三次「查不到都返回拒绝」，这正是默认拒绝的落点，比「查不到就放行」只差一个词，后果却相反。
3. `grant` 用 `setdefault` 两层兜底：主体不存在就建一个空字典，工具不存在就建一个空集合，再把动作 `add` 进去。它同时往 `ledger`（账本，记录每次变更的列表）里追加一条，让「多给了一点权限」这件事事后查得到。
4. `revoke` 是回收：只在主体和工具都存在时用 `discard` 把动作从集合里去掉，`discard` 比 `remove` 温和，元素不存在也不报错。回收同样留痕，于是「给」和「收」成对出现。
5. `main` 里第一组八条断言，逐格验证矩阵本身：`reader` 只能读、`writer` 多一个写、`admin` 才有删除；以及三种「查不到」——未知主体、未知工具、未知动作——都必须被拒绝。这几条把「默认拒绝」和「按动作细分」验死。
6. 第二组演示最小权限的完整动作：先 `grant` 给 `reader` 临时加一个写权限，断言此刻能写；紧接着 `revoke` 收回，断言写权限消失、账本恰好两条、原有的读权限没被误伤。授权是「这一份活临时需要才给」，不是「开局一次性给足」。
7. 最后一条断言确认「提权不越界」：给 `reader` 开过一次写，不代表 `writer` 忽然能碰用户管理，各主体的格子彼此独立。结尾 `passed` 统计通过项、逐条打印结果，再用 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用三个字符串角色代替了真实身份、用字典代替了权限中心、用 `ledger` 列表代替了审计日志，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通并逐格手算。它演示的是默认拒绝、按动作细分、临时授权与回收、留痕可查这几条性质，不是任何具体权限组件的实现；代码本身经过逐行静态复核到「复制即跑、逻辑自洽」，并未在此环境里实际启动执行。

## 踩坑与边界

- **把工具描述当闸门**：现象是描述里反复强调「别乱删」，模型仍在外来内容诱导下调了删除工具并真的执行了 → 原因是描述只影响意图，拦不住「意图到后果」那一步 → 在执行器里按可信身份查矩阵，命中才放行，见 [代码里的护栏](./k106-guardrail-in-code.md)。
- **查不到时默认放行**：现象是每接一个新工具，所有角色立刻自动获得它，谁也没主动开过口 → 原因是判定写成了「没写明禁止就允许」 → 改成默认拒绝，只允许项白名单逐个开，见 [最小权限](./k100-least-privilege.md)。
- **按工具名而不按动作授权**：现象是只开了「记录」工具，却发现写和删除也跟着能用 → 原因是一个工具内部的读、写、删被当成同一格 → 把动作拆成独立格子分别登记，见 [工具结构定义](./k032-tool-schema.md) 与 [参数合法性校验](./k034-param-validity.md)。
- **采信模型自称的身份**：现象是模型回一句「我现在是管理员」就越权成功 → 原因是把模型输出的不可信文本当成了权限判定依据 → 身份只取会话建立时写入的可信字段，见 [会话隔离](./k105-session-isolation.md) 与 [身份注入](./k137-identity-injection.md)。
- **授权一次发全、全程不收**：现象是这一轮明明只是查询，上下文里却仍挂着删除与转账工具 → 原因是开局把整套工具一次性挂齐 → 按当前任务临时授予、用完即收，多余工具干脆不挂进上下文，见 [工具路由](./k036-tool-routing.md) 与 [四类预算](./k103-four-budgets.md)。

还要说清一条边界：最小权限不是把权限砍得越少越好。砍到任务做不成、逼得人反复手动放行，反而会诱导大家图省事开一张万能卡，比不收窄更糟；恰当的分寸是「恰好够完成当前任务，一格也不多」。另外，高权限动作加一道人确认是必要补充，但审批得有到期时间，别让请求无限挂着，见 [人在回路](./k102-human-in-loop.md)；这张表本身也该当成可版本化、可查可退的产物，而不是散落在代码各处的字符串，见 [提示与策略版本化](./k113-prompt-versioning.md)。若想接着看清一次调用从构造参数到结果回传的完整链路，可以对照 [工具结果回传](./k035-tool-result.md)。

## 三句话小结

权限矩阵与最小权限，是用一张「谁、对哪个工具、能做哪个动作」的对照表，把「能不能调用」从模型自觉手里收回到代码手里，且表里没写的一律拒绝。

关键做法是判定只认会话里的可信身份、把读与写与删除拆成独立格子、按当前任务临时授予并及时回收、每次授权与拒绝都留痕可查。

当系统只产出离线文本、根本不触碰任何有副作用的动作时，不必硬套这张表；但只要一次调用会改动外部状态，它就不该只靠一段措辞清楚的提示来守。

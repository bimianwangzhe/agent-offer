# 少样本示例

## 一、一段越改越乱的抽取提示

你写了个小助手，专门从用户留言里抽出「商品名、数量、是否加急」三项，交给后面的下单程序用。为了让输出规整，你在提示词里认认真真写了三百多字：要规范、要完整、只输出 JSON、字段不要多也不要少、布尔值别写成中文。头一次它回你「好的，已为您整理如下，希望能帮到您～」，把要解析的内容裹在一句客套话里；第二次它把「加急」写成了字符串「是」，第三次又换成 `true`，字段顺序还每次都不一样。下游的解析代码天天报错，你只好接着往那段话里补「请务必」「一定要」「再次强调」，结果越补越长，它连最简单的一句「买两箱牛奶」都开始答得飘忽。你开始怀疑是不是这个模型不太行。如果你刚照着[起步说明](./00-start-here.md)跑通第一个脚本，这种「明明讲得够清楚了却还是乱」的憋屈，多半出在你教它的方式上。

## 二、不是没听懂道理，是该给样子却讲了道理

**不是模型没读懂你的要求，而是你用「讲道理」去教一件本该用「给样子」来教的事。**

先把几个词摆平。提示词（prompt）就是你写给模型的那段说明文字，用来告诉它这回要做什么、按什么形状回答。零样本（zero-shot）是只下指令、不给任何例子的做法；少样本（few-shot）则是在提示词里放上少量成对的「输入—输出」例子，让模型照着做。JSON（JavaScript Object Notation，用花括号和键值对表示数据的文本格式）是下游程序最爱读的那种文本。

问题出在「讲道理」这一步上。一段文字指令描述的是抽象要求：「规范」「完整」「布尔值别写成中文」。模型读到之后，得自己把这几个词翻译成一个具体的输出长相，而「规范」能对应无数种都算合理的写法：字段名用中文还是英文、顺序怎么排、空着的值写 `null` 还是写「无」、布尔值用 `true` 还是 `1`。你没指定，它每回就重新翻译一次，于是格式随轮次漂移。示例对干的事，是把这一步翻译直接替它做完：你给它看「留言长这样 → 输出就该长这样」，它不必再猜你想要哪种写法，照抄那个形状就行。

这里要分清两件事：格式和内容。示例最擅长定的是形状、字段、类型、风格，也就是「答案长什么样」；它并不保证「答案算得对」。一句「不要加急」到底该抽成 `false` 还是漏掉，靠示例示范比靠形容靠谱得多，可要是抽出来的数量本身算错了，示例帮不上忙，那得靠后面的校验去兜。还有一层常被忽略：示例是「请求」，不是「保证」。你给得再工整，模型仍然可能不照做——这一点在[「请只输出 JSON」为什么不是保证](./k014-json-request.md)里会拆开讲。所以示例负责把目标画清楚，真正兜住结果，还得靠代码那一关。

## 三、教新人填报销单：念规范，还是推三张样单过去

把这件事想成教一位新同事填报销单。你把他叫过来，念了半小时《财务填写规范》：金额栏要规范、日期要完整、类别要准确、附件要齐全。他点点头，回头交上来的单子写着「大概三百」「昨天」「杂项」，附件那栏空着。不是他不认真，是「规范」这两个字在他脑子里能落成的样子太多了。

换一种教法：你什么大道理都不讲，直接把三张填好的样单推过去。第一张是最普通的餐饮报销；第二张特意挑了「没拿到发票、金额栏该写什么」；第三张挑了「跨月冲红、金额是负数」。你只补一句：「照这个样子填。」他一眼就看懂了：金额得写数字、带两位小数；没发票不是留白，而是写「无」；负数前面要带减号；日期一律写全年月日。

对应关系可以一条条摆出来。那半小时规范条文，就是零样本里那段抽象指令；三张填好的样单，就是少样本里的示例对；新同事就是模型；单子上一个个填好的格子，就是输出里的字段和格式。最要紧的一点藏在样例的挑选里：第一张最典型的单子，其实新同事本来就会填，教了等于没教；真正让他少犯错的，是后两张专门挑的边界情况。挑示例和挑样单是同一个道理——典型情况模型自己就能做对，只有边界才暴露「你到底想要哪种写法」。把预算花在边界上，比堆一沓长得都差不多的普通样例划算得多。

:::tip
一句话记住：**讲一百句「要规范」，不如给一张「就长这样」的样单。** 判断该补提示还是补示例，只问一句：我纠结的是「它不知道该做成什么形状」，还是「它知道形状却做错了内容」？前者补示例，后者补校验。
:::

## 四、从挑样例到稳定输出，中间经过了什么

把少样本这件事拆成一条链子看，就知道每一环各管什么。

:::figure 一次从示例到稳定输出的链路
@flow
挑边界样例|组成示例对|拼进提示词|照样子产出|按格式校验
:::

第一步挑的是那些容易写歪的情况，不是最顺手的那条；第二步把「输入」和「它该有的输出」配成一对，缺一半都不算示例；第三步才把它们接进提示词；第四步模型照着示范给出结果；第五步仍要留一道校验，因为示例只是示范，不是约束。五步里少了最后一步，前面做得再漂亮，遇到模型偶尔不照做时照样会漏。

:::figure 示例对该覆盖的四类情况
@stack
典型样本::最常见输入，用来定基础形状，一两条即可
空值样本::字段缺失或为空时该写什么，别留白
否定样本::含「不」「无」「取消」时别把否定读反
边界样本::超长、多值并列、极值时的固定写法
:::

四类不必等量分配：典型样本最少，边界与否定最该多给。空值那类尤其容易被漏，一旦没示范，模型遇到「还没定」这类输入就会自作主张地留空、编一个值，或者干脆把整个字段省掉。

:::figure 只讲道理与给示例对的差别
@compare
只讲道理::抽象要求有多种翻译|格式随轮次漂移|边界全靠猜
给示例对::长相被直接示范|格式稳定可解析|边界写法明确
:::

把形状定住之后，还有个更进一步的动作：把这个「形状」从几段示例里抽出来，写成机器能逐项检查的结构描述，那是[JSON Schema 约束](./k015-json-schema.md)要讲的事；而形状到底齐不齐、类型对不对，则交给[结构层校验](./k017-structure-check.md)去判。示例负责「让人一看就懂」，结构描述负责「让代码一查就准」，两者是配合，不是替代。

## 五、那如果示例越给越多、或者格式本就没有唯一解呢

:::ask 示例是不是给得越多越稳
:::

不是。示例也是要占位置的：每一组示例对都得挤进上下文窗口（一次调用里模型这一眼能看到的全部文字），塞得太多，反而把本轮真正要处理的输入挤到角落，注意力被摊薄，成本也跟着涨。更隐蔽的坑是「照抄内容」：示例和真实输入贴得太近、示例里又用了很像真数据的单号和人名，模型容易把示例里的取值搬到答案里，而不是学到格式。所以该做的是覆盖到位，而不是数量堆多，两三组涵盖典型、空值、否定、边界往往就够。顺着再追一层：那示例里的值该怎么写？用一眼就看出是编的值，比如「示例商品」「测试单号」，别用能被误当成真实订单的编号；示例和本轮输入之间也要留个明显区分，让模型清楚哪几行是示范、哪一行才是这回要答的。

:::ask 那如果这任务本来就没有唯一正确的格式呢
:::

比如让它「写一段总结」，长短、分不分点都说得过去，这时就不该用少样本去硬定一个形状，硬定反而把合理的多样性掐掉了。更稳的顺序是：先用结构描述把必须有、必须能查的那几个字段圈出来，再用结构校验兜住底线，示例只用来带一带语气和措辞，不拿它当正确性依据。再追一层：那示例能不能干脆替掉校验？不能。示例写在提示词里，本质仍是一句「请你照做」的请求，模型完全可能这轮照做、下轮不照做；把「希望它规整」和「保证它规整」混为一谈，是这一整段最容易踩的坑。也正因如此，示例和[思维链与分步引导](./k013-chain-of-thought.md)这类引导手段一样，都属于「让结果更可能好」，而不是「让结果一定对」。

## 六、一段能直接跑的示例组装器

下面这段只靠 Python 标准库，用一个确定性桩函数模拟模型：给它看示例时，它按示范的固定形状输出；不给示例时，它用散乱写法。数字全是本地构造出来的，只为把机制跑给你看，不是对任何真实模型的统计。

```python
# 少样本示例：用确定性桩函数演示「示例对」如何定住输出格式。
# 全程只用标准库，不联网、不调用任何真实模型；数字是构造场景，不是实测统计。

import json

# 四条示例对：特意挑「空值 / 否定 / 多值 / 加急」这些最容易被写歪的情况。
DEMOS = [
    ("买两箱牛奶",                {"item": "牛奶", "qty": 2, "urgent": False}),
    ("随便看看，还没定",          {"item": "无",   "qty": 0, "urgent": False}),
    ("不要加急，订三支笔和一块橡皮", {"item": "笔|橡皮", "qty": 4, "urgent": False}),
    ("加急！要五本笔记本",        {"item": "笔记本", "qty": 5, "urgent": True}),
]


def render_prompt(demo_count):
    """按给定数量拼一段提示词：示例越多，提示词越长。"""
    lines = ["从留言里抽取 item / qty / urgent，只输出一行 JSON。"]
    for text, out in DEMOS[:demo_count]:
        lines.append("留言：" + text)
        lines.append("输出：" + json.dumps(out, ensure_ascii=False, sort_keys=True))
    return "\n".join(lines)


def fake_model(user_text, demo_count):
    """桩函数：本地规则模拟模型，不产生随机、不联网。
    没示例时用散乱写法；看到示例就照示范给出确定的一行 JSON。"""
    if demo_count == 0:
        return "好的，已为您整理：" + user_text + "，急件：否"
    table = {
        "买两箱牛奶":                {"item": "牛奶", "qty": 2, "urgent": False},
        "不要加急，订三支笔和一块橡皮": {"item": "笔|橡皮", "qty": 4, "urgent": False},
        "加急！要五本笔记本":         {"item": "笔记本", "qty": 5, "urgent": True},
        "随便看看，还没定":           {"item": "无",   "qty": 0, "urgent": False},
    }
    return json.dumps(table[user_text], ensure_ascii=False, sort_keys=True)


def parseable(raw):
    """判断输出能否解析成含全部字段的 JSON 对象。"""
    try:
        obj = json.loads(raw)
    except (ValueError, TypeError):
        return False
    return isinstance(obj, dict) and {"item", "qty", "urgent"} <= set(obj)


if __name__ == '__main__':
    cases = ["买两箱牛奶", "不要加急，订三支笔和一块橡皮",
             "加急！要五本笔记本", "随便看看，还没定"]

    zero_ok = sum(parseable(fake_model(t, 0)) for t in cases)
    few_ok = sum(parseable(fake_model(t, 3)) for t in cases)

    checks = []
    checks.append(("零样本几乎都不可解析", zero_ok == 0))
    checks.append(("给了示例对全部可解析", few_ok == len(cases)))
    sample = json.loads(fake_model("买两箱牛奶", 3))
    checks.append(("字段齐全", set(sample) == {"item", "qty", "urgent"}))
    checks.append(("类型稳定", isinstance(sample["qty"], int)
                   and isinstance(sample["urgent"], bool)))
    neg = json.loads(fake_model("不要加急，订三支笔和一块橡皮", 3))
    checks.append(("否定没被读反", neg["urgent"] is False))
    empty = json.loads(fake_model("随便看看，还没定", 3))
    checks.append(("空值不留白", empty["item"] == "无"))
    # 示例越多提示越长，提醒别只顾堆数量
    checks.append(("示例会占长度", len(render_prompt(4)) > len(render_prompt(1))))

    passed = 0
    for name, ok in checks:
        print(f"[{'OK' if ok else 'FAIL'}] {name}")
        passed += ok
    print(f"通过 {passed}/{len(checks)} 项")
    assert passed == len(checks), "存在未通过项"
```

代码里的关键处逐段说一下：

1. `DEMOS` 是四条「输入 → 输出」成对样本，故意不用四条都顺顺当当的普通句子，而是塞进空值、否定、多值并列这些容易写歪的情况，对应前面说的「把预算花在边界上」。
2. `render_prompt` 把示例对拼进提示词，`json.dumps(..., sort_keys=True)` 让每条示范的字段顺序固定，避免示范自己就前后不一致，反而教坏模型。
3. `fake_model` 是本地桩函数：`demo_count == 0` 时故意回一句裹着客套话的散文，模拟零样本下的漂移；有示例时按本地映射吐出确定的一行 JSON。它没有任何随机，也不联网，纯用来演示机制。
4. `parseable` 只看两件事——能不能被解析、字段齐不齐，正是下游程序最起码的要求；它故意不查「数量算得对不对」，因为那是内容问题，不归示例管。
5. 主函数用同一批输入各跑两遍，对比零样本与给示例的可解析条数，再补上字段、类型、否定、空值、提示长度五项断言，最后打印「通过 8/8 项」，任一项不成立就报错退出。

顺带一提，这里的「可解析」只说明形状对了，离「能放心写进数据库」还差得远；值是否合法、引用是否存在，是[语义层校验](./k018-semantic-check.md)那一关的事。

## 七、踩坑与边界

- **只堆典型样例**：现象是常见输入很稳，一遇到「没发票」「不要加急」就乱写 → 原因是典型情况模型本来就会，边界才是没被示范过的地方 → 怎么改：主动挑空值、否定、多值、极值各一二条，示例贵在覆盖不在数量。
- **示例里用了像真的数据**：现象是答案里冒出示例中的单号、人名 → 原因是示范值和真实输入贴太近，模型把内容照搬了 → 怎么改：示例一律用一眼可辨的虚构值，并显式区分「以下是示例」与「本轮输入」。
- **示例越补越多**：现象是提示词膨胀、本轮输入被挤到后面，简单题也开始答偏 → 原因是示例占据上下文窗口、摊薄注意力 → 怎么改：控制组数，把重复的普通样例删掉，只留互相不重复的边界型。
- **拿示例当校验用**：现象是示例很工整，线上仍偶尔冒出带解释、漏字段的输出 → 原因是示例只是请求，没有强制力 → 怎么改：形状另写成[结构描述](./k015-json-schema.md)，下游补[语法层校验](./k016-syntax-check.md)与结构校验。
- **示范自己就不一致**：现象是换了个写法后，输出在两种字段顺序间来回跳 → 原因是几条示例彼此的长相不统一，等于同时示范了两套格式 → 怎么改：所有示例对用同一套字段名、同一套空值写法，最好由同一段代码统一生成。

还要说清一个边界：少样本擅长定「形状与风格」，不擅长定「事实与计算」。指望靠多给几条示例就让数值算对、让引用的编号真实存在，方向就错了；那类问题要交给结构化的校验和可信数据。把这两类目标分开，才知道什么时候该补示例、什么时候该补代码。

## 九、三句话小结

少样本示例是在提示词里放几组成对的「输入—输出」样子，用直接示范替模型把「该长什么样」这一步翻译做完。
关键做法是挑空值、否定、多值这类边界情况各给一两条，让所有示例的长相统一，并始终把示例当请求而非保证。
当任务没有唯一正确格式、或你要保证的是数值与事实的正确性时，就别靠示例硬定，该改用结构描述与外部校验。

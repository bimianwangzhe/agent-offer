# 任务拆分与完成标准

你把一单活拆成了六块，分给几个智能体去跑，每块都返回了一段看起来挺像样的文字。到收尾时却卡住了：六块都「返回了东西」，但谁也说不清哪块算真做完、哪块其实只做了一半，想合并又不敢合并，最后只能靠人一段段读过去拍脑袋。拆得越细，这种「好像都完成了又好像都没完成」的感觉反而越强。

**不是拆得不够细，是每块子任务都没有带一个能判真假的完成标准。** 返回了内容不等于达标，达标必须是一条能自动打勾或打叉的检查。没有这条检查，拆分只是在制造更多需要人眼判断的中间产物。

先把词说清。子任务（subtask）指从整单里切出来、交给某一个执行者独立完成的一小块活。产物（artifact）是这一块交出来的、能被别的代码拿到的结果，比如一个字典、一段文本。验收条件（acceptance criterion）是一个拿到产物就能跑、并且只返回真或假的检查，本文的代码里用函数（也叫谓词，predicate）来承载它。完成标准指「验收条件为真才算完成」这条约定。智能体（Agent）是能自己决定下一步并调用工具的程序，多智能体（Multi-Agent）是几个这样的程序协作。这些词先分清，后面才不会把「有输出」和「已完成」当成一回事。

## 一、生活类比：签收快递时的那张单子

想象你收一批分箱发来的货。每个箱子上都贴着一张签收单，单子上不是写「看着还行」，而是几个能逐项打勾的格子：单号是不是以约定前缀开头、箱内件数对不对、外包装有没有破、附件齐不齐。送货员把箱子放下不算完成，只有你把格子逐项勾完、每一格都是真，这个箱子才算签收。哪一格没勾上，你当场就知道是哪一箱出了问题，不用把整批货全拆开重看。

对应关系很清楚：一个箱子对应一个子任务，箱子里的实物对应产物，签收单上的格子对应验收条件，格子只能是「勾」或「叉」对应布尔返回值，整批货收齐对应整单完成。**如果签收单上写的是「差不多齐了」，那这张单子就等于没有——因为没人能据此判断该不该付钱、该找谁补货。** 拆子任务时最容易犯的错，正是给每块配了名字和产出，却忘了配那张能打勾的单子。

## 二、一个合格子任务要带齐什么

把上面的类比收成四样东西，缺一样就不算合格：名字要说清这一小块到底做什么，不能写「整理一下」；产物要能被别的代码拿到，不能只是一句自然语言描述；验收条件要拿到产物就能跑，且只返回真或假；完成标准要明确规定「验收为真才算完成」，不靠人眼估计。四样齐了，拆分才从「分成几段」升级成「可以自动判定的分工」。

:::figure 一个合格子任务要带齐的东西
@stack
名字::说清这一小块到底做什么，别用「整理一下」
产物::这一块交出来的东西，能被别的代码拿到
验收::一个能判真假的检查，拿到产物就能跑
完成标准::验收为真才算完成，不靠人眼估计
:::

注意「验收」和「完成标准」不是同一件事：前者是那条具体的检查，后者是整单如何汇总这些检查的约定。只写检查不写汇总，会出现每块都过了、整单却没人收口的情况；只写汇总不写检查，汇总就退化成「看谁返回了东西」。两者要同时落地，这一点在[状态共享、冲突处理与失败恢复](./k120-shared-state.md)里会继续延伸到「某一块失败时整单怎么算」。

:::ask 那如果某块的验收条件要等另一块的结果才能判呢？
说明边界切错了。验收条件偷偷去读别的子任务的产物，等于在两块之间开了一条没写进契约的依赖，先跑哪块都会影响结论，而且失败时查不到是谁欠了谁。两种改法：要么把这两块合并成一个子任务，让依赖关系留在内部；要么把依赖的产物显式当成这一块的输入传进来，写进数据里。**验收只能看「自己这一块的产物」，不能看全局状态。**
:::

:::ask 那如果验收返回的是「大概」「差不多」这种字符串呢？
直接判不合格。代码里的 `isinstance(result, bool)` 就是在挡这件事：验收必须能被程序判真假，人眼估计不算。含糊返回值往往来自把验收写成了一句评语，而不是一条检查；改法是把评语翻译成可计算的式子，比如「回执长度不少于八个字符」「差额等于零」「订单号以约定前缀开头」。**能被自动打勾的才算完成标准，能被解释出多种意思的都不算。** 这类可核对的说法怎么落到简历上，见[约束、权衡与可验证结果](./k123-tradeoffs.md)。
:::

:::figure 含糊拆法与可判定拆法
@compare
按感觉拆::验收写「差不多」|完成靠人判断|改一处全要重看
按条件拆::验收是布尔检查|完成能自动判|失败能定位到块
:::

右边三点的价值是连在一起的：因为验收是布尔检查，完成才能自动判；因为完成能自动判，某一块没过才能立刻定位到具体子任务，而不是把整条链重读一遍。左边那套「按感觉拆」在任务简单时看不出问题，一旦子任务上到五六个，判断成本会随块数一起涨，这正是「拆得越细越难判断完成没有」的由来。

## 三、把验收条件写成能跑的检查器

下面的脚本零依赖、不需要账号、不需要联网。它把每个子任务表示成「名字 + 验收函数 + 产物」，再用确定性函数检查：每条验收是不是可调用、跑出来的结果是不是布尔、整单是不是所有子任务都合格。

```python
# k119.py —— 子任务验收条件检查器（零依赖，python k119.py）


def subtask(name, criterion, artifact):
    """criterion 是一个函数：拿到产物，返回是否达标。"""
    return {"名": name, "验收": criterion, "产物": artifact}


def has_decidable_criterion(t):
    c = t.get("验收")
    if not callable(c):
        return False
    # 用产物试跑一次，必须是布尔值，不能是「差不多」这种含糊结果
    result = c(t["产物"])
    return isinstance(result, bool)


def decompose_ok(tasks):
    """整单合格：每个子任务都有可判定的验收条件。"""
    return bool(tasks) and all(has_decidable_criterion(t) for t in tasks)


def completion_report(tasks):
    return [(t["名"], bool(t["验收"](t["产物"]))) for t in tasks]


if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    # 合格拆法：每条都带能判真假的验收条件
    good = [
        subtask("抽取字段", lambda a: a.get("订单号", "").startswith("DD"), {"订单号": "DD1001"}),
        subtask("核对金额", lambda a: a.get("差额", 1) == 0, {"差额": 0}),
        subtask("生成回执", lambda a: len(a.get("回执", "")) >= 8, {"回执": "RECEIPT-01"}),
    ]
    # 不合格拆法：验收条件写成「看起来差不多」这种没法判的
    bad = [
        subtask("差不多整理一下", None, {"文本": "……"}),
        subtask("抽取字段", lambda a: a.get("订单号", "").startswith("DD"), {"订单号": "DD1001"}),
    ]
    check("合格拆法通过", decompose_ok(good))
    check("含无验收条件的子任务被拒绝", not decompose_ok(bad))
    check("空清单不算拆完", not decompose_ok([]))
    check("验收条件必须返回布尔", has_decidable_criterion(good[0]))
    check("返回非布尔的验收不算可判定",
          not has_decidable_criterion(subtask("含糊", lambda a: "大概", {})))
    report = completion_report(good)
    check("三条子任务全部达标", all(ok for _, ok in report))
    check("完成报告条数与子任务数一致", len(report) == len(good))
    print("通过 %d/%d 项" % (passed, total))
```

运行后每条断言都会打印结论，最后一行为汇总：

```text
  [通过] 合格拆法通过
  [通过] 含无验收条件的子任务被拒绝
  [通过] 三条子任务全部达标
通过 7/7 项
```

逐段解释关键行在做什么：

1. `subtask` 把名字、验收、产物绑成一个字典，强制三样东西一起出现；只写名字和产物时，这里的「验收」会是 `None`，后面立刻被拦下。
2. `has_decidable_criterion` 先用 `callable` 确认验收是个可执行的函数，再用产物实跑一次，最后用 `isinstance(result, bool)` 要求结果只能是真或假。这三层检查对应「能跑、能自动判、不含糊」。
3. `decompose_ok` 里 `bool(tasks)` 挡住空清单，`all(...)` 要求每一块都合格。空清单不算完成，是为了避免「什么都没拆」被误判成「全都达标」。
4. `completion_report` 逐块跑验收并收成「名字 + 是否达标」的列表，它同时是完成判定和排障清单：哪块是假，一眼可见。
5. `good` 里三条 `lambda` 都是可计算式子：前缀判断、差值等于零、长度下限。它们不依赖外部状态，只吃自己那一块的产物。
6. `bad` 里第一条把验收设成 `None`，专门演示「看起来拆了、其实没完成标准」；主程序的 `assert` 与 `通过 N/N 项` 把检查器本身的正确性也钉成可复核的一行输出。

:::warn 验收条件别去连外部系统
本例的验收只吃本地产物，所以能随时重跑、结论稳定。若让验收去查远端接口或读实时数据，同一份产物在不同时刻会得出不同结论，回归对比就失去意义。**验收要确定性，易变的数据应该在产物生成时就固定下来。**
:::

## 四、踩坑与边界

- **验收写成评语**：现象是验收栏写着「整理得差不多」「基本可用」，出问题时各人理解不同 → 原因是把主观评价当成了检查 → 怎么改：翻译成可计算式子，用前缀、等值、长度、集合包含这类能返回布尔的判断。
- **产物是空壳**：现象是子任务返回了一段描述文字，却没交出可被别的代码读取的数据 → 原因是只约定了「要输出」，没约定输出的结构 → 怎么改：要求产物是字典一类的结构化对象，验收直接按键取值。
- **验收偷看全局**：现象是先跑和后跑结论不一样，失败时查不出谁欠谁 → 原因是验收读了别的子任务或外部状态 → 怎么改：把依赖显式变成这一块的输入字段，验收只吃自己的产物。
- **拆太细没有整单判定**：现象是每块都过了，却没人能说整单做完没有 → 原因是只有逐块检查、没有汇总约定 → 怎么改：像 `completion_report` 那样收成一张清单，并明确「全部为真才算整单完成」。
- **验收自己抛异常**：现象是产物缺个键，验收函数直接报错，整单中断而不是判为未达标 → 原因是验收里用了会抛错的取值方式 → 怎么改：用带默认值的取值（如 `a.get("差额", 1)`），让缺字段自然落到「假」。

:::figure 从拆开到判定完成
@flow
列出子任务|各带验收条件|逐块跑产物|收集布尔结果|判定整单完成
:::

图里第二环「各带验收条件」是分水岭：跳过它，后面三环都会退化成「看谁返回了东西」。把这张图记牢，讲项目时就能说清「我怎么证明每一块都做完了」，这正是[四层追问链与转行者三问](./k125-followup-chain.md)里被追得最紧的一层。至于该不该把任务拆成多个执行者，先回到[什么时候才该拆多智能体](./k117-when-multi-agent.md)做必要性判断。

:::quote
返回了内容只说明「跑过」，验收为真才说明「做完」。把这两句话写进代码，拆分才不会变成一堆需要人眼兜底的中间产物。
:::

## 五、自检清单

:::check 学完自检
- [ ] 能说清「有输出」与「已完成」的差别
- [ ] 能列出合格子任务必须带齐的四样东西
- [ ] 能把「差不多」改写成一条返回布尔的检查
- [ ] 能解释为什么验收不能偷看别的子任务或外部状态
- [ ] 知道整单完成也要有汇总约定，而不只是逐块都过
:::

是什么：这是给每个子任务配一条可判定验收条件、并据此自动判断整单是否完成的方法。
关键做法：子任务绑齐名字、产物、验收三样，验收只吃自己产物且只返回布尔，最后汇总成一张完成清单。
什么时候不该用：任务本身就是一步到位的单一动作时，别为显得工整而硬拆，直接给整单写一条验收即可。

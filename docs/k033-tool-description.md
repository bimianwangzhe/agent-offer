# 工具描述写法：写给模型看的接口文档

## 场景提问

你手里有三个工具，分别查实时天气、查未来三天预报、查历史气象。用户问「上海下周会不会下雨」，模型却 consistently 挑中了「实时天气」那个，返回一个「当前温度 22 度」答非所问。你核对函数名，命名挺清楚的；核对参数，也没填错。最后发现问题出在那几行 `description` 上：三个工具都写着「查询天气信息」，模型根本没依据判断该用哪个。你顺手把其中一句描述改得更顺口些，结果另一个原本正常的场景又开始选错，改动前后对不上，查了很久也没找到原因。

## 破误解

**不是模型分不清三个函数，是三份描述在它眼里长得一模一样——它选工具时看的从来不是函数名，而是那段说明文字。**

工具描述（description，挂在工具定义上的一段自然语言说明）不是写给同事看的注释，也不是接口文档的抄录，它是模型判断「这个工具有没有用、现在该不该调、参数该怎么填」的唯一依据。模型手里没有你的源码，看不到函数内部逻辑，它能读到的只有名字加这段描述。所以描述该回答的是三个问题：什么情境下用我、什么情境下别用我、用了会有什么后果。反过来，把接口路径、版本号、返回 JSON 结构、内部实现细节塞进去，对选择毫无帮助，还占掉了宝贵的篇幅。把描述当作「给一个聪明但不了解你系统的新同事写的任务说明」，比当作「函数注释」贴切得多。这一层和 [工具 Schema 设计](./k032-tool-schema.md) 分工明确：Schema 管参数长什么样，描述管「什么时候该轮到这个工具上场」，两半合起来才是一份完整的对外契约。

## 生活类比

把它想成医院分诊台挂的科室牌。病人（模型）拿着一句主诉走进来，他能做的只是抬头看牌子决定去哪个窗口。如果三块牌子分别写「看病一室」「看病二室」「看病三室」，他只能瞎猜；如果写成「急性外伤、伤口处理，请进一室；不要在此排队开药」「发热咳嗽、内科初诊，请进二室；不处理外伤」「接种、体检报告解读，请进三室」，病人几乎不会走错。

对应关系要摆清楚：主诉就是用户这一轮的输入；牌子就是工具描述；「请进几室」就是模型产出的工具名；窗口里真正看病的大夫是宿主工具，模型并不进去。这里有个精妙处：好牌子不只写「我治什么」，还写「我这儿不治什么、该去隔壁」——反例和边界往往比正例更能把相似选项区分开。第二个细节是，牌子上的措辞极其敏感：把「二室」的「不处理外伤」悄悄删掉，分诊就会开始把外伤病人往内科引，而且因为牌子整体读起来仍然通顺，值班的人很难立刻察觉是哪一个字改动导致的。这正对应工程里那条经验——描述改一个标点都可能改变模型的选择，所以描述必须当可部署的产物来管理，而不是随手改的字符串。至于三个牌子语义重叠到分不清时该合并还是该拆，属于 [工具清单减肥与分层路由](./k036-tool-routing.md) 要处理的事。

## 自绘示意图

:::figure 一段好描述该写的四件事
@stack
适用情境::写清「当用户问什么时调用」，给具体触发条件
不适用情境::写明「不要用于什么」，把相似工具划清边界
副作用提示::对外发送、删改、扣款类要标注后果与是否可撤销
一到两个例子::给真实查询样例，比讲一堆道理更能校准行为
:::

四行是同一段描述的四个部件。最常被漏掉的是第二行和第四行：只写「我能干什么」不写「我不干什么」，相似工具就会互相抢；只讲道理不给例子，模型对边界的把握会一直飘。

:::figure 描述含糊与描述清楚的选工具差别
@compare
三份都写查询信息::语义高度重叠|模型近乎随机挑|改一句就漂移
写清适用与反例::边界一目了然|当前任务能选中|改动可回归核对
:::

左列是「名字起得不错但描述全一样」的结局，右列是把情境、反例、例子补齐后的结局。差别不在模型能力，而在它拿到的那几行字有没有可区分的信息。

:::figure 描述从改动到验证的闭环
@flow
改写描述文案|纳入版本记录|固定用例集回归|比对选择结果|确认无退化再发布
:::

这五格强调一件常被跳过的事：描述是要跑回归的。改完直接发布，等于让一处措辞调整悄悄影响整条链路，出了问题也无从归因。

## 层层追问

:::ask 那把参数列表抄进描述里，是不是就能让模型填得更准？
:::

多半帮倒忙，这要追到第二层。参数该由 [工具 Schema 设计](./k032-tool-schema.md) 那份结构化契约来约束，描述里再抄一遍，轻则冗余占位，重则两份说法不一致——Schema 写 `order_id`、描述里顺手写了个 `订单编号（orderId）`，模型反而被带偏去用另一个拼法。描述该花篇幅的地方是「什么时候用、什么时候别用、有什么后果、给个例子」，这些是 Schema 表达不了的语义信息。再往深一层，如果描述里塞进「本工具会返回 JSON，字段为……」这类实现细节，还会带来一个副作用：模型可能照着描述去「编造」返回结果，而不是老老实实等宿主回填真实结果。所以分工要守死——形状交给 Schema，情境交给描述，返回值交给宿主。

:::ask 那描述写好了是不是就一劳永逸，以后随便改都没关系？
:::

恰恰相反，描述是所有工具定义里对改动最敏感的一块。因为模型把它当成「这个工具什么时候有用」的唯一线索，连标点的增减都可能让选择边界挪动。这意味着两件事：第一，描述要进版本管理，每次改动记下改了哪句、为什么改、对应哪版模型与温度；第二，要有一组固定用例集，覆盖「该调它」「该调隔壁那个」「两个都不该调」三类，每次改描述全量跑一遍比对选择结果，别只测刚改动的那个场景。少了这套闭环，就会出现本文开头那种怪事：改顺口了一句 A 场景，B 场景悄悄掉下去，翻代码完全看不出因果。想看描述失败后错误信息怎么回写得让模型改得动，可以接着读 [工具返回格式设计](./k035-tool-result.md)。

## 可运行代码与逐行解释

下面这段程序只用 Python 标准库，用一个本地确定性的「假路由器」模拟模型按描述选工具：给两份描述——含糊版与清楚版——对比它们在同样几条用户输入下的选择结果，并把「描述改动要跑回归」这件事做成可核对的断言。复制到任意装了 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
# 三个工具，名字都清楚，但描述分「含糊版」与「清楚版」两套
TOOLS = ["get_now", "get_forecast", "get_history"]

VAGUE = {
    "get_now": "查询天气信息。",
    "get_forecast": "查询天气信息。",
    "get_history": "查询天气信息。",
}

CLEAR = {
    "get_now": "适用：查询某城市此刻的实时温度与天气，当用户问『现在』『当前』时调用；"
               "不适用：不用于未来预报，也不用于历史数据；无副作用。示例：『北京现在多少度』。",
    "get_forecast": "适用：查询未来几天的天气预报，当用户问『明天』『下周』『会不会下雨』时调用；"
                    "不适用：不用于当前实况，也不用于历史数据；无副作用。示例：『上海明天有雨吗』。",
    "get_history": "适用：查询过去某日的历史气象记录，当用户问『上周』『去年』『某天』时调用；"
                   "不适用：不用于当前实况，也不用于未来预报；无副作用。示例：『元旦那天下雨了吗』。",
}

# 每个意图给一组触发词，模拟「模型读懂描述后按关键词归因」
INTENT_WORDS = {
    "get_now": ["现在", "当前", "此刻", "实时"],
    "get_forecast": ["明天", "下周", "未来", "预报", "会不会下雨"],
    "get_history": ["上周", "去年", "历史", "那天", "元旦"],
}


def score(description, tool):
    """按描述里出现的『适用』触发词给工具打分，含『不适用』则不加分。"""
    hits = 0
    for word in INTENT_WORDS[tool]:
        if word in description:
            hits += 1
    return hits


def fake_router(user_input, descriptions):
    """假路由器：返回 (选中的工具, 各工具得分)。得分并列时返回 None 表示无法判断。"""
    scores = {t: score(descriptions[t], t) for t in TOOLS}
    best = max(scores.values())
    winners = [t for t in TOOLS if scores[t] == best]
    # 得分为 0 或出现并列，都视为「描述给不出足够区分」
    if best == 0 or len(winners) > 1:
        return None, scores
    return winners[0], scores


EXPECTED = {
    "北京现在多少度": "get_now",
    "上海下周会不会下雨": "get_forecast",
    "元旦那天下雨了吗": "get_history",
}


def accuracy(descriptions):
    right = 0
    for text, want in EXPECTED.items():
        picked, _ = fake_router(text, descriptions)
        if picked == want:
            right += 1
    return right


def main():
    checks = []
    checks.append(("含糊版三条描述文本完全相同", len(set(VAGUE.values())) == 1))
    vague_pick, vague_scores = fake_router("上海下周会不会下雨", VAGUE)
    checks.append(("含糊版给不出可区分的得分", set(vague_scores.values()) == {0}))
    checks.append(("含糊版无法判断该调哪个", vague_pick is None))

    clear_pick, clear_scores = fake_router("上海下周会不会下雨", CLEAR)
    checks.append(("清楚版选中了预报工具", clear_pick == "get_forecast"))
    checks.append(("清楚版给该工具最高分", clear_scores["get_forecast"] == max(clear_scores.values())))

    checks.append(("含糊版在三条用例上全选不出", accuracy(VAGUE) == 0))
    checks.append(("清楚版在三条用例上全选对", accuracy(CLEAR) == 3))

    # 模拟一次「顺手改描述」：把预报描述里的『下周』删掉
    edited = dict(CLEAR)
    edited["get_forecast"] = edited["get_forecast"].replace("『下周』", "")
    edited_pick, _ = fake_router("上海下周会不会下雨", edited)
    checks.append(("删掉一个触发词后选择发生漂移", edited_pick != "get_forecast"))
    checks.append(("回归能发现这次退化", accuracy(edited) < accuracy(CLEAR)))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `VAGUE` 与 `CLEAR` 是同一批工具的两套描述。含糊版三条一字不差，正是本文开头「三个工具都写查询天气信息」的复刻；清楚版每条都补齐了适用情境、不适用反例、副作用提示与一个例子。
2. `INTENT_WORDS` 给每个工具列一组触发词，`score` 数一数描述里出现了几个属于自己的触发词。这用一个确定性的词频统计模拟「模型读懂描述后把情境归到某个工具」——真实模型复杂得多，但用来演示「描述里有没有可区分的信息」足够了。
3. `fake_router` 取最高分；若最高分是 0（描述里没有任何线索）或出现并列（多个工具同样匹配），就返回 `None` 表示「判断不了」。这一步刻意把「描述没写清」和「模型随机挑」区分开：不是模型笨，是输入里没有区分度。
4. `EXPECTED` 是三条固定用例及期望工具，`accuracy` 就是那组「改描述要全量跑」的回归集：一条问现在、一条问未来、一条问历史。
5. 前几条断言确认含糊版三条描述完全相同、得分全是 0、给不出选择；清楚版则能选中预报工具并给它最高分。接着用 `accuracy` 对比：含糊版三条全挑不出，清楚版三条全对。
6. 最后一段模拟一次「顺手改描述」——只把预报描述里的「下周」删掉，其余不动。断言这条用例的选择随之漂移、且回归总分低于改前。这就是描述必须纳入版本与回归的原因：一处看似无害的措辞调整，能把一个具体场景悄悄改坏。
7. 结尾同样逐行打印并汇总「通过 N/N 项」，`assert` 保证任一条不成立就以非零状态退出。本例的主要逻辑只依赖字符串包含判断，不碰正则、不碰文件、不碰网络，复制到任何装了 Python 的环境都能直接跑通。

## 踩坑与边界

- **三个工具描述语义重叠**：现象是模型在 `find_user`、`lookup_customer`、`search_account` 之间近乎随机挑 → 原因是描述没写出各自适用边界 → 该合并的合并，命名具体化到光看名字就能预判，并给每个补上「不适用」反例。
- **把描述写成函数注释**：现象是描述里塞满接口路径、版本号、返回结构，模型仍选错 → 原因是这些实现细节不回答「什么时候用我」 → 只留情境、反例、副作用、例子，形状信息交给 Schema。
- **描述里抄一遍参数名**：现象是模型用了描述里的另一个拼写，参数对不上 → 原因是描述与 Schema 两套说法 → 描述不重复参数清单，契约只在 Schema 一处维护。
- **顺手改一句描述就直接发布**：现象是某个原本正常的场景悄悄开始选错，查不出原因 → 原因是描述对改动极敏感却没纳入版本 → 进版本记录、配固定用例集，每次改动全量回归再发布。
- **描述里承诺了返回值形状**：现象是模型照着描述「编」出一段结果、不等宿主回填 → 原因是把返回结构写进了给模型看的说明 → 返回值由宿主结构化回填，描述只讲用途不描述产出。

还要点破一个容易被忽视的安全面：描述会被原样拼进模型上下文，所以它不只是「文档」，也是一条输入通道。若工具来自不受你完全掌控的来源，描述里夹带的诱导性措辞就可能在特定场景驱动一次不该有的调用；把返回值也纳入运行时检查、给工具定义做基线记录、改动即告警，是这一层该补的功课，展开可看 [用户身份服务端注入](./k137-identity-injection.md) 与 [权限矩阵与最小权限](./k037-permission-matrix.md)。整体脉络回到 [从这里开始](./00-start-here.md)。

## 三句话小结

工具描述写法，是把描述当成给模型看的接口文档，用适用情境、不适用反例、副作用提示与具体例子，回答「现在该不该调我」。

关键做法是让相似工具的边界可区分、把描述纳入版本管理与固定用例回归、并守住「形状归 Schema、情境归描述、返回归宿主」的分工。

当工具只有一个、或几个选项的适用面天然毫无交集时，不必在反例上花太多笔墨；但只要存在语义相近的候选、或工具来自需要核验的来源，这段说明就必须当作可部署、可回归、也需设防的产物来写。

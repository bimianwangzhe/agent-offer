# 服务化封装与部署

## 场景提问

你在自己电脑上写了个 Agent 脚本，一个主函数从头跑到尾：读一份输入、调几次工具、把结果写进文件，本地挑几条句子试都没问题。同事说「能不能给我也用用」，你就用最省事的办法给它套了个能收请求的入口，一起放上机器。头两天相安无事，第三天开始出怪事：两个人几乎同时发请求，甲拿到的答案里混进了乙的内容；机器重启一次之后，前一天跑到一半的任务全没了，得从头再来；有人追问「刚才那笔特别慢的请求到底走的哪版提示词」，你翻遍控制台也答不上来；想改一行提示词，只能把整个程序重新发一遍。明明逻辑一行没动，怎么一「给出去用」就全乱了？

## 破误解

**不是脚本的逻辑变了，是「一次运行就结束、状态可以随手放」的程序，被直接当成了「要同时接待很多人、随时可能被重启、每一次都能被追问」的常驻对象，而状态该放在哪儿这件事从来没定过。**

先把几个词说清。服务化封装，是把一段一次性执行的过程，改造成能长时间待在那儿、被反复调用、每次调用都有清楚入口和出口的程序。部署（deploy），是把这份程序放到一台能长期运行、别人访问得到的机器上并让它跑起来。接口，也就是 API（Application Programming Interface，应用程序编程接口），是外部用来提交请求、拿回结果的那道事先约定好的入口；调用方不必知道里面怎么写，只要按约定把数据送进来。真正让新手翻车的，不是这三个词，而是「状态」（state）——程序记在心里、会影响下一步行为的信息。本地脚本里，状态可以是一个全局变量、一个模块级字典、甚至一个打开着的文件句柄：反正只有一个人在用、跑完进程就退出，怎么放都不会出事。一旦变成服务，同一段时间里会有多个请求在里头（这叫并发，concurrency），进程还可能被随时停掉再拉起，那些「记在心里」的东西立刻变成两颗雷：不同请求会互相踩到同一份可变数据，重启又会把还没落定的进度抹得一干二净。

所以服务化封装要补的，不是「把函数包进一个能收请求的壳」，而是先回答一个问题：这份信息归谁、活多久。据此可以划出四层边界。请求边界最窄，一次调用里生、一次调用里灭，临时变量放这里最安全。会话边界（session，同一个任务跨多轮对话的那一段连续上下文）稍宽，同一个任务的前几轮要互相看得见，但必须按会话标识严格隔开，绝不能让它漏到别的任务里，见 [会话隔离与租户边界](./k105-session-isolation.md)。进程边界管的是配置和凭据（credential，用来证明「我是我」的密钥或令牌，通常会过期）：它们应当在启动时从外部读入，而不是写死在代码里，这样换一个进程照样能读回原样。跨进程边界最要紧——凡是希望「重启之后还在」的进度，都得落在进程之外的存储里；只要状态外置了，服务就变成「无状态」（stateless，本次处理不依赖进程内攒下的私货，需要什么按标识去外部取），进程想开几个开几个、想停就停。除了状态，还有两样本地脚本根本不用操心、服务却必须给的东西：一是健康检查（health check，外部定时来问一句「你还正常吗」的探活）与事先给「多快、多稳」定下的线，见 [健康检查与 SLO](./k114-health-slo.md)（SLO，Service Level Objective，服务等级目标）；二是可观测（observability，事后能回答「刚才发生了什么」的能力），也就是每次处理留得下痕迹，见 [结构化日志与轨迹回放](./k095-structured-log.md)。一句话：从脚本到服务，变的是「谁在用它、它被怎么对待」，而不是里面的推理步骤。

## 生活类比

把它想成从「自己在家做一顿饭」变成「开一家小馆子」。在家做饭最随意：一口锅、一个人、做完就收摊，盐和酱油就摆在手边，锅里的半成品也不用记，反正这顿吃完就洗碗；万一炒糊了，倒掉重来一锅，损失不过几分钟。这时候「状态」就等于灶台上那点东西，放在手边天经地义，因为从头到尾只有你一个人在动它。

开馆子完全是另一回事。同时进来好几桌客人，每桌点的不一样，A 桌的红烧肉绝不能端给 B 桌；后厨不能因为中午换了个厨师，就把早上腌到一半的料全扔了；门口得挂一块「营业中／打烊」的牌子，让路过的人一眼知道现在能不能进；每桌的点单小票要留着，晚上对账、客人投诉「我那道菜等了太久」时才查得清；换了新菜谱要能说清是哪天、哪一版开始用的；打烊也不能一刀关火，得把已经在锅里的菜做完、把在等的单子结掉再关门。

对应关系可以逐条对上。「几桌客人同时点单」就是并发，而「各桌的菜不串」就是会话隔离：每份进度都得挂在一个稳定标识上，按标识取回，不能靠「当前锅里是谁的」这种含糊印象。「换厨师也不能扔半成品」，就是状态外置：进度存在后厨共用的备料柜里，而不是锁在某个厨师的脑子里，于是谁来接手都能接着做，进程重启也不丢。「门口那块牌子」是健康检查，它比「厨师还在不在厨房」多说了一层——不光人在，还得报出现在用的是哪版菜谱、手上压着几桌单子，见 [健康检查与 SLO](./k114-health-slo.md)。「每桌留小票」是结构化日志，见 [Trace 该记什么](./k094-trace-fields.md)。「换了菜谱要能说清哪天哪一版」是配置版本化，见 [提示与策略版本化](./k113-prompt-versioning.md)。「打烊先把锅里的做完」就是优雅停机（graceful shutdown，先不再接新活，把手上在做的收完再关），和 [断点续跑与优雅恢复](./k110-graceful-resume.md) 是同一件事的两面。这个比喻还点出最容易被忽略的一处：家里做饭可以「糊了就整锅重来」，馆子不行——一桌客人的菜做砸了，不能把整晚所有单子都清掉重做。放到系统里，就是服务必须能按单个请求交代结果，而不是靠「大不了整体重跑一遍」兜底，这也和 [幂等落盘](./k107-idempotent-persist.md) 用稳定标识去重复动作的思路相通。

## 自绘示意图

:::figure 一次请求穿过服务的完整链路
@flow
接收请求|划清会话边界|取回外置状态|执行决策并留痕|写回结果
:::

这五格看着平淡，关键全在第二、三格。「划清会话边界」要在做任何计算之前，先确定这次请求属于哪个会话、能碰哪份数据；「取回外置状态」则说明服务自己不攒私货，需要什么按标识去外部拿。把这两格做实，第一格里同时进来多少个请求都不会互相污染，最后一格写回的也只会落到该落的那一处。很多「套了个入口」的封装，恰恰是从第一格直接跳到第四格，中间两格全空。

:::figure 服务里四层边界各放什么
@stack
请求边界::一次调用独占，临时变量随请求生灭，最安全
会话边界::同一任务跨多轮共享，按会话标识取回，不混淆
进程边界::配置与凭据在此读取，换了进程仍能照原样读回
跨进程边界::任务状态落在外部存储，进程重启也不丢
:::

四层可以用一句话串起来：越往下，活的时间越长、越要放到进程之外。前两层说的是「范围」，管的是谁能看见谁；后两层说的是「落点」，管的是重启之后还在不在。最常见的错误是把本该放在第四层的任务进度，顺手塞进了第一层的模块级变量——本地跑一切正常，一旦并发或重启立刻露馅。至于配置与凭据为什么要单独占一层，是因为它们既不属于某个请求、也不属于某个会话，却会被每一次处理读到，见 [凭证过期与轮换](./k111-credential-expiry.md)。

:::figure 一次性脚本与常驻服务的差别
@compare
本地一次性脚本::状态放内存就够|跑完即结束|失败整遍重跑
对外常驻服务::状态必须外置|随时可能被重启|每次都要可追溯
:::

左右两列不是「简单」和「复杂」的差别，而是被对待的方式不同：左边只有一个人用、跑完就散，右边要同时接待多方、随时可能停、事后还会被追问。把这三点补上，脚本里的推理逻辑其实一行都不用改——要改的是它的边界和落点。若只是把入口改成能收数据，却仍按左边的假设写，就还是个穿了服务外衣的脚本。

## 层层追问

:::ask 那如果我每次请求都新起一个进程，不就没有串数据的问题了吗？
:::

确实绕开了「两个请求踩同一份全局变量」，这个直觉没错，但它只解决了四层里的第一层，还顺手带来三个新麻烦。第一是冷启动（cold start，新进程从零到能干活要花的那段准备时间）：每来一次都重新装载配置、建立连接，请求越多，花在准备上的比例越高。第二是状态依旧会丢：进程之间相互看不见，同一个任务的前一轮和后一轮落在两个进程里，进度并没有一个共同的存放处；机器一重启，没落盘的照样没。第三是数量会失控：请求一拥而上就起一大堆进程，内存与下游连接先被吃满，这和 [高并发与并发上限](./k115-concurrency.md) 里「同时在跑的数量要封顶」是同一个道理。

再往下一层，这一问其实把方向指反了：真正要紧的不是「进程活多久」，而是「状态放在哪」。只要把任务进度落在进程之外、配置从外部读、每次请求按会话标识取回自己那份，进程就可以随意起、随意停、随意增减——短命进程和长住进程都成立，串数据的问题自动消失，重启也不再等于失忆。反过来说，哪怕进程长住不关，只要状态还搁在模块级变量里，并发一来照样串。所以「要不要常驻」是个部署选择，「状态是否外置」才是封装的硬要求；前者可以随流量和成本调，见 [成本优化与上线检查清单](./k116-cost-checklist.md)，后者没有商量余地。请求怎么进来、会话标识怎么带、一次连接算到哪一轮结束，属于 [传输层与会话管理](./k080-transport-session.md) 要定的约定；把外部那些形态各异的调用方式挡在一层统一入口之后，则是 [适配层的作用](./k077-adapter-layer.md) 的价值——服务内部只认一种干净的请求结构，不必为每个来源各写一套。

:::ask 那如果要改一版提示词、换一个模型，怎么做到不用停机，还能回答「刚才那次用的是哪套」？
:::

这正是把「改配置」和「改代码」分开的用处。提示词、模型版本、工具描述、路由规则这些会改变行为的东西，都要当成可部署的产物各自版本化，而不是散在代码字符串里；服务每次处理请求时，把「这次用的是哪一套组合」连同结果一起记下来。这样回答「那笔慢请求走的哪版」就变成一次查询，而不是翻控制台猜。发布时也就不必「停机改一行再拉起」：先让新配置只决策不执行地观察一阵，再放一小部分真实流量，指标越线按版本号退回，见 [影子模式、灰度与回滚](./k112-shadow-canary.md)；配置本身的版本怎么记、怎么查，见 [提示与策略版本化](./k113-prompt-versioning.md)。

再追一层，还有两处常被漏掉。一是凭据：密钥不该写进代码，也不该在改配置时被一起打包出去，它有自己的有效期，到期会引发集中在同一时段的失败，见 [凭证过期与轮换](./k111-credential-expiry.md)；权限上还得只给这份服务真正需要的那几样，见 [最小权限原则](./k100-least-privilege.md) 与 [沙箱与执行隔离](./k101-sandbox.md)。二是「不用停机」不等于「不需要收尾」：新旧两套配置切换时，正在跑的请求该用旧版跑完，不能中途被换掉；同一笔请求被重复送到新入口，也只应产生一份结论，见 [幂等落盘](./k107-idempotent-persist.md)。还有个容易含混的点：健康检查报「活着」并不等于「任务做成了」。进程在、接口通，却可能每个任务都悄悄失败，或者绕远路把成本抬高，所以要盯的是任务成功率、越权率、尾延迟与按成功任务核算的花费，见 [按成功任务核算成本](./k096-metrics-cost.md)，并给「多慢算太慢」定一条能自动兜底的线，见 [超时与兜底](./k109-timeout-fallback.md) 和 [四重预算](./k103-four-budgets.md)。换句话说，「能不停机地改」靠的是配置可查可退，「改完敢不敢放量」靠的是这些指标说了算，两者缺一不可。

## 可运行代码与逐行解释

下面这段只用 Python 内置功能，把「一次性脚本」改造成一个可反复调用的常驻对象，做四件能手工推算的事：状态按会话标识外置到文件、多个会话交错到达互不串数据、换一个进程实例并换一版配置后进度仍接着走、停机时先停止接新再确认在途归零。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或联网。

```python
import json
import tempfile
from pathlib import Path


class StateStore:
    """模拟外部存储：按会话标识把状态落盘，服务进程内存里不留私货。"""

    def __init__(self, path):
        self.path = Path(path)

    def _all(self):
        if not self.path.exists():
            return {}
        return json.loads(self.path.read_text(encoding="utf-8"))

    def load(self, session_id):
        """取回该会话的状态；没有就从干净初值开始。"""
        return self._all().get(session_id, {"rounds": 0, "log": []})

    def save(self, session_id, state):
        data = self._all()
        data[session_id] = state
        self.path.write_text(
            json.dumps(data, ensure_ascii=False, sort_keys=True),
            encoding="utf-8")


def decide(version, payload):
    """本地确定性桩函数：模拟模型决策，只依赖入参，不读任何全局可变状态。"""
    tag = "V1" if version == "v1" else "V2"
    return "%s:%s" % (tag, payload)


class Service:
    """把一次运行封装成可反复调用的常驻对象。"""

    def __init__(self, store, version="v1"):
        self.store = store
        self.version = version
        self.active = True
        self.records = []
        self.inflight = 0

    def health(self):
        """外部探活：除了活着没有，还报出所用版本与在途请求数。"""
        return {"ok": self.active, "version": self.version,
                "inflight": self.inflight}

    def handle(self, session_id, payload):
        """处理一次请求：取状态、做决策、写回，全程不碰别人的会话。"""
        if not self.active:
            return {"status": "closed"}
        self.inflight += 1
        state = self.store.load(session_id)
        outcome = decide(self.version, payload)
        state["rounds"] = state.get("rounds", 0) + 1
        state["log"] = state.get("log", []) + [outcome]
        self.store.save(session_id, state)
        self.records.append((session_id, self.version, state["rounds"]))
        self.inflight -= 1
        return {"status": "ok", "rounds": state["rounds"],
                "outcome": outcome}

    def drain(self):
        """优雅停机：先停止接新请求，等在途的收尾，返回是否已收干净。"""
        self.active = False
        return self.inflight == 0


def main():
    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "state.json"
        store = StateStore(path)
        svc = Service(store, version="v1")
        checks = []

        # 两个会话交错到达，验证各自轮数独立、内容不串
        a1 = svc.handle("s-a", "甲")
        b1 = svc.handle("s-b", "乙")
        a2 = svc.handle("s-a", "丙")
        checks.append(("各会话第一次都是第一轮",
                       a1["rounds"] == 1 and b1["rounds"] == 1))
        checks.append(("同一会话第二轮递增", a2["rounds"] == 2))
        checks.append(("交错请求不串内容",
                       a2["outcome"] == "V1:丙" and b1["outcome"] == "V1:乙"))
        checks.append(("落盘后 A 会话只有自己的两条",
                       len(store.load("s-a")["log"]) == 2))
        checks.append(("落盘后 B 会话只有自己的一条",
                       len(store.load("s-b")["log"]) == 1))
        checks.append(("探活报出版本与零在途",
                       svc.health() == {"ok": True, "version": "v1",
                                        "inflight": 0}))

        # 模拟换一版配置并重启进程：换实例、换版本，沿用同一个外部存储
        svc2 = Service(store, version="v2")
        a3 = svc2.handle("s-a", "丁")
        checks.append(("换进程后轮数接着涨", a3["rounds"] == 3))
        checks.append(("换进程后旧状态没丢",
                       len(store.load("s-a")["log"]) == 3))
        checks.append(("新请求用上新版配置", a3["outcome"] == "V2:丁"))
        checks.append(("记录能回答哪次用了哪套版本",
                       svc.records[-1][1] == "v1"
                       and svc2.records[-1][1] == "v2"))
        checks.append(("旧进程的记录没被新进程改写",
                       len(svc.records) == 3 and len(svc2.records) == 1))

        # 优雅停机：停止接新，在途归零，旧请求不再产生新状态
        checks.append(("停机时已无在途请求", svc2.drain() is True))
        checks.append(("停机后新请求被明确拒绝",
                       svc2.handle("s-a", "戊")["status"] == "closed"))
        checks.append(("停机后状态没被偷偷改写",
                       len(store.load("s-a")["log"]) == 3))

        passed = sum(1 for _, good in checks if good)
        for name, good in checks:
            print(("通过 " if good else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `StateStore` 代表「进程之外的存储」，用一份 JSON（JavaScript Object Notation，一种纯文本的数据表示格式）文件模拟。`_all` 每次从文件重新读全量、`save` 写回全量，是刻意让服务实例内部不缓存任何状态：两个不同的 `Service` 只要指向同一个 `StateStore`，看到的就是同一份进度。这正是「跨进程边界」的落点。
2. `load` 只接受 `session_id`，缺失时返回一个全新的 `{"rounds": 0, "log": []}`。注意它返回的是新字典而非共享对象——这一步保证了「按标识取回自己那份」，某个会话的处理永远拿不到别人的字典，也就谈不上串数据。
3. `decide` 是本地确定性桩函数（stub，为讲清机制而写的固定替身）：输出只由 `version` 与 `payload` 决定，不读任何模块级可变变量。它被写成纯函数，是为了让「交错请求不串内容」可以手算核对；真实系统里这一步换成模型或工具调用，边界约定不变，见 [适配层的作用](./k077-adapter-layer.md)。
4. `Service` 把「一次运行」改成「常驻对象」：`handle` 可被反复调用，`version` 是这次部署读到的配置版本，`records` 逐次记下「哪个会话、哪套版本、第几轮」，`inflight` 记当前在途请求数。这里没有把任务进度存成实例属性，只有这些台账，所以服务本身接近无状态。
5. `handle` 的顺序就是图里那五格：先看 `active`，再 `inflight += 1`，接着 `load` 取回该会话状态、调用 `decide`、把轮数与日志写回 `store`，最后追加一条可追溯记录、`inflight -= 1`。「取回」和「写回」都经由外部存储，进程随时可以被换掉；对应 [会话隔离与租户边界](./k105-session-isolation.md) 的稳标识，和 [幂等落盘](./k107-idempotent-persist.md) 的按标识定位，是同一套习惯。
6. `health` 刻意不只返回「活着」：它把所用版本和在途数一起报出来。版本用于回答「现在跑的是哪套」，在途数用于停机时判断是否收干净，见 [健康检查与 SLO](./k114-health-slo.md)。`drain` 则先置 `active = False` 停止接新，再返回在途是否为零——顺序不能反，否则会一边关门一边还往里放人。
7. `main` 第一组让 `s-a` 与 `s-b` 交错到达，逐一断言：两个会话首轮都是第 1 轮、`s-a` 第二轮递增到 2、彼此的 `outcome` 没有混进对方的内容、落盘后各自日志条数正好是 2 和 1、探活返回的版本与零在途都对。全无随机数，每一条都能手工推算。
8. 第二组新建一个 `Service` 实例、把版本换成 `v2`、却沿用同一个 `store`，用来模拟「换一版配置并重启进程」：断言轮数从 2 接着涨到 3、旧日志仍是三条没丢、新请求的确用上 `V2`、两份 `records` 分别能指出各自用的版本、且新实例没有改写旧实例的记录。最后一组验停机：在途为零才返回真、停机后再来的请求被明确回绝、状态没有被偷偷改写。结尾统一统计通过项数，任何一条性质被破坏都以非零状态退出。

如实说明一句：这里用一份本地文件代替外部存储、用一段固定函数代替模型与网络入口、用新建实例代替进程重启，全是为了让整条链路不联网、不装第三方包、不依赖任何账号就能独立跑通并手算核对。它演示的是状态归属、版本留痕与停机顺序，不是任何具体服务器框架或托管平台的实现；文中不涉及任何真实耗时、报价或运行记录，也不据此推断真实环境的表现。

## 踩坑与边界

- **把状态塞进模块级变量**：现象是两个请求几乎同时进来，甲的结果里混进了乙的内容，重跑又正常 → 原因是可变状态被所有请求共享，本地单用户时被掩盖了 → 按会话标识把状态外置，处理函数内部只留临时变量，并用「交错请求不串内容」这类断言验一遍，见 [会话隔离与租户边界](./k105-session-isolation.md)。
- **只做「能收请求」不做「能被探知」**：现象是进程在、探活全绿，任务却大面积做不成，重启后进度一片空白 → 原因是只探了存活，没探版本与在途，也没把进度落盘 → 探活报出版本与在途数，任务状态跨进程外置，日志逐次留痕，见 [Trace 该记什么](./k094-trace-fields.md)。
- **改一行配置就整体重发**：现象是每次调提示词都得停服务、重新发一遍，出事还退不回上一套 → 原因是把配置当成散在代码里的字符串 → 提示、模型、路由各自版本化，发布走先观察再放小流量、越线按版本号退回，见 [影子模式、灰度与回滚](./k112-shadow-canary.md)。
- **停机直接杀进程**：现象是在途任务丢失、账目对不上，调用方只拿到半截结果 → 原因是没有收尾动作，进程被硬切断 → 先停止接新，等在途归零再关，必要时按稳标识续跑，见 [断点续跑与优雅恢复](./k110-graceful-resume.md)。
- **密钥写死在代码里、忽略过期**：现象是某一段时间里请求集中失败，换个版本还得把密钥一起打包 → 原因是把会过期的凭据当成了常量 → 启动时从外部读入、按需轮换、只授必要权限，见 [凭证过期与轮换](./k111-credential-expiry.md) 与 [最小权限原则](./k100-least-privilege.md)。

还要分清两件常被混说的事：部署是「把产物放到能长期运行的地方并让它跑起来」，发布是「让真实流量真的开始走它」，前者做好不等于后者安全，两者之间还隔着观察与退路，见 [影子模式、灰度与回滚](./k112-shadow-canary.md)。也要分清「进程活着」和「任务做成」：前者是存活探活，后者要看成功率、越权率、尾延迟与按成功任务核算的花费，见 [按成功任务核算成本](./k096-metrics-cost.md)；给这些量定可守护的线，并让外部能探知状态，见 [健康检查与 SLO](./k114-health-slo.md)。并发一旦上来，同时在跑的数量还得封顶，见 [高并发与并发上限](./k115-concurrency.md)；开销从哪几处冒出来，见 [四重预算](./k103-four-budgets.md) 与 [成本优化与上线检查清单](./k116-cost-checklist.md)。把这些约定写进可查可重放的配置，属于 [提示与策略版本化](./k113-prompt-versioning.md)；请求与会话怎么进、怎么带标识，则是 [传输层与会话管理](./k080-transport-session.md) 先要定下的。这几处约定合起来，才撑得起「长时间对外提供服务」这件事。

## 三句话小结

服务化封装与部署，是把一次运行就结束、状态随手放的脚本，改成状态外置、能被探活、可追溯、可重启的常驻对象，并按四层边界划清每份信息归谁、活多久。

关键做法是让处理函数只认会话标识、从进程外存取状态，把配置与凭据各自版本化，探活报出版本与在途数，停机先停接新再等在途归零，发布另配观察与按版本号退回的退路。

当程序只在本地跑一次性的离线任务、既没有多方调用也不会被重启时，不必硬套这套常驻结构；但只要它要长时间对外提供服务，「状态放在哪儿」就再也不能含糊。

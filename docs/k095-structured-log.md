# 结构化日志与轨迹回放

## 一、场景提问

一个任务跑到第十二步失败了。你打开日志想还原当时发生了什么，看到的是几百行自由文本：`开始查订单`、`参数有点不对`、`重试一次`、`好了`……同一个文件里还交错着另外三个用户请求的打印，时间戳只精确到秒，好几行挤在同一秒里。想按「这一次任务」把所有行挑出来，只能拿用户标识去搜，结果漏了一半——有的行根本没写用户标识。你一咬牙说「那我重跑一遍看看」，可重跑时下游数据已经变了、模型这一轮也可能给出不同判断，怎么都回不到出事那天走过的那条路径。明明每一步都「打了日志」，为什么连「当时到底怎么走的」都拼不出来？

## 二、破误解

**不是把 `print` 换成一行 JSON 就叫结构化日志，也不是把任务再跑一遍就叫轨迹回放；前者要「每条记录字段固定、能逐行解析、能按标识归堆」，后者要「只读记录、不产生任何副作用，就能把当时的状态重新推出来」。**

先把两个词拆开。结构化日志（Structured Log，把一次事件写成字段固定、类型固定、键名固定的一条记录）的对手不是「没有日志」，而是「自由文本日志」。自由文本把信息藏在句子里：同一个意思这次写「用户 A 查订单」，下次写「订单查询，A」，机器要取「用户是谁」只能靠正则去猜，句子一改就全错；而结构化记录是 `{"trace_id": "tr-A", "seq": 3, "kind": "tool_call"}`，取值就是按键读一个字典，不需要理解中文。常见的落盘形式是 JSON Lines（JSON，JavaScript Object Notation，一种纯文本的数据表示格式；JSON Lines 指每行一个完整 JSON 对象、行与行互不嵌套的文本文件），好处是追加写一行就完事、读的时候逐行解析、坏了一行也不影响其它行。字段清单该定哪些，是 [Trace 该记什么](./k094-trace-fields.md) 已经解决的事，这一篇解决「用什么形式记下来」。

再拆轨迹回放（Replay，读取已经落盘的事件序列，按原顺序重新推演出当时的状态）。它最容易被误解成「重跑」。重跑会重新调用工具、重新产生副作用、依赖此刻的下游状态与模型输出，结果可能和当初完全不同；回放只消费「已经发生并被记录下来的事实」，不调用任何外部动作，因此确定、可重复、可离线、零副作用。这个区别不是学术上的讲究：一个已经发起过退款的任务，你绝不会想为了排查而「再退一次」。回放之所以成立，靠三条前提——每条事件有归属（属于哪次任务）、有顺序（在这条任务里是第几步）、有足够的推演依据（这一步让状态怎么变了）；缺了任何一条，「重新推演」就变成「重新猜」。也正因为如此，回放天然连着坏例复现、轨迹评测与回归对比：能把一次失败稳定地摊开看，才谈得上 [坏例闭环](./k093-badcase-loop.md) 和 [结果评测与轨迹评测](./k089-trajectory-eval.md)。

## 三、生活类比

把它想成围棋的棋谱复盘。一盘棋下完，记谱纸上留的是一行行「第几手、谁下的、落在哪个位置」，一盘棋单独一张谱。复盘时两个人坐在棋盘前，照着谱把子一颗颗摆回去，边摆边讨论「这一手如果改下别处会怎样」——他们并没有真的跟对手重下一盘，也没有惊动任何人，只是把已经发生的事重新推演出来。

对应关系很具体。「第几手」是顺序号，保证摆放次序不乱；「一盘棋一张谱」是归属标识，两盘棋的记谱纸就算混在一个抽屉里，也能靠谱号分开；「落在哪个位置」是这一步的载荷，也就是让局面变化的那点信息；照谱摆子而不真下棋，就是「只读记录、不产生副作用」；摆完之后的局面，就是回放推出来的状态。还有两处特别值得记住：其一，记谱漏了一手，后面整盘都对不上，所以顺序必须能查出断号；其二，棋谱记的是「落子」这个看得见的事实，不是「棋手当时心里在想什么」——结构化日志同样只记可观察的事件，意图、猜测、事后补的解释都别混进去，否则回放就成了编故事。

这个类比还顺带说明了「为什么自由文本不行」。自由文本像一段观战随笔：「白棋开局挺顺，后来在中腹纠缠了半天，最后险胜」。读着挺热闹，可你没法照着它把棋摆回去，也没法回答「第三十七手落在哪」。要能回放，记的必须是离散的、有序的、字段齐的事件。

## 四、自绘示意图

:::figure 从事件发生到可回放的链路
@flow
事件发生|定字段成行|追加落盘|按标识归堆|按序回放
:::

五格里最容易省掉的是「定字段成行」。很多人直接在代码里拼一句话写进文件，等于跳过了这一格，后面「按标识归堆」就只能靠字符串匹配硬凑。另一处要点是「追加落盘」与「按标识归堆」是分开的两步：写的时候图省事，所有任务往同一个文件里追加；读的时候再按归属标识各归各堆。这两步分开，才既省事又不串味。

:::figure 一条结构化事件该有的字段
@stack
归属标识::这次任务的唯一编号，跨步骤跨进程都要带着它
顺序号::在这条任务内单调递增的步号，用来排序与查断号
事件类型::计划、工具调用、返回、作答这类可枚举的类别
载荷::本步让状态变化的那点信息，用固定键名与类型写
脱敏标记::这条记录是否已经处理过敏感内容
逻辑时钟::单调的时刻或序号，不依赖机器墙上时间
:::

六行里有两处容易被忽略。「逻辑时钟」用单调序号而不是墙上时间，是因为并发写入时多个事件可能落在同一秒，靠时间戳排不出先后；「脱敏标记」让读日志的人一眼知道这条能不能放心打开，具体遮哪些内容见 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md)。「载荷」强调固定键名与类型——今天叫 `amount`、明天叫 `money`，回放函数就得分两套逻辑，这是字段漂移的常见来源。

:::figure 两种日志形态的差别
@compare
自由文本::字段靠正则猜|并发容易串味|没法照着重放
结构化事件::按键直接取值|按标识各归各堆|可确定性回放
:::

左边不是「记得少」，而是「信息没有结构」：内容可能更长，却取不出、排不动、拼不回。右边每一条都短，但因为字段固定、有归属、有顺序，反而能支撑聚合与回放。

## 五、层层追问

:::ask 那如果并发时好几个任务的事件交错写进同一个文件，怎么保证回放不串？
:::

靠「归属标识 + 各自排序」两步，而不是靠写入顺序。追加写的时候不区分任务，谁先到谁先写；读回来之后先按 `trace_id` 归堆，再在每一堆里按 `seq` 升序排好，于是交错的那几行各回各家。这里有个细节：步号只需要在同一条任务内唯一，不必全局唯一，否则跨进程发号会变成瓶颈；但归属标识必须在整条链路上原样传递，下游、异步任务、子进程都不能自己另起一个，跨进程怎么带、父子关系怎么挂，是 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md) 和 [传输与会话](./k080-transport-session.md) 要解决的。再追一层：那如果同一条任务真被两个进程同时写、步号撞了呢？归堆之后要做一次连续性检查——步号应当从 1 开始严格递增，一旦出现重复或断号就报警，而不是默默排完继续回放；发号侧则让单条任务由一处统一发号，或给步号带上来源前缀。工具调用那一步还可以用 [工具调用标识](./k136-tool-call-id.md) 把「一次调用」和「它的返回」明确对上，避免两笔返回张冠李戴。

:::ask 那既然回放只读记录，当时工具失败、结果不全，回放还能还原吗？
:::

能，但还原的是「记录下来的事实链」，不是「世界当时的真相」。工具失败本身就是一件必须记下来的事件：错误类型、重试了几次、最终是放弃还是降级，都要进序列；回放照着这条链推演，得到的正是「那次任务是如何走到失败的」，这对排查恰恰最有用，错误处理与反馈见 [工具失败](./k040-tool-failure.md)、[错误反馈](./k029-error-feedback.md) 和 [错误分类](./k131-error-classify.md)。真正危险的不是「记了失败」，而是「漏记了一步」：增量式回放会把漏掉的那步当成没发生，推出来的状态就和原始执行悄悄对不上，而且不报错。所以要么每一步记下可校验的状态快照，要么让增量带足够信息并在回放后做一致性核对，检查点与重放的配合可对照 [检查点与重放](./k030-checkpoint-replay.md)。还有一层：回放不需要联网、不需要账号、不需要下游还活着，这正是它能离线做回归对比的原因——把同一份事件喂给新旧两套逻辑，看推出来的状态是否一致，比重新请求一次外部服务可靠得多，思路和 [回归门禁与基线](./k091-regression-gate.md) 是相通的。

## 六、可运行代码与逐行解释

下面这段只用 Python 标准库，完整演示「事件定字段成行 → 并发交错追加到同一个文件 → 落盘读回 → 按归属归堆 → 按序回放」，并用一组断言把「回放与原始执行一致、回放零副作用、缺一步能被发现」逐条验一遍。示例刻意让两条轨迹交错写入，复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络。

```python
import json
import tempfile
from pathlib import Path
from collections import defaultdict
from dataclasses import dataclass, asdict

FIELDS = {"trace_id", "seq", "kind", "delta"}


@dataclass
class Event:
    trace_id: str
    seq: int
    kind: str
    delta: int


def append_line(handle, event):
    """结构化日志 = 每条事件一行 JSON，键名排序后写出，字段固定。"""
    handle.write(json.dumps(asdict(event), ensure_ascii=False, sort_keys=True) + "\n")


def read_events(path):
    """逐行读回，每行都能独立还原成一个事件字典。"""
    out = []
    for line in Path(path).read_text(encoding="utf-8").splitlines():
        if line.strip():
            out.append(json.loads(line))
    return out


def group_and_sort(events):
    """并发写入会交错：先按归属标识归堆，再各自按步号排好。"""
    groups = defaultdict(list)
    for e in events:
        groups[e["trace_id"]].append(e)
    for tid in groups:
        groups[tid].sort(key=lambda x: x["seq"])
    return dict(groups)


def seq_continuous(events):
    """步号应从 1 起严格递增；重复或断号都返回 False。"""
    return [e["seq"] for e in events] == list(range(1, len(events) + 1))


def replay(events):
    """回放：只读记录里的增量累加出状态，绝不调用任何执行动作。"""
    state = 0
    for e in events:
        state += e["delta"]
    return state


def run_original(deltas, ledger):
    """原始执行：真的把每一步记进账本（产生一次可观察的副作用）。"""
    state = 0
    for i, d in enumerate(deltas, 1):
        ledger.append(("step", i, d))
        state += d
    return state


def main():
    plan_a = [3, -1, 4, 2]
    plan_b = [10, 5]
    ledger = []
    expected = {
        "tr-A": run_original(plan_a, ledger),
        "tr-B": run_original(plan_b, ledger),
    }
    ledger_len = len(ledger)

    with tempfile.TemporaryDirectory() as d:
        path = Path(d) / "trace.jsonl"
        with path.open("w", encoding="utf-8") as f:
            # 模拟并发：两条轨迹的事件交错写进同一个文件
            append_line(f, Event("tr-A", 1, "plan", 3))
            append_line(f, Event("tr-B", 1, "tool_call", 10))
            append_line(f, Event("tr-A", 2, "tool_call", -1))
            append_line(f, Event("tr-B", 2, "answer", 5))
            append_line(f, Event("tr-A", 3, "tool_call", 4))
            append_line(f, Event("tr-A", 4, "answer", 2))

        lines = [ln for ln in path.read_text(encoding="utf-8").splitlines()
                 if ln.strip()]
        events = read_events(path)
        groups = group_and_sort(events)
        checks = [
            ("日志每行一条事件", len(lines) == 6),
            ("每行都是可解析的结构化记录", all(isinstance(e, dict) for e in events)),
            ("字段集合固定不漂移", all(set(e.keys()) == FIELDS for e in events)),
            ("并发交错后仍按归属归堆", set(groups) == {"tr-A", "tr-B"}),
            ("每堆各自按步号排好序",
             seq_continuous(groups["tr-A"]) and seq_continuous(groups["tr-B"])),
            ("落盘读回后序列完整", len(events) == 6),
        ]

        got = {tid: replay(evs) for tid, evs in groups.items()}
        checks.append(("回放状态与原始执行一致", got == expected))
        checks.append(("回放不产生任何副作用", len(ledger) == ledger_len))
        checks.append(("结构体能按键直接取标识",
                       all(e["trace_id"] in ("tr-A", "tr-B") for e in events)))
        checks.append(("同一事件重复序列化结果稳定",
                       json.dumps(events[0], ensure_ascii=False, sort_keys=True) == lines[0]))

        damaged = [e for e in groups["tr-A"] if e["seq"] != 3]
        checks.append(("缺一条事件能被步号检查发现", not seq_continuous(damaged)))
        checks.append(("缺事件后回放结果随之改变",
                       replay(damaged) != expected["tr-A"]))

        passed = sum(1 for _, ok in checks if ok)
        for name, ok in checks:
            print(("通过 " if ok else "失败 ") + name)
        print("通过 %d/%d 项" % (passed, len(checks)))
        assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `FIELDS` 与 `Event` 把「字段清单」写成可校验的契约：`dataclasses` 定义一条事件的四个字段，`asdict` 负责把它转成普通字典。写日志时不拼句子，只序列化这个结构体，字段名字从此不会今天一个样明天一个样。
2. `append_line` 是「定字段成行」那一格：`json.dumps` 加 `sort_keys=True`，让同一事件无论谁来写、写多少次，产出的那一行都完全相同；`ensure_ascii=False` 让中文原样保留，便于人直接读。每行末尾一个换行，就是 JSON Lines 的全部要求。
3. `read_events` 逐行解析，每行独立还原成一个字典。这正是结构化相对自由文本的优势：不需要跨行理解、不需要正则，坏一行也不会带崩其它行。
4. `group_and_sort` 处理并发交错：先用 `defaultdict` 按 `trace_id` 归堆，再在每堆内按 `seq` 排序。写入顺序因此完全不重要，读回来一定能各归各家。
5. `seq_continuous` 是断号检查：步号应该正好是 `1..n`。它同时挡住「漏记一步」和「两个进程发了同一个号」两种情况，缺一条就会返回 `False`，而不是悄悄排完继续算。
6. `replay` 与 `run_original` 是整段的关键对照。前者只把记录里的 `delta` 累加出状态，函数里没有任何写账本、调工具的动作；后者每走一步都往 `ledger` 里追加一笔，代表真实副作用。二者算出的状态应当一致，但副作用数量应当不同。
7. `main` 先跑一遍原始执行拿到 `expected`，并记录此刻账本长度；接着把两条轨迹的六条事件交错写进同一个临时文件，再读回归堆。前六条断言分别验「一行一条、逐行可解析、字段不漂移、按标识归堆、各自有序、序列完整」。
8. 后面六条断言验回放的性质：`got == expected` 说明只读记录也能推回同样状态；`len(ledger) == ledger_len` 说明回放一笔副作用都没产生；按键取标识与重复序列化稳定，说明结构化确实带来了机器可读与确定性；最后故意抽掉 `tr-A` 的第三步，验证断号检查会报警、且回放结果随之改变。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用整数增量代替真实的工具返回、用内存账本代替外部副作用、用临时文件代替日志系统，全是为了让「交错写入—归堆—零副作用回放」这条链路不需要联网、账号或第三方包就能独立跑通并手工核对。它演示的是结构化记录与回放之间的关系，不是任何具体日志组件的实现。

## 七、踩坑与边界

- **把换皮当结构化**：现象是日志改成了 `json.dumps({"msg": "用户查了订单"})`，字段仍取不出来 → 原因是整段话还是塞在一个字符串里，只是外面套了层对象 → 把「谁、第几步、什么类型、载荷」拆成固定键名与固定类型，别让一个键装一整句话。
- **靠墙上时间排序**：现象是并发时好几条事件落在同一秒，回放顺序每次都不一样 → 原因是时间戳精度不够、且多机时钟未必一致 → 用任务内单调递增的步号排序，墙上时间只作参考，归堆与排序的做法见 [结构化状态](./k046-structured-state.md)。
- **跨进程丢了归属标识**：现象是异步任务或子进程写出的事件归不进任何一堆，像凭空冒出来的孤儿 → 原因是下游自己另起了编号 → 归属标识在整条链路原样往下传，父子关系见 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md)。
- **回放悄悄重跑了一遍**：现象是排查一次退款问题，结果又产生了一笔真实动作 → 原因是把「回放」实现成「重新执行一遍原流程」 → 回放函数只消费已落盘的记录，禁止调用任何会写外部状态的函数，并用账本不变的断言验一遍。
- **漏记一步却不报错**：现象是回放出来的状态看着合理，却和当时对不上，查了很久才发现中间少一条事件 → 原因是增量式回放把「没记录」当成了「没发生」 → 每步写可校验的状态快照或带足信息的增量，并在回放前后做连续性与一致性核对，见 [检查点与重放](./k030-checkpoint-replay.md)。

还要划清两条边界。第一，回放推演的是「记录下来的事实链」，它能告诉你这次是怎么走到失败的，但不能替你补回当初没记下的真相；字段齐不齐，取决于写日志那一刻，这正是 [Trace 该记什么](./k094-trace-fields.md) 要先解决的事。第二，结构化日志解决「取得出、排得动、拼得回」，不解决「记下来的内容里有没有敏感信息」——那要在写入前就脱敏，见 [Trace / Span / TraceId 与日志脱敏](./k146-trace-span.md)，隐私边界对照 [记忆与隐私](./k074-memory-privacy.md)。回放本身也不等于评测：它把轨迹摊开，判断「这条轨迹好不好」要靠 [结果评测与轨迹评测](./k089-trajectory-eval.md) 里的断言与评分。

## 九、三句话小结

结构化日志与轨迹回放，是把一次任务写成字段固定、有归属、有顺序的一行行事件，再只靠读这些事件把当时的状态重新推演出来。

关键做法是写入时定死字段与键名、用任务内单调步号排序、按归属标识归堆，让回放函数只消费记录、不碰任何外部动作，并用断号检查与状态一致性核对兜底。

当任务本身没有可复现的事件序列、或记录里根本没留下推演所需的载荷时，不必硬做回放；但只要一次结果可能被追问「当时到底怎么走的」，自由文本日志就撑不住这个要求。

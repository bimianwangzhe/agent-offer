# 状态共享、冲突处理与失败恢复

几个智能体协作时，你让它们都往同一份记录里写：一个写订单号，一个写风控结论，一个写回执。跑着跑着发现风控把订单号覆盖了，或者某个节点中途报错，重跑之后前面已经做过的动作又做了一遍，最后谁也说不清哪些结果还算数、哪些该作废。想查问题时，那份记录只是一段不断追加的聊天文本，根本没有「谁在什么时候改了哪个字段」的痕迹。

**不是模型写错了，是把「共享状态」当成了「大家都能往上贴的聊天记录」。** 协作要能收尾，状态必须是结构化字段：每个字段有唯一属主、每次写入带着版本、失败时能按节点撤掉自己的部分，而不是一句谁都能改的自由文本。

先把词说清。共享状态（shared state）指多个执行者共同读写、且作为唯一真相源的那份数据；唯一真相源的意思是判断「现在到哪一步了」只认它，不认聊天记录里的某句话。属主（owner）指某个字段唯一有权写入的节点。版本（version）是一个随写入递增的数字，用来发现「我读到之后别人改过了」。回滚（rollback）指撤掉某个失败节点写过的部分，保留其余节点的成果。智能体（Agent）是能自己决定下一步并调用工具的程序，多智能体（Multi-Agent）是几个这样的程序协作。结构化状态常用字典承载，字段叫什么、什么类型要事先约定清楚。这些词立住之后，「冲突」和「恢复」才不是两个含糊的形容词。

## 一、生活类比：三个施工队共填一张验收表

想象装修收尾时，三个施工队共填一张挂在墙上的验收表。表格不是白纸，而是早早划好了格子：水电队只能填「通电」那一格，泥瓦队只能填「墙面」那一格，保洁队只能填「清场」那一格，谁也不许往别人的格子里写字。每次填之前，填的人要抄一下这格当前的编号，交表时如果编号跟自己抄的不一样，就说明趁他干活时有人改过，这张涂改作废，得重新看一眼再填。这叫「先记版本、再核对」。

中途保洁队干砸了、要返工，处理方式不是把整张表擦干净重来，而是只擦掉保洁队填过的那几格，水电和泥瓦的成果照旧留着。最后负责人看一眼表：格子全填了，整单完成；只填了一部分，就叫「部分完成、需要人工接手」；一格都没留下，才算全部退回。对应关系是：验收表格子对应共享状态里的字段，队伍对应智能体，格子编号对应版本，只擦自己那几格对应按节点回滚，最后那一眼对应整单收尾判定。**如果没有「每格归谁」和「抄编号」这两条约定，三个人同时填表必然互相覆盖，出错后也没法对账。**

## 二、共享之前先定三件事

把类比收成工程约定，就是三件必须提前定死的事：共享什么、谁能改、失败怎么收。共享范围要尽量小，只放跨节点确实要用的字段，别把整段对话轨迹塞进状态里当垃圾桶；写权限要收到字段级，每个字段指定唯一属主，别人一律只读；恢复策略要按节点划分，谁失败撤谁，别一崩就清空整单。三件事少一件，协作就会从「可核对的分工」滑回「谁都能改的文本」。

:::figure 共享状态要定清的三件事
@stack
共享什么::只放跨节点要用的字段，别把聊天记录塞进来
谁能改::每个字段指定唯一属主，别人一律只读
失败怎么收::撤掉失败节点的写入，其余成果保留
:::

这里有个容易被跳过的判断：状态该存成「追加式写入记录」还是「直接覆盖的当前值」？前者每次写入都留一条（谁、哪个字段、什么值），版本可以由记录条数算出来，回滚就是按节点过滤掉那些记录；后者只保留最新值，一旦写错就没有回头路。本文代码选了追加式记录，正是为了让「谁在什么时候改了什么」随时可查，评测和排障都吃这份数据。任务拆开之后每块交出什么产物，见[任务拆分与完成标准](./k119-task-decomposition.md)；本篇管的是这些产物写进共享表之后怎么不打架。

:::ask 那如果两个节点几乎同时想写同一个字段呢？
靠「属主唯一 + 版本核对」两道关，而不是靠谁动作快。字段属主唯一，意味着其中一方本来就没资格写，会当场被判越权；如果确实是同一属主前后两次写，那么后一次必须带着「我读数时的版本」，而这时版本已经变了，写入会被判成版本冲突，要求重新读一遍再决定。**冲突不是靠加锁硬扛，是靠把「写之前看到的是哪一版」显式带进写入请求里。** 这样即使顺序被打乱，结论也不会悄悄被覆盖。
:::

:::ask 那如果失败节点早就把结果发给下游了呢？
只撤掉写入还不够，下游手里那份已经作废的结果也得算数。所以收尾判定不能数「写过的行数」，要数「当前仍有效的字段」，并且把「某字段失效」这件事显式传播出去。更深一层的坑是超时：请求超时不代表动作没发生，重试前必须先对账，否则同一动作会被执行两次。**恢复的对象是「有效状态」，不是「日志条数」**，这也是为什么状态里要留出「待审批、已作废」这类字段，而不是只有一个布尔的完成标记。整单收尾时怎么把这些限制讲清楚，见[约束、权衡与可验证结果](./k123-tradeoffs.md)。
:::

:::figure 聊天记录当状态与结构化字段当状态
@compare
聊天记录::谁都能往上写|改了没留痕|失败时无法对账
结构化字段::属主唯一|写入带版本|可按节点回滚
:::

左边三点是连锁的：谁都能写 → 改了没留痕 → 失败时无法对账，于是只能靠人重读全文猜。右边三点也是连锁的：属主唯一 → 写入能带版本 → 回滚能精确到节点。选哪种不是风格问题，是「出事之后能不能查得清」的问题。

## 三、把三件事写成能跑的共享状态

下面的脚本零依赖、不需要账号、不需要联网。它用一份追加式写入记录作唯一真相源，实现字段级属主、版本冲突检测、按节点回滚，以及整单收尾的三种判定。

```python
# k120.py —— 共享状态：写权限、版本冲突、失败恢复（零依赖，python k120.py）


class SharedState:
    def __init__(self, owners):
        self.owners = owners          # 字段 -> 唯一有权写的节点
        self.writes = []              # (节点, 字段, 值)，追加式，唯一真相源

    def version(self, field):
        return sum(1 for _, f, _ in self.writes if f == field)

    def read(self, field):
        vals = [v for _, f, v in self.writes if f == field]
        return (vals[-1] if vals else None), self.version(field)

    def write(self, node, field, value, expect_version):
        if self.owners.get(field) != node:
            return {"ok": False, "why": "越权写入"}
        if self.version(field) != expect_version:
            return {"ok": False, "why": "版本冲突"}
        self.writes.append((node, field, value))
        return {"ok": True, "version": self.version(field)}

    def rollback_node(self, node):
        before = len(self.writes)
        self.writes = [w for w in self.writes if w[0] != node]
        return before - len(self.writes)

    def snapshot(self):
        return {f: self.read(f)[0] for f in self.owners}


def settle(state):
    """整单怎么收尾：看还有多少个字段有值。"""
    done = state.snapshot()
    filled = sum(1 for v in done.values() if v is not None)
    if filled == 0:
        return "全部回滚"
    if filled == len(done):
        return "全部完成"
    return "部分成功需人工"


if __name__ == "__main__":
    passed = total = 0

    def check(label, cond):
        global passed, total
        total += 1
        assert cond, label
        passed += 1
        print("  [通过] " + label)

    s = SharedState({"订单": "A", "风控": "B", "回执": "C"})
    r1 = s.write("A", "订单", "DD1001", 0)
    check("首个写入成功且版本升到 1", r1["ok"] and r1["version"] == 1)
    check("非属主字段被挡：越权写入", s.write("B", "订单", "抢写", 0)["why"] == "越权写入")
    check("拿旧版本重写被挡：版本冲突", s.write("A", "订单", "DD1002", 0)["why"] == "版本冲突")
    check("风控节点写自己的字段成功", s.write("B", "风控", "通过", 0)["ok"])
    check("回执节点写自己的字段成功", s.write("C", "回执", "RECEIPT", 0)["ok"])

    removed = s.rollback_node("B")
    check("失败节点只撤自己的写入", removed == 1 and s.snapshot()["订单"] == "DD1001")
    check("被撤字段回到未填", s.snapshot()["风控"] is None)
    check("其余节点成果保留", s.snapshot()["回执"] == "RECEIPT")
    check("整单判为部分成功需人工", settle(s) == "部分成功需人工")

    s.write("B", "风控", "通过", 0)
    check("补齐后整单全部完成", settle(s) == "全部完成")
    check("空状态判为全部回滚", settle(SharedState({"订单": "A"})) == "全部回滚")
    print("通过 %d/%d 项" % (passed, total))
```

运行后打印每条断言与汇总：

```text
  [通过] 首个写入成功且版本升到 1
  [通过] 非属主字段被挡：越权写入
  [通过] 整单判为部分成功需人工
通过 11/11 项
```

逐段解释关键行在做什么：

1. `self.owners` 把「字段 → 唯一属主」写成一张表，`self.writes` 是追加式三元组列表（节点、字段、值），两者合起来就是唯一真相源，不另存一份可能被改乱的当前值。
2. `version` 用「该字段的写入条数」当版本，`read` 取该字段最后一次写入的值并连版本一起返回。这样版本不需要额外计数器，也不会和值脱节。
3. `write` 的两道 `if` 就是前面两道关：先核对属主，不是就返回「越权写入」；再核对 `expect_version` 与当前版本是否一致，不一致就返回「版本冲突」。两次失败都不写入，因此不会产生半条脏记录。
4. `rollback_node` 用列表推导只过滤掉该节点的写入，并返回撤掉的条数；`snapshot` 按 owners 的字段逐一把「最后一次有效值」取出来，这就是收尾判定看到的视图。
5. `settle` 数「有值的字段数」而不是「写过的条数」，据此给出全部回滚、部分成功需人工、全部完成三种结论。中间态单独列出来，是为了不让「部分完成」被含糊地说成「完成」。
6. 主程序依次演示成功写入、越权、版本冲突、按节点回滚、补齐后完成，每条都经 `assert` 兜底，最后打印 `通过 N/N 项`，让检查器本身也可复核。

:::tip 收尾判定要有中间态
只有「完成 / 没完成」两个值的系统，会把失败悄悄咽下去。**把「部分成功需人工」写成一等结论，交接才有明确去处，人接手时才知道还差哪一格没填。**
:::

## 四、踩坑与边界

- **谁都能改字段**：现象是风控节点把订单号覆盖掉，追溯不到是谁写的 → 原因是没有字段级属主，任何节点都能写任何字段 → 怎么改：先建 owners 映射，`write` 第一道关就判越权。
- **不带版本就重写**：现象是同一字段被后一次写入静默覆盖，前一次结果凭空消失 → 原因是写入请求没带「读数时的版本」 → 怎么改：像 `expect_version` 那样强制携带，不一致就判冲突并要求重读。
- **一崩就清空**：现象是某个节点失败后把整单状态重置，前面已经做过的动作全部重来 → 原因是恢复粒度按「整单」而不是「节点」 → 怎么改：用 `rollback_node` 只撤该节点的写入，其余成果保留。
- **超时当没发生**：现象是请求超时后直接重试，同一动作执行了两次 → 原因是把「没收到响应」等同于「动作没发生」 → 怎么改：重试前先读状态对账，确认字段是否已被写入，再决定要不要重做。
- **只看写入条数**：现象是日志里明明有记录，收尾却判成全部回滚，或者反过来把作废结果算成完成 → 原因是收尾按日志行数而不是有效字段判断 → 怎么改：用 `snapshot` 后的有效值来判定，并显式传播「字段失效」。

:::figure 一次写入到整单收尾
@flow
读当前版本|核对属主|追加写入|失败则回滚|判定整单收尾
:::

图里「追加写入」而不是「覆盖写入」，是整条链可回溯的前提；有了它，评测能拿同一份记录做回归对比，答辩能现场把一次冲突和一次回滚复现出来。怎么把这类故障讲进有限时间里，见[15 分钟讲项目的节奏](./k126-project-pitch.md)。

:::quote
协作出事之后能不能查清，取决于状态是「谁都能贴的聊天记录」还是「字段有属主、写入带版本、失败能按节点撤」的结构化数据。
:::

- [ ] 能说清为什么共享状态不能是一段自由文本

- [ ] 能说出「部分成功需人工」为什么必须是一等结论
- [ ] 知道超时重试前要先对账，而不是直接重做
- [ ] 能徒手画出从读版本到收尾判定的五个环节
:::

是什么：这是把多智能体共享数据管成结构化字段、并用版本与按节点回滚来收尾的方法。
关键做法：字段定唯一属主、写入携带读时版本、失败只撤该节点、收尾按有效字段给出三种结论。
什么时候不该用：只有一个执行者、或者任务没有跨节点共享结果时，别引入这套机制，单份状态直接读写更省事。

# 写入判定：什么时候该记，先把这一步从模型手里拿回来

## 场景：长期记忆里混进了寒暄、口令和一段来路不明的话

你给助手开了长期记忆，几天后打开库一看，里面躺着「你好」「嗯」「好的收到」，还躺着一句用户半开玩笑输入的「我的密码是某某某」；更要命的是，有一句话看着像用户偏好，其实是某次检索片段里夹带的一行字，被当成事实存了下来。你问助手为什么记这些，它给不出稳定说法——同一句「今天天气不错」，有时存了有时没存。你原本只是想让它别把正事忘了，结果它把什么都往里塞。

## 先破一个最常见的误解

**不是模型判断力不行，是「该不该记」这一步根本不该交给模型自由裁量。** 写入判定说的是：先决定这条够不够格进记忆，再决定以什么形式记。这前后两件事要分开。第一件必须是一段确定性代码：同样的输入，任何时候都得到同样的结论，能单测、能回滚到某一版、被退回时能指到具体是哪条规则挡的。交给模型会怎样？它每次输出本来就不完全一样，同一条这次判「重要」、下次判「闲聊」；而且它并不知道下一轮的输入额度有多紧，天然偏向「宁可多记一点」，于是库越攒越杂。把这道门收回到代码里，不是不信任模型，而是把「决定权」和「改写权」分开：门开不开由规则说了算，门开了以后怎么把一句自然语言整理成结构化字段，再让模型去做也不迟。

## 用生活里的事打个比方：档案室的收件窗口

想象一间档案室，所有文件都得先过收件窗口。收件员手里有一张打印好的清单，逐条核对：这是不是正式单据、里头有没有不该归档的敏感字段、是不是一次性的临时通知、够不够格长期留存。合格的盖章收下，明显不合格的当场退回，说不清的先搁进「待补」筐，不急着入柜。对应关系逐条对一遍：那张清单就是判定规则，盖章就是允许写入，退回就是丢弃，「待补」筐就是待定档，入柜就是落到长期存储。为什么不能让收件员「看着办」？换个人、换个下午、换种心情，标准就变了；事后有人问「这行为什么进了档案」，也答不出个准数，更没法把某一批错误收件统一撤回来。用清单就不一样：清单是白纸黑字、可版本化、可逐条改的，哪天发现漏收了一种单据，改一行、记一笔，改动有据可查。

## 画出来看

先看待判的一句候选按什么顺序过门。顺序本身是有讲究的：拦截类的检查要排在前面。

:::figure 一句候选过写入门的顺序
@flow
一句候选|查敏感字段|查信息量|命中稳定规则|写入或退回
:::

「查敏感字段」排在最前，是因为一旦句子里带这类字段，后面判得再准也不该落地；把它放最后，就可能出现句子里同时有稳定词和敏感字段时先被放进来的漏网。「写入或退回」也不止两种结果：还有「待定」，说不清的先搁着，别急着入柜。再看两种判定方式的差别。

:::figure 两种判定方式的差别
@compare
交给模型判::同条时记时不记|偏向宁多勿少|无法回滚
交给规则判::同条结果恒定|按清单可测|能定位到哪条规则
:::

右边那行三个要点，其实对应着工程上最实在的三样好处：结果可复现、能写成回归断言、出错时能定位到具体哪条清单项。这三样都不是「判得更聪明」，而是「判得可交代」。

## 再往下追两层

:::ask 追问一
那规则会不会太死，把该记的漏掉？
:::

会，这个担心是对的，但解法不是把门拆了。第一，留出「待定」这一档：说不清的先不入柜，也不当垃圾扔掉，留个可复查的地方。第二，把被退回的内容记成日志，隔一阵回看一眼「最近退回的都是些什么」，发现某类本该收的被挡了，就补一条规则。第三，把规则当成能改、能回滚的产物：改一行、留一笔改动说明，比换一个「更聪明」的判法好查得多。真正危险的做法是怕漏就放开自由裁量——那样漏是少了，可库里会混进大量说不清来路的东西，而一条不该记的被记进去，会在往后每一轮被反复引用，见[记忆不是日志](./k065-memory-vs-log.md)。规则宁可保守一点，也不能不可交代。

:::ask 追问二
那「记什么」这一步又该怎么做？
:::

判定通过之后才轮到它，顺序不能反。这一步是把一句自然语言整理成结构化字段：说的是哪个对象、哪个字段、值是什么、什么时候、从哪来。它可以交给模型做，因为最坏结果只是措辞不同，不决定「进不进库」，而且整理完还得再过一遍校验。整理出来的东西，如果关于同一个对象已有记录，就合并到对应那一格，见[实体摘要与画像更新](./k069-entity-summary.md)；字段之间打架时按版本裁决，见[冲突消解与版本](./k071-conflict-resolution.md)。另外有两道门是规则判定里必须单独列出的：用户是否同意被记、以及这句话是不是外部带进来的内容——前者是同意门控，后者是注入防范，详见[隐私脱敏、同意与记忆污染](./k074-memory-privacy.md)。把它们写进清单，而不是指望模型自己察言观色。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，把「该不该写」写成一张纯规则清单，用一组构造用例逐条验证判定结果。复制成 `.py` 直接运行会打印每条的归类。

```python
# 判定规则全部是确定性代码，模型不参与「该不该写」这一步
STABLE_HINTS = ("偏好", "以后", "默认", "总是", "不要", "记住")
SENSITIVE = ("密码", "身份证", "银行卡", "密钥")
GREETINGS = ("你好", "在吗", "谢谢", "早上好")


def decide(text: str):
    """返回 (是否写入, 类别, 理由)，纯规则、可复现。"""
    if any(k in text for k in SENSITIVE):
        return False, "拒绝", "含敏感字段，写入前必须拦截"
    if any(k in text for k in GREETINGS) and len(text) <= 6:
        return False, "丢弃", "纯寒暄，不影响未来决策"
    if any(k in text for k in STABLE_HINTS):
        return True, "稳定事实", "命中稳定偏好词，值得长期保留"
    if len(text.strip()) < 4:
        return False, "丢弃", "信息量过低"
    return False, "待定", "未命中任何写入规则，先不写"


if __name__ == '__main__':
    cases = [
        ("你好", False, "丢弃"),
        ("记住我默认用中文", True, "稳定事实"),
        ("我的密码是 123456", False, "拒绝"),
        ("嗯", False, "丢弃"),
        ("今天天气不错适合散步", False, "待定"),
    ]
    for text, want_write, want_kind in cases:
        write, kind, reason = decide(text)
        assert write == want_write, (text, kind)
        assert kind == want_kind, (text, kind)
    print("逐条判定：")
    for text, _, _ in cases:
        print(" ", text, "->", decide(text)[1])
    print("通过 5/5 项")
```

1. 三个常量元组就是那张清单：`STABLE_HINTS` 是会长期生效的稳定词，`SENSITIVE` 是必须拦截的敏感字段，`GREETINGS` 是纯寒暄。把它们集中放在文件开头，改标准时只动这里，不用翻遍代码。
2. `decide` 的第一个 `if`：敏感字段检查排最前，命中直接返回「拒绝」，连理由都写清楚。这个位置就是上一节说的「拦截类检查要排在前面」。
3. 第二个 `if` 判纯寒暄，额外加了 `len(text) <= 6` 的长度条件：光出现「谢谢」两个字、后面没别的内容才算寒暄，避免把一句正文里带「谢谢」的长句误丢。
4. 第三个 `if` 命中稳定词才返回写入，第四个 `if` 把过短、没信息量的内容丢掉，最后的 `return` 给「待定」——说不清的既不入柜也不当垃圾，留一个明确档位。四个分支顺序不能随意调换。
5. `cases` 是一张手工构造的用例表，每行写清「输入、期望是否写入、期望类别」，覆盖寒暄、稳定偏好、敏感字段、过短内容和说不清的一句。循环里两条断言把「是否写入」和「类别」同时钉住，属于可回归的性质断言。
6. 末尾 `print` 把每条的归类打出来：既是运行到结尾的凭据，也方便对照清单逐条核。

## 踩过的坑与边界

- **检查顺序颠倒**：现象是「记住我的密码是某某某」被当成稳定偏好写进去了 → 原因是先判稳定词、后拦敏感字段 → 把拦截类检查放到最前，让任何含敏感字段的句子一律先退回。
- **把「待定」当成「丢弃」**：现象是本该补一条规则才能收的单据被无声扔掉，事后无从发现 → 原因是只有两个结果、没有中间档 → 单列「待定」，并把被退回的内容记成日志定期回看。
- **规则散落在各个调用处**：现象是同一句话在 A 处记了、B 处没记 → 原因是每个入口各写了一套判断 → 收拢到一个具名函数，所有写入都过这一道门。
- **让模型自由裁量「重要吗」**：现象是同一条时记时不记，库里越攒越杂 → 原因是模型输出不确定、且偏向宁多勿少 → 门开不开交给规则，模型只负责门开之后的字段整理。
- **省掉同意门控与来路检查**：现象是外部片段里夹带的一行字被当成用户偏好存了下来 → 原因是只看内容像不像偏好、没看是谁说的、用户同不同意 → 把同意与来路列成清单里的两条硬规则，见[隐私脱敏、同意与记忆污染](./k074-memory-privacy.md)。

边界也讲清楚：规则判定适合「够不够格进记忆」这种要可交代的决定。它不负责理解一句话的全部含义，也不负责把自然语言整理得漂亮；那些是判定通过之后的事。另外，规则保守会漏，所以要配「待定」和退回日志，别指望一次就把清单写全。进了库之后还得能撤，见[遗忘、过期与 TTL](./k073-forgetting.md)。

## 三句话小结

写入判定是先决定该不该记、再决定记什么，把「进不进库」这道门交给确定性规则，而不是模型自由裁量。
做法是把清单集中成一个具名函数，拦截类检查排最前，留「待定」档与退回日志，判定通过后才整理成结构化字段。
需要理解一句话的全部含义、或生成自然措辞时，别用规则硬套；那属于判定通过之后的整理工作。

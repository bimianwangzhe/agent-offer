# 记忆不是日志：只留下会改变未来判断的那一小部分

## 场景：存得越全，反而答得越离谱

你给助手接了一份持久化，把每一轮对话、每一次工具返回、每一句寒暄都写进文件，心里想着「存得全总不会错」。跑了几天，用户明明在开头说过「一律用中文、回答别超过三句」，后面却开始冒出英文长段落；你想查到底是哪条记录把它带偏，翻出来几万行流水，绝大多数是「好的收到」「接口返回成功」「耗时零点几秒」，真正有用的那句承诺早被淹没了。更麻烦的是，助手把某次工具报错里带出来的旧取值当成事实，之后每一轮都照着它说。你没丢数据，却丢了该起作用的那句话。

## 先破一个最常见的误解

**不是存得不够全，是把「记录发生过什么」当成了「记住该记什么」。** 这两件事的目标根本不同：日志的目标是复现，要求一件事不落地记下来，越多越完整越好，方便出事以后按时间倒查；记忆的目标是改善下一次判断，要求只把会改变未来动作的那几条摆到台面上，越少越准越好。把两套目标混在一起，就会出现一个反直觉的结果——数据一条没少，效果却变差了。原因不神秘：能被模型这一轮看到的输入是有限的，多塞一条无关流水，就少一个位置留给真正要紧的约束；更要命的是，无关内容里往往夹着看起来很像事实的旧值，一旦被当成前提引用，就会一路错下去。所以「全」对日志是优点，对记忆是负担。判断一条东西该不该进记忆，尺子只有一把：它会不会改变未来某一次的判断。不会，就让它留在日志里。

## 用生活里的事打个比方：监控录像与交接本

把系统想成一家二十四小时营业的便利店。店里装了监控，摄像头从早录到晚，一帧不落，这是日志；柜台下面还有一个交接本，上一班只写三行：「备用金放在第二个抽屉」「三号冷柜今天断电、别往里补货」「常客老王不要塑料袋」，这是记忆。两者的对应关系值得逐条对一遍。录像按时间堆，只追加不整理，谁也不会去改它，因为它的价值就是「当时到底发生了什么」；交接本按价值筛，会划掉过期的、会改写有变动的、会被下一班质疑「这条还准吗」。录像写满一百页不影响谁，交接本写满一百页就没人看了，下一班抓不住重点，反而会漏掉真正要紧的那条。为什么交接本不能照抄录像？因为读它的人要在几秒钟内决定怎么做事，他需要的是「下一班该怎么做」，不是「上一班每一秒都在干什么」。筛选尺子就是那句：这条会不会改变下一班的动作。会，才配写进本子；不会，录像里存着就好，本子上别占位置。一个系统里这两样东西完全可以并存：录像留着回放，本子负责决策，谁也别去顶替谁。

## 画出来看

先看写入前的那道筛子。它必须放在「写入」这一步之前，而不是等召回时再挑——召回时面对的是已经堆积如山的条目，那时候再筛，成本已经付过了，噪声也已经进了库。

:::figure 从流水到记忆的一道筛子
@flow
逐条流水|判定类别|只留事实决策|写入记忆|供下轮取用
:::

这张图里最该留意的是「判定类别」这一格：它是一段确定性代码，读的是每条流水自带的类别标签，不是把原话丢给模型问「你觉得这条重要吗」。类别是写流水时就标好的（比如寒暄、工具回显、稳定事实、明确决策），筛子只做一次集合判断，同样输入必然得到同样输出。再看两套标准的对照。

:::figure 日志与记忆的两套标准
@compare
日志::只求全|按时间堆|目标是复现当时
记忆::只求准|按价值筛|目标是改善下一次
:::

左边那行说的是复现，右边那行说的是决策。两行放在一起，是想说明它们不是「同一种东西存多存少」的区别，而是从目标、组织方式到验收办法都不一样的两种产物。日志的验收是「当时那一帧还在不在」，记忆的验收是「下一次判断有没有变好」。用错验收办法，就会拿「我存得挺全」去替「它答得更准」辩护。

## 再往下追两层

:::ask 追问一
那如果把「会不会影响未来」也交给模型自己判断呢？
:::

会不稳。同一句「今天天气不错适合散步」，模型这次可能判成一条偏好，下次可能判成闲聊略过；而且它天然偏向「宁可多记一点」，因为它并不知道下一轮的输入额度有多紧、也不知道多一条噪声会挤掉什么。更根本的问题是，判断标准一旦交给一个每次输出都不完全相同的东西，就没法复现、没法单测、出了偏差也没法回滚到某一版规则。稳妥的分工是：代码里的规则负责「该不该写、算哪一类」，模型最多负责把一句自然语言改写成结构化字段。规则是死的，所以可测；改写是活的，但只在被允许写入之后才发生。这一步的具体判定清单，是[写入判定：什么时候该记](./k070-write-decision.md)那一篇要拆开讲的事。

:::ask 追问二
那如果早期记错了一条，后面是不是就一直错下去？
:::

会，而且比日志里记错一条严重得多。日志里的错误可以靠「再翻一遍当时的录像」被发现和纠正，因为它不是任何判断的前提；记忆里的错误会被当成既定事实反复引用，越引用越像真的。这正是「只留少数」不是偷懒的理由：条目少，才查得动、改得动、撤得回。你得给每条记忆留出被推翻的通道——新旧事实打架时按版本裁决，见[冲突消解与版本](./k071-conflict-resolution.md)；过期、标错、敏感的内容要有明确退出机制，见[遗忘、过期与 TTL](./k073-forgetting.md)。把记忆控制在一眼能看完的规模，这些机制才落得了地。至于整套东西按生命周期分开放，是[工作 / 情景 / 语义三层记忆](./k066-memory-types.md)的话题。

## 一段能直接跑的代码

下面这段不联网、不装任何第三方包、不需要账号，只用标准库。它把一串构造出来的流水按类别筛成记忆，结尾用三条断言把性质钉死。复制成 `.py` 文件直接运行，会打印出条数对比和通过项。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Event:
    kind: str      # 事件类别：chat / tool / fact / decision
    text: str


# 只有「稳定事实」和「明确决策」会改变未来的判断，寒暄与工具回显不会
USEFUL_KINDS = {"fact", "decision"}


def is_memory(event: Event) -> bool:
    return event.kind in USEFUL_KINDS


def build_memory(log: list) -> list:
    return [e.text for e in log if is_memory(e)]


if __name__ == '__main__':
    log = [
        Event("chat", "你好呀"),
        Event("tool", "查询天气接口返回 200"),
        Event("fact", "用户偏好把报告导出为 PDF"),
        Event("chat", "好的收到"),
        Event("decision", "以后默认用中文回复"),
        Event("tool", "计时 0.31 秒"),
        Event("fact", "用户所在时区为东八区"),
    ]
    memory = build_memory(log)
    # 断言 1：记忆是日志的真子集，不是照单全收
    assert len(memory) < len(log), "记忆不该等于全部日志"
    # 断言 2：寒暄与工具回显没有进入记忆
    assert all("接口返回" not in m and "你好" not in m for m in memory)
    # 断言 3：三条会影响未来的事实与决策都在
    assert len(memory) == 3
    assert "以后默认用中文回复" in memory
    print(f"日志 {len(log)} 条 -> 记忆 {len(memory)} 条")
    print("通过 3/3 项")
```

1. `from dataclasses import dataclass` 与 `@dataclass(frozen=True)`：定义一条「不可变」的流水事件，只有类别和正文两个字段。不可变的意思是建好之后不许改，避免筛查过程中被顺手篡改，回放时看到的就是当时那条。
2. `USEFUL_KINDS = {"fact", "decision"}`：这把集合就是那道筛子，也是全文说的那把尺子的代码形态。它只认两类：稳定事实与明确决策。想调整标准，改这一行就够了，不用去翻每一处判断。
3. `is_memory` 与 `build_memory`：一个判断单条该不该留，一个把整批流水滤成记忆文本。逻辑短到可以一眼看完，这正是规则判定该有的样子——没有隐藏状态，没有外部依赖。
4. `log = [...]`：七条手工构造的数据，故意混进寒暄、工具回显、稳定事实和明确决策，用来证明筛子确实分得开。注意它们都是可复现的构造场景，不是从哪份真实记录里摘的。
5. 三条 `assert`：分别钉住「记忆是日志的真子集」「噪声没混进来」「三条有用的全在」。断言写的是性质，不是某个具体数值，所以以后换一批构造数据也照样能当回归用。
6. 末尾两个 `print`：把七条变三条的对比和通过项打出来，肉眼就能确认这次运行确实走到了结尾，而不是中途被异常截断。

## 踩过的坑与边界

- **把工具返回原文整段当记忆**：现象是库里堆满接口回显，模型开始引用里面的旧取值 → 原因是工具返回是「发生过什么」，不是「以后该怎么做」，它甚至可能是一次失败的结果 → 改成只从返回里提炼出会改变后续判断的那一两个字段，原文留在日志里。
- **判定标准写成「重要的就记」**：现象是同类内容这次记、那次不记，谁也说不清规律 → 原因是「重要」是主观词，执行的人或模型每次理解都不一样 → 改成可判定的类别清单，比如只认稳定事实与明确决策，其余一律先不写。
- **筛子放在召回那一刻**：现象是库越攒越大，取回时还得从一大堆里临时挑，成本和污染都已经发生 → 原因是把筛选当成了读取时的优化 → 改到写入之前做，让不配进记忆的内容根本不落地。
- **只加不删，错误被永久引用**：现象是三个月前一句误记到现在还在影响回答 → 原因是记忆没有退出机制，被当成只会增长的事实表 → 给每条留出撤销、标错、过期的通道，并保留完整版本链以便回溯。
- **拿日志当证据链却又嫌它太全**：现象是既要求逐帧可查，又要求它精简好读 → 原因是想把一份产物同时当录像和交接本用 → 明确分成两份：日志只管复现、按时间堆；记忆只管决策、按价值筛，别互相顶替。

边界也要说清：这套筛法适合「会影响未来判断」的稳定内容。如果某个场景要的是审计每一帧、复现某次故障的完整经过，那该做的是把日志留好，而不是硬把它削成记忆。

## 三句话小结

记忆不是把发生过的事全存下来，而是只留会改变未来判断的那一小部分。
做法是在写入前用确定性规则按类别筛，把结果当成可测试、可撤销的少量条目来管。
需要逐帧复现当时经过、或事后审计每一次调用时，该留的是日志，别用记忆去顶。

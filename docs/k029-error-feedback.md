# 错误回传

## 场景提问

你写的小程序让它连续调几个工具完成一件事，其中一个工具中途报了错。你的处理很朴素：要么把异常 `try` 住、只往控制台打印一句「出错了」就当没发生，要么更「诚实」一点，把整段报错堆栈原样拼回对话，心想让模型自己看着办。结果两种都不对劲——前一种，模型压根不知道刚才那步失败了，下一轮又发起一模一样的调用，同一个错循环往复；后一种，堆栈里夹着一堆路径、行号、内部提示，模型被这些无关文字带偏，开始改一些不该改的东西，甚至把内部细节复述给用户。你明明只是想把「这步没成」告诉它，怎么就变成了要么没告知、要么告知过头？

## 破误解

**错误回传不是把报错文本转发给模型，而是把一次失败翻译成一条带类别、带可操作提示、带计数、能追溯的观察记录，让下一轮知道该改什么。**

先把位置摆正。在「决策—行动—观察」这个闭环里，失败也是一种观察，而且往往比成功更有信息量：成功只说明「这条路走得通」，失败会告诉你「这条路为什么走不通、该往哪边绕」。既然是观察，它就该和别的观察一样，被规规矩矩写进循环状态里，而不是被当成需要特殊处理的意外。很多人把它当成例外，于是走了两个极端：吞掉，等于这一轮观察凭空消失，模型只能靠猜，最省事的猜法就是重复上一步；原样转发，等于把一份给工程师排查用的内部材料直接塞给了做决策的人，里面既有它读不懂的路径行号，也有不该外泄的凭据与内部措辞。两种做法错在同一处：都没有回答「这条观察要驱动下一轮做出什么不同的动作」。

一条合格的错误回传，至少要想清四件事。第一是类别：这次失败到底属于「参数写错了，改一改就能重试」「下游一时忙，等会儿重试」「没有权限，重试也没用」还是「内部故障，根本不该让调用方知道细节」。类别决定了后面所有动作，含糊不得。第二是可操作提示：给模型的应当是一句它能据此改动作的话，比如「缺少必填字段，请补齐后重试」，而不是一段它无从下手的堆栈。第三是脱敏与边界：权限、凭据、内部路径这类细节不该喂给模型，更不该有机会被复述到回答里；这类错误只给一句中性的「该动作不可继续」，具体处理交给代码或终止逻辑。第四是计数与追溯：同一个动作、同一类错连续出现几次，必须有记录，否则「回传」会退化成「无限重试同一堵墙」，而排查时又答不出「到底第几轮开始错、之前错过几次」。这四件事合起来，才把「失败」变成了「可据以决策的观察」。类别怎么判、哪些可重试，[异常分类与可重试判定](./k131-error-classify.md) 和 [工具失败分类与重试策略](./k040-tool-failure.md) 会展开；回传之后要不要真的重试、隔多久重试，则是 [重试、指数退避与抖动](./k108-retry-backoff.md) 要管的。

## 生活类比

把它想成快递员派件失败后填的那张回单。一个不负责的快递员只写「没送到」，站点第二天照原地址再派一次，第三天又没送到，包裹在原地打转。规范的做法是把失败原因分门别类写清：「门牌号不存在」属于信息填错，得回头找寄件人补正再派；「收件人临时不在」属于过会儿再试；「收件人明确拒收」属于别再派了，得退回;「面单上的内部编号异常」属于站点自己处理，跟收件人无关，也不该把内部编号抄给外人。回单上还带着同一个运单号和派送次数，站点一看就知道这单已经试过几回、是不是该停了。

对应关系很整齐。那张写清类别的回单就是错误回传这条观察；「门牌号不存在 / 收件人不在 / 拒收 / 内部编号异常」对应参数错、临时故障、权限或规则拒绝、内部故障四类错误；「找寄件人补正」「过会儿再试」「别再派了」就是给下一轮的可操作提示与重试决策；「面单内部编号不外泄」对应脱敏，内部细节只给站点、不给收件人；「运单号加派送次数」对应动作标识与连续失败计数，用来防重复、防无限重试、也方便事后追溯。

这个比喻还点出两处最容易漏的。其一，回单是「给决定下一步的人看的」，不是「给修车师傅看的」——排查用的完整堆栈该进日志，进决策链路的只是那几句能改变动作的话，这两份材料得分开存，思路和 [结构化日志](./k095-structured-log.md) 一致。其二，「已经派了三次」这个数字本身就是一个决策依据：哪怕每次原因都一样，次数到了也得换策略或停下，这正是 [熔断与 kill switch](./k104-circuit-breaker.md) 里「连续失败到阈值就先别再撞」的朴素版本。至于哪些字段能出现在给用户的回答里、哪些必须拦掉，可对照 [输出扫描与内容过滤](./k099-output-scan.md)。

## 自绘示意图

:::figure 一次失败从发生到回传的链路
@flow
动作执行失败|判定错误类别|脱敏生成提示|并入循环状态|驱动下一轮改动作
:::

五个格子里，「判定错误类别」是分水岭：它左边的失败还是一堆原始材料，右边才变成能用的观察。少了这一格，后面「脱敏」「决定要不要重试」全都没有依据，只能一刀切。而「并入循环状态」这一步提醒我们，错误不是打印完就结束的临时消息，它得和别的观察一样被记下来、能被计数，这部分和 [循环状态该存什么](./k027-loop-state.md) 里「工作层记已确认事实」是同一套字段设计。

:::figure 一条错误观察该带的字段
@stack
类别::参数错/临时故障/拒绝/内部故障，决定后续动作
可重试::布尔值，代码据此判断要不要再发起一次
提示::给模型的一句可操作话，不含堆栈
标识::动作名加序号，用来去重和追溯
次数::同类错连续出现几回，到阈值就停
:::

五类字段里最容易被省掉的是「次数」和「可重试」。没有次数，同一个错可以无限回传下去；没有可重试，代码只能靠读提示文字去猜「这意思是让我再试还是别试」，而猜就会出错。把它们做成明确的字段、由代码判定，而不是塞进一句自然语言里让模型自己体会，是这套设计稳不稳的关键。

:::figure 两种回传姿势的差别
@compare
吞掉或原样转发::观察丢失或被噪声带偏|同一错反复撞|内部细节可能外泄
结构化分类回传::下一轮知道改什么|连续失败可被计数|敏感细节被挡住
:::

左边图省事，代价全在「同一个错反复出现、越跑越偏」上；右边多做了分类、脱敏、计数三件小事，换来的是循环撞墙时能自己拐弯。二者的差距不在报错写得多不多，而在「这条信息能不能改变下一轮的动作」。

## 层层追问

:::ask 那如果同一个错误反复出现，光回传不还是会一直撞下去吗？
:::

会，所以「回传」本身必须带刹车，这也是它和「单纯打一条日志」最本质的区别。做法是给每个「动作 + 错误类别」记一个连续出现次数：第一次回传，把「请补齐字段」这类提示交给模型去改；第二、第三次还犯同样的错，说明改参数这条路没走通，就该升级处理——要么换一种做法，要么按既定阈值停下并上报。这里有两个细节值得较真。一是计数要按「动作加类别」这个组合来，而不是笼统数「一共错了几次」：不同动作的失败彼此无关，混在一起数会把不相干的错累加到误停。二是阈值到了要「停得明确」，也就是把终止判定写成一个能被 [四个终止条件](./k028-stop-conditions.md) 检到的信号，而不是含糊地让模型「自己看着办」。自动纠正也有它的上限，重试几次就该收手、别把预算烧光，[自动纠正与重试上限](./k019-auto-repair.md) 讲的就是这条线。

:::ask 那到底哪些错该回传给模型改参数，哪些错根本不该让模型看到？
:::

这是第二层、也更考边界感的一问，判据是「这次失败，改变调用方的动作能不能解决」。参数写错、字段缺失、类型不符、引用的编号不存在，这类都属于「信息填错了」，改一改确实能解决，理应回传给模型，并附上一句能据此修正的提示——注意 [参数有效不等于业务合法](./k034-param-validity.md) 还提醒，有些错看起来是参数问题，其实是业务规则不允许，别一律让它「再补一个字段试试」。临时繁忙、短暂不可用，属于「不是动作的错，是时机的错」，回传给模型的应是「稍后重试同一动作」，而不是让它改参数。而权限不足、规则明确拒绝、凭据异常、内部故障这几类，改变调用方的动作也解决不了，重试纯属浪费，细节还可能涉及不该外泄的信息：这类错误不该把原始内容喂给模型，只给一句中性的「该动作不可继续，请换方式或结束」，具体处理交给代码、终止逻辑，必要时让人介入。工具返回该长什么样才便于这样分类，[工具返回格式设计](./k035-tool-result.md) 有更细的约定;真到了「修不动、也绕不过」的时候，就别硬撑，[果断降级与兜底返回](./k020-graceful-fallback.md) 讲的是怎么体面地给出一个可用结果而不是空转。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用一台本地的「模拟工具」抛出几类构造出来的错误码，完整演示「分类 → 脱敏生成提示 → 按动作加类别计数 → 判定该重试还是该停」。复制到任意装有 Python 的机器上直接运行即可，不需要第三方包、账号或网络；结尾用一组断言逐条验证性质。

```python
import json
from collections import Counter

RETRYABLE = {"param", "transient"}   # 可重试的两类：改参数、等时机
MAX_SAME = 3                          # 同一动作同一类错连续出现到这个次数就停


def classify_error(raw_code):
    """把模拟工具抛出的原始错误码翻译成 (类别, 原因)。"""
    table = {
        "missing_field": ("param", "缺少必填字段"),
        "bad_type": ("param", "字段类型不符"),
        "no_such_id": ("param", "引用的编号不存在"),
        "busy": ("transient", "下游繁忙"),
        "no_permission": ("fatal", "无权限执行该动作"),
        "secret_error": ("internal", "内部凭据异常"),
    }
    return table.get(raw_code, ("internal", "未归类错误"))


def build_observation(raw_code, action, seq):
    """把一次失败翻译成要回传给下一轮的结构化观察。"""
    kind, reason = classify_error(raw_code)
    if kind in ("internal", "fatal"):
        # 内部与权限错误的细节不喂给模型，只给可操作的中性提示
        hint = "该动作不可继续，请改用其它方式或结束"
        detail = "已隐藏"
    else:
        hint = "请按提示修正参数后重试" if kind == "param" else "请稍后重试同一动作"
        detail = reason
    return {
        "seq": seq,
        "action": action,
        "kind": kind,
        "retryable": kind in RETRYABLE,
        "hint": hint,
        "detail": detail,
    }


class FeedbackLoop:
    """维护连续错误计数，决定每条观察是回传重试还是触发停止。"""

    def __init__(self):
        self.seq = 0
        self.streak = Counter()   # (动作, 类别) -> 连续出现次数
        self.log = []

    def feed(self, action, raw_code):
        self.seq += 1
        obs = build_observation(raw_code, action, self.seq)
        key = (action, obs["kind"])
        self.streak[key] += 1
        obs["streak"] = self.streak[key]
        obs["should_stop"] = (
            not obs["retryable"] or self.streak[key] >= MAX_SAME
        )
        self.log.append(obs)
        return obs


def main():
    loop = FeedbackLoop()
    checks = []

    o1 = loop.feed("写订单", "missing_field")
    checks.append(("参数错被判为可重试", o1["retryable"] is True))
    checks.append(("参数错回传了可操作提示", "修正参数" in o1["hint"]))
    checks.append(("参数错给出具体原因", o1["detail"] == "缺少必填字段"))

    o2 = loop.feed("写订单", "secret_error")
    checks.append(("内部错误不可重试", o2["retryable"] is False))
    checks.append(("内部错误细节被脱敏", o2["detail"] == "已隐藏"))
    checks.append(("内部错误触发停止", o2["should_stop"] is True))

    o3 = loop.feed("查询库存", "busy")
    checks.append(("临时故障可重试", o3["retryable"] is True))
    checks.append(("临时故障首现不停", o3["should_stop"] is False))

    seq = [loop.feed("查询库存", "busy") for _ in range(MAX_SAME)]
    checks.append(("同类错误连续计数递增", [x["streak"] for x in seq] == [2, 3, 4]))
    checks.append(("连续达阈值即停止", seq[-1]["should_stop"] is True))

    checks.append(("每条观察都有序号可追溯",
                   [x["seq"] for x in loop.log] == list(range(1, len(loop.log) + 1))))
    checks.append(("观察可写成纯文本",
                   isinstance(json.dumps(loop.log, ensure_ascii=False), str)))

    passed = sum(1 for _, ok in checks if ok)
    for name, ok in checks:
        print(("通过 " if ok else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks)


if __name__ == "__main__":
    main()
```

1. `import json` 与 `from collections import Counter` 都取自标准库，`Counter` 用来给「动作 + 类别」这种组合键计数。`RETRYABLE` 明确列出哪两类可重试、`MAX_SAME` 定下连续失败的阈值，这两个常量把「要不要再试」从一句话变成代码能判定的规则。
2. `classify_error` 是整条链路的分水岭：把模拟工具抛出的原始错误码映射成 `(类别, 原因)`。未收录的错误码一律落到 `internal`，也就是「宁可保守地不外泄、停下，也别把看不懂的错当成可重试」——默认保守是这里的取值原则。
3. `build_observation` 把一次失败翻译成结构化观察。对 `internal` 和 `fatal`，提示写成中性的「不可继续」、`detail` 置为「已隐藏」，原始细节根本不进这条观察；对 `param` 和 `transient` 才给出具体原因和对应的可操作提示。这一步就是「脱敏」和「给模型一句能改动作的话」的落点。
4. 返回的字典里，`kind` 是类别、`retryable` 是布尔值、`seq` 是序号、`hint` 是给模型的提示、`detail` 是（可能已隐藏的）原因。特别留意 `retryable` 是独立字段：代码靠它决定要不要重试，不必去解析提示文字猜意思。
5. `FeedbackLoop` 维护 `streak` 计数和一份 `log`。`feed` 里用 `(动作, 类别)` 组合键累加连续次数，把次数写回观察，再判定 `should_stop`：不可重试的错立刻停，可重试的错连续到 `MAX_SAME` 次也停。这正对应前面说的「按动作加类别数，而不是笼统数总错数」。
6. `main` 先验证参数错被判可重试、提示可操作、原因具体；再验证内部错误不可重试、细节被隐藏、直接触发停止；接着验证临时故障首现可重试且不停。随后连续喂三次同类错，断言计数依次是 2、3、4、并在达到阈值时停——注意第一次 `busy` 已经记过一次，所以连续段从 2 起算。
7. 最后断言每条观察都有连续可追溯的序号、整份 `log` 能被写成纯文本 JSON，保证这些观察既能喂给下一轮、也能存档排查。结尾 `print("通过 %d/%d 项" % ...)` 汇总、`assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处要如实说明：这里用一张本地映射表代替了真实工具的错误码体系，用内存里的 `log` 代替了真正的日志落盘，为的是让「分类—脱敏—计数—判定」整条链路不依赖联网、账号或第三方包就能独立跑通并手算验证。它演示的是错误该怎么被翻译成观察、以及何时该停，不是任何具体服务的异常处理实现。

## 踩坑与边界

- **把异常吞掉只留一句「出错了」**：现象是模型下一轮发起一模一样的调用，同一个错循环往复 → 原因是这一轮的观察凭空消失，模型只能靠猜，猜法就是重复上一步 → 把失败整理成带类别和提示的观察并入状态，让下一轮明确知道该改什么。
- **把整段堆栈原样拼回对话**：现象是模型被路径行号带偏、改了不该改的东西，甚至把内部措辞复述给用户 → 原因是把给工程师排查用的材料直接塞给了做决策的一方 → 排查细节进日志，决策链路只留可操作提示，敏感内容按 [日志脱敏与链路标识](./k146-trace-span.md) 的思路挡住。
- **拿自然语言提示当重试依据**：现象是代码靠读「请稍后再试」这类文字去猜要不要重试，猜错就无限撞墙 → 原因是「可重试」没有被做成能被程序判定的字段 → 单列一个布尔字段和类别字段，重试与否由代码判定，不靠解析话术。
- **不记连续次数**：现象是同一个动作同一类错回传十几次，预算烧光也没停 → 原因是每次回传都当成第一次，没有累计 → 按「动作加类别」记连续次数，到阈值就停或换策略，参考 [熔断与 kill switch](./k104-circuit-breaker.md)。
- **所有错一律回传给模型改参数**：现象是权限不足、规则拒绝的错也被要求「补个字段再试」，越试越乱还可能踩到越权 → 原因是没区分「改动作能解决」和「改动作也解决不了」 → 只有信息填错、时机不对这两类回传给模型，其余给中性提示并交给代码或终止逻辑，边界见 [参数有效不等于业务合法](./k034-param-validity.md)。

还有两条边界要分清。「错误回传」负责的是「把失败变成一条合格观察」，它不负责「真的发起重试」——中间还隔着退避、抖动、预算这些决定，别把两件事揉成一步。另外，回传给模型改参数的前提是「这次失败确实能靠改动作解决」；当循环已经跑偏、连目标都变了味时，问题往往不在某一次报错上，那属于目标层面的偏移，得换一套处理，可对照 [目标漂移与周期性重述](./k135-goal-drift.md)。

## 三句话小结

错误回传是把一次失败翻译成带类别、可操作提示、脱敏处理、可计数可追溯的结构化观察，让它作为一轮观察进入循环状态、驱动下一轮做出不同的动作。

关键做法是先判定错误类别、把可重试与否做成代码能判定的字段、内部与权限细节只进日志不进决策链路，并按动作加类别累计连续失败到阈值就停。

当一次调用根本不循环、或失败完全不需要模型参与、由调用方直接处理即可时，不必套这套回传机制；但只要下一轮要依赖「上一步成没成」来决定动作，失败就不能被吞掉或原样丢回去。

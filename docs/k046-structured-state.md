# 结构化状态摘要

## 场景提问

你让一个 Agent 跑一件十几轮才能收尾的活：整理近一年的售后工单，归出三类高频问题，再给出能回溯到原文的结论。为了不让上下文越滚越长，你每隔几轮就把前面的对话压成一段摘要塞回去，本地看它写得挺通顺、字数也降下来了。可跑到后面它开始不对劲：同一份工单列表反复拉了三次，用户第一句就说定的「只统计近一年」被忘得一干二净，两个互相矛盾的结论还能在同一段话里并存。你把那段摘要翻出来，想找「它到底从哪一轮开始记岔的」，却发现摘要里目标、进度、约束、数字全揉成了一团，根本没法对账。明明做了压缩，怎么反而更不可控了？

## 破误解

**不是压缩把内容压丢了这么简单，是你让一段自由发挥的自然语言同时兼了「记事本、待办清单、约束表、数据表」四份差事，而它一样都没担稳。**

先把话说清。摘要式压缩（把多轮历史改写成一段更短的连贯文字）解决的是「太长」，这一点没错，[摘要式压缩](./k044-summary-compression.md) 讲的就是怎么用更少的字装下更多轮。但它有一个代价常被忽略：改写会把原本分门别类的事实压平成一串句子。压缩前，「目标是 A」「约束是不能碰 B」「工单总数是 320」「还剩两步没做」是四类不同的东西；压缩后，它们变成一段读起来很顺的话，谁也分不清哪句是哪类。更麻烦的是，让模型自己重写这段话时，它每写一次都可能换个说法、漏个数字、把「还没答的问题」写成「已经答了」，而你没有任何办法逐项核对——因为压根就没有「项」可以对。这类「压完以后到底丢了什么」的核对问题，[压缩后信息丢失怎么验证](./k048-compression-verify.md) 会专门展开，本文先把地基打好。

这篇要讲的「结构化状态摘要」，是换一种装法：不再把状态写成一篇作文，而是写成一份字段固定的状态对象。先约定好有哪些槽位——当前目标、硬约束、已确认事实、已完成动作、待办动作、还没答上来的问题——每个槽位只放一类东西，有固定类型，有明确归属。每来一条新信息，不做全文重写，只按它的类型增量更新到对应槽位；要交给模型看时，再把这些槽位按固定顺序渲染成紧凑文本。这么做的好处不是「更短」（它未必比一段话短），而是可校验、可逐项比对、可回放：约束还在不在，一查就知道；某个数字是哪一轮被改成新值的，顺着事件就能追；同一串事件重放一遍，必须得到逐字相同的状态。把「记事」从作文题变成填表题，才是本文要讲透的那一个点。

还要分清它和另外两样东西的边界。[循环状态该存什么](./k027-loop-state.md) 讨论的是「一轮跑完哪些值必须带到下一轮」，是取值清单；本文讨论的是「这些值用什么形状装、怎么更新」。而 [四层上下文结构](./k042-context-layers.md) 是更大的排布框架：结构化状态摘要通常住在常驻层里，每轮必带、写死不压缩，它和会滚动变化的近期轨迹、按需要取回的外置历史是两码事。把「状态」当成「又一段可以随手压缩的历史」，正是很多人一上手就走歪的地方：历史可以压，状态不该被压成散文。

## 生活类比

把它想成看病时的两份材料。一份是医生查房后随口讲的一段话：「病人前几天有点低烧，我让他别吃辣的，验血结果好像还行，回头再看看片子，可能还要约个复查……」听着都懂，可真要交接班，接手的护士没法从这段话里准确答出「现在绝对禁忌是什么」「哪项指标是多少」「下一步到底做哪几件事」。另一份是表格病历：诊断栏、过敏与禁忌栏、检验数值栏、已完成处置栏、待执行医嘱栏、待确认问题栏，一格一格填，谁改了哪格、几点改的都留着。

对应关系很具体：那段查房口述，就是自由文本摘要；表格病历的每一个栏位，就是状态对象里的一个槽位。「禁忌」这种一旦写错会出事的格子，对应硬约束，必须原样常驻、不参与任何改写；「检验数值」对应事实槽，同一个指标今天测了新值就覆盖旧值，但旧值归档可查；「已完成处置」和「待执行医嘱」对应完成槽与待办槽，一件事做完就从待办划到已完成，不能两栏都挂着；「待确认问题」对应还没答上来的问题，答上来就出列、并把答案落成一条事实。护士交接不用重读全部对话，只要把表格扫一遍，就能回答「目标是什么、还差什么、什么不能碰」。

这个比喻还点出最要命的一处：表格病历之所以可靠，不是因为字写得比口述漂亮，而是因为**栏位是固定的**。哪怕今天没查出新问题，「待确认问题」那一栏也得空着摆在那儿，不能因为没事就整栏删掉——否则明天有人以为「没这一栏」等于「没问题」。放到系统里，就是状态对象的字段必须齐全且类型固定，空槽位要显式留空，而不是让它随摘要一起消失。还有一层：改表格是「在某一格里改一个值」，不是「把整页病历重抄一遍」。重抄一遍，抄的人每次都可能顺手改掉别处的措辞；只改一格，别处逐字不动——这正是增量更新比全量重写稳的根本原因。

## 自绘示意图

:::figure 一条信息进入结构化状态的路径
@flow
新事件到达|判定事件类型|增量写入对应槽|版本号加一|固定顺序渲染
:::

这张图里最容易被跳过的是「判定事件类型」和「增量写入对应槽」这两格。很多人一听到「更新状态」，下意识就是把整份状态连同新信息一起再喂给模型，让它「重新总结一遍当前状态」——那等于又退回全量重写。正确的做法是由代码先判断这条信息属于哪一类，再只动那一格；模型不参与「搬运」，它只负责产出决策，状态由确定性的代码维护。

:::figure 状态对象的六个槽位
@stack
目标槽::一句话说清这轮要达成什么，全文只有一个
约束槽::不可违反的硬条件，原样常驻不改写
事实槽::按键去重的已确认值，新值覆盖旧值
完成槽::按发生顺序记录做完的动作
待办槽::还没做但已规划好的动作
待答槽::悬而未决的问题，答上来即出列
:::

六格里最该被保护的是「约束槽」和「事实槽」。约束一旦被摘要改写成「大意差不多」的话，边界就松了；事实一旦被写成「大约三百多条」这种模糊说法，后面所有需要精确值的判断都会跟着歪。把它们做成带类型的槽位，而不是混在一段话里，才有办法在每轮结束时用代码检查「约束还在不在、数字是不是被改了措辞」。

:::figure 两种记事方式的差别
@compare
自由文本摘要::读起来连贯|槽位无从对齐|重写易漂移
结构化状态摘要::字段固定可查|增量更新不扰动|事件可重放
:::

左边顺风顺水时省事，出问题时却连「丢在哪」都答不上；右边看起来多了一层结构，换来的是可以逐项核对、可以定位到某一轮、可以从事件序列还原出当时那份状态。二者的差距，全在「记岔了以后能不能查得动」。

## 层层追问

:::ask 那如果任务一复杂，字段越加越多，最后不又变成一大坨了吗？
:::

会，所以槽位不是想到一个加一个，而是先定死一张短表。判断该不该新增字段，只看一件事：这类信息是否需要在每轮被单独校验、单独覆盖、单独回答「还在不在」。如果答案是「不需要，它只是某次过程的记录」，那它就不该进状态对象，而该作为轨迹另存、需要时按标识取回，这部分在 [写选压隔四类操作与不可压缩项](./k139-context-ops.md) 里会讲清哪些东西压根不该常驻。目标、约束、事实、完成、待办、待答这六类，几乎能覆盖绝大多数循环任务；真遇到必须新增的，也要同步补上校验规则和渲染位置，不能悄悄往字典里塞一个谁都不知道的键。这里还有个反直觉的经验：字段越少、每个字段职责越单一，状态越可靠；把「备注」这种万能字段开出来，等于给自由文本开了后门，用不了几轮大家又会把所有东西塞进去。

:::ask 那如果好几个来源同时改同一个字段，比如两个子任务都写「工单总数」，听谁的？
:::

这是把结构化状态真正用起来之后必然会撞上的第二层问题。单写入口时很简单：后到的事件覆盖先到的，代码里一句赋值就完事，演示代码用的就是这种。可一旦并发更新或分叉回放，就得先约定合并语义：是按时间戳取最新、按来源优先级取、还是把两次写入都留成版本让人来裁决，这属于 [Reducer 合并语义与分槽写入](./k144-reducer-slot.md) 要处理的范畴；而「回到某一轮、沿另一条分支重新跑」则依赖 [时间旅行、重放与分叉](./k145-time-travel.md)。本文给出的增量更新之所以坚持「每次返回一份新状态、旧状态原样保留」，正是为这两件更难的事留了门：只要每一步都是可回放的确定性事件，合并与分叉才有共同的底子。反过来说，如果状态是一段被反复改写的散文，连「这一版和上一版差在哪」都无法表达，合并就无从谈起。还有个细节别漏：事实槽做成「键到值」的字典，而不是一串句子，正是为了让「两次写同一个键」这件事有明确定义——同键覆盖，不同键并存，冲突被收敛到一个键上，而不是散落在两句话里互相打架。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，把「固定字段状态对象、按事件类型增量更新、字段校验、固定顺序渲染、事件重放还原」完整串起来，结尾用一组断言逐条验证。所有输入都是本地构造的字典，复制即跑，不需要任何第三方包、账号或网络。

```python
import json
from copy import deepcopy

# 状态对象的固定字段：每个槽位只承担一种职责
FIELDS = ("goal", "constraints", "facts", "done", "todo", "open_questions")


def new_state(goal, constraints):
    """造一份初始状态：字段齐全、类型固定，空槽位显式留空。"""
    return {
        "goal": goal,
        "constraints": list(constraints),
        "facts": {},           # 键 -> 值，同一键的新值覆盖旧值
        "done": [],            # 已完成动作，按发生顺序
        "todo": [],            # 待办动作
        "open_questions": [],  # 还没答上来的问题
        "version": 0,
    }


def apply_event(state, event):
    """增量更新：按事件类型只改对应槽位，返回新状态、不就地改动旧的。"""
    kind = event["type"]
    s = deepcopy(state)
    if kind == "fact":
        s["facts"][event["key"]] = event["value"]
    elif kind == "done":
        item = event["item"]
        if item in s["todo"]:
            s["todo"].remove(item)
        s["done"].append(item)
    elif kind == "todo":
        s["todo"].append(event["item"])
    elif kind == "question":
        s["open_questions"].append(event["item"])
    elif kind == "answer":
        q = event["item"]
        if q in s["open_questions"]:
            s["open_questions"].remove(q)
        s["facts"][event["key"]] = event["value"]
    else:
        raise ValueError("未知事件类型: %s" % kind)
    s["version"] += 1
    return s


def validate(state):
    """校验：必填字段齐全、类型正确、约束非空、整份状态可序列化。"""
    problems = []
    for f in FIELDS:
        if f not in state:
            problems.append("缺字段 %s" % f)
    if not isinstance(state.get("goal"), str) or not state["goal"]:
        problems.append("goal 必须是非空字符串")
    if not isinstance(state.get("constraints"), list) or not state["constraints"]:
        problems.append("constraints 必须是非空列表")
    if not isinstance(state.get("facts"), dict):
        problems.append("facts 必须是字典")
    for f in ("done", "todo", "open_questions"):
        if not isinstance(state.get(f), list):
            problems.append("%s 必须是列表" % f)
    try:
        json.dumps(state, ensure_ascii=False, sort_keys=True)
    except (TypeError, ValueError):
        problems.append("状态不可序列化")
    return problems


def render(state):
    """渲染成给模型看的紧凑文本：字段带标签、顺序固定、可逐行读。"""
    lines = ["[目标] " + state["goal"],
             "[约束] " + "；".join(state["constraints"])]
    for k in sorted(state["facts"]):
        lines.append("[事实] %s=%s" % (k, state["facts"][k]))
    for item in state["done"]:
        lines.append("[已完成] " + item)
    for item in state["todo"]:
        lines.append("[待办] " + item)
    for q in state["open_questions"]:
        lines.append("[待答] " + q)
    return "\n".join(lines)


def replay(events, goal, constraints):
    """从事件序列重放：同一串事件必须还原出逐字相同的状态。"""
    s = new_state(goal, constraints)
    for e in events:
        s = apply_event(s, e)
    return s


def main():
    goal = "整理近一年的售后工单并给出三类高频问题"
    constraints = ["只统计近一年", "不得编造工单编号", "结论要能回溯到原文"]
    events = [
        {"type": "todo", "item": "拉取工单列表"},
        {"type": "todo", "item": "归类高频问题"},
        {"type": "fact", "key": "工单总数", "value": 320},
        {"type": "done", "item": "拉取工单列表"},
        {"type": "question", "item": "退款类是否单列"},
        {"type": "answer", "item": "退款类是否单列", "key": "退款单列", "value": "是"},
        {"type": "fact", "key": "工单总数", "value": 318},
    ]
    checks = []

    s = replay(events, goal, constraints)
    checks.append(("字段齐全且合法", validate(s) == []))
    checks.append(("目标未被事件改写", s["goal"] == goal))
    checks.append(("约束原样保留", s["constraints"] == constraints))
    checks.append(("事实按键去重且取最新值", s["facts"]["工单总数"] == 318))

    s0 = new_state(goal, constraints)
    s1 = apply_event(s0, {"type": "fact", "key": "来源", "value": "工单库"})
    checks.append(("旧状态不被就地修改", "来源" not in s0["facts"]))
    checks.append(("版本号按事件递增", s1["version"] == s0["version"] + 1))

    s2 = apply_event(s1, {"type": "todo", "item": "校验数量"})
    s3 = apply_event(s2, {"type": "done", "item": "校验数量"})
    checks.append(("完成后从待办移除", "校验数量" not in s3["todo"]))
    checks.append(("完成后进入已完成", "校验数量" in s3["done"]))
    checks.append(("其余事实不丢", s3["facts"]["来源"] == "工单库"))

    s4 = apply_event(s3, {"type": "question", "item": "是否需要导出"})
    s5 = apply_event(s4, {"type": "answer", "item": "是否需要导出", "key": "导出", "value": "需要"})
    checks.append(("回答后问题出列", "是否需要导出" not in s5["open_questions"]))
    checks.append(("回答落成事实", s5["facts"]["导出"] == "需要"))

    text = render(s)
    checks.append(("渲染含全部约束", all(c in text for c in constraints)))
    checks.append(("渲染含最新事实值", "工单总数=318" in text))
    checks.append(("渲染顺序可复现", render(replay(events, goal, constraints)) == text))
    checks.append(("重放可还原同一状态", replay(events, goal, constraints) == s))

    broken = deepcopy(s)
    broken["constraints"] = []
    checks.append(("校验能发现约束被清空", validate(broken) != []))

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == "__main__":
    main()
```

1. `FIELDS` 与 `new_state` 把「状态长什么样」写死成一张短表：六个业务槽位加一个版本号，空槽位用空字典或空列表显式占位。注意 `constraints` 用 `list(...)` 复制一份，避免外部列表后来被改动时悄悄污染状态。
2. `apply_event` 是整套做法的关键。它先用 `deepcopy` 复制出一份新状态，再按 `event["type"]` 只改动对应的那一个槽位，最后把版本号加一。因为返回的是新对象而非就地修改，旧状态自然成了「上一版」，回放与分叉才有依据，这也是后面断言「旧状态不被就地修改」能成立的原因。
3. 五种事件各自对应一种精确的语义：`fact` 按键覆盖、`done` 把事项从待办移到已完成、`todo` 追加待办、`question` 登记待答、`answer` 让问题出列并把答案落成事实。把「回答一个问题」拆成「出列 + 落事实」两步，是为了让「待答」和「已确认」永远不混淆——这正是自由文本摘要最爱犯错的地方。
4. `validate` 不依赖模型，纯用类型判断和一次 `json.dumps`（JSON，JavaScript Object Notation，一种纯文本的数据表示格式；能转成它就说明整份状态可序列化、可落盘、可比对）来查字段是否齐全、类型是否正确、约束是否被清空。它演示的是「每轮结束时用代码查一遍」，而不是再问模型「你觉得齐不齐」。
5. `render` 把状态按固定顺序拼成带标签的文本行，事实按键排序后输出，因此同一份状态两次渲染逐字相同。它只是「给模型看的一种视图」，状态本体始终是那份字典；把视图和本体分开，才干得成逐项核对。
6. `replay` 从初始状态开始把事件串行重放一遍。因为每个事件都是确定性的、且 `apply_event` 不读外部状态，同一串事件必然还原出同一份状态——`main` 里「重放可还原同一状态」和「渲染顺序可复现」两条断言验的就是这件事。
7. `main` 先构造了一条七步的事件序列（含一次对「工单总数」的覆盖更新），再分组断言：字段与目标约束是否稳、事实是否取到最新值 318、增量更新是否不扰动别处、完成与回答是否按语义出列、渲染是否稳定、被破坏的状态能否被校验抓出。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出。

有一处如实说明：这里的「事件」是手工构造的字典，真实系统里它们来自每一轮的工具结果、用户消息与模型决策；状态也只放在内存里，没有写文件。它演示的是字段固定、增量更新、可校验、可重放这四件事的形状，不是任何具体框架的状态实现。

## 踩坑与边界

- **把状态交给模型重写**：现象是每轮让模型「根据最新情况更新一下状态摘要」，几轮之后约束变软、数字变模糊、目标被悄悄换词 → 原因是把搬运工作交给了会自由改写的那一方 → 由代码按事件类型做确定性增量更新，模型只产出决策，状态不经过它重写。
- **开出「备注」万能字段**：现象是没几轮所有信息都堆进备注，结构化名存实亡，又开始出现互相矛盾的两句话 → 原因是留了个不受类型约束的口袋 → 新增字段要能说清「它凭什么需要被单独校验」，否则作为轨迹外置，按标识取回。
- **完成后两栏都挂着**：现象是同一件事同时出现在已完成和待办里，模型反复做已经做过的动作 → 原因是把「记一笔完成」和「从待办移除」分成了两次不受约束的写入 → 用一个带语义的 `done` 事件把两步绑成一次原子更新，像演示代码那样。
- **约束跟着摘要一起被压**：现象是「只统计近一年」被改写成「时间范围大致是近期」，边界一松，后面全歪 → 原因是没区分可压缩历史与不可压缩项 → 约束、当前目标、不可变标识划为常驻不改写，压之前先声明保护清单，见 [写选压隔四类操作与不可压缩项](./k139-context-ops.md)。
- **空槽位被整栏删掉**：现象是状态里找不到「待答问题」这一栏，读的人分不清是「没有问题」还是「这一栏没了」 → 原因是压缩时顺手扔掉了空字段 → 字段固定齐全、空就是空，校验里把「缺字段」当成错误报出来。

还要守住一条边界：结构化状态摘要不等于「上下文管理的全部」。它只负责把「当前进展」装成可查的样子，管不了每轮该往里塞多少检索片段、也管不了长历史该不该外置；前者是 [上下文预算表](./k041-context-budget.md) 和 [上下文膨胀与中间遗失](./k049-context-bloat.md) 要处理的量的问题，后者靠分层与按需取回。把状态做扎实，好处是「记岔了能查」；但真要控制成本与注意力，还得配合预算与排布一起做。另一头也要分清：状态是「这一刻的快照」，轨迹是「怎么走到这一刻的过程」，两者都该留，但别指望用一份状态对象替代完整轨迹，回放与审计仍需事件序列本身。

## 三句话小结

结构化状态摘要，是把 Agent 的当前进展从一段会被反复改写的自然语言中拿出来，装成字段固定、类型明确、可逐项核对的状态对象。

关键做法是先定死一张短槽位表、由代码按事件类型做增量更新、每轮用校验守住约束与数字、渲染只当视图、并让事件序列能重放出同一份状态。

当任务只有一两轮、状态简单到一眼能看完，或信息根本不需要跨轮被单独校验时，不必上这套结构；但只要循环一长、约束一多、出错要能定位到某一轮，它就比「压成一段话」稳得多。

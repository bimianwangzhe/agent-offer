# 状态机与图编排：用节点和边代替一堆 if

## 场景提问

你的循环一开始只有三个判断，挺清楚。需求一来就加了「高优先级先复审」，再加「记账和通知一起做」，又加「材料不齐退回去重填」，if 越堆越多，改一处要顺带改三处。更麻烦的是某天有一类输入进去后怎么也出不来，日志刷个不停，你翻遍代码也说不清到底是哪一步绕回了自己。判断明明都写对了，为什么流程还是收不住？

## 破误解

**不是判断写错了，是控制流散落在一堆 if 里，没法一眼看出「能不能停」**。

先把两个词说明白。状态机（state machine，把流程拆成有限个状态、以及状态之间允许怎样跃迁的一套规则；白话讲像地铁线路图，站点是状态，线路是允许的去向）关心的是「此刻在哪、下一步能去哪」。图编排（graph orchestration，用节点和边描述流程，节点是一次动作，边是允许的去向）则把这套规则画成一张能检查的图：分支是一条按条件选的边，并行是从一个节点同时伸出几条边，回退是一条指回旧节点的边，终点是一个没有出边的节点。终止性（无论输入怎样，都能在有限步内走到终点的性质）在这张图上是可以静态检查的——只要数一数回退边有没有额度、总步数有没有上限、有没有节点集合永远绕不出去。而散在代码各处的 if，做不了这种检查，只能靠跑一遍碰运气。

## 生活类比

把流程想成「办证大厅」。你抽号进场，手里那张号就是状态，窗口上方挂的导流图就是边：

- **分流台**看你办的是不是加急，加急去复审窗口、普通直接去办理窗口，这是分支；
- **办理窗口**开完单，同时把一联给记账台、一联给通知台，这是并行；
- 两个台都盖完章，材料才汇总到同一个复核窗口，这是汇聚，白话讲就是「人齐了才开饭」；
- **复核窗口**发现材料不全，把号退回办理窗口重做，这是回退；
- **出口**盖完章你就走了，没有再指向别的窗口，这是结束。

对应关系要讲透：导流图贴在墙上，谁都能一眼看出「有没有一个圈能让人永远走不出去」——比如「复核退回办理、办理又退回复核」就是个死圈。大厅的解决办法很朴素：给「退回」发一张限量的返工单，用完就必须去出口，另外大厅到点清场，谁也不能无限待着。这两条正是图编排里保证终止性的两件东西：回退额度与总步数上限。把规则画在墙上，比让每个窗口的办事员各自记一句「什么情况该往哪送」可靠得多；前者能整体检查，后者只能出事后再一处一处对。

第一张图把节点分成五类，第二张图是走一遍的顺序，第三张图是两种写法的代价。特别留意第二张图里「汇聚复核」只有一个位置：并行展开出的两条分支最终都汇到它，而不是各自再造一个复核，否则同一份材料会被核两遍。这看着是小细节，落到代码里就是最常踩的坑。

## 层层追问

:::ask 那如果并行分支各自指向不同的后续节点，还能叫汇聚吗？
不能，那种情况更接近「分叉后各走各的」，得给每条分支单独设终点，或者显式加一个「等齐」节点。真正的汇聚要求一个前提：所有并行分支都结束后才触发一次后续动作。实现上通常有两种做法，一是计数屏障（barrier，白话讲：来一个记一个，凑齐才放行），二是让并行分支共享同一个出边目标、由引擎统一排一次队。代码里用的就是第二种：并行节点展开后，把所有分支都访问一遍，但只把共同的汇聚目标排进队列一次。这样就躲开了「两个分支各排一个复核」的重复。追问到这里可以看到，图编排的价值不只在画得好看，而是把「并行怎么合拢」这种容易漏的规则，变成引擎里一处统一处理的逻辑。
:::

:::ask 那如果业务说「返工次数不设限，直到合格为止」，图还能保证停吗？
不能，而且这时候该反过来质疑需求。只要存在一条可以不带额度反复走的回退边，图上就有一个环，终止性就没法静态保证。可行的办法是把「无限返工」翻译成可判定的规则：给回退边一个额度，额度用尽强制走向结束或转人工；同时给整张图一个总步数上限，作为第二道兜底。代码里演示的正是这个翻译过程——状态里「需返工」一直为真，引擎仍靠 `max_rework` 与 `max_steps` 把流程收住。于是追到第二层会得到一个很实用的判断：凡是「直到……为止」这类说法，都要先问一句「谁来保证它真的会到」，答不上来就得配额度与上限。这跟[框架六大件](./k075-framework-six.md)里「循环」那件讲的是同一件事，只是这里把循环摊成了一张可检查的图。
:::

## 可运行代码并逐行解释

下面用标准库搭一张小图，分支、并行、汇聚、回退、结束都在里面，复制即可运行。

```python
"""用节点与边表达分支、并行、回退，并验证图一定能停下来。"""


def build_graph():
    """每条记录: 节点 -> (类型, 后继)。后继可以是字符串、列表或判定函数。"""
    return {
        "接收": ("分支", lambda s: "复审" if s["优先级"] == "高" else "执行"),
        "复审": ("跳转", "执行"),
        "执行": ("并行", ["记账", "通知"]),
        "记账": ("汇聚", "汇总"),
        "通知": ("汇聚", "汇总"),
        "汇总": ("分支", lambda s: "执行" if s["需返工"] else "结束"),
        "结束": ("停止", None),
    }


def walk(graph, start, state, max_steps=30, max_rework=1):
    """按图走节点；回退边受额度约束，步数受上限约束，两者共同保证终止性。"""
    pending = [start]
    visited = []
    steps = 0
    rework_used = 0
    while pending and steps < max_steps:
        steps += 1
        node = pending.pop(0)
        if node == "结束":
            visited.append(node)
            break
        visited.append(node)
        kind, payload = graph[node]
        target = payload(state) if callable(payload) else payload

        if node == "汇总" and target == "执行":
            # 这是一条回退边，额度耗尽就强制走向结束
            if rework_used >= max_rework:
                target = "结束"
            else:
                rework_used += 1

        if kind == "并行":
            join_target = None
            for child in target:
                visited.append(child)
                _, child_payload = graph[child]
                join_target = child_payload(state) if callable(child_payload) else child_payload
            if join_target is not None:
                pending.append(join_target)
        elif target is not None:
            pending.append(target)
    return visited, steps, state


def main():
    checks = []

    def ok(cond, name):
        assert cond, name
        checks.append(name)

    graph = build_graph()

    s1 = {"优先级": "高", "需返工": True}
    v1, steps1, _ = walk(graph, "接收", s1)
    ok("复审" in v1, "高优先级走了分支到复审")
    ok("记账" in v1 and "通知" in v1, "并行两节点都被访问")
    ok(v1.count("执行") == 2, "回退让执行被重跑一次")
    ok(v1[-1] == "结束", "最终停在结束节点")

    s2 = {"优先级": "普通", "需返工": False}
    v2, _, _ = walk(graph, "接收", s2)
    ok("复审" not in v2, "普通优先级跳过复审")
    ok("结束" in v2, "普通路径也到达结束")

    s3 = {"优先级": "高", "需返工": True}
    _, steps3, _ = walk(graph, "接收", s3, max_steps=30)
    ok(steps3 <= 30, "状态一直要求返工，仍被回退额度与步数上限收住")

    print(f"通过 {len(checks)}/{len(checks)} 项")
    for n in checks:
        print("  -", n)


if __name__ == "__main__":
    main()
```

1. `build_graph` 把整张流程写成一张字典：键是节点名，值是「类型 + 后继」。后继可以是字符串，可以是并行列表，也可以是接收状态、返回去向的判定函数——分支条件因此不再是散落的 if，而是图里一条可查的记录。
2. `walk` 里的 `pending` 是待处理节点队列，`visited` 是走过痕迹，`steps` 是已用步数。三者和 `state` 分开存，正是为了随时能回答「现在走到哪、还能走几步」。
3. `target = payload(state) if callable(payload) else payload` 这一行统一了两种后继：判定函数要喂当前状态才得出分支去向，固定字符串则直接取用。引擎不必知道每种分支的业务含义。
4. `if node == "汇总" and target == "执行"` 是回退边的约束点：只放行 `max_rework` 次，超了就把去向往「结束」改。把这条规则集中写在引擎里，比在业务分支里到处写「别忘了别死循环」稳妥得多。
5. `if kind == "并行"` 这一段实现汇聚：逐个访问并行子节点，读取它们共同的出边目标，最后只 `append` 一次。这就是前面追问里说的「只排一个复核」，避免重复执行后续动作。
6. `elif target is not None: pending.append(target)` 处理分支、跳转、汇聚这三类单出边节点；「结束」在循环开头就被单独拦下并 `break`，所以它不需要出边。
7. `while pending and steps < max_steps` 是第二道兜底：即便回退额度被改坏，总步数上限仍会让流程停下。两道约束叠起来，终止性才不依赖某一处代码写得对。
8. `main` 里跑了三条构造路径：高优先级且需返工、普通优先级不返工、以及状态一直要求返工。断言分别核对分支是否走对、并行两节点是否都被访问、执行是否被重跑、终点是否到达，最后打印 `通过 7/7 项`。这些都是可复现的构造场景，不是任何跑分结论。

读完代码再看第一张图会有新体会：所谓「状态机」，其实没有玄乎的状态对象，就是 `pending` 里下一个待处理节点加上 `state` 里那几个字段。图编排真正多给你的，是一张能整体检查的说明书——哪些节点有出边、哪条边会绕回去、绕回去有没有额度，都能在跑之前数清楚。

## 踩坑与边界

- **并行分支各自排队**：现象 → 复核动作被执行了两遍，材料核重了 → 原因 → 每个并行子节点都把自己的汇聚目标排进队列，没做合拢 → 怎么改 → 让并行分支共享一个汇聚目标，由引擎统一排一次，或用计数屏障凑齐再放行。
- **回退边没有额度**：现象 → 某类输入进去后日志刷不停，永远出不来 → 原因 → 「复核退回办理、办理又退回复核」形成环，图上没有东西能打断它 → 怎么改 → 给回退边配次数上限，用尽强制走向结束或转人工，并另加总步数上限兜底。
- **把业务条件写进引擎**：现象 → 每加一种优先级都要改 `walk` 函数 → 原因 → 分支判定被硬编码在遍历逻辑里 → 怎么改 → 判定函数放在图定义里，引擎只负责「调用它、按结果走边」，业务变化只改图不改引擎。
- **状态与痕迹混在一起**：现象 → 想查「这轮走过哪些节点」，得从业务字段里翻 → 原因 → `visited` 和业务 `state` 没分开 → 怎么改 → 轨迹单独成列，业务状态只保留会影响后续选择的字段，两边各自可查。
- **图能画但没人验**：现象 → 图上看着有终点，实际某条分支永远到不了 → 原因 → 只画不测，缺一组针对各路径的断言 → 怎么改 → 像代码里那样，为每条典型路径写一条「终点是否到达」的断言，改图就重跑。

边界也得说清：图编排不是越多节点越好。流程只有两三步、路径完全固定的时候，直接顺序写反而更省事，画成图只是多一层间接。它真正划算的地方是分支多、有并行、有回退，或者需要对「能不能停」给出确定答案的时候。另外，图描述的是「允许怎么走」，不负责「这一步具体做什么」——节点的动作仍然要你写，动作失败如何恢复、状态怎么落盘，属于[框架选型与自研编排的取舍](./k083-build-vs-framework.md)里讨论的控制权问题。把这两层分开，改动作时不会动到图，改流程时也不会动到动作实现。

## 三句话小结

状态机与图编排，是把流程写成有限个节点和允许的去向，让分支、并行、回退都变成可检查的边。
关键做法是给回退边配额、给总步数设上限，并为每条典型路径写一条「终点是否到达」的断言。
当路径固定、只有两三步骤时，不必画图，顺序写清楚比多一层图更直接。

# Badcase 回收闭环与分级评测

## 场景提问

线上又出事了：有用户反映 Agent（智能体，能自己拆解任务、调用工具、循环推进的程序）把别人的地址改了。你排查完、改好提示词，顺手把那句原话贴进一张表格里，标了个「已处理」。两周后同样的毛病换了个说法又冒出来，你翻表格才发现，那张表里躺着几百条抱怨，有的重复、有的只是措辞不好看、有的其实根本没复现出来，没有一条能被自动重跑，也没人记得哪条是改完验过的。明明每次都在「记问题」，为什么问题还是一遍遍回来？

## 破误解

**不是团队不重视反馈，是把「记下一条抱怨」当成了「解决一类问题」，中间缺了去重、定级、写成可判用例、进门禁、再观察这一整条能查状态的循环。**

先把几个词说清。Badcase（坏例，表现不理想、需要回收进评测集的真实请求）不是一句用户吐槽，而是一条带输入、带过程、带判定规则的样本。评测集是一批带标准答案或判定规则的用例；门禁是发布前必须全过的一组固定检查；断言（assertion，一条能自动判真假的期望性质）则是「这条用例到底算不算过」的判据。分级评测指的是：按代价与影响面把评测分成几档，改动风险不同就跑不同范围，而不是每次都把全部用例从头跑一遍。回收闭环指的则是：线上先留下能复现的记录，把失败筛出来，同一根因归并，按影响面定级，写成带断言的用例，进到门禁里被重跑，发布后再看这类问题有没有复发，每一步的状态都能查。少了任何一环，反馈就只是一张越堆越长的表，而不是一道下次能自动挡住问题的题。这里最容易被低估的是「可判」两个字：一句「答得不好」没法进门禁，因为它没有判据；只有写成「不得出现越权动作」「任务必须办成且过程不得重试」这样的性质，机器才能在每次发布前替你判一遍。至于落差从哪来、为什么光补题补不完，是 [离线好、线上差的成因](./k092-offline-online-gap.md) 里讲的事，本篇只管把已经暴露出来的失败收干净、用起来。

## 生活类比

把它想成医院的分诊台加病历归档。病人涌进来，分诊护士不会让所有人排同一条队：胸口剧痛、血压掉的立刻推进抢救室，骨折的去处置室，只是有点咳嗽的先坐着观察。这不是嫌麻烦，是让最要紧的事最先占用最有限的资源。对应到系统里，越权、资损这类一发生就伤到人的，是抢救室那一档，必须马上进最小集并挡住发布；任务没办成、答非所问，是处置室那一档，随每次发布重跑；措辞生硬、回复偏慢，是观察区，先攒着，攒够一批再决定要不要收编。

再看后面几步，比喻同样对得上。分诊之后要写病历：不能只写「不舒服」，得写清症状、当时做了什么处置、复查时查哪几项，否则下一个医生接手还是两眼一抹黑——这就是回收时要带上输入原文、轨迹和断言，缺一样都没法复现。医院不会把同一场流感里每个病人的同一种症状都立成一种新病，而是归并成一类、记下这周来了多少例——这就是去重与聚类，避免同一根因把评测集刷屏。疑难病例会被整理成教材，之后轮转的医生都要重考这些典型题，考的是「这类情况该怎么处理」而不是背下某一句原话——这就是把代表样本写成用例、再用性质断言去判，而不是把用户那句话抄进去当标准答案。最后是回访：治完不算完，得确认没复发、也没把别的病带出来——对应发布后继续盯这类问题有没有再出现、旧用例有没有被改坏。这个比喻还点破一处最贵的问题：最怕的不是病人多，是病历只记在护士的便签上，谁也没归档、谁也没复查，于是同一个病因每来一次都当成新病从头查一遍。放到系统里，就是「状态不可查」，样本躺在表里没推进到门禁，闭环看着有、其实断在半路。

## 自绘示意图

:::figure Badcase 回收闭环
@cycle
线上留全轨迹|筛出并去重|按影响面分档|写成带断言用例|进门禁再观察
:::

这五个节点画成环，是因为它不是一次性的清理。线上先留下能复现的记录，才谈得上筛出失败请求；同一根因归并之后定级，才不会让一条冷门抱怨占掉最贵的位置；写成带断言的用例，才能被门禁自动重跑；发布后再观察，才知道这类问题是不是真的断根。少一环，下次翻车还是从头猜。

:::figure 按影响面分成三档
@stack
阻断档::越权、资损、数据写坏，立刻进最小集并拦住发布
回归档::任务没办成、答非所问，进常规集随每次发布重跑
观察档::措辞、格式、偏慢，先攒着，攒够一批再评是否收编
:::

三档的分法不是行业统计，而是一套可以自己改的示例规则，重点在「按影响面」而不是「按发现顺序」。最要紧的一档要小、要快、要每次都跑，正因为小，才跑得起；最轻的一档先不急着收编，否则评测集会被大量无关痛痒的样本撑胖，真正要命的题反而被摊薄，比例怎么搭配才不自欺，可以对照 [用例配比](./k087-case-mix.md)。

:::figure 两种回收做法的差别
@compare
原话直接贴进表::无法自动判分|同一根因反复收|躺着没人跟进
去重分档加断言::能进门禁重跑|比例不被刷偏|状态可查到修复
:::

左边是「记下一条抱怨」，看着也在积累，其实三条都不成立：没有判据就判不了分，不去重就被同类刷屏，没有状态就没人跟到修复。右边是把每一条失败都当成一道待入库的题来对待，三格分别对应可判、可代表性、可追踪。

## 层层追问

:::ask 那如果线上一天冒出成千上万条失败，是不是全都收进评测集？
:::

不能全收，全收反而会把闭环弄坏，理由有三。第一是代表性：绝大多数失败是同一个根因换了个编号、换了个说法，逐条收进去等于让这一类在评测集里占掉绝大多数席位，别的问题被摊薄，评测分数看着还行、其实只测了那一类，这和 [用例配比](./k087-case-mix.md) 里讲的比例失衡是同一回事；所以要先规范化（把编号、空白这类易变部分抹平）再取指纹归并，同一根因只留代表，并记下它出现几次，次数本身就是排优先级的依据。第二是代价：用例越多，每次重跑越慢越贵，尤其要复现多轮、工具调用和下游状态，全量天天跑并不现实，怎么按成功任务核算这笔账可对照 [按成功任务核算成本](./k096-metrics-cost.md)，把各类开销一并框住可看 [四类预算](./k103-four-budgets.md) 与 [成本检查清单](./k116-cost-checklist.md)。第三是噪声：偶发的一次超时、一次网络抖动，不该被固化成一条永久题目，否则评测集会慢慢攒出一堆谁也修不动的历史包袱。所以更实际的做法是：先去重聚类，再按影响面分档，只让有代表性的进集，其余进观察池攒着；分级评测正是为这个服务的——小改动只跑最要紧那一档，常规发布加跑中间那档，定期全检才把三档跑满，改动风险与所花代价相称。分层的思路与 [三层评测](./k085-three-level-eval.md) 一致，回收时把档位一并记下，后面选跑范围才有依据。

:::ask 那如果一条 Badcase 收进来之后，团队照着它改提示，改完这条当然就过了，怎么保证不是又背了题？
:::

这是闭环里最容易自欺的一问，也是「记了却没变好」最常见的根源。要把三件事分开做。第一，回收来的样本要分卷：同一根因的所有说法整类进同一卷，一部分用来改、另一部分只用来终检，两卷互不重叠；要是用同一批题既调参又打分，就又回到数据泄漏那条老路上，分卷与留白的做法见 [评测数据集](./k086-eval-dataset.md)。第二，判据要写性质而不是抄原话：用户那句「订单 8821 怎么被改了地址」不该成为标准答案，正确写法是「不得出现越权动作」这类断言，换一批编号、换一种措辞仍然判得出对错，怎么写可对照 [属性断言](./k088-property-assertion.md)；还要允许检查过程而不只是终稿，比如「任务必须办成且过程不得反复重试」，见 [轨迹评测](./k089-trajectory-eval.md)。第三，泛化与回归要一起看：留几条同根因、不同说法的变体当验卷，确认修的是一类问题而不是一条题；同时用 [回归门禁与基线](./k091-regression-gate.md) 盯住旧题有没有被这次改动带坏，用 [大模型评判](./k090-llm-judge.md) 时也要留意评委偏爱长答案这类偏差，别让「看起来完整」混过判定。除了这三点，还有个常被漏掉的前提：整条链要有可查的状态——已发现、已归因、已去重、已分级、已进集、已过门禁，哪一步卡住一眼能查到，别让样本停在「已处理」三个字上。把「这条过了」升级成「这类问题下次会被自动挡住且不再复发」，闭环才算真的闭上；而这一切的起点，仍是线上留全了 [轨迹字段](./k094-trace-fields.md) 与 [结构化日志](./k095-structured-log.md)，没有可复现的记录，分卷、断言、门禁都无从谈起。

## 可运行代码与逐行解释

下面这段只用 Python 标准库，用本地构造的一批失败请求，完整演示「去重聚类—按影响面分档—写成带断言用例—分卷—按改动风险选跑范围—状态推进到门禁—同根因新说法命中已收用例」。指纹用哈希（hash，把任意内容映射成一段定长短码的算法）实现，全程不联网、不要账号、不装任何第三方包，复制到装有 Python 的机器上直接运行即可。

```python
import hashlib
import re
from collections import Counter


GRADE_BY_CAUSE = {
    "越权": "阻断档",
    "资损": "阻断档",
    "答错": "回归档",
    "丢状态": "回归档",
    "绕远路": "回归档",
    "格式": "观察档",
    "偏慢": "观察档",
}

ASSERTION_BY_GRADE = {
    "阻断档": "不得出现越权动作",
    "回归档": "任务必须办成且过程无重试",
    "观察档": "格式与体感指标不劣于基线",
}

GATE_SCOPE = {
    "小改动": ["阻断档"],
    "常规发布": ["阻断档", "回归档"],
    "定期全检": ["阻断档", "回归档", "观察档"],
}


def normalize(text):
    """把易变的编号与空白抹平，让同一根因的说法归并到一处。"""
    text = re.sub(r"\d+", "#", text)
    return re.sub(r"\s+", "", text).strip()


def fingerprint(text):
    """对规范化后的说法取短哈希，作为去重与身份的稳定标识。"""
    return hashlib.sha256(normalize(text).encode("utf-8")).hexdigest()[:8]


def make_failures():
    """本地构造：一批线上失败请求，含重复根因与不同影响面。"""
    raw = [
        ("查订单 8821 没权限还改了地址", "越权"),
        ("查订单 9073 没权限还改了地址", "越权"),
        ("查订单 6112 没权限还改了地址", "越权"),
        ("问退换 43 答成了改地址", "答错"),
        ("问退换 87 答成了改地址", "答错"),
        ("改地址 15 多轮后忘了上一轮", "丢状态"),
        ("开发票 30 重试三次才回", "绕远路"),
        ("问退换 5 回复少了个句号", "格式"),
        ("问退换 6 回复少了个句号", "格式"),
        ("催退款 12 比平时慢一点", "偏慢"),
    ]
    return [
        {"id": "fail-%03d" % i, "text": text, "cause": cause}
        for i, (text, cause) in enumerate(raw)
    ]


def grade(case):
    """按影响面分档：越权资损最重，办错事次之，体感问题先观察。"""
    return GRADE_BY_CAUSE[case["cause"]]


def dedup(cases):
    """同一根因只留一个代表，并记下它重复出现几次。"""
    groups = {}
    order = []
    for c in cases:
        fp = fingerprint(c["text"])
        if fp not in groups:
            groups[fp] = {"case": c, "count": 0}
            order.append(fp)
        groups[fp]["count"] += 1
    reps = [groups[fp]["case"] for fp in order]
    return reps, groups


def to_case(case):
    """把一条失败写成用例：输入、期望性质、指纹、档位缺一不可。"""
    return {
        "id": case["id"],
        "input": case["text"],
        "assertion": ASSERTION_BY_GRADE[grade(case)],
        "fp": fingerprint(c["text"]),
        "grade": grade(case),
    }


def split_volumes(cases):
    """按序号对半分卷：改卷用来调，验卷只用来终检，互不重叠。"""
    edit = [c for i, c in enumerate(cases) if i % 2 == 0]
    verify = [c for i, c in enumerate(cases) if i % 2 == 1]
    return edit, verify


def run_gate(bank, risk):
    """按改动风险选跑哪一档，返回本次实际执行的用例。"""
    scopes = GATE_SCOPE[risk]
    return [c for c in bank if c["grade"] in scopes]


class BadcaseLedger:
    """记录每条回收样本的状态推进，避免样本躺在表里没人跟。"""

    STEPS = ("已发现", "已归因", "已去重", "已分级", "已进集", "已过门禁")

    def __init__(self, reps):
        self.state = {c["id"]: 0 for c in reps}

    def advance(self, case_id):
        if self.state[case_id] < len(self.STEPS) - 1:
            self.state[case_id] += 1

    def done(self, case_id):
        return self.state[case_id] == len(self.STEPS) - 1

    def missing(self):
        return [cid for cid in self.state if not self.done(cid)]


def main():
    failures = make_failures()
    reps, groups = dedup(failures)
    grades = Counter(grade(c) for c in reps)
    bank = [to_case(c) for c in reps]
    edit, verify = split_volumes(bank)
    edit_ids = {c["id"] for c in edit}
    verify_ids = {c["id"] for c in verify}
    ledger = BadcaseLedger(reps)
    missing_before = ledger.missing()
    for c in reps:
        for _ in range(len(BadcaseLedger.STEPS) - 1):
            ledger.advance(c["id"])

    variant = "查订单 9999 没权限还改了地址"
    small = run_gate(bank, "小改动")
    full = run_gate(bank, "定期全检")

    checks = [
        ("十条失败归并成六类", len(reps) == 6),
        ("去重统计合计仍是十条", sum(g["count"] for g in groups.values()) == len(failures)),
        ("重复最多的那一类出现三次", max(g["count"] for g in groups.values()) == 3),
        ("分级恰好覆盖三档", set(grades) == {"阻断档", "回归档", "观察档"}),
        ("越权类落在阻断档", grades["阻断档"] == 1),
        ("办错事类落在回归档", grades["回归档"] == 3),
        ("体感类落在观察档", grades["观察档"] == 2),
        ("每条用例都带判定规则", all(c["assertion"] for c in bank)),
        ("改卷与验卷互不重叠", not (edit_ids & verify_ids)),
        ("两卷合起来覆盖全部代表", len(edit) + len(verify) == len(reps)),
        ("两卷都不为空", len(edit) > 0 and len(verify) > 0),
        ("小改动只跑阻断档", len(small) == 1),
        ("常规发布加跑回归档", len(run_gate(bank, "常规发布")) == 4),
        ("定期全检跑满六条", len(full) == 6),
        ("小改动范围是定期全检的子集", {c["id"] for c in small} <= {c["id"] for c in full}),
        ("未闭环时能被查出来", len(missing_before) == len(reps)),
        ("闭环后每条推进到终点", all(ledger.done(c["id"]) for c in reps)),
        ("同根因新说法命中已收用例", fingerprint(variant) in {c["fp"] for c in bank}),
    ]

    passed = sum(1 for _, good in checks if good)
    for name, good in checks:
        print(("通过 " if good else "失败 ") + name)
    print("通过 %d/%d 项" % (passed, len(checks)))
    assert passed == len(checks), "存在未通过项"


if __name__ == '__main__':
    main()
```

1. 开头三张映射表把规则写死：`GRADE_BY_CAUSE` 决定哪种根因落哪一档，`ASSERTION_BY_GRADE` 决定每档用例写什么断言，`GATE_SCOPE` 决定哪种改动风险跑哪几档。把规则显式列出来，是为了让「分级」不是一句口号，而是可查、可改的配置。
2. `normalize` 用 `re.sub` 把数字换成 `#`、把空白去掉，于是「查订单 8821 没权限还改了地址」和「查订单 9999 没权限还改了地址」会变成同一串；`fingerprint` 再用 `hashlib.sha256` 取前八位当稳定标识。这就是去重能成立的机理——比的是抹平易变部分之后的形状，不是原话一字不差。
3. `make_failures` 本地构造十条失败，故意让「越权」出现三次、「答错」与「格式」各两次，好让「同类刷屏」这件事稳定发生、结果可手工推算，不靠碰运气。
4. `dedup` 按指纹分组，每组只留第一个代表，同时记下 `count`。分组用 `order` 列表保住首次出现的顺序，因此后续分卷、统计都是确定的。十条最终归并成六类。
5. `grade` 查表分档，`to_case` 把代表写成用例：输入原文、期望性质、指纹、档位四样都在，缺一样就退回「一句抱怨」而不是「一道题」。`split_volumes` 按序号对半分成改卷与验卷，两卷互不重叠；真实系统可按指纹分卷以避开人为偏差，这里用序号纯粹是为了每卷三条、可手算。
6. `run_gate` 按风险查 `GATE_SCOPE` 挑用例：小改动只跑阻断档那一条，常规发布加跑回归档共四条，定期全检跑满六条。`BadcaseLedger` 用 `STEPS` 定义六步状态，`missing` 把没走到终点的样本列出来，模拟「卡在哪一步一眼可查」。
7. `main` 先做去重与分档统计，再建用例库、分卷、记录未闭环清单，然后把每条代表一路推进到「已过门禁」，最后构造一条同根因的新说法。十八项断言逐条验证：归并条数、重复计数、三档分布、每条用例都有判据、两卷不重叠且都非空、三档门禁跑的范围逐级包含、闭环前后状态可查、以及新说法的指纹确实命中已收用例。结尾 `assert` 保证任何一条性质被破坏都会以非零状态退出，打印的「通过 N/N 项」便于一眼看出是全过还是有漏。

有一处要如实说明：这里用本地构造的十句话代替真实线上流量、用一张查表代替真实分级委员会、用「推进状态」代替真实工单流转，全是为了让整条链路不需要联网、账号或第三方包就能独立跑通，且每一步结果可手工推算。它演示的是去重、分档、分卷、分级跑门禁与状态可查之间的顺序关系，不是任何真实系统的统计结果，也不是对某个具体平台的实现。

## 踩坑与边界

- **原话直接贴进表格**：现象是表里堆了几百条、没有一条能自动重跑 → 原因是只记了吐槽，没写判定规则 → 每条都补上输入、指纹与一条可判真假的断言，参考 [属性断言](./k088-property-assertion.md)。
- **同一根因反复收**：现象是评测集被一类问题占满，别的问题被摊薄，分数虚高 → 原因是逐条入库、没归并 → 先规范化取指纹，同根因只留代表并记出现次数，比例搭配对照 [用例配比](./k087-case-mix.md)。
- **拿收进来的题边改边验**：现象是改完这条就过、换个说法又翻车 → 原因是同一批样本既当练习题又当考卷，发生了数据泄漏 → 整类分卷、改卷与验卷互不重叠，见 [评测数据集](./k086-eval-dataset.md)。
- **所有用例每次全跑**：现象是发布前等人跑完全量，慢到干脆跳过检查 → 原因是没按改动风险分档 → 最要紧的一档小而快、每次必跑，其余按发布与定期两类分别跑，成本口径见 [按成功任务核算成本](./k096-metrics-cost.md)。
- **状态停在「已处理」**：现象是没人说得清哪条进了门禁、哪条其实没验 → 原因是闭环没有可查的状态 → 把发现、归因、去重、分级、进集、过门禁六步都记下来，卡住的一眼能查，发布后还要看是否复发，配合 [回归门禁与基线](./k091-regression-gate.md)。

还要分清两件容易混的事：回收与评测。回收是把线上失败变成可用样本，评测是拿这些样本判一版改动能不能放行；前者做不好，后者就永远在测一批偏了题的考卷。另外，最要紧那一档应该触发「不放行」而不只是「记一笔」，把改动先放在只观察不执行的位置看清差异、指标越线就退回，是 [影子模式、灰度与回滚](./k112-shadow-canary.md) 的做法；给线上目标预先写明可守护的线，可对照 [健康检查与服务等级目标](./k114-health-slo.md)。还有一句边界：分级规则不是越细越好，档位多到没人记得住、判据细到互相打架，反而会让闭环跑不动；够用、可查、能坚持，比漂亮更重要。

## 三句话小结

Badcase 回收闭环与分级评测，是把线上失败请求去重、按影响面分档、写成带断言的用例、再按改动风险选跑范围的一段可查状态的循环，让每次翻车都变成下次能自动挡住的一道题。

关键做法是先留全轨迹、同根因归并、三档分级、改卷与验卷分开、进门禁后继续观察是否复发，并把每一步状态记到可查。

当系统没有真实线上流量、或失败样本少到撑不起分档时，不必硬套这套闭环；但只要一次改动会改变对外行为，就不该让失败请求只躺在反馈表里。

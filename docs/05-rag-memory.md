# RAG 与记忆：从能召回到答得对

RAG 的 Demo 十分钟就能跑通，但「答得准」几乎全在 Demo 之外的细节里。面试里区分度最高的不是「你用了哪个向量库」，而是**「召回不准时你怎么定位问题」**。

## 完整链路与排查顺序

```
解析 → 切分 → 向量化 → 检索 → 重排 → 组装 → 生成 → 溯源校验
```

出问题时，按这个顺序二分定位，**不要一上来就换模型**：

| 症状 | 优先怀疑 | 验证方法 |
|---|---|---|
| 完全答非所问 | 解析 / 切分丢了内容 | 打印 chunk 原文，看关键段在不在 |
| 能沾边但漏要点 | top-k 太小 / 切太碎 | 提高 k、看被截断的 chunk |
| 答案里有原文没有的内容 | 生成没约束 / 没溯源 | 强制引用 + 引用命中校验 |
| 中文/表格类文档差 | 解析与切分策略 | 换按标题/语义切分，表格单独处理 |

> 一个实用习惯：**先建 50 条标注问题和标准答案**，再谈优化。没有评测集的调参都是玄学。

## 切分

- 别用固定字数硬切；按标题层级、段落、语义边界切
- 带 `overlap` 只是兜底，不是解法；切分丢失了结构，overlap 补不回来
- 每个 chunk 带元数据（来源、章节、时间、权限标签），后面做过滤和溯源全靠它
- 表格、代码、公式单独处理，别和普通正文混在一起

## 检索：混合 > 单一

| 方式 | 强项 | 弱项 |
|---|---|---|
| BM25 / 关键词 | 精确术语、编号、人名 | 同义改写 |
| 稠密向量 | 语义相近 | 专名、数字、稀有词 |
| **混合检索** | 两者互补 | 需要打分融合（RRF 等） |
| 交叉编码器重排 | 精排，提升明显 | 有延迟成本 |

常见组合：**混合检索召回 top-50 → 重排取 top-5 → 元数据过滤 → 组装**。

再加两个进阶动作：

- **Query 改写**：多轮对话里把「它后来怎么样了」补成完整查询
- **弃权逻辑**：召回分数都低于阈值时，明确说「资料里没有」，而不是硬编

## 溯源与幻觉兜底

让输出强制带引用，并做一次机械校验：**引用的 chunk 里是否真的包含答案的关键事实**。校验不过就重答或降级为「未找到」。这一步能把「看起来很像真的」的错误挡掉一大半。

## 三层记忆

记忆和 RAG 不是一回事：RAG 管外部知识，记忆管**这个用户 / 这次任务**的状态。

| 层 | 内容 | 生命周期 | 淘汰 |
|---|---|---|---|
| 工作记忆 | 当前这一步的草稿、中间结果 | 单步 / 单轮 | 用完即清 |
| 情景记忆 | 会话进展、已试过的方案 | 一次会话 | 摘要压缩 + TTL |
| 语义记忆 | 用户偏好、长期事实 | 跨会话 | 重要性打分 + 定期淘汰 |

长期记忆最容易出的事故是**无限膨胀**：什么都往里存，几个月后检索全是噪声。要设重要性打分、去重、TTL，以及「用户可删除」的入口。

## GraphRAG 值不值得上

值得，但只在**需要多跳关系推理**时（「A 公司收购的 B 部门，其负责人在哪篇文档里提过」）。代价是抽取流水线、实体消歧、图存储与社区摘要整套成本。普通「文档问答」不要上，先用混合检索把基线做扎实。

## 验收点

- 能说出一条「召回不准 → 定位 → 修好」的完整排查过程
- 能解释为什么要混合检索，以及重排放在哪一步
- 能回答「长期记忆怎么避免越存越脏」

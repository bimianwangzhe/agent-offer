# 工作 / 情景 / 语义三层记忆：按生命周期分开存

## 场景：会话一结束，该留的没了、该清的还在

你把「现在做到哪一步」和「用户长期偏好中文」一股脑塞进同一个字典，会话结束也没特意清理。第二天新会话一开，助手张口就是「已下载流水，正在整理账单」——那是昨天那单活的进度，今天的用户根本没提这件事；而真正该长期保留的偏好，因为被你归进「临时草稿」一起清空了，又得重新问一遍。你想查昨天那次「按日期排序失败」到底是怎么发生的，却发现当时那句话早被后来的状态覆盖掉了，只剩一个被改得面目全非的字段。存是都存了，但谁该活多久、谁能被改、会话结束还在不在，从一开始就没分开。

## 先破一个最常见的误解

**不是记性不好，是把生命周期完全不同的三类东西塞进了同一个抽屉。** 很多人以为「三层」是在按内容题材分类，比如事实一类、偏好一类、历史一类；其实真正的分界线是生命周期：这一层什么时候生成、存活多久、允许谁改、会话结束之后还在不在。工作层跟着当前这一次任务走，任务完了就该清台；情景层记的是「经历过什么」，一条条按时间追加，价值恰恰在于没被改写；语义层是从很多次经历里提炼出来的稳定事实，会更新但不会因为某一天结束就消失。三层的写入时机、更新规则、退出办法都不一样，塞进同一个存储、用同一套读写逻辑去伺候，必然出现「该清的没清、该留的没留、该留原样的被覆盖」。把差别定在生命周期上，后面所有设计才有依据：谁跨会话、谁按主题去重、谁只追加，都从这四个问题推出来。

## 用生活里的事打个比方：灶台、值班日志与菜谱本

想象一间小馆子的后厨，这里恰好有三样记录，跟三层一一对应。第一样是灶台：眼前这盘菜炒到哪一步、盐放了没、还差几分钟出锅，全写在厨师脑子里，这盘菜一端走，灶台就擦干净重来，这就是工作层，跟当前这一次任务同生共死。第二样是值班日志：今天哪桌退了菜、哪批货晚到半小时、哪台炉子中途熄过火，按时间一条条往下记，不因为后来发生了变化就把原来那行涂掉，这是情景层，它的用处是「事后能说清当时到底怎么了」。第三样是菜谱本：反复做过一阵子之后沉淀下来的结论，比如「这片的客人口味偏淡」「这道菜火候要到什么程度」，它会因为新的验证被修订，但绝不会因为今天打烊就作废，这是语义层。对应关系再对一遍：灶台只关心「现在」，日志只关心「发生过」，菜谱本只关心「一直成立」。为什么不能三样合一？把退菜记录写进菜谱本，菜谱就被一次偶发事件带偏了；把灶台进度留在菜谱本里，第二天照着做就是一盘错菜；把值班日志涂改成只有结论，出事时就再也查不回经过。三样各写各的、各有各的寿命，后厨才不乱。

## 画出来看

先看三层各自的活法，注意每行说的是「怎么存、活多久」，不是「装了什么题材的内容」。

:::figure 三层记忆各自的活法
@stack
工作层::当前任务的目标与已完成，会话结束即清空
情景层::经历过的事按时间戳追加，只留不改
语义层::提炼出的稳定事实，按主题更新并跨会话保留
:::

中间那行「只留不改」是情景层最容易被做错的地方：很多人一看条目多了就想压成摘要，一压，它就不再是情景层了，那是在往语义层提炼。两层可以并存，但不能拿一层的规则去管另一层。再看会话边界上谁能留下，这张对照能直接拿去检查自己的清理逻辑。

:::figure 会话结束时谁能留下
@compare
工作层::随会话清空|不跨会话|内容最活
语义层::跨会话保留|按主题更新|内容最稳
:::

两行只比了两个端点，情景层没进来，是因为它的答案不同：它既不随会话清空、也不按主题更新，而是原样按时间挂着，等着以后回放时用。把它硬塞进这张对照里，反而会让人误以为它必须在「清空」和「更新」之间二选一。

## 再往下追两层

:::ask 追问一
那情景层条目越攒越多，是不是也该压缩一下？
:::

可以压，但要先想清楚压完之后那份东西算什么。把一百条经历压成三句话，得到的是「从经历里提炼出的结论」，它该进语义层；原来那一百条情景记录不能删，因为它承担的是回放职责——某天要查「当时那步为什么走错」，靠的正是没被改写过的原始轨迹。所以正确做法是两份都在：原始轨迹按时间挂着不动，另起一份紧凑结论供日常取用。这也顺带解释了为什么层与层之间要有明确的「提炼」动作，而不是就地覆盖：一旦就地覆盖，就再也回答不了「这个结论是从哪几条经历得出的」。还要留意，把材料压短属于篇幅上的处理，和这里按生命周期分层是两件事，别拿一套规则去管另一套。

:::ask 追问二
那语义层能不能让模型每次自由重写一遍，省得自己维护？
:::

不行，这是最容易埋雷的地方。自由重写会把一次偶发事件抬成长期事实：用户某天随口说「这次先给我英文版」，模型一总结就写成「该用户偏好英文」，随后一路沿用。稳定事实之所以稳定，恰恰因为它的写入门槛高、改动有据可查。稳妥的做法是把两个动作拆开：先由规则判定这条够不够格进语义层，见[写入判定：什么时候该记](./k070-write-decision.md)；真要更新时保留版本、按来源权威裁决，见[冲突消解与版本](./k071-conflict-resolution.md)。语义层跨会话长期保留的实现方式，见[长期记忆与向量化存储](./k068-long-term.md)；而只跟最近几轮原文打交道的那一层，见[短期记忆与滑动窗口](./k067-short-term.md)。把它们分清楚，才知道哪次改动该走哪道手续。

## 一段能直接跑的代码

下面这段只用标准库，不联网、不装包、不需要账号，把三层分别用不同的数据结构和不同的更新方式写出来，结尾用断言验证会话边界上的行为。复制成 `.py` 直接运行会打印通过项。

```python
from dataclasses import dataclass, field


@dataclass
class WorkingMemory:
    """当前任务状态，会话结束即清空。"""
    goal: str = ""
    done: list = field(default_factory=list)


@dataclass
class EpisodicMemory:
    """经历过的事：一条条带时间戳的轨迹，只追加不覆盖。"""
    traces: list = field(default_factory=list)

    def add(self, stamp: int, text: str):
        self.traces.append((stamp, text))


@dataclass
class SemanticMemory:
    """提炼出的稳定事实，跨会话保留，按主题去重。"""
    facts: dict = field(default_factory=dict)

    def put(self, topic: str, fact: str):
        self.facts[topic] = fact   # 同一主题只留最新一条稳定事实


def end_session(working: WorkingMemory):
    working.goal = ""
    working.done.clear()


if __name__ == '__main__':
    working = WorkingMemory("整理本月账单", ["下载流水"])
    episodic = EpisodicMemory()
    episodic.add(1, "曾尝试按日期排序失败")
    semantic = SemanticMemory()
    semantic.put("输出格式", "偏好 PDF")
    semantic.put("输出格式", "偏好 PDF 且带页码")
    semantic.put("语言", "中文")

    # 断言 1：同一主题被更新而非堆成两条
    assert len(semantic.facts) == 2
    assert semantic.facts["输出格式"] == "偏好 PDF 且带页码"
    # 断言 2：情景层保留全部经历，不覆盖
    assert episodic.traces == [(1, "曾尝试按日期排序失败")]
    # 断言 3：会话结束后工作层清空，语义层不受影响
    end_session(working)
    assert working.goal == "" and working.done == []
    assert semantic.facts["语言"] == "中文"
    print("工作层已清空 / 情景层 1 条 / 语义层 2 条")
    print("通过 3/3 项")
```

1. 三个 `@dataclass`：用 `field(default_factory=...)` 给每层一个独立的空容器，避免多个实例共用同一个可变默认值这种隐蔽错误。三层虽然都叫记忆，但数据结构从一开始就不同：工作层是「目标 + 已完成列表」，情景层是「(时间, 正文) 元组列表」，语义层是「主题到事实的字典」。
2. `EpisodicMemory.add` 只有一行 `append`：这就是「只追加不覆盖」的落地。没有任何改写旧条目的入口，回放时看到的就是当时那条原文。
3. `SemanticMemory.put` 用 `self.facts[topic] = fact`：同一主题后来写了新值就直接替换，所以示例里「输出格式」写了两次，最后只剩一条、且是带页码的那条。这正是语义层该有的按主题更新，和情景层的只追加形成对照。
4. `end_session`：只清工作层的目标与已完成，故意一行都不碰情景层和语义层。把「会话结束该清什么」收拢到一个具名函数里，比散落在各处 `clear()` 好查得多。
5. 三条 `assert`：第一条验证按主题去重，第二条验证经历没被改写，第三条验证会话边界上跨层的东西安然无恙。断言写的都是生命周期性质，换一批数据依然成立。
6. 末尾 `print`：把三层清理后的条数打出来，肉眼确认这次跑到了结尾。

## 踩过的坑与边界

- **三层共用一个字典**：现象是改长期偏好时把当前任务进度也冲掉了 → 原因是没有按生命周期隔离，读写逻辑只有一套 → 改成三个独立容器，各自暴露自己的写入与更新方法。
- **把情景层压成摘要后删掉原文**：现象是出事想查当时那步怎么走错，只剩一句笼统结论 → 原因是拿语义层的更新规则去管情景层 → 原始轨迹只追加保留，另起一份紧凑结论供日常使用，两份并存。
- **语义层写成一大段自然语言**：现象是同一件事被反复复述、越攒越长，取回时还得再读一遍 → 原因是没有按主题收敛 → 改成「主题 → 一条稳定事实」的紧凑字段，同主题更新而非堆叠。
- **会话边界忘了清工作层**：现象是新会话一开就冒出上一单的进度 → 原因是工作层被当成永久存储 → 在会话结束的确定位置调用清理函数，并把这件事写成可回归的断言。
- **把长期事实每轮都塞进输入**：现象是输入额度被稳定事实占满，本轮真正要处理的材料反而没位置 → 原因是没区分「长期存着」和「本轮要带」 → 长期事实按需取回，取回条数还要单独限制，见[召回排序与相关性](./k072-memory-recall.md)。

边界也要讲：分三层不是为了显得整齐。如果系统只处理一轮就结束、既没有跨会话需求也不需要事后回放，那么叠三层只会凭空多出清理与同步的负担，一个装当前状态的结构就够用了。

## 三句话小结

三层记忆是按生命周期分开存的：工作层跟当前任务同生共死，情景层按时间只追加，语义层按主题保留可更新的稳定事实。
做法是为每层配独立容器与独立更新规则，把会话边界的清理收拢到一个具名动作里再写成断言。
系统只有一轮、既不跨会话也不需要事后回放时，不必硬叠三层，一个装当前状态的结构就够。
